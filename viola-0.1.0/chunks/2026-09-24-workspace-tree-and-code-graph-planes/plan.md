## Implementation Steps
1. **`scripts/release-check.sh` (new).** Use `#!/usr/bin/env bash` and `set -euo pipefail`. Check first that jq
   is present; if not, print `tool-missing: jq` and exit 1 (the `deny-probes.sh:10-13` precedent).
   - **One judging function** reads cargo `--message-format=json` lines on stdin. It selects
     `reason == "compiler-artifact"` records whose `executable` is non-null and collects each record's
     `target.name`.
     - It fails with `release-check: FAILED — no executable in the build output` when the set is empty. This is the
       non-vacuity guard (obs-plan §9 Gate commands, G2's `test -n` precedent).
     - It fails with `release-check: FAILED — test-only binary <name>` for any name other than `viola`.
     - Otherwise it prints `release-check: viola only`.
   - **Default mode** runs `cargo build --release --locked --bin viola --message-format=json`. Its stdout goes into
     the judging function, and cargo's stderr passes through. A cargo failure fails the script, under pipefail. The
     script honours an inherited `CARGO_TARGET_DIR`: cargo reads it natively, and the script never sets it.
   - **`--probe` mode** feeds synthetic lines to the same judging function. Three records must be refused, each
     matched against its own fixed diagnostic: `viola` + `viola-harness`, `viola` + `viola-fake-agent`, and an empty
     stream. A control record set, `viola` alone, must pass. It prints `release-check probes: 3/3 refused, control
     clean` and exits 0, or prints a `FAILED` summary and exits 1.
   - Any other argument exits 2 with a usage line.
2. **`scripts/orphans-check.sh` (new).** Use the same header and discipline. Check first that `cargo modules
   --version` works; if not, print `tool-missing: cargo-modules` and exit 1.
   - **Default mode** enumerates targets with `cargo metadata --no-deps --format-version 1` and jq: every target
     whose kind is `lib` or `bin`. That is 5 at HEAD (research: `viola-core` lib, `viola-e2e` lib,
     `viola-harness` bin, `viola` bin, `viola-fake-agent` bin with required feature `fake-agent`).
     - It fails if the list is empty.
     - For each target it runs `cargo modules orphans -p <package> {--lib | --bin <name>} [--features <required
       features joined by ,>] --deny`. The `--features` flag is added only when `required-features` is non-empty;
       research measured `-p viola --bin viola-fake-agent --features fake-agent` at exit 0.
     - It counts the clean targets and prints `orphans-check: N/N targets clean`, or `orphans-check: FAILED —
       <package>/<target>` and exits 1.
   - **`--probe` mode** writes two throwaway crates under
     `target/orphans-probes/run-$(date -u +%Y%m%dT%H%M%SZ)-$$/`. Each has an empty `[workspace]` table, as
     `deny-probes.sh:35-41` does.
     - `orphan` holds `src/lib.rs` plus a stray `src/stray.rs`. It must exit non-zero and its log must contain the
       fixed string ``orphaned module `stray` `` (measured).
     - `control` holds `src/lib.rs` only. It must exit 0 and contain `No orphans found.` (measured).
     - It prints `orphans-check probes: 1/1 fired, control clean`, or a `FAILED` summary and exits 1.

## Constraints & rejected approaches
- **Listing `target/release/` to find test binaries:** rejected. A shared or cached target dir keeps stale exes;
  research saw `viola-harness.exe` remain after a `--bin viola` build. The check reads the build's own
  `compiler-artifact` records.
- **Wiring `cargo modules dependencies --acyclic`:** rejected. It fails by construction on every type with an
  inherent method, whatever the filters (research, cargo-modules 0.27.0). It stays an on-demand review (operator
  decision).
- **An rmcp `cargo tree` check that accepts "rmcp absent":** rejected as a vacuous pass (test-plan §3 preamble,
  "never a vacuous pass"). It moves to the viola-mcp entry.
- **Running the fuzz audit under `working-directory: fuzz`:** rejected. rustup would resolve
  `fuzz/rust-toolchain.toml`'s nightly, which the supply-chain job does not install.
- **Installing cargo-modules through taiki-e/install-action:** rejected. The pinned action has no cargo-modules
  manifest, and its fallback would fetch an unpinned binary.
- **A tsconfig covering `crates/viola-ui/`:** rejected. The page has no JS build step (design-system and
  layout-templates).
- **A new `viola-harness gate` suite value for the release or orphans check:** rejected. These are plain exit-code
  steps, like `lint` and `supply-chain`, and a new closed-enum value needs a §12 entry (test-plan §3).
- **Uploading the release binary:** rejected. v1 has no release artefacts (security-plan §Threat Model Summary,
  Infrastructure CI/CD), and it would be a new unscanned upload.
