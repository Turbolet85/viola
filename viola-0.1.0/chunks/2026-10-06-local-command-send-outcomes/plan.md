## Goal
`send` starts consuming the compiled local-command list. A ledger-listed local command with no measured
post-condition, or one whose post-condition is not measured on this CLI version, returns
`ok {confirmed:false, detail:"unconfirmable", cursor}` as soon as it is typed, and prints `[  ] unconfirmable` on
the readback mirror. `/clear` on a verified version is confirmed by its measured post-condition, a `session-start`
with cause `clear` and a new session id, and reads back like any confirmed send. Every other unconfirmed send stays
`not-delivered`; the decision reads the list, never a leading slash (per architecture §Established Decisions →
[Delivery Confirmation]; layout-templates §Output structure — `viola send`; obs-plan §4 Scenario "Confirmed `send`").
This lands the two clauses `verification-matrix.json#v1-29` still owes.

Three smaller items ride with it. The readiness-gate reading is measured end to end under the fake agent, with the
gate left exactly as it is (the P4 card's answer, option B, inputs#I2). The guard before verify's local-command paste
gets the remove-the-guard control it lacks. Two comments that still say verify makes seven settles are brought to ten.

No live `claude` session is planned: zero (inputs#I1). No ledger row, no stamp, no recorded fixture.

   - **Not listed:** as today.
   - **Listed, and its post-condition is none, or the version is not verified:** `send-issued`, the paste, then at
     once, with no window: the record `send-confirmed {cursor, confirmed:false}` in `events.ndjson`, the process-log
     line `send-confirmed` with `confirmed = false` and the same `corr`, `rpc_id`, `conn`, `srv_conn`, `from`,

     `{"ok":{"confirmed":false,"detail":"unconfirmable","cursor":<cursor>}}`. A failed paste is `input-not-ready`
     with the cursor, as for any send.
   - **Listed with `PostCondition::NewSession` on a verified version:** `send-issued`, the paste, then the window.
     The in-flight send waits for its post-condition and for nothing else; a `prompt-submitted` never claims it.

4. **The post-condition claim** — `src/run/send.rs`, in `append_hook_event`. A `session-start` line confirms the
   in-flight send when that send waits for a new session, the line's `cause` is the string `clear`, and its
   `agent_session_id` is a string that differs from the remembered id. Both fields are read as data that may be
   absent or `null`; neither then confirms. The order is the landed one: claim under the lock, append the line,
   settle with that line's `ts`. The send then ends through `Ctx::confirm` unchanged: the record
   `send-confirmed {cursor}` and the reply `{"ok":{"submitted_at":<that ts>,"cursor":<cursor>}}`. If the window
   closes first, the send is `not-delivered` / `no-prompt-submitted` with its cursor. The remembered id moves on
   every appended `session-start`, claimed or not.
   - Basis that the equality decides the recorded case: `SessionStart.default.json` carries `c0f0cc23…` and
     `SessionStart.clear-1.json` carries `d5d38bc2…` with `source` `clear` (research M4), so on a stamped wrapper the
     boot's line sets the remembered id and the replayed `clear-1` line differs from it.
