## What this chunk builds

The second and third driving verbs. `send` (landed 2026-10-04) types a prompt and returns a `cursor`. `wait` lets a driver park until the driven session does something it must react to, and `last` hands it the newest turn's text. Together they close the send → wait → last loop over the CLI. Nothing polls (architecture [Message Broker / IPC], `architecture.md:52`).

### 1. `wait` — cursor-based wake on driver-relevant events (working entry)
- Surfaces:
  - the CLI verb `viola wait <target> [--after <cursor>] [--timeout-ms <n>]` (architecture §Conventions CLI, `architecture.md:176`);
  - the channel method `wait` `{after?, timeout_ms?}` → `{event:<ndjson event line>, cursor}` or `{timed_out:true}` (`architecture.md:276`), served by `run` beside `hook.event` and `send`. Every `params` also carries `v` and `sender`, plus `from` when `VIOLA_NAME` is set.
  - Re-verified at P1: `METHODS` lists `"wait"` (`crates/viola-channel/src/server.rs:356`), and `run`'s `Methods::dispatch` answers it `-32601` today (`src/cmd/run.rs:103-105`), pinned by the unit test at `src/cmd/run.rs:579-582`, which changes here.
- The wake set is the driver-relevant kinds: `turn-ended`, `question`, `permission`, `plan`, `session-end` (`architecture.md:52`). `activity` never wakes `wait` (`architecture.md:172`). Neither do the wrapper's `wheel`, `budget-gate`, `send-issued`, `send-confirmed`, `send-refused` lines (`architecture.md:305`), nor `session-start` / `prompt-submitted` (absent from the set).
- `cursor` is the end offset of the returned event's line. It is the next `after`. `send`'s `ok` cursor is a valid `after` (architecture: "Every `send` `ok` payload and every `wait` event result carries `cursor`").
- **Already-logged events returned at once** (working entry): with `after`, `wait` returns the first driver-relevant event whose line STARTS at or after that byte offset, at once if it is already logged. So a turn that ends before the driver calls `wait` is never missed. Without `after`, it returns the next such event appended after the call.
- VERIFIED (research.md; architecture `:52`): `after` is a byte offset into `events.ndjson`. A mid-line `after` needs no reading of its own: the contract's "first driver-relevant event whose line STARTS at or after it" already skips the line it falls inside. An `after` past the file's end is still unpinned (no refusal detail, no clamp). That one is P4's, and a new detail is a §Conventions amendment at wrap.
- VERIFIED (research E3: `src/cmd/run.rs:104-105` answers `hook.dialog` `-32601`, and `HOOK_KINDS` holds no dialog kind): The dialog-pending rule ("a dialog already pending when `wait` is called without `after`, or with an `after` at or before that dialog's event line, is returned at once"; `architecture.md:52`) needs dialog events, which no code emits until `Dialog answers by dialog_id` (`working-route.md:78`). This chunk puts the dialog kinds in the wake filter. Whether the without-`after` pending-dialog return lands here (witnessable only with a hand-appended dialog line) or with `:78` is P4's call.
- Blocking: std threads and blocking I/O only — CLI `wait` is a blocking read on `viola-channel`'s sync client (architecture Tokio containment, `architecture.md:457`). VERIFIED (research E2): `viola-state` has no reader, tailing or notify. Every append that can wake a parked `wait` while its wrapper lives is made in the `run` process (`append_hook_event`, `src/run/send.rs:130-147`). The only out-of-process writer is the hook's direct SessionEnd (`src/cmd/hook.rs:227-236`), taken only when the channel did not take the event, so its wrapper is unreachable. The wake is therefore a signal on the wrapper's own append path, on the `SendSlot` Condvar + injected-clock precedent (`src/run/send.rs:44-124`). A timed re-read of the file is never the wake.
- The human always wins: a parked `wait` never blocks, refuses or delays a human keystroke (CLAUDE.md Critical Warnings).

### 2. Typed timeout and unreachable on a vanished wrapper (working entry)
- **Typed timeout:** with `timeout_ms`, `wait` returns `ok` with `{"timed_out":true}` when no driver-relevant event arrives in time (`architecture.md:52`). With no `timeout_ms` it blocks until one arrives. VERIFIED as open (no spec states a cap; research): Whether `timeout_ms` is bounded (a maximum, a zero) is open. The MCP default is an open item that must stay below the MCP client's tool-call timeout (`architecture.md:61`). MCP is not built here (§Boundaries).
- **Unreachable on a vanished wrapper:** if the endpoint vanishes while a caller is parked, the caller gets `instance-unreachable` — exit `21`, CLI `--json` `{"v":1,"error":"instance-unreachable","detail":null}` (`architecture.md:147`, `:310`). VERIFIED (research E1): a wrapper that exits while a client is blocked in `Client::request` yields `ChannelError::Closed` (EOF, `crates/viola-channel/src/frame.rs:31-32`) or `Io` (reset). `send` already maps both to exit 21 `during:"call"` (`src/cmd/send.rs:267`), so no client change is needed for the exit. The client's own `channel-response` for that case reads `error` / `-32603` at ERROR (`client.rs:81`), which is not obs-plan §4's `outcome:"instance-unreachable"`.
- VERIFIED as a founder fork (security extract C1; security-plan-amendments `2026-10-04-confirmed-send-with-cl-1-records`, the fourth gap's no-borrow clause): The pre-connect liveness check reuses `send`'s founder-ratified fourth dated gap: a liveness-only pre-check (the snapshot's pid + start time alive, the heartbeat live, an `endpoint` present; else exit 21), with no server identity and no strict-modes, until Epoch 6 `:109` / `:111` (security.md, the fourth exception). That exception names CLI `viola send` only. Whether `wait` / `last` may ride it, or need their own Decisions Log entry, is a fork the wrap would halt on. ### 3. `last` — the newest turn's text (working entry + CARRY 1)
- Surfaces: the CLI verb `viola last <target>` and the channel method `last` `{}` → `{last_assistant_message:<string|null>, ts:<string|null>}` (`architecture.md:277`).
- The value is the newest `turn-ended` event's `last_assistant_message` (`architecture.md:292`). The wrapper holds it in memory and rebuilds it from `events.ndjson` on start (`architecture.md:52`). Before any turn has ended, both fields are `null`.
- CARRY 1, verbatim: "chunk 2026-09-28-cli-output-tokens (P4 operator ruling: no code without a live consumer) left the message-mode escaper to this entry: over decoded `char`s every Unicode `Cc` (C0, DEL, C1 — `char::is_control`) prints as `\xHH` text, `\n` and `\t` kept, CR and DEL escaped; never a strip (security-plan §Input Validation; design-system Component Patterns 3); in `src/human.rs`".

- Upstream text (`last_assistant_message`) is content, never a command or config (CLAUDE.md Critical Warnings). It reaches no codes-only log. User content goes only to `instances/<name>/diagnostics/detail-*.ndjson`.
