ruling 2026-09-25; V15 instance half; V17 fix commits live). The mutation base stops coming from the push event
(`ci.yml:166`) and is derived by the harness from the repository's own history. It is the last master-flip commit
reachable from the parent of the oldest operator pre-CI commit, a bound no mid-pass commit can move (measured at this
phase: the unbounded pickaxe moves to a fix commit that edits a `· complete ·` line; the bounded one holds). The rule
lives in `resolve_base` only, so a local run and CI read the same base (per test-plan §3 `run` step 4 Base; architecture
§Infrastructure Patterns → CI/CD approach).

The `gate --mutants-legs` union judges each mutant only on the legs that COMPILE its line. A mutant unviable on the leg
that compiles its code is not a survivor, whatever the other leg reads. A mutant missed on a compiling leg stays one.

/ `:420`) without a product change. Outcomes alone cannot carry this rule: "compiled out" and "missed on a compiling
leg" both read `missed` (research.md §Measured). So the gate evaluates the `#[cfg]` attributes around each mutant's line

`gate`, §10 Mutation gate; obs-plan §8 integration point 6).

construction, so it hits on the scan's own `?t=` pattern whether fresh or stale. The `harness-<os>` upload stops

4. **Which legs compile a line** — a new harness module `crates/viola-e2e/src/harness/cfg_legs.rs`, declared in
   `harness/mod.rs`. Given the workspace root, a mutant name (`{path}:{line}:{col}: {description}`, as the leg files
   carry it) and the named legs, it returns the legs whose target compiles that line.
   - It parses the file with `syn` and collects every `#[cfg(…)]` on a syntax node whose span covers the line: items,
     impl and trait items, inline modules, fields, statements, expressions, match arms, and inner `#![cfg]`. At HEAD
     that means fn-level (viola-pty lib.rs:393/417) and statement-level (lib.rs:435/442) attributes.
   - It evaluates them per leg with three values: true, false, unknown. The leg family comes from the leg name's
     prefix: `windows-` → windows; `ubuntu-` → unix + linux; `macos-` → unix + macos.
   - Known predicates: `unix`, `windows`, `target_os = "linux"|"macos"|"windows"`, `target_family = "unix"|"windows"`,
     `not`, `all`, `any`. Everything else, `test` and `feature` included, is unknown.
   - A leg is dropped ONLY when some covering cfg is PROVEN false for it. An unknown leg family, an unparsable name, an
     unreadable or unparsable file, a line outside every cfg, and an unknown predicate all keep the leg. Uncertainty
     never exempts a mutant.
   - `cfg_attr` is not evaluated. Its one site gates no code (lib.rs:113).

  - `AGENT_RUN_CHUNK_BASE` stays as the override, because the harness's own tests pin bases through it
    (mutants.rs:384).
  - The wrap push reads `HEAD^`, per the tests extract's "a base equal to HEAD" anti-pattern.
  - The scan skips by exact path, not by file name, per obs-plan §8 integration point 6: exclusion is admissible only
    for a file never uploaded.

## Constraints & rejected approaches
- An outcome-only union ("unviable on any leg exempts") is rejected. It cannot tell a compiled-out `missed` from a
  compiling-leg `missed`, so shared code unviable on one OS and missed on the other would go green (overseer direction
  3's negative).
- Leg-side annotation (each leg records whether it compiles a mutant) is rejected. It changes the leg file's ratified
  content class (security-plan Decisions Log 2026-09-24; obs-plan §8 item 6) and the closed §3 shape, for the same
  information the gate reads from the source.
- A text scan for `#[cfg]` lines above a mutant is rejected: statement-level cfg (lib.rs:435/442) and nesting defeat it.
- Keeping the event-derived base anywhere in `ci.yml`, even as a fallback, is rejected. It is the value that made fix
  pushes read only their own delta.
- The unbounded pickaxe from HEAD is rejected as the rule: measured moving mid-pass (research.md §Measured).
- Removing the `?t=` pattern, or skipping every file named `chunk.diff`, is rejected. The first weakens the floor and
  the second opens a blind spot (security extract; obs-plan §8).
- A macOS mutants leg, the local Linux pre-push gate, and any product-crate change are out of scope (scope §Boundaries).
- No `concurrency:` block, no new action, no `sleep` in tests.

## Implementation notes
- **cargo-mutants on the new module:** `cfg_legs.rs` is harness lib code, so the legs mutate it. Every arm of the
  three-valued evaluator needs a literal-oracle case, including one per operand position of `all` / `any` (testing.md
  2026-09-24, operator swaps).
- **One body per OS:** no new `#[cfg(unix)]` / `#[cfg(windows)]` body in harness code (secret_scan.rs:231–244 pattern),
  so the plain `run --mutants` form fits this Windows host (verification-harness.md 2026-09-25).
- **Line numbers:** `proc-macro2` `span-locations` makes `Span::start().line` 1-based outside a proc macro. Without the
  feature it reads 0, and every mutant would fall to the conservative arm. That would pass nothing wrongly, but the
  witness would stay red, which is how the replay entry catches it.
- **Mutant-name parsing:** the name is `{path}:{line}:{col}: {description}`. Split at the first `": "`, then take
  `line` and `col` from the right; repo-relative paths contain no `": "`.
- **`gate()` signature change:** 16 call sites (research.md §Graph impact: gate_cmd + 15 tests). A non-mutant suite
  never reads the root.
