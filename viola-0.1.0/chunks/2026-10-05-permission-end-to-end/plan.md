## Goal
The `permission` dialog kind gets the end-to-end case `question` and `plan` already have (test-plan §6 Path 4; arch
§Standard Contracts `hook.dialog` / `answer` / `wait`). The recorded ordinary-tool PermissionRequest
(`fixtures/claude/<v>/PermissionRequest.permission-1.json`, Run C's synthetic `touch`) is replayed by the fake agent
through the real `viola hook permission-request` on a fourteen-row stamped home. It is logged once with a
wrapper-assigned `dialog_id`, wakes a parked `viola wait` (the owed `v1-30` wake witness for the `permission` kind),
and is answered by id with `viola answer`. The hook prints the PermissionRequest `allow` body, and in a second dialog
`deny` + `message`. The recorded PostToolUse lands an `activity` line that wakes no `wait`. An `allow` answer that
carries a suggestion field still emits no suggestion: the architecture's deliberate v1 limit (`architecture.md:280`),
witnessed end to end, which makes `verification-matrix.json#v1-16` provable here.

The PermissionRequest body for a `question` first raised by PermissionRequest is measured with zero live sessions,
statically from both installed CLI bundles (research M1). Both 2.1.288 and 2.1.287 would apply a PermissionRequest
`allow` WITH `updatedInput` on AskUserQuestion. The case is reachable under viola, rarely (research M2). Building the
body needs a 15th ledger row, its `viola verify` probe and a re-stamp of both versions, at least 8 live sessions
against the 3 left (research M3). So the `null` to the human stays, with M1–M3 as its recorded reason in the code and
the specs, and an end-to-end witness that such a question is logged once, answered `null` at once, and refuses a late
`answer`.

Two small items ride along. `tests/cli_answer.rs`'s header loses its stale owner name (W6). The `verify_window_`
class's 45 s override gets the one planted-hang control it lacks (research M4), so the testing rule's designed-floor
exception — the operator's fold, overseer-decided (inputs#I1) — is met in full by the class that motivated it. The
rule text itself is a wrap curation. No product behaviour changes: the only product edits are doc comments.
