## Goal
Turn H2 from a runner-only flake with two sightings into a measured fact about viola-pty's Windows seam. H2 is a key
lost after a ConPTY resize. The two sightings were ci#36296402785 and ci#36436266196, both in `test (windows-2025)`
under `run --coverage` (research.md §Mechanism claims re-derived). The work follows the founder's ruling of
2026-09-28 16:54, in the overseer's order: **localise first**, then **reproduce a fixed number of times on the runner
that failed**, then **fix it in the seam or document it as a measured platform limit**. The founder's product question
on H2 stays open. This chunk hands the founder a measurement, not an answer.

Localising comes first because today's recorder cannot say what was lost. The child reports its size only when the
second key arrives (`crates/viola-pty/src/lib.rs:454-459`). A report that stops at `byte 78` therefore cannot tell "the
resize never applied" from "it applied and the key was lost". The overseer's reading that the resize itself never
reached the child is carried as an open hypothesis, not a fact (scope.md §Folded freight 2, premise-corrected). A
second hypothesis, H2-CPR, comes from microsoft/terminal PR #19535 (merged 2025-11-18, marked for inbox servicing):
ConPTY may write a cursor-position request (`ESC[6n`) after each resize and wait for the reply, and the test rig
discards all output (`lib.rs:552-556`) and never answers. The recorder is built to decide between these on a real loss.

Reproduction runs where the loss happens: temporary measurement pushes that loop the recorder test inside the
windows-2025 `test` job, removed again before the chunk ends (operator + overseer answer at P4, 2026-09-29). The count
is **3 localised losses within at most 3 measurement pushes of 200 iterations**. The pass stops at the first push that
reaches it. A budget that ends short is reported as *not reproduced*, with the rate bound it measured, and never
re-pushed to reach the count. This follows the project's timing-red recipe: testing.md 2026-09-28 ("measure the phases
on the runner that failed … timing-only pushes allowed") and 2026-09-27 ("force it open … never sample the race"). It
is bound by test-plan §10's zero-flakiness budget and by the human-always-wins invariant (architecture §Established
Decisions [Human Takeover / Wheel]; a11y-plan §1; security-plan §Security Anti-Patterns → Universal).

## Implementation Steps

### Stage A — /implement (the recorder and the host reading)

1. **Child-side size watch** (`crates/viola-pty/src/lib.rs`, `tests::pty_child_entry`). Right after the `start …`
   line, the child starts a watcher thread. The thread reads `host_size()` in a loop, yielding between reads the way
   `lines()` does at `lib.rs:583`, and appends `size {cols}x{rows}` to the report each time the size differs from the
   last one it reported. The start size counts as reported. It writes codes only, one `write_all` per line, and stops
   when the process exits. The existing lines stay byte-identical (`start …`, `byte 78`, `byte 79 size=…`,
   `restored=…`), so the red's signature stays comparable.
2. **Test-side sequence** (`lib.rs` tests module). Add a sibling report
   `<temp dir>/viola-pty-watch/<test name>.test.report`, written by the test thread, one line per event, same codes-only
   rule. The lines are `resize-returned` right after `pty.resize(…)` returns, `key-written` after `write_all`,
   `key-flushed` after `flush`, and `dsr-cpr {n}`. Its lifecycle is the same as the child report: removed on a pass,
   kept on a panic or kill (extend `Child`'s `Drop` at `lib.rs:500-509`, and `report_path` at `lib.rs:513`).
3. **DSR count on the drain** (`tests::spawn_child_entry`, the drain thread at `lib.rs:552-556`). The thread counts the
   occurrences of the 4-byte sequence `ESC [ 6 n` in the output, including across read-buffer boundaries. It publishes
   the count through an `Arc<AtomicUsize>` on `Child`, and the test writes it as `dsr-cpr {n}` when it reads the
   verdict or panics. Only the count is recorded, never an output byte. It is evidence, never a pass/fail verdict
   (test-plan §11 E2E / R7).
4. **Kind-keyed waits.** The child report now has extra `size …` lines at positions that depend on timing, so replace
   the index-based reads (`lines(&child, 2)[1]`, `got[2]`, `got[3]` at `lib.rs:612-628` and `655-667`) with a wait for
   the exact line each assertion names: `byte 78`, `byte 79 size=120x40`, `restored=true` (testing.md 2026-09-24:
   "Wait on the exact line a test asserts"). The deadline panic (`lib.rs:582`) prints both reports whole, the child's
   and the test side's, so one red localises itself.
5. **A resize with no key** — new test `spawn_reports_a_resize_to_a_child_that_reads_no_key`. Spawn at 100x30 in a new
   child mode `watch`. In that mode the child reports `start`, runs the step 1 watcher and then parks, and never reads
   stdin. The test resizes to 120x40 and waits for `size 120x40`, then kills the child. This witness shows that a
   resize reaches the child apart from any key, which is the question the overseer ordered settled first. The mode
   rides `PTY_SEAM_TEST_MODE` in the child's spawn env, which only the test child reads (`lib.rs:540-543`). No `viola`
   build reads it.
6. **Localisation classes** — written once in the kept-report reading rule, in `evidence/localisation-rule.md`, before
   any runner loop. A lost iteration (the `byte 79` line missing at the deadline) is classified from the two reports:
   - **R — the resize never applied:** no `size 120x40` line from the watcher.
   - **K — the resize applied, the key was lost:** `size 120x40` is present, and `key-flushed` is present.
   - **E — the key arrived before the size changed:** `byte 79 size=100x30`, which is not a loss but a
     mis-ordering. It is recorded apart from R and K.

   `dsr-cpr {n}` is recorded beside every class.
7. **Host reading** — run the `package(viola-pty) & test(/resize/)` loop gate (Test Commands) on this host, and record
   in `evidence/host-localisation.md`: iterations, passes, every kept report, and the `dsr-cpr` count the host's conhost
   produces after a resize, read from one passing iteration's test-side report. Keep it with a temporary nextest
   `success-output` override (testing.md 2026-09-28) or a debug read of the count, removed before the stage ends. Host
   builds: 10.0.26200.9457, conhost 10.0.26100.8875 (research.md). A host loss, if one occurs, is classified by step 6.
   No host result stands for the runner (test-plan §11 Test Strategy).
8. **The measurement loop, pre-written, not committed.** Write the exact loop step the operator pass will insert into
   `.github/workflows/ci.yml` to `evidence/h2-loop-step.md`: a step in the `test` job, after the job's `run --coverage`
   step and before its uploads, guarded to `matrix.os == 'windows-2025'`, with `shell: bash` and fail-closed. It runs
   the viola-pty resize tests 200 times under the same instrumentation as the reds:
   `cargo llvm-cov nextest --no-report --profile ci -p viola-pty -E 'test(/spawn_runs_a_raw_child_that_sees_its_size_a_resize/)'`
   once per iteration. After each failed iteration it prints the kept `viola-pty-watch` reports to the job log. It ends

## Constraints & rejected approaches
- A standing ci.yml probe job — rejected at P4: it changes the recorded job count and adds runner time to every push for
  a roughly 1-in-16 event. The loop lives only in measurement commits.
- Raising `CHILD_WITHIN` or any bound to make the red pass — rejected: a timing red is never fixed by a bound
  (testing.md 2026-09-28), and the key never arrived within 7 s.
- viola itself answering a cursor-position request, or re-typing a key, in `run`'s pump — out of this plan. It would
  put viola-originated bytes into the child's input, a new crossing of the "Boundary widening" class
  (`.andromeda/playbook.md:36-38`, verdict escalate). If the localisation points there, it returns to the operator as
  an escalation, not a fix.
- Holding, queueing or re-ordering a human key behind a resize — banned (a11y-plan §11 Keyboard; security-plan §Security
  Anti-Patterns → Universal).
- A new env seam, a portable-pty bump, a new crate or a new `windows-sys` feature — not needed. `Win32_System_Console`
  is already a workspace feature (`Cargo.toml:201`), and any of these would be a P4 fork, not an implement choice.
- Uploading the kept reports as an artifact — not needed. The loop prints codes-only reports to the job log, so no
  unscanned upload is added (obs-plan §9; security-plan §Dependency Security → CI integration).
- Parsing the child's screen for a verdict — banned (test-plan §11 E2E). The DSR count is evidence beside a verdict,
  never the verdict.

## Implementation notes
- The watcher adds `size …` lines whose positions depend on timing, which is why step 4's kind-keyed waits come before
  any new assertion. The `kill_ends_a_child_that_would_never_exit` test (`lib.rs:671`) uses the `block` mode and is
  unaffected, since the watcher runs in every mode but `block` only parks.
- `ESC[6n` can straddle two `read` calls: the drain carries the last 3 bytes of each buffer into the next scan.
- The tests extract's "independent size oracle (test-plan §7)" describes the spec's target. At HEAD the fake agent's
  `size` receipt is sampled only around a byte read (`src/bin/viola-fake-agent.rs:463-473`), so it is not a model of a
