## Goal
Land viola's fourth interface: the stdio MCP server `viola mcp` (rmcp 3.4, features exactly `server` +
`transport-io`). It gives a wrapped driver session the tools `send · wait · last · answer · list`, each returning
the same result and refusal as its CLI verb's `--json` form, with refusals as code-only `isError` results. It has no
wheel or link tool, re-validates every input server-side, and bounds every call below the client's tool-call
timeout (architecture §Established Decisions [MCP], §Conventions Error handling schema; security-plan §Input
Validation, §Error Handling; test-plan §1, §4, §6).

The server is a thin adapter.
- Its frame tools reach the instance's wrapper through `viola-channel`'s new Tokio client behind the `tokio`
  feature, after the same liveness-only pre-check the CLI verbs make. That is the eighth dated gap the founder
  ratified (`inputs#I2` Q1), closed with the other seven by "Server verification before any frame" and "Home and
  code-bearing file integrity".
- Its `list` tool returns the same board document CLI `list --json` builds, including the one `claude agents
  --json` read (`inputs#I2` Q1).
- The root bin owns the subcommand, the home, the role log and the board. `viola-mcp` owns the runtime, the tools and
  the result mapping. The root bin hands the board in as a provider, so no crate edge points back at the root
  (architecture §Infrastructure Patterns → Crate dependency direction).

The chunk folds its five carried items:
- `viola-channel` stays tokio-ban-checked, through a `cargo tree` form (CARRY 1);
- the rmcp feature assertion lands as a non-vacuous lint step (CARRY 2);
- `role_of` names `mcp` as its own role (CARRY 3);

- the switch question is answered: group 2 only, a new entry claims `v1-33` (CARRY 5, `inputs#I2` Q3 and Q4).

     `{"error":"invalid-params","detail":"<field>"}` (the field a closed word: `target`, `text`, `after`,
     `timeout_ms`, `dialog_id`, `response`), and text `refused: invalid-params`. No frame is written.
   - **`send`**: the text first, in `refusal_of`'s order: `validate_paste_text`, then `typed_text` empty. A refusal is

     `send-refused` line (obs-plan §6).
   - **`answer`**: `validate_paste_text` on every free-text value of the response, with the same refusal.
   - **Frame tools** (`send`, `wait`, `last`, `answer`), the eighth dated gap (`inputs#I2` Q1):
     - `live_endpoint(home/instances/<target>)`; none → `{"error":"instance-unreachable","detail":null}`;
     - one Tokio-client request with `from` set to the server's own name when it has one;
     - `wait` sends `timeout_ms = min(given, WAIT_CAP)`, defaulting to `WAIT_CAP`, with `WAIT_CAP = 50_000` ms.
       It passes `after` through. The wrapper's own deadline ends the call, so no adapter-owned timer exists.
   - **Result mapping** (`src/result.rs`):
     - a channel `ok` → `isError: false`, `structuredContent` the `ok` payload, text its JSON;
     - a refusal → `isError: true`, `structuredContent` `{refusal, detail}`, text `refused: <reason>`;
     - a JSON-RPC fault → `isError: true`, `{"error":"wrapper-fault","detail":{code,message,data}}`;
     - `Connect` / `Closed` / `Io` → `{"error":"instance-unreachable","detail":null}`;
     - any other channel error, a reply of no known shape, or a `wait` / `last` refusal → the crate's one thiserror
       `McpError`, whose fixed message rmcp sends as a JSON-RPC error. This is a fault of the MCP call itself:
       code `-32603`, message `internal error`, data null.

     `src/cmd/client.rs:73-75,140-156`; `src/cmd/send.rs:130-155`).

     text, response or message reaches a span field or a line; only `text_bytes` is logged (obs-plan §4 viola-mcp
     row, §6, §8).

## Constraints & rejected approaches
- `spawn_blocking` around the sync client — rejected: architecture requires `viola-channel[tokio]` three times; a
  blocking pool would leave the arch edge unbuilt and CARRY 1 moot only by deviating.
- rmcp's typed `Parameters<T>` deserialisation as the validator — rejected: a serde failure would answer a JSON-RPC
  error carrying serde text (a field path and value), breaking the code-only rule (security-plan §Error Handling).
  Handlers take the raw object and validate it themselves.
- Reading `VIOLA_NAME` / `VIOLA_DIR` inside `viola-mcp` — rejected: the root bin already reads them
  (`resolved_home`, `own_name`); a second reader would add a `VIOLA_*` literal to the controls table for nothing.
- A copy of `live_endpoint` inside `viola-mcp` — rejected: two copies of the liveness pre-check drift; it moves to
  `viola-state` once.
- An adapter-owned `wait` timer — rejected: forwarding `timeout_ms = min(given, 50 000)` lets the wrapper's deadline
  end the call (`src/run/wait.rs:161`), so no second clock exists to test or to drift.
- A `wait` result carrying a resume cursor on timeout — not added: a wire change to the channel `wait` contract that
  the CLI does not have. A driver resumes with the `after` it passed (CLI parity).
- `cargo deny --exclude viola-mcp` or a `wrappers` allowlist for CARRY 1 — rejected: arch Build system rules both out
  (the `--exclude` false fail is measured).
- Any `pause`, `release`, `link`, `unlink` or screen tool — out: CLI-only or unbuilt (architecture [MCP]).
- A second live start (a refusing `viola mcp` at the CLI's start) — not made: the founder capped the chunk at one
  (`inputs#I2` Q2). Whether a registered server that exits 1 blocks the CLI's start stays unmeasured, and the
  start-time refusal keeps the spec's exit 1.
