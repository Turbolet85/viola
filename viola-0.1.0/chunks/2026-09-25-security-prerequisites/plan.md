repo and runs in CI (per security-plan §Security Decisions Log → Open questions; §Bootstrap phases

- **The SQOS spike.** Can interprocess 2.4.4's `local_socket::Stream::try_from(OwnedHandle)` adopt a handle that windows-sys
  `CreateFileW` opened with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED`? It blocks the
  Wrapper-channel client chunk.
- **The SHA-256 pick.** Which pure-Rust crate computes the truncated `<hash>`? It blocks the Instance-state chunk that
  writes `bin/`.

P3 measured both premises in a scratch probe (research.md §Measured facts):
- The spec's own path **passes**: the server reads `SecurityIdentification`.
- A no-SQOS open reads `SecurityImpersonation`, so the check discriminates.

- `sha2 =0.11.0` (no default features) passes the C-build ban and the licences, and builds on the 1.96 floor.

This chunk turns those measurements into durable witnesses:

No product crate is created: `viola-channel` and `viola-state` belong to their first consumers, per architecture
§Established Decisions [Module Boundaries].

## Constraints & rejected approaches
- **interprocess default connect** (`LocalSocketStream::connect` / `connect_without_waiting`) as the client open, a
  fallback or a test double — rejected. It opens without SQOS: measured, the server reads `SecurityImpersonation`
  (research.md case G), and security-plan §Security Anti-Patterns → Authentication forbids it.
- **A non-overlapped SQOS handle** — rejected. Adoption through `try_from` then hangs (research.md cases B and C).
- **std `OpenOptions::security_qos_flags` + `custom_flags(FILE_FLAG_OVERLAPPED)`** as the pinned open — not adopted here.
  It is a measured safe-Rust equivalent (case D), but the spec names the windows-sys path, which passes. It is recorded
  for the channel chunk to weigh, not implemented.
- **Adding `"0BSD"` to the `allow` list** — rejected by the operator's P4 ruling in favour of per-crate exceptions. A
  global allow admits any future 0BSD crate silently.
- **Creating `viola-channel` or `viola-state` to host the witnesses** — rejected per architecture §Established Decisions
  [Module Boundaries] ("each product crate is created by the first chunk that consumes it").
- **A product helper for the 16-hex `<hash>`** (e.g. in `viola-core`) — rejected. The re-hash belongs to `viola-state`'s
  `bin/` writer (scope §3). An unconsumed product function would also be an unkillable mutant (testing.md Session
  Additions 2026-09-24).
- **`FNV-1a` / `DefaultHasher` for `<hash>`** — rejected per security-plan §Security Anti-Patterns → Data Protection. FNV-1a
  stays only for endpoint names (architecture §Conventions).

## Implementation notes
- **Load-bearing mechanism, stated as an equality:**
  - For THESE inputs (same-user test process, byte-mode single-instance pipe, client flags
    `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED`, adoption by `Stream::try_from`), the
    server's `TokenImpersonationLevel` after `ImpersonateNamedPipeClient` equals 1. Measured on 1.98.1-msvc, Windows 11
    26200: case A, 3/3 runs.
  - The frame that PRODUCES it is the client's connect-time QoS. `try_from` re-opens the handle via `ReOpenFile(h, …,
    FILE_FLAG_OVERLAPPED)` with no SQOS flags (`named_pipe/c_wrappers.rs:182`), and the measured level shows the re-open
    keeps the original connection's level.
  - The control equality: flags `FILE_FLAG_OVERLAPPED` alone → 2 (case F).
- **Impersonation after the read:** `ImpersonateNamedPipeClient` needs the server to have read from the pipe first. The
  server reads before impersonating, which is the probe's order.
- **`OpenThreadToken`** is called with `OpenAsSelf = TRUE`. At Identification level the token is still queryable, which
  the probe confirmed.
- **Counts carry their basis:**
