## Goal
On Windows x64, `viola run` hosts its child in Microsoft's current ConPTY: `conpty.dll` and `OpenConsole.exe` from
`Microsoft.Windows.Console.ConPTY` 1.24.260710001 (the newest stable; research facts 1-2). The two files are committed
byte-identical to the official package, embedded in `viola`, and written write-if-absent into the pinned dir's own
subtree `bin/<version>-<hash>/conpty/`. At every start each file is re-hashed (full SHA-256 against compiled-in pins)
through a handle that denies other writers until the load and spawn are done. `conpty.dll` is then pre-loaded by
absolute path, so portable-pty `=0.8.1`'s bare-name `LoadLibraryW("conpty.dll")` (`psuedocon.rs:54`) returns that
module. The Authenticode signer is checked when the files are vendored and on every push in CI; at run time the hash
pin carries it (P4 fork 2).

The chunk also closes a load-path hole that exists today, measured in research fact 6: the bare-name load picks a
planted `conpty.dll` from the CWD or from `PATH`. Every `viola` process restricts its DLL search to System32 as the
second statement of `main`, so an absent, tampered or unloadable sideload degrades to kernel32's inbox ConPTY and never
to a planted file. The degrade never blocks, prints or refuses. It is recorded as codes on the `run.conpty_sideload`
span and on `process-start{subject:"claude-child"}` (per security-plan §Security Anti-Patterns → Universal "human always
wins", obs-plan §6, design-system §Surface: cli → Component Patterns 5).

The founder's acceptance is a measurement: the H2 key-after-resize race, 200 iterations on windows-2025, run once on
the sideloaded ConPTY and once on the inbox one in the same CI run. Both counts are recorded whatever they are; no target
rate is set. The race lives in a measurement-only viola-pty test behind a measurement-only feature, because the gating
H2 test waits for the new size since `dce98ad` (research, scope premise correction). It is removed with the loop before
the wrap.

## Implementation Steps
1. **Vendor the pinned files.** Write `scripts/conpty-vendor.sh`, modelled on `scripts/install-node.sh`'s pin model, with
   three modes.
   - **Default (re-vendor):**
     - fetch `https://api.nuget.org/v3-flatcontainer/microsoft.windows.console.conpty/<version>/microsoft.windows.console.conpty.<version>.nupkg`
       over TLS, failing closed;
     - refuse before extracting when its sha256 differs from the pin;
     - extract only `runtimes/win-x64/native/conpty.dll` and `build/native/runtimes/x64/OpenConsole.exe` into
       `vendor/conpty/<version>/x64/`;
     - refuse on a per-file sha256 mismatch;
     - on Windows, check each file's Authenticode through `powershell.exe -NoProfile` `Get-AuthenticodeSignature`:
       Status `Valid`, subject `CN=Microsoft Corporation, …`, issuer starting `CN=Microsoft Code Signing PCA`.
   - **`--verify`:** fetch into a `mktemp -d` dir outside the tree (removed on exit) and compare byte-for-byte with the
     committed files, then run the same signer check on the committed files. `--probe` mints its inputs in its own
     `mktemp -d` dir the same way, so neither mode writes into the tree.
   - **`--probe`:** prove each refusal on minted inputs (a nupkg sha mismatch refused before extraction, a file hash
     mismatch, an unsigned file, a TLS failure against an unreachable host) plus a matching control. It ends with one
     summary line `conpty-vendor probe: <n>/<n> refused, control clean`.
   - The pins have ONE textual home, `src/conpty.rs`, parsed by the script from the file text: version, nupkg sha256
     `175640566a3b59c4b132070ee96c2c77e5ab7edd2e92732a5eb3610bbf63d90e`, and the per-file sha256 `39fba271…d75d8`
     (`conpty.dll`) and `b7fd936c…cf8160` (`OpenConsole.exe`), with the full values in research fact 2.
   - Run the default mode once to produce `vendor/conpty/1.24.260710001/x64/{conpty.dll,OpenConsole.exe}`. Add the
     `.gitattributes` line marking `vendor/conpty/**` as `binary`.
2. **`src/conpty.rs`** (root bin), `cfg(all(windows, target_arch = "x86_64"))`. It holds:
   - the version;
   - the nupkg sha256 as text the script reads;
   - per file: its name, its `include_bytes!` of `vendor/conpty/1.24.260710001/x64/<name>` (via `CARGO_MANIFEST_DIR`),
     and its 64-hex SHA-256 literal.

   It knows nothing about paths under the home. Other Windows architectures compile no sideload, and their outcome is
   `not-built`.
3. **The DLL search restriction** — `crates/viola-pty/src/sideload.rs` (`cfg(windows)`), `pub mod sideload` in
   `lib.rs`: `restrict_dll_search()` calls `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`
   (`Win32_System_LibraryLoader`, already in the workspace feature list, `Cargo.toml:201`) and reports success. In
   `src/main.rs` it is the second statement, right after `std::panic::set_hook`, on Windows, for every role; its result
   is not logged there (obs is not initialised yet). The run's `run.conpty_sideload` span records it as the field
   `search_restricted` (bool).
4. **The pre-load** — same module: `preload(dll: &Path) -> Result<(), PtyError>` calls `LoadLibraryExW(abs path, null,
   0)`, keeps the module loaded for the process lifetime, and sets a process-wide backend flag. `PtyError` gains one
   variant `Load` (fixed message `"pty load failed"`), which is not a new enum. The seam's backend becomes a function
   `pty_backend() -> &'static str`: `conpty-sideload` after a successful `preload`, else `conpty` on Windows, `openpty`
   elsewhere. It replaces the const `PTY_BACKEND` at its 3 uses: `crates/viola-pty/src/lib.rs:122` (the `pty.spawn`
   field), `src/run/mod.rs:46`, and the test at `src/cmd/run.rs:615` (graph + grep, research §Graph impact).
   - The ordering invariant is documented on `preload`: it takes effect only before the process's first ConPTY use
     (portable-pty's `lazy_static`, `psuedocon.rs:61-63`).
5. **Companion pinning** — `crates/viola-state/src/pin.rs`, `cfg(windows)`: a new
   `pin_companions(pinned: &Pinned, subdir: &str, files: &[Companion]) -> Result<HeldCompanions, PinError>`.
   - `Companion` is `{ name, bytes, sha256_hex }`.
   - It creates `bin/<key>/<subdir>/` through `create_private_dir`.
   - Per file, it writes the file when absent through `replace_private_shared` (write-if-absent, never overwritten,
     like `pin_exe` `pin.rs:71-78`).
   - It then opens each file with `std::os::windows::fs::OpenOptionsExt::share_mode(FILE_SHARE_READ)`, hashes it (full
     SHA-256, 64 KiB chunks) and compares it with the pin.
     - Any difference → `PinError::HashMismatch`, file left as found.
     - An unreadable or unwritable file → `PinError::State`.
   - It returns the open handles plus the dir's absolute path.
   - `PinError` gains no variant. `pin_exe` and `verify` are unchanged (verify writes no companion).
6. **The start step** — `src/cmd/run.rs`: a new `#[instrument(skip_all, name = "run.conpty_sideload", fields(outcome =
   Empty, search_restricted = Empty))]` step placed right after `pin_and_plugin` (:168) and before the strip plan
   (:172). It runs `pin_companions(&pinned, "conpty", conpty::FILES)`, then, only when both files verified,
   `viola_pty::sideload::preload(<dir>/conpty.dll)`.
   - `outcome` ∈ `loaded` · `hash-mismatch` · `unreadable` · `load-failed` · `not-built`, a closed kebab-case code.
   - A missing or failed `OpenConsole.exe` never lets `conpty.dll` load. This closes the third state of research
     fact 4, the sideloaded dll on the inbox conhost.
   - The held handles live in `start` until `spawn_child` (:191) has returned, then drop, so the verified bytes are
     the loaded and launched bytes.
   - Nothing on this path prints, refuses or changes the exit code. Every failure maps to its outcome code and the run
     continues on the inbox ConPTY.
7. **The record** — `src/run/mod.rs` `log_child_start`: `process-start{subject:"claude-child"}` carries `pty_backend =
   viola_pty::pty_backend()`. When the Windows outcome is not `loaded` it also carries a new additive field
   `sideload_fallback` with that outcome code. The field is added to `schemas/diag-line.v1.json`'s `process-start`

   no mirror: it carries no `process-start` field (grep `pty_backend` schemas/diag-detail.v1.json: 0). The span-order
   test `src/cmd/run.rs:562-615` gains `run.conpty_sideload` on Windows.

## Constraints & rejected approaches
- **A run-time WinVerifyTrust check**, rejected at P4 (fork 2): the hash pin makes its failure branch unreachable, and
  WinTrust chain-building can touch the network.
- **A build-time fetch with no committed bytes**, rejected at P4 (fork 1): every Windows build would need the network,
  and a bare `cargo install --path .` would break.
- **A runtime download from `viola`**: never. `viola` makes no outbound call (security-plan §Threat Model Summary,
  Infrastructure → Networking).
- **Placing the files directly in `bin/<key>/`**: that dir is first on the child's `PATH`, so the whole `claude` tree
  would see them.
- **Overwriting a mismatched companion**: never, like `pin_exe`. A tampered file is left as found, and the run degrades.
- **A refusal, exit 1, stderr line or `hint:` for a sideload failure**: never. The human always wins, and `run` prints
  nothing once the child's screen is up.
- **Changing portable-pty (fork, bump off `=0.8.1`, psmux, own ConPTY)**: out of scope (architecture [PTY] swap
  triggers).
- **A `VIOLA_*` variable, config key, CLI flag or env seam that selects or disables the sideload**: never. The two H2 legs
  select by test name inside one measurement-only feature, which leaves the tree before the wrap.
- **Restricting the DLL search in test drivers** (the harness `supervise`, root `OuterPty`): out of scope. They are
  test processes, and the product restriction lives in `viola`'s `main`.
- **A `process-start` / `process-exit` pair for `OpenConsole.exe`**: not owed. `conpty.dll` launches it, not viola
  (research fact 5), exactly as the inbox `conhost.exe` was launched.
- **Pinning the companions through `pin_exe` or in `verify`**: rejected. `verify` spawns no PTY, and
  `tests/cli_verify.rs` pins its lines.
