## Goal
The wrapper serves the two channel methods `link` and `unlink` over its existing `LinkSet`, and the two verbs
`viola link <driver> <driven>` and `viola unlink <driver> <driven>` reach the driven instance's wrapper with them
(architecture §Established Decisions [Links], §Standard Contracts Channel methods). `link` records the pair once and
answers `{since, already_linked}`; `unlink` removes it, appending the first product `unlink` line, and answers the
empty object; an `unlink` of an absent pair appends nothing (the operator's answers,
`chunks/2026-10-10-session-links/inputs/I2-relay-2.md.txt`).

The verbs take the form the founder named (`inputs#I3`): `viola_state::strict::check_instance` on the home and the
driven instance's tree before any log opens and before any snapshot value is read (security-plan §Authentication &
Authorization, `~/.viola/` access control; the order of `src/cmd/revive.rs:116-121`), then the liveness-only
pre-check and the server check through `cmd::client::connect` like every other CLI frame verb (security-plan
§Authentication & Authorization, IPC client-side server verification). A refused check exits 21 with no log and no
line; a server that is not the recorded wrapper gets no frame and exits 21. `viola --help` gains its
`handoff:  link, unlink` row, and the three result lines print in design-system §Surface: cli pattern 4's forms.

No ledger row, no `viola verify` child, no re-stamp, no live `claude` start and no MCP tool: a link is recorded from
viola's own parameters, and `link` / `unlink` stay CLI-only (architecture [MCP]).

## Implementation Steps

1. **The two method handlers** (`src/run/links.rs`). The link set gains `link(params)` and `unlink(params)`, each
   returning the channel result or a `ProtocolError`. Each reads `params.driver` and `params.driven` as strings
   through `ViolaName::try_new`; a missing, non-string or invalid name is `ProtocolError::InvalidParams` (`-32602`,
   `data: null`). Then a `driven` that is not the set's own `name` is `-32602`, then a `driver` equal to `driven`
   is `-32602`. Neither method reads `from`: a `from` in the params, of any shape, changes nothing. `link` calls
   `record(driver)` and answers `{"ok":{"since":<since>,"already_linked":<bool>}}`; `unlink` calls
   `remove(driver)` and answers `{"ok":{}}` whether or not a pair was removed. A `record` / `remove` error is
   `ProtocolError::Internal` (`-32603`). Each answers only after the line and the snapshot write have been made
   (`change`, `src/run/links.rs:98-104`, unchanged). `remove` loses `#[cfg_attr(not(test), allow(dead_code))]`
   and its "not served yet" doc sentence; the module doc names the two methods. Neither method opens a span or
   writes a process-log line (obs-plan §4 Edge flows E3). Inline cases (keeps tests S2), named `links_set_method_*`:
   link twice (one line, the same `since`, `already_linked` false then true); unlink then link (a later `since`);
   unlink of an absent pair (no line, `{}`); each bad-name class (`../x`, `BUILDER`, `a/b`, `""`, 33 characters, a
   number, absent) on each param, a foreign `driven`, `driver` equal to `driven` (each `-32602`, no line, the
   snapshot's `links` unchanged); a `from` in the params, valid or not, changes nothing; a failing append is
   `-32603` with the set unchanged.

2. **The wrapper routes them** (`src/cmd/run.rs`). `Methods` (71-79) gains the `LinkSet`; `start` hands it the
   restored set (after `links.restore()`, 287, as it already hands it to `send` and `dialogs`); `dispatch_call`
   (134-145) routes `"link"` and `"unlink"` to it; the `Methods` doc comment (68-70) names the nine served methods.
   The unit helper `methods()` (778-810) builds a `LinkSet` over its instance dir. The case
   `methods_answer_method_not_found_for_every_other_method` (821-830) keeps `"anything"` alone and calls
   `dispatch_call`; a new case `methods_route_link_and_unlink_to_the_link_set` sends a valid `link` then `unlink`
   through `dispatch_call` and reads one `link` and one `unlink` line.

3. **The three result lines** (`src/human/verbs.rs`, re-exported from `src/human.rs`). One writer each, one
   `write_all` to the given `Write`, plain in every mode (design-system §Surface: cli pattern 4; keeps design S1–S3):
   - `link    <driver> -> <driven>  since <time>` (the word padded to `unlink`'s width, two-space gutters);
   - `link    <driver> -> <driven>  already linked`;
   - `unlink  <driver> -> <driven>`.
   `<time>` is the reply's `since` as its UTC clock time in whole seconds with `Z` (`%H:%M:%SZ`, always the time-only
   form: the wireframe shows no date, leaned per layout-templates §Output structure — wheel, handoff and dialog
   verbs); a `since` that is no RFC 3339 instant (the restore's `"unknown"`) prints through `escape_message`, as
   `override_end` does (28-39). Inline cases pin each line byte for byte and that none holds an ESC or a non-ASCII
   byte, a non-instant `since` included.

4. **The two verbs** (new `src/cmd/link.rs`, `src/cmd/unlink.rs`). `link.rs` holds the shared call, as
   `src/cmd/pause.rs:49-86`'s `wheel_call` serves `release`; `unlink.rs` is its thin second verb. Each verb takes
   `<driver>` and `<driven>` through `super::send::parse_name` and `--json`. The verb's instance is the driven one.
   In order:
   1. the absolute home and `<home>/instances/<driven>`; `check_instance(home, instance_dir)` — refused: under
      `--json` the document `{"v":1,"error":"instance-unreachable","detail":null}` on stdout with stderr empty,
      else `human::instance_state_pair(driven)` through `human::refuse`; exit 21; nothing under the home opened,
      no role file, no line (the shape of `src/cmd/list.rs:100-108` and `revive`'s, with exit 21 as every CLI verb
      but `run` / `mcp` / `revive` maps a strict-modes refusal, test-plan §5 On-disk);
   2. `client::start(home, &driven)` (the `cli` role file and `process-start`);
   3. `live_endpoint` — none: exit 21 through `client::unreachable` and `client::unable_unreachable(driven, …)`;
   4. params `{driver, driven}` plus `from` from `client::own_name()` when set;
   5. one request through `client::connect` under `#[instrument(skip_all, name = "cli.link")]` /
      `name = "cli.unlink"` (obs-plan §2 span naming: `cli.<verb>`; keeps obs S2);
   6. the reply through `client::answer_of`: an `ok` of `link` with a string `since` and a boolean
      `already_linked`, or an `ok` of `unlink` that is an object, prints the step-3 line built from the verb's own
      parsed names and the reply's keys, or under `--json` `{"v":1,"ok":<ok>}`, then `run::log_self_exit(0, None)`,
      exit 0; `Fault` → `client::fault`, exit 20; unreachable (`Dead`, `ServerUnverified`) → exit 21 with the cause's
      hint; a `Refused` or an `ok` of another shape → an internal error (exit 1 through the `main` catch site).
   Each module's test module, gated `#[cfg(test)]` + `#[cfg(not(target_os = "macos"))]` (testing.md 2026-10-26),
   holds `request_refuses_an_unverified_server_inside_its_dispatch_span` through `client::refused_inside`; `link.rs`
   also holds the reply-shape table (`#[case]` rows: each accepted and refused `ok` shape, a refusal, a fault).
