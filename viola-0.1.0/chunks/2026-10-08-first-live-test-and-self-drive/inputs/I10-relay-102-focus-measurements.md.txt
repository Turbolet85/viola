## What was measured

- **The focus dispatcher does not move the focused WINDOW for an existing window either.**
  `hyprctl dispatch 'hl.dsp.focus({ window = "address:<overseer1's window>" })'` answered `ok`; monitor `DP-2`
  switched from workspace 4 to workspace 3 and became the focused monitor; the cursor warped from `1280, 733`
  to `2722, 253`; and `hyprctl activewindow` still read `overseer.viola-overseer` on workspace 4, a workspace no
  longer shown. So the stuck focus is not about a NEW window, the second monitor, an empty workspace or foot.
- **Two witnesses agree.** `hyprctl clients -j` `focusHistoryID` stayed `0` on `overseer.viola-overseer` (1 on
  `viola.viola-builder`) before and after the dispatch — the same as `activewindow`.
- **DPMS is not the cause.** The same run with `hl.dsp.dpms("on")` first (both monitors `dpmsStatus` true): the
  same result. (With DPMS off `DP-2` reports 640 x 480; with it on the session windows read 1261 x 1390.)
- **Monitor focus and window focus are decoupled right now.** Before any dispatch, `HDMI-A-1` (workspace 7,
  empty) read `focused: true` while the active window was on `DP-2`.
- **No other spelling exists.** `hl.dsp.window.focus(...)` and `hl.dsp.focus_window(...)`: `attempt to call a nil
  value`. `hl.dsp.focus({ window = "class:overseer.overseer1" })`: `ok`, active window unchanged.
- **The window carries no pin.** `hyprctl getprop address:<viola-overseer> stay_focused` → `false`; `no_focus` →
  `false`; `pinned` false, `fullscreen` 0, not grouped, `inhibitingIdle` false. No locker process, `LockedHint=no`.
  Layers: only `omarchy-background` and `omarchy-bar` on each monitor. Submap `default`.
- **Options:** `input:follow_mouse` 1 · `input:mouse_refocus` true · `cursor:no_warps` false ·
  `misc:focus_on_activate` true.
- **Running:** `fcitx5` (an input method), pid 1850.
- **The pair's own launcher uses the same form** and discards its output: `vstart.sh:91` and `:101`
  (`hl.dsp.focus({ window = "address:…" })`), so its working was never read.
