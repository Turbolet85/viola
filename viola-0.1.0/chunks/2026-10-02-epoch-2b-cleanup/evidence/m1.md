## Step 9 — `restrict → Ok(())` (viola-state `src/fs.rs`): equivalent-mutant exemption
- **What the mutant does.** It replaces `restrict`'s body with `Ok(())`.
- **Why it is equivalent on this host.** On every non-Unix target the body already is `let _ = (path, mode); Ok(())`
  (`crates/viola-state/src/fs.rs:22-26`). The mutated function is identical to the original, so no test on Windows can
  tell them apart.
- **Where the effect is witnessed.** The Unix body (`set_permissions` to the explicit mode) is observed by
  `fs_private_modes_are_explicit` (`cfg(unix)`, `crates/viola-state/src/fs.rs:346-348`). It reads the 0700 / 0600 modes
  that this function sets. The mutant is killable only where that body compiles, so it is measured by the split-off WSL
  leg.
- **What this exemption does not claim.** It does not claim that the control is unobservable: its effect is observable
  and witnessed on Unix. On Windows the function sets nothing by design (its doc: "Sets `mode` on `path` on Unix; nothing
  elsewhere"), and viola-state sets no DACL there (a grep for `SetNamedSecurityInfo` / `SetSecurityInfo` /
  `SECURITY_ATTRIBUTES` finds only `viola-channel`'s pipe listener). So there is no Windows effect for a test to read.
- No code change.

## Kill tests landed
- **Step 7 — `search_restricted` ×2** (viola-pty, `crates/viola-pty/src/sideload.rs`):
  `search_restricted_reads_whether_the_restriction_took_effect`. Through the existing child-entry rig, a fresh process
  reports `before=false took=true after=true`. A mutant returning `true` fails `before`; one returning `false` fails `after`.
- **Step 8 — the `NotFound` guards** (viola-state, `crates/viola-state/src/pin.rs`):
  `pin_exe_refuses_a_copy_it_cannot_read_and_leaves_it` (every OS; it replaces the Unix-only
  `pin_exe_refuses_an_unreadable_copy_and_leaves_it`, whose body is its Unix half) and
  `pin_companions_refuses_a_companion_it_cannot_read_and_leaves_it` (Windows). How each case works:
  - It makes the present copy unreadable but still renamable. On Windows that is a deny read-data ACE for the current user,
    set by spawning System32 `icacls.exe` directly. On Unix it is mode 000.
  - It asserts that the call errs and that the tampered bytes are unchanged.
  - A drop guard removes the ACE (Windows) or restores mode 0600 (Unix).
  An achievable Windows form exists, so no exemption is recorded. Under each mutant the guard routes the read error to the
  replace, which renames over the copy, and the case reads red (below).
- **Step 10 — `refuse_stale`** (root, `tests/cli_instance_state.rs`): `run_refuses_a_frozen_wrapper_as_stale_on_windows`.
  The booted wrapper is frozen by a debugger attach (`DebugActiveProcess`, then `DebugSetProcessKillOnExit(FALSE)`, then the
  first debug event received and left unanswered). Its `heartbeat` is back-dated 60 s. The case asserts the exact stderr pair
  `unable: builder is still running but not answering` / `hint: viola list shows it as stale; stop that process before
  starting builder again`, and `refused_with(…, "already-live")`. `Frozen`'s drop detaches with `DebugActiveProcessStop`.
  It uses the root's existing `windows-sys` features: no new dependency or feature.
