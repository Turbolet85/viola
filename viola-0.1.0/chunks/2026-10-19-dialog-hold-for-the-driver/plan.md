## Goal
Close gap-list group 2 (items 27 and 28, `chunks/2026-10-08-first-live-test-and-self-drive/evidence/gap-list.md`),
the one group the founder ruled must close before the overseer switch (the CARRY, his answer to Q3 of chunk
2026-10-17-mcp-server-for-drivers). After this chunk a wrapped session can hold a dialog long enough for a driver to
relay it to a person and back. An expired hold leaves a record that wakes `viola wait`, so the driver learns the
dialog is gone.

The shape is the founder's own word (`inputs#I2`):
- **Q1 «Ключ, по умолчанию 60».** The hold is a new `config.json` key, `dialog_hold_s`: whole seconds from 60 to 3600,
  default 60, read once at the wrapper's start. A bad value falls back to 60 with one `parse-rejected` line. The
  hook's own bound and the `hooks.json` dialog `timeout` are compiled at the 3600 s ceiling, so `plugin/<key>/` stays
  byte-identical across starts. Q1 ratifies the key as a boundary widening.
- **Q2 «Отдать человеку».** At expiry the reply stays `null`: the CLI's own menu renders for the human, and a late
  `answer` is still refused `unknown-dialog`.
- **Q3 «Verify + 1 старт, 11 мин».** One live round on claude 2.1.287 on the Linux dev host: one `viola verify`, then
  one wrapped start whose one dialog is answered after about 11 minutes. No key is typed into any dialog, no ledger
  row is added, and a red is never re-fired.

The rest follows the masters: architecture [Hook Contract], §Standard Contracts and Config management;
security-plan §Input Validation; obs-plan §4; test-plan §4, §5 and §11; design-system / layout-templates cli
pattern 3; a11y-plan §8. The research's corrected premise decides the hook side (`research.md`, scope.md

## Acceptance Criteria
- (arch) `DIALOG_HOLD_DEFAULT` (60 s), `DIALOG_HOLD_MIN` (60 s) and `DIALOG_HOLD_MAX` (3600 s) are the hold's only
  homes. `DIALOG_DEADLINE` is gone from every Rust source (the count entry reads 0). The rendered dialog `timeout`
  (3615) outlasts `DIALOG_HOLD_MAX` by at least 10 s, and the hook's bound is `DIALOG_HOLD_MAX + 5 s` (per
  architecture §Established Decisions [Hook Contract]).
- (arch, security) `config.json`'s `dialog_hold_s` is read once at the wrapper's start, through `take(MAX_FRAME)` and
  `v` = 1. A whole number from 60 to 3600 is the hold. Every other value (0, 59, 3601, -1, 600.5, "600", null, true)
  gives 60 and exactly one `parse-rejected{parser:"config-json", detail:"malformed"}`. No value makes the hold
  unbounded or zero, no env var or flag sets it, and the key is a row of `tests/cli_controls_not_disableable.rs`
  (per security-plan §Input Validation, Configuration values row; §Security Anti-Patterns → Universal;
  architecture §Cross-cutting Patterns, Config management).
- (tests) On the injected clock, a dialog held with a 120 s hold is still pending one `STEP` before the hold and ends
  `null` at it. A human hand-back or an answer before the hold writes no `dialog-expired` line (per test-plan §4;
  §11 Universal).
- (arch, obs) An expired hold appends exactly one `dialog-expired` line with `source` `wrapper` and `data` keys
  exactly `dialog_id` and `dialog_kind`, with no question, plan or tool text. It wakes a parked `wait` (CLI, and the
  `mcp` `wait` through the same document), and the wrapper writes one `dialog-answered` with `deadline_hit` true under
  `corr` = the `dialog_id` (per architecture §Standard Contracts, ndjson event line and `wait`; obs-plan §4 Scenario:
  Dialog → `answer`).
- (arch, security) At expiry the reply stays `null`: the CLI's own menu is the human's, the hook exits 0 with an
  empty stdout, and a late `answer` is refused `not-delivered` / `unknown-dialog`, exit 13 (per architecture
  [Hook Contract]; security-plan §Error Handling; `inputs#I2` Q2).
- (tests) `EventKind::ALL` holds sixteen kinds and `WAIT_WAKE` six. `state_events.rs` round-trips the sixteen with
  zero on all three counts, and `wait_each_wake_kind_wakes` wakes on `dialog-expired` (per test-plan §5 Cross-module
  patterns, On-disk; §4).
- (design, layouts, a11y) `viola wait` woken by `dialog-expired` prints one line,
  `dialog-expired  <name>  dialog <id>  cursor <n>`, ASCII, with no SGR, written once. During a held dialog of any
  length `wait` prints nothing but its one `waiting:` line (per design-system §Surface: cli §Component Patterns 3;
  layout-templates §Output structure — `viola wait` / `viola last`; a11y-plan §4 P6).
- (a11y) The hold falls on the driver only: any human key still hands the held dialog back at once whatever the
  hold, and nothing in the hold or its key adds a human-facing time limit (per a11y-plan §8 Cognitive Accessibility
  → Timeout extensions; §1 tui boundary).
- (tests) The gate block is green: fmt, clippy (the PREREQ closed), G1, lint probes, the unit, integration and E2E
  layers, the named cases, the guards, the booted smoke, G2, G4 and `pre-push`. CI is green on the operator pass's
  final HEAD (per test-plan §3 `run`; §10 Build failure conditions).
- (manual, live) `evidence/live-round.md` records the round on claude 2.1.287 on the Linux dev host inside the
  founder's cap (`inputs#I2` Q3): one `viola verify` (`stamped 2.1.287  24 pass  0 fail`) and one wrapped start, each
  ledgered before it is made, no key typed into any dialog, no red re-fired. With `dialog_hold_s` 3600 it records:

  - the wrapper's `dialog-answered` with `deadline_hit` false and `duration_ms` ≥ 660 000;

  - `list`'s `dialog_pending` true at 300 s.

  The reading is taken for Linux; its Windows leg is owed to "Windows-only live measurements" (per architecture

- (security, obs) No file under `evidence/` holds a `CLAUDE*` value, an absolute path, prompt, question or assistant

## Constraints & rejected approaches
- A viola-built deny, or any decision, at expiry: rejected by the founder (`inputs#I2` Q2).
- A `hooks.json` timeout rendered per start from the configured hold: rejected. It breaks
  `replace_private_shared`'s identical-bytes premise for `plugin/<key>/` (security-plan §Data Protection), and the
  ceiling already suffices (research).
- An env var, a flag or a `VIOLA_*` variable for the hold, or any value meaning "forever" or "off": banned
  (security-plan §Security Anti-Patterns → Universal).
- A test seam shortening the hold, or an E2E case waiting out a real hold: not added. A seam needs a Decisions Log
  entry, and test-plan §11 keeps clock cases at the unit tier.
- A ledger row or `viola verify` probe for the CLI honouring a long hook timeout: not made (`inputs#I2` Q3, the ruled
  limit).
- A `dialog-expired` record on a human hand-back: not written. A hand-back is the human taking the dialog, not an
  expiry.
- A new obs `event` value or a new refusal detail word: none (the leans above).
- A key typed into any dialog in the live round, a fresh `proj/` that would show the trust dialog, a second wrapped
  start, or a re-fire after a red: not made (`inputs#I2` Q3).
