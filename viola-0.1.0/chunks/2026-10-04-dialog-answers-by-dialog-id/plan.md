## Goal
Land the dialog tier. A `question`, `permission` or `plan` dialog raised through the PreToolUse (`AskUserQuestion|ExitPlanMode`) and PermissionRequest hooks is logged exactly once with a wrapper-assigned `dialog_id`. It wakes a parked `wait`, including the without-`after` pending-dialog return `:76` left here. A driver can answer it by id with `viola answer`, and the hook prints the matching S3 / S7 / S8 decision body. One dialog is pending per instance; a second concurrent one, an unverified CLI or an expired 60 s deadline each leave the dialog to the human. An unknown id is refused `unknown-dialog` (exit 13). viola stays mechanism: it carries the driver's typed answer and never picks one (architecture §Established Decisions, the first principle; [Message Broker / IPC]; [Hook Contract]; §Standard Contracts `hook.dialog` / `answer`).

12. **The dialog slot** (new `src/run/dialog.rs`, wired in `src/cmd/run.rs` `Methods`):

    - **`hook.dialog` raise:** re-validate the kind (closed) and `data` (an object); assign the next id; append the dialog event (`source: hook`, `data` + `dialog_id`) through `WaitFeed::appending` BEFORE any reply (`architecture.md:307`). Then:
      - reply `null` at once when the snapshot's `cli_verified` is false, or another dialog is pending (the event is still logged);
      - else hold it pending (`pending_dialog {dialog_id, kind}` written to the snapshot through the one writer) and wait on a Condvar until an answer arrives or `DIALOG_DEADLINE` passes on the injected `Clock`;
      - on expiry, clear the pending dialog, rewrite the snapshot and reply `null`.
      - When `cli_verified` is true the decision flows on the 6-row spine stamp (the founder's dated gap to `:82`); nothing here reads a dialog row.
    - **The continuation** (S7; overseer resolution 2). Every raise from PreToolUse `ExitPlanMode` / `AskUserQuestion` records, per tool, `{dialog_id, kind, tool_input, outcome}` as the tool's ARMED continuation (replacing any earlier one of that tool). A `hook.dialog` continuation (PermissionRequest of that tool) whose `tool_input` equals the armed one's is the SAME dialog: it consumes the arm, appends NO event and replies at once — a `plan` answered `revise` → its `deny` + `message`; every other outcome (`approve`, a `question` answered, `null`, expired) → `null`. A continuation with no matching arm (a restart between the hooks, an unequal `tool_input`) is raised as its own dialog of the tool's kind (`plan` / `question`) and logged once; a `plan` so raised answers `revise` → PermissionRequest `deny` + `message` and `approve` → no body (the ignored path); a `question` so raised replies `null` at once and is left to the human (the PermissionRequest body for `AskUserQuestion` is unmeasured — owed to `:82`).
    - **`answer` `{dialog_id, from?, response}`** → `{}`, checked in order:
      - closed params: a non-`u64` id, a bad `from` or a malformed `response` is `-32602`, `data: null`;
      - `validate_paste_text` over every free-text value → `not-delivered`/`control-character`;
      - `cli_verified` false → `unverified-cli`;
      - an id that is not the pending one → `not-delivered`/`unknown-dialog`;
      - a `response` shape that is not the pending kind's → `-32602`;
      - else hand the answer to the waiting `hook.dialog` worker and clear the pending dialog.
      - No `human-typing` check and no link recording: the wheel and links are `:80`'s and `:93`'s (scope).
    - Obs (obs-plan §4 Scenario "Dialog → `answer`"):
      - spans `run.dialog_register` (`dialog_kind`, `pending_conflict`) and `run.dialog_await` (`deadline_ms`, `deadline_hit`);
      - `dialog-raised{corr:<dialog_id>, dialog_kind, hook_event}`;
      - `dialog-answered{corr, dialog_kind, from, from_trust:"self-reported", deadline_hit, duration_ms}`;
      - no question, answer or tool-input text on a home-level line.
