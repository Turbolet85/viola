**A11y tier:** `Standard (1)`
_Justification: cli and tui get output-discipline and boundary assertions plus manual screen-reader passes, with no WCAG conformance claim._

**A11y scope (entities needing assertions):**

The frontend is deferred to 0.2.0; its technology is not chosen.

**CLI and terminal entities**

- **Entity:** CLI verbs (`list`, `send`, `wait`, `last`, `answer`, `verify`, `pause`, `release`, `link`, `unlink`, `revive`, `plugin install`, `--help`) in human TTY, plain (non-TTY / `NO_COLOR` / `TERM=dumb`) and `--json` modes — assertable: output-discipline assertions on text and streams only; no automated a11y tool reaches a terminal.

- **Under `viola revive --json`:** every refusal of the start it shares with `run` prints one exit-1 document, `batch-script-child`, `pinned-hash-mismatch` and `squatted-name` among them and a program not found `internal-error`; a `pump_child` error prints none: the child has held the terminal, and viola writes nothing past it.

- **Entity:** `viola run` TUI passthrough, entered by `viola run` and by a `viola revive` whose preflight passed — boundary-only: the rendered content belongs to the vendor (`claude`) and is not traced; viola writes zero bytes to the terminal except the child's output, human keystrokes are never blocked, refused or delayed past the current atomic paste, and focus, mouse and resize sequences and terminal replies pass through and do not count as human editing; the boundary still holds after a contained vt100 feed panic (no viola literal on the outer terminal on every OS, the child's own bytes on Unix), its Windows byte reading owed to "Windows-only live measurements".

**Not-assertable (no UI surface)**

- **Entity:** Claude Code plugin: hooks (`viola hook`, `hook statusline`) and the stdio MCP server; wrapper IPC channel
  - **Source:** Arch excerpt, Surfaces ("a Claude Code plugin (hooks + stdio MCP server)"). Tests excerpt, E2E driver → ipc-internal and cli (`viola hook`).
  - **Assertability:** not-assertable
  - **Reason:** ipc-internal with no UI surface. Machine-to-machine traffic only.

- **Entity:** Internal crates (modular monolith)
  - **Source:** Arch excerpt, Project Intent ("one binary with compiler-enforced internal crates"). Tests excerpt, E2E driver → library-only.
  - **Assertability:** not-assertable
  - **Reason:** Library-only with no UI surface.

**Boundary-only vendor zones:** the only vendor-content boundary is the `viola run` TUI above, which a passed `viola revive` enters too.

**Compliance cross-check:** the security excerpt's A11y Compliance Triggers name no regime (no Section 508 / ADA / EAA / EN 301 549 / AODA / JIS X 8341). No regime-mandated SC applies to any surface.

**A11y surfaces & assistive tech reach:**

- **Surface:** cli (`viola` verbs) — no automated a11y tool reaches terminal output: output-discipline assertions on the existing CLI drivers stand in, and no WCAG conformance claim may rest on them; colour is only a second cue; no SGR, glyph or cursor control under `--json`, non-TTY, `NO_COLOR`, `TERM=dumb`, `viola run` or a passed `viola revive`; output is static and linear; C0/C1 control characters are escaped except `\n` and `\t`, which `list` rows escape too.

- **Surface:** tui (`viola run` passthrough, entered by a passed `viola revive` too; boundary-only) — no automated a11y tool applies and the rendered vendor `claude` TUI is never parsed; boundary assertions on the portable-pty outer-PTY driver check that viola emits zero terminal bytes of its own and never blocks or delays human keystrokes; viola's diagnostics for `run` go to `diagnostics/`, never to the terminal; a boundary guarantee only, no conformance claim about `claude`'s TUI.

**A11y assertion harness specification:**

- **A11y testing tool pick:**
  - **cli / tui:** no a11y tool. Use the existing `assert_cmd` / `trycmd` / portable-pty output-discipline assertions, with manual screen-reader passes as a supplement.

- **Keyboard test harness:**
  - **cli:** keyboard is not interactive. There is no prompt, TUI mode or pager. Assertions cover stdin/`--file` input only (arch excerpt, Critical paths hint 7).
  - **tui:** the automated boundary is that human keystrokes through the portable-pty outer PTY are never blocked. A manual keyboard pass is supplemental (Overseer Direction 5).

- **Screen reader test pattern:**
  - **Manual pass (supplemental):** NVDA (Windows Terminal), VoiceOver (macOS) and Orca (Linux) on Section 4 P4 and P6. It is founder-owned per the creator brief excerpt, Appendix A.

- **CI integration:**
  - **Runner:** tests' 5-command discipline, `scripts/agent-run.sh run` (or `.ps1`). 0.1.0 runs no browser a11y leg: it renders no page, and the frontend's a11y tooling is a 0.2.0 input, its technology not chosen.
  - **Where results land:** inside the existing suite entries of the `run` JSON (`suites[{suite:"nextest-integration"|"nextest-e2e"|"coverage",…}]`, with failures in `suites[].failures[]`).

## 8. Cognitive Accessibility

_Scope: no `cognitive-accessibility` trigger fired (a11y-scope Sec 5), so there is no AAA escalation. SC 2.2.6, 3.1.5 and 3.3.9 are not claimed. This section covers only the cognitive-relevant AA/A criteria that have a v1 surface. Every item below has an agent-runnable path built from research tools only._

### Timeout extensions

Detail: .andromeda/a11y-plan-detail/cognitive-accessibility.md — read whole.

- **Pattern:** v1 has no time limit, so there is nothing to warn about or extend.
- **Implementation:** no timeout-extension component is needed, and none is researched or adopted.

- **CLI:** every time bound viola holds — the `viola wait` timeout the caller passes, the MCP `wait` cap, the dialog hold, the `viola send` readiness gate, the confirmation windows, the status-line deadline, the `claude agents --json` read, the budget pause — falls on the driver, the user's own command or viola's own child, never on the human: no key is blocked, refused or delayed by it. There is no conformance claim for the terminal.

### Error recovery

Detail: .andromeda/a11y-plan-detail/cognitive-accessibility.md — read whole.

- **Pattern:** every error is a printed word followed by plain detail, and a recovery instruction where recovery exists; on the CLI, `unable  <reason>  <detail>` on stderr (`viola revive`'s exit-1 refusals and `viola verify`'s interrupted pair: one `unable: <text>` line), then `hint:` as the last stderr line, with a typed exit code; the one refusal with no hint is `unknown` (exit 14), whose detail is a code word or nothing, opaque to a reader; faults are not refusals and carry no hint; `--json` gives one document with no hint, except the `viola answer` and `viola send` exit-2 paths (a fixed stderr line, no document).

- **WCAG SC:** SC 3.3.1 Error Identification (A) + SC 3.3.3 Error Suggestion (AA).

- **Verification:** trycmd pins the `unable <reason> <detail>` + final `hint:` layout per refusal and assert_cmd the typed exit codes and a hint-free `--json`, on all three OS legs (the frame verbs' server-verify refusal on windows-2025 and ubuntu-latest only: macOS reports no peer pid).

### Plain language

Detail: .andromeda/a11y-plan-detail/cognitive-accessibility.md — read whole.

- **Reading level target:** none gated. SC 3.1.5 Reading Level (AAA) is not claimed, and no readability scorer is in a11y-research, so none is introduced (Decisions Log D-A11Y-16).
- **Pattern:**
  - The fixed copy set comes from design: `no wrapped sessions — start one with  viola run <name> -- claude`, `unknown` and `n/a`.
  - Every kebab-case reason/detail code (`not-delivered`, `human-typing`, `unverified-cli`) always sits beside the plain word `unable`.
  - The CLI never shows a stack trace or bare status number as the only error text.

- **Verification:** every fixed CLI string is pinned, by trycmd or, for `viola list`, `viola --help`, `viola plugin install`, the server-verify, `unwrapped-name` and `endpoint-lost` hints and the `viola link` / `viola unlink` result lines, by literal, so any copy change fails CI until the pinned string is updated on purpose.

### Consistency and predictability

Detail: .andromeda/a11y-plan-detail/cognitive-accessibility.md — read whole.

- **Consistent identification (SC 3.2.4, AA):** the `CAPTION` literal pins the caption order `NAME · LIVE · STATUS · WHEEL · DIALOG · CLI` for `viola list`.

- **Verification sources:** trycmd.

## 11. A11y Anti-Patterns (NEVER do these)

### Strategy

- NEVER claim WCAG conformance for the cli or the `viola run` TUI (the wrapper-hosted TUI, whether `viola run` or a passed `viola revive` started it). assert_cmd / trycmd / portable-pty results are output-discipline stand-ins for SC 1.3.2 / 1.4.1 / 3.3.1, not a11y-tool evidence.

### Keyboard

- NEVER block, refuse or delay a human keystroke in `viola run`, or in a start a passed `viola revive` made, past the current atomic paste, and never count focus / mouse / resize sequences or terminal replies as editing (P4) — a mouse report the Windows ConPTY already turned into win32 key-down records is typing (F-W3).

### Visual

- NEVER convey information by color alone (state indicators must
  have text / icon supplement per SC 1.4.1)
- NEVER colour CLI `unable` / `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` / a passed `viola revive`.

### Cognitive

- NEVER set harsh timeouts without warning (no warn-extend pattern per SC 2.2.1). v1 has none.
- NEVER show error without recovery suggestion (per SC 3.3.3). Every human-mode CLI refusal except `unknown` (exit 14, its detail a code word or nothing, design cli) ends with a `hint:` line.
- NEVER use jargon without a plain alternative. SC 3.1.5 AAA is not claimed, but a kebab-case reason/detail code (`not-delivered`, `human-typing`, `unverified-cli`) never appears without the plain word `unable`.
- NEVER render a stack trace as the only error text in the CLI.
- NEVER let the caption set or order of CLI `viola list` (NAME · LIVE · STATUS · WHEEL · DIALOG · CLI) drift from its `CAPTION` literal (SC 3.2.4).

### Motion

- NEVER add spinners (design ban).

### CI

- NEVER skip a11y on CI failure (a11y is FAIL-fast gate, not warning)
- NEVER use human-only a11y review without machine output (canonical
  agent-runnable principle)
- NEVER add a `suite` value (such as `a11y`) or a separate a11y driver outside `scripts/agent-run.* run`.

### SLO

- NEVER use retry-once policy for a11y violations — masks real
  failures (parallel to tests' zero-flakiness)
- NEVER define soft a11y SLO (must trigger build / deploy failure
  on threshold)

### Universal (agent-driven specific)

- NEVER use manual screen reader / keyboard / contrast as ONLY
  method — supplemental to automated tools OK
- NEVER use vendor-locked a11y tool as ONLY method (Stark Visual
  Studio plugin without machine output / Tenable.io UI-only without API)
- NEVER parse the rendered `claude` TUI screen for content or take screenshots as a11y evidence (R7; tests "no screen-content parsing").
