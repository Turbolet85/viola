- **cli (short-lived verbs), the server check:** each of the eight frame verbs (`send`, `wait`, `last`, `answer`, `pause`, `release`, `link`, `unlink`) verifies the wrapper through `cmd::client::connect` inside its dispatch span, after its own client-side refusals (for each of the eight, the instance check `client::refuse_untrusted` first, of the driven instance for `link` / `unlink`, then the liveness pre-check) and before any frame: the connected stream's peer pid and that process's OS start time against the one snapshot read, a closed `ServerVerdict` (`Matches|Mismatch|Unverifiable`). A mismatch or a check that cannot be made opens no `channel.request` span, writes no `channel-request` line and ends `process-exit{subject:"self", exit_code:21, detail:"server-verify-failed", during:"connect"}`. Linux and Windows; macOS reports no peer pid and stays on the recorded gap.
- The refusal's place is asserted by captured-span cases, one per CLI frame verb (`request_refuses_an_unverified_server_inside_its_dispatch_span` in each verb's module) and one for the hook (`hook_refuses_an_unverified_server_inside_hook_handle`), each through the shared test-only helper `cmd::client::refused_inside` (`assert_refused_inside`): the refusal happens inside its scenario's root span, and each case reads red with the check removed.
- **cli (short-lived verbs), the instance check:** the six frame verbs (`send`, `wait`, `last`, `answer`, `pause`, `release`) run `client::refuse_untrusted`, the instance check `link` / `unlink` share, on their named instance before any role file opens; a refused check (exit 21, the instance pair on stderr, or under `--json` exactly `{"v":1,"error":"instance-unreachable","detail":null}`) opens no process log and writes no line.
- **cli (`viola hook`), the server check:** the event and dialog paths share one `connect` inside `hook.handle` (`read_snapshot_or_replay`, its span `state.snapshot_recover` under `hook.handle`, then `connect_by`, then `verify_server`) before any frame. Only a snapshot read whole goes on: a replayed snapshot (it carries no `endpoint`, `pid` or `started_at`) or an absent one is unreachable, so no frame is sent and the hook fails open with `hook-decision{detail:"channel-unreachable"}`, a SessionEnd taking the direct `append_session_end`. A server that is not the recorded wrapper, or a check that cannot be made, gets no frame: no `channel.request` opens, and the hook fails open (exit 0, empty streams) with `hook-decision{detail:"server-verify-failed"}`; a SessionEnd whose check fails takes the direct `append_session_end`. Linux and Windows; macOS on the recorded gap.
- **ipc-internal (viola-mcp), the server check:** the frame tools `send`, `wait`, `last` and `answer` first run `check_instance` on their instance, before `live_endpoint` (a refusal returns `instance-unreachable` with `detail: null`, no frame and no line), then verify the wrapper after `TokioClient::connect`, inside `mcp.tool_call` (`server_verified`, the start time read on `tokio::task::spawn_blocking`). A mismatch or a check that cannot be made returns the codes-only `isError` `instance-unreachable` with no frame and no log line, as the unreachable path does. Linux and Windows; macOS on the recorded gap.

## 4. Span / Trace Coverage › #### Scenario: `viola run` start sequence to child spawn

<!-- detail: values · scenario-viola-run-start-sequence-to-child-spawn -->

- **Must-trace spans:** `run.start` (INTERNAL, root) › `state.snapshot_recover` (the start's one snapshot read, `read_snapshot_or_replay`, which the collision check takes) › `run.collision_check` › `run.pin_copy` › `run.conpty_sideload` (Windows) › `run.version_gate` (spawns the `version-probe`) › `channel.bind` › `run.budget_eval` (INTERNAL, `trigger="start"`; its attributes are under Scenario: Budget governor; chunk 2026-10-10-budget-governor) › `state.snapshot_write` › `state.heartbeat_start` › `pty.spawn` (CLIENT). Two start steps carry no span and no log line, by design (the operator's answer at the chunk 2026-10-10-statusline-pass-through wrap; that chunk's plan added no span name): the statusline source read, whose result is the snapshot's `statusline_command`, and the settings override write (`instances/<name>/settings.json` through `replace_private`, Unix only), which sits between the first snapshot and `pty.spawn`. The child's `--settings` argument, the source path and the command appear in no line or span. A third start step carries none either, as landed (chunk 2026-10-10-session-links): the link set's restore, one read pass over the instance's `events.ndjson` through `viola_state::events::read_from`, made beside the wait feed's rebuild and before the endpoint serves. It appends nothing and logs nothing, its result is the first snapshot's `links`, and the start appends no record for links, so the span chain above and the product order below are unchanged; `viola revive` starts through the same function.
- **Required span attributes:**
  - `run.start`: `instance`;
  - `run.collision_check`: `outcome` (`free|already-live|squatted-name`) — a `live` or `stale` holder is `already-live`; a `gone` one is `free` (taken over, its `events.ndjson` appended to); over a replayed snapshot, which carries no pid or start time, the heartbeat alone decides (a beat no older than `STALE_AFTER` is `already-live`, an older one `free`), and an absent snapshot or a failed read is `free`;
  - `run.pin_copy`: `outcome` (`ok|pinned-hash-mismatch`); the `.cmd`/`.bat` refusal (`batch-script-child`) is decided earlier, by viola-side program resolution (`resolve_program`, after obs init and before the strip plan and `pty.spawn`), and logged as `process-exit{subject:"self", exit_code:1, detail:"batch-script-child"}` with no child spawned and no `process-start{subject:"claude-child"}`;
  - `run.conpty_sideload` (Windows): `outcome` (`loaded|hash-mismatch|strict-modes-failed|unreadable|load-failed|not-built`; `strict-modes-failed` when the owner/DACL check refuses the `conpty/` dir or a companion, `PinError::StrictModes`, nothing written), `search_restricted` (bool) — never a refusal and never an exit change: any outcome but `loaded` leaves the child on the inbox ConPTY; never the companions' paths or hashes (D-36);
  - `run.version_gate`: `cli_version`, `cli_verified`;
  - `channel.bind`: `endpoint_kind` (`named-pipe|unix-socket`);
  - `state.snapshot_write`: `v`;
  - `pty.spawn`: `pty_backend` (`conpty-sideload|conpty|openpty`, from `viola_pty::pty_backend()`; `conpty-sideload` after a successful pre-load), `env_stripped_count`.
  - Never the endpoint name, `pinned_bin` path or env values.
- **Required log fields:**
  - Common fields with `process="run"` and `corr` null.
  - `process-start{subject:"self", service_name, version, os, pid, endpoint_kind}`.
  - `process-start` / `process-exit{subject:"version-probe", child_exit_status, duration_ms}`.
  - On failure, `process-exit{subject:"self", exit_code:1, detail}` with `detail` ∈ `already-live|squatted-name|pinned-hash-mismatch|batch-script-child` (Founder Direction 4; no path or pid). Before that log opens, the start (`run`'s, and `viola revive`'s) runs the home-tree check `check_home_tree` (through `checked_exe` and `refuse_tree`) on the home (to the read rule), the instance's set, `ledger/`, `bin/`, `plugin/`, `bin/<key>/`, the pinned exe, `plugin/<key>/` and its `hooks/` and `.claude-plugin/`: a refusal exits 1 with the home pair or the instance pair on stderr (`viola revive --json`: its `strict-modes-failed` document), opens no log, writes no line and starts no child, so it carries no `detail`. `viola revive` enters the same sequence through the same start, after an instance check that precedes the log init and writes no line when it refuses, then a preflight of its own, which makes one snapshot read and hands it to both its collision check and its recorded-directory reading (over an unreadable snapshot one replay, so one `state-recovered` line), whose refusals add `detail` ∈ `no-session|session-live|cwd-missing` (and `already-live`, from the same collision check) before any child is started; its `session-live` reading (skipped under `--fork`) writes one `process-start` / `process-exit{subject:"agents-probe"}` pair in `run-<name>.ndjson`, plus one `parse-rejected{parser:"claude-agents-json"}` on an oversize or malformed answer, and passes on a failed read; a revive that passes its preflight runs `run.collision_check` twice, once in the preflight and once inside the start.
  - On success, `process-start{subject:"claude-child", child_pid, pty_backend, cli_version, cli_verified, env_stripped_count, env_stripped_known, env_kept}` (D-34), plus, on Windows when the `run.conpty_sideload` outcome is not `loaded`, `sideload_fallback` (`hash-mismatch|strict-modes-failed|unreadable|load-failed|not-built`, D-36). A degraded sideload adds no `process-exit{exit_code:1}` and no panic line.
  - In `schemas/diag-line.v1.json`, `pty_backend` is `{ "type": "string" }`, while `sideload_fallback` is closed in the `process-start` properties to `hash-mismatch|strict-modes-failed|unreadable|load-failed|not-built` (`diag-detail.v1.json` carries neither). A sideload degrade is recorded on the existing info-level lines, never at `warn`, and no companion path or hash reaches a home-level line (D-36).
  - Product order `wheel{cause:"start"}` → `budget-gate` → `session-start` is verified from `events.ndjson` through `agent-run logs --kind`, not duplicated into process logs (`run` writes the first two; `session-start{source:"hook"}` is record three, sent by `viola hook` through `hook.event` since "Hooks to normalised events"; the harness `boot` readiness stage `start_records` checks `events.ndjson` lines 1-3 — `wheel{cause:"start"}` → `budget-gate` → `session-start{source:"hook"}` — with the missing code `<name>:events`).
- **Cleanup:**
  - `run.start` closes when `pty.spawn` returns.
  - The handle-wait thread emits `process-exit{subject:"claude-child", child_exit_status, exit_source:"handle-wait"|"kill-fallback"}`, never on reader EOF (ConPTY chaos class). `run` then emits `process-exit{subject:"self", exit_code, duration_ms}`.

## 4. Span / Trace Coverage › #### Scenario: Confirmed `send` (CL-1) from driver to readback

<!-- detail: values · scenario-confirmed-send-cl-1-from-driver-to-readback -->

- **Must-trace spans:** `send.client` (CLIENT; `cli` or `mcp.tool_call`) › `channel.request` (CLIENT) → `channel.dispatch` (SERVER, `run`) › `run.readiness_gate` › `pty.paste_write` › `run.confirm_window`. An unconfirmable send ends at `pty.paste_write` and opens no `run.confirm_window`. In the hook process: `hook.handle` › `channel.request(hook.event)`, the user-prompt-submit hook for an ordinary send and the session-start hook for a `/clear` confirmed by its new session or a `/compact` confirmed by its same session (verified CLI). One operation on this path carries no span and no line of its own, as landed (chunk 2026-10-10-session-links): the implicit link record (E3 below). After the second wheel and running-turn reads and directly before the send is issued, a `send` whose `from` is a name other than the wrapper's own records the link, so a new pair's `link` product line stands directly before that send's `send-issued` in `events.ndjson`, whose `cursor` is still the offset its own line starts at; a send refused at any earlier rung, one with no `from` and one under the wrapper's own name record nothing. A record that fails answers `-32603` with nothing issued and nothing typed, so no `send-issued` is written. `driver` and `driven` reach no process-log line.
  - The instance check comes first: CLI `send` runs `client::refuse_untrusted` after its text read and before any role file opens, and MCP `send` runs `check_instance` before `live_endpoint`; a refusal sends no frame and writes no line. The server check runs before `channel.request`, inside `send.client` (CLI) or `mcp.tool_call` (MCP): the peer pid and its start time against the one snapshot read, `live_endpoint`'s `read_snapshot_or_replay` (a replayed snapshot carries no `endpoint`, `pid` or `started_at`, so the path ends as unreachable). A server that is not the recorded wrapper, or a check that cannot be made, opens no `channel.request`, and the path ends there (Linux and Windows; macOS on the recorded gap).
- **Required span attributes:**
  - `channel.request` / `channel.dispatch`: `method="send"`, `conn`;
  - `run.readiness_gate`: `outcome` (`ready|input-not-ready`), `vt100_panicked` (bool);
  - `pty.paste_write`: `text_bytes` (the length of the typed text: the sent text with every CR LF pair and every other CR as one LF, and without its trailing CR and LF characters), `paste_mode="bracketed"`;
  - `run.confirm_window`: `window_ms`, the bound the send's own deadline reads (`SendSlot::window()`): 40 000 for a `/compact` send waiting for its compacted-session post-condition (`COMPACT_CONFIRM_WINDOW`, PROVISIONAL), else 10 000 (`CONFIRM_WINDOW_FALLBACK`).
  - Never text.
- **Required log fields:** common fields plus:
  - `channel-request{corr:<id>, conn, method, from, from_trust:"self-reported", sender}`;
  - `send-issued{corr:<cursor>, from, text_bytes}`, `text_bytes` the same typed-text length as on the span;
  - hook: `hook-invoked{hook_event:"user-prompt-submit", corr:null}` for an ordinary send; `hook-invoked{hook_event:"session-start", corr:null}` for a `/clear` confirmed by its new session or a `/compact` confirmed by its same session (verified CLI), no new event, detail or field (as landed, `src/cmd/hook.rs`: every hook invocation logs `hook-invoked` with its own `hook_event`; the line was not read on this path); an unconfirmable send waits for no hook line;
  - `send-confirmed{corr:<cursor>, confirmed, duration_ms}` (`confirmed:false` for `unconfirmable`; `duration_ms` runs from the send's arrival, the readiness gate's wait included);
  - or `send-refused{corr:<cursor>, refusal, detail, side:"wrapper", wheel}` with `detail` ∈ `input-not-ready|no-prompt-submitted|turn-running`. `turn-running` has two causes under the one closed detail and no new field: a running turn, or another `send` in flight. The running turn is in-memory wrapper state — marked by a `prompt-submitted` of any origin, ended by `turn-ended` / `session-start` / `session-end` or cleared by a `release` that returns the wheel — and writes no event, span or log line of its own. Either cause's refusal is this wrapper `send-refused` with no `cursor` (`corr` the end offset at refusal, D-28) and no `send-issued`, and the client exits 13;
  - client-side validation refusal, made before any frame: `send-refused{corr:null, refusal:"not-delivered", detail:"control-character"|"empty-text", side:"client"}`, with a mirror line on the wrapper side if the frame reached it. `empty-text` is an empty typed text, read after `control-character` and ahead of both wheel reads; the wrapper, deciding it on a frame sent straight to it, writes its own `send-refused{side:"wrapper"}` line with the same pair and `corr`, `conn` and `rpc_id`, and no `send-issued`. One line per deciding side, never the text;
  - client-side server-verification refusal, made after the client's own refusals and before any frame (Linux and Windows): no `channel-request` / `channel-response` line on either side; CLI `send` ends `process-exit{subject:"self", exit_code:21, detail:"server-verify-failed", during:"connect"}` at WARN, and MCP `send` writes no line;
  - `channel-response{corr:<id>, conn, result_class, refusal, detail, duration_ms}` on both sides;
  - every wrapper `send-*` line (here and in Scenarios 5 and 6) also carries `conn` (or `srv_conn`) and `rpc_id`, so `(conn, rpc_id)` on the send line equals `(conn, corr)` on this call's `channel-*` lines (D-30). The client-side `send-refused{side:"client"}` carries neither.
- **Cleanup:** `run.confirm_window` closes on the confirmation its send waits for, or on window expiry. For an ordinary send that is the matching `prompt-submitted{origin:"driver"}`. For a listed local command with a new-session post-condition on a verified CLI (`/clear`) it is the `session-start` whose `cause` is `clear` and whose `agent_session_id` is a string that differs from the id the send slot remembers; that send waits for its post-condition only, and no `prompt-submitted` claims it. For a listed local command with a compacted-session post-condition on a verified CLI (`/compact`) it is the `session-start` whose `cause` is `compact` and whose `agent_session_id` is a string equal to the id the send slot remembered before that line (nothing remembered claims nothing), no `prompt-submitted` claiming it either; its window is `COMPACT_CONFIRM_WINDOW` (40 s, PROVISIONAL), every other confirmed send's `CONFIRM_WINDOW_FALLBACK` (10 s). Expiry is `send-refused{detail:"no-prompt-submitted"}` for all three (no new detail). An unconfirmable send (a listed command with no post-condition, or any listed command on an unverified CLI) opens no `run.confirm_window`. `channel-response` is emitted from a `Drop` guard in `channel.dispatch`, so an early return or error still logs it. `send.client` closes with `process-exit{subject:"self", exit_code}` (0 / 10 / 11 / 12 / 13 / 14 / 20 / 21, or 1 `internal-error` on a reply with neither a parseable `result` nor an `error.code`); exit 20 carries `detail:"wrapper-fault"`, and exit 21 `detail:"instance-dead"` with `during` `connect` (no live snapshot, a replayed one included, or the connect failed) or `call` (the connection lost after it), or `detail:"server-verify-failed"` with `during:"connect"` (the serving process is not the recorded wrapper, or the check cannot be made; no frame sent; Linux and Windows, macOS on the recorded gap).
  - A `send` its instance check refuses (`client::refuse_untrusted`: exit 21, the instance pair, or under `--json` the `instance-unreachable` document) is refused before any role file opens: no `send.client` span, no `process-exit` and no line.

## 4. Span / Trace Coverage › #### Scenario: Dialog → `answer` (question / permission / plan), including the unverified-CLI branch

<!-- detail: values · scenario-dialog-answer-question-permission-plan-including-the-unverified-cli-branch -->

- **Must-trace spans:** `hook.handle` (SERVER) › `channel.request(hook.dialog)` → `channel.dispatch` › `run.dialog_register` › `run.dialog_await` › `hook.decision_emit`. Driver side: `answer.client` › `channel.request(answer)` → `channel.dispatch`. One operation on the driver side carries no span and no line of its own, as landed (chunk 2026-10-10-session-links): the implicit link record in the wrapper's `answer` handling (E3 below).
