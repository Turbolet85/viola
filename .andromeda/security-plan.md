## Threat Model Summary

_[ALL tiers — VERBATIM copy from threat-assessment.md]_

**Security tier:** `Minimal (0), with targeted elevations for the local privilege boundary`
_Justification: viola is a local-only, single-user tool. It has no accounts, no public network listener, no database, no stored credentials and no regulated data (Sections 1, 3, 4, 5), which rules out Standard's user-account and HTTPS concerns and Hardened's compliance drivers. It still goes beyond a plain Minimal profile in two ways. First, the local IPC endpoint is effectively a code-execution interface (`send` types prompts, `answer` can allow PermissionRequest tool calls). It currently has no decided per-OS enforcement of its same-OS-user boundary, and its names are predictable in shared namespaces (Windows pipes, `/tmp`). Second, several state files decide what code runs and whether dialogs are answered: `snapshot.json`'s `statusline_command`, the `hooks.json` exec paths, the pinned binaries and the ledger stamps. The baseline is therefore Minimal (dependency audit, input validation on config and external payloads, error sanitization). On top of it sit specific local-boundary items: IPC endpoint access control and server impersonation, bracketed-paste breakout in `send.text`, and integrity of `~/.viola/`. Each of these traces to Section 2._

**Data classification:**
- **Type:** user-content (prompt text and assistant output)
  - **Where:** `instances/<ViolaName>/events.ndjson`. `prompt-submitted.data.text` holds every submitted prompt (driver, human and harness), and `turn-ended.data.last_assistant_message` holds each final assistant reply. The wrapper keeps the latest reply in memory for `last`. The same lines go out verbatim over MCP `wait`/`last` and over CLI `wait`/`last` (Standard Contracts: event `data` per kind. Occupied Resources: Filesystem).
  - **Volume:** Per-user, persistent and growing. The file is never rotated or truncated, and bounding its size is an open item (Occupied Resources: Filesystem). Instance directories are reused and appended to, so it builds up across sessions (Established Decisions: Session Liveness).
- **Type:** user-content (tool-call arguments, plans, dialog questions and answers). This may incidentally include secrets or personal data the user's session touches.
  - **Where:** The `permission` event carries `{tool, input}`, where `input` is the tool call's full arguments as JSON. For Bash and Write-type tools that means shell commands and file bodies. `plan` carries the plan text and `question` carries questions, options and each option's description and preview text (`option_details`), which also go out over CLI `wait --json` and MCP `wait`. All of it is logged to `events.ndjson` and sent over the local-socket channel in `hook.dialog` (Standard Contracts: Event `data` per kind, `hook.dialog`).
  - **Volume:** Per-user, persistent, same retention as above.
- **Type:** config (includes a stored executable command string)
  - **Where:**
    - `config.json` holds budget thresholds.
    - `instances/<ViolaName>/settings.json` is the per-session statusline override. It holds `{"statusLine":{"type":"command","command":"<pinned path> hook statusline"}}`, never the user's command.
    - `snapshot.json` stores `statusline_command`, the user-written shell string that `hook statusline` reads through `VIOLA_DIR` and runs through a shell. This is the only shell-out in viola.
    - `<home>/statusline-source.json` (the Claude settings shape; viola only reads it) and, for the default home only, the user's `~/.claude/settings.json` are the inputs that decide `statusline_command` at each start.
    - `snapshot.json` also stores `endpoint`, the socket path clients connect to, and `pinned_bin`.
    - `ledger/stamps.json` holds the verified CLI versions. A stamp is what switches on dialog answering.
    - `plugin/<version>-<hash>/hooks/hooks.json` and `.mcp.json` hold the absolute exec paths Claude Code runs for every hook and for MCP.
    - `marketplace/viola/.mcp.json`, written by `viola plugin install`, holds the absolute exec path Claude Code runs for MCP in a session that installed the plugin.
    - `bin/<version>-<hash>/viola(.exe)` is the pinned executable.
    - Sources: Occupied Resources (Filesystem, Claude Code integration names); Standard Contracts (Hook contract, Instance snapshot); Established Decisions (Deployment / Distribution, CLI Version Compatibility).
  - **Volume:** Per-user, persistent. These are integrity-sensitive more than confidentiality-sensitive, because several of them decide what code runs.
- **Type:** credential (transient, inherited from the environment, never stored by viola)
  - **Where:** The `viola run` wrapper process's environment holds `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` and other `CLAUDE*` parent-identity variables, which are stripped from the child's environment (R8 strip list, Occupied Resources: Environment variables). The Claude subscription credentials belong to the unmodified `claude` CLI, and viola makes no model API calls (Stack: AI/ML N/A). Cross-cutting Patterns (Config management): "There are no secrets in v1." Two dev-host measurements crossed this boundary once each, on the founder's own live answers of 2026-10-07T09:43Z, each given after its widening was shown and relayed by the overseer (chunk 2026-10-07-live-rows-and-paste-shapes-on-the-dev-host, `evidence/scratch-session.md`): one fixed synthetic message sent once, through the CLI's own peer messaging, from the builder session into a scratch `claude` 2.1.287 probe session that was the one new idle peer; and a scratch hook's names-only list of its `CLAUDE*` environment, read against a literal copy of the floor. No value was read into any file, no product code, `viola verify` run or capture arm took part, and neither answer covers a second message, a verify child or any other probe.
  - **Volume:** Transient, in process memory only.
- **Type:** operational metadata. PII is limited to the OS username in paths.
  - **Where:**
    - Snapshots hold `pid`, `child_pid`, `agent_session_id`, `started_at` and the optional `cwd` (the start's spawn directory: an absolute host path that can carry the OS username; it lives in the 0600 snapshot only, on no log line, error body or stdout, and is omitted when absent).
    - `budget.json` holds subscription usage percentages and `resets_at`.
    - Sources: Standard Contracts (Instance snapshot); Occupied Resources (Filesystem).
  - **Volume:** Per-user, low sensitivity.
- **Type:** payment / health / multi-user PII: none. Stack lists no payment, identity or health SDKs, there is no database and no accounts (Stack; Established Decisions: Personal v1).

**Attack surface:**
- **Vector:** Local IPC, the wrapper channel (JSON-RPC 2.0 over ndjson). This is the highest-impact surface.
  - **Entry point:**
    - One endpoint per `viola run`: named pipe `\\.\pipe\viola-<h12>` on Windows, socket file `$TMPDIR/viola-<h12>.sock` (else `/tmp`) on Unix.
    - Methods: `send`, `wait`, `last`, `answer`, `pause`, `release`, `link`, `unlink`, `hook.dialog`, and `hook.event` notifications.
    - Whoever can connect can type prompts into the driven Claude session (`send`) and allow PermissionRequest dialogs (`answer` with `behavior:"allow"`). That amounts to running arbitrary tools, and so arbitrary code, as the user. They can also read the whole conversation (`wait`, `last`).
    - Sources: Occupied Resources (IPC endpoints); Cross-cutting Patterns (Local endpoint trust boundary).
  - **Trust boundary:**
    - v1 intends to trust every process of the same OS user and no other. How that is enforced per OS (pipe DACL, socket file mode, directory permissions) is not decided in arch and is explicitly handed to security.
    - There is no per-connection authentication. The `from` parameter is self-reported by the caller (the CLI and MCP take it from their own `VIOLA_NAME`), so link records and driver identity are not authenticated.
    - The endpoint name is predictable: FNV-1a over `ViolaName` + home path, which is not secret (Conventions: Endpoint name).
    - Consequences:
      - On Unix with `TMPDIR` unset, the socket sits in world-writable `/tmp`, so another local user can create the path first.
      - On Windows, the named-pipe namespace is shared across the machine.
      - Clients (`hook`, `send`, `mcp`) connect to the `endpoint` recorded in the snapshot and act on whatever server answers there. A process holding that name while the real wrapper is gone could receive `hook.dialog` payloads and send back dialog decisions.
      - `run`'s exclusive bind means a squatted name blocks startup (exit 1).
    - Input validation is limited to JSON-RPC parsing, the `v` check (`-32602`) and the `ViolaName` nutype.
    - It is open (arch defers it to security) whether a driver-originated `release` (params carrying `from`) should be refused. Established Decisions (MCP) records that an agent's Bash tool can call CLI `viola release` through `VIOLA_BIN`.
- **Vector:** CLI input, the `send` text written into the PTY.
  - **Entry point:** A bridge send is one `ESC[200~…ESC[201~` + CR write of the typed text: the text from stdin, `--file` or MCP `send.text`, with every CR LF pair and every other CR inside it as one LF, and without its trailing CR and LF characters (Established Decisions: Delivery Confirmation; Human Takeover / Wheel). A text whose typed text is empty is refused `not-delivered` / `empty-text` and nothing is written.
  - **Trust boundary:** Arch does not say whether sent text is checked for an embedded bracketed-paste terminator (`ESC[201~`) or other control sequences. Text containing one would end the paste early, and the rest would reach the `claude` TUI as typed keystrokes. The only post-hoc check is delivery confirmation, which compares `prompt-submitted` text with the typed text, that is the sent text with every CR LF pair and every other CR as one LF and without its trailing CR and LF characters, by exact equality with no tolerance on the submitted side (Established Decisions: Delivery Confirmation).
- **Vector:** The human's terminal, `viola run`'s own stdin.
  - **Entry point:** Every byte the terminal writes to `viola run`'s stdin: the human's keys, and the terminal's own focus reports, mouse reports and replies to the child's queries. A byte that is typing takes the wheel from the driver (`wheel{holder:"human",cause:"human-input"}`), and the next automation `send` is refused `human-typing` (Established Decisions: Human Takeover / Wheel).
  - **Trust boundary:** The stdin classifier's closed non-editing list (the founder's ruling F-W2): only a sequence on it never counts as typing, and every other byte does. The list was widened once, a boundary widening ratified by the founder himself on 2026-10-08 after the exact grammars and a narrower option of two were shown (relayed verbatim by the overseer; chunk 2026-10-08-first-live-test-and-self-drive): seven terminal reply shapes after `CSI`, each by exact grammar, the fields compared as bytes, no intermediate byte and the field count exact (`0 n`, `? 997;1 n` and `? 997;2 n`, `4;n;n t`, `6;n;n t`, `8;n;n t`, `48;n;n;n;n t`, `> 4;n m`), as measured on foot 1.28.0 on the Linux dev host, where those replies had taken the wheel from the driver at a live session's start. The nearest human keys (`n`, `t`, `m`, their Alt forms, their kitty key events) and a sequence one field or one prefix away stay typing, each pinned by a unit case, and a reply no terminal has been measured to write is never added on a guess. The classifier reads bytes, not time: a human who types a listed reply's bytes one key at a time is read as that reply. A key that reaches this stdin is the human's by construction, whoever typed it: at the same chunk an agent typed five keys into session terminals with `wtype`, each on a compositor the chunk started itself (nested as one client window of the locked desktop's compositor, one start for all live work) and each after a guard read that its one window was the active one. That crossing of the human's own input is the founder's ruling for that chunk's takeover proof (his answers of 2026-10-08, the method first, then the compositor's form and its price after they were shown, relayed verbatim by the overseer): the desktop's lock was never touched and read locked after the start, before each live step and twice after the end, the one call naming the desktop instance was a `locked` read, and no product code took part.
- **Vector:** Hook stdin payloads from Claude Code, exec-form `viola hook <event>`.
  - **Entry point:** JSON on stdin for SessionStart, UserPromptSubmit, PreToolUse (`AskUserQuestion|ExitPlanMode`), PermissionRequest, Stop, SessionEnd, Notification, PostToolUse and PostToolUseFailure, plus `hook statusline` with statusline JSON (Established Decisions: Hook Transport; Occupied Resources).
  - **Trust boundary:**
    - Parsing is tolerant in `viola-agent-claude`: no `deny_unknown_fields`, serde_path_to_error for drift reports (Established Decisions: Validation).
    - Upstream text is treated as content, never as commands (R1).
    - Any failure fails open to the human: exit 0 with no body.
    - `hook statusline` runs `statusline_command` from `snapshot.json` through a shell. That snapshot is found through `VIOLA_DIR`, so its integrity is set by filesystem permissions on the viola home.
- **Vector:** MCP over stdio. The driver is an LLM agent.
  - **Entry point:** Tools `send`, `wait`, `last`, `answer` and `list`, called by the driver session's model (Established Decisions: MCP).
  - **Trust boundary:**
    - Tool input schemas (schemars) and the `ViolaName` newtype check the input.
    - The driver model reads the driven session's output (`wait`/`last`), which arch classes as untrusted upstream text. The same model can then call `answer` on that session's PermissionRequest.
    - viola does not interpret that text (R1: mechanism, not policy). The decision to allow a permission rests with the driver model, outside viola.
    - Leaving `release`, `pause`, `link` and `unlink` off the MCP tool list is described as an affordance, not an enforcement.
- **Vector:** CLI arguments, flags and environment.
  - **Entry point:**
    - All subcommands.
    - `--home <dir>` and `VIOLA_DIR` choose which state tree, snapshot, `endpoint`, `statusline_command` and ledger stamps are used (Cross-cutting Patterns: Config management).
    - `answer` takes its `response` JSON from stdin or `--file`.
    - `viola run <name> -- <program> <args>` spawns the program as given.
  - **Trust boundary:** Same-user invocation, clap parsing, the `ViolaName` nutype, and tolerant `config.json` parsing.
- **Vector:** Filesystem state under `~/.viola/`.
  - **Entry point:**
    - Readers across processes: `snapshot.json`, `events.ndjson`, `budget.json`, `config.json`, `ledger/stamps.json`, `heartbeat`.
    - Code-bearing artefacts: `bin/<version>-<hash>/viola(.exe)` and `plugin/<version>-<hash>/hooks/hooks.json` / `.mcp.json`. Claude Code runs these on every hook event and for MCP. And `marketplace/viola/.mcp.json` (`viola plugin install`, never read back by viola), which Claude Code runs for MCP in a session that installed the plugin.

  - **Trust boundary:**

    - Readers tolerate torn lines (they skip and count them, and the next append heals a torn last line). The replay of the log for a snapshot that fails to parse, or carries a newer `v`, has two product readers, `viola revive`'s preflight and `viola list` (`viola_state::board::read`, chunk 2026-10-11-the-board-viola-list), each taking it after the strict-modes check on the instance's files; no other product reader takes it (Standard Contracts: Snapshot envelope).

- **Public internet API / file upload / OAuth / WebSocket / webhook:** none. Stack and Conventions list no public listener, no WebSocket ("No WebSocket and no polling endpoints in v1") and no hosting.

**Auth model:**
- **Approach:** none for v1 (as of 2026-09-23). The only principal is the local OS user.
  - Reason: Project Intent and Established Decisions (Personal v1) describe a single-user local tool with "no accounts, no hosting".
  - Access control therefore depends entirely on OS-level isolation: who can connect to each IPC endpoint and who can read or write `~/.viola/`. Cross-cutting Patterns (Local endpoint trust boundary) sets the target principal as "every process of the same OS user and no other".
  - Arch has decided no enforcement mechanism for that boundary on any OS. That decision is outstanding and belongs to this specialist.
- **Provider:** self-implemented. Stack contains no auth framework or identity SDK.
- **Scope:** per-OS-user for v1 (IPC and filesystem). Remote or phone access behind authentication is a later version and is N/A in this assessment (Project Intent: Scale path; Stack: Mobile N/A).
- **Development Style context:** agent-driven (Cross-cutting Patterns). The main automated callers are LLM driver sessions using MCP and the CLI, with no interactive login. That matches an ambient OS-user trust model rather than a credential flow.

**Infrastructure:**
- **Hosting:** local-only. Installed with `cargo install --path .`. No Docker, Compose, Kubernetes, serverless or PaaS (Infrastructure Patterns: Deployment model; Established Decisions: Hosting).
- **Database:** none. State is embedded flat files: ndjson append logs plus atomically replaced JSON snapshots, with std `File::lock` on sibling `.lock` files, under `~/.viola/` or `--home` (Stack: Database; Established Decisions: Database / State Store). Nothing is encrypted, and all of it is plaintext for readability by design.
- **Networking:** local only.
  - Per-instance named pipes (Windows) or Unix domain sockets (`$TMPDIR` or `/tmp`); no Linux abstract namespace.
  - MCP over stdio.
  - No outbound network calls by viola itself. The `claude` child handles the network to Anthropic on its own.

## Authentication & Authorization

_Included despite v1 auth approach "none". Threat Model Sec 6 elevates "IPC endpoint access control and server impersonation". Every principal check in viola is OS-level (IPC, filesystem). See the Security Decisions Log._

**Auth approach:** OS-user ambient trust, enforced per OS, on the IPC endpoints and `~/.viola/`.

## Input Validation

_[ALL tiers]_

**Boundary:** Validate at every point where untrusted data enters viola. Arch has two validation regimes (Established Decisions: Validation): tolerant parsing for external payloads, and versioned-tolerant parsing for viola's own formats. The requirements below are security floors that apply in both regimes. Shared validators live in `viola-core`, so the CLI, MCP and the wrapper all call the same function.

| Boundary | What to validate | How (stack-specific) |
|----------|-----------------|---------------------|
| Paste text: channel `send.text`, MCP `send.text`, CLI `send` stdin/`--file` | **Rule (exact set):** multi-line text is normal (relays, plans and free-text answers are multi-line, brief §4.1 S1), so three controls are **allowed**: LF (U+000A), CR (U+000D) and TAB (U+0009). ## Error Handling

_[ALL tiers]_

**External responses** (to channel clients, CLI `--json` and MCP drivers): sanitised.
- No anyhow context chains, no absolute paths, no upstream text (prompts, tool `input`, assistant output), no serde_path_to_error paths or values, and no internal type names.
- The `Display` impls on `PtyError` (hand-written), `ChannelError`, `StateError`, `AgentError`, `McpError` and `CoreError` (`thiserror`) use fixed messages. Variant fields that hold paths or payloads are excluded from `Display`.
- Channel `-32603` uses a fixed `message` ("internal error") with `data: null`.
- MCP `isError` results carry only the `structuredContent` codes from Conventions (`refusal`/`detail`, or `error: instance-unreachable | wrapper-fault | invalid-params` — `instance-unreachable` with `detail: null`, `wrapper-fault` with the JSON-RPC fault's `{code,message,data}`, `invalid-params` with a closed field word), and every `isError` text is `refused: <code>`. Any other handler fault, a reply of no known shape or a panicked call is the JSON-RPC error `-32603` `internal error` with `data: null` (chunk 2026-10-17-mcp-server-for-drivers).

**Internal logging (for debugging):**
- Full error detail goes only to `instances/<name>/diagnostics/` (files 0600; format owned by obs) or, for short-lived CLI verbs, to stderr. stderr never carries upstream text, tool `input`, drift-report values or any other value on the NEVER-log floor (Bootstrap phases, `logging-redaction-wire`).
- `hook` never writes to stderr and never exits non-zero (Hook Contract). A security check failing in `hook` (server verification mismatch, oversized stdin, strict-modes failure) still ends in exit 0 with no body, so the dialog renders for the human. As landed, `viola hook <event>` runs the stdin cap, the `VIOLA_NAME` / `VIOLA_DIR` shape checks and the one-object parse, and fails open with `hook-decision` detail `oversize-stdin` · `malformed-json` · `channel-unreachable`; server verification and strict-modes join at Epoch 6 (Decisions Log `2026-09-28`). Its hidden `--capture <DIR>` arm runs the stdin cap, the absolute, existing `<DIR>` check and the exclusive `create_private_new` claim, and writes the capture raw; with `--answers <DIR>` it also runs the `take(64)` closed-`ProbeAnswer` read and `probe_body`'s payload shape check, and prints one `decision_body` body to stdout only for a mapped answer. Its statusline form `hook statusline --capture <DIR> [--shell <WORD>]` runs the same stdin cap and `<DIR>` check and claim, writes the payload raw and the closed shell verdict, and prints nothing on any path. On every failure it prints nothing, its stderr is always empty, and it exits 0 (Decisions Log `2026-09-28`, capture arm; the founder's live ruling of 2026-10-05 on `--answers`; the founder's own answer to P4 fork 3 of chunk 2026-10-13-owed-ledger-rows («Run B + --settings», relayed verbatim by the operator, that chunk's `inputs#I1`), on the statusline form).

## Security Anti-Patterns (NEVER do these)

_[ALL tiers — single source of truth for all security bans]_

### Authentication

- NEVER create an interprocess Windows listener without `ListenerOptionsExt::security_descriptor`. The default DACL grants read to Everyone and anonymous.
- NEVER place a Unix socket directly in `/tmp` or at the `$TMPDIR` root (`/tmp/viola-<h12>.sock`). Always use a verified 0700 per-user directory (the Kea DHCP CVE-2025-32801/32802/32803 precedent).
- NEVER rely on the socket file's 0600 mode as the only Unix control: `unix(7)` says socket permissions may be ignored. NEVER set it with `ListenerOptionsExt::mode`: it returns `Unsupported` on macOS, which fails the bind; chmod after the bind instead.
- NEVER use Linux abstract-namespace sockets (no filesystem permissions).
- NEVER write any channel frame (`send`, `answer`, `hook.dialog`, `wait`/`last`, `pause`/`release`, and `hook.event` notifications, which carry prompt and reply text) before verifying the server's pid (Windows `server_process_id()`) or euid + pid (Linux/FreeBSD `peer_creds()`) plus sysinfo start time against `snapshot.json` (on macOS, where `peer_creds()` gives no pid: euid + the verified 0700 socket directory only, per the recorded known gap; the euid check is never skipped), and NEVER take those reference values (`endpoint`, `pid`, `started_at`) from a `snapshot.json` that has not passed the strict-modes check in the same process. The dated exceptions, until the Epoch 6 entries "Server verification before any frame" and "Home and code-bearing file integrity" land: `viola hook`'s `hook.event` (Decisions Log `2026-09-28`, ratified by the founder), CLI `viola send`'s `send` frame, CLI `viola wait` / `viola last`'s `wait` / `last` frames and CLI `viola answer`'s `answer` frame and CLI `viola pause` / `viola release`'s `pause` / `release` frames, each after the liveness-only pre-check, and `viola hook pre-tool-use|permission-request`'s `hook.dialog` frame after its payload shape check (the founder's rulings, live, 2026-10-04, relayed by the overseer; `answer` / `hook.dialog` the sixth dated gap; `pause` / `release` the seventh, F-W1), and `viola mcp`'s `send` / `wait` / `last` / `answer` tool frames after the liveness-only pre-check (the eighth dated gap: the founder's own answer to P4 fork Q1, 2026-10-17, relayed by the overseer, `inputs#I2` of chunk 2026-10-17-mcp-server-for-drivers); no other frame or process may borrow any of them.
- NEVER open a Windows client pipe without `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the default `connect_without_waiting` lets a squatter with SeImpersonatePrivilege impersonate the client).
- NEVER treat the channel `from` param as an authenticated identity. It is self-reported and serves link records and the `release` affordance guard only.
- Account-flow bans (reset enumeration, recovery questions, login rate limiting): N/A. There are no accounts or login endpoints (Threat Model: Auth model).

### Input

- NEVER trust schemars MCP schemas or client-side CLI checks alone. The wrapper re-runs `ViolaName::try_new`, the closed-enum deserialisation and `validate_paste_text`.
- NEVER join `instances/<name>` with a string that did not come out of `ViolaName::try_new` (MCP `target`, `link`/`unlink` params, notify events).
- NEVER write `send.text` or answer free text into the PTY if it contains any C0 control other than LF, CR and TAB (ESC above all), DEL (U+007F) or any C1 control (U+0080–U+009F), and NEVER strip them silently. Reject with `control-character`. The wrapper's `send` typing every CR LF pair and every other CR inside a text as one LF, and dropping its trailing CR and LF characters, of a text that has already passed `validate_paste_text` is not this stripping: CR and LF are allowed characters, validation runs first on the text as received, and no refused character is ever removed or typed (§Input Validation, Paste text row). Answer free text is typed as validated. NEVER refuse LF, CR or TAB: multi-line relays, plans and answers are normal. Refusing a text whose typed text is empty (`empty-text`) is not a refusal of those characters: there is nothing to type, and a text with content is never refused for holding LF, CR or TAB.
- NEVER run the control-character check over raw bytes. Check decoded `char`s, or valid UTF-8 continuation bytes (0x80–0xBF) are misread as C1.
- NEVER call `read_line` on a channel stream or `read_to_end` on hook stdin or child output without `Read::take(MAX_FRAME)`.
- NEVER enable serde_json's `unbounded_depth` feature.
- NEVER model `behavior`, `dialog_id`, the wheel holder or the dialog kind as free `String`s. Use closed enums or integers even under tolerant parsing.
- NEVER use a `claude agents --json` row `name` as a `ViolaName` or `target`.
- SQL ban: N/A (no database or query language).

### Data Protection

- NEVER create `~/.viola/`, `--home` or any file under it with the default umask. Directories are 0700 and files 0600 (`OpenOptionsExt::mode`); the only exception is the pinned `bin/<version>-<hash>/viola` at 0700, and NEVER make it group- or world-writable. On Windows, NEVER accept a `--home` outside `%USERPROFILE%` without an explicit protected user + SYSTEM DACL, and NEVER skip the Windows owner + DACL strict-modes check at startup (`#[cfg(windows)]` must not return `Ok(())` unchecked), and NEVER pass a NULL DACL, a volume without persistent ACLs, or an inherit-only `GENERIC_*` grant just because no specific-rights ACE matched.
- NEVER run `statusline_command` from a `snapshot.json` whose home or instance directory fails the strict-modes check. Write access there equals code execution.
- NEVER reuse an existing `bin/<version>-<hash>/viola(.exe)` without re-hashing it (SHA-256, truncated) against `<hash>`, NEVER derive `<hash>` from a non-cryptographic hash (FNV, `DefaultHasher`), and NEVER reuse existing `plugin/` files without rewriting them. NEVER load or launch a `bin/<version>-<hash>/conpty/` companion without its full SHA-256 re-hash against the compiled pin through a `FILE_SHARE_READ`-only handle held until the spawn, and NEVER overwrite or delete a companion that fails it (left as found; the child runs on the inbox ConPTY).
- NEVER spawn a `.cmd`/`.bat` PTY child through portable-pty. Resolve to a real `.exe` (portable-pty 0.8.1 bypasses std's BatBadBut escaping).
- NEVER make channel handles inheritable, and NEVER adopt a portable-pty replacement that calls `CreateProcessW` with `bInheritHandles = TRUE`.
- NEVER commit `fixtures/claude/*` recorded from sessions that used real (non-synthetic) prompts, or before checking them for home paths and usernames (a `workspace.repo` naming this repository's own remote is kept, Data Protection → Repository fixtures).

### API

- NEVER enable rmcp's `transport-streamable-http-server` or `auth` features.
- NEVER skip request size limits: `MAX_FRAME` on the channel.

- NEVER print `wait`/`last` human-mode output, or `list` rows taken from `claude agents --json`, to a terminal without escaping C0/C1 controls (the same class as RUSTSEC-2025-0055).
- NEVER use tracing-subscriber `<0.3.20` if obs selects it.

- NEVER expose absolute paths in any external error.

### Code Patterns

- NEVER interpret upstream text (prompts, `last_assistant_message`, plan text, question and option text, tool `input`) as a viola command or config (R1). `statusline_command` is the only shell-out, and NEVER add a second one.
- NEVER build screen signatures, harness prefixes or local-command lists from runtime or upstream text. They come only from compiled `viola-agent-claude` ledger rows. The harness prefixes are four compiled literals matched on the prompt's raw start, no trim (`<agent-message from=`, `<task-notification>`, `<\cross-session-message`, `<cross-session-message`); the escaped cross-session form is the one escaped tag that classifies `harness`, so a human who types it at a prompt's start is filed `harness` (the founder's ratified side effect, Decisions Log `2026-09-29`).
- NEVER enable interprocess `try_overwrite` (TOCTOU deletion of an attacker-swapped file).
- NEVER feed vt100 outside `catch_unwind`. A parser panic must not take down the human's terminal path.
- NEVER reference a GitHub Action by `@stable`, `@v2` or any mutable ref. Use a full SHA with a version comment.
- NEVER restore `Swatinem/rust-cache` in the v1.x release workflow.
- NEVER ship `self_update` without its `signatures` feature (zipsign). A checksum from the same release proves nothing.
- NEVER let `run --mutants` wipe any directory except the Windows host mutation scratch `<repo parent>/viola-mutants-scratch`. A pure guard refuses (`scratch-refused`) unless the resolved path's final component is exactly `viola-mutants-scratch` and the repository is neither that directory nor inside it. A drive or filesystem root has no final component, so it is refused. A failed removal is `scratch-wipe-failed`. The wiped scratch is re-created owner-only through `viola_state::fs::create_private_dir` (the protected user + SYSTEM DACL on Windows), so an instance tree a test lays inside it passes the strict-modes check as one under `%TEMP%` does; NEVER re-create it with a plain `create_dir_all`, whose inherited workspace-drive grants the check refuses, and NEVER loosen the check for it. NEVER fall back to `%TEMP%` or the repository, and NEVER print the path. The guard and the wipe run only on a Windows host (`HOST_SCRATCH = cfg!(windows)`); elsewhere the harness touches no scratch, and the Linux dev host's same-named NOCOW `TMPDIR` for mutation runs is the operator's, never wiped by the harness.
- NEVER let a test-side removal under `target/e2e-home` take anything but a dir the test side itself created: the root fixture chain's owner sweep and a test home's drop (by `owner.json` record, by its own `TempDir`) and harness `cleanup` (by the `viola-session-` name). On the Linux dev host that path is a link to the per-user tmpfs directory `/tmp/viola-e2e-home-<uid>`, so these creations and removals reach outside the working directory: a boundary widening, ratified by the founder (live, 2026-10-07T07:25Z, after it was shown to him as creating and deleting outside the working directory through the link; relayed by the overseer). The two keepers (`prepare_home_base` in `tests/support/home.rs`, `Workspace::ensure_e2e_home` in the harness) NEVER follow a linked base unless its target is absolute and one `lstat` of it reads a real directory with no group or other bit; a target that is itself a link is refused, so is a backing whose filesystem reads less than the 9 GiB headroom floor free (`statvfs`), and a refusal is a fixed message that names no path (the headroom one holds the two counts). They create the target with mode 0700 through the directory builder (never a chmod after, never a parent) and remove nothing. Ownership is not read separately: the `tempdir_in` that follows succeeds in an owner-only directory only for its owner. `viola` itself never reads or writes the backing by that name, and no CI runner has the link.

### Universal

- NEVER add a listener (TCP port, WebSocket, `http` hooks, MCP HTTP transport) or a new channel method without a Security Decisions Log entry mapping it to this plan's IPC controls.
- NEVER let a security refusal block the human. Refusals go only to automation (`send`/`answer`), and hooks fail open.
- NEVER let a `viola` process on Windows reach any DLL load before `viola_pty::sideload::restrict_dll_search()` (System32-only default search, the second statement of `main` in every role): a bare-name load, portable-pty's `LoadLibraryW("conpty.dll")` included, must never resolve from the CWD or `PATH`. NEVER pre-load the sideloaded `conpty.dll` by a relative path. A sideload failure degrades to the inbox ConPTY silently: NEVER a refusal, an exit change or a byte on the human's terminal.
- NEVER let an exec-form `command` in the embedded `hooks.json` or `.mcp.json`, or in `viola plugin install`'s `.mcp.json`, or the statusline command `viola run` writes into `instances/<name>/settings.json` (it wraps the statusline with `viola hook statusline`), resolve `viola` through PATH.
