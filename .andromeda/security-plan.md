## Threat Model Summary

Detail: .andromeda/security-plan-detail/threat-model-summary.md — read whole.

_[ALL tiers — VERBATIM copy from threat-assessment.md]_

**Security tier:** `Minimal (0), with targeted elevations for the local privilege boundary`
_Justification: viola is a local-only, single-user tool. It has no accounts, no public network listener, no database, no stored credentials and no regulated data (Sections 1, 3, 4, 5), which rules out Standard's user-account and HTTPS concerns and Hardened's compliance drivers. It still goes beyond a plain Minimal profile in two ways. First, the local IPC endpoint is effectively a code-execution interface (`send` types prompts, `answer` can allow PermissionRequest tool calls). It currently has no decided per-OS enforcement of its same-OS-user boundary, and its names are predictable in shared namespaces (Windows pipes, `/tmp`). Second, several state files decide what code runs and whether dialogs are answered: `snapshot.json`'s `statusline_command`, the `hooks.json` exec paths, the pinned binaries and the ledger stamps. The baseline is therefore Minimal (dependency audit, input validation on config and external payloads, error sanitization). On top of it sit specific local-boundary items: IPC endpoint access control and server impersonation, bracketed-paste breakout in `send.text`, and integrity of `~/.viola/`. Each of these traces to Section 2._

**Data classification:**

Data classes: user-content (prompts, assistant replies, tool-call arguments, plans and dialog text) logged to `events.ndjson` and sent over the channel; integrity-sensitive config, several files deciding what code runs (`statusline_command`, the hook and MCP exec paths, the pinned binary, the ledger stamps); a transient credential inherited from the environment, never stored by viola; operational metadata, PII limited to the OS username in paths.

The snapshot's recorded `cwd`, an absolute host path that can carry the OS username, stands in the 0600 snapshot only, on no log line, error body or stdout.

- **Type:** payment / health / multi-user PII: none. Stack lists no payment, identity or health SDKs, there is no database and no accounts (Stack; Established Decisions: Personal v1).

**Attack surface:**

**Vector:** Local IPC, the wrapper channel, the highest-impact surface: whoever can connect can type prompts into the driven session, allow PermissionRequest dialogs and read the whole conversation. v1 intends to trust every process of the same OS user and no other; there is no per-connection authentication, the self-reported `from` authenticates nothing, and the endpoint name is predictable.

**Vector:** CLI input, the `send` text written into the PTY as one bracketed paste of the typed text: an embedded paste terminator or other control sequence would end the paste early, and the rest would reach the `claude` TUI as typed keystrokes.

**Vector:** The human's terminal, `viola run`'s own stdin: a byte that is typing takes the wheel from the driver; only a sequence on the stdin classifier's closed non-editing list never counts as typing, and a reply no terminal has been measured to write is never added on a guess.

**Vector:** Hook stdin payloads from Claude Code, exec-form `viola hook <event>`: parsed tolerantly, upstream text treated as content, never as commands, and any failure failing open to the human; `hook statusline` runs `statusline_command` through a shell, its integrity set by filesystem permissions on the viola home.

**Vector:** MCP over stdio, the driver an LLM agent: tool input schemas and the `ViolaName` newtype check the input; each stdin line is capped at `MAX_FRAME` before rmcp reads it, an over-long line refused whole and ending the session, never dispatched in part; the driver model reads untrusted driven-session output and can answer that session's PermissionRequest, the decision resting with it, outside viola; leaving `release`, `pause`, `link` and `unlink` off the tool list is an affordance, not an enforcement.

**Vector:** CLI arguments, flags and environment: `--home` and `VIOLA_DIR` choose which state tree, snapshot, `endpoint`, `statusline_command` and ledger stamps are used; the trust boundary is same-user invocation, clap parsing, the `ViolaName` nutype and tolerant `config.json` parsing.

**Vector:** Filesystem state under `~/.viola/`, read across processes and holding the code-bearing artefacts Claude Code runs: its trust boundary is OS permissions on the user's home directory; readers tolerate torn lines, the pinned binary and plugin folders are never deleted in v1, and beyond the content hash in the folder name the start holds the home tree, the pinned binary and the plugin folders to the strict-modes check (owner and mode, or owner and DACL) before any log opens.

**Vector:** Child process spawning and PATH resolution (`claude agents --json`, the `--version` probe, `revive`'s `claude`, `viola verify`'s interactive children): the trust boundary is whatever the calling process's PATH resolves to; output parsing is tolerant and failure becomes `unknown`; verify's children are read only against the compiled signature literals, their row text leaving the process only as signature-only `--record` fixtures.

`viola verify`'s interactive children never get a byte written into any dialog, a start showing a modal killed with no key; each `agents-probe` spawn pair is logged with no row text, id, `cwd` or path.

**Vector:** Supply chain (build and CI): Cargo dependencies, SHA-pinned third-party GitHub Actions and rustup-installed toolchains; the trust boundary is `cargo deny check`, the sync-crate `tokio` bans, `Cargo.lock` and `publish = false`, the test-only `fuzz/` lockfile audited on its own by a ratified exemption; v1 has no release, no signing and no deploy stage.

- **Public internet API / file upload / OAuth / WebSocket / webhook:** none. Stack and Conventions list no public listener, no WebSocket ("No WebSocket and no polling endpoints in v1") and no hosting.

**Auth model:**
- **Approach:** none for v1 (as of 2026-09-23). The only principal is the local OS user.
  - Reason: Project Intent and Established Decisions (Personal v1) describe a single-user local tool with "no accounts, no hosting".
  - Access control therefore depends entirely on OS-level isolation: who can connect to each IPC endpoint and who can read or write `~/.viola/`. Cross-cutting Patterns (Local endpoint trust boundary) sets the target principal as "every process of the same OS user and no other".
  - Arch has decided no enforcement mechanism for that boundary on any OS. That decision is outstanding and belongs to this specialist.
- **Provider:** self-implemented. Stack contains no auth framework or identity SDK.
- **Scope:** per-OS-user for v1 (IPC and filesystem). Remote or phone access behind authentication is a later version and is N/A in this assessment (Project Intent: Scale path; Stack: Mobile N/A).
- **Development Style context:** agent-driven (Cross-cutting Patterns). The main automated callers are LLM driver sessions using MCP and the CLI, with no interactive login. That matches an ambient OS-user trust model rather than a credential flow.

**Infrastructure:**
- **Hosting:** local-only. Installed with `cargo install --path .`. No Docker, Compose, Kubernetes, serverless or PaaS (Infrastructure Patterns: Deployment model; Established Decisions: Hosting).
- **Database:** none. State is embedded flat files: ndjson append logs plus atomically replaced JSON snapshots, with std `File::lock` on sibling `.lock` files, under `~/.viola/` or `--home` (Stack: Database; Established Decisions: Database / State Store). Nothing is encrypted, and all of it is plaintext for readability by design.
- **Networking:** local only.
  - Per-instance named pipes (Windows) or Unix domain sockets (`$TMPDIR` or `/tmp`); no Linux abstract namespace.
  - MCP over stdio.
  - No outbound network calls by viola itself. The `claude` child handles the network to Anthropic on its own.
  - Sources: Occupied Resources (IPC endpoints); Stack (AI/ML N/A).

**CI/CD:** GitHub Actions `ci.yml` on push and PR over a native `windows-2025`, `macos-latest` and `ubuntu-latest` matrix, plus the weekly `nightly.yml` advisory and fuzz run; no deploy stage, no release artefacts and no secrets in v1, the real `claude` CLI running only locally.

**Compliance triggers:**
None: no compliance-regulated data detected.
- No payment data (no payment SDK in Stack).
- No health data.
- No children's data.
- No collection of personal data from third parties. The tool has no accounts and no hosting, and all logged content is the operator's own Claude session content kept on their own machine (Established Decisions: Personal v1; Project Intent).
- The v1.x public distribution in Project Intent (Scale path) still keeps all data local on each user's machine, so it adds no trigger in this assessment.

This tier is the SINGLE SOURCE OF TRUTH for how much security rigor downstream
skills (the phase loop per chunk + cross-cutting reads from design / tests /
obs / a11y) should apply.

## Authentication & Authorization

Detail: .andromeda/security-plan-detail/authentication-authorization.md — read whole.

_Included despite v1 auth approach "none". Threat Model Sec 6 elevates "IPC endpoint access control and server impersonation". Every principal check in viola is OS-level (IPC, filesystem). See the Security Decisions Log._

**Auth approach:** OS-user ambient trust, enforced per OS, on the IPC endpoints and `~/.viola/`.

**Library:**
- IPC: interprocess 2.4.4 (`ListenerOptionsExt::security_descriptor`, `Stream::peer_creds()`, its `pid()` also the client's read of the serving process: Linux `SO_PEERCRED`, Windows `GetNamedPipeServerProcessId` on the SQOS-opened client end, none on macOS), windows-sys 0.61.2 (`GetTokenInformation(TokenUser)`, `ConvertSidToStringSidW`, the SDDL-to-descriptor conversion under feature `Win32_Security_Authorization`, `CreateFileW` with SQOS flags), std chmod on the bound Unix socket, and sysinfo 0.39.6 (pid + start time). Not used: interprocess `SecurityDescriptor::deserialize` (it needs a `widestring` dependency) and `ListenerOptionsExt::mode` (see IPC access control (Unix)).

_Adapter note: viola has no passwords and no user store. The rows are adapted to an OS-principal model._

Password hashing — N/A: no accounts or passwords.

RBAC / permissions — capability-based, all or nothing: any caller that passes the OS check gets the full surface; no roles, the only principal being the local OS user.

IPC access control (Windows) — the listener gets an explicit protected DACL granting the user SID and SYSTEM only; the logon SID is deliberately not added, since the boundary v1 promises is the OS user; remote clients stay rejected, the first-pipe-instance behaviour is kept and the handle is not inheritable.

IPC access control (Unix) — the socket lives in a per-user 0700 directory, checked before bind and before any client connect (owner, mode, not a symlink), and is chmod 0600 right after the bind; a failed check refuses `run`, reports `instance-unreachable` to clients and fails `hook` open; `try_overwrite` stays off and the Linux abstract namespace is never used.

IPC server-side peer check (Unix) — on every accept, a peer whose euid differs from the server's is dropped before a frame is read.

IPC client-side server verification (anti-impersonation) — before the first frame of any method, the client runs the instance's strict-modes check, a refusal writing no frame and no line, and only then verifies the server against its one snapshot read: on Linux and Windows the connected peer's pid (Windows over an SQOS identification-level open) and that process's start time, a mismatch, a snapshot replayed from the log (no endpoint, pid or start time) or a check that cannot be made sending no frame, never falling back to a default connect; the client euid check and macOS (no peer pid; its euid and verified socket-directory checks) are owed to "Unix endpoint and home hardening".

Driver-originated `release` — the wrapper refuses a `release` whose params carry a string `from` (`-32602`, `release-from-driver`), before any budget is acted on: an affordance-level guard against drivers handing the wheel back to automation, not enforcement, since a same-user process can leave out `from`.

`~/.viola/` access control — the home is owner-only (Unix 0700 directories and 0600 files, the pinned `viola` 0700; Windows the inherited profile DACL, or a protected user + SYSTEM DACL outside it), every replaced file written through `replace_private`, its mode set before any byte, never relying on the umask; a strict-modes check refuses a trusted path another user can write, a home, instance directory or `diagnostics/` another user can read (Unix any group or other bit; Windows an allow ACE granting a read right to another SID, inherit-only included) or a symlinked `diagnostics/` folder or file, in every process that reads a trusted file, before its first read or open under the home.

**Accepted risk (driver prompt injection):** driven-session output (`wait`/`last`) can prompt-inject a driver LLM into an `answer` `allow`. What to answer is policy outside viola (R1/R4). viola's only part is the closed `behavior` enum and the `unverified-cli` gate: no non-`null` decision without a `viola verify` stamp for the child's CLI version.

## Input Validation

Detail: .andromeda/security-plan-detail/input-validation.md — read whole.

_[ALL tiers]_

**Boundary:** Validate at every point where untrusted data enters viola. Arch has two validation regimes (Established Decisions: Validation): tolerant parsing for external payloads, and versioned-tolerant parsing for viola's own formats. The requirements below are security floors that apply in both regimes. Shared validators live in `viola-core`, so the CLI, MCP and the wrapper all call the same function.

Paste text: channel `send.text`, MCP `send.text`, CLI `send` stdin/`--file` — the exact set: LF, CR and TAB allowed, every other C0 control, DEL and every C1 refused, checked over decoded `char`s; a text holding a refused character is refused whole, never stripped; the typed text is the only text `send` uses, an empty one refused `empty-text`; checked client-side and again, authoritatively, by the wrapper before anything is typed.

Dialog free text: `answer.response.message` (permission, plan) and `answer.response.answers.*` values (question) — the same exact set as `send.text`, refused `control-character`, checked first on both sides: in `viola answer` before any frame, and again, authoritatively, in the wrapper's `answer` handler.

Channel frames (IPC ndjson) — a `MAX_FRAME` cap before `read_line` (over it `-32600`, the connection closed), serde_json's default depth limit, never `unbounded_depth`, the `v` check, closed types for `behavior`, `dialog_id` and names, and each method's params checked by the wrapper (`-32602`) before `validate_paste_text`; an invalid `hook.dialog` is not registered, an invalid `hook.event` not appended.

Hook stdin (all hook events + `hook statusline`) — capped at `MAX_FRAME`, an over-limit payload detected, never silently truncated; the event maps into the closed `HookEvent`, the payload must be one JSON object, and parsing is tolerant but the fields that decide security map into closed enums; every failure fails open (exit 0, no body); `budget.json` is written by `hook statusline` alone; the hidden capture arms read no `VIOLA_*`, open no channel and always exit 0.

MCP tool inputs (`target`, `text`, `dialog_id`, `response`, `after`, `timeout_ms`) — the schemars schemas are advisory only, since rmcp does not enforce them: each handler checks the raw arguments itself (`ViolaName`, `u64`, the closed response enums, `validate_paste_text` on text and free-text answers), a failure being `invalid-params` with a closed field word and no frame.

MCP stdin (`viola mcp`'s transport, the driver's JSON-RPC lines) — each line capped at `MAX_FRAME`, its `\n` counted, by the reader viola hands rmcp, which reads stdin lines unbounded; a longer line releases no byte, is refused whole, never truncated or skipped, and ends the session as a stdin close does, recorded as one `parse-rejected` line holding no byte of it.

CLI arguments / stdin — every name through `ViolaName::try_new`; the home resolved, canonicalised and passed through the strict-modes check before any snapshot, `statusline_command` or ledger read, `ledger/stamps.json` checked before `ledger/` is created and again under its lock, a refusal reading and writing nothing; `answer` and `send` input read under `MAX_FRAME`, into the closed enums or through `validate_paste_text`, before any frame; `revive --json` prints codes, closed words and session-shaped ids only, never a path or pid.

Configuration values (`config.json`) — a tolerant parse capped at `MAX_FRAME`, `v` checked; a bad value takes its key's default, or is rejected whole, and is reported as `parse-rejected`; no value switches the budget gate off or makes the dialog hold zero or unbounded, and an identity-floor name in `claude_env_keep` has no effect.

Persistent-environment names (Windows registry) — `viola run` reads value names only, never data, into a bounded buffer; they only decide which inherited `CLAUDE*` names the R8 rule keeps, and an identity-floor name is stripped whatever the registry holds.

Test seam `FAKE_AGENT_PUMP_DELAY_MS` (only in a `viola` built with the test-only `fake-agent` feature) — `u64` milliseconds capped at 5 000, only holding the `run` pump back after the child starts; compiled out of every release build, it configures nothing, disables no control and widens no redaction.

Test seam `FAKE_AGENT_HOOK_PANIC` (only in a `viola` built with the test-only `fake-agent` feature) — a closed value, panicking only on exactly `1` with a fixed ASCII payload, the hook still failing open; compiled out of every release build, it configures nothing, disables no control and widens no redaction.

Terminal colour facts `NO_COLOR`, `TERM`, `COLORTERM` (read in every build, `viola list`'s human mode only) — only compared, never echoed, they decide only whether and how deep SGR bytes are written; they reach no log line, error or refusal, are never set by viola, change no escaping or check and widen no redaction.

Own state files on read (`snapshot.json`, `events.ndjson` replay/tail, `ledger/stamps.json`, `budget.json`, `heartbeat`) — each ndjson line capped at `MAX_FRAME`, an over-long, non-object or unterminated line counted as torn; a reader never writes; read only after the home strict-modes check; a snapshot that fails to parse or carries a newer `v` is replayed from the log by its readers, and a replayed one carries no `endpoint`, `pid`, `started_at` or `statusline_command`, so no frame is written and no command runs from it; `statusline_command` is trusted only because of that check, write access to it being code execution; every failed `budget.json` read is no reading.

Tailed paths (notify) — tail only `instances/<name>/events.ndjson` where `<name>` passes `ViolaName::try_new`, under the canonical home; ignore symlinks and names that fail parsing.

Child process output: `claude agents --json`, `--version` probe, `viola verify`'s interactive PTY runs — read under `MAX_FRAME` and parsed tolerantly, a failed `claude agents --json` read failing open; verify's PTY output read only against the compiled signature literals; an unwrapped row's `name` is never a `ViolaName` and never a valid `target`.

PTY output bytes (vt100) — fed under `catch_unwind`, the human's bytes written first; a caught panic or a dropped copy poisons the screen model, which then reads `input-not-ready`, while byte passthrough to the human terminal continues; the feed queue is bounded and a full queue never blocks the passthrough.

Child executable resolution (`run`, `revive`, `claude agents`) — `claude` resolved from the calling process's PATH, a same-user trust and accepted risk, its output untrusted and bounded; `viola run` resolves its child itself and hands portable-pty an absolute path; on Windows a `.cmd`/`.bat` child is refused, except a `claude` shim, resolved to its fixed `claude.exe` sibling when that exists; `revive`'s recorded `cwd` is read after the strict-modes check and used only as the spawn directory.

Session id as a child argv value (`viola revive`, `viola verify`'s Run E) — the id after `--resume` has the closed session-id shape and is one argv element of a direct spawn, never a shell, built only by `resume_args`; an `--id` the log does not hold is `no-session` before any spawn; no refusal line or hint holds the recorded directory, a pid or a logged id.

Statusline source (read at `viola run` start) — one capped, tolerant read of `<home>/statusline-source.json`, else, for the default home only, the user's `~/.claude/settings.json`: a command only from a `statusLine` of type `command`, non-empty, with no NUL, recorded as `snapshot.json`'s `statusline_command`; viola writes neither source.

Statusline shell-out (`viola hook statusline`, Unix only) — the recorded command runs only from `hook statusline`, as `/bin/sh -c` with the command as one argument, never on Windows; its stdout is capped and printed byte for byte, never parsed, its wait bounded; no log line or span carries the command, and it remains the only shell-out.

DLL search order + sideloaded ConPTY companions (Windows x64) — every `viola` process restricts the DLL search to System32 as the second statement of `main`, so a bare-name load never resolves from the CWD or `PATH`; the companions are loaded only after the owner/DACL strict-modes check of `bin/<version>-<hash>/conpty/` and each companion, made before the held open, and a full SHA-256 re-hash under a read-share-only handle, by absolute path, and any failure, a refused check included, degrades to the inbox ConPTY, recorded only as codes, never a refusal.

File upload / webhook / SQL — N/A: no upload, webhook or database surface.

**Parser surfaces (scope for fuzz / property coverage; tests owns the cases):** `validate_paste_text`, channel ndjson framing with `MAX_FRAME`, the hook stdin parser (including `hook statusline`), the `claude agents --json` output parser, and the vt100 feed under `catch_unwind`.

**Constants:** `MAX_FRAME` = 16 MiB, one const in `viola-core`, caps every external read (channel frames, hook stdin, the statusline source and command output, `answer` input, `viola mcp`'s stdin lines, sent text, child output, ndjson lines, `config.json` and the stamps read; viola's reads of its own executable are no external input); `replace_private_shared`'s fallback compare reads its target through `take(bytes.len() + 1)`, never the whole file; it is checked against data: a stamped largest hook payload within a factor of 4 of it is a signal to revisit the cap.

(See `## Security Anti-Patterns` § Input for input-validation bans.)

## Data Protection

Detail: .andromeda/security-plan-detail/data-protection.md — read whole.

_Minimal tier, adapted. "HTTPS enforced" does not apply, and viola does store sensitive user content (Threat Model: Data classification), so the file-permission controls stay in scope._

**In transit:**
- **TLS:** N/A. The IPC channel is local named pipes or Unix sockets, and MCP is stdio. Confidentiality in transit depends on the IPC ACLs (Authentication & Authorization).
- **HSTS:** N/A.
- **Certificate pinning:** N/A.
- **Handle inheritance:** portable-pty 0.8.1 calls `CreateProcessW` with `bInheritHandles = 0`, and interprocess listeners stay `inheritable(false)`, so channel handles never leak into the `claude` child. Any portable-pty swap (portable-pty-psmux 0.9.7 is the named candidate) must keep this property.

**At rest — per medium:**
- **Database:** N/A (none).

**Files (`~/.viola/`):** plaintext by design, protected by OS permissions only (Unix 0700 directories and 0600 files, the pinned `viola` 0700; Windows the inherited profile DACL, or a protected user + SYSTEM DACL outside it); the plugin files and the settings override are rewritten at every start, the override written on Unix only and only for a pinned path of plain characters, since a shell runs it unquoted; the pinned binary and the ConPTY companions are re-hashed before use.

Probe captures and probe dirs are owner-only and removed when verify passes, fails or is stopped, each run's guards removing only what that run created, never by a pattern or a listing; a kill or a crash leaves them to be removed by hand.

- **Logs:**
  - `events.ndjson` and the files in `instances/<name>/diagnostics/` are 0600 inside 0700 directories.
  - serde_path_to_error drift reports, which can quote tool `input`, are written only to `diagnostics/`.
  - Logging format and fields belong to obs.

**Repository fixtures:** `fixtures/claude/<cli-version>/` is recorded by `viola verify --record` from live sessions with synthetic probe prompts; before any write verify scrubs the home prefix and the user word, and refuses the whole recording when a path, the user word or an email-shaped token survives, naming the file and a closed code, never the content; recorded payloads are reviewed for home paths, usernames and tool `input` before committing.

Key management and Data lifecycle are omitted for Minimal tier: there are no keys at rest; `events.ndjson` retention and bounding is an open item owned by arch, and any rotation scheme must keep 0600/0700 permissions and valid offsets.

**Accepted risk (verify's trusted runs, B, C, D and E):** Runs B, C and D are real interactive turns under a trusted parent, so the CLI persists their transcripts under `~/.claude/projects/` and the user's own global hooks run for them; Run E adds no transcript, the print-mode probe leaves only an empty project dir, viola itself writes nothing under `~/.claude`, and Run A leaves nothing.

**Accepted residual (a scratch footer reading of a newer CLI):** one `viola run` start under a tmpfs `--home`, no key typed, only the footer rows, scrubbed, written to evidence; it is no product path and no standing permission: another such reading needs its own answer.

**Accepted residual (a live round of `viola plugin install`):** a live round runs the CLI's own four plugin commands at local scope from a `proj/` outside the work tree, passing the folder-trust dialog by keys into its own pty only, never a desktop key; the CLI's writes are its own, and viola itself writes nothing under `~/.claude` or into `~/.claude.json`.

**Dev-host prerequisite (the real-CLI probe):** `viola verify` against the real `claude` runs from a folder the user trusts in Claude Code whose external CLAUDE.md import is already answered; verify never answers it.

**Accepted risk (local availability):** until arch resolves `events.ndjson` retention, unbounded growth of the file can exhaust local disk, an availability impact only, with no confidentiality or integrity impact.

## Dependency Security

Detail: .andromeda/security-plan-detail/dependency-security.md — read whole.

_[ALL tiers]_

**Audit tool:**
- cargo-deny `>=0.20.2` (advisories, bans, licences, sources).
- zizmor `>=1.30.1` for GitHub Actions workflows.
- cargo-audit `>=0.22.2` is not gated in v1 (it would duplicate cargo-deny advisories on the same `Cargo.lock`). It is reserved for v1.x `cargo audit bin` scans of cargo-auditable release binaries.

The vendored Microsoft ConPTY binaries sit outside every cargo graph, so no lockfile audit reaches them: their gate is `scripts/conpty-vendor.sh` (`--verify` checks the nupkg and per-file SHA-256 and the Microsoft Authenticode signer; `--probe` shows its refusals and a clean control); at run time the SHA-256 pin carries the signer. An own audit, never an exemption.

**`deny.toml` additions** (beside arch's licence list, C-crate bans and obs's telemetry-crate and `veil` / `tracing-subscriber` feature bans — arch §Build system):
- `[advisories]`: `unmaintained = "all"` (the default), `unsound = "all"`, `yanked = "deny"`, and `ignore = [{ id = "RUSTSEC-2017-0008", reason = "serial via portable-pty =0.8.1; serial ports never opened" }]`. This is the only expected ignore; re-check it whenever the portable-pty pin moves.
- `[sources]`: `unknown-registry = "deny"`, `unknown-git = "deny"` (crates.io only; this also keeps CVE-2026-5222's sparse-registry class out of reach).
- `[licenses]`: the `allow` list stays exactly `["MIT", "Apache-2.0", "Zlib", "Unicode-3.0"]` (arch §Build system). `0BSD` is admitted only per crate, by `[[licenses.exceptions]]` for `doctest-file` and `recvmsg`, the two 0BSD crates interprocess 2.4.4 pulls in (measured at chunk 2026-09-25-security-prerequisites: `cargo deny` 0.20.2 read `licenses FAILED` without them). It is never added to `allow`, so any other 0BSD crate still fails the gate, and each new exception needs its own Decisions Log entry (operator ratification `2026-09-25`).
- `[[bans.features]]`:
  - `rmcp` denies `transport-streamable-http-server` and `auth`.

## Error Handling

Detail: .andromeda/security-plan-detail/error-handling.md — read whole.

_[ALL tiers]_

**External responses** (to channel clients, CLI `--json` and MCP drivers): sanitised.
- No anyhow context chains, no absolute paths, no upstream text (prompts, tool `input`, assistant output), no serde_path_to_error paths or values, and no internal type names.
- The `Display` impls on `PtyError` (hand-written) and on `AgentError`, `ChannelError`, `StateError`, `PinError`, `StampsError`, `StampsReadError`, `Refused`, `McpError` and `ServeError` (`thiserror`) use fixed messages. Variant fields that hold paths or payloads are excluded from `Display`.
- Channel `-32603` uses a fixed `message` ("internal error") with `data: null`.
- MCP `isError` results carry only the `structuredContent` codes from Conventions (`refusal`/`detail`, or `error: instance-unreachable | wrapper-fault | invalid-params` — `instance-unreachable` with `detail: null`, `wrapper-fault` with `{code,message,data}` as `viola_channel::sanitised_fault` closes them, never the peer's own, `invalid-params` with a closed field word), a `refusal` that is no code word (`viola_core::is_code_word`) reading `unknown` and a string `detail` that is none reading null, `of_reply` here and `reply_of` on CLI `--json` alike, and every `isError` text is `refused: <code>`. Any other handler fault, a reply of no known shape or a panicked call is the JSON-RPC error `-32603` `internal error` with `data: null` (chunk 2026-10-17-mcp-server-for-drivers).

**Internal logging (for debugging):**
- Full error detail goes only to `instances/<name>/diagnostics/` (files 0600; format owned by obs) or, for short-lived CLI verbs, to stderr. stderr never carries upstream text, tool `input`, drift-report values or any other value on the NEVER-log floor (Bootstrap phases, `logging-redaction-wire`).

`hook` never writes to stderr and never exits non-zero: a security check failing in `hook` still ends in exit 0 with no body, so the dialog renders for the human; its hidden capture arms print nothing on every failure, their stderr always empty, their exit always 0.

**Error format:**
- **Channel:** JSON-RPC `error` for protocol faults, including `-32600` for frames over `MAX_FRAME` and `-32602` for `release`-with-`from`, and `result.refusal` for `not-delivered`/`control-character` and `not-delivered`/`empty-text`.

**Error reporting integration:** None. viola makes no outbound network calls. If obs ever adds an external reporter, the Logging bans below apply before transmission.

## Security Anti-Patterns (NEVER do these)

_[ALL tiers — single source of truth for all security bans]_

### Authentication

Detail: .andromeda/security-plan-detail/security-anti-patterns.md — read whole.

- NEVER create an interprocess Windows listener without `ListenerOptionsExt::security_descriptor`. The default DACL grants read to Everyone and anonymous.
- NEVER place a Unix socket directly in `/tmp` or at the `$TMPDIR` root (`/tmp/viola-<h12>.sock`). Always use a verified 0700 per-user directory (the Kea DHCP CVE-2025-32801/32802/32803 precedent).
- NEVER rely on the socket file's 0600 mode as the only Unix control: `unix(7)` says socket permissions may be ignored. NEVER set it with `ListenerOptionsExt::mode`: it returns `Unsupported` on macOS, which fails the bind; chmod after the bind instead.
- NEVER use Linux abstract-namespace sockets (no filesystem permissions).

- NEVER write any channel frame before verifying the server against a `snapshot.json` that passed the strict-modes check in the same process (the euid check never skipped), except the dated gaps: every client's euid check and macOS's pid and start-time check (no peer pid) are owed to "Unix endpoint and home hardening"; no other frame or process may borrow them.

- NEVER open a Windows client pipe without `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the default `connect_without_waiting` lets a squatter with SeImpersonatePrivilege impersonate the client).
- NEVER treat the channel `from` param as an authenticated identity. It is self-reported and serves link records and the `release` affordance guard only.
- Account-flow bans (reset enumeration, recovery questions, login rate limiting): N/A. There are no accounts or login endpoints (Threat Model: Auth model).

### Input

- NEVER trust schemars MCP schemas or client-side CLI checks alone. The wrapper re-runs `ViolaName::try_new`, the closed-enum deserialisation and `validate_paste_text`.
- NEVER join `instances/<name>` with a string that did not come out of `ViolaName::try_new` (MCP `target`, `link`/`unlink` params, notify events).
- NEVER write `send.text` or answer free text into the PTY if it contains any C0 control other than LF, CR and TAB (ESC above all), DEL (U+007F) or any C1 control (U+0080–U+009F), and NEVER strip them silently. Reject with `control-character`. The wrapper's `send` typing every CR LF pair and every other CR inside a text as one LF, and dropping its trailing CR and LF characters, of a text that has already passed `validate_paste_text` is not this stripping: CR and LF are allowed characters, validation runs first on the text as received, and no refused character is ever removed or typed (§Input Validation, Paste text row). Answer free text is typed as validated. NEVER refuse LF, CR or TAB: multi-line relays, plans and answers are normal. Refusing a text whose typed text is empty (`empty-text`) is not a refusal of those characters: there is nothing to type, and a text with content is never refused for holding LF, CR or TAB.
- NEVER run the control-character check over raw bytes. Check decoded `char`s, or valid UTF-8 continuation bytes (0x80–0xBF) are misread as C1.
- NEVER call `read_line` on a channel stream or `read_to_end` on hook stdin or child output without `Read::take(MAX_FRAME)`, and NEVER hand rmcp a `viola mcp` stdin reader that does not cap each line at `MAX_FRAME`, nor truncate or skip an over-long line instead of ending the session.
- NEVER enable serde_json's `unbounded_depth` feature; `deny.toml` bans it (§Dependency Security).
- NEVER model `behavior`, `dialog_id`, the wheel holder or the dialog kind as free `String`s. Use closed enums or integers even under tolerant parsing.
- NEVER use a `claude agents --json` row `name` as a `ViolaName` or `target`.
- SQL ban: N/A (no database or query language).

### Data Protection

- NEVER create `~/.viola/`, `--home` or any file under it with the default umask. Directories are 0700 and files 0600 (`OpenOptionsExt::mode`); the only exception is the pinned `bin/<version>-<hash>/viola` at 0700, and NEVER make it group- or world-writable. On Windows, NEVER accept a `--home` outside `%USERPROFILE%` without an explicit protected user + SYSTEM DACL, and NEVER skip the Windows owner + DACL strict-modes check at startup (`#[cfg(windows)]` must not return `Ok(())` unchecked), and NEVER pass a NULL DACL, a volume without persistent ACLs, or an inherit-only `GENERIC_*` grant just because no specific-rights ACE matched.
- NEVER run `statusline_command` from a `snapshot.json` whose home or instance directory fails the strict-modes check. Write access there equals code execution.
- NEVER reuse an existing `bin/<version>-<hash>/viola(.exe)` without re-hashing it (SHA-256, truncated) against `<hash>`, NEVER derive `<hash>` from a non-cryptographic hash (FNV, `DefaultHasher`), and NEVER reuse existing `plugin/` files without rewriting them. NEVER load or launch a `bin/<version>-<hash>/conpty/` companion without its full SHA-256 re-hash against the compiled pin through a `FILE_SHARE_READ`-only handle held until the spawn, and NEVER overwrite or delete a companion that fails it (left as found; the child runs on the inbox ConPTY).
- NEVER spawn a `.cmd`/`.bat` PTY child through portable-pty. Resolve to a real `.exe` (portable-pty 0.8.1 bypasses std's BatBadBut escaping).
- NEVER make channel handles inheritable, and NEVER adopt a portable-pty replacement that calls `CreateProcessW` with `bInheritHandles = TRUE`.
- NEVER commit `fixtures/claude/*` recorded from sessions that used real (non-synthetic) prompts, or before checking them for home paths and usernames (a `workspace.repo` naming this repository's own remote is kept, Data Protection → Repository fixtures).

### API

- NEVER enable rmcp's `transport-streamable-http-server` or `auth` features.
- NEVER skip request size limits: `MAX_FRAME` on the channel and on each `viola mcp` stdin line.

### Secrets

- NEVER write `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` or any R8-stripped `CLAUDE*` value into any log or stderr, `events.ndjson`, snapshots, `diagnostics/` or fixtures (consolidated floor: Bootstrap phases, `logging-redaction-wire`).
- NEVER commit `.env` files, local `--home` test directories or signing material to git.
- NEVER hardcode credentials in source or in the `include_str!` plugin files.

### Logging

- NEVER echo serde_path_to_error drift reports or anyhow chains into MCP `structuredContent` or channel `error.data`, and NEVER print an anyhow chain to stderr that still contains a serde_json or serde_path_to_error source (its `Display` quotes input values such as tool `input`).
- NEVER write to stderr from `viola hook`, and NEVER exit non-zero from it, including on security-check failures.
- NEVER print `wait`/`last` human-mode output, or `list` rows taken from `claude agents --json`, to a terminal without escaping C0/C1 controls (the same class as RUSTSEC-2025-0055).
- NEVER use tracing-subscriber `<0.3.20` if obs selects it.
- NEVER create `diagnostics/` files readable by other users.
- NEVER expose absolute paths in any external error.

### Code Patterns

Detail: .andromeda/security-plan-detail/security-anti-patterns.md — read whole.

- NEVER interpret upstream text (prompts, `last_assistant_message`, plan text, question and option text, tool `input`) as a viola command or config (R1). `statusline_command` is the only shell-out, and NEVER add a second one.
- NEVER build screen signatures, harness prefixes or local-command lists from runtime or upstream text. They come only from compiled `viola-agent-claude` ledger rows. The harness prefixes are four compiled literals matched on the prompt's raw start, no trim (`<agent-message from=`, `<task-notification>`, `<\cross-session-message`, `<cross-session-message`); the escaped cross-session form is the one escaped tag that classifies `harness`, so a human who types it at a prompt's start is filed `harness` (the founder's ratified side effect, Decisions Log `2026-09-29`).
- NEVER enable interprocess `try_overwrite` (TOCTOU deletion of an attacker-swapped file).
- NEVER feed vt100 outside `catch_unwind`. A parser panic must not take down the human's terminal path.
- NEVER reference a GitHub Action by `@stable`, `@v2` or any mutable ref. Use a full SHA with a version comment.
- NEVER restore `Swatinem/rust-cache` in the v1.x release workflow.
- NEVER ship `self_update` without its `signatures` feature (zipsign). A checksum from the same release proves nothing.

- NEVER let `run --mutants` wipe any directory except the Windows host mutation scratch `<repo parent>/viola-mutants-scratch`, guarded by its exact final component; NEVER re-create it without owner-only permissions, loosen the strict-modes check for it, fall back to `%TEMP%` or the repository, or print the path.

- NEVER let a test-side removal under `target/e2e-home` take anything but a dir the test side itself created; its two keepers NEVER follow a linked base unless its target is absolute and an owner-only real directory, create the target 0700 and remove nothing; `viola` itself never reads or writes the backing by that name.

### Universal

Detail: .andromeda/security-plan-detail/security-anti-patterns.md — read whole.

- NEVER add a listener (TCP port, WebSocket, `http` hooks, MCP HTTP transport) or a new channel method without a Security Decisions Log entry mapping it to this plan's IPC controls.
- NEVER let a security refusal block the human. Refusals go only to automation (`send`/`answer`), and hooks fail open.
- NEVER let a `viola` process on Windows reach any DLL load before `viola_pty::sideload::restrict_dll_search()` (System32-only default search, the second statement of `main` in every role): a bare-name load, portable-pty's `LoadLibraryW("conpty.dll")` included, must never resolve from the CWD or `PATH`. NEVER pre-load the sideloaded `conpty.dll` by a relative path. A sideload failure degrades to the inbox ConPTY silently: NEVER a refusal, an exit change or a byte on the human's terminal.
- NEVER let an exec-form `command` in the embedded `hooks.json` or `.mcp.json`, or in `viola plugin install`'s `.mcp.json`, or the statusline command `viola run` writes into `instances/<name>/settings.json` (it wraps the statusline with `viola hook statusline`), resolve `viola` through PATH. It must be the absolute pinned `bin/<version>-<hash>/viola(.exe)` path, or the absolute path of the exe that ran `plugin install`. Claude Code runs these on every hook event and for MCP, so a PATH lookup hands code execution to whatever is earliest on the session's PATH (architecture.md Deployment / Distribution and Plugin Scope; Threat Model Sec 2, child process spawning and PATH resolution).

- NEVER answer a `hook.dialog` with a non-`null` decision unless `ledger/stamps.json` holds a `viola verify` stamp for the child's CLI version on which every relied ledger row passes, and NEVER let any process other than `viola verify` write `ledger/stamps.json`: a stamp is what switches on dialog answering, PermissionRequest `allow` included.

- NEVER answer a `hook.dialog` with a non-`null` decision unless `viola run`'s version gate read `ledger/stamps.json` through the strict-modes check (`read_stamps_strict`); a refusal is `cli_verified:false`.
- NEVER let a process other than the instance's own wrapper write `instances/<name>/snapshot.json`. `endpoint`, `pinned_bin` and `statusline_command` in it decide where clients connect and what `hook statusline` executes (architecture.md Instance snapshot, "written only by that instance's wrapper"; Threat Model Sec 1 config).

- NEVER let `config.json`, a `VIOLA_*` environment variable or a CLI flag switch off any control in this plan (the IPC DACL or socket-directory check, the peer or server verification, the home strict-modes check, `validate_paste_text`): environment variables are not a configuration channel. The carve-outs, the two test-only seams and the terminal colour facts, switch off nothing; NEVER add another such seam or environment read without its own Decisions Log entry.
