## Design Philosophy

- **Mechanism, not policy.** viola carries input, answers dialogs when told to, logs everything and holds the wheel, but it never decides what to answer. Andromeda's decision rights and any other driver-side policy stay outside the binary, so every feature has to be expressible as a general bridge verb.
- **Measured, never assumed.** Any behaviour of the `claude` CLI that viola relies on is a row in a version-stamped capability ledger. On a CLI build nobody has verified, viola degrades to transport-only (the readiness gate is partial there, while a verified build runs the full gate on the compiled signatures: a poisoned screen model or a screen not quiet within the maximum wait still refuses, and no signature is read), and every send is confirmed after the fact (a matching `prompt-submitted` or, for a local command on the ledger, its measured post-condition; otherwise `not-delivered`), never presumed. The one exception is a ledger-listed local command whose post-condition is "none" or not yet measured on this CLI version: it returns `ok` with `confirmed: false` and detail `unconfirmable`.
- **The human always wins the wheel.** Human keystrokes are never blocked, refused or delayed past the current atomic paste. Automation is refused with a typed reason (`human-typing`, `budget-paused`, `unverified-cli`, `not-delivered`) instead of competing with the human.
- **No daemon; the disk is the shared truth.** Every `viola run` owns its own local-socket endpoint, every other verb is a separate process that owns no endpoint (short-lived, except the long-running `mcp` and `ui`), and the state all processes share lives in ndjson logs and atomic snapshots that survive a crash on either side.
- **Cross-platform from the first commit, Windows first.** Windows is the first target. The Windows, macOS and Linux paths build and pass CI on every commit against the fake agent, so no design choice may depend on tmux, a shell or POSIX-only behaviour. The first live run was on the Linux dev host, by the founder's ruling R-L1 (2026-10-07, relayed by the overseer), at chunk 2026-10-08-first-live-test-and-self-drive (`claude` 2.1.287 in foot 1.28.0 under Hyprland 0.56.2); Windows live behaviour stays proven on the CI runner under the fake agent until an interactive Windows host exists.

## Established Decisions

- **[Scale / Product] Personal v1, cross-platform from day one.** The founder runs v1 on their own subscription, with no accounts, no hosting and the GUI on 127.0.0.1. It is still built and CI-tested on Windows, macOS and Linux from the first commit, and the on-disk state is parsed defensively. Rationale: retrofitting cross-platform support onto a PTY/IPC tool costs far more than carrying it from the start, and the later public version (individual Claude Code subscribers) must not need a rewrite.
- **[Scope Boundary] General bridge, nothing Andromeda-specific inside.** Rationale: R4 (mechanism, not policy). Decision rights belong to the driver, so viola stays reusable for any overseer/builder pair (Pulse, Conductor, viola itself).
- **[Agent Coverage] Claude-first, with one concrete `viola-agent-claude` crate and no adapter trait yet.** The PTY, channel, wheel and state layers speak only viola's normalised events. Hook JSON parsing, the dialog answer mapping (S3/S7/S8), the R8 identity strip, npm-shim → `claude.exe` resolution and the Claude-specific half of the CLI version gate (`parse_version`, the capability-ledger rows, the stamp merge and the `verified` verdict, the fixture scrub) live only in `viola-agent-claude`, which stays pure (no I/O, no `viola-state` dependency). The gate's bounded `--version` spawn and stamps verdict are the root bin's `run::version_gate`, and the stamps file I/O is `viola_state::stamps` (as landed by chunk 2026-09-28-capability-ledger-and-viola-verify). Rationale: a trait designed before a second agent exists would encode guesses. Isolating the agent in one crate keeps the later extraction mechanical.
- **[Concurrency / Backend Framework] Hybrid sync core + Tokio only in `mcp` and `ui` (KEYSTONE).** Rationale: portable-pty's handles are blocking, so the pump needs threads either way. `hook` spawns once per hook event and must not pay for runtime startup. rmcp, axum and interprocess-async all require Tokio, so it is confined to the subcommands that use them. CI enforces this with a sole-root `cargo deny` `tokio` ban (`deny-sync.toml`, run once per crate listed in `scripts/sync-crates.txt`), evaluated for the Windows, macOS and Linux target triples, plus a `cargo check` of the listed sync crates without the `tokio` feature on all three OSes (CI job 3).
- **[PTY] portable-pty `=0.8.1` pinned behind viola's own `pty` seam (spawn · read · write · resize · wait · kill).** Child exit is detected on the process handle, never on EOF, because ConPTY does not close the output stream on exit. If 0.8.1's Windows `kill()` misbehaves, the fallback is `TerminateProcess` on `child.process_id()` via windows-sys. The host stdin handed to the pump is `viola_pty::host_stdin()`: on Windows with a console stdin it is viola's own reader calling `ReadConsoleW` (no Ctrl-Z wakeup control; UTF-16 → UTF-8, a split surrogate carried, every `0x1A` kept, a 0-unit read read again), because std's console stdin drops a read's trailing `0x1A` and ends input on a lone `^Z` — source-read at the pinned toolchain and as measured on `windows-2025` (ci#37226294797, `tui_ctrl_z…` green); elsewhere, and for a redirected Windows stdin, it is `std::io::stdin()`. Its callers are `run`'s pump and the fake agent. Rationale: 0.8.1 is spike-proven (S1, O1 render stress, the Pulse live test, and about an hour driving this arch session in Windows Terminal with no PTY defect). 0.9.0 is excluded because of the Windows garbage-read bug wezterm#6783. Swap triggers: portable-pty-psmux 0.9.7 if the O1 stray-spaces artifact reproduces only under `viola run` (then test `PASSTHROUGH_MODE`). An own ConPTY on windows-sys 0.61.2 + nix 0.31.3 comes only after a measured defect the seam cannot absorb. As built (chunk 2026-09-25-pty-wrapper-on-windows, measured on the Windows host in its research facts 1-5): `viola run` puts its own host terminal into raw input + VT output for the run through `HostTerminal` (Windows console modes; Unix termios) and restores the saved modes on Drop — without it ConPTY line-buffers keys until Enter and swallows Ctrl-C; off a terminal it is a no-op. The child's cwd is set explicitly to viola's current directory (portable-pty 0.8.1 defaults to `%USERPROFILE%`). viola resolves the child program to an absolute path itself (portable-pty's Windows search tries the exact name first and hits the extensionless npm sh shim). The pump keeps the ConPTY input writer until the child exits, because dropping it makes conhost send `CTRL_CLOSE` to the child (exit `0xC000013A`). The exit is recorded as `exit_source` `handle-wait` or `kill-fallback`. As measured (chunk 2026-09-29-h2-conpty-resize-probe, H2): a key written through the seam right after `resize` returned can fail to reach the child — on the windows-2025 runner (image `windows-2025-vs2026` 20260922.246.2), in an isolated loop of the viola-pty red test under `cargo llvm-cov nextest`, 13 of 200 iterations lost it (ci#36527891850), every loss the same class: the child's key-free size watcher saw the new size, viola's writer wrote and flushed the key, and the Rust test child blocked in its console read never received it; ConPTY wrote no cursor-position request (`dsr-cpr 0` on every loss, and on the dev host, Windows 10.0.26200.9457 / conhost 10.0.26100.8875, which read 20/20). The measured span runs from the ConPTY input-pipe write to that test child's console read; where inside it the key is lost is not established (an overseer read of microsoft/terminal's current source, relayed at that chunk's wrap, found no input-buffer flush on the resize path — a relay, not verified here). Whether the real `claude` (Node/libuv, `ReadConsoleInputW`) loses a key typed right after a resize is unmeasured; the working-route entry "Windows-only live measurements" owns that measurement, blocked on an interactive Windows host (the harness's local `run --local-live`, a real-`claude` `viola verify`, does not claim it), and the founder's product question on H2 stays open. viola never holds, queues or re-orders a human key behind a resize ([Human Takeover / Wheel]). A test that writes a key after a resize waits for the child to observe the new size first (0 of 200 lost, ci#36529038462). As built (chunk 2026-09-29-sideloaded-conpty, founder ruling 2026-09-29): on Windows x64 the child's ConPTY is Microsoft's current one, sideloaded. Every `viola` process, in every role, restricts its DLL search to System32 as the second statement of `main` (`viola_pty::sideload::restrict_dll_search`, process-wide and one-way), so a bare-name load never picks a `conpty.dll` planted in the CWD or on `PATH`. `run` pins the embedded `conpty.dll` + `OpenConsole.exe` into `bin/<version>-<hash>/conpty/` ([Deployment / Distribution]) and pre-loads `conpty.dll` by absolute path (`viola_pty::sideload::preload`: a relative path is refused, the module is never freed), so portable-pty `=0.8.1`'s own bare-name `LoadLibraryW("conpty.dll")` returns that module and the child is hosted by the pinned `OpenConsole.exe`; the seam and portable-pty are unchanged, and viola-pty knows no pinned path. `viola_pty::pty_backend()` reports `conpty-sideload` after a successful pre-load, else `conpty` (Windows) or `openpty`. An absent, tampered, unreadable or unloadable sideload fails open to kernel32's inbox ConPTY with no byte, refusal or exit change (`sideload_fallback` on `process-start`). Spawners outside `viola run` stay on the inbox ConPTY: the harness `supervise::spawn_in_pty`, root `tests/support/outer_pty.rs` and viola-pty's own tests. H2 with and without, measured in one run on the windows-2025 runner (image `windows-2025-vs2026` 20260828.587, ci#36563868040, the measurement-only race of the pre-`dce98ad` shape, 200 iterations each): sideloaded 0 of 200 lost, inbox 14 of 200 lost — beside the inbox 13 of 200 above; no rate is claimed. The sideloaded host writes a different spawn preamble, `ESC[1t ESC[c ESC[?1004h ESC[?9001h` (the inbox one: `ESC[?9001h ESC[?1004h`), and its DA1 query `ESC[c` holds the child's start until something answers it — as measured at the chunk's `evidence/da1-stall.md` on the dev host, 3.54 s unanswered on pipes vs 0.54 s answered (0.48 s on the inbox host); a terminal answers it, and the answer travels through viola's pump, so the child's start now waits for the pump. viola stays silent (it never answers DA1 itself); the stall of a `viola run` with no terminal on its stdio is an open product finding, owned by the working-route entry "Windows-only live measurements", blocked on an interactive Windows host.
- **[Screen Model] vt100 0.16.2 as a pre-send readiness gate only.** After `turn-ended`, the gate waits for the screen to go quiet, then requires the absence of every known modal signature and waits, up to its maximum wait, for the version-stamped input-box signature. As landed, the model is the pure `viola_agent_claude::screen::Screen` (no I/O, no clock read; every instant is a parameter), and `run` feeds it on its own feed thread (`src/run/gate.rs`): a tee on the pump output writes the human's bytes first and then offers a copy with `try_send` into a queue bounded at `FEED_CAPACITY` = 256 messages (`sync_channel`; the pump copies at most 8192 bytes per write, so at most 2 MiB waits for the model), so the passthrough never waits on the model. The `Screen` sits behind a mutex shared by the feed thread and the `Gate` handle `send` reads (`Gate::wait_ready`, re-read every 20 ms); each feed and resize runs under `catch_unwind` inside that lock. A caught vt100 panic poisons the model until the host size changes, and so does a message the full queue drops (a dropped byte desynchronises the screen): one `parse-rejected{parser:"vt100-feed", detail:"oversize"}` per poisoning episode, and a size message carries the drop count at its offer, so a drop after a queued resize poisons the fresh screen again. A poisoned model reads `input-not-ready`. The quiet period (`QUIET_PERIOD` = 300 ms) and the maximum wait (`GATE_MAX_WAIT` = 8.5 s) are compiled built-ins in `viola-agent-claude`, validated per CLI version by the stamped `quiet-period` row (the ready and turn screens settle within `GATE_MAX_WAIT`). The maximum wait was 5 s until chunk 2026-10-07-send-waits-out-the-paste-hint raised it on the founder's live ruling of 2026-10-07T10:29Z (relayed by the overseer), so that it covers the CLI's 8.0 s paste hint ([CLI Version Compatibility]); the quiet period is unchanged. As measured on 2.1.287 at that chunk (`evidence/reverify-round.md`), the ready screen settled in 1 103 ms and the turn screen in 617 ms. The signatures are compiled in `viola_agent_claude::screen::SIGNATURES`: `input_box: ["for agents"]` and `modals: ["Yes, I trust this folder", "Yes, allow external imports"]` (`Signatures::holds_any`). A screen is ready when a row contains an input-box literal and no row contains a modal literal. The per-version `modal-signature` row (an untrusted start shows a compiled modal literal) and `input-box-signature` row (the ready and turn screens hold the input-box literal and no modal) validate them. They landed with chunk 2026-10-05-real-cli-verify-probes, through the typed-input `viola verify` probe the founder ratified live on 2026-10-05 (relayed by the overseer), which runs the installed `claude` locally on the dev host only. `run` passes `Some(&SIGNATURES)` to `gate::start` exactly when its version gate read `cli_verified` (`Launched.cli_verified`): the full gate on a verified CLI version, and the partial gate otherwise. The verdict's consumer is confirmed `send`. On a verified CLI a modal row refuses at once, and a quiet screen with no input-box row keeps the gate waiting for one until `GATE_MAX_WAIT` has passed since the send entered the gate. A screen not quiet within the maximum wait, a poisoned model and a quiet screen still without an input-box row at the bound are refused: `send` types nothing and reports `not-delivered` with detail `input-not-ready`. The wait lives in the pure verdict (`Screen::verdict` reads `waiting_since`), so `Gate::wait_ready` did not change for it. Rationale: CLI-native modals bypass every hook (measured on 2.1.280: the "Teach auto mode…" modal swallowed a paste), and the screen lags the hooks. Signatures are compiled literals that each version's stamp validates. On a CLI version with no passing stamp the gate is partial: `Screen::verdict(None, …)` still refuses a poisoned model and a screen not quiet within the maximum wait, and a quiet screen is ready with no row read, so delivery confirmation decides the rest (the overseer's F1 reading of "falls back to delivery confirmation only", 2026-10-04). `Screen::rows()` is the only row-text exit, and only `viola verify` reads it. As measured at chunk 2026-10-05-real-cli-verify-probes (research M13 and M19, the dev host's 2.1.288), the CLI's trust is inherited from a trusted parent folder. The external CLAUDE.md imports approval is keyed on the git root instead, so a subfolder of a repo whose import is unanswered shows "Allow external CLAUDE.md file imports?" until that answer is set. viola types into neither dialog.

- **[Links] A link `driver → driven` is recorded when a `send` or `answer` is issued from inside a wrapped session to another instance, or by an explicit `viola link <driver> <driven>`. `viola unlink` removes it.** A call counts as coming from inside a wrapped session when the calling process has `VIOLA_NAME` set. Repeated sends and answers add no line, and an explicit `viola link` of an existing pair adds none and returns `{}`, so `since` is the time of the first link after any `unlink`. `unlink` appends an `unlink` event. - **[Budget Governor] Soft stop at the turn boundary.** Once a configured threshold is crossed (defaults `five_hour` ≥ 90 %, `seven_day` ≥ 85 %), automated `send` is refused with `budget-paused` through the same refusal path as `human-typing`. Human keys are never blocked, and a running turn finishes. The pause lifts when `resets_at` passes or on `viola release --budget`. `release --budget` leaves the wheel where it is, and a plain `release` returns the wheel to `driver` without lifting a budget pause. `release --budget` is sent to one instance's wrapper and lifts the pause for that instance only, until the crossed window's `resets_at` passes, so the next over-threshold reading does not re-pause it. The wrapper evaluates its gate from `budget.json`, read under `budget.json.lock`, at three points: at start, when a `send` arrives, and at each `turn-ended`. It never polls. A crossed threshold, a passed `resets_at` or an expired override takes effect at the next of these points, and only then is `budget-gate` appended. The wrapper mirrors its budget-pause state, including any override, to the instance snapshot, where `list` and `ui` read it. With figures missing, viola uses the newest reading from any wrapped session and shows its age. With no reading at all it records `unknown` and does not block. The statusline is wrapped only for sessions started by `viola run`, through a per-session settings override that then runs the user's own statusline command unchanged. - **[Real-time Strategy] SSE through axum `Sse::keep_alive`, fed by notify 8.2.0 tailing the ndjson logs.** Rationale: a one-way stream fits a view-only page. WebSocket would open a two-way surface before any auth exists, and polling lags the hooks and adds disk reads.
- **[Session Liveness] Heartbeat file primary; pid + process start time decide `gone`, and `claude agents --json` only enriches it.** Rationale: the prototype's heartbeat proved reliable. A bare pid is unsafe because pids get reused, which is why start time is matched too: a snapshot whose pid is dead, or alive with another start time, is `gone` whatever the heartbeat says (Session liveness). `claude agents --json` adds idle/busy status and shows unwrapped sessions as read-only rows. A `viola run` whose `ViolaName` is `live` or `stale` refuses to start (exit 1, with a message naming the instance); once the endpoint exists, a name with an answering endpoint refuses the same way. Otherwise `run` starts in this order: program resolution (the `.cmd`/`.bat` refusal, which writes nothing), collision check, pinned copy and plugin folder, the ConPTY sideload (Windows x64, fail-open), version gate, exclusive bind of the endpoint (a bind that finds the name taken is an exit-1 refusal, `squatted-name`, so two concurrent starts cannot both win), first snapshot (with `endpoint`, `pinned_bin` and `statusline_command` once written; `pid`, `started_at`) and heartbeat, the start `wheel` and `budget-gate` events, then the child spawn, after which the snapshot is rewritten with `child_pid`. As landed by 2026-09-28-capability-ledger-and-viola-verify every step has its place (the sideload step added by 2026-09-29-sideloaded-conpty): program resolution → collision → pinned copy and plugin → ConPTY sideload (`run.conpty_sideload`, Windows: `pin_companions` + the absolute-path pre-load; `outcome` `loaded` · `hash-mismatch` · `unreadable` · `load-failed` · `not-built`, never a refusal; its held handles live until `spawn_child` returns) → strip plan → version gate (`run::version_gate`: the bounded `--version` read logged as a `version-probe` `process-start`/`process-exit` pair, the stamps read, `cli_version`/`cli_verified` carried into the first snapshot and the `claude-child` `process-start`; `run` prints nothing on any gate outcome) → endpoint bind → first snapshot → heartbeat → start events → spawn, so the child's first SessionStart hook finds a listening endpoint and a recorded snapshot. A gone instance's directory is reused at once, and its `events.ndjson` is appended to, never truncated.
- **[GUI Control Scope] View-only in v1.** Only GET routes plus SSE, bound to 127.0.0.1, with a Host allowlist of `127.0.0.1:<port>` and `localhost:<port>`. Reads are gated in v1 too, because loopback TCP lets other local OS users read prompts and tool `input`: a per-launch token, exchanged once at `/?t=` for the `viola_<port>` cookie (`HttpOnly; SameSite=Strict; Path=/`, then a 303 to `/`), gates `/api/info`, `/api/sessions`, `/api/links` and SSE `/api/events` (401 `urn:viola:problem:unauthorized` without it); `/`, `/assets/*`, `/health` and `/ready` stay ungated (security-plan §Authentication & Authorization). `ui` is a pure reader of the on-disk ndjson and `claude agents --json`. Rationale: a page that cannot change state gives DNS rebinding nothing to exploit beyond reading. The page shows each session row (wrapped, or read-only unwrapped), its liveness (`live` · `stale`), idle/busy status, wheel holder and any pending dialog. It also shows the budget reading and its age, the link set, the `skipped` counts, and a live event feed over SSE. In v1 it is view-only, and no control accepts input. The v1.x step is a brake: the reserved `POST /api/sessions/{name}/pause` and `POST /api/sessions/{name}/unlink` routes, with the same effect as CLI `viola pause` and `viola unlink`. What must hold is that no state-changing route is reachable cross-origin or without per-launch proof that the caller is the local user. The mechanism is owned by the security specialist.
- **[Timestamps] chrono 0.4.45, RFC 3339 UTC, millisecond precision everywhere viola writes.** External `resets_at` is parsed tolerantly, and a malformed value becomes `unknown`, never an error. Rationale: chrono is already in the tree through rmcp, and external clocks must never break parsing.
- **[Validation] Two regimes.** External payloads (hook JSON, `claude agents --json`, statusline) are parsed tolerantly: no `deny_unknown_fields`, `#[serde(default)]` / `Option<T>`, the raw `serde_json::Value` kept for the fixture recorder, and serde_path_to_error for drift reports. viola's own formats are versioned-tolerant: every channel `params`, event and snapshot carries `v`, and readers skip and count unknown kinds and fields. nutype newtypes `ViolaName` and `Percent`. No garde or validator. Rationale: the CLI changes between builds, and parsing must never break when the ledger is the thing that decides behaviour. `deny_unknown_fields` on own formats was rejected because mixed binary versions are real.
- **[Error Handling] thiserror 2.0.20, one enum per workspace crate (one ratified exception: `viola-pty`'s `PtyError` has a hand-written `Display`/`Error` with fixed messages, because the seam's normal dependencies are exactly portable-pty, tracing, windows-sys and libc; portable-pty's anyhow error is kept only as a boxed source. `viola-agent-claude`'s `AgentError` sits at the crate root and holds the stamps envelope's `StampsMalformed` beside the hook payload's `Malformed` — the second enum `StampError` was folded into it by chunk 2026-09-29-verify-stamped-test-homes-and-harness. One open divergence, not an exception: the crate also holds the thiserror enum `Refusal` (`BatchScriptChild`, `NotFound`, the `resolve_program` refusal), which predates that fold; the rule stands, and its fold or ratification is open); anyhow 1.0.104 only in the `viola` bin: its `main`, dispatch (`cmd::dispatch` returns the error with the resolved home and instance) and the catch-site reporter `viola::obs::report_internal_error`.** `RefusalReason` lives in `viola-core`. Rationale: callers branch on refusal variants across three surfaces (channel, CLI exit codes, MCP `isError`). anyhow's context chains are only useful where a person reads them: the owner's post-mortem, which gets the chain as `chain` in `instances/<name>/diagnostics/detail-<role>.ndjson`, never a role line, stdout or stderr.
- **[Module Boundaries] Cargo workspace, flat `crates/` layout, with the root `Cargo.toml` as both the `viola` bin package and `[workspace]`.** Members: `viola-core`, `viola-pty`, `viola-channel`, `viola-state`, `viola-agent-claude`, `viola-mcp`, `viola-ui`, plus the test-only `viola-e2e` (the `viola-harness` agent-run harness; no product crate depends on it). Each product crate is created by the first chunk that consumes it. `fuzz/` (the `viola-fuzz` cargo-fuzz targets) is NOT a member. It is its own cargo workspace, excluded by the root's `exclude = ["fuzz"]`, so its nightly toolchain and C++-building libfuzzer-sys never enter the root graph. Only `viola-mcp` and `viola-ui` list `tokio`, and `viola-channel`'s Tokio client sits behind a `tokio` feature only `viola-mcp` enables. Rationale: the compiler enforces that `viola-pty` cannot see `viola-agent-claude`. `cargo install --path .` requires the bin at the root. cargo_pup needs nightly and was rejected.
- **[Deployment / Distribution] `cargo install --path .`, with the plugin compiled into the binary (KEYSTONE).** `hooks/hooks.json`, `.mcp.json` and `.claude-plugin/plugin.json` are embedded via `include_str!`, and `plugin.json`'s version comes from `CARGO_PKG_VERSION`. At start, `viola run` copies its own exe to `<viola home>/bin/<CARGO_PKG_VERSION>-<short content hash>/viola(.exe)` if that copy is absent, and re-hashes an existing copy before reusing it: a copy that no longer matches refuses the start (exit 1, `pinned-hash-mismatch`) and is left as found. On Windows x64 the binary also embeds Microsoft's ConPTY companions (`src/conpty.rs`: `include_bytes!` of `vendor/conpty/<version>/x64/{OpenConsole.exe,conpty.dll}`; the package version, the nupkg SHA-256 and the two file SHA-256s have that file's text as their one home) and writes them write-if-absent to `bin/<version>-<hash>/conpty/` (`viola_state::pin::pin_companions`; never overwritten). At every start each companion is opened with `FILE_SHARE_READ` only and re-hashed in full against its pin, and the handles are held until the spawn. Unlike the exe, a mismatched companion never refuses the start: it is left as found, never loaded, and the child runs on the inbox ConPTY ([PTY]). The subdirectory, not the pinned dir itself, because the pinned dir is first on the child's PATH. The first start of a version writes the two files (1 176 216 B); as measured at chunk 2026-09-29-sideloaded-conpty on the dev host under a parallel test suite, `pin_companions` took a median 1 193 ms there (each write ~0.55 s), while CI's perf and test jobs stayed green (ci#36566391084) — the root tests seed their homes with the companions instead (test-plan §5), and no bound was raised. It rewrites the plugin files on every start to `<viola home>/plugin/<CARGO_PKG_VERSION>-<short content hash>/` and substitutes the copy's path (forward slashes) into every exec-form `command` in `hooks.json` and `.mcp.json`. It then passes that folder with `--plugin-dir`, sets `VIOLA_BIN` to the copy and puts the copy's folder first on the child's PATH. `hooks.json` registers seven exec-form entries, each `"command": "@@VIOLA_BIN@@"` (substituted at start) with `"args": ["hook", "<kebab event>"]`: SessionStart, UserPromptSubmit and Stop with `"timeout": 5`; SessionEnd with no `timeout` key; Notification, PostToolUse and PostToolUseFailure with `"async": true`. The dialog tier joins them (chunk 2026-10-04-dialog-answers-by-dialog-id): PreToolUse with `"matcher": "AskUserQuestion|ExitPlanMode"` and PermissionRequest, each with `"timeout": 75` — nine exec-form entries in all. Until the `mcp` verb exists, `.mcp.json` ships `{"mcpServers": {}}` (operator ruling at the 2026-09-27-instance-state-and-start-order plan: a registered command that exits 2 would block Claude Code). Hooks and MCP never search PATH. Rationale: the binary and the plugin can no longer drift apart. The prototype proved that PATH-found hooks run a different binary from the wrapper after a rebuild. The content hash is part of the key because `CARGO_PKG_VERSION` stays `0.1.0` across development rebuilds, so the version alone would collide. A rebuild therefore never changes what a running session calls. Known trade-off: a hook fix applies only to sessions started after the rebuild. The per-frame `v` + sender version stays as the second safety net, for the optional user-level install (`viola plugin install`), which is not bound to a wrapper's pinned copy.
- **[Plugin Scope] The plugin loads only into wrapped sessions via `--plugin-dir`.** Both driver and driven run under `viola run`. `viola plugin install` (a local marketplace) is optional, for the MCP verbs in an unwrapped driver. The installed plugin carries only `.mcp.json` and no hooks, so a wrapped session that also has it installed never runs two hook processes for one event (two `hook.dialog` requests for one dialog). Its `command` is the absolute path of the exe that ran `plugin install`, never a PATH lookup. Whether Claude Code loads both a `--plugin-dir` plugin and an installed plugin with the same name, and which `viola` MCP server a wrapped session then uses, is a capability-ledger row. Rationale: unwrapped sessions carry no viola hooks at all, so there is no per-tool-call spawn cost outside viola. The exceptions are `viola verify`'s transient unwrapped children, all gone when verify ends. The first is the print-mode probe, an unwrapped `claude -p` that loads only the `viola-verify-probe` plugin (four exec-form `hook <event> --capture` hooks) from `ledger/probes/<pid>/plugin/`. The other four are the interactive runs: Run A, untrusted in an OS-temp `viola-verify-*` dir and killed at its screen; Run B, trusted in `<cwd>/.viola-verify-<pid>/`; and Runs C and D, trusted in `<cwd>/.viola-verify-<pid>-dialogs/` and `<cwd>/.viola-verify-<pid>-plan/`, each loading the dialog-kind `viola-verify-probe` plugin. Runs B, C and D, as real interactive turns, also run the user's own global hooks and status line, and each leaves the CLI's session transcripts under `~/.claude/projects/` (an accepted residual, security-plan Data Protection): Run B two per real-CLI verify, its session and the one its pasted `/clear` opens, and C and D one each.
- **[CLI Conventions] Human text by default, `--json` for agents, a typed exit code per refusal. Prompt text comes from stdin or `--file`, never from a leading-slash argument.** viola warns when an argument carries a Git Bash rewritten-path prefix. Rationale: Git Bash rewrites `/skill` arguments into Windows paths (brief §6), and agents need machine-parseable refusals.
- **[CI/CD] GitHub Actions native matrix on three OSes, tests against the fake agent, the real CLI only in local live tests.** The fake agent is substituted by naming its executable after `--` (`viola run <name> -- <fake agent> <args>`). viola resolves the child program to an absolute path itself (on Windows a PATH search over PATHEXT only, never the bare name) and spawns that. A `.cmd`/`.bat` child is refused (exit 1, `batch-script-child`), except the `claude` npm shim: `claude.cmd`/`claude.bat` resolves to `<dir>/node_modules/@anthropic-ai/claude-code/bin/claude.exe` when that file exists, and the shim is never read. Each test runs in its own viola home (`--home`, see Config management), so parallel tests never share an endpoint, log or `budget.json`. Rationale: no tokens spent and no flakes in CI, and no cross-compilers (cross 0.2.5 is stale).
- **[Hosting] None.** Rationale: local-only v1. Docker, serverless and PaaS do not apply.
- **[Mobile] N/A in v1.** Rationale: the phone view is the same web page behind authentication, in a later version.
- **[AI/ML] N/A.** Rationale: D2, subscription only through the unmodified `claude` CLI. The binary makes no model API calls.
- **[Primary Keys] No database keys.** Instances are identified by `ViolaName`, endpoints by its short hash. Rationale: identity is by instance, never by location (R5).
- **[Naming] Product, binary and identifiers use the `viola` prefix.** Env vars are `VIOLA_NAME`, `VIOLA_DIR`, `VIOLA_BIN`, and the newtype is `ViolaName`. Two ratified exceptions: the test seams `FAKE_AGENT_PUMP_DELAY_MS` and `FAKE_AGENT_HOOK_PANIC`, each read only by a `viola` built with the test-only `fake-agent` feature and never present in a release build (§Occupied Resources → Environment variables). `BRIDGE_NAME` and `BridgeName` in earlier artifacts are superseded. Rationale: one name everywhere removes the need to translate between prototype and product.
- **[Deferred] Deferred to specialists and later versions:** the frontend framework (design specialist); brake auth and auth generally (security, v1.x); the test framework, fake-agent harness and `viola verify` probe design (tests); logging and observability (obs); self-update, signing, winget/Homebrew/Scoop and a marketplace entry (later version).

## Conventions

**Interfaces and versioning**
- **Five interfaces from one binary:** CLI verbs, MCP tools (stdio JSON-RPC 2.0), the hook stdin/stdout contract (owned by Claude Code), the wrapper channel (JSON-RPC 2.0 over ndjson on a local socket), and GUI HTTP GET + SSE. There is no REST write surface, GraphQL, gRPC or tRPC.
- **Protocol versioning:** an integer `v` starting at `1` in every channel `params`, ndjson event line, snapshot and GUI JSON body. Adding a field or event kind is additive and needs no bump. Removing or changing a field's meaning bumps `v`. A wrapper receiving `params.v` higher than it supports answers `-32602` with `data.supported` and `data.wrapper` (its `CARGO_PKG_VERSION`).
- **Sender version:** every channel `params` carries `"sender": "<CARGO_PKG_VERSION>"`. A snapshot's `writer` holds the same value for the binary that wrote it. `/api/info`'s `proto` is the highest channel and event-line `v` the binary speaks, while its own `v` versions the body.
- **GUI routes:** unversioned paths under `/api/` (`/api/sessions`, `/api/links`, `/api/events`, `/api/info`) plus `/health` and `/ready`. Only the GET method exists. Any other method gets `405`. Content types:
  - `application/json` for `/health`, `/ready`, `/api/info`, `/api/sessions` and `/api/links`.
  - `application/problem+json` for errors, carrying `v` as an extension member.
  - `text/event-stream` for `/api/events`.
  - `text/html` and each asset's own type for `/` and `/assets/*`.

  `/ready` answers 503 with its own readiness body, never Problem Details. `state-unreadable` applies to `/api/*` routes only.
- **Channel methods:** lower-case, dot-namespaced for hook traffic. Requests: `send`, `wait`, `last`, `answer`, `pause`, `release`, `link`, `unlink`, `hook.dialog`. `list` is not a channel method. Notifications: `hook.event`. JSON-RPC ids are integers, monotonic per connection.

**Error handling schema**
- **Channel refusal (a normal outcome, not an error):** `{"jsonrpc":"2.0","id":<n>,"result":{"refusal":"<reason>","detail":<string|null>}}`.
- **Channel success:** `{"jsonrpc":"2.0","id":<n>,"result":{"ok":<payload>}}`.
- **Channel protocol fault:** `{"jsonrpc":"2.0","id":<n|null>,"error":{"code":<int>,"message":"<text>","data":<object|null>}}` with codes `-32700` parse error, `-32600` invalid request, `-32601` unknown method, `-32602` bad params / unsupported `v`, `-32603` internal error.
- **`RefusalReason` (serialised kebab-case):** `human-typing` · `budget-paused` · `unverified-cli` · `not-delivered` · `unknown`. `unknown` is `#[serde(other)]`, so an older client can still read a refusal from a newer wrapper. `detail` values are kebab-case strings from a closed set per reason, extended only in `viola-core`:
  - `human-typing`: `null` · `manual-pause`
  - `budget-paused`: `five-hour` · `seven-day`
  - `unverified-cli`: `null`
  - `not-delivered`: `input-not-ready` · `no-prompt-submitted` · `turn-running` · `unknown-dialog` · `control-character` · `empty-text`
  - `unknown`: any value

  Readers treat an unrecognised `detail` as opaque text, never as an error. When several refusals apply, the wrapper returns only the first in this order. For `send`: `not-delivered`/`control-character` first (`viola_core::validate_paste_text`: LF, CR and TAB pass; every other C0, DEL and C1 is refused, never stripped; the CLI checks before any frame and the wrapper checks again), then `not-delivered`/`empty-text` (the typed text, the text with every CR LF pair and every other CR as one LF and without its trailing CR and LF characters ([Delivery Confirmation]), is empty; the CLI checks before any frame and the wrapper checks again, before the first wheel read; a text that also holds a refused character is still `control-character`), then `human-typing`, `budget-paused`, `not-delivered`/`turn-running` (a turn running, or another `send` in flight), then the readiness gate (`input-not-ready`, also when no child has started), then `human-typing` and `not-delivered`/`turn-running` read a second time once the gate has returned ready, and then the confirmation (`no-prompt-submitted`) outcome. A paste that fails after `send-issued` is `input-not-ready` with that send's `cursor`. For `answer`: `not-delivered`/`control-character` first (`validate_paste_text` on the response's free text; the CLI checks before any frame and the wrapper checks again), then `human-typing`, `unverified-cli`, `not-delivered`/`unknown-dialog`. `unconfirmable` is not a refusal detail. It appears only in an `ok` payload (`{"confirmed":false,"detail":"unconfirmable"}`), for a ledger-listed local command whose post-condition is "none" or not yet measured on this CLI version.
- **CLI exit codes:**
  - `0` ok
  - `1` internal error (anyhow edge), `viola run` refusing to start because its `ViolaName` is `live` or `stale` ([Session Liveness]; `detail:"already-live"`, stderr `unable: <name> is already live` / `hint: viola list`, or `unable: <name> is still running but not answering` with the stale hint), `viola run` refusing a pinned copy that fails its re-hash (`detail:"pinned-hash-mismatch"`, `unable: the pinned viola copy failed its integrity check`), `viola run` refusing a `.cmd`/`.bat` child program before any spawn (`process-exit{subject:"self", exit_code:1, detail:"batch-script-child"}`, the two fixed `unable:`/`hint:` stderr lines), and `viola run` losing the exclusive endpoint bind to another holder (`detail:"squatted-name"`, `unable: the endpoint for <name> is held by another process` / `hint: another process holds this name's endpoint; stop it or pick another name`, no path, pid or pipe name); `viola verify` with a failing ledger row (its stamp still written, last stdout line `stamped <ver>  <n> pass  <m> fail`) and verify's refusals, each an `unable:` + `hint:` pair on stderr with no path: `the claude CLI was not found` / `install Claude Code or put it on PATH`, `the claude CLI is a .cmd or .bat script` / `pass the real executable, not a .cmd or .bat shim`, `the CLI version could not be read` / `run claude --version to check the install`, `a recorded fixture is not clean: <file> <code>` (a screen: `<file> row <n>[ seam] <code>`; codes `home-path` · `absolute-path` · `username` · `email`; never the content) / `record with a viola home under your user home`, plus run's pinned-copy re-hash refusal; and the `cli` role's internal error: `src/main.rs` `role_of` files every first word but `run`, `hook` and a leading `-` flag under `cli` (so `send`, `wait`, `last`, `answer`, `pause`, `release` and `verify`), and a dispatch `Err` or a caught panic in any of them prints exactly `error: internal error` on stderr once, from the `main` catch site, no hint — no dispatch arm prints it; for `viola wait` / `viola last` exit 1 also covers a refusal reply, a reply of no known shape, and any channel error but a failed connect or a closed / reset connection (those are exit 21)
  - `2` usage error (clap, a second positional to `viola send` included; never produced by `viola hook`), and `viola send` text over `MAX_FRAME` or not UTF-8 (`error: the text must be readable UTF-8 of at most 16 MiB`)
  - `10` `human-typing`
  - `11` `budget-paused`
  - `12` `unverified-cli`
  - `13` `not-delivered`
  - `14` `unknown` refusal
  - `20` protocol fault from the wrapper
  - `21` instance unreachable (no live endpoint for the `ViolaName`)
- **`viola hook` exit codes:** always 0, including on clap parse errors, channel failures and panics caught at the edge. Exit 2 is forbidden.
- **MCP:** a success is a tool result with `isError: false` and the channel `ok` payload as `structuredContent` (for `list`, the caller-side `{items, budget, skipped}` payload). A refusal is a tool result with `isError: true` and the same `refusal` + `detail` in `structuredContent`. An unreachable instance and a wrapper protocol fault are also `isError: true` tool results. Their `structuredContent` is `{"error":"instance-unreachable"|"wrapper-fault","detail":…}`, the same as CLI `--json`. Only faults on the MCP connection itself are JSON-RPC errors.
- **GUI HTTP errors:** RFC 9457 Problem Details (`application/problem+json`) with `type` URNs:
  - `urn:viola:problem:host-not-allowed` (403)
  - `urn:viola:problem:method-not-allowed` (405)
  - `urn:viola:problem:not-found` (404)
  - `urn:viola:problem:state-unreadable` (503)
  - `urn:viola:problem:unauthorized` (401): a missing or mismatched `viola_<port>` cookie on a gated route ([GUI Control Scope])
  - `urn:viola:problem:cross-origin-forbidden` (403): reserved for the v1.x brake routes, not served in v1
- **Rust error types:** one error enum per crate, named `<Crate>Error` (`PtyError`, `ChannelError`, `StateError`, `AgentError`, `McpError`, `UiError`, `CoreError`), each a `thiserror` enum except `PtyError`, whose `Display`/`Error` are hand-written with fixed messages ([Error Handling]; `viola-agent-claude`'s pre-existing `Refusal` beside `AgentError` is the one open divergence named there). nutype validation errors fold into the owning crate's enum. `anyhow` appears only in the root bin crate.

**Naming patterns**
- **Crates:** `viola-<area>`, kebab-case. Rust modules and files are snake_case, types are UpperCamelCase, functions and variables are snake_case, and constants are SCREAMING_SNAKE_CASE (standard Rust).
- **JSON field names:** snake_case in every viola format (`last_assistant_message`, `resets_at` and `used_percentage` stay as Claude emits them).
- **Enum string values on the wire:** kebab-case (`#[serde(rename_all = "kebab-case")]`), covering event kinds, refusal reasons, details and wheel holders (`human`, `driver`).
- **Normalised event kinds (`viola-core`):** `session-start`, `turn-ended`, `prompt-submitted`, `question`, `permission`, `plan`, `session-end`, `activity`, `link`, `unlink`, `wheel`, `budget-gate`, `send-issued`, `send-confirmed`, `send-refused`. New kinds are added only in `viola-core`, never with Claude-specific names.
- **Hook → kind map (in `viola-agent-claude`):**
  - SessionStart → `session-start`. `data.cause` is one of `startup` · `clear` · `resume` · `compact` · `unknown`, and `data.agent_session_id` holds the new session id.
  - UserPromptSubmit → `prompt-submitted`.
  - PreToolUse `AskUserQuestion` → `question`.
  - PreToolUse `ExitPlanMode` → `plan`.
  - PermissionRequest → `permission`, except a PermissionRequest that repeats the armed `question` / `plan` dialog's tool with an equal `tool_input`: that is the dialog's continuation and raises no event.
  - Stop → `turn-ended`.
  - SessionEnd → `session-end`.
  - Notification, PostToolUse and PostToolUseFailure → `activity`. It is log-only and never wakes `wait`.
  - `hook statusline` emits no event.
- **Environment variables:** `VIOLA_` prefix, SCREAMING_SNAKE_CASE, for every variable the product reads or sets. Test-harness-only variables use the `AGENT_RUN_` prefix and are never read by the `viola` binary. The two ratified exceptions are the test seams `FAKE_AGENT_PUMP_DELAY_MS` (capped at 5 s; operator ruling, 2026-09-27) and `FAKE_AGENT_HOOK_PANIC` (fires only on the exact value `1`; the founder's ratification, 2026-09-28): each is read only under `cfg(feature = "fake-agent")`, is absent from release builds, and carries neither prefix because it is neither product plumbing nor harness-only.
- **On-disk files:** lower-case with `.ndjson` for logs, `.json` for snapshots and `.lock` for lock files, one lock file per guarded file (`<name>.lock`).
- **CLI:** flags are kebab-case long options (`--json`, `--file`, `--budget`, `--port`, and the global `--home`). Subcommands are single lower-case words. Verb arguments mirror the channel `params`: `viola send <target>` (text from stdin or `--file`), `viola wait <target> [--after <cursor>] [--timeout-ms <n>]`, `viola last <target>`, `viola answer <target> <dialog_id>` (the `response` object as JSON from stdin or `--file`), `viola pause <target>`, `viola release <target> [--budget]`, `viola link <driver> <driven>`, `viola unlink <driver> <driven>`. Like the MCP server, the CLI adds `from` from its own `VIOLA_NAME` when set.

**Data model conventions**
- **No database, so no UUID or serial keys.** The instance key is `ViolaName`: ASCII `[a-z0-9-]`, 1–32 characters, starting with a letter, enforced by nutype.
- **Endpoint name:** `viola-<h>`, where `<h>` is the first 12 hex characters of an FNV-1a 64-bit hash over `ViolaName` + `\0` + the absolute viola home path. It is hand-written in `viola-channel` and recorded in the instance snapshot. std `DefaultHasher` is forbidden because its output is not stable across Rust releases, and mixed binary versions must agree on the name.
- **Timestamps:** field `ts` on every event and frame, and `*_at` for other instants (`started_at`, `resets_at`, `written_at`). Always RFC 3339 UTC with milliseconds and a `Z` suffix, for example `2026-09-23T19:43:58.123Z` (chrono `to_rfc3339_opts(SecondsFormat::Millis, true)`).
- **Optional fields:** Rust `Option<T>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`. viola omits absent fields on write, and readers treat missing and `null` the same.
- **Unparseable external values** become the string `"unknown"` in viola's own records, never an error. This covers `resets_at`, `used_percentage` and a missing statusline window.
- **Percentages:** `Percent` newtype, 0–100, serialised as a JSON number.
- **ndjson line discipline:** one complete JSON object plus `\n` per single `write` call. Multi-line text travels as an escaped JSON string on one line.

## Standard Contracts

**GUI liveness: `GET /health`** (200 whenever the `ui` process serves requests)
```json
{"v":1,"status":"ok","name":"viola","version":"0.1.0","ts":"2026-09-23T19:43:58.123Z"}
```

**GUI readiness: `GET /ready`** (200 when viola home is readable. 503 with the same shape and `"status":"not-ready"` otherwise. `claude_agents` failing alone does not make it not-ready, because it only enriches.)
```json
{"v":1,"status":"ready","ts":"2026-09-23T19:43:58.123Z",
 "checks":{"viola_home":"ok","event_tail":"ok","claude_agents":"ok"}}
```
Check values: `"ok"` · `"unavailable"` · `"error"`.

**Service info: `GET /api/info`**
```json
{"v":1,"name":"viola","version":"0.1.0","proto":1,"pid":12345,
 "started_at":"2026-09-23T19:43:58.123Z","bind":"127.0.0.1:47319",
 "viola_home":"C:/Users/<user>/.viola",
 "verified_cli_versions":["2.1.280"]}
```

**GUI list envelope** (`/api/sessions`, `/api/links`). There is no pagination: lists are personal-scale and returned whole. `skipped` counts records a reader could not interpret, so the page can show them.
- `/api/sessions` item: `{name, wrapped, liveness, status, wheel?, budget_paused?, dialog_pending, cli_version?, cli_verified?}`.
  - `budget_paused` is the instance's own gate from its snapshot. It is `false` after a `release --budget` override, and it is absent when the session is unwrapped. The envelope's `budget.paused` only says that the newest reading crosses a threshold.
  - `wrapped: false` marks a read-only unwrapped row from `claude agents --json`. Its `name` is the session identifier that `claude agents --json` reports (part of the join-field ledger row). It is not a `ViolaName` and is never a valid `target`. Its `liveness` is `live` and `dialog_pending` is `false`, and `wheel`, `budget_paused`, `cli_version` and `cli_verified` are absent.
  - `liveness` is `live` or `stale`. Gone instances are omitted.
  - `status` is `idle`, `busy` or `unknown`.
  - `wheel` is `human` or `driver`, and is absent when the session is unwrapped.
  - The `/api/sessions` envelope also carries a top-level `budget`: `{five_hour, seven_day, read_at, paused}`, or `"unknown"`. `five_hour` and `seven_day` are each `{used_percentage, resets_at}`, with either field `"unknown"` when unparseable and the whole window `"unknown"` when the statusline omits it, because the two windows reset independently and a budget pause lifts at the crossed window's own `resets_at`. `budget.json` holds the same per-window reading plus `read_at`. The page derives the reading's age from `read_at`.
- `/api/links` item: `{driver, driven, since}`.
```json
{"v":1,"generated_at":"2026-09-23T19:43:58.123Z","items":[],
 "skipped":{"unknown_kinds":0,"unknown_fields":0,"torn_lines":0}}
```

**GUI HTTP error** (RFC 9457)
```json
{"v":1,"type":"urn:viola:problem:host-not-allowed","title":"Host not allowed","status":403,
 "detail":"Host header must be 127.0.0.1:47319 or localhost:47319"}
```

**SSE feed: `GET /api/events`** (`text/event-stream`, never compressed, `Sse::keep_alive` comment every 15 s)
- `event:` is the normalised event kind, for example `turn-ended`.
- `id:` is a composite cursor over every tailed instance: `<ViolaName>:<byte offset>` pairs joined by `,`, where each offset is the end of the last line sent for that instance, or, if none has been sent yet, the offset its tail started from. Every tailed instance is always listed, so an instance that was present but quiet is never replayed from 0. On reconnect, the browser's `Last-Event-ID` resumes every listed instance from its offset.
  - An instance missing from the cursor appeared after the stream started, so it is sent from offset 0.
  - An offset beyond the file's length means the file was replaced outside viola, since viola never truncates `events.ndjson`. That instance is replayed from 0.
  - Without `Last-Event-ID`, the stream starts at each file's current end, and the page first loads current state from `/api/sessions` and `/api/links`.
- `data:` is the ndjson event line, verbatim.

**ndjson event line** (`events.ndjson`, per instance)
```json
{"v":1,"ts":"2026-09-23T19:43:58.123Z","instance":"builder","kind":"turn-ended","source":"hook","data":{}}
```
`source` ∈ `hook` · `wrapper` · `cli`. `data` is kind-specific, uses only viola's normalised fields, and never embeds a raw Claude payload.

**Snapshot envelope** (atomically replaced JSON)
```json
{"v":1,"written_at":"2026-09-23T19:43:58.123Z","writer":"0.1.0","data":{}}
```
A snapshot whose `v` is higher than the reader supports, or that fails to parse, is ignored, and the state is rebuilt by replaying `events.ndjson`. Replay recovers only log-derived fields: `links`, `agent_session_id`, `wheel`, `budget_paused` and `budget_override_until`. Fields no event carries (`endpoint`, `pid`, `started_at`, `pinned_bin`, `statusline_command`, `cli_version`, `cli_verified`, `child_pid`, `pending_dialog`) are treated as absent. Liveness then rests on the heartbeat alone, so the instance is `live` or gone and never `stale`. The endpoint is rebuilt as described under IPC endpoints, and `hook statusline` prints nothing.

**Ledger stamps envelope** (`ledger/stamps.json`, atomically replaced JSON, written only by `viola verify` through `viola_state::stamps::update_stamps`)
```json
{"v":1,"written_at":"2026-09-28T15:14:02.311Z","writer":"verify","data":{"versions":{"2.1.283":{"verified_at":"2026-09-28T15:14:02.311Z","rows":{"shim-resolution":"pass"},"measured":{"largest_hook_payload":{"SessionStart":412}}}}}}
```
`writer` is the literal `"verify"`, not a binary version. `rows` maps each ledger row id to `"pass"` or `"fail"`; `measured` holds the probe's readings: `largest_hook_payload` per spine event, in bytes, and `typed_probe` `{ready_settle_ms, turn_settle_ms, prompt_latency_ms, max_turn_gap_ms}` from verify's interactive runs, and `dialog_probe` `{parallel_both_before_first_post}` (bool or null, from Run C's captures; additive, no `v` bump). `run` reads no field of `measured`. A merge replaces only its own version's entry and keeps unknown versions and unknown top-level and `data` fields; bytes of the wrong shape are replaced whole. A version is verified only when every one of its rows reads `pass`. A non-`v:1` or wrong-shaped envelope is `AgentError::StampsMalformed` to a reader (`ledger::verified` returns `Result<bool, AgentError>`), and `run`'s gate then records `cli_verified:false` with one `parse-rejected{parser:"ledger-stamps"}` line. `run`'s gate reads the file through `viola_state::stamps::read_stamps_strict`: a strict-modes refusal is the same outcome, its detail `strict-modes-failed`.

**Instance snapshot** (`instances/<ViolaName>/snapshot.json`, written only by that instance's wrapper, rewritten on every change to a field below): `data` is `{endpoint?, pid, started_at, pinned_bin, statusline_command?, cli_version?, cli_verified, wheel, budget_paused, budget_override_until?, pending_dialog?, links, child_pid?, agent_session_id?}`. `started_at` is the wrapper's own OS start time (sysinfo, whole seconds) rendered RFC 3339, so a reader can compare it with the same field of the recorded `pid`. `endpoint` is present from the first snapshot, because the bind precedes it; only a replay rebuild lacks it. The first snapshot is written before the spawn without `child_pid`; the rewrite straight after the spawn adds it.
- `pid` and `started_at` identify the wrapper process for the liveness check.
- `child_pid` is the pid of the spawned agent child, and `agent_session_id` is the one from the newest `session-start` event. Both exist only to join `claude agents --json` rows to this instance (see Session liveness).
- `cli_version` and `cli_verified` come from `run`'s version gate.
- `pending_dialog` is `{dialog_id, kind}` while a `hook.dialog` is open. It is removed when the dialog is answered, expires or is answered `null` on a wheel move. It is the only source of `dialog_pending` in `list` and `/api/sessions`. It is not rebuilt from the log, so a reader that falls back to replay reports `dialog_pending: false`.
- `links` is the set derived by replaying `link`/`unlink` events, as `{driver, driven, since}`.

**Wrapper channel frames** (JSON-RPC 2.0, one per line)
```json
{"jsonrpc":"2.0","id":7,"method":"send","params":{"v":1,"sender":"0.1.0","text":"line one\nline two"}}
{"jsonrpc":"2.0","id":7,"result":{"ok":{"submitted_at":"2026-09-23T19:43:59.004Z","cursor":48213}}}
{"jsonrpc":"2.0","id":8,"result":{"ok":{"confirmed":false,"detail":"unconfirmable","cursor":48213}}}
{"jsonrpc":"2.0","id":7,"result":{"refusal":"not-delivered","detail":"input-not-ready"}}
{"jsonrpc":"2.0","id":7,"error":{"code":-32602,"message":"unsupported protocol version","data":{"supported":1,"wrapper":"0.1.0"}}}
{"jsonrpc":"2.0","method":"hook.event","params":{"v":1,"sender":"0.1.0","ts":"2026-09-23T19:43:58.123Z","event":{"kind":"turn-ended","data":{"last_assistant_message":null}}}}
```

A frame is one line of at most `MAX_FRAME` bytes, its `\n` counted; a longer line is answered `-32600` and the connection is closed. Only `hook.event` may be id-less: any other frame without an `id` is not dispatched and is logged `parse-rejected{parser:"channel-frame", detail:"malformed"}`. A client may add `conn` (obs-plan D-10) to `params`; the server logs it and strips it before dispatch, so no method takes it as input and it is never identity.

**Channel methods: `params` → `ok` payload.** Every `params` also carries `v` and `sender`. `from` is the caller's `VIOLA_NAME` when set, and is omitted otherwise. The frame envelope does not type `from`: each method that reads it (`send`, `wait`, `last`, `answer`, `pause`) takes it absent, `null` or a valid `ViolaName` and answers anything else `-32602` `invalid params` with `data: null`, never `-32600`; `release` refuses any string `from` (below).
- `send` `{text, from?}` → `{submitted_at, cursor}` when confirmed, or `{confirmed:false, detail:"unconfirmable", cursor}`. `cursor` is the end offset of `events.ndjson` when the send was accepted, before the paste.
- `wait` `{after?, timeout_ms?, from?}` → `{event:<ndjson event line>, cursor}`, where `cursor` is the end offset of that event's line, or `{timed_out:true}`. `after` and `timeout_ms` are each absent or a non-negative integer that fits `u64` (`null`, a negative, a fraction or a string is `-32602`, `data: null`); unknown fields are ignored. The start offset is `after`, else `events.ndjson`'s end read at the call; a line counts only when it STARTS at or after it. A pending dialog comes first: an `after`-less `wait`, or one whose `after` is at or before the pending dialog's line, returns that dialog at once. Only `turn-ended` · `question` · `permission` · `plan` · `session-end` wake (`viola_core::EventKind::WAIT_WAKE`); the deadline is `now + timeout_ms` through `Instant::checked_add` (an unrepresentable instant is no deadline). The wake (`src/run/wait.rs` `WaitFeed`): one `Mutex` (a generation counter + the newest turn) and one `Condvar`; `WaitFeed::appending` runs each hook line's append inside the lock, then bumps the generation, keeps a `turn-ended` as the newest turn and wakes the parked calls. Only hook lines signal (the wrapper's own `send-*` and start records never wake). A parked `wait` reads the generation before each scan, re-scans only when it moves, and its 20 ms `wait_timeout` re-reads the injected clock against the deadline, never the file; it holds its connection's worker thread until a wake, its deadline or the wrapper's exit.
- `last` `{from?}` → `{last_assistant_message:<string|null>, ts:<string|null>}`: both `null` before any turn; a `turn-ended` whose message is not a string gives `null` plus its `ts`. The value is the `WaitFeed`'s newest turn, updated under the same lock hold as the append, so a caller who has seen a `turn-ended` line on disk always reads that turn; it is rebuilt once from the whole `events.ndjson` (`WaitFeed::rebuild`) before `server.serve` at `run` start.
- `answer` `{dialog_id, from?, response}` → `{}`. `response` is normalised per dialog kind:
  - `question`: `{answers:{<question>:<text>}, annotations?}`
  - `permission`: `{behavior:"allow"|"deny", message?}` — no suggestion slot: an offered `permission_suggestions` entry cannot be picked, a deliberate v1 limit (the founder's live ruling, 2026-10-04)
  - `plan`: `{behavior:"approve"|"revise", message?}`
- `pause` `{from?}` → `{wheel:"human"}` (the wheel `human` / `manual-pause`).
- `release` `{budget?:bool, from?}` → `{wheel:<holder>, budget_paused:bool}`. A string `from` is refused `-32602` `"invalid params"` with `data: {"reason":"release-from-driver"}` (`viola_channel::ProtocolError::ReleaseFromDriver`) plus one `release-from-driver` obs line; a `from` of another type, or a `budget` that is not a bool (`null` included), is `-32602` with `data: null`. `budget:true` leaves the wheel where it is; a `release` on a driver-held wheel changes nothing.
- `pause` and `release` are answered only after the move's `wheel` record has landed (`-32603` if it did not).
- `link` and `unlink` `{driver, driven}`, sent to the driven instance's wrapper → `{}`.
- `hook.event`, sent id-less by `hook` (a notification, no reply): `{ts, event:{kind, data}}`. The wrapper re-validates the event (`kind` is one of the five hook kinds `session-start` · `prompt-submitted` · `turn-ended` · `session-end` · `activity`; `data` is an object; for `prompt-submitted`, `text` is a string and `origin` is `harness` · `human`) and appends `{v, ts:<append time>, instance, kind, source:"hook", data}` to `events.ndjson`. An invalid event is not appended, and an append failure is `-32603`. A `prompt-submitted` whose `text` exactly equals the in-flight `send`'s typed text (the sent text with every CR LF pair and every other CR as one LF, and without its trailing CR and LF characters; any `origin` the hook filed) is appended with `origin:"driver"` instead, and only then settles that send ([Delivery Confirmation]). The one in-flight send no `prompt-submitted` claims is a listed local command waiting for its post-condition: a `session-start` whose `cause` is `clear` and whose `agent_session_id` is a string differing from the remembered one is appended unchanged and only then settles it.
- `hook.dialog`, sent by `hook` (served since chunk 2026-10-04-dialog-answers-by-dialog-id): `{kind:"question"|"permission"|"plan", data, hook_event, tool?, input?, continuation?}` → `{dialog_id, response:<object|null>}`. `null` means no decision, so the hook prints nothing. On an unverified CLI the wrapper replies `null` at once. A PermissionRequest that repeats the armed PreToolUse dialog's tool with an equal `tool_input` (question and plan, matched per tool) is that dialog's continuation: it appends no event, takes no new `dialog_id`, and is answered only from an armed `plan` revise (otherwise `null`).
- `list` is not a channel method. The calling process reads `instances/*/` (heartbeat and snapshot) and `claude agents --json` itself, so `list` needs no live wrapper. Its `ok` payload (CLI `--json` and MCP `list`) is `{items, budget, skipped}`, with the same item, `budget` and `skipped` shapes as `/api/sessions`.

**Event `data` per kind** (normalised in `viola-agent-claude`; upstream text is content, never commands, per R1):
- `session-start`: `{cause, agent_session_id}` (see the Hook → kind map).
- `prompt-submitted`: `{text, origin}`. `text` is the submitted prompt as it was typed: `viola-agent-claude` removes any `<pasted_content id=…>` long-paste wrapper together with the frame the CLI writes around it (two newlines before the open tag, one after the close tag, and a second after it when text follows that is not the next pair's own frame) and then reverses tag escaping before emitting the event, so for a wrapped paste `text` is the pasted text, and delivery matching compares it directly with the in-flight send's typed text, the sent text with every CR LF pair and every other CR as one LF and without its trailing CR and LF characters ([Delivery Confirmation]). For a `send` whose text ended in CR or LF characters, or held a CR or a CR LF inside, `text` is the text as typed, not as sent. The CLI drops a pasted text's last newline before the hook, wrapped or not (as measured on 2.1.287, chunk 2026-10-07-live-rows-and-paste-shapes-on-the-dev-host, `evidence/scratch-session.md`), so `text` for a pasted text that ended in a newline is one byte short of it. No `send` relies on this: `send` never types a text that ends in a newline. `origin` is `driver` · `human` · `harness`: the hook files only `human` · `harness`, and `driver` is set only by the wrapper's relabel of the in-flight send's own prompt.
- `turn-ended`: `{last_assistant_message}` (string or `null`). This is the source `last` rebuilds from.
- `question`: `{dialog_id, questions:[{question, options:[<label>], multi_select}]}`. Each `question` string is a key in `answer`'s `answers`.
- `permission`: `{dialog_id, tool, input}`. `input` is the tool call's arguments as a JSON value, carried as content, not the hook payload.
- `plan`: `{dialog_id, plan}`, with the plan as text.
- `session-end`: `{}`.
- `activity`: `{}`, plus `tool` when the hook names one.
- `link` / `unlink`: `{driver, driven}`.
- `wheel`: `{holder, cause}`, with `holder` `human` · `driver` and `cause` `start` · `human-input` · `manual-pause` · `release`.
- `budget-gate`: `{paused, window?, override_until?}` for the instance's own gate, with `window` `five-hour` · `seven-day`.
- `send-issued`: `{cursor, from?}`, where `cursor` is the offset this line starts at: the send's cursor.
- `send-confirmed`: `{cursor, confirmed?}`. A confirmed send writes `{cursor}`. An unconfirmable send writes `{cursor, confirmed:false}`, the one record of that outcome (it writes no `send-refused`). The field is additive: no `v` bump, and no product code reads the record.
- `send-refused`: `{refusal, detail, cursor?}`; `cursor` is absent for a refusal before `send-issued`.

The wrapper appends `wheel` and `budget-gate` (`source: wrapper`) once at start and on every change, and `send-issued` / `send-confirmed` / `send-refused` (`source: wrapper`) for each send. They are log-only and never wake `wait`. They are how the audit trail, the SSE feed and a replay learn the wheel holder, the budget gate and each send's outcome.

`hook.dialog`'s `data` is the same object as its dialog event's `data`, without `dialog_id`. Dialog hooks send only `hook.dialog`, never a `hook.event` for the same dialog. On receipt, the wrapper assigns the `dialog_id` and appends the dialog event (`source: hook`) before it can wake `wait` or reply. It does this even when it replies `null` at once (wheel `human`, unverified CLI, another dialog already pending, or a `question` first raised by PermissionRequest with no matching armed dialog — its body has no ledger row, so a late `answer` is refused `unknown-dialog`), so every dialog appears exactly once in the log; a matched continuation (above) appends nothing, being the same dialog.

**CLI `--json` output** mirrors the channel `result`: `{"v":1,"ok":{…}}` or `{"v":1,"refusal":"human-typing","detail":null}`, with the matching exit code. Outcomes that have no channel `result` use `error`:
- `{"v":1,"error":"instance-unreachable","detail":null}` (exit 21)
- `{"v":1,"error":"wrapper-fault","detail":{"code":<int>,"message":"…","data":<object|null>}}` (exit 20)

**MCP refusal result**
```json
{"content":[{"type":"text","text":"refused: budget-paused"}],"isError":true,
 "structuredContent":{"refusal":"budget-paused","detail":"five-hour"}}
```

**Hook contract** (produced only by `viola-agent-claude`)
- A decision is exit 0 with a `hookSpecificOutput` body. PreToolUse returns `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","updatedInput":{…}}}`. PermissionRequest returns `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow|deny","message":"…"}}}`.
- No decision is exit 0 with an empty stdout. Async-tier hooks always print nothing.
- `viola hook statusline` is exempt from both rules, because it is the statusline wrapper, not a Claude Code hook. It records the `rate_limits` reading to `budget.json` and runs the user's own statusline command with the same stdin. `run` resolves that command from the user's effective Claude Code settings at start (in `viola-agent-claude`) and records it in the instance snapshot. `hook statusline` reads it from there through `VIOLA_DIR`. The command is a user-written shell string, so it runs through the same shell Claude Code would use for it (a ledger row). This is the only shell-out in viola. It prints that command's stdout unchanged (empty if the command fails) and exits 0.

**Session liveness**
- The wrapper touches `<instance dir>/heartbeat` every 1 s. When the snapshot's pid + start time no longer name a running process (the pid is dead, or alive with another start time) the session is `gone`, whatever the beat's age. Otherwise a beat at most 5 s old is `live`, and an older or absent beat is `stale`.
- `claude agents --json` adds `status` (idle/busy) and lists unwrapped sessions as read-only rows. Its readers (`list`, `mcp` and `ui`, through `viola-agent-claude`) spawn it directly, resolving `claude` from their own PATH with the same npm-shim → `claude.exe` resolution `run` uses. If it is not found, fails or cannot be parsed, every row's `status` is `unknown`, no unwrapped rows are listed, and the outcome is never an error. A row that matches a wrapped instance's `child_pid` or `agent_session_id` in its snapshot is merged into that instance's row, never listed separately. Which of the two fields `claude agents --json` exposes for this join is a capability-ledger row (open item).

**Communication protocols**
- SSE for the GUI.
- JSON-RPC 2.0 over ndjson on local sockets for the wrapper channel.
- JSON-RPC 2.0 over stdio for MCP.
- No WebSocket and no polling endpoints in v1.

## Occupied Resources

**Network**
- **TCP `127.0.0.1:47319`:** the `viola ui` HTTP server (built-in default, overridable in `config.json` or with `viola ui --port <n>`). It never binds `0.0.0.0` or `::`. The Host allowlist is `127.0.0.1:<port>` and `localhost:<port>`.
- **No database port, no broker port, no other listening TCP port.** The MCP server is stdio only.

**HTTP routes (all GET)**
- `/`: the view page
- `/assets/*`: the page's static files, embedded in the binary
- `/health`, `/ready`, `/api/info`, `/api/sessions`, `/api/links`
- `/api/events`: SSE
- Reserved for the v1.x brake (not served in v1): `POST /api/sessions/{name}/pause` and `POST /api/sessions/{name}/unlink`.

**IPC endpoints**
- **Windows:** named pipe `\\.\pipe\viola-<h12>`, one per `viola run`.
- **Test-only:** named pipe `\\.\pipe\viola-test-sqos-<pid>-<label>` (Windows), created by `tests/channel_sqos_open.rs`, and endpoints named `viola-test-chan-<pid>-<label>` (a named pipe on Windows, a socket of that base name elsewhere), created by the channel tests (`tests/channel_endpoint.rs`, `tests/security_negatives_channel.rs`, the `viola-channel` crate tests and the `viola-e2e` cleanup tests). Both are outside the `viola-<h12>` namespace (the `test-` segment is never 12 lowercase hex characters), unique per test and never bound by `viola`.
- **Linux / macOS:** Unix domain socket file `<socket dir>/viola-<h12>.sock` in a per-user 0700 directory (security-plan arch amendment 2): `$XDG_RUNTIME_DIR/viola/` on Linux, `$TMPDIR/viola/` on macOS, and `/tmp/viola-<uid>/` only as a fallback; never the `/tmp` or `$TMPDIR` root. The socket is chmod 0600 after the bind. The start arbiter is the sibling `<socket dir>/viola-<h12>.lock`: `run` holds an exclusive lock on it, and a held lock is the taken-name refusal. `run` resolves the path once and records it as `endpoint` in the instance snapshot. Every other process (`hook`, `mcp`, CLI verbs, and `run`'s collision check) connects to the recorded `endpoint`, because processes spawned inside the session may run with a different environment from the wrapper. It rebuilds the path by the same rule only when the snapshot is missing or unreadable. Linux abstract-namespace names are never used, because they carry no filesystem permissions and any local user could connect (see Local endpoint trust boundary).

## Cross-cutting Patterns

- **Config management.** Precedence: CLI flags override `<viola home>/config.json`, which overrides built-in defaults.
  - Viola home: a global `--home <dir>` flag on every subcommand overrides the default `<user home>/.viola/`. Resolution order: `--home`, then the grandparent of `VIOLA_DIR` when it is set, then the default. As landed (read from the code at chunk 2026-10-08-first-live-test-and-self-drive: `resolve_home` in `src/cmd/mod.rs`, `src/cmd/hook.rs`): the CLI verbs take `--home`, else the default, and only `hook` takes the `VIOLA_DIR` step, so a CLI verb run inside a session without `--home` resolves the default home; the `VIOLA_DIR` step for the CLI verbs is owed to the working-route entry "CLI machine contract". `viola run --home <dir>` passes the home to the child only through `VIOLA_DIR`, so the pinned copy, plugin folder, endpoint hash, logs, `budget.json` and ledger stamps all follow it. This is the isolation point for tests: each test runs in its own home, and that home's `ledger/stamps.json` can stamp the fake agent's reported version.
  - `config.json` is parsed tolerantly (unknown keys skipped and counted) and carries `v`.
  - Settings: budget thresholds as `Percent` (defaults `five_hour` 90, `seven_day` 85), the GUI port (default 47319), `diagnostics_level` (`info` by default, or `debug`) and `claude_env_keep` (the Unix R8 pass-list of `CLAUDE*` names, default empty). `diagnostics_level` is the only source of the process-log level; `RUST_LOG` has no effect.
  - There are no secrets in v1, and environment variables are not a configuration channel. The `VIOLA_*` variables are wrapper-to-child plumbing set by `viola run` only. The only other variables any `viola` build reads are the two test seams `FAKE_AGENT_PUMP_DELAY_MS` (capped at 5 s) and `FAKE_AGENT_HOOK_PANIC` (exact value `1`, a forced fail-open `hook` panic), both compiled only under `cfg(feature = "fake-agent")` and absent from release builds: they configure nothing, disable no control and widen no redaction. This holds because clap is built without its `color` feature: that feature's anstream → anstyle-query route read `CLICOLOR`, `CLICOLOR_FORCE`, `NO_COLOR`, `TERM`, `COLORTERM` and `CI` and was closed at chunk 2026-09-28-cli-output-tokens (as measured at its research F1: `CLICOLOR_FORCE=1 viola --help` into a pipe gave 25 ESC bytes before, 0 after); a dependency or feature that reads an environment variable breaks this rule like a direct read does.
- **Development Style signal:** agent-driven.
- **Identity by instance, never by location.** Every hook, MCP call and CLI verb finds its instance through `VIOLA_NAME` (or an explicit `ViolaName` argument), never through the working directory. Two sessions in one folder never share records.
- **Fail open toward the human.** Any internal failure in `hook` produces exit 0 with no body, so the dialog renders for the human. Any failure to confirm delivery is reported as `not-delivered`, never retried blindly. The one exception is a local command on the ledger whose post-condition is "none" or not yet measured on this CLI version. It is reported as `ok` with `confirmed: false` and detail `unconfirmable`.
- **Mixed-version tolerance.** Every channel `params`, event, snapshot and config carries `v`, and channel `params` also carry the sender's `CARGO_PKG_VERSION`. Readers skip unknown kinds and fields and surface the counts. A newer request than the wrapper supports gets a `-32602` naming the wrapper's version.
- **Capability ledger as the single gate for CLI-specific behaviour.** Any new dependence on an undocumented `claude` behaviour is added as a ledger row in `viola-agent-claude`, with a `viola verify` probe that has a post-condition check. It is never hard-coded as an unconditional assumption. One ruled limit (the founder, live, 2026-10-07T11:37Z, relayed by the overseer): a CLI shape no `send` relies on needs no probe, which today covers the long-paste frame beside typed text and between two pairs ([CLI Version Compatibility], the long-paste wrapper). One shape `send` does rely on has no row yet and is not under that limit: an LF typed inside a bracketed paste is submitted unchanged (as measured on 2.1.287 on the Linux dev host at chunk 2026-10-09-inner-cr-and-crlf-in-a-sent-text, `evidence/live-run.md`, `rule-inner-lf`); its row is owed to `v1-34` on the working-route entry "Paste newline ledger row" ([Delivery Confirmation]). The dialog answer mapping (the S3/S7/S8 decision bodies) is gated by its own rows (`question-answer` · `plan-approve-revise` · `question-notes` · `dialog-concurrency`) inside the seventeen-row `cli_verified` ([CLI Version Compatibility]).
- **Tokio containment.** New code on the `run`, `hook`, `send` or channel-server paths uses std threads and blocking I/O. Only `viola-mcp` and `viola-ui` may build a runtime. CLI `wait` is a blocking read on `viola-channel`'s sync client.
- **Crash-safe disk writes.** Append-only logs use one `write` per line. Mutable files are replaced atomically. Every guarded file has its own `.lock` sibling. Readers always tolerate a torn last line.
- **Diagnostic output channels.** `hook` writes only its decision body to stdout and nothing to stderr (Hook Contract). While the child runs, `run` writes nothing to the terminal except the child's own output, because the terminal carries the child's screen. Every role's codes-only process log goes to its home-level role file under `diagnostics/`: `run-<name>`, `hook-<name>`, `mcp`, `ui-<port>` or `cli-<name>` `.ndjson`. Content-bearing detail belongs only in the instance's `diagnostics/detail-<role>.ndjson`. `mcp` writes only MCP frames to stdout, and its log goes to `diagnostics/mcp.ndjson`; it writes JSON to stderr only when that file cannot be opened. `ui` and short-lived CLI verbs may use stderr for their human output. The logger and the format are owned by obs.
- **Cross-platform discipline.**
  - Every path written into plugin files uses forward slashes.
  - Nothing shells out through `sh`, `bash` or `cmd`, except `hook statusline` running the user's own statusline command (see Hook contract).
  - Child processes are spawned directly.
  - Endpoint names are hashed and short.
  - Every OS-specific branch compiles and is tested on its CI runner.
- **Untrusted upstream text.** A driven session's `Stop` text and dialog payloads are content, never commands to viola. viola forwards them as escaped strings and never interprets them (R1).
- **Local endpoint trust boundary.** Any process that can open an instance's endpoint can `send` prompts and `answer` dialogs, including PermissionRequest. v1 trusts every process of the same OS user and no other. Each endpoint, whether a named pipe or a Unix socket file, must not be connectable by another OS user, and the GUI stays read-only. The security specialist owns how this is enforced per OS and any per-connection proof beyond it.

## Project Intent

- **Product type.** Hybrid local developer tool made of three parts:
  - a native cross-platform CLI binary;
  - a Claude Code plugin (hooks + stdio MCP server) that calls that binary;
  - a minimal view-only local web GUI served by the same binary.
- **Core function.** Lets one interactive Claude Code session drive another on the user's own subscription. It wraps the unmodified `claude` CLI in a PTY, types at turn boundaries, answers dialogs through hooks, and holds a one-driver wheel the human can take at any moment.
- **Growth model.** Modular monolith: one binary with compiler-enforced internal crates (`pty · channel · state · agent-claude · mcp · ui` around `core`), and no daemon.
- **How new functionality is added.**
  - New capabilities arrive as new subcommands or channel verbs, exposed consistently on the CLI (`--json`) and, where a driver needs them, as MCP tools.
  - New Claude behaviours arrive as capability-ledger rows in `viola-agent-claude`.
  - New GUI views arrive as GET routes.
  - State-changing GUI routes wait for the v1.x brake and its auth.
  - A second driven agent (for example Codex) arrives as a sibling `viola-agent-<name>` crate, at which point the adapter trait is extracted into `viola-core`.
- **Template patterns.** None. This is a single-product repository, not a fleet.
- **Scale path.**
  - v1 is personal (first live on the Linux dev host, by the founder's ruling R-L1; Windows, macOS and Linux CI-tested against the fake agent; Windows live awaits an interactive Windows host).
  - v1.x adds the GUI brake and then public distribution (dist 0.33.0 releases, signing, winget/Homebrew/Scoop, a marketplace entry, self_update 1.3.0).
  - A phone or remote view comes later, behind authentication.
