## 1. Obs Scope Summary

_[ALL tiers — VERBATIM copy from obs-scope.md]_

**Obs tier:** `Standard (1)`, with Minimal-tier exporter carve-outs.

_Justification (verbatim from obs-scope Section 6):_

The structure is Standard-class:
- 6 telemetry surface entries across 4 process roles (`run` / `hook` / `mcp` / `ui`) and 3 product parts;
- 7 instrumentable crates plus the embedded frontend;
- 7 must-trace paths plus 5 edge flows;
- 19 telemetry triggers, including cross-surface propagation through `corr`, perf budgets, chaos fault telemetry, multi-OS compat, and binding Founder Directions.

The tests tier is Comprehensive (2), and obs sits one step below it, within the ±1 band. The security tier is Minimal (the passed variable, and "no compliance triggers"), so there is no Comprehensive driver: no audit-log compliance trail and no PII-scrubbing regime beyond the NEVER-log floor.

The Standard defaults for exporters and error reporting are replaced by Minimal-tier shapes:
- No network OTLP loopback exporter and no opt-in error reporter. Upstream bans outbound network calls, bans new listeners without a Security Decisions Log entry, reserves stdout on 3 of 4 roles, and bans Tokio and C crates in the sync graph.
- No per-module log levels from the environment, because env vars are not a configuration channel.

The pipeline is the tests-bound one: `tracing` plus tracing-subscriber 0.3.23 JSON-per-line files under `diagnostics/`, correlated by `corr`, and consumed through `agent-run logs` / `status`.

Four items need Decisions Log entries or Phase 5 reconciliation:
- the `diagnostics/` directory root (tests `<home>/diagnostics/` vs arch and security `instances/<name>/diagnostics/`);
- `mcp` logging to stderr when `VIOLA_DIR` is unset;
- the `event` enum extensions (`release-from-driver`, chaos and liveness signals, the SSE lifecycle);
- `hook-invoked` `corr` timing relative to `dialog_id` assignment.

**Observability harness specification:**

- **OTel SDK init:** v1 initialises no OTel SDK exporter. The `tracing` facade plus the tracing-subscriber JSON formatter is the binding pipeline (tests excerpt, Log format; Founder Direction 1: "tests owns them"). The constraints ruling out an exporter:
  - no outbound network calls (security Error reporting);
  - a new listener, including a local OTLP receiver or metrics endpoint, needs a Security Decisions Log entry (security Anti-Patterns);
  - stdout is reserved on `hook`, `mcp` and `run` (arch Obs-Relevant Conventions);
  - `cargo deny` bans Tokio in the sync crates' graph and bans C-building crates (arch Observability Hints, Build policy).

  An OTel bridge layer is optional. It may only feed an in-process or file sink, and it must stay Tokio-free on the sync crates. Phase 2 evaluates whether it adds anything over the tests-fixed format.

  Init order per process:
  1. As the first statement in `main`, install a replacement panic hook that writes one JSON line and nothing to stderr. The default hook's stderr output breaks the hook contract and the `run` terminal.
  2. Parse clap.
  3. Resolve the home (`--home`, then the grandparent of `VIOLA_DIR`, then the default) and the instance (`VIOLA_NAME` or an argument).
  4. Open `diagnostics/<process file>` in append mode with 0600 permissions inside a 0700 directory.
  5. Install the subscriber with an explicit writer (never stdout).
  6. Emit `process-start`.

  For `run`, this completes before the start sequence, so the collision check and version gate are logged. For `ui`, it completes before the axum bind. For `mcp`, it completes before the rmcp stdio transport starts.
- **Service identity:** `service.name` is hardcoded `"viola"`. `service.version` is compile-time `env!("CARGO_PKG_VERSION")`. `deployment.environment` is N/A (local-only). Per line, role and instance are carried by the tests-required fields `process` (`run|hook|mcp|ui`) and `instance` (`ViolaName` or null), matching `sender` / `writer` / `/api/info` (arch Obs-Relevant Conventions, Service identity).
- **Logging stack:** `tracing` with tracing-subscriber 0.3.23, configured as `fmt().json().flatten_event(true).with_current_span(false)` (tests excerpt, verbatim). Version 0.3.23 satisfies the security Vector 9 floor of `>=0.3.20` (RUSTSEC-2025-0055). Sink rules:
  - one file per process role under `diagnostics/`;
  - no stdout sink on any role;
  - stderr only for `mcp` without `VIOLA_DIR`, and optionally for `ui`.

  The writer must emit each formatted line as a single `write` on an append-mode handle (arch Crash-safe disk writes). Concurrent `hook` processes share one file.

  The level filter is not read from `RUST_LOG`. Arch says "environment variables are not a configuration channel", and security Anti-Patterns ban env, flag or config values that disable any control. Any verbosity control therefore comes from `--home/config.json` or a CLI flag and must never bypass redaction. There is no separate agent-mode flag: JSON-to-file is the only mode.

  Timestamps must be RFC 3339 UTC with milliseconds and `Z` (tests excerpt, `timestamp`; arch Timestamps). Phase 2 must verify whether the tracing-subscriber default timer meets millisecond precision, or whether a chrono-based `FormatTime` (`to_rfc3339_opts(SecondsFormat::Millis, true)`) is needed.
- **Log format JSON schema:** (verbatim from tests excerpt, Section 3; binding. Obs may add fields and must not rename or remove any.)

```markdown
- **Format:** JSON-per-line. There are two streams:
  - **Event stream:** product events in `instances/<name>/events.ndjson`, exactly the arch Event line `{"v":1,"ts","instance","kind","source":"hook|wrapper|cli","data"}`.
  - **Process logs:** emitted by tracing-subscriber 0.3.23 `fmt().json().flatten_event(true).with_current_span(false)`, writing to `<home>/diagnostics/{run-<name>,hook-<name>,mcp,ui-<port>}.ndjson`. Files are 0600, dirs 0700, with one `write` per line.
- **Required fields:**
  - For process logs: `timestamp` (RFC 3339 UTC with ms and `Z`), `level` (`DEBUG|INFO|WARN|ERROR`), `target`, and `fields.message` (or the flattened `message`).
  - `event`, a closed kebab-case enum. A new value needs a Decisions Log entry, like the §3 closed enums. Each value fixes what its `corr` holds:
    - `channel-request`, `channel-response`: `corr` = the JSON-RPC request `id`
    - `dialog-raised`, `dialog-answered`: `corr` = `dialog_id`
    - `hook-invoked`, `hook-decision`: `corr` = `dialog_id` for dialog hooks, otherwise null
    - `send-issued`, `send-confirmed`, `send-refused`: `corr` = the send `cursor`
    - `process-start`, `process-exit`, `http-request`, `panic`: `corr` = null
  - `process` (`run|hook|mcp|ui`) and `instance` (a `ViolaName` or null).
  - `corr` is copied unchanged as a JSON number or string. It is never renamed (for example to `correlation_id`).

  obs-plan may add fields but must not rename or remove these. The harness greps on them.
- **Constraints:**
  - The hook trace is the `hook-<name>.ndjson` file. A failed write there is swallowed, so the hook still exits 0 and never writes to stderr.
  - No line may contain the GUI token, a `Cookie` header, `?t=`, or any stripped `CLAUDE*` value. This is enforced by the secret-scan test in §6.
- **Agent parsing:** lines parseable with `jq -c 'select(.event=="dialog-raised")'` or equivalent; NEVER multi-line stack traces. A panic in a hook is caught and logged as one `level:"ERROR", event:"panic"` line.
```

  Alignment gaps for Phase 3. Each needs additive fields or an enum extension through a Decisions Log entry; nothing is renamed.
  - (a) Founder Direction 4 says `release-from-driver` "must log as its own event". It is not in the closed `event` enum, so it needs a Decisions Log entry. The distinct detail codes for exit 21 and exit 1 can be an additive `detail` field.
  - (b) These signals have no `event` value today: heartbeat live→stale transitions, torn-line healing, snapshot replay recovery, the SSE stream open/close lifecycle, readiness-gate `input-not-ready`, and skipped-record counters (tests excerpt, Coverage Triggers: Crash-safe state, Parser surfaces, Child spawn). Phase 3 chooses between an additive field (for example `detail` on `process-*` / `http-request`) and an enum extension.
  - (c) `hook-invoked` is emitted before the wrapper assigns `dialog_id`, so `corr` can only be filled from `hook-decision` onward, or `hook-invoked` must be logged after the `hook.dialog` response.
- **Log file location:** Tests require `<home>/diagnostics/{run-<name>,hook-<name>,mcp,ui-<port>}.ndjson`. That differs from two upstream statements:
  - arch Obs-Relevant Conventions (Diagnostics location): `<viola home>/instances/<ViolaName>/diagnostics/`;
  - security Vector 2 and Data Classifications: only `instances/<name>/diagnostics/` may hold user content.

**Agent-readable invariants (apply across all signals):**
- Every signal produces machine-parseable output: JSON-per-line process logs (`diagnostics/*.ndjson`), the ndjson product event stream, and the JSON harness documents (`agent-run logs` / `status`). Perf gates produce hyperfine `--export-json` output and CI produces nextest JUnit XML.
- No human-only dashboards. No Grafana / Kibana / Datadog UI exists in the stack, and none may be added as a consumption surface.
- No proprietary APM SDK, as primary or at all. The v1 exporter role is filled by the local file sink (Section 3).
- No human-review-gated log analysis. Every verdict is a `jq` / harness assertion that sets an exit code.
- Every panic after init step 4 produces exactly one single-line structured record in its home-level role file: location, thread, role and instance. The bounded exemptions (the pre-init window, `cli` without an instance, `hook` without `VIOLA_NAME`, a failed step-4 role-file open) are listed in Section 10. The payload (one escaped JSON string) and the backtrace (a one-line JSON array of frames) are written only to the instance-scoped detail file (Section 7).
- Every cross-surface call carries correlation through the tests `corr` field plus the additive `conn` discriminator (Section 3, Trace context propagation). W3C `traceparent` is not used in v1: no consumer exists and channel `params` declare no trace-context field.

**Naming conventions** (upstream-context Obs-Relevant Conventions + obs-scope Section 4):
- **Span naming:** `<area>.<operation>` in snake_case. `<area>` is one of `run`, `pty`, `channel`, `state`, `hook`, `statusline`, `send`, `wait`, `last`, `answer`, `cli`, `mcp`, `ui`. `cli.<verb>` names the dispatch span of a short-lived verb that has no dedicated client span (for example `cli.list`, `cli.verify`, `cli.plugin_install`). Examples: `run.version_gate`, `pty.paste_write`, `ui.sse_stream`, `last.client`. Span names are code-internal, not wire contract.
- **Event naming:** the `event` field is a closed kebab-case enum (the tests list plus the Section 12 extensions). It is compiled in viola-core as `ObsEvent` with a kebab-case `Display`.
- **Metric naming:** derived metrics (jq-computed, never instruments) are named `viola.<area>.<measure>`, for example `viola.hook.duration_ms` (Section 5).
- **Log fields:** snake_case field names. Enum values are kebab-case (arch JSON / enum naming). Instants are `*_at` in RFC 3339 UTC with milliseconds and `Z`. Durations are `duration_ms` as an integer.
- **Resource attributes:** `service.name` = `"viola"` (a viola-core constant, the arch-fixed binary name). `service.version` = `viola_core::VERSION` = `env!("CARGO_PKG_VERSION")`. `deployment.environment` is N/A (local-only). Both are emitted once per process on `process-start` as `service_name` / `version`.

## 3. Observability Harness Contract

_[ALL tiers — central agent-driven mechanism; Section consumed by
setup-project to materialize OTel SDK init + log sinks + service
identity + snapshot generation]_

The architecture commits to the harness pattern (arch §Cross-cutting Patterns → Diagnostic output channels):
- `hook` writes only its decision body to stdout and nothing to stderr.
- `run` writes nothing to the terminal except the child's own output.
- Every role's codes-only process log goes to its home-level role file under `diagnostics/`, and content-bearing detail goes only to the instance's `diagnostics/detail-<role>.ndjson`.
- `mcp` writes only MCP frames to stdout.
- `ui` and short-lived CLI verbs may use stderr for their human output.
- The logger and the format are owned by obs.

This section specifies the concrete contract.

### Product mode — Normal vs Inverted (self-observing)

**Normal.** The self-observing-inversion trigger did not fire (obs-scope §5; Founder Direction 3: "Normal mode, not inverted: viola is not a telemetry product."). `events.ndjson` is a product audit log, not a collector. The Normal contract below applies, with the Minimal-tier exporter carve-outs from obs-scope §6.

### OTel SDK init

- **SDK packages:** **No OTel SDK in v1.** The OTel API role is filled by **tracing 0.1.44** (the facade in every instrumentable crate) and **tracing-subscriber 0.3.23** (the formatter and sink).
  - Researched and deferred to the root-bin edge only: `opentelemetry` / `opentelemetry_sdk` 0.33.0 and the `tracing-opentelemetry` 0.34.0 bridge. With no exporter they would add only dependency and cargo-mutants surface, and bridged span IDs would have no consumer.
  - If either is ever adopted, the Resource must be built with `Resource::builder_empty()`, never `Resource::builder()`: the latter's `EnvResourceDetector` reads `OTEL_*` env vars.
  - Cargo entry for every instrumentable crate: `tracing = "0.1.44"`.
  - Cargo entry for the root bin only: `tracing-subscriber = { version = "0.3.23", default-features = false, features = ["fmt", "json", "registry", "std"] }`. `ansi` and `tracing-log` are off (D-11). The `chrono` feature is off too: it only enables `ChronoUtc` / `ChronoLocal`, and `MillisUtc` uses the root bin's direct `chrono` dependency (D-26).
- **Init order** (one `viola_obs_init(role)` in the root bin, run in obs-scope §3 order):
  1. The **first statement in `main`** is `std::panic::set_hook(viola_panic_hook)`. The hook writes to a `OnceLock<Arc<File>>` that is empty until step 4, so it never falls back to stderr.
  2. clap parse.
  3. Resolve the home (`--home` → grandparent of `VIOLA_DIR` → `~/.viola/`), the instance and the role (`run` / `hook` / `mcp` / `ui` / `cli`). The instance source is fixed per role:
     - `run`: its own `ViolaName` argument. An inherited `VIOLA_NAME` (a `viola run` started from inside a wrapped session) never overrides it, so a wrapper never writes into another instance's `run-<name>.ndjson`;
     - `hook` and `mcp`: `VIOLA_NAME` only;
     - `cli`: the caller's `VIOLA_NAME`, then the target argument (Trace context propagation);
     - `ui`: no instance. Its file name needs `<port>`, and the GUI port can come from `config.json` (security Data Classifications, config values). For `ui` only, the step-5 `config.json` parse therefore runs here and its result is reused at step 5. `<port>` resolves flag → `config.json` → `47319` (arch precedence flags > config > defaults). A `ui` panic during that parse falls in the §7 pre-init window (D-29).
  4. **Home strict-modes first, diagnostics init after** (overseer fix pass 2, B2). When viola creates the home (a not-yet-existing `--home`, as the tests harness passes), it creates it first: 0700 on Unix, and on Windows the explicit protected user + SYSTEM DACL that security requires for a `--home` outside `%USERPROFILE%`. The role's security strict-modes check then runs on the home (owner, mode / DACL, not a symlink; security `~/.viola/` access control). Nothing under the home, `diagnostics/` included, is created or opened before that check passes. A refused home gets no diagnostics line: the role exits with its security outcome (`hook` fails open with exit 0), and a panic in this window falls in the §7 pre-init window (D-29). Roles with no strict-modes check in security still get the diagnostics checks below. Only then create `<home>/diagnostics/` with `DirBuilderExt::mode(0o700)` on Unix; on Windows it inherits the already-verified home DACL. Before the first write, `diagnostics/` and every opened diagnostics file (role file, and later the detail file) get the same checks as the home: on Unix, `lstat` owner == `geteuid()`, `mode & 0o077 == 0`, not a symlink (files opened with `O_NOFOLLOW`); on Windows, owner and DACL. A failed check is handled like a failed open (below), so a pre-existing foreign, permissive or symlinked diagnostics file is never written. Open the role file with `OpenOptions::new().append(true).create(true)` and `OpenOptionsExt::mode(0o600)` on Unix. If the open fails, the writer becomes `std::io::sink` (or stderr for `mcp` only, D-09). The instance detail file `<home>/instances/<name>/diagnostics/detail-<process>.ndjson` is **not** opened here. It is opened lazily, with the same append / 0600 / 0700 rules, by the first content-bearing record (chain, drift report), and the panic hook opens it itself when it is still closed. A failed detail open drops only the detail line, never the home-level line, and writes nothing to stderr. The error-free `hook` path therefore keeps exactly one log `open` (D-29).
  5. Parse `<home>/config.json` once for the process. `diagnostics_level` falls back to `"info"` when the file is missing or unreadable or the value is unknown. Then install the subscriber with an explicit writer (below). No subscriber exists during the parse, so its skipped-key count and failure `detail` are held in memory. A panic during the parse is still logged, because the role file exists after step 4.
  6. `obs_event!(ProcessStart, …)`, then `parse-rejected{parser:"config-json", detail, count}` if the step-5 parse failed or skipped keys (D-28).

  Per-role anchors:
  - `run`: steps 1–6 finish **before** `run.collision_check`, so exit-1 causes are logged. The panic hook is live before `pty.spawn`.
  - `ui`: before `axum::serve` binds `127.0.0.1:<port>`.
  - `mcp`: before the rmcp 3.4.1 stdio transport starts.
  - `hook`: one `config.json` read plus exactly one log `open`, then appends, which fits the `max < 1.0 s` gate.
- **Init body sketch (≤ 5 lines):**
  ```rust
  let sub = tracing_subscriber::fmt().json().flatten_event(true).with_current_span(false)
      .with_span_list(false).with_ansi(false).log_internal_errors(false).with_max_level(tracing::Level::DEBUG)
      .with_timer(MillisUtc).with_writer(diag_writer /* BoxMakeWriter over Arc<File> | sink */)
      .finish().with(viola_targets(cfg.diagnostics_level)); // filter::Targets = the only configurable level gate
  tracing::subscriber::set_global_default(sub)?;
  ```
  `MillisUtc` is a crate-local `FormatTime` that writes `chrono::Utc::now().to_rfc3339_opts(SecondsFormat::Millis, true)`. It is needed because the default `SystemTime` timer writes microseconds and `ChronoUtc::rfc_3339()` writes `+00:00` with automatic precision (obs-research, tracing-subscriber, finding 1).

### Service identity

- **service.name:** hardcoded `"viola"` as `viola_core::SERVICE_NAME`. This is the arch-fixed binary name, already served as `"name":"viola"` by `/health` and `/api/info`. It is never read from `OTEL_SERVICE_NAME` / `SERVICE_NAME`: arch says env vars are not a configuration channel.
- **service.version:** compile-time `pub const VERSION: &str = env!("CARGO_PKG_VERSION");` in viola-core. Every crate uses `version.workspace = true` and reads this one constant, so the log `version`, channel `sender`, snapshot `writer` and `/health.version` cannot drift apart.
- **deployment.environment:** N/A. viola is local-only with no hosting (arch Surfaces). No env-var fallback exists: env vars are not a configuration channel.
- **Resource attributes:** no OTel Resource is built in v1. The identity is emitted as fields on `process-start`: `service_name`, `version`, `os` (`windows|macos|linux` from `std::env::consts::OS`), `pid`. Every line carries the role (`process`) and the instance (`instance`). If the deferred bridge is ever adopted, use `Resource::builder_empty()` with these same values.

### Logging stack

- **Library:** tracing 0.1.44 (facade; Tokio-free, no C) + tracing-subscriber 0.3.23 (`fmt` JSON formatter; meets security Vector 9's `>=0.3.20`).
  - Every line is emitted through **one crate-local macro `obs_event!`**. It is defined in viola-core as a `macro_rules!` that expands to `::tracing::event!`, so viola-core itself stays I/O-free and tracing-free.
  - The macro always attaches `event` (the `ObsEvent` enum's kebab `Display`), plus `process` and `instance` from a process-global `OnceLock<ProcessCtx>`. Each is key absence when it has no value.
  - `corr` is an ordinary typed `key = value` field that the caller passes on the events that carry one. It is never `?`/`%`, and it is absent when null. The macro has no dedicated `corr` arm, because in `macro_rules` such an arm is ambiguous with the generic `key = value` arm. The schema confines `corr` to the corr-bearing events and types it `number|string`. As measured at chunk 2026-09-24-diagnostics-plane (`crates/viola-core/src/obs.rs`, `tests/contract_diag_schema.rs`).
  - `message` is a static literal equal to the event name, so it never carries interpolated content.
- **Format:** structured JSON-per-line. `on_event` formats into a thread-local buffer and makes one `write_all` per line on an append-mode handle, which meets the arch "one `write` per line" rule. The line is codes-only and stays well under 4 KiB. Every role file can have concurrent writers in separate processes, and the same rule covers all of them:
  - `hook-<name>.ndjson`, shared by hook processes;
  - `mcp.ndjson`, shared by one `viola mcp` per Claude session;
  - `cli-<name>.ndjson`, shared by concurrent short-lived verbs;
  - `run-<name>.ndjson` and `ui-<port>.ndjson`, briefly: a second `viola run <name>` or `viola ui` on a live name or port opens the same file at init step 4. It appends its `process-start` and its exit-1 `process-exit` (for example `detail:"already-live"`, Scenario 1) next to the live process's lines. The concurrent-append check covers this collision path too (D-29);
  - the instance detail files `detail-hook.ndjson`, `detail-cli.ndjson` and `detail-mcp.ndjson`, shared by those same processes. Their lines (chains, drift reports, one-line backtraces) are not codes-only and can exceed 4 KiB, so the size argument below does not apply to them. They rely only on the single `write_all` and the torn-line tolerance, and the concurrent-append check must include a detail line larger than 4 KiB (D-28).

  Each line is one `write_all` of one complete line on an append-mode handle. POSIX `O_APPEND` fixes the offset per write; on Windows, `append(true)` opens with `FILE_APPEND_DATA` only. Non-interleaving at this size is an assumption, not a POSIX guarantee, because the 4 KiB `PIPE_BUF` rule applies to pipes. Two things back it:
  - readers tolerate a torn line: the harness emits `{"torn":true}`, and G2 skips it through `fromjson?`;
  - a tests-owned concurrent-append check on windows-2025, macos-latest and ubuntu-latest asserts that every line of each shared file parses. This is a multi-platform-exporter-compat item. A torn line fails that check.
- **Mandatory builder settings beyond the tests line** (obs-research, tracing-subscriber, findings 2–4). Each is additive and renames or removes no required field:
  - `.log_internal_errors(false)`: the default `true` falls back to `eprintln`, which would break the Hook contract and the `run` terminal rule;
  - `.with_span_list(false)`: closes the `spans:[…]` leak path;
  - `.with_writer(...)` always explicit: the default writer is stdout;
  - `.with_ansi(false)`;
  - `with_file(false)` / `with_line_number(false)` left at their defaults, so no source paths.
- **Sink:** **file-only, one file per role.** There is no stdout sink on any role, and no pretty or dev sink. The files are:
  - `run`: `<home>/diagnostics/run-<name>.ndjson`;
  - `hook`: `<home>/diagnostics/hook-<name>.ndjson` (shared by concurrent hook processes; a write failure is swallowed);
  - `mcp`: `<home>/diagnostics/mcp.ndjson`, with stderr JSON only when the file cannot be opened (D-09);
  - `ui`: `<home>/diagnostics/ui-<port>.ndjson`;
  - `cli`: `<home>/diagnostics/cli-<name>.ndjson`, only when an instance resolves (D-06).

  Content-bearing records (full anyhow chains, serde_path_to_error drift reports, panic payload + backtrace) go **only** to `<home>/instances/<name>/diagnostics/detail-<process>.ndjson` (0600/0700), and only when an instance resolves (D-08).
  - They never pass through the tracing subscriber, whose one writer holds only the home-level role file.
  - The root-bin `viola::obs` detail writer formats each detail line itself, as the panic hook does: same `timestamp` (`MillisUtc` format), `level`, `target`, `message`, `event`, `process`, `instance`, and `corr` / `conn` keys. It writes each line with one `write_all` on the lazily opened detail handle.
  - No `obs_event!` call ever carries `chain`, `drift_report`, `panic_payload` or `backtrace`, and G4's `diag-line.v1.json` rejects a home-level line that does (D-30).
- **Agent-mode flag:** **none.** JSON-to-file is the only mode (obs-scope §3).
  - The level comes from `config.json` key `diagnostics_level` (`"info"` default | `"debug"`), applied through a `tracing_subscriber::filter::Targets` layer built in code.
  - It is never read from `RUST_LOG`, and `EnvFilter` / the `env-filter` feature is never enabled.
  - Level changes volume only. Every level uses the same field allow-list, so no setting can disable redaction (security Anti-Patterns).
  - Third-party targets (`rmcp`, `axum`, `tower_http`, `hyper`, `portable_pty`, `notify`, `sysinfo`, `interprocess`) are `OFF` in every sink, because their records lack the required fields. Their failures are captured at viola's seam from the returned `Result`s (D-11).

### Log format JSON schema

**Binding. Reproduced verbatim from test-plan.md §3 Test Harness Contract → Log format (re-synced in overseer fix pass 2, 2026-09-24, after test-plan amendments D-21 / 693e083 and fix pass 2, and again in fix pass 3 for Z7). Obs aligns to tests, not vice versa.**

```markdown

Files are 0600, dirs 0700, with one `write` per line.
- **Required fields:**
  - For process logs: `timestamp` (RFC 3339 UTC with ms and `Z`), `level` (`DEBUG|INFO|WARN|ERROR`), `target`, and `fields.message` (or the flattened `message`).
```

### Log file location

- **Path:** `<home>/diagnostics/{run-<name>,hook-<name>,mcp,ui-<port>,cli-<name>}.ndjson`.

### Snapshot / paste-to-AI integration

N/A: there is no pulse-class receiver in the stack. The paste-to-AI workflow runs through the tests harness instead of a tail of a single log file:
- `scripts/agent-run.sh logs` / `scripts/agent-run.ps1 logs` merges `events.ndjson` (`{"src":"events","instance","offset","record"}`) with every `diagnostics/*.ndjson` (`{"src":"diag","file","record"}`) and every instance detail line from `instances/*/diagnostics/detail-*.ndjson` (`{"src":"diag","file","instance","record"}`; the added `instance` tells apart the same `detail-<process>.ndjson` basename across instances, per tests `logs`). Torn lines appear as `{"torn":true,"offset":n}`. The merged output is filterable by `--instance`, `--kind`, `--process`, `--after`.
- `agent-run status` is the aggregate health snapshot: `state`, `last_error` closed enum, `api_sessions_equal_list`.
- Canonical agent queries:
  - To follow one send across every side: `agent-run logs | jq -c 'select(.record.instance=="B" and (.record.event|IN("send-issued","send-confirmed","send-refused")) and .record.corr==412)'`, where `B` is the send's target.
    - A send `cursor` is a byte offset into the target's own `events.ndjson`, so it is unique per target instance only. Two wrappers with identical start sequences (common in E2E) can both hold a send at 412, so `corr` alone mixes sends.
    - `send-*` lines with a cursor `corr` are emitted only by the target wrapper (`side:"wrapper"`, D-27), so the jq `instance` predicate is the target's. The caller-side `send-refused{side:"client"}` has `corr` null and is read from the caller's `channel-response{conn}` and `process-exit` instead.
    - The harness `--instance` filter is still not used. It would also drop the caller's `channel-*` lines, which carry the caller's instance (see Trace context propagation).
    - The `event` filter keeps out an unrelated `channel-request` whose JSON-RPC `id` happens to be 412.
    - The `channel-*` lines of the same send are reached from a matched send line: its `(conn, rpc_id)` equals their `(conn, corr)` (D-30). When refusals at the same offset must be told apart, add `and .record.rpc_id==<id>` to the query.
    - The hook side (`hook-invoked{hook_event:"user-prompt-submit"}`, `corr` null) joins by the wrapper's `instance` + `hook_event` + `timestamp` inside `run.confirm_window`;
  - `jq -c 'select(.record.level=="ERROR" and (.file|startswith("detail-")|not))'` lists every error and panic once. The detail-file duplicate of a panic line is excluded (§10).
- The harness `logs` glob must also cover `instances/*/diagnostics/detail-*.ndjson` (D-08). This additive harness change is part of tests amendment D-21.

### Trace context propagation

- **HTTP boundaries:** no W3C `traceparent` in v1. The browser sends no propagation header (obs-scope §3), and axum-tracing-opentelemetry 0.39.1 is rejected: it needs the deferred SDK, its W3C `traceparent` extraction has no sender, and its optional `/metrics` route would be a new listener. (Its MSRV 1.91 fits the raised 1.96 workspace floor, D-22, so MSRV is no longer a reason.)
  - Correlation on the `ui` side runs on the SSE `id:` cursor `<ViolaName>:<offset>` and `Last-Event-ID`.
  - `sse-opened` records `last_event_id_present` / `last_event_id_valid` and `resume_instances` (a count).
- **gRPC boundaries:** N/A (there is no gRPC in the stack).
- **IPC boundaries** (viola-channel JSON-RPC over interprocess 2.4.4 local sockets):
  - `corr` carries the JSON-RPC `id` on channel lines, `dialog_id` on dialog and hook lines, and the send `cursor` on send lines (tests).
  - **Additive `conn` field (D-10).** The client generates `conn = "<process>-<pid>-<t0>-<n>"`, with `t0` the process's start instant in Unix epoch milliseconds (captured once at init; Low sensitivity like `pid`) and `n` a per-process connection counter (D-32), and sends it in `params` alongside `v` / `sender` / `from`. Both sides log it on `channel-request` / `channel-response`. It is wire-safe under arch Mixed-version tolerance, because readers skip unknown fields. A server receiving a frame without `conn` from an older peer logs `srv_conn = "srv-<accept counter>"` instead.
  - **Join key.** The merged-log join key for channel lines is `(conn, corr)`, and `instance` is deliberately **not** part of it (D-25).
    - `conn` is unique across the session home (`<process>-<pid>-<t0>-<n>`, D-10, D-32). `<pid>` alone is not unique: PIDs are recycled, quickly on Windows. Every `hook` process opens exactly one connection (`n` = 1) and sends the same first JSON-RPC `id`, so without `t0` two hook calls from a reused PID would share `(conn, corr)`.
    - Each side logs its **own** instance. `cli` and `mcp` log the caller's `VIOLA_NAME`, which is also `from`. `run` logs the wrapper's `ViolaName`. So the two sides of one call carry different `instance` values.
    - `srv_conn` lines from older peers have no client-side counterpart. They join only within the server's own file.
  - **`cli` instance precedence** (init step 3): the caller's `VIOLA_NAME` comes first. The explicit target `ViolaName` argument becomes `instance`, and names the `cli-<name>.ndjson` file, only when `VIOLA_NAME` is unset. So `viola send --to B` run by driver A logs `instance:"A"` to `cli-A.ndjson`.
  - `agent-run logs --instance B` therefore shows only B's side of a call. To reach the caller, take `conn` from B's `channel-request` and query with no `--instance` filter, for example `agent-run logs | jq -c 'select(.record.conn=="cli-4812-1790219525118-1")'`.
  - **Send cursor on early refusals.** The arch `send` result returns `cursor` only on success or `unconfirmable`; a refusal result carries `refusal` + `detail` only. For a send refused before `send-issued` (`human-typing`, `budget-paused`, `input-not-ready`, `turn-running`), the wrapper's `send-refused` carries `corr` = the target's `events.ndjson` end offset at the moment of refusal. This value is a log join key only. It is never returned to the caller and is not a `wait after` value. After `send-issued`, every `send-*` line carries the issued cursor. The cursor alone is not a unique send key. Refusals at an unchanged end offset can share it, and a later issued send can reuse it.
  - **Send ↔ channel link (D-30).** Every wrapper `send-*` line also carries `conn` (or `srv_conn` for an older peer) and `rpc_id`, the JSON-RPC `id` of the `send` request it answers. The pair `(conn, rpc_id)` on a send line equals `(conn, corr)` on that call's `channel-request` / `channel-response`, on both sides. So the caller reaches the wrapper's send lines, and the wrapper's send lines reach the caller, without timestamp guessing. One send is identified by target `instance` + `corr` + `conn` + `rpc_id`.
  - `from` is logged with the constant companion `from_trust:"self-reported"` and is never treated as identity.
  - JSON-RPC notifications (`hook.event`) have no `id`, so their `channel-request` has a null `corr`. They join through `hook_event` + `instance` + `timestamp`.
- **Claude Code → hook stdin:** there is no inbound context. Correlate by `instance` + `dialog_id` (dialog hooks) or `instance` + `hook_event` + `timestamp`.
- **Internal async boundaries:**
  - `viola-ui` / `viola-mcp` (Tokio): spawned futures use `tracing::Instrument::instrument(span)` / `.in_current_span()`.
  - `run` std threads (PTY pump, handle-wait thread, channel server workers): the thread closure takes a cloned `tracing::Span` and runs inside `span.in_scope(...)`.
  - Because spans are not serialized, `corr`, `conn` and `instance` are always passed as **explicit values** into the thread or task and set on each `obs_event!`. They are never recovered from span context.

### Heartbeat ticks

_[Standard+ tier. The stall-detection intent is kept, with viola-specific mechanisms instead of 10–30 s tick lines (D-13).]_

- **Tick interval:**
  - `run`: the existing `<instance>/heartbeat` file, touched every **1 s** (arch contract). It is not logged per tick: a 1 s line into a never-rotated file would grow without bound.
  - `ui`: `Sse::keep_alive` every **15 s**. This is a tests perf gate, observed by the tests at `advance(15 s)` and not logged per keep-alive.
  - `mcp`, `hook` and short-lived CLI verbs: no tick (request-driven).
- **Tick event format:**
  - Transition-only `liveness-changed` (D-02), emitted by the long-lived reader `ui` when a watched instance's state changes. Fields: `subject_instance`, `liveness_from`, `liveness_to` (`live|stale|gone`), `heartbeat_age_ms`, `pid_alive` (sysinfo 0.39.6 pid + start-time check).
  - Short-lived readers (`list`) expose `liveness` in `--json` and `/api/sessions` instead, and the agent reads it from the `agent-run status` snapshot.
- **Stall detection:** the agent reads `agent-run status` (`state: degraded` when any item is `stale`), or `agent-run logs --process ui | jq 'select(.record.event=="liveness-changed")'`. The flip threshold is `heartbeat_age_ms > 5000` (4.9 s live / 5.1 s stale or gone).

- **Required span attributes:**
  - `channel.request` / `channel.dispatch`: `method="send"`, `conn`;
  - `run.readiness_gate`: `outcome` (`ready|input-not-ready`), `vt100_panicked` (bool);
  - `pty.paste_write`: `text_bytes`, `paste_mode="bracketed"`;

- **Required log fields:** common fields plus:

  - `send-issued{corr:<cursor>, from, text_bytes}`;
  - hook: `hook-invoked{hook_event:"user-prompt-submit", corr:null}`;

- **Surfaces involved:** cli or ipc-internal (mcp) → ipc-internal (channel) → cli (`run`) + persistent store (`events.ndjson` tail).

- **Required span attributes:**

- **Cleanup:** `wait.block` closes on the response or on the connection error. A mid-call disconnect is logged once, by the client.

#### Scenario: Dialog → `answer` (question / permission / plan), including the unverified-CLI branch

- **Surfaces involved:** cli (`hook` pre-tool-use / permission-request) → ipc-internal (`hook.dialog`) → cli (`run`) ← cli or ipc-internal (mcp) `answer`.
- **Must-trace spans:** `hook.handle` (SERVER) › `channel.request(hook.dialog)` → `channel.dispatch` › `run.dialog_register` › `run.dialog_await` › `hook.decision_emit`. Driver side: `answer.client` › `channel.request(answer)` → `channel.dispatch`.
- **Required span attributes:**
  - `run.dialog_register`: `dialog_kind` (`question|permission|plan`), `pending_conflict` (bool: a second concurrent dialog gets a `null` response);
  - `run.dialog_await`: `deadline_ms`, `deadline_hit`;
  - `hook.decision_emit`: `decision_emitted`.
- **Required log fields:** common fields plus:
  - wrapper: `dialog-raised{corr:<dialog_id>, dialog_kind, hook_event}`, then `dialog-answered{corr:<dialog_id>, dialog_kind, from, from_trust, deadline_hit, duration_ms}`;
  - hook: `hook-invoked{corr:<dialog_id>, hook_event, stdin_bytes, invoked_at}`, emitted once `dialog_id` is known (D-07), then `hook-decision{corr:<dialog_id>, hook_event, decision_emitted, deadline_hit, detail, duration_ms}`;
  - driver-side refusals: `channel-response{result_class:"refusal", refusal:"not-delivered", detail:"unknown-dialog"}` (exit 13), or `refusal:"unverified-cli"` (exit 12, answer withheld).
  - The question, answer and tool `input` never appear.
- **Cleanup:** `run.dialog_await` closes on answer or deadline. On deadline the hook emits `hook-decision{decision_emitted:false, deadline_hit:true}`, exits 0 with empty stdout, and the dialog renders for the human. Fail-open before `dialog_id` gives `hook-invoked{corr:null}` + `hook-decision{corr:null, detail}` (Section 6 fail-open codes).

#### Scenario: Human takes the wheel, automation is refused, `release` returns it

- **Surfaces involved:** cli (`run`, key input) + `events.ndjson` (`wheel`) → cli or ipc-internal (mcp) `send` refused → cli `release` → ipc-internal.
- **Must-trace spans:** `run.wheel_transition` (INTERNAL) › `channel.dispatch(send)` refused › `channel.dispatch(release)`.
- **Required span attributes:** `run.wheel_transition`: `wheel_from`, `wheel_to` (`human|driver`), `cause` (`human-key|manual-pause|release`). Never the typed keys.
- **Required log fields:** common fields plus:
  - `send-refused{corr:<cursor>, refusal:"human-typing", detail:null|"manual-pause", wheel:"human", side:"wrapper"}`, with the client `process-exit{exit_code:10}`;
  - `channel-request` / `channel-response{method:"release"}`;
  - when `release` arrives from a driver rather than the CLI, `release-from-driver{corr:<id>, conn, from, from_trust}` (D-01), never a generic `-32602` wrapper fault.
- **Cleanup:** `run.wheel_transition` is a point-in-time span. The `wheel` product event in `events.ndjson` is the audit record.

#### Scenario: Budget governor

- **Surfaces involved:** cli (`hook statusline`, shell-out) → persistent store (`budget.json`) → cli (`run`, evaluated at start, on `send` and at `turn-ended`) → `events.ndjson` (`budget-gate`).
- **Must-trace spans:** `hook.statusline` (SERVER) › `state.budget_write` › `statusline.shell_out` (CLIENT). In `run`: `run.budget_eval` (INTERNAL).
- **Required span attributes:**
  - `state.budget_write`: `five_hour_pct`, `seven_day_pct`;
  - `statusline.shell_out`: `shell_exit_status`, `duration_ms`;
  - `run.budget_eval`: `trigger` (`start|send|turn-ended`), `paused`, `window`.
  - Never `statusline_command`.
- **Required log fields:** common fields plus:
  - `hook-invoked{hook_event:"statusline", corr:null}`;
  - `process-start` / `process-exit{subject:"statusline-shell", shell_exit_status, duration_ms}`;
  - `hook-decision{hook_event:"statusline", budget_written, duration_ms}`;
  - `send-refused{corr:<cursor>, refusal:"budget-paused", detail:"five-hour"|"seven-day", window, used_percentage, resets_at, paused:true}` with client `exit_code:11`.
- **Cleanup:** `statusline.shell_out` closes on child exit. The user's stdout passes through unchanged and is never logged.

#### Scenario: GUI view: page load, sessions and links, live SSE tape with `Last-Event-ID` resume

- **Surfaces involved:** web-spa (`ui` backend, boundary-only frontend) + persistent stores (notify tail of `events.ndjson`).
- **Must-trace spans:** `ui.http_request` (SERVER, via the custom TraceLayer) for `/`, `/assets/*`, `/api/sessions`, `/api/links`, `/api/info`, `/ready`, `/health`. `ui.sse_stream` (SERVER, manual, with a `Drop` guard) covering open › resume › close. `state.tail_notify` (INTERNAL).
- **Required span attributes:**
  - `ui.http_request`: `method`, `path` (`uri.path()` only, truncated to 256 bytes), `route` (the matched route template or `unmatched`);
  - `ui.sse_stream`: `last_event_id_present`, `last_event_id_valid`, `resume_instances`.
- **Required log fields:** common fields with `process="ui"`, `instance` null, `corr` null, plus:
  - `process-start{subject:"self", port}`;
  - `http-request{method, path, route, status, problem, duration_ms, skipped}`, where `skipped` = `{unknown_kinds, unknown_fields, torn_lines}` on `/api/sessions`;
  - `sse-opened{last_event_id_present, last_event_id_valid, resume_instances}`, then `sse-closed{close_cause, events_sent, duration_ms}`, with `close_cause` ∈ `client-gone|server-shutdown|tail-error` (D-04);
  - `liveness-changed` per watched instance (D-02).
  - The token, `Cookie`, `?t=` and `ui/<port>.url` contents never appear. The one-time launch line is written to stderr directly, never through the subscriber.
- **Cleanup:** the `ui.sse_stream` guard's `Drop` emits `sse-closed` exactly once. Browser-side verdicts (TTI proxy, `TAPE` state words, readback states) are read by Playwright from DOM attributes and `performance` entries and joined to server `http-request` / `sse-opened` lines by timestamp.

**Edge flows** (tests E1–E5):
- **E1** (unwrapped hook no-op): no `VIOLA_NAME` means no file, no line, exit 0 and empty stdout/stderr, asserted by absence (D-16).
- **E2** (R8 strip): `env_stripped_count` / `env_stripped_known` on `process-start{subject:"claude-child"}`, never values (D-14).
- **E3** (`link` / `unlink`): `channel-request` / `channel-response{method:"link"|"unlink"}` on the driven wrapper; the product `link` / `unlink` events live in `events.ndjson`.
- **E4** (SSE resume): the `sse-opened` resume fields.
- **E5** (snapshot corruption): `state-recovered{detail:"snapshot-replayed"|"snapshot-unsupported-v", file:"snapshot.json", v_seen}` (D-03).
- **Capability ledger** (`ledger/stamps.json`, obs-scope §1 persistent stores):
  - Read inside `run.version_gate` as the child span `state.ledger_read`. Its outcome is the existing `cli_verified` on `process-start{subject:"claude-child"}`. A missing stamp gives `cli_verified:false` and the Scenario 4 `unverified-cli` branch.
  - An unreadable or unparsable ledger gives `parse-rejected{parser:"ledger-stamps", detail:"unreadable"|"malformed", count}` in `run-<name>.ndjson` and is treated as unverified.
  - The path and stamp contents never appear.
- **`verify` / `plugin install`:**
  - Dispatch spans: `cli.verify`, with `cli.verify_step` per step and `state.ledger_write` for the stamp, and `cli.plugin_install`.
  - With `VIOLA_NAME` set they log `process-start` / `process-exit{exit_code, detail}` to `cli-<name>.ndjson`. Run from a plain terminal with no instance, they write no process-log file (D-06). Their agent-readable outcome is then the exit code plus the `stamped <version>  N pass  N fail` stderr summary (design).
  - In CI, `viola verify` runs only against the fake agent: tests harness `boot` step 4 and the rstest `stamped_home` fixture, as the only writer of `ledger/stamps.json` (test-plan Decisions Log). The real-`claude` verify never runs in CI (arch Pipeline note; the arch amend is pending). No obs gate depends on verify's own log lines. Its home-level lines, when `VIOLA_NAME` is set, fall under G2, G4 and the secret scan like any other.

## 7. Error Capture & Reporting

_[Standard: included]_

**Platform pick:** **local error capture only, with no external platform.** The mechanism is thiserror 2.0.20 typed errors with fixed-message `Display` impls on `PtyError`, `ChannelError`, `StateError`, `AgentError`, `McpError`, `UiError` and `CoreError`. anyhow 1.0.104 is used at the root-bin dispatch edge and its catch-site reporter (`viola::obs::report_internal_error`) only, plus a hand-written `std::panic::set_hook` and `std::panic::catch_unwind` (obs-research, Error Reporting Platform).
- sentry 0.49.3 / sentry-tracing 0.49.3 are **not admissible**. They break the egress ban ("viola makes no outbound network calls"), and their default `reqwest` + `native-tls` + `tokio` transport breaks the cargo-deny C-crate (`openssl-sys`) and Tokio-in-sync-crates bans.
- tracing-panic 0.1.2 (stale) and human-panic 2.0.8 (writes a human report to stderr) were rejected.

**Default state:** there is no reporter, so there is nothing to opt into. Any future reporter must meet four conditions, recorded as a Decisions Log precondition:
- use the `ureq` + `rustls` transport;
- apply the NEVER-log floor in `before_send`;
- be off by default;
- never be enabled by an env var.

It would also need a security Decisions Log entry for the egress.

**`before_send` scrubbing pattern:** N/A in v1, because no reporter exists. Scrubbing sits at the source instead (Section 8). Scrubbing layers:
1. fixed `Display` strings on every thiserror type (no fields holding paths or payloads);
2. at dispatch, an anyhow chain whose source is a `serde_json::Error` / `serde_path_to_error::Error` is replaced by the fixed message `internal error` before it reaches stderr, `--json`, MCP `isError`, Problem Details or channel `error.data`;
3. the full chain is written as a one-line JSON array `chain:[...]` to `instances/<name>/diagnostics/detail-<process>.ndjson` only, and only when an instance resolves.

**Panic hooks:**
- The first statement of `main` installs `viola_panic_hook`. It never calls the default hook and never writes to stderr (the `hook` contract and the `run` terminal both forbid it).
- It writes **one** JSON line via a single `write_all` on the pre-opened `Arc<File>` held in a `OnceLock`, **not** through the tracing subscriber (no re-entrancy if the panic happened inside formatting). The line is `{"timestamp", "level":"ERROR", "target":"viola::panic", "message":"panic", "event":"panic", "process", "instance", "panic_location", "thread"}`. `corr` is never written, and `instance` is omitted when none resolved (always for `ui`). This is the same key-absence null encoding that `obs_event!` uses (§3 Null encoding, D-26).
- When an instance resolves, it also writes `{"event":"panic", ..., "panic_payload":"<escaped>", "backtrace":[...frames]}` as one line to `detail-<process>.ndjson`. The backtrace comes from `std::backtrace::Backtrace::force_capture()`, **not** gated by `RUST_BACKTRACE`, because env vars are not a configuration channel.
- The panic hook only writes. The exit is decided at a catch site:
  - **Main-thread catch site (every role):** everything after `set_hook` (clap parse, init and role dispatch) runs inside one `std::panic::catch_unwind` in the root bin's `main`. An `Err` maps to the role's exit below, so no role ends through an uncaught unwind (Rust's default exit 101). The role is taken from argv before clap runs: the first argument that is neither a global flag nor a flag's value (for example `--home <path>`) and that names a role subcommand (`run`, `hook`, `mcp`, `ui`; any other verb is `cli`). So `viola --home <dir> hook stop` is still a `hook`, and a pre-init panic in it still exits 0. Reading `argv[1]` alone would misclassify that form as `cli` and exit 1 (D-28).
  - **`run` worker threads:** the PTY pump and handle-wait thread bodies each run inside `catch_unwind`. An `Err` is sent to `main`, which takes the `run` exit path below, because the session cannot continue without either thread. A worker panic that leaves `main` running with no `process-exit` is forbidden. A panic in one channel server connection worker is contained: the `channel.dispatch` `Drop` guard logs `channel-response{result_class:"error", error_code:-32603}`, the connection closes, and `run` continues.
  - **Unwinding is required:** every Cargo profile keeps `panic = "unwind"`. `panic = "abort"` turns every `catch_unwind` into an abort, so `hook` would die by SIGABRT instead of exiting 0. Gate G3 (§9) enforces this.
- Per-role behaviour after the line:
  - `hook`: `catch_unwind` around dispatch, then exit 0 with empty stdout;
  - short-lived `cli`: exit 1 with the fixed stderr `error: internal error`;
  - `run`: `process-exit{subject:"self", exit_code:1, detail:"internal-error"}`, then exit 1, and nothing on the terminal while the child runs;
  - `mcp` / `ui`:
    - A panic inside a spawned Tokio task is logged by the hook. The runtime contains it at the task boundary, and the process continues.
    - A main-thread panic reaches the main-thread catch site. The process writes `process-exit{subject:"self", exit_code:1, detail:"internal-error"}` and then exits 1. `mcp` writes nothing to stdout on this path.
- Before step 4 of init, no file exists, so the panic hook writes nothing. This window contains only clap parsing and home resolution, plus the `config.json` parse for `ui`, which needs `<port>` to name its file (§3 init step 3, D-29).

**Error classes captured:**
- Unhandled panics (always): the one-line `event:"panic"`.
- Module-boundary errors (Standard+): every typed error that crosses a crate seam ends in a logged `process-exit{detail}`, `channel-response{result_class:"error", error_code}`, `hook-decision{detail}`, `http-request{status, problem}` or `send-refused`. Each carries codes only, at `WARN`/`ERROR` per Section 6.
- vt100 panics under `catch_unwind` in `run.readiness_gate` give `parse-rejected{parser:"vt100-feed"}` plus `send-refused{detail:"input-not-ready"}`, not a process panic.
- MCP rejects are `isError` codes only, mirrored by codes-only log lines.

**Error → span correlation:** errors correlate by `corr` + `conn` + `process` + `instance` (+ `timestamp`), not by `trace_id` / `span_id` (D-12). The detail-file line for a given error carries the same `event`, `corr` and `conn` as its home-level counterpart, so `jq` joins them. There is no Sentry or OTel bridge (both deferred or rejected).

**Gate commands.** Each gate is its own `run:` step with `shell: bash` on all three OSes, and is copied verbatim into `ci.yml`:
- **G1, bare `#[instrument]`.**
  - Needs ripgrep built with PCRE2. The runner images do not guarantee `rg`, so a SHA-pinned install step before G1/G3 installs an official ripgrep release binary (release binaries are built with PCRE2) and then runs `rg --pcre2-version` as its own check. Without that step `rg` exits 127, so G1/G3 fail closed on every commit rather than passing.
  - `-U` lets `\s*` span lines, so an `#[instrument(` with `skip_all` on the next line passes. `skip_all` must be the first argument (the §4 form).
  - rg exit 1 (no match) passes. Exit 0 (a violation) and exit 2 (a regex or I/O error) both fail the step. This replaces the earlier `(?!.*skip_all)` form: without `--pcre2` it exits 2 with empty stdout, so a "must be empty" check would pass on every commit.
- **G2, zero panics.**
  - `-n` makes `inputs` see every line, including the first, and makes empty input a pass (`true`) rather than exit 4. `-e` turns `false` into exit 1.
  - Scope is the home-level role files only. `detail-*.ndjson` repeats the panic line and is excluded (§10).
- **G4, schema conformance.** §10 counts schema-conformance failures as a build failure. G1–G3 do not measure them, and the Unit tests row checks only in-memory lines, so G4 checks real process output.
  - Scope: every line in the G2 file scope is checked against `schemas/diag-line.v1.json`, and every `instances/*/diagnostics/detail-*.ndjson` line against `schemas/diag-detail.v1.json` (§8).
  - It runs as its own step, `id: schema-conformance`, `if: always()` after the last test step. It exits non-zero on any failing line and prints `file`, line number and the failing schema keyword, never the line's content (detail lines carry the canary). The check body and the JSON Schema validator crate are tests-owned; obs owns both schemas.
  - A line that is not JSON is skipped and counted, as in G2, because chaos cases kill writers mid-line and a restarted writer appends after the torn line. Interleaved writes are caught by the concurrent-append check (§3 Logging stack), not by G4.

```sh
# G1: whole workspace from its root (root bin `viola` + crates/* + tests/ + fuzz/); target/ is skipped through .gitignore
set +e; rg -n -U --pcre2 --type rust '#\[(tracing::)?instrument\b(?!\(\s*skip_all\b)' .; test $? -eq 1
# G2: first fail if no home-level role file exists (an empty scope would pass vacuously); `awk 1` ends every file's last line with a newline; -R + fromjson? skip a torn line (not a panic record) instead of failing with jq exit 2
test -n "$(find target/e2e-home -path '*/diagnostics/*.ndjson' ! -name 'detail-*' -print -quit)"
find target/e2e-home -path '*/diagnostics/*.ndjson' ! -name 'detail-*' -exec awk 1 {} + | jq -R -n -e '[inputs|fromjson?|select(.event=="panic")]|length==0'
# G3: no abort panic strategy (profile `panic` key, `-C panic` rustflag, CARGO_PROFILE_*_PANIC env) in Cargo.toml, cargo config or workflows (§7); default regex engine; only rg exit 1 passes
set +e; rg -n --hidden -g 'Cargo.toml' -g 'config.toml' -g '*.yml' -g '*.yaml' "(panic|_PANIC)\s*[:=]\s*[\"']?abort" .; test $? -eq 1
```

## 10. SLO Invariants & Telemetry Budgets

_[ALL tiers]_

**Always-required SLO invariant (every tier):**
- **Zero unlogged panics:** every panic in `run`, `hook`, `mcp`, `ui` and `cli` **after init step 4** produces **exactly one** single-line `level:"ERROR", event:"panic"` record in its home-level role file, with no multi-line backtrace in home-level files, and `hook` still exits 0. Retry-once policies for panic handling are forbidden, in parallel with the tests' `retries = 0`.
  - **Counting rule:** "exactly one", the `viola.panic` counter and gate G2 (§9) count home-level role files only. The companion line in `detail-<process>.ndjson` also carries `event:"panic"` and is excluded. In merged `agent-run logs` output, count `select(.record.event=="panic" and (.file|startswith("detail-")|not))`.
  - **Bounded exemptions** (no file exists, so no line can be written):
    1. the pre-init window before step 4 (§7: clap parse and home resolution, plus the `ui` `config.json` parse);
    2. `cli` without a resolved instance (D-06);
    3. `hook` without `VIOLA_NAME` (D-16);
    4. a failed step-4 role-file open (§3 init step 4). The writer becomes `std::io::sink`, or stderr JSON for `mcp` (D-09), and the panic hook's `OnceLock` stays empty, so it writes nothing, not even to `mcp`'s stderr (D-32).

    The failure condition "a panic evidenced by an exit code without its line" applies only to processes whose `process-start` is in a home-level role file. For the exemptions the only evidence is the exit status. `hook` still exits 0, so a D-16 panic is unobservable by design (E1).

**Standard+ invariants:**
- **Liveness signal** (replaces 10–30 s tick lines, D-13): `run` touches `heartbeat` every 1 s. `liveness-changed` fires on every live↔stale↔gone transition the `ui` observes. The flip happens at >5 s (4.9 s live / 5.1 s stale or gone). When no `ui` runs, no `liveness-changed` line exists. The chaos class "stale heartbeat vs live pid" is then gated on the short-lived readers' `liveness` (`list --json`, `/api/sessions`) through `agent-run status` (`state: degraded`) (§3 Heartbeat ticks).
- **Module-boundary error logging:** every typed error that crosses a crate seam is logged once at `WARN`/`ERROR` with a closed `detail` / `error_code`. The full chain goes only to the instance detail file.
- **Correlation propagation:** every channel call logs `corr` + `conn` on both sides; every send line carries the send `cursor`; every dialog line carries `dialog_id`. W3C traceparent is not used (D-12).
- **Deterministic emission:** events key on hook events, `events.ndjson` offsets and DOM attributes. Nothing is derived from screen content, and no log-based wait relies on sleeps (creator explicit).

- A hyperfine `max` regression beyond the budgets above.
- A secret-scan hit, or a `diagnostics/` file that is not 0600 (or not DACL-protected on Windows).
- A schema-conformance failure: unknown `event` value, missing required field, or a field outside the catalog.
- A clippy `disallowed-macros` / `print_stdout` / `print_stderr` / `dbg_macro` failure; a `scripts/lint-probes.sh` failure (a ban that did not fire, a control that did not pass, or a raw `event!` outside `crates/viola-core/src/obs.rs`); a G1 bare-`#[instrument]` or G3 `panic = "abort"` hit, or either gate exiting with anything other than rg exit 1 (including exit 2 regex/I-O error and 127 missing `rg`); or a `cargo deny` (Tokio, C-crate, veil `toggle`, banned obs crates) failure.
- A surviving cargo-mutants mutant in obs code.

## 11. Obs Anti-Patterns (NEVER do these)

_[ALL tiers — single source of truth for all obs bans]_

### Telemetry Strategy

- NEVER over-instrument hot paths. The PTY pump read loop and the vt100 feed get no per-byte or per-chunk span or event; log gate outcomes only.
- NEVER skip spans or events on the 7 must-trace paths (Section 4). The agent loses its ability to debug.
- NEVER let the signal pyramid collapse into free text. Every line carries the closed `event` enum and `corr`.
- NEVER add an OTel SDK, OTLP exporter or `opentelemetry-stdout` without a Decisions Log entry. The stdout exporter is inadmissible on every role (stdout is reserved), and `opentelemetry-otlp`'s default `reqwest-blocking-client` spins up a Tokio runtime.
- NEVER derive telemetry from screen content. vt100 is used for readiness and modal gate outcomes only (brief §3.2), and Claude Code transcripts are never read as a contract.

### Spans / Traces

- NEVER include PII or content in span fields. Scrubbing at an exporter stage is too late, and v1 has no exporter stage at all.
- NEVER use a bare `#[instrument]`. It records every argument with `Debug` and leaks send text, `hook.dialog` payloads and tool `input`. Always use `#[instrument(skip_all, fields(...))]`.
- NEVER use `#[instrument(err)]` or `#[instrument(ret)]` on functions whose error or return can carry a serde / serde_path_to_error source or user content.
- NEVER use tower-http `DefaultMakeSpan` (it records the full `uri` including `?t=<token>`), and NEVER call `.include_headers(true)` (it logs `Cookie`).
- NEVER use high-cardinality span names: no instance names, dialog ids or paths in span names.
- NEVER leave the SSE span without a `Drop` guard. TraceLayer considers the response done at header send, so `sse-closed` would be lost.
- NEVER rely on span context to carry `corr` / `conn` / `instance` across threads or tasks. Spans are not serialized, so pass these as explicit values.

### Metrics

- NEVER create in-process metrics instruments (`opentelemetry` meters, `metrics` 0.24.6). There is no reader, exporter or listener to flush them.
- NEVER add a `/metrics` or other telemetry endpoint (for example axum-tracing-opentelemetry's `metrics-prometheus`) without a Security Decisions Log entry. It is a new listener.
- NEVER group derived metrics by unbounded keys (`path`, `corr`, `conn`, `pid`, `instance`). Group by the closed enums only.
- NEVER report latency without the gate statistic. The `max` from hyperfine is the enforced number; p50/p95 are report-only.

### Logs

- NEVER write telemetry to stdout on any role. stdout carries `--json` results (cli), the decision body (hook) and MCP frames (mcp), and `run`'s terminal carries the child's screen. The default tracing-subscriber writer is stdout, so `with_writer` is always explicit.
- NEVER leave `log_internal_errors` at its default `true`. Writer failures would `eprintln` to stderr and break the Hook contract and the `run` terminal.
- NEVER call `tracing::{event,info,warn,error,debug,trace}!` directly outside `viola_core::obs`. Only `obs_event!` guarantees `event`, `process` and `instance`; the caller sets `corr` explicitly as a typed field on the events that carry one. Enforcement: clippy `disallowed-macros` for the level macros, and the fail-closed raw-`event!` grep in `scripts/lint-probes.sh` for `event!` (§3 logger-stack-install).
- NEVER record `corr` with `?corr` / `%corr`. That stringifies numbers, and `corr` must be copied unchanged as a JSON number or string.
- NEVER read the level from `RUST_LOG`, enable the `env-filter` feature, or call `EnvFilter::from_default_env`. Env vars are not a configuration channel.
- NEVER write multi-line stack traces. Panics are one line; backtraces are one-line JSON arrays in the instance detail file only.
- NEVER log at `info` inside hot loops (PTY pump, notify tail per line). Use counts on the boundary event instead.
- NEVER use tracing-appender `non_blocking`. It drops lines when full, needs a `WorkerGuard` flush, and breaks the hook's exit-0 / `max < 1.0 s` gate and the zero-unlogged-panics invariant.
- NEVER rename tests fields (for example `corr` → `correlation_id`, `event` → `event_type`) or add `event` values without a Decisions Log entry.
- NEVER use `print!` / `println!` / `eprint!` / `eprintln!` / `dbg!` in the `hook`, `run` or `mcp` code paths of the product crates (`viola-harness` and the fake agent are exempt, §3 obs-ci-gate-wire). They bypass the file sink and break the Hook contract, the `run` terminal rule and MCP framing. Enforced by `[workspace.lints.clippy]` `print_stdout`, `print_stderr`, `dbg_macro` = `deny` under the §9 clippy step. Only the output modules that own `--json`, human CLI stderr, the hook decision body and the one-time `ui` launch line carry a local `#[allow]`, plus the fake agent's crate-level `#![allow]` in `src/bin/viola-fake-agent.rs` (a root-package bin, §3 obs-ci-gate-wire).
- NEVER install `tracing_log::LogTracer` (or any `log` bridge) by hand. D-11 keeps `tracing-log` off, and bridged records lack `event`, `corr`, `process` and `instance` (D-23).

### Error Reporting

- NEVER add sentry 0.49.3 (or any reporter) in v1. Egress is banned, and its default `native-tls` / `tokio` transport breaks cargo-deny.
- NEVER print an anyhow chain that still contains a serde_json / serde_path_to_error source to stderr, `--json`, MCP `isError`, Problem Details or channel `error.data`.
- NEVER call the default panic hook or let it run. Its stderr output breaks `hook` and the `run` terminal.
- NEVER enable any future reporter by env var or by default. It must be opt-in, use `ureq` + `rustls`, and apply the NEVER-log floor in `before_send`.
- NEVER treat local logs as optional. The file sink is the only error sink and must work with every other feature off.

### PII Scrubbing

- NEVER log any field not named in the Section 6 catalog (default-deny).
- NEVER enable veil's `toggle` feature (`VEIL_DISABLE_REDACTION` / `veil::disable()`). It is banned in cargo-deny.
- NEVER let `config.json`, a `VIOLA_*` env var or a CLI flag widen the field allow-list or disable redaction. Verbosity (`diagnostics_level`) changes volume only.
- NEVER log `CLAUDE*` values, the GUI token, `Cookie`, `?t=` or `ui/<port>.url` contents, at any level, in any file, detail files included. NEVER log `statusline_command`, send text, tool `input` or `last_assistant_message` in any home-level file. They may reach only the instance-scoped `detail-<process>.ndjson`, and only inside a chain or drift report (§8).
- NEVER put paths or pids inside `detail` codes (Founder Direction 4). Paths appear only in instance detail files.

### CI

- NEVER upload `diagnostics/` artifacts before the secret-scan step passes.
- NEVER use unpinned Actions. `actions/upload-artifact` v7.0.1 is pinned by commit SHA and checked by zizmor.
- NEVER lose the failing job's `diagnostics/`. G2, G4 and the secret scan run `if: always()`, and the uploads run `if: always()` / `failure()` combined with `steps.secret-scan.outcome == 'success'`, never bare. On a failed scan the hit report is uploaded instead (§9 Step order). A re-run is not a substitute under `retries = 0`.
- NEVER use human-review-gated log analysis. Every CI telemetry verdict is a `jq` / hyperfine assertion that sets an exit code.
- NEVER inject CI env metadata into product log lines. The product never reads env as configuration.

### SLO

- NEVER skip the zero-unlogged-panics invariant.
- NEVER add retry-once policies for panics or flaky telemetry assertions.
- NEVER define a budget without an exit-code-setting assertion (hyperfine `max` via `jq`).
- NEVER log a line per heartbeat tick or per SSE keep-alive. Log transitions and lifecycle only, because the files are never rotated.

### Universal (agent-driven specific)

- NEVER use proprietary APM as the ONLY exporter (Datadog APM SDK / NewRelic agent / AppDynamics primary). Vendor schemas break paste-to-AI workflows, and viola has no egress at all.
- NEVER use dashboards-only obs (Grafana / Kibana / Datadog UI as the sole consumption surface). Every signal is consumed through `agent-run logs` / `status` and `jq`.
- NEVER use human-review-gated log analysis ("ops team reviews daily" / "developer checks errors") without machine-parseable export.
- NEVER self-instrument as if the product were telemetry. viola is Normal mode (Founder Direction 3); do not turn `events.ndjson` into a collector, and do not add an OTLP receiver.
- NEVER resolve service identity at runtime from env vars (`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`). `"viola"` and `env!("CARGO_PKG_VERSION")` come from viola-core constants. Any future OTel Resource uses `Resource::builder_empty()`.
- NEVER skip scrubbing before any byte leaves the process. In v1 the only destination is local files, and the secret-scan test proves the floor.
