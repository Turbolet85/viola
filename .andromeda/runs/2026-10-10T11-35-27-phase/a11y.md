# a11y extract

## Relevance
partial — the chunk adds one CLI verb with four human-mode refusals and a `--list` print, and one new way into the `run` passthrough; a11y-plan binds both as cli output discipline and the tui boundary, with no WCAG conformance claim; no web-spa element, role, announcement or token is added.

## Constraints
- a11y-plan §1 A11y Scope Summary (CLI and terminal entities → CLI verbs) requires every CLI verb to hold output discipline in three modes: human TTY, plain (non-TTY / `NO_COLOR` / `TERM=dumb`) and `--json`. That entity's verb list does not name `revive`; the new verb falls under the entity by kind, and the list itself is a drift item for the wrap, not a reason to skip the modes.
- a11y-plan §8 Cognitive Accessibility (Error recovery → CLI) requires each of the four preflight refusals (`instance-live`, `cwd-missing`, `session-live`, `no-session`) to print the refusal line on stderr, then `hint:` as the last stderr line, with a typed exit code; `--json` gives one document with no hint. Whether `run`'s existing collision refusal, which scope item 4 reuses unchanged for `instance-live`, already has that layout is research's question.
- a11y-plan §8 Cognitive Accessibility (Error recovery → Verification, cli) pins a closed list of typed exit codes for the assert_cmd check. Whether the four refusals' codes fall inside that list is architecture §Conventions' answer at P2; a code outside it leaves that list stale and is a drift item for the wrap.
- a11y-plan §8 Cognitive Accessibility (Plain language) requires a kebab-case reason or detail code never to stand without the plain word `unable`, and the CLI never to show a stack trace or a bare status number as the only error text. A resume that fails inside the child is on the child's screen and is not viola's text.
- a11y-plan §6 Visual Design Verification (State color tokens → CLI equivalent) requires zero SGR of viola's own under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run`, and `unable` never coloured. `revive`'s refusals and its `--list` chain fall under it; the plan names SGR on three words only, none of which `--list` prints.
- a11y-plan §1 A11y Scope Summary (A11y surfaces → cli → Notes) requires static, linear output with no spinner or redraw, and C0/C1 control characters escaped in human-mode output. `--list` prints a `cause` and an id read from the log; whether those two fields can carry a control byte once the UUID validation of scope item 1 is in place is research's question.
- a11y-plan §1 A11y Scope Summary (CLI and terminal entities → `viola run` TUI passthrough) requires, once the child is spawned, zero viola bytes on the terminal beyond the child's output and no human keystroke blocked, refused or delayed past the current atomic paste. The revived session is that passthrough, so the boundary holds under either answer to the founder's open wheel question.

## Patterns to follow
- Refusal layout pinned by trycmd, typed exit codes and the no-hint `--json` document checked by assert_cmd, on all three OS legs (per a11y-plan §8 Cognitive Accessibility, Error recovery → Verification).
- Mode split of the checks: trycmd / assert_cmd for the non-TTY modes, the portable-pty outer PTY for the TTY-only behaviours (per a11y-plan §4 ARIA Patterns & Roles, P6).
- The tui boundary as three outer-PTY nextest cases, one per clause, with the fake agent as the child; the zero-viola-bytes case compares against an unwrapped fake-agent run on Linux and macOS and checks viola's own literals absent on Windows (per a11y-plan §3 Keyboard test harness → Tooling). Whether a revived start needs its own leg of these cases, or shares `run`'s start path so the existing cases already cover it, is research's question.
- The wheel is probed through records and typed exit codes, sequenced on logged lines, never on a timer and never by reading the child's screen (per a11y-plan §3 Keyboard test harness → Tooling).
- cli checks live in `nextest-integration` / `nextest-e2e` locally and in the CI `test` job's `coverage` suite; no a11y tool and no a11y suite is involved (per a11y-plan §3 A11y testing tool pick → Primary tool per surface).

## Anti-patterns to avoid
- Never colour CLI `unable`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` (per a11y-plan §11 A11y Anti-Patterns, Visual).
- Never ship a human-mode CLI refusal without its `hint:` line; the plan exempts one refusal only, and none of the four is it (per a11y-plan §11 A11y Anti-Patterns, Cognitive).
- Never claim WCAG conformance for the cli or the `viola run` TUI, and never parse the rendered `claude` screen for content as evidence (per a11y-plan §11 A11y Anti-Patterns, Strategy and Universal).

## Contract bindings
- a11y ↔ tests: the cli output-discipline checks are ordinary nextest cases inside the harness `run` JSON; a failure surfaces only in `suites[].failures[]`, and no a11y violation row is written for cli or tui (a11y-plan §3 Structured violation JSON schema → cli / tui; §9 CI Integration, Unit / integration stage).
- a11y ↔ design / layouts: the refusal wording, the hint lines and the `--list` line shape are design's and layout-templates' to give; a11y adds the layout order, the stream, the SGR ban and the escaping (a11y-plan §8 Cognitive Accessibility, Error recovery → CLI; §6 Visual Design Verification, State color tokens → CLI equivalent).
- a11y ↔ architecture: the four exit codes come from architecture §Conventions and are read against the closed list a11y's assert_cmd check names (a11y-plan §8 Cognitive Accessibility, Error recovery → Verification).
- a11y ↔ obs / web-spa: the status announcer's message list is closed, so a `session-start` with cause `resume` or a `state-recovered` line arriving on the tape is never announced; the chunk needs no page change (a11y-plan §7 Screen Reader Support, Live regions).
- a11y ↔ the founder's open question: a revived instance starting with the wheel at `human` would show the existing WHEEL word on the page, a state the plan already owns in `a11y-p4`; no new page state follows from either option (a11y-plan §4 ARIA Patterns & Roles, P4).

## Acceptance criteria contributions
- (a11y) Each of the four `revive` preflight refusals, in human mode, writes its refusal line to stderr and ends stderr with one `hint:` line, exits with its typed code, and under `--json` prints one document holding no hint text; pinned by trycmd and assert_cmd (per a11y-plan §8 Cognitive Accessibility, Error recovery).
- (a11y) `viola revive` refusal output and `viola revive --list` output hold no SGR and no cursor-control or redraw sequence under non-TTY, `NO_COLOR`, `TERM=dumb` and `--json`, and under the outer PTY `unable` carries no SGR (per a11y-plan §4 ARIA Patterns & Roles, P6).
- (a11y) With the fake agent as the revived child, the outer-PTY stream from the spawn onward carries no viola-originated literal, and a human key written during the revived session reaches the child unblocked (per a11y-plan §3 Keyboard test harness → Tooling).
- (a11y) `viola revive --list` prints one static line per chain entry in log order, with any C0/C1 byte in a printed field shown only in escaped form (per a11y-plan §1 A11y Scope Summary, A11y surfaces → cli → Notes).
