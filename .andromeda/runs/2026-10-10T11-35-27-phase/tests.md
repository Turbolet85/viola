## Constraints
- Layer placement: test-plan §11 Test Strategy requires parser, refusal-order and exit-code cases to sit in §4 and only cross-process behaviour in §6. The UUID check on `--id`, the "id must be in this instance's log" rule, the default-id pick (newest logged) and the order of the four preflight refusals are unit cases with labelled rstest `#[case]` rows (per test-plan §4 Conventions and §4 "What unit tests cover" → root bin); the kill-then-revive run is the cross-process case.
- Oracles are literals: test-plan §11 Unit requires the refusal order, the exit codes and the refusal names to be written as literals in the test, never imported from the product, and compared by serde kebab value and integer exit code, never by `Debug`.
- The fake agent builds no payload: test-plan §7 Fake agent requires a hook's stdin to be the bytes of a recorded `fixtures/claude/<cli-version>/<Event>.<variant>.json` (only UserPromptSubmit's `prompt` is set), ignores unknown arguments, and invents no shape before a recorded fixture; test-plan §7 Seed strategies (Recorded hook payloads) and §11 Test Data require fixtures to come only from a `viola verify` recording. The scope's "fake agent honours `--resume <id>` and reports a SessionStart with source `resume` and that id" therefore needs either a recorded SessionStart variant carrying `source: "resume"` or a plan amendment that lets the fake agent set that event's id. Whether such a recorded variant exists under any `fixtures/claude/<ver>/` (the `clear-1` SessionStart is the nearest) and what `--resume` does in the fake agent today is research's question; this is a fork for P4, since no live start is granted.
- Product state is never hand-written: test-plan §7 Seed strategies (On-disk product state) and §11 Test Data require `snapshot.json` and `events.ndjson` to come from a real `viola run` against the fake agent. The recorded `cwd` and the id chain a revive reads must be written by the wrapper the test started. A snapshot with no `cwd` (an older binary's) or an unreadable one may be made only under the same §7 exception the chaos tests use (altering a file the product already wrote), or below the surface in `crates/viola-state/tests/` (per test-plan §5 On-disk).
- Determinism: test-plan §2 Agent-runnable invariants and §11 E2E require every wait to key on an `events.ndjson` byte offset or another explicit signal, never a sleep, with nextest `retries = 0` (test-plan §10 Zero-flakiness budget). The dead instance's log is reused by the revived one, so the `session-start` the E2E asserts must be read past the offset taken before the revive (test-plan §3 `run` step 2 states the same rule for a `gone` name's files). The revive start may begin only after the killed wrapper reads gone by sysinfo pid + start time (per test-plan §6 Scenario Path 3 Cleanup) and its endpoint reads unconnectable (per test-plan §3 `run` step 2, `Wrapper::stop`: an exit code is not the endpoint gone).
- Three OSes: test-plan §9 Matrix builds and §11 Test Strategy require the kill-and-revive case to hold on `windows-2025`, `macos-latest` and `ubuntu-latest`; a Linux-only local green proves nothing for the other two. Whether the child's death with its wrapper is pinned on each OS (the scope's item 7) is research's question.
- A green fake-agent run is no proof of the real CLI: test-plan §11 Test Strategy forbids reading it as one and forbids the real `claude` in CI. The P4 · P6 · P7 · P12 readings are the chunk's own local measurement kept in its `evidence/` with its own launcher and readers — not a test layer, not harness surface (per test-plan §6 "Skipped as untestable"). `run --local-live` covers only `viola verify`'s seventeen rows and claims no other live measurement (per test-plan §3 `run`).

## Patterns to follow
- The root sync chain `home → fake_agent_path → stamped_home → booted_wrapper` in `tests/support/` with `Wrapper::boot` / `stop`, the one `events.ndjson` reader and wait in `events.rs`, the one started-child guard in `cli.rs`, the complete-lines reader in `ndjson.rs` (per test-plan §2 Test directory + naming conventions; test-plan §3 `run` step 2; test-plan §3 Test data bootstrap). A revive test defines no copy of any of them.
- The long-lived revived wrapper is driven like `viola run`: std::process or the outer PTY plus a `Drop` guard that kills then waits, exit read from `child.wait()`, verdicts from `events.ndjson`, the fake-agent receipt and the exit status (per test-plan §6 Drivers per surface, tui row; test-plan §5 Setup / teardown lifecycle). The receipt's `cwd` kind is the oracle for the child's spawn directory, and its `start` line the readiness signal (per test-plan §7 Fake agent).
- Refused revives are short-lived: assert_cmd against `CARGO_BIN_EXE_viola` in a root `tests/cli_*.rs`, one `--json` document per exit code, the human `unable:` / `hint:` pair pinned by literal asserts or a trycmd case (per test-plan §5 Driver(s); test-plan §5 Cross-module patterns → CLI).
- File prefix picks the layer: `cli_` is integration, `chaos_` / `tui_` run under the E2E filterset; functions are `<subject>_<condition>_<expected>` (per test-plan §2 File naming and Test function naming; test-plan §3 `run` steps 1 and 2).
- A fault is an explicit process or file operation on something the test itself started or the product already wrote, as `tests/chaos_torn_append.rs` does; a `state-recovered` line asserted in a chaos case is held to the diag-line schema inside the case (per test-plan §6 Chaos suite; test-plan §2 Chaos / Fault row).

## Anti-patterns to avoid
- Hand-writing `snapshot.json` (a `cwd`, an id) or an `events.ndjson` id chain to set a revive case up (per test-plan §11 Test Data).
- Reading the child's screen for the resume verdict, detecting exit by master EOF, or `.assert()` on the revived wrapper (per test-plan §11 E2E).
- A sleep between the kill and the revive, a retry, or an `#[ignore]` to park a flaking kill-and-revive case (per test-plan §11 E2E; test-plan §10 Zero-flakiness budget).
