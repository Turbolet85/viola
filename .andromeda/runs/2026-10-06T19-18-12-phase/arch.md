## Constraints
- **The ledger is the only gate, and the row set is closed.** Architecture §Cross-cutting Patterns → "Capability ledger as the single gate" requires every dependence on an undocumented `claude` behaviour to be a row in `viola-agent-claude` with a `viola verify` probe that has a post-condition check, never an unconditional assumption. §Established Decisions [CLI Version Compatibility] requires a version to be verified only when its stamp holds every landed row `pass`, and names the five subjects of this chunk (local commands, long-paste wrapper, tag escaping, harness prefixes, R8 identity floor) as rows owed to this entry. So every row added here moves the `cli_verified` bar for every stamped version. Whether the code reads a stamp that lacks a new row as not-verified is research's question. The plan prices a one-row addition as a new probe plus a re-stamp of both recorded versions (same §, the PermissionRequest-question sentence) — the precedent for this chunk's live-session price.
- **A local command's outcome is decided by the ledger, never by a leading slash.** §Established Decisions [Delivery Confirmation] requires exactly three outcomes: a listed command whose measured post-condition is met → `ok`, confirmed; a listed command whose post-condition is "none" or not measured on this CLI version → `ok`, unconfirmed, detail `unconfirmable`; everything else unconfirmed → `not-delivered`. A slash send that is not on the list is an ordinary send (skills fire UserPromptSubmit). `/clear`'s post-condition is fixed by the same § and by [CLI Version Compatibility] → Local commands; `/remote-control` is the plan's one named "no post-condition" command. §Design Philosophy → "Measured, never assumed" and §Cross-cutting Patterns → "Fail open toward the human" carry the same single exception. Not stated by the plan, so research / P4: (a) the full list of known local commands beyond those two; (b) how a row whose post-condition is "none" stays `pass` under the every-row-`pass` rule; (c) how `run` learns "not measured on this CLI version" given §Standard Contracts → Ledger stamps envelope requires `run` to read no field of `measured`.
- **`unconfirmable` rides the existing `send` contract, additively.** §Standard Contracts → Wrapper channel frames and → Channel methods (`send`) already fix the unconfirmed `ok` payload and its `cursor`; §Conventions → Error handling schema requires `unconfirmable` to appear only in an `ok` payload, never as a refusal `detail`; §Conventions → Protocol versioning makes the addition a no-bump change; §Standard Contracts → CLI `--json` output and §Conventions → MCP require the CLI and MCP surfaces to mirror the channel `ok` payload (exit `0`, `isError: false`). [Delivery Confirmation] bounds `send`'s total blocking time (gate wait + paste + window), which a post-condition wait must stay inside. Not stated by the plan, so research / P4: which `send-*` event line the wrapper appends for an unconfirmed-`ok` send (§Standard Contracts → Event `data` per kind names only issued / confirmed / refused), and what `submitted_at` carries for a `/clear` confirmed by a `session-start` rather than a `prompt-submitted` line.
- **Prompt normalisation order and exactness are fixed.** [CLI Version Compatibility] → Tag escaping, → The long-paste wrapper and → Harness prompt prefixes, with §Standard Contracts → Event `data` per kind (`prompt-submitted`), require: `harness` classified on the raw start first, then the long-paste wrapper removed (only the exact same-id pair, ends kept byte for byte), then the tag escape reversed; delivery matching exact, no trim ([Delivery Confirmation]). An escaped tag is typed text and never `harness`, with the one ratified cross-session exception ([Human Takeover / Wheel]). The rows this chunk adds measure that behaviour; they do not license changing the order. Whether the compiled code already follows it at HEAD is research's question.
- **Claude shapes stay in `viola-agent-claude`, and that crate stays pure.** §Established Decisions [Agent Coverage] and §Infrastructure Patterns → Crate dependency direction require the rows, `check`, the stamp merge, `IDENTITY_FLOOR`, the harness prefixes and the unwrap / un-escape to live in `viola-agent-claude` with no I/O and no `viola-state` dependency; the probe spawns and the stamps file I/O belong to the root bin and `viola_state::stamps`. [Delivery Confirmation] requires the wrapper-side matcher never to see a Claude-specific shape, so the local-command list and its post-conditions are `viola-agent-claude` data that `src/run/` consumes as a normalised verdict. §Conventions → Naming patterns (normalised event kinds) and → Error handling schema (`RefusalReason` details) allow new kinds or details only in `viola-core`, never with Claude-specific names. No new crate, no new dependency (§Established Decisions [Module Boundaries]); the `send` and `verify` paths stay std-thread (§Cross-cutting Patterns → Tokio containment).
- **Probes run under the existing `verify` child rules and the one stamps writer.** [CLI Version Compatibility] (the `viola verify` paragraph) and §Occupied Resources → Claude Code integration names require each interactive child to be a direct spawn under the R8 strip at the fixed size, output capped at `MAX_FRAME`, no byte written into a CLI dialog, a modal start killed with no key. A local command that opens a CLI-native dialog or picker falls under that rule. §Occupied Resources → Filesystem requires any probe dir to be 0700, removed on every exit path, and listed there (a new run dir is a registry amendment at wrap). §Standard Contracts → Ledger stamps envelope requires `viola verify` to stay the only writer, a merge to replace only its own version's entry, and new `measured` readings to be additive. §Established Decisions [CI/CD] and [CLI Version Compatibility] require the real `claude` probe and `--record` to run locally only; CI stamps from the fake agent.
- **The identity floor is not negotiable by a probe.** §Occupied Resources → Environment variables requires the floor names removed whatever the persistent environment or `claude_env_keep` says, with names only ever read (never a value), and lists the messaging socket and token among them. ## Patterns to follow
- **Rows ride the existing probe structure.** [CLI Version Compatibility] describes one print-mode probe and four interactive runs feeding `Probes { print, typed, dialogs }` into `check(row, &Probes)`, one stdout step line per row, a failing row still stamped with exit 1. A new row is first asked whether an existing run's capture answers it (Run B's one bracketed paste and its UserPromptSubmit capture are the natural carrier for paste-framing rows) before a new run is added.
- **Recorded fixtures are the CI twin of every live row.** §Occupied Resources → Repository (`fixtures/claude/<cli-version>/`) and → Binary, subcommands and exit codes (test-only binaries) describe `--record` writing scrubbed `<Event>.default.json` / `<Event>.<stem>-<n>.json` / `Screen.<phase>.json` only when 0 rows fail, and the fake agent replaying them through argv options. New rows need the same pair: a recorded shape and a fake-agent replay selected by argv.
- **The `/clear` post-condition reads fields the hook map already normalises.** §Conventions → Naming patterns (Hook → kind map) gives `session-start` its `cause` set, `clear` included, and `agent_session_id`; [Human Takeover / Wheel] has `session-start` end a running turn. The post-condition is expressible on normalised events alone.
- **Settle order of a send.** [Delivery Confirmation] (as landed) has the wrapper claim the matching line, append it, and only then settle the send, so the evidence line precedes the outcome line in `events.ndjson`; §Standard Contracts → Event `data` per kind keeps the `send-*` lines wrapper-sourced and log-only (they never wake `wait`). A post-condition-confirmed send follows the same order.
- **Probe readings go in `measured`, verdicts in `rows`.** §Standard Contracts → Ledger stamps envelope: `typed_probe` and `dialog_probe` are the precedent for an additive reading with no `v` bump.

## Anti-patterns to avoid
- Deciding `unconfirmable` (or anything) from a leading slash, a compiled list with no row behind it, or a presumed delivery — banned by [Delivery Confirmation] ("the decision depends on the ledger") and §Cross-cutting Patterns → "Capability ledger as the single gate".
- A Claude-specific literal (a command name, a tag, a prefix, a hook field) in `src/run/`, `viola-core` or any crate but `viola-agent-claude`; or file / process I/O inside the `ledger` module — banned by §Established Decisions [Agent Coverage] and §Infrastructure Patterns → Crate dependency direction.
- Reaching a measurement by widening a boundary: a new env var or `config.json` key for the probe or the fake agent (§Cross-cutting Patterns → Config management; §Occupied Resources → Environment variables lists the only two test seams), keeping a floor name in a probe child, typing into a dialog, or running the real `claude` in CI ([CI/CD]).
