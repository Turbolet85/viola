## Constraints
- The `unconfirmable` outcome is the third form of the mirror's outcome line: the open four-character box, the state word `unconfirmable`, on **stdout** with **exit 0**, and the box is never filled (per layout-templates §Surface: cli › Signature placement, item 2; §Output structure — `viola send`, third example).
- The outcome line keeps the mirror's fixed column layout: box, one space, the padded state word, the two-space gutter, NAME, then the outcome fields — for this outcome the unconfirmable note, a fixed text, in place of time / `cursor` / `reason  detail` (per layout-templates §Component — Hero / signature output line, Layout). The wireframe's unconfirmable line shows the note and no `cursor` field; whether the human line may also print the cursor the wire outcome carries is NOT stated by the plan — new fields go to `--json` first (per layout-templates §Surface: cli › IA notes, Output as a contract).
- The word column is padded so `open`, `read back`, `unable` and `unconfirmable` line up and the name always starts in the same column; `unconfirmable` is the widest of the four, so it sets the pad. Whether the code's pad already reaches that width is research's question (per layout-templates §Output structure — `viola send`, closing paragraph).
- Lines are appended, never redrawn: the TTY-only stderr issue line stays and the outcome prints under it; with stdout piped the issue line is dropped and the outcome line alone carries the mirror (per layout-templates §Output structure — `viola send`, closing paragraph).
- Under `--json` the unconfirmable outcome is the typed `ok` document with `confirmed:false` + `unconfirmable` on stdout, with the typed exit code, no glyph, no issue line and no hint (per layout-templates §Component — Hero / signature output line, Machine view). The document's exact keys are architecture's `send` wire contract, not this plan's.
- `viola verify` prints one stdout step line per ledger row in the `[NN/MM] <row id> <row words>  pass|fail` form, in ledger order, each appended once, then the `stamped <ver>  <n> pass  <m> fail` summary as the LAST stdout line; `MM` grows as owning chunks land their rows; plain ASCII, no colour, no progress bar, no redraw; `--record` adds no human line (per layout-templates §Output structure — `viola verify`). Every row this chunk adds needs a row id and row words in that form.
- The plan's ledger-order enumeration and its `[NN/14]` wireframe name fourteen rows only: this chunk's new row ids, their words and their position in ledger order are NOT in the plan. Their order is the ledger's (architecture [CLI Version Compatibility] / `LedgerRow::ALL`, research's question); the plan's enumeration and numerals are a drift item for the wrap (per layout-templates §Output structure — `viola verify`).

## Patterns to follow
- The issue line and the outcome line line up column for column so the two read as one strip entry — issue left, readback right, spread over time; the unconfirmable line joins that alignment exactly as the read-back and unable lines do (per layout-templates §Component — Hero / signature output line, second bullet).
- Streams are never mixed: results on stdout; the issue line, refusals, hints and errors on stderr. `unconfirmable` is a result (stdout, exit 0), not a refusal — hint lines are defined directly under refusals only, and the wireframe shows none under the unconfirmable line (per layout-templates §Component — Primary content block 2: refusal lines and the `unable` column, Hint line and Streams).
- The last printed line says what happened, to whom and where, and the exit code is the terminator — no terminator word follows the unconfirmable line or the verify summary (per layout-templates §Component — Footer / terminator).
- A local command that IS confirmed takes the ordinary filled-box read-back outcome line. The cli section names only the matching `prompt-submitted` as the read-back trigger; the `/clear` trigger (`session-start` with cause `clear`) is stated in the web-spa section only (per layout-templates §Surface: web-spa › Signature placement, third paragraph; §Surface: cli › Signature placement, item 2). Whether the code's cli mirror already fills on the new-session post-condition is research's question; the cli wording is a drift item for the wrap.
- A failed or panicked `send` or `verify` prints exactly the one fixed internal-error line from the one catch site, with no hint; a new probe's failure paths ride that site and mint no new human line form (per layout-templates §Component — Primary content block 2: refusal lines and the `unable` column, Line form).

## Anti-patterns to avoid
- No colour, spinner, check mark or `done` on the mirror: `unconfirmable` is words and brackets only, and `turn-ended` is never reported as a send outcome (per layout-templates §Component — Hero / signature output line, Colour and What never happens).
- No new human column, no reworded state word and no changed column order on an existing line: the human columns and words are a stable contract LLM drivers read (per layout-templates §Surface: cli › IA notes, Output as a contract).
- No path, pid, sent text or upstream text on any line this chunk adds — the unconfirmable note is fixed text, and a `verify` step line or refusal names a row id / fixture file and a closed code, never content (per layout-templates §Component — Primary content block 2: refusal lines and the `unable` column, Line form and Hint line).
