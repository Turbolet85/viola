# security extract

## Relevance
relevant — the chunk moves three security-owned lines (the compiled harness-prefix / local-command lists, the `viola verify` children rule, the stamp's row set that gates dialog answering) and makes the R8 identity floor a ledger row's subject; no auth, GUI, IPC-listener or dependency surface is added.

## Constraints
- **Compiled lists only.** security-plan §Security Anti-Patterns → Code Patterns requires screen signatures, harness prefixes and local-command lists to come only from compiled `viola-agent-claude` ledger rows, never from runtime or upstream text; it names the harness prefixes as exactly four compiled literals matched on the prompt's raw start with no trim, the escaped cross-session form being the one escaped tag that classifies `harness` (a founder-ratified side effect). The local-command set W2 lists and any prefix W4 measures land as compiled literals. A measurement that calls for a fifth literal, a preface-tolerant match (the `Another Claude session sent a message:` hypothesis) or a trimmed match departs from that line's text: a P4 fork with the side effect shown, not an implementation choice. Whether the tag un-escape in `hook.rs` runs before or after `origin` classification is research's question; the plan requires the match on the raw start.
- **The `verify` children rule holds for every new probe.** security-plan §Threat Model Summary (Attack surface → Child process spawning and PATH resolution) and §Data Protection (At rest → Interactive probe dirs) require each interactive child to be a direct spawn (never a shell) under the R8 strip, its output capped at `MAX_FRAME` into a `Screen` fed under `catch_unwind`, no byte written into any dialog (CLI-native or the probe's own), a modal start killed with no key, nothing written by viola under `~/.claude`, and every probe dir 0700 and removed on every exit path. The plan enumerates four interactive children (Runs A to D) and what each is pasted (Run B: one bracketed paste of the compiled `PROBE_PROMPT`). A fifth run, or a further paste into an existing run (a typed local command, a long paste, tag-like text), changes that enumerated boundary, which the plan records as the founder's live rulings: it goes to P4 as a founder card. A local command that opens a picker or a CLI-native dialog can be ended only by the run's kill, never by a key (Esc included).
- **R8 identity floor: names only, never weakened.** security-plan §Secret Management (Storage → Production) requires the identity floor (`IDENTITY_FLOOR`, 11 names, both messaging variables among them) to be removed from the child whatever the persistent set says, and requires the strip, the registry reader and the logs to handle names only and never read a value. The identity-floor row's probe and its evidence (stamp, recorded fixture, `process-start` names) are therefore name-level; no stripped `CLAUDE*` value may reach a log, diagnostic, event, snapshot, stamp or fixture (security-plan §Bootstrap phases, `logging-redaction-wire`). Producing a cross-session prompt by letting `CLAUDE_CODE_MESSAGING_TOKEN` / `_SOCKET` through to the probed child, or by viola reading or forwarding either value, is outside the plan; security-plan §Input Validation (Configuration values row) requires an identity-floor name in `claude_env_keep` to have no effect.
- **The stamp gates on the whole row set, and only `verify` writes it.** security-plan §Security Anti-Patterns → Universal requires that no non-`null` dialog decision flows without a `viola verify` stamp for the child's CLI version, that no process other than `viola verify` writes `ledger/stamps.json`, and that `run`'s version gate reads it through `read_stamps_strict`; it states the stamp as the fourteen rows of `LedgerRow::ALL` (counter `/14`) and records the earlier partial-stamp gap (R2) as closed. Growing `LedgerRow::ALL` moves that count: the plan's intent is that a stamp short of the full row set reads `cli_verified:false`, so a stamp written at 14 rows must not keep a version verified once the set grows. Whether the row check and the stamp merge already read a 14-row stamp as unverified after the growth is research's question. The stamp's version is the version of the binary the probe ran (2.1.289 on PATH today); whether `verify` takes the version from the same resolved binary it spawns is research's question. The plan's "fourteen" / `/14` text is a wrap re-derivation.
- **`send`'s refusal order and bounds stay ahead of the new outcome.** security-plan §Input Validation (Paste text row; Channel frames row, `send` params) requires `validate_paste_text` to run in the wrapper's `send` before anything is typed, first in its refusal order and authoritative, after the closed `send` params check, with reject-never-strip. The local-command classification that yields `unconfirmable` sits after both; a local-command-shaped text carrying a refused control still ends `not-delivered` / `control-character`. The match classifies sent text against the compiled list and decides only the confirmation outcome; security-plan §Security Anti-Patterns → Code Patterns (R1) requires upstream and sent text to stay content, never a viola command or config.
- **Recorded fixtures are synthetic and scrubbed.** security-plan §Data Protection (At rest → Repository fixtures) requires probe prompts to be synthetic, every string and key scrubbed before any write, the whole recording refused (exit 1, nothing written) when a home path, absolute path, username or email-shaped token survives, a screen fixture to keep only rows holding a compiled signature literal, and the refusal to name the file and a closed code, never the content. The new rows' recordings (the long-paste wrapper, the tag-escaped prompt, a harness-prefixed `prompt`) ride that path. A cross-session `prompt` captured from a real overseer or worker session is non-synthetic content and may not be committed as a fixture (security-plan §Security Anti-Patterns → Data Protection).
- **Codes only on the external surface.** security-plan §Error Handling (External responses) and §Bootstrap phases (`logging-redaction-wire`, Scope) require CLI `--json` output, channel `error.data` and role log lines to carry codes and fixed messages; user content, the sent text included, goes only to `instances/<name>/diagnostics/` (0600). `unconfirmable` is a closed `detail` value, and its mirror line and any `send` log line carry a code or a compiled row id, never the sent text or a path.

## Patterns to follow
- Hook-payload measurement goes through the hidden `hook <event> --capture <DIR>` arm that only `viola verify`'s probe plugins register: `take(MAX_FRAME + 1)`, an exclusively claimed 0600 `captures/<Event>.<k>.json` under the 0700 `ledger/probes/<pid>/`, a drop guard removing the probe dir on every exit path (security-plan §Input Validation, Hook stdin row, Capture arm; §Data Protection, Probe captures). No new caller, flag or arm.
- Typed probe input is a compiled prompt delivered as one bracketed paste, sent only to an input box with no modal showing (security-plan §Threat Model Summary, Child process spawning; §Input Validation, Paste text row).
- Screen reads compare against compiled signature literals only; PTY output is capped at `MAX_FRAME` and fed under `catch_unwind` (security-plan §Input Validation, Child process output row and PTY output bytes row).
- `ledger/stamps.json` is written under its `.lock` at 0600 through `viola_state::fs::replace_private`, read through `take(MAX_FRAME + 1)` (security-plan §Data Protection, Code-bearing artefacts; §Authentication & Authorization, `~/.viola/` access control row; §Input Validation, Constants).
- Fake-agent replay of the new rows stays behind the test-only `fake-agent` feature, which `scripts/release-check.sh` refuses in a release artifact (security-plan §Dependency Security, CI integration, the `release` job).

## Anti-patterns to avoid
- NEVER type a byte into a dialog or picker from a `verify` child, and NEVER have viola write under `~/.claude`; a probe that cannot be measured without a key is not measured (security-plan §Threat Model Summary, Child process spawning; `.claude/rules/security.md` restates it).
- NEVER add a `config.json` key, `VIOLA_*` variable, CLI flag or a further test seam that switches off a control or lets a partial probe yield a verified stamp; a new env seam for the fake agent needs its own Decisions Log entry (security-plan §Security Anti-Patterns → Universal, the last entry). A subset or single-row `verify` mode, if research proposes one, must not write a stamp that reads verified.
- NEVER borrow or widen a dated exception: `send` stays under its own liveness-only gap, `verify`'s `update_stamps` under its stamps-read gap, and no new frame, reader or process joins either (security-plan §Security Anti-Patterns → Authentication, the dated-exceptions entry; §Authentication & Authorization, IPC client-side server verification row).

## Contract bindings
- **security ↔ architecture [CLI Version Compatibility] / the ledger:** the row set that gates `cli_verified` is stated in security-plan §Security Anti-Patterns → Universal as fourteen rows; the chunk's new rows re-derive that count and its row list there, together with the harness-prefix line in §Code Patterns if the measured set changes.
- **security ↔ the founder's `verify` rulings:** the four-children enumeration in security-plan §Threat Model Summary, §Data Protection and §Input Validation is ruling-backed; any added run, added paste or added dir, and any change to the accepted transcript residual (security-plan §Data Protection, Accepted risk — verify's trusted runs: its per-verify transcript count; a `/clear` probe's new session may add to it), is shown at P4.
- **security ↔ tests (fixtures and the CI canary scan):** the new rows' recordings and fake-agent scripts are bound by the fixture scrub (security-plan §Data Protection, Repository fixtures), and the new tests' homes pass obs-plan §9's `viola-harness secret-scan` against this plan's NEVER-log floor, the stripped `CLAUDE*` canaries included (security-plan §Secret Management, Secret scanning in CI).
- **security ↔ obs:** the `send` outcome's log fields and `process-start`'s `env_stripped_known` / `env_kept` are names and codes only; format and fields are obs's, the floor is security-plan §Bootstrap phases (`logging-redaction-wire`).
- **security ↔ the live-probe boundary:** the real `claude` runs only locally, `verify` in CI only against the fake agent, no Claude credential on a runner (security-plan §Threat Model Summary, Infrastructure → CI/CD).

## Acceptance criteria contributions
- (security) The harness prefixes and the local-command list are compiled literals in `viola-agent-claude` — a grep of the changed sources shows none built from runtime, config or upstream text, and the prefix match reads the prompt's raw start with no trim (per security-plan §Security Anti-Patterns → Code Patterns).
- (security) A home whose stamp lacks any row of the grown `LedgerRow::ALL` reads `cli_verified:false`: the hook prints nothing and `viola answer` exits 12 `unverified-cli`; `ledger/stamps.json` has no writer but `viola verify` (per security-plan §Security Anti-Patterns → Universal).
- (security) The identity-floor row's stamp entry, its recorded fixture and every log line hold names only; `viola-harness secret-scan` passes over the chunk's test homes, and every new `fixtures/claude/<version>/` file passes `--record`'s scrub with no `home-path` · `absolute-path` · `username` · `email` refusal (per security-plan §Secret Management, Storage → Production; §Data Protection, Repository fixtures).
- (security) A `send` of a local-command-shaped text carrying a refused control ends `not-delivered` / `control-character` with nothing typed, and the `unconfirmable` outcome's `--json` body, mirror line and log line carry no sent text and no absolute path (per security-plan §Input Validation, Paste text row; §Error Handling, External responses).
