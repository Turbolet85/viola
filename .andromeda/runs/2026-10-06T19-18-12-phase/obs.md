# obs extract

## Relevance
partial — no obs infrastructure is built here, but W2 moves a must-trace path (Scenario 2, confirmed `send`: the `unconfirmable` outcome and the `/clear` post-condition close) and W2 + W4 extend `viola verify`'s probes, whose lines, spawn pairs and stdout shape obs-plan fixes; obs tier is Standard (1) with Minimal-tier exporter carve-outs (per obs-plan §1 Obs Scope Summary), so depth is closed-enum log lines and static spans, no metrics pipeline.

## Constraints
- obs-plan §4 Scenario "Confirmed `send` (CL-1) from driver to readback" requires an `unconfirmable` send to log as `send-confirmed` with `confirmed:false` on the issued cursor — an `ok` outcome, not a `send-refused` — after its `send-issued`, with the `channel-request` / `channel-response` pair on both sides and the client's `process-exit{subject:"self", exit_code}` inside that scenario's closed exit set. At HEAD the scope reads a local command as `not-delivered` / `no-prompt-submitted`; which lines the wrapper writes today for that path, and which exit code the new outcome takes, is research's question.
- obs-plan §3 Trace context propagation (IPC boundaries → Send cursor on early refusals, Send ↔ channel link) requires the `unconfirmable` result to carry `cursor` like a success, every `send-*` line after `send-issued` to carry that cursor in `corr`, and every wrapper `send-*` line to carry `conn` (or `srv_conn`) plus `rpc_id`; `corr` is copied unchanged as a JSON number (per obs-plan §3 Log format JSON schema).
- obs-plan §4 Scenario "Confirmed `send`" → Cleanup names exactly two closes for `run.confirm_window`: the matching `prompt-submitted{origin:"driver"}` or window expiry. A `/clear` confirmed by SessionStart source `clear` plus a new `session_id` is a third close the plan's text does not name, and the plan carries no post-condition vocabulary at all — the span's attribute set (`window_ms`) and the close rule need a wrap-time amendment, and any new attribute must be a closed-enum or numeric value (per obs-plan §4 Span naming convention).
- obs-plan §8 Default-deny posture requires every logged field to be named in the §6 Additive field catalog and admitted by `schemas/diag-line.v1.json` (top-level `unevaluatedProperties: false`); a new `event` value needs an obs Decisions Log entry (per obs-plan §3 Log format JSON schema, §11 Logs). The §6 catalog's shared `send-issued` / `send-confirmed` / `send-refused` row lists `detail`; whether the schema's per-event list admits `detail` on `send-confirmed` (so a line could tell `unconfirmable` from a future `confirmed:false` cause) is research's question. The §6 refusal-detail list is the arch `RefusalReason` details verbatim, and `unconfirmable` is not one of them.
- obs-plan §4 Edge flows → "`verify` / `plugin install`" requires the dispatch span `cli.verify` with one `cli.verify_step` per step and `state.ledger_write` for the stamp; with `VIOLA_NAME` set, `process-start` / `process-exit` around exactly six child spawn pairs (`version-probe`, `verify-probe`, four `verify-pty-probe`), with no row text, prompt or path in any line; stdout as one `[NN/MM] <row id> <row words>  pass|fail` line per ledger row and the last line `stamped <version>  N pass  N fail`. New rows move `MM`; a probe that needs a PTY run of its own moves the plan's spawn count of six (the `subject` enum of §6 Boundary-call wrappers already closes on `verify-pty-probe`). Whether the new rows ride Runs A–D or add a run is research's question, and it decides whether obs-plan §4 / §6 need an amendment.
- obs-plan §8 PII Scrubbing (Data classification rules) classes prompt text as High: the local-command text, the long-paste body, the tag-like probe text and a cross-session `prompt` never reach a home-level process-log line — `pty.paste_write` records `text_bytes` and `paste_mode` only (per obs-plan §4 Scenario "Confirmed `send`"), and the hook-side unwrap / un-escape / prefix match in `hook.rs` logs codes only. The same table classes R8-stripped `CLAUDE*` values as Critical: the identity-floor row's probe may surface names only (`env_stripped_count`, `env_stripped_known`, `env_kept` on `process-start{subject:"claude-child"}`, per obs-plan §4 Edge flows E2), never a value, and no env map is passed to a span or event.
- obs-plan §10 Standard+ invariants → Deterministic emission requires events to key on hook events and `events.ndjson` offsets, never on screen content: the `unconfirmable` verdict and the `/clear` confirmation are decided from the ledger row and the SessionStart hook event, and no log line is derived from what the screen shows after a typed local command.

## Patterns to follow
- Every new line goes through `obs_event!` with explicit typed fields under `#[instrument(skip_all, name = "<area>.<operation>", fields(...))]` with a static snake_case span name (per obs-plan §4 Span naming convention, §8 Integration points item 1).
- A normal product outcome logs at `info`: `send-confirmed{confirmed:false}` is `info`, like a refusal; `warn` / `error` stay for the cases the level table names (per obs-plan §6 Log levels mapping).
- `corr`, `conn` and `instance` cross `run`'s std threads as explicit values set on each `obs_event!`, never recovered from span context — the confirm window's thread included (per obs-plan §3 Trace context propagation → Internal async boundaries).
- `verify` logs its child spawns at the call site as `process-start{subject}` / `process-exit{subject, child_exit_status, duration_ms}` pairs, and `run_bounded` itself stays unlogged; the hidden `hook --capture` arm stays uninstrumented (no obs init, no role or detail file, stderr empty, exit 0) for any new probe capture (per obs-plan §6 Boundary-call wrappers, §4 Edge flows).
- The send terminal state stays derivable from the log alone: `viola.send.outcome` counts `send-confirmed{confirmed}` / `send-refused{refusal,detail,side}` grouped by closed enums only (per obs-plan §5 Per-surface / per-path metrics, Metric label cardinality discipline).

## Anti-patterns to avoid
- NEVER log send text, a prompt, a ledger row's text, a stamp's contents or the ledger path in a home-level line, and NEVER a `CLAUDE*` value in any file, detail files included (per obs-plan §11 PII Scrubbing; §4 Edge flows Capability ledger).
- NEVER add a field outside the §6 catalog or an `event` value without a Decisions Log entry, and NEVER rename a tests field (per obs-plan §11 Logs, §11 PII Scrubbing).
- NEVER write through `print!` / `eprintln!` / `dbg!` outside the output modules that own human CLI output: the `[  ] unconfirmable` mirror line belongs to such a module, and telemetry never goes to stdout (per obs-plan §11 Logs).

## Contract bindings
- obs ↔ tests: the log format is test-plan §3's, reproduced as binding — obs aligns to tests, not the reverse (per obs-plan §3 Log format JSON schema); the changed `send_window_local_command_is_not_presumed_delivered` case and the new `unconfirmable` case assert on these `send-*` lines, and their homes must live under `target/e2e-home/` so G2, G4 and the secret scan read them (per obs-plan §9 Pipeline integration).
- obs ↔ tests: in CI `viola verify` runs only against the fake agent at recorded version 2.1.287 (`tests/cli_verify.rs`, harness `boot` step 4, the `stamped_home` fixture), with `verify` the only writer of `ledger/stamps.json`, and no obs gate depends on verify's own lines (per obs-plan §4 Edge flows). New rows change what that fake-agent verify must replay; the row count is tests-/arch-owned, obs owns only the line and stdout shape.
- obs ↔ security: the High / Critical classes and the secret scan are security's NEVER-log floor carried into obs; the scan's canary set is one per identity-floor name plus an unknown name, and the E2E inputs carry a tests-owned canary that may appear only in `detail-*.ndjson` (per obs-plan §8 Integration points item 6). The 11-name `IDENTITY_FLOOR` is recorded in obs-plan §4 Edge flows E2 as measured on the Windows host; an identity-floor row measured on the Linux dev host that reads a different set is a spec drift to raise, not to absorb.
- obs ↔ design: the readback words `open|read back|unable|unconfirmable` on `<viola-readback>` and the CLI mirror are design-owned; their process-log counterparts are joined by the send cursor in `corr`, `unconfirmable` ↔ `send-confirmed{confirmed:false}` (per obs-plan §4 Frontend observable boundary).
- obs ↔ architecture: the `send` result shape (`cursor` on success or `unconfirmable`) and the `RefusalReason` details are arch-owned and mirrored verbatim (per obs-plan §3 Trace context propagation; §6 `detail` code catalog).

## Acceptance criteria contributions
- A `send` of a ledger-listed local command with no measured post-condition leaves, in the wrapper's role file, `send-issued{corr:<cursor>}` followed by exactly one `send-confirmed{corr:<cursor>, confirmed:false, duration_ms}` carrying `conn` + `rpc_id`, and no `send-refused` for that cursor (per obs-plan §4 Scenario "Confirmed `send` (CL-1) from driver to readback"; §3 Trace context propagation)
- G4 reports zero schema-conformance failures and G2 zero `event:"panic"` lines over the chunk's test homes: every field on the new or changed lines is in the §6 catalog and `schemas/diag-line.v1.json`, with any catalog or schema change landing in this chunk (per obs-plan §8 Default-deny posture; §9 Gate commands; §10 Error budget)
- The secret scan passes with the canary absent from every home-level `diagnostics/*.ndjson` after a local-command send, a long paste and a tag-like paste; only `text_bytes` describes the text (per obs-plan §8 Integration points item 6; §4 Scenario "Confirmed `send`")
- A fake-agent `viola verify` with `VIOLA_NAME` set writes only closed-`subject` spawn pairs between its `process-start` / `process-exit`, with no row text, prompt or path, and prints one `[NN/MM]` step line per ledger row — the new rows included — ending in `stamped <version>  N pass  N fail` (per obs-plan §4 Edge flows → `verify` / `plugin install`; §6 Boundary-call wrappers)
