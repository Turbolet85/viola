# design extract

## Relevance
partial — the cli surface only (the `viola send` readback mirror gains its `unconfirmable` line, a `/clear` send closes on its post-condition, and `viola verify`'s step counter grows past fourteen rows); no web-spa file is in the chunk's surfaces, so no colour, type, spacing, radius or motion token is rendered here.

## Constraints
- design-system §Surface: cli → Component Patterns → 2 (`viola send`: the readback mirror) requires the `unconfirmable` outcome to print as one line led by the `[  ]` mirror and the word `unconfirmable`, on stdout with exit 0, in the field order and padding of that section's sample (the word padded to the readback-word column, two spaces between fields). Whether a writer for this line exists at HEAD is research's question (the scope says it is new).
- design-system §Brand Identity → Signature element requires `unconfirmable` to reuse the open drawing and never the filled one: on the CLI that is `[  ]`, never `[RB]` and never `[/ ]`. The word alone tells it from `open` (§Self-Validation Protocol → 2 states this is intended).
- design-system §Color Palette → Domain status colors, rows `Readback::read` and `SessionStartCause::clear`, require a `/clear` send to close as read back on its post-condition (a session-start with cause `clear`), not as a refusal and not as `unconfirmable`; on the CLI that is the `[RB] read back` line of §Surface: cli → Component Patterns → 2, carrying name, time and cursor.
- design-system §Color Palette → Semantic Colors classes `unconfirmable` as Warning, degraded but not refused: it is not an `unable` line, takes no refusal reason or detail, and §Surface: cli → Component Patterns → 2 lists `hint:` lines for refusals only, so no hint follows it.
- design-system §Surface: cli → Tokens requires CLI colour to be spent only on the `DIALOG` word and `stale` rows; the `unconfirmable` line, the read-back line and every `verify` row line carry no SGR at any colour depth, and the same section's Colour decision order requires the ASCII mirror to print in every human output (piped, `NO_COLOR`, `TERM=dumb`), with `--json` replacing it by the JSON document.
- design-system §Surface: cli → Component Patterns → 5 (`verify`) requires one static appended stdout line per ledger row in the step-counter form (`[NN/TT]`, row id, one fixed ASCII description, `pass` or `fail`) and a last summary line `stamped <version>  <n> pass  <m> fail`, with `fail` uncoloured. The section's "fourteen rows today" is its own dated count and it states the count grows as owning chunks land rows; this chunk's rows move TT on every line and the summary figure. Whether the counter's denominator is derived from the row set or is a literal is research's question.
- design-system §Surface: cli → Tokens → Streams requires results on stdout and context, refusals and hints on stderr: the `unconfirmable` line is a result (stdout), the `[  ] open` issue line stays stderr and TTY-only, and under `--json` the whole result is one document on stdout with no hint text (§Surface: cli → Exit-code phraseology, exit 0 row).

## Patterns to follow
- The readback mirror column: every `viola send` outcome line starts with a three-state bracket mirror and a padded phraseology word, then name and outcome fields (design-system §Surface: cli → Component Patterns → 2). The new line joins that column; it does not introduce a fourth bracket form.
- The step counter as the project's one progress pattern: static lines appended once, nothing redrawn in place (design-system §Surface: cli → Component Patterns → 5; §Brand Identity → Per-surface values, cli rows at 0.2 / 0.0). Each new row needs a row id and one fixed description sentence in the style of the dialog rows named there; the plan names no wording for the local-command, long-paste, tag-escaping, harness-prefix or identity-floor rows, so their descriptions are new text this chunk authors and the wrap reconciles into that section.
- Standard phraseology: short fixed lower-case words, no filler, no guessing (design-system §Brand Identity → Domain anchors, "Standard phraseology"). The `unconfirmable` line's last field is the fixed phrase of the sample, not text derived from what was sent.
- The printed word for a build whose stamp does not cover the row set is `<version> unverified-cli`, uncoloured, in the CLI column (design-system §Color Palette → Domain status colors, `CliVerified::false`; §Surface: cli → Component Patterns → 1). Whether a fourteen-row stamp reads so after the row count grows is research's question.
- A `verify` refusal for a recording that is not clean prints the fixed-message line naming the fixture file and a closed code, then its hint, never the content (design-system §Surface: cli → Exit-code phraseology, exit 1 row) — applies if this chunk records new fixtures.

## Anti-patterns to avoid
- Never print "done" or "success" without context, and never a green tick or cross prefix: an unconfirmed local command must not be dressed as delivered, and the read-back line says what was read back, by whom, at which cursor (design-system §Anti-Patterns → Per-Surface Bans → cli; §Anti-Patterns → Rejected Defaults, the optimistic "Sent" entry).
- Never a spinner, progress bar or in-place redraw for the longer `verify` run, and never colour, glyphs or cursor control under `--json`, non-TTY, `NO_COLOR` or `TERM=dumb` (design-system §Anti-Patterns → Per-Surface Bans → cli; §Motion → Hard limits).
- Never print upstream text, paths or pids in an error or hint, and never hardcode a width or wrap a line: a probe's row line and any new refusal stay fixed ASCII text (design-system §Anti-Patterns → Per-Surface Bans → cli).

## Contract bindings
- design ↔ architecture (`send` wire contract, [Delivery Confirmation]): the `[  ] unconfirmable` line is the human mirror of the `ok` payload with `confirmed:false`; the `--json` document's fields are architecture's, the line's shape is design-system §Surface: cli → Component Patterns → 2.
- design ↔ architecture / obs (event catalog, CL-1): design-system §Surface: web-spa → Component Patterns → 2 (Sources, Data dependency) requires the web readback box to draw `unconfirmable` from an outcome record for `ok` / `confirmed:false`, and `read` for a `/clear` send from a session-start with cause `clear` and a new session id. No web code is in this chunk; whether the chunk's `send` path must write that outcome record now, or it stays owed to CL-1, is research's question.
- design ↔ agent-claude (`hook.rs` harness prefixes): the prefixes decide `PromptOrigin::harness`, which design-system §Color Palette → Domain status colors prints as a whole lamp-off `prompt · harness` tape line. A prefix the classifier misses surfaces as a different origin word on the tape; nothing renders in this chunk.
- design ↔ tests (test-plan §6): the CLI lines above are exact-text surfaces; the test that pins a local command's outcome and any `verify` output assertion carrying the row count read against design-system §Surface: cli → Component Patterns → 2 and 5.
- design ↔ security (NEVER-log floor, error sanitization): design-system §Surface: cli → Component Patterns → 2 requires that a hint never quote the sent text or any upstream text; the same holds for the fixture-not-clean refusal.
- design ↔ a11y (use of colour): the state of every line in this chunk is carried by a printed word with no colour at all, which is the not-colour-alone binding of design-system §Surface: cli → Tokens.

## Acceptance criteria contributions
- (design) A `send` of a ledger-listed local command with no measured post-condition prints exactly one stdout line led by `[  ]` and the word `unconfirmable`, padded and ordered as the section's sample, exits 0, and prints no `unable` word and no `hint:` line (per design-system §Surface: cli → Component Patterns → 2)
- (design) A `/clear` send confirmed by its new-session post-condition prints the `[RB] read back` line with name, time and cursor on stdout, exit 0 — never `[  ]`, never `[/ ]` (per design-system §Color Palette → Domain status colors, rows `Readback::read` and `SessionStartCause::clear`; §Surface: cli → Component Patterns → 2)
- (design) `viola verify` prints one static ASCII stdout line per ledger row in the `[NN/TT]` step-counter form with TT equal to the new row count on every line, then the `stamped <version>  <n> pass  <m> fail` summary as the last stdout line, with no SGR on any of them (per design-system §Surface: cli → Component Patterns → 5)
- (design) The `unconfirmable`, read-back and `verify` lines carry no SGR byte and no non-ASCII character in any mode, and under `--json` the send result is one JSON document on stdout with no mirror and no hint text (per design-system §Surface: cli → Tokens, Colour decision order and Streams; §Anti-Patterns → Per-Surface Bans → cli)
