### error-capture-reporting#2.1 · values · errors · ## 7. Error Capture & Reporting · lines 15–21
- The panic hook only writes. The exit is decided at a catch site:
  - **Main-thread catch site (every role):** everything after `set_hook` (clap parse, init and role dispatch) runs inside one `std::panic::catch_unwind` in the root bin's `main`. An `Err` maps to the role's exit below, so no role ends through an uncaught unwind (Rust's default exit 101). The role is taken from argv before clap runs: the first argument that is neither a global flag nor a flag's value (for example `--home <path>`) and that names a role subcommand (`run`, `hook`, `mcp`; `role_of` in `src/main.rs` names `revive` beside `run`, except `revive` followed (after any `--home` pair) by `--list` before a `--`, which is `cli`; a `--list` after `--` is the child's word; any other verb is `cli`). `viola revive`'s start arm logs as process `run` (the `run-<name>.ndjson` role file and `run`'s detail sink), opened by the log setup it shares with `run` only after its instance check and its home-tree check (`check_home_tree`, through `checked_exe`) have passed; a refused check on the start arm, or a refused home tree on `viola run`, is a stderr pair (on a refused home tree the home pair, or the instance pair for an instance-level refusal) and exit 1 with no process log opened. `viola revive <name> --list` is `cli`, so its dispatch `Err` or panic reaches the `cli` catch site (`process-exit{detail:"internal-error"}`, exactly `error: internal error`); its refused strict-modes check opens no log and writes no line (the stderr pair, or under `--json` the `strict-modes-failed` document, exit 1), and its `no-session` is `process-exit{exit_code:1, detail:"no-session"}` in the caller's `cli-<VIOLA_NAME>.ndjson` under a name, with the stderr pair or the `no-session` document (chunk 2026-10-17-cli-machine-contract). So `viola --home <dir> hook stop` is still a `hook`, and a pre-init panic in it still exits 0. Reading `argv[1]` alone would misclassify that form as `cli` and exit 1 (D-28).
  - **Catch-site reach:** on Unix a home under a regular file is a strict-modes refusal with no line — `viola verify` exits 1 with the home pair, the frame verbs exit 21 with the instance pair — so it never reaches the `cli` catch site; on Windows such a path stats `NotFound`, the check skips it as absent, and the catch-site line `process-exit{detail:"internal-error"}` stands.
  - **`mcp` at the catch site:** the `mcp` role writes no self `process-exit` line: `internal_error_exit_line` (`src/obs.rs`) writes for `Run` and `Cli` only.
  - **`run` worker threads:** the PTY pump and handle-wait thread bodies each run inside `catch_unwind`. An `Err` is sent to `main`, which takes the `run` exit path below, because the session cannot continue without either thread. A worker panic that leaves `main` running with no `process-exit` is forbidden. A panic in one channel server connection worker is contained: the `channel.dispatch` `Drop` guard logs `channel-response{result_class:"error", error_code:-32603}`, the connection closes, and `run` continues. The vt100 feed thread (`src/run/gate.rs`, detached) is contained too: its `catch_unwind` wraps each feed and resize, a caught panic poisons the screen model and writes one `parse-rejected`, nothing is sent to `main`, and `run` continues; the ban above covers the PTY pump and the handle-wait thread.
  - **`-32603` proof:** no failpoint or counted panic drives a `-32603` in a scanned home; the unit layer holds that fault (`answer_a_panicking_dispatch_is_internal_error_and_closes`, `links_set_method_an_append_that_fails_is_internal_with_the_set_unchanged`).
  - **Unwinding is required:** every Cargo profile keeps `panic = "unwind"`. `panic = "abort"` turns every `catch_unwind` into an abort, so `hook` would die by SIGABRT instead of exiting 0. Gate G3 (§9) enforces this.
