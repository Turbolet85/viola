# obs extract

## Relevance
Partial. The chunk adds no product telemetry and no product-crate code. It builds a harness/script gate, and obs plan rules on harness output, the mutation verdict, the `target/agent-run/` capture, and gate verdicts-as-exit-codes apply to it.

## Constraints
- The gate entry lives in `viola-harness` (`crates/viola-e2e`) or `scripts/`. That places it under the print-ban exemption: `viola-e2e` omits `[lints] workspace = true`, carries its own `[lints.clippy]`, and the harness prints exactly one JSON document per command on stdout. A gate placed in any product member (root `viola` or a product `crates/viola-*`) would fall under the `print_stdout` / `print_stderr` / `dbg_macro` = `deny` ban. Per obs-plan §3 Bootstrap phases → obs-ci-gate-wire, and §11 Logs (print-macro bullet).
- The ubuntu mutation leg's verdict follows the §9 Mutation row. A leg is red at its own run when its unviable mutants outnumber its caught ones. Across legs, each mutant is judged only by the legs whose `#[cfg]`s compile its line, and a missed obs-code mutant on its compiling leg stays red. The local leg must reproduce CI's per-leg rule, not a looser one. Per obs-plan §9 Pipeline integration (Mutation row).
- `target/agent-run/chunk.diff` (the mutation leg's diff) is the one path exempt from the Critical-class secret scan, matched by exact path. Every other `target/agent-run/*` member is scanned, and a `chunk.diff` anywhere else is still scanned. If the gate writes new files under `target/agent-run/` in the Windows tree, they fall inside the CI scan scope and the `harness-<os>` upload. They must be codes-only or synthetic-input only. Per obs-plan §8 PII Scrubbing → Integration points item 6; §9 Step order and conditions, step 3.
- `mutants.out/` is never uploaded because its `outcomes.json` holds absolute argv paths and its `log/` holds test output. Only a `mutants-verdict-<os>.json` of repo-relative locations and outcomes is admissible by content. The Linux clone adds a new absolute-path source: `/home/<user>/…`, where the OS username is the only PII in scope. Nothing from that clone's `mutants.out*` or `target/` should be synced back into anything that reaches a CI artifact. Per obs-plan §8 item 6 ("Unscanned uploads, admissible by content"); §8 data-classification table (Absolute paths row).
- If the gate runs the integration/E2E tests, the zero-panic invariant still holds on the Linux run. A `hook` panic exits 0, so only G2 over home-level role files under `target/e2e-home/` shows it. The zero-schema-failure budget likewise needs G4 over the same homes. Whether the local gate runs G2 and G4 (and needs `AGENT_RUN_KEEP_HOMES=1` so homes survive until the gates read them) or relies on nextest exit alone is a question for P3. Per obs-plan §10 Always-required SLO invariant (Zero unlogged panics); §10 Error budget; §9 Step order step 1 and Gate commands G2/G4.
- CI identity and host metadata (WSL distro, clone path, run ids) must never be injected into product log lines. They belong only in the harness's own JSON document. Per obs-plan §9 CI-specific resource attributes; §11 CI (last bullet).
- CI runs `scripts/lint-probes.sh` (the fail-closed raw-`event!` grep plus the both-ways ban probes) only on the Linux lint leg. Whether that counts as a Unix-only red this gate should also catch is for P3 to settle against scope item 4 ("Unix tests + ubuntu mutation leg"). If the gate runs it, a `lint-probes.sh` failure is a build failure. Per obs-plan §3 Bootstrap phases → logger-stack-install / obs-ci-gate-wire bullet 1; §10 Build / deploy failure conditions.

## Patterns to follow
- Agent-readable verdicts. The gate's output is one machine-parseable JSON document with a typed exit code that a `jq -e`-style assertion can consume. No human-read log or summary decides pass or fail. Per obs-plan §11 CI ("NEVER use human-review-gated log analysis…"); §11 Universal.
- Fail closed on a missing tool. The G1/G3 pattern treats rg exit 2 (regex or I/O error) and 127 (missing binary) as failures, and G2 fails when no home-level file exists so an empty scope cannot pass. The gate's missing-distro, missing-tool and empty-scope cases should likewise be named failures, never a vacuous green. Per obs-plan §9 Gate commands (G1 bullet, G2 comment); §10 Build / deploy failure conditions.
- Scan-then-upload ordering and the exact-path `chunk.diff` exclusion are the precedent for any new capture file. Name it narrowly and keep the scan covering everything else. Per obs-plan §9 Step order and conditions steps 2–4.
- Merged-log consumption goes through `agent-run logs` / `status`. If the gate surfaces Linux-run diagnostics back to the Windows agent, it should reuse that ndjson shape rather than invent a new stream. Per obs-plan §3 Snapshot / paste-to-AI integration.

## Anti-patterns to avoid
- No retry-once on a red local leg or a flaky assertion. A retry masks real Unix reds, the same way `retries = 0` works in the tests. Per obs-plan §11 SLO ("NEVER add retry-once policies…"); §10 Cross-input parallel.
- Never judge the mutation leg by caught/unviable counts or by a human reading `mutants.out`. The verdict (the §9 Mutation row rules) plus the exit code is the signal. Per obs-plan §11 CI; §9 Pipeline integration (Mutation row).
- Never let a Linux-clone absolute path (`/home/<user>/…`) or `mutants.out` content reach a scanned or uploaded surface (`target/agent-run/*` in the Windows tree, or `mutants-verdict-*.json`). Per obs-plan §11 PII Scrubbing ("NEVER put paths or pids inside `detail` codes"); §8 item 6.

## Contract bindings
- **obs ↔ tests §3 (harness).** The gate's stdout (one JSON document per command) and typed exit follow the harness print-exemption contract that obs grants `viola-e2e`. Per obs-plan §3 obs-ci-gate-wire.
- **obs §9 Mutation row ↔ test-plan §10 Mutation gate.** The per-leg unviable rule and the compiling-leg union are cited from test-plan. The local ubuntu leg must follow the same verdict.
- **obs §8 item 6 ↔ security (absolute paths, Medium class).** The Linux clone's `/home/<user>` paths belong to the same scrub-required class. Whether the gate's JSON output or its `base` / verdict lines carry clone-absolute paths is a question for P3.
- **obs §9 Step order ↔ test-plan §3 `cleanup` step 6.** This binding applies only if the local gate runs E2E homes plus G2/G4: then `AGENT_RUN_KEEP_HOMES=1` keeps homes until the gates have read them, which conflicts with the bounded-cache requirement in scope item 3.

## Acceptance criteria contributions
- (obs) The gate entry prints exactly one JSON document on stdout and signals red/green through a typed exit code. A missing distro or tool, or an empty test/mutant scope, exits non-zero with a named cause, never 0. Per obs-plan §11 CI; §9 Gate commands (fail-closed G1/G2 pattern).
- (obs) The local ubuntu mutation leg goes red when any judged mutant is missed or timed out, or when unviable exceeds caught. It never goes green from counts alone. Per obs-plan §9 Pipeline integration (Mutation row).
- (obs) After a gate run, `git status` and the CI secret-scan scope in the Windows tree show no new `mutants.out*`, Linux `target/` content, or file with a `/home/` absolute path under `target/agent-run/` other than `chunk.diff`. Per obs-plan §8 item 6; §9 Step order step 3.
- (obs) If the gate lives outside `crates/viola-e2e` and `scripts/`, clippy `print_stdout` / `print_stderr` still pass on every product member, and the CI member-list assertion ("only `viola-e2e` lacks `workspace = true`") stays green. Per obs-plan §3 obs-ci-gate-wire.
