Partial. The chunk adds no UI surface. It matters to a11y only because the local Linux leg becomes the first place, before a push, where the Unix-only cli/tui output-discipline oracles run. If the gate also includes `run --browser`, the web-spa a11y leg runs there too.

## Constraints
- a11y-plan §3 A11y Assertion Harness Contract → Keyboard test harness → Tooling requires three tui boundary nextest cases on all three OS legs. One is the zero-viola-bytes clause. On Linux and macOS that clause is a byte-for-byte comparison with an unwrapped fake-agent run under the same outer PTY. On Windows it only checks that viola's own literals are absent. So the full byte-for-byte check is a Unix-only red that this Windows host cannot reproduce, and the local Linux "Unix tests" should run it. Research must find out whether the plain nextest run inside WSL `Ubuntu` already runs these cases, and under which `cfg`.
- a11y-plan §9 CI Integration → Per-pipeline-stage table, row "Unit / integration (all three OS legs)", and §10 SLO Invariants → Standard+ invariants require the CLI output-discipline invariants (P4, P6) to pass on all three OS legs. They report under `nextest-integration` / `nextest-e2e` locally and under `coverage` in CI, "under the tests' mutation gate where they live in crate tests". So the local ubuntu mutation leg's verdict also covers these tests.
- a11y-plan §6 Visual Design Verification → State color tokens → CLI equivalent requires viola to emit zero SGR of its own under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run`. A gate launched through `wsl -d Ubuntu -- …` from Windows passes a different TTY/`TERM`/`NO_COLOR` environment to the tests. Research must check whether those tests set their own environment or inherit the gate's.
- a11y-plan §3 → CI integration and §9 → Pipeline integration: `run --browser` exits 2 with `browser-linux-only` only on Windows and macOS. A missing Chromium is a `browser-missing` failure and is never skipped. If the gate runs the browser leg, WSL `Ubuntu` counts as Linux, so both rules apply unchanged.
- a11y-plan §3 → Structured violation JSON schema: `ci_run_id` / `git_sha` are absent on local runs. a11y rows go only to `e2e-web/test-results/a11y/`, never to `<home>/diagnostics/`. cli/tui failures surface only as nextest failures in `suites[].failures[]`. This only applies if the browser leg is in the gate.
- a11y-plan §11 A11y Anti-Patterns → Strategy: a green local gate is output-discipline evidence only. It is never a WCAG conformance claim for cli or tui. CI stays the verdict of record, which matches the chunk's Boundaries.

## Patterns to follow
- Typed, named harness refusals such as `browser-linux-only` (exit 2) and `browser-missing` (failure, never a skip) in the `run` JSON (a11y-plan §3 → CI integration; §9 → Pipeline integration). This is the precedent for the chunk's inferred typed failure when the distro or a tool is not provisioned.
- All test entry goes through the 5-command discipline of `scripts/agent-run.{sh,ps1}` (`boot`, `run`, `status`, `cleanup`, `logs`), with `gate --require …` judging `suites[]` (a11y-plan §3 → CI integration).
- cli/tui evidence reports only through nextest `suites[].failures[]`, with no a11y rows and no new suite (a11y-plan §3 → Structured violation JSON schema → cli / tui).

## Anti-patterns to avoid
- Adding a `suite` value (such as `a11y`) or a separate driver outside `scripts/agent-run.*` (a11y-plan §11 → CI).
- Treating `browser-missing`, or a missing toolchain, as a skip or a green (a11y-plan §11 → CI; §10 → Cross-input parallel, zero-skip / `retries: 0`).
- Retry-once policies, or parking tests with `test.skip` / `#[ignore]` to get the local leg green (a11y-plan §11 → SLO; §10 → Cross-input parallel).

## Contract bindings
- a11y ↔ tests: the cli output-discipline and tui boundary cases live in the tests' nextest suites and mutation gate (a11y-plan §10 Standard+ invariants; §9 Unit / integration row). The local Linux leg's suite choice (plain nextest or instrumented `coverage`, which the scope leaves to P3) decides which suite name reports them.
- a11y ↔ tests §9: `ci.yml` is the one push/PR workflow and the pin source (a11y-plan §9 → Platform). If the browser leg is included, the Playwright/Chromium pins must come from the same source as the chunk's cargo pins.
- a11y ↔ obs: the violation-row schema applies only if the gate runs `run --browser` (a11y-plan §3 → Structured violation JSON schema).

## Acceptance criteria contributions
- The local Linux gate run executes the three tui boundary nextest cases with the Linux/macOS byte-for-byte zero-viola-bytes comparison active, with 0 skipped. A planted byte-level failure goes red locally (per a11y-plan §3 → Keyboard test harness → Tooling).
- The CLI output-discipline cases (P4, P6) run and pass in the local Linux run, with no skips, and are covered by the ubuntu mutation leg's verdict where they live in crate tests (per a11y-plan §10 → Standard+ invariants).
- If the gate includes `run --browser`: a Chromium missing inside `Ubuntu` produces a typed `browser-missing` failure that stops the push, not a skip or a green (per a11y-plan §9 → Pipeline integration; §11 → CI).
