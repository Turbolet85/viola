# security extract

## Relevance
Partial. The chunk touches only test, harness, scripts and docs, with no product surface. Security applies in three places: supply-chain pinning of the local Linux toolchain, secret and PII hygiene in what the sync carries and what the gate emits, and keeping the Unix-permission preconditions that the Unix tests exercise.

## Constraints
- The Linux toolchain must be the exact `rust-toolchain.toml` channel, installed through rustup. It must never float, and no toolchain action or distro-packaged `rustc` substitutes for it. Per security-plan §Dependency Security (Pinning: "product toolchain is pinned exactly by `rust-toolchain.toml` … the host and CI both install it through rustup").
- Build inputs stay crates.io only and lock-resolved. The Linux build and test run must use the committed `Cargo.lock` (`--locked`). Tool installs from crates.io should follow the plan's established `cargo install --locked` form. The `[sources]` rule `unknown-registry`/`unknown-git = "deny"` sets the source policy. Per security-plan §Dependency Security (`deny.toml` additions `[sources]`; CI integration, nightly `fuzz` job's `cargo install --locked`).
- `ci.yml`, `rust-toolchain.toml` and `deny.toml` are pin sources and must stay read-only. If this chunk edits a workflow after all, these rules apply: SHA-pinned actions with version comments, `permissions: {}` / `contents: read`, event values only through `env:`, and zizmor green. Per security-plan §Dependency Security (CI integration) and §Security Anti-Patterns → Code Patterns (mutable-ref ban).
- The sync must not carry git-ignored local `--home` test directories, `.env` files, `ui/*.url` token files or `diagnostics/` from the Windows tree into the clone. `.gitignore` excludes local `--home` test directories so recorded state never lands in git, and the clone carries git history. Per security-plan §Security Anti-Patterns → Secrets ("NEVER commit `.env` files, local `--home` test directories …") and §Bootstrap phases (`secret-scanning-ci-gate`, `.gitignore` clause).
- The gate's output (JSON, typed failures, stdout/stderr) must hold to the NEVER-log floor. It must never carry `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` or any other R8-stripped `CLAUDE*` value. The Windows agent session that invokes the gate holds these values, so they must not be forwarded into `wsl` (for example through `WSLENV`) or echoed. Per security-plan §Bootstrap phases (`logging-redaction-wire`) and §Secret Management (Storage, R8).
- The local ubuntu leg's mutants verdict must keep the admissible-by-content shape: repo-relative source locations and outcomes only, never an absolute path, argv, log path or test output. The Linux clone root (`/home/<user>/…`) carries the OS username, which is the only PII in scope. Per security-plan §Bootstrap phases (`secret-scanning-ci-gate`, `mutants-verdict-<os>.json` bullet) and §Threat Model Summary (Data classification: operational metadata).
- The Unix tests assume Unix permission semantics. The Unix strict-modes checks (0700 home, 0600 files, `mode & 0o077 == 0` read rule, owner == euid) and the per-user 0700 socket directory (`$XDG_RUNTIME_DIR/viola/` on Linux, `/tmp/viola-<uid>/` fallback) need a real Linux filesystem. A drvfs `/mnt/d` checkout would break them, which is a security reason for the scope's "never `/mnt/d`". Research must answer two questions: whether the code already implements the socket-directory and strict-modes checks, and whether WSL2 Ubuntu's `XDG_RUNTIME_DIR` (set there, usually unset on GitHub `ubuntu-latest`) sends the local leg down a different socket-directory path than CI's. Per security-plan §Authentication & Authorization (IPC access control (Unix); `~/.viola/` access control).

## Patterns to follow
- Toolchain from `rust-toolchain.toml` through `rustup toolchain install`, the same way `ci.yml` does it (security-plan §Dependency Security, CI integration "Toolchains come from `rustup toolchain install` steps").
- Exact pins for tools whose version decides the verdict. CI pins cargo-nextest and cargo-mutants exactly, which matches the plan's "exact pins … for lock-pinnable" things. Keep minimum-floor syntax only for audit tools such as cargo-deny and zizmor, which this gate does not run (security-plan §Dependency Security, "Tool-version syntax" note).
- `AGENT_RUN_CHUNK_BASE` stays only a local override. The base is derived by the harness from git history and never from an event value (security-plan §Dependency Security, CI integration event-payload bullet).
- The artifact canary scan's scope rule, in case the gate captures under `target/agent-run/` and scans it: everything is scanned except the mutation leg's exact-path `target/agent-run/chunk.diff`, and matched bytes are never printed (security-plan §Secret Management, "Secret scanning in CI").

## Anti-patterns to avoid
- Floating or unpinned toolchain or tool versions (`stable`, latest `cargo install` without a version, apt `rustc`). The plan pins by exact version or SHA, never by a mutable ref (security-plan §Security Anti-Patterns → Code Patterns; §Dependency Security Pinning).
- Syncing ignored local state (test homes, `.url` token files, `.env`) or writing any R8 `CLAUDE*` value into gate output or the clone (security-plan §Security Anti-Patterns → Secrets).
- A sync form that opens a TCP listener (for example `git daemon`, an rsync daemon or an SSH server in the distro). It would expose the working tree, including uncommitted content, to every local user outside the plan's same-OS-user controls. Prefer non-listening transports. The plan's listener ban is written for viola itself; this applies its spirit to the tooling (security-plan §Security Anti-Patterns → Universal, listener ban).

## Contract bindings
- CI security gate ↔ tests §CI Integration: the local gate is a pre-push filter only. The ubuntu `supply-chain` job (cargo deny, fuzz lockfile audit, ban probes, zizmor) and the `secret-scan` step stay CI-only and remain the verdict of record. The local gate must not be presented as covering them (security-plan §Dependency Security, CI integration; §Secret Management, Secret scanning in CI).
- Obs §9 canary scan ↔ harness capture: if the gate writes into `target/agent-run/`, those files fall under the obs-owned scan classes and the `chunk.diff` exclusion (security-plan §Bootstrap phases `secret-scanning-ci-gate`).
- The PII floor ↔ the harness verdict JSON contract, which must stay repo-relative (security-plan §Bootstrap phases `logging-redaction-wire`, operational-metadata bullet).

## Acceptance criteria contributions
- The provisioning step asserts that the Ubuntu rustc, cargo-nextest and cargo-mutants versions equal `rust-toolchain.toml` / `ci.yml:166`. Any mismatch or missing tool is a typed, named failure, not a pass. The Linux run uses `--locked` (per security-plan §Dependency Security, Pinning).
- A planted git-ignored file in the Windows tree (for example a dummy local `--home` test directory holding a `ui/1.url`) is absent from the Linux clone after sync, while a dirty tracked file reaches it (per security-plan §Security Anti-Patterns → Secrets).
- Run the gate with a canary value in `CLAUDE_CODE_MESSAGING_TOKEN` in the invoking Windows env. The gate's stdout, stderr and JSON output contain 0 occurrences of the canary, and the value is not visible in the Ubuntu run's environment (per security-plan §Bootstrap phases, `logging-redaction-wire`).
- The local ubuntu leg's verdict JSON contains 0 absolute paths (grep for the clone root, `/home/` and `/mnt/` = 0). Every source location starts with a repo-relative crate path (per security-plan §Bootstrap phases, `secret-scanning-ci-gate`).
