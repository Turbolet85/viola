# security extract

## Relevance
relevant — part A changes how a code-bearing artefact (`bin/<key>/viola(.exe)`, and possibly `plugin/<key>/`) is written under the home's integrity controls; part B is a build measurement whose security tie is the content-hash key and the release gate.

## Constraints
- The fix for the absent-copy race must keep hash-before-reuse unchanged: a present `bin/<version>-<hash>/viola(.exe)` is re-hashed (SHA-256, truncated to 16 hex, never FNV / `DefaultHasher`) before reuse, a mismatch refuses the start (exit 1), and a copy that fails the check is never run or overwritten. A concurrency fix may not treat "another start just wrote it" as a reason to skip the re-hash, and may not resolve a mismatch by replacing the file (per security-plan §Data Protection, Files (`~/.viola/`), code-bearing artefacts detail; per security-plan §Security Anti-Patterns › Data Protection).
- Every write the fix adds or changes (the pinned copy, a temp file, any lock sibling or marker) goes through the owner-only write discipline: mode set explicitly before any byte is written, never the umask, directories 0700, files 0600, the pinned `viola` the only 0700 file and never group- or world-writable (per security-plan §Authentication & Authorization, `~/.viola/` access control; per security-plan §Security Anti-Patterns › Data Protection).
- `plugin/<key>/` stays rewritten whole at every start, never trusted as an existing copy; the only accepted failed replace is `replace_private_shared`'s, which counts as done only when the file already holds exactly the rendered bytes. Any fix for a concurrent reader of `hooks.json` / `.mcp.json` keeps both rules (per security-plan §Data Protection, Files (`~/.viola/`), code-bearing artefacts detail; per security-plan §Security Anti-Patterns › Data Protection).
- `run`'s and `revive`'s starts hold the home tree, `bin/<key>/` and the pinned `viola(.exe)` included, to the strict-modes check before the wrapper log opens. The pin path may not move a create, a mode set or a write ahead of that check, and a refusal still writes nothing. Whether `verify`'s `pin_exe` call sits after its own `check_home_tree` in the code is research's question (per security-plan §Threat Model Summary, Filesystem state vector, boundary-filesystem detail).
- The hook, MCP and statusline exec-form `command`s keep naming the absolute pinned `bin/<version>-<hash>/viola(.exe)` path. A race fix may not point a hook at a temp copy, an alternate path or a PATH lookup to dodge a write in flight (per security-plan §Security Anti-Patterns › Universal).
- On Windows x64 the ConPTY companions' write-if-absent stays never-overwrite, with the `FILE_SHARE_READ`-only held handle until the spawn. A companion that fails its check is left as found, and a failed sideload stays silent: no refusal, no exit change, no terminal byte. Any Windows wait the exe's arm borrows from `pin_companions` keeps all three (per security-plan §Security Anti-Patterns › Data Protection; per security-plan §Security Anti-Patterns › Universal).
- Part B measures through the release build of `scripts/release-check.sh` (`cargo build --release --locked --bin viola`, judged on its own `compiler-artifact` records), with the toolchain pinned exactly by `rust-toolchain.toml`. Any build change proposed on the measurement's basis (a linker flag, a path remap, a profile key) keeps `--locked`, the C-building-crate ban and the test-only-feature refusal (per security-plan §Dependency Security, CI integration; per security-plan §Dependency Security, Pinning).

## Patterns to follow
- `viola_state::fs::replace_private` / `replace_private_shared`: a tempfile `persist` whose mode is set before any byte, and a failed replace accepted only when the bytes on disk equal the rendered bytes (per security-plan §Data Protection, code-bearing artefacts detail).
- `pin_companions`' Windows write-if-absent: it waits out `ERROR_SHARING_VIOLATION`, then re-hashes in full through a held `FILE_SHARE_READ`-only handle until `spawn_child` returns. It is the model for closing a write-versus-exec window without overwriting (per security-plan §Data Protection, code-bearing artefacts detail, the `conpty/` row).
- Single-writer state under a `.lock` sibling at 0600, as `ledger/stamps.json` is written under its `.lock`. Whether the pin write should take one is research's question (per security-plan §Data Protection, code-bearing artefacts detail).
- The fixed-message refusal: a pin mismatch or failure crossing to the user names no absolute path, pid or upstream text (per security-plan §Error Handling, External responses).

## Anti-patterns to avoid
- Never reuse a pinned exe without re-hashing it. Never key it on a non-cryptographic hash. Never overwrite or delete a code-bearing copy that fails its check (per security-plan §Security Anti-Patterns › Data Protection).
- Never let an exec-form `command` resolve `viola` through PATH, or through anything but the absolute pinned path (per security-plan §Security Anti-Patterns › Universal).
- Never widen the race window with a new environment read or seam (a pin-delay knob for the two-sided witness, say) without its own Decisions Log entry, under `cfg(feature = "fake-agent")` only and absent from every release build. No such seam may switch off a control (per security-plan §Security Anti-Patterns › Universal).

## Contract bindings
- security ↔ tests: the two-sided race witness (the unstamped two-instance harness boot, Path 7, or a narrower concurrent-pin control) must also show the hash-mismatch refusal and the 0700 mode holding under concurrency; the test-plan harness (`scripts/agent-run.*`) owns the rig.
- security ↔ obs: any new pin-wait or race-retry event goes through `obs_event!`. Under security-plan §Error Handling and §Security Anti-Patterns › Logging it carries no absolute path, so obs-plan's event catalog owns its shape.
- security ↔ arch: the `pin::pin_key` key (`<VERSION>-<16 hex>`) names both `bin/<key>/` and `plugin/<key>/`, so a non-reproducible rebuild keys a second pinned tree. Which readers key on it is arch's directory-tree contract, and research's to read.
- security ↔ tests CI: the per-OS `release` job (`scripts/release-check.sh` and its `--probe`) and `cargo deny check` are the gates any part-B build change must keep green.

## Acceptance criteria contributions
- After the fix, a present `bin/<key>/viola` whose bytes differ from `<hash>` is still refused (exit 1) and left byte-for-byte as found, on a single start and on two concurrent first starts (per security-plan §Data Protection, code-bearing artefacts detail).
- After two concurrent first starts on a fresh Unix home, the pinned `viola` reads 0700 with no group or other bit, and any lock, temp or marker file the fix adds reads 0600 inside a 0700 directory (per security-plan §Security Anti-Patterns › Data Protection).
- Every exec-form `command` in the written `plugin/<key>/hooks/hooks.json`, `.mcp.json` and the Unix `instances/<name>/settings.json` still names the absolute pinned path after the fix (grep verifies) (per security-plan §Security Anti-Patterns › Universal).
- `cargo deny check` passes and `scripts/release-check.sh --probe` reads 5/5 refused with a clean control. Any added test seam is `cfg(feature = "fake-agent")`-only and is absent from the release build's artifact records (per security-plan §Dependency Security, CI integration).
