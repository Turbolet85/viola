- (.andromeda/architecture-detail/cross-cutting-patterns.md:9) The concurrency fix must keep the pin in its place in `run`'s start: after the home is canonicalised and the collision check, before the endpoint bind. It must not move the pin ahead of the canonicalisation or past the bind.
  > `run`'s start canonicalises the home after its wrapper log has created it, before the collision check, the pin and the endpoint bind.
- (.andromeda/architecture-detail/cross-cutting-patterns.md:9) The pinned copy and the plugin folder are per home, not per instance. So the race is two starts on one home, and the fix and its witness must key on the home's `bin/<key>/` and `plugin/<key>/` (the canonical home), never on an instance.
  > `viola run --home <dir>` passes the home to the child only through `VIOLA_DIR`, so the pinned copy, plugin folder, endpoint hash, logs, `budget.json` and ledger stamps all follow it.
- (.andromeda/architecture-detail/cross-cutting-patterns.md:9) Per-test homes are the isolation point. The two-sided witness must put its two concurrent first starts in ONE fresh, unstamped test home of its own, so it reaches the shared-home race without sharing a home with any other test.
  > This is the isolation point for tests: each test runs in its own home, and that home's `ledger/stamps.json` can stamp the fake agent's reported version.
- (.andromeda/architecture.md:403) No runtime environment variable or `config.json` key may choose, switch or tune the pin's concurrency handling (a wait bound, a retry or a lock), and no dependency or feature added for it may read one. Any build-side change from measurement B stays outside the product's runtime reads.
  > There are no secrets in v1, and environment variables are not a configuration channel: a dependency or feature that reads one breaks this rule like a direct read does.
- (.andromeda/architecture.md:412) The pin's concurrency fix runs on `run`'s start path and in `verify`. It must use std threads and blocking I/O, with no runtime and no async primitive in `viola-state` or the root bin's start.
  > **Tokio containment.** New code on the `run`, `hook`, `send` or channel-server paths uses std threads and blocking I/O. Only `viola-mcp` may build a runtime.
- (.andromeda/architecture.md:413) The absent-copy write of `bin/<key>/viola(.exe)` and the per-start rewrite of `plugin/<key>/` must stay atomic replacements. Any lock the fix introduces for the pin must be a `.lock` sibling of the guarded file (`<name>.lock`), never a lock on the exe or a directory itself.
  > **Crash-safe disk writes.** Append-only logs use one `write` per line. Mutable files are replaced atomically. Every guarded file has its own `.lock` sibling.
- (.andromeda/architecture.md:414) Anything the fix records (a waited-out concurrent pin, a lost race) must go only to the role's codes-only process log under `diagnostics/`, never to the terminal or stderr of `run`, `hook` or `mcp`, and must carry no path.
  > While the child runs, `run` writes nothing to the terminal except the child's own output, because the terminal carries the child's screen. Every role's codes-only process log goes to its home-level role file under `diagnostics/`: `run-<name>`, `hook-<name>`, `mcp` or `cli-<name>` `.ndjson`. Content-bearing detail belongs only in the instance's `diagnostics/detail-<role>.ndjson`.
- (.andromeda/architecture.md:420) Any per-OS arm of the fix (the Unix exec-vs-write race, or a Windows `ERROR_SHARING_VIOLATION` wait on the exe like `pin_companions`') must compile and be tested on its own CI runner. Windows is read on the CI runner only.
  > Every OS-specific branch compiles and is tested on its CI runner.
