## Relevance
partial — Part A changes `viola run`'s start (the tui passthrough boundary) and `viola verify`'s pin step (a cli verb); Part B (two clean release builds compared by file and section) is a build measurement with no UI surface and is out of this domain.

## Constraints
- a11y-plan §1 A11y Scope Summary (tui surface) requires that viola write zero terminal bytes of its own across a `viola run` start, a passed `viola revive` start included, and that its diagnostics for `run` go to `diagnostics/`, never to the terminal: whatever the race fix adds to `pin_bytes` / `pin_exe` (a wait, a retry, a same-bytes acceptance, a lost-race reading) prints nothing to the outer PTY. Whether the current absent-copy arm already writes nothing on its failure path is research's question.
- a11y-plan §8 Cognitive Accessibility › Timeout extensions requires that every time bound viola holds fall on the driver, the user's own command or viola's own child, never on the human. Any bounded wait the fix adds to the start, for example on the Windows `ERROR_SHARING_VIOLATION` shape `pin_companions` already waits out, must be a bound on viola's own start that blocks, refuses or delays no human keystroke.
- a11y-plan §11 A11y Anti-Patterns › Keyboard requires that no human keystroke in `viola run`, or in a start a passed `viola revive` made, be blocked, refused or delayed past the current atomic paste. A concurrent first start whose pin wait overlaps a live sibling instance must leave that sibling's keystroke path untouched.
- a11y-plan §8 Cognitive Accessibility › Error recovery requires that a `viola run` / `viola revive` start refusal print the fixed `unable` / `hint:` pair (`hint:` the last stderr line, stdout empty, exit 1, no line written, no child), and that a `viola verify` refusal print the home-state pair with no step line or summary. If the fix adds a start refusal (for example, a lost race that finds different bytes at `bin/<key>/viola`), it takes that form. Whether the existing pin-mismatch refusal already does is research's question.
- a11y-plan §11 A11y Anti-Patterns › Cognitive requires that a stack trace or bare kernel error (for example the hypothesised `ETXTBSY`) never be the only error text on the CLI, and that a kebab-case code never appear without the plain word `unable`.
- a11y-plan §8 Cognitive Accessibility › Plain language requires that every fixed CLI string be pinned by trycmd or by literal, so a new or changed start or verify refusal text fails CI until its pinned string is updated on purpose.
- a11y-plan §11 A11y Anti-Patterns › Strategy requires that no WCAG conformance claim rest on the race witness or the boundary cases: they are output-discipline stand-ins only.

## Patterns to follow
- Per a11y-plan §3 Keyboard test harness, each start variant has its own zero-viola-bytes reading (`passthrough_with_a_statusline_source_adds_no_viola_bytes` in `tests/tui_passthrough.rs`, the revive reading in `tests/chaos_revive.rs`). On Linux and macOS the outer-PTY stream is compared byte for byte with an unwrapped fake-agent run. On Windows the check is that viola's own literals are absent, because ConPTY emits bytes of its own. A concurrent first-start reading would take the same shape.
- Per a11y-plan §8 Cognitive Accessibility › Error recovery, `run_refuses_a_widened_home_tree_before_its_log` (`tests/run_cli.rs`) pins a start refusal by the `HOME_PAIR` / `INSTANCE_PAIR` literals with stdout empty, no line and no child. A new pin refusal follows that literal-pinned form.
- Per a11y-plan §9 CI Integration, CLI and TUI boundary cases run inside the per-OS `test` job's single `coverage` suite on all three OS legs, judged by `gate --require coverage,doctest`.

## Anti-patterns to avoid
- Per a11y-plan §11 A11y Anti-Patterns › CI: never add a `suite` value or a separate driver outside `scripts/agent-run.* run` for the race witness.
- Per a11y-plan §11 A11y Anti-Patterns › SLO: never use a retry-once policy. A concurrent-start witness that passes only on a re-run masks the race, which parallels the tests' `retries: 0`.
- Per a11y-plan §11 A11y Anti-Patterns › Motion and › Visual: never add a spinner, progress redraw or SGR while a start waits out a concurrent pin.

## Contract bindings
- tui boundary ↔ tests harness: the zero-viola-bytes and keystroke-unblocked clauses are nextest cases inside the `coverage` suite on the three OS legs (a11y-plan §3 Keyboard test harness · §9 CI Integration ↔ test-plan §3 harness).
- terminal output discipline ↔ obs: start diagnostics, including any pin-race reading, go to `diagnostics/` / the process log, never to the terminal (a11y-plan §1 A11y Scope Summary tui surface ↔ obs-plan §6 event catalog).

## Acceptance criteria contributions
- (a11y) If the fix adds a wait or lost-race path to the start, an outer-PTY case over that path, with `viola-fake-agent` as the child, finds none of viola's own literals (`unable`, `hint:`, diagnostic text) in the stream on all three OS legs (per a11y-plan §3 Keyboard test harness)
- (a11y) Any start or verify refusal the fix adds or changes exits 1 with the fixed `unable` / `hint:` pair, `hint:` last on stderr and stdout empty, pinned by literal; no raw OS error or stack trace is the only text (per a11y-plan §8 Cognitive Accessibility › Error recovery)
- (a11y) The two-sided race witness runs inside the `coverage` suite with no retry and no new suite value, and is red before the fix and green after it on the same rig (per a11y-plan §10 SLO Invariants & A11y Budgets)
