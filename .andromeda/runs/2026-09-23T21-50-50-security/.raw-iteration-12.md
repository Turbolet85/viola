## Patches

### Patch 1: Unix strict-modes check covers plugin subfolders
**Reason:** Dimension 5, the "integrity of `~/.viola/`" elevation. `plugin/<version>-<hash>/hooks/` and `.claude-plugin/` hold `hooks.json` / `plugin.json` but are not on the Unix check list.
**Old:**
```
the `bin/<version>-<hash>/` and `plugin/<version>-<hash>/` folders the process uses or writes, or a trusted file itself
```
**New:**
```
the `bin/<version>-<hash>/` and `plugin/<version>-<hash>/` folders the process uses or writes (including the plugin folder's `hooks/` and `.claude-plugin/` subfolders, which hold `hooks.json` and `plugin.json`), or a trusted file itself
```

### Patch 2: Windows strict-modes check covers plugin subfolders
**Reason:** Dimension 5. The Windows check says each directory is checked separately because of bypass-traverse, but the list leaves out the plugin subfolders. A writable `hooks/` lets another user swap `hooks.json` after the atomic rewrite.
**Old:**
```
the `bin/<version>-<hash>/` and `plugin/<version>-<hash>/` folders the process uses or writes, and the trusted files themselves
```
**New:**
```
the `bin/<version>-<hash>/` and `plugin/<version>-<hash>/` folders the process uses or writes (including the plugin folder's `hooks/` and `.claude-plugin/` subfolders), and the trusted files themselves
```

### Patch 3: Decisions Log companion for plugin subfolder coverage
**Reason:** Output Protocol rule 5. Patches 1 and 2 change the boundary mechanism of the `~/.viola/` integrity control.
**Old:**
```
because a file can carry an explicit, non-inherited ACE that the directory checks do not see.
```
**New:**
```
because a file can carry an explicit, non-inherited ACE that the directory checks do not see. On both OSes the check also covers the plugin folder's `hooks/` and `.claude-plugin/` subfolders. `viola run` rewrites `hooks.json` and `plugin.json` into them atomically, and the replacement file keeps its own mode or ACL, so a writable subfolder would let another user replace them after the rewrite (code execution on every hook event).
```

### Patch 4: anyhow chains on stderr must not carry value-quoting serde sources
**Reason:** Dimension 1, obs/error floor consistency. "anyhow chains stop at the `viola` bin's human-mode stderr" lets a serde_json or serde_path_to_error source, whose `Display` quotes input values, put tool `input` or prompt text on stderr. The consolidated NEVER-log floor forbids that.
**Old:**
```
  - anyhow chains stop at the `viola` bin's human-mode stderr.
```
**New:**
```
  - anyhow chains stop at the `viola` bin's human-mode stderr. A chain printed there never includes a serde_json or serde_path_to_error source, or any other source whose `Display` can quote upstream text (serde errors quote the offending value). Map it to a fixed message before it joins the chain, and write the full error only to `instances/<name>/diagnostics/` when an instance is resolved (NEVER-log floor, `logging-redaction-wire`).
```

### Patch 5: § Logging ban covers stderr anyhow chains
**Reason:** Dimension 1 and the Anti-Patterns single source of truth. The ban lists Problem Details, MCP and `error.data`, but not the human-mode stderr chain, which is the one sink the plan explicitly routes anyhow chains to.
**Old:**
```
- NEVER echo serde_path_to_error drift reports or anyhow chains into Problem Details `detail`, MCP `structuredContent` or channel `error.data`.
```
**New:**
```
- NEVER echo serde_path_to_error drift reports or anyhow chains into Problem Details `detail`, MCP `structuredContent` or channel `error.data`, and NEVER print an anyhow chain to stderr that still contains a serde_json or serde_path_to_error source (its `Display` quotes input values such as tool `input`).
```
