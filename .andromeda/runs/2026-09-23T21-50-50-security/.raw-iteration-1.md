**Dim 2: Threat → Control Traceability (high)**

**Dim 3: Tool Anchoring (high)**

- External CLI floors use `>=` in Dependency Security, Bootstrap and the Decisions Log. OK.

**Dim 4: GUI Credential Lifecycle (high)**
- Confirmed the anchor. The plan says cookies are not port-scoped but never draws the leakage conclusion to other users' loopback servers. Patch 5 adds the conclusion and the page-side limit (CSP `'self'`/`'none'`). Patch 15 records the residual risk.
- Exchange failure: constant-time comparison, the 401 on a wrong `?t=`, and no-store on the failure response are all unstated → Patch 5.
- The fate of a stale `.url` after a crash is unstated → Patch 6.

**Dim 5: Tier Calibration / Elevation Coverage (high)**
- Confirmed the anchor.
  - "Windows: user-only DACL" is false for the default home.
  - There is no Windows startup check equivalent to strict-modes, although four other sections and the Universal ban treat that check as cross-OS.
  - → Patches 3 and 4, plus companion Patch 17.
- The same "user-only DACL" error repeats in Secret Management and the Token row → Patches 5 and 18.
- Over-engineering and SKIP markers: acceptable, no patch.

**Dim 6: Anti-Pattern Centralisation (medium)**
- The GUI output-encoding bans are missing from § API → one-line fix in Patch 19.
- `X-Forwarded-For` was filler; Patch 19 reframes it as "no access decision on client address".

**Dim 7: API Hardening (medium)**
- There is no connection or SSE-stream bound and no accepted risk for either → one-line change in Patch 20 plus the accepted risk in Patch 15.
- The compression predicate and Host edge cases are deferred.

### Patch 3: Windows startup home-integrity check (strict-modes equivalent)
**Reason:** Dim 5. The "integrity of `~/.viola/`" elevation has only a creation-time control on Windows, the primary host. Four sections and the Universal ban assume a cross-OS strict-modes check.
**Old:**
```
**Windows:** `%USERPROFILE%` inheritance (user + SYSTEM + Administrators) is accepted. A `--home` outside `%USERPROFILE%` gets an explicit protected user + SYSTEM DACL at creation (via windows-sys), or is refused if one cannot be set.
```
**New:**
```
**Windows:** `%USERPROFILE%` inheritance (user + SYSTEM + Administrators) is accepted. A `--home` outside `%USERPROFILE%` gets an explicit protected user + SYSTEM DACL at creation (via windows-sys), or is refused if one cannot be set. **Windows strict-modes check:** at the same four entry points (`run`, `ui`, `mcp`, `hook statusline`), read the owner and DACL of the home, `instances/<name>/`, `bin/` and `plugin/` (windows-sys `GetNamedSecurityInfoW` + `GetAce`). Ignore inherit-only ACEs. Refuse when the owner is not the user SID or Administrators, or when any allow ACE grants write, delete, `WRITE_DAC` or `WRITE_OWNER` to a SID other than the user, SYSTEM or Administrators (for example `Users`, `Authenticated Users`, `Everyone`). The outcomes match Unix. This covers pre-existing and later-modified homes, not only creation.
```

### Patch 5: Exchange failure, no recovery shortcut, cross-port cookie exposure (Token row)
**Reason:**
- Dim 4: constant-time `?t=`, the wrong-token outcome, headers on the failure response, the no-reprint boundary and the cross-port leakage conclusion are all unstated.
- Dim 5: the false "user-only DACL" phrase appears here too.
**Old:**
```
(file 0600, dir 0700 on Unix; the home's user-only DACL on Windows) and printed once to stderr at launch. **Exchange:** `GET /?t=<token>` validates the token, answers `Set-Cookie: viola_<port>=<token>; HttpOnly; SameSite=Strict; Path=/` with no `Max-Age` (a browser-session cookie), then redirects 303 to `/` so the token leaves the URL. **Cookie name:** includes the port, because cookies are not port-scoped and two `viola ui` launches on different ports must not overwrite each other.
```
**New:**
```
(file 0600, dir 0700 on Unix; on Windows the home's DACL per the `~/.viola/` access control row) and printed once to stderr at launch. **Exchange:** `GET /?t=<token>` compares the token with `constant_time_eq`. On a match it answers `Set-Cookie: viola_<port>=<token>; HttpOnly; SameSite=Strict; Path=/` with no `Max-Age` (a browser-session cookie), then redirects 303 to `/` so the token leaves the URL. On a mismatch it answers 401 `urn:viola:problem:unauthorized`, sets no cookie and does not redirect. The security headers, including `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, apply to that failure response too. `/` without `?t=` serves the ungated page. **No recovery shortcut:** no route reprints or re-issues the token. The page, the 401 `detail` and every other error never contain the token, the launch URL, or the `.url` path or contents. A lost cookie or launch line is recovered only from the stderr launch line, from the 0600 `.url` file, or by restarting `viola ui`. **Cookie name:** includes the port, because cookies are not port-scoped and two `viola ui` launches on different ports must not overwrite each other. **Cross-port exposure:** for the same reason, the browser also attaches `viola_<port>` to requests for any other `127.0.0.1` port, including a server run by another local OS user. The viola page itself never issues such requests (CSP `connect-src`/`img-src` `'self'`, `form-action 'none'`), so the cookie reaches another port only when the user navigates there directly while the browser session lives. This residual exposure is an accepted risk (see the Decisions Log).
```

### Patch 15: Accepted risks: PATH `claude`, cross-port cookie, local availability (Decisions Log companion)
**Reason:**

**Old:**
```

```
**New:**
```
  - `~/.viola/` content is plaintext by design.
  - `claude` for `claude agents --json` is resolved from the calling process's PATH (same-user trust). A planted `claude` can at most inject display rows into `list`, the MCP `list` tool and `/api/sessions`. Those rows are never a `ViolaName` or `target` and are rendered as text only.

The impact is availability of the human's view and disk only, with no confidentiality or integrity impact.
