## Threat Model Summary

_[ALL tiers — VERBATIM copy from threat-assessment.md]_

**Security tier:** `Minimal (0), with targeted elevations for the local privilege boundary`
_Justification: viola is a local-only, single-user tool. It has no accounts, no public network listener, no database, no stored credentials and no regulated data (Sections 1, 3, 4, 5), which rules out Standard's user-account and HTTPS concerns and Hardened's compliance drivers. It still goes beyond a plain Minimal profile in three ways. First, the local IPC endpoint is effectively a code-execution interface (`send` types prompts, `answer` can allow PermissionRequest tool calls). It currently has no decided per-OS enforcement of its same-OS-user boundary, and its names are predictable in shared namespaces (Windows pipes, `/tmp`). Second, the loopback HTTP GUI streams persistent, never-rotated prompt and assistant content, including raw tool arguments, to any local process without authentication, renders that untrusted text in a browser, and gains state-changing routes in v1.x. Third, several state files decide what code runs and whether dialogs are answered: `snapshot.json`'s `statusline_command`, the `hooks.json` exec paths, the pinned binaries and the ledger stamps. The baseline is therefore Minimal (dependency audit, input validation on config and external payloads, error sanitization). On top of it sit specific local-boundary items: IPC endpoint access control and server impersonation, bracketed-paste breakout in `send.text`, GUI output encoding, GUI cross-user and cross-origin readability, v1.x per-launch brake auth, and integrity of `~/.viola/`. Each of these traces to Section 2._

**Data classification:**
- **Type:** user-content (prompt text and assistant output)
  - **Where:** `instances/<ViolaName>/events.ndjson`. `prompt-submitted.data.text` holds every submitted prompt (driver, human and harness), and `turn-ended.data.last_assistant_message` holds each final assistant reply. The wrapper keeps the latest reply in memory for `last`. The same lines go out verbatim over SSE `/api/events` (`data:` is the event line), over MCP `wait`/`last` and over CLI `wait`/`last` (Standard Contracts: event `data` per kind, SSE feed. Occupied Resources: Filesystem).
  - **Volume:** Per-user, persistent and growing. The file is never rotated or truncated, and bounding its size is an open item (Occupied Resources: Filesystem). Instance directories are reused and appended to, so it builds up across sessions (Established Decisions: Session Liveness).
- **Type:** user-content (tool-call arguments, plans, dialog questions and answers). This may incidentally include secrets or personal data the user's session touches.
  - **Where:** The `permission` event carries `{tool, input}`, where `input` is the tool call's full arguments as JSON. For Bash and Write-type tools that means shell commands and file bodies. `plan` carries the plan text and `question` carries questions and options. All of it is logged to `events.ndjson`, streamed over SSE, and sent over the local-socket channel in `hook.dialog` (Standard Contracts: Event `data` per kind, `hook.dialog`).
  - **Volume:** Per-user, persistent, same retention as above.
- **Type:** config (includes a stored executable command string)
  - **Where:**
    - `config.json` holds budget thresholds and the GUI port.
    - `instances/<ViolaName>/settings.json` is the per-session statusline override.
    - `snapshot.json` stores `statusline_command`, the user-written shell string that `hook statusline` reads through `VIOLA_DIR` and runs through a shell. This is the only shell-out in viola.
    - `snapshot.json` also stores `endpoint`, the socket path clients connect to, and `pinned_bin`.
    - `ledger/stamps.json` holds the verified CLI versions. A stamp is what switches on dialog answering.
    - `plugin/<version>-<hash>/hooks/hooks.json` and `.mcp.json` hold the absolute exec paths Claude Code runs for every hook and for MCP.
    - `bin/<version>-<hash>/viola(.exe)` is the pinned executable.
    - Sources: Occupied Resources (Filesystem, Claude Code integration names); Standard Contracts (Hook contract, Instance snapshot); Established Decisions (Deployment / Distribution, CLI Version Compatibility).
  - **Volume:** Per-user, persistent. These are integrity-sensitive more than confidentiality-sensitive, because several of them decide what code runs.
- **Type:** credential (transient, inherited from the environment, never stored by viola)
  - **Where:** The `viola run` wrapper process's environment holds `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` and other `CLAUDE*` parent-identity variables, which are stripped from the child's environment (R8 strip list, Occupied Resources: Environment variables). The Claude subscription credentials belong to the unmodified `claude` CLI, and viola makes no model API calls (Stack: AI/ML N/A). Cross-cutting Patterns (Config management): "There are no secrets in v1."
  - **Volume:** Transient, in process memory only.
- **Type:** operational metadata. PII is limited to the OS username in paths.
  - **Where:**
    - `/api/info` exposes `pid`, `bind`, `viola_home` (for example `C:/Users/<user>/.viola`) and `verified_cli_versions`.
    - Snapshots hold `pid`, `child_pid`, `agent_session_id` and `started_at`.
    - `budget.json` holds subscription usage percentages and `resets_at`.
    - `/api/sessions` shows unwrapped session identifiers from `claude agents --json`.
    - Sources: Standard Contracts (Service info, GUI list envelope, Instance snapshot); Occupied Resources (Filesystem).
  - **Volume:** Per-user, low sensitivity.
- **Type:** payment / health / multi-user PII: none. Stack lists no payment, identity or health SDKs, there is no database and no accounts (Stack; Established Decisions: Personal v1).

**Attack surface:**
- **Vector:** Local IPC, the wrapper channel (JSON-RPC 2.0 over ndjson). This is the highest-impact surface.
  - **Entry point:**
    - One endpoint per `viola run`: named pipe `\\.\pipe\viola-<h12>` on Windows, socket file `$TMPDIR/viola-<h12>.sock` (else `/tmp`) on Unix.
    - Methods: `send`, `wait`, `last`, `answer`, `pause`, `release`, `link`, `unlink`, `hook.dialog`, and `hook.event` notifications.
    - Whoever can connect can type prompts into the driven Claude session (`send`) and allow PermissionRequest dialogs (`answer` with `behavior:"allow"`). That amounts to running arbitrary tools, and so arbitrary code, as the user. They can also read the whole conversation (`wait`, `last`).
    - Sources: Occupied Resources (IPC endpoints); Cross-cutting Patterns (Local endpoint trust boundary).
  - **Trust boundary:**
    - v1 intends to trust every process of the same OS user and no other. How that is enforced per OS (pipe DACL, socket file mode, directory permissions) is not decided in arch and is explicitly handed to security.
    - There is no per-connection authentication. The `from` parameter is self-reported by the caller (the CLI and MCP take it from their own `VIOLA_NAME`), so link records and driver identity are not authenticated.
    - The endpoint name is predictable: FNV-1a over `ViolaName` + home path, which is not secret (Conventions: Endpoint name).
    - Consequences:
      - On Unix with `TMPDIR` unset, the socket sits in world-writable `/tmp`, so another local user can create the path first.
      - On Windows, the named-pipe namespace is shared across the machine.
      - Clients (`hook`, `send`, `mcp`) connect to the `endpoint` recorded in the snapshot and act on whatever server answers there. A process holding that name while the real wrapper is gone could receive `hook.dialog` payloads and send back dialog decisions.
      - `run`'s exclusive bind means a squatted name blocks startup (exit 1).
    - Input validation is limited to JSON-RPC parsing, the `v` check (`-32602`) and the `ViolaName` nutype.
    - It is open (arch defers it to security) whether a driver-originated `release` (params carrying `from`) should be refused. Established Decisions (MCP) records that an agent's Bash tool can call CLI `viola release` through `VIOLA_BIN`.
- **Vector:** CLI input, the `send` text written into the PTY.
  - **Entry point:** A bridge send is one `ESC[200~…ESC[201~` + CR write of text from stdin, `--file` or MCP `send.text` (Established Decisions: Human Takeover / Wheel).
  - **Trust boundary:** Arch does not say whether sent text is checked for an embedded bracketed-paste terminator (`ESC[201~`) or other control sequences. Text containing one would end the paste early, and the rest would reach the `claude` TUI as typed keystrokes. The only post-hoc check is delivery confirmation, which compares `prompt-submitted` text with the sent text (Established Decisions: Delivery Confirmation).
- **Vector:** Local HTTP on loopback, view-only GET + SSE.
  - **Entry point:**
    - `viola ui` on `127.0.0.1:47319`.
    - Routes: `/`, `/assets/*`, `/health`, `/ready`, `/api/info`, `/api/sessions`, `/api/links`, and SSE `/api/events`, which carries raw event lines including prompts, assistant output and permission `input`.
    - `/api/events` accepts a client-supplied `Last-Event-ID` cursor (`<ViolaName>:<offset>,…`).
    - Reserved for v1.x, not served in v1: `POST /api/sessions/{name}/pause` and `POST /api/sessions/{name}/unlink`.
    - Sources: Occupied Resources (Network, HTTP routes); Standard Contracts (SSE feed).
  - **Trust boundary:**
    - Checks in place: bind to 127.0.0.1 only, never `0.0.0.0` or `::`; a Host allowlist of `127.0.0.1:<port>` and `localhost:<port>` against DNS rebinding; GET only, with 405 for any other method.
    - There is no token and no CSRF protection (Established Decisions: GUI Control Scope).
    - Loopback TCP is reachable by every local process, including other OS users' processes. So this surface does not follow the same-OS-user boundary set for the IPC endpoint: another local user can read the full event feed.
    - Arch does not specify a CORS policy.
    - Cursor parsing: instance names in `Last-Event-ID` are declared as `ViolaName`, whose charset is `[a-z0-9-]`, but arch does not say the header is parsed through the newtype before it reaches filesystem lookups.
    - The page renders untrusted upstream text: prompts, `last_assistant_message`, plan text and tool `input` (Cross-cutting Patterns: Untrusted upstream text). The frontend framework, and so its output-encoding behaviour, is deferred to design.
    - For the v1.x POST routes, arch requires that "no state-changing route is reachable cross-origin or without per-launch proof that the caller is the local user", with the mechanism owned by security.
- **Vector:** Hook stdin payloads from Claude Code, exec-form `viola hook <event>`.
  - **Entry point:** JSON on stdin for SessionStart, UserPromptSubmit, PreToolUse (`AskUserQuestion|ExitPlanMode`), PermissionRequest, Stop, SessionEnd, Notification, PostToolUse and PostToolUseFailure, plus `hook statusline` with statusline JSON (Established Decisions: Hook Transport; Occupied Resources).
  - **Trust boundary:**
    - Parsing is tolerant in `viola-agent-claude`: no `deny_unknown_fields`, serde_path_to_error for drift reports (Established Decisions: Validation).
    - Upstream text is treated as content, never as commands (R1).
    - Any failure fails open to the human: exit 0 with no body.
    - `hook statusline` runs `statusline_command` from `snapshot.json` through a shell. That snapshot is found through `VIOLA_DIR`, so its integrity is set by filesystem permissions on the viola home.
- **Vector:** MCP over stdio. The driver is an LLM agent.
  - **Entry point:** Tools `send`, `wait`, `last`, `answer` and `list`, called by the driver session's model (Established Decisions: MCP).
  - **Trust boundary:**
    - Tool input schemas (schemars) and the `ViolaName` newtype check the input.
    - The driver model reads the driven session's output (`wait`/`last`), which arch classes as untrusted upstream text. The same model can then call `answer` on that session's PermissionRequest.
    - viola does not interpret that text (R1: mechanism, not policy). The decision to allow a permission rests with the driver model, outside viola.
    - Leaving `release`, `pause`, `link` and `unlink` off the MCP tool list is described as an affordance, not an enforcement.
- **Vector:** CLI arguments, flags and environment.
  - **Entry point:**
    - All subcommands.
    - `--home <dir>` and `VIOLA_DIR` choose which state tree, snapshot, `endpoint`, `statusline_command` and ledger stamps are used (Cross-cutting Patterns: Config management).
    - `answer` takes its `response` JSON from stdin or `--file`.
    - `viola run <name> -- <program> <args>` spawns the program as given.
  - **Trust boundary:** Same-user invocation, clap parsing, the `ViolaName` nutype, and tolerant `config.json` parsing.
- **Vector:** Filesystem state under `~/.viola/`.
  - **Entry point:**
    - Readers across processes: `snapshot.json`, `events.ndjson`, `budget.json`, `config.json`, `ledger/stamps.json`, `heartbeat`.
    - Code-bearing artefacts: `bin/<version>-<hash>/viola(.exe)` and `plugin/<version>-<hash>/hooks/hooks.json` / `.mcp.json`. Claude Code runs these on every hook event and for MCP.
    - Sources: Occupied Resources (Filesystem); Established Decisions (Deployment / Distribution).
  - **Trust boundary:**
    - OS permissions on the user's home directory.
    - Readers tolerate torn lines and replay the log when a snapshot fails to parse (Standard Contracts: Snapshot envelope).
    - The pinned binary and plugin folders are never deleted in v1.
    - Nothing checks integrity beyond the content hash in the folder name.
- **Vector:** Child process spawning and PATH resolution.
  - **Entry point:**
    - `list`, `mcp` and `ui` spawn `claude agents --json`, resolving `claude` from their own PATH with npm-shim → `claude.exe` resolution.
    - `run` resolves the child executable and runs it once with `--version`.
    - `run` puts the pinned copy's folder first on the child's PATH.
    - Sources: Standard Contracts (Session liveness); Established Decisions (CLI Version Compatibility, Deployment / Distribution).
  - **Trust boundary:** Whatever the calling process's PATH resolves to. Output parsing is tolerant, and failure becomes `unknown`.
- **Vector:** Supply chain (build and CI).
  - **Entry point:**
    - Cargo dependencies. Arch notes interprocess has a single main maintainer and rmcp releases nearly weekly with its minor version pinned.
    - Third-party GitHub Actions: `dtolnay/rust-toolchain@stable` and `Swatinem/rust-cache@v2.9.2`.
    - Future v1.x public distribution and `self_update`.
    - Sources: Stack; Infrastructure Patterns (Build system, CI/CD approach).
  - **Trust boundary:** `cargo deny check` (licences, C-crate bans, tokio ban), `Cargo.lock`, and `publish = false`. In v1 there is no release, no signing and no deploy stage.
- **Public internet API / file upload / OAuth / WebSocket / webhook:** none. Stack and Conventions list no public listener, no WebSocket ("No WebSocket and no polling endpoints in v1") and no hosting.

**Auth model:**
- **Approach:** none for v1 (as of 2026-09-23). The only principal is the local OS user.
  - Reason: Project Intent and Established Decisions (Personal v1) describe a single-user local tool with "no accounts, no hosting". The GUI is view-only.
  - Access control therefore depends entirely on OS-level isolation: who can connect to each IPC endpoint and who can read or write `~/.viola/`. Cross-cutting Patterns (Local endpoint trust boundary) sets the target principal as "every process of the same OS user and no other".
  - Arch has decided no enforcement mechanism for that boundary on any OS. That decision is outstanding and belongs to this specialist.
  - The loopback HTTP GUI currently has no principal check, so it does not match the same-OS-user boundary (Section 2).
- **Approach for v1.x brake (state-changing GUI routes):** a per-launch local secret proving the caller is the local user (API-key style, bound to one `viola ui` launch).
  - Reason: Established Decisions (GUI Control Scope) requires "per-launch proof that the caller is the local user" and no cross-origin reachability.
  - There are no user accounts, so session cookies with login, JWT or OAuth have no identity provider or user store to bind to.
- **Provider:** self-implemented. Stack contains no auth framework or identity SDK: axum and tower-http are listed without any auth layer.
- **Scope:** per-OS-user for v1 (IPC and filesystem). Per-launch for the v1.x brake token. Remote or phone access behind authentication is a later version and is N/A in this assessment (Project Intent: Scale path; Stack: Mobile N/A).
- **Development Style context:** agent-driven (Cross-cutting Patterns). The main automated callers are LLM driver sessions using MCP and the CLI, with no interactive login. That matches an ambient OS-user trust model rather than a credential flow.

**Infrastructure:**
- **Hosting:** local-only. Installed with `cargo install --path .`. No Docker, Compose, Kubernetes, serverless or PaaS (Infrastructure Patterns: Deployment model; Established Decisions: Hosting).
- **Database:** none. State is embedded flat files: ndjson append logs plus atomically replaced JSON snapshots, with std `File::lock` on sibling `.lock` files, under `~/.viola/` or `--home` (Stack: Database; Established Decisions: Database / State Store). Nothing is encrypted, and all of it is plaintext for readability by design.
- **Networking:** local only.
  - TCP loopback `127.0.0.1:47319`, never `0.0.0.0` or `::`.
  - Per-instance named pipes (Windows) or Unix domain sockets (`$TMPDIR` or `/tmp`); no Linux abstract namespace.
  - MCP over stdio.
  - No outbound network calls by viola itself. The `claude` child handles the network to Anthropic on its own.
  - Sources: Occupied Resources (Network, IPC endpoints); Stack (AI/ML N/A).
- **CI/CD:**
  - GitHub Actions `ci.yml`, triggered on push and PR, on a native matrix of `windows-2025`, `macos-latest` and `ubuntu-latest`.
  - Jobs: fmt, clippy `-D warnings`, `cargo check` of the sync crates, `cargo deny check` (on ubuntu), tests against the fake agent with recorded fixtures, and `cargo build --release`.
  - No deploy stage, no release artefacts and no secrets in v1. The real `claude` CLI and `viola verify` run only locally.
  - v1.x adds a dist 0.33.0 release workflow with cargo-auditable 0.7.6, signing, winget/Homebrew/Scoop and `self_update` 1.3.0.
  - Sources: Infrastructure Patterns (CI/CD approach); Stack (Release).

**Compliance triggers:**
None: no compliance-regulated data detected.
- No payment data (no payment SDK in Stack).
- No health data.
- No children's data.
- No collection of personal data from third parties. The tool has no accounts and no hosting, and all logged content is the operator's own Claude session content kept on their own machine (Established Decisions: Personal v1; Project Intent).
- The v1.x public distribution in Project Intent (Scale path) still keeps all data local on each user's machine, so it adds no trigger in this assessment.

## Authentication & Authorization

_Included despite v1 auth approach "none". Threat Model Sec 3 also defines a per-launch local secret (API-key style), and Sec 6 elevates "IPC endpoint access control and server impersonation", "GUI cross-user and cross-origin readability" and "v1.x per-launch brake auth". Every principal check in viola is either OS-level (IPC, filesystem) or this per-launch secret (GUI). See the Security Decisions Log._

**Auth approach:** Two parts:
- OS-user ambient trust, enforced per OS, on the IPC endpoints and `~/.viola/`.
- A per-launch secret (API-key style) for the loopback GUI. It is exchanged once for a same-site cookie and applies to v1 reads and to v1.x brake writes.

**Library:**
- IPC: interprocess 2.4.4 (`ListenerOptionsExt::security_descriptor`, `SecurityDescriptor::deserialize`, `ListenerOptionsExt::mode`, `Stream::peer_creds()`, `PipeStream::server_process_id()`), windows-sys 0.61.2 (`GetTokenInformation(TokenUser)`, `ConvertSidToStringSidW`, `CreateFileW` with SQOS flags) and sysinfo 0.39.6 (pid + start time).
- GUI: getrandom 0.4.3 (token), constant_time_eq 0.6.0 (comparison), and an axum 0.8.9 middleware in `viola-ui`.

_Adapter note: viola has no passwords and no user store. The rows are adapted to an OS-principal model plus a per-launch local token._

| Token / session storage | **Token:** `viola ui` draws 32 bytes from `getrandom` at start, hex-encodes them and keeps them only in process memory. **Launch URL file:** `http://127.0.0.1:<port>/?t=<token>` is written to `<viola home>/ui/<port>.url` with atomic-write-file 0.3.1 (file 0600, dir 0700 on Unix; on Windows the home's DACL per the `~/.viola/` access control row) and printed once to stderr at launch. **Exchange:** `GET /?t=<token>` compares the token with `constant_time_eq`. On a match it answers `Set-Cookie: viola_<port>=<token>; HttpOnly; SameSite=Strict; Path=/` with no `Max-Age` (a browser-session cookie), then redirects 303 to `/` so the token leaves the URL. On a mismatch it answers 401 `urn:viola:problem:unauthorized`, sets no cookie and does not redirect. The security headers, including `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, apply to that failure response too. `/` without `?t=` serves the ungated page. **No recovery shortcut:** no route reprints or re-issues the token. The page, the 401 `detail` and every other error never contain the token, the launch URL, or the `.url` path or contents. A lost cookie or launch line is recovered only from the stderr launch line, from the 0600 `.url` file, or by restarting `viola ui`. **Cookie name:** includes the port, because cookies are not port-scoped and two `viola ui` launches on different ports must not overwrite each other. **Cross-port exposure:** for the same reason, the browser also attaches `viola_<port>` to requests for any other `127.0.0.1` port, including a server run by another local OS user. The viola page itself never issues such requests (CSP `connect-src`/`img-src` `'self'`, `form-action 'none'`), so the cookie reaches another port only when the user navigates there directly while the browser session lives. | IPC access control (Unix) | **Primary control:** the socket lives in a per-user directory with mode 0700: `$XDG_RUNTIME_DIR/viola/` on Linux, `$TMPDIR/viola/` on macOS, and `/tmp/viola-<uid>/` only as a fallback. | IPC server-side peer check (Unix) | On every accept, `stream.peer_creds()`; if `euid() != geteuid()`, drop the connection before reading a frame. | `viola-channel` sync + Tokio server |
| IPC client-side server verification (anti-impersonation) | **Windows client open:** open the pipe through windows-sys `CreateFileW(..., SECURITY_SQOS_PRESENT \| SECURITY_IDENTIFICATION \| FILE_FLAG_OVERLAPPED, ...)`, then adopt the handle with `interprocess::os::windows::named_pipe::local_socket::Stream::try_from(OwnedHandle)`. This adoption path is the open spike (Decisions Log). If the spike fails, the Windows client chunk stops until a replacement SQOS open is recorded in the Decisions Log; it never falls back to interprocess's default connect, which opens without SQOS (§ Authentication). **Windows identity check:** `server_process_id()` must equal the snapshot `pid`, and sysinfo's process start time must equal snapshot `started_at`. **Unix identity check:** `peer_creds().euid()` must equal `geteuid()`, and where available (Linux/FreeBSD) `peer_creds().pid()` must equal the snapshot `pid`, with the sysinfo start-time match. **macOS:** `peer_creds()` gives no pid, so verification there is euid + the verified 0700 socket directory, with no pid check. This is accepted for v1 (macOS is CI-only, brief O5) and recorded as a known gap for the public version. **Timing:** all of this runs before the first frame of any method is written on the connection, including `hook.event` notifications (UserPromptSubmit, Stop and PostToolUse carry prompt text, `last_assistant_message` and tool data) and `wait`/`last` requests, not only `send`, `answer` and `hook.dialog`. **On mismatch:** CLI/MCP report `instance-unreachable`, and `hook` fails open (exit 0, no body, a note in `diagnostics/`). **Collision check:** `run` uses the same verification. | `viola-channel` client (sync + `tokio` feature); windows-sys 0.61.2; sysinfo 0.39.6 |
| Driver-originated `release` | The wrapper rejects a `release` whose `params` carry `from` with `-32602` and `data: {"reason":"release-from-driver"}`. The CLI then exits 20. Per Standard Contracts, `release` params are `{budget?}` only. This is an affordance-level guard against drivers handing the wheel back to automation. It is not enforcement: a same-user process can leave out `from`. `pause`, `link` and `unlink` from drivers are allowed. | `viola` bin channel dispatch; `viola-core` param structs |
| `~/.viola/` access control | **Unix:** home (and any `--home`) is created 0700, and every file is created with `OpenOptionsExt::mode(0o600)`. Check that atomic-write-file's temp file is 0600 before rename. **Strict-modes check:** in every process that reads `snapshot.json`, `ledger/stamps.json` or `statusline_command` (that is, at the start of `run`, `ui`, `mcp`, every `hook <event>` including `hook statusline`, and every CLI client verb that resolves an instance's `endpoint`), refuse when the home, `instances/<name>/`, `bin/`, `plugin/` or `ledger/` is group- or world-writable or not owned by euid (ssh StrictModes style). The snapshot's `endpoint`, `pid` and `started_at` are the reference values for client server verification, so a client that skips this check verifies the server against values an attacker could have written. On failure `run`, `ui` and `mcp` exit 1; every `hook` event prints nothing and exits 0; CLI client verbs report `instance-unreachable` (exit 21). **Windows:** `%USERPROFILE%` inheritance (user + SYSTEM + Administrators) is accepted. A `--home` outside `%USERPROFILE%` gets an explicit protected user + SYSTEM DACL at creation (via windows-sys), or is refused if one cannot be set. **Windows strict-modes check:** at the same entry points as Unix, read the owner and DACL of the home, `instances/<name>/`, `bin/`, `plugin/`, `ledger/` and `ui/` (each checked separately, because Windows bypass-traverse makes a subdirectory reachable regardless of the home's ACL) (windows-sys `GetNamedSecurityInfoW` + `GetAce`). Refuse when the owner is not the user SID or Administrators, or when any allow ACE grants write, delete, `WRITE_DAC` or `WRITE_OWNER` to a SID other than the user, SYSTEM or Administrators (for example `Users`, `Authenticated Users`, `Everyone`); inherit-only ACEs may be ignored for this write rule only. **Read rule:** on the home, `instances/<name>/` and `ui/`, also refuse any allow ACE, including an inherit-only ACE with object-inherit, that grants read (`FILE_READ_DATA` / `GENERIC_READ`) to such a SID. Files viola creates inherit these DACLs, so a readable directory exposes `events.ndjson`, `diagnostics/` and `ui/<port>.url` (the GUI token). This is the Windows counterpart of Unix's 0600 file creation. The outcomes match Unix. This covers pre-existing and later-modified homes, not only creation. | `viola-state` home resolution; atomic-write-file 0.3.1; std `OpenOptionsExt`; windows-sys 0.61.2 |

_Authentication Recovery Flows: omitted, because the per-launch secret is API-key style and is not user-facing account auth. Recovery means restarting `viola ui`._

## Input Validation

_[ALL tiers]_

**Boundary:** Validate at every point where untrusted data enters viola. Arch has two validation regimes (Established Decisions: Validation): tolerant parsing for external payloads, and versioned-tolerant parsing for viola's own formats. The requirements below are security floors that apply in both regimes. Shared validators live in `viola-core`, so the CLI, MCP and the wrapper all call the same function.

| Boundary | What to validate | How (stack-specific) |
|----------|-----------------|---------------------|
| Paste text: channel `send.text`, MCP `send.text`, CLI `send` stdin/`--file` | **Rule (exact set):** multi-line text is normal (relays, plans and free-text answers are multi-line, brief §4.1 S1), so three controls are **allowed**: LF (U+000A), CR (U+000D) and TAB (U+0009). Everything else in this set is **refused**: every other C0 control (U+0000–U+0008, U+000B–U+000C, U+000E–U+001F, including ESC U+001B above all), DEL (U+007F) and every C1 control (U+0080–U+009F, including CSI U+009B). The check runs over decoded `char`s of the UTF-8 `&str`, never over raw bytes, because UTF-8 continuation bytes 0x80–0xBF are not C1 controls. This stops a bracketed-paste breakout through an embedded `ESC[201~`. **Reject, don't strip:** stripping would break the delivery-confirmation exact match. **Where it runs:** `viola_core::validate_paste_text(&str) -> Result<(), CoreError>`, called client-side (CLI, MCP) before sending and again by the wrapper before the PTY write (the wrapper's check is authoritative). **Wire outcome:** refusal `not-delivered` with new detail `control-character`, checked before the Conventions refusal order. | `viola-core`; the `run` pump's paste writer in `src/run/` |
| Dialog free text: `answer.response.message` (permission, plan) and `answer.response.answers.*` values (question) | The same exact set as `send.text`: LF, CR and TAB allowed; every other C0 control, DEL and C1 refused with `control-character`. | `viola_core::validate_paste_text`; the `answer` handler |
| Channel frames (IPC ndjson) | **Size cap:** wrap the stream reader in `Read::take(MAX_FRAME)` before `read_line`; an over-limit frame gets `-32600` and the connection is closed. **Depth:** serde_json's default recursion limit of 128 (never `unbounded_depth`). **Version:** the `v` check (`-32602`). **Closed types:** `behavior` is a closed enum (`allow`/`deny`, `approve`/`revise`), `dialog_id` is `u64`, and `link`/`unlink` `driver`/`driven` go through `ViolaName::try_new`. | `viola-channel` framing; serde 1.0.229; serde_json 1.0.151; nutype 0.8.0 |
| Hook stdin (all hook events + `hook statusline`) | **Size cap:** `Read::take(MAX_FRAME)` on `read_to_end`; over the limit, fail open (exit 0, no body, a note in `diagnostics/`). **Parsing:** tolerant (Established Decisions: Validation), but fields that decide security (dialog kind and the decision body) map into closed enums in `viola-agent-claude`. **Timestamps:** `resets_at` is parsed with chrono in UTC only; a malformed value becomes `"unknown"`. | `viola-agent-claude` hook parser; serde_path_to_error 0.1.20; chrono 0.4.45 |
| SSE `Last-Event-ID` header | Split on `,`. Parse each `<name>:<offset>` pair with `ViolaName::try_new` and `u64::from_str` before any `instances/<name>` join. If any pair fails, drop the whole header and start at each file's current end (the no-header behaviour); never skip just the bad pair. | `viola-ui` SSE handler; nutype 0.8.0 |
| Host header (every GUI route) | Read `http::header::HOST` directly and compare it exactly with `127.0.0.1:<port>` or `localhost:<port>`; anything else gets 403 `urn:viola:problem:host-not-allowed`. Do not use axum-extra's `Host` extractor. | `viola-ui` middleware, outermost layer |
| v1.x brake path param `{name}` | `ViolaName::try_new`; on failure 404 `urn:viola:problem:not-found`. | `viola-ui` route extractor |
| MCP tool inputs (`target`, `text`, `dialog_id`, `response`, `after`, `timeout_ms`) | The schemars 1.2.2 schemas are advisory only, because rmcp does not enforce them server-side. Deserialise `target` into `ViolaName`, `dialog_id` into `u64` and `response` into the closed channel enums, and apply `validate_paste_text` to `text` and the free-text answer fields. | `viola-mcp` tool handlers; schemars 1.2.2; rmcp 3.4.1 |
| CLI arguments / stdin | **Names:** every `ViolaName` argument uses `#[arg(value_parser = parse_viola_name)]`, which calls `ViolaName::try_new`. **Home path:** `--home` and `VIOLA_DIR` are canonicalised (`std::fs::canonicalize`) and then pass the `~/.viola/` strict-modes check before any snapshot, `statusline_command` or ledger read. **`answer` response:** the JSON from stdin or `--file` is read with `Read::take(MAX_FRAME)` into the closed `response` enums. | `src/main.rs` clap 4.6.7 derive; `viola-state` home resolution |
| Configuration values (`config.json`) | Tolerant parse (unknown keys counted). Thresholds go into `Percent` (0–100) and `port` into `u16`. `v` is checked. | `viola-state`; nutype 0.8.0 |
| Own state files on read (`snapshot.json`, `events.ndjson` replay/tail, `ledger/stamps.json`, `budget.json`, `heartbeat`) | **Line cap:** replay and tail read each ndjson line with a `MAX_FRAME` cap; an over-long line counts as `torn_lines`. **Integrity:** read only after the home strict-modes check. `snapshot.json`'s `statusline_command` is trusted only because of that check (write access to it equals code execution). | `viola-state` readers |
| Tailed paths (notify) | Tail only `instances/<name>/events.ndjson` where `<name>` passes `ViolaName::try_new`, under the canonical home. Ignore symlinks (`symlink_metadata`) and names that fail parsing. | `viola-state` tailing; notify 8.2.0 |
| Child process output: `claude agents --json`, `--version` probe | **Parsing:** read with `Read::take(MAX_FRAME)` and parse tolerantly; failure becomes `unknown`. **Identifiers:** an unwrapped row's `name` is never a `ViolaName` and never a valid `target` (Standard Contracts: GUI list envelope). | `viola-agent-claude`; std `process::Command` |
| PTY output bytes (vt100) | Feed through `std::panic::catch_unwind`. On a panic, the readiness gate degrades to `not-delivered`/`input-not-ready` and byte passthrough to the human terminal continues. | `src/run/` pump + `viola-agent-claude` screen model; vt100 0.16.2 |
| Child executable resolution (`run`, `claude agents`) | `list`, `mcp` and `ui` resolve `claude` for `claude agents --json` from the calling process's PATH. This is same-user trust and an accepted risk (Decisions Log). Its output is untrusted: it is bounded by `MAX_FRAME`, and a row's `name` is never a `ViolaName` or `target` in CLI `list`, the MCP `list` tool or `/api/sessions`. The GUI renders it as text only. On Windows, resolve the npm `.cmd` shim to `claude.exe` before spawning. `viola run` refuses (exit 1) when the resolved PTY child is a `.cmd`/`.bat`, because portable-pty 0.8.1 builds its own `CreateProcessW` command line without std's BatBadBut escaping. | `viola-agent-claude` shim resolution; `viola-pty` spawn |
| File upload / webhook / SQL | N/A. No upload, webhook or database surface (Threat Model: Attack surface). | — |

**Constants:** `MAX_FRAME = 16 MiB`, one const in `viola-core`, shared by channel frames, hook stdin, `answer` input, child output and ndjson line reads. It is the default, sized above the largest expected `permission.input` (Write-tool file bodies). **Checked against data, not a guess:** a capability-ledger row records the largest hook payload seen (bytes of hook stdin, per event kind), measured by `viola verify` and stamped per CLI version in `ledger/stamps.json`. A stamped maximum within a factor of 4 of `MAX_FRAME` is a signal to revisit the cap (see the Decisions Log).

**Parser surfaces (scope for fuzz / property coverage; tests owns the cases):** `validate_paste_text`, the `Last-Event-ID` parser, channel ndjson framing with `MAX_FRAME`, the hook stdin parser (including `hook statusline`), the `claude agents --json` output parser, and the vt100 feed under `catch_unwind`.

## Data Protection

_Minimal tier, adapted. "HTTPS enforced" does not apply (loopback-only plain HTTP), and viola does store sensitive user content (Threat Model: Data classification), so the file-permission controls stay in scope._

**In transit:**
- **TLS:** N/A. The GUI binds only `127.0.0.1` (never `0.0.0.0` or `::`), the IPC channel is local named pipes or Unix sockets, and MCP is stdio. Confidentiality in transit depends on the loopback bind plus the GUI cookie check and the IPC ACLs (Authentication & Authorization).
- **HSTS:** N/A (plain HTTP on loopback, per tower-http research).
- **Certificate pinning:** N/A.
- **Handle inheritance:** portable-pty 0.8.1 calls `CreateProcessW` with `bInheritHandles = 0`, and interprocess listeners stay `inheritable(false)`, so channel handles never leak into the `claude` child. Any portable-pty swap (portable-pty-psmux 0.9.7 is the named candidate) must keep this property.

**At rest — per medium:**
- **Database:** N/A (none).
- **Files (`~/.viola/`):** Plaintext by design (Established Decisions: Database / State Store). Protected by OS permissions only:
  - Unix: 0700 directories and 0600 files.
  - Windows: the inherited `%USERPROFILE%` DACL (user + SYSTEM + Administrators), or an explicit protected user + SYSTEM DACL for a `--home` outside `%USERPROFILE%`.
  - The strict-modes check runs at startup (Authentication & Authorization, `~/.viola/` access control).
  - **Code-bearing artefacts:**
    - `viola run` always rewrites `plugin/<version>-<hash>/` files with atomic-write-file rather than trusting an existing copy.
    - `instances/<name>/settings.json` (the per-session override whose statusline command Claude Code executes) is rewritten by `viola run` at every start with atomic-write-file (0600) and never reused from an existing copy. Its command uses the absolute pinned `bin/<version>-<hash>/viola(.exe)` path (§ Universal).
    - `<hash>` is a truncated SHA-256 of the exe bytes (the first 16 hex characters of the digest). Before reusing an existing `bin/<version>-<hash>/viola(.exe)`, `viola run` re-hashes the file with SHA-256 and compares the truncated result with `<hash>`. On a mismatch it refuses to start (exit 1). The SHA-256 implementation is an open question (Decisions Log). It must be pure Rust, pass the cargo-deny C-build ban, and be recorded in the Decisions Log before the chunk that writes `bin/`. A non-cryptographic fallback is banned (§ Data Protection). Because the hash is cryptographic, this catches substitution as well as accidental corruption. Tampering by the same OS user (who could also rewrite the folder name) stays outside the v1 boundary.
    - `ledger/stamps.json` is written only by `viola verify`, under its `.lock`, with 0600.
- **Logs:**
  - `events.ndjson` and `instances/<name>/diagnostics/` are 0600 inside 0700 directories.
  - serde_path_to_error drift reports, which can quote tool `input`, are written only to `diagnostics/`.
  - Logging format and fields belong to obs.
- **Repository fixtures:** `fixtures/claude/<cli-version>/` is recorded by `viola verify` from live sessions and committed. Probe prompts must be synthetic. Review recorded payloads for home paths, usernames and tool `input` before committing.

_Key management and Data lifecycle subsections are omitted for Minimal tier. There are no keys at rest; the GUI token lives in memory for one launch. `events.ndjson` retention and bounding is an open item owned by arch. Security's only requirement is that any rotation scheme keeps 0600/0700 permissions and keeps offsets valid (see the Decisions Log)._

## Secret Management

_[ALL tiers]_

**Storage:**
- **Production:** No stored secrets in v1 (Cross-cutting Patterns: Config management, "There are no secrets in v1"; environment variables are not a configuration channel).
  - The only secret viola creates is the GUI per-launch token. It lives in `viola ui` process memory and in `<viola home>/ui/<port>.url` (0600 inside a 0700 dir on Unix; on Windows the home's DACL, which admits only the user, SYSTEM and Administrators and is checked at startup).
  - Inherited credentials (`CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` and the other `CLAUDE*` identity variables) stay only in the `viola run` wrapper's environment. They are removed from the child by the R8 strip list and are never serialised into events, snapshots, diagnostics or the ledger.
- **Development:** Same as production. Tests use their own `--home` directory, and each `viola ui` under test generates its own token.
- **Production / dev separation:** Every `viola ui` launch generates a fresh token, so no token is shared across launches or environments.

**Never in code:** No token, key or credential literal in source or in the embedded plugin files (`hooks.json`, `.mcp.json`, `plugin.json` carry only exec paths).

**Secret scanning in CI:** Not in v1. The repo and CI hold no secrets, and security-research.md catalogues no secret scanner (see the Decisions Log). Revisit when the v1.x release workflow adds signing credentials.

**Rotation cadence:**
- **API keys / DB passwords:** N/A.
- **JWT signing keys:** N/A.
- **TLS certificates:** N/A (loopback HTTP).
- **GUI per-launch token:** rotated on every `viola ui` start. Never persisted beyond the `.url` file, which is removed on graceful shutdown.
- **Per-incident:** suspected token exposure (for example the launch URL pasted somewhere) → restart `viola ui`.

**Access auditing:** N/A in v1 (no secret manager). The token file's 0600 mode is the access control.

**What counts as secret:**
- The GUI per-launch token and the launch URL that contains it.
- The `viola_<port>` cookie value.
- The inherited `CLAUDE_CODE_MESSAGING_TOKEN` / `CLAUDE_CODE_MESSAGING_SOCKET`.
- From v1.x: Azure Artifact Signing credentials (dist) and the zipsign private key (self_update `signatures`), both held only as CI secrets in the release workflow.

## Error Handling

_[ALL tiers]_

**External responses** (to channel clients, CLI `--json`, MCP drivers and GUI clients): sanitised.
- No anyhow context chains, no absolute paths, no upstream text (prompts, tool `input`, assistant output), no serde_path_to_error paths or values, and no internal type names.
- `/api/info`'s `viola_home` is the only intended path disclosure, and after this plan it sits behind the GUI cookie.
- `thiserror` `Display` impls on `PtyError`, `ChannelError`, `StateError`, `AgentError`, `McpError`, `UiError` and `CoreError` use fixed messages. Variant fields that hold paths or payloads are excluded from `Display`.
- Channel `-32603` uses a fixed `message` ("internal error") with `data: null`.
- MCP `isError` results carry only the `structuredContent` codes from Conventions (`refusal`/`detail`, or `error: instance-unreachable | wrapper-fault`).

**Internal logging (for debugging):**
- Full error detail goes only to `instances/<name>/diagnostics/` (0600; format owned by obs) or, for `ui` and short-lived CLI verbs, to stderr. stderr never carries upstream text, tool `input`, drift-report values or any other value on the NEVER-log floor (Bootstrap phases, `logging-redaction-wire`). The one-time `viola ui` launch line is that floor's only exception.
- `hook` never writes to stderr and never exits non-zero (Hook Contract). A security check failing in `hook` (server verification mismatch, oversized stdin, strict-modes failure) still ends in exit 0 with no body, so the dialog renders for the human.

**Error format:**
- **GUI:** RFC 9457 Problem Details (`application/problem+json`) with `v`. Fixed `detail` strings. New `type` URNs this plan adds to Conventions:
  - `urn:viola:problem:unauthorized` (401): missing or invalid `viola_<port>` cookie or `?t=` token. Fixed `detail` that never contains the token, the launch URL, or the `.url` path or contents. No route re-issues the token (Authentication & Authorization, Token / session storage).
  - `urn:viola:problem:cross-origin-forbidden` (403, v1.x POST only).
- `urn:viola:problem:state-unreadable` must not name the unreadable path.
- **Channel:** JSON-RPC `error` for protocol faults, including `-32600` for frames over `MAX_FRAME` and `-32602` for `release`-with-`from`, and `result.refusal` for the new `not-delivered`/`control-character`.

**Error reporting integration:** None. viola makes no outbound network calls. If obs ever adds an external reporter, the Logging bans below apply before transmission.

(See `## Security Anti-Patterns` § Logging for error-disclosure bans.)

## Security Anti-Patterns (NEVER do these)

_[ALL tiers — single source of truth for all security bans]_

### Authentication

- NEVER create an interprocess Windows listener without `ListenerOptionsExt::security_descriptor`. The default DACL grants read to Everyone and anonymous.
- NEVER place a Unix socket directly in `/tmp` or at the `$TMPDIR` root (`/tmp/viola-<h12>.sock`). Always use a verified 0700 per-user directory (the Kea DHCP CVE-2025-32801/32802/32803 precedent).
- NEVER rely on `ListenerOptionsExt::mode(0o600)` as the only Unix control. It returns `Unsupported` on macOS, and `unix(7)` says socket permissions may be ignored.
- NEVER use Linux abstract-namespace sockets (no filesystem permissions).
- NEVER write any channel frame (`send`, `answer`, `hook.dialog`, `wait`/`last`, and `hook.event` notifications, which carry prompt and reply text) before verifying the server's pid (Windows `server_process_id()`) or euid + pid (Linux/FreeBSD `peer_creds()`) plus sysinfo start time against `snapshot.json` (on macOS, where `peer_creds()` gives no pid: euid + the verified 0700 socket directory only, per the recorded known gap; the euid check is never skipped), and NEVER take those reference values (`endpoint`, `pid`, `started_at`) from a `snapshot.json` that has not passed the strict-modes check in the same process.
- NEVER open a Windows client pipe without `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the default `connect_without_waiting` lets a squatter with SeImpersonatePrivilege impersonate the client).
- NEVER treat the channel `from` param as an authenticated identity. It is self-reported and serves link records and the `release` affordance guard only.
- NEVER compare the GUI token or cookie with `==`. Use `constant_time_eq`.
- NEVER issue the `viola_<port>` cookie without `HttpOnly` and `SameSite=Strict`, or leave the token in the address bar after the `?t=` exchange.
- Account-flow bans (reset enumeration, recovery questions, login rate limiting): N/A. There are no accounts or login endpoints (Threat Model: Auth model).

### Input

- NEVER trust schemars MCP schemas or client-side CLI checks alone. The wrapper re-runs `ViolaName::try_new`, the closed-enum deserialisation and `validate_paste_text`.
- NEVER join `instances/<name>` with a string that did not come out of `ViolaName::try_new` (`Last-Event-ID`, MCP `target`, `link`/`unlink` params, notify events, the brake `{name}`).
- NEVER parse `Last-Event-ID` pair by pair while skipping bad pairs. Drop the whole header.
- NEVER write `send.text` or answer free text into the PTY if it contains any C0 control other than LF, CR and TAB (ESC above all), DEL (U+007F) or any C1 control (U+0080–U+009F), and NEVER strip them silently. Reject with `control-character`. NEVER refuse LF, CR or TAB: multi-line relays, plans and answers are normal.
- NEVER run the control-character check over raw bytes. Check decoded `char`s, or valid UTF-8 continuation bytes (0x80–0xBF) are misread as C1.
- NEVER call `read_line` on a channel stream or `read_to_end` on hook stdin or child output without `Read::take(MAX_FRAME)`.
- NEVER enable serde_json's `unbounded_depth` feature.
- NEVER model `behavior`, `dialog_id`, the wheel holder or the dialog kind as free `String`s. Use closed enums or integers even under tolerant parsing.
- NEVER use a `claude agents --json` row `name` as a `ViolaName` or `target`.
- SQL ban: N/A (no database or query language).

### Data Protection

- NEVER create `~/.viola/`, `--home` or any file under it with the default umask. Directories are 0700 and files 0600 (`OpenOptionsExt::mode`). On Windows, NEVER accept a `--home` outside `%USERPROFILE%` without an explicit protected user + SYSTEM DACL, and NEVER skip the Windows owner + DACL strict-modes check at startup (`#[cfg(windows)]` must not return `Ok(())` unchecked).
- NEVER run `statusline_command` from a `snapshot.json` whose home or instance directory fails the strict-modes check. Write access there equals code execution.
- NEVER reuse an existing `bin/<version>-<hash>/viola(.exe)` without re-hashing it (SHA-256, truncated) against `<hash>`, NEVER derive `<hash>` from a non-cryptographic hash (FNV, `DefaultHasher`), and NEVER reuse existing `plugin/` files without rewriting them.
- NEVER spawn a `.cmd`/`.bat` PTY child through portable-pty. Resolve to a real `.exe` (portable-pty 0.8.1 bypasses std's BatBadBut escaping).
- NEVER make channel handles inheritable, and NEVER adopt a portable-pty replacement that calls `CreateProcessW` with `bInheritHandles = TRUE`.
- NEVER bind `viola ui` to `0.0.0.0` or `::`. Plain HTTP is acceptable only on loopback.
- NEVER derive the GUI token from anything but `getrandom` (no timestamps, pids or hashes of paths).
- NEVER commit `fixtures/claude/*` recorded from sessions that used real (non-synthetic) prompts, or before checking them for home paths and usernames.

### API

- NEVER add `tower_http::cors::CorsLayer` or any `Access-Control-Allow-*` header to `viola-ui`.
- NEVER use axum-extra's `Host` extractor for the allowlist (it can lose the port on HTTP/2), and NEVER enable axum's `http2` feature.
- NEVER apply the Host allowlist only to `/api/*`. It runs before routing on every route, including `/assets/*` and SSE.
- NEVER serve `/api/*` or SSE without the `viola_<port>` cookie check, or add a state-changing route without the cookie plus the `Sec-Fetch-Site`/`Origin` check.
- NEVER compress `text/event-stream`, and NEVER serve assets through `ServeDir` or a filesystem handler.
- NEVER make an access decision on the client address or on `X-Forwarded-For` / `Forwarded` headers. There is no proxy; access rests on the Host allowlist and the cookie.
- NEVER render event fields or unwrapped session names with `innerHTML`, `v-html`, `dangerouslySetInnerHTML` or any Markdown-to-HTML renderer, and NEVER serve inline `<script>`, inline event handlers or `eval` (GUI output-encoding elevation; API Security, Frontend output-encoding constraints).
- NEVER enable rmcp's `transport-streamable-http-server` or `auth` features.
- NEVER skip request size limits: `MAX_FRAME` on the channel, body rejection on v1.x POSTs.

### Secrets

- NEVER write `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` or any R8-stripped `CLAUDE*` value into any log or stderr, `events.ndjson`, snapshots, `diagnostics/` or fixtures (consolidated floor: Bootstrap phases, `logging-redaction-wire`).
- NEVER print or log the GUI token outside the one-time launch line and the 0600 `.url` file. NEVER log the `Cookie` request header.
- NEVER keep a credential in a URL beyond the one-time `?t=` exchange. Redirect 303 immediately and send `Referrer-Policy: no-referrer`.
- NEVER commit `.env` files, local `--home` test directories or signing material to git.
- NEVER hardcode credentials in source or in the `include_str!` plugin files.
- NEVER share one GUI token across `viola ui` launches.

### Logging

- NEVER echo serde_path_to_error drift reports or anyhow chains into Problem Details `detail`, MCP `structuredContent` or channel `error.data`.
- NEVER write to stderr from `viola hook`, and NEVER exit non-zero from it, including on security-check failures.
- NEVER print `wait`/`last` human-mode output to a terminal without escaping C0/C1 controls (the same class as RUSTSEC-2025-0055).
- NEVER use tracing-subscriber `<0.3.20` if obs selects it.
- NEVER create `diagnostics/` files readable by other users.
- NEVER expose absolute paths other than `/api/info`'s `viola_home` (cookie-gated) in any external error.

### Code Patterns

- NEVER interpret upstream text (prompts, `last_assistant_message`, plan text, tool `input`) as a viola command or config (R1). `statusline_command` is the only shell-out, and NEVER add a second one.
- NEVER build screen signatures, harness prefixes or local-command lists from runtime or upstream text. They come only from compiled `viola-agent-claude` ledger rows.
- NEVER use the cookie as anything but an opaque random value compared server-side. It carries no claims to sign.
- NEVER enable interprocess `try_overwrite` (TOCTOU deletion of an attacker-swapped file).
- NEVER feed vt100 outside `catch_unwind`. A parser panic must not take down the human's terminal path.
- NEVER reference a GitHub Action by `@stable`, `@v2` or any mutable ref. Use a full SHA with a version comment.
- NEVER restore `Swatinem/rust-cache` in the v1.x release workflow.
- NEVER ship `self_update` without its `signatures` feature (zipsign). A checksum from the same release proves nothing.

### Universal

- NEVER add a listener (TCP port, WebSocket, `http` hooks, MCP HTTP transport) or a new channel method without a Security Decisions Log entry mapping it to this plan's IPC/GUI controls.
- NEVER let a security refusal block the human. Refusals go only to automation (`send`/`answer`), and hooks fail open.
- NEVER assume the same-OS-user boundary holds on the loopback GUI without the cookie check. Loopback TCP is reachable by every local user.
- NEVER let an exec-form `command` in the embedded `hooks.json` or `.mcp.json`, or in `viola plugin install`'s `.mcp.json`, or the statusline command `viola run` writes into `instances/<name>/settings.json` (it wraps the statusline with `viola hook statusline`), resolve `viola` through PATH. It must be the absolute pinned `bin/<version>-<hash>/viola(.exe)` path, or the absolute path of the exe that ran `plugin install`. Claude Code runs these on every hook event and for MCP, so a PATH lookup hands code execution to whatever is earliest on the session's PATH (architecture.md Deployment / Distribution and Plugin Scope; Threat Model Sec 2, child process spawning and PATH resolution).
- NEVER answer a `hook.dialog` with a non-`null` decision unless `ledger/stamps.json` holds a `viola verify` stamp for the child's CLI version. NEVER let any process other than `viola verify` write `ledger/stamps.json`. A stamp is what switches on dialog answering, including PermissionRequest `allow` (Threat Model Sec 1 config; architecture.md CLI Version Compatibility).
- NEVER let a process other than the instance's own wrapper write `instances/<name>/snapshot.json`. `endpoint`, `pinned_bin` and `statusline_command` in it decide where clients connect and what `hook statusline` executes (architecture.md Instance snapshot, "written only by that instance's wrapper"; Threat Model Sec 1 config).
- NEVER let `config.json`, a `VIOLA_*` environment variable or a CLI flag switch off any control in this plan: the IPC DACL or socket-directory check, the peer or server verification, the home strict-modes check, the GUI Host allowlist, the GUI cookie check or `validate_paste_text`. Environment variables are not a configuration channel (architecture.md Cross-cutting Patterns: Config management), and `VIOLA_DIR` is set by a child any same-session agent can influence.

**Initial entry:**

`2026-09-23` — Initial security plan generated by `/andromeda-security`
- **Tier:** Minimal (0) with targeted local-boundary elevations. Justified by: local-only, single-user, no accounts, no database, no stored credentials, no regulated data.
