- tests: the parser surfaces are named in one place. No patch.

**Dim 2: Threat → Control Traceability / TMS Fidelity**
- All nine vectors map to controls or accepted risks: PATH `claude` and cross-port cookie are accepted risks, `heartbeat` is in the own-state row, disk and connection exhaustion are accepted risks. The §1 classes are covered (`permission.input`, `budget.json`, `/api/sessions`, `settings.json`). The TMS was already restored in iteration 2. No patch.

**Dim 3: Tool Anchoring**
- The SHA-256 open question is cross-referenced, with a phase and constraints. rmcp uses the floored range consistently, and external CLIs use `>=` floors. atomic-write-file over tempfile is an arch decision (architecture.md line 48), so no security justification is owed. No patch.

**Dim 4: GUI Credential Lifecycle**
- Cross-port leak is an accepted risk with a Decisions Log entry. The exchange uses constant-time comparison, returns 401 with no cookie, applies the headers to the failure response, has no recovery shortcut, and handles the stale `.url` after a crash. A same-site page on another port cannot read `/api/*` (no CORS, CORP same-origin), and the brake rejects `Sec-Fetch-Site: same-site`. No patch.

**Dim 5: Tier Calibration / Elevation Coverage**
- **Defect (Windows, integrity of `~/.viola/`):** the Windows write rule says "inherit-only ACEs may be ignored for this write rule only".
  - An `(OI)(IO)` write grant to `Users` on `bin/`, `plugin/`, `instances/<name>/` or `ledger/` passes the check.
  - Every file viola then creates inherits that grant: the pinned exe, `hooks.json`, `snapshot.json` (`statusline_command`) and `stamps.json`.
  - Result: another local user gets code execution between checks. The re-hash only catches this at the next `viola run`, while hooks run the exe on every event.
  - This contradicts the read rule, which does count inherit-only ACEs, and the Decisions Log's "tolerates only the user, SYSTEM and Administrators as writers".
  - The likely reason for the exemption was false positives on `CREATOR OWNER`. The fix is to exempt that SID specifically. **Patch 1**, with Decisions Log companion **Patch 2**.
- Over-engineering: the v1.x signing entries under "What counts as secret" are minor Standard-tier material. Deferred.

**Dim 6: Anti-Pattern Centralisation**
- The output-encoding bans are already in § API, and the `X-Forwarded-For` ban was reframed. Moving the Universal bans would be restructuring without a functional defect. No patch.

**Dim 7: API Hardening**
- Resource bounds are an accepted risk, and compression is now structural.
- Host edge cases are left implicit: missing `Host` (HTTP/1.0), `LOCALHOST` case, trailing dot, a missing port. /implement could write `headers.get(HOST).map_or(true, …)`. A one-line fix. **Patch 4.**

## Patches

### Patch 1: Windows write rule must count inheritable ACEs (only CREATOR OWNER exempt)
**Reason:** Dim 5 (integrity of `~/.viola/` on Windows) plus a cross-section inconsistency. Ignoring inherit-only ACEs lets an object-inherit write grant to other SIDs pass the check. Every file viola creates in `bin/`, `plugin/`, `instances/<name>/` or `ledger/` then inherits that write grant, so another user can replace the pinned exe or `snapshot.json`.
**Old:**
```
inherit-only ACEs may be ignored for this write rule only.
```
**New:**
```
inherit-only ACEs count for this write rule too, because files and subdirectories viola creates inherit them (an object-inherit write grant to `Users` on `bin/`, `plugin/`, `instances/<name>/` or `ledger/` would make the pinned exe, `hooks.json`, `snapshot.json` or `stamps.json` writable by other users between checks). `CREATOR OWNER` (S-1-3-0) is treated as the user for both the write and read rules, because it resolves to the creating user.
```

### Patch 2: Decisions Log companion for the inheritable-ACE write rule
**Reason:** Output Protocol rule 5 (the boundary mechanism changed) and Dim 5. The key decision must record that the writer rule also covers inheritable ACEs and that `CREATOR OWNER` is treated as the user.
**Old:**
```
that tolerates only the user, SYSTEM and Administrators as writers, and as readers
```
**New:**
```
that tolerates only the user, SYSTEM and Administrators (`CREATOR OWNER` treated as the user) as writers, counting inheritable ACEs because viola's files inherit them, and as readers
```

### Patch 3: Assign code-bearing artefact controls to a bootstrap phase
**Reason:** Dim 1 (route/setup-project). These MUST controls for the "integrity of `~/.viola/`" elevation appear in no phase, so a chunk distiller for `viola run` or `viola-state` would not surface them: always rewriting `plugin/` and `settings.json`, absolute pinned exec paths instead of a PATH lookup, and `viola verify` as the only writer of `stamps.json`.
**Old:**
```
  - `viola-state`: SHA-256 re-hash of `bin/<version>-<hash>/viola(.exe)` before reuse. The hash crate must first be picked and recorded under the Decisions Log open question.
```
**New:**
```
  - `viola-state`: SHA-256 re-hash of `bin/<version>-<hash>/viola(.exe)` before reuse. The hash crate must first be picked and recorded under the Decisions Log open question.
  - `viola run` / `viola-state`: rewrite `plugin/<version>-<hash>/` files and `instances/<name>/settings.json` with atomic-write-file (0600) at every start, never reusing an existing copy. Every exec-form `command` they carry is the absolute pinned `bin/<version>-<hash>/viola(.exe)` path, never a PATH lookup (§ Universal). `ledger/stamps.json` is written only by `viola verify`, under its `.lock`, with 0600.
```

### Patch 4: Host allowlist edge cases
**Reason:** Dim 7. The row says "exactly" but does not say what happens when there is no `Host` header or it arrives in an unusual form. /implement could treat a missing header as a pass.
**Old:**
```
It compares the raw `HOST` header exactly with `127.0.0.1:<port>` or `localhost:<port>` and returns 403 `urn:viola:problem:host-not-allowed`.
```
**New:**
```
It compares the raw `HOST` header exactly with `127.0.0.1:<port>` or `localhost:<port>` and returns 403 `urn:viola:problem:host-not-allowed`. A missing `Host` header (HTTP/1.0), any other letter case (`LOCALHOST:<port>`), a trailing-dot host, or a missing or different port also gets the 403; there is no fallback to the request URI authority.
```
