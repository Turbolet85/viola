# security extract

## Relevance
relevant — the chunk writes a new code-bearing artefact (an `.mcp.json` whose `command` Claude Code executes) under the viola home, may spawn the `claude` CLI and write under `~/.claude`, and adds a ledger row to the set that gates dialog answering.

## Constraints
- The installed plugin's `.mcp.json` `command` must never resolve `viola` through PATH: per security-plan §Security Anti-Patterns → Universal (the exec-form `command` clause), it is the absolute pinned `bin/<version>-<hash>/viola(.exe)` path or the absolute path of the exe that ran `plugin install`. Which of the two the chunk writes, and whether the exe path is canonicalised, is research's question; note that per security-plan §Data Protection (Code-bearing artefacts) only the pinned copy is SHA-256 re-hashed before reuse, so a `current_exe` path carries no hash check of its own.
- Every directory and file under `<home>/marketplace/` takes the home's modes: per security-plan §Authentication & Authorization (`~/.viola/` access control), Unix 0700 dirs / 0600 files set explicitly (never the umask), every replaced file through `viola_state::fs::replace_private`, the write discarded if the mode cannot be set; on Windows a `--home` outside `%USERPROFILE%` gets the protected user + SYSTEM DACL.
- Per security-plan §Authentication & Authorization (`~/.viola/` access control), the strict-modes check's directory and trusted-file list names `bin/`, `plugin/`, `ledger/` and the `plugin/<version>-<hash>/` folders (`hooks/`, `.claude-plugin/`), not `marketplace/`. The installed plugin is code-bearing, because Claude Code runs its `command` for MCP. Whether `marketplace/` and its `.mcp.json` join that list, and whether `plugin install` runs the check on the home before it writes, is an open question for arch/research; the plan does not settle it.
- No viola write under `~/.claude`: per security-plan §Data Protection (Accepted risk, verify's trusted runs), "viola itself writes nothing under `~/.claude`". Two things would cross that line: a `plugin install` that spawns `claude plugin marketplace add` / `claude plugin install`, and a `viola verify` precedence probe that installs and removes a plugin. Each is a boundary widening that needs the founder's own word (`inputs#I1`), not a delegate's.
- Any `claude` child this chunk spawns (in `plugin install` or in a verify probe) follows security-plan §Input Validation (Child executable resolution, Child process output): a direct spawn of the resolved program under the R8 strip, never a `.cmd`/`.bat`, stdout through `take(MAX_FRAME + 1)` with a kill bound, tolerant parse into a closed failure. Per security-plan §Threat Model Summary (Vector: child process spawning and PATH resolution), a verify step adding a live start or a run is a widening that must be shown and ratified, as verify's Runs B and E were.
- External errors from the new verb are codes only: per security-plan §Error Handling, CLI `--json` output carries no absolute path (so not the marketplace path or the exe path), no anyhow chain and no serde source, and `Display` impls use fixed messages.
- A new ledger row changes the stamp gate: per security-plan §Security Anti-Patterns → Universal (the stamp clause), a non-`null` dialog decision flows only when every row of `LedgerRow::relied()` passes. A relied 24th row makes every earlier stamp read `cli_verified:false`, and the clause's row count and its `/23` and `/20` counters are amended with it.

## Patterns to follow
- `viola_state::fs::replace_private` / `create_private_new` / `create_private_dir` for every write under the home, with the temp file's mode set before any byte is written (per security-plan §Authentication & Authorization, `~/.viola/` access control).
- `viola run`'s whole rewrite of `plugin/<version>-<hash>/` at every start, never reusing an existing copy (per security-plan §Data Protection, Code-bearing artefacts). A re-run of `plugin install` rewriting its tree mirrors it.
- Home resolution through `resolved_home` + `canonical_home` under the global `--home` (per security-plan §Input Validation, CLI arguments / Home resolution). Its `VIOLA_DIR` step and the canonicalisation are still NOT ratified.
- The bounded `claude agents --json` read in `src/run/agents.rs` (a direct spawn, the R8 strip, `take(MAX_FRAME + 1)`, killed at 5 s) is the model for any `claude plugin …` spawn (per security-plan §Input Validation, Child process output).
- `client::refused_document`'s exact `{"v":1,"error":"<code>","detail":null}` shape for a `--json` refusal: closed codes, no path or pid (per security-plan §Input Validation, CLI arguments / `revive` arguments).

## Anti-patterns to avoid
- A bare `viola`, or any PATH-resolved word, as a `command` in `viola plugin install`'s `.mcp.json`. Also any `hooks` content in the installed plugin, since the wrapped session must not run two hook processes per event (per security-plan §Security Anti-Patterns → Universal).
- Creating marketplace files or dirs under the default umask, or reusing an existing code-bearing file without rewriting it (per security-plan §Security Anti-Patterns → Data Protection).
- Spawning `claude` through `sh`/`cmd` or as a `.cmd`/`.bat` PTY child, or interpreting CLI output as a command (per security-plan §Security Anti-Patterns → Data Protection and → Code Patterns: `statusline_command` stays the only shell-out).

## Contract bindings
- security ↔ obs: the `cli.plugin_install` span and `process-start` / `process-exit{exit_code, detail}` lines (obs-plan §4) fall under the NEVER-log floor (security-plan §Bootstrap phases, `logging-redaction-wire`). No absolute path reaches CLI `--json` error output, and no R8-stripped `CLAUDE*` value reaches any line.
- security ↔ tests/fixtures: if a precedence probe records with `--record`, its fixture passes the scrub and refusal codes `home-path` · `absolute-path` · `username` · `email` (security-plan §Data Protection, Repository fixtures). An `.mcp.json` holding the absolute exe path would be refused, not kept.
- security ↔ arch: the `marketplace/` tree's place on the strict-modes trusted list (security-plan §Authentication & Authorization) is tied to architecture §Directory tree and §Plugin Scope.
- security ↔ ledger/verify: a new verify probe step inherits verify's child-spawn bounds and its no-key-into-any-dialog rule (security-plan §Threat Model Summary, Vector: child process spawning and PATH resolution).

## Acceptance criteria contributions
- The written `.mcp.json` registers `viola` with an absolute `command` (the pinned path or the running exe's absolute path) and `args: ["mcp"]`. The installed plugin holds no `hooks.json` and no `hooks` key. A case pins both, and none passes with a bare `viola` (per security-plan §Security Anti-Patterns → Universal).
- On Unix, every directory under `<home>/marketplace/` reads mode 0700 and every file 0600, with the umask set permissive during the test. A re-run rewrites the tree to the same bytes and modes (per security-plan §Authentication & Authorization, `~/.viola/` access control).
- Every `viola plugin install --json` refusal document holds only a closed code with `detail` null, and no absolute path appears on its stdout or stderr (per security-plan §Error Handling).
- Two measurements are recorded as evidence. First, the live round shows that a registered `viola mcp` exiting 1 does not block the human's `claude` start; a block is a finding against "NEVER let a security refusal block the human". Second, the chunk's viola code writes nothing under `~/.claude` unless the founder's own word for that write is cited (per security-plan §Security Anti-Patterns → Universal; security-plan §Data Protection, Accepted risk).
