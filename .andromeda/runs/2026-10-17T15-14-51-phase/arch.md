# arch extract

## Relevance
relevant — the chunk serves an occupied-but-unserved subcommand (`plugin install`), writes the reserved `marketplace/` tree, and adds a capability-ledger row the plan already names (plugin precedence).

## Constraints
- The installed plugin carries only `.mcp.json` (no hooks, ever), so a wrapped session that also has it installed never runs two hook processes for one event; its `command` is the absolute path of the exe that ran `plugin install`, never a PATH lookup (per architecture §Established Decisions → [Plugin Scope]). Whether "the exe that ran it" means the canonical `current_exe` or a pinned `bin/<version>-<hash>/viola` copy is not settled by the plan; the plan names the per-frame `v` + sender version as the safety net for an install not bound to a wrapper's pinned copy (per architecture §Established Decisions → [Deployment / Distribution]).
- Whether Claude Code loads both a `--plugin-dir` plugin and an installed plugin of the same name, and which `viola` MCP server a wrapped session then uses, is a capability-ledger row, not an assumption (per architecture §Established Decisions → [CLI Version Compatibility], its "Plugin precedence" row; and per architecture §Cross-cutting Patterns → Capability ledger as the single gate: a new undocumented-CLI dependence is a row in `viola-agent-claude` with a `viola verify` probe carrying a post-condition check).
- `marketplace/` under the viola home is written only by `viola plugin install` (per architecture §Occupied Resources → Filesystem); every replaced file there goes through the one helper `viola_state::fs::replace_private`, mode set before any byte (per architecture §Established Decisions → [Snapshot writer]); a path written into a plugin file uses forward slashes (per architecture §Cross-cutting Patterns → Cross-platform discipline).
- The plugin name and the MCP server name are both `viola`, and its tools reach a session as `mcp__plugin_viola_viola__<tool>` (per architecture §Occupied Resources → Claude Code integration names) — the installed plugin reusing that name is exactly what the precedence row measures.
- The verb follows the CLI contract: human text by default, `--json` for agents, a typed exit code per refusal (per architecture §Established Decisions → [CLI Conventions]); its `--json` documents take the `{"v":1,"ok":{…}}` / `{"v":1,"error":"<code>","detail":null}` shapes, codes only, no path (per architecture §Standard Contracts → CLI `--json` output); exit codes stay within the occupied set `0, 1, 2, 10–14, 20, 21` (per architecture §Occupied Resources → Binary, subcommands and exit codes) — a new code would be an amendment, not a free choice.
- Whether a registered `viola mcp` that exits 1 (its start-time home / `diagnostics/` `check_path` refusal) blocks the CLI's start is recorded as unmeasured; the exit-2 "would block" claim is an operator ruling, never a measurement (per architecture §Established Decisions → [Deployment / Distribution]; `mcp`'s exit-1 shape per architecture §Occupied Resources → Binary, subcommands and exit codes).
- Any `claude` child the verb or its probe spawns (e.g. `claude plugin …`, if the founder's word allows a spawn) is spawned directly, never through `sh`/`bash`/`cmd` (per architecture §Cross-cutting Patterns → Cross-platform discipline); the new verb's code stays on std threads and blocking I/O — only `viola-mcp` builds a runtime (per architecture §Cross-cutting Patterns → Tokio containment).

## Patterns to follow
- The embedded plugin pattern: plugin templates live under `plugin/`, embedded via `include_str!`, `plugin.json`'s version from `CARGO_PKG_VERSION`, the exe path substituted into every exec-form `command` at write time (per architecture §Established Decisions → [Deployment / Distribution]); the `.mcp.json` registration shape `{"mcpServers": {"viola": {"command": <abs>, "args": ["mcp"]}}}` is the one already landed for the `--plugin-dir` plugin (same anchor).
- Claude-specific shapes (the marketplace manifest, the installed plugin's `.claude-plugin/plugin.json` / `.mcp.json` documents, the new ledger row and its `check`) belong in `viola-agent-claude` beside `plugin_files` and the pure `ledger` module (per architecture §Infrastructure Patterns → Crate dependency direction; per architecture §Inherited Defaults, Agent isolation).
- The verb's dispatch lands as one module per subcommand in `src/cmd/` — the tree already reserves `plugin` there (per architecture §Infrastructure Patterns → Project directory structure); the home comes from the global `--home` through `resolved_home` / `canonical_home` like every verb arm of `dispatch` (per architecture §Cross-cutting Patterns → Config management). Whether `src/cmd/plugin.rs` already exists is research's question.
- A new ledger row joins `LedgerRow::ALL` with its per-OS relied membership (`relied()`), probed by a `viola verify` run step with a post-condition (per architecture §Cross-cutting Patterns → Capability ledger as the single gate; per architecture §Established Decisions → [CLI Version Compatibility]).

## Anti-patterns to avoid
- No PATH lookup in any `command` the verb writes, and no hooks entry in the installed plugin (per architecture §Established Decisions → [Plugin Scope]; "Hooks and MCP never search PATH" per architecture §Established Decisions → [Deployment / Distribution]).
- No hard-coded assumption about which same-named `viola` server wins, or about `viola mcp` exit 1 not blocking the CLI — each is a measured row or an open measurement, never presumed (per architecture §Cross-cutting Patterns → Capability ledger as the single gate).
- No new environment variable or config channel for the verb (no flag/env disabling a control): `VIOLA_*` is wrapper-to-child plumbing set by `viola run` only (per architecture §Cross-cutting Patterns → Config management).

## Contract bindings
- arch ↔ security: the absolute-path `command` and the `~/.claude` write boundary (a `claude plugin …` spawn or a verify probe installing a plugin writes under `~/.claude`, which the plan's verify residual does not cover) — arch §Established Decisions → [Plugin Scope] binds to security-plan's NEVER clause on `viola plugin install`'s `.mcp.json` and its Data Protection residual.
- arch ↔ tests: the precedence row changes `LedgerRow::ALL` (23 today per architecture §Infrastructure Patterns → Crate dependency direction) and, if relied, the relied set that gates `cli_verified` (per architecture §Established Decisions → [CLI Version Compatibility]); verify's probe and its fake-agent replay are the test plan's.
- arch ↔ obs: a CLI verb's codes-only process log goes to `diagnostics/cli-<name>.ndjson` (per architecture §Cross-cutting Patterns → Diagnostic output channels); the producer list in architecture §Occupied Resources → Filesystem (`diagnostics/`) does not yet name `plugin install`.
- arch ↔ design: `viola --help`'s `setup:` row gains `plugin install` once served (the occupied subcommand list, per architecture §Occupied Resources → Binary, subcommands and exit codes; layout is the design plan's).
