## Relevance
relevant — a new served CLI verb (`--json` / exit contract, on-disk writes under the home), a possible 24th capability-ledger row probed by `viola verify` (moves the verify, contract and harness row literals), the `viola --help` literal move, and live-only measurements that the plan confines to local evidence.

## Constraints
- test-plan §5 Cross-module patterns (CLI) requires root `tests/cli_*.rs` to cover the `--json` document per exit code, and §1 Coverage scope already lists `plugin install` among the CLI verbs under that contract. So the verb's first serving needs a case for each exit it can take. The labelled case table of `tests/cli_machine_contract.rs` is the shape for a document plus a literal exit. Whether that file or a new `cli_plugin_install.rs` hosts it is a decision for planning.
- test-plan §5 Cross-module patterns (CLI) pins `viola --help` through the `HELP` literal of `help_is_the_grouped_verb_table`, and makes `help_lists_only_served_verbs` assert that no `plugin` appears in the table. Serving `plugin install` therefore requires both literals to move together, and the "no `plugin`" exclusion in that case to be restated. The completeness case of `tests/cli_controls_not_disableable.rs` (in the same section) requires every long flag in `viola --help`'s `Options:`, every `config.json` property and every `VIOLA_*` literal in product sources to be a row of its table. Whether this verb adds any of them is research's question.
- test-plan §5 Cross-module patterns (CLI) fixes the relied row literals at 23: `ROW_IDS: [&str; 23]` in `contract_ledger_probes.rs`, `STEPS_PASS` / `ROW_IDS` in `tests/cli_verify.rs` (23 on Unix / 20 on Windows, step lines `[NN/MM]`), and the last line `stamped <ver>  <n> pass  0 fail` with `<n>` the relied count. A new precedence row changes each per-OS literal, and if the row is relied, the `cfg(unix)` / `cfg(windows)` relied counts change too. That includes the fixed fail counts of the no-dialog, no-framing and modal-screen cases (`19 pass  4 fail`, `21 pass  2 fail` and the rest).
- test-plan §3 `run` (5-command implementation) requires `--local-live`'s suite to check each relied literal row id in `LEDGER_ROWS` (`[&str; 23]` under `cfg(unix)`) and `LIVE_PASS` under the same split (`run_local_live_reads_the_relied_rows`). A new relied row moves those harness literals too. `--local-live` refuses in CI (`live-in-ci`, exit 2).
- test-plan §7 Seed strategies requires `ledger/stamps.json` to come only from `viola verify --home` run against the fake agent (`stamped_home`, the harness `boot`). A relied precedence row is one the fake agent cannot answer, and every stamped test home would then read `cli_verified:false`. So the fake agent needs a recorded or replayed shape for the new probe. Whether the probe can be expressed on the fake agent without a write under `~/.claude` is research's question. The same row requires on-disk product state to be produced only by running real verbs in a fresh home, never hand-written. A test reads the marketplace tree only as `viola plugin install` wrote it.
- test-plan §7 Fake agent (binding contract behaviour) requires the fake agent to read hooks only from `<plugin-dir>/hooks/hooks.json` and to spawn only absolute commands, receipting a non-absolute one `command_absolute:false, ran:false`. It grows only by argv options or mode words, with no env var. Any fake-agent support for an installed same-name plugin, or for `claude plugin …` subcommands, follows that rule, and its option count is the architecture list's rule.
- test-plan §6 Non-path suites (Security control negatives, Single writers) requires `ledger/stamps.json` and `snapshot.json` to stay byte- and mtime-unchanged when every writer-capable entry point other than their owners runs. `viola plugin install` is a new writer-capable entry point. The same suite's umask-independent-modes case requires home files at 0600 and directories at 0700 under `umask 000`. The marketplace tree under the home is held to that, per architecture's disk rule. Whether the existing case reaches anything beyond `viola run` is research's question.

## Patterns to follow
- A per-test fresh `--home` created by viola under `tempdir_in("<workspace root>/target/e2e-home")` through `TestHome`. Test-started `viola` drops `VIOLA_NAME` / `VIOLA_DIR` / `VIOLA_BIN` (`UNWRAPPED`), and a path oracle compares `resolved(home)`, never `TestHome::path()` (test-plan §5 Setup / teardown lifecycle; §5 Cross-module patterns (CLI), home resolution).
- One started-child runner and guard in `tests/support/cli.rs` (`spawn` / `viola`, `spawn_on` / `viola_on` with a planted bin dir on `PATH`), with no copy of the runner in a test file. `tests/support/fake.rs` (`claude_bin` / `claude_in` / `empty_bin`) is the one place a test plants the fake agent as `claude`. Any test of a verb that might spawn `claude` runs under a test-scoped `PATH` (test-plan §2 Test directory + naming conventions; §7 Seed strategies, `claude agents --json` row).
- Ledger arms are pinned in `viola-agent-claude` unit cases named `check_<row>_passes_on_the_recorded_shape`, `check_<row>_fails_on_each_broken_post_condition` and `check_<row>_fails_with_no_capture`, beside the relied-set cases (`verified` reads `LedgerRow::relied()`). The version gate's older-stamp oracle in `src/run/version_gate.rs` holds that a stamp of only the older ids reads unverified (test-plan §4 What unit tests cover, viola-agent-claude).
- The umask negative runs `sh -c 'umask 000; exec viola …'` and reads modes back with `std::fs::metadata` (test-plan §6 Non-path suites, Security control negatives).
- Integration files are named `<surface>_<topic>.rs` (`cli_`), and test functions `<subject>_<condition>_<expected>` in snake_case (test-plan §2 Test directory + naming conventions).

## Anti-patterns to avoid
- NEVER import the product's ledger rows (`LedgerRow::ALL` / `relied()`) as the test oracle. Row ids and counts are literals in the test (test-plan §11 Unit).
- NEVER run the real `claude` in CI, and NEVER treat a green fake-agent run, or a Linux-only local run, as proof of real-CLI precedence or exit-1 behaviour. Both live readings are this chunk's own local measurement in its `evidence/`, not a test layer and not harness surface (test-plan §11 Test Strategy; §6 Drivers per surface, the "untestable" list).
- NEVER hand-write `ledger/stamps.json` or `snapshot.json`, and NEVER commit a `--home` test dir (test-plan §11 Test Data).

## Contract bindings
- tests ↔ obs: the `cli.plugin_install` span and the `process-start` / `process-exit` lines under `VIOLA_NAME` land in home-level `diagnostics/*.ndjson`, which the G4 schema-conformance check validates against `schemas/diag-line.v1.json` over `target/e2e-home/**`. The secret and canary scan covers the same tree (test-plan §6 Non-path suites, Schema conformance / Error sanitization and secret scan).
- tests ↔ security: the error-sanitization scan requires CLI `--json` documents to carry no absolute path (`/home/`, `/Users/`, drive letter, temp home prefix). Meanwhile the written `.mcp.json` `command` must be the absolute exe path (the security-plan NEVER clause). Whether the verb's `--json` result or any printed `claude plugin …` step can name the marketplace or exe path without failing that scan is research's question (test-plan §6 Non-path suites, Error sanitization and secret scan).
- tests ↔ architecture: `LedgerRow::ALL` and the relied set drive the verify step counter, `contract_ledger_probes.rs` and the harness `LEDGER_ROWS`, all as literals (test-plan §5 Cross-module patterns (CLI); §3 `run`).

## Acceptance criteria contributions
- `viola plugin install --home <fresh>` has root `tests/cli_*.rs` cases that read its `--json` document and literal exit for each exit it takes. The written `.mcp.json` names `viola` with an absolute `command` and `args` `["mcp"]`, the installed plugin carries no hooks file, and a re-run leaves the same tree (per test-plan §5 Cross-module patterns (CLI)).
- `help_is_the_grouped_verb_table` passes with `plugin install` in the `HELP` literal's `setup:` row, and `help_lists_only_served_verbs` passes with `viola plugin install --help` exiting 0 and the "no `plugin`" exclusion restated (per test-plan §5 Cross-module patterns (CLI)).
- If a precedence row joins the ledger, three things hold. `contract_ledger_probes.rs` and `tests/cli_verify.rs` list each relied literal row id once and end `stamped <ver>  <n> pass  0 fail`, with `<n>` the new per-OS literal relied count. The harness's `LEDGER_ROWS` / `LIVE_PASS` move with it. `stamped_home` still stamps with 0 fail against the fake agent (per test-plan §5 Cross-module patterns (CLI); §3 `run`).
- The per-OS coverage gate holds for the new code: `--fail-under-lines 85 --fail-under-functions 95 --fail-under-regions 80`, no widening of `COVERAGE_IGNORE`, `retries = 0` (per test-plan §10 Coverage thresholds / Zero-flakiness budget).
