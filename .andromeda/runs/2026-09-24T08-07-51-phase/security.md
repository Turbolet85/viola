# security extract

## Relevance
Partial. This chunk is test infrastructure, not a product trust boundary. It touches fixture and data hygiene, secret non-leakage into receipts and fixtures, new dev dependencies under cargo-deny, and the fake-agent doubles of several security-relevant parser surfaces.

## Constraints
- Committed fixtures (`fixtures/fake-scripts/*.json` and any future `fixtures/claude/<cli-version>/`) must hold synthetic text only and be checked for home paths, usernames and tool `input` before commit. The chunk's scrub-and-schema walk is the automated form of this rule for paths and usernames. Tool-`input` review is not covered by the regex set, so it stays a manual check (per security-plan §Data Protection, "Repository fixtures"; §Security Anti-Patterns › Data Protection, the `fixtures/claude/*` ban).
- Receipts record "env names" only, never values. `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` and every other R8-stripped `CLAUDE*` value must never be written to any fixture, log, diagnostic or stderr. This matters here because tests often run inside a live Claude Code session whose real token is in the inherited environment (per security-plan §Bootstrap phases `logging-redaction-wire`; §Security Anti-Patterns › Secrets; §Secret Management "What counts as secret").
- Local `--home` test directories must never land in git, and `.gitignore` must exclude them. Whether `<workspace>/target/e2e-home/` is already covered, for example by a `target/` ignore, and whether `AGENT_RUN_KEEP_HOMES=1` / `AGENT_RUN_KEEP_FAILED=1` kept homes stay inside that ignored tree, is for research to confirm (per security-plan §Bootstrap phases `secret-scanning-ci-gate`; §Security Anti-Patterns › Secrets "NEVER commit … local `--home` test directories").
- The fixture `home` must be a path that does not exist yet, so the product creates it. §Authentication & Authorization (`~/.viola/` access control) requires 0700/0600 creation and a strict-modes check with a read rule that refuses a pre-existing home carrying group/other permissions or foreign ACEs. A fixture that pre-creates the home with tempfile/umask defaults would undermine or falsely trip that later check. Whether HEAD's `run` already enforces any of this is research's question. The amendment history says it does not yet (per security-plan §Authentication & Authorization, `~/.viola/` access control row; §Security Anti-Patterns › Data Protection, the umask ban).
- The fake agent's hook invocation must run the exact exec-form `command` written into `plugin/…/hooks.json` / `instances/<name>/settings.json` and never resolve `viola` through PATH. The double must not paper over a product PATH lookup. A test-written command that is not an absolute pinned path should be observable in the receipt, not silently fixed (per security-plan §Security Anti-Patterns › Universal, exec-form `command` ban; §Data Protection "Code-bearing artefacts").
- New dev dependencies (rstest, tempfile, proptest, jsonschema, and whatever the fake bin needs) must be pinned in `[workspace.dependencies]`, resolve from crates.io only, and pass `cargo deny check` (C-build ban, `tokio` ban in the sync crates' graph, advisories, `[sources]`). jsonschema's default features may pull an HTTP client or TLS stack (remote `$ref` resolution). Whether the chosen feature set stays pure Rust and deny-clean is research's question (per security-plan §Dependency Security "Pinning", "`deny.toml` additions", "CI integration").
- Test-only knobs (`FAKE_CLAUDE_AGENTS_MODE`, `AGENT_RUN_KEEP_*`, the fake-agent flags) must stay inside the `fake-agent`-feature bin and the harness. None of them may become a `VIOLA_*`, config or CLI path that can switch off a product control (per security-plan §Security Anti-Patterns › Universal, the "NEVER let `config.json`, a `VIOLA_*` environment variable or a CLI flag switch off any control" ban).

## Patterns to follow
- Per-child environment through `Command::env` and never `std::env::set_var`. This lets tests witness the R8 strip at the child boundary without leaking values process-wide (per security-plan §Secret Management "Storage", inherited credentials).
- Fake-agent modes that act as adversarial inputs to the parser surfaces the plan lists for fuzz/property coverage. `--vt100-panic-bytes` targets vt100 under `catch_unwind`. `FAKE_CLAUDE_AGENTS_MODE=oversize|malformed` targets `claude agents --json` parsing, which must be `MAX_FRAME`-bounded, tolerant, and map failure to `unknown`. Receipts with raw hex and `bare_esc` target the bracketed-paste / `validate_paste_text` breakout class. The doubles should produce hostile input faithfully, including the embedded `ESC[201~` and C0/C1 bytes (per security-plan §Input Validation "Parser surfaces", PTY output row, child-process output row, paste-text row; §Threat Model Summary, CLI input vector).
- `ViolaName` proptest strategies should cover the `[a-z0-9-]` charset boundary and path-join-hostile inputs (`..`, separators, uppercase, control chars), because `ViolaName::try_new` is the only gate before any `instances/<name>` join (per security-plan §Security Anti-Patterns › Input "NEVER join `instances/<name>` …"; §Input Validation CLI arguments row).
- The scrub walk's rejection arms (`^[A-Za-z]:[\\/]`, `/home/`, `/Users/`, `\\Users\\`, non-placeholder usernames) must be proven on planted bad inputs. The OS username is the only PII in scope (per security-plan §Threat Model Summary, operational metadata; §Bootstrap phases `logging-redaction-wire`, the operational-metadata bullet).

## Anti-patterns to avoid
- Committing fixtures or scenario scripts that contain real prompts, absolute home paths or real usernames (per security-plan §Security Anti-Patterns › Data Protection).
- Writing any `CLAUDE*` credential value, or any other secret, into a receipt, fixture, kept test home artefact or test stderr (per security-plan §Security Anti-Patterns › Secrets).
- Adding a CI step that interpolates an event-payload value through `${{ }}` inside `run:`. If item 7's mutation-gate fix touches `ci.yml`, values like `AGENT_RUN_CHUNK_BASE` must go through `env:`, and actions stay full-SHA pinned (per security-plan §Dependency Security "CI integration"; §Security Anti-Patterns › Code Patterns, the mutable-ref ban).

## Contract bindings
- security §Data Protection "Repository fixtures" ↔ the tests-domain fixture hygiene walk (test-plan §7 Fixture hygiene) ↔ obs PII scrubbing. Username-in-path is the shared PII definition.
- security §Secret Management / `logging-redaction-wire` NEVER-log floor ↔ the fake-agent receipt format (a harness-owned test format). Receipts carry env names only.
- security §Dependency Security `cargo deny check` job ↔ tests §CI Integration (one `ci.yml`, deny as job 4 on ubuntu). The new dev-deps and the item-7 mutants change land in that same workflow.
- security §Input Validation parser surfaces ↔ fake-agent modes (oversize/malformed agents JSON, vt100 panic bytes, bracketed-paste receipts). Tests owns the cases, and security owns the floors those cases must witness.

## Acceptance criteria contributions
- A planted fixture containing an absolute home path (Windows drive, `/home/`, `/Users/`, `\Users\`) or a non-placeholder username fails the scrub walk, and the walk asserts a nonzero match count, so it cannot pass vacuously on the empty `fixtures/claude/` glob (per security-plan §Data Protection "Repository fixtures").
- A test runs the fake agent with a sentinel value in `CLAUDE_CODE_MESSAGING_TOKEN` and asserts that the receipt holds the variable name at most and never the sentinel value (per security-plan §Bootstrap phases `logging-redaction-wire`).
- `cargo deny check` passes with the new dev-dependencies, all pinned in `[workspace.dependencies]` and resolved from crates.io (per security-plan §Dependency Security "CI integration").
- `git check-ignore` confirms that `target/e2e-home/` (including kept homes) is ignored (per security-plan §Bootstrap phases `secret-scanning-ci-gate`).
