# a11y extract

## Relevance
partial. The chunk builds no UI. It changes the harness `boot` / `status` lifecycle, which a11y-plan §3 and §9 make the entry point of every browser a11y spec. It also changes the stamped/unstamped state that the a11y web paths render (the `cli_verified:false` strip, unverified-CLI withholding). And it touches `viola verify`, whose CLI step-line output is a11y-plan §4 P6 surface.

## Constraints
- Tier Standard (1), and the WCAG AA label applies to web-spa only. cli/tui get output-discipline stand-ins with no conformance claim (per a11y-plan §1 A11y Scope Summary). Nothing in this chunk may claim or widen WCAG conformance for the `verify` CLI output or the harness.
- The browser a11y suite runs through the tests' 5-command discipline. Each test uses `boot --session pw-<spec>-<test id>-<workerIndex>`, then `/?t=<token>` from `ui/<port>.url`, then `cleanup`. `status` (`state:"ready"`) is the readiness precondition and `logs` is the triage read (per a11y-plan §3 CI integration; §9 Pipeline integration). Adding `boot` step 4 (stamp through `viola verify`), the `--unstamped` opt-out, the `verify-failed` typed outcome and readiness line 3 must keep that per-test lifecycle intact for `run --browser` on all three OS legs.
- The a11y web paths render the unverified-CLI states: the WRAPPED rack's `cli_verified:false` strip state (per a11y-plan §1, WRAPPED rack entity) and P3 "unverified-CLI withholding" (per a11y-plan §4 Critical Paths 3). Once `boot` stamps by default, any browser spec that asserts those states needs the explicit `--unstamped` form. Whether any `e2e-web/` spec already boots a session that depends on the current no-stamp default is research's question.
- `verify` CLI output discipline: step lines `[NN/NN] … pass|fail`, linear and static, no `\r` redraw or spinner, no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`, and `fail` carrying no SGR (per a11y-plan §4 Critical Paths 6 and §4 P6 assertion list). The new `version-probe` / probe-child spawn logging (item 7) goes to the process log. It must not change `verify`'s stdout/stderr step lines. Whether assert_cmd/trycmd tests already pin those lines is research's question.
- Zero-flake budget: Playwright `retries: 0`, and timing keys on logged events and DOM signals, never sleeps (per a11y-plan §10 Performance budget and Cross-input parallel). The added `boot` stamp step must reach readiness by an event, never a sleep, and its added wall time counts toward the < 10 min `run --browser` ubuntu budget (per a11y-plan §10 Performance budget).
- `browser-missing` is a failure, never a skip, and the a11y verdict is judged on the ubuntu leg only (per a11y-plan §9 Pipeline integration). A new `verify-failed` boot outcome must likewise surface as a failure to the browser suite, never as a skip.

## Patterns to follow
- One harness, one driver: a11y specs are ordinary `e2e-web/` files in the existing `playwright` suite, and results land in `suites[{suite:"playwright",…}]` with `gate --require playwright` (per a11y-plan §3 CI integration). Harness changes extend `boot` / `status` / `run`, not the suite set.
- The CLI P6 assertions run through assert_cmd / trycmd for non-TTY output and the portable-pty outer PTY for TTY behaviour, inside the `coverage` suite on all three OS legs (per a11y-plan §4 P6; §9 table, Unit / integration row). Any `verify` output assertion added here follows that pattern.
- The fake agent is the sanctioned source of test events. P6's C0/C1 escaping setup already drives `viola wait` / `viola last` from a `viola-fake-agent` event (per a11y-plan §4 P6). Moving the fake agent's default version to the recorded `2.1.283` must keep those setups running.

## Anti-patterns to avoid
- NEVER add a `suite` value (such as `a11y`), a `webServer`, or a separate driver outside `scripts/agent-run.* run --browser` (per a11y-plan §11 CI). `run --local-live` stays a separate run mode and is never a second browser driver.
- NEVER treat `browser-missing` as a skip, and never park a spec with `test.skip` / `test.fixme` / quarantine (per a11y-plan §11 CI, SLO). The same applies to a spec that meets a `verify-failed` boot.
- NEVER colour CLI `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` (per a11y-plan §11 Visual). This covers the `verify` step lines the chunk touches.

## Contract bindings
- a11y ↔ tests harness: the browser a11y lifecycle binds to test-plan §3's `boot` / `status` / `cleanup` / `logs` contract (per a11y-plan §3 CI integration; §9 Pipeline integration). The `boot` readiness line 3, `--unstamped` and `verify-failed` changes are test-plan §3 changes that the a11y specs consume.
- a11y ↔ obs: the a11y violation rows mirror obs field names (per a11y-plan §3 Structured violation JSON schema). The `diag-line.v1.json` `subject` amendment (item 7) is additive to the process-log shape. Renaming an obs binding field is banned (per a11y-plan §11 Universal).

## Acceptance criteria contributions
- A browser spec's `boot --session pw-…` still reaches `status` `state:"ready"` with the stamp step in place, and `run --browser` stays green on all three legs, with the a11y verdict judged on ubuntu (per a11y-plan §9 Pipeline integration).
- Any web a11y state that depends on an unverified CLI (the `cli_verified:false` strip, P3 withholding) is booted through the explicit `--unstamped` form. No spec relies on the removed no-stamp default (per a11y-plan §4 Critical Paths 3; §1 WRAPPED rack entity).
- `viola verify` human-mode output is still `[NN/NN] … pass|fail` step lines, with no SGR under non-TTY / `NO_COLOR` / `--json` and none on `fail`, after the spawn-logging change. assert_cmd covers it in the `coverage` suite (per a11y-plan §4 P6).
- A `verify-failed` boot fails the run with its typed outcome and is never counted as a skip (per a11y-plan §11 CI, SLO).
