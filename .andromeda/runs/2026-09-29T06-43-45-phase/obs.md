## Constraints
- Child spawns log a `process-start` / `process-exit` pair with a closed `subject`; `version-probe` carries `child_exit_status` + `duration_ms` (per obs-plan §6 Boundary-call wrappers → Child / shell spawns; §4 Scenario 1 required log fields). The §6 `subject` enum today is `self|claude-child|version-probe|agents-probe|statusline-shell`, so the verify print-mode probe child needs a NEW `subject` value. It must enter the §6 additive field catalog and `schemas/diag-line.v1.json` together, because the schema is default-deny (per obs-plan §8 Default-deny posture; §11 PII Scrubbing "NEVER log any field not named in the Section 6 catalog"). It lands through the wrap amendment path with a §12 Decisions Log entry (per obs-plan §3 Log format JSON schema, closed-enum rule; §11 Logs). The §5 `viola.child.exit` counter groups by `subject`, so the new value stays a closed kebab-case code.
- `run_bounded` is shared by `run`'s version gate and `verify` (scope item 7). §4 Scenario 1 already requires `run` to log the `version-probe` pair inside `run.version_gate`. Whether `run` does that today is research's question. Placing the lines in the shared helper or at the verify call sites must leave exactly one pair per spawn on each path, with no duplicate on `run` (per obs-plan §4 Scenario 1; §10 Deterministic emission).
- `verify` logs to `cli-<name>.ndjson` only when `VIOLA_NAME` is set. With no instance (a plain terminal, and most likely the test-home stamping path) it writes no process-log file. Its outcome is then the exit code plus the `[NN/MM] … pass|fail` / `stamped <version>` stdout (per obs-plan §4 E-flows `verify` / `plugin install`; D-06). No obs gate depends on verify's own lines. When they exist, they fall under G2, G4 and the secret scan (per obs-plan §4 `verify` bullet 4).
- The ledger read keeps its obs outcome: a missing stamp gives `cli_verified:false` on `process-start{subject:"claude-child"}`, and an unreadable or unparsable `ledger/stamps.json` gives `parse-rejected{parser:"ledger-stamps", detail:"unreadable"|"malformed", count}` in `run-<name>.ndjson`. The path and stamp contents never appear (per obs-plan §4 Capability ledger; §6 `detail` code catalog). Folding `StampError::Malformed` into `AgentError` (CARRY 4) must keep that mapping and a fixed-message thiserror `Display` (per obs-plan §7 Platform pick, scrubbing layer 1).
- Every integration-test home, meaning each `StampedHome` now stamped through `viola verify`, the explicitly-unstamped form, `contract_ledger_probes.rs` homes and harness `boot` homes, lives under `target/e2e-home/`. That keeps G2, G4, the secret scan and the `diag-<os>` upload over them. A `hook` panic exits 0, so a home outside that root hides it (per obs-plan §9 Pipeline integration → Integration tests row; §10 Zero unlogged panics).
- The hook fail-open path (item 8) logs `hook-invoked` + `hook-decision{detail}` with `detail` from the closed fail-open list (`channel-unreachable`, `server-verify-failed`, …) at `warn`, `corr` null. `channel-request` is logged per IPC invocation, and a `hook.event` notification's `channel-request` carries a null `corr` (per obs-plan §6 `detail` code catalog and Log levels mapping; §6 Boundary-call wrappers → IPC invocation; §3 Log format, `corr` rules). The red's extra `channel-request` means the hook reached some endpoint. Whether the hook client logs `channel-request` only after a successful connect is research's question.
- `run --local-live` drives the real `claude`, so its inputs are not synthetic. Uploading `detail-*.ndjson` and `target/agent-run/` is admissible only because every CI input is synthetic, and a non-synthetic source must first drop those upload paths. The `live-in-ci` refusal is what keeps the local-live home and its harness capture out of every CI upload (per obs-plan §8 Integration points item 6, detail-file upload and "Any non-synthetic input source …").

## Patterns to follow
- Emit through `obs_event!` only, with typed `key = value` fields. `message` is the static event name, and `process` / `instance` come from `ProcessCtx` (per obs-plan §3 Logging stack).
- Spawn pair shape: `process-start{subject}` before the spawn, `process-exit{subject, child_exit_status, duration_ms}` after the bounded wait. This mirrors `statusline-shell` / `version-probe` (per obs-plan §4 Scenario 1 and Scenario 6 Budget governor).
- Dispatch spans for verify: `cli.verify` › `cli.verify_step` per step › `state.ledger_write`, all as `#[instrument(skip_all, fields(..))]` (per obs-plan §4 `verify` / `plugin install`; §8 Integration points item 1).
- The harness reads readiness line 3 (`session-start{source:"hook"}`, record three of `events.ndjson`) through `agent-run logs --kind`. It is not duplicated into process logs (per obs-plan §4 Scenario 1 required log fields, last bullet).
- A schema amendment follows the precedent: the hand-maintained `schemas/diag-line.v1.json` enum and the §6 catalog change together, and the tests-owned conformance check (`tests/contract_diag_schema.rs`) proves the schema accepts the new value and still rejects an unknown one (per obs-plan §3 Bootstrap phases → log-format-schema-emit; §8 Default-deny posture).

## Anti-patterns to avoid
- No bare `#[instrument]`, no raw `tracing::{event,info,…}!`, no `print!`/`eprintln!` in product paths of the new spawn logging or the error-enum fold. The fake agent and `viola-harness` stay the only print-exempt members (per obs-plan §11 Spans / Traces and Logs; §3 obs-ci-gate-wire).
- No paths, pids, the probe's argv or captured payloads in any `detail` code or home-level field. Log only `subject`, `child_exit_status` and `duration_ms` for the probes (per obs-plan §11 PII Scrubbing; §6 `detail` code catalog).
- No sleeps or retry-once to steady the item-8 witness or the harness readiness wait. A green re-run is not a close (per obs-plan §10 Deterministic emission and Cross-input parallel; §11 SLO).

## Acceptance criteria contributions
- `viola verify` run with `VIOLA_NAME` set writes, into `cli-<name>.ndjson`, one `process-start` / `process-exit{subject:"version-probe", child_exit_status, duration_ms}` pair for the `--version` read and one pair under the new probe `subject` for the print-mode probe. Each line passes G4 against the amended `schemas/diag-line.v1.json`, the tests-owned schema check rejects an unamended unknown `subject`, and `run`'s version gate still writes exactly one `version-probe` pair (per obs-plan §6 Child / shell spawns; §4 Scenario 1; §8 Default-deny posture).
- Every home created by `StampedHome` (both stamped and explicitly-unstamped forms), `tests/contract_ledger_probes.rs` and harness `boot` sits under `target/e2e-home/`. In the `test` job, G2 finds a non-empty scope and zero non-seam `event:"panic"` lines, and G4 reports zero conformance failures (per obs-plan §9 Integration tests row and G2/G4; §10 Error budget).
- After the `StampError` → `AgentError` fold, an unreadable or malformed `ledger/stamps.json` read by `run` still yields exactly one `parse-rejected{parser:"ledger-stamps", detail:"unreadable"|"malformed"}` line and `cli_verified:false`, with a fixed `Display` and no path in any line (per obs-plan §4 Capability ledger; §7 scrubbing layer 1).
- Item 8's witness reads the stopped home's `hook-<name>.ndjson`: with the colliding condition forced, the unreachable-endpoint case records `hook-invoked` then `hook-decision{detail:"channel-unreachable"}` with no `channel-request`. With the fix removed the same witness reads red, deterministically and without retries (per obs-plan §6 fail-open `detail` codes; §10 Deterministic emission; §11 SLO).
