# layouts extract

## Relevance
partial — the chunk builds no web-spa region and no new CLI screen. It becomes a CONSUMER of the existing `viola verify` CLI output (the test-home seam and harness `boot` step 4 read the verb's result), and item 7 adds spawn logging beside that verb's output. The web-spa surface is untouched.

## Constraints
- `viola verify`'s human output is fixed, per layout-templates §Surface: cli / Output structure — `viola verify`: one appended stdout step line per ledger row (`[NN/MM] <row id> <row words>  pass|fail`, in ledger order), then `stamped <ver>  <n> pass  <m> fail` as the LAST stdout line. Exit 0 only when every row passes. Exit 1 on a failing row OR a refusal, and a failing row still writes the stamp. `--record` adds no human line. Item 1 ("`stamped` reads true only from the verb's result") and item 2 (`verify-failed`) must key on this contract. An exit-1 run that still wrote a stamp must not read as stamped-and-passing.
- `MM` grows only as owning chunks land their rows (layout-templates §Output structure — `viola verify`: six rows today, `shim-resolution` … `largest-hook-payload`). The chunk's Boundaries keep new ledger rows out, so `tests/contract_ledger_probes.rs` and the stamping seam should see `MM` = 06. A consumer must not hard-code a count that a later row breaks. Whether the seam parses step lines at all, or only the exit code plus the summary, is research's question.
- Streams stay separate, per layout-templates §Component — Primary content block 2 (Streams) and §Surface: cli (Expression level): results go to stdout; refusals, `hint:` lines and errors go to stderr. `verify` prints plain ASCII with no colour, no redraw and no progress bar. Item 7's new `version-probe` / probe-child `process-start`/`process-exit` pairs are log lines, so they must leave both human streams of `verify` unchanged (no added line, no reordering).
- `verify`'s refusal and failure forms are fixed, per layout-templates §Component — Primary content block 2: exit-1 refusals are `unable: <text>` + `hint:` pairs from the fixed set (CLI not found, `.cmd`/`.bat` shim, version unreadable, recorded payload holds a path or username), with no name, path or pid. A failed or panicked `verify` prints exactly `error: internal error` and no hint. The harness's `verify-failed` outcome and the seam's unstamped branch must cover all three shapes (failing row, `unable:` refusal, `error: internal error`) without quoting their text into a result that carries paths.
- `viola run` is passthrough at expression 0.0 and prints nothing while the child runs, per layout-templates §Output structure — `viola run` / §Surface: cli (Expression level). The item 5 `agent-run run --local-live` session against the real `claude` must not expect or inject any human line from `viola run` on the child's terminal. Its start refusals are the fixed `unable: <name> is already live` + `hint: viola list` form.
- The `verify` usage is `viola verify [--record <DIR>] [-- <program> [args…]]`, program default `claude` (layout-templates §Output structure — `viola verify`). Stamping "against the fake agent" should use the `-- <program>` form. The layout lists no `--json` for `verify`, so whether a machine view exists at HEAD is research's question. Adding one would be a design change, not an implementation choice (per layout-templates §IA notes, "Output as a contract").

## Patterns to follow
- The last line says what happened: for `verify` the closing `stamped <version>  <n> pass  <n> fail` line plus the exit code is the terminator, with no `done.`/`success` word (layout-templates §Component — Footer / terminator). The seam and `boot` should judge on the exit code together with that last stdout line, not on a scraped middle line.
- Output as a stable contract, per layout-templates §IA notes: LLM drivers and the harness may read human words and columns, so they stay stable, and a new field goes into `--json` first. The harness `boot` JSON document (`verify-failed`, readiness line 3) is the machine view. It must not add or change a human `verify` line.
- The `hint:` lines are breadcrumbs that name the next verb (`viola verify`, `viola list`) and never `viola release` (layout-templates §Component — Primary navigation). Any new hint the harness or seam surfaces follows this, though the harness's own output shape belongs to test-plan §3.

## Anti-patterns to avoid
- Adding a human line, colour, spinner or progress redraw to `viola verify` (item 7's logging included). The verb's step-line and summary layout is fixed, and `fail` is never coloured (layout-templates §Output structure — `viola verify`, §Surface: cli Expression level).
- Treating an exit-1 `verify` run as stamped because `ledger/stamps.json` was written. The layout says a failing row still writes the stamp (layout-templates §Output structure — `viola verify`), so "stamp file exists" is not "the verb passed".
- Surfacing `verify`'s refusal or detail text (names, paths, upstream text) in a hint, a harness result or a test assertion message. Hints never quote upstream text or name a path or pid (layout-templates §Component — Primary content block 2, Hint line).

## Contract bindings
- layouts ↔ tests (test-plan §3 `boot` / `verify-failed` / readiness): harness `boot` step 4 and `tests/support/home.rs`'s stamped form consume `verify`'s exit code and summary line as defined in layout-templates §Output structure — `viola verify`. The typed harness outcome is test-plan's shape, and the human `verify` output it reads is this plan's.
- layouts ↔ obs (obs-plan §6 Child / shell spawns; `diag-line.v1.json` `subject` amendment): item 7's spawn log lines go to the process log only. The `verify` stdout/stderr layout must come out byte-identical for the same rows (layout-templates §Component — Primary content block 2, Streams).
- layouts ↔ architecture (capability ledger row order): the step-line order and `MM` follow the ledger (layout-templates §Output structure — `viola verify`). `contract_ledger_probes.rs` runs over those rows and must not reorder or add to them within this chunk's boundary.

## Acceptance criteria contributions
- (layouts) A stamped test home or harness `boot` reads stamped only when `viola verify` exits 0 and its last stdout line is `stamped <recorded version>  <n> pass  0 fail`. A fixture that forces one failing row (exit 1, stamp still written) yields the unstamped / `verify-failed` outcome (per layout-templates §Output structure — `viola verify`).
- (layouts) After item 7, a `viola verify` run against the fake agent at 2.1.283 prints the same stdout step lines and summary, and the same (empty) stderr, as before the change. The new `process-start`/`process-exit` pairs appear only in the process log (per layout-templates §Component — Primary content block 2, Streams, and §Output structure — `viola verify`).
- (layouts) Each `verify` refusal shape the seam or harness can meet (`unable:` + `hint:` pair, `error: internal error`) maps to the typed `verify-failed` / unstamped outcome, and no path, name or upstream text is copied into that outcome (per layout-templates §Component — Primary content block 2).
