# security extract

## Relevance
partial — no product surface (no new IPC/HTTP/input boundary or secret), but the chunk moves the local gate's environment boundary, disposes of the WSL root-install launcher and its pins, touches `run --mutants` (scratch wipe, `chunk.diff`), and scores mutants inside the Unix IPC access controls.

## Constraints
- The native Linux pre-push stage must keep the boundary that security-plan §Secret Management (Development, the pre-push gate bullet) sets for gate launches: the child gets exactly `HOME` and `PATH` under `env -i`, and no host environment value (the inherited `CLAUDE*` credentials included) crosses. Under the same §, any assignment whose value comes from the host is a boundary widening that needs its own Decisions Log entry. The plan text describes the WSL form (`wsl.exe … --exec /usr/bin/env -i`); it does not cover a native launch. Whether a native PATH that gains `~/.local/viola-venv/bin`, or any entry beyond the former distro-derived `<home>/.local/viola-node/bin`, is a widening goes to the founder live at P4. Phase does not presume it.
- Under security-plan §Secret Management (Development), the root launch `wsl-provision.sh --install-deps` stays operator-only: never the gate tool, a harness command or a pre-push stage. Before any re-provision it must stop running user-writable code as uid 0 (apt-get only, over an allowlisted dry-run list). If the chunk keeps any WSL path, this requirement comes with it. If the chunk retires the WSL tooling, the requirement retires with it, recorded at wrap. Silently dropping it is not a disposition.
- If `scripts/wsl-exec.sh` survives, security-plan §Secret Management (Development) still forbids any gate, harness command or plan entry from running a distro command through it (its `--probe` is the one exemption). A native replacement launcher would be a new launcher and needs the same no-caller discipline plus a Decisions Log entry.
- Under security-plan §Dependency Security (Pinning), the gate host is an install site of CI's own pins and never a new version source. The tool versions (cargo-nextest, cargo-mutants, cargo-llvm-cov from ci.yml's `test`-job `tool:` line, Node via `install-node.sh`'s sha256 check) must match their pin lines, and `pre-push` keeps refusing `tool-pin-mismatch` / `tool-missing`. Moving that refusal from the distro to the native host must not weaken it. Whether the native stage already checks it is research's question.
- Under security-plan §Security Anti-Patterns → Code Patterns (the `run --mutants` scratch bullet), `run --mutants` may wipe nothing except a dir whose final component is exactly `viola-mutants-scratch`, with the repository neither that dir nor inside it. It never falls back to a temp dir or the repo, and never prints the path. The bullet is worded for the Windows host. A Linux-host scratch location, or a `--copy-target=true` / prebuild form for viola-e2e, must stay inside the same guard. Whether the Linux path already goes through it is research's question.
- Under security-plan §Secret Management (Secret scanning in CI), `viola-harness secret-scan` skips `run --mutants`' `target/agent-run/chunk.diff` by exact path, and that file stays out of the `harness-<os>` upload. The C3 prefix pin (`--src-prefix=a/ --dst-prefix=b/`) must not move or rename that file, and a hostile-git-config test must not write diff output anywhere else under `target/agent-run/`.
- The 12 `cfg(unix)` mutants include viola-channel `host_socket_dir`, `listen`, `open_by` and `Guard::drop`. These are the code behind security-plan §Authentication & Authorization: the "IPC access control (Unix)" row (the 0700 per-user dir with its `lstat` owner/mode/symlink check, and the chmod 0600 after bind) and the "IPC client-side server verification" row. A survivor there is a gap in the test coverage of a security control. Dispose of it with a killing test where one can be written. An "equivalent" record must argue that the control's observable behaviour is unchanged.

## Patterns to follow
- The two-sided canary witness the earlier gate used (security-plan §Secret Management, Development): the gate's canary entry reads 0 `CLAUDE*` names inside the launched child, and a control that deliberately forwards one reads 1. A native `env -i` stage can reuse this shape to prove exactly `HOME` + `PATH` cross.
- The `--probe` self-test pattern (`release-check.sh --probe`, `wsl-exec.sh --probe`, `conpty-vendor.sh --probe`; security-plan §Dependency Security, CI integration, and §Secret Management): a boundary tool proves its own refusals before it is trusted as a gate.
- Pins parsed from the file text, never from the environment (security-plan §Dependency Security, Pinning: `install-node.sh` reads ci.yml's `NODE_PIN_*`, and the provisioner parses the `tool:` line). A native-host provisioning or pin check should keep this single home.
- Test-only features stay test-side (security-plan §Dependency Security, CI integration, `release-check.sh`). The viola-e2e boundary form's prebuild (`viola --features fake-agent`) builds into the mutation copy or scratch only and never into a release artifact path.

## Anti-patterns to avoid
- Adding a host-derived assignment to the gate's `env -i` launch (a `TMPDIR`, a venv path, `GIT_CONFIG_*`) without a Decisions Log entry and the founder's live word (security-plan §Secret Management, Development). The C3 hostile-config test should set its git config inside the test, not by widening the gate environment.
- Letting a uid-0 launch run user-writable code, or wiring any root launch into a gate, harness command or pre-push stage (security-plan §Secret Management, Development).
- Adding a new env-var seam to a `viola` build so viola-e2e can find the bins it spawns (security-plan §Security Anti-Patterns → Universal: only `FAKE_AGENT_PUMP_DELAY_MS` / `FAKE_AGENT_HOOK_PANIC`, `cfg(feature = "fake-agent")`; another seam needs a Decisions Log entry). A seam that lives only in the test-only viola-e2e harness is outside that ban.

The spec bodies that name the WSL distro, `wsl-exec.sh` or `wsl-provision.sh` (security-plan §Secret Management Development, §Dependency Security Pinning, and `.claude/rules/security.md`) reconcile at this chunk's wrap through `security-plan-amendments.md`, not in phase.

## Acceptance criteria contributions
- The native pre-push stage launches its child with exactly `HOME` and `PATH`. A canary witness reads 0 `CLAUDE*` names inside it, against a forwarding control that reads 1. Any further PATH entry carries the founder's live ruling, recorded for wrap's Decisions Log (per security-plan §Secret Management, Development).
- No pre-push stage, harness command or plan `[[gate]]` runs `wsl-provision.sh --install-deps` or any uid-0 launch. If `wsl-exec.sh` survives, `grep -rn wsl-exec` over `crates/`, `src/`, `.github/` and `scripts/agent-run.*` finds no caller, and every plan gate hit is exactly `wsl-exec.sh --probe` (per security-plan §Secret Management, Development).
- `pre-push` still refuses `tool-pin-mismatch` / `tool-missing` on the native host when an installed tool or Node differs from its ci.yml pin line (per security-plan §Dependency Security, Pinning).
- On the Linux host, `run --mutants` (the viola-e2e form included) wipes only a `viola-mutants-scratch`-named dir outside the repo, and its scratch guard still reads `scratch-refused` for any other path. `secret-scan` still skips `target/agent-run/chunk.diff` by exact path after the C3 prefix pin (per security-plan §Security Anti-Patterns → Code Patterns; §Secret Management, Secret scanning in CI).
