# arch extract

## Relevance
relevant: a new workflow file, a new CI surface and harness-arm behaviour all fall under §Infrastructure Patterns → CI/CD approach, §Occupied Resources and §Cross-cutting Patterns. No product crate, wire contract or Standard Contract surface is touched.

## Constraints
- §Infrastructure Patterns → CI/CD approach requires exactly two workflows (`ci.yml` is the only push/PR pipeline; `nightly.yml` runs on schedule plus `workflow_dispatch`). It also states "CI runs no mutation job": mutation testing runs only through `agent-run run --mutants` [`--file` / `--package <member>`] for the epoch-boundary audit. A third, dispatch-only workflow that runs `run --mutants` contradicts that text as written. It is a wrap amendment to that key and to §Infrastructure Patterns → Project directory structure (the `.github/workflows/` tree lists only `ci.yml` and `nightly.yml`). Show it at P4 as a widening; do not presume it is ratified.
- §Infrastructure Patterns → CI/CD approach requires least privilege in every workflow: `permissions: {}` at the top level, `contents: read` per job, every `uses:` pinned by full commit SHA with a version comment, event-payload values (a dispatch input included) passed to a step only through `env:`, and zizmor asserting all of it. The `supply-chain` job's `zizmor --format=json .github/workflows/` covers any new file in that directory by path. Whether the current invocation picks up a new file with no edit is research's question.
- §Infrastructure Patterns → CI/CD approach fixes the setup recipe: `actions/checkout` v7.0.1 with `persist-credentials: false`; `rustup toolchain install` reading `rust-toolchain.toml` (no toolchain action); `taiki-e/install-action` v2.87.19 for version-pinned cargo tools; every gate step fail-closed `shell: bash`. The same key allows no `concurrency:` block, and keeps `Swatinem/rust-cache` to `ci.yml` only (stated as `ci.yml` only). The cargo-mutants pin a new workflow installs must match the version the harness and the host use. Which version that is, and whether taiki-e carries a manifest for it, is research's question.
- §Occupied Resources (Repository, `<repo parent>/viola-mutants-scratch/`) requires that on Windows (`HOST_SCRATCH = cfg!(windows)`) `run --mutants` places cargo-mutants' `TMP`/`TEMP` copies and `--output` in a sibling-of-repo scratch whose final component is exactly `viola-mutants-scratch`, with a `scratch-refused` guard and no fallback to `%TEMP%` or the repo. The scratch path is never printed (only `scratch_bytes`). On a runner this needs a writable parent directory of the checkout. Whether `windows-2025`'s checkout parent allows that, and whether its depth keeps the copy under the Windows path limit (host-win32.md 2026-10-03, `LNK1104`), are research's questions.
- §Occupied Resources (Environment variables, test-harness only) records `AGENT_RUN_CHUNK_BASE` as "CI runs no mutation job and never sets it". It also records that `run --mutants` sets `AGENT_RUN_KEEP_HOMES=0` and `AGENT_RUN_KEEP_FAILED=0` on the `cargo mutants` command. Its `CI` row says the variable's one effect is the `run --local-live` refusal. A workflow that runs the harness under `CI` must keep that row true, and must not set the chunk base unless the §Occupied Resources text is amended.
- §Occupied Resources (Repository, `target/run-archive/<n>/`) requires the run archive, which holds the mutation arm's `outcomes.json`, never to be uploaded, because it carries absolute argv paths. §Occupied Resources (`target/agent-run/chunk.diff`) records that file as the one `secret-scan` skips and the one excluded from uploads. Any result the workflow keeps as an artifact or prints is bound by both rows.
- §Cross-cutting Patterns → Cross-platform discipline requires "every OS-specific branch compiles and is tested on its CI runner". The workflow is the mutation-scoring complement of that rule for `cfg(windows)` items. It must not change any `cfg(windows)` code shape to suit a Linux test (scope §Boundaries).

## Patterns to follow
- `nightly.yml` (§Infrastructure Patterns → CI/CD approach) is the precedent for a non-push workflow: a `workflow_dispatch` trigger that fires from the repository's default branch, jobs with no cache, and an upload gated on outcome (`fuzz/artifacts/` on `failure()`).
- `ci.yml`'s upload chain (§Infrastructure Patterns → CI/CD approach, `test` job) is the shape for any artifact: `secret-scan` with `id: secret-scan` and `if: always()`, then uploads with `actions/upload-artifact` v7.0.1, 7 days, only on `steps.secret-scan.outcome == 'success'`, and a `secret-scan-<os>` upload on its failure.
- The harness is the one entry point (§Infrastructure Patterns → CI/CD approach: "mutation testing runs only through `agent-run run --mutants`"), called through the OS's shim (`scripts/agent-run.ps1` or `.sh`), as the `test` job calls `run --coverage`. A second hand-rolled `cargo mutants` invocation would break that rule.
- Pinned tools that are not on taiki-e are installed with `cargo install --locked <tool>@<ver>` as their own step (§Infrastructure Patterns → CI/CD approach: the zizmor, hyperfine and cargo-modules precedent).
- `target/mutants/` as `MUTANTS_TARGET` with `--copy-target=true` (§Occupied Resources, Repository) stays the mutation target dir on every host. Each copied tree builds its own test binaries.

## Anti-patterns to avoid
- Making the mutation run blocking: no `push`, `pull_request` or `schedule` trigger, no `needs:` link with `ci.yml`, never a required check. Per §Infrastructure Patterns → CI/CD approach ("CI runs no mutation job") and the 2026-09-28 ruling it records.
- Putting a credential on the runner: no secret, no `persist-credentials: true`, no Claude CLI. Per §Infrastructure Patterns → CI/CD approach ("The real `claude` CLI runs only locally, never in CI") and its least-privilege rule.
- Fixing the temp-dir leak with a cleanup step bolted onto the workflow or harness, in place of the mechanism. Per §Occupied Resources (Repository, `target/e2e-home/` row: removals go through owner records and `remove_owned`, "never by age or name"), and the scope's CARRY 3 acceptance.

## Contract bindings
- arch ↔ security: a new workflow file binds to security-plan §Dependencies and CI (SHA pins, `permissions: {}`, zizmor, no secret). Any artifact binds to the secret-scan gating and the run-archive and `chunk.diff` no-upload rows (§Occupied Resources).
- arch ↔ tests: `run --mutants` (`--package` / `--file` arms, the `mutants` nextest profile in `.config/nextest.toml` per §Infrastructure Patterns → Project directory structure, and the `Booted` guard named in the §Occupied Resources `AGENT_RUN_KEEP_FAILED` row) is test-plan §3 / §10 Mutation-gate territory. The leak fix and the dispatch recipe land there, and the recipe also lands in `.claude/docs/commands.md`.
- arch ↔ obs: if the harness under the workflow writes run documents or the `outcomes.json` read, it stays within obs-plan §8 artifact admissibility (the `supply-chain` precedent "admissible by content"). Whether a mutation artifact is admissible is a question for the obs extractor.

## Acceptance criteria contributions
- The new workflow file declares `on: workflow_dispatch` only, `permissions: {}` at the top level, `contents: read` per job, `runs-on: windows-2025`, SHA-pinned `uses:` lines with version comments and `persist-credentials: false`. `zizmor --format=json .github/workflows/` in `supply-chain` reports it clean, and no `ci.yml` job `needs:` it (per architecture §Infrastructure Patterns → CI/CD approach).
- The workflow runs mutants only through the harness verb (`agent-run run --mutants` with `--package` / `--file`), never a bare `cargo mutants` step. The Windows scratch arm resolves under the `viola-mutants-scratch` guard without `scratch-refused` or `LNK1104` (per architecture §Occupied Resources, `<repo parent>/viola-mutants-scratch/` row).
- No uploaded artifact or printed log line carries `target/run-archive/**` (`outcomes.json`), `target/agent-run/chunk.diff` or the scratch path. Any upload is gated on a passing `secret-scan` step (per architecture §Occupied Resources, Repository rows, and §Infrastructure Patterns → CI/CD approach upload chain).
- At wrap, §Infrastructure Patterns → CI/CD approach ("two workflows", "CI runs no mutation job"), §Infrastructure Patterns → Project directory structure (`.github/workflows/` tree) and the §Occupied Resources `AGENT_RUN_CHUNK_BASE` row are amended to name the dispatch-only mutation workflow, or the divergence is recorded as HOLD for the founder (per architecture §Infrastructure Patterns, keyed contracts U35).
