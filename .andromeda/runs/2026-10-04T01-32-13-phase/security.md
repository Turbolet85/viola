## Relevance
partial — the chunk adds a CI workflow (supply-chain trust boundary, workflow hardening, artifact disclosure) and touches `run --mutants`' scratch/temp handling; it adds no product IPC, HTTP, input or secret surface.

## Constraints
- The new workflow file must carry the hardening security-plan §Dependency Security (CI integration) requires of every workflow: workflow-level `permissions: {}`, job-level `contents: read`, every `uses:` pinned by full commit SHA with a version comment, `actions/checkout` with `persist-credentials: false`, toolchains via `rustup` steps (no toolchain action). Preferring the four already-pinned actions keeps the Threat Model's supply-chain entry list (security-plan §Threat Model Summary, Vector: Supply chain) unchanged; any fifth action is a new pinned entry point to record. Whether the existing `ci.yml` steps already satisfy this is research's question; the new file must satisfy it on its own.
- `zizmor .github/workflows/` must cover the new file and read clean with no new suppression or ignore (per security-plan §Dependency Security, CI integration; security.md §Dependencies and CI "never … silence zizmor to reach green"). Whether the `supply-chain` job's zizmor invocation already globs every file under `.github/workflows/` (so no `ci.yml` edit is needed) is research's question.
- If the workflow takes any `workflow_dispatch` input (e.g. a package/file selector), that value is event payload and reaches a step only through `env:`, never `${{ }}` inside `run:` (per security-plan §Dependency Security, CI integration, event-payload line); prefer a closed `type: choice` over free text. `run --mutants` derives its base from git history; `AGENT_RUN_CHUNK_BASE` stays a local override only (same anchor) — the workflow must not set it from an input.
- No secret and no credential on the runner: the workflow references no `secrets.*`, no Claude credential, no token beyond the default `GITHUB_TOKEN` at `contents: read` (per security-plan §Threat Model Summary, Infrastructure CI/CD "no secrets in v1"; §Secret Management, Secret scanning in CI).
- Any artifact upload of mutation output is a disclosure decision: the `mutants.out/` upload was removed because `outcomes.json` held absolute argv paths and `log/` held test output, and the only unscanned CI upload left is the nightly `fuzz/artifacts/` (per security-plan §Bootstrap phases, `secret-scanning-ci-gate`). Uploading `mutants.out/` (or any part of it) unscanned is a widening of that list and needs its own Decisions Log entry; in this autonomous run that is a P4 HOLD, never ratified here. The admissible-by-content precedent is a verdict file holding repo-relative source locations and outcomes only, never absolute paths (security-plan-amendments 2026-09-24-quality-gates; retired 2026-09-28).
- `run --mutants` may wipe only `<repo parent>/viola-mutants-scratch` behind the pure `scratch-refused` guard, never falls back to `%TEMP%` or the repository, never prints the path, and runs the guard and wipe only under `HOST_SCRATCH = cfg!(windows)` (per security-plan §Security Anti-Patterns → Code Patterns). On the windows runner this means the scratch is the runner workspace's repo parent; whether the harness's Windows arm resolves it correctly there is research's question.
- The temp-dir leak fix (CARRY 3) must not widen the harness's deletion surface: the Linux dev host's NOCOW `TMPDIR` is the operator's and is never wiped by the harness (per security-plan §Security Anti-Patterns → Code Patterns, last clause). The fix must make tests clean up their own temp dirs / nested copies (the mechanism), not add a harness sweep of `TMPDIR` or any directory other than the guarded scratch.

## Patterns to follow
- `nightly.yml` as the shape for a non-`ci.yml` workflow: separate file, `workflow_dispatch` trigger, own jobs, same pinned-action set and permission blocks (security-plan §Dependency Security, CI integration).
- The `perf` job's tool-install pattern: a CLI tool installed as its own step with an exact version (`cargo install --locked …@x.y.z` or the pinned `taiki-e/install-action` at ci.yml's `test`-job `tool:` line version), no new action, no `github.event` value (security-plan §Dependency Security, CI integration; §Pinning — cargo-mutants' version source is ci.yml's `test`-job `tool:` line).
- Scan-gated uploads: every upload that could carry run output waits on `viola-harness secret-scan` succeeding (`if:` on the scan step), and `target/agent-run/chunk.diff` is excluded from any harness-capture upload by exact path (security-plan §Secret Management, Secret scanning in CI; §Bootstrap phases `secret-scanning-ci-gate`).
- Printing outcome counts and repo-relative missed/timeout coordinates to the job log rather than uploading `mutants.out/` keeps within the NEVER-log floor's ban on absolute paths in external output (security-plan §Bootstrap phases `logging-redaction-wire`, operational-metadata bullet) — a candidate form for the readable result.

## Anti-patterns to avoid
- Referencing any action by a mutable ref (`@v2`, `@stable`, `@main`) (security-plan §Security Anti-Patterns → Code Patterns).
- Interpolating a dispatch input or other `github.event` value with `${{ }}` inside `run:` (template injection; security-plan §Dependency Security, CI integration).
- Letting the harness delete outside the guarded scratch, or printing the scratch path, as a leak "fix" (security-plan §Security Anti-Patterns → Code Patterns, `run --mutants` scratch ban).
