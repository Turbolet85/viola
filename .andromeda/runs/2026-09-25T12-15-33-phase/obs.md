## Constraints
- New dependencies must keep tracing-subscriber at the `>=0.3.20` floor. They must add no Tokio to the sync crates' graph and no C-building crate, and must pass `cargo deny` on all three targets. This covers interprocess `=2.4.4`, windows-sys `=0.61.2` and the SHA-256 crate (candidate `sha2`, no `asm`) (per obs-plan §1 Telemetry triggers → Vector 9 supply chain; §3 Bootstrap phases → logger-stack-install "cargo check of the sync crates without Tokio, plus cargo deny check on all three targets").
- The workspace `cargo deny` bans owned by obs must still fire after the new deps enter `[workspace.dependencies]`. They are: `opentelemetry-otlp`, `opentelemetry-stdout`, `sentry`, `tracing-appender`, the tracing-subscriber `env-filter` feature, and the veil `toggle` feature. A `cargo deny` failure is a build failure (per obs-plan §3 Bootstrap phases → otel-sdk-install; §9 Pipeline integration → Lint / typecheck row; §10 Build / deploy failure conditions).
- The spike and the known-answer test must not use `print!` / `println!` / `eprint!` / `eprintln!` / `dbg!`. They must not add a new `#[allow(clippy::print_stdout, clippy::print_stderr)]` exemption either. The exempt set is closed: `viola-e2e`, the fake-agent bin, and the named output modules. Evidence goes into assertions, not printed output. Whether the CI clippy step lints test targets is research's question (per obs-plan §11 Obs Anti-Patterns → Logs; §3 Bootstrap phases → obs-ci-gate-wire).
- If the spike emits any diagnostic line, it goes through `obs_event!` only. There is no raw `tracing::*!` / `event!`, no bare `#[instrument]`, and no new `event` enum value without a Decisions Log entry. G1 and the `lint-probes.sh` raw-`event!` grep scan the whole workspace, `tests/` included (per obs-plan §11 → Logs and Spans / Traces; §9 Gate commands → G1).
- The `interprocess` tracing target stays `OFF` in every sink. Its failures are captured at viola's seam from the returned `Result`s. This matters only if the spike is kept as a durable witness that reuses production seams (per obs-plan §3 Logging stack → Agent-mode flag, D-11).
- The `Cargo.toml` edits for the licence add no abort panic strategy (`panic = "abort"`, a `-C panic` rustflag, or a `CARGO_PROFILE_*_PANIC` env). This applies to the root `[workspace.package]` and to `fuzz/Cargo.toml` (per obs-plan §9 Gate commands → G3; §10 Build / deploy failure conditions).

## Patterns to follow
- Prove a ban both ways. `scripts/lint-probes.sh` plants a violation and a clean control in throwaway crates. The chunk's `scripts/deny-probes.sh` requirement ("still proving every ban fires") has the same shape (per obs-plan §3 Bootstrap phases → logger-stack-install, raw-tracing ban; §10 "a ban that did not fire, a control that did not pass").
- Record measurements as evidence ("as measured at chunk X", with a run-artifact path). The `diagnostics-plane` and `observability-gates` entries do this, and the SQOS result and the hash pick should be recorded the same way (per obs-plan §3 Logging stack, `corr` bullet; §3 Bootstrap phases → logger-stack-install, clippy measurement citation).
- Multi-OS parity. A `#[cfg(windows)]` witness running on the `windows-2025` legs follows the native matrix. OS-specific behaviour, here named pipe versus Unix socket, is isolated behind the same contract and never gets an OS-specific sink (per obs-plan §1 Telemetry triggers → multi-platform-exporter-compat; §9 Platform).

## Anti-patterns to avoid
- Do not let a new dependency bring in banned obs crates or features transitively: an OTel exporter, sentry, tracing-appender `non_blocking`, or `env-filter` (per obs-plan §11 → Telemetry Strategy, Error Reporting and Logs).
- Do not widen the unscanned-upload set. If the chunk changes what the `supply-chain` artifact holds (`deny.json`, `deny-fuzz.json`, `zizmor.json`), each member must still carry no absolute path, argv or log content. Otherwise it is scanned or dropped (per obs-plan §8 Integration points → item 6, "Unscanned uploads, admissible by content").
- Do not print test output that could carry a host path or pipe name into `junit.xml`. The secret scan covers `target/nextest/ci/junit.xml`, because nextest stores failing tests' captured output there (per obs-plan §9 Step order → step 3; §8 table, the Absolute paths row).
