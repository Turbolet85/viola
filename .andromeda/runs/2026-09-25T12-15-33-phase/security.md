Relevant. The chunk exists to close the two security-plan Decisions Log open questions (the SQOS spike and the SHA-256 crate) and to add security-gated dependencies.

## Constraints
- The Windows client open must be windows-sys `CreateFileW(..., SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED, ...)` adopted through `interprocess::os::windows::named_pipe::local_socket::Stream::try_from(OwnedHandle)`. If adoption fails, a replacement SQOS open must be recorded in the Decisions Log before the Windows client chunk can go ahead. Per security-plan §Authentication & Authorization (row "IPC client-side server verification (anti-impersonation)") and §Bootstrap phases `auth-scaffolding-baseline` (the `viola-channel` client bullet).
- interprocess's default connect (no SQOS) is "never an acceptable fallback". The plan names only the windows-sys `CreateFileW` path. Any other open, such as the scope's std `OpenOptionsExt::security_qos_flags` + `custom_flags(FILE_FLAG_OVERLAPPED)` hypothesis, counts as a "replacement SQOS open" and needs its own Decisions Log record. Whether std's open gives an adoptable handle at the Identification level is research's question. Per security-plan §Security Decisions Log → Open questions (spike).
- `<hash>` must be a truncated SHA-256 of the exe bytes: the first 16 hex characters of the digest. The implementation must be pure Rust, must pass the cargo-deny C-build ban, and must be recorded in the Decisions Log before the chunk that writes `bin/`. Per security-plan §Data Protection (At rest → Code-bearing artefacts), §Security Decisions Log (Arch amendment 8; Open questions, SHA-256 crate) and §Bootstrap phases `auth-scaffolding-baseline` (Amendment 8; the `viola-state` re-hash bullet).
- Every new third-party dependency (interprocess, windows-sys, the hash crate) must be pinned exactly in `[workspace.dependencies]`, with `Cargo.lock` committed. rmcp's minor range is the only exception. Per security-plan §Dependency Security (Pinning).
- `cargo deny check` must pass all four families over the root graph. `[sources]` is crates.io only (`unknown-registry`/`unknown-git = "deny"`). `[advisories]` has `unsound = "all"` and `yanked = "deny"`, and RUSTSEC-2017-0008 is the only expected ignore. If a new crate lands in a sync crate, the sole-root `deny-sync.toml` tokio ban still holds. `scripts/deny-probes.sh` must still prove every ban live. Whether windows-sys (via windows-targets) and `sha2`'s graph (`cpufeatures`, `digest`, `block-buffer`, with no `asm` feature) stay free of `cc` is research's question. Per security-plan §Dependency Security (`deny.toml` additions; CI integration Job 4) and §Threat Model Summary (Supply chain trust boundary).
- The licence edit to `fuzz/Cargo.toml` must keep the fuzz exemption's conditions: `fuzz` never joins the root `[workspace]`, and the separate `cargo deny --manifest-path fuzz/Cargo.toml ... check advisories sources` audit stays green. The root trust boundary names `publish = false`, and adding `license` must not remove it. Per security-plan §Dependency Security (the `fuzz/` bullet), §Security Decisions Log `2026-09-24` (Conditions) and §Threat Model Summary (Supply chain trust boundary).
- Channel handles must never be inheritable. The spike's `CreateFileW` handle is the open the client will reuse, so it inherits this rule. Per security-plan §Data Protection (In transit → Handle inheritance).

## Patterns to follow
- The windows-sys SQOS `CreateFileW` + `Stream::try_from(OwnedHandle)` shape that the plan pins for the later `viola-channel` client (the Library line of security-plan §Authentication & Authorization lists windows-sys 0.61.2 and interprocess 2.4.4). A durable `#[cfg(windows)]` witness pins exactly that open for reuse.
- Settling an open question means a dated Decisions Log entry (Decision / Rationale / Conditions / By), the same format as the `2026-09-24` fuzz-exemption entry in security-plan §Security Decisions Log. The chunk's wrap writes it from repo evidence; phase and implement do not amend the plan.
- Every ban is proven live by `scripts/deny-probes.sh` alongside `cargo deny check` (security-plan §Dependency Security, `deny.toml` additions). A new crate is shown to pass the bans, not just assumed to.
- A `deny.toml` `ignore` entry is added only with a `reason` naming the disabled feature, and only under the 7-day CVE SLA (security-plan §Dependency Security, Critical CVE response SLA). A new ignore to get a crate through the gate is not the pattern.

## Anti-patterns to avoid
- NEVER open a Windows client pipe without `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`. The default `connect_without_waiting` lets a squatter with SeImpersonatePrivilege impersonate the client. This covers test doubles and fallbacks too (security-plan §Security Anti-Patterns → Authentication).
- NEVER derive `<hash>` from a non-cryptographic hash (FNV, `DefaultHasher`) (security-plan §Security Anti-Patterns → Data Protection).
- NEVER make channel handles inheritable (security-plan §Security Anti-Patterns → Data Protection).

Per security-plan §Dependency Security (Pinning; CI integration; `fuzz/` bullet).
