# arch extract

## Relevance
Partial. The architecture plan decides where the spike and the hash pick live, how dependencies are pinned, the dependency and CI gates, and the workspace or crate boundaries. It says nothing about SQOS semantics, the hash algorithm or truncation length, or licensing. Those belong to the security plan, the test plan and the founder ruling.

## Constraints
- architecture §Infrastructure Patterns → Build system requires every third-party version to be pinned once in `[workspace.dependencies]`. interprocess 2.4.4 and windows-sys 0.61.2 are already named in architecture §Stack and Technologies (Wrapper IPC and PTY rows). The SHA-256 crate is not in any Stack row. Adding it is new Stack content, and the wrap must record it as an amendment.
- architecture §Established Decisions [Module Boundaries] requires that "each product crate is created by the first chunk that consumes it". The chunk's own §3 boundary says it is neither `viola-channel` nor the `viola-state` writer. So neither crate should be created here only to hold the spike or the pin. Research decides where the spike and the hash known-answer test live: root `tests/` under `#[cfg(windows)]`, `viola-e2e`, or a dev-dependency. Research must also check that the chosen spot gives cargo-deny a resolved graph containing the pick. An unused `[workspace.dependencies]` entry never reaches `Cargo.lock`, so `cargo deny check` could pass without ever seeing the crate.
- architecture §Established Decisions [Concurrency] and §Cross-cutting Patterns → Tokio containment require only the sync API of interprocess ("Tokio flavour only in `viola-mcp`"). The spike must not turn on any interprocess `tokio` feature. If the hash crate lands in a sync crate (`scripts/sync-crates.txt`), the sole-root `deny-sync.toml` ban must stay green for that crate (architecture §Infrastructure Patterns → Build system).
- architecture §Infrastructure Patterns → Build system (Dependency policy) keeps the C-crate bans (`cc`, `libsqlite3-sys`, `openssl-sys`). They are checked for the Windows, macOS and Linux target triples, so `cfg(windows)` dependencies such as windows-sys are covered. `scripts/deny-probes.sh` must still prove every ban fires. The `fuzz/` libfuzzer-sys C++ build is the only ratified exemption, and it must not grow.
- architecture §Stack and Technologies (Language / runtime row) and the `msrv` CI job require the pick and its features to build on the declared floor, `rust-version = "1.96"`, with `RUSTUP_TOOLCHAIN=1.96`. The build uses `resolver = "3"`, which prefers versions compatible with that MSRV.
- architecture §Cross-cutting Patterns → Cross-platform discipline requires that "every OS-specific branch compiles and is tested on its CI runner". The `#[cfg(windows)]` spike must therefore actually run on the `windows-2025` legs of `test`, and on the `mutants` windows leg if it has mutable code. It must not end up compiled out everywhere.
- architecture §Occupied Resources → IPC endpoints reserves `\\.\pipe\viola-<h12>` for `viola run` endpoints. The spike's test-owned pipe server should use a name that cannot collide with that namespace. architecture §Conventions (Data model: Endpoint name) keeps the FNV-1a hash for the endpoint name. The SHA-256 pick replaces only the content `<hash>` of `bin/` and `plugin/`, not the endpoint hash.

## Patterns to follow
- Dependency pinning: add the crate to `[workspace.dependencies]` with an exact or minor pin, the way `portable-pty = "=0.8.1"` and rmcp `~3.4` are pinned. Members inherit it with `.workspace = true` (architecture §Infrastructure Patterns → Build system). The licence field should be inherited the same way through `[workspace.package]`, next to the existing `version.workspace = true`.
- Windows-only dependencies go in target-gated tables. windows-sys is already "Windows only" in `viola-pty` (architecture §Infrastructure Patterns → Crate dependency direction). Whichever crate the spike uses should gate windows-sys and its needed features the same way.
- Every gate needs a probe that proves it fires: `deny-probes.sh`, `lint-probes.sh` and `orphans-check.sh --probe` each carry a planted failure plus a clean control (architecture §Infrastructure Patterns → Build system). This matches the scope's remove-the-guard discipline.
- `fuzz/` is its own cargo workspace, excluded from the root, with its own `Cargo.toml` and lock (architecture §Established Decisions [Module Boundaries], §Occupied Resources → Workspace crates). So `fuzz/Cargo.toml` needs its own `license`; it cannot inherit one from the root `[workspace.package]`.
- New repo-root files (`LICENSE-MIT`, `LICENSE-APACHE`, `README.md`) and any new test file should appear in the architecture §Infrastructure Patterns → Project directory structure tree through a wrap amendment. Occupied Resources should list only resources the product reads or sets, not every file (the "Registry over-reach" precedent in the amendment history).

## Anti-patterns to avoid
- Never use std `DefaultHasher` for anything that must stay stable across binaries or releases (architecture §Conventions → Data model: Endpoint name). The chunk's ban on FNV-1a for the content hash comes from the security plan. FNV-1a stays correct for endpoint names.
- Never use a direct-parent `wrappers` allowlist or a workspace-wide `--exclude` to make the tokio ban pass (architecture §Infrastructure Patterns → Build system). If a new crate's feature pulls in tokio, fix the dependency instead.
- The spike and hash test must not add any executable to the release build. `scripts/release-check.sh` fails on any `compiler-artifact` executable other than `viola` (architecture §Infrastructure Patterns → CI/CD approach, target job 6). Test-only code stays in test targets or behind a test-only feature.

## Contract bindings
- Architecture and security: the `bin/<version>-<hash>/` and `plugin/<version>-<hash>/` keys come from architecture §Established Decisions [Deployment / Distribution] and §Occupied Resources → Filesystem, which say only "a short hash of the exe's content". The SHA-256 algorithm, the 16-hex truncation and the SQOS open are set by the security plan. Architecture supplies the path shape; security supplies the hash value.
- Architecture and security: architecture §Cross-cutting Patterns → Local endpoint trust boundary gives the security specialist ownership of per-OS endpoint enforcement. The SQOS client open is part of that. architecture §Stack and Technologies (Wrapper IPC) pins the adoption API version (interprocess 2.4.4).
- Architecture and tests: the spike's `#[cfg(windows)]` witness enters the CI `test` job's coverage run (per-OS floors), the `mutants` windows-2025 leg (the unviable-to-caught rule), `msrv`, and the per-OS `lint` orphans gate (architecture §Infrastructure Patterns → CI/CD approach).
- Architecture, supply chain and licensing: `deny.toml` `[licenses]` and `private = { ignore = true }` rely on architecture §Inherited Defaults → Publishability (`publish = false` on every member). Adding `license = "MIT OR Apache-2.0"` must not change `publish = false`.

## Acceptance criteria contributions
- (arch) interprocess `=2.4.4`, windows-sys `=0.61.2` and the SHA-256 crate are each pinned exactly once in root `[workspace.dependencies]`. windows-sys is target-gated to Windows. No interprocess `tokio` feature is enabled anywhere the sync crates can reach. (per architecture §Infrastructure Patterns → Build system; §Established Decisions [Concurrency])
- (arch) `cargo deny check` passes on the root graph, and that graph actually contains the SHA-256 crate: `cargo tree -i <crate>` resolves it, so the check is not vacuous. The per-sync-crate `deny-sync.toml` runs pass. `scripts/deny-probes.sh` still reports every ban firing. The msrv job (`RUSTUP_TOOLCHAIN=1.96 cargo check --workspace`) passes. (per architecture §Infrastructure Patterns → Build system; §Stack and Technologies, Language / runtime row)
- (arch) No new product crate (`viola-channel`, `viola-state`) is created by this chunk. `scripts/release-check.sh` still reports `viola` as the only release executable. `scripts/orphans-check.sh` passes on every lib/bin target, including any new test target. (per architecture §Established Decisions [Module Boundaries]; §Infrastructure Patterns → CI/CD approach, target job 6 and `lint`)
- (arch) The Windows spike runs, and does not skip, on the `windows-2025` CI legs. Its pipe name is outside the `viola-<h12>` endpoint namespace. (per architecture §Cross-cutting Patterns → Cross-platform discipline; §Occupied Resources → IPC endpoints)

## Relevant amendment history
- **2026-09-24-supply-chain-and-workflow-gates:** the tokio ban moved to sole-root `deny-sync.toml`, run once per crate in `scripts/sync-crates.txt`. `deny.toml` now has four families (advisories, licences, sources, bans for C, telemetry and features), and `deny-probes.sh` proves each ban. This matters for the `fuzz/Cargo.toml` licence edit and its `cargo deny --manifest-path fuzz/Cargo.toml` check.
- **2026-09-24-three-os-ci-headless-harness-skeleton:** the declared floor is `rust-version = "1.96"`, with an exact 1.98.1 toolchain pin. The same chunk established that "each product crate is created by its first consumer" and registered the test-only `viola-e2e`. Why: intent F-19 and the shipped manifests. These set the MSRV the pick must meet and the rule against creating `viola-channel` or `viola-state` early.
- **2026-09-24-workspace-tree-and-code-graph-planes:** the orphans gate runs per lib/bin target, and `release-check.sh` judges the release build's own artifacts. Why: stale test-only executables were measured in shared target dirs. Any new spike or test target goes through both gates.
