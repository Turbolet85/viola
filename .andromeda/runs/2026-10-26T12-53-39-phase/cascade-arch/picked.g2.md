### established-decisions#5.1 · values · dec-database-state-store · ## Established Decisions · lines 46–47
- **[Database / State Store] ndjson append logs + atomic JSON snapshots + std `File::lock` on separate `.lock` files (KEYSTONE).** Each event line is written with one `write` call. The next append heals a torn last line; readers count it and never rewrite the log. As landed (chunk 2026-10-10-self-healing-state): every appender (`append_event`, `append_event_at`, `try_append_event`) reads the log's last byte under the lock it already holds and, when the log is not empty and that byte is not LF, writes one LF and its line in a single write. The line then starts on a fresh line, no earlier byte moves, and every offset handed out before still starts the same line; `append_event_at` hands its builder and returns the offset its line really starts at (L + 1 after a heal, L otherwise). The healing process logs one `state-recovered` line, and an append that did not heal logs none. The one reader (`viola_state::events::read_from`: the wrapper's `wait` scan and `last` rebuild, `replay::session_chain`, the pass `viola revive` reads the logged session ids from, and since chunk 2026-10-10-session-links the wrapper's link-set restore at start, `LinkSet::restore`, one pass from offset 0, and since chunk 2026-10-11-the-board-viola-list `viola list`'s `viola_state::board::log_pass`, one pass from offset 0 per scanned instance whose snapshot read or was absent) counts what it steps over, per read, as `unknown_kinds`, `unknown_fields` and `torn_lines`: a line whose `kind` it does not know is not returned (`link` and `unlink` are known kinds since that chunk, returned and no longer counted); a known-kind line with a top-level key outside the six, or a `data` key outside its kind's list, is returned and counted once; an over-long line, a terminated line that is not one JSON object and the unterminated last line of the read count as torn, the last still neither returned nor rewritten.
 The counts are not logged. `viola list` is the first surface that shows them (chunk 2026-10-11-the-board-viola-list): `list --json`'s `skipped` `{unknown_kinds, unknown_fields, torn_lines}` and the BAY line's `skipped a - b - c`, each summed over every scanned instance, gone ones included. The wheel is decided in the wrapper's memory and mirrored to a snapshot. Budget readings are timestamped, last-writer-wins, under `File::lock`. Rationale: the audit trail stays human-readable and `tail`-able, there is no C in the build, and there is no daemon to serialise writers. SQLite (C build, binary format) and redb (multi-process mode hardened only 2026-09-06) were rejected. Lock files are separate from logs because append + exclusive lock fails on Windows (rust-lang/rust#54118). Upgrade path if a real query need appears: a derived, rebuildable SQLite index (rusqlite) beside the authoritative log. The log stays the source of truth.

### established-decisions#7.1 · values · dec-message-broker-ipc · ## Established Decisions · lines 60–61
- **[Message Broker / IPC] interprocess 2.4.4 `local_socket`, one endpoint per `viola run`, behind viola's own `channel` seam.** `hook` blocks on the channel for a dialog answer. `wait` blocks until the next driver-relevant event (`turn-ended`, `question`, `permission`, `plan`, `session-end` or `dialog-expired`) and returns that event, so nothing polls and a driver parked in `wait` learns that a dialog is pending. If a dialog is already pending when `wait` is called without `after`, or with an `after` at or before that dialog's event line, it returns that dialog at once (as landed by 2026-10-04-dialog-answers-by-dialog-id: `hook.dialog` is served, the dialog line is appended and signalled through `WaitFeed::appending_dialog` and cleared through `WaitFeed::dialog_settled`). With an `after` past that line the driver has already seen the dialog, so `wait` blocks for the next driver-relevant event, and a driver that leaves a dialog to the human never spins. Each dialog event carries a wrapper-assigned `dialog_id` (an integer, monotonic per instance, with the counter restored from `events.ndjson` on start so an id never repeats across wrapper restarts), and `answer` names its target by that id. At most one dialog is pending per instance. A `hook.dialog` that arrives while another is pending is answered `null` at once, so that dialog renders for the human. Its event is still logged with its own `dialog_id`, and a later `answer` for it is refused `not-delivered` with detail `unknown-dialog`. Whether Claude Code can hold two dialog hooks open at once (for example on parallel tool calls) is a capability-ledger row. `wait` takes an optional `after` cursor and an optional `timeout_ms`. `after` is a byte offset into the instance's `events.ndjson`.
 `wait` returns the first driver-relevant event whose line starts at or after it, at once if that event is already logged, so a turn that ends before the driver calls `wait` is never missed. Every `send` `ok` payload and every `wait` event result carries `cursor`, the offset to pass as the next `after`. Without `after`, `wait` returns the next such event appended after the call. With no `timeout_ms` it blocks until an event arrives, and if the endpoint vanishes first the caller gets `instance-unreachable`. On timeout it returns `ok` with `{"timed_out":true}`. `last` returns the `last_assistant_message` of the newest `turn-ended` event. The wrapper holds it in memory and rebuilds it from `events.ndjson` on start. Endpoint names are a short hash of the instance, never the raw `VIOLA_NAME` + path. On Windows the client connects only through the SQOS Identification open (windows-sys `CreateFileW` with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED`, adopted by `Stream::try_from`), never interprocess's default connect, so a squatted or rogue server cannot impersonate the client; a non-overlapped handle adopted this way hangs (as measured at chunk 2026-09-25-security-prerequisites). Rationale: one API over named pipes and Unix sockets, sync and Tokio flavours, and no daemon. macOS caps socket paths at about 104 bytes. Accepted risk: interprocess has one main maintainer, which the seam contains.

### established-decisions#11.1 · values · dec-mcp · ## Established Decisions · lines 85–92
- **[MCP] rmcp 3.4.1, stdio, tools `send · wait · last · answer · list`. `release` is CLI-only.** Refusals are `isError: true` tool results mapped from `result.refusal`. Rationale: it is the official SDK, tracks spec 2026-07-28, and the pinned minor limits churn from its near-weekly releases. `answer` and `list` are how a driver answers dialogs under R7 and sees sessions, and the prototype driver uses both every session. `release` stays off the driver's tool surface, so a driver is never offered a way to hand the wheel back to automation. This is an affordance, not an enforcement: an agent's Bash tool can still run CLI `viola release` (for example through `VIOLA_BIN`), and the Local endpoint trust boundary accepts it because v1 trusts every process of the same OS user. The wrapper refuses a `release` whose `params` carry a string `from` (`-32602`, `data.reason` `release-from-driver`), so CLI `viola release` run inside a wrapped session (`VIOLA_NAME` set) is refused; `from` is self-reported (`from_trust:"self-reported"`), so this deters rather than enforces. `pause`, `link` and `unlink` are CLI-only for the same reason: they are human controls over the wheel and the link topology, and links made by drivers are already recorded from `from` on `send` and `answer`. Tool inputs:
  - `send {target, text}`
  - `wait {target, after?, timeout_ms?}`
  - `last {target}`
  - `answer {target, dialog_id, response}`, with `response` in the channel `answer` shape
  - `list {}`

  `target` is a `ViolaName`, and the server adds `from` from its own `VIOLA_NAME` only when it has a name of its own. As landed (chunk 2026-10-17-mcp-server-for-drivers): each handler takes the raw argument object and re-validates it, a schema violation being the `invalid-params` result with a closed field `detail` and no frame (§Conventions, Error handling schema), and an internal handler fault being the JSON-RPC error `-32603` `internal error` with `data: null`; MCP `wait` sends `timeout_ms` = `min(given, 50 000)` (`viola_mcp::WAIT_CAP`, `wait_timeout`), 50 000 ms when none is given, and `after` as given.
