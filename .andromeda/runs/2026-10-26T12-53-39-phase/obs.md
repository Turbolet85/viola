# obs extract

## Relevance
relevant — two newly served channel methods and two new CLI frame verbs fall under the channel-line, server-check, process-exit and default-deny rules. The plan's E3 edge flow currently describes the explicit methods as not built, so it is amended by this chunk.

## Constraints
- obs-plan §6 Log Coverage (Boundary-call wrappers) requires every `link` / `unlink` call to log `channel-request` / `channel-response` with `method`, `corr`, `conn`, `result_class`, `error_code` and `sender` on both sides. These lines must never record `params` or result bodies. The `driver` / `driven` names, `since` and `already_linked` therefore never appear on a channel line, not even hashed. Whether `schemas/diag-line.v1.json` already admits `method:"link"|"unlink"` is research's question.
- obs-plan §6 Log Coverage (Log levels mapping) puts the new `-32602` refusals (a `driven` that is not the serving wrapper's name, or `driver` equal to `driven`) on `channel-response{result_class:"error", error_code:-32602}` at WARN. Today's `-32601` answer to `link` / `unlink` goes away for these methods.
- obs-plan §4 Span / Trace Coverage (detail `values · spans`, "cli (short-lived verbs), the server check") requires every frame verb to verify the wrapper through `cmd::client::connect` inside its dispatch span, before any frame. That rule names six verbs today. On a mismatch, or a check that cannot be made, the verb writes no `channel.request` span and no `channel-request` line, and it ends `process-exit{subject:"self", exit_code:21, detail:"server-verify-failed", during:"connect"}` at WARN. This holds on Linux and Windows; macOS stays on the recorded gap. `viola link` / `viola unlink` would be the seventh and eighth verbs under it.
- obs-plan §2 Telemetry Strategy (Naming conventions) closes the span `<area>` list (`run … release, cli, mcp`), and it contains no `link` or `unlink`. Each verb's dispatch span is therefore `cli.<verb>` (for example `cli.link`) unless the plan is amended to add an area. The name is a static string with no instance name in it.
- obs-plan §3 Observability Harness Contract (Trace context propagation, `cli` instance precedence) logs the caller's `VIOLA_NAME` as `instance` and file name. The explicit target argument names `cli-<name>.ndjson` only when `VIOLA_NAME` is unset. For these verbs that target is the driven instance named in scope.
- obs-plan §8 PII Scrubbing & Compliance (Default-deny posture) allows a line to carry only fields named in the §6 catalog. `channel-request` already carries `from`, which is logged only alongside `from_trust:"self-reported"` (§3 Trace context propagation). Any new field on a channel line, `process-exit` or another event needs a §6 catalog entry and a schema change first. A new `event` value needs a Decisions Log entry (§11 Logs).
- obs-plan §4 Span / Trace Coverage (Edge flows, E3) describes the implicit link as having no process-log line, no `event` value and no span. It also says the explicit methods are unbuilt (`-32601`) and that no product path appends an `unlink` line. The product `link` / `unlink` kinds belong to `events.ndjson` only. Per §2 Telemetry Strategy, obs never copies event payloads into process logs, so the explicit methods' trace is their `channel-*` pair, the product line and the snapshot's `links`.

## Patterns to follow
- `obs_event!` with explicit typed fields, under `#[instrument(skip_all, name = "...", fields(...))]`, with `corr` / `conn` / `instance` passed as explicit values (obs-plan §4 Span / Trace Coverage; §3 Trace context propagation, Internal async boundaries).
- The `channel.dispatch` `Drop` guard that emits `channel-response` on every return path, early returns and errors included (obs-plan §4 Scenario: Confirmed `send`). The new method arms should get their response line from this guard rather than an emit of their own.
- The shared server check `cmd::client::connect` inside the dispatch span. Each frame verb has a captured-span case `request_refuses_an_unverified_server_inside_its_dispatch_span` built on `cmd::client::refused_inside` (obs-plan §4 Span / Trace Coverage, detail `values · spans`).
- The precedents where a refused strict-modes check opens no process log and writes no line: `viola list`, `viola plugin install` and `viola revive --list` (obs-plan §4 Span / Trace Coverage, detail table row "cli (short-lived verbs)"; §6 Log Coverage, Filesystem refusals). This binds only if the founder's P4 form is "the instance check ahead of the snapshot read". On the CLI verbs today, `strict-modes-failed` cannot occur (§4 Scenario: `wait` / `last`).
- `run::links` emits no `obs_event!` and declares no span (obs-plan §4 Span / Trace Coverage, Edge flows E3). The landed `LinkSet::remove` path keeps that.

## Anti-patterns to avoid
- A bare `#[instrument]`, or `#[instrument(err)]` / `#[instrument(ret)]`, on the link verbs or the method handlers, and any `driver` / `driven` / `since` value in a span field. Also banned: a raw `tracing::{info,warn,…}!` / `event!` outside `viola_core::obs` (obs-plan §11 Obs Anti-Patterns, Spans / Traces and Logs).
- Telemetry on stdout. Under `--json`, stdout carries the verb's result document only, and the `link … since …Z` / `already linked` / `unlink …` human lines are output, not log lines (obs-plan §11 Obs Anti-Patterns, Logs).
- A `detail` code holding a path, pid, start time or endpoint, or a field outside the §6 catalog (obs-plan §11 Obs Anti-Patterns, PII Scrubbing).

## Contract bindings
- obs ↔ tests: test-plan §6 Scenario E3 (steps 1 and 3, the raw-channel name negative, `tests/channel_links.rs`) asserts the `link` / `unlink` lines and the `channel-*` pair that obs-plan §4 Edge flows E3 describes. The harness `agent-run logs` merges `events.ndjson` (`src:"events"`) with `diagnostics/*.ndjson` (obs-plan §3 Snapshot / paste-to-AI integration).
- obs ↔ tests: the test-plan §3 Log format, carried verbatim in obs-plan §3 Log format JSON schema, binds the `corr` rule for `channel-request` / `channel-response`. `schemas/diag-line.v1.json` requires `corr` on them except for `hook.event` and the `-32700` / `-32600` responses.
- obs ↔ security: the founder's P4 form (dated strict-modes gap vs `check_instance` ahead of the snapshot read) decides whether a refused check writes an exit-21 line or no line. The security plan's server check (§Authentication & Authorization) is the one logged as `server-verify-failed`.
- obs ↔ metrics: `viola.channel.duration_ms` per `method` picks up `link` / `unlink`. The new `-32602` causes widen the documented over-count of `viola.compat.v_rejected` (obs-plan §5 Metric Coverage).

## Acceptance criteria contributions
- A served `viola link` / `viola unlink` (and the raw-channel `link` / `unlink`) leaves one `channel-request` / `channel-response{method:"link"|"unlink"}` pair on each side. The pair is joinable on `(conn, corr)`, and no line holds a `driver` / `driven` name, `since`, `already_linked` or a path (per obs-plan §6 Log Coverage, Boundary-call wrappers; §3 Trace context propagation).
- On Linux and Windows, a serving process that is not the recorded wrapper makes `viola link` / `viola unlink` exit 21. The verb writes no `channel-request` line and exactly one `process-exit{subject:"self", exit_code:21, detail:"server-verify-failed", during:"connect"}` at WARN. Each verb has a captured-span case proving the refusal falls inside its dispatch span, and that case reads red with the check removed (per obs-plan §4 Span / Trace Coverage, detail `values · spans`).
- A `driven` that does not name the serving wrapper, and a `driver` equal to `driven`, each log `channel-response{result_class:"error", error_code:-32602}` at WARN, and no `-32601` answers `link` / `unlink` (per obs-plan §6 Log Coverage, Log levels mapping).
- Every line the new paths write validates against `schemas/diag-line.v1.json` (G4), so there are zero schema-conformance failures, zero secret-scan hits and zero `event:"panic"` lines (per obs-plan §10 SLO Invariants & Telemetry Budgets, Error budget).
