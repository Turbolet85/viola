## Patterns to follow
- Root `tests/cli_links.rs` (`binary(cli_links)`): each case starts from a stamped home and verdicts come from `events.ndjson` records (as in `links_a_send_from_another_instance_links_once` and `links_survive_a_wrapper_restart`). Per test-plan §6 Scenario: E3, the explicit-verb cases extend this binary.
- File and function naming per test-plan §2 Test directory + naming conventions: the channel suite is a `channel_`-prefixed root binary (the scope names `tests/channel_links.rs`), functions are `<subject>_<condition>_<expected>`, table cases are rstest `#[case::label]`, and every live-log read goes through `tests/support/ndjson.rs`.
- The server-identity negative and its control (`security_negative_cli_verb_writes_no_frame_to_a_server_that_is_not_the_recorded_wrapper` / `security_negative_cli_verb_reaches_the_recorded_wrapper`, run in `--json` and human mode) are the shape a new frame verb joins, per test-plan §6 Security control negatives.
- `tests/cli_machine_contract.rs` `every_verb_prints_one_document_and_its_literal_exit_over_a_wrapper_s_life` reads each driver-facing verb's `--json` document and literal exit over one wrapper's life. Per test-plan §5 CLI (detail), it is the candidate home for the verbs' `--json` / exit pinning.
- The E5 link leg (`e5_the_replay_reads_the_link_the_wrapper_wrote`) replays a product-written log equal to the snapshot's `links`, with all three skip counts 0. Per test-plan §6 Scenario: E5, a product-written `unlink` can now be read back the same way.

## Anti-patterns to avoid
- Hand-writing `snapshot.json`, `events.ndjson` link lines or `ledger/stamps.json` for a booted-wrapper test (per test-plan §11 Test Data).
- Using the product's refusal ordering or name validator as the oracle, or comparing codes by `Debug` string. The refused names, `-32602` and the exit codes are test literals (per test-plan §11 Unit).
- Waiting with `sleep(N)`, or asserting at E2E what a lower layer can hold. The name and pair-equality rules belong in unit tests, and E3 asserts only the cross-process record count (per test-plan §11 E2E and §11 Test Strategy).

## Contract bindings

The strict-modes form chosen at P4 decides whether an exit-21 strict-modes case applies (test-plan §6 Exit-cause matrix).

- tests ↔ layouts: the `HELP` literal follows layout-templates §Output structure — `viola --help` (the `handoff:` row between `wheel:` and `setup:`). The three human result lines are pinned by literal or trycmd per test-plan §5 Driver(s).
- tests ↔ arch: verification-matrix `v1-13`'s `link` half requires every human `link` line to be derivable from the `--json` result. Whether an MCP result is needed is the scope's open claim question, not a test this plan mandates.
