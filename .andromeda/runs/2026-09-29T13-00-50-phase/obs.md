# obs extract

## Relevance
partial — the chunk is mainly test-side (fake agent, contract suite, fixture schema check) plus one classifier fix in `viola-agent-claude`. Obs applies at the home and diagnostics boundary those runs write, at the print-ban exemption, and at the closed-enum or no-content rules the classifier fix must keep.

## Constraints
- Recorded fixtures are not a telemetry source, and obs adds no fixture content. They are scrub-required data owned by security and tests (per obs-plan §1 Build and CI infrastructure entity; §8 Data classification table, "Recorded fixtures" row). The contract suite reads them as test input. Neither the suite nor the fake agent turns them into log fields.
- Every viola home that the contract suite or a fake-agent integration run creates must live under `target/e2e-home/`, so that G2, G4, the secret scan and the `diag-<os>` upload cover it. A `hook` panic exits 0, so a home outside that root would hide the panic (per obs-plan §9 Pipeline integration, Integration tests row; §9 Step order 1, `AGENT_RUN_KEEP_HOMES=1`).
- Uploading detail files is admissible only because every input is synthetic. "Any non-synthetic input source must first drop `detail-*.ndjson` and `target/agent-run/` from the upload paths" (per obs-plan §8 Integration points item 6). The suite feeds recorded `viola verify` fixture payloads through `viola hook`. P3 research must settle whether the committed `fixtures/claude/2.1.283/*` payloads are synthetic (scrubbed or canary-bearing) or captured real content. The upload paths depend on that answer.
- Prompt text (`prompt-submitted.data.text`) and tool `input` never reach a home-level process-log line. They reach an instance `detail-<process>.ndjson` only inside a chain or a drift report (per obs-plan §8 Data classification table, High rows; §11 PII Scrubbing). The harness-origin classifier fix inspects the prompt prefix, and that prefix is prompt content. No log field may record it, whole or in part.
- Default-deny applies: a field or `event` value not in the §6 catalog fails G4. Adding an `event` value or renaming a field needs an obs Decisions Log entry (per obs-plan §8 Default-deny posture; §11 Logs, "add `event` values"). The matcher evaluation and the origin fix bring no new event, field or `detail` code unless P4 records a D-entry. The closed enums in play are `hook_event` (`pre-tool-use|post-tool-use|…`) and `parse-rejected.parser` (`hook-stdin|prompt-submitted`) (per obs-plan §6 Additive field catalog; §6 `detail` code catalog).
- The fake agent must print, because it emulates the `claude` CLI on stdout and stderr. It is exempt from the `print_stdout` / `print_stderr` ban only through the crate-level `#![allow]` in `src/bin/viola-fake-agent.rs`. Product-crate code paths (`hook`, `viola-agent-claude`) keep the ban (per obs-plan §3 Bootstrap phases, obs-ci-gate-wire; §11 Logs, the print-macro rule).
- In CI, `viola verify` runs only against the fake agent's print mode at the recorded 2.1.283, and the real-`claude` verify never runs in CI. No obs gate depends on verify's own lines. When `VIOLA_NAME` is set, those lines fall under G2, G4 and the scan (per obs-plan §4 Edge flows, `verify` / `plugin install`). The hidden `hook --capture` arm stays uninstrumented: no obs init, no `hook-invoked` / `hook-decision` (per obs-plan §4 Edge flows; §10 Bounded exemptions 5).

## Patterns to follow
- Product-crate logging goes only through `obs_event!` with explicit typed fields. Any new or changed function in `viola-agent-claude` or `src/cmd/hook` that carries a span uses `#[instrument(skip_all, name = "<area>.<operation>", fields(..))]`, with `skip_all` as the first argument (per obs-plan §4 Span naming convention; §9 G1; §11 Spans / Traces). Whether `prompt_origin` is instrumented today at all is research's question.
- A hook invoked by the fake agent's matcher evaluation (for example `pre-tool-use`) is logged as `hook-invoked` / `hook-decision` with the closed `hook_event` value and fail-open `detail` codes. The corr rule is `corr:null` before `dialog_id` is known (per obs-plan §4 Scenario Dialog → `answer`; §6 Additive field catalog and fail-open codes).
- A payload the hook cannot parse is reported as `parse-rejected{parser:"hook-stdin"|"prompt-submitted", detail:"malformed"|"oversize", count}` at `warn`, never with its content (per obs-plan §6 `detail` code catalog and Log levels mapping).
- Wheel attribution is observed through the existing `run.wheel_transition` span. Its `cause` enum is closed at `human-key|manual-pause|release`, and the `wheel` product event in `events.ndjson` is the audit record. A prompt the classifier marks as harness origin adds no new `cause` value (per obs-plan §4 Scenario Human takes the wheel).
- `prompt-submitted{origin:"driver"}` is the product-event key that closes `run.confirm_window`. The origin fix must leave driver-origin prompts classified as they are today (per obs-plan §4 Scenario Confirmed `send`, Cleanup).

## Anti-patterns to avoid
- NEVER log prompt text, a prompt prefix or tag literal, fixture payload bytes, or tool `input` in a home-level line. Content goes only to a detail file, inside a chain or drift report (per obs-plan §11 PII Scrubbing).
- NEVER put a print macro in a product-crate `hook`, `run` or `mcp` path. The fake agent's crate-level `#![allow]` does not extend to them (per obs-plan §11 Logs).
- NEVER add a retry-once for a flaky contract or telemetry assertion, and never close a red with a green re-run (per obs-plan §11 SLO).

## Contract bindings
- obs ↔ tests §3/§4: fake-agent integration homes sit under `target/e2e-home/`, where G2 and G4 run and the secret scan applies its canary rule. The canary value and the scan body are tests-owned; obs owns the two schemas (per obs-plan §9 G4; §8 item 6).
- obs ↔ security Data Classifications: recorded fixtures are scrub-required. Whether they count as synthetic decides whether `detail-*.ndjson` may stay in the `diag-<os>` upload (per obs-plan §8 item 6).
- obs ↔ arch Standard Contracts: `prompt-submitted.origin` and `wheel` are `events.ndjson` product events that arch owns. Obs only consumes them (confirm-window close, wheel-transition audit) and does not copy their payload into process logs (per obs-plan §1 Persistent stores entity).
- obs ↔ G2 seam exemption: a contract run that exercises the `fake-agent` panic seam is exempt only at exactly `src/cmd/hook/seam.rs:<digits>` (per obs-plan §9 G2).

Every such home lies under `target/e2e-home/` (per obs-plan §9 Gate commands G2/G4; §9 Pipeline integration, Integration tests).

- (obs) The chunk adds no new `event` value, field, `parser` or `detail` code without an obs Decisions Log entry. The `schemas/diag-line.v1.json` `event` enum still equals `ObsEvent` (per obs-plan §8 Default-deny posture; §3 Bootstrap phases, log-format-schema-emit; §11 Logs).
