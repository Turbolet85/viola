# obs extract

## Relevance
relevant — `viola list` is a new short-lived `cli` verb the plan names (`cli.list`, the `list --json` `skipped` gauge source, the short-lived reader's `liveness`), and it becomes a new caller of two `viola-state` paths that carry process-log lines.

## Constraints
- obs-plan §2 Naming conventions and §4 Span naming convention require the verb's dispatch span to be `cli.list`: a static name, declared `#[instrument(skip_all, name = "cli.list", fields(...))]` with an explicit field allow-list, no `err` and no `ret`. `skip_all` is the first argument, the form obs-plan §9 Gate commands (G1) accepts.
- obs-plan §4 Instrumentation per surface (row "cli (short-lived verbs)") requires `process-start` / `process-exit{exit_code, detail}` in `cli-<name>.ndjson` only when an instance resolves. obs-plan §3 Trace context propagation (`cli` instance precedence) names the caller's `VIOLA_NAME` first and a target argument second; `list` has no target argument, so its only instance source is the caller's `VIOLA_NAME`. With none, obs-plan §3 Log file location and obs-plan §10 Always-required SLO invariant (bounded exemption 2) require no process-log file and no line. Whether the existing `cli` dispatch already opens the role log and writes the pair for any verb `role_of` classes as `cli` is research's question.
- obs-plan §7 Panic hooks (per-role behaviour, short-lived `cli`) requires a panicked or failed `list`, when an instance resolves, to write `process-exit{subject:"self", exit_code:1, detail:"internal-error"}` to `cli-<name>.ndjson`, the chain to `detail-cli.ndjson` only, then the one fixed stderr line in one `write_all` and exit 1. obs-plan §10 Always-required SLO invariant requires exactly one home-level `panic` line for a panic after init step 4.
- obs-plan §3 OTel SDK init (Init order, step 4) requires the home strict-modes check before anything under the home is created or opened, and a refused home gets no diagnostics line. Its Per-role anchors record that the role-file open itself sets an existing home to 0700, so a check made after it passes a home at 0770. The plan words an anchor for `run`, `revive`, `ui`, `mcp` and `hook`, and none for `list`: where `list`'s instance check stands against the `cli` role-file open (the `VIOLA_NAME`-set case) is research's question, and a P4 matter if the code opens the log first.
- obs-plan §4 Edge flows (Torn append) states that the reader's per-read counts (`unknown_kinds`, `unknown_fields`, `torn_lines`) have no process-log carrier; obs-plan §5 Per-surface / per-path metrics makes `list --json`'s `skipped` a source of the `viola.parse.skipped` gauge. obs-plan §6 Additive field catalog names `skipped` on `http-request` only, and obs-plan §8 Default-deny posture makes a field outside the catalog a build failure: the counts go in the `--json` document, never on a `cli` line.
- obs-plan §4 Edge flows (E5) requires `viola_state::replay::read_snapshot_or_replay` to write one `state-recovered{detail:"snapshot-replayed"|"snapshot-unsupported-v", file, v_seen}` WARN line per call, under the spans `state.snapshot_recover` and `state.replay`. `list` calls it once per instance, so each fallback is one line in the caller's `cli-<name>.ndjson`, carrying the caller's `instance`. obs-plan §6 Additive field catalog gives `state-recovered` no subject-instance field (only `liveness-changed` has `subject_instance`): N recovered snapshots read as N lines that do not name their instance. That is a gap for the review card, not a field to add in this slice (a new field is a catalog and `schemas/diag-line.v1.json` amendment, obs-plan §8 Default-deny posture).
- obs-plan §6 `detail` code catalog (Filesystem refusals) requires the `viola-state` call site that skips a symlinked entry to emit `parse-rejected{parser:"state-entry", detail:"symlink-ignored", count}` once per scan, at `warn`, into the scanning process's role file, with the entry name and the link target never logged. The same catalog closes the `state-entry` details at `malformed`, `unreadable` and `symlink-ignored`. `list`'s walk of `instances/*/` is such a scan. Whether a scan call site that writes this line already exists is research's question. A per-instance strict-modes refusal has no catalogued line on this parser; what `list` logs for a refused instance is unworded by the plan.

## Patterns to follow
- One emitter: every line goes through `obs_event!` with typed fields named in the catalog, `message` a static literal (obs-plan §3 Logging stack; obs-plan §6 Additive field catalog).
- Check before log: `viola revive`'s start arm and `viola hook statusline` run `check_instance` before the role file opens, and a refusal opens no log and writes no line (obs-plan §3 OTel SDK init, Per-role anchors; obs-plan §10 Always-required SLO invariant, bounded exemption 7).
- A silent budget read: `viola_state::budget::read_budget` carries no span and no line, and a refused, unreadable, over-cap or other-`v` file reads as no reading (obs-plan §4 Scenario: Budget governor). `list`'s `budget: "unknown"` is that outcome's only trace.
- Liveness as a read value: a short-lived reader exposes `liveness` in its `--json` and emits no `liveness-changed`, which is the long-lived `ui` reader's transition line (obs-plan §3 Heartbeat ticks; obs-plan §10 Standard+ invariants, Liveness signal).
- Human and machine output through the output modules: `src/human.rs` writes with one `write_all` on a locked handle, uses no print macro and carries no `#[allow]` (obs-plan §11 Logs, the print-macro ban). Test homes stand under `target/e2e-home/`, so G2, G4 and the secret scan read the verb's lines (obs-plan §9 Pipeline integration, Integration tests row).

## Anti-patterns to avoid
- NEVER write telemetry to stdout: on a `cli` verb stdout carries the `--json` result and, for `list`, the board (obs-plan §11 Logs).
- NEVER log a field outside the catalog, a new `event` value or a new closed `detail` without a Decisions Log entry, and never a path, pid, scanned entry name or instance directory name in a home-level line (obs-plan §11 PII Scrubbing; obs-plan §11 Logs).
- NEVER write one line per scanned instance at `info` inside the walk, and never put an instance name in a span name or group a derived metric by `instance`: counts go on the boundary line (obs-plan §11 Logs; obs-plan §11 Spans / Traces; obs-plan §11 Metrics).

## Contract bindings
- obs ↔ tests harness: `agent-run status` reads `list --json` for `api_sessions_equal_list` and for `state: degraded` when any item is `stale` (obs-plan §3 Snapshot / paste-to-AI integration; obs-plan §3 Heartbeat ticks). The chaos class "stale heartbeat vs live pid" is gated on `list --json`'s `liveness` when no `ui` runs (obs-plan §10 Standard+ invariants, Liveness signal). Whether the harness's `status` already calls `list` or reads a stand-in is research's question.
- obs ↔ tests gates: the verb's home-level lines fall under G2, G4 and the secret scan, and G4 validates them against the obs-owned `schemas/diag-line.v1.json` (obs-plan §9 Gate commands; obs-plan §8 Default-deny posture).
- obs ↔ security: the check-before-log order binds to security-plan's strict-modes rule (obs-plan §3 OTel SDK init, Init order step 4). The row-mode escaper binds to the rule that C0 and C1 controls are escaped in any human terminal rendering of untrusted rows (obs-plan §8 PII Scrubbing, Data classification rules). Snapshot `endpoint` and `pinned_bin` are scrub-required in external output, so neither belongs in a `list` item (obs-plan §8 PII Scrubbing, Data classification rules).
- obs ↔ design: `list --json`'s `skipped` and the GUI's ATIS `skipped N · N · N` box are one derived gauge (obs-plan §5 Per-surface / per-path metrics); the `/api/sessions` half is not this slice's.
- obs ↔ architecture, at the wrap: obs-plan §4 Edge flows (E5) counts the snapshot readers and the product callers of the replay by a stated rule; a `list` that calls `read_snapshot_or_replay` moves that count.

## Acceptance criteria contributions
- With a valid `VIOLA_NAME`, one `viola list` run leaves in `cli-<name>.ndjson` one `process-start{subject:"self"}` and one `process-exit{subject:"self", exit_code:0}` with `process:"cli"`; with no `VIOLA_NAME`, the run creates no `cli-*.ndjson` under the home's `diagnostics/` (per obs-plan §4 Instrumentation per surface)
- `viola list --json` writes exactly one JSON document to stdout and `viola list` only the board; no diagnostics line reaches stdout or stderr on either form (per obs-plan §11 Logs)
- A `list` run with `VIOLA_NAME` set, over a home where one instance's snapshot is unreadable, leaves exactly one `state-recovered{detail:"snapshot-replayed", file:"snapshot.json"}` WARN line in the caller's role file, and that item still shows `wheel`, `budget_paused` and `liveness` (per obs-plan §4 Edge flows, E5)
- Every home-level line a `list` case writes validates against `schemas/diag-line.v1.json` with no `skipped` field, no entry name and no path, and the `cli.list` declaration passes G1 (per obs-plan §9 Gate commands)
