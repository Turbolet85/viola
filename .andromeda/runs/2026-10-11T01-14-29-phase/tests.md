## Patterns to follow
- Commands the implementation must pass: `scripts/agent-run.sh run --unit`, then `scripts/agent-run.sh run --integration --filter 'binary(<stem>)'` per new or touched root test binary, then the whole instrumented `run --coverage` with `gate --require coverage,doctest,playwright` (the operator pass's `pre-push` runs that chain) (per test-plan §3 `run`, Test selection and step 1; per test-plan §3 `pre-push`). `run --e2e` is a usage error until its selector lands and is no gate of this chunk (per test-plan §3 `run`, Test selection).
- Root cases use the one boot chain `home → fake_agent_path → stamped_home → booted_wrapper`, the shared started-child guard and runner, the one `events.ndjson` reader and the complete-lines reader in `tests/support/`; no root test file defines its own copy of any of them, and every wait is bounded by the shared `WITHIN` and is exit-aware (per test-plan §3 `run`, step 2; per test-plan §2 Test directory + naming conventions).
- Land the owed readings where the plan's as-landed cases already stand: the `torn_lines` reading beside `tests/chaos_torn_append.rs`' stopped-wrapper `File::set_len` case, the forward-compat lines appended to a product-written log in `chaos_forward_compat.rs`, the budget readings as `path6_*` root cases fed through `tests/support/statusline.rs`, the E5 reading as an `e5_*` root case (per test-plan §6 Chaos suite; per test-plan §6 Path 6, As landed; per test-plan §6 Scenario E5, As landed). Whether `chaos_forward_compat.rs` exists yet is research's question.
- Names: root binaries carry the `cli_` / `chaos_` prefix that the layer filtersets select on, functions read `<subject>_<condition>_<expected>`, and a critical-path case reads `path<N>_<slug>` (per test-plan §2 Test directory + naming conventions). Table-driven cases use rstest `#[case]` with readable labels (per test-plan §4 Conventions).
- Human rows: the plan's target is a trycmd `viola-list` case for the piped board, with snapbox redactions and verify mode only (per test-plan §5 Cross-module patterns → CLI; per test-plan §7 Seed strategies, the Human-mode expected output row). Its separator line is the unwrapped rack's and is not in this slice, and `viola verify`'s human lines landed as literal assert_cmd asserts instead (per test-plan §5 Cross-module patterns → CLI, the `tests/cli_verify.rs` bullet). Whether trycmd is in any manifest, and which of the two forms pins this slice's rows, is research's question; the plain-output witness `tests/cli_output_plain.rs` is the model for a no-ESC-byte assertion on both streams (per test-plan §5 Cross-module patterns → CLI).

## Anti-patterns to avoid
- NEVER hand-write `snapshot.json`, `budget.json` or `ledger/stamps.json` in a booted-wrapper case, a newer `v` or a hostile CLI version string included; if no product path can put a control character into the snapshot's recorded version, the escaper is held at unit level and no integration case plants one (per test-plan §11 Test Data; per test-plan §11 Test Strategy).
- NEVER synchronise with `sleep(N)` or a test-owned timer, never use `.assert()` on the long-lived wrapper, and never read the child's rendered screen for a verdict: `list` cases wait on `events.ndjson` offsets or receipts and judge on the exit code, the document and the stdout lines (per test-plan §11 E2E; per test-plan §11 Universal).
- NEVER take the product's own tables as the oracle or a Linux run as proof for the other OSes: the six captions, the closed words, the document keys and exit 21 are literals in the test, and `cfg`-split behaviour is proven only on its own runner (per test-plan §11 Unit; per test-plan §11 Test Strategy).

## Contract bindings
- tests ↔ architecture: the `list` `ok` payload and the GUI list envelope are the shapes the plan's `list --json` line cites; a shape change there moves the literals in these cases (test-plan §1 Status endpoint shape).
- tests ↔ harness `status`: `agent-run status` runs `viola list --json` and nests its document as the `list` member, which the plan keeps `null` only "while `viola list`" is unbuilt, with `down` and `last_error` `list-exit-<code>` for a non-zero exit (test-plan §3 `status`; test-plan §3 Status endpoint shape; test-plan §3 Closed enums). The scope does not say whether this slice wires that member; it is a question for the plan and the review card, and `status` passes the `claude agents --json` stub's `PATH`, which the slice does not read.
- tests ↔ obs: every root test home stays under `target/e2e-home/`, so any diagnostics line a `viola list` child writes there is read by the zero-panic gate, `schema-check` and `secret-scan` (test-plan §5 Setup / teardown lifecycle; test-plan §3 `schema-check`; test-plan §3 `secret-scan`). The read-or-replay function logs one `state-recovered` line per replayed snapshot (test-plan §4 viola-state), so a `list` over an unreadable or newer snapshot is a new writer of that line: which role file takes it and its schema row are obs-plan's, and the content canary must stay out of home-level role files (test-plan §6 Error sanitization and secret scan).
- tests ↔ security: `list` is named among the entry points that must leave `snapshot.json` and `ledger/stamps.json` byte-identical (test-plan §6 Security control negatives → Single writers), and its error documents carry no absolute path, serde path or `Caused by` (test-plan §6 Error sanitization and secret scan).
- tests ↔ layout / design: the CLI caption row must equal the web `columnheader` texts; only the CLI half exists in this slice, so the caption literals here are the half the later parity case reads (test-plan §6 Cross-surface parity).

- `scripts/agent-run.sh run --unit` and `run --integration --filter 'binary(<stem>)'` pass for every new or touched binary, with unit cases for the row escaper and the pure row and count logic written against literals, and `run --coverage` with `gate --require coverage,doctest,playwright` green at the 85 / 95 / 80 floors with no skipped and no retried test (per test-plan §10 Quality Gates & Coverage Targets, Coverage thresholds and Zero-flakiness budget).
- On a wrapper booted from `stamped_home`, `viola list --json --home <h>` exits 0 with one document whose `.ok.items` holds that instance as `wrapped:true`, `liveness:"live"`, beside `.ok.budget` and the three `.ok.skipped` counts; on a home that fails strict-modes it exits 21 with a document and a last-line `hint:` naming the cause (per test-plan §6 Path 1, Verification signal; per test-plan §6 Exit-cause matrix).

- With a product-written `snapshot.json` cut mid-object, and in a sibling case set to `v` 99, `list --json` shows the instance `live` and never `stale` with the replay-recovered `wheel` and `budget_paused` and `dialog_pending:false`, and the file's bytes unchanged; with a reading over the threshold fed through `viola hook statusline`, `.ok.budget.paused` and the item's `budget_paused` read `true`, the item turns `false` after `release --budget` while `.ok.budget.paused` stays, and the board's cell shows the same state (per test-plan §6 Scenario E5; per test-plan §6 Path 6, Verification signal).
