# arch extract

## Relevance
relevant — the chunk audits and bounds every external reader across the root bin and five library crates, so it turns on the workspace boundary, the channel frame contract, the validation regime, the `ViolaName` data-model rule and the screen-model decision.

## Constraints
- Every channel frame is one line of at most `MAX_FRAME` bytes counting its `\n`. A longer line is answered `-32600` and the connection is closed. An id-less frame other than `hook.event` is not dispatched. Methods that read `from` take it absent, `null` or a valid `ViolaName`, and anything else is `-32602` with `data: null`, never `-32600`. This holds for both server and client reads (per architecture §Standard Contracts, Wrapper channel frames and Channel methods).
- External payloads (hook JSON, `claude agents --json`, the statusline payload) are parsed tolerantly: no `deny_unknown_fields`, `#[serde(default)]` / `Option<T>`. viola's own formats are versioned-tolerant: readers skip and count unknown kinds and fields. The only validators are the nutype newtypes `ViolaName`, `Percent` and `DialogHold` (no garde or validator). A closed type added by this chunk must use these regimes and must not tighten a parse into a refusal (per architecture §Established Decisions, [Validation]).
- The instance key `ViolaName` is ASCII `[a-z0-9-]`, 1–32 characters, starting with a letter, enforced by nutype. Identity is by instance, never by location, so any name that reaches a path join must pass this shape first (per architecture §Conventions, Data model conventions; per architecture §Cross-cutting Patterns, Identity by instance).
- Refusal order: `not-delivered` / `control-character` (`validate_paste_text`: LF, CR and TAB pass; every other C0, DEL and C1 is refused, never stripped) comes first for `send` and for `answer`'s free text. The CLI checks before any frame and the wrapper checks again. After that, a typed text left empty is refused `empty-text` (per architecture §Conventions, RefusalReason; per architecture §Established Decisions, [Delivery Confirmation]).
- MCP handlers re-validate their raw arguments (`target` through `ViolaName::try_new`, `text` a string, `after` / `timeout_ms` absent, `null` or `u64`, `dialog_id` `u64`, `response` through `Response::parse`). A failure is an `isError: true` `invalid-params` result with one of the closed field words and no frame written (per architecture §Conventions, MCP).
- The vt100 model is a pre-send readiness gate only. Each feed and resize runs under `catch_unwind`. A caught panic or a dropped queue message poisons the model, which then reads `input-not-ready`. The tee writes the human's bytes first and offers the model a copy with `try_send`, so the passthrough never waits on the model (per architecture §Established Decisions, [Screen Model]).
- Every external file under the home or `~/.claude` listed in the scope has its reader and cap named in the plan: `config.json` (`MAX_FRAME`, `v` = 1, a bad value falls to its default), `budget.json` (`take(MAX_FRAME + 1)`, over the cap means no reading), `statusline-source.json` and `~/.claude/settings.json` (`take(MAX_FRAME)`), `ledger/stamps.json` (over the cap is an error, read through `read_stamps_strict` in `run`). `claude --version` and `claude agents --json` are drained through `MAX_FRAME` / `take(MAX_FRAME + 1)` and killed at 5 s. Whether each reader in the code already applies its cap is research's question (per architecture §Occupied Resources, Filesystem; per architecture §Standard Contracts, Session liveness).

## Patterns to follow
- One shared bound: `MAX_FRAME` (16 MiB) is a `viola-core` constant. The validators (`validate_paste_text`, `ViolaName::try_new`) also live in `viola-core`, and the wrapper re-runs them. A new bound or closed type belongs in `viola-core` when more than one crate reads it, and Claude-specific shapes stay in `viola-agent-claude` (per architecture §Infrastructure Patterns → Crate dependency direction; per architecture §Established Decisions, [Agent Coverage]).
- The documented over-size form is `take(MAX_FRAME + 1)`, with over the cap read as "no reading" or a refusal. It is used by `budget::read_budget`, the hook and statusline stdin and `run::agents` through `version_gate::run_capped`. Reuse that form and its helper rather than write a new capped reader per call site (per architecture §Occupied Resources, Filesystem; per architecture §Standard Contracts, Session liveness).
- Unparseable external values become the string `"unknown"` in viola's own records, never an error. `resets_at` is parsed tolerantly into `unknown` (per architecture §Conventions, Data model conventions; per architecture §Established Decisions, [Timestamps]).
- Snapshot reads go through `read_snapshot_classified` / `read_snapshot_or_replay` under the same `MAX_FRAME` bound. A snapshot that is over the cap, fails to parse or has a higher `v` is ignored and replayed from `events.ndjson`. No product code under `src/` calls `read_snapshot` (per architecture §Standard Contracts, Snapshot envelope).

## Anti-patterns to avoid
- No `deny_unknown_fields` on viola's own formats or on external payloads. Mixed binary versions are real, and a closed type must skip and count an unknown value, not reject the record (per architecture §Established Decisions, [Validation]).
- No Tokio outside `viola-mcp`, and no new crate edge against the manifest-enforced direction (`viola-core` depends on no viola crate; `viola-agent-claude` stays pure, no I/O). A bounded reader added to a sync crate must keep it tokio-free (per architecture §Established Decisions, [Concurrency / Backend Framework]; per architecture §Infrastructure Patterns → Crate dependency direction).
- No env var or `config.json` key that widens, lifts or disables a cap. Environment variables are not a configuration channel (per architecture §Cross-cutting Patterns, Config management).

## Contract bindings
- arch ↔ security: the `MAX_FRAME` / depth / closed-type / `ViolaName` rules here are the shapes that security-plan §Input Validation enforces. The `-32600` oversize answer and the MCP `invalid-params` result are the wire outcomes of those checks (architecture §Standard Contracts, Wrapper channel frames; §Conventions, MCP).
- arch ↔ obs: an over-cap or rejected input is surfaced as a `parse-rejected{parser, detail}` line, for example `channel-frame` / `malformed`, `vt100-feed` / `oversize` and `config-json`. The parser and detail vocabulary is obs-owned (obs-plan §3 event catalog). The `fuzz/` workspace's six targets (`viola_name`, `channel_frame`, `hook_stdin`, `vt100_feed`, `paste_text`, `claude_agents_json`) are the test-side surface of these same boundaries (architecture §Occupied Resources, Repository).
- arch ↔ tests: CLI exit `2` is the code for `viola send` text over `MAX_FRAME` or not UTF-8, and exit `13` for `not-delivered` (architecture §Conventions, CLI exit codes). A witness per boundary asserts these.

## Acceptance criteria contributions
- (arch) A channel line longer than `MAX_FRAME` (its `\n` counted) is answered `-32600` and the connection is closed, on the server, and the client's read is bounded the same way (per architecture §Standard Contracts, Wrapper channel frames).
- (arch) `cargo tree` / grep finds no `unbounded_depth` and no new `deny_unknown_fields` in the product graph, and every closed type added skips and counts an unknown value per its format's rule (per architecture §Established Decisions, [Validation]).
- (arch) Every path join on an instance, driver, driven or `VIOLA_NAME` name runs on a value that has passed `ViolaName::try_new` (or its closed-shape validator: session-id shape, pinned key). An MCP `target` that fails returns `invalid-params` / `target` with no frame written (per architecture §Conventions, Data model conventions and MCP).
- (arch) A forced vt100 feed panic leaves the child's bytes passing through to the host terminal unchanged, and the next `send` is refused `not-delivered` / `input-not-ready` with nothing typed (per architecture §Established Decisions, [Screen Model]).
