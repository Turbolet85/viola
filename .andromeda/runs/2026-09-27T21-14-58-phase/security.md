# security extract

## Relevance
relevant — the chunk opens the hook stdin trust boundary, the first `hook.event` client connect, the code-bearing `hooks.json` exec paths and the hot-path `snapshot.json` reader (security-plan §Threat Model Summary, Attack surface: "Hook stdin payloads" and "Filesystem state under `~/.viola/`").

## Constraints
- **Fail open, always.** security-plan §Error Handling (Internal logging) and §Security Anti-Patterns → Logging require that `viola hook` never writes stderr and never exits non-zero, including when a security check fails (oversized stdin, strict-modes failure, server-verification mismatch): exit 0, no body, so the dialog renders for the human. §Security Anti-Patterns → Universal adds that no security refusal may block the human. The panic path is included (CLAUDE.md invariant; CARRY 1's pre-clap role classification is how the catch site learns it is `hook`).
- **Bounded, tolerant stdin parse.** security-plan §Input Validation (row "Hook stdin") requires `Read::take(MAX_FRAME)` before `read_to_end`, with over-limit input failing open plus a `diagnostics/` note; tolerant parsing in `viola-agent-claude` (no `deny_unknown_fields`), with any security-deciding field in a closed enum; serde_json default depth only (§Security Anti-Patterns → Input: never `unbounded_depth`). `resets_at`, if the statusline parser lands here, is UTC-only via chrono, malformed → `"unknown"`.
- **Strict-modes, then server verification, then the first frame.** security-plan §Authentication & Authorization (row "`~/.viola/` access control") names every `hook <event>` as an entry point that runs the strict-modes check before it reads `snapshot.json`. It also requires refusal (for `hook`: silent exit 0) when the home, `instances/<name>/`, the `plugin/<version>-<hash>/hooks/` folder or `snapshot.json` fails. Row "IPC client-side server verification" requires that server verification happen before the first `hook.event` notification is written: on Windows, the SQOS `CreateFileW` open, then `server_process_id()` + sysinfo start time checked against the snapshot `pid`/`started_at`; on Unix, `peer_creds` euid (+ pid where available). Whether the landed `viola-channel` client and `viola-state` strict-modes already do this on the `hook` path is research's question.
- **Exec-form hooks by absolute pinned path.** security-plan §Security Anti-Patterns → Universal requires every `command` in the embedded `hooks.json` to be the absolute pinned `bin/<version>-<hash>/viola(.exe)` path, never a PATH lookup. §Data Protection (At rest, Code-bearing artefacts) requires `plugin/<version>-<hash>/` to be rewritten at every start through `replace_private_shared`, never reused. §Secret Management (Never in code) says the plugin files hold exec paths only, no credential literal.
- **Content routing and the NEVER-log floor.** security-plan §Bootstrap phases (`logging-redaction-wire`) allows prompt text, tool `input` and serde_path_to_error drift reports only in the contract payloads (`events.ndjson`, via `hook.event`) and in `instances/<name>/diagnostics/` (0600). They never go to stderr or to any external error. R8-stripped `CLAUDE*` values reach no event, diagnostic or fixture (§Secret Management, Storage). §Error Handling requires that errors crossing the channel carry fixed messages only.
- **Upstream text is content.** security-plan §Security Anti-Patterns → Code Patterns requires that the `prompt-submitted` normalisation never interpret prompt text as a command or config. The harness prefixes (`<agent-message from=`, `<task-notification>`) and the `<pasted_content` wrapper shape must come only from compiled `viola-agent-claude` ledger rows, never from runtime or upstream text.
- **Instance resolution for the silent no-op.** security-plan §Input Validation (row "CLI arguments / stdin") requires `VIOLA_DIR`/`--home` to be canonicalised and to pass strict-modes before any snapshot read. A name must pass `ViolaName::try_new` before any `instances/<name>` join (§Security Anti-Patterns → Input). No `VIOLA_*` env var may switch off a control (§Security Anti-Patterns → Universal). Resolving through env must not bypass any of these checks.

## Patterns to follow
- One replace helper: `viola_state::fs::replace_private` sets the temp file's mode before any byte is written, then does `sync_all` + `persist` (security-plan §Authentication & Authorization, `~/.viola/` access control). CARRY 5's sharing-violation retry belongs inside that helper, bounded. On final failure the target stays as it was, and a failed mode set still discards the write.
- The pinned SQOS client recipe: `CreateFileW` with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED`, then `Stream::try_from(OwnedHandle)`, as pinned by `tests/channel_sqos_open.rs` (security-plan §Bootstrap phases, `viola-channel` client). Never interprocess's default connect.
- Error sanitization at the boundary: fixed-message `Display` on the `<Crate>Error` enums; a serde/serde_path_to_error source is mapped to a fixed message before it joins a chain; full detail goes only to `diagnostics/` (security-plan §Bootstrap phases, `error-sanitization-wire`).
- Parser-surface coverage: the hook stdin parser (including `hook statusline`) is a named fuzz/property surface (security-plan §Input Validation, "Parser surfaces"). The new target lives in the separate `fuzz/` workspace with a synthetic corpus (§Dependency Security, `fuzz/` exemption; §Bootstrap phases, `secret-scanning-ci-gate`: a non-synthetic seed must first drop the `fuzz/artifacts/` upload).

## Anti-patterns to avoid
- NEVER write stderr or exit non-zero from `viola hook`, and NEVER write a `hook.event` frame before server verification against a `snapshot.json` that passed strict-modes in the same process (security-plan §Security Anti-Patterns → Logging, → Authentication).
- NEVER let a `hooks.json` command resolve `viola` through PATH, and NEVER reuse existing `plugin/` files without rewriting them (security-plan §Security Anti-Patterns → Universal, → Data Protection).
- NEVER let a hook process write `snapshot.json`: only the instance's own wrapper writes it (security-plan §Security Anti-Patterns → Universal). NEVER let the CARRY 5 retry degrade the replace into an in-place truncate/write, a delete-then-rename window, or a mode carried over from the replaced file (§Security Anti-Patterns → Data Protection: never the umask).

## Contract bindings
- **security ↔ obs:** drift reports go only to `detail-hook.ndjson` (obs-plan §8, the `drift_report` field). The `hook` role at the catch site must stay exit 0 with empty stderr (obs §7, CARRY 1). The CI `secret-scan` canary covers the new hook diagnostics (security-plan §Secret Management, Secret scanning in CI ↔ obs-plan §9).
- **security ↔ tests:** the hook stdin and normalisation parsers are fuzz/proptest surfaces (security-plan §Input Validation, "Parser surfaces" ↔ test-plan §6 Property suite). If the fuzz target adds a path dep, `fuzz/Cargo.lock` changes, and the `supply-chain` fuzz-lockfile audit must still pass (§Dependency Security).
- **security ↔ tests/CI (perf):** the hyperfine install for the perf job follows §Dependency Security: any new `uses:` must be pinned by full SHA; an external CLI tool takes a floor; `permissions: {}` / `contents: read`. If perf enters the WSL pre-push leg, that is a re-provision, and the operator-only `--install-deps` narrowing binds (§Secret Management, Development; handoff CARRY 6).
- **security ↔ arch:** `MAX_FRAME` for hook stdin is checked against the "largest hook payload seen" ledger row (security-plan §Input Validation, Constants; Decisions Log amendment 7). That row belongs to :51, and this chunk only names it.

## Acceptance criteria contributions
- Driving `viola hook` with stdin over `MAX_FRAME`, with malformed JSON, with no resolvable instance, with an unverifiable server (snapshot `pid`/`started_at` mismatch or strict-modes failure) and with a forced panic each gives exit 0, empty stdout, empty stderr and no new `events.ndjson` line (per security-plan §Error Handling, Internal logging; §Authentication & Authorization, IPC client-side server verification).
- Every `command` in the rendered `plugin/<version>-<hash>/hooks/hooks.json` is the absolute pinned `bin/<version>-<hash>/viola(.exe)` path, with no bare `viola` (the M6 `command_absolute` witness) (per security-plan §Security Anti-Patterns → Universal).
- In a test that holds `snapshot.json` open across a `replace_private`, the replace lands once the holder releases. A forced final failure leaves the prior bytes intact, and the replaced file keeps 0600 on Unix (per security-plan §Authentication & Authorization, `~/.viola/` access control).
- The CI `secret-scan` step passes over test homes that include `detail-hook.ndjson`, and no drift-report value or prompt text appears on any stderr or channel `error.data` (per security-plan §Bootstrap phases, `logging-redaction-wire`; §Secret Management, Secret scanning in CI).
