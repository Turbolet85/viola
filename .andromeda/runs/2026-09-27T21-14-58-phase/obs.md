# obs extract

## Relevance
relevant: this chunk adds the `hook` process role's first live code path (sink, catch site, `hook-invoked`/`hook-decision`, `hook.event` channel lines), the first shared `hook-<name>.ndjson`/`detail-hook.ndjson` writers, the first `drift_report` producer and the hook perf gate. Obs tier is Standard (per obs-plan §1/§2).

## Constraints
- `hook` role init: instance comes from `VIOLA_NAME` only (never the home or an argument); home strict-modes run before anything under the home is opened; then exactly one `config.json` read and exactly one log `open` of `<home>/diagnostics/hook-<name>.ndjson` (append, 0600/0700); `detail-hook.ndjson` opens lazily, only on the first content-bearing record. A failed role-file open makes the writer `std::io::sink` and writes nothing to stderr (per obs-plan §3 OTel SDK init steps 3-6, D-29). Whether `viola_obs_init` already has a `hook` arm is research's question.
- Unwrapped no-op: with no `VIOLA_NAME`, `hook` writes no file and no line, exits 0 with empty stdout/stderr, asserted by absence. This overrides the security Vector 4 "missing `VIOLA_NAME`" logging trigger (per obs-plan §4 Edge flows E1, D-16, §10 bounded exemption 3).
- Exit-0 catch site: the panic hook stays the first statement of `main`. The main-thread `catch_unwind` must classify the role from argv before clap runs: the first argument that is neither a global flag nor a flag's value (`viola --home <dir> hook …` is still `hook`), never `argv[1]`. For `hook`, an `Err` maps to exit 0 with empty stdout. A panic after init step 4 writes exactly one `level:"ERROR", event:"panic"` line to `hook-<name>.ndjson`, plus the payload/backtrace line to `detail-hook.ndjson`. Every Cargo profile keeps `panic = "unwind"` (per obs-plan §7 Panic hooks, D-28, §10 Zero unlogged panics). Whether `role_file_name` / the catch site already map `hook` to exit 0 is research's question (scope CARRY 1(2)).
- Hook log lines: `hook-invoked` and then `hook-decision` with `hook_event` from the closed enum (`session-start|user-prompt-submit|stop|session-end|…`) and `stdin_bytes`, `invoked_at`, `decision_emitted`, `duration_ms`. Non-dialog hooks and pre-`dialog_id` fail-open paths emit `hook-invoked` at once with `corr` absent (null is written as key absence, never a literal `null`). Fail-open paths carry a closed `detail` at `warn`: `oversize-stdin`, `malformed-json`, `channel-unreachable`, `server-verify-failed`, `strict-modes-failed`. Parser failures may also emit `parse-rejected{parser:"hook-stdin"|"prompt-submitted", detail:"malformed"|"oversize", count}` (per obs-plan §6 Additive field catalog, `detail` code catalog, Log levels mapping; §4 Scenario 2/4; D-07; §3 Null encoding).
- Channel hand-off: a `hook.event` is an id-less JSON-RPC notification. Its `channel-request` omits `corr` and joins by `instance` + `hook_event` + `timestamp`. The hook client sends the additive `conn = "hook-<pid>-<t0>-1"` (one connection per hook process), and both sides log it. `params` bodies are never logged (per obs-plan §3 Trace context propagation, D-10/D-32; §6 Boundary-call wrappers IPC invocation).
- Content routing: prompt text (`prompt-submitted.data.text`, `HookEventParams.data`) never reaches a home-level line; only `text_bytes`/`stdin_bytes` may. The payload type carries veil `#[derive(Redact)]` + `#[redact]`. A serde_path_to_error drift report goes only as `drift_report` into `instances/<name>/diagnostics/detail-hook.ndjson`, through the `viola::obs` detail writer (never through the subscriber), and the external surface gets the fixed message (per obs-plan §8 Data classification rules, Integration points 1/2/5, §7 scrubbing layers 2-3, D-30).
- Shared-writer atomicity: every line of `hook-<name>.ndjson` and `detail-hook.ndjson` is one `write_all` of one complete line on an append-mode handle. Detail lines can exceed 4 KiB, so they rely only on that rule plus torn-line tolerance (per obs-plan §3 Logging stack Format, D-28).
- Hook perf budget: `hyperfine 1.20.0 --warmup 3 --runs 30 --export-json`, gated on `max`: `session-end` `max < 1.0 s`; the spine hooks (`session-start`, `user-prompt-submit`, `stop`) `max <` the spine deadline, which is tests-owned and provisionally 1.0 s. Each is asserted by `jq -e '.results[0].max < …'`. Every perf hook command runs with `VIOLA_NAME` set and a home under `target/e2e-home/`, in the same per-OS job that runs G2/G4/the secret scan (per obs-plan §10 Performance budgets, §9 Step order 1, D-30).

## Patterns to follow
- Every hook line goes through `obs_event!` with explicit typed fields and a static `message` equal to the event name. Spans are `#[instrument(skip_all, name = "hook.handle", fields(...))]` › `channel.request` (and `hook.decision_emit` where a body is emitted), with `corr`/`conn`/`instance` passed as explicit values (per obs-plan §3 Logging stack, §4 Span naming and surface table row "cli (`viola hook`)", §11 Spans / Traces).
- Dispatch errors end in one codes-only `hook-decision{detail}` at `WARN`, with the full chain in `detail-hook.ndjson` only. This is the §7 module-boundary rule applied through the `cmd::Failure` / `report_internal_error` sink the scope names (per obs-plan §7 Error classes captured, §10 Module-boundary error logging).
- The product `session-start` event lands in `instances/<name>/events.ndjson` as the arch Event line with `source:"hook"`, after `wheel{cause:"start"}` → `budget-gate`. Its order is verified via `agent-run logs --kind`, not duplicated into process logs (per obs-plan §4 Scenario "`viola run` start sequence", §3 Log format JSON schema Event stream).
- Perf evidence: hyperfine JSON is uploaded as `perf-<os>` under `if: always()`, and the report-only quantiles use the §5 `-R`/`fromjson?` snippet over `hook-decision.duration_ms` (`viola.hook.duration_ms`) (per obs-plan §9 Telemetry artifact handling, §5 Per-surface metrics).

## Anti-patterns to avoid
- No `print!`/`eprintln!`/`dbg!` and no default panic hook on the `hook` path. Keep `log_internal_errors(false)` and an explicit writer. Only the output module that owns the hook decision body carries a local `#[allow]`; this chunk's non-dialog hooks emit no body (per obs-plan §11 Logs, Error Reporting).
- No bare `#[instrument]`, `err`/`ret`, raw `tracing::*!`/`event!`, or `?corr`/`%corr`. No prompt text, stdin payload, tool `input`, path or pid in any home-level field or `detail` code (per obs-plan §11 Spans / Traces, Logs, PII Scrubbing).
- No new `event` value, `detail` code or `parser` value without a Decisions Log entry and a `schemas/diag-line.v1.json` update. This includes any line the `replace_private` retry (CARRY 5) might want (per obs-plan §11 Logs, §8 Default-deny posture, §6 `detail` code catalog).

## Contract bindings
- obs ↔ tests §3 Log format: the `hook-<name>.ndjson` / `detail-hook.ndjson` lines are validated by G4 against `diag-line.v1.json` / `diag-detail.v1.json` (`drift_report` is a detail-only field); G2 counts `hook` panics in home-level files only (per obs-plan §9 Gate commands, §8 Detail-file scope).
- obs ↔ tests concurrent-append check: the three-OS check over the shared hook files, with a detail line larger than 4 KiB, is tests-owned; obs requires it (per obs-plan §3 Logging stack, D-28; scope CARRY 1(1)).
- obs ↔ tests §9/§10 perf job: the hyperfine hook fixture (with `VIOLA_NAME`, home under `target/e2e-home/`) and the spine deadline value are tests-owned; obs requires the `jq -e` `max` assertion and G2 over that home (per obs-plan §10, D-30).
- obs ↔ security Vector 4 / NEVER-log floor: the fail-open codes and the no-stderr rule come from security; obs supplies the `detail` catalog, the veil redaction and the secret-scan canary rule (the canary is never in home-level files) (per obs-plan §6 `detail` code catalog, §8 Integration points 6).

## Acceptance criteria contributions
- A `viola hook <event>` run with no `VIOLA_NAME` leaves no `hook-*.ndjson` file and no line, exits 0 and has empty stdout and stderr. A wrapped run with a forced panic, including the form `viola --home <dir> hook …`, exits 0 with empty stdout/stderr and writes exactly one `event:"panic"` line in `hook-<name>.ndjson` (per obs-plan §4 Edge flows E1, §7 Panic hooks, §10 Zero unlogged panics).
- A wrapped UserPromptSubmit/SessionStart run writes `hook-invoked` and `hook-decision{hook_event, duration_ms}` lines that pass G4 against `diag-line.v1.json` with `corr` absent, and the synthetic prompt's canary appears in no home-level `diagnostics/*.ndjson`. A malformed or oversize stdin yields a `warn` `hook-decision` with a closed fail-open `detail` and exit 0 (per obs-plan §6 Additive field catalog, §8 Integration points 6, §9 G4).
- A schema-drifting hook payload produces a `drift_report` line only in `instances/<name>/diagnostics/detail-hook.ndjson`, which passes `diag-detail.v1.json`, and nothing content-bearing in `hook-<name>.ndjson` (per obs-plan §8 Data classification rules, Detail-file scope).
- In the per-OS perf job, `jq -e '.results[0].max < 1.0' perf/hook-session-end.json` and each spine-hook `jq -e` deadline assertion set the exit code. The hook runs use `VIOLA_NAME` and a `target/e2e-home/` home, and G2 over that home reports zero panics (per obs-plan §10 Performance budgets, §9 Step order 1).
