# a11y extract

## Relevance
partial — the plugin hooks and the wrapper channel are a not-assertable surface (per a11y-plan §1, "Not-assertable (no UI surface)": "Claude Code plugin: hooks … ipc-internal"), so no WCAG criterion, ARIA role, focus order or contrast pair binds here. What remains is the `viola run` tui boundary the hook process sits inside, and the facts this chunk writes to `events.ndjson`, which the web tape reads later.

## Constraints
- The tui boundary's first clause holds with hooks active: a11y-plan §1 (tui surface, boundary clauses) and §4 P4 require that viola writes zero bytes to the terminal other than the child's output. A `viola hook` that writes stderr, a body or a non-zero exit could be rendered by the `claude` TUI as viola-originated text. Whether the installed CLI shows hook stderr or exit status in its screen is an undocumented CLI behaviour. That is research's question, and a ledger row for :51 to probe. It is not something to assume here.
- The tui boundary's second clause holds: a11y-plan §1, §4 P4, §5 ("tui: … Human keystrokes are never blocked or delayed past the atomic paste") and §11 Keyboard require that no human keystroke is blocked, refused or delayed. The UserPromptSubmit hook runs on the human's own submit, so the hook deadline (item 6, the perf job) is also the ceiling on how long viola can delay a human submit. Whether the provisional `max < 1.0 s` spine deadline is short enough to count as "not delayed" is for arch/tests to name. a11y adds only that the bound must exist and be gated, not advisory (per a11y-plan §10 SLO bans on soft SLOs).
- The hook-to-kind map reads the hook payloads only. It never reads the rendered child screen (per a11y-plan §11 Universal, R7 "NEVER parse the rendered `claude` TUI screen for content").
- Truth over presentation: the tape and announcements may show only what hooks and the wrapper observed (per a11y-plan §11 Universal, "NEVER overclaim in the GUI"). So `prompt-submitted.origin` must be recorded only when it can be decided. If `driver` cannot be decided in this chunk, the event must not state it as a guess. Whether it can be decided is P3's question, as the scope already notes.
- `prompt-submitted.text` is content that reaches assistive technology only as `textContent` later (per a11y-plan §1 web-spa notes, "Event content has no semantic structure", and §7 → Heading hierarchy). The normalisation may remove only the `<pasted_content>` wrapper and reverse the CLI's escaping. It must not add markup or structure meant for later rendering.
- No WCAG conformance claim rests on this chunk's tests (per a11y-plan §11 Strategy, "NEVER claim WCAG conformance for the cli or the `viola run` TUI"). Its hook assertions are output-discipline and boundary stand-ins only.

## Patterns to follow
- The tui boundary assertions run on the portable-pty outer-PTY driver, with no a11y tool (per a11y-plan §3 → Keyboard test harness → tui, and §4 per-surface tool reach table). If this chunk adds a boundary witness for hooks, it goes there as a nextest case on all three OS legs, not in the browser suite.
- Hook output discipline follows the stdout/stderr split the plan already asserts for cli verbs (per a11y-plan §4 P6: assert_cmd / trycmd on stdout and stderr, all three OS legs). For `hook` the expected streams are empty stdout, empty stderr and exit 0.
- Failures and panics go to `diagnostics/` only, never to the terminal (per a11y-plan §1 tui surface notes, "viola's diagnostics for `run` go to `diagnostics/`, never to the terminal"). This extends to the `hook` process's `hook-<name>.ndjson` / `detail-hook.ndjson`.

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke past the current atomic paste. A hook that stalls UserPromptSubmit past its gated deadline is this ban's failure mode (per a11y-plan §11 Keyboard).
- NEVER parse the rendered `claude` TUI screen, or take screenshots, to classify a hook, an origin or a readiness event (per a11y-plan §11 Universal, R7).
- NEVER write a11y rows into `<home>/diagnostics/`, and never rename an obs binding field or write a literal `null` for `corr` / `instance` on the new `hook` process lines (per a11y-plan §11 Universal and §1 structured violation JSON schema, "Constraints this plan honours").

## Contract bindings
- a11y ↔ tests (perf): the hook deadline gated by `agent-run run --perf` (test-plan §9/§10) is also the a11y tui clause "keystrokes never delayed" (a11y-plan §1 tui, §4 P4). The perf `max` breach fails that clause as well. a11y names no number of its own.
- a11y ↔ obs: `hook` process lines use the obs field shape the a11y plan binds to without renaming (a11y-plan §1 structured violation JSON schema → `process` closed enum `run|hook|mcp|ui`, `corr` rules for `hook-invoked`).
- a11y ↔ arch (event line): `prompt-submitted{text, origin}` and `session-start{source:"hook"}` feed the tower tape later (a11y-plan §1 web-spa → Tower tape; §11 Universal "never overclaim"). The event content stays plain text for the `textContent` rendering.

## Acceptance criteria contributions
- (a11y, boundary) `viola hook` exits 0 with empty stdout and empty stderr on every path the chunk exercises: unwrapped no-op, bad stdin, unreachable wrapper, verify failure and panic. Asserted with assert_cmd on all three OS legs, with no WCAG claim (per a11y-plan §1 tui boundary clause 1 and §11 Strategy).
- (a11y, boundary) Under a wrapped fake-agent run with hooks registered, the outer-PTY stream carries no viola-originated bytes: byte for byte against the unwrapped run on Linux/macOS, and viola's own literals absent on Windows ConPTY. Asserted by extending the existing P4 clause-1 case to a session whose hooks fire (per a11y-plan §4 P4 tui case (1)). Whether that case already runs with hooks active is research's question.
- (a11y, boundary) The hook deadline gate is binding (a breach fails the job), not a report, and it covers the UserPromptSubmit hook on the human-submit path (per a11y-plan §1 tui boundary clause 2, §10 SLO "NEVER define soft a11y SLO").
