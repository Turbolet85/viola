# a11y extract

## Relevance
partial — the chunk is mostly ledger, verify-probe and send-slot internals with no new surface; its a11y reach is the human-visible edges it moves: the `viola send` outcome for `/compact` (P2), the longer driver-side confirm window against the human keyboard path (P4, tui boundary), and `viola verify`'s step lines growing by one row (P6).

## Constraints
- The new compact confirm window is a bound on the driver only: no human keystroke into a `viola run` (or a passed `viola revive`) start may be blocked, refused or delayed past the current atomic paste while a `/compact` send waits for its SessionStart of cause `compact` (per a11y-plan §11 Keyboard; per a11y-plan §1 tui entity boundary clauses). Whether the send slot's wait already leaves the keyboard path untouched across a longer window is research's question.
- a11y-plan §8 Timeout extensions requires every time bound to fall on the driver or viola's own child, never on the human, with no warn-extend pattern needed only because v1 has no human-facing time limit; a new compiled compact bound must keep that property, and the section's driver-side bound list is where such a bound is stated (per a11y-plan §8 Timeout extensions).
- viola writes zero bytes of its own to the terminal while the child holds it, including during the compact confirm window and its expiry (per a11y-plan §1 tui entity boundary clauses; per a11y-plan §3 Keyboard test harness, the zero-viola-bytes clause).
- Whatever human-mode text a `/compact` send prints (confirmed, `unconfirmable`, or a refusal) is static and linear: no spinner, `\r` redraw or cursor control during the longer wait, and no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` (per a11y-plan §1 cli surface Notes; per a11y-plan §11 Motion).
- A human-mode refusal keeps the `unable  <reason>  <detail>` then final `hint:` form on stderr with a typed exit code, and `--json` carries no hint; a kebab-case code never appears without the plain word `unable` (per a11y-plan §8 Error recovery; per a11y-plan §8 Plain language).
- `viola verify`'s output for the 24th row follows the P6 form `[NN/NN] … pass|fail`, linear and static, with `fail` never coloured (per a11y-plan §4 P6; per a11y-plan §11 Visual).
- No WCAG conformance claim rests on any case this chunk adds; assert_cmd / trycmd / portable-pty results stay output-discipline stand-ins (per a11y-plan §11 Strategy).

## Patterns to follow
- The readiness-gate takeover case `send_under_the_paste_hint_a_human_key_during_the_gate_wait_wins` as the shape for a driver wait that a human key must win: sequenced on the wrapper's `channel-request` line and the `wheel` record, never a timer (per a11y-plan §3 Keyboard test harness).
- The budget gate's paired readings in `tests/cli_budget.rs` (`path6_a_reading_over_the_threshold_refuses_the_send`): a driver-side bound proven beside a human key still reaching the child and the outer-PTY stream holding none of viola's literals (per a11y-plan §3 Keyboard test harness; per a11y-plan §8 Timeout extensions).
- Fixed CLI strings pinned by trycmd or by literal so any copy change fails CI until updated on purpose — applies to a new verify step line or any new `send` outcome text (per a11y-plan §8 Plain language).
- Cases run inside the existing `nextest-integration` / `nextest-e2e` suites (CI: the per-OS `coverage` suite) on all three OS legs (per a11y-plan §9 Pipeline integration).

## Anti-patterns to avoid
- Parsing the rendered `claude` TUI screen for content as evidence — the compact post-condition and its tests rest on the SessionStart hook, never on screen content (per a11y-plan §11 Universal).
- Adding a spinner or progress redraw to cover the longer compact wait (per a11y-plan §11 Motion).
- Adding a new `suite` value or a separate driver for the new cases, or a retry-once policy for a flaky window case (per a11y-plan §11 CI; per a11y-plan §11 SLO).

## Contract bindings
- a11y ↔ tests: the keyboard / zero-viola-bytes boundary cases run on the tests' portable-pty `=0.8.1` outer-PTY driver and land in the harness `run` JSON `suites[].failures[]` (per a11y-plan §3 Keyboard test harness; per a11y-plan §9 Per-pipeline-stage a11y artifacts).
- a11y ↔ architecture/obs: the compact window's value is a compiled bound (PROVISIONAL at P4); a11y-plan §8 Timeout extensions states each driver-side bound by name and value, so the bound's statement there follows whatever P4 sets (per a11y-plan §8 Timeout extensions).

## Acceptance criteria contributions
- (a11y) A human key written while a verified `/compact` send waits in its compact confirm window reaches the child unblocked, and the outer-PTY stream holds none of viola's own literals (`unable`, `hint:`, a send outcome word), as a portable-pty nextest case sequenced on log records, not a timer (per a11y-plan §3 Keyboard test harness).
- (a11y) The human-mode output of a `/compact` send at each outcome carries no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`, no `\r` redraw or cursor sequence during the wait, and any refusal ends with `hint:` last on stderr with its typed exit code, pinned by literal or trycmd (per a11y-plan §4 P6; per a11y-plan §8 Error recovery).
- (a11y) The new row's `viola verify` step line keeps the `[NN/NN] … pass|fail` form, its total moved by the new row as the step set is built (how verify numbers its steps against `LedgerRow::ALL` is research's question), with `fail` uncoloured and the pinned verify strings updated on purpose (per a11y-plan §4 P6; per a11y-plan §8 Plain language).
