## Project signals (from arch + input)

- **Product type:** Hybrid local developer tool (arch §Project Intent): a native cross-platform CLI binary + a Claude Code plugin (hooks + stdio MCP server) calling it + a minimal view-only local web GUI served by the same binary.
- **Surfaces in current scope:** 4 — CLI verbs (`run · send · wait · last · list · answer · pause · release · link · unlink · verify · ui · plugin install`); hook + wrapped-TUI passthrough; MCP tools (`send · wait · last · answer · list`); web-spa strip-bay page (view-only). Deferred: GUI brake routes, phone/remote view, distribution.
- **Crates / modules:** 8 product (`viola` root bin, `viola-core`, `-pty`, `-channel`, `-state`, `-agent-claude`, `-mcp`, `-ui`) + 2 test-side (`viola-e2e`, feature-gated `viola-fake-agent`) per intent F-23 — 10.
- **Capabilities (Established Decisions count):** 37 items in arch §Established Decisions (PTY, screen model, delivery confirmation, state store, IPC, API style, MCP, hook transport/contract, wheel, links, budget, ledger, real-time, liveness, GUI scope, …).
- **Standard Contracts:** ~16 — GUI `/health` · `/ready` · `/api/info` · sessions/links envelopes · Problem Details · SSE feed · event line · snapshot envelope · instance snapshot · channel frames · 9 channel methods · event data per kind · CLI `--json` · MCP refusal · hook contract · session liveness.
- **Cross-cutting concerns:** 12 (config management, identity by instance, fail open, mixed-version tolerance, capability ledger gate, Tokio containment, crash-safe writes, diagnostic channels, cross-platform discipline, untrusted upstream text, local endpoint trust boundary, agent-driven style).
- **Security tier (cross-input):** Minimal (0) with targeted elevations for the local privilege boundary (security-plan §Threat Model Summary) — IPC endpoint as a code-execution interface, loopback GUI streaming content, code-bearing state files.
- **Project signals from input.md:** subscription-only through the unmodified binary; Windows first with 3-OS CI from day one; a first live test (overseer drives builder) is the foundation's acceptance; security is first-class because the bridge types into sessions that run commands. Version intent (`viola-0.1.0/intent.md`) is authoritative and ordered (a)–(g), with founder route rules (overseer-relayed, user-confirmed binding).
- **Existing Scopes:** None — new project (greenfield; repo holds only `refs/`, `.andromeda/` masters and a stray `prototype/`).

## Calibration outcome

- **Hierarchy depth:** 3 levels (epoch → sub-block → chunk)
- **Reasoning:** 4 surfaces × 10 crates with 37 established decisions and 53 intent capabilities puts the two dense epochs (Foundation infra, the web UI) at 8–11 concerns each → depth 2 inside them, while the slice, capability and hardening epochs stay depth 1; three levels is the resulting maximum, not a default.

### Adjustments applied (optional)

- **Re-calibration (self-correction before Phase 1 output):** decomposing the first-pass single "thin Windows slice" epoch yielded 12 chunks against a median of 5 — over the 2×-median balance bound — so it splits at its natural seam into "Windows slice I: wrapper, events, ledger" (the driven side) and "Windows slice II: driving verbs and live proof". "Session state & governance" now precedes "Driver surface" because `list` and the MCP `list` tool read the board; the exit-cause catalogue (F-18) moves to the end of security hardening because three of its causes (strict modes, server verification, pinned-hash mismatch) only exist there.
- **+1 epoch (split of (d)):** intent group (d) "Remaining v1 capabilities" carries 9 findings (F-34 moves into the slice; F-35–F-42 remain) plus the arch amendments they implement (F-13, F-20, F-24) — ~12 concerns, 2× the median epoch — so it splits into "Session state & governance" (state healing, statusline, budget, links, board) and "Driver surface" (CLI contract, output discipline, MCP, plugin install).
- **Founder route rules (binding, user-confirmed):** epoch ORDER is fixed by the intent's (a)–(g) + the rules — Foundation (chunk 1 = 3-OS CI + headless harness with fake agent, five agent-run commands, JSON logs; all infrastructure before feature code) → the thin Windows slice → the remaining v1 capabilities → security hardening → web UI → cross-OS completion / ship. Two security prerequisites are pulled FORWARD into the slice: the SQOS spike before the channel-client chunk, the pure-Rust SHA-256 choice before the chunk that writes `bin/` (intent F-43).

## Epoch outline (8 epochs)

- **Drilldown depth:** 2

- **Concerns:**

  - Toolchain floor 1.96 + pinned stable (F-19)
  - Headless harness `boot · run · status · cleanup · logs` via identical shims (F-02; TP §3)
  - Fake agent + recorded-fixture contract suite + fixture hygiene (F-03; TP §6-§7)
  - Structured JSON logs from every process + `logs` merge view (F-04; OB §3, §6)
  - Diagnostics roots and sinks — the logging half of F-17
  - Obs gates: panic hook, schema conformance, canary secret scan, print/log lint bans (F-05; OB §7-§10)
  - Mutation gate per chunk from chunk 1 (F-06)
  - Coverage / perf / property-corpus / no-flake gates + one `gate` verdict (F-07)
  - Code-graph seeded + Rust plane on first code + TS plane stated (F-08)

  - Sub-blocks: (1a) CI + harness spine · (1b) observability plane · (1c) quality gates + tree

### Epoch 2 — Windows slice I: wrapper, events, ledger

- **Scope:** The driven half of the slice on Windows — the two chunk-blocking security prerequisites, the PTY wrapper, instance state + start order, the wrapper channel, hooks → normalised events, and the capability ledger with `viola verify`.
- **Drilldown depth:** 1

## Notes for Phase 1 synthesis

- **Founder rule — chunk 1:** the first chunk is 3-OS CI + the headless harness (fake agent, the five agent-run commands, JSON logs), with the per-chunk mutation gate live from it (F-06 "from chunk 1"). "No crate without a real consumer and a test" governs every crate's first appearance: each product crate is born in the first chunk that consumes it (`viola-pty` at the PTY wrapper, `viola-state` at instance state, `viola-channel` at the channel, `viola-agent-claude` at the first Claude-specific behaviour, `viola-mcp` at the MCP server, `viola-ui` at the ui server).
- **Founder rule — ordering:** all infrastructure (Epoch 1) before feature code; then the thin Windows slice (Epochs 2–3); heavy security ACL work (Epoch 6) after the slice.
- **F-43 placement:** the SHA-256 choice precedes the chunk that writes `bin/` (instance state); the SQOS spike precedes the chunk that writes the channel client. Both sit at the head of Epoch 2; neither drags the ACL work forward. A failed spike never falls back to an unprotected connect.
- **Security amendment ordering (S:358-364):** amendments land no later than their implementing chunk — (8) at instance state, (2)(6) at the channel, (7) at the ledger, (3) at confirmed send, (4) at the wheel, (1)(5) at the ui server, which is F-09's claim point.
- **Capability claim rule (binding):** every intent finding (v1-01…v1-53) must be claimed by at least one chunk; arch-amendment findings (F-09…F-26) are claimed by the chunk that implements them (its wrap reconcile amends arch). The overseer checks capability-to-chunk coverage at the P4 review, so Phase 1 keeps `coverage-map.md` in the run dir.
- **Ledger before answers:** an unstamped CLI withholds every dialog answer, so the ledger + `viola verify` (incl. verify-against-fake-agent in CI, F-14) precede the dialog-answer chunk.
- **Unix-specific work after the Linux live run:** cross-platform code paths build and test on all three OSes from chunk 1, but the Unix-specific parity chunk lands only after one live Linux `viola run` (F-53; H:180-181).
- **Observability rides every chunk:** logs land in chunk 1; each later chunk emits its own events under the closed vocabulary — obs is not a late epoch.
- **Design/a11y bootstrap:** the web toolchain + a11y harness and the design token bundle land at the head of the page sub-block in Epoch 7 (the only UI surface); the CLI output discipline (design cli + a11y P4/P6) lands in Epoch 5.
