## Relevance
partial — no web-spa surface, but M1's PTY survivors, M2's red and P5's orphan child all touch the tui/cli boundary stand-ins (P4/P6) that a11y-plan gates inside the nextest/coverage suites.

## Constraints
- a11y-plan §3 Keyboard test harness → Tooling (and §4 P4 tui) requires three separate portable-pty outer-PTY nextest cases on all three OS legs. They cover (1) zero viola-originated bytes, (2) human keystrokes delivered unblocked past the current atomic paste, and (3) `\x1b[I`/`\x1b[O`, mouse and resize sequences never moving the wheel. On Windows the zero-bytes case must run on both the sideload backend and the inbox fallback. M1's `PortablePty::resize`, `HostTerminal::drop` and `sideload::search_restricted` survivors sit under this seam. Research must answer two questions: whether these cases exist at HEAD, and whether they are among M2's 80 failures.
- a11y-plan §10 Standard+ invariants require the CLI output-discipline invariants (P4, P6) to pass on all three OS legs inside `nextest-integration` / `nextest-e2e` (CI: the `coverage` suite). Where those invariants live in crate tests, the epoch-boundary mutation audit (test-plan §10) covers them. M2's red binaries (`run_cli`, `hook_fail_open`, `cli_verify`, `cli_version_gate`, …) may host them. Whether they do is research's question. If they do, M2's green read is also this invariant's read.
- a11y-plan §10 Cross-input parallel: a flake keeps the chunk red until its root cause is fixed. `retries: 0` holds, and `test.skip` / `#[ignore]` are banned. M2 cannot reach green by ignoring, retrying or quarantining a case.
- a11y-plan §1 Critical path 4 (SC 2.1.1 boundary stand-in) and §11 Keyboard: a human keystroke in `viola run` is never blocked, refused or delayed past the current atomic paste. A P5 outcome where a `claude` child outlives its wrapper with no wheel is a path where the human cannot take over. Any fix routed from P5, and any M2 readiness/timing fix in the wrapper, must keep this clause.
- a11y-plan §1 CLI integration ("No new suite") and §9 Unit/integration row: results land in the existing harness `run` JSON `suites[]` entries (`nextest-integration`, `nextest-e2e`, `coverage`) under `gate --require coverage,doctest,playwright`. If P2's deadline lint is a test, it rides an existing suite. A new `suite` enum value needs a Decisions Log entry.
- a11y-plan §10 Performance budget, and §11 SLO's "never wait on sleeps or `waitForTimeout` in a11y specs": a11y specs wait on auto-waiting locators and SSE/DOM signals. Their Playwright `timeout` is a bound on `analyze()` (< 30 s), not a wait. If P2's lint scope reaches `e2e-web/`, it may assert a bound sits below a kill line, but it must not push any a11y spec toward a time-based wait. Whether the lint's scope includes `e2e-web/` is research's question.
- a11y-plan §11 Strategy: never claim WCAG conformance for the cli or the `viola run` TUI. The re-taken coverage figure and any M1 killing tests are output-discipline stand-in evidence, not a11y conformance evidence.

## Patterns to follow
- Outer-PTY boundary case shape (a11y-plan §3 Keyboard test harness → Tooling): inject through the portable-pty outer PTY with `viola-fake-agent` as the child, and assert on the outer byte stream and the wheel state. This is the observation channel through which a resize or drop-time-restore effect can become visible to a killing test.
- Windows split (a11y-plan §3 Keyboard test harness → Tooling): Windows checks only that viola's own literals are absent, because the ConPTY host emits its own preamble on each backend. The sideload and inbox-fallback preambles are both recorded there, so an M2 diff of in-repo vs copied runs (`target/conpty-seed` is a suspect) can classify bytes the host produces rather than viola.
- Signal-keyed timing (a11y-plan §10 Performance budget): timing claims key on logged events and DOM signals, never on sleeps. This is the model for any readiness wait M2 repairs ("wrapper builder not ready", "timed out waiting for start").
- Binary verdict, no baseline (a11y-plan §9 Pipeline integration): a red is new by construction, with no fingerprint baseline that admits known failures. This matches M2's "open red until its cause is known".

## Anti-patterns to avoid
- Never block or delay a human keystroke past the atomic paste, and never count focus / mouse / resize sequences as editing (a11y-plan §11 Keyboard). This applies to any M1 resize test or fix.
- Never use a retry-once policy, `test.skip`, `#[ignore]` or a quarantine to read a suite green (a11y-plan §11 SLO; §10 Cross-input parallel).
- Never parse the rendered `claude` TUI screen for content or take screenshots as evidence (a11y-plan §11 Universal). P5's real-CLI leg measures through `Get-Process` and `claude agents --json` rows only.

## Contract bindings
- a11y-plan §3 Keyboard test harness ↔ test-plan §3 harness suites (`nextest-integration` / `coverage`): the tui boundary cases are nextest cases graded by the tests gate, so M2's diagnosis and fix grade them too.
- a11y-plan §10 Standard+ (CLI output discipline in crate tests) ↔ test-plan §10 mutation gate (`missed == 0`): M1's scoped mutation run is the evidence path for any output-discipline or boundary assertion that lives in a touched unit.
- a11y-plan §9 Unit/integration row ↔ the per-OS `test` job's `gate --require coverage,doctest,playwright`: the re-taken coverage feeds the same suite entry that carries the a11y stand-ins.
