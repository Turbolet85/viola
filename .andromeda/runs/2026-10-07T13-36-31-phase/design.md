# design extract

## Relevance
partial — the chunk draws no new surface and touches no token, type, spacing, motion or web component; it changes which of the already-specified readback outcomes and tape lines a newline-ending `send` lands on, and one of its three candidate remedies (the refusal) would need vocabulary the plan does not hold. The folded CI red (scope item 14) has no design surface.

## Constraints
- A send counts only once the matching `prompt-submitted` reads it back; until then it is open, and otherwise it is `unable` plus a typed reason — nothing is presumed. The remedy must reach "read back" through that match (or a measured post-condition), never by reporting success on the send's own say-so (per design-system §Brand Identity, domain anchor "Readback" and "Design direction").
- The confirmed outcome of scope item 2 must print as the existing read-back result: the `[RB] read back` line on stdout at exit 0 with name, time and cursor, in the padded form of the send sample. No new result word or line shape is introduced for a text that ended in a newline (per design-system §Surface: cli → Component Patterns, "2. `viola send`: the readback mirror").
- Streams stay split for whatever the remedy prints: results on stdout; the issue line, refusals and each refusal's `hint:` line on stderr; under `--json` one JSON document on stdout with the typed exit code and no hint text (per design-system §Surface: cli → Tokens (platform-specific), "Streams").
- The refusal vocabulary is a fixed set of short words, and each `RefusalDetail` variant has its own row. The plan's `not-delivered` details are `input-not-ready`, `no-prompt-submitted`, `turn-running`, `unknown-dialog` and `control-character`; it holds no detail word for "text ends in a newline". A remedy that refuses such a text therefore either reuses an existing detail in its listed meaning or needs a new row, a new hint and a new exit-13 word that this chunk cannot write into the master (per design-system §Color Palette → Semantic Colors, "Domain status colors").
- Every refusal a driver can receive carries exactly one `hint:` line keyed by reason (or reason · detail), human-mode only, and a hint never quotes the sent text or any upstream text. A refusal remedy has no listed hint; an invented wording is not covered by the plan (per design-system §Surface: cli → Component Patterns, "2. `viola send`: the readback mirror").
- The exit-code phraseology table fixes exit 13's human first words to the five listed `not-delivered` details and exit 0's result line to stdout; the chunk's outcome must stay inside that table (per design-system §Surface: cli → Component Patterns, "Exit-code phraseology").
- On the page, a matched driver prompt is folded into its send line's readback and prints no line of its own; a prompt filed `human` prints `prompt · human` at weight 600, and a `wheel` event prints `wheel  <holder> · <cause>`. The plan requires the event log of a confirmed newline-ending send to yield the folded form and no `human · human-input` line; the page code itself is not this chunk's (per design-system §Color Palette → Semantic Colors, "Domain status colors").

## Patterns to follow
- The readback mirror's four printed states — `[  ] open`, `[RB] read back`, `[/ ] unable`, `[  ] unconfirmable` — are the whole output set of `viola send`; a newline-ending send resolves to one of them, with `unable` padded to the readback-word column (per design-system §Surface: cli → Component Patterns, "2. `viola send`: the readback mirror").
- The web readback box takes `read` from the next `prompt-submitted` with origin `driver` in that instance's log, and `refused` from `send-refused`; the relabel to `origin:"driver"` on a claim is what the box reads, so the remedy keeps that event sequence (`send-issued` → driver `prompt-submitted`) as its source of truth (per design-system §Surface: web-spa → Component Patterns, "2. `<viola-readback>`: the readback box").
- `unconfirmable` is reserved for a send whose `ok` payload carries `confirmed:false` (a local command with no measured post-condition); it is not a fallback for a prompt the wrapper failed to match (per design-system §Surface: web-spa → Component Patterns, "2. `<viola-readback>`: the readback box").
- Human output is ASCII only and static: no colour beyond amber `DIALOG` and dim `stale`, so the send lines this chunk exercises carry no SGR in any mode (per design-system §Surface: cli → Tokens (platform-specific), "Colour decision order" and "Width").

## Anti-patterns to avoid
- Never print "done" or "success" without context: a confirmed send says what was read back, by whom and at which cursor (per design-system §Anti-Patterns → Per-Surface Bans, cli).
- Never print upstream text, paths, pids or anyhow chains in an error or hint: a refusal remedy's line and hint may name the cause as a fixed word only, never the sent text or its last byte in quoted form (per design-system §Anti-Patterns → Per-Surface Bans, cli).
- No optimistic confirmation: a clearance does not count until it is read back, so the remedy may not mark the send confirmed ahead of the matching `prompt-submitted` (per design-system §Anti-Patterns → Rejected Defaults, "Optimistic 'Sending…' spinner").

## Contract bindings
- design ↔ architecture: the `RefusalReason` / `RefusalDetail` / `PromptOrigin` / `WheelCause` rows mirror architecture.md's enums one row per variant. A remedy that adds or repurposes a detail is an architecture amendment first and a design row second, both the wrap's (per design-system §Color Palette → Semantic Colors, "Domain status colors").
- design ↔ security: the hint and refusal lines sit under the NEVER-log floor and the fixed-message rule; the cli ban cites the security plan directly (per design-system §Anti-Patterns → Per-Surface Bans, cli).
- design ↔ tests: the chunk's confirmed-outcome case reads the `ok` result and the event lines; where it also reads human output, the expected text is the send sample's `[RB] read back` line, stdout, exit 0 (per design-system §Surface: cli → Component Patterns, "2. `viola send`: the readback mirror"). Whether an existing test already pins that line for a plain send is research's question.
- design ↔ a11y: a readback refusal is one of the events the page announces, and the send line's accessible name is carried by the word cell; the chunk changes which word a newline-ending send produces, not the announcement rule (per design-system §Surface: web-spa → Component Patterns, "2. `<viola-readback>`: the readback box").

## Acceptance criteria contributions
- (design) A `send` whose text ends in a newline and is delivered prints the `[RB] read back  <name>  <time>  cursor <n>` result on stdout with exit 0, and no `[/ ] unable` line or `hint:` line on stderr (per design-system §Surface: cli → Component Patterns, "2. `viola send`: the readback mirror").
- (design) The instance's event log for that send holds `send-issued` followed by a `prompt-submitted` with origin `driver` and no `wheel` line with cause `human-input`, so the page's readback box source resolves to `read` and no `prompt · human` line is drawn (per design-system §Surface: web-spa → Component Patterns, "2. `<viola-readback>`: the readback box").
- (design) The chunk introduces no refusal reason, detail word, hint wording or exit-code word absent from the plan; if P4 chooses the refusal remedy, the plan names the missing row and hint as a held amendment instead of shipping an unlisted word (per design-system §Surface: cli → Component Patterns, "Exit-code phraseology").
- (design) Under `--json` the same send returns one `{"v":1,"ok":{…}}` document on stdout with no hint text and no styled byte (per design-system §Surface: cli → Tokens (platform-specific), "Streams").
