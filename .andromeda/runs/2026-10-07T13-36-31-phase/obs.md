## Constraints
- obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback requires an ordinary delivered send to write, wrapper side, `send-issued{corr:<cursor>, from, text_bytes}` then `send-confirmed{corr:<cursor>, confirmed, duration_ms}`, with `run.confirm_window` closing on the matching `prompt-submitted{origin:"driver"}`; `send-refused{detail:"no-prompt-submitted"}` is the line for window expiry only. On the path the remedy covers, a newline-ended send must therefore end on `send-confirmed`, on the same cursor, `conn` and `rpc_id` as its `send-issued`. Whether the code's `send-*` emission already follows the claim's outcome with no edit of its own is research's question.
- obs-plan §6 Log Coverage (additive field catalog, `detail` code catalog) and §3 Log format JSON schema close the `event` enum, the `send-*` field list and the refusal details (the arch `RefusalReason` details verbatim); a new `event` value needs a Decisions Log entry. The remedy may add no event, field or detail. The third remedy shape (refuse with nothing typed) has no listed detail of its own: it is either an existing detail used as the catalog defines it, or an enum widening the plan does not hold — P4's to say, not answered here.
- obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback names one `text_bytes` on both `send-issued` and the `pty.paste_write` span and gives no rule for a pasted text that differs from the sent text. The second remedy shape (strip the last newline before the paste) makes the two differ by one byte; which text `text_bytes` counts there is unstated in the plan and belongs on the P4 card. The first shape (wrapper-side acceptance) leaves both equal.
- obs-plan §8 PII Scrubbing (data classification row "Prompt text, assistant output") requires that send text and `prompt-submitted.data.text` reach no home-level process-log line: only `text_bytes` is logged, under `#[instrument(skip_all)]`. The comparison of the sent text with the submitted prompt must log neither side, nor a diff, a length pair outside the catalog, or the dropped byte.
- obs-plan §4 Scenario: Human takes the wheel, automation is refused, `release` returns it requires one `run.wheel_transition` per wheel change and `send-refused{refusal:"human-typing", wheel:"human", side:"wrapper"}` on a send refused under a human-held wheel. A confirmed newline-ended send changes no wheel, so it must leave no such transition and the following send no such refusal line; the `wheel` record in `events.ndjson` stays the audit record.
- obs-plan §10 SLO Invariants & Telemetry Budgets (Standard+ invariants, Deterministic emission) requires events to key on hook events and `events.ndjson` offsets, nothing derived from screen content, and no log-based wait resting on a sleep. The claim must recognise its prompt from the hook event, never from the screen model, and the new test's wait for the confirmed outcome must be event-driven.
- obs-plan §9 CI Integration (Telemetry artifact handling; Step order and conditions) requires `harness-<os>` to carry `target/agent-run/` less `chunk.diff`, captured on failure before the scan, with G2, G4 and the secret scan `if: always()` and every upload gated on the scan's success at `retention-days: 7`; obs-plan §8 PII Scrubbing (integration point 6, "Unscanned uploads, admissible by content") keeps `target/run-archive/<n>/` out of every upload. The plan names no upload path over `target/llvm-cov-target/`; whether attempt 1's corrupt profile is inside any artifact is research's question against that run. A fix for the red that adds or widens an upload must meet the same guard (scanned before upload, or dropped).

## Patterns to follow
- Every line through `obs_event!` with explicit typed fields and `corr` set as a typed value; spans as `#[instrument(skip_all, name = "<area>.<operation>", fields(...))]` with static names (obs-plan §4 Span / Trace Coverage, span naming convention).
- `corr`, `conn` and `instance` passed as explicit values into the thread that handles the `hook.event` and the thread that holds the send's window, never recovered from span context (obs-plan §3 Trace context propagation → Internal async boundaries).
- One send is identified by target `instance` + `corr` + `conn` + `rpc_id`; the test reads its outcome by that join, not by timestamp (obs-plan §3 Trace context propagation → IPC boundaries, Send ↔ channel link).
- No metric code: `viola.send.outcome` and `viola.send.confirm_ms` are derived from the `send-confirmed` / `send-refused` lines, grouped by closed enums only; the newline-ended send moves between existing groups (obs-plan §5 Metric Coverage, per-surface / per-path metrics).
- The new case's viola home under `target/e2e-home/`, so G2, G4, the secret scan and the `diag-<os>` upload read it (obs-plan §9 CI Integration, Pipeline integration → Integration tests).

## Anti-patterns to avoid
- NEVER log send text or prompt text in a home-level file, and NEVER log a field outside the §6 catalog (obs-plan §11 Obs Anti-Patterns → PII Scrubbing) — a "claim mismatch" diagnostic line is both.
- NEVER add an `event` value or rename a tests field without a Decisions Log entry, and NEVER call the raw tracing macros outside `viola_core::obs` (obs-plan §11 Obs Anti-Patterns → Logs).
- NEVER add a retry-once policy for a flaky telemetry assertion (obs-plan §11 Obs Anti-Patterns → SLO); a re-run is not a substitute under `retries = 0` (obs-plan §11 Obs Anti-Patterns → CI) — the folded red is not closed by a green attempt, and its fix may not drop a failing job's diagnostics.

## Contract bindings
- obs ↔ tests harness: the `send-*` lines and their `corr` rule are the test-plan §3 Log format reproduced verbatim (obs-plan §3 Log format JSON schema); obs aligns to tests. The new case's assertions on `send-issued` / `send-confirmed` read them through `agent-run logs`; the product lines it also reads (`prompt-submitted` with `origin`, absence of `wheel`) are the arch event stream in `events.ndjson`, not obs lines.
- obs ↔ architecture: obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback says "the matching `prompt-submitted{origin:"driver"}`" and defines no match rule; the rule (and its newline exception sentence, scope item 12) is architecture's. Refusal details are the arch `RefusalReason` details verbatim (obs-plan §6 Log Coverage, `detail` code catalog).
- obs ↔ security: the High-class rule for send and prompt text, and the tests-owned canary that every synthetic input embeds (obs-plan §8 PII Scrubbing, integration point 6); the new case's sent text carries the canary like any other.
- obs ↔ design / a11y: the readback words `read back` / `unable · <reason> · <detail>` are driven by the same `send-confirmed` / `send-refused` lines (obs-plan §4 Span / Trace Coverage, Frontend observable boundary); the newline-ended send's readback follows the line with no page change.
- obs ↔ tests (the folded red): G2's scope and single seam exemption, G4 and the zero-unlogged-panics invariant bind any change to the fake agent's or `viola hook`'s exit path — `hook` still exits 0 and each panic still writes exactly one line (obs-plan §10 SLO Invariants & Telemetry Budgets, Zero unlogged panics; obs-plan §9 CI Integration, Gate commands G2).

## Acceptance criteria contributions
- (obs) For a sent text whose last byte is a newline, on the path the remedy covers, the wrapper's role file holds one `send-issued` and one `send-confirmed` whose `confirmed` is not `false`, sharing `corr` (the send cursor), `conn` and `rpc_id`, and no `send-refused{detail:"no-prompt-submitted"}` on that cursor; with the remedy removed the control reads the `send-refused` line instead (per obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback).
- (obs) The send that follows it writes no `send-refused{refusal:"human-typing", wheel:"human"}` (per obs-plan §4 Scenario: Human takes the wheel, automation is refused, `release` returns it).
- (obs) `schemas/diag-line.v1.json` and `schemas/diag-detail.v1.json` are unchanged by the remedy, G4 passes on the new case's home, G2 counts zero, and the canary in the sent text appears in no home-level `diagnostics/*.ndjson` (per obs-plan §9 CI Integration, Gate commands G2 / G4; obs-plan §8 PII Scrubbing, integration point 6).
- (obs) Any `ci.yml` edit made for the folded red leaves G2, G4 and the secret scan `if: always()`, keeps every upload gated on `steps.secret-scan.outcome == 'success'`, and adds no artifact member that is neither scanned nor admissible by content (per obs-plan §9 CI Integration, Step order and conditions; obs-plan §8 PII Scrubbing, integration point 6).
