# security extract

## Relevance
relevant — the chunk changes what `send` types into the PTY after validation, which is the plan's paste-text boundary (security-plan §Input Validation, Paste text row; §Threat Model Summary, Attack surface: CLI input, the `send` text written into the PTY).

## Constraints
- security-plan §Input Validation (Paste text row) requires `validate_paste_text` to run first, on the text as received, over decoded `char`s, with CR, LF and TAB allowed and every other C0, DEL and C1 refused whole. The inner CR and CRLF rule must sit after that check and must not move, weaken or reorder it: a text that holds a refused character and an inner CR or CRLF is still refused `not-delivered` / `control-character` with nothing typed.
- security-plan §Input Validation (Paste text row) requires the typed text to be taken once (`viola_agent_claude::hook::typed_text`) and to be the only text `send` uses from there on: the local-command classification, the in-flight text of the exact match, `text_bytes` and the paste. The inner rule therefore belongs inside that one taking, not as a second transformation at the paste site or the match site. Whether every reader in the code takes that one value is research's question.
- security-plan §Input Validation (Paste text row) states today that the typed text removes every trailing CR and LF "and nothing else", naming a CR or LF that is not at the very end as kept. The chunk lands a founder's ruling that changes that sentence, so the plan and the chunk's rule disagree until the wrap amends the row. The row records each such ruling with who gave it, when, who relayed it and the chunk: the plan needs those four facts on disk for the amendment (the same wording stands in §Threat Model Summary, Attack surface: CLI input, both bullets, and in §Security Anti-Patterns § Input).
- security-plan §Threat Model Summary (Attack surface: CLI input, the `send` text written into the PTY) names delivery confirmation, the comparison of the `prompt-submitted` text with the typed text, as the only post-hoc check on a paste. The chunk must reach a confirmed send by changing what is typed, never by loosening that comparison (no CR-insensitive or newline-normalising match on the submitted side): a looser match would file a prompt the driver did not type as the driver's.
- security-plan §Input Validation (CLI arguments / stdin row) requires the client's `refusal_of` to read a refused character first and then the empty typed text, exit 13, both before any frame; §Input Validation (Paste text row) requires the wrapper to repeat the empty-text refusal directly after the typed text is taken and before the first wheel read, with nothing reserved, issued or typed. Under the new rule both sides must still reach the same verdict for a text of only CR and LF characters, through the one shared function.
- security-plan §Security Anti-Patterns § Input requires answer free text to be typed as validated. The inner CR rule is `send`'s alone and must not reach `answer.response.message` or the question answers. Whether the `answer` path shares any code with `typed_text` is research's question.
- security-plan §Error Handling (Error format: Channel) lists the `send` refusals carried in `result.refusal` as `not-delivered` / `control-character` and `not-delivered` / `empty-text`, and §Error Handling (External responses) requires codes and fixed messages with no upstream text. The chunk adds no refusal detail and changes no rung; a hint or refusal line must not quote the sent text or name the position of a CR.

## Patterns to follow
- One paste, one write: security-plan §Input Validation (Paste text row) requires the paste to be one `ESC[200~…ESC[201~` + CR `write_all` of the typed text through `viola-pty`'s `PasteHandle`. The CR after the terminator is the paste's own submit key and is outside the typed text; "the typed text holds no CR" concerns the bracketed content only.
- Refusal order: security-plan §Input Validation (Paste text row, Wire outcome) requires `control-character`, then `empty-text`, both checked before the Conventions refusal order, with the wrapper's check authoritative and first.
- Shared validators: security-plan §Input Validation (Boundary paragraph) requires shared validators to live in `viola-core` so the CLI, MCP and the wrapper call the same function; the client's read of the typed text for its empty-text check uses the same `typed_text` the wrapper uses, never a client-side copy of the rule.
- Client-side refusal record: security-plan §Input Validation (CLI arguments / stdin row) requires a client refusal to exit 13 before any frame with a `send-refused{side:"client"}` line; a case added for a CR-only text follows that form.
- Content placement: security-plan §Bootstrap phases (`logging-redaction-wire`) requires user content outside the contract payloads to go only to `instances/<name>/diagnostics/`. A test or probe that reads the typed or submitted text for the absence of a CR reads it from a contract payload (`prompt-submitted` in `events.ndjson`) or from the PTY, never from a new log line that carries the text.

## Anti-patterns to avoid
- security-plan §Security Anti-Patterns § Input: NEVER refuse LF, CR or TAB, and NEVER strip a refused character silently. The inner rule must not be built as a refusal of a text for holding a CR (the option the founder did not choose), and the conversion must touch only CR, an allowed character, after validation has passed.
- security-plan §Security Anti-Patterns § Universal: NEVER let `config.json`, a `VIOLA_*` variable or a CLI flag switch off `validate_paste_text`, and environment variables are not a configuration channel. No key, variable or flag may select the old or the new CR behaviour or skip the check for a pre-converted text.
- security-plan §Security Anti-Patterns § Code Patterns: NEVER build the local-command list from runtime or upstream text. The classification of the converted typed text reads only the compiled `viola-agent-claude` list; the chunk adds no entry derived from a sent text.

## Contract bindings
- tests: security-plan §Input Validation (Parser surfaces) names `validate_paste_text` as a fuzz / property surface whose cases tests owns; the changed `typed_text` table and property (test-plan §4) carry the security floor that conversion follows validation and removes no refused character.
- obs: security-plan §Input Validation (Paste text row) requires `text_bytes` to read the typed text, so its value for a text with CR LF pairs falls below the sent byte count; the field's definition is obs-plan's, and the `send-refused` line's shape is obs-plan's.
- architecture: security-plan §Threat Model Summary (Attack surface: CLI input) cites Established Decisions: Delivery Confirmation and Human Takeover / Wheel for the typed text and the exact match; the wrap's amendments to the two must land together.
- architecture (capability ledger): security-plan §Security Anti-Patterns § Universal requires a stamp to hold exactly the seventeen ledger rows before a non-`null` dialog decision flows. A probe row added for a shape `send` relies on would change that count and every stamped home's `cli_verified`; the scope plans none, and one found necessary at P3 is a P4 card.
- wrap amendments owed in this plan: §Threat Model Summary (Attack surface: CLI input, entry point and trust boundary), §Input Validation (Paste text row) and §Security Anti-Patterns § Input (the carve-out sentence, which names only the dropping of trailing CR and LF, not a substitution inside the text).
- live confirmation: security-plan §Data Protection (Accepted risk: verify's trusted runs) requires that viola itself writes nothing under `~/.claude` and accepts the CLI's own transcripts as a residual for `viola verify`'s runs. The plan does not state that class for a hand-driven live rig; the cap of starts is the operator's direction in the scope, not this plan's.
- fixtures: security-plan §Data Protection (Repository fixtures) requires synthetic probe prompts and a scrub for home paths and usernames in `fixtures/claude/`. The scope plans no fixture; the plan states this rule for fixtures only, and whether committed chunk evidence is held to it is not stated there.

## Acceptance criteria contributions
- A wrapper-side test sends a text that holds a refused character (ESC) and an inner CR or CRLF and reads `not-delivered` / `control-character` with no byte written to the PTY and no wheel read (per security-plan §Input Validation, Paste text row).
- A property over texts that pass `validate_paste_text` reads that the typed text passes it too, holds no CR, and holds no character that is neither in the received text nor LF (per security-plan §Security Anti-Patterns § Input).
- A text of only CR and LF characters, mixed orders included, is refused `not-delivered` / `empty-text`, exit 13, by the client before any frame and by the wrapper before the first wheel read, with nothing reserved, issued or typed (per security-plan §Input Validation, CLI arguments / stdin row).
- For a text with an inner CR or CRLF, the bracketed content of the one paste write equals the in-flight text byte for byte, and the send is confirmed by an equality on that text with no normalisation of the submitted side (per security-plan §Threat Model Summary, Attack surface: CLI input, the `send` text written into the PTY).
