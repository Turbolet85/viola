## Relevance
relevant — the chunk changes the one rule architecture §Established Decisions [Delivery Confirmation] turns on (what `send` types), inside the crate and call sites that entry names.

## Constraints
- architecture §Established Decisions [Delivery Confirmation] is written for the state BEFORE this chunk: it requires the typed text to drop the trailing CR and LF characters and nothing else, and it names the inner CR / CR LF outcome as measured, not fixed and carried on the working route. The chunk lands the founder's ruling for exactly that carried case, so the entry's "nothing else" wording and its inner-case sentences are the wrap's expected amendment, not a rule the plan may keep. Everything else in the entry stays binding (next items).
- architecture §Established Decisions [Delivery Confirmation] requires `validate_paste_text` to run first on the text as received, the typed text to be taken once directly after it through `viola_agent_claude::hook::typed_text`, and that one value to be the only text `send` uses: the local-command classification, the in-flight text the match compares, `text_bytes` and the paste. The CR-to-LF rule has to sit inside that single taking; whether every reader in the code already reads the one value is research's question.
- architecture §Established Decisions [Delivery Confirmation] requires the match to be exact equality between the typed text and the normalised `prompt-submitted` `text`, with nothing else trimmed, and requires `prompt-submitted` (relabelled `driver`) to precede `send-confirmed` in `events.ndjson`. The chunk reaches "confirmed" by changing what is typed, never by loosening the comparison.
- architecture §Conventions → Error handling schema fixes the `send` refusal order (`control-character` first, then `empty-text` before the first wheel read, then the wheel, budget, turn and gate rungs) and the closed `not-delivered` detail list, with exit 13 for `not-delivered`. The chunk adds no detail and moves no rung; a text holding a refused character beside a CR stays `control-character`, and a text of only CR and LF characters stays `empty-text`.
- architecture §Established Decisions [Agent Coverage] and §Inherited Defaults (Agent isolation) require Claude-specific knowledge to live only in `viola-agent-claude`. "The CLI submits a CR as an LF" is such knowledge, so the rule belongs in that crate's `hook` module; the root bin consumes the result and holds no CR handling of its own. architecture §Infrastructure Patterns → Crate dependency direction requires that crate to stay pure and Tokio-free; the rule needs no new dependency there or in the root bin.
- architecture §Design Philosophy (Measured, never assumed) and §Cross-cutting Patterns (Capability ledger as the single gate for CLI-specific behaviour) require every CLI behaviour a `send` relies on to be a ledger row with a `viola verify` probe; the one ruled limit there is that a shape no `send` relies on needs no probe. After the change a `send` relies on the CLI submitting a pasted text's inner LF, and a run of inner LFs, unchanged. Whether a stamped row or a compiled Run B paste text already measures that is research's question; if none does, it is a P4 card, as the scope already says.
- architecture §Established Decisions [Human Takeover / Wheel] requires that only the in-flight send's own matching prompt is relabelled `driver` and moves no wheel, and that a prompt which is not the typed text claims nothing and, filed `human`, still moves the wheel. The chunk must leave that logic untouched: the driver keeps the wheel because the match now succeeds, not because the wheel rule changed.

## Patterns to follow
- One function, two product callers: `viola_agent_claude::hook::typed_text` is read by the wrapper's `send` (`src/run/send.rs`) and by the client's `refusal_of` (`src/cmd/send.rs`), per architecture §Established Decisions [Delivery Confirmation]. Both must read the same rule after the change; a rule that needs an owned value instead of a slice changes the signature both callers see.
- Local-command classification is exact equality of the typed text with a `LOCAL_COMMANDS` entry, no trimming, no case folding, never a leading-slash test, per architecture §Established Decisions [Delivery Confirmation]. The chunk keeps it reading the typed text; whether any list entry holds a newline is research's question (the scope's own check).
- Normalisation of `prompt-submitted` (long-paste wrapper and its frame removed, tag escaping reversed) happens in `viola-agent-claude` before the event is emitted, so the wrapper-side matcher sees no Claude shape, per architecture §Standard Contracts (Event `data` per kind → `prompt-submitted`) and §Established Decisions [CLI Version Compatibility] (the long-paste wrapper). A typed text that gains LFs can cross the wrap condition that entry records as read statically, not measured; whether the unwrap returns exactly the typed text for such a text is research's question.
- Proof tiers follow architecture §Established Decisions [CI/CD]: unit and cross-process tests against the fake agent on the three CI OSes, the real CLI only in local live tests. Live results are written in the entry's own form (version, host, chunk, evidence file, named readings, an explicit "not measured" list), per architecture §Established Decisions [Delivery Confirmation].
- A send that cannot be confirmed is reported `not-delivered` and never retried, per architecture §Cross-cutting Patterns (Fail open toward the human). The live session's stop rule in the scope (one unconfirmed send ends the readings) matches it.

## Anti-patterns to avoid
- Loosening the match (a CR-insensitive or trimmed comparison in `SendSlot::claim` or in the hook normaliser) instead of changing the typed text: banned by the exact-match rule in architecture §Established Decisions [Delivery Confirmation] and §Standard Contracts (Channel methods → `hook.event`).
- Running the CR rule before `validate_paste_text`, or presenting it as a strip of a refused character: architecture §Conventions → Error handling schema requires validation first on the received text and "refused, never stripped".
- Hard-coding the CLI's CR or LF reading as an unconditional assumption with no ledger row or cited measurement behind it: banned by architecture §Cross-cutting Patterns (Capability ledger as the single gate for CLI-specific behaviour).
