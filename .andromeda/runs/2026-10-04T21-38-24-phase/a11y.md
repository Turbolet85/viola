# a11y extract

## Relevance
partial: the chunk adds no web-spa component, ARIA role, focus behaviour or key binding. It does add one new user-visible refusal (`not-delivered` / `turn-running` on an automated `send`) on the cli surface, inside the P2 and P4 paths. It also adds a state that must never reach the human keystroke path in `viola run`.

## Constraints
- The human always wins at the tui boundary. The running-turn state gates automated `send` only. It must never block, refuse or delay a human keystroke past the current atomic paste, and a human prompt that starts a turn must still be typed through unhindered (per a11y-plan §1 Critical Paths P4, SC 2.1.1 boundary stand-in; §5 Keyboard Navigation → tui; §3 Keyboard test harness → Tooling).
- The CLI refusal follows the error-recovery pattern. Human mode writes `unable  not-delivered  turn-running` to stderr, then a final `hint:` line, and exits with the refusal's typed exit code. `--json` is one document with no hint text. The reason and detail are given in text, never by colour alone (per a11y-plan §8 Error recovery → CLI; §1 Critical Paths P6, the SC 1.3.2 / 1.4.1 / 3.3.1 output-discipline stand-ins). The hint copy for `turn-running` is design's (the driver calls `wait` first). Whether a pinned `turn-running` hint string already exists is research's question.
- The kebab-case detail `turn-running` never appears without the plain word `unable` beside it, and a refusal never shows a bare code, URN or stack trace as its only text (per a11y-plan §8 Plain language).
- Output discipline holds on the new refusal path. `unable` takes no SGR. No SGR, glyph or cursor control appears under `--json`, non-TTY, `NO_COLOR` or `TERM=dumb`. The output is static and linear, with no spinner or redraw while a turn runs (per a11y-plan §1 A11y Scope → cli Notes; §6 State color tokens → CLI equivalent).
- Zero viola-originated terminal bytes. A `turn-running` refusal types nothing into the child and writes nothing of viola's own (refusal text, `hint:`, diagnostics) to the outer PTY stream (per a11y-plan §3 Keyboard test harness → Tooling, the zero-viola-bytes clause; §1 A11y Scope → tui).
- If a web-spa page is wired to `send-refused` at this point, the refusal reaches it only as the existing P2 readback-refused state, announced once through the single polite status region as `send to builder unable, <reason>, <detail>`, with no focus move. Whether the GUI page and its readback-refusal path have landed yet is research's question. This chunk builds no web surface (per a11y-plan §7 Live regions; §4 Per-component pattern catalog → P2; §5 Focus restoration → Live updates).
- Make no WCAG conformance claim for the cli or tui evidence this chunk produces. The assert_cmd / trycmd / portable-pty results are output-discipline stand-ins only (per a11y-plan §11 Strategy; §2 A11y Strategy).

## Patterns to follow
- The `human-typing` refusal pattern from P4: `send` refused on stderr with a typed exit code, pinned by assert_cmd. The `turn-running` case is its sibling at the next refusal rung (per a11y-plan §4 P4 → cli).
- The trycmd pin of `unable <reason> <detail>` plus the final `hint:` for each refusal, and assert_cmd checks of the typed exit codes and of no hint under `--json`, on all three OS legs. A new refusal detail gets its own pinned case, so any copy change fails CI until the pin is updated on purpose (per a11y-plan §8 Error recovery → Verification; §8 Plain language → Verification).
- The portable-pty outer-PTY boundary cases (zero viola bytes; human keystrokes unblocked). Each is its own nextest case on all three legs, and the fake agent is the child, so the case never parses `claude` content (per a11y-plan §3 Keyboard test harness → Tooling).

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste. A running turn is a reason to refuse automation only (per a11y-plan §11 Keyboard).
- NEVER colour CLI `unable`, never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run`, and never print a human-mode refusal without its `hint:` line, since `turn-running` is not the opaque `unknown` exception (per a11y-plan §11 Visual; §11 Cognitive).
- NEVER parse the rendered `claude` TUI screen to decide or witness that a turn is running. Turn state comes from hook lines only (per a11y-plan §11 Universal (agent-driven specific), R7).

## Contract bindings
- The CLI refusal copy binds to design §User-Facing Error Surfaces → CLI refusals. The `turn-running` detail and its `hint:` text are design-owned strings that the trycmd pin mirrors.
- The refusal binds to the obs `send-refused` event (joined on `corr` = the send cursor), which drives the web P2 readback-refused state and its status announcement (a11y-plan §1 Critical Paths P2 Source → obs Focus-Relevant Span Coverage).
- The boundary cases bind to the tests E2E driver → tui / cli (portable-pty `=0.8.1` outer PTY, assert_cmd / trycmd) inside the single instrumented `coverage` suite on all three OS legs (a11y-plan §2 Runner / CLI output discipline).

## Acceptance criteria contributions
- (a11y) A human-mode `viola send` refused during a running turn writes `unable`, `not-delivered` and `turn-running` as text on stderr, ending with a `hint:` line, with no SGR under non-TTY / `NO_COLOR` / `TERM=dumb`. The same refusal under `--json` is one document with no hint. A trycmd / assert_cmd case pins the copy and the typed exit code on all three OS legs (per a11y-plan §8 Error recovery → Verification).
- (a11y) During a running turn (including a harness-origin turn), human keystrokes injected through the portable-pty outer PTY reach the child unchanged and unblocked while an automated `send` is refused `turn-running` (per a11y-plan §3 Keyboard test harness → Tooling; §4 P4 → tui).
- (a11y) Across a `turn-running` refusal, the outer-PTY byte stream contains none of viola's own literals (refusal text, `hint:`). On Linux and macOS it also contains no SGR or cursor control the child did not emit (per a11y-plan §3 Keyboard test harness → Tooling, the zero-viola-bytes clause).
