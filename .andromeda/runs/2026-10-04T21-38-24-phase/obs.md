# obs extract

## Relevance
partial — the chunk adds no new obs surface, but it widens when the wrapper emits `send-refused{detail:"turn-running"}` on a must-trace path (Confirmed `send`) and touches `release` on the wheel path, so the existing line shapes, `corr` rules and default-deny catalog bind it.

## Constraints
- A running-turn refusal is a wrapper-side `send-refused{refusal:"not-delivered", detail:"turn-running", side:"wrapper", wheel}` plus the `channel-response{result_class:"refusal", refusal, detail}` on both sides, and the client's `process-exit{subject:"self", exit_code}`. The refusal is logged whether its cause is the in-flight `send` slot or the new running-turn state; `detail` stays the one closed code `turn-running`, with no new value to tell the two causes apart (per obs-plan §4 Scenario: Confirmed `send` (CL-1); §6 `detail` code catalog, "Refusal details are the arch `RefusalReason` details verbatim").
- A send refused at the `turn-running` rung comes before `send-issued`, so it has no arch cursor. Its wrapper `send-refused` carries `corr` = the target's `events.ndjson` end offset at the moment of refusal (a log join key, never returned to the caller), plus `conn` and `rpc_id` so that `(conn, rpc_id)` joins it to that call's `channel-*` lines. No `send-issued` line and no `pty.paste_write` span may precede it, because nothing is typed (per obs-plan §3 Log format JSON schema, `send-*` corr rule, D-28 / D-30; §4 Scenario: Confirmed `send`, "every wrapper `send-*` line … also carries `conn` … and `rpc_id`").
- No new `event` value (for example a turn-started / turn-cleared line) and no new field may be emitted without an obs Decisions Log entry. The scope assumes no new event kind; the running-turn state is not a catalogued field on any line, and `schemas/diag-line.v1.json` default-denies anything outside the §6 catalog (per obs-plan §6 Additive field catalog; §8 Default-deny posture; §11 Logs "add `event` values without a Decisions Log entry").
- `release` clearing the running-turn state stays inside the existing wheel telemetry. `run.wheel_transition` keeps its closed `cause` (`human-input|manual-pause|release`) and fires only on a wheel change. A `release` on a driver-held wheel "appends nothing", so a turn-state clear on that path must not add a `wheel` record or a new line. Whether `release` on a driver-held wheel clears the turn state at all is research's question (per obs-plan §4 Scenario: Human takes the wheel, automation is refused, `release` returns it).
- Turn start and end must key on hook-sourced events (`prompt-submitted`, `turn-ended`, `session-start`, `session-end`), never on screen content. vt100 stays a readiness/modal gate input only (per obs-plan §10 Standard+ invariants, "Deterministic emission"; §11 Telemetry Strategy "NEVER derive telemetry from screen content").
- The `prompt-submitted` records that now drive the turn state (the `human` and `harness` origins included) carry prompt text. That text, and any `<task-notification>` / `<agent-message>` body, never reaches a home-level process-log line. Only codes and `text_bytes` are logged (per obs-plan §8 Data classification rules, the prompt text row; §11 PII Scrubbing).
- Any new or changed wrapper code on the send or wheel path logs only through `obs_event!` under `#[instrument(skip_all, fields(..))]`, with `corr` as a typed field, never `?corr` / `%corr` (per obs-plan §11 Logs; §11 Spans / Traces "NEVER use a bare `#[instrument]`").

## Patterns to follow
- The existing wrapper `turn-running` refusal emission beside the in-flight `SendSlot` check in `src/run/send.rs`. The new running-turn rung should reuse the same `send-refused` emission point and fields rather than add a second emitter. Whether that site already emits the D-28 end-offset `corr` and the D-30 `conn` / `rpc_id` is research's question (per obs-plan §4 Scenario: Confirmed `send`).
- The `channel-response` `Drop` guard in `channel.dispatch`, so an early-return refusal still logs its response line (per obs-plan §4 Scenario: Confirmed `send`, Cleanup).
- The human-typing refusal line shape on the wheel path, `send-refused{…, wheel:"human", side:"wrapper"}`. A turn-running refusal while the driver holds the wheel carries `wheel:"driver"` (per obs-plan §4 Scenario: Human takes the wheel).
- The derived counter `viola.send.outcome`, grouped by `[side, detail]` over home-level role files. The new refusals land in the existing `turn-running` bucket with no new grouping key (per obs-plan §5 Per-surface / per-path metrics; Metric label cardinality discipline).

## Anti-patterns to avoid
- NEVER log a line per turn transition or per `prompt-submitted` / `turn-ended` pass-through in the wrapper's hook-event path. Log the refusal outcome only; the `events.ndjson` record is the audit trail (per obs-plan §11 Logs "NEVER log at `info` inside hot loops"; §11 Telemetry Strategy "NEVER over-instrument hot paths").
- NEVER put the running-turn state, an origin label or prompt text into a `detail` code or a free-text field; `detail` stays the closed `turn-running` (per obs-plan §11 PII Scrubbing; §11 Telemetry Strategy "NEVER let the signal pyramid collapse into free text").

## Contract bindings
- obs ↔ tests §3 Log format: the `send-refused` `corr` rule for pre-`send-issued` refusals (the `turn-running` case is named there) and the `(conn, rpc_id)` join are tests-bound. A new E2E case through the fake agent can assert the refusal through `agent-run logs` with `select(.event=="send-refused" and .detail=="turn-running")` and the absence of a `send-issued` for that `rpc_id` (per obs-plan §3 Log format JSON schema; §3 Snapshot / paste-to-AI integration).
- obs ↔ tests G4 / `schemas/diag-line.v1.json`: the lines written by the new wrapper unit and E2E cases count toward the zero schema-conformance-failure budget (per obs-plan §9 G4; §10 Error budget).
- obs ↔ arch §Standard Contracts: whether the running-turn state rides `snapshot.json` or any event is arch's to settle (P3). Obs requires only that no process-log field is added for it without a Decisions Log entry (per obs-plan §6 Additive field catalog).

## Acceptance criteria contributions
- A driver `send` during a running turn (a harness `<task-notification>` turn, or one left after a wheel move) produces exactly one wrapper `send-refused{refusal:"not-delivered", detail:"turn-running", side:"wrapper"}` carrying `corr` (the end offset), `conn` and `rpc_id`, with no `send-issued` and no `pty.paste_write` for that `rpc_id` (per obs-plan §3 Log format JSON schema D-28 / D-30; §4 Scenario: Confirmed `send`).
- Every home-level `diagnostics/*.ndjson` line written by the chunk's new tests validates against `schemas/diag-line.v1.json` (G4 green), with no new `event` value or field (per obs-plan §8 Default-deny posture; §9 G4).
- The secret-scan canary planted in the test prompts (`human` / `harness` `prompt-submitted` text) appears in no home-level process-log line (per obs-plan §8 Integration points item 6).
- A `release` on a driver-held wheel that clears the turn state writes no `wheel` record and no `run.wheel_transition` (per obs-plan §4 Scenario: Human takes the wheel, "a `release` on a driver-held wheel appends nothing").
