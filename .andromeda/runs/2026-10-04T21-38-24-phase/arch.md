# arch extract

## Relevance
relevant — the chunk implements a wrapper-state rule and a refusal rung that architecture §Established Decisions [Human Takeover / Wheel] and §Conventions (Error handling schema) already specify as target state.

## Constraints
- architecture §Established Decisions [Human Takeover / Wheel] requires: a `prompt-submitted` marks a turn running; `turn-ended`, `session-start` or `session-end` ends it; an automated `send` while a turn is running is refused `not-delivered` / `turn-running`, never queued, with nothing typed; the `viola release` that returns the wheel clears the running-turn state; `release` never empties the in-flight `send` slot. The same entry also says a `release` on a driver-held wheel "changes nothing and appends nothing" (and §Standard Contracts → Channel methods `release` says "changes nothing"). Whether clearing the in-memory turn state counts as such a change, given that it appends no line, is open for P3/P4 to settle. The entry's "as built, no running-turn state exists beyond the in-flight `send` slot" clause becomes a wrap amendment.
- architecture §Conventions (Error handling schema, the `send` order) requires the rung order `control-character` → `human-typing` → `budget-paused` → `not-delivered`/`turn-running` (a turn running, or another `send` in flight) → readiness gate (`input-not-ready`) → confirmation (`no-prompt-submitted`). Only the first applicable refusal is returned. The `answer` order has no `turn-running` rung, so `answer` and `hook.dialog` stay ungated by turn state. `turn-running` is already in the closed `not-delivered` detail set, so the chunk needs no new detail. Details are extended only in `viola-core`.
- architecture §Established Decisions [Delivery Confirmation] + §Standard Contracts → Channel methods (`hook.event`) require the in-flight send's own matching `prompt-submitted` to be relabelled `origin:"driver"` and appended before `send-confirmed`. A turn marked running by that prompt must not disturb the confirming send's settle. The scope says the mark applies to any origin (`driver` · `human` · `harness`). `hook.event` accepts exactly the five hook kinds. Whether `turn-ended` / `session-start` / `session-end` pass through the same wrapper append path as `prompt-submitted` is a question for research.
- architecture §Conventions (Naming patterns: Normalised event kinds) and §Standard Contracts (Event `data` per kind; Instance snapshot) require new event kinds only in `viola-core`, and the snapshot `data` field list is a closed contract. Running-turn state is not among its fields or among replay's log-derived fields. Mirroring it to the snapshot, or emitting it as an event, would amend those contracts. That needs a decision; do not add it by default.
- architecture §Standard Contracts (Event `data` per kind: `send-refused`) requires `{refusal, detail, cursor?}`, with `cursor` absent for a refusal before `send-issued`. A `turn-running` refusal falls before `send-issued`. That paragraph also makes `send-*` lines `source:"wrapper"`, log-only, never waking `wait`.
- architecture §Cross-cutting Patterns (Tokio containment) + §Established Decisions [Concurrency / Backend Framework] require the turn-state code on the `run` / `send` / channel-server paths to use std threads, blocking I/O and std locks only.
- architecture §Infrastructure Patterns → Crate dependency direction requires the wheel and its gates in the root bin to consume only normalised events. Claude-specific shapes stay in `viola-agent-claude`. The API-error-turn hook is a ledger row per [Human Takeover / Wheel] and §Cross-cutting Patterns (Capability ledger), and this chunk adds none.

## Patterns to follow
- One lock over related wrapper state: `WheelSlot` holds holder and cause under one lock (`src/run/wheel.rs`, per architecture §Established Decisions [Human Takeover / Wheel]). Follow that shape when placing running-turn state beside, not inside, the `SendSlot` flight slot.
- The `WaitFeed::appending` hook-line append runs inside the feed's lock and keeps the newest `turn-ended` (per architecture §Standard Contracts → Channel methods `wait`). Whether that is the right point to observe turn-start/turn-end kinds atomically with the append is a question for research.
- Wheel-move side effects (events, snapshot, span) run on the wheel's worker thread. Every snapshot write goes through the single `Snapshots` holder `src/run/snapshot.rs` (per architecture §Established Decisions [Human Takeover / Wheel]). This applies only if the chunk touches the snapshot.
- Mixed-version tolerance: any new field carries `v`, and readers skip unknown kinds and fields (per architecture §Cross-cutting Patterns, Mixed-version tolerance).

## Anti-patterns to avoid
- Queueing a refused `send`, typing any byte for it, or retrying it blindly (per architecture §Established Decisions [Human Takeover / Wheel]; §Cross-cutting Patterns, Fail open toward the human).
- Gating or delaying a human keystroke, `answer` or `hook.dialog` on the running-turn state. Refusals go to automated `send` only (per architecture §Design Philosophy, "The human always wins the wheel"; §Conventions `answer` order).
- Adding a Claude-named event kind or refusal detail, a hard-coded API-error-hook assumption, or any config key / `VIOLA_*` var / flag that disables the gate (per architecture §Conventions, Naming patterns; §Cross-cutting Patterns, Capability ledger; §Conventions, Environment variables).

## Contract bindings
- arch ↔ tests: the `send` refusal order and the `send-refused` line shape are the wire contract the wrapper unit cases and the fake-agent end-to-end case assert. The witness needs a fake-script turn with a `prompt-submitted` (a `harness` or `human` origin) and no `turn-ended` (architecture §Occupied Resources → Repository `fixtures/fake-scripts/`).
- arch ↔ obs: `send-refused` (`source:"wrapper"`, log-only) and the `wheel` record on `release` feed the audit trail and the SSE feed (architecture §Standard Contracts, Event `data` per kind). Whether turn start/end gets an obs line is obs's call.
- arch ↔ security: `release` keeps its `-32602 release-from-driver` refusal for a string `from` (architecture §Standard Contracts → Channel methods). `from` stays self-reported, never identity.

## Acceptance criteria contributions
- (arch) A `send` (no `send` in flight) after a `human` or `harness` `prompt-submitted` with no `turn-ended` returns `{"refusal":"not-delivered","detail":"turn-running"}`, writes no paste byte, and appends one `send-refused` line without `cursor` and no `send-issued` (per architecture §Established Decisions [Human Takeover / Wheel]; §Standard Contracts, Event `data` per kind).
- (arch) Rung order holds with a turn running: control characters → `control-character`; human wheel → `human-typing` / `manual-pause`; otherwise `turn-running`, never `input-not-ready` (per architecture §Conventions, Error handling schema).
- (arch) Each of `turn-ended`, `session-start` and `session-end` ends the running turn, and a following `send` goes on past the `turn-running` rung. A wheel-returning `viola release` after a human take clears the turn state but leaves an in-flight `send` slot in place. `answer` is never refused `turn-running` (per architecture §Established Decisions [Human Takeover / Wheel]; §Conventions `answer` order).
- (arch) No new event kind, `RefusalReason`, detail value or snapshot field lands, unless architecture §Standard Contracts is amended for it at wrap. The bin-side turn-state code stays tokio-free and Claude-shape-free (per architecture §Conventions, Naming patterns; §Cross-cutting Patterns, Tokio containment; §Infrastructure Patterns → Crate dependency direction).
