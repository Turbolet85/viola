# obs extract

## Relevance
partial — the chunk adds tests, a harness exclusion and a workflow fit, and no product telemetry; obs binds it through the mutation row of its CI section, the upload and path rules for mutation output, and the closed strict-modes codes.

## Constraints
- obs-plan §9 CI Integration (Platform) requires `windows-mutants.yml` to stay the dispatch-only Windows mutation leg that uploads nothing: a raised ceiling or a per-file split of the `viola` job adds no upload step, and the per-job reading comes from the job's own output.
- obs-plan §9 CI Integration (Pipeline integration, Mutation row) requires obs code (`obs_event!` call sites, `MillisUtc`, the panic hook, the `cfg(windows)` code in `src/panic_frames.rs`) to be scored like product code, and reads a missed or timed-out obs-code mutant, or unviable outnumbering caught, as red at that run. The host exclusion of scope §3 may take out of the count only a mutant whose covering predicate is false on the host; whether the pinned recipe (`cover.py`) separates the nine `cfg(unix)` twins in `src/panic_frames.rs` from that file's `cfg(windows)` mutants is research's question.
- obs-plan §10 SLO Invariants & Telemetry Budgets (Build / deploy failure conditions) requires a surviving cargo-mutants mutant in obs code at a `run --mutants` to count as a failure: an obs-code mutant leaves the measurable set by a false predicate, never by an equivalence label that a test on that host could have settled.
- obs-plan §8 PII Scrubbing & Compliance (Integration points, item 6, Unscanned uploads) requires that `mutants.out/` is never uploaded, that the Windows host mutation scratch path is never printed (documents carry only `scratch_bytes`), and that the run document names `target/run-archive/<n>/` only by the repo-relative `archived`. Any field the exclusion adds to the `run --mutants` document follows the same rule: repo-relative coordinates and counts, no absolute path. Whether the document's current fields already hold to this is research's question.
- obs-plan §6 Log Coverage (`detail` code catalog, Filesystem refusals) requires a strict-modes refusal to surface only as the closed code `strict-modes-failed` (on `process-exit` exit 21, on `hook-decision`, and on `parse-rejected{parser:"ledger-stamps"}`), at `warn`, with no path. A Windows-side refusal test that reads telemetry asserts these codes; the chunk adds no `event` or `detail` value. Whether the entry-point tests of scope §1 read telemetry or only the typed error is the plan's choice, and what the existing tests assert is research's question.
- obs-plan §3 Log file location requires diagnostics on Windows to sit under the home DACL (user, SYSTEM, Administrators), and obs-plan §10 SLO Invariants & Telemetry Budgets (Build / deploy failure conditions) lists a `diagnostics/` file that is not DACL-protected on Windows as a failure. The mutants at `fs.rs` `win::protect` / `win::dacl_of` and `strict.rs` `win::owner_and_dacl` sit in that mechanism; whether a test that runs on `windows-2025` already fails when the DACL is wrong is research's question.
- obs-plan §9 CI Integration (Pipeline integration, Integration tests row) requires every test that boots a viola process to keep its home under `target/e2e-home/`, so G2, G4 and the secret scan cover it in `test (windows-2025)`. It applies only if a new refusal test starts the binary; a unit test over a temp directory writes no role file and is outside it.

## Patterns to follow
- Mutation stays off the push path: obs-plan §9 CI Integration (Pipeline integration, Mutation row) places it at `agent-run run --mutants` on demand and in the dispatch-only, report-only Windows workflow, with no push or pull-request job.
- The dispatch is read by an agent from machine output: obs-plan §2 Telemetry Strategy (Agent-readable invariants) requires every verdict to be a harness assertion that sets an exit code, and obs-plan §9 CI Integration (CI-specific resource attributes) places CI identity in the run metadata fetched with `gh run view --json`.
- `viola-harness` prints exactly one JSON document per command on stdout and carries its own `[lints.clippy]` table without the print bans (obs-plan §3 Bootstrap phases, `obs-ci-gate-wire`); the exclusion logic in `crates/viola-e2e/src/harness/run/mutants/` keeps that one-document shape.
- Product members keep `[lints] workspace = true` with `print_stdout` / `print_stderr` / `dbg_macro` denied (obs-plan §3 Bootstrap phases, `obs-ci-gate-wire`). New Windows-gated test code in `viola-state` and `viola-pty` lives in such members; whether the bans reach their test targets is research's question.
- The new Windows-gated tests first run under the `test` job's fixed order, tests then G2 and G4 both `if: always()` (obs-plan §9 CI Integration, Step order and conditions).

## Anti-patterns to avoid
- NEVER fit a job inside its ceiling by a retry: obs-plan §11 Obs Anti-Patterns (SLO) bans retry-once policies for flaky assertions, in parallel with the tests' `retries = 0`.
- NEVER let the workflow's green rest on a human read of a log: obs-plan §11 Obs Anti-Patterns (CI) requires every CI verdict to set an exit code. An equivalence argument is a recorded exclusion input, not a substitute for a job's verdict.
- NEVER add an `event` value, rename a tests-bound field, or put a print macro in a product code path to make a refusal observable to a test (obs-plan §11 Obs Anti-Patterns, Logs); a new value needs a Decisions Log entry, which the chunk's boundaries rule out.

## Contract bindings
- obs ↔ tests: obs-plan §9 CI Integration (Pipeline integration, Mutation row) and obs-plan §10 SLO Invariants & Telemetry Budgets (Build / deploy failure conditions) both defer the mutation verdict to test-plan §10 Mutation gate. The `run --mutants` document's fields are tests-owned (test-plan §3, the `run` contract); obs binds them only through the path rule of obs-plan §8 PII Scrubbing & Compliance (Integration points, item 6).
- obs ↔ security: the strict-modes and DACL checks under mutation are security's control; obs holds their telemetry face (obs-plan §6 Log Coverage, `detail` code catalog, Filesystem refusals) and the Windows permission of the sink (obs-plan §3 Log file location).
- obs ↔ wrap: obs-plan §9 CI Integration states the Windows workflow's shape in two places (Platform: "uploads nothing"; the Mutation row: its invocation form and an obs-code score pinned to one run). If the chunk changes that shape or re-scores `src/panic_frames.rs`, those two sites are the expected obs amendment at wrap. Phase amends neither.

- In the dispatch's harness documents no obs-code mutant reads missed or timed out, and no obs-code mutant measurable on `windows-2025` sits in the excluded set (per obs-plan §9 CI Integration, Pipeline integration, Mutation row).
- Every field the exclusion adds to the `run --mutants` document carries repo-relative coordinates or counts only, with no absolute path and no scratch path (per obs-plan §8 PII Scrubbing & Compliance, Integration points, item 6).
- G2 and G4 read green in `test (windows-2025)` on the push that carries the new Windows-gated tests, and `schemas/diag-line.v1.json` gains no `event` or `detail` value (per obs-plan §9 CI Integration, Gate commands).
