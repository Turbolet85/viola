## Patterns to follow
- Outcome parity: security-plan §Authentication & Authorization (`~/.viola/` access control row) states the Windows outcomes match Unix (the per-role exits, the hook's silent exit 0, `instance-unreachable` for client verbs, `parse-rejected` with detail `strict-modes-failed` at the version gate). A Windows refusal test may assert the same typed outcome its Unix twin asserts.
- Per-object checks: security-plan §Authentication & Authorization (`~/.viola/` access control row) requires each directory and each trusted file to be checked separately on Windows. A refusal test sets the offending owner or ACE on one object at a time, so a mutant that erases one object's check cannot hide behind another's refusal.
- Refusal plus clean control: security-plan §Dependency Security (CI integration) proves each gate by a probe that shows the refusals and a clean control (`conpty-vendor.sh --probe`, `release-check.sh --probe`, G2's `--probe`). A strict-modes test pairs each refused case with an admitted control, so a mutant that refuses everything is also caught.
- Fixed, path-free messages: security-plan §Error Handling requires fixed `Display` messages with no path or payload. Any new exclusion field or refusal in the harness document follows it, and security-plan §Dependency Security (CI integration) keeps the document's paths repo-relative.
- Evidence from the job log: security-plan §Bootstrap phases (`secret-scanning-ci-gate`) records why the `mutants.out/` upload was removed (absolute argv paths in `outcomes.json`, test output in `log/`). The dispatch's per-job reading and the six retry-loop mutants' record are taken from the job log's outcome lines, not from a raw `mutants.out/` copy.

## Anti-patterns to avoid
- Reaching a refusal path by weakening the control: no `cfg`, feature, environment variable, config key or CLI flag that switches the strict-modes check off or makes it answer for a test, and no new test seam (security-plan §Security Anti-Patterns → Universal: the two `fake-agent` seams are the only carve-outs; another needs a Decisions Log entry, which this chunk's boundaries exclude).
- Reaching green by loosening the workflow: no mutable action ref, no `inputs:`, no upload, no `needs:` edge from `ci.yml`, no silenced zizmor finding, no mutation job added to `ci.yml` (security-plan §Security Anti-Patterns → Code Patterns for the SHA pin; security-plan §Dependency Security (CI integration) for the rest).
- Letting the exclusion hide a control: a mutant in a body the Windows build does compile is never left out of the count as "host-excluded" (security-plan §Security Anti-Patterns → Data Protection: the Windows owner + DACL check is never skipped). The exclusion applies only where the covering `cfg` predicate is false on the grading host.
