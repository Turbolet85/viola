## Constraints
- **The verdict has no "argued" arm.** test-plan §3 `run` (step 4, Verdict) requires zero missed, zero timeout and unviable not above caught, read from the run's own `outcomes.json`, for a `package` document to read `ok:true`. The plan records no disposition under which a mutant the host compiles and grades missed stops counting because an equivalence argument exists. Scope §6 wants every job's document `ok:true` with "the fifteen killed or argued": for the three mutants scope §1 reads as equivalent on a Windows build, the plan must name how they leave the missed count (a restated expression, or the exclusion of scope §3 extended to them) — an argument in `evidence/` alone leaves the job red. A technical fork, the operator's.
- **Host-unreachable mutants are recorded, never called equivalent or caught.** test-plan §10 (Mutation gate) requires a mutant a host cannot compile or reach (inside a `cfg` item or block, or behind a `cfg!` const) to be recorded by coordinate as not measured there and owed to the route entry that measures it; `missed == 0` then reads over the measurable set. That paragraph names this entry as the owner of the two `scratch.rs` mutants and, by its rule, of the six retry-loop mutants of scope §2. The word "equivalent" is barred for this class; it is not the same class as the three of the bullet above.
- **The exclusion is not in the plan's `run` contract.** test-plan §3 `run` (step 4, Package and Verdict; Output format) describes no step that leaves a mutant out before the counts are read, and no document field that carries one. §10's "reads over the measurable set" is stated as a recording rule. Moving it into the harness (scope §3) changes the `run` contract's Verdict and, if the document shows the left-out set, its Output format: an expected test-plan amendment at wrap, named in the plan. Whether the harness already holds any such filter is research's question.
- **Closed enums stay closed.** test-plan §3 Closed enums requires a Decisions Log entry for any new `mutants.verdict` or `run` `reason` value. The scope's boundary allows none that needs the founder, so the exclusion must be carried without a new enum value (a count or a list beside the existing `package` object is not an enum value; whether that reading holds is the operator's).
- **A mutant is killed by its own package's tests.** test-plan §3 `run` (step 4, Test scope) keeps cargo-mutants' per-package test scope: the `strict.rs` and `fs.rs` mutants must be killed by `viola-state`'s own tests, the `is_console` mutants by `viola-pty`'s own, the `viola-e2e` ones only under `--package viola-e2e`. A root integration test or a `viola-e2e` scenario kills none of the fifteen.
- **The workflow's shape is fixed by the plan.** test-plan §9 (Pipeline structure, Mutation row) requires `windows-mutants.yml` to be `workflow_dispatch` only with no inputs, one `mutants (<package>)` job per package on `windows-2025`, `fail-fast: false`, a 120 min ceiling, report-only, no cache and no upload; §9 (the workflow-permissions and tool-pin paragraph) requires `permissions: {}`, per-job `contents: read`, SHA-pinned actions, its two tool pins equal to the `test` job's line (asserted by `tests/contract_windows_mutation_scope.rs`), and no `concurrency:` block. Either fork of scope §4 (a raised ceiling, or a per-file split that makes more than one job per package) departs from that row's words and is an expected amendment; a split must not add a dispatch input.
- **Every wait a mutant can reach stays under the kill line.** test-plan §3 Bootstrap phases (`test-runner-install`, `[profile.mutants]`) requires a caught mutant to end at the nextest kill (10 s; 30 s for `viola-e2e`; 45 s for the `verify_window_` class), below cargo-mutants' 20 s auto-timeout floor for a root-size baseline, so that it never grades Timeout; under `terminate = "wait"` each caught mutant also waits for its running tests, which is the wall-time term scope §4 has to fit. Any new Windows-gated test must carry no unbounded wait. The measured growth of the `viola` job's baseline is not explained by the plan; its cause is research's question.

## Patterns to follow
- **Windows strict-modes cases through synthetic descriptors.** test-plan §4 (What unit tests cover, viola-state) requires the Windows strict-modes check to be driven by security descriptors built from SDDL strings and fed to the descriptor-check function, for the cases a hosted runner cannot provision (a foreign-owner SID, a volume without persistent ACLs); §8 (What to mock, Filesystem) allows a stub only there and requires a real tempfile home everywhere else. Whether `win::persistent_acls` and `win::check` already expose a point where such a descriptor or volume answer can be fed is research's question; `console::is_console` has no recorded test intent in §4 (viola-pty), so its killing test has no plan pattern to cite.
- **Unit placement and naming.** test-plan §4 (Conventions) requires inline `#[cfg(test)] mod tests`, `subject_condition_expected` names and labelled rstest `#[case]` tables; the same section's `viola-e2e` exception requires a labelled case table in one `#[test]` there (no dev-dependencies), which is the form for the exclusion logic's unit cases in `crates/viola-e2e/src/harness/run/mutants/`.
- **Compile out by `cfg`, never park.** test-plan §3 `run` (Output format, the `skipped` rule) counts a test compiled out by `#[cfg(windows)]` / `#[cfg(unix)]` as neither run nor skipped, and §10 (Zero-flakiness budget) bars `#[ignore]` as a parking place. A Windows-only killing test is `cfg`-gated; it shows as absent on the Linux dev host, not as skipped.
- **The inner loop and the Windows form.** test-plan §3 `run` (Test selection) gives the scoped form `run --mutants --file <path>` (verdict `scoped`) for a fix loop and `run --mutants --package <member>` with `--file` for the boundary form the workflow runs; §10 (Mutation gate) requires any mutation run on the Linux dev host to take `TMPDIR` on the operator's NOCOW scratch dir.
- **Reading a dispatch.** test-plan §9 (Pipeline structure, Mutation row) makes the job log the only output of a `windows-mutants.yml` job (the harness document plus the per-mutant outcome lines `--caught --unviable` print, §3 `run` step 4 Command); §9 (Test report format) reads job conclusions with `gh run view --json jobs`. A cancelled job prints no harness document, so its per-mutant reading comes from the outcome lines alone.

## Anti-patterns to avoid
- NEVER treat a Linux-only local run as proof for Windows: OS-branch code is verified only on its own runner (test-plan §11 Test Strategy). The Linux proof of the exclusion logic with stand-in spans proves the logic, not the Windows grade of any of the fifteen.
- NEVER trust the cargo-mutants exit code alone; count missed, timeout, unviable and caught in `outcomes.json` (test-plan §11 Quality). A job's green is read from the document's counts, and a run whose left-out set swallowed most mutants must still fail `unviable <= caught` over what remains.
- NEVER over-stub, monkey-patch production code at runtime, or assert on private internals in place of observable behaviour (test-plan §11 Mocking; §11 Unit). A killing test asserts the refusal a caller sees; a seam added only to reach a mutant goes through an existing trait or an injected value, and expected values are test literals, not the product's own constants.
