# security extract

## Relevance
relevant — the chunk adds a wrapper read of `budget.json` that decides a refusal, a `config.json` threshold reader, a wider `release --budget` result, and it re-orders the strict-modes check on `viola revive` (and, if the measurement confirms it, on `hook statusline`).

## Constraints
- **`revive` check order (item 7).** security-plan §Authentication & Authorization (`~/.viola/` access control, Strict-modes check) requires `viola_state::strict::check_instance` on both `revive` arms before any snapshot or log value is used, a refusal of `strict-modes-failed` (exit 1, one `unable:` / `hint:` pair, no child started, and on the start arm one `process-exit` line in `run-<name>.ndjson`), and names this entry as the owner of the log-before-check order. The same row's Unix read rule also refuses a home that grants any group or other bit, not only a writable one. The plan asks for both the check ahead of the log and a `process-exit` line for the refusal: where that line is written once the check runs first, and whether writing it narrows the home, is research's question. The plan marks the present order "read in source, not measured on `revive`"; whether the code at HEAD still has it is research's question.
- **Statusline arm refusal (item 8).** security-plan §Authentication & Authorization (`~/.viola/` access control, Strict-modes check) requires `hook statusline` to run `check_instance` on its canonicalised instance directory before its log opens, and a refusal to run no command, print nothing, leave `budget.json` unchanged and exit 0. security-plan §Error Handling (Internal logging) requires that a strict-modes failure in `hook` still ends in exit 0, no body and an empty stderr. Whether a refused invocation's own log opening lets the next invocation over the same home pass is not stated in the plan: it is research's measurement, and a confirmed result is a departure from this row.
- **The gate's read of `budget.json` (item 2).** security-plan §Input Validation (Own state files on read) lists `budget.json` among the own state files: a reader reads through the `MAX_FRAME` bound, never writes, and reads only after the home strict-modes check, with a closed list of dated exceptions none of which names a wrapper read of `budget.json`. security-plan §Input Validation (Hook stdin, Statusline payload) requires that `budget.json` is written only by the `hook statusline` arm, so the gate reads and never writes it. security-plan §Authentication & Authorization (`~/.viola/` access control) keeps the trusted-file list at `snapshot.json`, `ledger/stamps.json` and the pinned `viola`: `budget.json` is not on it, and the plan records no ratification of a wrapper refusing a driver on that file's content. Whether the start's check covers the later reads at `send` and `turn-ended`, and whether the file needs a check of its own, is unsettled in the plan: it goes to research and to the review card as the scope's item 10 names it, never as ratified.
- **Thresholds from `config.json` (item 1).** security-plan §Input Validation (Configuration values) requires a tolerant parse with unknown keys counted, thresholds into `Percent` (0 to 100), `v` checked and the read capped at `MAX_FRAME`. The plan states what a bad value becomes only for `diagnostics_level` and `claude_env_keep`; it states none for a threshold, so what an out-of-range or malformed threshold becomes is not covered here.
- **The `release` frame (item 4).** security-plan §Authentication & Authorization (Driver-originated `release`) requires `-32602` with `data: {"reason":"release-from-driver"}` and one `release-from-driver` line for a `release` whose `from` is a string, with or without `budget`, and describes the guard as an affordance, not enforcement: the budget lift inherits that limit. security-plan §Input Validation (Channel frames, `pause` / `release` params) requires `budget` to be absent or a bool, anything else (`null` included) `-32602` with `data: null`. security-plan §Authentication & Authorization (IPC client-side server verification, the seventh dated gap) covers CLI `viola release`'s frame after the liveness-only pre-check, its residual naming a squatter that answers a `release`; `release --budget` rides that gap and borrows no other.
- **The `budget-paused` refusal (item 3).** security-plan §Input Validation (Paste text, Where it runs / Wire outcome) requires the wrapper's `validate_paste_text` first in its refusal order and authoritative, with `control-character` then `empty-text` checked before the Conventions order, so `budget-paused` sits after both. security-plan §Error Handling (External responses; Error format, Channel) requires a refusal to travel as `result.refusal` with a code and detail only: no absolute path, no upstream text, no internal type name, and no reading value beyond the closed window word.
- **What stays the founder's (item 10).** security-plan §Security Anti-Patterns § Universal requires a non-`null` dialog decision only on a stamp where every row of `LedgerRow::ALL` passes, with `ledger/stamps.json` written by `viola verify` alone; the plan ties a stamp to dialog decisions only and states no stamp requirement for a `budget-paused` refusal. security-plan §Threat Model Summary (Attack surface, child process spawning and PATH resolution) fixes `viola verify`'s interactive children at four runs, each paste and dialog answer a dated founder ruling. A `rate_limits` row, a probe child, a re-stamp or a live start is therefore outside what the plan admits today; whether a new row would gate `cli_verified` for homes already stamped is a price the card states, not a decision this plan holds.

## Patterns to follow
- The statusline arm's order is the model for `revive`'s start arm: canonicalise the instance directory, the instance check, then the log (per security-plan §Input Validation, Statusline shell-out row, "The arm's order").
- The stamps read is the model for a state file a gate depends on: the check first, a capped read, and a refusal, an unreadable file or a malformed file each ending in one `parse-rejected` line and the conservative reading (per security-plan §Input Validation, Own state files on read, Integrity).
- The snapshot mirror (`budget_paused`, `budget_override_until`) is written by the instance's own wrapper alone, through `viola_state::fs::replace_private` at 0600 with the mode set before any byte (per security-plan §Authentication & Authorization, `~/.viola/` access control, Unix); any `.lock` sibling the gate creates is 0600 by an explicit mode, never the umask.
- Shared validators and bounded newtypes live in `viola-core` and the wrapper re-runs them; a client check is advisory (per security-plan §Input Validation, Boundary).
- The harness flag plants `<home>/statusline-source.json` from the test side: the product binary reads that file and writes neither source, and the planted command reaches the one ratified shell-out and no other (per security-plan §Input Validation, Statusline source row and Statusline shell-out row).

## Anti-patterns to avoid
- Never let a refusal block, refuse or delay the human: refusals go to automation only and hooks fail open (per security-plan §Security Anti-Patterns § Universal).
- Never let `config.json`, a `VIOLA_*` variable or a CLI flag switch off a control: the home strict-modes check is on that ban's list, so the `revive` fix takes no bypass, and no env var becomes a threshold channel (per security-plan §Security Anti-Patterns § Universal). The ban's list does not name the budget gate; the gate's bound is the `Percent` rule of §Input Validation (Configuration values).
- Never run `statusline_command` from a snapshot whose home or instance directory fails the strict-modes check, never add a second shell-out, and never let a process other than the instance's wrapper write `snapshot.json` (per security-plan §Security Anti-Patterns § Data Protection, § Code Patterns and § Universal); never add a channel method without a Decisions Log entry, and never read `from` as identity when deciding whose pause an override lifts (per security-plan §Security Anti-Patterns § Universal and § Authentication).

## Contract bindings
- **obs:** the gate's `run.budget_eval`, `budget-gate` and `send-refused` lines and the `revive` refusal lines sit under the NEVER-log floor of security-plan §Bootstrap phases (`logging-redaction-wire`): `budget.json` values are named there as admissible in `diagnostics/`, absolute paths never reach an external error, and security-plan §Input Validation (Session id as a child argv value) requires that no `revive` refusal line or hint holds the recorded directory, a pid or a logged id. obs owns the fields; whether a reading's value on a role log line fits the floor is the obs extract's binding to confirm.
- **tests:** the `revive` witness and any statusline-arm witness are `cfg(unix)` cases; the Windows case of `check_instance` is owed to "Home and code-bearing file integrity" (per security-plan §Authentication & Authorization, `~/.viola/` access control). The CI `secret-scan` reads the test homes the new Path 6 cases make (per security-plan §Bootstrap phases, `secret-scanning-ci-gate`), and a test-side removal under `target/e2e-home` takes only a dir the test side created (per security-plan §Security Anti-Patterns § Code Patterns).
- **architecture:** the trusted-file list and the instance-file order (architecture §Occupied Resources), the `release` params `{budget?, from?}` and the refusal order (architecture §Standard Contracts / §Conventions) are the other side of the constraints above; a ruling on `budget.json`'s trust lands in both masters.
- **route:** the home check at every entry point and the removal of the seven dated gaps stay with the Epoch 6 entries "Server verification before any frame" and "Home and code-bearing file integrity" (per security-plan §Authentication & Authorization, IPC client-side server verification); this chunk closes none of them.

## Acceptance criteria contributions
- A `viola revive` over a home with a group- or other-writable mode is refused `strict-modes-failed`: exit 1, one `unable:` / `hint:` pair holding no recorded directory, pid or logged id, no child started; the case fails on the log-before-check order (per security-plan §Authentication & Authorization, `~/.viola/` access control, Strict-modes check).
- A `viola hook statusline` over a home that fails the check runs no command, prints nothing, leaves `budget.json` byte-identical, writes no stderr and exits 0, on the first invocation and on the next one over the same untouched home if research confirms the one-invocation hypothesis (per security-plan §Authentication & Authorization, `~/.viola/` access control, Strict-modes check).
- A `release` frame carrying a string `from` and `budget: true` answers `-32602` with `data: {"reason":"release-from-driver"}`, logs one `release-from-driver` line and leaves the snapshot's `budget_paused` and `budget_override_until` unchanged; a `budget` that is not a bool answers `-32602` with `data: null` (per security-plan §Authentication & Authorization, Driver-originated `release`).
- The gate's `budget.json` read goes through the `MAX_FRAME` bound and writes no file: an over-cap, unparseable or absent `budget.json` yields no reading, and the file's bytes and mode are unchanged after a start, a refused `send` and a `turn-ended` (per security-plan §Input Validation, Own state files on read).
