## Relevance
relevant — the chunk builds the `run` half of a must-trace path (obs-plan §4 Scenario: Budget governor), adds the first producer of the `budget-paused` refusal line, and moves a strict-modes check across the log init on `viola revive` (obs-plan §3 OTel SDK init).

## Constraints
- obs-plan §4 Scenario: Budget governor requires an INTERNAL span `run.budget_eval` in `run` at each of the gate's three points, with the attributes `trigger` (closed: `start|send|turn-ended`), `paused` and `window`, and nothing else named. It is declared in the form obs-plan §4 Span naming convention fixes (static name, `skip_all`, an explicit field list, neither `err` nor `ret`). Whether any `run.budget_eval` span exists at HEAD is research's question (scope item 2 reads the gate as a constant).
- obs-plan §4 Scenario: Budget governor requires the refused automated send to write a `send-refused` line with `refusal:"budget-paused"`, `detail` `five-hour|seven-day`, `window`, `used_percentage`, `resets_at`, `paused:true`, and the client's `process-exit` with `exit_code:11`. obs-plan §3 Log format JSON schema fixes its `corr` as the target's `events.ndjson` end offset at the refusal (a join key, never returned), with no `send-issued`; obs-plan §4 Scenario: Confirmed `send` (CL-1) requires `conn` and `rpc_id` on every wrapper `send-*` line. The Budget governor scenario's field list names neither `side` nor `wheel`, while obs-plan §5 Per-surface / per-path metrics groups `send-refused` by `side`: whether `schemas/diag-line.v1.json` already admits the four budget fields on `send-refused`, their types (a `resets_at` that is `unknown` included), and whether `side:"wrapper"` is required on this line is research's question.
- obs-plan §6 Log levels mapping puts a refusal at `info` (a normal product outcome), a `process-exit` with exit code 1 at `error`, and a `hook-decision` carrying a fail-open `detail` at `warn`. The budget refusal, the revive refusal and the statusline arm's refusal each take the level that table gives.
- obs-plan §8 Default-deny posture requires that a field is logged only if obs-plan §6 Additive field catalog names it, with gate G4 failing the build otherwise; obs-plan §3 Log format JSON schema requires a Decisions Log entry for any new `event` value. So the lift by `release --budget` and a gate change get no process-log event of their own: their carriers are `channel-request` / `channel-response{method:"release"}` (obs-plan §4 Scenario: Human takes the wheel) and the product `budget-gate` record, which obs-plan §4 Scenario: `viola run` start sequence says is verified from `events.ndjson` and not duplicated into process logs. `override_until` is in no process-log field list of the catalog.
- obs-plan §6 `detail` code catalog closes `parse-rejected.parser` to ten members, none for `budget.json`, and obs-plan §4 Scenario: Budget governor names no span for a read of that file (only `state.budget_write`, on the hook side). The plan therefore gives the wrapper's new `budget.json` read no carrier for an unreadable, unparseable or newer file: it either reads as no reading with no line, or the chunk needs a Decisions Log entry and a schema change. Which one is a P3/P4 matter; obs-plan §1 Obs Scope Summary (the persistent-stores entity) only says the file's percentages and `resets_at` may be logged as structured fields.
- obs-plan §3 OTel SDK init (steps 5 and 6) requires one `config.json` parse per process and, after `process-start`, one `parse-rejected{parser:"config-json", detail, count}` when the parse failed or skipped keys; obs-plan §6 `detail` code catalog gives that parser `malformed`, `unreadable` and `unknown-keys` only. An out-of-range or malformed threshold has no detail of its own there: which detail it takes, or none, is undecided by the plan and goes to P3 with scope item 1. Whether the threshold reader can reuse the landed parse is research's question. obs-plan §8 PII Scrubbing (data classification table) allows threshold values as structured fields.
- obs-plan §3 OTel SDK init holds two statements the revive reorder sets against each other. Step 4 requires the home's strict-modes check first and diagnostics init after, nothing under the home created or opened before the check passes, and no diagnostics line for a refused home. The same key's per-role `run` anchor, with obs-plan §6 `detail` code catalog, states that `viola revive`'s start arm runs its log init before its preflight so that its `strict-modes-failed` refusal is one `process-exit{subject:"self", exit_code:1, detail}` in `run-<name>.ndjson`, and obs-plan §10 SLO Invariants & Telemetry Budgets says that arm's role file is not exempt. The plan must settle where the reordered refusal is recorded; either answer rewrites that anchor at the wrap. A check ahead of the role-file open also puts `check_instance` inside the pre-init window whose contents obs-plan §7 Error Capture & Reporting (Panic hooks) lists as clap parsing and home resolution.
- obs-plan §3 OTel SDK init (the `hook` anchor) records, as read in source and not measured, that `viola hook statusline` opens its role file after a refused check and writes `hook-invoked` and `hook-decision{detail:"strict-modes-failed"}`, and that this opening narrows the refused home. obs-plan §4 Scenario: Budget governor lists that `hook-decision` detail as a required line. If scope item 8's measurement confirms the hypothesis and the fix stops the opening, that required line loses its carrier and the scenario, the anchor and obs-plan §6 `detail` code catalog (the arm's four fail-open codes) need an amendment; if the line is kept, the fix must show how it is written without narrowing the home.

## Patterns to follow
- Every new line goes through `obs_event!` with explicit typed fields under an `#[instrument(skip_all, name = "...", fields(...))]` span, per obs-plan §8 PII Scrubbing (Integration points, item 1).
- The `budget-paused` refusal follows the wrapper refusal shape obs-plan §4 Scenario: Human takes the wheel gives for `human-typing` (one wrapper `send-refused`, `corr` the end offset, the client's `process-exit` with its exit code), and the `channel-response` for both the refused `send` and `release --budget` comes from the `Drop` guard in `channel.dispatch`, per obs-plan §4 Scenario: Confirmed `send` (CL-1), Cleanup.
- `run.budget_eval` takes the model of `run.wheel_transition`: a point-in-time span with a static name and closed-enum attributes, per obs-plan §4 Scenario: Human takes the wheel.
- The order the plan records for the statusline arm (instance check ahead of the log init) is the precedent for `revive`, per obs-plan §3 OTel SDK init (the `hook` anchor); how that arm writes its refusal line is research's read.
- Every viola home the chunk's tests and the harness flag `boot --statusline-echo` make sits under `target/e2e-home/`, so G2, G4 and the secret scan read its lines, per obs-plan §9 CI Integration (Pipeline integration, Integration tests row).

## Anti-patterns to avoid
- Never log a field outside the catalog or add an `event` value without a Decisions Log entry, and never let `config.json` widen the allow-list, per obs-plan §11 Obs Anti-Patterns § PII Scrubbing and § Logs. A budget field on any line but `send-refused`, an `override_until` field, or a new `parser` member falls under it.
- Never put a path or a pid inside a `detail` code, and never log `statusline_command` in a home-level file, per obs-plan §11 Obs Anti-Patterns § PII Scrubbing. The refused home or instance directory is named in no line.
- Never rely on span context to carry `corr`, `conn` or `instance` across threads, and never record `corr` with `?corr` / `%corr`, per obs-plan §11 Obs Anti-Patterns § Spans / Traces and § Logs. The gate's `turn-ended` evaluation and its `send` evaluation may run on different threads: each passes its values explicitly.

## Contract bindings
- obs ↔ tests harness: obs-plan §3 Log format JSON schema is test-plan §3 Log format reproduced, obs aligning to tests. The `budget-paused` `corr` rule, the `agent-run logs --kind` read of `budget-gate` and Path 6's `send-refused` signals bind there; the schema `schemas/diag-line.v1.json` is obs-owned and the G4 check body tests-owned (obs-plan §9 CI Integration, Gate commands).
- obs ↔ tests harness: `budget.read_at` is a harness-snapshot gauge read through `agent-run status`, per obs-plan §5 Metric Coverage (Metric instrument types). Whether `status` carries it at HEAD is research's question.
- obs ↔ security: the order of strict-modes and diagnostics init (obs-plan §3 OTel SDK init, step 4) is security-plan's home access control seen from the log side; the revive and statusline items move both plans together. The loggable class of budget percentages, `resets_at` and thresholds comes from security's Data Classifications through obs-plan §8 PII Scrubbing.
- obs ↔ architecture: refusal details are the arch `RefusalReason` details verbatim (`five-hour`, `seven-day`), per obs-plan §6 `detail` code catalog; `budget-gate` is the arch Event line, not a process-log event.

## Acceptance criteria contributions
- An automated `send` refused by the gate writes exactly one wrapper `send-refused` with `refusal:"budget-paused"`, `detail` `five-hour` or `seven-day`, `window`, `used_percentage`, `resets_at`, `paused:true`, `corr` the end offset, `conn` and `rpc_id`, no `send-issued`, and the client's `process-exit` carries `exit_code:11` (per obs-plan §4 Scenario: Budget governor).
- `run.budget_eval` is opened once per evaluation at start, on `send` and at `turn-ended`, with `trigger`, `paused` and `window` and no other attribute, and gate G1 reads clean over the tree (per obs-plan §4 Scenario: Budget governor).
- Every home-level line the chunk's tests produce passes G4 against `schemas/diag-line.v1.json` with no field outside the catalog, and G2 counts zero panic lines over the same homes (per obs-plan §9 CI Integration, Gate commands).
- A `viola revive` over a group-writable home records its refusal the way the plan settles and the witness asserts it: either one `process-exit{subject:"self", exit_code:1, detail:"strict-modes-failed"}` at `ERROR` in `run-<name>.ndjson` with no `process-start{subject:"claude-child"}`, or no diagnostics line at all; in both cases nothing under the refused home was created or opened before the check decided (per obs-plan §3 OTel SDK init).
