# arch extract

## Relevance
relevant — the chunk touches the Hook Contract, the hook tier deadlines, the env-var exception list, an occupied target dir (`target/perf/`), the CI job topology and the ndjson line discipline.

## Constraints
- **Fail open, even on panic.** `viola hook` must exit 0 on every path, including panics caught at the edge. Exit 2 is forbidden, and nothing may be written to stderr. An internal failure yields exit 0 with no body (per architecture §Conventions "`viola hook` exit codes"; §Established Decisions [Hook Contract]; §Cross-cutting Patterns "Fail open toward the human"). The panic seam's case has to prove this on the built binary. Whether the edge catch already covers a panic raised inside the seam's call site is a question for research.
- **The deadlines stay provisional and hook-local.** `SPINE_DEADLINE` = 750 ms is the crate-private connect deadline. It covers the spine tier, and SessionEnd uses it within viola's ~1 s budget. The 1.5 s SessionEnd budget is never raised. Naming it as "the product constant the perf gate reads" remains an open item owned by the "Readiness gate and timing constants" chunk (per architecture §Established Decisions [Hook Transport]). So this chunk measures against the deadline and must not promote or retune it. The async tier (Notification, PostToolUse, PostToolUseFailure) prints nothing (same §).
- **The env-var exception list is closed.** Every variable the product reads is `VIOLA_*`. The architecture text names `FAKE_AGENT_PUMP_DELAY_MS` as "the one ratified exception" and "the one other variable any `viola` build reads" (per architecture §Conventions "Environment variables"; §Established Decisions [Naming]; §Occupied Resources "Environment variables → Test seam"; §Cross-cutting Patterns "Config management"). `FAKE_AGENT_HOOK_PANIC` must follow the same shape: read only under `cfg(feature = "fake-agent")`, absent from release builds, configuring nothing, disabling no control and widening no redaction. Those four "one exception" statements are wrap-cascade amendments. They are not edits for this chunk to make.
- **`target/perf/` is already occupied, with a fixed build line.** The line is `cargo build --release --workspace --features fake-agent --target-dir target/perf`, with binaries under `target/perf/release`. Its hyperfine exports are recorded as "the separate `perf/*.json`" (obs-plan §9) (per architecture §Occupied Resources "Repository"). The scope instead writes `perf-<hook>.json` into the run's artifacts, and `gate.rs` reads `perf-*.json`. Research has to settle which name and location is right. Any new path gets recorded at wrap.
- **Crash-safe lines and output channels.** Each line must be one complete JSON object plus `\n` in a single `write`, and readers must tolerate a torn last line (per architecture §Conventions "ndjson line discipline"; §Cross-cutting Patterns "Crash-safe disk writes"). The panic payload and backtrace are content-bearing, so they may appear only in the instance's owner-only `diagnostics/detail-hook.ndjson` (0600, format owned by obs and fixed by `schemas/diag-detail.v1.json`). They never go to the codes-only `hook-<name>.ndjson`, stdout or stderr (per architecture §Occupied Resources "Filesystem"; §Cross-cutting Patterns "Diagnostic output channels"; §Established Decisions [Error Handling]). The scope needs a single-write line over 4 KiB to stay whole under concurrent appends on all three OSes. Whether that holds is a question to measure, not something the plan asserts.
- **Workspace placement and Tokio containment.** The seam belongs to the root `viola` bin (the hook subcommand under `src/cmd/`). The perf arm and `gate` belong to the test-only `viola-e2e` (`viola-harness`), and no product crate depends on it. The `hook` path stays on std threads with no runtime (per architecture §Established Decisions [Module Boundaries], [Concurrency / Backend Framework]; §Cross-cutting Patterns "Tokio containment"; §Occupied Resources "Workspace crates").
- **CI discipline.** Every workflow sets `permissions: {}` at the top and `contents: read` per job. Every `uses:` is pinned by full commit SHA, and every gate step is fail-closed `shell: bash`. A pinned tool is installed either through the pinned `taiki-e/install-action` line or through `cargo install --locked <tool>@<ver>` in the job that runs it. The count of wired jobs (8 jobs, 15 check-runs) and the job list change if perf becomes its own per-OS job (per architecture §Infrastructure Patterns "CI/CD approach"). The perf run must cover all three OSes (per architecture §Established Decisions [CI/CD]).

## Patterns to follow
- **The `FAKE_AGENT_PUMP_DELAY_MS` precedent:** a `#[cfg(feature = "fake-agent")]` fn at the one read site (`hold_pump_start` in `src/cmd/run.rs`). It is a test seam, not a configuration channel (per architecture §Occupied Resources "Environment variables → Test seam"). The sync crates' code-free `fake-agent = []` features let package-scoped builds resolve (per architecture §Occupied Resources "Workspace crates").
- **Pinned tool install with a probe.** ripgrep and Node use a script that installs the official asset, checks its sha256 and supports `--probe` (`install-ripgrep.sh`, `install-node.sh`). The alternatives are the pinned taiki-e line or `cargo install --locked` in the job that runs the tool (per architecture §Infrastructure Patterns "CI/CD approach", "Setup steps"). The hyperfine 1.20.0 pin fits one of these shapes.
- **A separate `CARGO_TARGET_DIR` per tool that runs cargo** (`target/harness/`, `target/mutants/`, `target/release-check/`, `target/perf/`). The reason: a running exe cannot be relinked on Windows (per architecture §Occupied Resources "Repository").
- **The gate verdict step:** an `if: always()` `Gate verdict` step running `gate --require <suites>` after the suite step (the `test` job's `gate --require coverage,doctest,playwright`; `msrv`; `fuzz-replay`) (per architecture §Infrastructure Patterns "CI/CD approach", "Jobs wired today").
- **Direct child spawns from the harness.** The harness runs `npm ci` and `node …/cli.js` directly, with no shell and no npx (per architecture §Stack and Technologies, "Browser e2e" row; §Cross-cutting Patterns "Cross-platform discipline"). By default hyperfine runs its subject through a shell, and that would add shell startup to every `viola hook` sample. Whether to use `--shell=none` / `-N` is a question for research.

## Anti-patterns to avoid
- Promoting, renaming or retuning `SPINE_DEADLINE`, or raising the SessionEnd budget, to make a perf row pass. A breach is a finding to surface, not a retune (per architecture §Established Decisions [Hook Transport]).
- Letting the panic seam, or anything built with `fake-agent`, reach a release artifact. `scripts/release-check.sh` fails any `compiler-artifact` whose `features` include `fake-agent` (per architecture §Infrastructure Patterns target job 6). Also banned: a seam that disables a control or acts as a config channel (per architecture §Cross-cutting Patterns "Config management").
- Any stderr write, any exit other than 0, or any stdout body from `viola hook` on the panic path (per architecture §Conventions "`viola hook` exit codes"; §Cross-cutting Patterns "Diagnostic output channels").

## Contract bindings
- **arch ↔ tests:** `run --perf` and the `target/perf/` build line come from test-plan §10. The job-shape fork is test-plan §9 (its own per-OS job) against obs-plan §10 (a step inside `test`). The architecture job list in §Infrastructure Patterns "CI/CD approach" records whichever shape lands.
- **arch ↔ obs:** the hyperfine exports are `perf/*.json` per obs-plan §9, against the scope's `perf-<hook>.json`. The `detail-hook.ndjson` line format is obs-owned (`schemas/diag-detail.v1.json`, pinned by `tests/contract_diag_schema.rs`), and D-28's concurrent-append half is obs-plan's (per architecture §Occupied Resources "Repository" / "Filesystem").
- **arch ↔ security:** the new seam needs a security-plan Decisions Log entry. The architecture "one ratified exception" statements (§Conventions, §Established Decisions [Naming], §Occupied Resources, §Cross-cutting Patterns "Config management") widen in the same wrap cascade. `release-check.sh`'s test-only-feature refusal is the release-side control.
- **arch ↔ WSL pre-push:** `scripts/wsl-provision.sh` replays ci.yml's `test`-job `cargo install --locked` pins (per architecture §Stack and Technologies CI/CD row; §Infrastructure Patterns pre-push). If hyperfine is added to that line, the distro gets re-provisioned, and that triggers the travelling CARRY 3.

## Acceptance criteria contributions
- With `FAKE_AGENT_HOOK_PANIC` set, a `fake-agent` build of `viola hook <event>` panics inside the seam and still exits 0 with zero stderr bytes and zero stdout bytes. The seam's read site is compiled only under `cfg(feature = "fake-agent")` (per architecture §Conventions "`viola hook` exit codes"; §Occupied Resources "Environment variables → Test seam").
- `scripts/release-check.sh` (and its `--probe`, reading `5/5 refused, control clean`) still passes on the chunk's tree, and the release artifact carries `viola` only, with no `fake-agent` feature (per architecture §Infrastructure Patterns target job 6).
- Under concurrent `viola hook` processes, every `detail-hook.ndjson` line, including the over-4 KiB panic line, parses as one whole JSON object terminated by `\n`, and no payload or backtrace text appears in `hook-<name>.ndjson` (per architecture §Conventions "ndjson line discipline"; §Cross-cutting Patterns "Crash-safe disk writes", "Diagnostic output channels").
- The perf build uses exactly the `target/perf/` line. The chunk adds no env var other than `FAKE_AGENT_HOOK_PANIC`, and every new CI step keeps SHA-pinned `uses:`, `permissions: {}` / `contents: read` and fail-closed `shell: bash` on all three OSes (per architecture §Occupied Resources "Repository", "Environment variables"; §Infrastructure Patterns "CI/CD approach").
