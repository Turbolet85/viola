# obs extract

## Relevance
relevant — the chunk builds the obs-plan §10 hook perf budgets, the §9 perf artifact and job placement, the §7 hook panic path on the real binary, and the >4 KiB detail-line half of the §3 concurrent-append check (D-28).

## Constraints
- obs-plan §10 (Performance budgets) requires hook timing with hyperfine 1.20.0 run as `--warmup 3 --runs 30 --export-json`. `session-end` is gated at `max < 1.0 s`. The spine hooks (`session-start`, `user-prompt-submit`, `stop`) and `pre-tool-use` on an unverified CLI are gated at `max <` the spine deadline, whose value tests owns (provisionally 1.0 s, above the hook's own provisional 750 ms). Obs requires only that each gate sets the exit code. §10 says this chunk brings those rows, the `--perf` arm and the per-OS perf job into existence. p50/p95 are report-only and p99 is not computed.
- obs-plan §10 (row "Obs overhead on `hook`") and Decisions Log D-30 require every hyperfine hook command to run with `VIOLA_NAME` set and a home under `target/e2e-home/`, on the tests-owned instance fixture. Without it the timed command is the D-16 no-op (no log open, no channel call) and the gate passes without testing anything. The perf job must run G2 over that home, because a hook panic exits 0 and hyperfine cannot see it.
- obs-plan §9 (Step order item 1 and the telemetry-artifact table) requires the perf gates to run in the same per-OS job as the integration/E2E tests, before G2 and G4 (both `if: always()`) and before the secret scan. Its reason: a separate job would either upload no diagnostics or collide on `diag-<os>`. hyperfine output goes up as `perf-${{ matrix.os }}` with `if: always()` (timings and command lines only), so a failing assertion still leaves its sample. This is obs's side of CARRY 1's job-shape fork. test-plan §9 takes the other side.
- obs-plan §7 (Panic hooks) requires the following for the forced panic:
  - The first statement of `main` installs a hook that never calls the default hook and never writes stderr.
  - The hook writes one home-level line `event:"panic"` (`level:"ERROR"`, `target:"viola::panic"`, `panic_location`, `thread`, no `corr`) with one `write_all` on the pre-opened handle, not through the tracing subscriber.
  - When an instance resolves, it also writes one `detail-hook.ndjson` line carrying `panic_payload` and a `backtrace` frame array from `Backtrace::force_capture()`, not gated by `RUST_BACKTRACE`.
  - The main-thread `catch_unwind` finds the role from argv, so `viola --home <dir> hook <event>` still counts as `hook`.
  - `hook` then exits 0 with empty stdout. `panic = "unwind"` is kept (G3).
- obs-plan §3 (Logging stack, the detail-files bullet; D-28) requires the concurrent-append check to include a detail line larger than 4 KiB. It must prove whole lines under one `write_all` per line on an append-mode handle, with torn-line tolerance, and every line of each shared file must parse, on windows-2025, macos-latest and ubuntu-latest. §3 names the hook panic payload + backtrace as the only hook detail line that large and assigns this half to this chunk.
- obs-plan §10 (zero unlogged panics, including its counting rule) and §9 (G2) require exactly one home-level `event:"panic"` line per panic after init step 4, and zero such lines across all home-level role files under `target/e2e-home/` (detail files excluded). §9 (Integration tests row) also requires every integration-test home to be under `target/e2e-home/`, because a hook panic exits 0 and a home outside that root would hide it. The forced-panic case writes its panic line on purpose, so under the plan as written it would turn G2 red. The obs plan has no exemption for a deliberate panic. P3/P4 must settle how the case's home and G2's scope fit together, and that may need an obs-plan amendment through the wrap cascade. Widening or narrowing G2 on the side is not an option.
- obs-plan §3 (Logging stack, Sink) and §8 (Detail-file scope; D-30) require the panic payload and backtrace to stay in `instances/<name>/diagnostics/detail-hook.ndjson` only. A home-level line carrying `panic_payload` or `backtrace` fails `diag-line.v1.json`. Detail lines are checked by G4 against the obs-owned `schemas/diag-detail.v1.json`, and the secret scan covers them.

## Patterns to follow
- obs-plan §5 canonical quantile snippet: `awk 1 … | jq -R -n` with `fromjson?` over `hook-decision.duration_ms`, filtered per `hook_event`. It gives the report-only p50/p95/max for the derived metric `viola.hook.duration_ms`. The gate itself reads hyperfine's `max`.
- obs-plan §9 G2 command form: a non-empty-scope check first, then `find … ! -name 'detail-*' -exec awk 1 {} + | jq -R -n -e '…length==0'`, which skips torn lines and sets the exit code. Reuse this shape for any panic count this chunk adds.
- obs-plan §3 torn-line tolerance: the harness emits `{"torn":true}` for an unparseable line and G2/G4 skip and count it. The concurrent-append check itself treats a torn line as failure.
- obs-plan §3 (Logging stack), the head chunk's 8-process concurrent `viola hook` check (16 whole lines in `hook-<name>.ndjson`, 8 in `detail-hook.ndjson`): extend it with the >4 KiB panic detail line rather than building a parallel check. Whether the existing check can take the seam-driven processes directly is for research to answer.
- obs-plan §7 panic-hook write path: one `write_all` on the pre-opened `Arc<File>` in a `OnceLock`, with the detail line formatted by the root-bin `viola::obs` writer using the same key set (§3 Sink). Whether the code already writes the detail companion line with `force_capture()` is for research to answer.

## Anti-patterns to avoid
- obs-plan §11 SLO / CI: NEVER define a budget without an assertion that sets the exit code (hyperfine `max` through `jq -e` or the harness gate). NEVER add retry-once for panics or flaky telemetry assertions. NEVER use human-reviewed log analysis as a verdict.
- obs-plan §11 Metrics: NEVER report hook latency without the gate statistic, since hyperfine `max` is the enforced number. NEVER create in-process metric instruments to time hooks.
- obs-plan §11 Logs / Error Reporting: NEVER write multi-line stack traces, since the backtrace is a one-line JSON array in the detail file only. NEVER call or chain to the default panic hook. NEVER emit anything to stderr or stdout on the hook panic path.

## Contract bindings
- obs §10 ↔ test-plan §10: the spine deadline value and the rows the gate requires are tests-owned. Obs requires only an exit-code-setting `max` assertion per timed hook. Artifact naming needs reconciling: obs §9/§10 name `perf/hook-<event>.json` checked by `jq -e '.results[0].max < …'`, while the scope names harness-written `perf-<hook>.json` checked by `gate.rs` against `SPINE_DEADLINE_S`. Research should settle which form satisfies §10, or whether both are needed.
- obs §9 Step order ↔ test-plan §9: the perf-job shape fork (CARRY 1). Obs requires the gates inside the per-OS test job so that G2, the secret scan and `diag-<os>` cover the perf home.
- obs §10 row "Obs overhead on `hook`" ↔ the tests-owned perf-job instance fixture (`VIOLA_NAME` plus a home under `target/e2e-home/`).
- obs §10 / §9 G2 ↔ test-plan §6 Security sweep forced-panic case: the deliberate panic line against the zero-panic gate (see Constraints).
- obs §3 concurrent-append requirement ↔ the tests-owned concurrent-append check body. Obs owns `schemas/diag-detail.v1.json`, and tests owns the G4 check body and validator.
- obs §8 ↔ security-plan: the seam's Decisions Log entry and seam rule are security-owned. Obs needs only that the seam's panic path produce the §7 lines and nothing on stdout or stderr.

## Acceptance criteria contributions
- Each gated hook has a per-OS hyperfine 1.20.0 `--export-json` sample (`--warmup 3 --runs 30`) whose `max` assertion sets the job's exit code. A breach fails the run, and the samples upload as `perf-<os>` under `if: always()` (per obs-plan §10 Performance budgets, §9 telemetry-artifact table).
- Every timed hook command runs with `VIOLA_NAME` set and a home under `target/e2e-home/`. That home's `hook-<name>.ndjson` holds `hook-decision` lines from the timed runs, not an empty D-16 no-op, and G2 and G4 run over it with `if: always()` (per obs-plan §10 row "Obs overhead on `hook`", §9 Step order).
- The forced-panic case on the built binary exits 0 with empty stdout and stderr. It writes exactly one home-level `event:"panic"` line in `hook-<name>.ndjson`, with no `panic_payload` or `backtrace`, conforming to `diag-line.v1.json`. It writes one `detail-hook.ndjson` line with `panic_payload` and a one-line `backtrace` array, conforming to `diag-detail.v1.json`. G2 stays green on the resolved home or scope (per obs-plan §7 Panic hooks, §10 zero unlogged panics).
- Concurrent forced-panic `viola hook` processes leave `detail-hook.ndjson` lines over 4 KiB. Every line parses whole and the line count matches the process count, on all 3 CI OSes (per obs-plan §3 Logging stack, D-28).
