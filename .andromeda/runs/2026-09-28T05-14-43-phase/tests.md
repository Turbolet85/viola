## Constraints
- test-plan §10 Performance budgets (Perf run rules) requires `run --perf` to: build its own non-instrumented `cargo build --release --workspace --features fake-agent --target-dir target/perf` (never the debug `boot` build or an llvm-cov build, never with `LLVM_PROFILE_FILE` set); boot two sessions through `viola_e2e::harness::boot` with the binary dir at `target/perf/release` — `perf-stamped-<pid>` (spine + SessionEnd rows) and `perf-unstamped-<pid>` (`--unstamped`, for the `pre-tool-use` row), both homes under `target/e2e-home/`; pass hyperfine the session's `VIOLA_NAME` / `VIOLA_DIR` and a fixture payload via `--input` so every timed hook takes the real logging and channel path, never the no-instance no-op; call hyperfine exactly as `-N --warmup 3 --runs 30 --export-json target/agent-run/artifacts/perf-<hook>.json`; after the last hyperfine call and before `cleanup`, treat any `event:"panic"` line in either home's role files (`diagnostics/*.ndjson` minus `detail-*`) as a `perf` breach; then require `cleanup` `ok:true` for both sessions; a failed boot exits 1 with the boot `reason`, never a missing or skipped row.
- test-plan §10 Performance budgets (table) fixes the timed rows: `session-end`, the spine `session-start` / `user-prompt-submit` / `stop`, and `pre-tool-use` on an unverified CLI (`hook.dialog` → `null` at once). Each is gated on `max < 1.0 s` (provisional until arch request (3) names the constant), with mean / median / stddev reported for trend only. The scope's "[inferred] async tier" row is not in this table. Whether it is timed and required is P3/P4's call, and adding a gated row the table does not list is a test-plan amendment.
- test-plan §10 Performance budgets (Verdict, Spine deadline) requires the verdict to come from one evaluation of the exported JSON by `viola-harness gate`: no rerun, no outlier trimming, no second attempt. A breach is fixed in the product or escalated through a Decisions Log entry. The gate stays at the provisional `1.0 s` literal, and the hook's own `SPINE_DEADLINE` (750 ms) is not retuned here (naming the constant stays with "Readiness gate and timing constants").
- test-plan §3 `run` / `gate` requires `--perf` to add suite `"perf"` to the `run` output document and to `run-summary.json`, the input `gate --require perf` checks for presence, `failed == 0` and `skipped == 0`. It also requires `gate` to breach on a required `perf-*.json` that is missing, unreadable, or whose `.results[0].max` is at or over the §10 gate (detail `perf-*.json` / `<file> max X >= 1`; a missing artifact is a breach, never a pass). test-plan §3 Bootstrap `ci-tool-install` requires `run --perf` to exit 1 with `reason:"tool-missing"` naming hyperfine when it is not on PATH. Whether the existing `gate.rs` reader already matches this breach shape is research's question.
- test-plan §9 CI Integration (Perf row, Coverage-report row, tool paragraph) specifies a **per-OS Perf job** whose last step is `viola-harness gate --require perf`. Hyperfine 1.20.0 is installed by `cargo install --locked hyperfine@1.20.0` in the job that invokes it, not through taiki-e. The job needs `permissions: {}` at the top level and `contents: read` per job, SHA-pinned `uses:`, and rust-cache as its only cache. CI never installs or pins `jq` for this verdict. On the job-shape fork (entry CARRY 1), test-plan §9 takes the own-job side, and moving the perf run into the `test` job is a test-plan amendment. §9 Build failure conditions and §10 list a hyperfine `max` breach as a red build.
- test-plan §6 Non-path suites (Security sweep) and §1 (security-vector-coverage, hook stdin) require the forced-panic case to run on the real built binary through `FAKE_AGENT_HOOK_PANIC`, compiled only under feature `fake-agent`: exit 0, empty stderr, no body. The case joins root `hook_fail_open.rs` (assert_cmd), which the §3 layer filtersets run in the integration layer. test-plan §10 Performance budgets (Status) and "the same deadlines are also asserted at unit speed" require every fail-open case to keep the `Instant` bound `< 1.0 s` (`hook_fails_open_silently_within_the_spine_bound`).
- test-plan §5 Integration (Module ↔ DB, Concurrent-append check) requires separate processes appending at once to `detail-hook.ndjson`, with at least one line larger than 4 KiB, on all 3 CI OSes. Every line of every file must parse as one JSON object, and a torn or interleaved line fails the test. test-plan §5 (CLI and env) and §6 Security sweep require `tests/cli_controls_not_disableable.rs` to be an rstest `#[case]` table over every `VIOLA_*` env var, global flag and `config.json` key, written as literals (§11 Unit), with the seam's name as a row. Whether the file exists yet, and whether this chunk builds the full Vector 6 table or only the seam's row, is research's question (scope item 5).

## Patterns to follow
- The root fail-open matrix pattern: assert_cmd cases in `tests/hook_fail_open.rs`, each asserting exit 0 + empty stderr + empty stdout + the `Instant` bound (test-plan §6 Non-path suites; §10 Performance budgets Status). The forced-panic case is one more case in that matrix. Each case sets its env through `Command::env`.
- The landed concurrent-hook check `hook_processes_append_whole_lines_side_by_side` (8 processes, 16 lines in `hook-<name>.ndjson`, 8 in `detail-hook.ndjson`, every line parsed with serde_json) is the base the >4 KiB panic detail line extends (test-plan §5 Module ↔ DB).
- Harness arm shape: one JSON document + typed exit per command, a `suites[]` entry per suite, artifacts written under `target/agent-run/artifacts/`, and a tool-presence probe before running (test-plan §3 `run`, §3 Bootstrap `ci-tool-install`). The `--fuzz-replay` arm is the nearest sibling: tool probe, `tool-missing`, and per-target entries.
- Per-job gate tail: every test-running CI job ends in `viola-harness gate --require <exactly the suites it ran>` (test-plan §3 `gate`; §9 Coverage-report row). The MSRV and fuzz-replay jobs are the single-suite precedents (`nextest-unit`, `fuzz-replay`).
- Perf sessions reuse the harness `boot` / `cleanup` library code and homes under `target/e2e-home/` (test-plan §3 5-command implementation boot step 2; §10 Perf session), so obs-plan §9's G2 / secret-scan / diag upload paths see them.

## Anti-patterns to avoid
- Gating a hook deadline on hyperfine `mean` (or any percentile), or retrying, trimming or re-running a breaching perf row (test-plan §11 Quality; §10 Verdict; §11 Universal "NEVER add retry-once policies").
- Setting `FAKE_AGENT_HOOK_PANIC` with `std::env::set_var` in a test, or calling `.env_clear()` on the spawned `viola hook` without re-adding `LLVM_PROFILE_FILE` (test-plan §11 Integration). Use `Command::env` per child.
- Stubbing `viola hook`, or letting a timed perf row hit the no-instance no-op path. The real pinned binary must run with `VIOLA_NAME` / `VIOLA_DIR` set (test-plan §11 Mocking; §10 Perf session).

- tests ↔ WSL pre-push (CARRY 3): `scripts/wsl-provision.sh` replays the pins it parses from the `test` job's `tool:` line (test-plan §9 tool paragraph). Hyperfine goes in by `cargo install --locked` in its own job. Whether this chunk touches the provisioner, or adds a perf stage to `pre-push`, is research's question.

## Acceptance criteria contributions
- `scripts/agent-run.sh run --perf` (and the `.ps1` shim) writes one `target/agent-run/artifacts/perf-<hook>.json` per §10 row (`session-start`, `user-prompt-submit`, `stop`, `session-end`, `pre-tool-use` unverified). It adds suite `perf` to `run-summary.json`, exits 1 with `reason:"tool-missing"` when hyperfine is absent, and turns a planted `event:"panic"` role-file line into a `perf` breach. After it, `viola-harness gate --require perf` exits 0 below the gate, and exits 1 with a `perf` breach on a missing artifact or on `max >= 1.0` (per test-plan §10 Performance budgets; §3 `gate`).
- `ci.yml` runs the perf gate on all three OSes (`windows-2025`, `macos-latest`, `ubuntu-latest`). The job installs hyperfine with `cargo install --locked hyperfine@1.20.0`, ends in `viola-harness gate --require perf`, and passes zizmor with SHA-pinned `uses:`, `permissions: {}` and `contents: read`. The CI run is green on that sha (per test-plan §9 CI Integration, Perf row and Build failure conditions).
- Root `tests/hook_fail_open.rs` gains a forced-panic case: the built `viola hook` run with `FAKE_AGENT_HOOK_PANIC` exits 0 with empty stderr and empty stdout within `< 1.0 s`, under `--features fake-agent`. `scripts/release-check.sh` still ends `release-check: viola only` (per test-plan §6 Non-path suites Security sweep; §1 security-vector-coverage hook stdin; §9 Release-build row).
- The concurrent `viola hook` append check puts at least one `detail-hook.ndjson` line over 4 KiB (the panic payload + backtrace), and every line in every shared file parses as one JSON object on all 3 CI OSes. The chunk passes `run --coverage` (lines 85 / functions 95 / regions 80, per OS) and the two-leg mutation union (`missed == 0`, `timeout == 0`, `unviable <= caught`) over its diff (per test-plan §5 Module ↔ DB; §10 Coverage thresholds and Mutation gate).
