# a11y extract

## Relevance
partial — the chunk builds no viola-owned UI surface (a11y-plan §1 A11y Scope Summary classes `hook statusline` as not-assertable); the only a11y reach is the `viola run` TUI passthrough boundary, which the chunk's new start steps and the fake agent's new statusline behaviour must leave intact.

## Constraints
- a11y-plan §1 A11y Scope Summary (Not-assertable → the Claude Code plugin entity) classes `viola hook`, `hook statusline` included, as ipc-internal with no UI surface: the wrapper, `budget.json` and `instances/<name>/settings.json` take no a11y assertion, no `@sc-*` tag and no SC claim.
- a11y-plan §1 A11y Scope Summary (CLI and terminal entities → `viola run` TUI passthrough) requires that viola write zero bytes to the terminal except the child's output, and binds both `viola run` and a passed `viola revive`. The chunk's new start steps (reading the named settings source, rewriting the override file, passing the override to the child) must add no viola-originated terminal byte on any outcome, a missing or unreadable source included.
- a11y-plan §1 A11y Scope Summary (A11y surfaces → tui, Notes) requires `run`'s diagnostics to go to `diagnostics/`, never the terminal. A failed settings read or override write that the masters make a diagnostic follows that rule. Whether such a failure is a silent degrade or a start refusal is architecture's to state, not this plan's; if it is a refusal printed before the child holds the terminal, a11y-plan §8 Cognitive Accessibility (Error recovery → CLI) requires the `unable` line then `hint:` last on stderr with a typed exit code.
- a11y-plan §1 A11y Scope Summary (A11y surfaces → cli, Notes) requires no SGR, glyph or cursor control from viola under `viola run` or a passed `viola revive`. The statusline's bytes are the user's command output carried by the child; viola adds none of its own around them.
- a11y-plan §3 Keyboard test harness (Tooling, the zero-viola-bytes clause) requires, on the Linux and macOS legs, the outer-PTY stream of a wrapped fake-agent run to equal an unwrapped fake-agent run byte for byte. The chunk gives the fake agent a `settings.json` read and a `statusline-echo` mode: whether a statusline the fake agent runs reaches its screen output, and whether the existing comparison case still holds once the wrapped run receives an override the unwrapped run does not, is research's question.
- a11y-plan §4 ARIA Patterns & Roles (the ARIA component inventory, ATIS header row) and §3 WCAG criteria mapping (Per-SC verification map, SC 1.4.1 row) assert the budget reading only where the page renders it. The scope builds the writer of `budget.json` and no reader, so no web-spa assertion, `sc-coverage.json` entry or `e2e-web/` file moves in this chunk.
- a11y-plan §2 A11y Strategy requires that no WCAG conformance claim rest on cli or tui results: any case this chunk adds on the terminal side is a boundary or output-discipline stand-in.

## Patterns to follow
- The boundary cases run on the portable-pty outer-PTY driver with `viola-fake-agent` as the child, one nextest case per boundary clause on all three OS legs (a11y-plan §4 ARIA Patterns & Roles, Must-be-accessible path scenarios → P4 tui; §3 Keyboard test harness → Tooling). A statusline-bearing start, if research finds one is needed to keep the zero-bytes clause read, follows that form.
- On Windows the zero-bytes check asserts that viola's own message literals are absent, never byte equality, because the ConPTY host emits bytes of its own (a11y-plan §3 Keyboard test harness → Tooling).
- A revived start has its own reading of the boundary: a passed `viola revive` writes no `unable` or `hint:` line while the child holds the terminal (a11y-plan §3 Keyboard test harness → Tooling). The scope's inference that revive writes the override file through the same start puts the new steps under that reading too.
- The manual tui pass (NVDA + Windows Terminal, the wrapped `claude` TUI reads the same as unwrapped, Must-Work O1) is supplemental and founder-owned, recorded as JSON rows under `a11y/sr-pass/` (a11y-plan §7 Screen Reader Support, Per-surface SR test pattern; §3 Screen reader test pattern → Per-surface test spec, Manual pass spec format). The plan names no statusline step in it; "user output unchanged" is the property that pass would read, and this chunk neither runs it nor claims it.

## Anti-patterns to avoid
- NEVER parse the rendered `claude` TUI screen for content or take screenshots as a11y evidence (a11y-plan §11 A11y Anti-Patterns → Universal): the proof that the user's statusline output is unchanged reads the wrapper's own stdout and the fake agent's marker file, not the child's screen.
- NEVER claim WCAG conformance for the cli or the `viola run` TUI, whether `run` or a passed `revive` started it (a11y-plan §11 A11y Anti-Patterns → Strategy).
- NEVER use a manual screen-reader pass as the only method (a11y-plan §11 A11y Anti-Patterns → Universal): the boundary's gating evidence is the automated outer-PTY case.

## Contract bindings
- a11y ↔ tests harness: cli and tui produce no a11y violation rows; a boundary failure surfaces only as a nextest failure in the harness `run` JSON `suites[].failures[]` (a11y-plan §3 Structured violation JSON schema → cli / tui), inside the per-OS `test` job's `coverage` suite on all three OS legs (a11y-plan §9 CI Integration, the Unit / integration stage row).
- a11y ↔ tests fake agent: the zero-viola-bytes comparison takes the fake agent's unwrapped output as its reference (a11y-plan §3 Keyboard test harness → Tooling), so the fake agent's `statusline-echo` mode and `settings.json` read (test-plan's, per the scope's item 6) are an input to an a11y boundary case.
- a11y ↔ obs: `run`'s diagnostics for the new start steps go to the process log under `diagnostics/`, never the terminal (a11y-plan §1 A11y Scope Summary, A11y surfaces → tui, Notes).

## Acceptance criteria contributions
- (a11y) With the fake agent as the child and a user statusline command configured, the outer-PTY stream across a `viola run` start holds none of viola's own message literals on every OS leg (per a11y-plan §3 Keyboard test harness → Tooling).
- (a11y) The existing zero-viola-bytes case stays green on all three OS legs after the fake agent gains its `settings.json` read, with the Linux and macOS byte-for-byte comparison against the unwrapped run intact (per a11y-plan §4 ARIA Patterns & Roles, Must-be-accessible path scenarios → P4 tui).
- (a11y) A start whose statusline source is absent or unreadable writes no line of viola's own to the terminal while the child holds it (per a11y-plan §1 A11y Scope Summary, CLI and terminal entities → `viola run` TUI passthrough).
- (a11y) No test added by this chunk reads the child's rendered screen for the statusline text (per a11y-plan §11 A11y Anti-Patterns → Universal).
