# obs extract

## Relevance
relevant — the chunk builds the `viola hook statusline` wrapper, its shell-out and the `budget.json` write, which obs-plan §4 Scenario: Budget governor names as a must-trace path; the `run`-side half of that scenario (`run.budget_eval`, the `budget-paused` `send-refused` fields) belongs to the next route entry "Budget governor" and is not extracted here.

## Constraints
- obs-plan §4 Scenario: Budget governor requires the span chain `hook.statusline` › `state.budget_write` › `statusline.shell_out` on the wrapper, with the attribute lists it names per span and `statusline_command` on none of them; `statusline.shell_out` closes on the child's exit. Spans are code structure only in v1 (obs-plan §2 Telemetry signal pyramid: not serialized), so the verdict surface is the log lines, not the spans.
- obs-plan §4 Scenario: Budget governor requires three line groups in the hook's role file for one statusline invocation: `hook-invoked` with `hook_event` statusline and no `corr`; a `process-start` / `process-exit` pair with `subject` `statusline-shell` carrying `shell_exit_status` and `duration_ms`; and `hook-decision` with `hook_event` statusline, `budget_written` and `duration_ms`. Whether `schemas/diag-line.v1.json` and `ObsEvent`'s field lists already admit `statusline`, `statusline-shell`, `shell_exit_status` and `budget_written` is research's question (obs-plan §6 Additive field catalog names all four as target state).
- obs-plan §8 PII Scrubbing (Default-deny posture) requires that a field reach a home-level line only if obs-plan §6 Additive field catalog names it for that event; an uncatalogued field is a G4 failure. For this chunk that bounds the `run`-side work too: obs-plan §6 names no field on `process-start` for the settings override, the settings source or the snapshot's `statusline_command`, so a line saying which source was read, or that the override was passed, is a catalog and schema amendment, not a free addition.
- obs-plan §8 PII Scrubbing (Data classification rules, the `statusline_command` row) requires the command string in no home-level log, and in the instance detail file only as part of an error chain. The user command's stdout passes through unchanged and is never logged (obs-plan §4 Scenario: Budget governor, Cleanup); the statusline stdin is recorded by size only (`stdin_bytes`, obs-plan §6 Additive field catalog).
- obs-plan §1 Telemetry surfaces (the `viola hook <event>` and `viola hook statusline` surface) requires the file sink `hook-<name>.ndjson` only, nothing on stderr, a swallowed log-write failure with exit 0, one `write` per line on an append handle, and logger init of one open plus appends. For the statusline arm stdout carries the user command's output, so no telemetry byte may share it.
- obs-plan §6 `detail` code catalog closes the `hook-decision` fail-open codes at seven values, and obs-plan §6 Log levels mapping puts a `hook-decision` carrying one at `warn`. The scope's fail-open cases map onto it only in part: a strict-modes refusal before the shell-out and an oversize or malformed stdin have codes; a missing or unreadable snapshot, a snapshot without the command, and a failed or timed-out user command have none named. Whether an existing code fits each (and whether `deadline` / `deadline_hit` covers a bound on the user command) is research's question; a new code is a schema amendment under G4 (obs-plan §9 Gate commands).
- obs-plan §10 SLO Invariants & Telemetry Budgets (Zero unlogged panics) requires one single-line `panic` record in the role file for a panic in the statusline arm after init step 4, with the hook still exiting 0; the bounded exemptions it lists (no `VIOLA_NAME`, a failed role-file open) apply to this arm as to any hook. No new exemption is named for statusline.

## Patterns to follow
- The existing hook arms are the template: `#[instrument(skip_all, name = "<area>.<operation>", fields(..))]` with `<area>` from the closed list (it already holds `hook`, `state` and `statusline`), `catch_unwind` around dispatch, the writer falling back to a sink on open failure (obs-plan §4 Instrumentation per surface, the `viola hook` row; obs-plan §2 Naming conventions).
- The shell-out follows the child-spawn wrapper pattern used for the version and verify probes: a `process-start` / `process-exit` pair logged at the call site with a closed `subject`, exit status and `duration_ms`, no argv, no path (obs-plan §6 Boundary-call wrappers, Child / shell spawns).
- Every line goes through `obs_event!` with explicit typed fields, `corr` absent when null, `message` the static event name (obs-plan §3 Logging stack; obs-plan §3 Log format JSON schema, Null encoding).
- A typed error crossing a crate seam ends in one logged `hook-decision` with a closed `detail`; its full chain goes only to `detail-hook.ndjson` and only when an instance resolves (obs-plan §7 Error Capture & Reporting, Error classes captured and Scrubbing layers).
- The `run`-side snapshot write stays inside the existing `state.snapshot_write` span, whose attribute list holds `v` only (obs-plan §4 Scenario: `viola run` start sequence to child spawn). The plan names no span for the `settings.json` rewrite or the settings-source read; a new one takes the same `skip_all` form with no path-valued or command-valued field (obs-plan §4 Span naming convention).

## Anti-patterns to avoid
- Never log `statusline_command`, the statusline stdin or the user command's stdout in any home-level file, at any level (obs-plan §11 Obs Anti-Patterns → PII Scrubbing).
- Never a bare `#[instrument]`, and never `err` / `ret` on a function whose error or return can hold the command string, a serde source or upstream text — the settings read and the statusline JSON parse are both such functions (obs-plan §11 Obs Anti-Patterns → Spans / Traces).
- Never add an `event` value, rename a tests field, or write telemetry to stdout or stderr on the hook path; a new `event` value needs a Decisions Log entry (obs-plan §11 Obs Anti-Patterns → Logs).

## Contract bindings
- obs ↔ tests harness: the hook role file's line format is the tests-bound log format; obs may add fields but not rename or remove (obs-plan §3 Log format JSON schema). `agent-run logs` reads these lines; test-plan §6 Path 6 is the consuming critical path (obs-plan §4 Scenario: Budget governor names it as its source).
- obs ↔ tests gates: the chunk's E2E homes must stand under `target/e2e-home/` so G2, G4 and the secret scan read the statusline lines — a hook panic exits 0 and is invisible otherwise (obs-plan §9 Pipeline integration, Integration tests row). obs owns `schemas/diag-line.v1.json`; the check body is tests-owned (obs-plan §9 Gate commands, G4).
- obs ↔ security: `statusline_command` is High (integrity) in the security Data Classifications that obs-plan §8 PII Scrubbing reproduces; the test statusline command is an absolute path to the fake agent, so the path rule (home-level lines path-free) binds it as well (obs-plan §8 PII Scrubbing, the Absolute paths row).
- obs ↔ tests canary: every E2E and integration input is synthetic and carries the tests-owned canary, which may appear in `detail-*.ndjson` only (obs-plan §8 PII Scrubbing, Integration points item 6). The synthetic statusline payload and the fake `statusline-echo` marker are such inputs; whether the canary rule's test body already scans a statusline case is research's question.
- obs ↔ tests perf: obs-plan §10 Performance budgets times five hook rows and names no statusline row; `hook-decision.duration_ms` per `hook_event` is still required as the report-only sample (obs-plan §5 Per-surface / per-path metrics, Hook latency). A gated statusline row would be a tests-owned addition.
- obs ↔ later entries: the `budget.read_at` gauge is read through `agent-run status` (obs-plan §5 Metric instrument types); its reader is outside this chunk.
- obs ↔ `viola verify` (behind the founder's stop rule): a statusline probe that used the hidden `--capture` arm would be uninstrumented by design, with no role file and no lines (obs-plan §4 Edge flows, `verify` / `plugin install`).

## Acceptance criteria contributions
- (obs) One wrapped statusline invocation with `VIOLA_NAME` set leaves, in `hook-<name>.ndjson`, `hook-invoked` then the `statusline-shell` `process-start` / `process-exit` pair then `hook-decision`, each with `hook_event` or `subject` as named, `budget_written` on the decision and no `corr`; without `VIOLA_NAME` it leaves no file and no line (per obs-plan §4 Scenario: Budget governor; obs-plan §4 Edge flows E1).
- (obs) G4 reads clean over every home-level line the chunk's tests produce, and G1 reads clean over the new spans (per obs-plan §9 Gate commands).
- (obs) Neither the synthetic statusline command string, the statusline stdin's content nor the echo marker appears in any home-level `diagnostics/*.ndjson`; the secret scan and the canary rule read clean (per obs-plan §8 PII Scrubbing, Integration points item 6).
- (obs) G2 reads zero panic lines over the chunk's homes, and a failing or absent user command still ends in a `hook-decision` line with exit 0 and empty stderr (per obs-plan §10 SLO Invariants & Telemetry Budgets, Zero unlogged panics; obs-plan §7 Error Capture & Reporting, Error classes captured).
