# security extract

## Relevance
relevant — the chunk builds viola's only shell-out (`hook statusline` running `statusline_command`), a code-bearing per-session file (`instances/<name>/settings.json`), a new home file (`budget.json`) and a new external reader (the user's settings source).

## Constraints
- **Strict-modes before the shell-out.** security-plan §Authentication & Authorization (`~/.viola/` access control row) requires the strict-modes check in every process that reads `statusline_command`, and names `hook statusline` in that entry-point set; on a failure a `hook` prints nothing and exits 0. The row's dated interim gap for `viola hook <event>` is worded for the snapshot's `endpoint` read only, and no dated exception in the plan names the statusline arm, so the arm may borrow none. The row requires the Windows owner + DACL check at the same entry points as Unix. Whether an existing check (`viola_state::strict::check_instance` or another) already covers the home, the instance directory and `snapshot.json` on both OS families is research's question.
- **`VIOLA_DIR` before the `statusline_command` read.** security-plan §Input Validation (CLI arguments / stdin row) requires `--home` and `VIOLA_DIR` to be canonicalised and then pass the strict-modes check before any `statusline_command` read. The same row records a ratified interim gap for `viola hook <event>`'s event path (no canonicalisation, an absolute `VIOLA_DIR` ending `<home>/instances/<name>` and a `VIOLA_NAME` through `ViolaName::try_new` instead). The plan does not state that this gap reaches the statusline arm, and the scope leaves the canonicalised `VIOLA_DIR` to Epoch 6: which rule the statusline arm reads `VIOLA_DIR` under is not settled by the plan and is a boundary question for the review card, not a lean.
- **Hook stdin bounds.** security-plan §Input Validation (Hook stdin row, which names `hook statusline`) requires `Read::take(MAX_FRAME + 1)` on `read_to_end` so an over-limit payload is detected and fails open (exit 0, no body); a payload that is not one JSON object fails open; an absent or invalid `VIOLA_NAME` exits 0 with nothing written anywhere; parsing is tolerant; `resets_at` is parsed with chrono in UTC only and a malformed value becomes `"unknown"`.
- **The override file is code-bearing.** security-plan §Data Protection (At rest, Code-bearing artefacts) requires `instances/<name>/settings.json` to be rewritten by `viola run` at every start through the shared tempfile `persist` helper at 0600, never reused from an existing copy, its command the absolute pinned `bin/<version>-<hash>/viola(.exe)` path. security-plan §Bootstrap phases (`auth-scaffolding-baseline`) repeats it with the mode set on the temp file before the write. Whether `viola revive`'s start reaches the same writer is research's question.
- **Home files: explicit modes, one replace helper, one snapshot writer.** security-plan §Authentication & Authorization (`~/.viola/` access control row) requires every file under the home at 0600 through `OpenOptionsExt::mode` and every replaced file through `viola_state::fs::replace_private`, never the umask, the write discarded if the mode cannot be set; this binds `budget.json`, its `.lock` sibling and `settings.json`. security-plan §Security Anti-Patterns → Universal requires that only the instance's own wrapper writes `snapshot.json`, because `statusline_command` in it decides what `hook statusline` executes: the hook arm records nothing there.
- **NEVER-log floor for the command string, fail-open for the hook.** security-plan §Bootstrap phases (`logging-redaction-wire`) admits the `statusline_command` string in `snapshot.json` and `instances/<name>/settings.json` as contract payloads and otherwise sends it only to `instances/<name>/diagnostics/`: never a stderr line, CLI `--json` error output, MCP `isError` result, Problem Details or channel `error.data`; absolute paths stay out of every external error, and `budget.json` values may be written to `diagnostics/`. security-plan §Error Handling (Internal logging) requires that `hook` never writes stderr and never exits non-zero, a failed security check included.
- **One shell-out, no switch.** security-plan §Security Anti-Patterns → Code Patterns names `statusline_command` as the only shell-out and bans a second one. security-plan §Security Anti-Patterns → Universal bans any `config.json` key, `VIOLA_*` variable or CLI flag that switches off the home strict-modes check, and any test seam beyond the two recorded ones without its own Decisions Log entry: the per-home redirect for tests must be neither.

## Patterns to follow
- The replace helper's order: temp file in the parent, mode set before any byte, `sync_all`, `persist` (security-plan §Authentication & Authorization, `~/.viola/` access control row).
- Rewrite rather than trust: the plugin files are rewritten at every start instead of reusing an existing copy, and the plan gives `settings.json` the same treatment (security-plan §Data Protection, At rest, Code-bearing artefacts).
- The check-then-use order `viola revive` is specified with: the strict-modes check on the instance's files runs before any snapshot value is used (security-plan §Authentication & Authorization, `~/.viola/` access control row). Whether that check fits a hook process as it stands is research's question.
- The hook's fail-open shape with codes only: an oversize or malformed stdin ends in exit 0, no body, and a codes-only diagnostics note (security-plan §Input Validation, Hook stdin row; security-plan §Error Handling, Internal logging).
- Fixed messages before an error chain: a serde source that can quote an input value is mapped to a fixed message before it joins an anyhow chain (security-plan §Bootstrap phases, `error-sanitization-wire`); this applies to a parse failure of the user's settings source and of the statusline JSON.

## Anti-patterns to avoid
- NEVER run `statusline_command` from a `snapshot.json` whose home or instance directory fails the strict-modes check: write access there equals code execution (security-plan §Security Anti-Patterns → Data Protection).
- NEVER let the statusline command `viola run` writes into `instances/<name>/settings.json` resolve `viola` through PATH (security-plan §Security Anti-Patterns → Universal).
- NEVER write to stderr from `viola hook`, and NEVER exit non-zero from it, including on security-check failures (security-plan §Security Anti-Patterns → Logging).

## Contract bindings
- **architecture (capability ledger).** security-plan §Security Anti-Patterns → Universal ties a non-`null` dialog decision to a stamp holding the seventeen ledger rows (`LedgerRow::ALL`, counter `/17`). A statusline ledger row added to that set would change what a stamp must hold, so a home stamped under the seventeen would read `cli_verified:false` and dialog answering would stop until a re-stamp. Whether a new row joins the gating set is the founder's (the scope's item 8), and the count in that plan section moves with it.
- **architecture (instance snapshot, `VIOLA_DIR`).** security-plan §Threat Model Summary (Attack surface: hook stdin; CLI arguments, flags and environment) places the integrity of `statusline_command` on the filesystem permissions of the home that `VIOLA_DIR` selects; the snapshot field and the env plumbing are architecture's contracts.
- **obs.** The diagnostics notes of a failed statusline run, and the absence of the command string from every process-log line, are bound by security-plan §Bootstrap phases (`logging-redaction-wire`); the CI artifact canary scan that enforces the floor (a non-0600 diagnostics file included) is obs-plan §9 as cited by security-plan §Secret Management (Secret scanning in CI).
- **tests.** security-plan §Input Validation (Parser surfaces) lists the hook stdin parser, `hook statusline` included, as fuzz / property scope whose cases tests owns. The fake agent's `statusline-echo` mode stays behind a test-only feature: security-plan §Dependency Security (CI integration) requires `scripts/release-check.sh` to refuse any artifact built with `test-support` or `fake-agent`. A recorded statusline payload committed under `fixtures/claude/<cli-version>/` falls under security-plan §Data Protection (Repository fixtures): synthetic prompts, the scrub, and the whole-recording refusal on a surviving home path, username or email; a statusline JSON carries directory paths, so whether a synthetic test input holds one is research's question.
- **Not stated by the plan (for P3 and the review card; none of this is coverage).** The plan holds no rule for: which shell runs the command per OS, a bound on the wait for the command, the command's environment or working directory, or where the command's own stderr goes; the read of the user's Claude Code settings source as an input boundary (size cap, tolerant parse); a per-home redirect file as a code-deciding home file (the trusted-file list of security-plan §Authentication & Authorization names `snapshot.json`, `ledger/stamps.json` and the pinned `viola` only); `budget.json`'s lock discipline. The plan's body carries no dated founder ratification for the shell-out or for the every-start rewrite of `settings.json`, and a search of the Decisions Log history files for `statusline` read no entry naming either.

## Acceptance criteria contributions
- `viola hook statusline` started against a home or an instance directory that fails the strict-modes check runs no command, prints nothing, leaves stderr empty and exits 0 (per security-plan §Security Anti-Patterns → Data Protection; security-plan §Authentication & Authorization, `~/.viola/` access control row).
- After a start over a pre-existing, altered `instances/<name>/settings.json`, the file holds the freshly rendered bytes at mode 0600 and its statusline command begins with the absolute pinned `bin/<version>-<hash>/viola(.exe)` path; `budget.json` written by the hook reads mode 0600 on Unix (per security-plan §Data Protection, At rest, Code-bearing artefacts; security-plan §Authentication & Authorization, `~/.viola/` access control row).
- A statusline stdin of `MAX_FRAME + 1` bytes, and one that is not a JSON object, each end in exit 0 with empty stderr and no partial write of `budget.json`; a malformed `resets_at` is recorded as `"unknown"` (per security-plan §Input Validation, Hook stdin row).
- A marker placed in the test statusline command is found in no process-log line, no stderr and no external error body of any verb in the run; it stands only in `snapshot.json`, `instances/<name>/settings.json` and `instances/<name>/diagnostics/` (per security-plan §Bootstrap phases, `logging-redaction-wire`).
