# tests extract

## Relevance
relevant — `viola hook statusline`, the per-start instance `settings.json`, the `budget.json` reading, the fake agent's `statusline-echo` mode and the harness's `boot --statusline-echo` are all named test surfaces (test-plan §1 Coverage scope, §6 Path 6, §7 Fake agent, §3 `boot`); Path 6's budget, refusal and override bullets stay outside this chunk.

## Constraints
- Tier and layer placement: test-plan §1 (Test tier) sets Comprehensive, and §2 Test pyramid requires unit, integration, property and E2E cover for this surface on all three OSes; §11 Test Strategy requires each case at the lowest layer that can hold it (the `rate_limits` parser, the `"unknown"` fallback and any clock case in §4; only the cross-process pass-through in §5 / §6) and bars a Linux-only run as proof for the Windows or macOS branch of the per-OS shell code.
- Hook signal: test-plan §1 Surfaces under test (cli, `viola hook <event>` and `viola hook statusline`) requires exit 0 and empty stderr on every case, with the side effect read as `budget.json` contents; §1 Coverage triggers (hook stdin) requires the fail-open cases and that `statusline_command` does not run when the home fails strict-modes. Whether the landed fail-open matrix can take a statusline arm as it stands is research's question.
- Test data origin: test-plan §7 Seed strategies requires `budget.json` to come only from generated statusline stdin piped into the real `viola hook statusline`, and `settings.json` (on-disk product state) only from a real `viola run` in a fresh home; a sentinel may be written only into a file the product already wrote (§6 Path 1 step 5).
- Fake-agent shape rule: test-plan §7 Fake agent says `statusline-echo` and the `settings.json` read land with this consumer chunk and that no shape is invented before a recorded fixture. Synthetic statusline stdin is sanctioned as test input by §1 Coverage scope (budget data source) and §8 What to mock, never as a file under `fixtures/claude/<ver>/`. The plan does not settle whether the fake agent itself may feed statusline stdin with no recorded payload (its one named unrecorded payload is the `--resume` SessionStart, by the operator's word); that is P3's and P4's to close.
- Harness flag: test-plan §3 `boot` binds `--statusline-echo` (run before boot step 5, the marker file under the session home's `fake/`, the settings source redirected into the session home) and requires exit 2 `statusline-source-unresolved` until architecture names the source, never a test against a guessed source; §3 Closed enums requires a Decisions Log entry for a new value. Whether the harness already implements that refusal is research's question.
- Time: test-plan §11 Universal bars a test-owned timer, sleep or elapsed-time verdict and bars an in-process clock for another process; a bound on the user's statusline command is therefore clock-driven in a §4 unit case, and a cross-process case may wait on it only through the product's own exit code or status. §10 Zero-flakiness budget keeps `retries = 0` with no `#[ignore]` parking.
- Real CLI: test-plan §11 Test Strategy bars the real `claude` in CI and bars reading a green fake-agent run as proof of real-CLI behaviour; §6 (Skipped as "untestable") places a live reading in the chunk's own `evidence/`, local only. This bounds what a fake-agent rehearsal may claim for the settings-override mechanism, the shell per OS and `rate_limits.*`.

## Patterns to follow
- Integration shape: test-plan §5 Boundary types (Hook exec ↔ channel ↔ disk) and §6 Drivers per surface (cli `viola hook` / `hook statusline`): assert_cmd on the real binary, `VIOLA_NAME` / `VIOLA_DIR` set with `Command::env`, an `Instant` deadline, `LLVM_PROFILE_FILE` re-added after any `.env_clear()`; root `tests/hook_<topic>.rs` (§2 File naming), a fresh home under `target/e2e-home` (§5 Setup / teardown lifecycle).
- Unit and property shape: test-plan §4 What unit tests cover (viola-agent-claude: statusline `rate_limits` parsing, malformed `resets_at` to `"unknown"`) with labelled rstest cases, and §6 Property suite (statusline JSON with arbitrary `resets_at`, `cases: 512`) with seeds committed under `proptest-regressions/` (§7 Seed strategies, Randomized data). The tests live in the crate that owns the parser, because §3 `run` step 4 (Test scope) grades a crate's mutants by that crate's own tests.
- Rewrite-on-start shape: test-plan §6 Path 1 step 5 (stop the wrapper, plant a sentinel in the instance's `settings.json`, start again) with §1 Coverage triggers (filesystem) as the mandate. Path 1's verification bullet names the absolute `pinned_bin` for `hooks.json` only; the same reading on `settings.json` is this chunk's addition. Whether the landed Path 1 test plants a `settings.json` sentinel is research's question.
- Pass-through E2E shape: test-plan §6 Path 6 steps 1, 2 and 6 through `harness_session` with the flag (§3 `run` step 2), the fake agent running the real pinned binary through the file `run` wrote (§8 What NOT to mock) and spawning only an absolute command directly, receipts as `v:1` kebab-kind lines, the agent waiting for a running hook before it exits (§7 Fake agent).
- Canary: test-plan §6 Error sanitization and secret scan (Canary) requires every statusline payload a test feeds to embed the `tests/support` canary, which may never reach a home-level diagnostics line.

## Anti-patterns to avoid
- Never hand-write `budget.json` or `snapshot.json`, and never stub `viola hook` in E2E (test-plan §11 Test Data; §11 Mocking).
- Never claim Path 6 from the pass-through bullets alone, and never push a parser or fallback case up to E2E (test-plan §11 Test Strategy: a multi-surface path needs a driver step per surface; a lower-layer case stays lower).
- Never synchronise on `sleep(N)`, never drive a spawned `viola hook statusline` with `MockClock`, and never pass the per-home redirect or any test value with `std::env::set_var` (test-plan §11 E2E; §11 Universal; §11 Integration).

## Contract bindings
- tests ↔ architecture: test-plan §3 `boot` and §6 Path 6 step 1 wait on architecture naming the settings source (the plan's §12 open question). The chunk's per-home redirect is that resolution, so the `boot` contract, the `statusline-source-unresolved` refusal and Path 6 step 1 change with it (a test-plan amendment at wrap).
- tests ↔ security: test-plan §1 Coverage triggers (hook stdin; filesystem; CLI and env) carry security Vectors 4, 7 and 6. §6 Security control negatives (Single writers) requires that `hook statusline` changes neither `snapshot.json` nor `ledger/stamps.json`. §5 Cross-module patterns (CLI, `tests/cli_controls_not_disableable.rs`) requires any new flag or `config.json` key, the redirect included if it lands as one, to join the table, and its completeness case fails otherwise.
- tests ↔ obs: test-plan §6 Schema conformance (obs gate G4), the secret scan and the zero-panic gate read every home under `target/e2e-home/**` (§3 `boot` step 2); any diagnostics line `hook statusline` writes is judged there, and the content canary binds to obs-plan §8.
- tests ↔ capability ledger (behind the founder's word): the seventeen-row literals in test-plan §5 Cross-module patterns (CLI, `contract_ledger_probes.rs` and `tests/cli_verify.rs`), §3 `run` (`--local-live`), §3 `boot` step 4 and §4 What unit tests cover (viola-agent-claude, the version gate) all move if a statusline row lands; a new `viola verify` child needs a fake-agent mode (§7 Fake agent) and recorded, scrubbed fixtures (§7 Seed strategies, Recorded hook payloads; §7 Fixture hygiene).
- tests ↔ fuzz: test-plan §1 Coverage triggers (property-test) counts `hook statusline` inside the hook stdin parser surface, and §2 Test pyramid (Property-based) adds fuzz targets as parsers land. The plan does not say whether the `hook_stdin` target must reach the statusline parser or gain a seed; P3 closes it.
- Plan gaps for P3 / P4: test-plan §10 Performance budgets names no row and no deadline for `hook statusline` (five rows, required by name in §3 `gate`); §7 Fake agent lists no receipt kind for a statusline-command run; §6 Path 6 step 6 gives a Unix chmod only, no Windows form.
- tests ↔ a11y / design: (none) — Path 6's Playwright `path6` test and the ATIS cell need the governor.

## Acceptance criteria contributions
- `scripts/agent-run.sh run` (unit and integration, then fake-agent E2E) is green with the new tests, 0 failed and 0 skipped, and `run --coverage` holds lines ≥ 85, functions ≥ 95 and regions ≥ 80 per OS job with the ignore regex unchanged; no chunk mutation gate applies (per test-plan §3 `run`; §10 Coverage thresholds; §10 Mutation gate; §11 CI)
- With a home whose user statusline command is the fake agent's `statusline-echo`, synthetic stdin piped into `viola hook statusline` gives stdout equal to the marker byte for byte, exit 0, empty stderr and a `budget.json` holding the fed percentage; under a 0770 home (Unix) it gives exit 0, empty stdout and an unchanged marker file (per test-plan §6 Path 6, Verification signal)
- A malformed `resets_at` reads `"unknown"` in a unit case, and the statusline `resets_at` property runs at `cases: 512` with its regressions file committed (per test-plan §4 What unit tests cover; §6 Property suite)
- After a restart, a sentinel planted in the instance's `settings.json` is gone and the file's command is the absolute pinned path, never a PATH lookup (per test-plan §6 Path 1 step 5; §1 Coverage triggers, filesystem)
