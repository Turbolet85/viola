# arch extract

## Relevance
relevant — the chunk lands four resources architecture already names (`hook statusline`, `instances/<name>/settings.json`, `budget.json` + its lock, the snapshot's `statusline_command`) and touches the capability-ledger gate, the start order and the one ratified shell-out.

## Constraints
- **Workspace placement.** architecture §Infrastructure Patterns → Crate dependency direction and §Infrastructure Patterns → Project directory structure require the Claude-specific shapes of this chunk (statusline JSON parsing, the resolution of the user's effective Claude Code settings, the settings-override argument shape) to live in `viola-agent-claude`; file I/O (the `budget.json` replace and its lock, the `settings.json` replace) to go through `viola-state`; the `hook statusline` arm and the start wiring to live in the root bin, which consumes only normalised shapes. The same key file states the target edge `viola-agent-claude` → `viola-state` but records the crate as landed WITHOUT that dependency, the edge arriving "with the chunk that consumes it": whether settings resolution makes this chunk that consumer, or the read stays in the root bin with only the shape in the agent crate, is research's question.
- **Capability ledger is the single gate.** architecture §Cross-cutting Patterns (Capability ledger as the single gate for CLI-specific behaviour) requires every relied-on undocumented `claude` behaviour to be a ledger row in `viola-agent-claude` with a `viola verify` probe and a post-condition, never an unconditional assumption; the ruled limit there covers only shapes no `send` relies on, and the plan records no such limit for the statusline. architecture §Established Decisions [CLI Version Compatibility] names the three statusline rows (`rate_limits.*`, the settings-override mechanism, the per-OS shell) and assigns them to Epochs 4 and 5.
- **A new row moves `cli_verified`.** architecture §Established Decisions [CLI Version Compatibility] requires a version to count as verified only when its stamp holds EVERY landed row `pass`, and prices an added row as a probe plus a re-stamp of every stamped version (five `claude` starts per verify). So landing any of the three rows in the closed set without a re-stamp turns the one stamped version unverified. What `run` does with the override on a CLI that holds no stamp for it is not stated by the plan beyond architecture §Design Philosophy (Measured, never assumed); it is unsettled in this master.
- **The wrapper's contract.** architecture §Standard Contracts → Hook contract requires `viola hook statusline` to record the `rate_limits` reading, run the user's own command with the same stdin, print that command's stdout unchanged (empty on failure) and exit 0, with the command read from the instance snapshot through `VIOLA_DIR` and resolved by `run` at start. architecture §Established Decisions [Hook Contract] requires every `hook` path to exit 0, never write stderr, never produce exit 2, and exit at once when `VIOLA_NAME` is absent. No bound on the wait for the user's command is stated in either section: that bound is research's question.
- **One shell-out, nothing else.** architecture §Cross-cutting Patterns (Cross-platform discipline) requires every child to be spawned directly and admits exactly one shell-out, `hook statusline` running the user's command through the shell Claude Code would use for it; architecture §Standard Contracts → Hook contract makes that shell a ledger row. architecture §Design Philosophy (Cross-platform from the first commit, Windows first) requires the Windows, macOS and Linux branches to build and pass CI against the fake agent.
- **Disk state.** architecture §Established Decisions [Snapshot writer] requires every replaced file to go through the one helper (`viola_state::fs::replace_private`), with no call site carrying its own temp-and-rename code. architecture §Established Decisions [Database / State Store] requires budget readings to be timestamped, last-writer-wins, under `File::lock` on a separate `.lock` file. architecture §Occupied Resources (Viola home files: `budget.json` + `budget.json.lock`) requires `hook statusline` to be the only writer; architecture §Occupied Resources → Claude Code integration names requires the override at `instances/<ViolaName>/settings.json`, written by `viola run` at start.
- **Snapshot and start order.** architecture §Standard Contracts → Instance snapshot requires `statusline_command` to be an optional field of a snapshot only the instance's wrapper writes; architecture §Standard Contracts → Snapshot envelope requires a replayed or unreadable snapshot to give no `statusline_command`, in which case `hook statusline` prints nothing. architecture §Established Decisions [Session Liveness] places `statusline_command` in the FIRST snapshot, written before the spawn. That start order names no step for the `settings.json` write: its position (after the pinned copy, whose path it carries, and before the spawn) is the plan's to fix and research's to check against the landed order.
- **No new configuration channel.** architecture §Cross-cutting Patterns (Config management) requires that environment variables are not a configuration channel, lists the `config.json` settings as a closed set, and names the viola home (`--home`, passed to the child only through `VIOLA_DIR`) as the isolation point for tests. architecture §Conventions → Naming patterns (Environment variables) admits only the `VIOLA_` prefix and two ratified test seams. The plan states no form for the per-home redirect of the settings source: architecture gives the isolation point, not the mechanism, so the form is research's question and any new key, variable or flag would be an amendment.

## Patterns to follow
- **Tolerant external parse.** architecture §Established Decisions [Validation] sets the regime for the statusline payload: no `deny_unknown_fields`, defaulted or optional fields, the raw value kept, serde_path_to_error for drift reports. architecture §Conventions → Data model conventions (Unparseable external values; Percentages; Timestamps) and §Established Decisions [Timestamps] fix how a malformed `resets_at`, `used_percentage` or a missing window is recorded, and that `read_at` is RFC 3339 UTC with milliseconds.
- **Additive optional snapshot field.** architecture §Standard Contracts → Instance snapshot (the `cwd` bullet) is the landed precedent for a field written when present, omitted otherwise, with `v` unchanged; architecture §Conventions → Data model conventions (Optional fields) and §Conventions → Interfaces and versioning (Protocol versioning) give the serde form and the no-bump rule.
- **Pinned absolute path, rewritten every start.** architecture §Established Decisions [Deployment / Distribution] is the pattern for a code-bearing file `run` writes: the pinned copy's path substituted into the exec-form `command`, the file rewritten on every start, no PATH search; architecture §Cross-cutting Patterns (Cross-platform discipline) requires forward slashes in paths written into plugin files. Whether the forward-slash rule extends to `settings.json`, which is not a plugin file, is research's question.
- **Find the instance through the recorded state.** architecture §Occupied Resources → Environment variables (`VIOLA_NAME`, `VIOLA_DIR`) is the pattern the wrapper follows: the home derived as the grandparent of `VIOLA_DIR`, values read from the recorded snapshot instead of re-derived; architecture §Cross-cutting Patterns (Identity by instance, never by location) forbids using the working directory.
- **Fake agent surface.** architecture §Occupied Resources → Binary, subcommands and exit codes (Test-only binaries) describes `viola-fake-agent` as driven by argv options with no env, behind feature `fake-agent`; a `statusline-echo` mode and a settings read extend that surface, and its option count there is amended at wrap. architecture §Established Decisions [CI/CD] gives the substitution after `--` and one viola home per test.

## Anti-patterns to avoid
- Spawning the user's command, or anything else, through `sh`, `bash` or `cmd` outside the single `hook statusline` exception, or letting the override's command resolve through PATH (architecture §Cross-cutting Patterns (Cross-platform discipline); architecture §Established Decisions [Deployment / Distribution]).
- Touching the user's own statusline configuration, or wrapping the statusline for a session not started through `run`'s start path (architecture §Established Decisions [Budget Governor]).
- Giving `hook statusline` any state it does not own: an event line, a snapshot write, a channel frame, Tokio, or a Claude-specific name outside `viola-agent-claude` (architecture §Conventions → Naming patterns (Hook → kind map); architecture §Standard Contracts → Instance snapshot; architecture §Cross-cutting Patterns (Tokio containment); architecture §Inherited Defaults (Agent isolation)).

## Contract bindings
- **arch ↔ security:** the shell-out, the strict-modes check before it, the 0600 `settings.json` and its pinned command, and the command string's place under the NEVER-log floor are security-plan's; architecture §Cross-cutting Patterns (Cross-platform discipline) and §Occupied Resources (Viola home files) only name the resources.
- **arch ↔ tests:** the fake agent's new mode and its option count (architecture §Occupied Resources → Binary, subcommands and exit codes), the per-home isolation point (architecture §Cross-cutting Patterns (Config management)) and the fake-agent-only CI rule (architecture §Established Decisions [CI/CD]) bind test-plan's Path 6 and its property suite.
- **arch ↔ obs:** architecture §Cross-cutting Patterns (Diagnostic output channels) sends the wrapper's codes-only lines to `diagnostics/hook-<name>.ndjson` and content-bearing detail to the instance's `detail-hook.ndjson`; which catalog lines `hook statusline` writes is obs-plan's.
- **arch ↔ the route entry "Budget governor":** the reading's shape in `budget.json` is the read contract of the gate, `list` and `ui` (architecture §Occupied Resources (Viola home files: `budget.json`); architecture §Standard Contracts, the `/api/sessions` envelope's `budget` bullet). The plan states the per-window reading plus `read_at` and does not spell out the file's own envelope: whether it takes the Snapshot envelope with `v` (architecture §Cross-cutting Patterns (Mixed-version tolerance)) is research's question, and it must be settled here because the next entry reads it.
- **arch ↔ `viola verify`:** each of the three rows needs its probe in the verify child set (architecture §Established Decisions [CLI Version Compatibility]); the child set is security-plan's and the founder's.

## Acceptance criteria contributions
- (arch) Statusline payload parsing, settings resolution and the override's argument shape live in `viola-agent-claude`; the `budget.json` and `settings.json` writes go through `viola-state`'s one replace helper; no sync crate gains a Tokio edge and no crate edge runs against the stated direction (per architecture §Infrastructure Patterns → Crate dependency direction).
- (arch) `viola hook statusline` exits 0 with empty stderr on every path, prints the user command's stdout byte for byte, and prints nothing when the snapshot is absent, unreadable or holds no `statusline_command` (per architecture §Standard Contracts → Hook contract and §Standard Contracts → Snapshot envelope).
- (arch) `budget.json` is written only by `hook statusline`, by atomic replace under `budget.json.lock`, in the home derived from `VIOLA_DIR`, and holds the per-window reading plus `read_at` with the `"unknown"` forms for an unparseable field and an omitted window (per architecture §Occupied Resources (Viola home files: `budget.json` + `budget.json.lock`) and §Conventions → Data model conventions).
- (arch) The chunk adds no environment variable, `config.json` key, channel method, event kind or listener, and the snapshot's `v` stays 1 with `statusline_command` omitted when the user has no statusline (per architecture §Cross-cutting Patterns (Config management) and §Conventions → Interfaces and versioning (Protocol versioning)).
