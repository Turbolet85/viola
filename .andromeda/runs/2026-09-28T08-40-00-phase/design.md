# design extract

## Relevance
relevant: this chunk builds the cli surface's token, depth, decision-order, stream and escaping layer, which is exactly what design-system §Surface: cli specifies. The web-spa sections (layout, CSS tokens, motion) are out of scope.

## Constraints
- **Token set is closed and per-depth.** design-system §Surface: cli → Tokens (platform-specific) requires exactly four emitted tokens: `attention`, `stale`, `callsign` and `reset`. Each has a fixed SGR string for each of the three depth columns, and `attention` traces to Core Colors Accent #D97706 (per design-system §Color Palette → Core Colors). The handoff-blue row is "not used" at every depth with no index reserved, and backgrounds are "never set". The module therefore must not be able to produce a blue SGR or any background SGR.
- **The stale × cock interaction is fixed.** Per design-system §Surface: cli → Tokens (the `stale` row), a whole stale row is dim, the word `stale` is always printed in LIVE, and on a row that is both stale and cocked only the `DIALOG` word is amber and not dim, while the kind word and the rest of the row stay dim. The layer's span API has to be able to express "dim row, with one amber non-dim span inside" and a `reset` after every styled span.
- **Decision order and depth are chosen once, first match wins.** design-system §Surface: cli → Colour decision order lists seven no-colour conditions in a fixed order (`--json` → `viola run` → `hook`/`mcp` → `NO_COLOR` → `TERM=dumb` → stdout not a terminal → Windows VT enable failed). A match means no colour, no glyph and no SGR. Otherwise the depth rule (truecolor via `COLORTERM`, 256 via `TERM` containing `256color` or Windows VT success, else 16) is evaluated once per process. The Toolkit bullets fix std `IsTerminal` for TTY detection and windows-sys `SetConsoleMode(ENABLE_VIRTUAL_TERMINAL_PROCESSING)` for VT enabling, with failure meaning no colour.
- **The ASCII words survive every human mode.** Per design-system §Surface: cli → Colour decision order (the preamble) and §Iconography → Separator, "glyph" means a non-ASCII symbol. So `[RB]`, `[  ]`, `[/ ]` and `->` are words that still print when output is piped or under `NO_COLOR` and `TERM=dumb`, and only `--json` replaces them. Human output is ASCII only (per §Surface: cli → Width), with two-space column separation and ` - ` inside a field (per §Iconography → Separator).
- **The streams are split.** design-system §Surface: cli → Streams puts results and data on stdout, and puts context lines, refusals, each refusal's `hint:` line (directly after it), `error: …` lines and the `viola ui` launch line on stderr. Under `--json` the whole result, refusals and `error` objects included, is one JSON document on stdout with the typed exit code, and no `hint:` line is printed.
- **Styled spans exist only on the board.** Per design-system §Surface: cli → Component Patterns 1, colour applies to the `viola list` rows (NAME bold, `DIALOG` amber, stale row dim). Per §Component Patterns 3, 5 and the Exit-code phraseology, `wait`'s `question … dialog` is not coloured, `verify`'s `fail` is uncoloured, the `ui` launch line is unstyled even on a TTY (no bold, no OSC 8), and `error: internal error` is a fixed, uncoloured message with no hint. The decision order checks only stdout's TTY, which is consistent with that: no stderr line is ever styled.
- **Escaping has a floor and a stricter tier.** Per design-system §Surface: cli → Component Patterns 1, every upstream-origin field has C0/C1 controls rendered as `\x1B`-style hex text (binding the security plan's floor). `list` table rows also escape `\n` and `\t` (`\x0A`, `\x09`), so a row stays one fixed-width line (T5, ratified). Per §Component Patterns 3, `wait` / `last` message text keeps `\n` and `\t`. The layer therefore needs two escape modes, row and message, not one.

## Patterns to follow
- A hand-written SGR module in the `viola` bin that adds no dependency (per design-system §Surface: cli → Toolkit / Framework). The windows-sys call is named there as "already in the stack". Whether the workspace already enables the `Win32_System_Console` feature for the `viola` bin is research's question.
- A pure decision function over injected facts (mode or verb, the `NO_COLOR` / `TERM` / `COLORTERM` readings, stdout-is-TTY, the VT-enable result) that returns either `Plain` or a depth. This mirrors the plan's two first-match-wins lists (per design-system §Surface: cli → Colour decision order), so each rung and each depth cell is unit-testable on every OS without a console.
- A per-depth token table indexed by (token, depth), taking its values verbatim from design-system §Surface: cli → Tokens (platform-specific), with `reset` closing every span. A plain mode emits the same text with zero SGR bytes, so the words carry every state (per §Surface: cli → Platform-Specific Notes, "conhost without VT").
- Colour is a second cue only: every styled span is adjacent to or contains its word (`DIALOG` followed by the uncoloured kind word; `stale` in LIVE), per design-system §Brand Identity (the cli, human TTY expression row) and §Color Palette → Core Colors (Accent).
- Fixed-message errors: the catch-site line is exactly `error: internal error` on stderr, uncoloured, with no hint and no chain (per design-system §Surface: cli → Exit-code phraseology, row 1, and §Platform-Specific Notes, "Stack traces").

## Anti-patterns to avoid
- Colouring anything other than `DIALOG` (amber) and `stale` rows (dim), or colouring either without its word. No green `✓` / red `✗`, no emoji, no blue for `->` link output, no background (per design-system §Anti-Patterns → Per-Surface Bans → cli, and §Surface: cli → Tokens, the handoff blue and backgrounds rows).
- Emitting colour, glyphs or cursor control under `--json`, non-TTY, `NO_COLOR`, `TERM=dumb` or `viola run`. Giving `viola hook` / `viola mcp` any output path. Using a spinner, progress bar or live redraw (per design-system §Anti-Patterns → Per-Surface Bans → cli; §Brand Identity, the 0.0 expression row; §Motion → Hard limits).
- Mixing data and messages across streams, or styling or OSC-8-wrapping the `viola ui` launch line (per design-system §Anti-Patterns → Per-Surface Bans → cli).

## Contract bindings
- **design ↔ a11y (not colour alone, SC 1.4.1).** Colour must remain a second cue beside a printed word (per design-system §Anti-Patterns → Per-Surface Bans → cli, "never either without its word"). The a11y plan's use-of-colour mapping is the counterpart. No cli contrast pairing is measurable, because the terminal background belongs to the user.
- **design ↔ security-plan §Input Validation.** The C0/C1 `\x1B`-style escaping of upstream-origin fields is the security plan's floor. The `list`-row `\n`/`\t` escaping is design's stricter tier (per design-system §Surface: cli → Component Patterns 1, T5).
- **design ↔ security-plan (env-var reading).** The decision order and depth rules require reading `NO_COLOR`, `TERM` and `COLORTERM`, and the Width section later needs `COLUMNS`. This is in tension with security.md's "the only env vars outside `VIOLA_*` any `viola` build reads are the two test seams". Whether a named exception is needed, given that these variables can only turn colour off or down, is for P3 and P4 (scope premise).
- **design ↔ obs-plan §7.** The catch-site `error: internal error` phraseology (per design-system §Surface: cli → Exit-code phraseology) is the human face of obs-plan §7's per-role rule. `viola run` prints nothing (the decision order's rung 2) and matches obs-plan §7's `run` role.
- **design ↔ architecture (`--json` shapes and exit codes).** The `--json` document is `{"v":1,…}` on stdout with the typed exit code (per design-system §Surface: cli → Streams and the Exit-code phraseology table). The document shapes are owned by architecture.md §Standard Contracts / §Conventions.

## Acceptance criteria contributions
- (design) A unit test drives the pure colour decision over injected facts. Each of the seven rungs, taken alone with the others permissive, yields plain output (zero `\x1b` bytes), and the first matching rung wins when several hold. With none matching, `COLORTERM=truecolor|24bit` → truecolor, `TERM=*256color*` or Windows VT success → 256, and anything else → 16 (per design-system §Surface: cli → Colour decision order).
- (design) Each token's emitted SGR equals the design-system value for its depth (`attention` at truecolor / 256 / 16, plus `stale`, `callsign` and `reset`). Every styled span ends with `reset`. No depth can emit a blue foreground or any background SGR, and a stale-and-cocked row renders with `DIALOG` amber and not dim while the kind word and the rest of the row stay dim (per design-system §Surface: cli → Tokens (platform-specific)).
- (design) In plain mode the same rendered line keeps the ASCII words `[RB]`, `[  ]`, `[/ ]` and `->` and contains only ASCII (per design-system §Surface: cli → Colour decision order preamble and §Surface: cli → Width).
- (design) The escaping has two modes. Row mode renders C0/C1 and `\n`/`\t` as `\x1B`-style hex (`\x0A`, `\x09`), so the output is one line. Message mode renders C0/C1 as hex but keeps `\n` and `\t`. Neither mode strips a character (per design-system §Surface: cli → Component Patterns 1 and 3).
