# security extract

## Relevance
partial — the chunk builds the human-output layer that carries upstream text to a terminal (output-encoding floor), reads new non-`VIOLA_*` environment variables, and sets the stderr error shape. It adds no listener, channel method, secret or state file.

## Constraints
- **Escape C0/C1 controls in human-mode output of upstream-origin fields, keeping `\n` and `\t`.** Per security-plan §Bootstrap phases (`logging-redaction-wire`, the human-mode CLI bullet) and §Security Anti-Patterns → Logging (the RUSTSEC-2025-0055 class), `wait`/`last` human output and every `list` row field taken from `claude agents --json`, including unwrapped session names, must be escaped (§Threat Model, Decisions Log accepted risk on a planted `claude`; §Input Validation, the child-executable-resolution row). The plan sets the minimum set. The design-system's stricter `list`-row escaping of `\n`/`\t` (T5) is compatible with it. The plan's output rule names only "C0/C1". It does not say whether DEL (U+007F) or CR belong in the output escape set: the input rule names DEL separately, and the output rule keeps only `\n` and `\t`. P3/P4 settles this and says so explicitly.
- **Classify controls over decoded `char`s, never raw bytes.** Per §Security Anti-Patterns → Input (the raw-bytes ban) and §Input Validation (paste-text row), UTF-8 continuation bytes 0x80–0xBF are not C1. The plan states this for the input check, and the same hazard applies to an output escaper over `&str`. Whether a shared C0/C1/DEL predicate already exists beside `viola_core::validate_paste_text` that the escaper can reuse is a question for research.
- **Environment variables are not a configuration channel.** Per §Secret Management (Production) and §Security Anti-Patterns → Universal, no env var, `VIOLA_*` variable, flag or `config.json` key may switch off a control. `NO_COLOR`, `TERM` and `COLORTERM` (and `COLUMNS` later) may therefore only turn SGR decoration off or down, and must never reach the C0/C1 escaper or any other control. The plan's sentence names the only non-`VIOLA_*` variables as the two `fake-agent` test seams. Whether that sentence already admits recognised terminal conventions, or needs a named Decisions Log entry and amendment, is P3's question (scope premise "Env-var tension"). Security's floor holds either way: decoration only, never a control.
- **stderr carries no upstream text or NEVER-log floor value.** Per §Error Handling (Internal logging) and §Bootstrap phases (`logging-redaction-wire`), this covers context lines, refusals, `hint:` lines and `error: …` lines. The one-time `viola ui` launch line is the floor's only exception. The layer may route it to stderr, but must never log, echo or copy it anywhere else.
- **`--json` output carries codes and fixed messages only.** Per §Error Handling (External responses) and §Bootstrap phases (`logging-redaction-wire`, operational metadata), the one JSON document on stdout, refusals and `error` objects included, holds no anyhow chain, absolute path, upstream text, serde_path_to_error path or value, or internal type name.
- **The catch site's stderr is chain-free.** Per §Bootstrap phases (`error-sanitization-wire`) and §Security Anti-Patterns → Logging, a human-mode stderr chain never contains a serde_json or serde_path_to_error source. The full error goes only to `instances/<name>/diagnostics/`. This binds only if the chunk gives the catch site a reachable `cli` role (scope CARRY; P3 closes which).
- **`viola hook` never writes stderr and never exits non-zero.** Per §Security Anti-Patterns → Logging and §Error Handling, the layer must give `hook` (and `mcp`, whose stdout is MCP frames) no output path. The decision order's early `hook`/`mcp` → plain exit is not enough on its own: no print call may be reachable from those roles at all.

## Patterns to follow
- Escape rather than strip. §Input Validation (paste-text row) and §Security Anti-Patterns → Input ban silent stripping for input. On output, the matching pattern renders each control as visible `\xHH` text, so the human sees that a control was present and upstream text stays inert content (§Security Anti-Patterns → Code Patterns, R1).
- windows-sys is already the Win32 seam: §Input Validation (persistent-environment row, windows-sys 0.61.2 `Win32_System_Registry`). VT enabling through `SetConsoleMode` is a new feature on that pinned crate, not a new crate. On any failure the output falls back to plain, never to colour, so the failure can only remove decoration.
- Shared validation logic lives in `viola-core` so that every caller runs the same function (§Input Validation, Boundary). If the escaper's control classification is shared with `validate_paste_text`'s set, keep one definition.
- Fixed-message errors: `Display` impls and printed `error:` lines use fixed strings with no path or payload interpolated (§Error Handling, External responses; §Bootstrap phases `error-sanitization-wire`).

## Anti-patterns to avoid
- Printing `wait`/`last` output or `claude agents --json`-derived `list` fields to a terminal unescaped, including under non-TTY/`NO_COLOR`/`TERM=dumb`, where the colour decision is "plain" but the escaping must still run (§Security Anti-Patterns → Logging; §Bootstrap phases `logging-redaction-wire`). Also banned: running the control check over raw bytes (§Security Anti-Patterns → Input).
- Letting a newly read env var (`NO_COLOR`, `TERM`, `COLORTERM`) or a flag widen output, re-enable something a control turned off, or skip escaping (§Security Anti-Patterns → Universal).
- Writing an anyhow chain with a serde source, an absolute path or upstream text to stderr or `--json` output, and writing anything to stderr from `viola hook` (§Security Anti-Patterns → Logging).

## Contract bindings
- **security ↔ design-system:** the output escape set (security floor: C0/C1, keep `\n`/`\t`) must agree with design-system §Streams and component 1 (`wait`/`last` keep `\n`/`\t`), and with the ratified T5 `list`-row rule (also escapes `\n`/`\t`). The design rule may be stricter than the floor, never looser.
- **security ↔ architecture:** the env-var tension. Architecture Cross-cutting Patterns (Config management) and security-plan §Secret Management both state the env-var rule. Admitting `NO_COLOR`/`TERM`/`COLORTERM` may require amending both together, plus a Decisions Log entry (§Security Anti-Patterns → Universal gates further env inputs on an entry).
- **security ↔ obs:** the catch-site CARRY is `error: internal error` on stderr with the chain in the detail file only (obs-plan §7). It rests on the NEVER-log floor (§Bootstrap phases `logging-redaction-wire`), which the obs logger implements. The obs-plan §9 secret-scan canary classes (`?t=`, the GUI token) are the backstop if any test drives the launch-line path.
- **security ↔ tests:** §Input Validation's "Parser surfaces" list names `validate_paste_text`, but not the new output escaper. Whether it gets fuzz or property coverage is for tests to decide.

## Acceptance criteria contributions
- The escaper runs over decoded `char`s. In message mode it renders every C0 control except `\n`/`\t` (ESC U+001B included) and every C1 control (CSI U+009B included) as `\xHH` text, and in `list`-row mode it also escapes `\n`/`\t`. Multi-byte UTF-8 (for example `é`, `€`, whose continuation bytes fall in 0x80–0xBF) passes through unchanged, and nothing is stripped (a unit table proves each case). (per security-plan §Bootstrap phases `logging-redaction-wire`; §Security Anti-Patterns → Input / → Logging)
- Escaping holds in every human mode: a test drives the same upstream-origin string through the TTY, non-TTY, `NO_COLOR`, `TERM=dumb` and failed-VT decisions and gets identical escaped text each time. Only SGR bytes differ, and no env reading changes the escaper's output. (per security-plan §Security Anti-Patterns → Universal / → Logging)
- `viola hook` and `viola mcp` have no path into the output layer, checked by grep or a code-graph query from those roles. The existing hook fail-open tests stay green (exit 0, empty stdout and stderr). (per security-plan §Security Anti-Patterns → Logging; §Error Handling)
- `cargo deny check` and `bash scripts/deny-probes.sh` stay green, and `Cargo.lock` gains no new crate: at most a windows-sys feature on the pinned crate. If the catch-site CARRY binds, its stderr is exactly `error: internal error`, with no chain, path or serde source. (per security-plan §Dependency Security; §Bootstrap phases `error-sanitization-wire`)
