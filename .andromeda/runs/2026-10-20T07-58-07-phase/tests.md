## Constraints
- The `[profile.mutants]` kill lines are a contract, not a free knob: the default 10 s kill, then three overrides in first-match order (`test(/verify_window_/)` 45 s first, ahead of `package(viola-e2e)` 30 s and `test(/send_window_/)`). The order is pinned by `mutants_verify_window_override_stands_before_the_harness_package_override` and the deadlines by `test_deadlines_sit_below_the_nextest_kill_line` (`tests/contract_lints.rs`). Every in-test wait a root-package mutant can reach must stay below cargo-mutants' ~20 s auto-timeout floor, or a hang grades Timeout instead of caught. Item (1)'s override or faster replay, and item (2)'s headroom under 45 s, have to hold all of this (per test-plan §3 Bootstrap phases (`test-runner-install`, `[profile.mutants]`)).
- `[profile.ci]`'s verify-driven `binary(…)` line (a 20 s kill) and the `verify_window_` class (a 60 s kill) are on that same contract, and so is its rule that a slow case joins a class by carrying the class's name. `contract_fake_agent_drift` and `cli_send` sit on the 20 s line, and `cli_budget` too. Any rename or new override has to keep both profiles coherent (per test-plan §3 Bootstrap phases (`test-runner-install`, `[profile.ci]`)).
- Zero flakiness: `retries = 0`, no retry budget and no `#[ignore]` parking. A test that is slow or reads red under a kill is fixed at its root cause inside this chunk, never by raising a retry count (per test-plan §10 Zero-flakiness budget).
- Mutation scope: this chunk runs no mutation (the scope's standing constraint). The plan's mutation verdict rules are what the next boundary reads: `missed == 0` after host exclusion, `timeout == 0`, `unviable <= caught`. A mutant this host cannot reach is recorded as "not measured here; owed to {route entry}" by coordinate, never as "equivalent" and never counted caught. Items (3) and (4) (viola-pty's 78 unviable against 11 caught, the 16 survivors) are worded against these rules (per test-plan §10 Mutation gate).
- Coverage gates stay at lines 85 / functions 95 / regions 80 per OS, and `COVERAGE_IGNORE` (`viola-fake-agent|crates[/\\]viola-e2e|tests[/\\]support|fuzz[/\\]`) is not widened. Item (5)'s moves (`ledger.rs`'s test module, the `typed.rs` / `board.rs` splits) must not move product code under an ignored path (per test-plan §10 Coverage thresholds / Stack adjustments).
- Item (8)'s cause finding has to keep to the plan's evidence discipline. The plan holds one measured mechanism: an instrumented child killed during its exit-time profile write leaves a short profile that `llvm-profdata` refuses. Earlier corrupt-header reds are "recorded, not established". A claimed cause needs a two-sided reading, and the witness `scripts/profraw-census.sh` stays a dev-host script with no CI, `pre-push` or harness hook (per test-plan §10 Stack adjustments).
- `pre-push`'s stages (`host` · `tools` · `linux-tests`), `reason`s and `detail`s are closed enums. A new value needs a Decisions Log entry. Examples: a `/tmp` headroom stage or reason for item (9), or a coverage-merge reason for item (8) (per test-plan §3 5-command implementation (Closed enums)).

## Patterns to follow
- A slow case is put under a kill line by its class name, as `verify_window_boot_with_an_unknown_cli_version_is_verify_failed` was renamed into the `verify_window_` class with its body unchanged. Each change is proved by a planted-hang control (TIMEOUT under `mutants`, PASS under the default profile) and a baseline count with no TIMEOUT (per test-plan §3 Bootstrap phases (`test-runner-install`, `[profile.mutants]`)).
- A survivor is disposed in a ledger (`evidence/survivors.ndjson`) by a nextest case in the package that owns the mutated file. Where needed this follows a behaviour-preserving restatement that makes the site reachable. Each case is shown red under its hand-applied mutant and green when restored, with no mutation run made. That is the precedent for item (4), and it also covers the `viola-mcp` three that only `crates/viola-e2e/tests/mcp_tools.rs` kills (per test-plan §10 Mutation gate).
- The MCP E2E driver is an rmcp `client`-only test that spawns and owns the `viola mcp` child, closes its stdin and awaits its exit. It never uses `TokioChildProcess`, which left a truncated profile. Item (7)'s replay case lives beside `mcp_tools_list_is_exactly_the_five_tools_and_list_matches_the_cli` in `crates/viola-e2e/tests/mcp_tools.rs` (per test-plan §6 Drivers per surface (ipc-internal MCP stdio)).
- Root support helpers have one home each in `tests/support/`, and no root test file defines its own copy. Item (6)'s `dialogless_home` change stays inside `tests/support/home.rs` on the `home → fake_agent_path → stamped_home → booted_wrapper` chain (per test-plan §2 Test directory + naming conventions; §3 Test data bootstrap (Mechanism)).
- Root homes sit under `target/e2e-home`. On the Linux dev host that is a link to the owner-only tmpfs `/tmp/viola-e2e-home-<uid>`, and each home pins a debug `viola`. Mutation runs take `TMPDIR=<repo parent>/viola-mutants-scratch` because `/tmp` is a 32 GB `usrquota` tmpfs. These are the facts item (9)'s headroom read rests on (per test-plan §3 Test data bootstrap (Mechanism); §10 Mutation gate).

## Anti-patterns to avoid
- Never import the product's own ledger rows as the test oracle: expected values are literals in the test. Item (6) asks `dialogless_home` to derive its summary from `LedgerRow::relied()`, which conflicts with this ban, and `contract_ledger_probes`' `ROW_IDS` and `cli_verify`'s `STEPS_PASS` stay literals. Two questions follow. Research must answer whether a fixture helper's precondition line counts as an oracle. P4 must settle whether this needs a ruling or a Decisions Log entry (per test-plan §11 Unit).
- Never use production data in tests. Fixtures come only from `viola verify` probe text, scrubbed and walked by `tests/contract_fixture_hygiene.rs`. Item (7)'s "recorded live `tools/list` exchange" is not verify probe text. Its source, scrub and hygiene-walk coverage must be planned, and so must its placement (outside `fixtures/claude/<ver>/`, where every dir is on exactly one stamped or drift-only list) (per test-plan §11 Test Data; §7 Fixture hygiene).
- Never treat a Linux-only local run as proof for Windows: item (3)'s Windows baselines (`wipe_scratch_…` `Err(Writable)`, `path6_the_boundaries_and_the_window_word` at the 10 s kill) stay owed to the next boundary's Windows leg, whatever the local proof reads (per test-plan §11 Test Strategy).
