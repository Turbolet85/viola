## Patterns to follow
- If the board split changes where its cases live, the masters' file citations follow by wrap cascade, not by an implement edit. §4 P6, §6 and §8 cite those cases in `src/human/board.rs`, `tests/cli_list.rs` and `tests/cross_list_rows.rs` by function name (per a11y-plan §4 Must-be-accessible path scenarios).
- A re-scoped `.claude/rules/a11y.md` keeps its body's terminal rules (keyboard, visual, harness), names `.andromeda/a11y-plan.md` §3 and §4–§8 as its authority, and states no web rule. The frontend is deferred to 0.2.0 with its technology not chosen (per a11y-plan §5 Keyboard Navigation; per a11y-plan §6 Visual Design Verification).
- Output-discipline and boundary cases run as ordinary nextest cases inside the existing suites, CI's `coverage` suite under `gate --require coverage,doctest` included. A moved or sped-up case stays in them (per a11y-plan §9 CI Integration).

## Anti-patterns to avoid
- Never add a retry to the nextest `mutants` profile override (item 1, 2 or 3) to get past the kill. The zero-flakiness rule is `retries: 0`, and a retry-once policy masks real failures (per a11y-plan §11 A11y Anti-Patterns, SLO; per a11y-plan §10 SLO Invariants & A11y Budgets).
- Never add a `suite` value (such as `a11y`) or a separate a11y driver outside `scripts/agent-run.* run` while re-scoping the harness or the rule files (per a11y-plan §11 A11y Anti-Patterns, CI).
- Never let the item (10) rewording claim WCAG conformance for the cli or the `viola run` TUI. The tier's cases stand in for SC 1.3.2 / 1.4.1 / 3.3.1 only (per a11y-plan §11 A11y Anti-Patterns, Strategy).
