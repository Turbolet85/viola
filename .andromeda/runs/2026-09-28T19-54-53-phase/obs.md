## Constraints
- The §9 Pipeline integration "Mutation" row puts obs-code mutation under the per-leg `mutants-verdict-<os>.json`, the `mutants-verdict` job's `gate --require mutants --mutants-legs …` union and the local `viola-harness pre-push` union. All of that is what this chunk removes. obs-plan is a spec master, so phase does not amend it: the plan lists the row's rewrite (mutation's home becomes the epoch-boundary audit) as an expected wrap amendment, next to test-plan §3/§10 (per obs-plan §9 Pipeline integration).
- §10 "Build / deploy failure conditions" includes "A surviving cargo-mutants mutant in obs code". With the per-chunk and CI gates gone, this condition is judged at the epoch-boundary audit, not per build. The plan lists it as an expected wrap amendment. Obs code (`obs_event!` call sites, `MillisUtc`, the panic hook, the TraceLayer closures) stays under cargo-mutants the way product code does, only at the audit (per obs-plan §10 Build / deploy failure conditions; §9 Pipeline integration).
- The ci.yml edit must leave the obs gate chain as it is. §9 requires G2 and G4 `if: always()` after the last test step. It also requires the secret scan `id: secret-scan` to run `if: always()` and the `diag-<os>` / `harness-<os>` / `junit-<os>` uploads to stay gated on `steps.secret-scan.outcome == 'success'`, with `secret-scan-<os>` uploaded on a scan failure. The same holds in the `perf` job. Any `needs:` or ordering edge that pointed at a removed mutation job gets removed, and nothing gets rerouted around these steps (per obs-plan §9 Step order and conditions; §11 CI).
- §8 item 6 exempts exactly one path from the secret scan and the `harness-<os>` upload: `target/agent-run/chunk.diff`, described as "the mutation leg's diff". Research must answer whether anything the chunk keeps still writes that file (the `run --mutants` arm, or only the removed CI and pre-push legs). If nothing does, the plan may drop the exemption, which narrows it. It may never widen it or re-point it to another path (per obs-plan §8 PII Scrubbing item 6; §9 Telemetry artifact handling, `harness-<os>` row).
- The kept `run --mutants` arm stays bound by the §8 item 6 content rules. `mutants.out/` and `target/run-archive/<n>/` are never uploaded. The host mutation scratch `<repo parent>/viola-mutants-scratch/` is never printed, and documents carry its size only as a byte count (`scratch_bytes`). Removing the CI `mutants-verdict-<os>.json` uploads retires their "unscanned, admissible by content" clause, which is a wrap amendment (per obs-plan §8 PII Scrubbing item 6, Unscanned uploads).
- §8 item 6 requires the local `viola-harness pre-push` document to carry no absolute path. Its `cache` section's `windows_scratch_bytes` / `windows_scratch_bytes_after` are byte counts of the host mutation scratch, asserted by `pre_push_document_carries_no_absolute_path`. When the mutation leg leaves pre-push, any fields that only existed for it may go. The no-absolute-path assertion over the remaining document must stay (per obs-plan §8 PII Scrubbing item 6).
- Every CI telemetry verdict is a machine assertion that sets an exit code. Removing the mutation gate must not leave behind a human-reviewed step, a `continue-on-error` or an advisory-only mutation leg in CI (per obs-plan §11 CI; §11 Universal).

## Patterns to follow
- Scan-gated upload shape: `if: always() && steps.secret-scan.outcome == 'success'` for artifacts and `if: always() && steps.secret-scan.outcome == 'failure'` for the hit report. Copy it wherever a surviving step is touched, and never use a bare `always()` / `failure()` (per obs-plan §9 Telemetry artifact handling).
- A host path becomes a byte count (`scratch_bytes`, `windows_scratch_bytes`), never a printed path, and a unit test asserts no absolute path in the harness document (per obs-plan §8 PII Scrubbing item 6).
- Gates are fail-closed, exit-code-judged bash steps (G1–G4 in §9). Any mutation-related gate command or probe left in `scripts/` keeps a fail-closed exit rather than becoming a silent no-op (per obs-plan §9 Gate commands).

## Anti-patterns to avoid
- NEVER lose the failing job's `diagnostics/`, and NEVER upload before the secret scan passes. A workflow edit that reorders or drops an `if:` on G2, G4, the scan or the gated uploads breaks this (per obs-plan §11 CI).
- NEVER widen the secret scan's exemption set, for example by moving the `chunk.diff` skip to a new path or directory while retiring the mutation leg (per obs-plan §8 PII Scrubbing item 6; §11 PII Scrubbing).
- NEVER use human-review-gated analysis as a CI verdict (per obs-plan §11 CI).

## Contract bindings
- obs §9 Pipeline integration "Mutation" row ↔ test-plan §10 Mutation gate and test-plan §3 pre-push: the three change together as one set of wrap amendments that name the epoch-boundary audit as mutation's home.
- obs §8 item 6 secret-scan scope and `chunk.diff` exemption ↔ security-plan (NEVER-log floor, secret scan) ↔ tests (the scan body and canary are tests-owned): a change to the exemption set crosses all three.
- obs §8 item 6 pre-push document path rule ↔ tests harness unit test `pre_push_document_carries_no_absolute_path` (tests-owned body, obs-owned invariant).
- obs §10 zero-unlogged-panics / G2 ↔ the `test` job, which keeps running the harness mutants-arm tests. Any home those tests create stays under `target/e2e-home/` so G2, G4 and the scan cover it (§9 Integration tests row). Whether the mutants-arm tests create any viola home at all is research's question.
