## Constraints
- The kept `run --mutants` arm keeps its verdict contract: counts come from the run's own `mutants.out/outcomes.json` (the host mutation scratch on Windows), `missed == 0 && timeout == 0 && unviable <= caught`; exit codes 1/4/5/6/70 are `mutants-exit-<code>`; the `no-rust-delta` / `test-only-rust-delta` / `scoped` / `counted` classification holds. Nothing in the retirement may weaken the arm `/andromeda-code-audit` will call (per test-plan §3 `run` step 4 Classification / Verdict, §3 Exit code semantics, §11 Quality "NEVER trust the cargo-mutants exit code alone").
- Harness commands keep the 5-command discipline: one JSON document on stdout, exit 0/1/2. A flag or selector that is retired (`gate --mutants-legs`, `run --leg`, if P3 retires them) must fail as a usage error, never pass vacuously. Closed enums shrink only through a Decisions Log entry: `invalid-leg`, `scoped-leg`, the leg-verdict `outcome` set, the `pre-push` stages `linux-leg` / `windows-leg` / `union` and reasons `verdict-missing` / `base-mismatch` (per test-plan §3 Exit codes, §3 Closed enums "A new value needs a Decisions Log entry").
- `pre-push`'s remaining stages (`host · tools · sync · cache · linux-tests · vm-release · windows-tests`) keep their order, fail-fast rule and codes/counts-only document. `tools` keeps checking cargo-mutants at the §9 `test`-job pin only if the kept arm still needs it on the distro; whether it does is research's question (per test-plan §3 `pre-push`).
- CI: every job that runs a harness suite still ends with `viola-harness gate --require <that job's suites>` (`coverage,doctest,playwright` in `test`, `perf`, `fuzz-replay`, `nextest-unit`); `lint`, `supply-chain` and `release` stay plain exit-code jobs; all actions stay SHA-pinned under `permissions: {}`. The `test` job's `tool:` line is the single version source that `scripts/wsl-provision.sh` parses, so keeping `cargo-mutants@27.1.0` on it keeps provisioning inputs unchanged (per test-plan §9 pipeline table and tool-install paragraph, §3 Bootstrap `quality-gate-config-emit` / `ci-tool-install`).
- The macOS 73 s CARRY is a timing finding under the zero-flakiness budget: fix it at its cause or measure and record it; never raise the kill line (the `[profile.ci]` `slow-timeout = { period = "30s", terminate-after = 4 }` 120 s bound) or add a retry to make it pass (per test-plan §10 Zero-flakiness budget, §3 Bootstrap `test-runner-install`, §11 CI "NEVER set nextest `retries` above 0").
- The harness's own tests of the kept arm (`run_mutants_passes_when_the_change_is_tested`, `run_mutants_reports_survivors_of_an_untested_change`, the scoped/classification cases) keep running in the per-OS `test` job; tests of removed code (the union judge, `cfg_legs`) go with that code, never parked under `#[ignore]` (per test-plan §10 Zero-flakiness budget "`#[ignore]` … not allowed as a parking place", §9 E2E/Coverage rows).
- Spec masters are amended at wrap, not in phase: the mutation gate is named well beyond §3 and §10 — §1 harness `run` step 4 and the mutation trigger ("scoped to each chunk diff … surviving mutants are red"), §2 Mutation row, §3 `gate` mutants breach / union bullet / CI paragraph and `pre-push`, §3 Bootstrap `quality-gate-config-emit` ("zero missed or timed-out mutants"), §9 Coverage-report / Mutation / Quality-gates rows, Matrix builds, Test report format (`chunk.diff` exclusion, `mutants-verdict-<os>.json` upload), Build failure conditions, §10 Mutation gate and Build failure conditions, §11 CI ("a fixed two-leg OS matrix plus one `mutants-verdict` job, by design"), plus a new §12 Decisions Log entry recording the founder ruling (per test-plan §12 Decisions Log convention).

## Patterns to follow
- Measure before fixing, and cite the run: every prior mutation change carries a CI run id or a named evidence file (e.g. the `unviable-exceeds-caught` threshold, the stale-test-binary red) — the 73 s cause hypothesis (outer `cargo llvm-cov nextest` jobserver / coverage `RUSTFLAGS` inherited by the nested cargo) is closed the same way (per test-plan §10 Mutation gate witness style, §12 entries' "Witness" lines).
- Literal oracles in harness tests: expected verdict values, codes and counts written as literals in the test, never imported from the harness (per test-plan §11 Unit "NEVER import the product's own … as the test oracle"; §12 `run_mutants_mixed_src_and_test_delta_without_outcomes_stays_outcomes_missing`).
- Isolation of nested cargo: the kept arm's tests run their nested cargo on a private `CARGO_HOME` and the mutation run's own `CARGO_TARGET_DIR=target/mutants`, so they never relink a running harness exe (per test-plan §3 `run` step 4 Command).
- A per-chunk gate change lands as one §12 entry with Decision / Rationale / Impact (section list) / By (per test-plan §12 Decisions Log).

## Anti-patterns to avoid
- Never read the retirement as license to "skip a gate just this once" or to lower another bar: coverage thresholds, `--ignore-filename-regex`, `retries = 0` and every non-mutation gate stay byte-for-byte (per test-plan §11 Quality, §11 CI).
- Never fix the 73 s by raising the 120 s kill, trimming the test, or adding a retry budget (per test-plan §10 Zero-flakiness budget, §11 Quality "NEVER add retry-once policies").
- Never let the kept arm trust cargo-mutants' exit code alone or report a zero-count run as a pass (per test-plan §11 Quality, §3 `run` step 4 Verdict).
