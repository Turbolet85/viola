## Patches

### Patch 1: Fix the instance source per role and resolve the `ui` port before its file is opened
**Reason:** Downstream Readiness / Obs Scope Faithfulness. Step 3 gives no per-role instance rule, so a nested `viola run B` could log as its parent instance. Step 4 opens `ui-<port>.ndjson` before step 5 parses the `config.json` that can hold the port.
**Old:**
```
  3. Resolve the home (`--home` → grandparent of `VIOLA_DIR` → `~/.viola/`), the instance (`VIOLA_NAME` or an explicit `ViolaName` argument) and the role (`run` / `hook` / `mcp` / `ui` / `cli`).
```
**New:**
```
  3. Resolve the home (`--home` → grandparent of `VIOLA_DIR` → `~/.viola/`), the instance and the role (`run` / `hook` / `mcp` / `ui` / `cli`). The instance source is fixed per role:
     - `run`: its own `ViolaName` argument. An inherited `VIOLA_NAME` (a `viola run` started from inside a wrapped session) never overrides it, so a wrapper never writes into another instance's `run-<name>.ndjson`;
     - `hook` and `mcp`: `VIOLA_NAME` only;
     - `cli`: the caller's `VIOLA_NAME`, then the target argument (Trace context propagation);
     - `ui`: no instance. Its file name needs `<port>`, and the GUI port can come from `config.json` (security Data Classifications, config values). For `ui` only, the step-5 `config.json` parse therefore runs here and its result is reused at step 5. `<port>` resolves flag → `config.json` → `47319` (arch precedence flags > config > defaults). A `ui` panic during that parse falls in the §7 pre-init window (D-29).
```

### Patch 2: Define when the detail file is opened
**Reason:** Downstream Readiness. Step 4 opens only the role file, and the panic hook writes to "the pre-opened `Arc<File>`". Nothing says when `detail-<process>.ndjson` is opened or what happens if that open fails. The `hook` "exactly one log `open`" claim depends on the answer.
**Old:**
```
If the open fails, the writer becomes `std::io::sink` (or stderr for `mcp` only, D-09).
```
**New:**
```
If the open fails, the writer becomes `std::io::sink` (or stderr for `mcp` only, D-09). The instance detail file `<home>/instances/<name>/diagnostics/detail-<process>.ndjson` is **not** opened here. It is opened lazily, with the same append / 0600 / 0700 rules, by the first content-bearing record (chain, drift report), and the panic hook opens it itself when it is still closed. A failed detail open drops only the detail line, never the home-level line, and writes nothing to stderr. The error-free `hook` path therefore keeps exactly one log `open` (D-29).
```

### Patch 3: Update the §7 pre-init window to match the `ui` config parse
**Reason:** Downstream Readiness / cross-section consistency with Patch 1. The `ui` `config.json` parse now runs before step 4.
**Old:**
```
- Before step 4 of init, no file exists, so the panic hook writes nothing. This window contains only clap parsing and home resolution.
```
**New:**
```
- Before step 4 of init, no file exists, so the panic hook writes nothing. This window contains only clap parsing and home resolution, plus the `config.json` parse for `ui`, which needs `<port>` to name its file (§3 init step 3, D-29).
```

**New:**

### Patch 5: Run G2 even when a test step fails
**Reason:** Performance Budget & SLO Discipline. Only G4 is `if: always()`, so a failed test step skips G2. §10 measures panics only through G2's exit code, which leaves them unmeasured on the failing runs.
**Old:**
```
1. Integration and E2E tests (every viola home under `target/e2e-home/`), then G2, then G4 (`if: always()`).
```
**New:**
```
1. Integration and E2E tests (every viola home under `target/e2e-home/`), then G2 and G4, **both** `if: always()`. A failed test step must not skip G2: failing runs are where panic lines are most likely, and §10 measures panics only through G2's exit code (D-29).
```

### Patch 6: Extend the concurrent-writer rule to colliding `run` / `ui` files
**Reason:** Log Format Alignment to Tests. A second `viola run <name>` or `viola ui` on a live name or port opens the live process's file at init step 4 and appends its lines there (Scenario 1 exit-1 causes). The shared-file list omits both files.
**Old:**
```
Four kinds of file have concurrent writers in separate processes, and the same rule covers all of them:
  - `hook-<name>.ndjson`, shared by hook processes;
  - `mcp.ndjson`, shared by one `viola mcp` per Claude session;
  - `cli-<name>.ndjson`, shared by concurrent short-lived verbs;
```
**New:**
```
Every role file can have concurrent writers in separate processes, and the same rule covers all of them:
  - `hook-<name>.ndjson`, shared by hook processes;
  - `mcp.ndjson`, shared by one `viola mcp` per Claude session;
  - `cli-<name>.ndjson`, shared by concurrent short-lived verbs;
  - `run-<name>.ndjson` and `ui-<port>.ndjson`, briefly: a second `viola run <name>` or `viola ui` on a live name or port opens the same file at init step 4. It appends its `process-start` and its exit-1 `process-exit` (for example `detail:"already-live"`, Scenario 1) next to the live process's lines. The concurrent-append check covers this collision path too (D-29);
```
