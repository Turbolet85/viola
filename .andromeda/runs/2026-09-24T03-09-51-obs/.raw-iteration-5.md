## Patches

### Patch 1: Add G4 schema-conformance gate over real CI output
**Reason:** Dimension 1/4. §10 counts schema-conformance failures as a build failure and budget item, but no §9 gate measures them over real process output. That breaks §11 SLO "NEVER define a budget without an exit-code-setting assertion".
**Old:**
```
  - Scope is the home-level role files only. `detail-*.ndjson` repeats the panic line and is excluded (§10).
```
**New:**
```
  - Scope is the home-level role files only. `detail-*.ndjson` repeats the panic line and is excluded (§10).
- **G4, schema conformance.** §10 counts schema-conformance failures as a build failure. G1–G3 do not measure them, and the Unit tests row checks only in-memory lines, so G4 checks real process output.
  - Scope: every line in the G2 file scope is checked against `schemas/diag-line.v1.json`, and every `instances/*/diagnostics/detail-*.ndjson` line against `schemas/diag-detail.v1.json` (§8).
  - It runs as its own step, `id: schema-conformance`, `if: always()` after the last test step. It exits non-zero on any failing line and prints `file`, line number and the failing schema keyword, never the line's content (detail lines carry the canary). The check body and the JSON Schema validator crate are tests-owned; obs owns both schemas.
  - A line that is not JSON is skipped and counted, as in G2, because chaos cases kill writers mid-line and a restarted writer appends after the torn line. Interleaved writes are caught by the concurrent-append check (§3 Logging stack), not by G4.
```

**New:**

Their viola homes must live under `target/e2e-home/` (the directory layout is tests-owned), so G2, G4, the secret scan and the `diag-<os>` upload cover them. A `hook` panic exits 0, so a home outside that root would hide it. perf: hyperfine JSON with `max` assertions | uploaded artifacts + G2 / G4 + budget assertion exit codes |
| E2E tests | `agent-run logs` / `status`; Playwright DOM-attribute reads; zero-`event:"panic"` gate G2 and schema gate G4 (below) | uploaded artifacts + gate exit codes |

### Patch 4: Place the config.json read in init order
**Reason:** Dimension 1. Step 5 uses `cfg.diagnostics_level`, but no step reads `config.json`. `parse-rejected{parser:"config-json"}` (D-05) cannot be emitted while the config is parsed, because no subscriber exists yet. The `hook` anchor also leaves out the config read.
**Old:**
```
  5. Install the subscriber with an explicit writer (below).
  6. `obs_event!(ProcessStart, …)`.

  Per-role anchors:
  - `run`: steps 1–6 finish **before** `run.collision_check`, so exit-1 causes are logged. The panic hook is live before `pty.spawn`.
  - `ui`: before `axum::serve` binds `127.0.0.1:<port>`.
  - `mcp`: before the rmcp 3.4.1 stdio transport starts.
  - `hook`: exactly one `open` plus appends, which fits the `max < 1.0 s` gate.
```
**New:**
```
  5. Parse `<home>/config.json` once for the process. `diagnostics_level` falls back to `"info"` when the file is missing or unreadable or the value is unknown. Then install the subscriber with an explicit writer (below). No subscriber exists during the parse, so its skipped-key count and failure `detail` are held in memory. A panic during the parse is still logged, because the role file exists after step 4.
  6. `obs_event!(ProcessStart, …)`, then `parse-rejected{parser:"config-json", detail, count}` if the step-5 parse failed or skipped keys (D-28).

  Per-role anchors:
  - `run`: steps 1–6 finish **before** `run.collision_check`, so exit-1 causes are logged. The panic hook is live before `pty.spawn`.
  - `ui`: before `axum::serve` binds `127.0.0.1:<port>`.
  - `mcp`: before the rmcp 3.4.1 stdio transport starts.
  - `hook`: one `config.json` read plus exactly one log `open`, then appends, which fits the `max < 1.0 s` gate.
```

### Patch 5: Pre-clap role detection must skip global flags
**Reason:** Dimension 4. With the global `--home` flag, `argv[1]` is `--home`, so a `hook` is misread as `cli` and a pre-init panic exits 1. That breaks the Hook contract and §10's "`hook` still exits 0".
**Old:**
```
The role is taken from `argv[1]` before clap runs, so a pre-init panic in a `hook` process still exits 0.
```
**New:**
```
The role is taken from argv before clap runs: the first argument that is neither a global flag nor a flag's value (for example `--home <path>`) and that names a role subcommand (`run`, `hook`, `mcp`, `ui`; any other verb is `cli`). So `viola --home <dir> hook stop` is still a `hook`, and a pre-init panic in it still exits 0. Reading `argv[1]` alone would misclassify that form as `cli` and exit 1 (D-28).
```

### Patch 6: Extend the multi-writer append rule to shared detail files
**Reason:** Dimension 5. `detail-hook.ndjson`, `detail-cli.ndjson` and `detail-mcp.ndjson` are appended by the same concurrent processes as their home-level files. Their lines are content-bearing and can exceed 4 KiB, and neither the append rule nor the concurrent-append check covers them.
**Old:**
```
Three files have concurrent writers in separate processes, and the same rule covers all three:
  - `hook-<name>.ndjson`, shared by hook processes;
  - `mcp.ndjson`, shared by one `viola mcp` per Claude session;
  - `cli-<name>.ndjson`, shared by concurrent short-lived verbs.
```
**New:**
```
Four kinds of file have concurrent writers in separate processes, and the same rule covers all of them:
  - `hook-<name>.ndjson`, shared by hook processes;
  - `mcp.ndjson`, shared by one `viola mcp` per Claude session;
  - `cli-<name>.ndjson`, shared by concurrent short-lived verbs;
  - the instance detail files `detail-hook.ndjson`, `detail-cli.ndjson` and `detail-mcp.ndjson`, shared by those same processes. Their lines (chains, drift reports, one-line backtraces) are not codes-only and can exceed 4 KiB, so the size argument below does not apply to them. They rely only on the single `write_all` and the torn-line tolerance, and the concurrent-append check must include a detail line larger than 4 KiB (D-28).
```

### Patch 7: Define `corr` for sends refused before `send-issued`
**Reason:** Dimension 2/5. The arch `send` refusal result carries no `cursor`, and tests Path 2 logs the cursor only once the send is accepted. Yet Scenarios 2, 5 and 6 log `send-refused{corr:<cursor>}` for pre-acceptance refusals (`human-typing`, `budget-paused`, `input-not-ready`, `turn-running`). The send join in the cross-surface-trace-propagation trigger (target `instance` + `corr`) has no defined value for them.
**Old:**
```
  - `from` is logged with the constant companion `from_trust:"self-reported"` and is never treated as identity.
```
**New:**
```
  - **Send cursor on early refusals.** The arch `send` result returns `cursor` only on success or `unconfirmable`; a refusal result carries `refusal` + `detail` only. For a send refused before `send-issued` (`human-typing`, `budget-paused`, `input-not-ready`, `turn-running`), the wrapper's `send-refused` carries `corr` = the target's `events.ndjson` end offset at the moment of refusal. This value is a log join key only. It is never returned to the caller and is not a `wait after` value. After `send-issued`, every `send-*` line carries the issued cursor. The caller reaches either case through `(conn, corr)` on its `channel-*` lines (D-28).
  - `from` is logged with the constant companion `from_trust:"self-reported"` and is never treated as identity.
```
