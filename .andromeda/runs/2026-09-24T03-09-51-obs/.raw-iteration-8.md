**1. Downstream Readiness**
- The G1, G2 and G3 commands, the step order, the upload gates, crate ownership, the `disallowed-macros` exemption, route position and ownership, and the a11y boundary were all fixed in earlier iterations. I found no new command bugs in G1–G4 or the perf `jq -e` checks.
- **New finding (setup-project wiring):** the plan never says how detail-file lines are emitted. The §3 init sketch installs one subscriber with one writer (`diag_writer`), which holds the home-level role file only. If an `obs_event!` carrying `chain` or `drift_report` goes through that subscriber, it lands in a file that is supposed to hold codes only. The plan needs a boundary rule saying detail lines bypass the subscriber and use a writer like the panic hook's. **Patch needed.**

**2. Obs Scope Faithfulness**
- The join key `(conn, corr)`, the `cli` instance precedence, the D-16 override, the `<area>` list, ledger and verb coverage, and the Section 1 pointer are all in place.
- **New finding (cross-surface-trace-propagation):** nothing joins the send lines to the channel lines.
  - Wrapper `send-issued`/`send-confirmed`/`send-refused` lines carry only `corr` = cursor. Their §6 catalog row has no `conn` and no JSON-RPC id.
  - `channel-*` lines carry `corr` = JSON-RPC `id` and no cursor.
  - So the canonical query's "channel-* lines of the same send join on (conn, corr)" cannot be reached from a matched send line. The §3 claim "The caller reaches either case through `(conn, corr)`" is false.
  - D-28 made this worse: when a send is refused, its `corr` is the end offset at that moment. Back-to-back refusals, or a later issued send, can share that value, so `corr==412` mixes separate sends.
  - **Patches needed** in three places: the §6 catalog, §3 propagation and the §3 canonical query.
- Trigger map, multi-platform-exporter-compat row: it cites only §3 Log file location and §9. Append atomicity is in §3 Logging stack, and the named-pipe vs socket and ConPTY vs openpty differences are in §4 Scenario 1 (`endpoint_kind`, `pty_backend`). **Patch needed.**

### Patch 1: Add the send→channel link fields to the send-* catalog row

### Patch 2: Correct the false caller-reach claim and define the send↔channel join
**Reason:** Dimension 2. `(conn, corr)` on channel lines cannot reach cursor-keyed send lines, and D-28's end-offset `corr` is not unique.
**Old:**
```
After `send-issued`, every `send-*` line carries the issued cursor. The caller reaches either case through `(conn, corr)` on its `channel-*` lines (D-28).
```
**New:**
```
After `send-issued`, every `send-*` line carries the issued cursor. The cursor alone is not a unique send key. Refusals at an unchanged end offset can share it, and a later issued send can reuse it.
  - **Send ↔ channel link (D-30).** Every wrapper `send-*` line also carries `conn` (or `srv_conn` for an older peer) and `rpc_id`, the JSON-RPC `id` of the `send` request it answers. The pair `(conn, rpc_id)` on a send line equals `(conn, corr)` on that call's `channel-request` / `channel-response`, on both sides. So the caller reaches the wrapper's send lines, and the wrapper's send lines reach the caller, without timestamp guessing. One send is identified by target `instance` + `corr` + `conn` + `rpc_id`.
```

### Patch 3: Make the canonical send query reach the channel lines
**Reason:** Dimension 2. The query's channel-join bullet has no key starting from a matched send line.
**Old:**
```
The `channel-*` lines of the same send join on `(conn, corr)`.
```
**New:**
```
The `channel-*` lines of the same send are reached from a matched send line: its `(conn, rpc_id)` equals their `(conn, corr)` (D-30). When refusals at the same offset must be told apart, add `and .record.rpc_id==<id>` to the query.
```

### Patch 4: Route detail lines outside the subscriber
**Reason:** Dimension 1 (setup-project crate wiring). The only subscriber writer is the home-level role file, and the plan never says how `chain` / `drift_report` lines reach `detail-<process>.ndjson`.
**Old:**
```
Content-bearing records (full anyhow chains, serde_path_to_error drift reports, panic payload + backtrace) go **only** to `<home>/instances/<name>/diagnostics/detail-<process>.ndjson` (0600/0700), and only when an instance resolves (D-08).
```
**New:**
```
Content-bearing records (full anyhow chains, serde_path_to_error drift reports, panic payload + backtrace) go **only** to `<home>/instances/<name>/diagnostics/detail-<process>.ndjson` (0600/0700), and only when an instance resolves (D-08).

  - No `obs_event!` call ever carries `chain`, `drift_report`, `panic_payload` or `backtrace`, and G4's `diag-line.v1.json` rejects a home-level line that does (D-30).
```
