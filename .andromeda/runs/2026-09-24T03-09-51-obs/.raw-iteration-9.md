## Patches

### Patch 1: The §2 Errors row names every `catch_unwind` site from §7
**Reason:** Dimension 4 (cross-section consistency). The §2 Errors row still limits `catch_unwind` to `hook`. §7 defines a main-thread catch site for every role, the `run` worker threads, and the vt100 gate. Without this, a reader of the pyramid would not implement the catch site that makes `cli` exit 1 and `run` emit `process-exit{internal-error}`.
**Old:**
```
plus `catch_unwind` on `hook` (Section 7)
```
**New:**
```
plus `std::panic::catch_unwind` at the main-thread catch site of every role, around `hook` dispatch, in the `run` PTY pump and handle-wait threads, and around the vt100 feed (Section 7)
```

### Patch 2: The §2 panic invariant gets the §10 exemptions and the correct payload shape
**Reason:** Dimension 4. The §2 invariant is unconditional ("Every panic"), which contradicts the §10 bounded exemptions (pre-init window, D-06, D-16) and the "after init step 4" scope. It also says the payload is a JSON array, but §7 writes `panic_payload` as an escaped string and only `backtrace` as an array. The `diag-detail.v1.json` author would type the field wrongly.
**Old:**
```
- Every panic produces exactly one single-line structured record: location, thread, role and instance. The payload and backtrace are serialized as JSON arrays and written only to the instance-scoped detail file (Section 7).
```
**New:**
```
- Every panic after init step 4 produces exactly one single-line structured record in its home-level role file: location, thread, role and instance. The bounded exemptions (the pre-init window, `cli` without an instance, `hook` without `VIOLA_NAME`) are listed in Section 10. The payload (one escaped JSON string) and the backtrace (a one-line JSON array of frames) are written only to the instance-scoped detail file (Section 7).
```

### Patch 3: The §5 Counter derivation tolerates torn lines and names its input scope
**Reason:** Dimension 4 / Dimension 1. `jq -s` aborts with exit 2 on a torn line (D-30 rationale), and chaos cases produce torn lines by design. The command also names no input files. If it read detail files, it would double-count panic lines. The companion quantile snippet and G2 already use `awk 1 | jq -R -n … fromjson?`. This row was left open at iteration 8.
**Old:**
```
| Counter | Occurrences of an `event` / `detail` / `refusal` value | `jq -s 'map(select(.event=="send-refused"))|group_by(.detail)|map({d:.[0].detail,n:length})'` |
```
**New:**
```
| Counter | Occurrences of an `event` / `detail` / `refusal` value | `awk 1 diagnostics/*.ndjson | jq -R -n '[inputs|fromjson?|select(.event=="send-refused")]|group_by([.side,.detail])|map({side:.[0].side,d:.[0].detail,n:length})'`, over home-level role files only (detail files repeat lines; a torn line is skipped as in G2) |
```

### Patch 4: The Scenario 2 field list carries the D-30 send↔channel link fields
**Reason:** Dimension 2 (cross-surface-trace-propagation). D-30 made `conn`/`rpc_id` on wrapper `send-*` lines the only join between the cursor-keyed send lines and the id-keyed channel lines. So far it was added to the §6 catalog only. The Scenario 2, 5 and 6 "Required log fields" that `/andromeda-implement` builds from still omit it, so a delivered send cannot be joined to its call.
**Old:**
```
`channel-response{corr:<id>, conn, result_class, refusal, detail, duration_ms}` on both sides.
```
**New:**
```
`channel-response{corr:<id>, conn, result_class, refusal, detail, duration_ms}` on both sides;
  - every wrapper `send-*` line (here and in Scenarios 5 and 6) also carries `conn` (or `srv_conn`) and `rpc_id`, so `(conn, rpc_id)` on the send line equals `(conn, corr)` on this call's `channel-*` lines (D-30). The client-side `send-refused{side:"client"}` carries neither.
```
