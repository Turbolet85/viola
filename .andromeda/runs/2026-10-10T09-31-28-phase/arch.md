# arch extract

## Relevance
relevant — the chunk lands the healing, replay, count and version-tolerance halves of architecture's State Store keystone, inside `viola-state`, `viola-channel` / the wrapper and `src/cmd/verify*`.

## Constraints
- **Torn-line healing is owed here, and its form is not stated.** architecture §Established Decisions [Database / State Store] requires that readers heal a torn last line, and names healing and `state-recovered` as owed to the working-route entry "Self-healing state"; it records the one reader as skipping an unterminated last line unreturned and unrewritten (whether that still holds at HEAD is research's question). Architecture does not say which process heals, whether a byte is written, or what a concurrent writer sees: that form is P3's and P4's to name, inside the bounds below.
- **Byte offsets into `events.ndjson` stay valid for ever.** architecture §Occupied Resources → Filesystem requires that v1 never rotates or truncates `events.ndjson`, because `wait`'s `after`, `send`'s `cursor` and the SSE ids are byte offsets into it, and that any scheme keeps existing offsets valid. A heal that shortens the file, rewrites it through a replace, or moves the start of a logged line breaks that; architecture §Standard Contracts → SSE feed reads an offset past the file's length as "replaced outside viola".
- **One `write` per line, one `.lock` sibling per guarded file.** architecture §Cross-cutting Patterns → Crash-safe disk writes and §Conventions → Data model conventions (ndjson line discipline) require a complete object plus its newline in one `write`; architecture §Established Decisions [Database / State Store] requires the lock on a separate `.lock` file (append plus exclusive lock fails on Windows). Any byte a heal appends follows both, and architecture §Established Decisions [Hook Transport] requires that the SessionEnd direct append writes nothing while `events.ndjson.lock` is held, so a heal that holds that lock bounds what the hook's fallback can do.
- **Snapshot fallback is a closed rule.** architecture §Standard Contracts → Snapshot envelope requires that a snapshot whose `v` is higher than the reader supports, or that fails to parse, is ignored and the state rebuilt by replaying `events.ndjson`; it names the five log-derived fields the replay recovers and the nine fields treated as absent, and requires that liveness then rests on the heartbeat alone (`live` or gone, never `stale`), that the endpoint is rebuilt by the IPC-endpoint rule, and that `hook statusline` prints nothing. architecture §Standard Contracts → Instance snapshot requires that `pending_dialog` is never rebuilt from the log, so a replay reader reports `dialog_pending: false`. Which readers take the fallback today is research's question.
- **Only the wrapper writes `snapshot.json`, through one path.** architecture §Standard Contracts → Instance snapshot requires that the file is written only by that instance's wrapper; architecture §Established Decisions [Human Takeover / Wheel] requires every snapshot write to go through the one in-process holder (`Snapshots`), and architecture §Established Decisions [Snapshot writer] requires every replaced file to go through `viola_state::fs::replace_private`, with no call site carrying its own temp-and-rename code. A rebuild made by `wait`, `last`, `hook` or a CLI verb is therefore in memory; architecture names no second writer.
- **Version tolerance: additive is free, newer is refused by number.** architecture §Conventions → Interfaces and versioning (Protocol versioning) requires that a wrapper receiving `params.v` higher than it supports answers `-32602` with `data.supported` and `data.wrapper`; architecture §Standard Contracts → Wrapper channel frames fixes that frame's `message` and `data` shape; architecture §Established Decisions [Validation] requires that readers of viola's own formats skip and count unknown kinds and fields and never use `deny_unknown_fields`. Whether `viola-channel` or the wrapper already answers so is research's question. Architecture states the refusal for a frame that can be answered; what the wrapper does with an id-less `hook.event` of a higher `v` is not stated.
- **Placement, direction and dependencies are fixed.** architecture §Infrastructure Patterns → Crate dependency direction requires that `viola-state` depends on `viola-core` and on no other viola crate, and that the root bin alone holds anyhow; architecture §Established Decisions [Concurrency / Backend Framework] requires `viola-state` and `viola-channel` to stay tokio-free (the sole-root ban per `scripts/sync-crates.txt`); architecture §Stack and Technologies pins every crate the chunk may use and lists no signal-handling crate, so a signal handler for `viola verify` would be a new dependency needing its own decision. Healing, replay and the counts belong in `viola-state`; the newer-peer refusal in `viola-channel` or the wrapper; the probe-dir owner record and remover in `src/cmd/verify*`.

## Patterns to follow
- **Replay at wrapper start already has three precedents.** architecture §Established Decisions [Message Broker / IPC] requires the `dialog_id` counter to be restored from `events.ndjson` on start and `last` to be rebuilt from it; architecture §Standard Contracts → Channel methods names that rebuild as one pass over the whole file before the server serves; architecture §Established Decisions [Links] requires the link set to be derived by replaying `link` / `unlink`. A snapshot replay follows the same shape: one pass, the log as the only source. Whether these three share a reader today is research's question.
- **The `skipped` envelope is the named surface for the counts.** architecture §Standard Contracts → GUI list envelope fixes `skipped` as three counters (`unknown_kinds`, `unknown_fields`, `torn_lines`), and architecture §Standard Contracts → Channel methods (the `list` row) requires the same shape in `list`'s `ok` payload on the CLI `--json` and MCP surfaces; architecture §Established Decisions [GUI Control Scope] requires the page to show them. Both consumers are later entries (the board, Epoch 8), so the count's type in `viola-state` should already carry the contract's three names. The scope reports the reader's count today as `oversize` and `malformed`; how those map onto the three is P3's.
- **Owner record plus owner-gone removal exists test-side.** architecture §Occupied Resources → Repository (the `target/e2e-home` row) describes `owner.json` `{pid, started_at}` beside a test home, a sweep that takes only a dir whose recorded owner process is gone, never by age or name and never a dir without a record, and a remover that deletes the record last so a part-way removal stays sweepable. The probe-dir remover of item 6 has that shape to follow; it is a test-side pattern, not yet a product mandate.
- **Process identity is pid plus start time, read through `viola-state`.** architecture §Established Decisions [Session Liveness] requires start time beside the pid because pids are reused, and architecture §Infrastructure Patterns → Crate dependency direction places the sysinfo liveness check in `viola-state`. An owner record's liveness read reuses it.
- **New kinds and fields are additive and live in `viola-core`.** architecture §Conventions → Naming patterns (Normalised event kinds) lists fifteen kinds, the set CARRY 1's round-trip covers, and requires new kinds only in `viola-core`; architecture §Conventions → Interfaces and versioning requires that an added field or kind needs no `v` bump. `state-recovered` is not among the fifteen: it is not an `events.ndjson` line by architecture's list.

## Anti-patterns to avoid
- Healing by truncating, rotating or atomically replacing `events.ndjson`, or by any write that changes where an already logged line starts (architecture §Occupied Resources → Filesystem; §Established Decisions [Session Liveness], a gone instance's log is appended to, never truncated).
- Failing a read on an unknown kind, an unknown field or a newer `v` in viola's own formats, or adding `deny_unknown_fields` to them (architecture §Established Decisions [Validation]; §Cross-cutting Patterns → Mixed-version tolerance).
- Removing a probe dir on its name or a bare pid, or removing one that carries no owner record (architecture §Established Decisions [Session Liveness], a bare pid is unsafe; §Occupied Resources → Repository, never a dir without a record).

## Contract bindings
- **arch ↔ obs:** architecture §Cross-cutting Patterns → Diagnostic output channels requires codes-only lines in the home-level role file and content only in the instance's `detail-<role>.ndjson`; `state-recovered` and any `skipped` line are obs's records carried on that channel, and architecture §Standard Contracts → Snapshot envelope and GUI list envelope fix the facts they report (`v` seen, the three counters).
- **arch ↔ security:** architecture §Conventions → Error handling schema fixes the `-32602` fault as a code, a fixed message and a closed `data`; the strict-modes reads at every snapshot reader and what a remover may trust from a record on disk are security-plan's. architecture §Occupied Resources → Filesystem requires verify's probe dirs to be 0700 and removed on every exit path; a kill is outside that sentence.
- **arch ↔ tests:** architecture §Standard Contracts → ndjson event line and Event `data` per kind are the shapes the `crates/viola-state/tests/` round-trip pins; architecture §Cross-cutting Patterns → Cross-platform discipline requires every OS-specific branch to compile and be tested on its CI runner, which covers a Windows-side heal under `File::lock` and a probe-dir record's start-time read.
- **arch ↔ the next entry:** architecture §Standard Contracts → Snapshot envelope lists `agent_session_id` among the log-derived fields, the value "viola revive" reads from this chunk's replay.
- **arch ↔ wrap:** architecture §Established Decisions [Database / State Store] and §Infrastructure Patterns → Project directory structure (the `viola-state` comment) each name this entry as the owner of healing; both sentences go stale when the chunk lands. An owner record in a probe dir, and any new flag or subcommand for a remover, are new entries for architecture §Occupied Resources.

## Acceptance criteria contributions
- (arch) After a heal `events.ndjson` is never shorter than before it, and a `cursor` or `after` taken before the heal still names the start of the same line (per architecture §Occupied Resources → Filesystem).
- (arch) A `snapshot.json` that does not parse, or whose `v` is above the reader's, yields a replay that carries exactly the five log-derived fields, leaves the nine non-log fields absent, reports `dialog_pending: false`, and is never written back by a process other than the instance's wrapper (per architecture §Standard Contracts → Snapshot envelope and Instance snapshot).
- (arch) A request frame whose `params.v` is above the supported one is answered `-32602` with `data.supported` and `data.wrapper`, a fixed message, and no path or upstream text (per architecture §Conventions → Interfaces and versioning; §Standard Contracts → Wrapper channel frames).
- (arch) The chunk adds no viola-crate dependency to `viola-state`, no tokio to a sync crate, and no third-party crate outside the pinned stack; every new on-disk name and CLI surface it lands is listed for architecture §Occupied Resources (per architecture §Infrastructure Patterns → Crate dependency direction; §Established Decisions [Concurrency / Backend Framework]; §Occupied Resources).
