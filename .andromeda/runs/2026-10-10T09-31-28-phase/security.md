# security extract

## Relevance
relevant — the chunk works inside the plan's "Filesystem state under `~/.viola/`" surface (own-state readers, replay, snapshot trust), touches the channel's version refusal, and adds a directory remover the plan states no rule for.

## Constraints
- Bounded line reads: security-plan §Input Validation (row "Own state files on read", Line cap) requires every `events.ndjson` replay and tail line to be read under the `MAX_FRAME` cap, with an over-long line counted and never returned; the same row names the healing of an unterminated last line and its count as owed to this entry. The healing path, the replay path and any new reader this chunk adds stay under that cap (also §Input Validation, Constants: ndjson line reads share the one `MAX_FRAME`). Whether the landed reader already satisfies the cap on every path the chunk adds is research's question.
- Strict-modes before trust, exceptions unchanged: security-plan §Input Validation (row "Own state files on read", Integrity) requires own-state reads only after the home strict-modes check, and lists the dated interim exceptions by verb. A replay or rebuild added to a reader inherits that reader's existing standing (checked, or one of the listed exceptions); the chunk adds no new exception and narrows none (the exception set is fixed per security-plan §Authentication & Authorization, row "`~/.viola/` access control", Strict-modes check). Which readers get the replay is research's question; a reader outside the listed set that would read `snapshot.json` without the check is a boundary widening, not a plan detail.
- Snapshot writer is the wrapper alone: security-plan §Security Anti-Patterns → Universal requires that no process other than the instance's own wrapper writes `instances/<name>/snapshot.json`, because `endpoint`, `pinned_bin` and `statusline_command` in it decide where clients connect and what executes. A rebuild done by any other process stays in memory. Where the wrapper itself writes a rebuilt snapshot, security-plan §Authentication & Authorization (row "`~/.viola/` access control") requires the one helper `viola_state::fs::replace_private`, mode set before any byte.
- Code-deciding snapshot fields are not log-derived by any plan rule: security-plan §Input Validation (row "Own state files on read", Integrity) states `statusline_command` is trusted only because of the strict-modes check, and security-plan §Authentication & Authorization (row "`~/.viola/` access control") names `endpoint`, `pid` and `started_at` as the reference values for server verification. The plan states no rule under which any of these may be taken from an `events.ndjson` replay. The scope's "only log-derived fields" must keep them out of the replayed set unless P4 rules otherwise; which fields the code treats as log-derived is research's question.
- `events.ndjson` permissions and identity survive a heal: security-plan §Data Protection (At rest, Logs) requires `events.ndjson` and `diagnostics/` files at 0600 inside 0700 directories, and security-plan §Authentication & Authorization (row "`~/.viola/` access control", Windows Read rule) rests its per-file check on `events.ndjson` being appended to across sessions and never replaced. A heal form that replaces, truncates or re-creates the file departs from that premise; a heal that only appends keeps it. The form is architecture's to name; this plan's floor is that the file is never created or re-created under the umask (security-plan §Security Anti-Patterns → Data Protection).
- External outputs carry codes and counts only: security-plan §Error Handling (External responses) requires no absolute path, no upstream text, no serde path or value and no internal type name in channel errors, CLI `--json`, MCP results or Problem Details, and fixed `Display` messages on `StateError` / `ChannelError`. This binds the newer-peer refusal (security-plan §Input Validation, row "Channel frames (IPC ndjson)", Version: the `v` check is `-32602`), the surfaced unknown-kind / unknown-field counts, and any `state-recovered` text. A skipped or torn line's bytes, and any value from it, reach only `instances/<name>/diagnostics/` (security-plan §Bootstrap phases, `logging-redaction-wire`, Scope). Whether the refusal already exists, and what its `data` holds, is research's question; the plan states the code and not a `data` shape for it.
- The verify remover has no stated rule: security-plan §Data Protection (At rest, "Interactive probe dirs" and "Probe captures") requires the probe dirs 0700 and removed on every exit path by a drop guard, and names the `.gitignore` line as the only provision for a leftover. The plan states no owner record for a probe dir and no remover of a dead run's leftover, in the cwd, the OS temp root or `ledger/probes/<pid>/`. An owner record written inside a 0700 probe dir is a file viola creates, so the 0600-explicit rule of security-plan §Security Anti-Patterns → Data Protection applies to it where it sits under the home, and by the same §Data Protection (At rest, "Interactive probe dirs") 0700 requirement where it sits outside. What a remover may trust and delete needs a rule this plan does not hold: per the scope it goes to P4 as a priced card.

## Patterns to follow
- Count, do not fail, on viola's own formats: security-plan §Input Validation (row "Configuration values (`config.json`)") is the plan's stated form for unknown keys (tolerant parse, unknown keys counted, `v` checked, read capped), and §Input Validation (row "Own state files on read") the form for skipped lines (skipped and counted). The unknown-kind / unknown-field count follows the same shape.
- Process identity as pid plus start time: security-plan §Authentication & Authorization (row "IPC client-side server verification", Windows / Unix identity check) identifies a live process by pid and the sysinfo start time, never pid alone. It is the plan's only stated liveness-identity form and the nearest precedent for an owner record of a probe dir; sysinfo is already in the stack per security-plan §Authentication & Authorization (Library), so the precedent needs no new dependency.
- Removal only of what the remover's own side created, by a record: security-plan §Security Anti-Patterns → Code Patterns holds two removal guards (the test-side `target/e2e-home` sweep by `owner.json` record with a linked base refused and a fixed, path-free refusal; the `run --mutants` scratch guard by exact final component, never printing the path). Both are test-side or harness rules and bind no product code; they are the precedent a product-side remover is shaped against, not coverage for it.
- Symlink refusal on a path read from disk: security-plan §Input Validation (row "Tailed paths (notify)") ignores symlinks through `symlink_metadata` and takes only names that pass `ViolaName::try_new` under the canonical home. Any instance path the replay joins follows the name rule (security-plan §Security Anti-Patterns → Input).
- Hooks stay fail-open under any new check: security-plan §Error Handling (Internal logging) requires a failing check in `hook` to end in exit 0 with no body and an empty stderr. A version mismatch, an unreadable or newer snapshot, or a torn log met on the hook path follows it.

## Anti-patterns to avoid
- NEVER read an ndjson line, a snapshot or an owner record without the `Read::take(MAX_FRAME)` bound, and NEVER enable `unbounded_depth` to parse a replayed line (security-plan §Security Anti-Patterns → Input).
- NEVER let a newer-peer or version refusal reach the human or block a keystroke, and NEVER let `config.json`, a `VIOLA_*` variable or a flag relax the strict-modes check, the `v` check or the line cap to make a recovery succeed (security-plan §Security Anti-Patterns → Universal).
- NEVER add a channel method to surface the counts or the recovery without a Security Decisions Log entry mapping it to the IPC controls (security-plan §Security Anti-Patterns → Universal); a new field on an existing result is not a new method, a new method is.

## Contract bindings
- security ↔ obs: `state-recovered` and any `skipped` line are obs-owned records that must satisfy the NEVER-log floor of security-plan §Bootstrap phases (`logging-redaction-wire`): no skipped-line bytes, no user content, no absolute path outside `diagnostics/`. Obs-plan's `file` (basename only), `offset` and `v_seen` fields are the obs side of that floor.
- security ↔ architecture: which process heals, whether the file is touched, and the newer-peer refusal's `data` shape are architecture's (State Store, channel frames); security-plan §Input Validation (row "Channel frames (IPC ndjson)") fixes only the frame cap, depth, `-32602` for the `v` check and closed param types, and security-plan §Data Protection's closing note requires of any scheme that reshapes `events.ndjson` (written there for rotation) that permissions stay 0600/0700 and offsets stay valid.
- security ↔ tests: the artifact canary scan named in security-plan §Secret Management (Secret scanning in CI) reads test-home diagnostics and the harness capture; the new crate-level `viola-state` suite's homes and any chaos-case fixtures fall under it: a floor value in a role file or a non-0600 diagnostics file on Unix fails it. The plan's synthetic-content rule (security-plan §Security Anti-Patterns → Data Protection) is written for `fixtures/claude/*` only; it names no rule for a committed `viola-state` test fixture, so synthetic event bodies there are the consistent reading, not a cited mandate.
- security ↔ tests: a parser the chunk adds or changes on the own-state read path sits beside the surfaces security-plan §Input Validation (Parser surfaces) scopes for fuzz / property coverage; that list does not name the `events.ndjson` reader, so whether tests adds it is test-plan's call, not a mandate here.
- security ↔ founder rulings: the `viola verify` dir rules in security-plan §Data Protection (At rest, "Interactive probe dirs") are the founder's live rulings; a remover or an owner record changes what verify writes and deletes outside the home, so its rule is a P4 question (see Constraints, last item).

## Acceptance criteria contributions
- Every line read the chunk adds or changes on `events.ndjson` (heal, replay, count) is taken through the `MAX_FRAME` bound, and an over-long or non-object line is counted and never returned or echoed; a test with an over-cap line and a torn tail proves the count and the absence of the bytes from every external output (per security-plan §Input Validation, row "Own state files on read").
- After a heal and after a wrapper-side snapshot rebuild, `events.ndjson` and `snapshot.json` read 0600 inside 0700 directories on Unix, the snapshot written only by the wrapper through `replace_private`; a non-wrapper reader's rebuild writes no file (per security-plan §Authentication & Authorization, row "`~/.viola/` access control", and security-plan §Security Anti-Patterns → Universal).
- The newer-peer refusal and the surfaced counts carry a code, a fixed message and numbers only: no absolute path, no line content, no serde path or value, in channel `error`, CLI `--json` and MCP output (per security-plan §Error Handling, External responses).
- No reader gains a `snapshot.json` or `ledger/stamps.json` read outside the strict-modes check beyond the dated exceptions already listed, and no remover built here takes a directory that carries no owner record (the first per security-plan §Input Validation, row "Own state files on read", Integrity; the second is the scope's boundary and has no plan anchor until P4 rules it).
