## Constraints
- **Commands and layers.** test-plan §3 `run` step 1 puts inline tests in the unit filterset (`scripts/agent-run.sh run --unit`) and every `kind(test)` binary that carries no E2E prefix in the integration filterset; §3 `run` step 2 puts root `chaos_*.rs` in the fake-agent E2E filterset. So the crate-level `crates/viola-state/tests/` suite of scope item 5 is NOT run by `run --unit`, and no chaos file is either: a gate block of "unit plus smoke" (`inputs#I1`) executes neither unless the plan names them through §3 `run` Test selection (`run --integration --filter 'binary(<stem>)'`, or the default `run`, which is steps 1 and 2). Whether `--e2e` is still a usage error at HEAD is research's question (§3 `run` Test selection says so until the first E2E binary's filterset lands). The smoke is `boot` → `status` → `cleanup` (§3 `status`): scope item 2 changes the wrapper's start, and §3 `boot` readiness reads the snapshot that start writes.
- **Unit cases the plan requires.** test-plan §4 "What unit tests cover" → viola-state requires four cases this chunk owns (torn-line count with no panic; an over-long line counted as torn; an unsupported `v` or a parse failure routed to replay; replay recovering exactly the named field set with `dialog_pending:false`), and §4 → viola-channel requires the `-32602` mapping with its `data` members for a higher `v`. The plan names the counts `torn_lines`, `unknown_kinds`, `unknown_fields` (§1 Status endpoint shape); whether the code's `Skipped { oversize, malformed }` already satisfies that naming, and whether the `-32602` case already exists since chunk 2026-09-27-wrapper-channel, are research's questions.
- **Crate-level suite.** test-plan §5 "Cross-module patterns covered" → On-disk requires the event-kind round-trip of the six-key line in `crates/viola-state/tests/`, with the `ts` shape, and §2 Test pyramid (Integration row) requires a crate-level `tests/` suite per arch Standard Contract on a real tempfile home. This is CARRY 1 verbatim; whether the directory exists at HEAD is research's question.
- **A verdict lives in the crate that owns the code.** test-plan §11 Test Strategy bans asserting at E2E what a lower layer can hold, and §3 `run` step 4 (Test scope) requires a mutant in a `crates/viola-<area>` crate to be killed by that crate's own tests. No mutation run is planned here (`inputs#I1`), and §10 Mutation gate places the score at the epoch boundary: the healing, replay and counting logic in `viola-state` therefore needs its verdicts in `viola-state`'s own unit and crate-level tests, not only in root `chaos_*.rs`.
- **Chaos cases, and which the plan lets this entry owe.** test-plan §1 (chaos-test trigger) and §2 Test pyramid (Chaos / Fault row) make chaos tests required; §6 Chaos suite holds the torn-append case and the forward-compat case, §6 Scenario E5 the snapshot-corruption pair (mid-object truncation, and envelope `v:99` in a sibling test). Their verification signals read `skipped.*` on `list --json` and `/api/sessions`, and E5 reads `list --json` liveness; §3 Status endpoint shape carries an interim form "while `viola list` / `viola ui` are unbuilt". Which of those surfaces exist at HEAD is research's question: the surface-independent halves (the count rises by one, the next append starts on a fresh line, the rebuilt snapshot's fields, no refusal of start, `wait --after` not waking on an unknown kind) are assertable without them; the `list` / `/api/sessions` halves and §6 Cross-surface parity of `.skipped` belong where those surfaces land. E5's step 1 also drives `link`, `pause` and a budget pause: whether each verb and its log record exist is research's question, and it bounds how much of the replay field set E5 can show here.
- **Where test bytes come from.** test-plan §7 Seed strategies requires on-disk product state to come only from real product runs, with the chaos tests as the exception for corrupting files the product already wrote; §11 Test Data bans a hand-written `snapshot.json`. §4's envelope case needs a snapshot with an unsupported `v` and a torn log line at unit level, and the plan does not say how a unit or crate-level case obtains them (the crate's own writer then a corruption, or a literal). That is a gap to settle at P3/P4, not to assume.
- **Determinism and the OS matrix.** test-plan §2 Agent-runnable invariants requires waits keyed on `events.ndjson` byte offsets and no sleep for synchronisation; §10 Zero-flakiness budget keeps `retries = 0` and forbids `#[ignore]` as a parking place; §11 Universal limits chaos faults to explicit process and file operations or existing mockall seams. §11 Test Strategy also bans reading a Linux-only local run as proof for Windows or macOS: the healing's file behaviour is proven per OS only by the CI legs (§1 multi-os-compat trigger).

## Patterns to follow
- A fresh home per test under the `target/e2e-home` base, created by viola itself, removed on drop (test-plan §5 Setup / teardown lifecycle; §3 Test data bootstrap, Mechanism and Per-test isolation). §3 `run` step 2 states that root `tests/support/` cannot be imported by another package, so a `crates/viola-state/tests/` suite needs its own home fixture; the plan states the base-dir rule for the root chain and the harness only.
- Root chaos files are named `chaos_<topic>.rs` and take the one `events.ndjson` reader, the one complete-lines reader (`tests/support/ndjson.rs`, newline-terminated lines only) and the one started-child guard from `tests/support/`, with no file-local copy (test-plan §2 Test directory + naming conventions). The torn-append fault is a kill of the test's own wrapper followed by `File::set_len` (§6 Chaos suite); a started wrapper is held in a `Drop` guard (§5 Setup / teardown lifecycle).
- Table-driven cases are rstest `#[case]` rows with readable labels, named `<subject>_<condition>_<expected>` (test-plan §4 Conventions); expected values are literals written in the test (§11 Unit). §11 Unit names three product lists that may not serve as the oracle; whether the event-kind set of the round-trip suite falls under the same rule is P4's read. §7 Seed strategies (Randomized data) lists event lines among the proptest strategies, with committed `proptest-regressions/`; §1's property-test trigger does not list the `events.ndjson` reader among its seven surfaces, so a property is allowed, not required.
- A guard is shown red once by a planted input or a removed guard, recorded, not kept as a test (test-plan §7 Fixture hygiene: planted inputs prove each class red). This is the plan's shape for `inputs#I1`'s remove-the-guard demonstration.
- For scope item 6: test-plan §3 Test data bootstrap (Cleanup) holds the plan's existing answer to the same problem on the test side — an owner record of pid and start time written beside the dir, a sweep that takes only a dir whose recorded owner is gone, never by age or name and never a dir without a record, the record deleted last. `tests/cli_verify.rs` is where verify's "no run dir left behind" assertion lives (§5 Cross-module patterns → CLI).

## Anti-patterns to avoid
- NEVER mock the on-disk state or hand-write `snapshot.json`, `ledger/stamps.json` or `budget.json` (test-plan §11 Integration; §11 Test Data).
- NEVER synchronise with `sleep(N)`, a test-owned timer or a retry; a flake is fixed at its cause inside the chunk (test-plan §11 E2E; §11 Universal; §10 Zero-flakiness budget).
- NEVER inject the mid-write fault through a failpoint crate that pulls tokio into the sync crates, or by patching production code at run time (test-plan §11 Mocking).

## Contract bindings
- **obs ↔ harness log format:** `state-recovered` is a value of the closed product `event` enum with `corr` null (test-plan §3 Log format, Required fields); a NEW event value for the skipped counts would need a Decisions Log entry under the same rule. Every home-level diagnostics line the healing writes under `target/e2e-home/**` is validated against obs-plan's `schemas/diag-line.v1.json` (§6 Schema conformance; §3 `schema-check`), where a non-JSON line is counted, not failed.
- **harness `logs` ↔ the event log:** §3 `logs` emits a torn or unparseable line as a marked record and never drops it; a healing that touches the file must keep that reading true.
- **arch ↔ harness status:** the `skipped{unknown_kinds, unknown_fields, torn_lines}` envelope is the arch `list` / GUI HTTP shape that §3 `status` polls and §3 Status endpoint shape nests verbatim (interim `null` while `viola list` / `viola ui` are unbuilt).
- **security ↔ tests:** §1 security-vector-coverage (filesystem), Vector 7, requires the over-long line counted in `skipped.torn_lines`; §6 Security control negatives → Single writers requires `snapshot.json` bytes and mtime unchanged by every entry point but the wrapper, which binds a client-side replay to memory; §6 Error sanitization and secret scan forbids an absolute path and the content canary in home-level diagnostics, which binds `state-recovered`'s `file` to a basename.
- **arch channel ↔ tests:** the newer-peer refusal is `-32602` with its `data` members at unit level (§4 → viola-channel) and for a higher `params.v` at integration level (§5 Cross-module patterns → Wrapper channel).

## Acceptance criteria contributions
- `scripts/agent-run.sh run --unit` exits 0 with the four `viola-state` cases present, and `scripts/agent-run.sh run --integration --filter 'binary(<the crate-level stem>)'` exits 0 with every event kind round-tripping in `crates/viola-state/tests/`; both documents read `failed` 0 and `skipped` 0 (per test-plan §3 `run` step 1 · §4 What unit tests cover → viola-state · §5 Cross-module patterns → On-disk)
- A root chaos case kills its own wrapper mid-append and shortens the file: the torn count rises by exactly 1 and the next append starts on a fresh line; a truncated `snapshot.json` and an envelope `v:99` each lead to a start that is not refused, with the log-derived fields rebuilt and `dialog_pending:false` (per test-plan §6 Chaos suite · §6 Scenario E5)
- An unknown `kind` and a known kind with an unknown field are each counted exactly once and fail nothing, and a `wait --after` from before the append does not wake on the unknown kind; a request with a higher `v` reads `-32602` with the supported version (per test-plan §6 Chaos suite, forward-compat lines · §5 Cross-module patterns → Wrapper channel)
- The CI `run --coverage` legs hold the per-OS floors on lines, functions and regions with the new code in, with no widening of the ignore regex (per test-plan §10 Coverage thresholds · §11 CI)
