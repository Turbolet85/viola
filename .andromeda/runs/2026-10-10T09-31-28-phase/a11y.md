# a11y extract

## Relevance
partial — the chunk builds no web-spa markup (the UI's replay is Epoch 8's, the board is a later entry), and `viola-state`, the channel and the hook are not-assertable per a11y-plan §1 A11y Scope Summary → Not-assertable (no UI surface); a11y reaches it only where an item puts text on a terminal (a newer-peer refusal on a CLI verb, a count "surfaced" on a CLI verb, a line from `viola verify`'s remover) and where the wrapper heals or replays inside `viola run`.

## Constraints
- a11y-plan §1 A11y Scope Summary → CLI and terminal entities makes the CLI verbs (`send`, `wait`, `last`, `answer`, `verify` among them) assertable for output discipline only, in human TTY, plain and `--json` modes; any text this chunk adds to one of those verbs falls under it. Which verbs gain text here (item 3's "surfaced", item 4's refusal, item 6's remover) is research's question; a11y-plan names no surface for the unknown-kind count on the CLI.
- a11y-plan §1 A11y Scope Summary → `viola run` TUI passthrough requires that viola write zero bytes to the terminal except the child's output and that a human keystroke is never blocked, refused or delayed past the current atomic paste. A heal of a torn line, a snapshot replay or a `state-recovered` record made by the wrapper must put nothing on the terminal and hold no keystroke. Whether the wrapper heals or replays at start, before the child exists, or inside the pump is research's question.
- a11y-plan §1 A11y Scope Summary → Surface: tui → Notes requires that viola's diagnostics for `run` go to `diagnostics/`, never to the terminal: the recovery record and the skipped and unknown counts of a `run` process are covered by it.
- a11y-plan §8 Cognitive Accessibility → Error recovery requires every human-mode CLI refusal to read `unable  <reason>  <detail>` on stderr with `hint:` as the last stderr line and a typed exit code, `--json` to give one document with no hint, and a fault to carry no hint. Item 4's newer-peer refusal is bound by it if it reaches a human-mode verb; whether it surfaces as a refusal or as a fault, and with which exit code, is research's question (the section names `unknown`, exit 14, as the one refusal without a hint).
- a11y-plan §8 Cognitive Accessibility → Plain language requires that a kebab-case reason or detail code never stand without the plain word `unable`, and that the CLI never show a Problem URN, a stack trace or a bare status number as the only error text: the supported version in the newer-peer refusal is detail beside `unable`, not the whole message.
- a11y-plan §4 ARIA Patterns & Roles → Must-be-accessible path scenarios → P6 requires CLI output to be static and linear (no redraw, no spinner), `verify` lines to keep the `[NN/NN] … pass|fail` shape, no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`, and C0/C1 controls escaped. A remover line inside `viola verify` and any count line are bound by it; a value read back from disk and printed (an unknown kind's name, a file basename) is content to escape, not viola's own literal. Whether any such value is printed at all is research's question.
- a11y-plan §11 A11y Anti-Patterns → Strategy forbids a WCAG conformance claim for the cli or the `viola run` TUI: every check this chunk adds on a terminal is an output-discipline stand-in, never conformance evidence.

## Patterns to follow
- A refusal's human-mode layout is pinned by a trycmd case and its typed exit code and hint-free `--json` by assert_cmd, on all three OS legs (per a11y-plan §8 Cognitive Accessibility → Error recovery → Verification). A new refusal reason takes one of each.
- Every fixed CLI string is pinned by trycmd so that a copy change fails until the pin is moved on purpose (per a11y-plan §8 Cognitive Accessibility → Plain language → Verification).
- The zero-viola-bytes clause is its own nextest case over the portable-pty outer PTY with the fake agent as the child: byte for byte against an unwrapped run on Linux and macOS, viola's own literals absent on Windows, on both ConPTY backends (per a11y-plan §3 Keyboard test harness → Tooling). Whether that case's start already runs over a torn log or an unreadable or newer snapshot is research's question.
- An output-discipline failure surfaces only as a nextest failure in `suites[].failures[]`; the cli and tui write no a11y row (per a11y-plan §3 Structured violation JSON schema → cli / tui).
- CLI output-discipline cases live inside `nextest-integration` / `nextest-e2e`, in CI inside the per-OS `test` job's `coverage` suite (per a11y-plan §9 CI Integration → Per-pipeline-stage a11y artifacts, Unit / integration row).

## Anti-patterns to avoid
- NEVER colour `unable` / `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` (per a11y-plan §11 A11y Anti-Patterns → Visual).
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste: a heal or a replay is not a reason to hold one (per a11y-plan §11 A11y Anti-Patterns → Keyboard).
- NEVER show an error without its recovery suggestion, and never a Problem URN, stack trace or bare status as the only error text on the CLI (per a11y-plan §11 A11y Anti-Patterns → Cognitive).
