# obs extract

## Relevance
relevant — the chunk lands the heal and replay behind `state-recovered`, the reader skip counts and the newer-peer refusal, all of which obs-plan catalogues as process-log signals; item 6 (the `verify` leftover remover) is partial.

## Constraints
- obs-plan §6 Additive field catalog (`state-recovered`, D-03) requires the heal and the replay to be recorded as the one closed event with its closed `detail` set and its four named fields, and §6 Log levels mapping requires it at `warn`; §3 Log format JSON schema requires its `corr` to be null, written as key absence. Whether `viola_core`'s `ObsEvent` and `schemas/diag-line.v1.json` already admit this event with exactly these fields is research's question.
- obs-plan §4 Edge flows (E5) requires the snapshot path to tell its two causes apart by `detail` and to carry `v_seen` and the snapshot's basename; obs-plan §1 Telemetry triggers (chaos-instrumentation) requires the torn-line heal to carry file and offset. Both are requirements on the code this chunk adds, in every process that performs a recovery.
- obs-plan §8 Default-deny posture requires every logged field to be named in the §6 catalogue, and §3 Log format JSON schema requires a Decisions Log entry (and the tests amendment) for any new `event` value. So logging today's read-time skip counts on a line that does not already carry them, or a field that tells the newer-peer cause apart, is a catalogue and schema addition raised to P4, never a silent add.
- obs-plan §4 Scenario "GUI view" and §5 Per-surface / per-path metrics (`viola.parse.skipped`) name the only carriers of the skip counts: the `skipped` object on the `/api/sessions` request line and `list --json`. Both belong to later route entries; the plan names no process-log carrier for a `wait` / `last` read. The plan's count names (three: unknown kinds, unknown fields, torn lines) differ from the reader's two counts the scope reads at HEAD; how the counts built here map onto the plan's three is research's question.
- obs-plan §6 Boundary-call wrappers (IPC invocation) requires the newer-peer refusal to be logged as the existing channel pair with codes only, never `params` or a result body; §6 Log levels mapping puts a `-32602` response at `warn`; §5 Per-surface / per-path metrics (`viola.compat.v_rejected`) records that this count over-counts until the line tells the causes apart. Whether the refusal already exists in `viola-channel` or the wrapper, and what its line carries, is research's question.
- obs-plan §8 Data classification rules require home-level lines to stay path-free (a `file` field is a basename) and free of event payloads; obs-plan §2 Telemetry signal pyramid (Audit Logs row) forbids copying `events.ndjson` payload into a process log. A heal line therefore carries an offset and a basename, never the torn bytes; the same holds for any line the item-6 remover writes (no probe-dir path; a pid only as a typed field, per §8 Data classification rules, Low row).
- obs-plan §3 Logging stack (Sink) fixes where a line lands: the role file of the process that did the recovery, and none for a short-lived verb with no resolved instance. obs-plan §10 Performance budgets (Obs overhead on `hook`, and the spine `max` rows) bounds any replay placed on a hook's snapshot read. obs-plan §10 Operational retention (no rotation) makes emission cadence a design point: a reader that meets the same torn line or the same newer snapshot on every read must not grow a never-rotated file per read. The plan states no cadence for `state-recovered`; P3 and P4 name it.

## Patterns to follow
- One emitter: `obs_event!` with explicit typed fields and a static message, inside `#[instrument(skip_all, name = "state.<operation>", fields(..))]`, sync only in `viola-state` (per obs-plan §3 Logging stack; §4 Span naming convention; §1 Instrumentation scope, `viola-state`). The plan names `state.snapshot_write`, `state.tail_notify` and `state.ledger_read` but no span for the heal or the replay; new names follow the `state` area form and are code-internal, not wire contract (per obs-plan §2 Naming conventions).
- Count on the boundary, one line per scan or episode: the `state-entry` skip is logged once per scan with a `count`, and the vt100 poisoning once per episode (per obs-plan §6 `detail` code catalog, Filesystem refusals; §7 Error classes captured).
- Failures are captured at the viola seam from the returned `Result`: a fixed-`Display` `StateError`, a codes-only home-level line, the full chain only in the instance detail file through the root bin's detail writer (per obs-plan §7 Platform pick and its scrubbing layers; §3 Logging stack, Sink).
- `verify`'s existing shape for item 6: `cli.verify` with `cli.verify_step` spans, start and exit lines in `cli-<name>.ndjson` only when `VIOLA_NAME` is set, no process-log file from a plain terminal, and the hidden capture arm left uninstrumented (per obs-plan §4 Edge flows, `verify` / `plugin install`). No obs gate depends on `verify`'s own lines.
- Metrics are derived by `jq` over the lines, never instruments: `viola.state.recovered` from the event's `detail` (per obs-plan §5 Per-surface / per-path metrics).

## Anti-patterns to avoid
- Never a line per record in a read or tail loop, and never a line per tick; counts ride the boundary event (per obs-plan §11 Obs Anti-Patterns, Logs; §11 Obs Anti-Patterns, SLO).
- Never a field outside the §6 catalogue, and never a path or pid inside a `detail` code (per obs-plan §11 Obs Anti-Patterns, PII Scrubbing).
- Never `#[instrument(err)]` / `ret`, a bare `#[instrument]`, a raw tracing macro or a print macro on the snapshot parse and replay path, whose error carries a serde source (per obs-plan §11 Obs Anti-Patterns, Spans / Traces; §11 Obs Anti-Patterns, Logs).

## Contract bindings
- obs ↔ tests harness `logs`: the merged output reports a torn line as its own record with an offset, and event records carry byte offsets (obs-plan §3 Snapshot / paste-to-AI integration). If the heal changes bytes on disk, test-plan §3 `logs` owns what the harness then prints.
- obs ↔ tests chaos and gates: E5 and the crash-safe-state cases read `state-recovered` (obs-plan §4 Edge flows; §2 Trigger coverage map, chaos-instrumentation); their homes must sit under `target/e2e-home/` so G2, G4 and the secret scan read them, and G4 skips and counts a non-JSON line (obs-plan §9 Pipeline integration, Integration tests; §9 Gate commands, G4). Whether the new `crates/viola-state/tests/` suite makes on-disk homes, and where, is the tests extract's.
- obs ↔ tests log format: the event enum and its `corr` rules are reproduced from test-plan §3; an enum or field change moves both plans (obs-plan §3 Log format JSON schema).
- obs ↔ architecture: byte offsets are the `wait after`, send-cursor and `Last-Event-ID` cursors and must stay valid (obs-plan §3 Log file location, Rotation; §10 Operational retention). The form of the heal is architecture's; obs binds only that no offset already handed out moves.
- obs ↔ security: `strict-modes-failed` and `instance-dead` stay their own exit-21 codes, and `wait` / `last` keep the liveness-only pre-check until Epoch 6 (obs-plan §6 `detail` code catalog; §4 Scenario "`wait` / `last` event-driven readback"). Whether a replayed snapshot changes which code a client logs is security's and architecture's to say.
- obs ↔ design / a11y: the page's skipped-counter box reads the same three counts (obs-plan §4 Frontend observable boundary). Not built here; only the shape must not be foreclosed.

## Acceptance criteria contributions
- (obs) A healed torn last line, an unreadable snapshot rebuilt by replay and a newer-`v` snapshot each leave a `state-recovered` line at `WARN` in the recovering process's role file, with the matching closed `detail`, a basename `file`, `offset` or `v_seen` as catalogued, and no `corr` key; a test asserts each line present with its fields, so the call site is not an unkilled mutant at the next audit (per obs-plan §6 Additive field catalog; §4 Edge flows E5; §6 Log levels mapping; §10 Build / deploy failure conditions).
- (obs) Every line this chunk adds validates against `schemas/diag-line.v1.json` with zero G4 failures, in an in-memory writer test and in real process output (per obs-plan §9 Pipeline integration, Unit tests; §9 Gate commands, G4; §10 Error budget).
- (obs) A torn line, a corrupt snapshot, a newer snapshot and a newer peer's request produce zero `event:"panic"` lines: G2 stays clean over the chunk's test homes (per obs-plan §10 Always-required SLO invariant; §9 Gate commands, G2).
- (obs) No home-level line added here carries an absolute path, a probe-dir name, event-line content or the tests canary (per obs-plan §8 Integration points, item 6; §8 Data classification rules).
