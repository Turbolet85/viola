## Output Protocol

You are an iteration agent improving the viola architecture document (`architecture-draft.md`). Follow these rules exactly.

1. **Output patches and a changelog only.** Do not reproduce the full document.
2. **Patch format.** Number each patch and use this form:

   ### Patch N: <short description>
   **Old:**
   ```
   <exact text copied verbatim from the current document, long enough to be unique>
   ```
   **New:**
   ```
   <replacement text>
   ```

   The **Old** text must match the document character for character, including backticks, em-dashes, `·` separators and list markers, or the patch cannot be applied. Keep each patch as small as it can be while staying unambiguous. To add text, quote the adjacent anchor line as **Old** and give that line plus the new content as **New**.
3. **Changelog.** Give one line per patch in the form `[Iteration N] [substantive|cosmetic] description`.
   - **Substantive** means the patch changes or adds a technical fact, contract, decision, rationale, constraint, version, name or resource.
   - **Cosmetic** means wording, formatting or ordering only.
4. **Prohibited:**
   - reproducing the full document;
   - restructuring or renaming sections without a concrete defect behind it;
   - labelling a cosmetic change as substantive;
   - inventing measured facts (CLI versions, spike results, ledger measurements) that the document does not already support. If a fact is missing and cannot be derived, add an explicit, named open item (for example "confirmation window: default N s, ledger-tunable") instead of a fabricated measurement;
   - adding specialist-owned choices: frontend framework, CSS or component library, logger crate, test framework, auth library.
5. **If you find no issues:** output "No patches", then a single changelog line `[Iteration N] [cosmetic] No issues found`.

Keep these document-level invariants when you patch:
- Mechanism, not policy (R4).
- The human always wins the wheel.
- No daemon.
- `viola hook` always exits 0 and never produces exit 2.
- Tokio is confined to `viola-mcp` and `viola-ui`.
- Claude-specific shapes live only in `viola-agent-claude`.
- Every undocumented CLI behaviour is a capability-ledger row.

## Analysis Dimensions

### 1. Internal Consistency [priority: high]
- **Tokio containment.** "Established Decisions → Concurrency" and CI job 3 check only `cargo check -p viola-channel -p viola-pty -p viola-state`. The `deny.toml` ban in "Infrastructure Patterns → Build system" also names `viola-core` and `viola-agent-claude`. Meanwhile the Stack row and "Cross-cutting → Tokio containment" still say "(and `wait` if it goes async)". Do these three places agree on which crates must stay Tokio-free? If `wait` goes async, the root bin (which holds `src/cmd/wait`) would need Tokio. Does that contradict "Only `viola-mcp` and `viola-ui` list `tokio`"? Resolve the `wait` question one way and align every mention.
- **Placement of tailing, liveness and vt100.** The directory tree comment says `viola-state` does "tailing", but "Crate dependency direction" gives `notify` only to `viola-ui` and says `viola-state` → `viola-core` only. `sysinfo` appears only under `viola-ui`, yet CLI `list` and the heartbeat "pid + start-time check from the snapshot" also need liveness. Neither `vt100` nor `jsonschema` is placed in any crate. Does every Stack dependency land in exactly one crate in the dependency-direction list, consistent with the tree comments?
- **Versioning language.** "Snapshot envelope" and "Database / State Store" speak of a snapshot whose "`v` major version is unreadable", but Conventions define `v` as a single integer with no major/minor split. `/api/info` also carries `"proto":1` next to `"v":1`, and `proto` is never defined. Are the versioning terms (`v`, `proto`, `sender`, `writer`) used with one meaning across Conventions, Standard Contracts and Cross-cutting "Mixed-version tolerance"? Also check that Design Philosophy's list of four refusal reasons matches the five `RefusalReason` values (with `unknown`), and that exit codes `10–14` line up with them.

### 2. Decision Completeness [priority: high]
- **Missing `pause` decision.** The `pause` subcommand and the `pause` channel method appear in the Stack clap row, Channel methods and Occupied Resources. No Established Decision says what `pause` does: does it take the wheel for the human, trigger a manual budget pause, or something else? It is also unclear how it interacts with `release` / `release --budget`, or why it is CLI-only while MCP omits it. Add the decision and its rationale, or remove the verb.
- **Unstated timeouts.** Several blocking waits have no stated value or failure outcome:
  - the delivery "confirmation window" in "Delivery Confirmation";
  - how long a sync-tier `PreToolUse`/`PermissionRequest` hook blocks on `hook.dialog` for a driver's `answer`, and which `timeout` value `hooks.json` sets;
  - how long `wait` blocks before returning. MCP tool calls from the driver have a client-side timeout.

  Is each one a documented default, a ledger row or config, and what does the caller receive when it expires? A hook timeout must still fail open.
- **Wheel state transitions.** Which holder is the wheel given at `viola run` start? Does a `/clear` (SessionStart source `clear`) or a harness turn change it? What does `send` return while a turn is still running (the busy state before `turn-ended`)? No `RefusalReason` covers "turn in progress". Should one be added, or is `send` queued, or is it `not-delivered`? State this explicitly.

### 3. Conventions Specificity [priority: high]
- **Detail vocabulary.** `detail` values are "kebab-case strings, for example `input-not-ready` and `no-prompt-submitted`". Is the full closed set of `detail` values listed per `RefusalReason`, so that drivers and CLI `--json` consumers can branch on them? Is it stated whether unknown `detail` strings must be tolerated the way `#[serde(other)]` tolerates unknown refusals?
- **Instance unreachable (exit 21).** How does this outcome surface on the channel and MCP surfaces? It cannot be a channel frame, because there is no endpoint. Is it an MCP `isError` refusal with some reason, or a JSON-RPC error with a code? Specify the MCP and `--json` shapes for exit 21 and for exit 20 (protocol fault) so that all three surfaces map one-to-one.
- **Problem Details scope.** `urn:viola:problem:state-unreadable` (503) is defined, but `/ready` returns 503 with its own `{"status":"not-ready"}` body. Say whether `/ready` and `/health` are exempt from RFC 9457. Also give the `Content-Type` for each GUI route, and state whether problem responses carry the `v` field that Conventions requires in "every … GUI JSON body".

### 4. Downstream Readiness (bidirectional) [priority: high]
- **Tests specialist.** Is there an explicit test-mode injection point? CI runs "against the fake agent", but the document has no way to point viola at an isolated viola home. `<user home>/.viola/` is fixed, and "environment variables are not a configuration channel". It also never says how the fake agent is substituted for `claude` in `viola run <name> -- claude <args>`, or which `cargo test -p viola-<x>` targets exist per crate. If any of this is absent, add an arch-level constraint such as a `--home` flag or a test-only env var, without choosing the test framework.
- **Obs and security specialists.**
  - **Obs.** Where do diagnostic logs go, given that `viola hook` must print nothing on stdout for async tiers and exit 0 always? Is it stderr, a per-instance file, or nothing? Are `events.ndjson` growth and rotation addressed, given that SSE `id:` uses byte offsets into that file?
  - **Security.** Is the local-socket trust model stated? Consider the default ACL of `\\.\pipe\viola-<h12>` on Windows and the permissions of `$TMPDIR/viola-<h12>.sock` on Unix. Any local process that can connect can `send` prompts or `answer` PermissionRequest dialogs. If this is only implicit, elevate it to a Decision or Cross-cutting bullet the security specialist can consume.
- **Design, a11y and scope template.** The GUI has `/`, `/assets/*`, `/api/sessions`, `/api/links` and `/api/events`. Is there a specialist-facing summary of what the page must show? That means session rows (wrapped vs read-only unwrapped, `stale`), links, wheel holder, budget age, and `skipped` counts, and it should include input modalities (keyboard-only, view-only, live-updating SSE regions) for a11y. Could a per-feature scope doc and the route/dev-sequence step be written without asking questions? For example, is it stated how `/assets/*` gets embedded, and the item shapes of `/api/sessions` and `/api/links`?

### 5. Complexity Calibration [priority: medium]
- **Tooling for a personal v1.** Is this tooling proportional for a personal, Windows-live, single-user tool? The list is seven workspace crates, 15 subcommands, cargo-deny, cargo-modules and optional jsonschema. And do the v1.x release tools (dist 0.33.0, cargo-auditable 0.7.6, self_update 1.3.0) belong in the v1 Stack table, or should they move to a clearly marked "later" note so they do not look like v1 dependencies?
- **Missing robustness.** Look for gaps the "no daemon, disk is shared truth" design creates:
  - `~/.viola/bin/<version>-<hash>/` and `plugin/<version>-<hash>/` gain a new directory on every dev rebuild, with no cleanup rule. Can a running session's pinned copy be deleted safely?
  - `events.ndjson` grows without bound.
  - Stale `instances/<ViolaName>/` directories after a crash are never reclaimed.
  - Nothing says what happens when a second `viola run` uses a `ViolaName` that is already live (endpoint collision).

  Add minimal, proportional rules. Do not introduce a daemon.
- **Governor and ledger weight.** Does the budget governor (thresholds, `resets_at`, the statusline wrapper, `budget.json` last-writer-wins) and the per-row capability ledger add the right amount of mechanism for v1? Or is some piece underspecified in a way that pushes complexity into the build? One example is the `statusline` entry in the hook-event argument list: it must print the user's statusline output, which conflicts with the hook tiers' "print nothing" and `hook` exit rules.

### 6. API Contract Completeness [priority: medium]
- **Channel method shapes.** Standard Contracts show frames only for `send` and `hook.event`. Are request `params` and `ok` payloads specified for `wait`, `last`, `list`, `answer`, `pause`, `release`, `link`, `unlink` and `hook.dialog`? In particular:

- **SSE multi-instance resume.** `/api/events` fans out events from every instance, but `id:` is `<ViolaName>:<byte offset>`, and the browser sends back only the last `Last-Event-ID`. On reconnect, how are the other instances' positions resumed? Specify the reconnect semantics, for example a composite cursor, replay-from-snapshot, or a per-instance query param, and what happens when the offset exceeds the file length.
- **GUI item shapes.** Are the `items` element shapes for `/api/sessions` and `/api/links` defined? This includes the fields for liveness state (`live`/`stale`/gone), `status` idle/busy, wrapped vs unwrapped, wheel holder, budget reading and age, and link `driver`/`driven`.
