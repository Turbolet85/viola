# security extract

## Relevance
Partial. This chunk is obs's CI-gate phase. Security's share is limited to four things: the NEVER-log floor, which is what the secret scan checks; the CI supply-chain rules for the edited `ci.yml` (pinning, permissions, zizmor); the rule that a hook fails open and never writes to stderr, which binds the panic hook and the print-lint `#[allow]` sites; and making sure no unresearched secret scanner gets in.

## Constraints
- The secret scan's subject is the consolidated NEVER-log floor in security-plan §Bootstrap phases → `logging-redaction-wire`. It covers the GUI token, the launch URL or `.url` contents, the `Cookie` header, the `?t=` query string, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` and every other R8-stripped `CLAUDE*` value. The list of what counts as secret is in security-plan §Secret Management → "What counts as secret". The scan's patterns must cover these values and must not narrow or diverge from the floor ("must not diverge from it", same §).
- Every action step added or changed in `ci.yml` must use a full commit SHA with a version comment. That covers the PCRE2 ripgrep install step and the `upload-artifact` steps. security-plan §Dependency Security → CI integration and §Security Anti-Patterns → Code Patterns ("NEVER reference a GitHub Action by `@stable`, `@v2` or any mutable ref") require this. `actions/upload-artifact` must be the listed `043fb46d…` (v7.0.1). If the ripgrep install uses an action outside the four-action pinned set, §Dependency Security needs an amendment. Keeping `taiki-e/install-action@7623a79…` or a checksum-verified download avoids that. Which route the step takes is P3/P4's call.
- The edited `ci.yml` keeps workflow-level `permissions: {}` and job-level `contents: read`, and `actions/checkout` keeps `persist-credentials: false`. Event-payload values (for example `AGENT_RUN_CHUNK_BASE`) reach steps only through `env:` and never through `${{ }}` inside `run:`. `zizmor .github/workflows/` must still pass on the ubuntu leg. Source: security-plan §Dependency Security → CI integration.
- `viola hook` never writes to stderr and never exits non-zero, including when a security check fails. Source: security-plan §Error Handling → Internal logging and §Security Anti-Patterns → Logging. The panic-hook-first gate and the "hook panic still exits 0" invariant have to hold this on hook paths: the panic hook must not print a payload to stderr there. Whether the current panic hook already stays silent on stderr under `hook` is research's question.
- The `print_stderr` / `print_stdout` `#[allow]` sites must not open a stderr route for upstream text, tool `input`, drift-report values, anyhow chains that still hold a serde source, or absolute paths. Only the one-time `viola ui` launch line may carry the token. Source: security-plan §Error Handling → Internal logging, §Bootstrap phases → `error-sanitization-wire`, and §Security Anti-Patterns → Logging. Human-mode `wait`/`last`/`list` output modules must keep escaping C0/C1 controls (§Security Anti-Patterns → Logging).
- Security does not wire a general repo secret scanner in v1, and none was researched. Source: security-plan §Secret Management → "Secret scanning in CI" and §Bootstrap phases → `secret-scanning-ci-gate`. The chunk's scan must stay obs's ripgrep canary scan over the three listed artifact roots. Do not add gitleaks or any other scanner dependency without a Security Decisions Log entry.
- No new crates. The lint config changes (`[workspace.lints]`, `clippy.toml`, per-member `[lints]`) must leave `cargo deny check` green across all four families, and must not touch `[workspace.dependencies]` pins or the `deny.toml` bans. Source: security-plan §Dependency Security → Pinning and `deny.toml` additions.

## Patterns to follow
- The prior chunk's canary floor already treats `CLAUDE*` values this way (master-route: "CLAUDE* canary floor at HEAD sinks"). Reuse the same fixed synthetic canary values as the scan's search patterns rather than inventing new ones (security-plan §Secret Management).
- Pinned-action form: `uses: owner/repo@<40-hex-sha> # vX.Y.Z`. Reuse the four SHAs recorded in security-plan §Dependency Security → CI integration.
- Uploads run in scan-gated order: scan first (`if: always()`), then uploads that depend on a clean scan. Uploaded homes hold only synthetic fake-agent content, consistent with security-plan §Data Protection → Repository fixtures (probe prompts must be synthetic).
- Keep `target/e2e-home/` out of git, per security-plan §Bootstrap phases → `secret-scanning-ci-gate`: "`.gitignore` excludes any local `--home` test directories". Whether `.gitignore` or `target/` already covers every test-home root is research's question.

## Anti-patterns to avoid
- NEVER reference a GitHub Action by a mutable ref (security-plan §Security Anti-Patterns → Code Patterns).
- NEVER write to stderr from `viola hook` or exit non-zero from it, and NEVER print an anyhow chain that still holds a serde_json or serde_path_to_error source (security-plan §Security Anti-Patterns → Logging).
- NEVER write the GUI token, `Cookie`, `?t=` query or any R8-stripped `CLAUDE*` value into logs, `diagnostics/` or fixtures. Uploaded artifacts count here (security-plan §Security Anti-Patterns → Secrets).

## Contract bindings
- The obs §9 `secret-scan` step (the scan mechanism, owned by obs) checks security's NEVER-log floor (the subject, security-plan §Bootstrap phases → `logging-redaction-wire`). test-plan §6 "Error sanitization and secret scan" is the test-side enforcement, and test-plan §3 `cleanup` step 6 / `AGENT_RUN_KEEP_HOMES=1` keeps the homes alive for the scan. All three must name the same value set.
- The CI security gate (zizmor, `cargo deny check`, pinned actions and permissions) lives in the same `ci.yml` as the obs gates and the tests jobs: one workflow, with security as a job (security-plan §Dependency Security → CI integration ↔ test-plan CI Integration).
- The hook fail-open rule (security-plan §Error Handling) meets obs's panic-hook-first gate and the CLAUDE.md "hook panic exits 0" invariant.
