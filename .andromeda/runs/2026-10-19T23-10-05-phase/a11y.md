# a11y extract

## Relevance
partial — the chunk is ledger-row probe and confirm-path work (no new UI), but it touches three a11y-held surfaces: `viola verify`'s step-line output (P6), the `send` paste / confirm path that the human-keystroke boundary binds (P4), and the folded macOS flake, whose two failing cases include an a11y output-discipline witness (`cross_list_rows_print_no_sgr_under_no_color_dumb_piped_or_json`).

## Constraints
- a11y-plan §4 (P6) requires `viola verify` output to stay linear and static, as `[NN/NN] … pass|fail` step lines with no `\r` redraw, cursor movement or spinner. Any change to the step lines or the summary that a row fix brings (for example a row's verdict wording) keeps that form. Whether the current verify output already meets it is research's question.
- a11y-plan §11 Visual bans colouring `fail`/`unable`, and bans emitting SGR under non-TTY, `NO_COLOR`, `TERM=dumb`, `--json`, `viola run` or a passed `viola revive`. A per-row failure reason added to `verify`'s output (the scope notes the verdicts give none) is held to this.
- a11y-plan §8 Error recovery requires every human-mode CLI refusal except `unknown` to print `unable <reason> <detail>` and then a final `hint:` line, with a typed exit code. If the chunk adds or rewords a `send` refusal on the confirm path (for example `no-prompt-submitted` / `unconfirmable` under a changed local-command confirm), it keeps that shape. `--json` carries no hint.
- a11y-plan §8 Timeout extensions requires the confirm windows (`CONFIRM_WINDOW_FALLBACK` 10 s, `COMPACT_CONFIRM_WINDOW` 40 s PROVISIONAL) and the readiness gate's `GATE_MAX_WAIT` to bound only the driver. A retuned window or a changed `/clear` / `/compact` confirm takes no key and blocks, refuses or delays none, and leaves the wheel untouched.
- a11y-plan §11 Keyboard bans blocking, refusing or delaying a human keystroke past the current atomic paste. A change to how `send` types a paste (the `paste-newline` path, the exact match, framing) keeps the paste one atomic write. The scope's case (b), where product reliance changes, is where this is at risk.
- a11y-plan §11 Universal bans parsing the rendered `claude` TUI screen for content (R7). A corrected probe oracle, or a product confirm that follows a changed CLI, rests on hook post-conditions or signature-only screens, never on screen content.
- a11y-plan §10 sets the zero-flakiness rule (`retries: 0`, a flake keeps the chunk red until its root cause is fixed). The folded macOS readiness flake, which failed `cross_list_rows_print_no_sgr_under_no_color_dumb_piped_or_json` and `cross_list_rows_print_escaped_in_the_captions_columns_in_every_mode`, closes only on its found cause, never on a green re-run.

## Patterns to follow
- The P6 output-discipline witnesses that a11y-plan §4 lists (`tests/support/sgr.rs` `redraws`, assert_cmd checks on no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`) as the shape for any new or changed `verify` output assertion.
- The stop table in `tests/cli_verify.rs` (the interrupted `unable:` / `hint:` pair, a11y-plan §8 Error recovery) as the precedent for pinning a fixed `verify` stderr pair by literal.
- The keyboard harness's readiness-gate case `send_under_the_paste_hint_a_human_key_during_the_gate_wait_wins`, sequenced on the `channel-request` line and the `wheel` record and never on a timer (a11y-plan §3 Keyboard test harness), as the model for any new boundary case on a changed `send` path.
- The P4 zero-viola-bytes outer-PTY comparison (a11y-plan §3 Keyboard test harness) re-run unchanged against any fake-agent path the chunk changes or replays from new `fixtures/claude/2.1.302/` captures.

## Anti-patterns to avoid
- Closing the macOS flake by re-running, or by adding a retry or `#[ignore]` (a11y-plan §11 SLO bans retry-once; a11y-plan §10 sets zero-flakiness).
- Reading the rendered `claude` screen for content to repair an oracle (a11y-plan §11 Universal, R7).
- Adding a colour, spinner or redraw to `verify`'s per-row output while surfacing a failure reason (a11y-plan §11 Visual / Motion).

## Contract bindings
- a11y ↔ tests: the P4 / P6 cases are ordinary nextest cases inside the per-OS `test` job's `coverage` suite, behind `gate --require coverage,doctest` with skips never allowed. No new `suite` value is added (a11y-plan §3 CI integration, §9). The flake fix therefore lands as a nextest-level cause fix, not as a harness or retry change.
- a11y ↔ design: any new `verify` failure text follows design-system cli pattern 2 (the `unable:` / `hint:` fixed-message form) that a11y-plan §8 Error recovery cites.

## Acceptance criteria contributions
- (a11y) If `verify`'s output changes, its human-mode output stays `[NN/NN] … pass|fail` step lines with no SGR on `fail` and no ESC byte under non-TTY / `NO_COLOR` / `TERM=dumb`, checked by assert_cmd on all three OS legs (per a11y-plan §4 P6).
- (a11y) The P4 boundary cases (zero viola bytes on the outer PTY, a human key during a gated or typed `send` wins the wheel and reaches the child) stay green on all three OS legs against the changed `send` paste / confirm path (per a11y-plan §3 Keyboard test harness).
- (a11y) `cross_list_rows_print_no_sgr_under_no_color_dumb_piped_or_json` and `cross_list_rows_print_escaped_in_the_captions_columns_in_every_mode` are green on `macos-latest` with the readiness flake's root cause named, and no retry or skip is added (per a11y-plan §10 SLO Invariants & A11y Budgets).
- (a11y) Any new or reworded human-mode `send` refusal on the confirm path prints `unable <reason> <detail>` and then a final `hint:` with a typed exit code, pinned by literal (per a11y-plan §8 Error recovery).
