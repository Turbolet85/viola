# tests extract

## Relevance
relevant: the chunk widens the strict-modes entry-point set, adds the Windows DACL proof of `check_instance`, and touches the seeded-home carve-out, the pinned-exe re-hash, the plugin rewrite and the single-writer negatives, all of which test-plan names as owed to "Home and code-bearing file integrity".

## Constraints
- Every strict-modes refusal has a fixed verdict per surface: exit 1 for `run` / `mcp` / `viola revive`, hook exit 0 with no output (and, for the statusline arm, nothing under the home read or opened after a refused check), and CLI exit 21 for every other verb. Each new entry point this chunk guards (`send`, `wait`, `last`, `answer`, `pause`, `release`, the hook events, the `mcp` frame tools, `verify`'s stamps read) needs a case asserting its verdict (per test-plan §5 Integration Test Strategy, Cross-module patterns › On-disk).
- A witness for a check placed before the role-file open has to read the directory's mode back after the refusal, because opening a role file narrows an existing home to 0700 and a check placed after it would pass a 0770 home. The `link` / `unlink` case is the precedent. Whether each verb's check already sits before its open is research's question (per test-plan §5 Integration Test Strategy, Cross-module patterns › On-disk).
- Windows strict-modes is unit-tested over synthetic SDDL descriptors fed to the descriptor-check function. A widened DACL on an instance tree on Windows is not covered by any test and is owed to this route entry (per test-plan §4 Unit Test Strategy, viola-state). Only the foreign-owner-SID and non-persistent-ACL descriptors may be stubbed, because the filesystem is not mocked (per test-plan §8 Mocking & Stubbing Discipline, What to mock › Filesystem).
- Windows x64 root starts `seed_conpty` the home before viola runs, so a seeded home skips viola's own DACL at creation and fails `check_instance` on Windows. This entry owns making the seed let viola create the home first. Until then, a case that drives a check-guarded path on every OS starts from `stamped_home` (per test-plan §5 Integration Test Strategy, Setup / teardown lifecycle; §3 Test data bootstrap, Mechanism).
- The harness never pre-creates a `--home`. It passes a not-yet-existing `<parent>/home`, because a pre-created home inherits the workspace ACL and fails the Windows strict-modes check. Any change to the seed or to home creation must keep that order (per test-plan §3 `boot`, step 2).
- On-disk product state comes only from real viola runs. The only hand-made exceptions are the chaos tests' corruption of files viola wrote, `seed_conpty`, and the server-identity impostors' test-built `snapshot.json`. A single-writer or re-hash case may not plant `stamps.json` or `snapshot.json` by hand (per test-plan §7 Test Data & Fixtures, Seed strategies).
- The `RUNNER_TEMP` negative case (a not-yet-existing `--home` outside `%USERPROFILE%` gets a protected DACL whose ACEs are exactly the user and SYSTEM, and a pre-existing directory with an inherited broader ACL is refused with exit 1) is owed to this route entry. Its home goes under `target/e2e-home`, never `%TEMP%` (per test-plan §6 E2E Test Strategy, Security control negatives).

## Patterns to follow
- `tests/cli_links.rs` `link_verbs_refuse_a_widened_instance_before_any_log` (`cfg(unix)`) widens the driven instance while its wrapper runs. It asserts exit 21 in both modes, the fixed `unable:` / `hint:` pair or the `instance-unreachable` document, no line in the verb's log, no frame at the wrapper, and the mode read back as found. Its remove-the-guard control moves the check and reads red (per test-plan §6 E2E Test Strategy, Exit-cause matrix).
- `tests/security_negatives_server_identity.rs` runs one negative per verb across eight verbs in both modes, each with a positive control against the recorded wrapper. That shape fits the strict-modes negatives of the frame verbs this chunk guards (per test-plan §6 E2E Test Strategy, Security control negatives › Server identity).
- `wipe_scratch_takes_an_instance_tree_the_check_accepts_where_a_plain_dir_does_not` is a `#[cfg(windows)]` unit on CI's `windows-2025` leg. It pairs a tree that passes `check_instance` with a sibling granted Users write through `icacls` (its exit asserted) that reads `Writable`. It is a working form for the Windows instance-tree proof (per test-plan §3 `run`, `--mutants` host scratch).
- The `strict_instance_*` unit cases (five widened modes, a viola-written tree passes, a missing instance dir passes, an unstattable path is unreadable) are the table a Windows DACL row joins (per test-plan §4 Unit Test Strategy, viola-state).
- Path 1's tamper-and-rewrite steps cover pinned-exe re-hash and per-start plugin rewrite: one byte overwritten at `pinned_bin` exits 1, and a sentinel in `plugin/` hooks.json and the Unix `settings.json` is gone after restart, with absolute `pinned_bin` commands (per test-plan §6 E2E Test Strategy, Scenario: Path 1).

## Anti-patterns to avoid
- Never treat a Linux-only local run as proof for Windows or macOS. The DACL check and the seeded-home question (CARRYs 12 and 13) are proven only on CI's `windows-2025` leg (per test-plan §11 Test Anti-Patterns, Test Strategy).
- Never hand-write `ledger/stamps.json`, `snapshot.json` or `budget.json`. Never mock on-disk state at integration level; use a real tempfile home (per test-plan §11 Test Anti-Patterns, Test Data / Integration).
- Never use `#[ignore]` or a retry to park a Windows-only red. The chunk stays red until the root cause is fixed (per test-plan §10 Quality Gates & Coverage Targets, Zero-flakiness budget).

## Contract bindings
- tests ↔ obs: a refused check writes no log line (obs-plan §10 exemption 7), and the cases assert that no line was added. Every home stays under `target/e2e-home` so that obs-plan §9's G2, G4, secret scan and uploads cover it. A change to the seed must not create a third carve-out outside the scans (test-plan §5 Setup / teardown lifecycle; §3 Test data bootstrap).
- tests ↔ security: the entry-point set and the dated strict-modes exceptions this chunk closes are security-plan §Local trust boundary's. Test-plan §6 Security control negatives (single writers, umask-independent modes, Windows `--home` DACL) is the negative-test body for those controls.
- tests ↔ architecture: test-plan §6 Scenario E5 steps 1–3 (readers onto `read_snapshot_or_replay`) are owed to this entry, but whether they are built depends on the founder's P4 ruling (scope CARRY 19). If they are built, E5's two set-against signals need restating: start appends `wheel{holder:"driver"}`, and the replay writes no file.

## Acceptance criteria contributions
- Each newly guarded entry point refuses a group-writable home or instance before any role file opens, in both `--json` and human modes. The verdicts are: CLI exit 21 with the `instance-unreachable` document, MCP `instance-unreachable` with `detail: null`, hook exit 0 with no body. In every case no line is added to any log and the mode reads back as found (per test-plan §5 Integration Test Strategy, Cross-module patterns › On-disk).
- On `windows-2025`, `check_instance` refuses an instance tree whose DACL grants another principal write, beside a passing control tree. The seeded-home refusal is either removed by letting viola create the home first, or recorded with the refused DACL read (per test-plan §4 Unit Test Strategy, viola-state; §5 Integration Test Strategy, Setup / teardown lifecycle).
- `tests/cli_controls_not_disableable.rs` holds the 0770 `--home` → exit 21 control negative in every row. Whether it already does is research's question (per test-plan §5 Integration Test Strategy, Cross-module patterns › CLI).
- `agent-run pre-push` is green on Linux (`run --coverage` then `gate --require coverage,doctest`), and CI is green on all three OSes with per-OS coverage at lines ≥ 85, functions ≥ 95, regions ≥ 80 (per test-plan §3 `pre-push`; §10 Quality Gates & Coverage Targets, Coverage thresholds).
