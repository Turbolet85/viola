# obs extract

## Relevance
relevant — the chunk moves strict-modes checks ahead of role-file opens on every frame verb, `hook`, `mcp`, `verify` and `run`, re-hashes pinned and ConPTY binaries, and checks diagnostics files before writing them, so it touches init order, the refusal-line rules, the closed `detail` catalog and the exemption list of the zero-unlogged-panics invariant.

## Constraints
- Init step 4 requires the order "home strict-modes first, diagnostics init after": nothing under the home, `diagnostics/` included, may be created or opened before the role's check passes, and a refused home gets no diagnostics line (`hook` fails open with exit 0). The anchors for this order are the per-role ones that already stand: `viola hook statusline` and `viola link` / `viola unlink` run `check_instance` before `client::start`'s role-file open, because that open narrows a 0770 home to 0700 (per obs-plan §3 OTel SDK init). Whether `client::start` for `send`, `wait`, `last`, `answer`, `pause`, `release`, `hook`'s nine events, `verify` and `run` already keeps this order is research's question.
- Before the first write, `diagnostics/` and every diagnostics file opened (the role file, and later the lazily opened `instances/<name>/diagnostics/detail-<process>.ndjson`) require the same checks as the home: on Unix `lstat` owner == euid, `mode & 0o077 == 0`, no symlink, and `O_NOFOLLOW`; on Windows the owner and the DACL. A failed check is handled like a failed open: the writer becomes `std::io::sink` (stderr JSON for `mcp` only), a failed detail open drops only the detail line, and nothing reaches stderr (per obs-plan §3 OTel SDK init). Whether the Windows owner + DACL read is made before the detail file opens is research's question.
- A refused check made before init is a bounded exemption of the zero-unlogged-panics invariant. Today the list names only revive, `hook statusline`, `list`, `mcp`'s home check, `plugin install` and `link` / `unlink` (exemptions 1 and 7). Each entry point this chunk adds (the six CLI frame verbs, `hook`'s nine events, `mcp`'s frame tools, `verify`, `run`) must be added there by amendment, or must log its refusal after a passed init. The plan names neither choice for these verbs. CARRY 14 leaves "a refused check writes no line" open for the founder (per obs-plan §10 SLO Invariants & Telemetry Budgets, Zero unlogged panics, bounded exemptions 1 and 7).
- The closed `detail` catalog already holds `strict-modes-failed` on `process-exit` exit 21 and on `hook-decision`, where no arm of the build writes it yet. It also holds `pinned-hash-mismatch` on `process-exit` exit 1, and `parse-rejected{parser:"ledger-stamps", detail:"strict-modes-failed"}` at WARN for `run`'s version gate. A refusal that is logged takes one of these words with no path or pid, and any new word needs a Decisions Log entry and a `schemas/diag-line.v1.json` change (per obs-plan §6 Log Coverage, log-details: process-exit exit 21 / hook-decision fail-open codes / Filesystem refusals).
- The plan's own text says `strict-modes-failed` "cannot occur" on `wait` / `last`, with "its check owed to the route entry 'Home and code-bearing file integrity'". The chunk closes that owed check, so the scenario text needs an amendment that says what a refused check writes on those verbs (per obs-plan §4 Span / Trace Coverage, Scenario: `wait` / `last` event-driven readback).
- On Windows, `run.conpty_sideload`'s `outcome` is closed to `loaded|hash-mismatch|unreadable|load-failed|not-built`, and so is `sideload_fallback` on `process-start{subject:"claude-child"}`. A sideload outcome is never a refusal and never an exit change, and it never carries a companion path or hash. If the owner/DACL check added to `conpty/` maps to a new word, it needs D-36's schema and Decisions Log route (per obs-plan §4 Span / Trace Coverage, Scenario: `viola run` start sequence to child spawn).
- The `pinned_bin` path, `endpoint`, pids, start times and home paths never reach a home-level line, span or `detail` code. `run.pin_copy` carries only `outcome` (`ok|pinned-hash-mismatch`) (per obs-plan §8 PII Scrubbing & Compliance, Data classification rules).

## Patterns to follow
- `viola link` / `viola unlink`: `check_instance` on the home and `instances/<driven>` before `client::start`'s log init. A refusal opens no role file, writes no `process-start` / `process-exit` and leaves the mode as found. The log opens only after the check passes, followed by the liveness pre-check and the server check (per obs-plan §3 OTel SDK init, per-role anchor `cli`).
- `viola hook statusline`: the instance check before the hook init. A refused instance returns exit 0 with no `config.json` read, no role file, no `hook-invoked` / `hook-decision` and the home left as found (per obs-plan §3 OTel SDK init, per-role anchor `hook`).
- `run`'s version gate reads the stamps through `read_stamps_strict` inside `state.ledger_read`. A refusal is `parse-rejected{parser:"ledger-stamps", detail:"strict-modes-failed"}` and `cli_verified:false`, with no path or stamp content. This is the model for `verify`'s `update_stamps` read (per obs-plan §4 Span / Trace Coverage, paths: Capability ledger).
- MCP: `instance-unreachable` is logged by no line. Its outcome stays inside `mcp.tool_call` and the `isError` code is its only record (per obs-plan §7 Error Capture & Reporting, Error classes captured).

## Anti-patterns to avoid
- Opening a role or diagnostics file, or calling `create_private_dir` on the home, before the strict-modes check. A check made after the open passes a home at 0770 (per obs-plan §3 OTel SDK init).
- Putting a path, pid, start time, endpoint or hash inside a `detail` code or any home-level field (per obs-plan §11 Obs Anti-Patterns, PII Scrubbing).
- Adding an `event` value or a closed-enum word (a `detail`, `outcome` or `sideload_fallback` value) without a Decisions Log entry, and writing anything to stderr from a refused `hook` (per obs-plan §11 Obs Anti-Patterns, Logs).

## Acceptance criteria contributions
- For each entry point this chunk adds, a home or instance tree at 0770 (Unix), or with a widened DACL (Windows), is refused before any role file opens. The refused home's mode is left as found, no `process-start` is written, and the result is exit 21 for CLI frame verbs, exit 0 with empty stdout and stderr for `hook`. A test reads both the mode and the absence of the line (per obs-plan §3 OTel SDK init).
- Every line the chunk adds validates against `schemas/diag-line.v1.json` / `diag-detail.v1.json` under G4. No home-level line carries a path, pid, start time, endpoint or hash, and the secret scan stays at 0 hits (per obs-plan §10 SLO Invariants & Telemetry Budgets, Error budget).
- The §10 bounded-exemption list and the §4 `wait` / `last` scenario text are amended in the same chunk to name each new pre-init refusal, so no panic is left that an exit code evidences without a line and no exemption covers (per obs-plan §10 SLO Invariants & Telemetry Budgets, Zero unlogged panics).
- With the instance check in the timed path, `gate --require perf` still passes all five hook rows (`session-start`, `user-prompt-submit`, `stop`, `session-end`, `pre-tool-use`) under hyperfine `max` < 1.0 s, and the error-free `hook` path keeps exactly one log `open` (per obs-plan §10 SLO Invariants & Telemetry Budgets, Performance budgets).
