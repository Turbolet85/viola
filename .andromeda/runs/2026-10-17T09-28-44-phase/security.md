# security extract

## Relevance
relevant — the chunk adds the MCP stdio surface (Threat Model's "MCP over stdio" vector), a new process that writes `send` / `wait` / `last` / `answer` channel frames, a new `.mcp.json` exec command, and the workspace's one Tokio + rmcp dependency graph.

## Constraints
- Server-side re-validation of every MCP tool input, the schemars schemas advisory only: `target` into `ViolaName::try_new` before any `instances/<name>` join, `dialog_id` into `u64`, `response` into the closed channel enums, and `validate_paste_text` on `send.text` and on the free-text answer fields (`message`, `answers.*`), reject-never-strip; the `send` client side also refuses an empty typed text as `not-delivered` / `empty-text` before any frame, as CLI `send` does (per security-plan §Input Validation, rows "MCP tool inputs" and "Paste text" and "Dialog free text"). Whether the wrapper's own re-validation already covers a frame an MCP client writes is research's question.
- Frame-before-verification ban: no channel frame (`send`, `wait` / `last`, `answer`) may be written before server verification (pid + start time, Unix euid) against a `snapshot.json` that passed strict-modes in the same process; the seven dated exceptions are each closed to borrowing ("no other frame or process may borrow any of them"), so the MCP server writing frames after only a liveness pre-check needs either the verification in this chunk or a new dated exception — a boundary decision for the founder's own word, never a decisive lean (per security-plan §Security Anti-Patterns → Authentication, and §Authentication & Authorization, row "IPC client-side server verification").
- `mcp` is named in the strict-modes entry-point set: the home / `instances/<name>/` / trusted-file owner-and-mode check (with the `mode & 0o077` read rule) before any `snapshot.json` value is used, and on failure `mcp` exits 1 (per security-plan §Authentication & Authorization, row "`~/.viola/` access control"). Whether that set membership is to be met here or folds into the same founder fork as the frame verification is research's and P4's question.
- External errors are code-only: an MCP `isError` result carries only the Conventions `structuredContent` codes (`refusal` / `detail`, or `error: instance-unreachable | wrapper-fault`), no anyhow chain, no absolute path, no upstream text, no serde_path_to_error path or value, no internal type name; `McpError`'s `Display` uses fixed messages with path- or payload-bearing fields excluded (per security-plan §Error Handling).
- rmcp features exactly `server` + `transport-io`; `transport-streamable-http-server` and `auth` stay banned by `deny.toml` `[[bans.features]]`; rmcp takes the minor range `>=3.4.1, <3.5` with `Cargo.lock` resolving `>=3.4.1` (per security-plan §API Security, and §Dependency Security "Pinning").
- The `.mcp.json` the embedded plugin carries registers `viola mcp` by the absolute pinned `bin/<version>-<hash>/viola(.exe)` path, never a PATH lookup, and `plugin/<version>-<hash>/` is rewritten at every start through the shared tempfile `persist` helper, never reused (per security-plan §Security Anti-Patterns → Universal, and §Bootstrap phases "auth-scaffolding-baseline").
- The MCP `list` tool's `claude agents --json` read, if this chunk builds it, is a direct spawn under the R8 strip, stdout through `take(MAX_FRAME + 1)`, killed at 5 s, parsed tolerantly into rows or the closed `AgentsFailure`; an unwrapped row's `name` is never a `ViolaName` or `target` (per security-plan §Input Validation, row "Child process output"). The plan reads "`mcp` spawns none (its `list` is not built)" — the tool's read is new surface to plan against that row.

## Patterns to follow
- The shared validators live in `viola-core` and every surface calls the same function: `viola_core::validate_paste_text`, then the typed-text rule (`viola_agent_claude::hook::typed_text`) and the client refusal order of `refusal_of` in `src/cmd/send.rs` (`control-character`, then `empty-text`) (per security-plan §Input Validation, row "Paste text").
- The CLI client verbs' bounded readers and code-only documents: `Read::take(MAX_FRAME)` before every `read_line` / `read_to_end`, serde_json default depth, closed codes only in every external result (per security-plan §Input Validation "Constants", and §Bootstrap phases "error-sanitization-wire").
- The one bounded `claude agents --json` read shared by `list`, `revive` and verify's Run B (`run::agents::read_here` per the plan's Child executable resolution row), reused rather than re-spelled for the MCP `list` tool (per security-plan §Input Validation, row "Child executable resolution").
- The NEVER-log floor's scope rule: `wait` / `last` results over MCP carry content by design; outside those payloads user content and drift reports go only to `instances/<name>/diagnostics/` (0600) (per security-plan §Bootstrap phases "logging-redaction-wire").

## Anti-patterns to avoid
- NEVER trust schemars MCP schemas alone; NEVER join `instances/<name>` with an MCP `target` that did not come out of `ViolaName::try_new`; NEVER use a `claude agents --json` row `name` as a `target` (per security-plan §Security Anti-Patterns → Input).
- NEVER echo serde_path_to_error drift reports or anyhow chains into MCP `structuredContent`, and NEVER expose absolute paths in any external error (per security-plan §Security Anti-Patterns → Logging).
- NEVER treat the `from` param (taken from the server's own `VIOLA_NAME`) as an authenticated identity; leaving `release` / `pause` / `link` / `unlink` off the tool list is an affordance, not enforcement, and the wrapper's `release-from-driver` `-32602` stays the guard (per security-plan §Security Anti-Patterns → Authentication, and §Authentication & Authorization row "Driver-originated `release`").

## Contract bindings
- security ↔ tests (CI supply-chain gate): `viola-mcp` is the first member to enable `viola-channel[tokio]`, so the per-sync-crate `deny-sync.toml` sole-root tokio ban must keep `viola-channel`'s own normal graph covered by another form, and `scripts/deny-probes.sh` must still prove every ban fires; the rmcp `[[bans.features]]` gate sits beside the non-vacuous `cargo tree -e features` assertion (per security-plan §Dependency Security, `deny.toml` additions and CI integration).
- security ↔ obs (NEVER-log floor ↔ artifact canary scan): any new `mcp` role file and its diagnostics fall under `viola-harness secret-scan` (stripped `CLAUDE*` needles, content canary in home-level role files, 0600 diagnostics) (per security-plan §Secret Management "Secret scanning in CI").
- security ↔ arch (Conventions refusal codes): the MCP `isError` `structuredContent` codes are Conventions' closed set, including the `budget-paused` refusal with detail `five-hour` | `seven-day` whose hint never names `release` (per security-plan §Error Handling).
- security ↔ dialog gating: an `answer` tool's non-`null` decision flows only under a strict-modes-read `viola verify` stamp for the child's CLI version, else `unverified-cli`; the driver-prompt-injection residual is accepted (per security-plan §Authentication & Authorization "Accepted risk (driver prompt injection)").

## Acceptance criteria contributions
- An MCP `send` with `text` holding ESC (or any refused C0 / DEL / C1) returns an `isError` result `not-delivered` / `control-character` and writes no frame; an empty or newline-only `text` returns `not-delivered` / `empty-text`; an invalid `target` is refused before any path join (per security-plan §Input Validation).
- Every MCP refusal and fault result's `structuredContent` holds only closed codes (`refusal` / `detail` or `error: instance-unreachable | wrapper-fault`), and a test asserts no home path, username or upstream text in it (per security-plan §Error Handling).
- `cargo deny check` passes with the rmcp `[[bans.features]]` ban live, `cargo tree -e features -p viola --edges normal` shows rmcp at exactly `server` + `transport-io` (asserting rmcp present first), and `bash scripts/deny-probes.sh` still proves every ban fires with `viola-channel`'s normal graph tokio-ban-checked (per security-plan §Dependency Security).
- The tool list holds exactly `send · wait · last · answer · list` (no `pause`, `release`, `link`, `unlink`), and the embedded `.mcp.json` `command` is the absolute pinned path (per security-plan §Security Anti-Patterns → Universal).
