# arch extract

## Relevance
relevant — the chunk lands the plan's sixth product crate (`viola-mcp`), the `mcp` subcommand and role, the fourth interface (MCP tools), the `.mcp.json` registration and the workspace's only Tokio runtime.

## Constraints
- Tokio is confined to `viola-mcp`: architecture §Established Decisions [Concurrency / Backend Framework] (KEYSTONE) requires a sync std-thread core with Tokio 1.53.1 built only in `mcp`. CI enforces it through the sole-root `deny-sync.toml` ban per `scripts/sync-crates.txt` crate plus a `cargo check` of the sync crates without `viola-channel`'s `tokio` feature, so `viola-mcp` never joins that list. Per architecture §Cross-cutting Patterns (Tokio containment), new code on the `run`, `hook`, `send` or channel-server paths stays blocking.
- Crate edges are fixed by architecture §Infrastructure Patterns → Crate dependency direction: `viola-mcp` → `viola-core`, `viola-channel[tokio]`, `viola-state`, `viola-agent-claude`, rmcp, schemars, tokio, and nothing else. It may not reach the root bin. architecture §Established Decisions [Module Boundaries] requires that only `viola-mcp` lists `tokio`, and that `viola-channel`'s Tokio client sits behind a `tokio` feature that only `viola-mcp` enables. The CLI's agents read (`run::agents`, `run::resolve_program`, `version_gate::run_capped`) and its `--json` document builders live in the root bin today. How MCP `list` and the CLI-parity results reach them without a back-edge is research's question.
- The tool surface is fixed. architecture §Established Decisions [MCP] requires rmcp 3.4.1 over stdio with exactly the tools `send · wait · last · answer · list`, and the inputs `send {target, text}`, `wait {target, after?, timeout_ms?}`, `last {target}`, `answer {target, dialog_id, response}` (response in the channel `answer` shape) and `list {}`. `target` is a `ViolaName`, and the server adds `from` from its own `VIOLA_NAME`. `release`, `pause`, `link` and `unlink` stay off the tool list. Per architecture §Stack and Technologies, rmcp takes features `server` + `transport-io` and schemars 1.2.2 provides the input schemas. architecture §Infrastructure Patterns → Build system requires rmcp's minor to be pinned (`~3.4`) in `[workspace.dependencies]`.
- The result mapping is fixed by architecture §Conventions (Error handling schema, MCP bullet). A success is `isError: false` with the channel `ok` payload as `structuredContent`; for `list` that payload is the caller-side `{items, budget, skipped}`. A refusal is `isError: true` with the same `refusal` + `detail`. An unreachable instance or a wrapper protocol fault is `isError: true` with `{"error":"instance-unreachable"|"wrapper-fault","detail":…}`, as in CLI `--json`. Only faults on the MCP connection itself are JSON-RPC errors. The refusal codes, `detail` sets and per-verb refusal order are those of architecture §Conventions (`RefusalReason`), `budget-paused` / `five-hour` | `seven-day` included.
- Every call stays below the client's tool-call timeout. architecture §Established Decisions [Delivery Confirmation] bounds a `send` at the readiness gate's maximum wait, plus the atomic paste, plus the window: 18.5 s with the compiled 8.5 s and 10 s. On the MCP surface that total must stay below the client's tool-call timeout. architecture §Established Decisions [MCP] leaves the default `timeout_ms` for MCP `wait` as an open item that must also stay below it. Choosing that default is this chunk's decision.
- The server's identity and home come from `VIOLA_NAME`. architecture §Cross-cutting Patterns (Identity by instance, never by location) requires every MCP call to find its instance through `VIOLA_NAME` or an explicit `ViolaName`, never through the working directory. architecture §Occupied Resources (Environment variables, `VIOLA_DIR`) requires `mcp` to derive the viola home as the grandparent of `VIOLA_DIR`. It also records that the CLI verbs' `VIOLA_DIR` step is NOT ratified. Whether `mcp` shares `resolve_home` / `canonical_home` and inherits that unratified status is a question for research and P4. Per architecture §Occupied Resources (IPC endpoints), `mcp` connects to the snapshot's recorded `endpoint` and rebuilds the path by rule only when the snapshot is missing or unreadable.
- Output channels and the role log are fixed. architecture §Cross-cutting Patterns (Diagnostic output channels) requires `mcp` to write only MCP frames to stdout and to log codes only to the home-level `diagnostics/mcp.ndjson`. It writes JSON to stderr only when that file cannot be opened, and content-bearing detail goes only to `instances/<name>/diagnostics/detail-<role>.ndjson`. architecture §Design Philosophy (No daemon) names `mcp` as the one long-running non-wrapper process, and it owns no endpoint.

## Patterns to follow
- Thin adapter over the channel. architecture §Established Decisions [API Style] gives the channel the same JSON-RPC 2.0 shape as MCP "so `mcp` is a thin adapter". Every forwarded `params` carries `v` and the sender's `CARGO_PKG_VERSION`. Per architecture §Conventions, `list` is no channel method: architecture §Standard Contracts requires `list` to be a caller-side read of `instances/*/`, `budget.json` and one `claude agents --json` read joined by `viola_state::board::join`, failing open to `status: unknown`. That section records "`mcp`'s `list` is not built".
- Plugin registration by pinned path. architecture §Established Decisions [Deployment / Distribution] (KEYSTONE) embeds `.mcp.json` via `include_str!` and rewrites it on every start under `plugin/<version>-<hash>/`. It requires the copy's forward-slash path to be substituted into every exec-form `command`, and holds `{"mcpServers": {}}` only until the `mcp` verb exists. Hooks and MCP never search PATH. architecture §Occupied Resources (Claude Code integration names) requires the MCP server name `viola` and the tools `send`, `wait`, `last`, `answer`, `list`.
- Implicit links from `from`. architecture §Established Decisions [Links] requires the MCP server, like the CLI, to pass its own `VIOLA_NAME` as `from`. The driven wrapper records the link, so the server adds no link control of its own.
- Errors. architecture §Conventions (Rust error types) requires one thiserror enum `McpError` for the crate, with fixed messages, and `anyhow` only in the root bin. architecture §Established Decisions [Error Handling] keeps the anyhow chain only in the owner's `detail-<role>.ndjson`.
- Tolerant own formats. architecture §Established Decisions [Validation] allows no `deny_unknown_fields` on viola's own formats, so the server's forwarded and returned payloads stay versioned-tolerant. The schemars schemas are advertised only, and the server re-validates.

## Anti-patterns to avoid
- No Tokio, rmcp or `tokio`-featured `viola-channel` edge into any sync crate or the `hook` path. Never drop `viola-channel` from tokio-ban coverage. architecture §Infrastructure Patterns → Build system records that the feature owner false-fails as its own sole root once `viola-mcp` enables `tokio`, and says it "is covered through the sync roots that depend on it". By architecture §Infrastructure Patterns → Crate dependency direction, no listed sync crate depends on `viola-channel`. Whether coverage survives this chunk is research's question (CARRY 1).
- No network listener. architecture §Occupied Resources (Network) allows no listening TCP port, and the MCP server is stdio only. architecture §Infrastructure Patterns → Build system keeps the `deny.toml` feature bans on rmcp `auth` / `transport-streamable-http-server`.
- No driver-facing wheel or link verb. architecture §Established Decisions [MCP] keeps `release`, `pause`, `link` and `unlink` CLI-only: no tool, no hint and no description names them.

## Contract bindings
- arch ↔ security: architecture §Cross-cutting Patterns (Local endpoint trust boundary) defers per-connection proof to the security specialist. The MCP server is a new frame writer, and it needs either server verification or a dated exception. That choice is the boundary fork (scope), owned by security-plan.
- arch ↔ obs: the `mcp` role and its `diagnostics/mcp.ndjson` file (architecture §Cross-cutting Patterns, Diagnostic output channels) bind to obs-plan's catch-site and role catalogue (`src/main.rs` `role_of`, CARRY 3).
- arch ↔ tests/CI: the rmcp release-graph assertion (`cargo tree -e features -p viola --edges normal` showing exactly `server` + `transport-io`) is owed to this chunk by architecture §Infrastructure Patterns → Build system, beside the `deny.toml` feature bans and the per-sync-crate `deny-sync.toml` step of architecture §Infrastructure Patterns → CI/CD approach (CARRY 1 and 2).
- arch ↔ agent ledger: the `list` tool's agents join is the ledger row `agents-join`, per architecture §Standard Contracts (Session liveness). Plugin precedence between a `--plugin-dir` and an installed `viola` MCP server is a ledger row owed to "Optional plugin install", per architecture §Established Decisions [Plugin Scope], not to this chunk.

The `budget-paused` case is included.
