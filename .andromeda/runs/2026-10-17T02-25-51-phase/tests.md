# tests extract

## Relevance
relevant — the chunk is the CLI `--json` / typed-exit / hint / `--home` / `config.json` contract that test-plan §1, §4 (root bin), §5 (CLI) and §6 (Exit-cause matrix) name as the CLI verbs' test surface, and §6 Exit-cause matrix names this entry ("CLI machine contract") as the owner of `viola revive`'s `--json` document.

## Constraints
- Test-plan §1 Coverage scope (the entity "CLI verbs and the `--json` / exit-code contract") and §1 Surfaces under test (the cli surface) state `revive` takes no `--json` and gives no JSON document (exit 0 / 1 / 2, an `unable:` / `hint:` pair, `--list` rows). Test-plan §6 Exit-cause matrix (the `revive` exit-1 rows) assigns "the `--json` document" to "CLI machine contract". If this chunk adds a revive document, both §1 statements need a test-plan amendment in the same chunk. Whether revive gets a document at all is P3/P4's call against CARRY 2.
- Test-plan §1 Surfaces under test (cli) sets the CLI signal: exit 0, 1, 2, 10–14, 20 or 21, plus one JSON document on stdout, either `{"v":1,"ok":…}`, `{"v":1,"refusal":…,"detail":…}` or `{"v":1,"error":…}`. Human mode is checked by line match: `unable … ` plus a last-line `hint:`, and no SGR under non-TTY / `NO_COLOR` / `TERM=dumb`.
- Test-plan §4 root bin requires a unit table for the exit-code mapping from `RefusalReason` / fault to 0/1/2/10–14/20/21. It must include a literal unknown refusal string that deserialises to `unknown` and maps to exit 14 with a `--json` refusal document, never panicking and never mapping to 20. Test-plan §2 Test pyramid (Unit row) places that exit-code table in rstest 0.27.0 `#[case]` rows.
- Test-plan §5 Cross-module patterns (CLI) requires root `tests/cli_*.rs` to cover "the `--json` document per exit code". Test-plan §5 Cross-module patterns (CLI) also requires `tests/cli_controls_not_disableable.rs` to cover every `VIOLA_*` env var, global flag and `config.json` key with a completeness case. That case fails if `viola --help` lists a flag, or the config schema lists a key, that the table lacks. So `--home` and any `VIOLA_DIR` read this chunk adds to the CLI verbs, plus the keys `diagnostics_level` and `claude_env_keep`, fall under it. Whether the table already holds them is research's question.
- Test-plan §5 Cross-module patterns (Wrapper channel, out-of-range `Percent`) sets the threshold contract. A bad `five_hour` / `seven_day` value falls back to that key's default and never refuses a start, with exactly one `parse-rejected{parser:"config-json"}` line per bad key. Test-plan §5 Cross-module patterns (On-disk) fixes the strict-modes refusal exits: 1 for `run` / `mcp` / `revive`, 0 with no output for `hook`, and 21 for every other CLI verb.
- Test-plan §6 Exit-cause matrix requires each case to assert three things: the exit code, the `--json` document, and a last stderr `hint:` line that names that cause. A hint shared across causes fails the table, and no driver-facing hint contains `release`. Test-plan §6 Exit-cause matrix also records that the revive rows joining the rstest table and the unwrapped-name hint belong to "Exit-cause code catalogue", not to this chunk.
- Test-plan §6 Error sanitization and secret scan requires that CLI `--json` documents hold no absolute path, serde path or `Caused by`, that every -32603 is exactly `"internal error"` / `null`, and that the content canary never appears in a home-level `diagnostics/*.ndjson` line.

## Patterns to follow
- Use the one started-child guard and runner in `tests/support/cli.rs`: `Running`, `Ran`, `spawn` and `viola`, with stdout and stderr captured beside the exit code. Use `spawn_on` / `viola_on` for a planted bin dir, and run a plain `spawn` of `list` under an empty bin dir. No root test file defines its own copy (per test-plan §2 Test directory + naming conventions).
- Give each test a fresh home under `target/e2e-home` via `TestHome::new`. A case that drives a check-guarded path on every OS starts from `stamped_home`. A default-home case uses `TestHome::default_of_user` with `HOME` (`USERPROFILE` on Windows) set on that one child (per test-plan §5 Setup / teardown lifecycle and test-plan §7 Seed strategies).
- The existing `tests/cli_revive.rs` exit-1 cases are the model for revive outcomes: exit 1, one `process-exit` line with its closed `detail`, one `unable:` line, a distinct last `hint:` line, and no child. The two `--list` refusals and the clap exit 2 for a malformed `--id` follow the same shape (per test-plan §6 Exit-cause matrix).
- Name table cases with rstest `#[case::label]` and name tests `<subject>_<condition>_<expected>` (per test-plan §4 Conventions).
- `e5_list_reads_a_live_wrapper_through_the_replay` (`tests/cli_list.rs`) already reads one `state-recovered` line logged under a name. It is the existing witness CARRY 3's scanned-instance field would extend (per test-plan §6 Scenario E5).

## Anti-patterns to avoid
- Never take the product's own refusal ordering, exit mapping or row lists as the test oracle. Write exit codes and refusal words as literals, and never compare a `RefusalReason` or an exit code by its `Debug` string (per test-plan §11 Unit).
- Never set `VIOLA_DIR` / `VIOLA_NAME` with `std::env::set_var`; use `Command::env` per child. Never call `.env_clear()` without re-adding `LLVM_PROFILE_FILE` (per test-plan §11 Integration).
- Never hand-write `snapshot.json`, `ledger/stamps.json` or `budget.json` in a booted-wrapper test. A `config.json` value is planted by the test because viola only reads it (per test-plan §11 Test Data).

## Contract bindings
- tests ↔ obs (log format): a `cli` process writes `cli-<name>.ndjson` with `process`, `instance` (absent when null) and the closed `event` enum. `state-recovered` carries `corr` null, and a new field is obs-plan's to add, never a rename (per test-plan §3 Log format). If `viola revive --list` opens the `cli` role log, or `state-recovered` gains a scanned-instance field, every home-level line must still validate against `schemas/diag-line.v1.json` in the G4 step (per test-plan §6 Schema conformance).
- tests ↔ harness status: `agent-run status` nests the `viola list --json` document verbatim and reads its exit as `last_error` `list-exit-<code>` (per test-plan §3 Status endpoint shape). The harness runs that `list` with an explicit `--home` and with `VIOLA_NAME` / `VIOLA_DIR` / `VIOLA_BIN` removed (per test-plan §3 5-command implementation, `status`). So a `VIOLA_DIR`-grandparent step in the CLI's home resolution must keep `--home` first, or the harness reading changes.
- tests ↔ harness cleanup: `cleanup` step 4 requires `viola last <name> --json --home <home>` to exit 21 once the endpoint is gone (per test-plan §3 5-command implementation, `cleanup`).
- tests ↔ security: the CLI-and-env vector requires negatives for a `--home` / `VIOLA_DIR` failing strict-modes (exit 1 / 21 / hook 0), an out-of-range `Percent` in `config.json`, and "no env / flag / config disables a control" (per test-plan §1 Coverage triggers, security-vector-coverage (CLI and env)).

## Acceptance criteria contributions
- `scripts/agent-run.sh run --integration` passes with root `tests/cli_*.rs` cases. For each verb this chunk gives a document, they assert the one `--json` document and its literal exit for every outcome the verb reaches (0, 1, 2, 10–14, 20, 21) (per test-plan §5 Cross-module patterns (CLI)).
- A root-bin rstest `#[case]` table maps each `RefusalReason` and each fault to its literal exit. An unknown refusal string maps to 14 with a `--json` refusal document, never 20 and never a panic (per test-plan §4 root bin).
- Every refusal cause this chunk touches is asserted with its exit, its `--json` document (where the verb has one) and a last `hint:` that names that cause. The hints are distinct across causes and none contains `release` (per test-plan §6 Exit-cause matrix).
- The per-OS coverage gate holds: lines ≥ 85 %, functions ≥ 95 %, regions ≥ 80 % (per test-plan §10 Coverage thresholds).
