Retiring it means `--list` writes `process-start` / `process-exit` into `diagnostics/cli-<name>.ndjson` when an instance resolves (D-06), and the plan's exemption 6 text, the §4 cli-row "except `viola revive <name> --list`" clause and the §7 Panic hooks main-thread catch-site sentence on `--list` are amended together. Exemption 7 also covers `revive`'s start-arm refused check writing no line. That is the operator's answer, unruled by the founder, and it sits against his "structured log from every process" direction. The scope does not name it, so it is not this chunk's to change without his word.
- obs-plan §4 (Span / Trace Coverage, the `cli (short-lived verbs)` row) requires `viola list` to open its `cli-<name>.ndjson` only after its strict-modes scan has passed, and only when `VIOLA_NAME` parses. A refused scan opens no log and writes no `process-start` / `process-exit`. Security-plan §Input Validation also requires `check_instance` before any log opens, so a `--list` that newly opens a role log must place the open after that check. Whether `--list`'s two refusals (`strict-modes-failed`, `no-session`) then write a `process-exit` line is P3/P4's to settle against the closed detail catalog.
- obs-plan §4 (E5) requires each `state-recovered` line that `viola list`'s `board::read` writes to carry the caller's instance in `instance`, and owes naming the scanned instance to this chunk. obs-plan §6 (Additive field catalog) allows a field only when its `state-recovered` row names it. obs-plan §8 (Default-deny posture) requires every logged field to be in `schemas/diag-line.v1.json`'s per-event list, or G4 fails the build. The new field takes a `ViolaName` value only, never a path or pid (obs-plan §11 PII Scrubbing).
- obs-plan §6 (`detail` code catalog) closes `process-exit` details per exit: exit 1 is the listed 13-value enum; exit 21 is `instance-dead` · `strict-modes-failed` · `server-verify-failed`; exit 20 is `wrapper-fault`. A `--json` error document (`instance-unreachable`, `wrapper-fault`) and the `process-exit` detail logged for the same outcome must use codes from these closed sets. A new code needs the schema enum and catalog amended. Whether `instance-unreachable` maps to `instance-dead` in the log is research's question.
- obs-plan §2 (Telemetry Strategy, init order step 3) requires every process to resolve the home as `--home`, then the grandparent of `VIOLA_DIR`, then the default, before step 4 opens `diagnostics/<process file>`. So the CLI verbs' `--home` resolution decides which home's `diagnostics/` receives `cli-<name>.ndjson`. Whether the CLI verbs already take the `VIOLA_DIR` step is research's question (the scope reads that only `hook` does).
- obs-plan §6 (`detail` code catalog, `parse-rejected`) requires `config.json` rejections to be `parse-rejected{parser:"config-json"}` with `detail` ∈ `malformed` · `unreadable` · `unknown-keys`. Skipped unknown keys are counted in `count`, at `warn` per obs-plan §6 (Log levels mapping), with `corr` null. Whether the current reader already emits `unknown-keys` is research's question.
- obs-plan §11 (PII Scrubbing) requires that no `config.json` key, `VIOLA_*` variable or CLI flag widens the field allow-list or disables redaction. `diagnostics_level` changes volume only, and `debug` is enabled only by `diagnostics_level:"debug"` (obs-plan §6 Log levels mapping), never by `RUST_LOG`.

## Patterns to follow
- A dispatch span per verb named `cli.<verb>` (for example `cli.list`, `cli.verify`), or the verb's own client span (`send.client`, `wait.block`, `answer.client`, `pause.client`, `release.client`), always `#[instrument(skip_all, fields(..))]` (per obs-plan §2 Span naming and obs-plan §4 cli row). A `revive --list` dispatch span would follow `cli.<verb>`.
- The `viola list` shape for a short-lived verb's role log: strict-modes check first, then open `cli-<name>.ndjson` only under a parsed `VIOLA_NAME`, then `process-start` … `process-exit{subject:"self", exit_code, detail}`. With no instance, no file and no line (D-06) (per obs-plan §4 cli row).
- A `cli` internal fault: `process-exit{subject:"self", exit_code:1, detail:"internal-error"}` through `obs::internal_error_exit_line`, the chain only in `detail-cli.ndjson`, then exactly `error: internal error\n` on stderr in one `write_all` and exit 1 (per obs-plan §7 Panic hooks).
- Human refusals go through `src/human.rs` `refuse` / `write_refusal` (one `write_all` on the locked stderr, no print macro, no `#[allow]`). Only the modules that own `--json` output may carry a local `#[allow]` for a print macro (per obs-plan §11 Logs).
- Events go out only through `obs_event!`, which sets `event` / `process` / `instance` (per obs-plan §11 Logs).

## Anti-patterns to avoid
- Never write telemetry to stdout on any role. stdout carries only the `--json` result on `cli` (per obs-plan §11 Logs).
- Never log a field not named in the §6 catalog, and never put a path, pid, upstream text or `config.json` value inside a `detail` code or field (per obs-plan §11 PII Scrubbing).
- Never use a bare `#[instrument]`, or `#[instrument(err)]` / `#[instrument(ret)]`, on a function whose error can carry a serde source. Never print an anyhow chain holding a serde source to stderr or `--json` (per obs-plan §11 Spans / Traces and obs-plan §11 Error Reporting).

## Contract bindings
- obs ↔ tests: test-plan §3 Log format (reproduced in obs-plan §3 Log format JSON schema). `process:"cli"` writes `cli-<name>.ndjson` only with a resolved instance. Obs may add fields (the `state-recovered` scanned-instance field) but renames or removes none. A new `event` value would need a Decisions Log entry. The harness `logs` / `status` read these files.
- obs ↔ CI: obs-plan §9 G4 validates real process output against `schemas/diag-line.v1.json`, and G2 counts `event:"panic"` lines. Integration homes for new `revive --list` / CLI-contract tests must live under `target/e2e-home/` so G2, G4 and the secret scan cover them (obs-plan §9 Integration tests row).
- obs ↔ security: the NEVER-log floor and default-deny (obs-plan §8, security-plan §Input Validation). The new field and any new `process-exit` line name a `ViolaName` and closed codes only. `check_instance` comes before any log opens.
- obs ↔ architecture: the `--json` error documents and the exit map (architecture §Standard Contracts CLI `--json` output, §Conventions CLI exit codes) must agree with the `process-exit{exit_code, detail}` that the same outcome logs (obs-plan §6 `detail` code catalog).

## Acceptance criteria contributions
- (obs) `viola revive <name> --list`, run under a resolved instance after a passed instance check, writes one `process-start` and one `process-exit` into `diagnostics/cli-<name>.ndjson`. A forced panic in it leaves exactly one `level:"ERROR", event:"panic"` line in that file. obs-plan §10 lists exemption 6 no more (per obs-plan §10 Zero unlogged panics).
- (obs) Under a `VIOLA_NAME`, `viola list` over a scanned instance with an unreadable snapshot writes one `state-recovered{detail:"snapshot-replayed"}` line. The line's `instance` is the caller and a new catalogued field is the scanned `ViolaName`. The line validates against `schemas/diag-line.v1.json` (G4), and the obs-plan §6 `state-recovered` row and the §4 E5 text name the field (per obs-plan §4 E5).
- (obs) A `config.json` with an unknown key yields one `parse-rejected{parser:"config-json", detail:"unknown-keys", count}` at `warn` with no `corr`. No `config.json` value (including `diagnostics_level`) changes the logged field set (per obs-plan §6 `detail` code catalog).
- (obs) Every new or changed `process-exit` line from a CLI verb carries `exit_code` equal to the process exit, and a `detail` from the closed per-exit set that agrees with the `--json` document for the same outcome. No telemetry byte reaches stdout (per obs-plan §6 `detail` code catalog).
