## Constraints
- Every relied-on undocumented `claude` behaviour must be a ledger row in `viola-agent-claude` with a `viola verify` probe that checks a post-condition, never an unconditional assumption; architecture §Cross-cutting Patterns → Capability ledger as the single gate names `viola revive`'s `--resume` dependence as the one relied-on dependence with no row, owed with `/compact`'s to `v1-34` on this entry (per architecture §Cross-cutting Patterns → Capability ledger as the single gate).
- The relied set is `LedgerRow::ALL` filtered by `relied_on(row, …)` per OS; a version is verified only when every relied row reads `pass`, verify's step line count `MM` is `LedgerRow::relied().len()`, and an all-`pass` stamp of an older id set reads unverified — so each new row must state where it is relied and every older home falls to `cli_verified:false` until re-stamped (per architecture §Established Decisions [CLI Version Compatibility]; per architecture §Standard Contracts → Ledger stamps envelope).
- `viola verify`'s child set is fixed in the plan: one print probe, four interactive PTY runs (A–D), Run B's five compiled pastes; each past widening (the added pastes, Run B's probe `--settings`) is recorded as the founder's own answer, and no run or start was added without one — a sixth child or a `/compact` paste is a widening of that set (per architecture §Established Decisions [CLI Version Compatibility]).
- The local-command decision depends on the compiled ledger list (`ledger::LOCAL_COMMANDS`) by exact equality of the typed text, never a leading-slash test; a listed command whose post-condition is "none", or any listed command on an unverified version, is `ok` `unconfirmable` at once; a listed command on a verified version waits the window for its post-condition only and no `prompt-submitted` claims it; the hook tap appends the claiming `session-start` unchanged before `send-confirmed`; any other unconfirmed send is `not-delivered` / `no-prompt-submitted`. Today the plan's claim rule is `/clear`'s alone (cause `clear`, an id differing from the remembered one); whether the code's claim can take a same-id `compact` session-start is research's question (per architecture §Established Decisions [Delivery Confirmation]; per architecture §Standard Contracts (`hook.event`)).
- Claude-specific shapes stay in `viola-agent-claude`, whose `ledger` module is pure (no I/O, no clock, no `viola-state` dependency); `viola_agent_claude::resume_args` is the one product home of the `--resume` / `--fork-session` literals, and the stamps file I/O stays in `viola-state` and the root bin (per architecture §Established Decisions [Agent Coverage]; per architecture §Infrastructure Patterns → Crate dependency direction; per architecture §Occupied Resources → Claude Code integration names).
- `session-start`'s `data.cause` already admits `resume` and `compact` in the normalised map, and new kinds are not the route for these shapes; whether `normalise` maps a SessionStart `source` `compact` / `resume` to those causes today is research's question (per architecture §Conventions → Hook → kind map).

## Patterns to follow
- The statusline rows' shape (chunk 2026-10-13-owed-ledger-rows): rows appended to `LedgerRow::ALL`, per-OS reliance through `relied_on`, `check(row, &Probes)` reading Run B's captures, a `ledger::*_variants` helper naming the recorded files, `[NN/MM]` read from `relied()` (per architecture §Established Decisions [CLI Version Compatibility]).
- `/clear`'s local-command row: a `LOCAL_COMMANDS` entry with its post-condition, Run B's compiled `PROBE_LOCAL_COMMAND` paste counted in `FRAMING_TURNS`, `SessionEnd.clear-<n>` / `SessionStart.clear-<n>` variants through `ledger::framing_variants`, replayed by the fake agent's `--framing` (per architecture §Established Decisions [CLI Version Compatibility]; per architecture §Established Decisions [Delivery Confirmation]).
- The fake agent's `--resume <id>` today rewrites `SessionStart.default` (`source` `resume`, `session_id` the id); a recorded resume variant would replace that rewrite in the same test-only bin, with options counted by the plan's list rule (per architecture §Occupied Resources → Binary, subcommands and exit codes).
- A revived start's id is one argv element of a direct spawn, of the `is_session_id` shape, built by `resume_args` (per architecture §Occupied Resources → Claude Code integration names).

## Anti-patterns to avoid
- Hard-coding `--resume` reopening a session or `/compact`'s post-condition without a row and a probe, or classifying a local command by a leading slash (per architecture §Cross-cutting Patterns → Capability ledger as the single gate; per architecture §Established Decisions [Delivery Confirmation]).
- A `--resume` literal or a Claude payload shape outside `viola-agent-claude`, or a `viola-state` / I/O dependency added to its `ledger` module (per architecture §Infrastructure Patterns → Crate dependency direction).
- A verify child spawned through `sh` / `bash` / `cmd`, or a Tokio runtime on the `send` / `run` / `verify` paths (per architecture §Cross-cutting Patterns → Cross-platform discipline; per architecture §Cross-cutting Patterns → Tokio containment).

## Contract bindings
- arch ↔ security: the verify child-set widening (a sixth `--resume` child, a `/compact` paste in Run B) and the live-start cap are founder rulings; the security plan's bounds on verify's PTY children (direct spawn under the R8 strip, `MAX_FRAME`, guards, no key into a dialog) bind any new child; the logged id on a child's command line is an already-ratified crossing for `revive` only.

- `/compact` sent by a driver on a verified CLI is confirmed only by its measured post-condition through the ledger list (exact match), with the claiming `session-start` appended before `send-confirmed`; on an unverified CLI it is `ok` `unconfirmable` (per architecture §Established Decisions [Delivery Confirmation]).
- The `--resume` flag literal and both rows' probe checks live only in `viola-agent-claude`, whose `ledger` module gains no I/O and no `viola-state` edge (per architecture §Infrastructure Patterns → Crate dependency direction).
- Any recorded resume / compact fixture is written only on a 0-fail `--record`, passes the scrub and hygiene walk, and the plan's `2.1.287` file count and `ROW_IDS` match the committed set (per architecture §Occupied Resources → Repository).
