# obs extract

## Relevance
partial — the chunk adds no new telemetry surface of its own, but it moves `viola verify`'s logged child set and stdout count, adds a claim arm to `send`'s confirm window, and stamps rows that `run`'s version gate reports as `cli_verified`.

## Constraints
- obs-plan §4 Span / Trace Coverage (Capability ledger → `verify` / `plugin install`) requires `verify` under a `VIOLA_NAME` to log exactly its six child spawns as `process-start{subject}` / `process-exit{subject, child_exit_status, duration_ms}` pairs: `version-probe`, `verify-probe`, then one `verify-pty-probe` pair for each of Runs A–D. No line may carry row text, a prompt or a path. A sixth verify child (the `--resume` probe the scope floats) therefore changes a pair count the plan states as "six". The plan has to be amended alongside it, and the child must be logged at the call site like the others.
- obs-plan §4 Span / Trace Coverage (Capability ledger → `verify` / `plugin install`) requires `verify`'s stdout to print one `[NN/MM] <row id> <row words>  pass|fail` line per relied row. `MM` is `LedgerRow::relied()`'s count, which the plan states as 21 on Unix and 18 on Windows. The last line, `stamped <version>  N pass  N fail`, must sum to `MM`. New relied rows move `MM` on every OS where they are relied.
- obs-plan §4 Span / Trace Coverage (Capability ledger → `verify` / `plugin install`) requires a `verify` stopped by Ctrl-C or TERM to start no further spawn. It must close every pair it opened (a killed child closes with `duration_ms` and no `child_exit_status`) and end with `process-exit{subject:"self", exit_code:1, detail:"interrupted"}`. Any added child or start falls under the same stop rule.
- obs-plan §4 Span / Trace Coverage (Scenario: Confirmed `send` (CL-1) → Cleanup) requires `run.confirm_window` to close on the confirmation its send waits for. Today the plan names only `/clear`'s post-condition: a `session-start` of `cause` `clear` whose `agent_session_id` differs from the slot's id. Expiry is `send-refused{detail:"no-prompt-submitted"}`, and the plan says outright that no new detail is added. An unconfirmable send opens no `run.confirm_window`. A `/compact` post-condition (cause `compact`, the same id) would be a second claim arm that the plan text does not yet describe. Whether the code already claims only a new id is research's question.
- obs-plan §4 Span / Trace Coverage (Capability ledger, `ledger/stamps.json`) requires the stamp to be read inside `run.version_gate` as the child span `state.ledger_read`. Its outcome is `cli_verified` on `process-start{subject:"claude-child"}`, and a missing or non-covering stamp gives `cli_verified:false`, which is the `unverified-cli` branch. The stamp's path and contents never appear in a line.
- obs-plan §6 Log Coverage (Boundary-call wrappers → Child / shell spawns) requires `schemas/diag-line.v1.json` to close `subject` as `self|claude-child|version-probe|verify-probe|verify-pty-probe|agents-probe|statusline-shell`. It also requires every `verify` spawn pair's `process-exit` to carry `child_exit_status` and `duration_ms`. A new child either reuses a listed `subject` or needs a new enum member in both the schema and the §6 catalog.
- obs-plan §4 Span / Trace Coverage (Capability ledger → `verify` / `plugin install`) requires the hidden `hook <event> --capture <DIR> [--answers <DIR>]` arm to stay uninstrumented: no `VIOLA_*` read, no obs init, no role or detail file, no `hook-invoked` / `hook-decision`. That includes any new SessionStart `resume` / `compact` capture a probe files through it.

## Patterns to follow
- Log each verify child spawn at its call site, with `run_bounded` itself left unlogged, as one `process-start` / `process-exit` pair per child (per obs-plan §6 Log Coverage, Child / shell spawns).
- Model a `/compact` confirmation on the `/clear` path: the hook side logs `hook-invoked{hook_event:"session-start", corr:null}`, and the wrapper ends the send with `send-confirmed{corr:<cursor>, confirmed, duration_ms}`, with no `prompt-submitted` claiming it (per obs-plan §4 Span / Trace Coverage, Scenario: Confirmed `send` (CL-1)).
- On a verify stop, close every opened pair before the self `process-exit{detail:"interrupted"}` (per obs-plan §4 Span / Trace Coverage, Capability ledger → `verify` / `plugin install`).
- Emit every new line through `obs_event!` under `#[instrument(skip_all, fields(..))]`, and set `corr` explicitly as a typed field (per obs-plan §11 Obs Anti-Patterns, Logs and Spans / Traces).

## Anti-patterns to avoid
- NEVER add an `event` value, a closed `subject` / `detail` member or a field that is not in the §6 catalog without a Decisions Log entry. The posture is default-deny, enforced by G4 (per obs-plan §11 Obs Anti-Patterns, Logs and PII Scrubbing).
- NEVER derive telemetry or a probe verdict from screen content, and never read Claude Code transcripts as a contract. This matters for any "did the resumed session keep its turns" measurement (per obs-plan §11 Obs Anti-Patterns, Telemetry Strategy).
- NEVER put content, PII or paths in span fields or `detail` codes. A logged session id is Low and may appear as a typed field (`agent_session_id`), but never inside a `detail` code (per obs-plan §8 PII Scrubbing & Compliance and §11 Obs Anti-Patterns, PII Scrubbing).

## Contract bindings
- obs ↔ tests: `schemas/diag-line.v1.json`, with its closed `subject` enum and its 12-member `process-exit` `detail` enum, is checked by G4 over real fake-agent process output under `target/e2e-home/`. Any enum change lands in the schema and the §6 catalog together (per obs-plan §9 CI Integration and §6 Log Coverage).
- obs ↔ tests: CI's `viola verify` runs only against the fake agent (print mode plus the four PTY runs) in `tests/cli_verify.rs`, harness `boot` step 4 and the rstest `stamped_home` fixture, and the real-CLI verify runs only through `run --local-live`. An added child or paste needs fake-agent coverage there (per obs-plan §4 Span / Trace Coverage, Capability ledger → `verify` / `plugin install`).
- obs ↔ security: what verify's lines may carry (no row text, prompt or path) and the session-id classification (Low, typed field only) follow obs-plan §8 PII Scrubbing & Compliance. The verify child-set widening itself is security-plan's ruling, not obs's.
- obs ↔ arch: `session-start` of cause `resume` / `compact` is a product event in `events.ndjson`, and the plan does not copy it into process logs (per obs-plan §4 Span / Trace Coverage, Scenario: `viola run` start sequence to child spawn).

## Acceptance criteria contributions
- Under a `VIOLA_NAME`, an uninterrupted `viola verify` writes exactly the spawn-pair count the amended plan names for its child set, each `process-exit` with `child_exit_status` and `duration_ms`, and no prompt, row text or path in any line (per obs-plan §4 Span / Trace Coverage, Capability ledger → `verify` / `plugin install`).
- `verify`'s step lines read `[NN/MM]` with `MM` equal to `LedgerRow::relied()`'s count on the host OS, and the last line's `N pass  N fail` sums to `MM` (per obs-plan §4 Span / Trace Coverage, Capability ledger → `verify` / `plugin install`).
- A `/compact` send on a verified CLI writes `send-confirmed{confirmed:true}` once its post-condition `session-start` arrives. On expiry it writes `send-refused{detail:"no-prompt-submitted"}`, and no new detail value appears (per obs-plan §4 Span / Trace Coverage, Scenario: Confirmed `send` (CL-1)).
- G4 passes against `schemas/diag-line.v1.json` over the chunk's fake-agent homes (per obs-plan §9 CI Integration).
