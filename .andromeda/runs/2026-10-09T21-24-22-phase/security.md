partial — the chunk changes no boundary, wire shape or control, but three function splits and nine of the eighteen survivors sit in files that carry security controls (`strict.rs`, `fs.rs`, `stamps.rs`, `events.rs`, `src/cmd/hook.rs`, `src/cmd/verify.rs`, `ledger.rs`), and the scaffolding lift touches the test-home and test-only-feature rules.

## Constraints
- `fs.rs:290:19` is the content guard of `replace_private_shared`. security-plan §Data Protection (At rest, Files, Code-bearing artefacts) requires that a failed replace counts as done only when the file already holds exactly the rendered bytes. The mutant removes that condition, so its disposition is read against this requirement: a recorded argument cannot rest on the weakened behaviour being acceptable. Whether an existing test already reaches a failed replace over differing bytes is research's question.
- `strict.rs:34:23` sits inside the strict-modes check. security-plan §Authentication & Authorization (`~/.viola/` access control row) requires a refusal at every listed entry point when the home, a listed directory or a trusted file fails the owner / mode rule. Whether the mutated `NotFound` guard turns a refusal into a pass (any stat error read as "absent") is research's question; if it does, the survivor is a hole in a control and is killed by a test, not argued.
- `stamps.rs:28:19` separates an absent `ledger/stamps.json` from an unreadable one. security-plan §Input Validation (Own state files on read row, and the Constants paragraph) requires that an unreadable or malformed stamps file, or a strict-modes refusal, reads `cli_verified:false` through `read_stamps_strict`, and that an over-cap file is an error in `read_stamps`. Whether the guard at that coordinate feeds the strict read path or only `update_stamps` is research's question.
- `events.rs:96:19`, `:149:19` and `:209:24` sit in the one `events.ndjson` reader. security-plan §Input Validation (Own state files on read row) requires each line taken through the `MAX_FRAME + 1` cap, an over-long or non-object line skipped and counted, and an unterminated last line neither returned nor healed. A kill test added here asserts those outcomes and adds no healing or truncation. Whether `:209:24` is the cap comparison is research's question.
- The split of `record` (`src/cmd/verify.rs`) stays inside security-plan §Data Protection (Repository fixtures): the scrub runs before any write, a dirty recording is refused whole with nothing written, and the refusal names the fixture file and a closed code, never the content. Whether `record` at that coordinate is the function that orders the scrub and the write is research's question; if it is, the split keeps that order in one visible place.
- The split of `dialog_variants` and the six `ledger.rs` survivors stay inside security-plan §Security Anti-Patterns → Universal (the stamp bullet): a non-`null` dialog decision requires a stamp holding all seventeen rows of `LedgerRow::ALL`, each `pass`. No split or kill test changes the row set, a row's verdict rule or who writes `ledger/stamps.json`. Whether any of the six coordinates sits in a row verdict or in `probe_body` is research's question.
- `src/cmd/hook.rs:214:72` and `src/cmd/mod.rs:133:5`: security-plan §Error Handling (Internal logging) requires that `viola hook` never writes stderr and never exits non-zero, on every failure including a security check's. A kill test for either asserts through exit 0, empty stderr and the body or no-body outcome, and no helper split out of the hook path adds a write or an exit code.

## Patterns to follow
- Test homes: every test, lifted scaffolding included, uses its own `--home` directory made through the test side's keeper (security-plan §Secret Management, Storage → Development; the keeper rule is security-plan §Security Anti-Patterns → Code Patterns, the `target/e2e-home` bullet).
- A kill test that needs a state file writes it with explicit modes through the shared helper, never relying on the umask (security-plan §Authentication & Authorization, `~/.viola/` access control row).
- If the audit's "one helper" for `src/run/send.rs` is taken, the helper keeps the refusal order: `validate_paste_text` first and authoritative, the typed text taken once, the empty typed text refused before the first wheel read (security-plan §Input Validation, Paste text row).
- Mutation records: the plan's own mutation workflow keeps the harness document and outcome lines with repo-relative paths only (security-plan §Dependency Security, CI integration, the `windows-mutants.yml` bullet), and it records that the tool's raw `outcomes.json` holds absolute argv paths and its `log/` holds test output (security-plan §Bootstrap phases, `secret-scanning-ci-gate`). The plan states both for CI uploads and does not rule on a committed `evidence/` copy; which form the copied outcomes take is P4's question.
- A local mutation run on the Linux dev host touches no scratch through the harness, and the host's mutation `TMPDIR` is the operator's (security-plan §Security Anti-Patterns → Code Patterns, the `run --mutants` bullet).

## Anti-patterns to avoid
- No new environment seam, config key or flag to make a mutant reachable by a test: the two `FAKE_AGENT_*` seams are the only carve-outs, and another needs its own Decisions Log entry (security-plan §Security Anti-Patterns → Universal, the last bullet). This covers the split of `submit` and the four `viola-fake-agent.rs` survivors.
- No test-side removal under `target/e2e-home` of anything the test side did not create. A lifted `Running` with its `Drop`, or a shared boot helper, removes only its own `TempDir` or owner-recorded dir (security-plan §Security Anti-Patterns → Code Patterns, the `target/e2e-home` bullet).
- No reuse of an existing `plugin/` file without rewriting it, and so no argument that accepts `replace_private_shared` returning done over bytes it did not check (security-plan §Security Anti-Patterns → Data Protection, the re-hash and rewrite bullet).

## Contract bindings
- security ↔ tests: the survivor kills in `viola-state` and `src/cmd/hook.rs` are test-plan work whose assertions are this plan's refusal outcomes (strict-modes refusal, fail-open hook, the content guard). The mutation tier and its record form are the test plan's.
- security ↔ tests (release build): the scaffolding lift may not make a test-only feature or binary reachable by the release build. `scripts/release-check.sh` refuses `test-support` and `fake-agent` artifacts, and `viola-channel`'s `test-support` is enabled only by the root package's `[dev-dependencies]` (security-plan §Dependency Security, CI integration, the `release` job bullet).
- security ↔ obs: the artifact canary scan reads everything under `target/agent-run/` except `run --mutants`' `chunk.diff` (security-plan §Secret Management, Secret scanning in CI); a harness document the `viola-e2e` score run leaves there is in its reach. G2's one exemption is the exact `src/cmd/hook/seam.rs:<digits>` location (security-plan §Dependency Security, CI integration, the G2 bullet); a new forced panic elsewhere in the hook path would read red.
- security ↔ architecture: the capability-ledger row set that gates `cli_verified` is architecture's contract and this plan's gate; the `dialog_variants` split binds to both.
