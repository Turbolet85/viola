## Constraints
- a11y-plan §4 P6 requires the cli output-discipline checks (no SGR in the plain modes, every SGR span beside its word under the outer PTY, linear static output, C0/C1 escaping) on all three OS legs. Scope §2 names `sgr_attributes` in `tests/cli_output_plain.rs`, and scope §1 lifts scaffolding out of root `cli_*` test files. Whether those files host the P6 checks is research's question; where they do, a split or a lift must leave every P6 assertion asserting what it asserted before.
- a11y-plan §4 P4 requires the tui boundary as separate nextest cases, one per boundary clause, plus the gate-wait case under clause (2), on all three OS legs. Scope §1 lifts a wrapper boot and an `events()` reader out of `tests/tui_wheel.rs` and `tests/cli_wheel.rs`. Whether those files host the P4 cases is research's question; where they do, sharing the scaffolding must not merge, drop or rename a case.
- a11y-plan §3 Keyboard test harness (Tooling) requires the tui cases to be sequenced on the wrapper's logged records and the `wheel` record, never on a timer, and to run with `viola-fake-agent` as the child, one case under its paste-hint hold. Scope §2 splits `submit` in `src/bin/viola-fake-agent.rs` and scope §5 targets four survivors in that file. Whether `submit` or those lines carry the paste-hint hold is research's question; the fake agent's behaviour under those cases must not change.
- a11y-plan §6 State color tokens (CLI equivalent) requires a per-OS form of the `viola run` check: a byte-for-byte comparison with an unwrapped fake-agent run on Linux and macOS, and the absence of viola's own literals on `windows-2025`, on both ConPTY backends. A helper lifted into `tests/support/` must keep that per-OS branch, and a fake-agent split must leave the bytes the fake agent emits unchanged.
- a11y-plan §3 A11y testing tool pick (Primary tool per surface) requires the cli checks on assert_cmd + predicates + trycmd and the tui checks on the portable-pty outer-PTY driver at the inherited pin, which a11y never re-pins. The shared scaffolding of scope §1 must stay on those drivers and introduce no other.
- a11y-plan §3 Structured violation JSON schema (cli / tui) requires that a cli or tui output-discipline failure surfaces only as a nextest failure in the harness `run` JSON, with no a11y row. A shared child-run-and-wait helper must therefore leave a failing assertion a nextest failure of the calling test, never a swallowed or reclassified result.
- a11y-plan §10 (Standard+ invariants; Cross-input parallel) requires the P4 and P6 invariants to pass on all three OS legs inside the nextest suites, with `#[ignore]` banned and no retry. A test added for a scope §5 survivor, or any test whose scaffolding scope §1 moves, may not be parked or retried to reach green.

## Patterns to follow
- State and step ordering read from logged events and records, never from a sleep (a11y-plan §3 Keyboard test harness, Tooling). The scope notes that every wait already uses `Watch` and `WITHIN`; the shared helper keeps that form.
- One nextest case per boundary clause, the wheel probed step-wise after each step (a11y-plan §4 P4).
- SGR asserted by adjacency to its word under the outer PTY, and by absence in the plain modes, never by a colour value alone (a11y-plan §4 P6; a11y-plan §6 State color tokens, CLI equivalent).
- Every cli and tui state driven through the fake agent and the harness, with the tests' existing drivers as the only instruments (a11y-plan §4 Per-surface a11y testing tool reach).
- Refusal layout and typed exit codes pinned by trycmd and assert_cmd per refusal (a11y-plan §8 Error recovery, Verification). A shared `viola(…) -> Ran` runner keeps stderr and the exit code available to each caller's own assertion.

## Anti-patterns to avoid
- NEVER parse the rendered `claude` TUI screen for content, or take a screenshot as evidence, in a shared test helper (a11y-plan §11 Universal).
- NEVER record a cli or tui test result, or a mutation outcome over those tests, as WCAG conformance evidence: they are output-discipline stand-ins only (a11y-plan §11 Strategy).
- NEVER let a function split in product code colour `unable` / `fail` or emit SGR in a plain mode or under `viola run` (a11y-plan §11 Visual). Scope §2 splits `record` in `src/cmd/verify.rs`; whether that function writes the `verify` step lines is research's question.

## Contract bindings
- a11y ↔ tests (harness): the cli and tui checks run inside the tests' nextest suites and the CI `test` job's `coverage` suite, and their verdict is the harness `run` JSON; there is no a11y suite value and no a11y row for these surfaces (a11y-plan §9 Per-pipeline-stage a11y artifacts, Unit / integration row; a11y-plan §3 Structured violation JSON schema, cli / tui).
- a11y ↔ tests (mutation): a11y-plan §10 Standard+ invariants hands the crate-hosted output-discipline invariants to the epoch-boundary mutation audit of test-plan §10. The chunk's runs in scope §4 and §5 are one-shot measurements, not that audit; they neither replace it nor add an a11y gate.
- a11y ↔ architecture: the tui boundary driver is the inherited portable-pty pin (a11y-plan §3 A11y testing tool pick, Primary tool per surface).
- a11y ↔ security: the C0/C1 escaping check of P6 is set up through a `viola-fake-agent` event, so a change to the fake agent binds to that check (a11y-plan §4 P6).
