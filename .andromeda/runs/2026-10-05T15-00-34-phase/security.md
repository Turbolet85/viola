# security extract

## Relevance
partial — W3d-a/W3d-b touch the PermissionRequest decision path (the highest-impact dialog: `allow` runs a tool as the user), its stamp gate, closed types and free-text check; W6 and F1 (a test-header reword, a nextest bound and its rule text) carry no security surface.

## Constraints
- A non-`null` dialog decision, PermissionRequest `allow` included, flows only when `ledger/stamps.json` holds a `viola verify` stamp for the child's CLI version covering all fourteen rows, read by `viola run`'s version gate through `read_stamps_strict`; a partial stamp or a strict-modes refusal is `cli_verified:false`, the hook prints nothing and `answer` exits 12 `unverified-cli` (per security-plan §Security Anti-Patterns › Universal, the two stamp bullets; §Input Validation, "Own state files on read" row). How the fake-agent home of the new `permission` case gets its stamp is research's question; the case must not reach a body by any route that skips this gate.
- `behavior` (`allow`/`deny`), `dialog_id` (`u64`), the dialog kind, `hook_event` and `tool` stay closed types on both the `hook.dialog` and `answer` params; the wrapper maps `response` into the closed per-kind enums before anything else (per security-plan §Input Validation, "Channel frames" row; §Security Anti-Patterns › Input). If W3d-b's measurement leads to a PermissionRequest body for a `question`, that body comes from the closed enums through the existing decision-body builder (`dialog::decision_body`, which the capture arm already uses per §Input Validation, "Hook stdin" row), never from upstream text.
- A `deny` `message` (and any question free-text answer) passes `validate_paste_text` over decoded `char`s on both sides: `viola answer` refuses before any frame (exit 13), and the wrapper's `answer` handler re-checks authoritatively. LF/CR/TAB are allowed, and other controls are rejected, never stripped (per security-plan §Input Validation, "Dialog free text" row; §Security Anti-Patterns › Input).
- `viola hook permission-request` fails open on every failure: exit 0, empty stderr, no body, so the dialog renders for the human. The `null` to the human for a `question` first raised by PermissionRequest is that same no-body outcome (per security-plan §Error Handling, Internal logging; §Security Anti-Patterns › Logging and › Universal, "NEVER let a security refusal block the human").
- The sixth dated gap stays exactly as ratified: `viola answer`'s `answer` frame goes after the liveness-only pre-check, and `viola hook pre-tool-use|permission-request`'s `hook.dialog` frame goes after only its payload shape check. This chunk adds no new frame, process or verb under it and borrows no other gap (per security-plan §Authentication & Authorization, "IPC client-side server verification" row, fourth interim gap here / sixth overall; §Security Anti-Patterns › Authentication).
- `permission.input` (the tool call's full arguments: Bash commands, file bodies) is user content. It travels only in the by-design contract payloads (`events.ndjson`, SSE, `hook.dialog`, `wait`/`last`) and in `diagnostics/`. It never reaches stderr, CLI `--json` errors, channel `error.data` or a `Display` impl (per security-plan §Threat Model Summary, data classification "user-content (tool-call arguments…)"; §Bootstrap phases, `logging-redaction-wire` and `error-sanitization-wire`; §Error Handling, External responses).
- The case replays the committed `fixtures/claude/{2.1.288,2.1.287}/` recordings. A new fixture, if W3d-b's live fallback were ever used, comes only from `viola verify --record` with synthetic prompts and the scrub-or-refuse pass, and is reviewed for home paths, usernames and tool `input` before commit (per security-plan §Data Protection, Repository fixtures; §Security Anti-Patterns › Data Protection, the fixtures bullet).

## Patterns to follow
- Dialog classification is closed: `viola_agent_claude::dialog::classify` maps the one stdin object into `DialogKind` / `DialogTool`, a malformed dialog payload is `AgentError::DialogMalformed` (fail open), the reply read is bounded at `DIALOG_DEADLINE + 5 s`, and stdout takes one write (per security-plan §Input Validation, "Hook stdin" row).
- One shared validator: `viola_core::validate_paste_text` is called client-side and again in the wrapper, and the client check is advisory (per security-plan §Input Validation, Boundary preamble and "Dialog free text" row; §Security Anti-Patterns › Input, first bullet).
- Mechanism, not policy: viola's only part in an `allow` is the closed `behavior` enum and the `unverified-cli` gate. What to answer stays with the driver (per security-plan §Authentication & Authorization, accepted risk "driver prompt injection"; §Threat Model Summary, MCP vector trust boundary).
- Test seams exist only under `cfg(feature = "fake-agent")`, and only the two ratified ones (`FAKE_AGENT_PUMP_DELAY_MS`, `FAKE_AGENT_HOOK_PANIC`) (per security-plan §Input Validation, the two test-seam rows; §Security Anti-Patterns › Universal, the config bullet). The permission case and F1's planted-hang control should reuse existing seams. Whether an existing seam suffices is research's question.

## Anti-patterns to avoid
- NEVER let a `hook.dialog` get a non-`null` decision (PermissionRequest `allow` above all) without the fourteen-row stamp read through `read_stamps_strict`, and NEVER have a test or helper write `ledger/stamps.json` by any route other than `viola verify` (per security-plan §Security Anti-Patterns › Universal).
- NEVER model `behavior`, `dialog_id` or the dialog kind as free `String`s, even in a new question-via-PermissionRequest body (per security-plan §Security Anti-Patterns › Input).
- NEVER add another env-var test seam, or let one switch off a control, without its own Decisions Log entry (per security-plan §Security Anti-Patterns › Universal, the config bullet).

## Contract bindings
- security ↔ architecture §Standard Contracts (`hook.dialog`, `answer`): the closed param types and the stamp-gated decision body are this plan's floors on those contracts (security-plan §Input Validation, "Channel frames" row).
- security ↔ test-plan §6 Path 4: the `permission` case is the end-to-end witness of the `allow`/`deny` body path. The `unverified-cli` and `control-character` refusals bind to it as negative cases.
- security ↔ obs-plan §6 (dialog events): the hook's fail-open outcomes are `hook-decision` detail codes in `diagnostics/`, codes only, with `permission.input` kept to `diagnostics/` per the NEVER-log floor (security-plan §Bootstrap phases, `logging-redaction-wire`; §Error Handling).
- security ↔ capability ledger: a non-`null` body flows only under the fourteen-row stamp (security-plan §Security Anti-Patterns › Universal). Whether a question-via-PermissionRequest body, if built, is covered by the existing dialog rows or needs the null kept is P4's question. The scope adds no row.

## Acceptance criteria contributions
- (security) In the `permission` end-to-end case, every `viola hook permission-request` run exits 0 with empty stderr, and the case leaves no `allow` body on a home whose stamp is absent or partial: there the hook prints nothing and `viola answer` exits 12 `unverified-cli`. Whether an existing test already covers this for the `permission` kind is research's question (per security-plan §Security Anti-Patterns › Universal; §Error Handling, Internal logging).
- (security) A `deny` `message` carrying a refused control (for example ESC U+001B) makes `viola answer` exit 13 `control-character` before any frame, while LF/CR/TAB in it are accepted (per security-plan §Input Validation, "Dialog free text" row).
- (security) The diff adds no caller of the liveness-only pre-check, and no `hook.dialog` / `answer` frame path, beyond the sixth gap's ratified set (`viola answer`, `viola hook pre-tool-use|permission-request`). A grep over `src/` for the pre-check helper and frame writers shows no new site (per security-plan §Authentication & Authorization, "IPC client-side server verification" row; §Security Anti-Patterns › Authentication).
- (security) `cargo deny check` stays green with no new dependency, ignore or skip, and no new `FAKE_AGENT_*` name appears in product source (per security-plan §Dependency Security; §Security Anti-Patterns › Universal).
