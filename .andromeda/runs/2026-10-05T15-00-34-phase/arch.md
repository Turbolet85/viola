# arch extract

## Relevance
relevant — W3d-a exercises the `hook.dialog` / `answer` / `wait` contracts end to end for the `permission` kind, and W3d-b turns on the Hook → kind map, the continuation rule and the capability-ledger gate; W6 and F1 are outside the architecture domain.

## Constraints
- A PermissionRequest maps to the `permission` kind, except one that repeats the armed `question` / `plan` dialog's tool with an equal `tool_input`, which is that dialog's continuation and raises no event (per architecture §Conventions → Hook → kind map). The plan does not say what kind a PermissionRequest for AskUserQuestion gets when no `question` is armed (W3d-b's case). Research checks how `dialog.rs` maps it today and states what it finds; the plan does not settle it.
- `hook.dialog` `{kind, data, hook_event, tool?, input?, continuation?}` → `{dialog_id, response}`. The wrapper must assign the `dialog_id`, monotonic per instance, and append the dialog event (`source: hook`) before it wakes `wait` or replies. It must do this even when it replies `null` at once, so every dialog appears exactly once in the log. A dialog hook sends no `hook.event` for the same dialog (per architecture §Standard Contracts → Channel methods `hook.dialog`, and the `hook.dialog` `data` paragraph after Event `data` per kind).
- The `permission` event's `data` is `{dialog_id, tool, input}`, with `input` carried as content. `answer`'s `permission` response is `{behavior:"allow"|"deny", message?}` with no suggestion slot (a deliberate v1 limit) → `{}` (per architecture §Standard Contracts → Event `data` per kind / Channel methods `answer`).
- `wait` must wake on `permission` (one of `EventKind::WAIT_WAKE`). A pending dialog comes first: an `after`-less `wait`, or a `wait` whose `after` is at or before the dialog's line, returns it at once. At most one dialog is pending per instance (per architecture §Established Decisions [Message Broker / IPC]; §Standard Contracts → Channel methods `wait`).
- The PermissionRequest decision body is exactly `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow|deny","message":"…"}}}`, produced only by `viola-agent-claude`. A `null` answer means exit 0 with empty stdout. `hook` never writes stderr and never exits 2 (per architecture §Standard Contracts → Hook contract; §Established Decisions [Hook Contract]).
- A non-`null` dialog decision needs a stamp for the child's CLI version in which all fourteen rows pass. On an unverified CLI the wrapper answers `null` at once (per architecture §Established Decisions [CLI Version Compatibility]). The end-to-end case therefore runs in a test home whose stamps verify the fake agent's version (per architecture §Cross-cutting Patterns → Config management, the test-isolation point).
- viola is mechanism, not policy. It carries the driver's `allow` / `deny` and decides nothing, and dialog payloads are content, never commands (per architecture §Design Philosophy "Mechanism, not policy"; §Cross-cutting Patterns → Untrusted upstream text).

## Patterns to follow
- Workspace placement: Claude-specific shapes stay only in `viola-agent-claude`, so any W3d-b body belongs in its `dialog.rs` mapping, beside `decision_body`. The wrapper side (`src/run/`, `src/cmd/hook/`) stays agent-agnostic (per architecture §Inherited Defaults "Agent isolation"; §Established Decisions [Module Boundaries]).
- Tests run against the fake agent on all three CI OSes. They name its executable after `--`, and each test runs in its own `--home`; the real CLI runs only in local live tests (per architecture §Established Decisions [CI/CD]).
- The fake agent's `--dialogs` mode replays the recorded `<stem>-<n>` variants in claim order. A call's PreToolUse fires first; with no decision its PermissionRequest fires; a decision from either fires its PostToolUse. The `permission` stem is committed for `2.1.287` and `2.1.288` (per architecture §Occupied Resources → test-only binaries and `fixtures/claude/<cli-version>/`). The plan describes `--dialogs` as verify's interactive mode, so research checks whether it can drive a `viola run` end-to-end case unchanged.
- The hook, `run` and channel-server paths use sync std threads only, and CLI `wait` / `answer` use the sync channel client (per architecture §Cross-cutting Patterns → Tokio containment).

## Anti-patterns to avoid
- Do not hard-code a new dependence on undocumented `claude` behaviour. Every such dependence is a capability-ledger row with a `viola verify` probe (per architecture §Cross-cutting Patterns → Capability ledger as the single gate). A W3d-b body built from a static bundle read would be that kind of dependence, while scope says "No ledger row is added and no re-stamp is planned". If the measurement calls for a body, P4 resolves this conflict: either name the existing row that covers it, or keep the `null` with its recorded reason.
- Add no new event kind, channel method, `VIOLA_*` / env var or `hooks.json` entry. Kinds are added only in `viola-core`, and the nine registered hook events stay as they are (per architecture §Conventions → Normalised event kinds / Environment variables; §Occupied Resources → Registered hook events).
- Do not weaken the fail-open rule. Any internal failure in `hook` must give exit 0 with no body, so the dialog renders for the human (per architecture §Cross-cutting Patterns → Fail open toward the human).

The fake agent's replay of `fixtures/claude/{2.1.288,2.1.287}/PermissionRequest.permission-1.json` and `PostToolUse.permission-1.json` is arch's §Occupied Resources contract for fixtures and the fake agent.

## Acceptance criteria contributions
- (arch) A replayed ordinary-tool PermissionRequest appends exactly one `permission` event (`source: hook`, `data` `{dialog_id, tool, input}`, with a wrapper-assigned integer `dialog_id`) before any reply, and its PostToolUse appends one `activity` line that does not wake `wait` (per architecture §Standard Contracts → `hook.dialog` / Event `data` per kind; §Conventions → Hook → kind map).
- (arch) A `wait` parked before the dialog returns that `permission` event with a `cursor`. `viola answer` by that `dialog_id` with `{behavior:"allow"}` and with `{behavior:"deny", message}` returns `{}`, and the hook prints exactly the PermissionRequest `hookSpecificOutput` body for each, with exit 0 and empty stderr (per architecture §Standard Contracts → Channel methods `wait` / `answer`, Hook contract).
- (arch) W3d-b ends in one of two states. Either the `question` first raised by PermissionRequest keeps `null`, with the recorded reason written where the plan's "owed to Permission end to end" clause sits, or its body lives only in `viola-agent-claude` and is gated by a named ledger row. No Claude-specific shape appears outside that crate (per architecture §Established Decisions [CLI Version Compatibility]; §Inherited Defaults "Agent isolation"; §Cross-cutting Patterns → Capability ledger as the single gate).
- (arch) No new event kind, channel method, env var or registered hook event is added, and there is no Tokio on the hook, `run` or CLI-verb paths (per architecture §Conventions; §Occupied Resources; §Cross-cutting Patterns → Tokio containment).
