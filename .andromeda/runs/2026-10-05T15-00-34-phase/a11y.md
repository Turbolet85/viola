# a11y extract

## Relevance
partial: the chunk has no web-spa or new UI surface. It reaches a11y only through the cli surface: `viola wait` and `viola answer` on the `permission` kind (must-be-accessible Path 3 / P6), and the human fallback when a PermissionRequest body stays `null`.

## Constraints
- a11y-plan §1 (Surface: cli) and §11 Anti-Patterns → Strategy require that cli checks stay output-discipline stand-ins for SC 1.3.2 / 1.4.1 / 3.3.1 (assert_cmd 2.2.2 + predicates 3.1.4 + trycmd 1.2.1, portable-pty outer PTY). The `permission` end-to-end case can never support a WCAG conformance claim.
- a11y-plan §1 Critical paths → 3 and §4 Must-be-accessible path scenarios → P3 name the cli half of "Dialog pending, then `answer` (question / permission / plan)": `viola answer`, with the `unverified-cli` refusal text on the CLI owed by `a11y-p3`. Whether a cli assertion of that refusal already exists at HEAD, and whether it covers the `permission` kind, is research's question.
- a11y-plan §4 P6 and §1 (Surface: cli → Notes) require that human-mode `wait` output under a non-TTY has no SGR (and none under `NO_COLOR`, `TERM=dumb` or `--json`). They also require that a TTY `waiting: <name>` line appears once on stderr with no redraw, and that C0/C1 controls in `wait` / `last` text are escaped while `\n` / `\t` stay raw. This applies wherever a woken `wait` prints PermissionRequest payload text such as tool `input`. Whether the human-mode `wait` path prints dialog payload at all is research's question.
- a11y-plan §8 Error recovery requires every human-mode cli refusal on the `answer` path to print `unable  <reason>  <detail>` on stderr with `hint:` as the last stderr line (except `unknown`, exit 14) and to exit with a typed code (`10`–`14`, `20`, `21`). Faults carry no hint, and `--json` gives one document with no hint text.
- a11y-plan §8 Timeout extensions requires the dialog deadline to bound the driver and never the human. On expiry the hook exits 0 with no body and the dialog renders for the human in the `claude` TUI, and a later `answer` is refused `not-delivered` / `unknown-dialog` (exit 13). The W3d-b outcome "the `null` to the human stays" relies on this same human fallback.
- a11y-plan §1 (A11y assertion harness specification → CLI output discipline), §9 (Per-pipeline-stage table → Unit / integration) and §10 (Standard+ invariants) require cli output-discipline checks to run on all three OS legs inside `nextest-integration` / `nextest-e2e` locally, and inside the per-OS `coverage` suite in CI.
- a11y-plan §8 Plain language requires that a kebab-case reason/detail code (`not-delivered`, `unverified-cli`, `unknown-dialog`) never appears without the plain word `unable` beside it, with trycmd pinning each fixed CLI string.

## Patterns to follow
- Use the cli tool reach in a11y-plan §4 (Per-surface a11y testing tool reach → cli row): assert_cmd / predicates for exit codes and stderr shape, trycmd for pinned copy, and the portable-pty outer PTY only for TTY-only behaviour.
- Mirror the `question` / `plan` case shape for the `permission` case (scope W3d-a) so that a11y-plan §4 P3's three kinds stay covered by one cli pattern.
- Follow a11y-plan §8 Consistency and predictability: refusal words and codes stay identical across dialog kinds. The `permission` kind reuses the existing refusal copy and never adds a kind-specific variant.

## Anti-patterns to avoid
- Never claim WCAG conformance for the cli or the `viola run` TUI on the strength of this chunk's assert_cmd / trycmd results (a11y-plan §11 Strategy).
- Never parse the rendered `claude` TUI screen or use a screenshot as evidence. This applies to any W3d-b live measurement, where the static bundle read is the planned route (a11y-plan §11 Universal).
- Never colour `unable` / `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`. Never add a new harness `suite` value for the case (a11y-plan §11 Visual; §11 CI).

## Contract bindings
- a11y ↔ tests: cli output discipline uses the tests' own harness and gate (`gate --require coverage,doctest,playwright`), with no a11y rows and no new suite (a11y-plan §9 Per-pipeline-stage table → Unit / integration; test-plan §6 Path 4 owns the case itself).
- a11y ↔ design: the cli refusal layout (`unable <reason> <detail>` + `hint:`) is design's cli copy, and a11y pins it through trycmd (a11y-plan §8 Error recovery → cli; §8 Plain language).
- a11y ↔ obs: the a11y harness context assumes obs's `dialog-raised` / `dialog-answered` events carry `corr` = `dialog_id`, the same id this case answers by (a11y-plan §1 A11y assertion harness specification). The obs extract owns the event shape.
- Boundary (not this chunk): the web-spa half of Path 3 (the cocked strip, the `status` text "builder: dialog pending, permission", the title `DIALOG <name> · viola`) belongs to the `a11y-p3` Playwright spec (a11y-plan §4 P3), and this chunk's surfaces do not include `viola-ui`.

## Acceptance criteria contributions
- (a11y) Any human-mode `viola answer` refusal the `permission` case asserts prints `unable <reason> <detail>`, then `hint:` as the final stderr line, with its typed exit code. The `--json` form carries no hint text (per a11y-plan §8 Error recovery).

- (a11y) Where W3d-b leaves the PermissionRequest `null` for a question, the hook exits 0 with no body, so the dialog stays with the human in the `claude` TUI (per a11y-plan §8 Timeout extensions).
- (a11y) The `permission` case runs on all three OS legs inside the existing nextest / `coverage` suite, with no new `suite` value and no skip (per a11y-plan §9 Per-pipeline-stage table → Unit / integration; §10 Standard+ invariants).
