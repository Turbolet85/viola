# security extract

## Relevance
relevant. The chunk crosses the child-process spawning / PATH-resolution boundary, handles the inherited `CLAUDE*` credentials, adds the portable-pty dependency (which brings in an advisory ignore), and edits CI supply-chain surfaces (`ci.yml`, `install-ripgrep.sh`).

## Constraints
- security-plan §Input Validation (row "Child executable resolution") and §Security Anti-Patterns → Data Protection require that `viola run` refuses with exit 1, and never spawns, a PTY child that resolves to `.cmd`/`.bat`, because portable-pty 0.8.1 builds its own `CreateProcessW` command line without BatBadBut escaping. The same row requires the npm `.cmd` shim to resolve to `claude.exe` before spawning. Resolving from the calling process's PATH is an accepted same-user risk per §Security Decisions Log `2026-09-23` → Accepted risks.
- security-plan §Secret Management → Storage requires that `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_MESSAGING_SOCKET` and the other `CLAUDE*` identity variables stay only in the wrapper's environment and are removed from the child by the R8 strip. §Bootstrap phases → `logging-redaction-wire` (the consolidated NEVER-log floor) bans every stripped value from any log, stderr line, diagnostic, snapshot, `events.ndjson` or fixture. This includes error bodies and test output that echo the environment.
- security-plan §Data Protection → In transit ("Handle inheritance") requires that portable-pty's `CreateProcessW` keeps `bInheritHandles = 0`, and that any portable-pty swap (portable-pty-psmux 0.9.7 is the named candidate) keeps that property. Whether the pinned `=0.8.1` spawn path used here actually does so is research's question.
- security-plan §Dependency Security → Pinning requires portable-pty to be pinned exactly `=0.8.1` in `[workspace.dependencies]` with `Cargo.lock` committed. §Dependency Security → `deny.toml` additions requires `[advisories]` to carry `ignore = [{ id = "RUSTSEC-2017-0008", reason = "serial via portable-pty =0.8.1; serial ports never opened" }]` as the only expected ignore, re-checked whenever the pin moves. The same section requires the C-build ban, `[sources]` crates.io-only, and the exact licence `allow` list to keep passing. Any new licence exception pulled in by portable-pty's graph needs its own Decisions Log entry. Whether the ignore and pin are already present is research's question.
- security-plan §Error Handling requires that `PtyError`'s `thiserror` `Display` uses fixed messages, with variant fields that hold paths or payloads excluded. §Bootstrap phases → `error-sanitization-wire` requires anyhow chains to stop at the bin's human-mode stderr with no absolute paths or upstream text.
- security-plan §Dependency Security → CI integration requires that `ci.yml` edits keep: actions pinned by full SHA with a version comment; event-payload values reaching steps only through `env:`; `permissions: {}` / `contents: read`; and zizmor passing. For the `install-ripgrep.sh` fold, the plan has no ripgrep-specific row. The download's integrity rests on its sha256 verification (the scope says to keep it intact), so any revocation-check relaxation (`--ssl-revoke-best-effort`) must not weaken or bypass that checksum gate.
- security-plan §Security Anti-Patterns → Universal forbids any `VIOLA_*` environment variable or CLI flag switching off a plan control. If this chunk sets `VIOLA_NAME` / `VIOLA_DIR` / `VIOLA_BIN` on the child (P3/P4 decide), they carry values only and never act as control switches.

## Patterns to follow
- Keep the R8 list and shim resolution in `viola-agent-claude` and the spawn in `viola-pty`, matching the "Stack reference" column of §Input Validation (row "Child executable resolution": `viola-agent-claude` shim resolution; `viola-pty` spawn).
- Build the environment strip as a removal list applied to the child's `CommandBuilder`, and assert absence in tests. Use canary values in fixtures and E2 so obs's artifact canary scan (§Secret Management → "Secret scanning in CI", the stripped-`CLAUDE*` class) can detect a leak, and never print or write the matched bytes.
- Refusals for security reasons fail closed for automation but never block the human (§Security Anti-Patterns → Universal). The `.cmd` refusal is a startup exit 1, the same as the other `run` startup refusals in §Authentication & Authorization.
- If a vt100 screen model is fed from the pump in this chunk, it goes inside `std::panic::catch_unwind`, and byte passthrough to the human continues after a panic (§Input Validation, row "PTY output bytes"; §Security Anti-Patterns → Code Patterns). Whether this chunk feeds vt100 at all is for P3/P4.
- Any windows-sys kill fallback reuses the stack's `windows-sys =0.61.2` pin (§Authentication & Authorization, Library) rather than adding a new crate.

## Anti-patterns to avoid
- NEVER spawn a `.cmd`/`.bat` PTY child through portable-pty (§Security Anti-Patterns → Data Protection).
- NEVER write any R8-stripped `CLAUDE*` value into any log, stderr, `events.ndjson`, snapshot, `diagnostics/` or fixture (§Security Anti-Patterns → Secrets).
- NEVER make channel handles inheritable, or adopt a portable-pty replacement that calls `CreateProcessW` with `bInheritHandles = TRUE` (§Security Anti-Patterns → Data Protection). NEVER reference an Action by a mutable ref (§Security Anti-Patterns → Code Patterns).

## Contract bindings
- security ↔ obs: the stripped `CLAUDE*` values are canary classes in obs-plan §9's `viola-harness secret-scan` (security-plan §Secret Management → "Secret scanning in CI"; §Bootstrap phases → `secret-scanning-ci-gate`). The E2 strip scenario's fixtures and harness capture feed that scan.
- security ↔ tests: the E2 scenario (test-plan §3 `run`) is the strip witness, and fixtures must be synthetic with no home paths or usernames (§Data Protection → "Repository fixtures"). The `.cmd` refusal and the strip each need a remove-the-guard mutation run (operator standing direction). CI supply-chain checks (`cargo deny`, deny probes, zizmor) stay in the ubuntu supply-chain job (§Dependency Security → CI integration).
- security ↔ architecture: R8 list membership (the "measured list") and the npm-shim resolution home are arch contracts. Security only requires the strip and the no-log floor. The portable-pty swap path (→ portable-pty-psmux 0.9.7) is arch's named path, and security binds it to keep `bInheritHandles = 0` (§Data Protection → In transit) and to the 7-day CVE SLA (§Dependency Security → Critical CVE response SLA).

## Acceptance criteria contributions
- A child resolving to `.cmd` or `.bat` is refused with exit 1 and no process is spawned, and an npm `claude.cmd` shim resolves to and spawns the real `claude.exe`. The guard test fails when the refusal is removed (per security-plan §Input Validation, row "Child executable resolution"; §Security Anti-Patterns → Data Protection).
- The spawned child's environment contains none of the R8 variables (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_BRIDGE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, and the rest of the measured list), and the CI `secret-scan` step passes with canary values set in the wrapper's environment (per security-plan §Secret Management → Storage; §Bootstrap phases → `logging-redaction-wire`).
- `cargo deny check` passes on the root graph with portable-pty `=0.8.1` pinned, RUSTSEC-2017-0008 is the only `[advisories]` ignore and carries its reason, and no licence is added to `allow` (per security-plan §Dependency Security → `deny.toml` additions and Pinning).
- zizmor passes on the edited `ci.yml`, and the ripgrep install still fails on a sha256 mismatch after the resilience change (a probe proves this) (per security-plan §Dependency Security → CI integration).
