# a11y extract

## Relevance
partial. This chunk builds the `viola run` passthrough, which is the tui boundary-only surface in the a11y plan. That surface has no WCAG claim, no ARIA and no axe. The chunk has no web-spa surface, and the plan's axe, focus, contrast and ARIA sections do not apply.

## Constraints
- The a11y plan §1 (A11y Scope Summary → `viola run` TUI passthrough entity, and the tui surface) classifies `viola run` as boundary-only. The rendered `claude` TUI is vendor content. The a11y assertion boundary is viola's wrapper, and it has three clauses:
  - viola writes zero bytes to the terminal except the child's output;
  - human keystrokes are never blocked, refused or delayed past the current atomic paste;
  - focus, mouse and resize sequences pass through and do not count as human editing.

  The chunk's "zero own bytes" passthrough is the implementation side of clauses 1 and 2.
- a11y-plan §1 tui surface → Notes requires viola's `run` diagnostics to go to `diagnostics/` and never to the terminal. This covers the new PTY seam's own logging, spawn errors and the `log_child_exit` output. Whether the current `src/run/` code writes anything to the wrapper's stdout or stderr during passthrough is a question for research.
- a11y-plan §1 cli surface → Notes and §6 State color tokens (CLI equivalent) require zero SGR, glyph or cursor control from viola under `viola run`. §11 Visual has the matching ban.
- The a11y plan §8 Error recovery covers CLI refusals. A refusal is `unable  <reason>  <detail>` on stderr, then `hint:` as the last stderr line, with a typed exit code. The `.cmd`/`.bat` refusal and any shim-resolution failure happen before the child is spawned. If they reach the human, they are CLI refusals and fall under this pattern, not under the passthrough zero-bytes clause. Whether that refusal is human-facing, and which reason/exit code it uses, is for P3/P4 to settle against design and architecture.
- The a11y plan §3 A11y testing tool pick names the tui tool as the portable-pty outer-PTY boundary driver, on the inherited `=0.8.1` pin. §12 D-A11Y-13 records that pin as an inherited risk: 0.9.0 is the maintained line, and a11y does not re-pin. The chunk's `[workspace.dependencies]` pin must stay `=0.8.1`.
- a11y-plan §10 (Build / deploy failure conditions) and §3 Structured violation JSON schema ban `CLAUDE*` values from every a11y artifact. The R8-stripped values must not show up in any outer-PTY test output or fixture that the a11y cases attach.
- The a11y plan §11 Strategy bans any WCAG conformance claim for the `viola run` TUI. portable-pty results are output-discipline stand-ins only.

## Patterns to follow
- The a11y plan §3 Keyboard test harness → Tooling defines the zero-viola-bytes check:
  - The child is `viola-fake-agent` under the outer PTY.
  - On Linux and macOS, the stream is compared byte for byte with an unwrapped fake-agent run.
  - On Windows ConPTY, which re-renders output, the check is that viola's own literals (diagnostics, refusal text, `hint:`) and any SGR or cursor control the child did not emit are absent.
  - Each boundary clause is its own nextest case on all three OS legs.
- The a11y plan §4 P4 tui bullet lists the three outer-PTY nextest cases. Which of them this chunk can land is open, because the chunk excludes the wheel, the wrapper channel and the paste validation path. Clause (1), a partial clause (2) (keystrokes delivered unblocked) and the start/exit portion of the byte stream look reachable. Clause (3) (wheel) and the `human-typing` refused-send step do not. P3/P4 decide whether to land them now or re-pin them.
- The a11y plan §9 Per-pipeline-stage table (Unit / integration row) routes the tui boundary results through harness `run` JSON: `nextest-integration`/`nextest-e2e` locally, the `coverage` suite in CI. They are gated by `gate --require coverage,doctest` and produce no a11y rows. §3 Structured violation JSON schema (cli / tui) says failures surface only as nextest `suites[].failures[]`.
- a11y-plan §3 Screen reader test pattern (tui) adds a supplemental, founder-owned pass: NVDA with Windows Terminal, checking that the wrapped `claude` TUI reads the same as unwrapped (Must-Work O1). It is never the gating evidence.

## Anti-patterns to avoid
- Never parse the rendered `claude` TUI screen for content, and never use screenshots as a11y evidence. This is R7 (a11y-plan §11 Universal, §1 tui surface). Boundary tests may check viola's own literals and bytes only.
- Never block, refuse or delay a human keystroke in `viola run` past the current atomic paste. Never count focus, mouse or resize sequences as editing (a11y-plan §11 Keyboard).
- Never emit SGR under `viola run` (a11y-plan §11 Visual).

## Contract bindings
- **a11y ↔ tests harness:** the outer-PTY driver and `viola-fake-agent` are tests-owned. The chunk's switch of `supervise`, the `run_cli` tests and `tests/support/home.rs` `Wrapper` from the stdin pipe to the PTY form is the harness change the a11y tui boundary cases depend on (a11y-plan §3 Keyboard test harness → Tooling; §9 Unit / integration row).
- **a11y ↔ obs:** `run` diagnostics go to `<home>/diagnostics/run-<name>.ndjson`, never to the terminal. Obs owns that line shape (a11y-plan §1 tui Notes; §3 Structured violation JSON schema, process logs). a11y rows are never written into `diagnostics/` (a11y-plan §11 Universal).
- **a11y ↔ security:** stripped `CLAUDE*` values must not appear in any artifact (a11y-plan §10 failure conditions).

## Acceptance criteria contributions
- (a11y) Under the outer PTY on the windows-2025 leg, the byte stream across `viola run` start and exit with `viola-fake-agent` contains none of viola's own message literals and no SGR or cursor control the child did not emit. On the Linux and macOS legs it matches the unwrapped fake-agent run byte for byte. It never inspects `claude` content. (per a11y-plan §3 Keyboard test harness → Tooling; §4 P4 tui clause 1)
- (a11y) Human keystrokes written to the outer PTY reach the child unblocked and unmodified, as a separate nextest case on all three OS legs. (per a11y-plan §4 P4 tui clause 2; §5 Focus order per layout → tui)
- (a11y) A `.cmd`/`.bat` refusal or shim-resolution failure shown to the human prints `unable  <reason>  <detail>` then a final `hint:` on stderr with no SGR and a typed exit code, pinned by trycmd/assert_cmd. This applies only if P3/P4 confirm the refusal is human-facing. (per a11y-plan §8 Error recovery → CLI)
- (a11y) viola's own spawn and exit diagnostics for `run` land only in `diagnostics/`, and zero diagnostic bytes appear on the wrapper's terminal stream. (per a11y-plan §1 tui surface → Notes)
