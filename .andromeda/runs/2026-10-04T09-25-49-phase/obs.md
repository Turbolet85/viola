# obs extract

## Relevance
relevant — `wait` / `last` is one of obs-plan's seven must-trace paths (§4 Scenario: `wait` / `last` event-driven readback), and CARRY 2 is the §7 `cli`-role panic contract itself.

## Constraints
- obs-plan §4 Scenario `wait` / `last` requires the span chain `wait.block` (CLIENT) › `channel.request` → `channel.dispatch` › `run.wait_dispatch` (INTERNAL), and `last.client` › `channel.request` for `last`. `wait.block` carries `after` and `timeout_ms`. `run.wait_dispatch` carries `woken_kind` (`turn-ended|question|permission|plan|session-end`) or `timed_out`. Span kinds are listed in §4 Span kinds, and names stay static per the §4 naming convention. Whether any of these spans exist in code today is research's question.
- obs-plan §4 (same scenario) and the §6 additive field catalog require `channel-request{corr:<JSON-RPC id>, conn, method:"wait"|"last", after, timeout_ms}` and `channel-response{corr, conn, result_class, outcome, duration_ms}`, with `outcome` ∈ `<woken kind>|timed-out|instance-unreachable`. Both are logged on both sides (§10 Correlation propagation), and `channel-response` is emitted from the `channel.dispatch` `Drop` guard (§4 Scenario: Confirmed `send`, Cleanup). The `corr` = JSON-RPC `id` rule comes from §3 Log format JSON schema. That schema requires `corr` on `channel-request` unless `method` is `hook.event`. Research should check whether `schemas/diag-line.v1.json` already admits `after`, `timeout_ms` and `outcome`, the `wait` / `last` `method` values and the `outcome` values. Under default-deny (§8 Default-deny posture), any field it lacks fails G4 (§9).
- Client exit lines: obs-plan §4 (same scenario) and the §6 `detail` code catalog require `process-exit{subject:"self", exit_code, detail}` in `cli-<name>.ndjson` when an instance resolves (D-06). Exit 21 carries `detail` ∈ `instance-dead|strict-modes-failed|server-verify-failed` plus `during` ∈ `connect|call`. An endpoint that vanishes mid-wait is `instance-dead` + `during:"call"`, and the client logs that disconnect once (§4 Cleanup). Exit 21 is logged at `warn`, exit 1 / 20 at `error` (§6 Log levels mapping). The wire refusal stays `instance-unreachable`. The log `detail` code is a separate closed vocabulary.
- `cli`-role panic (CARRY 2): obs-plan §7 Panic hooks → Per-role behaviour requires a short-lived `cli` verb to write `process-exit{subject:"self", exit_code:1, detail:"internal-error"}` (via `obs::internal_error_exit_line`) when an instance resolves, then exactly one `error: internal error\n` in one `write_all`, with no hint, and exit 1. §7 Main-thread catch site requires the role to come from argv before clap runs (D-28): `run|hook|mcp|ui` are named roles, and any other verb is `cli`. So `send` / `wait` / `last` fall under `cli`. The arch-side fix shape (one catch site) is P4's, not obs's.
- Zero unlogged panics: obs-plan §10 Always-required SLO invariant requires every post-init-step-4 panic in `cli` to produce exactly one home-level `level:"ERROR", event:"panic"` line. The bounded exemption 2 (`cli` without a resolved instance, D-06) is the only `cli` carve-out. §7 says the panic hook only writes. The exit is decided at the catch site.
- Content floor: obs-plan §8 Data classification makes `last_assistant_message` (and prompt text inside a returned `events.ndjson` line) High. It must never reach a home-level `diagnostics/*.ndjson` line, and may appear only in an instance `detail-<process>.ndjson` inside a chain. §4 Scenario `wait` / `last` restates it ("`last_assistant_message` never appears"). The §8 Scrubbing libraries / Integration points require veil `#[derive(Redact)]` with `#[redact]` on `LastResult.last_assistant_message`. Whether that type and attribute exist yet is research's question. The `wait` result's `event` payload is the same content class and gets the same treatment. No result body is ever logged, not even hashed (§6 Boundary-call wrappers, IPC invocation).
- Deterministic, non-polling emission: obs-plan §10 Standard+ invariants (Deterministic emission) require the wake to key on `events.ndjson` offsets and hook events, never on screen content or sleeps. §11 Telemetry Strategy bans deriving telemetry from screen content. Any tail or notify used for the wake logs cursor advances at `debug` only (§6 Log levels mapping, `debug` row), never a per-line `info` (§11 Logs).

## Patterns to follow
- The landed `send` path is the template for `wait` / `last`: client dispatch span › `channel.request`; codes-only `channel-*` lines with `corr` + `conn`; `process-exit{exit_code, detail, during}` on the client (obs-plan §4 Scenario: Confirmed `send`, Cleanup). Reuse its exit-21 `during` split for `connect` vs `call`.
- Emit only through `obs_event!` under `#[instrument(skip_all, name = "...", fields(...))]` with an explicit typed field allow-list. Set `corr` as a typed field, never `?corr` / `%corr` (obs-plan §4 naming convention; §11 Logs; §8 Integration points 1).
- `wait.block`'s `after` / `timeout_ms` and the `outcome` / `woken_kind` values are closed enums or integers, so they are admissible grouping keys or attributes. The derived counter `viola.wait.outcome` reads `channel-response{method:"wait"}.outcome` (obs-plan §5 Per-surface metrics), so the `outcome` field is what that metric depends on.
- Panic witness at unit level: the §7 per-role mapping is tested as role → exit → line tables. Extending those tables to `send` / `wait` / `last`, with a once-only assertion, satisfies §7 without a new seam. A real-binary forced panic would need a seam, and a seam needs a Decisions Log entry plus any G2 exemption (§10 Counting rule; §9 G2). That is P4's call.

## Anti-patterns to avoid
- NEVER use a bare `#[instrument]` or `#[instrument(ret)]` / `(err)` on the `wait` / `last` client or dispatch functions. `ret` would record the returned event line or `last_assistant_message` (obs-plan §11 Spans / Traces; §11 PII Scrubbing).
- NEVER log a field outside the §6 catalog, and never put a path, pid or upstream text in a `detail` code (obs-plan §11 PII Scrubbing; Founder Direction 4). That includes the `after` value's file path and the event `data`.
- NEVER let a `cli` panic print `error: internal error` twice, or exit without its home-level `event:"panic"` line when an instance resolves (obs-plan §10 SLO "exactly one"; §11 SLO). Never call the default panic hook (§11 Error Reporting).

## Contract bindings
- obs ↔ tests §3 Log format: `corr` = the JSON-RPC `id` on `wait` / `last` `channel-*` lines. Null is written as key absence (obs-plan §3 Log format JSON schema, Null encoding). `process:"cli"` writes `cli-<name>.ndjson` (D-06). The harness `agent-run logs --process cli` and G2 / G4 read these files.
- obs ↔ security §Logging / Data Classifications: the High class `last_assistant_message` / event payload goes to detail files only. The tests-owned canary secret scan asserts that no home-level `diagnostics/*.ndjson` carries the canary (obs-plan §8 Integration points 6). E2E inputs for `last` must embed that canary.
- obs ↔ arch §Conventions: exit 21 / exit 1 / exit 20 map to `process-exit.detail` codes (`instance-dead` + `during`, `internal-error`, `wrapper-fault`), per obs-plan §6 `detail` code catalog. The wire `instance-unreachable` refusal stays the arch's.
- obs ↔ schemas: any new `outcome` / `woken_kind` value or `method` value that `schemas/diag-line.v1.json` lacks needs a schema change in this chunk, or G4 fails (obs-plan §8 Default-deny posture; §9 G4). A new `event` value needs a Decisions Log entry (§11 Logs). This chunk should need none.

## Acceptance criteria contributions
- A `viola wait` that wakes on an appended driver-relevant line leaves, in `run-<name>.ndjson` and `cli-<name>.ndjson`, `channel-request{method:"wait", corr, conn}` and `channel-response{method:"wait", outcome:<woken kind>, corr, conn, duration_ms}` on both sides. A `timeout_ms` expiry leaves `outcome:"timed-out"`. All lines pass G4 against `schemas/diag-line.v1.json` (per obs-plan §4 Scenario: `wait` / `last` event-driven readback; §9 G4).
- Killing the wrapper while `wait` is parked gives client `process-exit{subject:"self", exit_code:21, detail:"instance-dead", during:"call"}` at `warn`, logged once (per obs-plan §4 Scenario: `wait` / `last`, Cleanup; §6 Log levels mapping).
- A `last` / `wait` run with a canary-bearing assistant message leaves the canary in no home-level `diagnostics/*.ndjson` line. It may appear only in `detail-*.ndjson` (per obs-plan §8 Integration points 6; §4 Scenario: `wait` / `last`).
- A panic in each of `send` / `wait` / `last` with a resolved instance yields exactly one home-level `event:"panic"` line, `process-exit{exit_code:1, detail:"internal-error"}`, exactly one `error: internal error` stderr line, and exit 1. An ordinary dispatch `Err` prints that stderr line exactly once (per obs-plan §7 Panic hooks → Per-role behaviour; §10 Always-required SLO invariant).
