# security extract

## Relevance
relevant: the switch adds no new surface, but the live drive crosses the plan's local trust boundary at the home, the dialog-answer gate, the wheel, the exec paths and the interim client gaps.

## Constraints
- The switched builder's home must pass the strict-modes check before any snapshot, stamp or `statusline_command` read. Per security-plan §Authentication & Authorization (`~/.viola/` access control), a home or `instances/<name>/` with any group or other bit (`mode & 0o077 != 0`) is refused: `run` and `mcp` exit 1, CLI verbs report `instance-unreachable` (exit 21), `list` refuses the whole board, and `hook` fails open with no trace. The prototype's `~/.viola` at 0755 therefore cannot serve as the product home without a mode change. Per the same section, opening a log narrows an existing home to 0700, which is why the check runs before the log. Whether the prototype's shared state root may be narrowed, or a separate `--home` is used, is the plan's choice. That choice also affects the other overseers' builders.
- Per security-plan §Security Anti-Patterns → Universal, "answers a review" needs a `viola verify` stamp in that home for the builder child's CLI version, read by `run`'s version gate through `read_stamps_strict` and covering the full relied set (`/24` on Unix). Without one, `answer` exits 12 `unverified-cli` and the hook prints nothing. On the installed 2.1.296, with every stamp on 2.1.287, getting that stamp means one `viola verify` run (five interactive PTY children). That run stays inside the bounds in security-plan §Threat Model Summary (Attack surface, child process spawning) and adds the transcript residual of security-plan §Data Protection (Accepted risk, verify's trusted runs). Both count toward the founder's start cap.
- Per security-plan §Authentication & Authorization (Driver-originated `release` row), a `release` whose params carry a string `from` is refused `-32602` `release-from-driver`, and CLI `viola release` takes `from` from `VIOLA_NAME` (exit 20 from a driver session). The release ending the takeover proof must therefore come from the human's side, from a process with no `VIOLA_NAME`, and never from the overseer session.
- Per security-plan §Threat Model Summary (Attack surface, the human's terminal), a key that reaches `viola run`'s stdin is the human's by construction. An agent typing it with `wtype` is a crossing of the human's own input. The founder ruled on it for chunk 2026-10-08-first-live-test-and-self-drive only: a nested compositor, a guard read that its window is the active one, and the desktop lock never touched. Whether that ruling covers this chunk's key, or whether it is a boundary widening for the P4 dialog, is research's and the plan's question.
- Per security-plan §Authentication & Authorization (IPC client-side server verification row), the overseer's product verbs (`send`, `wait`, `last` and `answer` as CLI verbs or `viola mcp` tools) write their frames only under the dated liveness-only interim gaps, until the Epoch 6 entries "Server verification before any frame" and "Home and code-bearing file integrity" land. A defect fix folded into this chunk must not add a frame, method or process that borrows a gap.
- Per security-plan §Input Validation (Paste text row and CLI arguments row), the pipeline skill and `/clear` reach `send` only as stdin or `--file` text. That text passes `validate_paste_text` and the empty-typed-text check, and `/clear` followed by LF, CR or CRLF is classified as the local command. Per the same section's Configuration values row, the overseer-home `dialog_hold_s` (3600 under this chunk's CARRY) is a whole number from 60 to 3600, read only from `config.json`. No env var or flag sets it, and a bad value takes 60 with one `parse-rejected` line.
- Per security-plan §Security Anti-Patterns → Universal, every exec-form `command` in the switched builder's `plugin/<version>-<hash>/` `hooks.json` and `.mcp.json`, in `instances/<name>/settings.json`, and in any `marketplace/viola/.mcp.json` is an absolute path, never a PATH lookup. Here `viola` first on PATH is the prototype. Per security-plan §Data Protection (Code-bearing artefacts), the pinned copy is re-hashed (SHA-256, truncated) before reuse. `plugin install`'s command is the canonical exe that ran the install and is never re-hashed, so an MCP command pointing at a `target/debug/viola` that the builder rebuilds is an integrity question for research.

## Patterns to follow
- Let the product create its own home: 0700 directories and 0600 files set explicitly, with every replaced file going through `viola_state::fs::replace_private` (per security-plan §Authentication & Authorization, `~/.viola/` access control). Do not adopt a pre-existing tree whose modes it did not set.
- Record a live round's CLI-side writes as counted residuals (transcripts under `~/.claude/projects/`, trust entries in `~/.claude.json`), with viola itself writing nothing under `~/.claude`, as the plugin chunk's accepted residual did (per security-plan §Data Protection, Accepted residual of a live round).
- Run any real-CLI `viola verify` from a folder the user trusts whose external CLAUDE.md import is already answered. Verify never answers a dialog, and a modal start is killed with no key (per security-plan §Data Protection, Dev-host prerequisite).
- Refusals go to automation only, and hooks fail open. A refused `send` or `answer` during the drive is recorded as the overseer's evidence, never routed around (per security-plan §Security Anti-Patterns → Universal).

## Anti-patterns to avoid
- Never let `config.json`, a `VIOLA_*` variable or a CLI flag switch off the strict-modes check, the server or peer verification, `validate_paste_text` or the `unverified-cli` gate to get the switch through (per security-plan §Security Anti-Patterns → Universal).
- Never resolve `viola` through PATH in an exec-form command or in the overseer's start line (per security-plan §Security Anti-Patterns → Universal).
- Never commit a live `--home`, a `.env` or any R8-stripped `CLAUDE*` value with the chunk's evidence (per security-plan §Security Anti-Patterns → Secrets).

## Contract bindings
- security ↔ capability ledger and test plan: the `unverified-cli` gate reads the relied ledger rows stamped by `viola verify`, so whether the builder's CLI version is stamped decides whether v1-33's "answers a review" can pass live (security-plan §Security Anti-Patterns → Universal).
- security ↔ obs: the NEVER-log floor (security-plan §Bootstrap phases, `logging-redaction-wire`) binds the live round's diagnostics and any harness `secret-scan` over them. The wheel and `release-from-driver` lines are obs events the takeover proof reads.
- security ↔ arch: the home choice (shared `~/.viola` or a separate `--home`) is an Occupied Resources decision whose strict-modes outcome security fixes (security-plan §Authentication & Authorization).

## Acceptance criteria contributions
- The live record shows the review dialog answered with a non-`null` decision only on a home whose stamp covers the builder child's CLI version over the relied set. Otherwise it records the `unverified-cli` refusal (exit 12) as such, never a workaround (per security-plan §Security Anti-Patterns → Universal).
- The switched builder's home and `instances/<name>/` read mode 0700 (no `& 0o077` bit) at the live round, and `viola list` / `send` against it never return `instance-unreachable` from a strict-modes refusal (per security-plan §Authentication & Authorization).
- The takeover's `wheel{holder:"human"}` is followed by a `release` that logs no `release-from-driver` line, issued from a process without a string `from` (per security-plan §Authentication & Authorization).
- Every exec-form `command` in the switched builder's `hooks.json`, `.mcp.json` and `settings.json`, and any installed `marketplace/viola/.mcp.json`, is an absolute path, never a bare `viola` (per security-plan §Security Anti-Patterns → Universal).
