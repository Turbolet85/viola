## Constraints
- Nothing overseer- or Andromeda-specific may enter the binary: the overseer's start line, `vstart.sh` / `vb.sh` / `vbr.sh` / `waitm.sh` / `waitlong.sh` / `scr.sh` changes and its procedure stay driver-side, and a gap found (groups 3 and 4) is surfaced, not built (per architecture §Established Decisions → [Scope Boundary]; per architecture §Design Philosophy, "Mechanism, not policy").
- A non-`null` dialog decision requires the child's CLI version to be stamped in the wrapper's own home (every relied row `pass`); on an unstamped version (the installed 2.1.296 against 2.1.287-only stamps) the wrapper still types, runs the wheel and emits events, but withholds dialog answers and drivers get `unverified-cli` (exit 12). Whether the overseer's chosen home already holds a stamp for the builder's version is research's question (per architecture §Established Decisions → [CLI Version Compatibility]; per architecture §Conventions, CLI exit codes).
- The home is chosen by `--home`, then the `VIOLA_DIR` grandparent (only when `VIOLA_NAME` / `VIOLA_DIR` pass the shape check), then `<user home>/.viola`; a `--home` carries the pinned copy, plugin folder, endpoint hash, logs, `budget.json`, `config.json` and ledger stamps with it, and only the default home falls back to `~/.claude/settings.json` for the statusline. Whether `~/.viola` (the prototype's 0755 state root) can be used by the product is research's question (per architecture §Cross-cutting Patterns → Config management).
- `run` pins a copy at `<home>/bin/<version>-<hash>/viola`, re-hashes an existing copy on every start (a mismatch refuses `pinned-hash-mismatch`, exit 1), and the plugin's hooks and `.mcp.json` carry that pinned path literally; the child gets `VIOLA_BIN` and a `PATH` prefixed with the pinned folder (per architecture §Occupied Resources → Filesystem; per architecture §Occupied Resources → Environment variables; per architecture §Infrastructure Patterns → Deployment model).
- A `viola run` whose `ViolaName` is `live` or `stale` refuses (exit 1, `already-live`), and `viola revive`'s preflight refuses `session-live` when one `claude agents --json` read lists the logged session live in another `claude` (skipped under `--fork`) — so the builder's switch from the prototype-wrapped session must end that session first or fork. Whether a prototype-wrapped session is listed by that read is research's question (per architecture §Established Decisions → [Session Liveness]).
- Any human editing key since the last turn boundary moves the wheel to the human and `send` is refused `human-typing` (exit 10); the wheel returns only by an explicit `release`, a CLI-only human verb (a `release` carrying `from` is refused `-32602` `release-from-driver`; no MCP `release` tool) (per architecture §Established Decisions → [Human Takeover / Wheel]; per architecture §Established Decisions → [MCP]; per architecture §Standard Contracts, channel methods).
- The dialog hold is `config.json`'s `dialog_hold_s` (whole seconds 60–3600, default 60), read once at the wrapper's start, so the overseer's 3600 must be in the builder's home's `config.json` before the builder's start; the 3600 s ceiling stays PROVISIONAL until a hold near it is read live at this entry (per architecture §Cross-cutting Patterns → Config management; per architecture §Established Decisions → [Hook Contract]).

## Patterns to follow
- Drive only through the five driver verbs — CLI `send · wait · last · answer · list` with `--json` and typed exits, or the MCP tools reaching a session as `mcp__plugin_viola_viola__<tool>` — with `wait --after <cursor>` taking `send`'s `cursor` (a byte offset into `events.ndjson`) (per architecture §Conventions, CLI; per architecture §Occupied Resources, Claude Code integration names; per architecture §Standard Contracts, channel methods).
- Prompt text (a pipeline skill such as `/andromeda-…`, and `/clear`) goes through stdin or `--file`, never a leading-slash argument (per architecture §Established Decisions → [CLI Conventions]).
- A `/clear` send is a ledger-listed local command: confirmed by its post-condition `session-start{cause:"clear"}` on a verified CLI, `ok` with `confirmed:false` / `unconfirmable` on an unverified one — the log line is then the evidence (per architecture §Design Philosophy, "Measured, never assumed"; per architecture §Conventions, normalised event kinds).
- Identity by instance, never by location: a driver call from inside a wrapped session carries `from` from its own `VIOLA_NAME`, and the driven wrapper records the implicit `link` once (per architecture §Cross-cutting Patterns → Identity by instance; per architecture §Established Decisions → [Links]).
- The product is named by an absolute path, never a `PATH` lookup (the prototype is first on the host's `PATH`); inside a wrapped session `"$VIOLA_BIN"` names the pinned copy (per architecture §Occupied Resources → Environment variables; per architecture §Established Decisions → [Plugin Scope]).

## Anti-patterns to avoid
- No config key, `VIOLA_*` variable or flag may switch off the version gate, the wheel or the hold bounds to make the live proof pass (per architecture §Cross-cutting Patterns → Config management).
- No driver-facing step, MCP tool or hint issues `viola release`; the release in the takeover proof is the human's (per architecture §Established Decisions → [MCP]).
- No Claude-specific shape added outside `viola-agent-claude`, and no unmeasured CLI behaviour relied on without a ledger row and `viola verify` probe (per architecture §Cross-cutting Patterns → Capability ledger as the single gate).
