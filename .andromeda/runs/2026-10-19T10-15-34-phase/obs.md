## Constraints
- The dialog half of the proof, the long hold included, is mandated by obs-plan §4 Scenario: Dialog → `answer`: `run.dialog_await` carries `deadline_ms` (the `dialog_hold_s` hold in ms, 60 000–3 600 000) and `deadline_hit`; an answer writes `dialog-answered{corr:<dialog_id>, dialog_kind, from, from_trust, deadline_hit, duration_ms}`, and the hold's end writes one `dialog-expired` product line plus `dialog-answered{deadline_hit:true}` with no `from`. A late answer's measured hold (the CARRY on the 3600 s ceiling) is that line's `duration_ms`; whether the overseer's home sets `dialog_hold_s` 3600 is the plan's choice. A non-`null` answer on an unstamped CLI is `refusal:"unverified-cli"` (exit 12, answer withheld), per obs-plan §4 Scenario: Dialog → `answer`.
- The clear between skills is confirmed per obs-plan §4 Scenario: Confirmed `send` (CL-1): `/clear` on a verified CLI is confirmed by the `session-start` whose `cause` is `clear` and whose `agent_session_id` differs from the remembered id, within `CONFIRM_WINDOW_FALLBACK` (10 s); on an unverified CLI (the installed 2.1.296 with no stamp) the send is unconfirmable, opens no `run.confirm_window` and ends `send-confirmed{confirmed:false}`. Which branch the live run takes is research's question (the CLI version the builder runs and the home's stamps).
- The takeover is recorded per obs-plan §4 Scenario: Human takes the wheel: the `wheel` product event in `events.ndjson` is the audit record (`run.wheel_transition` `cause` `human-input`, `wheel_to` `human`); an automated `send` while the human holds it is `send-refused{refusal:"human-typing", wheel:"human", side:"wrapper"}` with client exit 10; a `release` carrying a string `from` (CLI `viola release` forwards `VIOLA_NAME`) is refused `-32602` with one `release-from-driver` line. So the human's `viola release` must come from a shell with no `VIOLA_NAME` to return the wheel; whether the shell the operator uses carries one is research's question.
- Where the live record lands is fixed by obs-plan §3 Log file location: `<home>/diagnostics/{run-<name>,hook-<name>,mcp,cli-<name>}.ndjson`, `<home>` resolved `--home` → `VIOLA_DIR` → `~/.viola/`, files 0600 in 0700 dirs, content-bearing detail only in `<home>/instances/<name>/diagnostics/detail-<process>.ndjson`, no rotation (`events.ndjson` offsets are the `wait after` / `send cursor` cursors). The builder's home choice (default `~/.viola` vs a separate `--home`) therefore decides where the evidence is read.
- Short-lived verbs log per obs-plan §4 (Instrumentation per surface, cli row) and §1 (D-06): a CLI verb writes `process-start` / `process-exit` into `cli-<name>.ndjson` only under a parsed `VIOLA_NAME`, else no file; `viola mcp` always writes `mcp.ndjson` (stderr JSON only when it cannot be opened), its tools under `mcp.tool_call`. Whether the overseer session's inherited prototype `VIOLA_NAME` / `VIOLA_DIR` resolve a product home or name a `cli-<name>.ndjson` is research's question.
- Live inputs are non-synthetic, so obs-plan §8 PII Scrubbing binds: prompt and skill text, `last_assistant_message`, dialog questions and answers and tool `input` never reach a home-level line and reach only instance `detail-<process>.ndjson` inside a chain or drift report; "any non-synthetic input source must first drop `detail-*.ndjson` … from the upload paths" (obs-plan §8 PII Scrubbing, Integration point 5).
- obs-plan §10 SLO Invariants requires zero unlogged panics: every panic after init step 4 is exactly one `level:"ERROR", event:"panic"` line in its home-level role file, counted over home-level files only (detail files excluded), with no retry-once policy.

## Patterns to follow
- Read the live proof back from closed event kinds, never free text: `send-issued` / `send-confirmed` / `send-refused` keyed by `corr` (the send cursor) and `(conn, rpc_id)`, `channel-request` / `channel-response{method:"wait", outcome}` with `outcome` one of the six wake kinds (`dialog-expired` included), `dialog-raised` / `dialog-answered` keyed by `dialog_id` (obs-plan §4 Scenario: `wait` / `last` event-driven readback; §10 Correlation propagation).
- Liveness is the 1 s `heartbeat` file read through `list --json` `liveness` (4.9 s live / 5.1 s stale), never a logged tick (obs-plan §3 Heartbeat ticks).
- Any defect fix logs only through `obs_event!` with explicit typed fields under `#[instrument(skip_all, name = "<area>.<operation>", fields(..))]`, at the level obs-plan §6 Log levels mapping assigns (refusals `info`, `process-exit` exit 1/20 `error`, exit 21 `warn`).
- A fix adding a field or a `detail` code extends obs-plan §6's Additive field catalog / `detail` code catalog and `schemas/diag-line.v1.json` together (default-deny, obs-plan §8 Default-deny posture).

## Anti-patterns to avoid
- Deriving any signal from screen content — the product stores no screen, and the overseer's screen read (`scr.sh`, gap-list group 3) must not be rebuilt as telemetry (obs-plan §11 Telemetry Strategy; §10 Deterministic emission).
- Copying send text, `last_assistant_message`, dialog text, tool `input`, `statusline_command` or any `detail-*.ndjson` line into chunk evidence or a home-level line; paths or pids inside `detail` codes (obs-plan §11 PII Scrubbing).
- A new `event` value or a renamed field without a Decisions Log entry; a bare `#[instrument]` or `print!` / `eprintln!` in a `run` / `hook` / `mcp` path (obs-plan §11 Logs; §11 Spans / Traces).
