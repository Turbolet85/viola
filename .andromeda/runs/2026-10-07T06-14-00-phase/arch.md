# arch extract

## Relevance
partial — the chunk builds no product surface (no crate API, channel verb, route or wire format); arch binds it through the resource registry's `target/e2e-home` entry, the shared replace helper's durability step, the env-var rule, the CI/CD contract (CI's home reads and the native `pre-push`) and the endpoint-name / socket-dir rules.

## Constraints
- architecture.md §Occupied Resources → Repository (the `target/e2e-home/…` entry) registers the harness-session, root-test and local-live homes under `target/e2e-home/` — gitignored, kept in CI for the obs gates, each `viola-test-*` dir with `owner.json` beside `home`, both removals through `remove_owned`. The chosen backing must leave every one of those paths resolving as registered; any form that changes what the entry states (where the bytes live, what the sweep walks, what "gitignored" covers) is named for the wrap's amendment of that entry. Whether the owner-record sweep and `remove_owned` behave the same when `target/e2e-home` is a mount point or a link is research's question.
- architecture.md §Established Decisions [Snapshot writer] requires every replaced file to go through the one helper `viola_state::fs::replace_private` / `replace_private_shared` (temp file beside the target, mode before any byte, write, `sync_all`, `persist`), with no call site carrying its own temp + rename. The chunk changes none of it. Because that decision places the temp file beside the target and ends in a `persist`, the backing boundary must sit at or above a home, never inside one (derived from the decision, not stated in it): a temp file and its target on two filesystems cannot be persisted atomically.
- architecture.md §Established Decisions [Deployment / Distribution] requires `viola run` to copy its own exe into `<viola home>/bin/<version>-<hash>/` when absent, re-hash an existing copy before reuse, and have every hook and MCP entry call that pinned path; architecture.md §Occupied Resources → Filesystem (the `bin/<version>-<hash>/viola(.exe)` entry) requires the copy to be 0700 on Unix. The backing must therefore honour Unix modes and owner and permit execution from inside a home. Whether the candidate tmpfs (the host's `/tmp`, or a founder-run mount and its options) is mounted so that a pinned copy can be executed and its modes kept is research's question.
- architecture.md §Conventions → Naming patterns (Environment variables) requires any test-harness-only variable to carry the `AGENT_RUN_` prefix and never be read by the `viola` binary; architecture.md §Cross-cutting Patterns → Config management requires that environment variables are no configuration channel and that the viola home resolves only as `--home`, then the grandparent of `VIOLA_DIR`, then the default. A "harness option" form of the backing therefore lives wholly on the test side (the `--home` the tests already pass), adds no `VIOLA_*` variable, no product flag and no third test seam.
- architecture.md §Infrastructure Patterns → CI/CD approach requires the CI `test` and `perf` jobs to run with `AGENT_RUN_KEEP_HOMES=1` and then read the kept homes (G2, the G4 `schema-check`, `secret-scan`, and the `diag-*` uploads over `target/e2e-home/**/diagnostics/*.ndjson`). CI's behaviour is unchanged by this chunk: no step, glob, upload or gate in `ci.yml` moves, and the runners' homes stay on the runner's disk. Each such glob either holds as written under the chosen backing or is named for the wrap's amendment of that key.
- architecture.md §Infrastructure Patterns → CI/CD approach requires the local `pre-push` to run natively on the Linux host in the working tree itself, every child under `/usr/bin/env -i` with `HOME` and `PATH` only and no further assignment, running the ubuntu `test` job's `run --coverage`, `run --browser` and gate. A backing selected by an environment value therefore never reaches `pre-push`'s children; the backing must be in force for them without any assignment (a property of the path itself, or of test-side code that reads no host value). Whether the present harness and root test chain derive the homes' path without an environment read is research's question.
- architecture.md §Conventions → Data model conventions (Endpoint name) requires the endpoint name to hash `ViolaName` + `\0` + the absolute viola home path, and architecture.md §Occupied Resources → IPC endpoints requires the Unix socket and its `.lock` arbiter to live in the per-user 0700 socket dir (`$XDG_RUNTIME_DIR/viola/` on Linux), not under the home. The backing moves no socket; with the homes' path unchanged the endpoint names are unchanged. Whether the code canonicalises the home path before hashing or recording it (so that a link, unlike a mount, would change the hashed path and the snapshot's recorded paths) is research's question.

## Patterns to follow
- A dev-host environment fact that is not harness code is recorded in the registry as such: architecture.md §Occupied Resources → Repository (the `<repo parent>/viola-mutants-scratch/` entry) carries the Linux dev host's `TMPDIR` requirement as "an environment fact, not harness code", with the measurement behind it and without printing the path. A founder-run mount or a link is recorded the same way at the wrap.
- The same entry (architecture.md §Occupied Resources → Repository, `<repo parent>/viola-mutants-scratch/`) records the host's `/tmp` as a quota-bounded tmpfs on which a full run died on the quota. P4's pricing of the no-root backing reads the transient batch size and the kept homes (`AGENT_RUN_KEEP_HOMES` / `AGENT_RUN_KEEP_FAILED`) against that recorded bound.
- A home that sits outside `target/e2e-home` is a named, ratified carve-out, never a default: architecture.md §Occupied Resources → Filesystem (the `<temp dir>/viola-chaos-*/home` entry) names it the second carve-out to the test-data rule and states what leaving the path means (outside G2, G4 and the secret scan). This is why the homes' path stays `<workspace>/target/e2e-home` under the new backing.
- Test-side sites outside the repository are registry entries: architecture.md §Occupied Resources → Filesystem (the "Test-side install sites, outside the repository" entry, and the `viola-pty-watch` / `viola-root-watch` entries) lists each with its writer and the line that `viola` never reads or writes it. A backing directory outside the repository (for example under the OS temp dir) gets such an entry at the wrap.
- Test-only code stays in the two test-side homes of the path logic: architecture.md §Occupied Resources → Environment variables names the root test chain (`tests/support/home.rs`) and `viola-harness` (`viola-e2e`) as the readers of the `AGENT_RUN_KEEP_*` variables, and architecture.md §Infrastructure Patterns → Crate dependency direction keeps `viola-e2e` test-only with no product crate depending on it. A harness-side backing change lands in both, so the root rstest homes and the harness sessions stay under one rule.

## Anti-patterns to avoid
- Removing, skipping or conditioning `sync_all` in the shared helper, or adding a second temp + rename path for test homes: architecture.md §Established Decisions [Snapshot writer] makes the helper the one writer and `sync_all` part of it, and architecture.md §Cross-cutting Patterns → Crash-safe disk writes requires mutable files to be replaced atomically. The pinned copy is product durability, not a test seam.
- A new variable read by any `viola` build, or a product flag, to pick a backing: architecture.md §Cross-cutting Patterns → Config management limits the non-`VIOLA_*` reads of any `viola` build to the two ratified `fake-agent` seams.
- A Linux-only arm that changes what the other hosts or CI do, or that no CI runner exercises: architecture.md §Design Philosophy (Cross-platform from the first commit, Windows first) forbids a design choice that depends on POSIX-only behaviour, and architecture.md §Cross-cutting Patterns → Cross-platform discipline requires every OS-specific branch to compile and be tested on its CI runner. A host-only backing that lives in test code must still leave the ubuntu runner on its disk; how a dev-host-only branch is tested without changing CI is a P4 question.

## Contract bindings
- arch ↔ tests: the homes' location, the keep variables and the owner-record sweep are registered in architecture.md §Occupied Resources (Repository, Environment variables) and implemented under the tests domain's harness contract and test-data rule (test-plan §3, §5); a change to how a home's directory is created binds both.
- arch ↔ obs: architecture.md §Infrastructure Patterns → CI/CD approach wires G2, G4 and the `diag-*` uploads over `target/e2e-home`; their scopes and globs are obs's (obs-plan §9). Whether the tools behind them traverse a link at `target/e2e-home` on the dev host is research's question; CI is untouched.
- arch ↔ security: the strict-modes check (architecture.md §Stack and Technologies, the State-file primitives row: Unix modes and owner through libc) and the `pre-push` `env -i` boundary (architecture.md §Infrastructure Patterns → CI/CD approach) are enforced under security-plan; a home whose parent is a shared tmpfs root and any new assignment on the `pre-push` launcher are security's to judge.
- arch ↔ wrap: a new occupied resource (a mount, a link target, a backing dir, a harness variable) is recorded in architecture.md §Occupied Resources at the wrap; nothing in the plan's body is edited by the chunk itself.
