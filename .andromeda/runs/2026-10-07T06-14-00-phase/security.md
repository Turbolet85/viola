# security extract

## Relevance
partial — a dev-host test-backing chunk that changes no product control, but it moves where test homes (0700/0600 state, a pinned executable, content-bearing logs) physically live, and two of its three candidate mechanisms (a link, a harness option) touch home canonicalisation, the env-crossing rule of the pre-push launcher and the no-seam rule.

## Constraints
- security-plan §Authentication & Authorization (`~/.viola/` access control) requires every home, "any `--home`" included, to be 0700 with 0600 files, the pinned `bin/<version>-<hash>/viola` 0700 and executable, and requires the Unix strict-modes check (owner == euid, no group/world write, the `mode & 0o077` read rule on the home, `instances/<name>/` and `ui/`) at every entry point that reads `snapshot.json`, `ledger/stamps.json` or `statusline_command`. The chosen backing must leave all of this true for a test home. Whether a tmpfs reached through a mount or a link reports owner and mode as the check reads them, and whether its mount options allow executing the pinned copy (a `noexec` backing fails every hook and MCP exec), is research's question.
- security-plan §Input Validation (CLI arguments / stdin row, Home path) requires `--home` and `VIOLA_DIR` to be canonicalised and then pass strict-modes before any snapshot, `statusline_command` or ledger read. A link at `target/e2e-home` makes the canonical home the link target, a mount leaves it the workspace path: P4 prices the two differently on this row. Whether the code canonicalises on every path a test start takes, and what then keys off the canonical path, is research's question.
- security-plan §Authentication & Authorization (`~/.viola/` access control) requires every replaced file to go through `viola_state::fs::replace_private`: temp file in the target's parent, mode set before any byte, `sync_all`, `persist`. The chunk may not remove, skip or seam any of the four steps; the stall is removed by the backing, never by the helper.
- security-plan §Security Anti-Patterns → Universal requires that no `config.json` key, `VIOLA_*` variable or CLI flag switch off a control (the home strict-modes check is named) and that no further test seam exist without its own Decisions Log entry. A "harness option" backing must live wholly on the test side (`viola-e2e` / `tests/support`); a `viola` product crate reading a new variable, key or flag for it is a boundary widening.
- security-plan §Secret Management (Storage, Development) requires every pre-push child to run under the launcher with exactly `HOME` and `PATH`, no host value crossing, and names any assignment taking a host value a boundary widening with its own Decisions Log entry. A backing selected by an inherited variable does not reach pre-push children under that rule: either the backing needs no variable (a mount, a link, a path constant), or the widening goes to the founder.
- security-plan §Dependency Security (Pinning, the `pre-push` bullet) requires that no harness command, gate or pre-push stage launch anything as uid 0 and that no provisioning script exist. A tmpfs mount, an fstab or unit entry is therefore never the builder's or the harness's act; it is the founder's hand at the desk, which matches the scope's boundary.
- security-plan §Bootstrap phases (`secret-scanning-ci-gate`) requires `.gitignore` to exclude any local `--home` test directory, and requires CI's `viola-harness secret-scan` to read test-home diagnostics before any scan-gated upload. The backing path, link or mount point must stay untracked, and the scan's and the uploads' view of `target/e2e-home` in CI must be unchanged.

## Patterns to follow
- The plan's own model for a directory under a world-writable parent is the per-user 0700 directory verified by `lstat` (owner == euid, `mode & 0o077 == 0`, not a symlink), with a per-uid name as the `/tmp` fallback (security-plan §Authentication & Authorization, IPC access control (Unix)). The plan mandates it for the socket directory, not for a home's parent; a no-root backing under `/tmp` should follow it by analogy, and P4 should say so as a choice, not as an existing mandate.
- One home per test, each `viola ui` under test with its own token (security-plan §Secret Management, Storage, Development): the backing changes where the homes' parent lives, never the one-home-per-test shape.
- Host-scoped harness behaviour is gated by host and leaves operator-owned host directories alone: the mutation scratch guard runs only on Windows, and the Linux dev host's `TMPDIR` for mutation runs is "the operator's, never wiped by the harness" (security-plan §Security Anti-Patterns → Code Patterns). A Linux-dev-host-only backing follows the same split.
- A boundary widening is shown to the founder and recorded as a dated Decisions Log entry before it lands (security-plan §Secret Management, Storage, Development; §Security Anti-Patterns → Universal). If the priced option needs one (a launcher assignment, a product-side read), it is a P4 fork for the founder, not a builder's call.

## Anti-patterns to avoid
- Never make the new backing pass by relaxing, bypassing or conditionally skipping the home strict-modes check, the mode-before-write step or `sync_all` (security-plan §Security Anti-Patterns → Universal; §Security Anti-Patterns → Data Protection, the default-umask ban on `--home` and every file under it).
- Never let a harness sweep or cleanup delete outside the workspace through a link: the plan's only sanctioned harness wipe is the guarded Windows mutation scratch, refused on any other resolved path (security-plan §Security Anti-Patterns → Code Patterns). Whether the present home sweep resolves a link at `target/e2e-home` and removes entries on the far side is research's question.
- Never commit a local `--home` test directory or anything recorded from one (security-plan §Security Anti-Patterns → Secrets); kept homes (`AGENT_RUN_KEEP_HOMES` / `AGENT_RUN_KEEP_FAILED`) on the new backing hold `events.ndjson`, `diagnostics/` and `ui/<port>.url` and stay protected only by their 0700/0600 modes (security-plan §Data Protection, At rest — Files, Logs).

## Contract bindings
- security ↔ obs / tests: the artifact canary scan (`viola-harness secret-scan`, obs-plan §9 step 3) reads test-home diagnostics and each home's `ui/*.url`, and gates the test-home uploads (security-plan §Secret Management, Secret scanning in CI). W3's read of every CI glob over `target/e2e-home/**` is also a read of this gate: a scan that finds no home is a vacuous pass. Whether the scan's walk and the upload globs follow a link is research's question (CI itself is out of the backing's reach by scope).
- security ↔ architecture: the endpoint name is derived from `ViolaName` + the home path, and the cookie-gated `/api/info` discloses `viola_home` (security-plan §Threat Model Summary, Attack surface, Local IPC and operational metadata). A backing that changes the canonical home changes both values; architecture §Conventions (Endpoint name) and §Occupied Resources (Filesystem) own the statement.
- security ↔ tests: the pre-push launcher's two-assignment environment (security-plan §Secret Management, Storage, Development) binds test-plan §3's harness: any harness option must work with no variable beyond `HOME` and `PATH` reaching the children.
- security ↔ architecture (hook path): `viola hook <event>` requires an absolute `VIOLA_DIR` ending `<home>/instances/<name>` and does not canonicalise it under the ratified interim gap (security-plan §Input Validation, CLI arguments / stdin row). Whether `run` hands the hook the canonical or the as-given home under a link backing is research's question.

## Acceptance criteria contributions
- On the new backing a test home reads 0700 directories, 0600 files and a 0700 pinned `viola` owned by the running euid, and a `viola run` test start records no strict-modes refusal and executes its pinned copy (per security-plan §Authentication & Authorization, `~/.viola/` access control).
- The chunk's diff adds no environment read, `config.json` key or CLI flag to any `viola` product crate and leaves `replace_private`'s mode-set, `sync_all` and `persist` untouched (per security-plan §Security Anti-Patterns → Universal).
- Every pre-push launcher call still carries exactly `HOME` and `PATH`, and the diff adds no uid-0 launch and no provisioning script (per security-plan §Secret Management, Storage, Development).
- `git status` after a full local run shows no test home, link or backing path tracked or untracked-unignored, and the CI `secret-scan` step and its scan-gated uploads are byte-unchanged in `ci.yml` (per security-plan §Bootstrap phases, `secret-scanning-ci-gate`).
