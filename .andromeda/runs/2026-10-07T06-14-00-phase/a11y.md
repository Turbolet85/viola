# a11y extract

## Relevance
partial — the chunk builds no UI surface, no CLI output and no a11y check; it re-backs the test homes that a11y's harness sessions and its nextest-hosted CLI / TUI checks start `viola` in, so only the harness-substrate, scrub and no-masking rules of the plan apply.

## Constraints
- a11y-plan §3 CI integration requires every web a11y spec to run inside the tests' harness lifecycle (`boot` → test → `cleanup` through `scripts/agent-run.* run --browser`), with no separate driver. If the backing is done as "a harness option" (scope W1), it must stay inside those five commands and leave the per-test session lifecycle as that contract states it; whether the harness's `boot` homes actually sit under `target/e2e-home` (scope premise, `crates/viola-e2e/src/harness/mod.rs:84`) is research's question.
- a11y-plan §3 Structured violation JSON schema (Scrubbing) requires any absolute filesystem path — the viola home is its named example — in an a11y attachment to fail the test as `scrub-leak`. A backing reached through a link or a mount can change the home's resolved absolute path (for example to a tmpfs location); whether the scrubber's path match covers the home's path under the chosen backing, and whether any a11y attachment carries a home path at all, is research's question.
- a11y-plan §3 Structured violation JSON schema (Emission location) requires a11y rows to live under `e2e-web/test-results/a11y/` and never under `<home>/diagnostics/`. The backing must not relocate or shadow `e2e-web/test-results/`; the chunk's W3 read of "every CI glob that reads `target/e2e-home/**`" does not, by this plan, include an a11y glob — whether ci.yml's upload step is written that way is research's question.
- a11y-plan §9 CI Integration (Pipeline integration) requires the web a11y verdict to be judged on the ubuntu CI leg only, with the browser suite running on all three legs. The scope's "CI is unchanged in behaviour" must hold for that leg's `run --browser` and its gate: the backing is a Linux dev-host matter and no CI step, glob or env may change the a11y leg.
- a11y-plan §10 SLO Invariants & A11y Budgets requires the CLI output-discipline invariants (P4, P6) to pass on all three OS legs inside `nextest-integration` / `nextest-e2e` (CI: `coverage`). Those cases start `viola` in test homes; the backing must leave them passing unmodified on the dev host and untouched on Windows and macOS.
- a11y-plan §10 SLO Invariants & A11y Budgets requires `retries: 0` and no retry-once policy. The stalled-start reds this chunk addresses are closed by removing the stall's cause on the dev host, never by a retry, a widened timeout or a parked test on any a11y-bearing suite.

## Patterns to follow
- One harness, one driver: a11y adds no suite and no second driver beside `scripts/agent-run.* run --browser` (per a11y-plan §9 CI Integration, Pipeline integration) — a backing change follows the same shape, landing beneath the existing commands rather than beside them.
- Waits key on DOM signals and logged events, never on sleeps (per a11y-plan §10 SLO Invariants & A11y Budgets, Performance budget) — the chunk's contended reading is a measurement of its own and adds no sleep or timing allowance to an a11y spec.
- The TUI boundary cases run on the tests' portable-pty outer-PTY driver on all three OS legs (per a11y-plan §4 ARIA Patterns & Roles, P4) — they are consumers of the test home, unchanged in assertion by where its bytes land.

## Anti-patterns to avoid
- NEVER a retry-once policy, a sleep / `waitForTimeout`, or a `test.skip` / `test.fixme` / quarantine tag to get past a stalled start in an a11y spec (per a11y-plan §11 A11y Anti-Patterns, SLO).
- NEVER a new `suite` value, a `webServer` or a separate driver outside `scripts/agent-run.* run --browser` as the vehicle for the backing (per a11y-plan §11 A11y Anti-Patterns, CI).
- NEVER a11y violation rows written into `<home>/diagnostics/`, whatever backs the home (per a11y-plan §11 A11y Anti-Patterns, Universal).

## Contract bindings
- a11y ↔ tests harness: a11y's per-test `boot` / `cleanup` session lifecycle rides the tests' five-command harness (a11y-plan §3 CI integration ↔ test-plan §3); where that harness places its homes is the tests plan's statement, not a11y's — the a11y plan names no home path.
- a11y ↔ tests Error sanitization: the absolute-path scrub on a11y attachments (a11y-plan §3 Structured violation JSON schema, Scrubbing) binds to the tests plan's Error sanitization trigger; a changed resolved home path is judged there.
- a11y ↔ tests CI gate: the a11y verdict sits inside the `playwright` suite entry and `gate --require …playwright` on the ubuntu leg (a11y-plan §9 CI Integration ↔ test-plan §9 / §10); the chunk's CI-glob read (W3) shares that workflow file.

## Acceptance criteria contributions
- (a11y) With the new backing in place on the dev host, `scripts/agent-run.sh run --browser` still boots, runs and cleans up each `pw-<spec>-<test id>-<workerIndex>` session through the unchanged five commands, with no new suite, driver or `webServer` (per a11y-plan §3 CI integration).
- (a11y) No a11y attachment produced under the new backing carries the home's resolved absolute path: zero `scrub-leak` rows, or research records that no a11y spec exists yet to produce one (per a11y-plan §3 Structured violation JSON schema).
- (a11y) The chunk's diff changes no step, glob or env of the ubuntu leg's `run --browser` / `gate` in `ci.yml`, and `e2e-web/test-results/` stays the a11y artifact root (per a11y-plan §9 CI Integration).
- (a11y) The stalled-start fix adds no retry, sleep, timeout widening or skip to any suite that carries a11y checks (`playwright`, `nextest-integration`, `nextest-e2e`, `coverage`) (per a11y-plan §10 SLO Invariants & A11y Budgets).
