# tests extract

## Relevance
relevant — the chunk changes what backs the test homes on the Linux dev host, and the homes' location, lifetime, sweep and CI read-out are test-plan contracts (§3 `boot`, §3 `cleanup`, §3 Test data bootstrap, §5, §7, §9).

## Constraints
- test-plan §5 Setup / teardown lifecycle requires every rstest home to be a not-yet-existing `home` path inside a `tempdir_in("<workspace root>/target/e2e-home")` parent, so that viola creates the home itself, and admits exactly two carve-outs (`seed_conpty`, `TestHome::outside_scan()`), each a dated ruling. A backing that leaves that path string and that creation order intact needs no amendment here; a backing that puts any home elsewhere is a third carve-out and is named for the wrap (W3), never taken silently. Whether `TestHome::new` and the harness reach the path in a way a mount or a link leaves untouched is research's question.
- test-plan §3 `boot` step 2 requires the harness home's parent to come from `tempdir_in("<workspace root>/target/e2e-home")` and the home itself to be created by viola at 0700, never pre-created by the harness. Whether viola's home creation and the strict-modes checks hold when `target/e2e-home` is a tmpfs mount point or a link target (owner, mode, canonicalised path) is research's question; the scope's Boundaries forbid changing those checks to make it hold.
- test-plan §3 Test data bootstrap (Cleanup) requires a root `TestHome` to remove its home on drop through `remove_owned`, to record `owner.json`, and a new `TestHome` to sweep only the dirs whose recorded owner process is gone; `AGENT_RUN_KEEP_HOMES` / `AGENT_RUN_KEEP_FAILED` keep homes in place. The backing must leave all of that working on the new filesystem; kept homes then occupy the backing until swept, which P4 prices against the backing's capacity (each home carries a pinned copy of the binary, per test-plan §3 `run` step 4 Command).
- test-plan §7 Test data lifecycle (CI) requires CI homes to live under the workspace's `target/e2e-home/` on the ephemeral runner and to be kept until the obs gate steps have run. The chunk must change nothing a CI runner executes on that path: no `ci.yml` step, no harness default that a runner would pick up. Whether a chosen mechanism is inert off the Linux dev host (CI ubuntu included) is research's question.
- test-plan §3 `pre-push` requires every child of the local gate to run under `/usr/bin/env -i` with only `HOME` and `PATH` set, no host value crossing. A backing selected through an environment variable would not reach the pre-push children without widening that launcher, so a "harness option" candidate is priced against this at P4; a path-level backing (mount or link) crosses unaided.
- test-plan §3 Bootstrap phases `test-runner-install` requires the nextest `ci` profile's kills as written (the 20 s kill of the twelve verify-driven binaries, the default kill, `retries = 0`), and test-plan §3 `run` step 2 requires `WITHIN` = 7 s as the bound of every other root wait. The chunk's green must come from the backing; no kill, no `WITHIN`, no override moves (the §5 Setup / teardown lifecycle precedent records "no bound was raised").
- test-plan §10 Mutation gate records that on the Linux dev host `/tmp` is a quota tmpfs a full viola-e2e mutation run overflowed, and requires mutation runs to take `TMPDIR` on a NOCOW btrfs dir; cargo-mutants copies the tree, `target/` included. A backing that puts homes on that same tmpfs shares its quota, and a mount point or link at `target/e2e-home` is inside the copied tree: what the copy does with it, and where a copied tree's tests put their homes, is research's question (test-plan §3 `run` step 4 Command sets `AGENT_RUN_KEEP_HOMES=0` there).

## Patterns to follow
- Homes by `tempfile` under one workspace-relative root, the home created by the product: test-plan §5 Setup / teardown lifecycle and test-plan §3 `boot` step 2. One backing at `target/e2e-home` covers the rstest chain, harness sessions, the perf session (test-plan §10 Performance budgets, Perf session) and the `--local-live` verify home (test-plan §3 `run`, `--local-live`), which is the home the next route entry's live round uses.
- A timing problem is closed by a measured two-sided reading recorded in the chunk's `evidence/`, the way test-plan §5 Setup / teardown lifecycle records the `seed_conpty` carve-out (a dev-host median under a parallel suite) and test-plan §5 Module ↔ PTY records "6/6 red before the fix, 6/6 green after". W2's contended red/green reading follows that shape: same contention on both sides, counts and seconds, the backing the only variable.
- A host-specific environment fact is recorded in the plan as an operator-set fact with the harness arm left unchanged, as test-plan §10 Mutation gate does for the Linux dev host's `TMPDIR` ("an environment fact; the harness's scratch arm stays Windows-only"). If the chosen backing is a mount or a link the founder or operator sets, it is recorded the same way.
- The local verdict is the harness's: `scripts/agent-run.sh pre-push` (stages `host` · `tools` · `linux-tests`: `run --coverage`, `run --browser`, `gate --require coverage,doctest,playwright`) per test-plan §3 `pre-push`; a single test through `scripts/agent-run.sh run --integration --filter '<nextest filterset>'` per test-plan §3 `run` Test selection.

## Anti-patterns to avoid
- No retry, no raised kill, no parked test to turn the stalled starts green: test-plan §10 Zero-flakiness budget and test-plan §11 CI (`retries` above 0) / §11 Quality (retry-once policies).
- No committed test whose verdict is a test-owned timer or an elapsed-time reading of the contended start: test-plan §11 Universal (real time without injection). The contended reading is evidence, not a suite member.
- No test seam that skips or fakes the start's on-disk writes to dodge the stall: test-plan §11 Integration (never mock the on-disk state; a real tempfile home) and test-plan §7 Seed strategies (on-disk product state produced only by the real `viola run`). And a green on the Linux dev host proves nothing for the other OSes' homes: test-plan §11 Test Strategy (a Linux-only local run).

## Contract bindings
- obs ↔ tests: obs-plan §9's G2 (`scripts/g2-zero-panics.sh`), G4 (`schema-check`), the secret scan and the `diag-<os>` / `diag-perf-<os>` uploads read `target/e2e-home/**` (test-plan §3 `schema-check`, §3 `secret-scan`, §9 Test report format, §3 Bootstrap phases `ci-tool-install`). These are the "CI globs" of W3; they run in CI's `test` and `perf` jobs, and whether any of them is also run locally over a mounted or linked `target/e2e-home` (and whether its walker follows a link) is research's question.
- security ↔ tests: the home is created by viola at 0700 and must pass strict-modes at every reader (test-plan §3 `boot` step 2; test-plan §6 Exit-cause matrix lists a strict-modes failure as an exit 21 / exit 1 cause; test-plan §6 Security control negatives, Umask-independent modes). A tmpfs backing must give the same owner and mode answers; security-plan owns the check, tests own the homes it runs on.
- security ↔ tests (Windows): test-plan §6 Security control negatives (Windows `--home` outside `%USERPROFILE%`) requires a Windows DACL test's home to sit where the CI homes live, `target/e2e-home`, never under the temp dir. It bounds the change to the Linux dev host.
- tests-domain statements of where homes live, for W3's read (each holds as written if the path string is unchanged, else is named for the wrap): test-plan §3 `boot` step 2 · §3 `run` step 2 (`target/e2e-home/viola-test-*`) · §3 `run` `--local-live` · §3 `cleanup` step 6 · §3 `logs` Retention window · §3 `schema-check` · §3 `secret-scan` · §3 Test data bootstrap (Mechanism, Cleanup) · §5 Setup / teardown lifecycle · §6 Error sanitization and secret scan (Canary) · §6 Schema conformance · §7 Test data lifecycle · §9 Test report format · §10 Performance budgets (Perf session).

## Acceptance criteria contributions
- With the backing in place, `<workspace root>/target/e2e-home` is still the `tempdir_in` root of every rstest and harness home, and each home is still created by viola (per test-plan §5 Setup / teardown lifecycle).
- `scripts/agent-run.sh pre-push` reads `ok:true` at stage `linux-tests` on the new backing, with `.config/nextest.toml` and `WITHIN` unchanged in the chunk's diff (per test-plan §3 `pre-push`).
- The chunk's `evidence/` holds one contended reading on the present backing (red) and one on the new backing under the same contention (green), each with its counts and seconds; no test in the suite carries an elapsed-time verdict for it (per test-plan §11 Universal).
- After a run on the new backing, a root `TestHome`'s drop and the dead-owner sweep leave no home behind beyond those `AGENT_RUN_KEEP_*` keeps, and CI's `test` job still finds its kept homes under `target/e2e-home/**` for G2, G4, the secret scan and the `diag-<os>` upload (per test-plan §3 Test data bootstrap).
