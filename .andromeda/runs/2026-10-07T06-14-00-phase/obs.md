# obs extract

## Relevance
partial — the chunk adds no span, event, field or metric (its Boundaries leave `viola`'s start untouched); obs applies only through where the homes' diagnostics live: the scan root the obs gates read, the init-order checks on the home, the retention of a kept home, and how the contended reading is taken from existing lines.

## Constraints
- obs-plan §9 CI Integration (Pipeline integration, Integration tests row) requires every viola home of a fake-agent run to live under `target/e2e-home/`, because G2, G4, the secret scan and the `diag-<os>` upload read that root and a `hook` panic exits 0. Whatever backing is chosen, the homes must stay reachable at that path as those readers walk it; a backing that moves a home off that path as seen from the workspace hides its panic lines.
- obs-plan §9 CI Integration (Gate commands, G2) requires G2 to refuse an empty scope and takes its scope from a plain walk that starts at `target/e2e-home`. A link-shaped backing turns that start point into a link: whether the walk as written descends it, and whether any dev-host path (the pre-push gate, a local `agent-run` gate run) executes G2, G4 or the scan at all, is research's question. P4 prices the link option with that answer, not without it.
- obs-plan §9 CI Integration (Step order and conditions) requires CI's homes to be kept (`AGENT_RUN_KEEP_HOMES=1`) until G2, G4, the secret scan and the scan-gated uploads have read them, in both the `test` and the `perf` job. The chunk's "CI unchanged" must hold for that step order and its conditions, not only for the home path.
- obs-plan §9 CI Integration (Telemetry artifact handling) fixes the upload paths as globs under `target/e2e-home/**`. W3's read of the CI globs covers these rows; each either holds as written under the chosen backing or is named for the wrap's amendment.
- obs-plan §3 OTel SDK init (Init order, step 4) requires the home's strict-modes check to pass before anything under the home is created, then the same owner / mode / not-a-symlink checks on `diagnostics/` and every opened diagnostics file, and gives a refused home no diagnostics line at all. Whether the code's checks look only at the home and its entries or also at an ancestor of the home (the link or mount point above it) is research's question; a refusal there would be silent in the role files and would surface only as an empty G2 scope or an exit code.
- obs-plan §3 Log file location requires 0600 files in 0700 directories for the diagnostics and sets their retention to the lifetime of the session home, with no rotation. A tmpfs backing ends that lifetime at a reboot or an unmount: a home kept for a red reading (the diagnosis input) no longer survives one, so what the proof needs from a home is copied into the chunk's `evidence/`, and the documents W3 touches state the new lifetime.
- obs-plan §8 PII Scrubbing & Compliance (Integration points, item 6) requires that no run document, pre-push document or uploaded artifact carries an absolute host path, and treats a dev-host scratch location as an environment fact that no document prints. The backing's absolute location falls under the same rule if a harness option or a document comes to name it.

## Patterns to follow
- Read the stalled start from lines the plan already requires: obs-plan §4 Span / Trace Coverage (Scenario: `viola run` start sequence to child spawn) puts `run.pin_copy` between the wrapper's own `process-start` and the child's, and requires a `duration_ms` on the version probe's exit line; obs-plan §6 Log Coverage (Required fields) gives every line a millisecond UTC timestamp. The gap between those lines in `run-<name>.ndjson` brackets the copy without a new field. Whether the code writes the wrapper's `process-start` before the pin copy is research's question.
- Derive the reading the way obs-plan §5 Metric Coverage (Metric instrument types) derives every metric: raw samples computed by `jq` over the home-level role files with the torn-line-tolerant form, no in-process instrument.
- Consume the homes through the harness, per obs-plan §3 Snapshot / paste-to-AI integration: `agent-run logs` / `status` over the homes at their unchanged path are the agent's read of a start on either backing.
- Treat the backing as obs-plan §8 PII Scrubbing & Compliance (Integration points, item 6) treats the Linux dev host's mutation scratch: a host environment fact outside harness code where possible, named by no document.

## Anti-patterns to avoid
- NEVER add a field, an event value or a duration to a start line in order to measure the stall: obs-plan §11 Obs Anti-Patterns (PII Scrubbing: default-deny against the §6 catalog; Logs: no new `event` value without a Decisions Log entry).
- NEVER reach the green reading through a retry or a widened wait: obs-plan §11 Obs Anti-Patterns (SLO) bans retry-once policies for flaky telemetry assertions, and obs-plan §10 SLO Invariants & Telemetry Budgets (Deterministic emission) bans log-based waits that rely on sleeps.
- NEVER let the product learn of the backing: obs-plan §11 Obs Anti-Patterns (CI) bans host or CI metadata in product log lines, the product reading no environment as configuration; a backing option, if one is built, stays on the harness side.

## Contract bindings
- obs ↔ tests (home layout): obs-plan §9 CI Integration (Pipeline integration) names the directory layout under `target/e2e-home/` tests-owned, and the keep-homes switch and `cleanup` belong to test-plan §3; the backing is decided there, and obs only requires that its gates' root still holds the homes.
- obs ↔ tests (carve-out): obs-plan §7 Error Capture & Reporting (Error classes captured) and obs-plan §9 CI Integration (Pipeline integration) keep the one `TestHome::outside_scan()` home under the system temp dir, outside G2, G4, the secret scan and the upload. A tmpfs backing placed under the same temp dir must be a dedicated directory that does not contain that home, or the carve-out's deliberate panic line enters G2's scope.
- obs ↔ security: the init-order checks of obs-plan §3 OTel SDK init (Init order, step 4) and the modes of obs-plan §3 Log file location are security's strict-modes rules applied to the diagnostics; the tests secret-scan test enforces the modes.
- obs ↔ tests (liveness): obs-plan §3 Heartbeat ticks keeps the `heartbeat` file inside the instance directory of the home, and obs-plan §10 SLO Invariants & Telemetry Budgets (Performance budgets, Heartbeat staleness flip) gates the flip through `agent-run status`; the file moves with the backing.
- obs ↔ tests (perf): obs-plan §10 SLO Invariants & Telemetry Budgets (Performance budgets, Obs overhead on `hook`) is judged in CI's `perf` job over a home under `target/e2e-home/`; a dev-host timing taken on tmpfs is not that gate's measurement surface.

## Acceptance criteria contributions
- (obs) `ci.yml`'s `test` and `perf` jobs read unchanged after the chunk in the home root, `AGENT_RUN_KEEP_HOMES=1`, the G2 / G4 / secret-scan scopes and the `diag-<os>` / `diag-perf-<os>` upload paths (per obs-plan §9 CI Integration, Step order and conditions).
- (obs) On the new backing, a harness boot on the dev host leaves home-level role files that G2's own walk from `target/e2e-home` finds (a non-empty scope), and G2 and G4 read green over them (per obs-plan §9 CI Integration, Gate commands).
- (obs) Those role files are 0600 in 0700 directories on the new backing, and the run writes no `strict-modes-failed` or `symlink-ignored` line that the same run on the present backing does not write (per obs-plan §3 Log file location).
- (obs) The contended reading in `evidence/` is machine-readable — per-start samples as numbers with the maximum stated, taken from line timestamps or harness output — and carries no absolute host path (per obs-plan §5 Metric Coverage, Metric instrument types).
