@extract_section name=constraints
- The Unix IPC controls must survive the removal unchanged when a `cfg(unix)` arm loses its gate. The socket stays in a verified per-user 0700 directory and is chmod 0600 after the bind. On accept, a peer whose euid differs is dropped before any frame. On Linux the client checks the server's pid and start time, its euid and the socket directory before the first frame, with the closed words `server-verify-failed` and `socket-dir-refused` kept as they are (per security-plan §Authentication & Authorization). Whether any Linux path today runs only through a `cfg(any(unix, windows))` or similar shared arm that the removal could drop is research's question.
- Making a `cfg(unix)` arm unconditional must leave no fallback arm (`cfg(not(unix))`, a catch-all or a stub) that returns `Ok(())` without a check from the strict-modes check, the socket-directory check or the peer and server verification (per security-plan §Security Anti-Patterns › Data Protection, the unchecked-`Ok(())` ban).
- No `config.json` value, `VIOLA_*` variable, flag or feature seam may switch off a control, and no seam may force a refusing peer-euid decision. The only carve-outs are the two `fake-agent` test seams and the terminal colour facts (per security-plan §Security Anti-Patterns › Universal; per security-plan §Input Validation, test-seam rows).
- `deny.toml` keeps every §Dependency Security addition when the `[target.'cfg(windows)']` dependencies and their entries leave: `[advisories]` (`unsound`, `yanked = "deny"`, the single RUSTSEC-2017-0008 ignore); `[sources]` deny; the licence `allow` list exactly MIT, Apache-2.0, Zlib and Unicode-3.0, with 0BSD admitted only per crate, never added to `allow`; and `[[bans.features]]` for rmcp `transport-streamable-http-server`/`auth` and serde_json `unbounded_depth` (per security-plan §Dependency Security). Research has to answer whether the 0BSD exceptions (`doctest-file`, `recvmsg`) and the three target triples of `deny-sync.toml` still resolve after the removal.
- Every workflow that remains keeps its hardening: workflow `permissions: {}` and job `contents: read`; actions pinned by full SHA with a version comment and `persist-credentials: false`; event values reaching a step only through `env:`; no `concurrency:` block; no toolchain action, only rustup (per security-plan §Dependency Security).
- The security gates must keep running on the ubuntu leg: `cargo deny check` over all four families plus the fuzz lockfile audit; `nightly.yml`'s advisories and fuzz jobs; zizmor; `scripts/rmcp-features.sh` in the lint job; `scripts/release-check.sh` with its `--probe`; G2 with exactly one exemption and its `--probe`; and the artifact canary `secret-scan`, which gates every upload (per security-plan §Dependency Security; per security-plan §Secret Management).
- The ConPTY vendor gate (`scripts/conpty-vendor.sh` and the `windows-2025` CI step) and `windows-mutants.yml` may leave only together with what they gate (`vendor/conpty/`, `src/conpty.rs`, the Windows mutation run). The plan text naming them is an expected amendment, and writing it is the wrap's job (per security-plan §Dependency Security, dep-conpty and deps-supply-chain detail).
@extract_section name=patterns
- Probe before gate. Each security gate shows it fires before it judges: `scripts/deny-probes.sh` (every ban live, clean control), `release-check.sh --probe` (5/5 refused), G2 `--probe` and `conpty-vendor.sh --probe`. Each surviving gate keeps its probe, and any change in a probe count after the removal is measured, never assumed (per security-plan §Dependency Security).
- The artifact canary scan (`viola-harness secret-scan`, `if: always()`) gates every scan-gated upload, and the per-OS upload names follow the `perf-<os>`, `diag-perf-<os>` and `harness-<os>` form. The Linux leg keeps this ordering (per security-plan §Secret Management; per security-plan §Dependency Security).
- `viola-harness pre-push` runs on the native Linux host under `env -i` with exactly `HOME` and `PATH`, and its `tools` stage parses the tool pins from the `test` job's `tool:` line in ci.yml. Restructuring ci.yml must keep that line parseable (per security-plan §Dependency Security; per security-plan §Secret Management).
- Owner-only home creation through `replace_private`, with the mode set before any byte and never the umask, is the Unix arm that stays (per security-plan §Authentication & Authorization).
@extract_section name=anti_patterns
- NEVER leave a check-free `Ok(())` arm in the strict-modes or IPC verification paths when collapsing `cfg` arms (per security-plan §Security Anti-Patterns › Data Protection).
- NEVER reference a GitHub Action by a mutable ref in a rewritten workflow (per security-plan §Security Anti-Patterns › Code Patterns).
- NEVER, while folding a `cfg(unix)` path, place the socket at the `/tmp` or `$TMPDIR` root, use the Linux abstract namespace, set the mode through `ListenerOptionsExt::mode` or enable `try_overwrite` (per security-plan §Security Anti-Patterns › Authentication; per security-plan §Security Anti-Patterns › Code Patterns).
