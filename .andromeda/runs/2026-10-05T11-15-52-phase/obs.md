## Relevance
partial — the chunk is ledger/verify/dialog-gate mechanism; obs binds through verify's spawn logging, the dialog must-trace path (the permission end-to-end case, the R2 gate closure), the uninstrumented `--capture` arm and the High-class handling of recorded dialog payloads.

## Constraints
- obs-plan §4 (Capability ledger → `verify` / `plugin install`) requires `verify`'s dispatch spans `cli.verify` › `cli.verify_step` (one per step) › `state.ledger_write`, and, with `VIOLA_NAME` set, exactly the spawn pairs it names: one `version-probe`, one `verify-probe`, one `verify-pty-probe` pair per interactive PTY run, each `process-exit` carrying `child_exit_status` + `duration_ms`, with no row text, prompt or path in any line (D-35, §6 Boundary-call wrappers). If the dialog re-probe adds an interactive run or a spawn, the "four spawn pairs" wording changes, and a new `subject` value is a closed-enum change to `schemas/diag-line.v1.json` that needs a §12 Decisions Log entry (§3 Log format JSON schema: "a new value needs a Decisions Log entry"). Whether the re-probe reuses `verify-pty-probe` for its runs is a P4 design question.
- obs-plan §4 (Capability ledger) and §10 (bounded exemption 5) require the hidden `hook <event> --capture <DIR>` arm to stay uninstrumented: no `VIOLA_*` read, no obs init, no role/detail file, no `hook-invoked` / `hook-decision`, and empty stdout and stderr. Any M7 widening that makes a probe hook answer (a decision body on stdout, or obs init) changes this text and exemption 5, so it is a plan amendment that follows the founder's ruling, never a silent change. Whether HEAD's arm still writes nothing to stdout is research's question.
- obs-plan §4 (Scenario: Dialog → `answer`) requires the full dialog must-trace path for the `permission` kind's end-to-end case: spans `hook.handle` › `channel.request(hook.dialog)` → `channel.dispatch` › `run.dialog_register` (`dialog_kind`, `pending_conflict`) › `run.dialog_await` (`deadline_ms`, `deadline_hit`) › `hook.decision_emit` (`decision_emitted`); wrapper `dialog-raised` / `dialog-answered` and hook `hook-invoked` / `hook-decision` lines with `corr` = `dialog_id` (D-07 ordering). Whether the code already emits these for `permission-request` is research's question.
- obs-plan §4 (Scenario: Dialog → `answer`, unverified-CLI branch) and §6 (`detail` code catalog) fix the observable outcome of the R2 gap's closure as `cli_verified` on `process-start{subject:"claude-child"}`, `channel-response{refusal:"unverified-cli"}` (exit 12) and the `hook-decision` fail-open `detail:"unverified-cli"`. A per-kind gate (each dialog kind keyed on its own row) that needs a new field (for example a per-row verified set) or a new `detail` code is a §6 catalog change under default-deny (§8 Default-deny posture) and needs a Decisions Log entry. Keying on the existing boolean and code needs none.
- obs-plan §4 (Capability ledger) requires a stamps read in `run.version_gate` to stay inside `state.ledger_read`, with a malformed, unreadable or strict-modes-refused file giving `parse-rejected{parser:"ledger-stamps"}`, and the path and stamp contents never logged. A stamps shape that grows from 10 to 14 rows must keep an older-shape or partial stamp reading as `cli_verified:false` (or the dialog-tier refusal), never as a panic or an unlogged fault.
- obs-plan §8 (Data classification: "Tool `input`, plan text, dialog questions/answers", High) and §11 PII Scrubbing require that dialog payloads the re-probe captures (AskUserQuestion questions, ExitPlanMode plan text, PermissionRequest `tool_input`) never reach a home-level process-log line. Recorded fixtures are scrub-required data owned by security and tests, and "obs adds no fixture content" (§8 table, Recorded fixtures row).
- obs-plan §11 Telemetry Strategy ("NEVER derive telemetry from screen content") and §10 (Deterministic emission) require that a re-probe judging "a dialog was raised" or "the decision took effect" from the vt100 screen produce only a verify pass/fail outcome on stdout. It must emit no new log event derived from screen text.

## Patterns to follow
- Call-site spawn logging in `verify` (one `process-start` / `process-exit{subject, child_exit_status, duration_ms}` pair per child, `run_bounded` itself unlogged), per obs-plan §6 Boundary-call wrappers (Child / shell spawns).
- `#[instrument(skip_all, name = "<area>.<operation>", fields(..))]` plus `obs_event!` with explicit typed fields only. Static span names; never a dialog id, row id text or path in a span name, per obs-plan §4 (Span naming convention) and §8 Integration points 1.
- `verify`'s agent-readable outcome for a plain-terminal run is the exit code plus the `[NN/MM] <row id> <row words>  pass|fail` step lines and the final `stamped <version>  N pass  N fail` line on stdout (design-system §Streams). The counter grows with `LedgerRow::ALL`, per obs-plan §4 (Capability ledger, `verify`).
- veil `#[redact]` on `HookDialogParams.data` / `AnswerParams.response` and codes-only dialog events (`dialog_kind`). Any new dialog body or PermissionRequest mapping type carries the same type-level redaction, per obs-plan §8 Integration points 2.

## Anti-patterns to avoid
- NEVER log the probe's captured dialog payloads, the probe prompts or the probe dirs (`ledger/probes/<pid>/`, `.viola-verify-<pid>/`) in any home-level line, nor a path or pid inside a `detail` code (obs-plan §11 PII Scrubbing; Founder Direction 4).
- NEVER add an `event`, `subject` or `detail` value, or a field outside the §6 catalog, without a §12 Decisions Log entry and the matching `schemas/diag-line.v1.json` change (obs-plan §11 Logs: "NEVER … add `event` values without a Decisions Log entry"; §11 PII Scrubbing: default-deny).
- NEVER use print macros or a bare `#[instrument]` in the new verify / dialog code. Stdout carries only verify's step lines and the hook decision body (obs-plan §11 Logs, §11 Spans / Traces).

## Contract bindings
- obs ↔ tests §3 (Log format): the permission end-to-end case and any new verify spawn are validated by G4 against `schemas/diag-line.v1.json` (closed `subject` enum, `corr` required on `dialog-raised` / `dialog-answered` and on `hook-decision` for `permission-request` without `detail`), per obs-plan §3 Log format JSON schema and §9.
- obs ↔ tests (secret scan / canary): the `permission` end-to-end case's synthetic tool `input` carries the tests-owned canary, and it may appear only in `detail-*.ndjson`, never in a home-level file (obs-plan §8 Integration points 6, High classes). The fake agent's dialog-fixture replay stays synthetic, so the `diag-<os>` / `harness-<os>` uploads stay admissible (§8: "Any non-synthetic input source must first drop `detail-*.ndjson` … from the upload paths"). A real recorded dialog payload must never become a CI replay input unless it is scrubbed.
- obs ↔ tests harness: CI `verify` runs only against the fake agent at the recorded version (harness `boot` step 4, rstest `stamped_home`, `tests/cli_verify.rs`), and verify stays the only writer of `ledger/stamps.json`. The real-`claude` re-probe runs only through local `run --local-live` (refused under `CI`), per obs-plan §4 (Capability ledger, last bullet).
- obs ↔ security: the `--capture` arm's uninstrumented contract (founder ratification 2026-09-28) and the High class of dialog payloads, and the ruling on the M7 widening, decide whether §4 / §10 exemption 5 need an amendment (obs-plan §4, §10, §8).
