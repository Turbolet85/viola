# a11y extract

## Relevance
partial — the chunk is ledger, verify-probe and dialog-gate work with no new UI surface; a11y reach is limited to the CLI output discipline of `viola verify`'s step lines (the counter grows) and the `unverified-cli` refusal/state word, whose firing condition moves when R2's gap closes (Paths P3 and P6).

## Constraints
- a11y-plan §1 (CLI and terminal entities; Surface: cli) scopes `verify` and `answer` as assertable only through output-discipline assertions (assert_cmd / trycmd / outer-PTY SGR checks) on all three OS legs, with no WCAG conformance claim. Any new or changed `verify` / `answer` output this chunk lands falls under that discipline. The plan also lists the hook / plugin / IPC traffic (the `--capture` arm, `hook.dialog`) as not-assertable (§1 Not-assertable).
- a11y-plan §4 P6 requires `verify` output to stay linear and static, as `[NN/NN] … pass|fail` step lines with no `\r` redraw, cursor movement or spinner. It also requires no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`, and no SGR on `fail`. The `/10` → `/14` counter growth and any new dialog-row step lines must keep this shape. Whether the interactive re-probe's PTY children can leak bytes or redraws onto verify's own stderr is research's question.
- a11y-plan §4 P3 (`a11y-p3` row) requires the `unverified-cli` state word in the CLI column and the `viola answer` `unverified-cli` refusal text on the CLI. When R2's gap closes, a stamp without passing dialog rows may withhold a non-`null` decision. Wherever that happens, the withholding must still surface as the same `unverified-cli` text, not a new or silent refusal. Whether the gate reuses `unverified-cli` or mints a new code is P4's design question. A new code would need its own state word and copy pin.
- a11y-plan §8 Error recovery (CLI) and §11 Cognitive require every human-mode CLI refusal except `unknown` to print `unable  <reason>  <detail>` on stderr, with `hint:` as the last stderr line and a typed exit code. `--json` carries no hint. A dialog-gate refusal reshaped by this chunk keeps that layout.
- a11y-plan §8 Plain language requires every kebab-case code (`unverified-cli` included) to sit beside the plain word `unable`, and every fixed CLI string to be pinned by trycmd. A copy change to the `verify` step names or the refusal detail must update its pin on purpose.
- a11y-plan §1 (tui entity) and §2 Surface: tui define the R7 boundary: viola owns none of the rendered `claude` TUI content, and the plan treats it as vendor content.

## Patterns to follow
- The §4 P6 test shape: trycmd / assert_cmd for the non-TTY modes of `verify`, and the portable-pty outer PTY for the TTY-only behaviours (no redraw, SGR only beside its word), run on all three OS legs (a11y-plan §4 P6; §3 A11y testing tool pick, cli row).
- The §4 P3 / `a11y-p3` pairing: the CLI `answer` refusal text and the web CLI-column state word assert the same `unverified-cli` fact. Keep the two in step if the gate's predicate changes (a11y-plan §4 P3; §3 WCAG criteria mapping, SC 1.4.1 row).
- The §8 Error recovery CLI layout (`unable <reason> <detail>` plus a final `hint:` line, typed exits `10`–`14`, `20`, `21`) applies to any refusal the dialog gate emits.

## Anti-patterns to avoid
- NEVER parse the rendered `claude` TUI screen for content, or take screenshots as a11y evidence (a11y-plan §11 Universal, R7). This bears on the M7 card's "probe keys the rendered dialog" option. The previous chunk ratified signature-only screens, but reading a dialog's content off the screen is a different act. That boundary is the founder card's to price, and this extract does not rule on it.
- NEVER show a kebab-case code (`unverified-cli`) without the plain word `unable`, and never end a human-mode refusal without `hint:` (except `unknown`) (a11y-plan §11 Cognitive).
- NEVER add a spinner, `\r` redraw or progress animation to `verify`'s longer interactive re-probe, even though the run is longer (a11y-plan §1 Surface: cli Notes, "static and linear"; §11 Motion).

## Contract bindings
- a11y ↔ tests: the P3 / P6 output-discipline checks run inside `nextest-integration` / `nextest-e2e` locally, and inside the CI `test` job's `coverage` suite on all three legs (a11y-plan §9; §10 CLI invariants). The `/14` counter and any changed refusal copy bind to the trycmd pins (a11y-plan §8 Plain language).
- a11y ↔ design: the `unverified-cli` state word and its `--ink` / `--rule-field` warning encoding (a11y-plan §6 State color tokens) bind to design's cli and web copy for the CLI column, if the gate's predicate changes which sessions show it.

## Acceptance criteria contributions
- (a11y) `viola verify`'s non-TTY output across the grown ledger is one `[NN/14] … pass|fail` line per row, with no SGR, no `\r` and no cursor or erase sequence. Under the outer PTY, `fail` carries no SGR (per a11y-plan §4 P6).
- (a11y) A non-`null` decision withheld because the child version's stamp lacks passing dialog rows prints `unable  unverified-cli  <detail>` with a final `hint:` line and the typed exit code in human mode, and no hint under `--json`, pinned by trycmd / assert_cmd (per a11y-plan §8 Error recovery; §4 P3 `a11y-p3`).
- (a11y) Every new or reworded fixed CLI string the chunk lands (dialog-row step names, refusal detail) has an updated trycmd pin in the same change (per a11y-plan §8 Plain language).
