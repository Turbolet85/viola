## Constraints
- layout-templates §Surface: cli / Output structure — `viola verify` requires one stdout step line per ledger row, in the form `[NN/MM] <row id> <row words>  pass|fail`, in ledger order. `MM` "grows as owning chunks land their rows", so the four dialog-tier rows (S3, S7, S8, dialog concurrency) each need a row id and row words. The plan names neither today. P4 must fix them, and the wrap amends the plan's ordered row list and its `[NN/10]` example to the new count (the scope infers `/14`).
- layout-templates §Output structure — `viola verify` requires the summary `stamped <ver>  <n> pass  <m> fail` as the last stdout line. Exit is 0 when every row passes and 1 on a failing row or a refusal, and the stamp is still written on a failing row. It also requires plain ASCII, no colour (`fail` is never coloured), each step line appended once, no progress bar and no redraw. This holds even though the interactive dialog re-probe makes each step slower.
- layout-templates §Output structure — `viola verify` requires the `--help` text to stay one static ASCII paragraph that names no path. That paragraph says verify never answers a dialog. If the founder's M7 ruling (W3c) changes what verify does with a dialog, the paragraph's wording must be re-read against the ruling and amended at the wrap, never left stating a false claim.
- layout-templates §Component — Primary content block 2 requires the `--record` refusal to stay `unable: a recorded fixture is not clean: <file> <code>` with its `hint:` line, using the closed codes `home-path` · `absolute-path` · `username` · `email`. The line names the fixture file and the check, never the content. Dialog payload fixtures (plan text, `tool_input`) fall under this form. A new code would be a layout amendment, not an implementation choice.
- layout-templates §Component — Primary content block 2 sets the typed exit tail: exit 12 is `unverified-cli`, and every refusal line has the form `unable  <name>  <reason>  <detail>` on stderr, followed by its own `hint:` keyed by reason. If closing the R2 gap refuses a non-`null` `viola answer` against a stamp without the dialog rows, the refusal must surface in this form. Under `--json` it is one document on stdout with no stderr line. Whether the existing `unverified-cli` hint wording still fits a "stamp present but dialog rows failing" cause is P4's to check: §Primary content block 2 gives every cause its own hint.
- layout-templates §Output structure — wheel, handoff and dialog verbs and §Component — Footer / terminator fix `viola answer`'s success line as `answered  <name>  dialog <id>`, the last printed line. §Output structure — `viola wait` / `viola last` fixes a dialog result as `<kind>  <name>  dialog <id>  cursor <n>`, uncoloured. The `permission` end-to-end case (W3d) reads these forms.
- layout-templates §IA notes (Output as a contract) requires the human columns and words to stay stable, with new fields going into `--json` first. The six-column `viola list` / web strip, including the CLI column's `<ver> verified` / `<ver> unverified-cli` words, gets no new column or word from the dialog tier. Any "dialog rows verified" signal goes to `--json` first, or is a design change.

## Patterns to follow
- The `viola verify` example block in §Output structure — `viola verify`: zero-padded `[NN/MM]`, the row id, then the row words, then two spaces before `pass|fail`, closed by the `stamped` summary line.
- The refusal plus hint pair in §Component — Primary content block 2: a refusal line, then a `hint:` that is the last stderr line and points to the next verb by name (for example `viola verify`). It never names a path or pid and never quotes upstream text.
- The stream split in §Component — Primary content block 2 (Streams): results go to stdout; refusals, hints and errors go to stderr; the two are never mixed. A failed or panicked verb prints exactly `error: internal error` once, with no hint.
- The terminator rule in §Component — Footer / terminator: no `done.` or summary banner. The exit code and the last line carry the outcome. For verify, the `stamped` summary closes the run.

## Anti-patterns to avoid
- No spinner, elapsed counter, progress bar, in-place redraw or colour on `viola verify`, however long the interactive dialog re-probe runs (§Output structure — `viola verify`; §Surface: cli expression level 0.0/0.2).
- No dialog payload content (plan text, `tool_input`, question text, `annotations`) in any human line, hint or refusal detail. A `--record` refusal names only the file and the closed code (§Component — Primary content block 2).
- No new human column or word on `viola list` / the web strip for dialog-tier verification (§IA notes, Output as a contract).
