# arch extract

## Relevance
relevant: the chunk moves a `viola-core` product constant tied to the Hook Contract, adds a normalised event kind and changes the `wait` wake rule (both Standard Contracts), and may add a `config.json` key and a per-start rendered `hooks.json`.

## Constraints
- architecture §Established Decisions [Hook Contract] makes the dialog hold the product constant `viola_core::DIALOG_DEADLINE`, kept beside `SPINE_DEADLINE`. It requires the hook's reply read to be bounded at the deadline plus 5 s, with one stdout write. It also requires the dialog hooks' `hooks.json` `timeout` to sit above the deadline by a test-pinned margin, so that viola ends the wait and Claude Code never does. Any longer or configurable hold must keep all three related in this way. On expiry the hook exits 0 with no body and the dialog renders for the human. Exit 2 and stderr stay forbidden.
- architecture §Established Decisions [Hook Contract] and §Standard Contracts (Instance snapshot, `pending_dialog`) require the wrapper to clear the pending `dialog_id` and the snapshot's `pending_dialog` on expiry. A late `answer` is then refused `not-delivered` / `unknown-dialog`. That refusal word is in the closed detail set (§Conventions, Error handling schema), so an expired-hold record must not change the refusal a late `answer` gets unless that set is amended in `viola-core`.
- architecture §Conventions (Naming patterns, Normalised event kinds) says a new kind is added only in `viola-core`. It must be kebab-case and carry no Claude-specific name. §Conventions (Interfaces and versioning) treats a new kind as additive with no `v` bump. §Cross-cutting Patterns (Mixed-version tolerance) has an older reader skip and count it as an unknown kind.
- architecture §Standard Contracts (ndjson event line) requires `data` to be kind-specific, built from viola's normalised fields only, and never to embed a raw Claude payload. An expired-hold record therefore carries ids and closed words only (for example `dialog_id` and the dialog kind), never the question, plan or tool `input` text.
- architecture §Standard Contracts (Channel methods, `wait`) defines the wake set as the closed `EventKind::WAIT_WAKE` (`turn-ended` · `question` · `permission` · `plan` · `session-end`). It says only hook lines signal the `WaitFeed`, and the paragraph after Event `data` per kind says every wrapper-appended record is log-only and never wakes `wait`. If a wrapper-sourced expiry record must wake `wait`, the contract changes in both places and the change must be stated. Whether the record should be `source: wrapper` or `source: hook` is a design question for this chunk.
- architecture §Cross-cutting Patterns (Config management) and §Occupied Resources (Filesystem, `config.json`) apply if the hold becomes configurable. The precedence is CLI flags > `config.json` > built-in default. Environment variables are not a configuration channel. A key is read once at the wrapper's start through a `MAX_FRAME`-capped read. A bad value takes the key's default with one `parse-rejected{parser:"config-json"}` line, and no value switches a control off. A hold setting must therefore be a closed, bounded range and never "forever".
- architecture §Cross-cutting Patterns (Capability ledger as the single gate for CLI-specific behaviour) and §Design Philosophy ("Measured, never assumed") apply to the CLI honouring a dialog-hook `timeout` past 75 s on 2.1.287. That is an undocumented CLI behaviour, so it needs a ledger row with a `viola verify` probe, or the ruled limit: a shape no `send` relies on needs no probe. §Established Decisions [Hook Transport] also makes the hook tier map itself a ledger row that `verify` re-stamps.

## Patterns to follow
- A product time bound is a compiled, labelled-PROVISIONAL constant with a single home, validated per CLI version where the CLI's behaviour is involved. Follow `COMPACT_CONFIRM_WINDOW` as precedent: its own 40 s PROVISIONAL constant, gated by the `local-command-compact` row and chosen in one place (`SendSlot::window()`) that every reader uses (per architecture §Established Decisions [Delivery Confirmation]).
- A bounded user setting follows the budget thresholds, read through `run::budget::read_thresholds`: a whole-number newtype in a closed range (`Percent`, 0–100), read once at the wrapper's start, a bad key falling back to its default with one `parse-rejected` WARN line, and the schema in `schemas/config.v1.json` (per architecture §Occupied Resources, Filesystem / Repository, and §Conventions, Data model conventions).
- Plugin templates are embedded with `include_str!` and rendered at every start with placeholder substitution (`@@VIOLA_BIN@@`) into `plugin/<version>-<hash>/`. A rendered `timeout` would follow the same `plugin_files` path in `viola-agent-claude` (per architecture §Established Decisions [Deployment / Distribution]).
- Dialog lifecycle signalling goes through the wait feed: the dialog line is appended before it can wake `wait` or reply (`WaitFeed::appending_dialog`), and its end goes through `WaitFeed::dialog_settled` (per architecture §Established Decisions [Message Broker / IPC] and §Standard Contracts, `hook.dialog`).
- Crate placement follows the manifest direction. The constant and the new kind go in `viola-core`. The `hooks.json` shape and `timeout` go in `viola-agent-claude`, which stays pure. The hold, its expiry record and the `wait` wake stay in the root bin's `src/run/` on std threads, with no Tokio outside `viola-mcp` (per architecture §Infrastructure Patterns → Crate dependency direction and §Cross-cutting Patterns, Tokio containment).

## Anti-patterns to avoid
- A viola-built `deny` (or any decision body) at expiry would be viola deciding a dialog no one answered. That breaks "Mechanism, not policy" (per architecture §Design Philosophy and §Established Decisions [Scope Boundary]). Today's no-decision reply (`null`, the CLI's own menu, left to the human) is the mechanism-side default (per architecture §Cross-cutting Patterns, Fail open toward the human). Departing from it is a founder fork.
- Do not render a per-start `timeout` into the existing `plugin/<version>-<hash>/` key without settling the identity rule. `replace_private_shared` counts a failed replace as done when the target already holds the same bytes, which assumes every concurrent start of one version writes the plugin files identically. Two starts with different holds would break that assumption (per architecture §Established Decisions [Snapshot writer] and [Deployment / Distribution]). Whether the code keys or writes the plugin dir in a way that tolerates this is research's question.
- No hold may outlive the human. A wheel move to `human` (an editing key, or `viola pause`) must still answer the pending `hook.dialog` with `null` at once and clear its `dialog_id`, however long the hold is (per architecture §Established Decisions [Human Takeover / Wheel]).

## Contract bindings
- arch §Conventions (Normalised event kinds) and §Standard Contracts (Event `data` per kind) ↔ obs event catalog (obs-plan §6): the new kind needs a catalog row and its process-log or span counterpart.
- arch §Standard Contracts (`wait` wake set) ↔ MCP `wait` tool (§Established Decisions [MCP]: `WAIT_CAP` 50 000 ms below claude 2.1.287's tool-call default) ↔ tests (a driver re-parking `wait` across a hold longer than the cap).
- arch §Established Decisions [Hook Contract] margin ↔ tests: the pinned test `hooks_json_dialog_timeouts_outlast_the_dialog_deadline` must read the rendered `timeout` against the hold actually in force.
- arch §Occupied Resources (`config.json`, `schemas/config.v1.json`) ↔ security-plan §Input Validation (bounded value; no key disables a control).
- arch §Standard Contracts (Instance snapshot, `pending_dialog`) ↔ the `list` payload's `dialog_pending` (§Standard Contracts, `list` payload).
- arch §Conventions (CLI) ↔ layout-templates (the human `wait` line in `src/human.rs` for the new kind).
- arch §Cross-cutting Patterns (Capability ledger) ↔ `viola verify` / `LedgerRow::ALL` and the relied set: this applies only if a dialog-hook timeout row is minted.

## Acceptance criteria contributions
- The rendered dialog-hook `timeout` in `hooks.json` exceeds the hold in force by the pinned margin, and the hook's reply read is bounded at the hold plus the reply grace. On expiry the hook exits 0 with an empty stdout and stderr, and the dialog renders for the human (per architecture §Established Decisions [Hook Contract]).
- The expired-hold record is a `viola-core` kebab-case kind whose `data` holds only `dialog_id` and the closed dialog kind, with no upstream text. The line carries `v` 1, and a reader that does not know the kind skips and counts it (per architecture §Conventions, Normalised event kinds / Interfaces and versioning, and §Standard Contracts, ndjson event line).
- If the hold is configurable, the setting is a `config.json` key in a closed range, read once at start. An out-of-range or malformed value takes the default with one `parse-rejected{parser:"config-json"}` line, and no environment variable or flag sets it (per architecture §Occupied Resources, Filesystem, and §Cross-cutting Patterns, Config management).
- architecture.md is amended at wrap where the chunk changes it: [Hook Contract]'s deadline and margin, §Occupied Resources' `timeout 75` and any new `config.json` key, §Conventions' kind list, and §Standard Contracts' Event `data` per kind and the `wait` wake rule if a wrapper record now wakes (per architecture §Occupied Resources, the new-resource record amended at wrap).
