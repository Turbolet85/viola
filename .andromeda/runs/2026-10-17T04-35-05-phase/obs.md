## Relevance
partial — the chunk is mostly terminal presentation (a11y / design), but obs-plan owns the stdout/stderr reservation, the `run` zero-terminal-bytes rule, the human-typing refusal lines, the no-env-config ban, and the two master sentences CARRY 1 names.

## Constraints
- obs-plan §3 (intro, the harness pattern) requires that `run`, and a revived start, write nothing of their own to the terminal while the child runs; the only exception is a pre-spawn start refusal, written as the two fixed `unable:` / `hint:` lines through `src/human.rs` `refuse` → `write_refusal` (one `write_all` on the locked stderr, a closed pipe swallowed). Case (1) "zero wrapper bytes" is that rule measured on the outer PTY. Whether the pump already holds it byte-for-byte is research's question.
- obs-plan §3 (intro, the harness pattern) allows short-lived CLI verbs to use stderr for their human output, and reserves stdout for `--json` results, the hook decision body and MCP frames. The `waiting: <name>` line, `verify`'s step lines and any colour therefore stay on the streams that clause assigns and never cross into a reserved one.
- obs-plan §3 Logging stack (Mandatory builder settings, Sink) requires `.with_ansi(false)`, an explicit writer, `.log_internal_errors(false)`, and a file-only sink per role with no stdout or pretty sink. The colour layer this chunk adds (SGR tokens, the depth rule) must never reach a `diagnostics/` line or a logger setting.
- obs-plan §7 (Panic hooks) requires that the panic hook never write to stderr and that `run` show nothing on the terminal while the child runs. On a short-lived `cli` internal fault it requires exactly `error: internal error\n` in one `write_all`, with no hint. No discipline change may add colour, a hint or an escape to that line.
- obs-plan §4 (Edge flows, `verify` / `plugin install`) fixes `verify`'s human output: one `[NN/MM] <row id> <row words>  pass|fail` stdout line per relied ledger row (`MM` = `LedgerRow::relied()`), a last line `stamped <version>  N pass  N fail`, refusals as the fixed stderr `unable:` + `hint:` pair, and the stop pair `unable: verify was stopped before it finished` / `hint: run viola verify again to stamp this CLI`. a11y-plan P6's step-line clause is checked against that shape, never re-worded through it.
- obs-plan §4 (Scenario: Human takes the wheel, automation is refused, `release` returns it) requires a refused send under a human-held wheel to log `send-refused{refusal:"human-typing", detail:null, wheel:"human", side:"wrapper"}` and a client `process-exit{exit_code:10}`, with `run.wheel_transition` carrying `wheel_from` / `wheel_to` / `cause` (`human-input`) and never the typed keys. Scenario 2's `run.readiness_gate` `outcome` is closed at `ready|input-not-ready`. How the new "key during the readiness gate" case is recorded on that span (no outcome, or a new value needing an amendment) is research's question.
- obs-plan §8 (PII Scrubbing, data classification table) requires C0/C1 in untrusted rows to be escaped in human terminal output, and keeps `last_assistant_message` and prompt text out of every home-level `diagnostics/` line. Escaping the human text of `wait` / `last` changes terminal bytes only, never a log field.

## Patterns to follow
- One-`write_all` human stderr writer: `src/human.rs` `refuse` → `write_refusal` on the locked stderr, a closed pipe swallowed, no print macro and no `#[allow]` (obs-plan §3 (intro, the harness pattern); obs-plan §11 Logs).
- Print-macro lint discipline: `[workspace.lints.clippy]` `print_stdout` / `print_stderr` / `dbg_macro` = `deny`. Only the output modules that own `--json`, human CLI stderr and the hook decision body may carry a local `#[allow]`, and only where they use a print macro (obs-plan §3 Bootstrap phases, `obs-ci-gate-wire`; obs-plan §11 Logs).
- Dispatch spans for short-lived verbs are `cli.<verb>` (or the dedicated client span such as `wait.block` / `last.client`), declared `#[instrument(skip_all, name = "...", fields(...))]` with static names (obs-plan §2 Naming conventions; obs-plan §4 Instrumentation per surface). A pure colour-decision function needs no span.
- `run`-terminal faults go to the file sink only (`process-exit{subject:"self", exit_code:1, detail:"internal-error"}`, chain in `detail-run.ndjson`), never to the outer terminal (obs-plan §7 Per-role behaviour after the line).

## Anti-patterns to avoid
- NEVER treat env vars as a configuration channel for logging: no `RUST_LOG` / `EnvFilter`, and no CI or `OTEL_*` metadata. The `NO_COLOR` / `TERM` / `COLORTERM` reads this chunk proposes (a boundary widening held for the founder) must not touch the logger's level, field allow-list or redaction (obs-plan §11 Logs; obs-plan §11 Universal (agent-driven specific); obs-plan §11 PII Scrubbing).
- NEVER log per byte or per key in the PTY pump, and never record typed keys. Proving "unblocked human keys" adds no per-key span or `info` line in the hot loop (obs-plan §11 Telemetry Strategy; obs-plan §11 Logs).
- NEVER log a field outside the §6 catalog or add an `event` value without a Decisions Log entry. If the chunk does add a line (for example a colour-decision or gate-abort record), it needs a catalog row, `schemas/diag-line.v1.json` and an amendment (obs-plan §11 PII Scrubbing; obs-plan §11 Logs; obs-plan §6 Additive field catalog).

## Contract bindings
- obs ↔ tests: any new outer-PTY case (zero wrapper bytes, keys during a send) places its viola home under `target/e2e-home/`, so G2, G4 and the secret scan read it; the one carve-out is `tests/chaos_feed_panic.rs` (obs-plan §9 Pipeline integration, Integration tests row; obs-plan §9 Step order and conditions).
- obs ↔ security: the colour env reads are the security-plan Secret Management / architecture Config management widening CARRY 2 names. On obs's side, env vars stay out of logger configuration (obs-plan §1 Obs Scope Summary; obs-plan §9 CI-specific resource attributes).
- obs ↔ a11y / design-system: a11y-plan P4 cases (1) and (2) and P6's step lines bind to obs-plan §3 (intro) and §4's `verify` output shape. The SGR tokens stay on the terminal and out of the `.with_ansi(false)` file sink.
- CARRY 1 (master text, a wrap amendment and never a phase edit): obs-plan §3 (intro) still calls `src/human.rs` "the root bin's only human-stderr writer for a start refusal, called by `run` and by `revive`", and §11 Logs names only `run`'s, `revive`'s and `revive --list`'s refusals as writing through it. Both are amended to the set of stderr writers the chunk leaves. Which verbs call `human::` today (the scope cites `verify`'s four sites and ten files) is research's question.

## Acceptance criteria contributions
- An outer-PTY run of `viola run` over the fake agent shows zero viola-originated bytes on the terminal stream, while its `run-<name>.ndjson` still carries `process-start` / `process-exit` (the terminal stays silent and the file sink keeps logging) (per obs-plan §3 (intro, the harness pattern)).
- With a key written while a verified `send` waits in the readiness gate: `run-<name>.ndjson` holds one `send-refused{refusal:"human-typing", wheel:"human", side:"wrapper"}` and no `send-issued` for that send; the client exits 10; and no line or span field carries the typed key (per obs-plan §4 Scenario: Human takes the wheel, automation is refused, `release` returns it).
- Every `diagnostics/*.ndjson` line the chunk's cases produce passes G4 against `schemas/diag-line.v1.json` / `diag-detail.v1.json` with no SGR or ESC byte in any value, and G2 reads zero `event:"panic"` lines over those homes (per obs-plan §10 Error budget).
- `viola verify`'s stdout keeps the `[NN/MM] … pass|fail` step lines and the `stamped <version>  N pass  N fail` summary, with no SGR under non-TTY / `--json`, and an internal fault still prints exactly `error: internal error` (per obs-plan §4 Edge flows, `verify` / `plugin install`; obs-plan §7 Panic hooks).
