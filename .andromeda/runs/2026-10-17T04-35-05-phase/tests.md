## Relevance
relevant — every clause of the chunk (plain or styled human output, grouped `--help`, `wait` / `last` escaping, zero wrapper bytes, human keys during a send) lands on test-plan's cli and tui surfaces, its outer-PTY driver and its unit tier.

## Constraints
- Tier is `Comprehensive (2)`. The cli surface checks human mode by matching stdout/stderr lines, and it requires no SGR under non-TTY / `NO_COLOR` / `TERM=dumb`. The TTY rendering (bold NAME, amber `DIALOG`, dim `stale`) needs a pseudo-TTY on stdout. It is driven through the same outer-PTY driver as the tui surface, never by inspecting the child agent's screen (per test-plan §1 Surfaces under test, cli).
- Styled TTY output is checked by running the verb inside the portable-pty outer PTY (`tests/support/outer_pty.rs`), asserting only on the SGR sequences in the verb's own output. Human layouts are pinned by trycmd 1.2.1, except the `viola list` board, which is pinned by literal asserts in `tests/cli_list.rs`. On the tui surface, exit is detected only through `child.wait()`, with the master reader drained on its own thread (per test-plan §6 Drivers per surface).
- The CLI tier requires a trycmd `tests/cmd/*.toml` case for `viola-help`, with snapbox `[..]` redactions, and no `\x1b[` under non-TTY / `NO_COLOR` / `TERM=dumb`. `tests/cli_output_plain.rs` is the plain-output witness for clap's own output on all 3 OSes. Help and a usage error under `CLICOLOR_FORCE=1` / `CLICOLOR=1` into a pipe carry no ESC. Under the outer PTY, help carries no bold `1` or underline `4`: the `ESC [ params m` parameters are parsed, never the screen text, because ConPTY adds its own `ESC[m`. Whether a `viola-help` trycmd case exists today is research's question. The grouped table changes what both cases pin (per test-plan §5 Cross-module patterns covered, CLI).
- The root bin's unit tier requires human-mode C0/C1 escaping in `wait` / `last` that keeps `\n` and `\t`. In `list` rows (`escape_row`), every control character prints as `\xHH`. Whether `wait` / `last` already escape is research's question (per test-plan §4 Unit Test Strategy, root bin).
- `viola verify`'s human lines are pinned by literal assert_cmd asserts in `tests/cli_verify.rs`: one `[NN/MM] <row id> <row words>  pass|fail` step line per relied row (`MM` 23 on Unix, 20 on Windows) and the last stdout line `stamped <ver>  <n> pass  <m> fail`. Any reshaping to a11y-plan P6's appended step lines must keep those literals true or amend them (per test-plan §5 Cross-module patterns covered, CLI).
- A key written into the outer PTY while a `send` waits in the readiness gate is covered end-to-end by `send_under_the_paste_hint_a_human_key_during_the_gate_wait_wins`. Its green is a floor: the `wheel` record comes before `send-refused`, the exit is 10 `human-typing`, nothing is typed and the key reaches the child. The second wheel read's proof is the four clock-driven unit cases. The refusal at the 8.5 s bound is unit-tier only (per test-plan §6 Scenario: Path 2, Verification signal). The wheel's outer-PTY steps live in `tests/tui_wheel.rs` (per test-plan §6 Scenario: Path 5).
- Gates hold per OS job: lines ≥ 85 %, functions ≥ 95 %, regions ≥ 80 %, with `#[cfg(windows)]` / `#[cfg(unix)]` code covered only on its own runner. The Windows VT-enable branch of the fact reader is therefore covered on `windows-2025` (per test-plan §10 Quality Gates & Coverage Targets). There are no retries: a flake keeps the chunk red until its root cause is fixed (per test-plan §10 Zero-flakiness budget).

## Patterns to follow
- The SGR parameter parser in `tests/cli_output_plain.rs` parses `ESC [ params m` and never screen text, with one self-check case against literals. Reuse it for the amber / dim / bold span checks and for the no-SGR modes (per test-plan §5 Cross-module patterns covered, CLI).
- The mode matrix of `cross_list_rows.rs`: the same verb run piped, under `NO_COLOR`, under `TERM=dumb` and inside the outer PTY. On Windows, the terminal case reads escaped text under a 200-column terminal because ConPTY re-renders the stream with its own escapes, so the no-ESC assertion is Unix-only. This carries over to the Windows leg of "zero wrapper bytes" (literals absent rather than byte-equal) (per test-plan §6 `list` row integrity).
- Shared helpers come only from `tests/support/`: `cli.rs` (`spawn` / `viola`, stdout and stderr as two captures), `outer_pty.rs`, `home.rs` (`TestHome`, a fresh home under `target/e2e-home`), `events.rs` (the one reader and its wait), `fake.rs` (`empty_bin` for a `list` that reads no host `claude`). No test file defines its own copy. Binary prefixes choose the layer: `cli_` reports as integration; `tui_`, `cross_` and `path<N>_` report as E2E. Test names follow `<subject>_<condition>_<expected>` (per test-plan §2 Test directory + naming conventions).
- Inject environment facts per child with `Command::env` (`NO_COLOR`, `TERM`, `COLORTERM`, `CLICOLOR_FORCE`), and put the colour decision order and depth rule in a pure function over injected facts, with unit-tier rstest `#[case]` tables (per test-plan §2 Test pyramid, Unit row; §11 Integration).

## Anti-patterns to avoid
- NEVER parse the rendered child screen (the vt100 grid, the PTY master output) for content. A verdict comes from `events.ndjson`, the fake-agent receipt and exit status. The zero-wrapper-bytes case compares or scans bytes on the outer stream rather than reading the screen for content, and how it reconciles with this ban is the plan's to state. NEVER use `sleep(N)` for sync, and NEVER detect exit by master EOF (per test-plan §11 E2E).
- NEVER use `std::env::set_var` in tests (it is `unsafe` in edition 2024), and NEVER call `.env_clear()` without re-adding `LLVM_PROFILE_FILE` (per test-plan §11 Integration). NEVER import the product's own SGR tokens or decision order as the oracle: the expected escape sequences and rung order are test literals (per test-plan §11 Unit).
- NEVER treat a Linux-only local run as proof for Windows or macOS. The ConPTY leg of "zero wrapper bytes" and the VT-enable save and restore are proven only on the `windows-2025` runner. NEVER assert at E2E a case a lower layer can hold (per test-plan §11 Test Strategy).

## Contract bindings
- tests ↔ a11y: a11y-plan §3's keyboard test harness tooling and its P4 / P6 cases run on tests' outer-PTY driver (`tests/support/outer_pty.rs`). They report in the E2E layer only if the binary matches `^(path[0-9]*|tui|mcp|cross|chaos|contract)_` (per test-plan §3 `run`, step 2); a `cli_` binary reports under `run --integration`.
- tests ↔ security / architecture (Config management): the completeness case in `tests/cli_controls_not_disableable.rs` reads the `Options:` section of `viola --help`. A grouped help must keep that section readable, or the case moves with it. A new env read (`NO_COLOR` / `TERM` / `COLORTERM`) is outside its `VIOLA_*` literal scan (per test-plan §5 Cross-module patterns covered, CLI).
- tests ↔ obs: any case that boots a wrapper keeps its home under `target/e2e-home`, so the canary secret scan and the G4 schema conformance check (`schemas/diag-line.v1.json`) cover any role line the chunk's writers add (per test-plan §6 Error sanitization and secret scan / Schema conformance).
