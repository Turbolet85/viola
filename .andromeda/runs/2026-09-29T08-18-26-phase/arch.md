# arch extract

## Relevance
relevant — the chunk changes the Windows PTY backend under the [PTY] decision, adds files to the pinned bin dir (§Occupied Resources → Filesystem) and inserts a step into `run`'s start order ([Session Liveness]).

## Constraints
- **The PTY seam stays as it is.** architecture §Established Decisions [PTY] requires portable-pty `=0.8.1` behind viola's own `pty` seam. Its only swap triggers are portable-pty-psmux, and an own ConPTY on windows-sys, which may come only after "a measured defect the seam cannot absorb". A sideload that changes which `conpty.dll` 0.8.1's bare-name load resolves to must leave the pin, the seam's verbs (spawn · read · write · resize · wait · kill) and `[workspace.dependencies]` (§Infrastructure Patterns → Build system) unchanged. [PTY] is also where the H2 record lives (the ci# run, the 13/200 figure, the loss class). The with and without results of this chunk belong in that same record, stated as measured facts naming their runs. The founder's product question on H2 stays open unless the measurement answers it.
- **Crate boundary of `viola-pty`.** Per §Infrastructure Patterns → Crate dependency direction, `viola-pty` depends on no viola crate and knows no agent. Its third-party set is exactly portable-pty, tracing, windows-sys (Windows only) and libc (Unix only), with no thiserror. `PtyError` is the hand-written exception under [Error Handling]. The hash check, the pinned-path knowledge and the `replace_private` writes therefore cannot live in `viola-pty` through a `viola-state` dependency. sha2 is a `viola-state` product dependency (§Stack and Technologies → Content hash). The chunk has two options for the pre-load: `viola-pty` takes an already-verified absolute path from its caller, or the pre-load lives in the root bin before the first spawn. Either way, windows-sys features can grow only in the manifest of the crate that uses them. The root bin already carries `Win32_System_LibraryLoader` (Crate dependency direction → `viola` root bin). Where the code lives is a P3/P4 question.
- **Pinned copy discipline covers the new files.** §Established Decisions [Deployment / Distribution] requires the pinned copy under `<viola home>/bin/<CARGO_PKG_VERSION>-<short content hash>/` to be written if absent and re-hashed before every reuse. [Snapshot writer] requires every such write to go through `viola_state::fs::replace_private`. `replace_private_shared` is the variant for "files every concurrent start of one version writes identically", which is the pinned copy's own case. It must set the mode before any byte is written: 0600, or 0700 for an executable. §Occupied Resources → Filesystem (`bin/<version>-<hash>/`) says v1 never deletes pinned copies. Whether `viola_state::pin::pin_exe` can be widened to further files, or whether a sibling writer is needed, is research's question.
- **The failure semantics must be named, not borrowed.** Today a pinned exe that fails its re-hash refuses the start with exit 1 and `pinned-hash-mismatch` (§Conventions → CLI exit codes, `1`; [Deployment / Distribution]). The scope's fallback is different: an absent, hash-failed or signature-failed sideload degrades to the inbox ConPTY. That follows the §Design Philosophy "human always wins" rule and §Cross-cutting Patterns "Fail open toward the human". The two regimes differ, so arch has to be amended to record the sideload's degrade as distinct from the exe's refusal. Any new refusal or exit code would need a §Conventions amendment.
- **Place in the start order.** §Established Decisions [Session Liveness] fixes `run`'s start order: program resolution → strip plan → collision → pinned copy and plugin → version gate → endpoint bind → first snapshot → heartbeat → start events → spawn. The sideload pin and verify step, and the pre-load, each need an exact named place in that list. The pre-load must come before portable-pty's first ConPTY use, and the list is amended at wrap. `run` prints nothing to the terminal while the child runs (§Cross-cutting Patterns → Diagnostic output channels). The degrade therefore reaches the operator only through the process log and the event/snapshot record, never through stderr once the child's screen is up.
- **No configuration channel and no network.** §Cross-cutting Patterns → Config management rules that environment variables are not a configuration channel. No `VIOLA_*` variable, `config.json` key or CLI flag may select or disable the backend, and no dependency or feature may read an environment variable (§Occupied Resources → Environment variables lists every variable read). The deployment model is local-only (§Infrastructure Patterns → Deployment model). No listening port or runtime fetch exists beyond §Occupied Resources → Network, so a runtime download from `viola` is outside the architecture. Per the scope, that is a founder question.
- **Cross-platform discipline.** §Cross-cutting Patterns → Cross-platform discipline requires every OS-specific branch to compile and be tested on its CI runner, and children to be spawned directly. The sideload code is `cfg(windows)`. macOS and Linux keep openpty unchanged (§Design Philosophy "Cross-platform from the first commit, Windows first"). `OpenConsole.exe` is launched only by `conpty.dll` beside it, never by viola through a shell.

## Patterns to follow
- **Embedded bytes written out at start.** The plugin is compiled in with `include_str!` and written out by `viola run` on every start (§Established Decisions [Deployment / Distribution]; §Stack and Technologies → Container runtime / deployment). If P4 chooses "travel inside the build", the `include_bytes!` analogue of this pattern keeps the binary and its sideload unable to drift apart, and the pinned key's content hash changes with the bytes by construction.
- **Pinned, sha256-verified official download scripts.** `scripts/install-ripgrep.sh` and `scripts/install-node.sh` each follow the same shape (§Infrastructure Patterns → CI/CD approach, Setup steps; Project directory structure): an official release asset checked against a published sha256, with a `--probe` mode proving digest mismatch is refused, TLS failure fails closed and a matching digest passes, and one textual home for the pin (the `NODE_PIN_*` lines). This is the shape for a build-time `.nupkg` fetch.
- **Truncated SHA-256 key plus chunked re-hash.** Per §Stack and Technologies → Content hash, sha2 `=0.11.0` hashes content in 64 KiB chunks before reuse. The key is 16 hex characters, and a pure-Rust hash means no `cc`. Pinning each sideload file by its own full SHA-256 goes beyond the key's truncation and has to say so explicitly.
- **Windows API through windows-sys behind the owning seam.** The `TerminateProcess` kill fallback and `HostTerminal`'s console modes sit behind the `pty` seam (§Stack and Technologies → PTY layer). The channel's SQOS open and listener DACL sit in `viola-channel` (→ Wrapper IPC). Load-path restriction and trust verification calls follow this pattern, with features added per crate (`Win32_Security_WinTrust` is not enabled today, per the scope).
- **Registry amendment for new resources.** Every new file, path or test-only artefact gets its §Occupied Resources entry, as the test-only `<temp dir>/viola-pty-watch/` reports did (Filesystem). New entries include the two pinned files, any fetch or cache dir under `target/`, and any pin home.

## Anti-patterns to avoid
- Forking portable-pty, bumping it off `=0.8.1` (0.9.0 is excluded for wezterm#6783), swapping to psmux, or building an own ConPTY on windows-sys as a side effect of this chunk. All four are gated by [PTY]'s swap triggers (§Established Decisions [PTY]).
- A C-building crate, a non-crates.io source, or Tokio in a sync crate. `viola-pty` and `viola-state` are listed in `scripts/sync-crates.txt` under the sole-root `deny-sync.toml` ban (§Infrastructure Patterns → Build system; §Established Decisions [Concurrency / Backend Framework]).
- A PATH-, CWD- or search-order-dependent load of any file viola runs or loads. The pinned-path discipline of [Deployment / Distribution] ("Hooks and MCP never search PATH"; the prototype's PATH-found hooks ran a different binary) applies equally to `conpty.dll`.

## Contract bindings
- **arch ↔ obs.** The backend the spawn used goes on the `pty.spawn` span, which `viola-pty` emits (Crate dependency direction; obs-plan owns the `pty_backend` values). If the backend or degrade reason also enters the instance snapshot or an event, §Standard Contracts → Instance snapshot (a closed `data` field list, with replay-recoverable fields named) or the event line must be amended, carrying `v` under §Cross-cutting Patterns → Mixed-version tolerance.
- **arch ↔ security.** The signature trust root, the hash pins and the DLL search-order restriction are owned by the security-plan. Arch supplies the pinned-dir location and the write helper ([Deployment / Distribution], [Snapshot writer]). The licence record for a non-crate binary sits outside `cargo deny`'s crate graph, and arch's licence rule covers only workspace crates (§Infrastructure Patterns → Build system, Licence).
- **arch ↔ tests.** The H2 loop runs on the `windows-2025` leg (§Stack and Technologies → CI/CD). If it is re-added to `ci.yml`, the job and check-run counts in §Infrastructure Patterns → CI/CD approach ("7; 15 check-runs") change for its lifetime, or `ci.yml` returns byte-identical afterwards. The release gate `scripts/release-check.sh` judges `viola` as the only executable artifact (target job 6), so any `OpenConsole.exe` produced by the build must be squared with it. The test homes under `target/e2e-home/` get pinned bins too, and so gain the sideload files (§Occupied Resources → Repository).

## Acceptance criteria contributions
- `viola-pty`'s normal dependencies remain portable-pty `=0.8.1`, tracing, windows-sys and libc, with no viola crate and no thiserror. `[workspace.dependencies]` still pins portable-pty as `=0.8.1` (per architecture §Infrastructure Patterns → Crate dependency direction and §Established Decisions [PTY]).
- `conpty.dll` and `OpenConsole.exe` are written only under `<viola home>/bin/<version>-<hash>/`, only through `replace_private`/`replace_private_shared`, and are re-hashed before every reuse. The `bin/<version>-<hash>/` entry in §Occupied Resources → Filesystem names both files (per architecture §Established Decisions [Deployment / Distribution], [Snapshot writer]).
- The [Session Liveness] start-order list names the sideload's step(s), and the pre-load precedes the spawn. With the sideload absent or failing hash or signature on Windows, `viola run` still starts and spawns the child on the inbox ConPTY with exit 0 behaviour unchanged. The exe's own `pinned-hash-mismatch` refusal is unaffected (per architecture §Established Decisions [Session Liveness] and §Conventions → CLI exit codes).
- No new env var, `config.json` key or CLI flag selects or disables the backend. The macOS and Linux `cargo check`/test legs pass with no sideload code compiled in. The [PTY] entry records the with and without H2 results by run id (per architecture §Cross-cutting Patterns → Config management and Cross-platform discipline; §Established Decisions [PTY]).
