# obs extract

## Relevance
partial — the chunk is transport and supply-chain work (arch and security own most of it); obs owns how the backend used and the fallback are recorded, the start-sequence spans, the default-deny schema and the gates over the H2 measurement legs.

## Constraints
- The backend actually used must be recorded on the `pty.spawn` span and on `process-start{subject:"claude-child"}` through `pty_backend`, which obs-plan §4 Scenario "`viola run` start sequence to child spawn" and the §6 `process-start` catalog define as the closed enum `conpty|openpty`. Telling the sideloaded ConPTY apart from the inbox one needs either a new closed value or a new additive field. Either way it is a closed kebab-case code, it goes into the §6 catalog and `schemas/diag-line.v1.json`, and it gets an obs Decisions Log entry (per obs-plan §8 Default-deny posture and §12, following the D-35 precedent for widening a closed enum). An additive field is obs-owned; a new `event` value is not: tests own the event list, so it would travel as a test-plan §3 amendment (per obs-plan §3 Log format JSON schema, "obs-plan may add fields but must not rename or remove these", and D-21). Whether the schema's `pty_backend` definition is an enum today is research's question.
- A fallback to the inbox ConPTY is a degrade, not a refusal and not a failure exit. It must not reuse `pinned-hash-mismatch` or any other `process-exit` exit-1 code: in obs-plan §6's `detail` code catalog and D-20 those codes end the run with exit 1. If the fallback is recorded with a reason (absent / hash mismatch / signature failure), the reason is a new closed kebab-case code with a catalog entry (per obs-plan §6 `detail` code catalog and §11 PII Scrubbing, "NEVER put paths or pids inside `detail` codes").
- Paths never reach a home-level line: not the pinned bin dir, not `conpty.dll`'s path, not `OpenConsole.exe`'s path. A span or event carries only codes and counts, and paths go only to the instance detail file inside a chain (per obs-plan §4 Scenario 1, "Never the endpoint name, `pinned_bin` path or env values", and §8 data classification rows Medium and Low).
- Any new span on the start sequence (the pre-load, the hash or signature check, the choice of backend) is declared `#[instrument(skip_all, name = "<area>.<operation>", fields(...))]`, with a static snake_case name, an explicit field allow-list, and no `err` / `ret` (per obs-plan §4 Span naming convention and §11 Spans / Traces; gate G1 per §9). It sits inside `run.start` before `pty.spawn`, after obs init steps 1–6, so the panic hook and the role file are live when it runs (per obs-plan §3 OTel SDK init, per-role anchor `run`).
- Load, hash and signature failures are captured at viola's seam from the returned `Result`. `portable_pty` and every other third-party target stays `OFF`, and no `log` bridge is installed to surface them (per obs-plan §6 Per-module log levels, D-11 and D-23). A spawn failure on either backend still ends as `process-exit{subject:"self", exit_code:1, detail:"internal-error"}`, with the chain in `detail-run.ndjson` (per obs-plan D-23).
- The new outcome needs a level row. Refusals and other normal outcomes are `info`; `warn` is reserved for recovered or degraded conditions. The level of a sideload that was present but rejected, as against one that was simply absent, is an obs decision to record (per obs-plan §6 Log levels mapping).
- The obs contract is identical on every OS: macOS and Linux keep emitting `pty_backend` as today, with the same line schema (per obs-plan §1 trigger multi-platform-exporter-compat, "ConPTY vs openpty in `pty` spans").

## Patterns to follow
- D-35 is the template for widening a closed code set: one Decisions Log entry, the §6 catalog row, and the `schemas/diag-line.v1.json` `$defs` enum updated together (per obs-plan §12 D-35).
- One boundary line per decision, never a line per call or per byte. The backend choice is logged once per `viola run`, on the existing `process-start{subject:"claude-child"}` and `pty.spawn` span (per obs-plan §11 Telemetry Strategy, "NEVER over-instrument hot paths", and §6 Boundary-call wrappers, PTY seam).
- Every line goes through `obs_event!` with explicit typed fields. There is no raw `tracing::*!`, and there is no print macro in the `run` path (per obs-plan §3 Logging stack and §11 Logs; clippy `disallowed-macros` and the `scripts/lint-probes.sh` raw-`event!` grep).
- Spawn logging for viola's own children is a `process-start` / `process-exit` pair at the call site, with `subject` from a closed enum (per obs-plan §6 Boundary-call wrappers, Child / shell spawns). If P3 finds that viola, not `conpty.dll`, launches `OpenConsole.exe`, that launch needs a new `subject` value under its own Decisions Log entry. Which process launches it is research's question.

## Anti-patterns to avoid
- NEVER log a field or value outside the §6 catalog (a new `pty_backend` value, a sideload-outcome field, a signature-result code) without the catalog row, the schema update and a Decisions Log entry. G4 fails the build on it (per obs-plan §11 PII Scrubbing and §10 Build / deploy failure conditions).
- NEVER put an absolute path, a DLL or exe path, a hash, or the NuGet package's file layout into a home-level line or into a `detail` code (per obs-plan §11 PII Scrubbing and §8 Medium row). Hash values are not in the §6 catalog.
- NEVER let a sideload check panic on the `run` start path, or surface its failure on the terminal. Failures are `Result`s mapped to codes, and a panic here counts against G2's zero-panic budget (per obs-plan §10 Always-required SLO invariant and §3 Observability Harness Contract, the `run` terminal rule).

## Contract bindings
- obs ↔ tests (H2 measurement): each H2 loop leg, with and without the sideload, should be able to show from its diagnostics which backend it actually ran on, through `process-start{subject:"claude-child"}.pty_backend` (or the new field), read through `agent-run logs`/`jq`. The loop's measurement protocol and verdict body are tests-owned (per obs-plan §3 Snapshot / paste-to-AI integration and §9 Pipeline integration).
- obs ↔ tests (CI): if the H2 loop comes back as a CI job, its viola homes live under `target/e2e-home/`. G2, G4 and `secret-scan` then run `if: always()`, and any upload is gated on `steps.secret-scan.outcome == 'success'`, with SHA-pinned `actions/upload-artifact` v7.0.1 and `retention-days: 7` (per obs-plan §9 Step order and conditions, Telemetry artifact handling, and §11 CI).
- obs ↔ security: the fallback reason codes and any signature-check outcome are the codes-only mirror of security's DLL-load and signature-trust decisions. Security owns what counts as a rejection, obs owns the field shape and level (per obs-plan §8 Integration points and §3 Bootstrap phases, the ownership split).
- obs ↔ arch: `pty.spawn` stays the CLIENT span of the `viola-pty` seam. Whether the load-path control lands in `viola-pty` or in the root bin decides which crate's target (`viola_pty` or `viola`) emits the new span; both are `INFO` in the `Targets` filter (per obs-plan §4 Span kinds and §6 Per-module log levels).

## Acceptance criteria contributions
- On Windows, a `viola run` with the verified sideload and one without it each emit a `process-start{subject:"claude-child"}` line whose `pty_backend` (or new additive field) tells the two backends apart. macOS and Linux still emit `openpty`. Every new value or field is in the §6 catalog, in `schemas/diag-line.v1.json` and in an obs Decisions Log entry, and G4 passes over both runs' homes (per obs-plan §4 Scenario "`viola run` start sequence to child spawn", §6 Additive field catalog, §8 Default-deny posture, §12).
- An absent, hash-mismatched or signature-failed sideload yields a run that reaches `process-start{subject:"claude-child"}` on the inbox backend. It logs no `process-exit{exit_code:1}` and no `event:"panic"` line (G2 clean), and records the fallback reason only as a closed kebab-case code (per obs-plan §6 `detail` code catalog, §10 Always-required SLO invariant, §11 PII Scrubbing).
- No home-level `diagnostics/*.ndjson` line from these runs contains the pinned bin dir, a `conpty.dll` or `OpenConsole.exe` path, or a file hash. This is checked by a grep over the test homes alongside the secret scan (per obs-plan §4 Scenario 1, "Never ... `pinned_bin` path", and §8 data classification, Medium and Low rows).
- If the H2 loop runs in CI, its job runs G2, G4 and `secret-scan` `if: always()` over homes under `target/e2e-home/`, and uploads only behind the scan gate (per obs-plan §9 Step order and conditions and §11 CI).
