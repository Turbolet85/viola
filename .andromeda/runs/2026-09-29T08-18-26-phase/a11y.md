# a11y extract

## Relevance
partial: the chunk is Windows PTY transport with no web-spa, cli-output or ARIA surface. It swaps the ConPTY backend under the `viola run` tui passthrough, which a11y-plan §1 scopes as a boundary-only surface, so only the three tui boundary clauses and their Windows-leg assertions apply.

## Constraints
- The `viola run` TUI passthrough (the `claude` TUI hosted in ConPTY/openpty) is a boundary-only entity. Per a11y-plan §1 (CLI and terminal entities → `viola run` TUI passthrough), the wrapper must (a) write zero bytes to the terminal except the child's output, (b) never block, refuse or delay a human keystroke past the current atomic paste, and (c) pass focus, mouse and resize sequences through without counting them as human editing. The clauses bind whichever ConPTY backend is live: the sideloaded `conpty.dll`/`OpenConsole.exe` or the inbox kernel32 fallback.
- Per a11y-plan §1 (Surface: tui → Notes), `run` diagnostics go to `diagnostics/`, never to the terminal. The scope's fallback record (which backend was used, and why the sideload was absent or rejected on a hash or signature failure) must therefore reach obs/diagnostics only. No warning or `hint:` line may be printed into the child's terminal stream.
- Per a11y-plan §5 (tui) and §11 (Keyboard, the last bullet), the terminal belongs to the child. The sideload's pre-load, verification and fallback steps must not block or delay a human keystroke. Any verification cost the scope lets P3 measure must land before the spawn, never on the keystroke path.
- Per a11y-plan §3 (Keyboard test harness → Tooling), the Windows zero-viola-bytes check asserts only that viola's own literals are absent. That is because ConPTY itself emits a spawn preamble (`ESC[?9001h ESC[?1004h …`, an OSC 0 title, `ESC[?25h`) and re-renders nested output, as measured at chunk 2026-09-25-pty-wrapper-on-windows research fact 4. That measurement is of the inbox ConPTY. Whether the sideloaded OpenConsole emits the same preamble is research's question, and the check must still tell ConPTY's bytes apart from viola's under both backends.
- Per a11y-plan §1 (Surface: tui → Notes) and §11 (Strategy), this is a boundary guarantee, not a conformance claim. The backend change carries no WCAG claim for the TUI.
- Per a11y-plan §12 D-A11Y-13, the tests' outer-PTY driver is portable-pty `=0.8.1`, inherited, and a11y does not re-pin it. The scope's no-fork/no-swap boundary matches this.

## Patterns to follow
- The three tui boundary clauses are three separate portable-pty outer-PTY nextest cases on all three OS legs, one per clause, per a11y-plan §4 (P4 → tui) and §3 (Keyboard test harness → Tooling). The Windows leg must exercise them under the backend that `viola run` actually selects.
- The boundary cases run with the tests' `viola-fake-agent` as the child and never inspect `claude` content, per a11y-plan §3 (Keyboard test harness → Tooling).
- On the Windows leg, the zero-viola-bytes check matches viola's own literals (diagnostics, refusal text, `hint:`). It does not compare byte for byte against an unwrapped run, per a11y-plan §3 (Keyboard test harness → Tooling).
- The founder-owned manual pass for this surface is NVDA + Windows Terminal, confirming that the wrapped TUI reads the same as unwrapped (Must-Work O1). It is supplemental only and recorded as `a11y/sr-pass/<date>-<at>.json` rows, per a11y-plan §3 (Screen reader test pattern) and §7 (Per-surface SR test pattern).

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste, and never count focus, mouse or resize sequences as editing. A slow or failed sideload check must degrade to the inbox ConPTY without stalling input (per a11y-plan §11 Keyboard).
- NEVER parse the rendered `claude` TUI screen for content, or take screenshots as a11y evidence. The H2 loop and any backend comparison must not use screen content as a11y evidence (per a11y-plan §11 Universal).
- NEVER emit SGR or any viola-originated text into the `viola run` stream. This includes a sideload-fallback notice (per a11y-plan §11 Visual, the `viola run` clause, and §1 tui Notes).

## Contract bindings
- a11y ↔ tests: the three tui boundary cases are nextest cases in the tests harness on all three OS legs (a11y-plan §4 P4, §9 CI Integration, the unit/integration row). Whichever CI change puts the sideload beside the test binaries on the Windows legs decides which backend those cases exercise. The tests' own outer-PTY driver is also portable-pty `=0.8.1`, which the scope says loads `conpty.dll` by bare name. Whether a `conpty.dll` placed beside the test binaries is also picked up by the outer-PTY driver, and so changes the Windows ConPTY preamble the zero-bytes check tolerates, is research's question.
- a11y ↔ obs: the backend-used record (the scope's `pty.spawn` `pty_backend` field or an event) must reach obs/diagnostics and never the terminal (a11y-plan §1 tui Notes). The field shape is the obs extract's.

## Acceptance criteria contributions
- (a11y) On windows-2025, the three tui boundary nextest cases pass with `viola run` on the sideloaded backend: zero viola-originated literals on the outer-PTY stream, human keystrokes delivered unblocked past the atomic paste, and focus/mouse/resize sequences leaving the wheel unmoved (per a11y-plan §4 P4 → tui and §3 Keyboard test harness → Tooling).
- (a11y) With the sideload absent or rejected (hash or signature failure), `viola run` spawns on the inbox ConPTY. The Windows zero-viola-bytes case still passes, so no fallback notice, warning or `hint:` reaches the terminal stream (per a11y-plan §1 Surface: tui → Notes and §11 Visual).
- (a11y) Keystroke-unblocked holds on the fallback path: a human keystroke injected during a driver `send` is delivered, whichever backend was selected (per a11y-plan §1 CLI and terminal entities → `viola run` TUI passthrough, clause 2, and §11 Keyboard).
