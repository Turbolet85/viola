## Relevant amendment history
- **2026-09-29-verify-stamped-test-homes-and-harness** — widened the closed `subject` enum with `verify-probe` through §6's catalog, `schemas/diag-line.v1.json` and a new Decisions Log entry, D-35. It also required every child spawn viola makes to log a `process-start`/`process-exit` pair at the call site, and it left §1 untouched under the verbatim-scope rule. This is the exact template the extract names for a new `pty_backend` value, a sideload-outcome field or fallback-reason code, and a new `subject` if viola itself launches `OpenConsole.exe`. The next obs Decisions Log entry is D-36. Like the §1 trigger "ConPTY vs openpty in `pty` spans", §1 stays as written, and §4, §6 and §12 carry the change.
- **2026-09-25-pty-wrapper-on-windows** — gave `process-start{subject:"claude-child"}` its current field set (`env_kept`, D-34 superseding D-14). It moved `batch-script-child` so that program resolution decides it before the strip plan and `pty.spawn` (it had been decided by `run.pin_copy`), and it recorded that `viola-pty`'s `PtyError` has a hand-written fixed `Display` (no thiserror in `viola-pty`). A proposal to make `viola-pty` tracing-free was rejected because obs §3 and §4 require seam spans (`pty.spawn`), which were carried to "Wrapper channel". This matters here in four ways: the new backend field joins the same claude-child line; any new pre-spawn step (pre-load, hash or signature check) must be placed in the same resolution → strip → spawn order; the load and hash errors in `viola-pty` follow the fixed-`Display` rule; and a span emitted from `viola-pty` is admissible because the crate is not tracing-free.
- **2026-09-27-instance-state-and-start-order** — amended §4 Scenario 1 (the `run.collision_check` outcomes, the product event order) and the §6 `detail` catalog: `already-live` covers live and stale holders, and a `gone` holder is taken over with no exit-1 line. This chunk inserts spans into that start sequence. It also sets the precedent for a non-failure outcome that writes no exit-1 `process-exit`, which is the shape the inbox-ConPTY fallback must take, and it shows that a new `detail` code needs its own §6 catalog row.
- **2026-09-28-cli-output-tokens** — `run`'s one pre-spawn stderr exception covers every start refusal (`.cmd`/`.bat` child, live or stale name, tampered pinned copy, squatted endpoint): two fixed lines through `src/human.rs` `refuse` → `write_refusal`, with no print macro and no `#[allow]` in `src/human.rs`. The sideload fallback is a degrade, not a refusal, so it must not reach this writer or the terminal. A hash mismatch on the sideloaded files must stay distinct from the tampered-pinned-copy refusal that already exists (`pinned-hash-mismatch`, exit 1).
- **2026-09-28-capability-ledger-and-viola-verify (verify's outcome, `hook --capture`, `boot` readiness)** — "Kept": §6's requirement of a `process-start`/`process-exit` pair for every child spawn stands, and an overseer ruling says the spec stays right rather than being amended down to shipped code. If P3 finds that viola, not `conpty.dll`, launches `OpenConsole.exe`, that launch owes a pair with a new `subject`. The spec cannot be relaxed to leave it unlogged.
- **2026-09-28-capability-ledger-and-viola-verify (raw panic frames, `cli` internal-error line)** — §7's panic detail `backtrace` is raw frames (`0x<ip> <module path> base=… +0x<offset>`) from `src/panic_frames.rs`, captured through `GetModuleHandleExW`/`GetModuleFileNameW`. They land only in the detail file and are resolved offline against the pinned copy. When the sideload is loaded, a frame in `conpty.dll` carries that module's path, which is admissible only in the detail file, never in a home-level line. Offline resolution against the pinned bin dir will now meet a second module there.
- **2026-09-28-hook-perf-gate (the `perf` job's uploads)** — the precedent for a separate per-OS measurement job. It runs its own G2, G4 and secret scan, and its uploads (`perf-<os>`, `diag-perf-<os>`) happen only after a successful scan; a failed scan withholds them and uploads `secret-scan-<job>-<os>` instead. The move was escalated as D-obs-pii and ratified as "same channel, only a second artifact name". If the H2 200-loop comes back as a CI job with and without the sideload, it follows this shape. Its diagnostics, which show `pty_backend` per leg, ride the scan-gated class.
- **2026-09-28-hook-perf-gate (G2's exact-path seam exemption)** — G2 runs as `scripts/g2-zero-panics.sh` in each job. Its only exemption is a panic line at exactly `src/cmd/hook/seam.rs:<digits>`, ratified by the founder, and a further exemption needs a Decisions Log entry. A panic in the sideload check on the `run` start path counts against G2 with no exemption available, which supports the extract's rule that sideload failures are `Result`s mapped to codes.
- **2026-09-27-browser-verdict-reachability** — fixed the CI `test` job's step order at G2 → G4 → capture → scan → uploads → gate (the browser suite joined step 1 without changing it) and brought each new JUnit under the `target/agent-run/*` secret-scan scope. Any sideload-placement step or H2 measurement step added to the Windows legs has to sit inside this order.
- **2026-09-26-ci-chunk-base-and-union-verdict** — narrowed the secret scan's `target/agent-run/*` scope by exactly one file (`chunk.diff`), and only because the upload drops the same file. The escalation was applied as routine because it was not a boundary widening. If an H2 loop artifact is excluded from the scan, this is the precedent: the upload must drop the same path, or the change is a boundary widening that needs escalation.
- **2026-09-24-quality-gates** — created §8 item 6's class of "unscanned uploads, admissible by content", with each unscanned member listed by name and justified by its content. An H2 verdict or measurement file uploaded outside the scan needs its own inventory bullet.
- **2026-09-24-workspace-tree-and-code-graph-planes** — added the `supply-chain` artifact to the unscanned inventory. It was escalated as the playbook's never-routine "boundary widening" class and ratified with the guard binding: a member that could carry a host path or log content is scanned before upload, or dropped. This matters for any new NuGet fetch, provenance or signature-check output uploaded from CI, which must contain no DLL or exe path and no host path.
- **2026-09-24-supply-chain-and-workflow-gates** — §9 Platform: `ci.yml` is the single push/PR workflow, and `nightly.yml` beside it runs only the scheduled checks. If the NuGet pin gets a scheduled re-check, or the H2 loop lands outside `ci.yml`, §9 Platform must be amended.
- **2026-09-24-diagnostics-plane** — the schema's default-deny is a top-level `unevaluatedProperties: false`, not a per-event `additionalProperties: false`. `diag-detail.v1.json` is self-contained, with the event enum inlined, and `obs_event!` attaches only `event`, `process` and `instance`; everything else is an explicit typed field. A new `process-start` field must therefore be declared where `unevaluatedProperties` sees it (the `$defs` / `allOf` branch for `process-start`), and any enum change is mirrored in the inlined copy in `diag-detail.v1.json` if it is referenced there.
- **2026-09-27-wrapper-channel** — `schemas/diag-line.v1.json` carries per-event conditional `required` rules (if-then on `event` and discriminating fields) with negative tests. If the backend field is made required on `process-start{subject:"claude-child"}` on Windows only, or on every OS, it follows this conditional-required pattern and its negative test.
- **2026-09-24-observability-gates** — the raw-tracing ban is enforced by `clippy.toml` `disallowed-macros` (the level macros by path) plus a fail-closed raw-`event!` grep in `scripts/lint-probes.sh` on the Linux lint leg, and a `lint-probes.sh` failure is a build failure (D-33). Every new sideload or backend line must go through `obs_event!`. The Windows-only code path is still grepped on the Linux leg, so a raw `event!` under `cfg(windows)` still fails.
- **2026-09-24-log-redaction-and-never-log-floor** — anyhow is scoped to the root-bin dispatch edge and `viola::obs::report_internal_error`, which renders `chain:[...]` only into `detail-<process>.ndjson`, and only when an instance resolves. A spawn failure on either backend still ends through this reporter as `process-exit{detail:"internal-error"}`, and a load or signature error chain that holds a DLL path stays in the detail file.
- **2026-09-27-hooks-to-normalised-events** — amended §4 Scenario 1 (`session-start{source:"hook"}` is record three) and set the §10 spine gate at a provisional 1.0 s, with a 750 ms hook connect deadline under it. Pre-loading and signature-checking on the `run` start path adds time ahead of `pty.spawn`. §10's timing rows and Scenario 1's record order are the budgets the added start cost is measured against.
- **2026-09-28-mutation-testing-to-the-epoch-boundary** — obs code meets cargo-mutants only at `agent-run run --mutants` (the epoch-boundary code audit, or on demand), and a surviving mutant in obs code is a failure there.
