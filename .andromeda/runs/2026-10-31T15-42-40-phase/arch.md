# arch extract

## Relevance
relevant — the chunk moves a locked external contract (CLI `--json` and MCP error bodies) and reads the exit-code set, the closed code words and the check-before-log order across the root bin, `viola-core`, `viola-channel` and `viola-mcp`.

## Constraints
- The typed exit set stays as listed; causes are told apart inside exits 21 and 1, and each cause keeps the exit the plan assigns it, which also fixes the split between the exit-21 strict-modes refusals (`list`, `plugin install`, `link`, `unlink`, the six frame verbs) and the exit-1 ones (`run`, `revive`, `verify`) (per architecture.md §Occupied Resources → Binary, subcommands and exit codes; per architecture.md §Conventions → CLI exit codes).
- The plan requires today's one `instance-unreachable` document with `detail: null` for every exit-21 cause, and says the server-mismatch cause has no `--json` code of its own; `v1-18`'s distinct code contradicts that text, so where the code is carried (`error` or `detail`) is an amendment of this plan, not an implementation detail, and belongs to P4 (per architecture.md §Standard Contracts → CLI `--json` output; per architecture.md §Conventions → CLI exit codes, the exit-21 server-check row).
- Removing a field or changing its meaning bumps `v`, while an added field does not; the plan states this rule for channel `params`, event lines and snapshots, and the `--json` documents carry the same `v: 1`. A driver that branches on `error == "instance-unreachable"` is the reader at stake, so P4's carry choice must say whether the rule binds it (per architecture.md §Conventions → Protocol versioning).
- MCP's `isError` body is required to be shaped like CLI `--json`, with text `refused: <code>`; a moved CLI document moves the MCP body with it, the `list` tool's refused board included (per architecture.md §Conventions → MCP; per architecture.md §Standard Contracts → Session liveness, the `claude agents --json` row).
- `revive --json` owes a document for each refusal `run`'s start makes after a passed preflight, and the plan names this chunk as the owner. Whether the code still prints none, and whether `session-live` is built as the plan's exit-1 row states against the scope's stale CARRY, is research's question (per architecture.md §Standard Contracts → CLI `--json` output; per architecture.md §Conventions → CLI exit codes, the `viola revive` preflight row).
- A strict-modes or home-tree check runs before any log, because opening a log narrows an existing home, and a refused check writes no line; giving a cause a log form cannot move a check after a log open. The MCP frame tools' strict-modes and server-mismatch refusals are also required to write no line, so "reaches the process log" cannot hold for them without a P4 naming (per architecture.md §Occupied Resources → Filesystem, the `instances/<ViolaName>/` row; per architecture.md §Conventions → MCP, the two frame-tool rows).
- `viola hook` always exits 0 and never writes to stderr, and it is not a row of the catalogue; `viola mcp` writes only MCP frames to stdout, so its refused home check stays silent there and is named outside the table or given a reason (per architecture.md §Established Decisions → [Hook Contract]; per architecture.md §Cross-cutting Patterns → Diagnostic output channels).

## Patterns to follow
- `client::refused_document` is the named writer of the exit-1 revive documents and of `plugin install`'s exit-21 document; `client::refuse_untrusted` is the frame verbs' strict-modes refusal. New documents extend these writers rather than adding a parallel one (per architecture.md §Standard Contracts → CLI `--json` output; per architecture.md §Conventions → CLI exit codes).
- A refusal has two forms: human mode an `unable:` / `hint:` pair on stderr, `--json` one stdout document with stderr empty, each holding no path or pid (per architecture.md §Conventions → CLI exit codes).
- Code words are read through `viola_core::is_code_word` and on-wire enum values are kebab-case; a closed list that the root bin, `viola-channel` and `viola-mcp` all read can only sit in `viola-core`, because the direction runs into it and `viola-mcp` does not depend on the root bin, which holds the hints (per architecture.md §Conventions → Code word; per architecture.md §Infrastructure Patterns → Crate dependency direction).
- Error bodies are enumerated in `tests/contract_error_bodies.rs`'s tables, with each body naming a writer and a witness and a census over the product's error writers; a new body lands as a row or the census goes red (per architecture.md §Cross-cutting Patterns → Sanitised error surfaces).
- Human lines go only through the root bin's `human` module, its hints in `src/human/hints.rs`, under the workspace print denials (per architecture.md §Infrastructure Patterns → Build system; per architecture.md §Infrastructure Patterns → Project directory structure).

## Anti-patterns to avoid
- A code, document, MCP text or log `detail` holding a path, a pid, an id or upstream text, or an anyhow chain reaching anything but the instance's detail file (per architecture.md §Cross-cutting Patterns → Sanitised error surfaces; per architecture.md §Established Decisions → [Error Handling]).
- A log opened, a line written or a home narrowed ahead of a strict-modes or home-tree refusal in order to record its cause (per architecture.md §Occupied Resources → Filesystem, the home-tree row).
- A cause told apart by a new exit code or a new `RefusalReason`; refusals are the channel's typed outcomes, and exit 21 and exit 1 are outcomes with no channel `result` (per architecture.md §Standard Contracts → CLI `--json` output; per architecture.md §Conventions → `RefusalReason`).

## Contract bindings
- arch ↔ obs: new `process-exit` `detail` values enter `schemas/diag-line.v1.json`, an obs-owned default-deny schema pinned by `tests/contract_diag_schema.rs`; the logger and format stay obs's (per architecture.md §Occupied Resources → Repository; per architecture.md §Cross-cutting Patterns → Diagnostic output channels).
- arch ↔ security: the sanitised-surface rule binds every new code; whether a distinct code tells a same-user process more than `detail: null` is read against the security plan under the same-user trust boundary, and a widening is the founder's word (per architecture.md §Cross-cutting Patterns → Local endpoint trust boundary).
- arch ↔ design-system: the plan cites design-system for the server-verify hint's wording, so a hint and its code move together on both plans (per architecture.md §Conventions → CLI exit codes, the exit-21 server-check row).
- arch ↔ tests: on macOS `server_verdict` returns `Matches` with no comparison, so a server-verification case cannot be reached there, and the table's OS gating must say so; the socket directory's own gap stays with its route entry (per architecture.md §Standard Contracts → Session liveness, the server identity row; per architecture.md §Cross-cutting Patterns → Cross-platform discipline).
- arch ↔ all plans: the document text this chunk moves is amended at wrap in architecture.md's §Standard Contracts and §Conventions, with the design-system, security-plan and test-plan text naming it moving in step (per architecture.md §Standard Contracts → CLI `--json` output).
