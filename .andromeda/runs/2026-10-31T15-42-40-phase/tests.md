# tests extract

## Relevance
relevant: the chunk builds the plan's named Exit-cause matrix binary and moves the `--json` / MCP / log signals that several landed suites assert.

## Constraints
- test-plan §1 Test Scope Summary (Test tier) sets Comprehensive, so each cause needs its own negative test on every surface it reaches, and the CLI, `--json`, MCP and process-log signals are all in scope (per test-plan §1 Test Scope Summary).
- test-plan §6 Exit-cause matrix requires an rstest `#[case]` table with one negative test per cause of exit 21 and exit 1, each asserting the exit code, the `--json` document and a last stderr `hint:` line naming that cause. A hint shared across causes fails the table, and driver-facing hints never contain `release` (per test-plan §6 Exit-cause matrix).
- test-plan §6 Exit-cause matrix names a home binary for each landed cause outside the table: server verification, the frame verbs' strict-modes, `run` and `verify` home-tree, `revive`, the link verbs, the unwrapped name. It also owes this entry the unwrapped-name hint, the table join and the `revive --json` document after a passed preflight. Which rows move and which stay named elsewhere is P3/P4's call (per test-plan §6 Exit-cause matrix).
- test-plan §5 On-disk fixes the strict-modes outcome per verb, and requires no line and no frame on the refused paths, with the mode or ACL read back as found. A refusal gaining a code does not relax this (per test-plan §5 Cross-module patterns, On-disk).
- test-plan §6 Cross-surface parity requires MCP `structured_content` to equal CLI `--json` for the same refusal, and the §1 cross-surface-coordination trigger requires identical payloads for the same channel result. The text is written for `{refusal, detail}`, so whether a per-cause exit-21 code falls under it depends on the P4 contract choice (per test-plan §6 Cross-surface parity; per test-plan §1 Coverage triggers).
- test-plan §6 Error sanitization requires every new code and document to hold no absolute path, serde path or `Caused by`, through the three surface witnesses and the `tests/contract_error_bodies.rs` census. test-plan §6 Security control negatives adds no pid, start time, path or endpoint on the server-verification cause (`digit_runs`) (per test-plan §6 Error sanitization and secret scan; per test-plan §6 Security control negatives).
- test-plan's header bars editing the plan during phase and implement runs, yet §1 Surface cli, §1 CLI verbs, §5 On-disk, §5 MCP and §6 Exit-cause matrix all spell the exit-21 document. A moved contract therefore owes a plan amendment outside the phase run, with each spelling named in it (per test-plan header; per test-plan §5 Cross-module patterns, On-disk).

## Patterns to follow
- Layer and command: the `cross_` prefix puts the binary in suite `nextest-e2e`, so it is selected with `scripts/agent-run.sh run --e2e --filter 'binary(cross_exit_causes)'`. Landed `cli_*` and `security_negatives_*` binaries use `run --integration --filter 'binary(<stem>)'`, and `chaos_` and `contract_` binaries report in the E2E layer (per test-plan §3 `run`).
- Binary home, an open tension for P3: test-plan §2 Directory pattern places `cross_` suites in `crates/viola-e2e`, whose table-driven cases per test-plan §4 Conventions are labelled case tables with no rstest dev-dependency. §6 requires rstest and the scope names root `tests/cross_exit_causes.rs`, and §3 `run` step 1 reads a root `cross_` binary as in the layer. A root binary uses the root `[[test]]` `required-features = ["fake-agent"]` form, and whether that form applies to this file is research's question (per test-plan §2 Test directory + naming; per test-plan §4 Conventions).
- Case shape: readable `#[case::label]` names, `<subject>_<condition>_<expected>` function names, both modes per cause. The `--json` arm is the document with stderr empty and the human arm is the `unable:` / `hint:` pair, as the landed `revive` and server-identity cases assert them. Exact hint strings are pinned by trycmd once the product defines them, or by literal as `viola list` and `--help` are (per test-plan §6 Exit-cause matrix; per test-plan §5 Driver(s); per test-plan §4 Conventions).
- Provoking each cause: real `viola` runs from `stamped_home` in a fresh home under `target/e2e-home`, a home the test makes itself through `create_private_dir`, the squatter bound first through the server API, and the impostor's test-built `snapshot.json` carve-out. The fake agent stands in as `claude` under a test-scoped `PATH`, and a test-started `viola` drops `VIOLA_NAME`, `VIOLA_DIR` and `VIOLA_BIN` (per test-plan §7 Seed strategies; per test-plan §5 Boundary types covered; per test-plan §5 Cross-module patterns, CLI).
- OS branches: `.cmd` / `.bat` is `#[cfg(windows)]`, server verification is `#[cfg(not(target_os = "macos"))]` with its macOS case owed to the route entry "Unix endpoint and home hardening", the Windows strict-modes case uses a Users grant through `icacls`, and Linux-only socket-directory cases keep their `cfg` (per test-plan §6 Exit-cause matrix; per test-plan §6 Security control negatives).

## Anti-patterns to avoid
- NEVER import the product's code list, hint table or refusal ordering as the oracle, and never compare by `Debug` string. Expected codes, exit integers and hint strings are literals in the test (per test-plan §11 Unit).
- NEVER hand-write `snapshot.json`, `budget.json` or `stamps.json`, sync on `sleep`, or use `try_overwrite`. Waits key on logged events or the product's own exit, and the impostor carve-out stays the only written snapshot (per test-plan §11 Test Data; per test-plan §11 E2E; per test-plan §11 Integration).
- NEVER treat a Linux-only local run as proof for the Windows or macOS causes, and NEVER put at E2E a case a lower layer can hold: ordering and mapping cases belong in §4 (per test-plan §11 Test Strategy).

## Contract bindings
- tests §3 Log format ↔ obs `schemas/diag-line.v1.json`: a new `process-exit` `detail` must be valid against obs's schema, because the §6 Schema conformance check fails on any non-conforming home-level line. A new `event` value would need a Decisions Log entry, and §3 Log format names `detail` only as a field. Whether the schema closes the `detail` values is research's question.
- tests §6 Exit-cause matrix ↔ design-system cli patterns: the matrix asserts the hint strings the design-system defines, and it cites the server-verification hint and the unwrapped-name hint byte for byte.
- tests §6 Exit-cause matrix and Error sanitization ↔ security-plan error rules and arch CLI/MCP contracts: the document's shape is owned upstream, so the chunk's P4 contract choice changes what these suites assert.
- tests §3 Status endpoint shape ↔ obs status: `viola list --json` is the harness's `status`, so `list`'s refusal document joining the table must leave the `.ok.items` read intact.

## Acceptance criteria contributions
- `scripts/agent-run.sh run --e2e --filter 'binary(cross_exit_causes)'` passes, with one case per built cause asserting the exit code, the `--json` document and the last `hint:` line, and every cause outside the table named by its row's binary or by a reason (per test-plan §6 Exit-cause matrix).
- The table fails when two causes share a hint or any driver-facing hint contains `release`, proved by a check that goes red on a planted duplicate (per test-plan §6 Exit-cause matrix).
- Every new code passes the error-body witnesses and the `tests/contract_error_bodies.rs` census with no path, pid or upstream text, and the MCP and CLI bodies of each cause carry the same code (per test-plan §6 Error sanitization and secret scan; per test-plan §6 Cross-surface parity).
- The `viola revive --json` refusals after a passed preflight (`batch-script-child`, `pinned-hash-mismatch`, `squatted-name`, the `claude`-not-on-`PATH` `internal-error`) each print their exit-1 document in a case; `pre-push` and the CI `test` jobs stay green on all three OSes at line ≥ 85, function ≥ 95, region ≥ 80, with no retry and no `#[ignore]` (per test-plan §6 Exit-cause matrix; per test-plan §10 Coverage thresholds; per test-plan §10 Zero-flakiness budget).
