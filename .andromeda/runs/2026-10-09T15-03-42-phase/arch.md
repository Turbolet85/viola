## Constraints
- **The typed text has one site and one moment.** architecture.md §Established Decisions → [Delivery Confirmation] requires `validate_paste_text` to run first on the text as received, then the typed text to be taken ONCE (`viola_agent_claude::hook::typed_text`), and that one text to be the only one `send` uses afterwards: the local-command classification, the in-flight text the match compares, `text_bytes` and the paste. The ruling in scope §6 widens what that one function removes; it adds no second strip site and no trim at the compare site (the entry requires the match to stay exact, "nothing else trimmed"). The entry's present wording (LF only, "not a CR"; a newline-only text "typed as an empty text"; the trailing-CR case "carried on the working route") predates the ruling and is target text the chunk's wrap must amend. Whether any consumer today reads the received text instead of the typed text is research's question.
- **The widened strip widens local-command classification.** architecture.md §Established Decisions → [Delivery Confirmation] requires a listed command to be classified by exact equality of the typed text with a `LOCAL_COMMANDS` entry (no case folding, never a leading-slash test), and records that the founder was shown the LF consequence (`/clear` plus a newline is `/clear`). Under the ruling the same follows for `/clear` plus CR or CRLF. The plan holds no statement that this consequence was shown for CR; it is a contract consequence to show at P4 and to pin by a test.
- **A refusal detail is a closed set, extended only in `viola-core`.** architecture.md §Conventions → Error handling schema requires `not-delivered` details to be kebab-case strings from the closed per-reason set, extended only in `viola-core`, with readers treating an unrecognised detail as opaque text. The same passage fixes the order in which `send`'s refusals apply and states that the wrapper returns only the first. The new newline-only detail therefore needs (a) its name in `viola-core`, (b) a stated rung in that order, both contract changes shown at P4 and amended at wrap. Whether "refused at once" places it beside `control-character` (ahead of `human-typing`) or after the wheel rungs is not stated by the plan or by the ruling as scope.md quotes it.
- **No new exit code, no new wire shape, no `v` bump.** architecture.md §Conventions → CLI exit codes maps `not-delivered` to exit 13 for every detail, and architecture.md §Occupied Resources → Binary, subcommands and exit codes closes the set at `0, 1, 2, 10–14, 20, 21`. architecture.md §Standard Contracts → Event `data` per kind requires `send-refused` to be `{refusal, detail, cursor?}` with `cursor` absent for a refusal before `send-issued`, so a refusal "at once" carries none. architecture.md §Conventions → Interfaces and versioning makes an added detail value additive (no bump).
- **Placement follows the crate direction; `viola-core` cannot call the strip.** architecture.md §Infrastructure Patterns → Crate dependency direction requires `viola-core` to depend on no viola crate and `viola-agent-claude` to stay pure (no I/O; its `ledger`, `hook` and `dialog` modules pure), with the root bin the only consumer of all members. So a newline-only check placed in `viola-core` (beside `validate_paste_text`) cannot be written in terms of `viola_agent_claude::hook::typed_text`; a check written on the typed text sits in `viola-agent-claude` or the root bin. Where the refusal is decided is the plan's choice inside that limit. The same key requires the §2 splits to stay in their owners: `dialog_variants` in the pure `viola_agent_claude::ledger` (the key names it as part of that module's surface, read by `verify`), `record` in the root bin's `src/cmd/verify.rs`, `submit` in the root package's test-only `viola-fake-agent` bin.
- **A new reliance on CLI behaviour is a ledger row; a shape no `send` relies on is not.** architecture.md §Cross-cutting Patterns → Capability ledger as the single gate for CLI-specific behaviour requires any new dependence on an undocumented `claude` behaviour to be a row with a `viola verify` probe, with one ruled limit: a CLI shape no `send` relies on needs no probe. architecture.md §Established Decisions → [CLI Version Compatibility] prices a new row: an 18th row, its probe, and a re-stamp of every stamped version, a verify being five `claude` starts. That is the whole of this chunk's cap of 5 starts (scope.md, `inputs#I1`). A design in which `send` never types a trailing CR or LF leaves the CLI's CR and CRLF handling a shape no `send` relies on (the LF precedent in the same [Delivery Confirmation] entry); a design that matches around what the CLI drops would be a new reliance. The live CRLF and several-CR readings are evidence for the choice, not a row.
- **Compiled waits are not sized to a test's kill.** architecture.md §Established Decisions → [Screen Model] requires `GATE_MAX_WAIT` (8.5 s) and `QUIET_PERIOD` to be compiled built-ins validated per CLI version by a stamped row, and architecture.md §Established Decisions → [Delivery Confirmation] requires `CONFIRM_WINDOW_FALLBACK` (10 s) to be compiled, never configured, with `send` blocking at most the sum of the gate's maximum wait, the paste and the window. Scope §4 (the kill above the test's designed wait) and P21 (a kill equal to the window) move the test-side kill in `.config/nextest.toml`, never these constants. The plan does not state how many gate waits `boot_with_an_unknown_cli_version_is_verify_failed` makes; that stays the scope's hypothesis for P3.

## Patterns to follow
- **Validate, then normalise once, then one text everywhere** — the shape architecture.md §Established Decisions → [Delivery Confirmation] gives `send` (validator on the received text, `typed_text` taken once, every later consumer on the typed text). The CR/CRLF strip extends the one function; the newline-only refusal is decided where the typed text (or its emptiness) is first known.
- **An input refusal is checked on both sides** — architecture.md §Conventions → Error handling schema has the CLI check `control-character` before any frame and the wrapper check again. A newline-only refusal that is input validation follows the same two-sided form; whether the CLI client can reach the check without a new dependency edge is settled by the crate-direction constraint above.
- **Human text has one writer** — architecture.md §Infrastructure Patterns → Build system requires the root bin's only human writer to be `src/human.rs` (`write_refusal`: the fixed `unable:` / `hint:` pair as ONE `write_all`; `send`'s readback mirror), with no print allow in the root bin. A new refusal's human lines land there, fixed text, no payload.
- **The root test chain is the shared home for scaffolding** — architecture.md §Infrastructure Patterns → Project directory structure names `tests/support/` as the sync root fixture chain, and architecture.md §Occupied Resources → Filesystem (the test-only `viola-root-watch` row) names its bounded wait primitive (`tests/support/watch.rs` `Watch`, bound `WITHIN`, the report file a killed test keeps) and `Wrapper::stop` / `stop_keep`'s endpoint wait. The §1 child-run-and-wait and boot-and-wait helpers lift onto that primitive, not a new wait loop. That row counts the root waits on a child ("9"); a lift that changes the count is a wrap amendment. Whether `tests/support/` already holds a boot helper the per-file copies duplicate is research's question.
- **CI pins on the fake agent, the real CLI only locally** — architecture.md §Established Decisions → [CI/CD] requires tests against the fake agent with each test in its own `--home`, the real `claude` only in local live runs. The §6 outcomes are pinned by fake-agent tests; the live CRLF and several-CR readings are local evidence recorded in the plan's "as measured at chunk …, `evidence/…`" form.

## Anti-patterns to avoid
- **Loosening the match instead of the typed text** — a trim, a CR-tolerant compare, case folding or a leading-slash test at the match or classification site is banned by architecture.md §Established Decisions → [Delivery Confirmation] (exact match, the decision "depends on the ledger, never on a leading slash").
- **A behaviour knob or a Claude shape in the wrong place** — no env var, flag or `config.json` key for the strip or the refusal (architecture.md §Cross-cutting Patterns → Config management: env vars are not a configuration channel; `AGENT_RUN_*` is harness-only), and no detail name carrying a Claude-specific term (architecture.md §Conventions → Naming patterns: new wire values only in `viola-core`, never Claude-specific).
- **Mutation work wired into a gate** — architecture.md §Infrastructure Patterns → CI/CD approach requires `ci.yml` to carry no mutation job, `windows-mutants.yml` to stay dispatch-only (no inputs, never a gate or required check), and mutation runs to go only through `agent-run run --mutants`. Scope §4 and §5 add no workflow step, no `[[gate]]` entry and no change to that workflow beyond what `tests/contract_windows_mutation_scope.rs` already holds equal.

## Acceptance criteria contributions
- A `send` whose text ends in CR, CRLF or LF (the endings as measured live in this chunk) is typed without them, its `prompt-submitted` is appended `origin:"driver"`, it ends `ok` `{submitted_at, cursor}` and no `wheel` record follows; `text_bytes`, the local-command classification and the in-flight match all read that one typed text (per architecture.md §Established Decisions → [Delivery Confirmation]).
- A newline-only `send` is answered `not-delivered` with the new detail, a member of `viola-core`'s closed set, at exit 13, with no `send-issued`, nothing typed, the wheel unmoved and a `send-refused` line that carries no `cursor`; CLI `--json` mirrors the channel `result` (per architecture.md §Conventions → Error handling schema).
- The chunk adds no exit code, channel method, env var, config key or `v` bump, and no manifest dependency edge: `viola-core` still depends on no viola crate and `viola-agent-claude` on no I/O (per architecture.md §Infrastructure Patterns → Crate dependency direction).
- Shared test scaffolding lands under `tests/support/` as sync code on the existing `Watch` bound, and `ci.yml` / `windows-mutants.yml` gain no mutation step or gate (per architecture.md §Infrastructure Patterns → CI/CD approach).
