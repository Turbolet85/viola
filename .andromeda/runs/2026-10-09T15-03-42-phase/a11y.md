## Patterns to follow
- One trycmd case per refusal pinning the `unable <reason> <detail>` + final `hint:` layout, with assert_cmd for the typed exit code and for `--json` carrying no hint text, on all three OS legs (per a11y-plan §8 Error recovery, Verification).
- Outer-PTY cases wait on a logged line or a record, and the wheel is probed by an `answer` to no pending dialog (per a11y-plan §3 Keyboard test harness, label Tooling).
- A cli or tui output-discipline failure surfaces only as a nextest failure in `suites[].failures[]`; no a11y row is written for either surface (per a11y-plan §3 Structured violation JSON schema, label cli / tui).
- A live reading on a real `claude` session is supplemental and never gating; the pinned proof is the automated case (per a11y-plan §3 Keyboard test harness, label Tooling, the takeover reading). The CRLF and several-CR readings of scope §6 stand the same way beside the tests that pin them.
- A route entry is cited by its title (per a11y-plan §3 Keyboard test harness, label Tooling: the working-route entry "Windows-only live measurements"), the form scope §8 follows. Read at this extraction: a11y-plan.md and its nine key files hold no bare `:125` / `:127` / `:133` / `:135`, so scope §8 owes no a11y edit.

## Anti-patterns to avoid
- Never block, refuse or delay a human keystroke in `viola run` past the current atomic paste (per a11y-plan §11 A11y Anti-Patterns, Keyboard): the newline-only refusal and the trailing-newline strip must not be reachable from the human input path.
- Never show a human-mode CLI refusal without its `hint:` line (the one exception is `unknown`), and never a kebab-case code without the plain word `unable` (per a11y-plan §11 A11y Anti-Patterns, Cognitive).
- Never parse the rendered `claude` TUI screen for content (per a11y-plan §11 A11y Anti-Patterns, Universal): what the CLI submitted for a CRLF or several-CR ending is read from records, not from the screen.
