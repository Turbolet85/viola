- Validation runs first, on the text as received, and a text that holds a refused character is refused whole with nothing typed (per security-plan §Input Validation, Paste text row). The wider strip must keep that order: a text ending in CR or CRLF that also holds a refused character is still `not-delivered` / `control-character`. Whether the code's strip site runs after `validate_paste_text` on every path is research's question.
- security-plan §Input Validation, Paste text row, as written, names the trailing LF as the ONE removal and excludes a CR by name (`security-plan.md:226`). - The typed text is taken once and is the only text `send` uses afterwards: the local-command classification, the delivery-confirmation exact match, `text_bytes` and the paste (per security-plan §Input Validation, Paste text row). The CR / CRLF strip must feed all four from that one taking; a strip applied at the match site alone would leave the pasted bytes and the compared text apart. Whether the four consumers read one value today is research's question.
- The wrapper's check is authoritative and client-side checks are advisory; shared validators live in `viola-core` so the CLI, MCP and the wrapper call the same function (per security-plan §Input Validation, Boundary paragraph). The newline-only refusal therefore has to be decided in the wrapper's `send` whatever the client also does; a client-only refusal does not meet the plan. Where the new check's home is (`viola-core` beside `validate_paste_text`, or beside `typed_text`) is a plan decision.
- An external refusal carries codes and fixed messages only: no upstream text, no absolute path, on channel `result.refusal`, CLI `--json` and MCP `isError` alike (per security-plan §Error Handling, External responses). The new refusal detail is a closed code; the newline-only text, its length or its bytes never ride the refusal or a log line outside `instances/<name>/diagnostics/`.
- Strict-modes on the home, the trusted files and `ledger/stamps.json` refuses on a failed check, and a refusal on the stamps read is `cli_verified:false` (per security-plan §Authentication & Authorization, `~/.viola/` access control row). Scope §5's survivors at `strict.rs:34:23` and `stamps.rs:28:19` sit in the files that carry those controls: each is closed by a test that shows the control's outcome, or by an argument that the mutant is equivalent, never by a change that makes the check more tolerant. Whether those two lines are on the refusal path is research's question.
- Inherited `CLAUDE*` identity values stay in the wrapper's environment, are removed from the child by R8 and are never serialised (per security-plan §Secret Management, Storage). The chunk's live `claude` starts (cap 5, scope §6) record names and codes in `evidence/`, never a value; a start made outside `viola run` is not under the strip, and the plan records its two earlier out-of-strip measurements as covering no other probe (per security-plan §Threat Model Summary, Data classification, credential bullet).

## Anti-patterns to avoid
- NEVER strip a refused character, and never extend the trailing-newline removal to answer free text, which is typed as validated (per security-plan §Security Anti-Patterns → Input). The same bullet says NEVER refuse LF, CR or TAB: the newline-only refusal refuses a text with nothing left to type, not a character, and the amendment has to word that so the two sentences do not contradict.
- NEVER let a refusal block the human, and NEVER add a `config.json` key, `VIOLA_*` variable, CLI flag or a third test seam that shortens, skips or switches off a control to make a test reachable (per security-plan §Security Anti-Patterns → Universal). The newline-only refusal goes to automation's `send` only; scope §4's kill sizing and scope §5's kills use the two existing `fake-agent` seams or none.
- NEVER build local-command lists, harness prefixes or screen signatures from runtime text, and NEVER let a test-side removal under `target/e2e-home` take a dir the test side did not create (per security-plan §Security Anti-Patterns → Code Patterns). The first binds scope §2's split of `dialog_variants` and the strip's effect on local-command classification; the second binds scope §1's shared scaffolding.
