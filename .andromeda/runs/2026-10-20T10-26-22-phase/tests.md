## Constraints
- **Where a kill must live.** Per test-plan §3 `run` (5-command implementation, step 4 "Test scope"), cargo-mutants runs without `--test-workspace`. Each mutant is tested only by the tests of the package that owns the mutated file, so a `crates/viola-<area>` mutant must be killed by that crate's own tests, and the `viola-e2e` scenarios never run against another package's mutants. So survivors #12–#14 can only be killed inside `viola-mcp`'s own package, in `crates/viola-mcp/src/**` units or `crates/viola-mcp/tests/`, never by `crates/viola-e2e/tests/mcp_tools.rs`. The same holds for #1–#3 (`viola-agent-claude`), #15–#16 (`viola-state`) and #4–#11 (`viola-e2e`'s own tests under `--package viola-e2e`). Whether a package test already reaches `serve`, `get_info`, `list_tools` or `live_endpoint` is research's question.
- **What "recorded" means to the audit.** Per test-plan §10 Mutation gate, `run --mutants` requires `missed − host-excluded == 0`. Per test-plan §3 `run` (step 4 "Verdict"), a missed record leaves the count only when its whole span sits under a `cfg` predicate proved false for the host. A survivor closed as "recorded" (equivalent, or teardown with no observable output) that is not host-excluded still reads `missed` under that rule. How the next audit's reader treats a recorded survivor has to be worded so that audit reads it closed. That wording is P3/P4's question.
- **No mutation run in this chunk.** Per test-plan §10 Mutation gate, no chunk, pre-push or CI mutation gate exists; mutation runs only at the epoch boundary or through an on-demand `run --mutants`. The chunk's gates are `pre-push` and the Lint stage. Per test-plan §3 `pre-push`, its last stage is `run --coverage` then `gate --require coverage,doctest`, and `tools` checks the pins. Per test-plan §9 Pipeline structure (Lint row), the Lint stage is fmt, clippy `-D warnings`, the sync-crate `cargo check` and `bash scripts/orphans-check.sh --probe && bash scripts/orphans-check.sh`. The orphans check matters for every new module file item (5) creates.
- **viola-e2e test shape.** Per test-plan §4 Conventions, `viola-e2e` carries no `[dev-dependencies]`, so its table-driven cases are one labelled case table in one `#[test]` (no rstest edge added). Test names follow `<subject>_<condition>_<expected>`. Kills #4–#11 take this form.
- **Test placement and the moves.** Per test-plan §4 Conventions and §2 Test directory + naming conventions, unit tests sit inline as `#[cfg(test)] mod tests` at the bottom of each source file. M1's `ledger/tests.rs` departs from that wording. §4 and §5 also cite test sites by file (`src/human/board.rs` units `bay_line_*` / `board_row_*`, the `crates/viola-agent-claude/src/ledger.rs` arms). After the split those citations go stale. That is drift for the wrap; nothing in the chunk edits the spec.
- **The MCP oracle.** Per test-plan §1 Surfaces under test (the MCP stdio surface), `tools/list` is exactly the five tools, its result carries `ttlMs` 0 and `cacheScope` `private`, and it holds no `release`, `pause`, `link` or `unlink`. Per test-plan §4 viola-mcp, `tools/list` is exactly `send, wait, last, answer, list`. Item (7)'s replay case asserts these against the recorded exchange.
- **Item (7)'s driver and the fixture's class.** Per test-plan §6 Drivers per surface (the MCP stdio row), the driver is an rmcp client over a `viola mcp` child the test spawns and owns: it closes stdin and awaits exit, never uses `TokioChildProcess`, and lives in `crates/viola-e2e` (rmcp `client` only). The binary takes an E2E prefix from `^(path[0-9]*|tui|mcp|cross|chaos|contract)_`, per test-plan §2 Test directory + naming conventions. Per test-plan §2 the Contract row binds each `fixtures/claude/*/*.json` class to a schema by file name; a file outside the StatusLine / Agents / Screen classes falls to `schemas/claude-fixture.v1.json`. So a recording placed there needs a class and schema of its own. Where it lives is P3's question.

## Patterns to follow
- **Planted-red witness.** A check is proven by a planted input that turns it red. Per test-plan §7 Fixture hygiene, "Planted inputs prove each class red". Per test-plan §6 Contract suite, the `drift` comparator names a planted order swap and a planted one-byte difference. The hand-applied mutant (fails applied, passes reverted) is the same shape, and so is item (7)'s negative: a recorded result with `ttlMs` / `cacheScope` removed must fail.
- **Transport-free MCP handler tests.** Per test-plan §5 Cross-module patterns (MCP), `crates/viola-mcp/tests/handlers.rs` drives the transport-free `viola_mcp::Tools` handle against a `viola_channel::Server` `TestWrapper`, with the snapshot written through `viola_state::snapshot::write_snapshot`. This is the in-package home for the `get_info` / `list_tools` kills (#13, #14). What reaches `serve` (#12) is research's question.
- **Byte-for-byte replay.** Per test-plan §6 Contract suite, recorded fixtures are compared byte for byte against the committed files, never against an insta snapshot. Item (7)'s replay of the recorded `tools/list` exchange follows this.
- **Pure liveness cases.** Per test-plan §4 viola-state, the liveness classifier is tested as the pure `classify(beat_age, same_process)`, fed ages directly with no clock. Kills #15 and #16 on `live_endpoint` follow it, over a real tempfile home whose snapshot comes from the writer.

## Anti-patterns to avoid
- Per test-plan §11 Unit: never import the product's own ledger rows (`LedgerRow::relied()`) as the oracle. Survivor #1 (`relied_here`) is killed against a literal relied set. Per test-plan §11 Test Strategy, a Linux-only reading is never proof for Windows, and the relied set differs by OS (24 on Unix, 21 on Windows).
- Per test-plan §11 Test Data: never hand-write `snapshot.json`, `ledger/stamps.json` or `budget.json` (for #15 and #16, write through the writer). Fixtures come only from scrubbed probe text, never production data. Item (7)'s recording comes from a live start, not `viola verify` probe text, which departs from that rule as written.
- Per test-plan §11 Test Strategy: never run the real `claude` in CI. The live start that records item (7) is local only (`--local-live` refuses when `CI` is set). The committed case replays the recording without the real CLI.
