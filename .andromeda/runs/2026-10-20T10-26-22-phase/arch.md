## Patterns to follow
- The module-root-plus-phase-directory split of `src/run/send.rs` into `src/run/send/*`, per architecture §Infrastructure Patterns → Project directory structure. The root keeps the public items and re-exports its children's names (`SendSlot`, `append_hook_event`, `parse_from`) so every caller keeps its path. `#[cfg(test)]`-only children and test support (`relabel.rs`, `test_support.rs`) sit beside it as their own files.
- The `src/human.rs` root with `src/human/*` children, where `pub(crate) use` re-exports keep every caller's path, per architecture §Infrastructure Patterns → Project directory structure. This is the pattern a `src/human/board/` split extends.
- Recorded `claude` exchanges live under `fixtures/claude/<cli-version>/`. They are scrubbed (the home becomes `~`, the user word becomes `<user>`), refused whole when unclean with the closed codes `home-path` · `absolute-path` · `username` · `email` (the content never named), validated by a test-side schema under `schemas/`, and walked by `tests/contract_fixture_hygiene.rs`. All of this is per architecture §Occupied Resources (the `fixtures/claude/<cli-version>/` and `schemas/claude-statusline-fixture.v1.json` rows).
- Test-harness-only variables use the `AGENT_RUN_` prefix. The product reads or sets only `VIOLA_*` variables, per architecture §Conventions → Naming patterns (Environment variables).

## Anti-patterns to avoid
- A split that leaves a file no module declares. Per architecture §Stack and Technologies (the Code quality row, cargo-modules) and §Infrastructure Patterns → CI/CD approach (the lint job's `Module orphans (per lib/bin target)`), `scripts/orphans-check.sh` refuses an orphan module.
- A product crate depending on `viola-e2e` to reach a kill, or tokio entering a sync crate to drive a test. Both are banned by architecture §Infrastructure Patterns → Crate dependency direction and §Cross-cutting Patterns → Tokio containment.
- A `tools/list` replay that accepts a result without `ttlMs` / `cacheScope`. Per architecture §Conventions → Error handling schema (the MCP bullet), the result carries `ttlMs` 0 and `cacheScope` `private`, because claude 2.1.287 on protocol `2026-07-28` drops every tool without them.

## Contract bindings
- arch ↔ tests: the Windows mutation matrix. Per architecture §Infrastructure Patterns → CI/CD approach, `tests/contract_windows_mutation_scope.rs` requires every product file with a `cfg(windows)` gate to be listed in `windows-mutants.yml`, and the root package is split by file. If a split of `typed.rs` or `board.rs` moves a `cfg(windows)` gate into a new file, that file joins the matrix. Whether either source holds such a gate is research's question.
- arch ↔ security: the recorded `tools/list` fixture. Per architecture §Occupied Resources (the `fixtures/claude/<cli-version>/` row), the recording goes through the same scrub, unclean refusal and hygiene walk as the other recordings. The NEVER-log floor's content is the security plan's.
- arch ↔ tests: the audit unit and the nextest `mutants` profile. Per architecture §Infrastructure Patterns → Project directory structure, `.config/nextest.toml` holds the `ci` and `mutants` profiles, and per §Occupied Resources (the `target/mutants/` row) cargo-mutants builds every test binary in its own copy. A kill counts only where that package-scoped build runs it.
- arch ↔ obs/tests: a new fixture kind, and a new `schemas/` file if one is added, are new occupied resources. Per architecture §Occupied Resources, they are recorded at the wrap.
