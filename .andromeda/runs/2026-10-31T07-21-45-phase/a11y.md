# a11y extract

## Relevance
partial — only the CLI half binds (the `--json` document and the human-mode refusals beside it, tier Standard (1), no WCAG target or conformance claim per a11y-plan §1); the MCP and channel surfaces are not-assertable per a11y-plan §1, and the chunk adds no UI, keyboard, focus or motion surface.

## Constraints
- a11y-plan §8 Error recovery requires the error layout to survive sanitising: a human-mode refusal stays a printed word, plain detail and a final `hint:` on stderr with a typed exit code, and only `unknown` (exit 14) goes without a hint. Fixing a `Display` message or folding `Refusal` into `AgentError` must not cost a human refusal its detail or hint; whether any such message reaches human mode today is research's question.
- a11y-plan §8 Error recovery requires that faults stay outside the refusal form: `error: wrapper fault` and `error: internal error` carry no hint, and a code-only fault body must not be recast as a refusal or gain recovery text.
- a11y-plan §8 Error recovery requires `--json` to give one document with no hint; the closed `error` code and the code-shaped or null `detail` this chunk sets must stay that single document, with no message or recovery field added to carry what was removed.
- a11y-plan §1 A11y surfaces requires no SGR, glyph or cursor control under `--json`, and C0/C1 control characters escaped apart from the `\n` and `\t` exceptions it names; whether every `--json` error path meets this once free text is removed is research's question.
- a11y-plan §8 Plain language requires a kebab-case reason or detail code to sit beside the plain word `unable` in human-mode CLI output, and no stack trace or bare status number as the only error text; `viola mcp` and the wrapper channel are machine-to-machine and sit outside this rule per a11y-plan §1 Not-assertable, so the MCP `refused: <code>` text owes no a11y assertion.
- a11y-plan §8 Plain language requires every fixed CLI string to be pinned by trycmd or a literal, so a copy change this chunk makes on a CLI surface has to fail CI until its pin is updated on purpose.
- a11y-plan §3 CI integration requires any a11y-relevant witness to be an ordinary nextest case in the existing suites, under `gate --require coverage,doctest` on every leg of `ci.yml`'s `test` job, and a11y-plan §10 Standard+ invariants requires the P4 and P6 output-discipline cases to stay green on all three OS legs.

## Patterns to follow
- The per-refusal verification shape of a11y-plan §8 Error recovery: trycmd pins the layout, assert_cmd reads the typed exit code and a hint-free `--json`.
- The server-verify witness that a11y-plan §8 Error recovery names in `tests/security_negatives_server_identity.rs`: over each verb and both modes it reads the hint last, no ESC byte, the exact document, and no output holding the recorded pid, the home's path or the endpoint. It is the plan's nearest model for the chunk's per-surface proof; its macOS gate is the recorded gap, which is owed to "Unix endpoint and home hardening".
- The named fixed-pair literals of a11y-plan §8 Plain language (`INSTANCE_PAIR`, `HOME_PAIR`, `HINT`), for pinning any fixed text the chunk touches instead of matching it loosely.
- The tool split of a11y-plan §3 A11y testing tool pick: assert_cmd, predicates and trycmd for output discipline, with no a11y tool for terminal output.

## Anti-patterns to avoid
- Removing recovery while removing free text: a human-mode CLI refusal other than `unknown` that ends without a `hint:` line (a11y-plan §11 Cognitive).
- Rendering an anyhow chain or stack trace as the only CLI error text, or printing a bare kebab-case code without `unable` in human mode (a11y-plan §11 Cognitive).
- Adding an `a11y` suite value or a separate driver for the chunk's proof, or claiming WCAG conformance from it (a11y-plan §11 CI; a11y-plan §11 Strategy).

## Contract bindings
- a11y ↔ tests: failures of the chunk's CLI witnesses surface only as nextest failures in `suites[].failures[]` of the harness `run` JSON, with no a11y artifact and no a11y rows (a11y-plan §3 CI integration; a11y-plan §3 Structured violation JSON schema).
- a11y ↔ design-system: the fixed human-mode copy and the `unable:` / `hint:` form come from design-system §Surface: cli, so a text change there is design's copy as well as a pinned string (a11y-plan §8 Error recovery; a11y-plan §8 Plain language).
- a11y ↔ exit-cause catalogue: the `viola revive --json` start-refusal document is owed to "Exit-cause code catalogue" (a11y-plan §1 A11y scope) and stays out of this chunk per its boundaries.

## Acceptance criteria contributions
- (a11y) Each CLI refusal whose message or enum the chunk changes still prints, in human mode, `unable <reason> <detail>` (or the one `unable:` line of the named exit-1 forms) with `hint:` as the last stderr line and its typed exit code; `unknown` (exit 14) prints no hint (per a11y-plan §8 Error recovery).
- (a11y) Each CLI `--json` error witness reads exactly one document on the failure it drives, with no hint text and no ESC byte in the output (per a11y-plan §8 Error recovery; a11y-plan §1 A11y surfaces).
- (a11y) A fixed CLI string the chunk changes lands with its trycmd case or literal updated in the same change, and no CLI error path shows a stack trace or a code without `unable` as its only human-mode text (per a11y-plan §8 Plain language).
- (a11y) The chunk's witnesses run as nextest cases inside the existing suites and pass `gate --require coverage,doctest` on the three OS legs, with no new `suite` value (per a11y-plan §3 CI integration).
