relevant — the three surfaces are architecture's own locked error contracts, and the freight's enum fold and `-32602` cause split sit on its [Error Handling] decision and channel schema.

## Constraints
- Enum ownership: per architecture §Established Decisions → [Error Handling] the one-enum-per-crate rule stands, anyhow stays in the root bin, and the plan holds one ratified exception (`PtyError`) and three open divergences (`Refusal`, `ServeError`, `StampsError`). The scope's CARRY calls `Refusal` "the one" divergence; the plan's count is three, so P4 decides whether the chunk closes one or all, each by a fold or a ratification recorded in the plan. A fold stays inside its crate and adds no dependency edge (per architecture §Infrastructure Patterns → Crate dependency direction: `viola-pty` takes no thiserror, and `viola-agent-claude`'s landed `Refusal` sits in its pure surface).
- Channel faults: architecture §Conventions → Error handling schema fixes the fault envelope and the five codes, and §Standard Contracts → Wrapper channel frames plus §Standard Contracts → Channel methods name fixed messages. CONFLICT TO RULE: the scope says `error.data` is "a code or null", but the plan mandates object `data` on `-32602`: `data.supported` + `data.wrapper` (the wrapper's version; §Conventions → Interfaces and versioning) and `data.reason` `release-from-driver` (§Standard Contracts → Channel methods). Either the scope's clause reads "closed fields, no free text", or the plan changes; P4 rules, and it is not settled here.
- CLI documents: architecture §Standard Contracts → CLI `--json` output requires the `v` + `ok` / `refusal` / `error` shapes and their exit codes. CONFLICT TO RULE: it mandates `wrapper-fault`'s `detail` as the JSON-RPC fault's `{code,message,data}` object, so the scope's "code-shaped or null `detail`" holds only if that object's every field is itself fixed or closed. A `run` start refusal after a passed preflight prints no document, owed to "Exit-cause code catalogue" (same section), so the chunk's enumeration names that gap as out and does not fill it.
- MCP results: architecture §Conventions → MCP (detail `.andromeda/architecture-detail/conventions.md`, conv-mcp-results) fixes the `isError` shapes, the `refused: <code>` text, the closed `invalid-params` field words and `-32603` `internal error` / `data: null`. It also reserves `-32602` for an unknown tool name: whether that rmcp-built error echoes the caller's tool name is research's question, since an echo would be caller text on an error surface. `wrapper-fault` carries the same object as the CLI's, so the ruling above binds both.
- Closed detail sets: architecture §Conventions → Error handling schema (`RefusalReason`; detail conv-refusal-reason) requires each `detail` from a closed set per reason, extended only in `viola-core`. The same section sets `unknown`'s detail to any value and has readers treat an unrecognised detail as opaque text, so a relayed newer-wrapper refusal is a route for free text onto the CLI and MCP surfaces. Whether the relay passes it through unchecked is research's question.
- Content confinement: architecture §Established Decisions → [Error Handling] (detail dec-error-handling) requires the anyhow chain to reach only `detail-<role>.ndjson`, never a role line, stdout or stderr, and §Cross-cutting Patterns → Diagnostic output channels confines content-bearing detail to that file. §Occupied Resources → Environment variables requires the R8 strip, its registry reader and the logs to handle names only, never a value. §Standard Contracts → Instance snapshot keeps `cwd` off every error body. Whether every `Display` reaching a surface already satisfies this is research's question.
- Contract versioning: architecture §Conventions → Interfaces and versioning makes an added field additive and a removed or re-meant field a `v` bump, so narrowing a live `message` or `data` is read against that rule first. The same rule governs the CARRY's new cause on the `channel-response` line. §Cross-cutting Patterns → Mixed-version tolerance still requires a `-32602` naming the wrapper's version for a too-new request, which any `data` ruling has to keep or amend explicitly.

## Patterns to follow
- A single codes-only writer for refusal documents, `client::refused_document`, holding no path, pid or id (per architecture §Standard Contracts → CLI `--json` output); new CLI error documents route through one such writer, not per-verb formatting.
- The contract-binary shape for the enumeration: a table of named boundaries each naming its witness, a source census that goes red on an unnamed one, and a self-check over a planted hit (per architecture §Cross-cutting Patterns → Bounded readers, detail crosscut-bounded-readers, `tests/contract_bounded_readers.rs`).
- Fixed-message error types, the precedents being `PtyError`, `McpError::Internal` and `ServeError` / `StampsError`, with an upstream cause kept only as a boxed source, never in `Display` (per architecture §Established Decisions → [Error Handling]).
- The single catch site: exactly `error: internal error` once from `main`, the chain sent to the post-mortem detail file by `viola::obs::report_internal_error` (per architecture §Conventions → CLI exit codes, detail conv-exit-codes; §Established Decisions → [Error Handling]).
- Naming the code and never the content, as the fixture recorder's refusal does with its file and check code (per architecture §Occupied Resources → Repository, `fixtures/claude/<cli-version>/`).

## Anti-patterns to avoid
- Closing the sets at the reader: `deny_unknown_fields` on own formats is a rejected decision and an unknown kind, field or detail is skipped or opaque, never an error, so sanitising binds what viola writes and leaves readers tolerant (per architecture §Established Decisions → [Validation]; §Conventions → Error handling schema).
- A second anyhow surface: no anyhow in a member crate, and no chain or serde source text in a role line, stdout, stderr or `--json` body (per architecture §Established Decisions → [Error Handling]).
- Moving an exit code or adding a `RefusalReason` to make a failure nameable: the exit table and refusal set are locked and the catalogue is another entry's (per architecture §Conventions → CLI exit codes; §Conventions → Error handling schema).
