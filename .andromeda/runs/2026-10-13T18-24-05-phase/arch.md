# arch extract

## Relevance
relevant — the chunk is the root `viola` bin's `verify` stop path plus two literal moves onto `viola-agent-claude`'s constants, and architecture §Occupied Resources names this entry as the owner of the `--settings` move.

## Constraints
- Workspace placement: `verify` is the root `viola` bin's dispatch (`src/cmd/verify.rs`, `src/cmd/verify/typed.rs`), and Claude-specific shapes (the program name `claude`, the flag `--settings`) belong only in `viola-agent-claude`. The root bin's two literals therefore move onto that crate's constants: `viola_agent_claude::statusline::SETTINGS_FLAG`, which `run` already uses, and `viola_agent_claude::PROGRAM`, which a revived start uses. Each argv must stay byte-identical. Whether the constants are visible and hold the same bytes is research's question (per architecture §Occupied Resources → Claude Code integration names; per architecture §Inherited Defaults, Agent isolation).
- Any OS-specific handler the stop needs (Unix SIGINT/SIGTERM, Windows console control events) must go through the existing manifest edges. The root bin's `libc` is declared Unix-only for `backtrace` + `dladdr`. Its `windows-sys` is declared for the R8 registry reader, `Win32_System_Diagnostics_Debug` and `Win32_System_LibraryLoader`, and `Win32_System_Console` is declared only on `viola-pty`. A handler in the root bin therefore widens a declared edge and is amended at wrap. A handler in `viola-pty` must stay agent-agnostic. Whether the root's `windows-sys` dependency already enables the needed feature is research's question (per architecture §Infrastructure Patterns → Crate dependency direction).
- Cross-platform from the first commit: no design choice may depend on POSIX-only behaviour. The stop path needs a Windows branch beside the Unix one, and every OS-specific branch must compile and be tested on its own CI runner (per architecture §Design Philosophy, Cross-platform from the first commit; per architecture §Cross-cutting Patterns, Cross-platform discipline).
- Tokio containment: `verify` is a sync CLI verb on std threads and blocking I/O. Only `viola-mcp` / `viola-ui` may build a runtime (per architecture §Cross-cutting Patterns, Tokio containment; per architecture §Established Decisions [Concurrency / Backend Framework]).
- An interrupted `verify` exits with a code from the defined set (`0, 1, 2, 10–14, 20, 21`). §Conventions defines no code for an interrupted verify. Exit 1 covers verify's failing row and its refusals, and the `cli` role's internal error prints `error: internal error` only from the `main` catch site. A new code such as 130 would be a master amendment and a P4 fork, never a silent addition (per architecture §Conventions, CLI exit codes; per architecture §Occupied Resources → Binary, subcommands and exit codes).
- Three dir sets are each held by a drop guard and "removed on every exit path": the probe dir `ledger/probes/<pid>/`, the interactive probe dirs (Run A's OS-temp `viola-verify-*` from `tempfile`, and `<cwd>/.viola-verify-<pid>/`, `-dialogs/`, `-plan/`), and the `.gitignore` line `/.viola-verify-*/` covering a leftover. This chunk makes Ctrl-C/TERM real exit paths. The wording that admits a SIGKILL or crash leftover is a wrap amendment (per architecture §Occupied Resources → Filesystem).
- `verify`'s transient children must all be gone when verify ends. The children are the print-mode probe plus Runs A–D. No run writes a byte into a CLI dialog, and a modal start is killed with no key. Stamps go through the one writer, and a failing row still writes its stamp. The plan says nothing about whether an interrupted run writes a stamp, so the scope's expectation of none is not arch coverage (per architecture §Established Decisions [Plugin Scope]; per architecture §Established Decisions [CLI Version Compatibility]).

## Patterns to follow
- Dir ownership by drop guard: `ProbeDir`, `TrustedDir` and the `tempfile` guard each own one dir. The stop path should let the guards that hold this run's paths do the removal, never a listing (per architecture §Occupied Resources → Filesystem).
- End the child through the PTY seam (spawn · read · write · resize · wait · kill), with child exit detected on the process handle. On Windows, dropping the ConPTY input writer makes conhost send `CTRL_CLOSE` to the child (exit `0xC000013A`), so the order of child end, reap and guard drop matters (per architecture §Established Decisions [PTY]).
- OS console/tty handling already sits behind `viola-pty`'s `HostTerminal` (`windows-sys` `Win32_System_Console`, `libc` on Unix), with restore-on-Drop. That is the existing precedent for OS-specific signal and console code behind a seam (per architecture §Stack and Technologies, PTY layer).
- Agent-crate constants as the one home of a CLI literal, as `run` does with `SETTINGS_FLAG` and `resume_args` does with its two flags (per architecture §Occupied Resources → Claude Code integration names).

## Anti-patterns to avoid
- Adding a crate such as `ctrlc` or `signal-hook`, or any edge the manifests do not declare, to carry the handler. New edges are a P4 fork only if the existing graph cannot carry it (per architecture §Infrastructure Patterns → Crate dependency direction).
- `tokio::signal` or any async runtime in `verify` (per architecture §Cross-cutting Patterns, Tokio containment).
- Shelling out (`kill`, `taskkill`, `sh -c`) to end a child: children are spawned and ended directly, and `hook statusline` is the only shell-out (per architecture §Cross-cutting Patterns, Cross-platform discipline).

## Contract bindings
- The arch rule that the dirs are "removed on every exit path" (architecture §Occupied Resources → Filesystem) is the same rule as security-plan §Data Protection and security.md's verify-children rule (no key into any dialog, dirs removed on every exit path). The entry names both masters, and any wording change is one wrap amendment across them.
- The arch exit-code set (architecture §Conventions, CLI exit codes) binds to the obs event catalog: the `cli` role's process-log line for an interrupted verify is read there at P2 and not invented.
- The arch rule that CI runs `verify` against the fake agent's print and interactive modes, with the real CLI local only (architecture §Established Decisions [CLI Version Compatibility]; [CI/CD]), binds to the test-plan harness: the stop is proven against the fake agent on all three CI OSes, with no live `claude` start.
- Arch's crate dependency direction (architecture §Infrastructure Patterns → Crate dependency direction) binds to security's `cargo deny` bans (no C-building crate, no new source).

## Acceptance criteria contributions
- No `"--settings"` literal remains in `src/cmd/verify/typed.rs` and no `"claude"` program literal in `src/cmd/verify.rs`. Runs C/D use `viola_agent_claude::statusline::SETTINGS_FLAG`, and verify's default program uses `viola_agent_claude::PROGRAM` if P4 confirms the lean. Every built argv is byte-identical to before (per architecture §Occupied Resources → Claude Code integration names).
- `Cargo.lock` gains no package. Any `windows-sys` feature or `libc` use the handler adds is recorded as a crate-dependency-direction amendment (per architecture §Infrastructure Patterns → Crate dependency direction).
- A `verify` stopped by Ctrl-C or TERM under the fake agent exits with a code in `0, 1, 2, 10–14, 20, 21`. When it returns, none of that run's dirs remain (`ledger/probes/<pid>/`, `<cwd>/.viola-verify-<pid>{,-dialogs,-plan}/`, its Run A temp dir), and no probe child is left running (per architecture §Occupied Resources → Filesystem; per architecture §Conventions, CLI exit codes).
- The Unix and Windows stop branches each compile and are exercised on their own CI runner (per architecture §Cross-cutting Patterns, Cross-platform discipline).
