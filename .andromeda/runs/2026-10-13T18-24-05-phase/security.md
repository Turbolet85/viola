# security extract

## Relevance
relevant — security-plan §Data Protection (Code-bearing artefacts; Probe captures; Interactive probe dirs) names this entry and states the removal-on-every-exit-path mandate the chunk extends to Ctrl-C / TERM; §Threat Model Summary (Attack surface: Child process spawning and PATH resolution) governs how verify's PTY children may be ended.

## Constraints
- security-plan §Data Protection (At rest, Interactive probe dirs) requires Run A's OS-temp `viola-verify-*` dir and Runs B/C/D's `<cwd>/.viola-verify-<pid>[-dialogs|-plan]/` dirs to be removed on every exit path, passing or failing, each by its own drop guard; an interrupted run (SIGINT/SIGTERM, the Windows console control events P2 settles) is an exit path under that mandate. Whether the guards' `Drop` actually runs on today's stop paths is research's question (the scope's CARRY says no signal is handled).
- security-plan §Data Protection (At rest, Probe captures) requires the content-bearing `ledger/probes/<pid>/` tree (0700 dir, 0600 captures) to be removed whole by a drop guard on every exit path of `verify`, with only a scrubbed `--record` copy leaving it; the interrupt path owes the same removal, and no partial `--record` fixture may be written from an interrupted run without passing the full scrub of §Data Protection (Repository fixtures).
- security-plan §Threat Model Summary (Attack surface: Child process spawning and PATH resolution) requires that no verify run writes a byte into any dialog (CLI-native or the probe's own) and that a modal is ended by a kill with no key; the stop path therefore ends the PTY child without typing into a dialog. Whether Run B's existing Ctrl-C / Ctrl-C / kill ending may be reused on an interrupt while a modal could be on screen is research's question, and a departure is a P4 fork.
- security-plan §Threat Model Summary (Attack surface: Child process spawning and PATH resolution) requires verify's children to stay direct spawns (never through a shell) under the R8 strip, output capped at `MAX_FRAME` into a `Screen` fed under `catch_unwind`; the `claude` → `viola_agent_claude::PROGRAM` and `--settings` → `statusline::SETTINGS_FLAG` moves must leave each run's argv byte-identical.
- security-plan §Data Protection (At rest, Code-bearing artefacts) names `src/cmd/verify/typed.rs`'s two `--settings` literals as owed to this entry, to move onto the agent crate's `statusline::SETTINGS_FLAG`; the same section requires `ledger/stamps.json` to be written only by `viola verify`, under its `.lock`, at 0600.
- security-plan §Authentication & Authorization (`~/.viola/` access control) requires every replaced file under the home to go through `viola_state::fs::replace_private` (mode set on the temp file before any byte, then `persist`), so an interrupt landing during the stamps write leaves the old or the new `stamps.json` whole, never torn; whether an interrupted run writes any stamp at all is P2's read of the architecture conventions (the scope expects none).
- security-plan §Dependency Security (deny.toml additions; Pinning) requires any dependency the signal handler needs to pass `cargo deny check` (the arch C-build ban and the `deny-sync.toml` tokio ban included) and to be pinned in `[workspace.dependencies]`; a new crate (e.g. `ctrlc`, `signal-hook`) or a new `windows-sys` feature is a graph change the gates must read green.

## Patterns to follow
- Removal by the run's own creation record, never by a listing: the drop-guard-per-dir model of §Data Protection (Interactive probe dirs; Probe captures), mirrored by §Security Anti-Patterns (Code Patterns)'s test-side removal rule (only a dir the test side itself created, by its own `TempDir` / `owner.json` record).
- Owner-only creation: 0700 dirs / 0600 files set explicitly, never the umask (§Security Anti-Patterns, Data Protection), unchanged for any dir a newly built guard owns.
- Fixed-message refusals and exits: `Display` impls with fixed messages and no path or payload fields (§Error Handling, External responses), as the `--record` refusal names a file and a closed code, never content (§Data Protection, Repository fixtures).
- Windows process start order: `restrict_dll_search()` is the second statement of `main` in every role (§Security Anti-Patterns, Universal); a console control handler is registered after it, never ahead of any DLL load.

## Anti-patterns to avoid
- Removing by pattern: no glob of `viola-verify-*`, no `<pid>` scan, no removal of an older run's, another process's or a kill/crash leftover — the analogue of §Security Anti-Patterns (Code Patterns)'s bans on a wipe outside the one guarded scratch and on a test-side removal of a dir not its own.
- Typing into the child on the stop path: no byte into a dialog or modal (§Threat Model Summary, Attack surface: Child process spawning and PATH resolution).
- Leaking state on the interrupt message or line: no absolute path (the probe dirs, the home, the cwd), no pid-bearing path, no screen row or upstream text on stdout, stderr, `--json` or a log line (§Error Handling, External responses; §Security Anti-Patterns, Logging).

## Contract bindings
- security ↔ obs: the interrupted-run `obs_event!` line (obs-plan event catalog, read at P2) stays under the NEVER-log floor (security-plan §Bootstrap phases, `logging-redaction-wire`) and names no path or screen text (§Security Anti-Patterns, Logging).
- security ↔ arch: the interrupted run's exit status comes from architecture §Conventions (exit codes); the flags passed to the child are architecture §Occupied Resources, which with security-plan §Data Protection names this entry.
- security ↔ tests: the stop is proven against the fake agent or a test-owned child, never a live `claude` start (scope boundary); verify runs in CI only against the fake agent (security-plan §Threat Model Summary, Infrastructure: CI/CD).
- security ↔ masters (wrap): §Data Protection (Interactive probe dirs; Probe captures) says "every exit path"; stating SIGKILL / a crash as the exception is a wrap amendment, never a phase edit.

## Acceptance criteria contributions
- A verify run stopped by SIGINT and by SIGTERM (Unix; Windows events as P2 settles) leaves none of the dirs that run created — Run A's temp dir, its `<cwd>/.viola-verify-<pid>[-dialogs|-plan]/` dirs and `ledger/probes/<pid>/` — while a pre-planted foreign `.viola-verify-<otherpid>*` dir and a pre-planted `viola-verify-*` temp dir survive untouched (per security-plan §Data Protection, Interactive probe dirs / Probe captures).
- On the stop path no byte is written to the child's PTY while a dialog or modal is on screen; the child is ended and reaped before its dirs are removed (per security-plan §Threat Model Summary, Attack surface: Child process spawning and PATH resolution).
- Each verify run's argv is byte-identical before and after the `PROGRAM` / `SETTINGS_FLAG` moves, and no `"--settings"` or default-program `"claude"` literal remains in `src/cmd/verify.rs` / `src/cmd/verify/typed.rs` outside test modules (per security-plan §Data Protection, Code-bearing artefacts).
- `cargo deny check` and `bash scripts/deny-probes.sh` pass with whatever the handler adds to the graph, and no new dependency enters outside `[workspace.dependencies]` pins (per security-plan §Dependency Security, deny.toml additions / Pinning).
