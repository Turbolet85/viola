# a11y extract

## Relevance
Partial. This chunk adds no UI surface, so no WCAG success criterion applies. The overlap is limited to the `ci.yml` workflow hygiene that the future a11y CI steps will have to pass, and to where the zizmor step sits in the ubuntu leg.

## Constraints
- Every a11y-added CI action must pass this chunk's zizmor / least-privilege gate. a11y-plan §3 "CI integration" and §9 "Artifact retention" require the `e2e-web/test-results/` upload to use `actions/upload-artifact` v7.0.1, SHA-pinned per zizmor. So the full-SHA pinning (with a version comment), `permissions: {}`, per-job `contents: read` and `persist-credentials: false` policy set here must be the same policy that step is written against later.
- a11y-plan §12 D-A11Y-14 places the a11y lint stage (eslint-plugin-lit-a11y 5.1.1, html-validate 11.16.0) on the ubuntu leg of `ci.yml`, before `run --browser`, "like clippy/zizmor". The zizmor step this chunk adds must therefore leave room for a later lint stage on the same leg, before `run --browser`, without reordering or merging jobs.
- a11y-plan §9 "Pipeline integration" requires the web a11y gate to stay ubuntu-only, inside the single `ci.yml` workflow with its `[windows-2025, macos-latest, ubuntu-latest]` matrix. If this chunk splits workflows or tightens jobs (for example a separate scheduled workflow for the weekly advisory run), it must not move or fork the E2E/a11y leg out of `ci.yml`.
- a11y-plan §3 "Bootstrap phases" → a11y-ci-gate-wire requires the post-gate aggregation step and the artifact upload to run with `if: always()`. Any job-level permission or condition this chunk sets on the ubuntu leg must not stop later `if: always()` steps from running. Whether `ci.yml` already has an upload step is research's question.
- a11y-plan §9 "CI-specific resource attributes" needs `GITHUB_RUN_ID` / `GITHUB_SHA` on the a11y violation rows. The chunk's rule that event-payload values reach steps only through `env:` is compatible with this and should be kept as the pattern for passing them. These are context values, not event payload, so zizmor template-injection should not flag them.

## Patterns to follow
- Pin actions by full commit SHA with a version comment. a11y-plan §3 "CI integration" already names `actions/upload-artifact` v7.0.1 under this rule, so use the same format in every workflow this chunk adds or edits.
- Use one workflow for the PR pipeline, `ci.yml` (a11y-plan §9). Add new gates as steps on the right leg, not as new `suite` values or separate drivers.

## Anti-patterns to avoid
- Never add a separate a11y driver, `suite` value or `npm test:a11y` outside `scripts/agent-run.* run --browser` (a11y-plan §11 "CI"). This applies if the chunk exposes its dependency-policy gate through `scripts/agent-run.{sh,ps1}`: that must not change the `run --browser` / `gate --require playwright` contract.
- Never skip a11y when CI fails, because it is a fail-fast gate (a11y-plan §11 "CI"). Permission or job-condition changes must not add `continue-on-error` or skip paths that later a11y steps would inherit.

## Contract bindings
- a11y CI gate ↔ tests §9 / CI pipeline structure: the a11y lint, E2E, aggregation and upload steps share the ubuntu leg of `ci.yml` with this chunk's zizmor and `cargo deny` steps (a11y-plan §9; §12 D-A11Y-14).
- a11y upload-artifact pinning ↔ security-plan §Dependencies (pinning) via zizmor (a11y-plan §3 "CI integration").
- Scope note: the a11y npm devDependencies (`@axe-core/playwright` 4.13.0, colorjs.io, tabbable, virtual-screen-reader, html-validate, eslint-plugin-lit-a11y) are npm packages, pinned through the lockfile (a11y-plan §3 "Bootstrap phases" → a11y-tooling-install). They fall outside `deny.toml` / cargo-deny, so this chunk's supply-chain policy does not cover them and a11y claims no cargo-deny entry.

## Acceptance criteria contributions
- zizmor over `.github/workflows/` finds no unpinned `uses:` and no `excessive-permissions` in any workflow this chunk touches. This is the same rule the later a11y `actions/upload-artifact` v7.0.1 step must pass (per a11y-plan §3 "CI integration").
- `ci.yml` stays the single PR workflow and its ubuntu leg stays in place, so the later a11y lint stage (D-A11Y-14) can sit between the zizmor/clippy-style static steps and `run --browser` (per a11y-plan §9).
