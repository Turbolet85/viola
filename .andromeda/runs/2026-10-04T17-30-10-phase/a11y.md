# a11y extract

## Relevance
partial: the chunk is the tui boundary and cli half of a11y-plan §4 P4 ("Human takes the wheel"). The web-spa half (the WHEEL `cell`, `a11y-p4`, axe in the WHEEL `human` state) is Epoch 8 and outside this scope.

## Constraints
- a11y-plan §4 P4 (tui) requires three portable-pty outer-PTY nextest cases on all three OS legs, one per §1 tui boundary clause: (1) zero viola-originated bytes on the outer-PTY stream, (2) human keystrokes delivered unblocked past the current atomic paste, (3) `\x1b[I` / `\x1b[O`, mouse and resize sequences do not move the wheel. This chunk is the first in which clause (3) can be asserted at all, because the wheel could not move before it. Research has to answer whether cases (1) and (2) already exist at HEAD from earlier chunks, and in what shape.
- a11y-plan §4 Path 4 "Required focus order" (tui) and §5 Keyboard Navigation (tui) require that human keystrokes are never blocked or delayed past the atomic paste, and that focus, mouse and resize sequences are ignored for wheel purposes. Ignoring a sequence for the wheel does not mean swallowing it. The bytes still reach the child, which matches scope §2.
- a11y-plan §3 Keyboard test harness → Tooling requires the outer PTY to inject human keystrokes during a driver `send`. It also requires the zero-viola-bytes check to cover start, a driver `send`, a refused automation send (`human-typing`) and exit. On every leg none of viola's own literals may appear (diagnostics, refusal text, `hint:`). On Linux and macOS the stream must match an unwrapped fake-agent run byte for byte. On Windows the check is literal absence, run on both backends: the sideload default, and the inbox fallback through `conpty_sideload`'s tampered-companion case.
- a11y-plan §1 Surface tui, Notes: `run` diagnostics go to `diagnostics/` and never to the terminal. A wheel move, a `human-typing` / `manual-pause` refusal and a `hook.dialog` `null` answer under a human wheel must therefore emit zero bytes onto `viola run`'s terminal.
- a11y-plan §4 P4 (cli) and §8 Error recovery require that `send` refused `human-typing` prints `unable  <reason>  <detail>` on stderr, ends with a `hint:` line and returns a typed exit code (10). `--json` gives one document with no hint, and trycmd pins the layout for each refusal. The same requirements apply to the new `manual-pause` detail and to `answer`'s `human-typing` slot.
- a11y-plan §8 Plain language requires every kebab-case code (`human-typing`, `manual-pause`) to sit beside the plain word `unable`. Both are fixed copy, pinned by trycmd.
- a11y-plan §1 Surface cli, Notes, requires static, linear output with no SGR under non-TTY, `NO_COLOR`, `TERM=dumb`, `--json` or `viola run`. The new `pause` / `release` verbs fall under this. The cli structural equivalents list the `--help` group label `wheel`, which is where `pause` / `release` belong.

## Patterns to follow
- tui boundary cases run on the tests' portable-pty `=0.8.1` outer-PTY driver with `viola-fake-agent` as the child, reported through the harness `run` JSON nextest suites (per a11y-plan §3 Keyboard test harness → Tooling; §9 Unit / integration row).
- Linux/macOS evidence is a byte-for-byte comparison against an unwrapped fake-agent run under the same outer PTY. Windows evidence is the absence of viola's literals, because the ConPTY host emits its own preamble (per a11y-plan §3 Keyboard test harness → Tooling).
- CLI refusals: trycmd pins `unable <reason> <detail>` + final `hint:`, and assert_cmd checks the typed exit codes (`10`–`14`, `20`, `21`) on all three OS legs (per a11y-plan §8 Error recovery → Verification).
- These results stand in as output discipline for SC 2.1.1 / 1.3.1 / 1.4.1 on tui/cli and are not a11y-tool evidence (per a11y-plan §4 P4 SCs; §11 Strategy).

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste, and never count focus / mouse / resize sequences as editing (per a11y-plan §11 Keyboard, last bullet).
- NEVER parse the rendered `claude` TUI screen for content (R7). The wheel classifier reads stdin byte provenance only and never the vt100 screen (per a11y-plan §11 Universal).
- NEVER colour CLI `unable`, and never emit SGR under `viola run`, non-TTY, `NO_COLOR`, `TERM=dumb` or `--json`. Never claim WCAG conformance for cli/tui (per a11y-plan §11 Visual; §11 Strategy).

## Contract bindings
- a11y ↔ tests: the three P4 tui cases and the `human-typing` exit-10 assertions are nextest rows in the harness `run` JSON (`nextest-integration` / `nextest-e2e`). They produce no a11y rows and no `@sc-*` tag (per a11y-plan §9 Unit / integration row). The scope's §10 negative in `cli_controls_not_disableable` (exit 10) covers the same code.
- a11y ↔ design (cli copy): a11y-plan §8 / §11 Cognitive require a `hint:` line on every human-mode refusal except `unknown`. CLAUDE.md Session Learnings forbid any driver-facing hint that suggests `viola release`. The `human-typing` / `manual-pause` hint copy has to meet both, so P4 owns the exact text and design's cli copy owns where it is pinned.
- a11y ↔ CARRY §9 (ConPTY focus reports): a11y-plan §3 Keyboard test harness → Tooling records that both ConPTY hosts emit `ESC[?1004h` (focus-reporting enable) on spawn. Whether injected `\x1b[I` / `\x1b[O` reach the child through ConPTY is still the unmeasured hypothesis. Case (3) on windows-2025 must measure it, not presume it. If ConPTY swallows the sequences, "no wheel move" holds trivially on that leg and passthrough goes unwitnessed. That outcome is a recorded finding, not a pass by construction.
- a11y ↔ obs: the `wheel` event line and the `send-refused` `wheel` field are obs-plan's. a11y adds no field and writes no violation row to `diagnostics/` (per a11y-plan §11 Universal).

## Acceptance criteria contributions
- (a11y) Outer-PTY case (3), on all three OS legs, injects `\x1b[I`, `\x1b[O`, a mouse report and a resize while the wheel is `driver`. Pass: no `wheel` event is appended, the snapshot `wheel` stays `driver`, and the fake agent receives the focus and mouse bytes unchanged (per a11y-plan §4 P4 tui; §3 Keyboard test harness → Tooling).
- (a11y) Outer-PTY case (2) injects human keystrokes during a driver `send`. Pass: the bytes reach the child right after the paste's closing write, none are lost or reordered, and the wheel moves to `human` (per a11y-plan §4 P4 tui; §5 Keyboard Navigation tui).
- (a11y) Outer-PTY case (1) covers start, a driver `send`, a refused `human-typing` send and exit. Pass: zero viola literals (refusal text, `hint:`, diagnostics) on every leg, and a byte-for-byte match with the unwrapped run on Linux/macOS (per a11y-plan §3 Keyboard test harness → Tooling).
- (a11y) `viola send` under a human wheel, with cause `human-input` and with cause `manual-pause`: exit 10; stderr `unable  human-typing  <detail>` with a final `hint:` that does not name `viola release`; no SGR under non-TTY; `--json` carries no hint. Pinned by trycmd and checked by assert_cmd on all three legs (per a11y-plan §4 P4 cli; §8 Error recovery).
