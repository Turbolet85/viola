# security extract

## Relevance
relevant — the chunk brings two channel methods (`pause`, `release`) into service and two CLI verbs that write frames. It also adds the `release-from-driver` guard and puts wheel refusals ahead of automated input, all on the local IPC trust boundary (per security-plan §Threat Model Summary, Local IPC vector).

## Constraints
- A `release` whose `params` carry `from` must be refused `-32602` with `data: {"reason":"release-from-driver"}`, and the CLI must then exit 20. `release` params are `{budget?}` only. `pause` (and `link`/`unlink`) from drivers stay allowed. This guard is an affordance, not enforcement, and must not be described as enforcement (per security-plan §Authentication & Authorization, "Driver-originated `release`" row). Amendment 4 is owed "before the `viola` bin channel dispatch" (per security-plan §Bootstrap phases, auth-scaffolding-baseline). Whether `crates/viola-core/src/obs.rs`'s existing `ReleaseFromDriver` already covers the wire refusal is research's question.
- The channel `from` param is self-reported. It may serve only link records and the `release` affordance guard, and never as an authenticated identity: no wheel decision may key on `from` (per security-plan §Security Anti-Patterns → Authentication).
- The wheel holder, like `behavior`, `dialog_id` and the dialog kind, must be a closed enum or integer, never a free `String`, even under tolerant parsing. This covers the snapshot `wheel`, the `wheel` event and the `{wheel:<holder>}` results of `pause` / `release` (per security-plan §Security Anti-Patterns → Input).
- No security refusal may block the human. Refusals (`human-typing`, `manual-pause`, `release-from-driver`) go only to automation (`send` / `answer` / a driver's `release`), and hooks fail open. A `null` `hook.dialog` answer while the wheel is human is the fail-open direction (per security-plan §Security Anti-Patterns → Universal). A non-`null` decision still requires the strict-read verify stamp, and the human wheel never widens that (per security-plan §Security Anti-Patterns → Universal, the two `hook.dialog` stamp bullets).
- No channel frame may be written before server verification (pid / euid + sysinfo start time against a strict-modes-passed `snapshot.json`). The six dated exceptions name `hook.event`, `send`, `wait` / `last`, `answer` and `hook.dialog` only, and "no other frame or process may borrow any of them" (per security-plan §Security Anti-Patterns → Authentication; §Authentication & Authorization, "IPC client-side server verification" row). CLI `viola pause` / `viola release` are in none of the six gaps. Either they land full verification, or a seventh dated gap is ruled and recorded before they ship. Which one is P4's to surface to the founder, never a silent borrow. Separately, no new channel method may be served without a Security Decisions Log entry mapping it to the IPC controls (per security-plan §Security Anti-Patterns → Universal). `pause` / `release` appear in the Threat Model's method list, but the Decisions Log names neither. Whether that list counts as the mapping is P4's question.
- The `pause` / `release` frames take the channel controls: `Read::take(MAX_FRAME)` framing, default serde depth, the `v` check (`-32602`), and closed params (per security-plan §Input Validation, "Channel frames" row). The row does not yet type `pause` `{}` / `release` `{budget?:bool}`, so their param-validation clause is owed in the plan. A CLI `<name>` argument goes through `parse_viola_name` → `ViolaName::try_new` (per security-plan §Input Validation, "CLI arguments / stdin" row).
- External errors from `pause` / `release` / the wheel refusals use fixed codes and messages only: no absolute path, no upstream text, no anyhow chain with a serde source, and `-32603` exactly `"internal error"` / `data: null` (per security-plan §Error Handling). Human keystroke bytes seen by the editing-key classifier are user content. They may reach only `instances/<name>/diagnostics/`, never a log line, an event, `send-refused` or stderr (per security-plan §Bootstrap phases, logging-redaction-wire).

## Patterns to follow
- The dated-gap pattern: a frame that skips server verification gets a founder ruling, a Decisions Log entry and named Epoch 6 owners (`:109` / `:111`), and it is mirrored in the "CLI arguments / stdin" and "IPC client-side server verification" rows (per security-plan §Authentication & Authorization; §Input Validation).
- Wrapper-side re-validation: client checks are advisory, and the wrapper re-runs closed-enum deserialisation on every method's params (per security-plan §Security Anti-Patterns → Input, first bullet).
- Fail open to the human: `hook.dialog` gets `null` at once under a human wheel or a wheel move, and the dialog renders for the human (per security-plan §Error Handling, the internal-logging `hook` bullet; §Security Anti-Patterns → Universal).
- Harness-turn classification uses only the four compiled `HARNESS_PREFIXES` literals on the prompt's raw start, no trim. The founder-ratified side effect (a typed escaped cross-session tag is filed `harness`) stands (per security-plan §Security Anti-Patterns → Code Patterns).

## Anti-patterns to avoid
- Silently routing CLI `pause` / `release` through the existing liveness-only pre-check by borrowing the `send` / `wait` / `last` / `answer` gap (per security-plan §Security Anti-Patterns → Authentication).
- Blocking, refusing, delaying or swallowing a human byte: focus, mouse and resize bytes and bytes held during a paste must still reach the child. Refusing the human instead of automation is the same mistake (per security-plan §Security Anti-Patterns → Universal).
- Exposing `release` or `pause` as an MCP tool or driver-facing hint. Their absence from MCP is an affordance (per security-plan §Threat Model Summary, MCP vector), and adding a `config.json` key, `VIOLA_*` env var or CLI flag that disables a wheel refusal is banned (per security-plan §Security Anti-Patterns → Universal, last bullet).

## Contract bindings
- security ↔ architecture §Standard Contracts: the `release` params `{budget?}`, the `-32602` `release-from-driver` data shape and CLI exit 20 must match the arch channel table (`pause` `{}` → `{wheel}`, `release` → `{wheel, budget_paused}`).
- security ↔ tests (test-plan §5 CLI): `tests/cli_controls_not_disableable.rs` gains the human-wheel negative (exit 10), and the `release-from-driver` refusal needs a CLI/channel test.
- security ↔ obs (obs-plan §4 CL-1): the `wheel` event and the `send-refused` lines' `wheel` field carry holder/cause codes only, under the NEVER-log floor (no keystroke bytes).
- security ↔ a11y (a11y-plan §3 tui): focus, mouse and resize bytes never move the wheel and still pass through unchanged. This is the same "human always wins" floor.

## Acceptance criteria contributions
- A channel `release` frame whose params carry `from` gets `-32602` with `data.reason == "release-from-driver"`, and CLI `viola release` maps it to exit 20. A `pause` carrying `from` is accepted (per security-plan §Authentication & Authorization, "Driver-originated `release`" row).
- While the wheel is `human`, automated `send` and `answer` are refused (`human-typing`, detail `manual-pause` after `viola pause`). Human stdin bytes in the same window still reach the child unchanged and undelayed past the current atomic paste (per security-plan §Security Anti-Patterns → Universal).
- grep finds no `String`-typed wheel holder or cause in the snapshot, event or channel result types: they deserialise into closed enums (per security-plan §Security Anti-Patterns → Input).
- Before CLI `pause` / `release` ship, there is either full server verification on their frames or a recorded Security Decisions Log dated-gap entry naming them. The `pause` / `release` param-validation clause is added to the "Channel frames" row (per security-plan §Security Anti-Patterns → Authentication / → Universal; §Input Validation).
