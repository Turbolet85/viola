## Relevance
relevant — the chunk lands obs-plan §4's must-trace path "Human takes the wheel, automation is refused, `release` returns it", the `wheel` field owed on wrapper `send-refused` (CARRY §11), and the `release-from-driver` event (D-01).

## Constraints
- obs-plan §4 Scenario "Human takes the wheel…" requires a point-in-time `run.wheel_transition` (INTERNAL) span with exactly `wheel_from`, `wheel_to` (`human|driver`) and `cause`, and never the typed keys. The `wheel` product event in `events.ndjson` is the audit record. No process-log line duplicates it, and the plan names no `wheel-*` value in the closed `event` enum.
- obs-plan §4 Scenario "Human takes the wheel…" plus §6 additive catalog (`send-*` row) require the wrapper `send-refused{refusal:"human-typing", detail:null|"manual-pause", wheel:"human", side:"wrapper"}` with client `process-exit{exit_code:10}`. The obs-plan-amendments entry "2026-10-04-confirmed-send-with-cl-1-records — feed overflow…" (**Kept**) keeps the `wheel` field required on every wrapper `send-refused`, and says it ships without it only until this entry. So the `turn-running` / `input-not-ready` / `no-prompt-submitted` refusals owe `wheel` too.
- obs-plan §3 Log format JSON schema (the `send-*` corr rule, D-28 / D-30) requires that a `human-typing` refusal, which comes before `send-issued`, carries `corr` = the target's `events.ndjson` end offset at refusal time, a log join key never returned to the caller, plus `conn` and `rpc_id` on the wrapper side.
- obs-plan §3 Log format JSON schema (accepted `event` values, D-01) and §6 catalog row `release-from-driver` require a `release` carrying `from` to log its own `release-from-driver{corr:<JSON-RPC id>, conn, from, from_trust}` event, never a generic `-32602` wrapper fault (§4 Scenario "Human takes the wheel…"). It is logged at `warn`, since `channel-response` carries `-32602` (§6 Log levels mapping). The `human-typing` / `manual-pause` refusals are product outcomes at `info`.
- obs-plan §4 Instrumentation per surface (cli short-lived row) requires the new `pause` / `release` verbs to have a `cli.<verb>` dispatch span and `process-start` / `process-exit{exit_code, detail}` into `cli-<name>.ndjson` once an instance resolves. Their wrapper side requires `channel-request` / `channel-response{method:"pause"|"release"}` with `corr` + `conn` on both sides (§10 Correlation propagation). Neither line may carry a params or result body (§6 Boundary-call wrappers, IPC).
- obs-plan §8 Data classification plus §4 Scenario "Human takes the wheel…" require that human keystroke bytes and the stdin classifier's input never reach a span field, a log line or a detail line. The wheel is logged only through closed codes (`holder`, `cause`, `detail`).
- obs-plan §4 Dialog → `answer` scenario requires `answer`'s new `human-typing` slot to surface as `channel-response{result_class:"refusal", refusal:"human-typing"}` (exit 10), like `unknown-dialog` / `unverified-cli`. A `null` answer of a pending `hook.dialog` on a wheel move is still a dialog outcome under that scenario's `dialog-answered` / `hook-decision` lines. The plan does not say which `from` / `deadline_hit` values that wrapper-initiated `null` carries, and P3/P4 must settle it rather than invent it.

## Patterns to follow
- Every new line goes through `obs_event!` under `#[instrument(skip_all, name = "...", fields(...))]` with an explicit field allow-list. Static span names only (obs-plan §4 Span naming convention; §8 Integration points 1).
- `channel-response` is emitted from the `channel.dispatch` `Drop` guard, so an early refusal return in the new `pause` / `release` / wheel-refusal arms still logs it (obs-plan §4 Scenario Confirmed `send`, Cleanup).
- The `corr` / `conn` / `instance` values reach the stdin-pump and wheel code as explicit values, never through span context across threads (obs-plan §11 Spans / Traces).
- Refusal `detail` values are the arch `RefusalReason` details verbatim (`manual-pause`). Whether `viola-core`'s obs enum and `schemas/diag-line.v1.json` already admit `wheel` on `send-refused` and the `release-from-driver` event (`crates/viola-core/src/obs.rs:22` names the variant, per scope §7) is research's question (obs-plan §6 `detail` code catalog; §8 Default-deny posture).

## Anti-patterns to avoid
- NEVER put a per-byte or per-chunk span or event on the PTY pump read loop or the stdin editing-key classifier, and never log at `info` inside it. Log the wheel transition only, once per change (obs-plan §11 Telemetry Strategy; §11 Logs).
- NEVER log a field outside the §6 catalog (default-deny, G4). In particular, never log the typed bytes, a key name or a byte class as a new field on the wheel path (obs-plan §11 PII Scrubbing; §8 Default-deny posture).
- NEVER derive the wheel or its telemetry from screen content. The wheel rests on stdin byte provenance and `prompt-submitted` origin only (obs-plan §11 Telemetry Strategy; §10 Deterministic emission).

## Contract bindings
- obs ↔ arch: the cause vocabulary differs. obs-plan §4 lists `run.wheel_transition.cause` as `human-key|manual-pause|release`, while `architecture.md:299` and test-plan (`:126`, `:265`, `:819`) name the product `wheel` cause `human-input`. Spans are not serialized in v1 (`with_current_span(false)`, §3 Log format), so no line carries the span value. P4 should pick one spelling for code, and an obs-plan amendment should align `human-key` → `human-input`. It must not be silently diverged.
- obs ↔ tests: the harness `start_records` check and `agent-run logs --kind wheel` read the `wheel` product event from `events.ndjson` (obs-plan §4 Scenario `viola run` start sequence). The new `wheel{holder:"human", cause:"human-input"|"manual-pause"}` and `wheel{holder:"driver", cause:"release"}` records are what tests assert, and the process logs are not.
- obs ↔ tests (G4): `schemas/diag-line.v1.json` requires `corr` on `release-from-driver` and on wrapper `send-*` lines (§3 Log format JSON schema). It must accept `wheel` on `send-refused`, or the §10 zero schema-conformance budget goes red.
- obs ↔ security: `release-from-driver` mirrors security.md §Local trust boundary's `-32602` refusal, where `from_trust` is `"self-reported"` (obs-plan §6 catalog). Whether the `pause` / `release` client frames ride the liveness-only pre-check is security's dated-gap question. obs records `process-exit` 21 `detail` accordingly (§6 `detail` code catalog).
- obs ↔ metrics: `viola.send.outcome` and `viola.compat.v_rejected` count `send-refused{refusal,detail,side}` and `-32602`. `human-typing` joins the first, and `release`-with-`from` already over-counts the second (obs-plan §5 Per-surface metrics).

## Acceptance criteria contributions
- (obs) Each human editing key or `viola pause` that changes the wheel, and each `viola release`, yields exactly one `wheel` product event with closed `holder` / `cause` values. A second key while `human`, and any focus, mouse or resize byte, adds no wheel line and no process-log line. No diagnostics or detail file holds the typed bytes. Checked by the synthetic canary in the secret scan (per obs-plan §4 Scenario "Human takes the wheel…"; §8 Integration points 6).
- (obs) Every wrapper `send-refused` line, whether `human-typing` (`detail` absent or `manual-pause`), `turn-running`, `input-not-ready` or `no-prompt-submitted`, carries `wheel`, `side:"wrapper"`, `corr`, `conn` and `rpc_id`. The client's `process-exit` carries `exit_code:10` for `human-typing`, and the G4 schema check passes (per obs-plan §4 Scenario "Human takes the wheel…"; §3 Log format JSON schema).
- (obs) A `release` frame carrying `from` logs one `release-from-driver{corr, conn, from, from_trust:"self-reported"}` line plus `channel-response{error_code:-32602}` at `warn`. A plain CLI `release` / `pause` logs `channel-request` / `channel-response{method:"release"|"pause"}` on both sides, with no params body (per obs-plan §6 Additive field catalog; §6 Log levels mapping).
- (obs) G2 reads 0 `event:"panic"` lines across the new wheel / pause / release tests, and every `cli-<name>.ndjson` of `pause` / `release` holds one `process-start` and one `process-exit{exit_code}` (per obs-plan §10 Always-required SLO invariant; §4 Instrumentation per surface).
