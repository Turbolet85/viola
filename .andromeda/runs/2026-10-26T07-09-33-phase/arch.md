# arch extract

## Relevance
partial — the architecture plan names no server-verification mechanism (that is security-plan's; arch's own §Cross-cutting Patterns "Local endpoint trust boundary" hands per-connection proof to the security specialist), but it fixes where the check lives, what it compares against, and how each client surfaces a failure.

## Constraints
- architecture §Standard Contracts (Instance snapshot) requires `pid` and `started_at` to be what identifies the wrapper process. `started_at` is the wrapper's own OS start time (sysinfo, whole seconds) rendered RFC 3339, so the client compares a sysinfo reading of the server pid against it at the same precision. The snapshot is written only by that instance's wrapper, so no client writes or repairs it.
- architecture §Standard Contracts (Snapshot envelope, detail `contract-snapshot-envelope`) requires a replay rebuild to treat `endpoint`, `pid` and `started_at` as absent. It also names the five `read_snapshot(` product callers that still read an unreadable or newer snapshot as absent (`src/cmd/client.rs`, `run`'s collision check, `src/cmd/hook.rs` twice, `src/cmd/hook/statusline.rs`). A replayed snapshot therefore has no pid or start time to verify against, and moving any client onto the replay is the held CARRY 7 change. Whether the code keeps today's absent → exit 21 / fail-open outcome is research's question.
- architecture §Conventions (CLI exit codes, detail `conv-exit-codes`) requires exit `21` for an unreachable instance, and §Standard Contracts (CLI `--json` output) requires the document `{"v":1,"error":"instance-unreachable","detail":null}`. A failed check on `send` / `wait` / `last` / `answer` / `pause` / `release` must use this existing code and document, with no new exit code or error word.
- architecture §Conventions (MCP, detail `conv-mcp-results`) requires an unreachable instance to be an `isError: true` result with `structuredContent` `{"error":"instance-unreachable","detail":null}` and text `refused: instance-unreachable`, not a JSON-RPC error. A failed check in the MCP `send` / `wait` / `last` / `answer` tools must use that shape. The `list` tool writes no frame and is not a client of this check.
- architecture §Established Decisions [Hook Contract] and §Conventions (`viola hook` exit codes) require `viola hook` to exit 0 always, with no stderr and no body. §Established Decisions [Hook Transport] (detail `dec-hook-transport`) also requires every spine hook's connect plus write to stay within `SPINE_DEADLINE` (1 s), using the 750 ms `CONNECT_DEADLINE`. A verification step on the hook path must fit inside that budget. SessionEnd's fallback (channel, then a `try_lock` direct append, then nothing) must stay within its 1.5 s budget.
- architecture §Established Decisions [Concurrency / Backend Framework] and §Cross-cutting Patterns (Tokio containment) require the check on the CLI and `hook` paths to use std threads and blocking I/O. Only `viola-mcp` may build a runtime, so the MCP tools' check runs either through the Tokio client or on a blocking thread inside `viola-mcp`, and nothing on the hook path pays for runtime startup.
- architecture §Infrastructure Patterns → Crate dependency direction requires sysinfo and the pid + start-time liveness check to live in `viola-state` (`liveness::live_endpoint` is the shared liveness read used by CLI `send` / `wait` / `last` / `answer` / `pause` and `viola-mcp`'s frame tools). `viola-channel` → `viola-core` plus interprocess, libc (Unix only) and windows-sys (Windows only), with no `viola-state` edge. An endpoint-side server-pid read belongs in `viola-channel`, and the comparison with the snapshot sits above it, in `viola-state` or the root bin. Whether a new edge is needed is research's question.

## Patterns to follow
- One shared client pre-check: `viola_state::liveness::live_endpoint`, moved out of `src/cmd/client.rs` so the CLI verbs and `viola-mcp` share one read (per architecture §Infrastructure Patterns → Crate dependency direction). Extend that one seam rather than adding a check per verb.
- The channel seam owns endpoint mechanics: the Windows SQOS Identification open (`client::open_handle`, adopted by `Stream::try_from`) is shared by the sync client and `TokioClient` through crate-private helpers (per architecture §Established Decisions [Message Broker / IPC] and §Infrastructure Patterns → Crate dependency direction). A server-identity read at connect should follow the same shared-helper shape, so both clients take it.
- Every non-run process connects to the `endpoint` recorded in the snapshot, never a rebuilt path while the snapshot is readable (per architecture §Occupied Resources → IPC endpoints, detail `res-ipc-endpoints`). Verification compares that same snapshot's `pid` / `started_at` from one read.
- Fixed refusal documents come from one writer, `client::refused_document`, with codes only (no path, pid or id) (per architecture §Standard Contracts, CLI `--json` output).

## Anti-patterns to avoid
- A bare pid as identity: pids get reused, so pid and start time must both match (per architecture §Established Decisions [Session Liveness]).
- A verification failure turned into a new refusal reason, exit code, MCP error word or hook body. `RefusalReason` and the exit-code table are closed sets extended only through `viola-core` and the conventions (per architecture §Conventions, `RefusalReason` and CLI exit codes). A mismatch is "instance unreachable", not a refusal.
- A `tokio` edge in a sync crate, or in `viola-channel`'s normal graph without its `tokio` feature (per architecture §Established Decisions [Module Boundaries]).

## Contract bindings
- arch ↔ security: architecture §Cross-cutting Patterns (Local endpoint trust boundary) leaves the per-connection proof to security-plan. The pid + start-time rule, the macOS euid + dir gap, the strict-modes "same process" precondition and the dated exceptions closed here are all security's. Arch fixes only the snapshot fields it reads (`pid`, `started_at`, `endpoint`) and the outcome shapes.
- arch ↔ tests: the outcome shapes (exit 21 plus the `instance-unreachable` document, the MCP `isError` result, hook exit 0 with empty stdout and stderr) are the E2E fixtures' assertions (architecture §Conventions, CLI exit codes / MCP).
- arch ↔ obs: the `channel-request` / `channel-response` lines and the `channel.request` span the shared client helpers emit (architecture §Infrastructure Patterns → Crate dependency direction) are where a failed check would surface in the codes-only process log (architecture §Cross-cutting Patterns, Diagnostic output channels).

## Acceptance criteria contributions
- (arch) A CLI frame verb (`send`, `wait`, `last`, `answer`, `pause`, `release`) whose server pid or start time does not match the snapshot exits 21 and, under `--json`, prints exactly `{"v":1,"error":"instance-unreachable","detail":null}`, with no frame written (per architecture §Conventions, CLI exit codes, and §Standard Contracts, CLI `--json` output).
- (arch) An MCP `send` / `wait` / `last` / `answer` call on a mismatch returns `isError: true` with `structuredContent` `{"error":"instance-unreachable","detail":null}`, not a JSON-RPC error (per architecture §Conventions, MCP).
- (arch) `viola hook <event>` on a mismatch exits 0 with empty stdout and stderr and writes no frame, and a spine event still finishes within `SPINE_DEADLINE` (per architecture §Established Decisions [Hook Contract] / [Hook Transport]).
- (arch) No product crate other than `viola-mcp` gains a `tokio` edge, and `scripts/channel-tokio-free.sh` and the sole-root `deny-sync.toml` loop stay green (per architecture §Established Decisions [Module Boundaries]).
