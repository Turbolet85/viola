# security extract

## Relevance
relevant — this chunk is the client side of the IPC trust boundary, the highest-impact surface (per security-plan §Threat Model Summary, boundary-ipc), and it closes the dated interim gaps that §Authentication & Authorization and §Security Anti-Patterns › Authentication name for exactly this route entry.

## Constraints
- Verification runs before the first frame of every method on the connection: `send`, `wait` / `last`, `answer`, `pause` / `release`, `hook.dialog`, and the `hook.event` notifications (which carry prompt text, `last_assistant_message` and tool data), not only `send` / `answer` / `hook.dialog`. What it checks per OS: on Windows `server_process_id()` must equal the snapshot `pid` and sysinfo's start time must equal `started_at`, after the SQOS identification-level open. On Unix `peer_creds().euid()` must equal `geteuid()` (never skipped), and where available (Linux/FreeBSD) `peer_creds().pid()` plus the sysinfo start time must match the snapshot. On macOS it is euid plus the verified 0700 socket directory only, a recorded known gap (per security-plan §Authentication & Authorization, IPC client-side server verification row). `run`'s collision check uses the same verification. Whether a client in `run`'s start, `revive`, `list` or `verify` writes a frame is research's question (per security-plan §Authentication & Authorization, IPC client-side server verification row, "Collision check").
- The reference values (`endpoint`, `pid`, `started_at`) must never come from a `snapshot.json` that has not passed the strict-modes check in the same process. A client that skips that check is verifying against values an attacker could have written (per security-plan §Security Anti-Patterns › Authentication; per security-plan §Authentication & Authorization, `~/.viola/` access control). The plan closes each dated gap only when both "Server verification before any frame" and "Home and code-bearing file integrity" land. So whether this chunk takes the strict-modes half with it, or verifies against an unchecked snapshot until that later entry, is a boundary question for P4. Whether the code already runs `viola_state::strict::check_instance` on any of these client paths is research's question (per security-plan §Input Validation, own-state-files row).
- On a mismatch, or a check that cannot be made, no frame is written. CLI verbs report `instance-unreachable` (exit 21). MCP tools return `{"error":"instance-unreachable","detail":null}`. `hook` fails open: exit 0, no body, a note in `diagnostics/` (per security-plan §Authentication & Authorization, IPC client-side server verification row, "On mismatch").
- `viola hook` never writes stderr and never exits non-zero, including on a server-verification mismatch, so the dialog renders for the human (per security-plan §Error Handling, the `hook` row). A security refusal never blocks the human, and refusals go only to automation (per security-plan §Security Anti-Patterns › Universal).
- External error output on a mismatch carries codes and fixed messages only. No absolute path, pid or `started_at` reaches CLI `--json` output, MCP `isError` results or channel `error.data`. Pids and `started_at` may go only to `instances/<name>/diagnostics/` (0600) (per security-plan §Bootstrap phases, `logging-redaction-wire`; per security-plan §Error Handling, External responses).
- No `config.json` key, `VIOLA_*` env var or CLI flag may switch off the server verification (per security-plan §Security Anti-Patterns › Universal).
- Today an absent, unreadable or newer snapshot reads as absent for the five non-replay readers (`src/cmd/client.rs`, `run`'s collision check, `src/cmd/hook.rs` twice, `src/cmd/hook/statusline.rs`), and the plan keeps it that way. The classified read and the log replay have exactly two product callers, `viola revive`'s preflight and `viola list`, each after `check_instance` (per security-plan §Input Validation, own-state-files row; per security-plan §Threat Model Summary, boundary-filesystem). Moving a client onto the replay is CARRY 7's held fork, not a lean.

## Patterns to follow
- The Windows client open is the `CreateFileW(... SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED ...)` recipe adopted through `Stream::try_from(OwnedHandle)`, pinned by `tests/channel_sqos_open.rs`. Verification extends that client and never replaces it (per security-plan §Bootstrap phases, auth-scaffolding-baseline; per security-plan §Authentication & Authorization, IPC client-side server verification row).
- The named library surface: interprocess 2.4.4 `Stream::peer_creds()` / `PipeStream::server_process_id()` and sysinfo 0.39.6 for pid plus start time. No new dependency is implied (per security-plan §Authentication & Authorization, Library).
- The check comes before anything under the home is opened. `hook statusline` is the landed model: `check_instance` on the canonicalised instance directory runs before its log opens, because a check made after obs init passes a home at 0770 (per security-plan §Authentication & Authorization, `~/.viola/` access control).
- Each negative is asserted with a test-owned control that shows the opposite outcome, as `tests/security_negatives_channel.rs` does for the Windows listener (per security-plan §Authentication & Authorization, the witness rows).

## Anti-patterns to avoid
- NEVER write any channel frame before the server is verified, and NEVER let a frame or process borrow a dated gap it was not given (per security-plan §Security Anti-Patterns › Authentication).
- NEVER fall back to interprocess's default connect for a Windows client pipe. Without SQOS it lets a squatter impersonate the client (per security-plan §Security Anti-Patterns › Authentication).
- NEVER treat the channel `from` param as identity. It is self-reported and verifies nothing about the server or the client (per security-plan §Security Anti-Patterns › Authentication).

## Contract bindings
- **arch:** the snapshot's `pid`, `started_at` and `endpoint` are the reference values, written only by the instance's own wrapper (per security-plan §Security Anti-Patterns › Universal); exit 21 / `instance-unreachable` follows the exit-code conventions.
- **obs:** a `hook` fail-open on a mismatch writes a note to `diagnostics/`. Whether that is a new `hook-decision` detail code beside the landed `oversize-stdin` · `malformed-json` · `channel-unreachable` belongs to obs (per security-plan §Error Handling, the `hook` row).
- **tests:** per-OS mismatch negatives (pid, start time, euid), each with a control. macOS is the euid-plus-directory arm only (per security-plan §Authentication & Authorization, IPC client-side server verification row).
- **route:** "Home and code-bearing file integrity" carries the strict-modes half, and "Unix endpoint and home hardening" carries the Unix directory check before client connect that the macOS arm leans on (per security-plan §Authentication & Authorization, IPC access control (Unix)). The wrap amends the dated-gap text in security-plan §Authentication & Authorization, §Input Validation (CLI row, own-state-files row) and §Security Anti-Patterns › Authentication; it is a master amendment, not a phase edit.

## Acceptance criteria contributions
- With an endpoint served by a process whose pid or start time differs from the snapshot, no client writes a frame. CLI exits 21 `instance-unreachable`, MCP returns `isError` `{"error":"instance-unreachable","detail":null}`, and `hook` exits 0 with empty stdout and stderr, no `hook.event` appended and no `hook.dialog` registered (per security-plan §Authentication & Authorization, IPC client-side server verification row).
- Every client that writes a frame (`send`, `wait`, `last`, `answer`, `pause`, `release`, `hook.event`, `hook.dialog`, and `viola mcp`'s `send` / `wait` / `last` / `answer`) reaches its first write only through the verification; no liveness-only path to a frame remains (per security-plan §Security Anti-Patterns › Authentication).
- On a mismatch, the bytes printed on stdout and stderr and the MCP `structuredContent` hold no absolute path, pid or `started_at` (per security-plan §Error Handling, External responses).
- Windows client opens still read `SecurityIdentification` at the server, and no code path opens through interprocess's default connect (per security-plan §Security Anti-Patterns › Authentication).
