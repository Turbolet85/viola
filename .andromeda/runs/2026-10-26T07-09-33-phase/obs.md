# obs extract

## Relevance
relevant: the chunk changes the outcome codes and fail-open lines of every frame-writing client (CLI `send` · `wait` · `last` · `answer` · `pause` · `release`, the `hook` client, the `mcp` frame tools), and the obs plan already reserves the codes the server check writes.

## Constraints
- A CLI verb refused by the server check ends with one `process-exit{subject:"self", exit_code:21, detail}` whose `detail` is the closed code `server-verify-failed`, with `strict-modes-failed` the code for a strict-modes refusal and `instance-dead` kept for the liveness cause. Each cause behind exit 21 gets its own code, and no code holds a path or pid (per obs-plan §6 Log Coverage, detail `log-details`, "`process-exit` exit 21"; per obs-plan §1 Obs Scope Summary, Telemetry triggers, Founder Direction 4). The line is at `warn` (per obs-plan §6 Log Coverage, Log levels mapping). Whether `during` (`connect|call`) also rides a `server-verify-failed` line is not stated by the plan. P4 decides it.
- The hook client fails open on a mismatch or on a check it cannot make. It writes only to `hook-<name>.ndjson`: `hook-invoked{corr:null}` immediately, then `hook-decision{corr:null, detail:"server-verify-failed"}` (or `strict-modes-failed`) at `warn`. It exits 0 with stdout and stderr empty (per obs-plan §6 Log Coverage, detail `log-details`, `hook-decision` fail-open codes; per obs-plan §4 Span / Trace Coverage, Scenario Dialog → `answer`, Cleanup "Fail-open before `dialog_id`"; per obs-plan §1 Obs Scope Summary, Telemetry triggers, security Vector 4).
- An `mcp` tool call that the check refuses returns `isError` with the code `instance-unreachable` only. Its log line in `mcp.ndjson` follows the same codes-only rule: no upstream text, absolute path or type name (per obs-plan §1 Obs Scope Summary, Telemetry surfaces, `viola mcp` Notes; per obs-plan §1 Obs Scope Summary, Telemetry triggers, security Vector 5).
- Default-deny: a field is logged only if the §6 catalog names it. A new field for the check (a server pid, a recorded or observed start time, a mismatch kind) is a catalog and `schemas/diag-line.v1.json` change, not a free addition (per obs-plan §8 PII Scrubbing & Compliance, Default-deny posture). Home-level lines stay path-free, and `endpoint` is never logged (per obs-plan §8 PII Scrubbing & Compliance, Data classification rules).
- Any span added for the check follows the `<area>.<operation>` snake_case form, with `<area>` taken from the closed list. It is declared `#[instrument(skip_all, name = "...", fields(...))]` with an explicit allow-list, and `err` / `ret` are banned. It sits inside the existing client spans (`send.client`, `wait.block`, `last.client`, `answer.client`, `pause.client` / `release.client`, `hook.handle` › `channel.request`, the `mcp` per-tool span) (per obs-plan §2 Telemetry Strategy, Naming conventions; per obs-plan §4 Span / Trace Coverage, Span naming convention).
- A snapshot reader moved to the classified read (`viola_state::replay::read_snapshot_or_replay`, CARRY 8) would start writing one `state-recovered{detail:"snapshot-replayed"|"snapshot-unsupported-v", file:"snapshot.json"}` line at WARN per call. Today the plan says the other five readers write no such line. That move is bound to CARRY 7's founder hold, so the line set changes only if he rules for it (per obs-plan §4 Span / Trace Coverage, Edge flows E5).
- The hook role keeps zero unlogged panics and exit 0 on the new check path, with no retry-once policy (per obs-plan §10 SLO Invariants & Telemetry Budgets, Zero unlogged panics).

## Patterns to follow
- Emit every line through `obs_event!` with explicit typed fields, and pass `corr` / `conn` / `instance` as explicit values, never from span context (per obs-plan §11 Obs Anti-Patterns, Logs; per obs-plan §3 Trace context propagation, Internal async boundaries).
- Follow the client exit-line shape of the `send` and `wait` / `last` scenarios: `send.client` / `wait.block` close with `process-exit{subject:"self", exit_code, detail}`. The client alone logs a lost connection, once (per obs-plan §4 Span / Trace Coverage, Scenario Confirmed `send`, Cleanup; per obs-plan §4 Span / Trace Coverage, Scenario `wait` / `last`, Required log fields).
- A refused check writes no frame. The plan has no `channel-request` line for a frame that was never sent, so a refusal made before any frame logs only its outcome line, on the model of the client-side `send-refused{side:"client"}` written before any frame (per obs-plan §4 Span / Trace Coverage, Scenario Confirmed `send`, client-side validation refusal).
- Content-bearing detail, if any (an error chain), goes only to `instances/<name>/diagnostics/detail-<process>.ndjson` (per obs-plan §7 Error Capture & Reporting, Scrubbing layers 3; per obs-plan §3 Observability Harness Contract).

## Anti-patterns to avoid
- Never put a pid, a start time, an endpoint name or a path inside a `detail` code or a span name (per obs-plan §11 Obs Anti-Patterns, PII Scrubbing; per obs-plan §11 Obs Anti-Patterns, Spans / Traces).
- Never write to stdout or stderr from the hook's fail-open path, and never use `print!` / `eprintln!` / `dbg!` in the `hook`, `mcp` or client paths (per obs-plan §11 Obs Anti-Patterns, Logs).
- Never log `from` as an authenticated identity. The server check is the identity control, and `from` keeps `from_trust:"self-reported"` (per obs-plan §3 Trace context propagation, IPC boundaries).

Whether that schema's closed `process-exit` `detail` enum (13 values) and its `hook-decision` `detail` enum already admit `server-verify-failed` and `strict-modes-failed` is research's question (per obs-plan §6 Log Coverage, detail `log-details`; per obs-plan §9 CI Integration, G4).
- obs ↔ security-plan §Local trust boundary / §Error Handling: the check's refusal codes (exit 21, MCP `instance-unreachable`, hook fail-open) mirror the security clause "verify the server before the FIRST frame". The obs `detail` codes are the logged side of that clause (per obs-plan §1 Obs Scope Summary, Telemetry triggers, security Vectors 1, 4 and 5).
- obs master text names this entry as owner of a gap. That text becomes a wrap amendment once the check lands: §4 Scenario `wait` / `last` says "`strict-modes-failed` / `server-verify-failed` cannot occur on `wait` / `last` until client-side server verification lands", and the §12 history (amendment `2026-10-04-wait-and-last`) records exit 21 as `instance-dead` only (per obs-plan §4 Span / Trace Coverage, Scenario `wait` / `last` event-driven readback).
- obs ↔ tests §10 perf: the `hook` path gains the server check, and the spine hooks stay under the hyperfine `max` gates (per obs-plan §10 SLO Invariants & Telemetry Budgets, Performance budgets).

## Acceptance criteria contributions
- A CLI frame verb pointed at an endpoint whose server pid or start time differs from `snapshot.json` exits 21. It writes exactly one `process-exit{subject:"self", exit_code:21, detail:"server-verify-failed"}` at WARN, with no path, pid or endpoint in any line, and no `channel-request` line for that call (per obs-plan §6 Log Coverage, detail `log-details`).
- A `viola hook` event and a dialog hook facing the same mismatch each exit 0 with stdout and stderr empty. Each writes `hook-decision{corr:null, detail:"server-verify-failed"}` at WARN to `hook-<name>.ndjson` and nothing else outside that file (per obs-plan §6 Log Coverage, detail `log-details`, `hook-decision` fail-open codes).
- An `mcp` frame tool facing the mismatch returns `isError` carrying only `instance-unreachable`, and its `mcp.ndjson` line carries codes only (per obs-plan §1 Obs Scope Summary, Telemetry surfaces, `viola mcp`).
- Every line written on these paths passes G4 against `schemas/diag-line.v1.json`, with zero G2 panics and zero secret-scan hits (per obs-plan §10 SLO Invariants & Telemetry Budgets, Error budget).
