### cross-cutting-patterns#1.1 · values · crosscut-config · ## Cross-cutting Patterns · lines 8–12
- **Config management.** Precedence: CLI flags override `<viola home>/config.json`, which overrides built-in defaults.
  - Viola home: a global `--home <dir>` flag on every subcommand overrides the default `<user home>/.viola/`. Resolution order: `--home`, then the grandparent of `VIOLA_DIR` when it is set, then the default. As landed (chunk 2026-10-17-cli-machine-contract): `resolve_home(flag, name, dir, user_home)` in `src/cmd/mod.rs` resolves `--home` as given, else the `instance_of` home when both `VIOLA_NAME` and `VIOLA_DIR` pass the one shape check (a valid `ViolaName`, an absolute dir ending `instances/<name>`), else `<user home>/.viola`, a failing pair falling through; `resolved_home` reads the two variables and `std::env::home_dir()` once, at every verb arm of `dispatch`; `canonical_home` canonicalises a home that exists (`std::fs::canonicalize`, a Windows `\\?\C:\…` written back as `C:\…`, every other verbatim form kept) and keeps `std::path::absolute`'s spelling for one that does not, creating nothing; `run`'s start canonicalises the home after its wrapper log has created it, before the collision check, the pin and the endpoint bind. `viola run --home <dir>` passes the home to the child only through `VIOLA_DIR`, so the pinned copy, plugin folder, endpoint hash, logs, `budget.json` and ledger stamps all follow it. The statusline source follows the home too: `<home>/statusline-source.json` is the source whenever it exists, and only the default home (`canonical_home(default_home(user_home))`, `default_home` shared by `resolve_home` and the source rule) falls back to the user's `<user home>/.claude/settings.json`, so a home named by `--home` or reached through `VIOLA_DIR` never reads the user's settings. The rule has no `config.json` key and no environment variable; `start` reads `std::env::home_dir()` for it, the read `resolved_home` already made. This is the isolation point for tests: each test runs in its own home, and that home's `ledger/stamps.json` can stamp the fake agent's reported version.
  - `config.json` is parsed tolerantly (unknown keys skipped and counted) and carries `v`.
  - Settings: budget thresholds as `Percent` (defaults `five_hour` 90, `seven_day` 85), `diagnostics_level` (`info` by default, or `debug`) and `claude_env_keep` (the Unix R8 pass-list of `CLAUDE*` names, default empty) and `dialog_hold_s` (the dialog hold as a `DialogHold`, whole seconds 60–3600, default 60). `diagnostics_level` is the only source of the process-log level; `RUST_LOG` has no effect.
  - There are no secrets in v1, and environment variables are not a configuration channel. The `VIOLA_*` variables are wrapper-to-child plumbing set by `viola run` only. The only other variables any `viola` build reads are the two test seams `FAKE_AGENT_PUMP_DELAY_MS` (capped at 5 s) and `FAKE_AGENT_HOOK_PANIC` (exact value `1`, a forced fail-open `hook` panic), both compiled only under `cfg(feature = "fake-agent")` and absent from release builds, and, in every build, `NO_COLOR`, `TERM` and `COLORTERM`, read by viola's own colour layer (`src/human/style.rs`, `viola list`'s human mode only) to decide whether and how deep its SGR bytes are written (the founder's own word, chunk 2026-10-17-cli-output-discipline): they configure nothing, disable no control and widen no redaction. viola's reader is the only one because clap is built without its `color` feature: that feature's anstream → anstyle-query route read `CLICOLOR`, `CLICOLOR_FORCE`, `NO_COLOR`, `TERM`, `COLORTERM` and `CI` and was closed at chunk 2026-09-28-cli-output-tokens (as measured at its research F1: `CLICOLOR_FORCE=1 viola --help` into a pipe gave 25 ESC bytes before, 0 after); a dependency or feature that reads an environment variable breaks this rule like a direct read does.
