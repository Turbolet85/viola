## Relevance
partial: the chunk adds no web-spa surface. Its a11y reach is the new `viola verify` CLI output, plus the `viola run` tui boundary that the version gate and the transport-only degrade must keep. The web `unverified-cli` CLI-column word and the `viola answer` `unverified-cli` refusal belong to later chunks (Epochs 5/8 and 3, per scope Boundaries).

## Constraints
- `viola verify` is a named a11y cli entity. It has three modes: human TTY, plain (non-TTY / `NO_COLOR` / `TERM=dumb`) and `--json`. Only output-discipline assertions apply to it, and it carries no WCAG conformance claim (per a11y-plan §1 A11y Scope Summary → CLI and terminal entities; §11 Strategy).
- Must-be-accessible Path 6 lists `verify` output. It must be linear and static: `verify` step lines of the form `[NN/NN] … pass|fail`, with no spinner and no redraw. It stands in for SC 1.3.2, 1.4.1 and 3.3.1 (per a11y-plan §1 → Must-be-accessible paths, path 6; §4 → P6).
- SGR rules, per a11y-plan §6 State color tokens (CLI equivalent) and §4 → P6:
  - `fail` is never coloured.
  - No SGR is emitted under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`.
  - Any SGR viola does emit must sit beside its word.
  - Whether `verify` should emit any SGR at all, given that the prior chunk built clap without `color`, is research's question.
- The catch-site `error: internal error` is a fault, not a refusal. It carries no `hint:` line, and under `--json` the output is one document with no hint text (per a11y-plan §8 Error recovery → CLI).
- The `viola run` tui boundary holds while the version gate and the transport-only degrade are active:
  - viola writes zero bytes of its own to the terminal, so any unverified-cli diagnostic goes to `diagnostics/` and never to the terminal;
  - human keystrokes are never blocked, refused or delayed.
  - Withholding dialog answers applies only to automation, never to the human answering in the TUI.
  - Sources: a11y-plan §1 → tui entity (boundary-only) and Notes; §1 Path 4; §11 Keyboard.
- A kebab-case code never appears without its plain word. If `verify` or `run` surfaces a code such as `unverified-cli` to a human, it sits beside the plain word `unable` (per a11y-plan §8 Plain language; §11 Cognitive).
- There are no a11y violation rows for the cli. Output-discipline failures surface only as nextest failures in `suites[].failures[]` (per a11y-plan §3 Structured violation JSON schema → cli / tui).

## Patterns to follow
- Pin every fixed `verify` string with trycmd, and assert streams and exit codes with assert_cmd 2.2.2 + predicates 3.1.4. This covers the step lines, the `stamped <ver>  <n> pass  0 fail` result line and the `error: internal error` catch-site line. A copy change then fails CI until the pin is updated (per a11y-plan §3 A11y testing tool pick → cli; §8 Plain language → Verification).
- Check TTY-only behaviour under the portable-pty `=0.8.1` outer PTY: no `\r` redraw, cursor-movement or erase sequence, and every SGR beside its word. Check the non-TTY modes with trycmd / assert_cmd. All of this runs on all three OS legs (per a11y-plan §4 → P6; §9 Per-pipeline-stage a11y artifacts → Unit / integration row).
- On Windows, the `viola run` zero-viola-bytes check is that viola's own literals are absent. It does not compare the stream byte for byte, because ConPTY emits its own SGR and cursor bytes (per a11y-plan §3 Keyboard test harness → Tooling; §6 State color tokens).

## Anti-patterns to avoid
- Never colour CLI `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` (per a11y-plan §11 Visual).
- Never add a spinner or redraw to `verify` while probes run. This includes live Haiku probes that take seconds (per a11y-plan §11 Motion "never add spinners"; §4 → P6 linear static output).
- Never claim WCAG conformance for the cli, never parse the rendered `claude` TUI screen for content, and never print a stack trace or anyhow chain as the only error text (per a11y-plan §11 Strategy, Universal and Cognitive).

## Contract bindings
- **a11y ↔ tests:** the `verify` output-discipline cases run inside the tests' `nextest-integration` / `nextest-e2e` suites (CI: `coverage`) under `gate --require coverage,…`. They add no a11y suite value and write no a11y rows (per a11y-plan §9; §10 Standard+ invariants → CLI output-discipline invariants).
- **a11y ↔ design:** the `[NN/NN] … pass|fail` step-line shape, the SGR policy and the `error: internal error` phraseology come from design-system §Surface: cli. a11y asserts them and does not define them (per a11y-plan §1 → cli surface Notes; §6 State color tokens).
- **a11y ↔ obs:** the catch-site chain goes only to the detail file, never to the terminal. This matches the tui/cli rule "diagnostics go to `diagnostics/`, never to the terminal" (per a11y-plan §1 → tui surface Notes).

## Acceptance criteria contributions
- A trycmd / assert_cmd case shows that `viola verify` in plain mode (non-TTY, `NO_COLOR`, `TERM=dumb`) and in `--json` mode emits no SGR byte. Under the portable-pty outer PTY, it shows that the `verify` output has no `\r` redraw, cursor-movement or erase sequence, and that `fail` carries no SGR. The case runs on all three OS legs (per a11y-plan §4 → P6).
- A trycmd case pins the `verify` step-line form `[NN/NN] … pass|fail` and the final `stamped <ver>  <n> pass  0 fail` line in linear order (per a11y-plan §1 → Must-be-accessible paths, path 6).
- An assert_cmd case shows that a forced catch-site fault in `viola verify` prints exactly `error: internal error` on stderr, uncoloured, with no `hint:` line, and that the `--json` output carries no hint text (per a11y-plan §8 Error recovery → CLI).
- A portable-pty boundary case shows that `viola run` against an unverified fake-agent version (transport-only degrade) adds no viola-originated bytes to the outer-PTY stream. On Windows, viola's own literals are absent. The case also shows that human keystrokes are still delivered unblocked. Whether the existing P4 boundary cases already cover the degraded path is research's question (per a11y-plan §3 Keyboard test harness → Tooling; §4 → P4).
