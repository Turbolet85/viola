## Relevance
relevant — the chunk lands the ledger gate that architecture names as its single gate for CLI-specific behaviour. It also adds the `verify` verb, a new home file (`ledger/stamps.json`), a new repo tree (`fixtures/claude/`) and a new step in `run`'s start order.

## Constraints
- **Placement.** Ledger rows, probes, post-condition checks, the version gate's parse and the fixture scrub are Claude-specific, so they live only in `viola-agent-claude` (per architecture §Established Decisions → [Agent Coverage] and §Cross-cutting Patterns → "Capability ledger as the single gate"). Architecture requires the rows to be a compiled-in, closed set: a CLI version → behaviours mapping holds only the measured values, and the rows themselves are never data on disk (per §Occupied Resources → Filesystem, `ledger/stamps.json`). No new normalised event kind may carry a Claude-specific name. Any new kind is added only in `viola-core` (per §Conventions → Naming patterns, "Normalised event kinds").
- **Crate edges.** `viola-agent-claude` → `viola-state` is the sanctioned edge, and it "arrives with the chunk that consumes it". vt100 arrives the same way (per §Infrastructure Patterns → Crate dependency direction). Both crates stay sync crates in `scripts/sync-crates.txt`, under the sole-root `deny-sync.toml` tokio ban and CI target job 3 (per §Established Decisions → [Concurrency / Backend Framework], §Cross-cutting Patterns → Tokio containment). `verify` is a short-lived CLI verb: std threads, blocking I/O, no runtime. Whether this chunk's screen-signature rows need vt100 now, or only a signature value, is research's question.
- **`stamps.json` on disk.** `viola verify` is the only writer of `ledger/stamps.json`. It writes through `viola_state::fs::replace_private` with its own `ledger/stamps.json.lock` sibling. `run`'s version gate and `ui` are its only readers (per §Occupied Resources → Filesystem; §Established Decisions → [Snapshot writer]; §Cross-cutting Patterns → Crash-safe disk writes). As one of viola's own formats it carries `v` and is versioned-tolerant: readers skip and count unknown fields, and it has no `deny_unknown_fields` (per §Conventions → Protocol versioning; §Established Decisions → [Validation]; §Cross-cutting Patterns → Mixed-version tolerance). Timestamps inside it are RFC 3339 UTC with milliseconds and `Z`, as `*_at` (per §Conventions → Data model conventions).
- **Version gate.** `run` gets the version by running the resolved child executable once with `--version`, spawned directly with no shell. That is the same absolute-path, npm-shim → `claude.exe` resolution the spawn uses. Output it cannot parse counts as an unlisted version (per §Established Decisions → [CLI Version Compatibility], [CI/CD]; §Cross-cutting Patterns → Cross-platform discipline). The gate's step in the start order is fixed: after the pinned copy and plugin, before the exclusive endpoint bind (per §Established Decisions → [Session Liveness]). `cli_version`/`cli_verified` go into the first snapshot and are not rebuilt by replay (per §Standard Contracts → Instance snapshot, Snapshot envelope).
- **Transport-only degrade.** On an unlisted or unverified version the wrapper still types, runs the wheel and emits events, but withholds dialog answers: `hook.dialog` is answered `null` at once. The `unverified-cli` refusal has detail `null`, exit `12`, and ranks second in `answer`'s refusal order (per §Established Decisions → [CLI Version Compatibility], [Hook Contract]; §Standard Contracts → Channel methods `hook.dialog`; §Conventions → Error handling schema, CLI exit codes). The dialog tier (PreToolUse, PermissionRequest) is registered "by the dialog chunk, never earlier with a no-decision body" (per §Established Decisions → [Deployment / Distribution]). Whether any dialog path exists today for the degrade to withhold is research's question.
- **Errors and output channels.** anyhow stays in the root bin. `viola-agent-claude` errors fold into its one thiserror `AgentError` with fixed messages (per §Established Decisions → [Error Handling]; §Conventions → Rust error types). The `verify` verb's human stderr goes only through `src/human.rs` under the workspace `print_stderr` ban. The context chain goes only to the owner-only `detail-<role>.ndjson`, and codes-only lines go to the home-level `cli-<name>.ndjson` role file (per §Infrastructure Patterns → Build system (Lint); §Cross-cutting Patterns → Diagnostic output channels). Which role-file name `verify` uses when no instance resolves is research's and obs's question.
- **CLI surface.** `verify` is already a listed subcommand with a module slot in `src/cmd/`, and it takes the global `--home` (per §Occupied Resources → Binary, subcommands and exit codes; §Infrastructure Patterns → Project directory structure; §Cross-cutting Patterns → Config management). It must stay inside the closed exit-code set `0, 1, 2, 10–14, 20, 21`. Human text is the default, and `--json` output uses the `{"v":1,…}` mirror (per §Conventions → CLI exit codes; §Established Decisions → [CLI Conventions]; §Standard Contracts → CLI `--json` output). A post-condition failure has no code in that set, so it needs a P4 decision, and a new code is an architecture amendment. No new env var is allowed. The fake agent's `--version` and probe support live in the test-only `viola-fake-agent` bin behind feature `fake-agent` (per §Occupied Resources → Environment variables, Binary; §Established Decisions → [Naming]).

## Patterns to follow
- **One replace helper.** Every replaced file goes through `viola_state::fs::replace_private` with a `.lock` sibling, opened for write. No call site carries its own temp + rename (per §Established Decisions → [Snapshot writer], [Database / State Store]).
- **Tolerant external parsing for the recorder.** External payloads are parsed with `#[serde(default)]`/`Option<T>`, and the raw `serde_json::Value` is kept for the fixture recorder, with serde_path_to_error drift reports. An unparseable external value becomes `"unknown"`, never an error (per §Established Decisions → [Validation]; §Conventions → Data model conventions). The `--version` parse follows the same tolerance: an unparseable version is an unlisted version, never a failure.
- **Measured values live in the stamp.** Per-version measured values, such as the confirmation window, the readiness gate's quiet period and maximum wait, and the largest hook payload, belong in the stamp beside the row, not in `config.json`. A compiled-in fallback lives in `viola-agent-claude` (per §Established Decisions → [Delivery Confirmation], [Screen Model]).
- **Test isolation by home.** Each test runs in its own `--home`, and stamps in a test home are produced there (per §Cross-cutting Patterns → Config management; §Established Decisions → [CI/CD]). The fake agent is substituted by naming its exe after `--`.
- **The one stderr writer.** `src/human.rs` owns one writer, one `write_all`, and swallows a closed pipe (per §Infrastructure Patterns → Build system (Lint)). The catch-site line joins its callers. The reporter stays `viola::obs::report_internal_error` (per §Established Decisions → [Error Handling]).

## Anti-patterns to avoid
- **No hard-coded CLI behaviour.** Do not hard-code any CLI behaviour as an unconditional assumption, and do not put Claude payload shapes outside `viola-agent-claude` (per §Cross-cutting Patterns → "Capability ledger as the single gate"; §Inherited Defaults → Agent isolation).
- **No second writer of `stamps.json`.** No test-support seam, harness or `run` may write `stamps.json`, not even to "stamp the fake agent's version" directly (per §Occupied Resources → Filesystem, `ledger/stamps.json`). §Cross-cutting Patterns → Config management's phrase "that home's `ledger/stamps.json` can stamp the fake agent's reported version" is satisfied only through `viola verify --home`.
- **No shell, no Tokio.** Do not spawn the `--version` probe or any `verify` probe through `sh`/`bash`/`cmd`, and do not bring Tokio into `viola-agent-claude`/`viola-state` through a new dependency or feature (per §Cross-cutting Patterns → Cross-platform discipline, Tokio containment).

## Acceptance criteria contributions
- (arch) Every ledger row, probe and post-condition, the `--version` parse and the fixture scrub are defined in `viola-agent-claude`. No Claude-specific shape appears in `src/`, `viola-state` or `viola-core`, and `viola-agent-claude` stays tokio-free under the sole-root `deny-sync.toml` ban (per architecture §Established Decisions → [Agent Coverage], §Infrastructure Patterns → Crate dependency direction).
- (arch) `ledger/stamps.json` is written only by `viola verify`, through `viola_state::fs::replace_private` under `ledger/stamps.json.lock`. It carries `v`, and a reader tolerates an unknown field. A repo-wide search finds no other writer, test support included (per architecture §Occupied Resources → Filesystem, §Established Decisions → [Snapshot writer]).
- (arch) `viola run` runs its version gate between the pinned copy/plugin step and the endpoint bind. Unparseable `--version` output yields `cli_verified:false`, and a version stamped by `viola verify --home <home>` against the fake agent yields `cli_verified:true` with `cli_version` set in the first snapshot (per architecture §Established Decisions → [Session Liveness], [CLI Version Compatibility], §Standard Contracts → Instance snapshot).
- (arch) `viola verify` exits only with codes from the closed set, or the set is amended in the same chunk. Its failure path prints exactly `error: internal error` through `src/human.rs`, with no chain on stderr (per architecture §Conventions → CLI exit codes, §Established Decisions → [Error Handling]).
