# obs extract

## Relevance
partial — the chunk is capability-ledger rows and `viola verify` probes; obs bears on verify's spawn-pair logging, the closed `subject` / `parser` enums, the ledger read's outcome line and the content floor for the new probe shapes (resume start, `/compact` paste, statusline child, `rate_limits`, `claude agents --json`).

## Constraints
- obs-plan §4 Edge flows (`verify` / `plugin install`) requires `viola verify`, under a `VIOLA_NAME`, to log each child spawn at the call site as one `process-start{subject}` / `process-exit{subject, child_exit_status, duration_ms}` pair between its own `process-start` / `process-exit`, with no row text, prompt or path in any line. The plan currently pins that count at six pairs (`version-probe`, `verify-probe`, four `verify-pty-probe` for Runs A–D). Any new verify child this chunk adds (a resume start, a `claude agents --json` start, a statusline-bearing run) moves that count and the plan text that pins it. Whether a new paste inside Run B adds no pair is research's question.
- obs-plan §4 Edge flows (`verify` / `plugin install`) also requires a verify stopped by Ctrl-C or TERM to start no further spawn, close every pair it opened (a killed child closes with `duration_ms` and no `child_exit_status`), and end `process-exit{subject:"self", exit_code:1, detail:"interrupted"}`. Each new spawn has to join that closure.
- obs-plan §6 Log Coverage (Boundary-call wrappers → Child / shell spawns) requires `schemas/diag-line.v1.json` to close `subject` at `self|claude-child|version-probe|verify-probe|verify-pty-probe|agents-probe|statusline-shell`. A `claude agents --json` start maps to the existing `agents-probe`. A resume child, if it is a new verify PTY run, has no subject of its own: either it reuses `verify-pty-probe` or it needs a new enum member, which is a schema change. A `claude agents --json` parse failure is `parse-rejected{parser:"claude-agents-json"}` and the value `"unknown"`.
- obs-plan §6 Log Coverage (Additive field catalog) admits only fields named in the catalog (default-deny, enforced by `unevaluatedProperties: false`). A new field on any verify line, such as a row id, a session id from a resume probe or a `rate_limits` value, has to be catalogued first.
- obs-plan §4 Edge flows (Capability ledger) requires `run`'s version gate to read `ledger/stamps.json` as the child span `state.ledger_read`. Its outcome is `cli_verified` on `process-start{subject:"claude-child"}`, and a missing stamp gives `cli_verified:false`. Only an unreadable, malformed or strict-modes-refused file gives `parse-rejected{parser:"ledger-stamps"}`, and the path and stamp contents never appear. Once rows are added, every home stamped before them reads unverified. Whether a row-missing stamp writes any line is research's question.
- obs-plan §8 PII Scrubbing (Data classification rules) keeps `statusline_command` out of every home-level line (the `statusline.shell_out` span records `shell_exit_status` and `duration_ms` only). It never logs `claude agents --json` rows verbatim (only `parse-rejected` counts) and keeps prompt text out of home-level lines. Budget percentages and `resets_at` are Low and may be logged as typed fields. Recorded fixtures are not a telemetry source, and obs adds no fixture content.
- obs-plan §10 SLO Invariants (Bounded exemptions, item 5) leaves the hidden `hook --capture` arm with no obs init, no role file and no line. A new probe capture through it (a SessionStart of source `resume` or `compact`, a statusline payload) stays uninstrumented. A panic there writes no line, and the hook still exits 0.

## Patterns to follow
- Verify spawn logging at the call site, with `run_bounded` itself unlogged, one pair per child with `child_exit_status` and `duration_ms` (per obs-plan §6 Log Coverage, Child / shell spawns).
- Span naming `<area>.<operation>`, using the existing verify spans `cli.verify` (dispatch), `cli.verify_step` (per step) and `state.ledger_write` (the stamp). No row id, instance name or path goes in a span name (per obs-plan §2 Telemetry Strategy; §11 Spans / Traces).
- `#[instrument(skip_all, fields(...))]` with explicit typed fields only, and every line through `obs_event!` (per obs-plan §8 PII Scrubbing, Integration points 1; §11 Logs).
- When the resume probe or the statusline probe reaches the budget path, use the budget-governor line set unchanged: `hook-decision{hook_event:"statusline", budget_written}`, which is true only when the payload held `rate_limits` and the write succeeded, plus `process-start` / `process-exit{subject:"statusline-shell"}` only when a shell is built (per obs-plan §4 Scenario: Budget governor).

## Anti-patterns to avoid
- NEVER log a field not named in the §6 catalog, and NEVER add an `event` value without a Decisions Log entry (per obs-plan §11 PII Scrubbing; §11 Logs).
- NEVER derive telemetry from screen content: the new PTY probes may read screens for readiness and verdicts only (per obs-plan §11 Telemetry Strategy).
- NEVER log `statusline_command`, send or paste text (the `/compact` probe paste included) in a home-level file, and NEVER put a path or pid inside a `detail` code (per obs-plan §11 PII Scrubbing).

## Contract bindings
- obs ↔ tests: G4 checks every home-level line against `schemas/diag-line.v1.json` (obs owns the schema, tests own the check body), and G2 counts zero panics. Both cover verify's `cli-<name>.ndjson` lines whenever a home sits under `target/e2e-home/` (per obs-plan §9 CI Integration, Gate commands).
- obs ↔ tests: in CI `viola verify` runs only against the fake agent at 2.1.287 (`tests/cli_verify.rs`, harness `boot` step 4, the rstest `stamped_home` fixture). The real-`claude` verify runs only through local `run --local-live`, and no obs gate depends on verify's own lines (per obs-plan §4 Edge flows, `verify` / `plugin install`).
- obs ↔ security: the `statusline_command`, `claude agents --json` rows and recorded-fixture classifications are security-sourced. Fixture scrubbing (`--record` refusal codes) stays security- and tests-owned (per obs-plan §8 PII Scrubbing).
- obs ↔ design-system: verify's agent-readable outcome is its stdout step lines `[NN/MM] <row id> <row words>  pass|fail` and the last line `stamped <version>  N pass  N fail`. `MM` moves with the row count (per obs-plan §4 Edge flows, `verify` / `plugin install`, citing design-system §Streams).

## Acceptance criteria contributions
- Under a `VIOLA_NAME`, one fake-agent `viola verify` round writes exactly one `process-start` / `process-exit` pair per child it starts, each with a `subject` from the closed enum and `child_exit_status` + `duration_ms` on the exit. The plan's pinned pair count matches the new child set, and an interrupted round closes every pair it opened (per obs-plan §4 Edge flows, `verify` / `plugin install`).
- Every home-level line written by verify and by any new probe path passes G4 against `schemas/diag-line.v1.json` (any new `subject` member or field added to the schema first), and G2 reads zero uncounted panics (per obs-plan §9 CI Integration, Gate commands).
- No home-level `diagnostics/*.ndjson` line from a verify round carries a probe prompt, the `/compact` paste text, a statusline command string, a `claude agents --json` row or an absolute path (per obs-plan §8 PII Scrubbing).
- A home stamped before the new rows starts `run` with `process-start{subject:"claude-child", cli_verified:false}`. There is no `parse-rejected{parser:"ledger-stamps"}` line unless the file is unreadable, malformed or strict-modes-refused (per obs-plan §4 Edge flows, Capability ledger).
