## Relevance
relevant — every row this chunk lands is a capability-ledger row whose probe, recorded fixtures, stamp count and shape-pinned test readers the test plan governs.

## Constraints
- test-plan §1 (multi-version-compat trigger) requires every ledger row to have a `viola verify` probe with a post-condition, read by a local run's exit code and its `stamped … pass … fail` line. Each row the chunk adds (resume, `/compact`, statusline override, `/bin/sh`, `rate_limits`, `claude agents --json` join field) needs both before it may gate `cli_verified`.
- test-plan §5 (Integration Test Strategy, `contract_ledger_probes.rs`) requires `viola verify --home <tmp>` against the fake agent with `--dialogs --framing` to list each literal ledger row id exactly once with its post-condition result. It must end `stamped <ver>  <n> pass  0 fail`, with `<n>` equal to the literal row count. The same check runs against the real CLI under `--local-live`. The stamped and drift-only fixture-dir lists (`2.1.287` stamped; `2.1.283`, `2.1.288` drift-only) are test literals, and every fixture dir sits on exactly one list.
- test-plan §5 (Integration Test Strategy, `tests/cli_verify.rs`) pins the `[NN/18]` step lines, the last `[18/18] paste-newline …`, and the partial-failure shapes by literal: a run without the framing replay reads `stamped 2.1.0  17 pass  1 fail`, and the tag-turn modal case reads `16 pass  2 fail`. Each added row moves the step counter and every one of these shapes. A run without a new row's replay must fail only that row.
- test-plan §4 (Unit Test Strategy) requires the version gate's older-stamp oracle: a stamp holding exactly the older row ids, all `pass`, reads unverified. The plan's text still says "fourteen older row ids" while `LedgerRow::ALL` holds eighteen. Whether the code's oracle reads fourteen or seventeen, and how it moves with each new row, is research's question. The same section requires a statusline `rate_limits` parsing case, where a malformed `resets_at` becomes `"unknown"`, and a `claude agents --json` parser case, where an over-`MAX_FRAME` or malformed payload gives `unknown` and a row `name` never becomes a `ViolaName`.
- test-plan §7 (Test Data & Fixtures, Seed strategies → Recorded hook payloads) requires these steps for every recorded payload: record it locally by live `viola verify`, scrub it, run the `unclean` check, and commit it. A dirty payload refuses the whole recording, and CI replays every recorded payload. §7 (Fake agent) also requires that no fake-agent shape is invented before a recorded fixture exists: `agents --json` lands with its consumer chunk. It names the rewritten `--resume` SessionStart payload (5 key names against the live 10) as owed to this route entry's recorded payload.
- test-plan §7 (Fixture hygiene) requires the `tests/contract_fixture_hygiene.rs` run-time walk to cover each new `fixtures/claude/<ver>/*.json` variant. The walk fails on absolute paths, usernames and email-shaped tokens, and validates against `schemas/claude-fixture.v1.json`, whose enum is the fake agent's nine `REGISTERED_EVENTS`. The checker reports only a violation class, and planted inputs prove each class red.
- test-plan §3 `run` (`--local-live`) requires the harness's `LEDGER_ROWS` literal (`[&str; 18]` today) and its `LIVE_PASS` unit proof to read each literal row id. Suite `local-live` fails `row-missing` on a home stamped at fewer rows, and it refuses `live-in-ci` (exit 2) when `CI` is set. A row added to the product without this literal moving leaves the live suite reading the old count.

## Patterns to follow
- The paste-newline row's three named unit cases (test-plan §4, Unit Test Strategy, ledger framing arms): passes on the recorded shape, fails when the post-condition is broken, fails without a matching capture. Each new row's check takes the same three-case form against its own capture.
- Fake-agent replay of a recorded variant with its bytes unchanged, reached through a stem and gated by an existing option (test-plan §7, Fake agent: `--framing`'s `paste-<n>` / `clear-<n>` via `ledger::framing_stem` "with no option added"). A new variant such as a recorded `SessionStart` resume, or a compaction pair, follows this path and replaces any rewritten payload.
- Stamps only from `viola verify` against the fake agent, through the rstest `stamped_home` fixture or a harness session (test-plan §7, Seed strategies → `ledger/stamps.json`). Statusline-fed state only through `tests/support/statusline.rs` / `plant_statusline_source` piped into `viola hook statusline` (test-plan §7, Seed strategies → `budget.json` and statusline source rows).
- Literal assert_cmd asserts of verify's human lines and its stderr `unable:` / `hint:` pairs, with no run dir left behind (test-plan §5, Integration Test Strategy, `tests/cli_verify.rs`).

## Anti-patterns to avoid
- Importing `LedgerRow::ALL`, the row ids or the row count as the test oracle (test-plan §11 Unit). Row ids, counts and the older-stamp set are written as literals. Every shape-pinned reader moves with each row: the verdict vector, the stamp's rows object, the older-stamp oracle, the dialog-less summary, the framing-variant list and the harness `LEDGER_ROWS`. A sweep of count literals alone does not cover them.
- Running the real `claude` or `viola verify` against it in CI, or treating a green fake-agent run as proof of real-CLI behaviour (test-plan §11 Test Strategy). The new rows' real-CLI readings are local `--local-live` / live-round measurements only. Never treat a Linux-only reading as proof for Windows or macOS, for example `/bin/sh` having no Windows arm.
- Hand-writing `ledger/stamps.json` or `budget.json`, or changing an insta / trycmd snapshot by interactive review (test-plan §11 Test Data; §11 Universal). Snapshots and fixtures change only through the local `viola verify` fixture refresh, then get committed.

## Contract bindings
- tests ↔ security: §7 (Fake agent) requires the fake agent to spawn an absolute settings `statusLine.command` directly, split on white space, never through a shell. A `/bin/sh` row can therefore not be shown by the fake agent and rests on the live reading. Any new verify child shape (resume start, compaction paste, statusline child, `claude agents` invocation) is bound by security-plan's founder-ratified verify child set before a test can exercise it.
- tests ↔ obs: §3 `run` Output format binds suite `local-live` and its failure codes (`build`, `verify-exit-<n>`, `verify-exit-none`, `row-missing`) to the harness JSON document. §5 (`tests/cli_verify.rs`) requires every verify role-log line to be valid against `schemas/diag-line.v1.json`.
- tests ↔ architecture: the literal row-id lists in `contract_ledger_probes.rs`, `tests/cli_verify.rs` and the harness `LEDGER_ROWS` mirror architecture's capability-ledger row set (§Cross-cutting Patterns, Capability ledger). Each must move with it.

## Acceptance criteria contributions
- `contract_ledger_probes.rs` lists each literal row id, every one the chunk lands included, exactly once, and ends `stamped 2.1.287  <N> pass  0 fail`, with `<N>` the new literal row count (per test-plan §5, Integration Test Strategy).
- `tests/cli_verify.rs` reads `[NN/<N>]` step lines ending at the last added row. Its partial-failure shapes are restated at the new count, and a run without a new row's replay fails only that row (per test-plan §5, Integration Test Strategy).
- Each new row's check has unit cases showing it passes on the recorded shape, fails on a broken post-condition, and fails without a matching capture. The older-stamp oracle reads a stamp missing only the new rows as unverified (per test-plan §4, Unit Test Strategy).
- The `tests/contract_fixture_hygiene.rs` walk and the fake-agent contract suite are green over every newly recorded variant. A live `run --local-live` round ends `stamped <ver>  <N> pass  0 fail` with suite `local-live` passing, run locally and never in CI (per test-plan §7, Fixture hygiene; §3 `run`).
