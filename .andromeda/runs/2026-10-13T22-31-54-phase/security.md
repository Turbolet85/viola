# security extract

## Relevance
relevant — every shape this chunk adds widens `viola verify`'s founder-ratified child set, reaches the stamp that gates dialog decisions, or adds committed fixtures, and two shapes (statusline, `claude agents --json`) touch the only shell-out and an untrusted child-output parser.

## Constraints
- Any new verify child shape (a `--resume` start, a `/compact` paste, a statusline child, a `claude agents --json` invocation) is outside the child set that per security-plan §Threat Model Summary (Attack surface, child process spawning and PATH resolution) is enumerated child by child with each crossing's founder ruling. That section requires every verify child to be a direct spawn (never through a shell) under the R8 strip, with output capped at `MAX_FRAME` into a `Screen` fed under `catch_unwind`, and every paste to be a compiled literal typed only into a settled input box. It also requires that no byte is typed into any dialog, that a modal start is killed with no key, and that viola writes nothing under `~/.claude`. A widening lands only on the founder's own word, asked at P4 with its count. A user-scope status-line reading would mean writing `~/.claude/settings.json` and is banned by the same section.
- Per security-plan §Security Anti-Patterns → Universal, a non-`null` dialog decision flows only when the stamp for the child's CLI version holds every `LedgerRow::ALL` row as `pass`. That section's text pins the set at eighteen (counter `/18`) and states that a stamp holding exactly an older id set, all `pass`, records `cli_verified:false`. Each row added moves that count and that older-stamp rule, and leaves every existing home unverified until its next `viola verify`. Per security-plan §Security Anti-Patterns → Universal, `ledger/stamps.json` is written only by `viola verify`, and `run`'s version gate reads it only through `read_stamps_strict`.
- Per security-plan §Security Anti-Patterns → Code Patterns, local-command lists come only from compiled `viola-agent-claude` ledger rows, never from runtime or upstream text. Listing `/compact` with a post-condition must therefore be a compiled `LOCAL_COMMANDS` entry and a compiled `PostCondition` variant. Per security-plan §Security Anti-Patterns → Code Patterns, `statusline_command` stays the only shell-out, and no second one may be added (a statusline or `/bin/sh` probe must not make viola itself run a shell).
- Per security-plan §Input Validation (Session id as a child argv value), the id after `--resume` is built only by `viola_agent_claude::resume_args`, has the closed `is_session_id` shape, is one argv element of a direct spawn, and appears in no refusal line. The ratified crossing covers an id read from the instance's log or typed with `--id`. Whether a verify probe may put an id it captured from its own child's SessionStart onto a second child's command line (a new source) is a question for P4. Whether `resume_args` can serve the probe as-is is research's question.
- Per security-plan §Input Validation (Hook stdin row, capture arm), the hidden `hook <event> --capture` arm takes only a `HookEvent`, and the word `statusline` is read first and is not one. Capturing a statusline payload (`rate_limits`, the `/bin/sh` reading) through a verify probe is therefore a new capture shape outside the ratified arm, a widening for P4. Per security-plan §Input Validation (Statusline shell-out row), `budget.json` is written only by `hook statusline`, and a probe must not write it.
- Per security-plan §Input Validation (Child process output row), output from `claude agents --json` is read through `Read::take(MAX_FRAME)` and parsed tolerantly, with a failure becoming `unknown`. Per security-plan §Input Validation (Child executable resolution row), `claude` comes from the calling process's PATH under same-user trust (an accepted risk), and an unwrapped row's `name` is never a `ViolaName` or `target`.
- Per security-plan §Data Protection (Repository fixtures), every newly recorded fixture goes through `--record`'s scrub, which replaces the home prefix with `~` and the user word with `<user>`, and the whole recording is refused when a home path, an absolute path, the username or an email survives. The live resume payload's added keys (`scratchpad_dir`, `transcript_path`, `cwd`) carry absolute host paths. Per security-plan §Data Protection (Repository fixtures), probe prompts must be synthetic.

## Patterns to follow
- Run B's compiled paste constants, the newest being `PROBE_NEWLINE_PASTE`. Each is pasted only into rows that hold the input-box literal and no modal literal, waited for up to `PROBE_DEADLINE`, and ended with no key on a modal, a poisoned screen or the deadline (per security-plan §Threat Model Summary, child process spawning and PATH resolution).
- Per-run 0700 probe dirs, each with its own drop guard. A guard removes only what its run created, when verify passes, fails or is stopped by Ctrl-C or TERM, and never by a pattern or a listing (per security-plan §Data Protection, Interactive probe dirs and Probe captures).
- The capture arm's exclusive `create_private_new` claim at 0600 and its `take(64)` closed `ProbeAnswer` read. Every failure ends in exit 0 with nothing printed (per security-plan §Input Validation, Hook stdin row).
- A single product home for each flag literal: `statusline::SETTINGS_FLAG`, shared by `run` and Runs C/D, and `resume_args` for `--resume` / `--fork-session` (per security-plan §Data Protection, Code-bearing artefacts; security-plan §Input Validation, Session id as a child argv value).
- A statusline override document written only on Unix, only for a pinned path made of plain characters, and naming the absolute pinned `viola` path, never one found through PATH (per security-plan §Data Protection, Code-bearing artefacts; security-plan §Security Anti-Patterns → Universal).

## Anti-patterns to avoid
- Adding a shell-out beyond `statusline_command`, or building a local-command list or screen signature from runtime or upstream text (security-plan §Security Anti-Patterns → Code Patterns).
- Using a `claude agents --json` row `name` as a `ViolaName` or `target`, or reading child output without `Read::take(MAX_FRAME)` (security-plan §Security Anti-Patterns → Input).
- Letting a non-`null` dialog decision flow on a stamp that lacks a new row, or letting any process other than `viola verify` write `ledger/stamps.json` (security-plan §Security Anti-Patterns → Universal).

## Contract bindings
- Stamp row set ↔ tests: the older-stamp oracle, the stamp's rows object, the verdict vector, the dialog-less summary and the framing-variant list all pin the row set by shape. They move together with the security-plan §Security Anti-Patterns → Universal count.
- Fixture scrub ↔ tests and obs: recorded fixtures replay under the fake agent in CI. The NEVER-log floor (security-plan §Bootstrap phases, `logging-redaction-wire`: no R8-stripped `CLAUDE*` value in any fixture) binds to obs §9's artifact canary scan.
- Capability ledger ↔ architecture: architecture §Cross-cutting Patterns (Capability ledger) names this entry for the `rate_limits` row. The `budget-paused` gate's reliance on that row binds security-plan §Input Validation (Own state files on read, `budget.json`) to the new row.
- Stamp read ↔ obs: a refused or malformed stamp read is one `parse-rejected{parser:"ledger-stamps"}` line and `cli_verified:false` (security-plan §Input Validation, Own state files on read).

## Acceptance criteria contributions
- A home whose stamp holds exactly the eighteen pre-chunk ids, all `pass`, reads `cli_verified:false`, its hook prints no decision, and `answer` exits 12 `unverified-cli`. The same holds for each intermediate row set the chunk passes through (per security-plan §Security Anti-Patterns → Universal).
- Every fixture file the chunk adds under `fixtures/claude/<cli-version>/` passes `--record`'s scrub, and a search of those files for `/home/`, `/Users/`, `\Users\`, the username and an email shape finds nothing (per security-plan §Data Protection, Repository fixtures).
- No new process spawn goes through `sh`, `bash` or `cmd`. `/bin/sh` appears as a spawn argument only in `viola_agent_claude::statusline::shell_argv` (per security-plan §Security Anti-Patterns → Code Patterns).
- After a live verify round, viola has written no file under `~/.claude` (the CLI's own transcripts are the accepted residual), and every new probe dir is removed on pass, fail and Ctrl-C (per security-plan §Data Protection, Interactive probe dirs).
