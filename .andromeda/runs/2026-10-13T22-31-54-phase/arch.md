## Relevance
relevant — the chunk adds capability-ledger rows and `viola verify` probes, the mechanism arch names as the single gate for CLI-specific behaviour, and the plan already names "Owed ledger rows" as where each of these rows is owed.

## Constraints
- Every relied-on undocumented `claude` behaviour must be a ledger row in `viola-agent-claude` with a `viola verify` probe that checks a post-condition, never an unconditional assumption. The ruled limit "a CLI shape no `send` relies on needs no probe" is the test for whether a row is owed before its consumer exists. The plan names `--resume`, `rate_limits`, the `--settings` statusline override and `/bin/sh` as relied on, outside that limit, and owed to "Owed ledger rows". It records the Windows legs as owed to "Windows-only live measurements" (per arch §Cross-cutting Patterns, Capability ledger as the single gate for CLI-specific behaviour).
- A CLI version is verified only when its stamp holds every landed row as `pass`. Each member added to `LedgerRow::ALL` therefore leaves every older stamp reading `cli_verified:false` until it is re-verified. On an unverified version viola stays transport-only and withholds dialog answers. The plan enumerates the eighteen members in order and the `[NN/MM]` step line with `MM` = `LedgerRow::ALL.len()`. Every one of those has to move with a new row (per arch §Established Decisions [CLI Version Compatibility]).
- `viola verify`'s child set is fixed in the plan: one print-mode probe, then Runs A–D, each a direct spawn under the R8 strip at 80×24. Run B gets five compiled bracketed pastes in a set order, ending with `/clear`. Runs C and D answer dialogs only through the probe hook's `--answers` body. No run writes a byte into a CLI dialog, and a modal start is killed with no key. A resume start, a compaction turn, a statusline child or a `claude agents --json` invocation is a shape outside this set (per arch §Established Decisions [CLI Version Compatibility]).
- `viola-agent-claude` is the only crate that knows Claude payload shapes, `claude agents --json` included. Its `ledger` module stays pure: rows, compiled probe texts, `LOCAL_COMMANDS`, `check`, `framing_variants` and `dialog_variants`. Its `statusline` module reads no file, clock or environment. The stamps file I/O and the settings override stay in `viola-state` and the root bin. A new `viola-state` edge for this crate arrives only with a consumer that needs it (per arch §Infrastructure Patterns → Crate dependency direction).
- A local command fires no UserPromptSubmit, so the ledger has to list each known one with its post-condition or "none" (`ledger::LOCAL_COMMANDS`). A listed command whose post-condition is "none", or that is listed on an unverified version, is typed and answered `ok` / `confirmed:false` / `unconfirmable` with no confirmation window. Nothing else is ever unconfirmable. Listing `/compact` brings it under this rule (per arch §Established Decisions [Delivery Confirmation]).
- `ledger/stamps.json` is written only by `viola verify` through `viola_state::stamps::update_stamps`. Its `rows` maps row id → `pass`/`fail`, and `measured` is additive with no `v` bump. A merge replaces only its own version's entry, and `run` reads no field of `measured`. `run`'s gate reads the file through `read_stamps_strict` (per arch §Standard Contracts, Ledger stamps envelope).
- Which field `claude agents --json` exposes for the join (`child_pid` or `agent_session_id`) is an open ledger row. Its readers (`list`, `mcp`, `ui`, through `viola-agent-claude`) are required to spawn it directly with the npm-shim resolution, and any failure makes `status` `unknown`, never an error. The plan records that no reader spawns it yet (per arch §Standard Contracts, Session liveness).

## Patterns to follow
- The row-landing pattern: a new member of the closed `LedgerRow::ALL` is read by `check(row, &Probes)`. Run B's added texts are compiled literals in `ledger`, waited for one more UserPromptSubmit and one more Stop (`ledger::FRAMING_TURNS`, paste-order stems `paste-1` · `paste-2` · `paste-3` · `clear-1`). Verify prints one step line per row and then `stamped <ver>  N pass  M fail`. A failing row still writes its stamp, and verify exits 1 (per arch §Established Decisions [CLI Version Compatibility]).
- The recorded-variant pattern: `--record <DIR>` writes `<Event>.<stem>-<n>.json` variants only when 0 rows fail. They are scrubbed, refused whole on an `unclean` code (`home-path` · `absolute-path` · `username` · `email`) and walked by `tests/contract_fixture_hygiene.rs`. The fake agent replays them. The plan's committed-set description for `fixtures/claude/2.1.287/` carries a file count beside its rule (per arch §Occupied Resources → Repository).
- The fake agent's argv options are counted by their list. Its `--resume <id>` rewrites the recorded `SessionStart.default` (sets `source` `resume` and the id), and its `--settings` + `--statusline-stdin` serve the statusline tests. A recorded resume capture would be the replacement the scope names (per arch §Occupied Resources → Binary, subcommands and exit codes).
- `viola_agent_claude::resume_args` is the one product home of the `--resume` / `--fork-session` literals (per arch §Occupied Resources → Claude Code integration names).
- CI drives `verify` against the fake agent's print and interactive modes only. The real `claude` probe and `--record` run locally only (per arch §Established Decisions [CI/CD]).

## Anti-patterns to avoid
- Landing a Claude-specific shape or flag literal outside `viola-agent-claude`, or giving its pure `ledger` / `statusline` modules file, clock or environment reads (per arch §Infrastructure Patterns → Crate dependency direction).
- viola shelling out through `sh`, `bash` or `cmd` for a probe. Children are spawned directly, and the only shell-out is `hook statusline` running the user's own command (per arch §Cross-cutting Patterns, Cross-platform discipline).
- A new environment variable or `config.json` key as a probe or test seam. Only the two `fake-agent` seams exist (per arch §Cross-cutting Patterns, Config management).

## Contract bindings
- arch ↔ security: the plan's verify child set is the security plan's founder-ratified verify-children bullet. Any shape added to it is a boundary widening and needs the founder's word.
- arch ↔ tests: `contract_ledger_probes` stamps the committed `2.1.287` set at the row count. `tests/contract_fixture_hygiene.rs` walks every recorded variant. Readers that pin the row set by shape (verdict vector, a stamp's rows object, the older-stamp oracle, the dialog-less summary, `framing_variants`) move with each row.
- arch ↔ obs: a malformed or strict-modes-refused stamp writes `parse-rejected{parser:"ledger-stamps"}` and records `cli_verified:false`. `cli_verified` / `cli_version` go into the snapshot and the `claude-child` `process-start`.

## Acceptance criteria contributions
- Each landed row is a member of `LedgerRow::ALL` with a `check` arm. Verify's step lines read `[NN/MM]` with `MM` equal to the new `LedgerRow::ALL.len()`. A stamp holding only the earlier eighteen ids, all `pass`, reads unverified (per arch §Established Decisions [CLI Version Compatibility]).
- The new rows, their compiled probe texts and any `LOCAL_COMMANDS` entry live in `viola-agent-claude`'s pure `ledger` module. The crate gains no `viola-state` dependency unless a consumer in this chunk needs one (per arch §Infrastructure Patterns → Crate dependency direction).
- Any new recorded capture (for example a SessionStart of source `resume`) is written only by `--record` on a 0-fail round and passes the scrub and hygiene walk. The committed-set count in the plan is updated with its rule beside it (per arch §Occupied Resources → Repository).
- The chunk adds no environment variable, `config.json` key or viola-side shell-out, and CI runs the new rows against the fake agent only (per arch §Established Decisions [CI/CD]).
