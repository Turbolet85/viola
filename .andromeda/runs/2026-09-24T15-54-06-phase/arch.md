## Patterns to follow
- Tree annotation style from architecture.md §Infrastructure Patterns → Project directory structure: one line per artifact with a `#` role comment. Test-only items are marked "test-only" (for example `viola-e2e/`, `src/bin/viola-fake-agent.rs`), and separate workspaces are marked as excluded (`fuzz/`).
- Registration form for gitignored `target/` outputs from architecture.md §Occupied Resources → Repository: each entry names its writer, what it contains, the upload artifact name and retention if any, and "gitignored". Examples are `target/secret-scan/hits.json`, `target/supply-chain/` and `target/deny-probes/`. Any new report dir (for example a release-check output) follows this form.
- architecture.md §Infrastructure Patterns → Build system proves each gate is live: `scripts/deny-probes.sh` and `scripts/lint-probes.sh` each run a negative probe per ban plus a clean control. A new "no test binary in release" check should likewise be shown to fail when a test binary is present.
- `supply-chain` job shape from architecture.md §Infrastructure Patterns → CI/CD approach: ubuntu only, cargo-deny 0.20.2 from taiki-e/install-action, JSON reports in `target/supply-chain/` uploaded as artifact `supply-chain` under `if: always()`. The fuzz-lock audit step joins this job.
- Gate verdict aggregation through `viola-harness gate --require …` (architecture.md §Infrastructure Patterns → CI/CD approach, `test`, `msrv` and `fuzz-replay` jobs). A new gate joins by adding its `--require` token.

## Anti-patterns to avoid
- Registry over-reach (the amendment-history precedent): do not register config files or tree-only directories as §Occupied Resources rows. `e2e-web/`, `a11y/sr-pass/` and `viola-ui/assets/` go in the §Project directory structure tree. Only resources that viola or the harness write or read at run time go in Occupied Resources (per architecture.md §Occupied Resources; amendments on `tests/support/` and the supply-chain config files).
- Letting `fuzz/` or its libfuzzer-sys C++ build into the root graph: no `fuzz` in root `members` and no `--workspace` pass that pulls it in (per architecture.md §Established Decisions [Module Boundaries]; §Infrastructure Patterns → Build system).
- Checking the tokio ban with `--exclude` over the workspace or with a direct-parent `wrappers` allowlist (per architecture.md §Infrastructure Patterns → Build system).
