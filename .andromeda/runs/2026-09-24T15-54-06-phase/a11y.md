## Relevance
Partial. This chunk only lists a11y artifacts in the architecture tree (items 2 and 6) and edits `ci.yml`, where a11y has pipeline placement rules. It builds no UI surface, so no WCAG, focus, contrast or ARIA mandate is exercised here.

## Constraints
- The architecture's tree, workspace wording and dependency policy must name every a11y-owned path the plan requires. Per a11y-plan §3 Bootstrap phases (a11y-tooling-install, screen-reader-test-spec-setup, a11y-ci-gate-wire, violation-json-emission-wire), those paths are:
  - `e2e-web/fixtures/a11y.ts`, `e2e-web/.htmlvalidate.json`, `e2e-web/eslint.config.js`, `e2e-web/a11y/sc-coverage.json`;
  - `e2e-web/test-results/{a11y,lint}/`;
  - `a11y/sr-pass/TEMPLATE.json` and `a11y/sr-pass/<date>-<at>.json` (per a11y-plan §3 Screen reader test pattern → Manual pass spec format);
  - `crates/viola-ui/assets/index.html`, following the workspace `crates/<name>` layout.
  Which of these HEAD's architecture already lists is research's question.
- `e2e-web/schemas/a11y-row.v1.json` is owned by tests and is a different file from the obs `schemas/diag-line.v1.json`. The tree must not merge them or place a11y rows under root `schemas/` (per a11y-plan §3 Structured violation JSON schema → Binding fields; §12 D-A11Y-09).
- a11y rows are harness test artifacts only. They are written under `e2e-web/test-results/a11y/`, never to `<home>/diagnostics/`, and never emitted by the viola binary (per a11y-plan §3 Structured violation JSON schema → Emission location). This supports the chunk's "release build free of test-only binaries" goal: no a11y harness code or output belongs in release output.
- In `ci.yml`, the web a11y work runs only on the ubuntu leg: the lint stage (eslint-plugin-lit-a11y and html-validate) runs before `run --browser`, and the aggregation and upload steps run after the gate with `if: always()`. It adds no new harness `suite` value (per a11y-plan §9 Per-pipeline-stage table; §12 D-A11Y-14). The chunk may add a release-build job or cargo-tree/modules steps to the per-OS `lint` job. Those must not reorder or displace the a11y lint step's planned position once it lands.
- `ci.yml` is the only push/PR workflow for a11y, and `nightly.yml` carries no a11y step (per a11y-plan §9 Platform). The `supply-chain` fuzz-audit addition must not bring an a11y step into nightly, or move one there.
- For the TypeScript-plane decision (item 6), a11y's TypeScript files are `e2e-web/fixtures/a11y.ts` and the a11y specs in `e2e-web/tests/*.spec.ts` (e.g. `bay-steady-state.spec.ts` holding `a11y-tokens` / `surface-absence`). The Lit sources in `crates/viola-ui/` are linted by ESLint from `e2e-web/`, with no JS build step (per a11y-plan §3 Bootstrap phases → a11y-ci-gate-wire; §3 Contrast verification harness). The plan requires no TS code-graph plane; whether and when one exists is outside a11y's authority.

## Patterns to follow
- a11y specs are ordinary files in `e2e-web/`, run through `scripts/agent-run.* run --browser` → `npx --prefix e2e-web playwright test` under `gate --require playwright` (per a11y-plan §3 CI integration). The tree listing should describe `e2e-web/` as the single place for tests and a11y code, not a separate a11y package.
- a11y lint configs live in `e2e-web/` so plugins resolve from `e2e-web/node_modules`. The html-validate target is the `assets/index.html` that `viola-ui` embeds (per a11y-plan §3 Bootstrap phases → a11y-ci-gate-wire).
- `actions/upload-artifact` v7.0.1 is SHA-pinned per zizmor and uploads `e2e-web/test-results/` with `if: always()` (per a11y-plan §9 Artifact retention). Any new upload step this chunk adds, such as for a release build, should follow the same pinning convention.

## Anti-patterns to avoid
- Adding a `suite` value such as `a11y`, a `webServer`, or a separate `npm test:a11y` driver while wiring new CI gates or `viola-harness gate` entries (per a11y-plan §11 CI).
- Running `--browser` on the Windows or macOS legs, or treating `browser-missing` as a skip, when restructuring per-OS jobs (per a11y-plan §11 CI).
- Writing a11y violation rows into `<home>/diagnostics/`, or listing them as a product artifact in the tree or report-dir inventory (per a11y-plan §11 Universal).
