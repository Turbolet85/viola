# tests extract

## Relevance
relevant — the chunk is test-harness and E2E-layer work: the 5-command `boot` / `run` / `status` surface, the first `path_` E2E binary, and the Path 1 and Path 6 scenarios.

## Constraints
- `run --e2e` runs step 2's E2E filterset as suite `nextest-e2e`. `--all` and the default selection run it after step 1. Once the first E2E-prefixed binary exists, the integration layer becomes `kind(test) & !binary(/^(path|tui|mcp|cross|chaos|contract)_/)`. A `binary()` regex that matches no binary is a filterset parse error, so the exclusion goes in together with the first binary. A root `tests/*.rs` stem that matches one of the six prefixes would leave the integration layer; whether one exists today (§6 names `tui_wheel` and `chaos_*`) is research's question (per test-plan §3 `run`, steps 1–2).
- Each E2E scenario picks its fixture by its §6 Cleanup line. Path 1 ("TempDir drop", a test-owned outer PTY) uses the `viola_e2e::fixtures` chain `home → fake_agent_path → stamped_home → booted_wrapper`, which lands with this first consumer against the same contract as the sync root copy. Path 6 ("harness `cleanup`") uses `harness_session`. That fixture always skips boot step 1, takes its bin dir from the test executable's own target dir and never from `CARGO_BIN_EXE_*`, uses the session id `<test name>-<label>-<pid>`, and has its `session.cleanup()` report asserted with no `false` field. No test shells out to `agent-run` / `viola-harness` (per test-plan §3 `run`, step 2).
- With no `--instance` flag, `boot`'s instances stay `overseer` and `builder`. `--statusline-echo` runs before boot step 5 and writes `<home>/statusline-source.json`, naming `<bin dir>/viola-fake-agent[.exe] statusline-echo` and appending to `<home>/fake/statusline.marker`. `--agents-mode recorded|oversize|malformed` defaults to `recorded`, writes the fake agent's `agents-mode` file beside `target/agent-run/<session>/bin/claude[.exe]`, sets no env var, and is recorded in `session.json` and `supervise.json` (per test-plan §3 `boot`).
- `status` runs `viola list --json --home <home>` on the harness `PATH` and nests the verbatim document as `list`. `state` is `ready` when every booted instance reads `liveness:"live"`, `degraded` when any item is `stale`, and `down` when `list` exits non-zero. `ok` is true only for `ready`. Exit is 0 for ready, 1 for degraded or down (the document still printed), and 2 for `unknown-session` (per test-plan §3 `status`, and §3 Status endpoint shape). `last_error` takes only `null` or `list-exit-<code>`; any new value needs a Decisions Log entry (per test-plan §3 Closed enums).
- Path 1 covers steps 1–6 whole on its listed surfaces (tui, ipc-internal, cli `list --json`). The squat in step 4 binds the computed endpoint name through the interprocess server API before `run`. The `settings.json` half of step 5 is Unix-only, and its Windows branch writes no file (per test-plan §6 Path 1). The squatter never uses `try_overwrite` (per test-plan §8 Mocking libraries, Fake servers row).
- Path 6 step 7's two-instance leg re-feeds `five_hour` 91, runs `release builder --budget --json` only, reads `list --json`, then sends to both instances. Its signals are: `.ok.budget.paused` stays true; `builder` `budget_paused:false` and `overseer` true; `builder`'s snapshot carries `budget_override_until`; one `budget-gate{paused:false, override_until}` record for `builder` only; `send` exits 0 to `builder` and 11 `five-hour` to `overseer`; and `override_until` is later than the record's `ts` and equals the snapshot's. Override expiry is not driven here, and no wrapper starts mid-session (per test-plan §6 Path 6).
- The base `target/e2e-home` is prepared only through `Workspace::ensure_e2e_home`. A plain base is created as a directory. On Unix a linked base needs an absolute target: when the target is gone it is made at 0700 with one non-recursive create, and the base is accepted only when one `lstat` reads a real owner-only directory. A refused base reads `reason:"build-failed"` and no new reason is added. This is the contract the dangling-link CARRY 5 case must survive (per test-plan §3 `boot`, step 2).

## Patterns to follow
- The root statusline helpers `plant_statusline_source`, `statusline_marker` and `statusline_echo_command` (`tests/support/home.rs`). The statusline source is written by the test and only read by viola; `budget.json` comes only from statusline stdin piped into `viola hook statusline` (per test-plan §7 Seed strategies).
- The `claude agents --json` fake: `viola-fake-agent` copied as `claude` into a test-scoped bin dir, answering from the `agents-mode` / `agents-rows.json` files and the `sessions/<pid>.json` registry beside its exe. Every test-started `list` runs under a test-scoped `PATH` (per test-plan §7 Seed strategies).
- The root `booted_wrapper` wait: staged readiness (`process-start` for `self` and `claude-child`, then the fake agent's `start` receipt, then snapshot and heartbeat). It is bounded by `WITHIN` (7 s, below the `mutants` profile's 10 s kill), fails at once when the wrapper exits first, and its stop waits for `wait_endpoint_gone`. The `viola-e2e` copy holds the same contract (per test-plan §3 `run`, step 2).
- The `Booted` guard in `crates/viola-e2e/tests/harness_lifecycle.rs`. On drop, even after a failed assertion, it runs `cleanup(.., keep_homes = true)` and then removes the home unless `AGENT_RUN_KEEP_FAILED=1` and the thread is panicking (per test-plan §3 Test data bootstrap).
- An OS-split assertion is written `cfg(unix)` with its Windows branch stated: the marker equality and the `settings.json` override are Unix's, while exit 0 with empty stderr holds on every OS (per test-plan §6 Path 6, verification signal).

## Anti-patterns to avoid
- `sleep(N)` for synchronisation, parsing the child screen, detecting exit by master EOF, or calling `assert_cmd .assert()` on the long-lived `viola run` (per test-plan §11 E2E).
- Hand-writing `ledger/stamps.json`, `snapshot.json` or `budget.json` in a booted-wrapper test. The same applies to harness-side plants beyond the statusline source and the `agents-mode` file the contract names (per test-plan §11 Test Data).
- `std::env::set_var` in tests. Env is set per child with `Command::env`, which is also why `--agents-mode` sets no env var (per test-plan §11 Integration).

## Contract bindings
- tests ↔ architecture: `status`'s nested `list` member is the verbatim `viola list --json` document (architecture §Standard Contracts, the `list` payload). Its polled per-item and envelope fields are those named in test-plan §3 `status`.
- tests ↔ obs: harness and `viola-e2e` fixture homes live under `target/e2e-home/` so that obs-plan §9's G2 zero-panic gate, the G4 `schema-check`, the `secret-scan` and the `diag-<os>` upload read them (test-plan §3 `boot`, step 2). Path 6's `budget-gate{paused:false, override_until}` record is an event-catalog shape (obs-plan §6).
- tests ↔ CI: in CI the instrumented `run --coverage` replaces the nextest invocations of steps 1 and 2, so the new `path_` binary runs under it, and the test job gates `coverage,doctest` (test-plan §9, Coverage report row). Whether `ci.yml` or `gate --require` names `nextest-e2e` anywhere is research's question (`gate::SUITES` already lists it, test-plan §3 `gate`).

The WATCH case `send_under_the_paste_hint_a_human_key_during_the_gate_wait_wins` stays red-on-recurrence (per test-plan §10 Coverage thresholds and Zero-flakiness budget).
