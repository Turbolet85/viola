# a11y extract

## Relevance
partial: the chunk adds no UI surface. It touches a11y in three ways: it moves where the cli / tui output-discipline cases run (the `nextest-e2e` selector and the integration layer's `!binary(…)` exclusion); Path 1's `path_` binary drives a `viola run` start under a test-owned outer PTY (the tui boundary); and Path 6's harness leg refuses a `send` while the human path must stay open.

## Constraints
- a11y-plan §9 CI Integration requires the CLI output-discipline and TUI boundary cases to stay ordinary nextest cases inside `nextest-integration` / `nextest-e2e` locally, and inside the per-OS `test` job's single instrumented `coverage` suite in CI, on all three OS legs. Re-cutting the integration filterset must not drop any of them from every suite the gate reads.
- a11y-plan §3 CI integration (key file) requires no new `suite` enum value and no separate driver: `run --e2e` adds only the existing `nextest-e2e` value, and a11y adds no rows of its own to the `run` JSON.
- a11y-plan §3 Keyboard test harness (key file) names a11y boundary cases in root files whose names match the E2E regex `^(path|tui|mcp|cross|chaos|contract)_`: `tests/tui_passthrough.rs` (`passthrough_with_a_statusline_source_adds_no_viola_bytes`) and `tests/chaos_revive.rs` (the kill-and-revive case). a11y-plan §4 P6 names `tests/cross_list_rows.rs` too. This contradicts the scope's `[inferred]` "no root `tests/` file name starts with one of the six prefixes". Whether those files exist at HEAD, and so move from `nextest-integration` to `nextest-e2e` once the exclusion is switched on, is research's question.
- a11y-plan §1 A11y Scope Summary (tui entity) requires that a `viola run` start writes zero bytes of its own to the terminal and never blocks, refuses or delays a human keystroke past the current atomic paste. Path 1's outer-PTY start falls under this boundary, even though §1 does not carry Path 1 as an a11y path ("Not carried as paths").
- a11y-plan §8 Timeout extensions requires the budget pause to bind the driver only: an automated `send` is refused `budget-paused` / `five-hour` (exit 11) with nothing typed, and no key is blocked, refused or delayed. The same section requires `viola hook statusline` to exit 0 with empty stderr in every case, which covers the `--statusline-echo` feed.
- a11y-plan §8 Error recovery requires every human-mode refusal to print `unable  <reason>  <detail>` on stderr with `hint:` as the last stderr line and a typed exit code, and requires `--json` to carry no hint. This covers Path 6's exit-11 `send` to `overseer` in whichever mode the leg uses, and `viola list`'s exit-21 pair if `status` reads one.
- a11y-plan §1 A11y Scope Summary (cli entity notes) requires no SGR, glyph or cursor control under `--json` or non-TTY. The `list --json` document that `status` nests verbatim is a `--json` stream.

## Patterns to follow
- The outer-PTY zero-viola-bytes reading per a11y-plan §3 Keyboard test harness: on every leg, check that none of viola's own literals (`unable`, `hint:`, refusal text) appear. On Linux and macOS, also compare byte for byte with an unwrapped fake-agent run. On windows-2025, check only that the literals are absent (ConPTY host bytes, both backends). Path 1's `path_` binary can reuse this shape for its start.
- The closed-gate keyboard reading per a11y-plan §3 Keyboard test harness (`path6_a_reading_over_the_threshold_refuses_the_send`, `tests/cli_budget.rs`): with the automated `send` refused, a human key still reaches the child, and the outer-PTY stream holds none of `unable`, `hint:` and `budget-paused`. The harness-session Path 6 leg re-asserts the driver side (exit 11 / exit 0). The human-side reading is already held at the root tier.
- Sequencing on log records, never a timer, per a11y-plan §3 Keyboard test harness (the `channel-request` line and the `wheel` record). This applies to any new outer-PTY step in Path 1.
- `cfg(unix)` gating with the Windows branch stated, per a11y-plan §6 Visual Design Verification (the windows-2025 check is literal absence). This is the shape for the statusline marker assertion that is Unix-only.

## Anti-patterns to avoid
- a11y-plan §11 CI: never add a `suite` value (such as `a11y`) or a separate a11y driver outside `scripts/agent-run.* run`.
- a11y-plan §11 SLO: never use a retry-once policy. The WATCH red (`send_under_the_paste_hint_a_human_key_during_the_gate_wait_wins`, the a11y P4 keyboard case per §3 Keyboard test harness) is never closed by a green re-run or by a retry in the new `nextest-e2e` profile.
- a11y-plan §11 Universal: never parse the rendered `claude` TUI screen for content (R7). Path 1's readiness and Path 6's legs read logs, snapshots and exit codes, never screen text.

## Contract bindings
- a11y ↔ tests §3 `run` (`5-command-implementation.md`): the a11y cases' location is the integration / E2E filtersets. a11y-plan §9 CI Integration binds to the `nextest-e2e` suite and to CI's `coverage` suite. Whether the CI `coverage` suite's filterset already includes E2E-prefixed binaries is research's question.
- a11y ↔ tests §3 Status endpoint shape: `status` nests `viola list --json` verbatim. a11y-plan §1 A11y Scope Summary (no SGR under `--json`) applies to that document.
