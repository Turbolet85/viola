# security extract

## Relevance
partial. The chunk adds no product surface. Its security weight sits in four places: the test-side home base under `target/e2e-home` (CARRY 5), the session-home files the new boot flags write, the Path 1 steps that exercise local-boundary controls (squat, tamper, rewrite), and the Path 6 leg's `release --budget` and its strict-modes-gated `viola list` read.

## Constraints
- A test-side removal under `target/e2e-home` may take only a directory the test side itself created: the owner sweep, a test home's own `TempDir`, or harness `cleanup` by the `viola-session-` name. The two keepers (`prepare_home_base`, `Workspace::ensure_e2e_home`) follow a linked base only when its target is absolute and one `lstat` reads a real directory with no group or other bit. A target that is itself a link is refused, with a fixed message that names no path. The keepers create the target at 0700 through the directory builder (no chmod afterwards, no parent) and remove nothing. So the CARRY 5 fix must go through a keeper, never a bare `create_dir_all` over the link (per security-plan §Security Anti-Patterns → Code Patterns, the `target/e2e-home` entry).
- Every directory and file the harness creates under a session `--home` is created at 0700 / 0600 explicitly, never under the umask. This includes `<home>/statusline-source.json`, written by `boot --statusline-echo` (per security-plan §Security Anti-Patterns → Data Protection). `viola list` refuses the whole board with exit 21 when the home or `instances/<name>/` grants any group or other bit, or when a trusted file fails the check. A badly created home would therefore read `down` / `list-exit-21`, not `ready` (per security-plan §Authentication & Authorization, `~/.viola/` access control, the `list` clause and the read rule).
- The planted statusline source must have the shape `run` accepts: a `statusLine` of type `command`, non-empty, with no NUL, read through `take(MAX_FRAME)`. viola only reads it and records the command only in `snapshot.json`. A source of another shape gives no command and logs no line (per security-plan §Input Validation, Statusline source row). The command runs only through `hook statusline` as `/bin/sh -c <command>`, on Unix only, after `check_instance`. On Windows no command runs, so the marker assertion is `cfg(unix)` (per security-plan §Input Validation, Statusline shell-out row).
- `budget.json` is written only by the `hook statusline` arm (per security-plan §Input Validation, Hook stdin row). The Path 6 re-feed of `five_hour` 91 must go through `viola hook statusline`, never a direct harness write of `budget.json`.
- `viola release` sends `from` from `VIOLA_NAME`. A `release` carrying a string `from` is refused `-32602` `release-from-driver` (CLI exit 20) before `budget` is acted on, and lifts nothing (per security-plan §Authentication & Authorization, Driver-originated release row). The leg's `viola release builder --budget --json` must therefore run with no `VIOLA_NAME` in its environment. Whether the harness already clears `VIOLA_*` from the verbs it spawns is research's question.
- `status`'s `viola list` read spawns `claude agents --json` directly under the R8 strip, reads stdout through `take(MAX_FRAME + 1)`, and kills it at 5 s. A failed, oversize or malformed read leaves the board as `board::read` gave it (STATUS `unknown`, no unwrapped row) and `list` still exits 0 (per security-plan §Input Validation, Child process output row). So `--agents-mode oversize|malformed` must not by itself turn `status` into `down`.
- Any dependency `viola-e2e` gains for the squat step (an interprocess listener) comes from `[workspace.dependencies]`, and `cargo deny check` still passes over the root `Cargo.lock` (per security-plan §Dependency Security, Pinning and `deny.toml` additions). `viola-e2e` is test-only. The tokio ban is per sync crate (`deny-sync.toml`), and the E2E suite runs with `viola/fake-agent`, a feature `scripts/release-check.sh` refuses in a release artifact (per security-plan §Dependency Security, CI integration).

## Patterns to follow
- Home-base preparation goes through `Workspace::ensure_e2e_home` (harness) or `prepare_home_base` (`tests/support/home.rs`), the two keepers named in security-plan §Security Anti-Patterns → Code Patterns. A witness for a dangling link reads red before the fix.
- Owner-only creation goes through `viola_state::fs::create_private_dir` (protected user + SYSTEM DACL on Windows) and `viola_state::fs::replace_private` (mode set on the temp file before any byte). Then a tree laid under a test home passes `check_instance` on all three runners (per security-plan §Security Anti-Patterns → Code Patterns, the `run --mutants` entry; §Authentication & Authorization, `~/.viola/` access control).
- The fake agent's agents mode is a file beside `target/agent-run/<session>/bin/claude[.exe]`, never an environment variable. The only non-`VIOLA_*` variables any `viola` build reads are the two `fake-agent` seams (per security-plan §Security Anti-Patterns → Universal, the env-var carve-outs).
- Path 1's squat step relies on `run`'s exclusive bind: Windows `FILE_FLAG_FIRST_PIPE_INSTANCE`, Unix `try_overwrite` off. A held name gives exit 1. On Unix the endpoint is `<per-user 0700 dir>/viola-<h12>.sock`, so the squatter binds there (per security-plan §Authentication & Authorization, IPC access control (Windows) and (Unix) rows). Whether `viola-e2e` can reach the endpoint-name function is research's question.

## Anti-patterns to avoid
- NEVER call a plain `create_dir_all` over `target/e2e-home`, follow a link whose target is not an absolute owner-only directory, or remove a directory the test side did not create (per security-plan §Security Anti-Patterns → Code Patterns).
- NEVER add a new environment-variable seam for the harness flags (`--agents-mode`, `--statusline-echo`) without a Decisions Log entry, and NEVER let a `fake-agent` seam reach a release build (per security-plan §Security Anti-Patterns → Universal).
- NEVER add a second shell-out. `statusline_command`, run by `hook statusline`, is the only one, and the harness and the `path_` binary spawn `viola` and the fake agent directly (per security-plan §Security Anti-Patterns → Code Patterns, R1 entry).

## Contract bindings
- security ↔ obs/tests: the new `nextest-e2e` JUnit report and the `status` document (which nests `viola list --json` verbatim) land under `target/agent-run/`. That tree is read by the `viola-harness secret-scan` canary scan against the NEVER-log floor, and scan-gated uploads wait for it (security-plan §Secret Management, Secret scanning in CI; obs-plan §9; test-plan §3).
- security ↔ tests: the `target/e2e-home` link backing is a founder-ratified boundary widening (security-plan §Security Anti-Patterns → Code Patterns), and test-plan §3's `boot` step 2 (`ensure_e2e_home`) is its harness half.
- security ↔ tests: `status`'s `down` / `list-exit-21` derivation reads `list`'s whole-board refusal shape `{"v":1,"error":"instance-unreachable","detail":null}` (security-plan §Authentication & Authorization, `~/.viola/` access control) under test-plan §3's Status endpoint shape.

## Acceptance criteria contributions
- The CARRY 5 case runs green with `target/e2e-home` a dangling link: it re-makes the target at 0700 through `Workspace::ensure_e2e_home`, refuses a non-absolute or linked target with a fixed message that names no path, and removes only directories it created. Its witness reads red on the pre-fix `create_dir_all` path (per security-plan §Security Anti-Patterns → Code Patterns).
- After `boot --statusline-echo`, `<home>/statusline-source.json` reads mode 0600 inside a 0700 home on Unix, and the booted pair's `status` reads `ready`: `viola list --json` passes its strict-modes scan, not exit 21 (per security-plan §Security Anti-Patterns → Data Protection; §Authentication & Authorization, `~/.viola/` access control).
- The Path 6 two-instance leg's `viola release builder --budget --json` runs with no `VIOLA_NAME` and exits 0. A control run with `VIOLA_NAME` set exits 20 `release-from-driver` and leaves both instances' budget fields unchanged (per security-plan §Authentication & Authorization, Driver-originated release row).
- Path 1's tamper step: a pinned `bin/<version>-<hash>/viola` whose bytes no longer hash to `<hash>` refuses the start with exit 1. Each start rewrites `plugin/<version>-<hash>/` and, on Unix, `instances/<name>/settings.json`, and every exec `command` they carry is the absolute pinned path (per security-plan §Data Protection, At rest, Code-bearing artefacts).
