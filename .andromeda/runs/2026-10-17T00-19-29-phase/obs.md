## Relevance
partial — the chunk builds test-layer surfaces (the `path_` E2E binary, `run --e2e`, `boot` flags, `status`'s `list` member) and changes no product instrumentation, but its new homes, the `status` document and the Path 1 / Path 6 signals sit on obs gates and contracts.

## Constraints
- Every viola home a new `path_` case or harness session creates lives under `target/e2e-home/`, so G2, G4, the secret scan and the `diag-<os>` upload cover it; the only home allowed outside that root is `tests/chaos_feed_panic.rs`'s `outside_scan()` carve-out, and homes are kept (`AGENT_RUN_KEEP_HOMES=1`) until the gate steps have read them (per obs-plan §9 Pipeline integration, Integration / E2E rows, and §9 Step order and conditions, step 1). Whether Path 1's "TempDir drop" fixture is rooted under `target/e2e-home/` is research's question.
- `agent-run status` derives stall detection only from `viola list --json`'s `liveness`: `state: degraded` when any item is `stale`. The flip is a heartbeat older than 5 s (4.9 s live, 5.1 s stale or gone), and no process logs a liveness transition, so the new `status` → `list` path adds no tick or transition line anywhere (per obs-plan §3 Heartbeat ticks).
- `viola list` run by `status` writes its `cli.list` process log, and its `agents-probe` `process-start` / `process-exit` pair, into `cli-<name>.ndjson` only after its strict-modes scan passes and only under a parsed `VIOLA_NAME`. A refused scan (exit 21) opens no role file and writes no line. A `claude agents --json` row is never logged verbatim, only `parse-rejected{parser:"claude-agents-json"}` counts (per obs-plan §4 Instrumentation per surface, cli row; §6 Boundary-call wrappers; §8 PII Scrubbing data classification table). Whether the harness `status` sets `VIOLA_NAME` for that `list` run, which decides whether a role file appears in the session home, is research's question.
- Path 1's product order `wheel{cause:"start"}` → `budget-gate` → `session-start{source:"hook"}` is checked from `events.ndjson` through `agent-run logs --kind`, never duplicated into process logs. The start-refusal steps (duplicate `run`, squat, tamper) end in one `process-exit{subject:"self", exit_code:1, detail}` with `detail` ∈ `already-live|squatted-name|pinned-hash-mismatch`, and carry no path or pid (per obs-plan §4 Scenario: `viola run` start sequence to child spawn; §6 `detail` code catalog).
- On Path 6's two-instance leg, `release --budget` gets no span and no line of its own: its trace is the `channel-request` / `channel-response` pair of method `release`, the `budget-gate` record and the snapshot's two budget fields. A `budget-gate` record is appended only when the triple (paused, window, override end) changes. The refused `send` is `send-refused{refusal:"budget-paused", detail:"five-hour", window, used_percentage, resets_at, paused:true}` with client `exit_code:11` (per obs-plan §4 Scenario: Budget governor).
- The statusline feed through `viola hook statusline` writes `hook-invoked{hook_event:"statusline"}` / `hook-decision{hook_event:"statusline", budget_written, duration_ms}`. The `statusline-shell` process pair appears only where a shell is built (never on Windows). `statusline_command` reaches no span or line (per obs-plan §4 Scenario: Budget governor; §8 PII Scrubbing data classification table).
- `viola-harness` (`crates/viola-e2e`) and the fake agent are exempt from the print bans, because the harness prints exactly one JSON document per command on stdout. The exemption is `viola-e2e`'s own `[lints.clippy]` table without `print_stdout` / `print_stderr`. Product crates keep the ban (per obs-plan §3 Bootstrap phases, `obs-ci-gate-wire`; §11 Logs).

## Patterns to follow
- Read signals through `agent-run logs`, the merged ndjson (`{"src":"events",instance,offset,record}` / `{"src":"diag",file[,instance],record}`), with the canonical `jq` selects: follow one send by the target's `instance` + `event` + `corr`, and list errors excluding `detail-*` files (per obs-plan §3 Snapshot / paste-to-AI integration).
- Count panics in merged output with `select(.record.event=="panic" and (.file|startswith("detail-")|not))`, over home-level role files only (per obs-plan §10 Always-required SLO invariant, counting rule).
- G2's scope starts at `target/e2e-home/` with a trailing slash, so a scope that is a link to a directory is descended (the Linux dev host's tmpfs link). The CARRY 5 dangling-link fix keeps that link shape intact rather than replacing it (per obs-plan §9 Gate commands, G2 comment; §3 Log file location, Rotation).
- Unix-only signals of the statusline shell-out (the `statusline-shell` pair, and the marker it drives) are asserted under `cfg(unix)`, with the Windows branch stated as "no shell built" (per obs-plan §4 Scenario: Budget governor, Required log fields).
- Waits key on hook events and `events.ndjson` offsets, never on sleeps or screen content (per obs-plan §10 Standard+ invariants, Deterministic emission).

## Anti-patterns to avoid
- NEVER add a retry-once policy for a flaky telemetry assertion. This applies to the WATCH red on the `cli_send` paste-hint case and to any new leg's red (per obs-plan §11 SLO).
- NEVER create a test home outside `target/e2e-home/` beyond the one ratified chaos carve-out, because a hook panic exits 0 and would go uncounted (per obs-plan §9 Pipeline integration, Integration tests row).
- NEVER lose the failing job's diagnostics: G2, G4 and the secret scan stay `if: always()`, and the harness capture into `target/agent-run/` runs before the scan (per obs-plan §11 CI).

## Contract bindings
- obs ↔ tests §3 Status endpoint shape: `state` (`ready` / `degraded` / `down`) is the agent's stall-detection surface over `list --json` `liveness` (obs-plan §3 Heartbeat ticks); the gauge `liveness` via `agent-run status` (obs-plan §5 Metric instrument types).
- obs ↔ tests §3 `boot` readiness stage `start_records` (`events.ndjson` lines 1-3, missing code `<name>:events`) (obs-plan §4 Scenario: `viola run` start sequence to child spawn).
- obs ↔ CI / tests: G2 (zero panics) and G4 (schema conformance against `schemas/diag-line.v1.json` / `schemas/diag-detail.v1.json`) read every new home's role and detail files, including the new `nextest-e2e` suite's homes (obs-plan §9 Gate commands).
- obs ↔ security: the `harness-<os>` artifact's `target/agent-run/status.json` now nests the verbatim `list` document and is secret-scanned before upload. Every input stays synthetic and carries the canary (obs-plan §9 Telemetry artifact handling; §8 PII Scrubbing, Integration points item 5).
