## Patches

### Patch 1: Worker-scoped Playwright sessions and the cross-runner ownership rule
**Reason:** Downstream Readiness and Cross-Surface Coordination. `globalSetup` has no worker index and cannot pass per-scenario instance flags. The `Playwright:` bullets inside Rust scenarios have no execution path.
**Old:**
```
  3. Browser: `npm ci --prefix e2e-web`, then `npx --prefix e2e-web playwright test`. Playwright `globalSetup` calls `agent-run boot --session pw-<worker>` and `globalTeardown` calls `agent-run cleanup --session pw-<worker>`.
```
**New:**
```
  3. Browser: `npm ci --prefix e2e-web`, then `npx --prefix e2e-web playwright test`. Playwright `globalSetup` runs once, in the main process, and only performs boot step 1 (`cargo build --workspace --features fake-agent`). It has no worker index, so it never boots a session.
     - Sessions are worker-scoped. A worker-scoped fixture runs `scripts/agent-run.sh boot --session pw-<spec>-<workerIndex> <that spec's --instance / --ui flags>`, and on teardown `scripts/agent-run.sh cleanup --session pw-<spec>-<workerIndex>`. Both must return `ok:true`.
     - Cross-runner rule for §6: every `Playwright:` verification bullet in a Rust `path_` or E-scenario is owned by a test in the spec that the scenario names, and the test title contains the scenario id (for example `path2`) so `--grep path2` selects it. That test boots its own session with the scenario's instance flags. It drives the scenario's CLI steps itself, running `viola <verb> --home <session home> --json` through `child_process` with the home read from `session.json`. In that same session it asserts both the CLI exit code and `--json` result and the DOM state for the same event. The DOM line is found by the unique text the test sent.
     - The Rust scenario owns every non-DOM bullet. No Rust test drives Chromium, and no spec observes a nextest-owned session.
```

### Patch 3: Close the log `event` enum and fix which `corr` each event carries
**Reason:** Downstream Readiness. The harness greps an open, example-only `event` list, and which correlation id each event carries is ambiguous.
**Old:**
```
  - `event` (a kebab-case event type, for example `channel-request`, `hook-invoked`, `dialog-raised`, `send-confirmed`).
  - `process` (`run|hook|mcp|ui`) and `instance` (a `ViolaName` or null).
  - A correlation ID `corr`: the channel request `id`, `dialog_id` or send `cursor`.
```
**New:**
```
  - `event`, a closed kebab-case enum. A new value needs a Decisions Log entry, like the §3 closed enums. Each value fixes what its `corr` holds:
    - `channel-request`, `channel-response`: `corr` = the JSON-RPC request `id`
    - `dialog-raised`, `dialog-answered`: `corr` = `dialog_id`
    - `hook-invoked`, `hook-decision`: `corr` = `dialog_id` for dialog hooks, otherwise null
    - `send-issued`, `send-confirmed`, `send-refused`: `corr` = the send `cursor`
    - `process-start`, `process-exit`, `http-request`, `panic`: `corr` = null
  - `process` (`run|hook|mcp|ui`) and `instance` (a `ViolaName` or null).
  - `corr` is copied unchanged as a JSON number or string. It is never renamed (for example to `correlation_id`).
```

### Patch 7: Real perf-gate semantics (columns, warm-up, perf build, final verdict, constant, exclusions)
**Reason:** Performance Budget Coverage.
- The headers promise percentiles that are never computed.
- No warm-up is stated, and no non-instrumented build.
- There is no rule against reruns.
- There is no rule for replacing the provisional value with the product constant.
- The SSE row waits in real time, which breaks the §11 Universal ban.
- Some perf-critical paths are neither covered nor excluded on purpose.
**Old:**
```
The gate is on the `max` sample: Claude Code hook deadlines are hard cutoffs. p50 and p95 are reported for trend only. The p99 column equals `max` over the listed runs.

| Path / operation | p50 | p95 | p99 |
|------------------|-----|-----|-----|
| `viola hook session-end` (fixture stdin, live wrapper) via `hyperfine -N --runs 30 --export-json` per OS | reported | reported | gate: `max < 1.0 s` (`jq -e '.results[0].max < 1.0'`) |
| Spine hooks `session-start`, `user-prompt-submit`, `stop` (same method, `VIOLA_NAME`/`VIOLA_DIR` exported to hyperfine) | reported | reported | gate: `max <` the arch spine deadline. Until arch pins that value, the gate uses `1.0 s` (see Decisions Log). |
| `viola hook pre-tool-use` on an unverified CLI (`hook.dialog` → `null` at once) | reported | reported | gate: `max <` spine deadline (same provisional `1.0 s`) |
| SSE keep-alive interval (`viola-ui`, tokio paused clock) | n/a | n/a | gate: a keep-alive comment is emitted at `advance(15 s)`; the real-time smoke sees one within 16 s per OS |
| Heartbeat staleness flip (`viola-state`, mock_instant) | n/a | n/a | gate: 4.9 s → live; 5.1 s → gone/stale (exact boundary test) |
```
**New:**
```
The gate is on the `max` sample, because Claude Code hook deadlines are hard cutoffs. Mean, median and stddev from the hyperfine JSON are reported for trend only. No percentile is computed or gated.

Perf run rules (all inside `agent-run run --perf`):
- **Binary under test:** `--perf` first runs its own non-instrumented `cargo build --release --workspace --features fake-agent --target-dir target/perf`. It never reuses the debug `boot` build or a `cargo llvm-cov` build, and never runs with `LLVM_PROFILE_FILE` set.
- **Invocation:** every hyperfine call is `-N --warmup 3 --runs 30 --export-json target/agent-run/artifacts/perf-<hook>.json`. Warm-up runs absorb first-execution costs, for example Windows Defender scanning a freshly built exe, and are not part of `max`.
- **Verdict:** `viola-harness gate` evaluates the exported JSON once; the `jq -e` expressions below are equivalent. There is no rerun, no outlier trimming and no second attempt. A breach is fixed in the product or escalated through a Decisions Log entry, never retried away.
- **Spine deadline:** once arch request (3) lands, the gate reads the named product constant (for example a `viola-core` const imported by `viola-harness`), not an edited literal in `ci.yml` or this table. Until then the provisional `1.0 s` applies.

| Path / operation | Trend (hyperfine JSON) | Gate |
|------------------|------------------------|------|
| `viola hook session-end` (fixture stdin, live wrapper), per OS | mean, median, stddev | `max < 1.0 s` (`jq -e '.results[0].max < 1.0'`) |
| Spine hooks `session-start`, `user-prompt-submit`, `stop` (same method, `VIOLA_NAME`/`VIOLA_DIR` exported to hyperfine) | mean, median, stddev | `max <` the arch spine deadline; provisional `1.0 s` until arch names it (see Decisions Log) |
| `viola hook pre-tool-use` on an unverified CLI (`hook.dialog` → `null` at once) | mean, median, stddev | `max <` spine deadline (same provisional `1.0 s`) |
| SSE keep-alive interval (`viola-ui`, tokio paused clock) | n/a | a keep-alive comment is emitted at `advance(15 s)` and not before it. There is no real-time smoke (§11 Universal). |
| Heartbeat staleness flip (`viola-state`, mock_instant) | n/a | 4.9 s → live; 5.1 s → gone/stale (exact boundary test) |

Deliberately not in this table:
- `send` → `prompt-submitted` confirmation latency and `wait` wake latency. Both are bounded by product constants that are still open (arch request 1), so they are asserted as behaviour in Paths 2 and 3, not timed.
- `boot`'s 20 s / 10 s deadlines. These are harness readiness timeouts, not product budgets.
```
