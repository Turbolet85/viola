# a11y extract

## Relevance
Partial. The chunk has no UI surface. Two parts of it still bind to this plan: (1) it creates the product `event`/`process` vocabulary and the line schema that the plan's harness-side violation rows copy their field names from, and (2) the `viola run` diagnostics sink and panic hook sit on the plan's tui boundary, where viola may write zero bytes to the terminal.

## Constraints
- a11y-plan §3 → Structured violation JSON schema → Binding fields and §12 D-A11Y-09 require that `a11y-violation` is **not** a product `event` enum value. It gets no `ObsEvent` variant, and its rows are validated against the tests-owned `e2e-web/schemas/a11y-row.v1.json`, never against `schemas/diag-line.v1.json`. One line in the plan still contradicts this: §12 → Resolved questions (the "`a11y-violation` event value" bullet) says it was "accepted as a tests + obs enum amendment". The later fix-pass-3 Z7 entry replaces that. Research must check that the obs-plan §3 enum list this chunk builds from (tests set + D-01…D-06) does not still carry the value.
- a11y-plan §3 → Structured violation JSON schema (Row shape, Binding fields, Additive fields) requires the obs field names to stay exactly as they are, because a11y rows mirror them: `timestamp`, `level`, `target`, `message`, `event`, `process`, plus `service_name`, `version`, `os` from obs Service Identity. `message` must equal the event name, and there is no `trace_id`/`span_id`. `process-start` and the macro output must use these exact keys.
- a11y-plan §1 → Scope Summary (web-spa surface → Service identity tagging) and §3 → Binding fields require `process:"ui"` to exist as a value. So `ObsProcess` must include `ui`, even though only `run` has a producer today.
- a11y-plan §1 → Obs additions a11y inherits (D-21) requires that a missing key means null. `schemas/diag-line.v1.json` must reject a literal `null` for `corr`/`instance`, and lines must never contain the GUI token, `Cookie`, `?t=` or stripped `CLAUDE*` values.
- a11y-plan §1 → Scope Summary (tui surface → Notes, and the `viola run` boundary-only Reason) requires three things during `viola run`: viola writes zero bytes to the terminal except the child's output; run diagnostics go to `diagnostics/` and never to the terminal; human keystrokes are never blocked or delayed. The per-role sink needs an explicit file writer and `with_ansi(false)`. The panic payload must go to `detail-run.ndjson` or the home-level diag line, never to stderr. Research must answer whether the current panic hook (or the default Rust hook it may chain to) already writes to stderr during `run`.
- a11y-plan §3 → Structured violation JSON schema → Emission location requires a11y rows to stay at `e2e-web/test-results/a11y/<test-id>.ndjson`. They are never written to `<home>/diagnostics/` and never emitted by the viola binary. So the torn-line-aware `logs` merge has no a11y source to ingest.

## Patterns to follow
- The harness-side row shape in a11y-plan §3 → Structured violation JSON schema (Row shape) shows what depends on this chunk: a line that mirrors the obs field names without renaming any and adds only snake_case fields. The obs line schema should keep that additive-only style.
- The "absent = null, never a literal `null`" rule is used for both obs lines and a11y rows (a11y-plan §3 → Binding fields: `instance`/`corr` omitted). `diag-line.v1.json` should enforce it with optional keys.
- The existing tui boundary check reuses the tests' portable-pty `=0.8.1` outer-PTY driver to assert that viola emits zero terminal bytes of its own (a11y-plan §1 → tui surface → Automated tool reach; §3 → Keyboard test harness → tui). Use it to show that moving the run lines to the new sink and panic routing adds no terminal output.
- The plan names CLI SGR discipline and `process:"cli"` for short-lived verbs (a11y-plan §1 → cli surface → Service identity tagging). The `cli-<name>` role file added in this chunk should carry `process:"cli"`.

## Anti-patterns to avoid
- Renaming an obs binding field, writing a literal `null` for `corr`/`instance`, or treating a11y violation rows as `diagnostics/` content (a11y-plan §11 → Universal).
- Emitting SGR or any viola-originated terminal output under `viola run`, including diagnostics or panic text (a11y-plan §11 → Visual, the SGR ban under `viola run`; §1 tui boundary).
- Blocking or delaying a human keystroke in `viola run` (a11y-plan §11 → Keyboard). Per-line `write_all` to diag and detail files on the run path must not stall the input relay.

## Contract bindings
- a11y violation JSON ↔ obs §3 Log format / `ObsEvent` / `schemas/diag-line.v1.json`: a11y rows mirror the obs field names and `process` values but are schema-separate (tests-owned `a11y-row.v1.json`). They are outside the product enum (a11y-plan §3 → Structured violation JSON schema; D-A11Y-09).
- a11y rows `service_name`/`version`/`os` ↔ obs Service Identity (`viola_core::{SERVICE_NAME, VERSION}`). Rows take `version` from `GET /health`, which must be the same single source (a11y-plan §3 → Additive fields).
- tui boundary ↔ tests portable-pty driver: "zero bytes of viola's own on the terminal" is asserted there (a11y-plan §1 → tui surface).

## Acceptance criteria contributions
- `ObsEvent` and the `event` enum in `schemas/diag-line.v1.json` contain no `a11y-violation` value, and the tests-owned equality check between the two enums passes (per a11y-plan §3 → Structured violation JSON schema → Binding fields; D-A11Y-09).
- `process-start` lines carry `service_name`, `version`, `os`, `pid` with those exact key names; every line carries unrenamed `timestamp`/`level`/`target`/`message`/`event`/`process`, with `message` equal to the event name; `ObsProcess` includes `ui` and `cli` (per a11y-plan §3 → Row shape / Additive fields; §1 → Service identity tagging).
- `schemas/diag-line.v1.json` rejects a line with a literal `"corr":null` or `"instance":null` and accepts the same line with those keys omitted (per a11y-plan §1 → Obs additions a11y inherits; §11 → Universal).
- The portable-pty boundary check stays green on the migrated `viola run` path: viola writes zero bytes of its own to the terminal, and a forced panic in `run` puts its payload in `detail-run.ndjson` or the diag file, with nothing on stderr/stdout (per a11y-plan §1 → tui surface → Notes; §11 → Visual).
