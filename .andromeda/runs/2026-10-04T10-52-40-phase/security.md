# security extract

## Relevance
relevant — this chunk is the first that can emit a non-`null` dialog decision (PermissionRequest `allow` = code execution as the user), adds the `answer` verb and serves `hook.dialog`, crossing the IPC trust boundary named in security-plan §Threat Model Summary (Sec 1 local endpoint; the `answer` `allow` threat).

## Constraints
- **Stamps-read gap must close before any non-`null` decision.** security-plan §Security Anti-Patterns › Universal forbids answering a `hook.dialog` non-`null` while `run`'s version gate still reads `ledger/stamps.json` without the strict-modes check, and names "Dialog answers by dialog_id" as the entry before which that interim gap closes on `run`'s read. The `~/.viola/` access-control row (§Authentication & Authorization) and the Own-state-files row (§Input Validation) list that read as the second dated exception, ratified only until Epoch 6. So this chunk must add strict-modes to `run`'s stamps read, or prove no non-`null` decision is reachable. Proving that would defeat the chunk's purpose. Whether `src/run/version_gate.rs` already runs the check is research's question.
- **No dated exception covers the `hook.dialog` or `answer` frames.** security-plan §Security Anti-Patterns › Authentication and the IPC client-side server verification row (§Authentication & Authorization) require server verification (pid / euid + sysinfo start time, against a snapshot that passed strict-modes in the same process) before the first frame of `answer` and `hook.dialog`. The ratified exceptions cover only `hook.event`, CLI `send`, and CLI `wait` / `last`, and "no other frame or process may borrow any of them". The scope's Boundaries defer server verification to Epoch 6 (`:109` / `:111`). That conflicts with this rule, so P4 must settle it: either build verification + strict-modes for these two frames, or get a new dated founder ruling that is recorded in the plan. It cannot be assumed by analogy with `send` / `wait` / `last`. Whether the `viola-channel` client already has a verifying open path is research's question.
- **`unverified-cli` gate.** security-plan §Security Anti-Patterns › Universal and the driver-prompt-injection accepted risk (§Authentication & Authorization) require that `hook.dialog` never gets a non-`null` decision without a `viola verify` stamp for the child's CLI version. That gate and the closed `behavior` enum are viola's only defence against a prompt-injected driver `allow`. `answer` on an unstamped CLI is refused (`unverified-cli`).
- **Closed types on the wire.** security-plan §Input Validation (Channel frames row) and §Security Anti-Patterns › Input require `behavior` to be a closed enum (`allow`/`deny`, `approve`/`revise`), `dialog_id` a `u64`, and the dialog kind a closed enum, never free `String`s, even under tolerant parsing. The Hook stdin row puts the security-deciding fields (dialog kind, decision body) into closed enums inside `viola-agent-claude`.
- **Free-text answers go through the paste validator.** security-plan §Input Validation (Dialog free text row) and §Security Anti-Patterns › Input require `answer.response.message` (permission, plan) and every `answer.response.answers.*` value (question) to pass `viola_core::validate_paste_text` in the `answer` handler. LF/CR/TAB are allowed; other C0, DEL and C1 get `control-character`; the validator rejects, never strips. The wrapper re-runs it and client checks are advisory (CLAUDE.md shared-validator rule).
- **CLI `answer` input bound.** security-plan §Input Validation (CLI arguments / stdin row) requires the `answer` response JSON to come from stdin or `--file` through `Read::take(MAX_FRAME)` into the closed `response` enums, with `<target>` via `parse_viola_name` / `ViolaName::try_new`.
- **Hook fails open on every security failure.** security-plan §Error Handling (Internal logging) and §Security Anti-Patterns › Logging / Universal require the dialog-tier `viola hook` to exit 0 with no body and no stderr on any failure, including a verification or strict-modes mismatch, a channel error, or a deadline. A refusal never blocks the human, and refusals go only to automation (`answer`).

## Patterns to follow
- The send/wait/last precedent for a new frame. The channel row in security-plan §Input Validation types each method's params: a bad param is `-32602` `"invalid params"` with `data: null`, reached at the method rather than the envelope, and unknown fields are ignored. `answer` follows the same shape, and `from` follows the shared `send` rule.
- The liveness-only pre-check's documentation pattern (§Authentication & Authorization, IPC server-verification row). If P4 takes a founder ruling rather than building verification, each new gap is recorded the same way in every row that lists the exceptions: dated, naming the `:109` / `:111` removal entries, stating the residual, and stating "borrows no other exception".
- `viola_state::stamps::read_stamps` (§Input Validation, Own-state-files row) is the one stamps reader: no lock, `take(MAX_FRAME + 1)`, and a malformed file gives a `parse-rejected{parser:"ledger-stamps"}` WARN with `cli_verified:false`. A strict-modes failure on it should also fail closed to `cli_verified:false` (withhold), never open.
- Content payloads by design. security-plan §Bootstrap phases (`logging-redaction-wire`, the floor's Scope clause) lets dialog content (question text, plan text, tool `input`) ride `events.ndjson`, `hook.dialog` and `wait` results. Outside those, the content goes only to `instances/<name>/diagnostics/`.
- Fixed-message errors. security-plan §Error Handling requires `answer` refusals and channel errors to carry codes and fixed messages only (`-32603` = `"internal error"` / `data: null`), with no path or upstream text.

## Anti-patterns to avoid
- Interpreting question, plan or tool `input` text as a command or config, or choosing an answer inside viola (security-plan §Security Anti-Patterns › Code Patterns, R1; accepted risk in §Authentication & Authorization). This covers the permission-suggestion decision too. Which suggestion is applied must come from the driver's typed `response`, and viola must never synthesise or widen it. Whether the suggestion field fits the closed `response` enums is research's / P4's question, because the plan names no suggestion field.
- Modelling `behavior`, `dialog_id` or the dialog kind as a free `String`, or stripping control characters from answer text instead of refusing them (security-plan §Security Anti-Patterns › Input).
- Writing the `answer` or `hook.dialog` frame after only a liveness check without a recorded ruling, or borrowing the `hook.event` / `send` / `wait`-`last` exceptions (security-plan §Security Anti-Patterns › Authentication).

## Contract bindings
- security ↔ obs: the spans and events `dialog-raised`, `dialog-answered` and `hook-decision` must never carry question, answer or tool `input` text (the NEVER-log floor, security-plan §Bootstrap phases `logging-redaction-wire`; obs-plan `:670-678`). `hook-decision` detail codes are the fail-open vocabulary (§Error Handling).
- security ↔ tests: the `answer` unstamped negative (exit 12) in `tests/cli_controls_not_disableable.rs` (CARRY 3) is the witness that no flag, env var or config switches off the `unverified-cli` gate (security-plan §Security Anti-Patterns › Universal, the no-disable rule). The fixtures recorded for the tool-bearing PreToolUse / PermissionRequest events carry tool `input`, so they must hold no R8-stripped `CLAUDE*` value, token or secret (NEVER-log floor; CLAUDE.md).
- security ↔ architecture: the closed `response` normalisation per kind (`architecture.md:278-281`) is the security plan's closed-enum boundary, and the S3 / S7 / S8 mapping stays in `viola-agent-claude` (§Input Validation, Hook stdin row).

## Acceptance criteria contributions
- With `ledger/stamps.json` (or `ledger/`) group- or world-writable, or not owned by euid, `run` reports `cli_verified:false`: `hook.dialog` replies `null` and `answer` is refused `unverified-cli` (exit 12), even when a matching stamp is present. A test witnesses this, and the plan's stamps-read interim-gap text is amended to drop `run`'s read (per security-plan §Security Anti-Patterns › Universal; §Authentication & Authorization `~/.viola/` access control).
- An `answer` whose `message` or `answers.*` value carries ESC / another C0 / DEL / C1 is refused `control-character` before any other refusal and writes nothing to the PTY or hook body, while LF / CR / TAB pass. A non-enum `behavior` or a non-`u64` `dialog_id` is `-32602` with `data: null` (per security-plan §Input Validation, Dialog free text and Channel frames rows).
- Every dialog-tier hook failure path (channel unreachable, deadline hit, malformed reply, verification or strict-modes failure) exits 0 with empty stdout and empty stderr (per security-plan §Error Handling, Internal logging).
- The `answer` and `hook.dialog` frames are written only after server verification against a strict-modes-checked snapshot, OR the plan's §Authentication & Authorization server-verification row and §Security Anti-Patterns › Authentication carry a new dated founder ruling naming exactly these two frames before the chunk lands. A grep of the plan verifies whichever P4 chose (per security-plan §Authentication & Authorization, IPC client-side server verification).
