# a11y extract

## Relevance
partial: the chunk's cli surface (`viola answer` refusals, `viola wait`'s human-mode dialog line) and the tui boundary (a dialog left to the human) are in scope; the web-spa half of Path 3 (cocked strip, `status`, `document.title`) is Epoch 8 and out of scope; the hook and channel are not assertable (per a11y-plan §1 A11y Scope Summary → Not-assertable, the plugin hooks / IPC entity).

## Constraints
- The cli carries no WCAG conformance claim. a11y-plan §1 A11y Scope Summary → Surface: cli and §11 A11y Anti-Patterns → Strategy require that the `answer` / `wait` checks be output-discipline stand-ins for SC 1.3.2 / 1.4.1 / 3.3.1, run with assert_cmd / trycmd / the portable-pty outer PTY. They are never to be called a11y-tool evidence.
- Every human-mode `viola answer` refusal must follow the CLI error-recovery layout in a11y-plan §8 Cognitive Accessibility → Error recovery: `unable  <reason>  <detail>` on stderr, then `hint:` as the last stderr line, with a typed exit code (`unverified-cli` → 12, `unknown-dialog` → 13, and `not-delivered` / `control-character` per §Conventions). Only `unknown` (exit 14) and the faults (`error: internal error`, `error: wrapper fault`) carry no hint. `--json` must give one document with no hint text. a11y-plan §8 → Plain language requires the kebab-case code always to sit beside the plain word `unable`.
- Colour may only ever be a second cue. a11y-plan §1 → Surface: cli → Notes and §4 ARIA Patterns & Roles → P6 allow amber only on `DIALOG`, always beside the word. `unable` gets no SGR. No SGR, glyph or cursor control may appear under `--json`, non-TTY, `NO_COLOR`, `TERM=dumb` or `viola run`. The new `wait` dialog line `<kind>  <name>  dialog <id>  cursor <n>` and the `answer` refusals inherit this. Research must answer whether the landed human writers already apply it to a dialog line.
- `wait` output must be static and linear: `waiting: <name>` printed once on stderr (TTY only), with no spinner, `\r` redraw or cursor movement while a `wait` is parked on a dialog. a11y-plan §4 → P6 and §1 → Path 6 require this.
- Control characters must be escaped in human mode. a11y-plan §4 → P6 requires C0/C1 to be escaped in `wait` / `last` text, with `\n` / `\t` kept raw. Research must answer whether a dialog event's human-mode rendering in `wait` carries any upstream-derived text (question, plan, tool `input`), and so needs the escaper the wait-and-last chunk landed, or only viola-owned fields.
- The human is never blocked. a11y-plan §1 → Entity: `viola run` TUI passthrough (boundary-only) and §11 → Keyboard (last bullet) require viola to write zero terminal bytes of its own, and never to block or delay a human keystroke. A dialog this chunk does not answer (the deadline expiry, a second dialog while one is pending, an unverified CLI's immediate `null`) must therefore reach the human's `claude` TUI unchanged, with the hook writing nothing to stderr.
- viola sets no time limit on a human. a11y-plan §8 → Timeout extensions allows `viola wait` to return `timed_out` only for a timeout the caller passes in. The dialog deadline must limit only automation's answer window: on expiry the dialog renders for the human, who then has no limit (SC 2.2.1 stand-in, no claim).

## Patterns to follow
- Pin each refusal with trycmd, using a case per `answer` refusal (`unverified-cli`, `unknown-dialog`, `not-delivered`, `control-character`) for the `unable … hint:` layout, plus assert_cmd for the typed exit codes and the hint-free `--json`, on all three OS legs. This follows a11y-plan §8 → Error recovery → Verification → cli and §4 → P3 (the "`viola answer` refusal `unverified-cli` text on the CLI" check).
- Reuse the P6 control-byte injection setup from a11y-plan §4 → P6. A `viola-fake-agent` event carries C0 / C1 bytes (ESC / CSI included) and the human-mode output is asserted escaped. Extend it to the dialog-kind `wait` line if research finds upstream text reaching that line.
- Assert SGR discipline in two modes, following a11y-plan §4 → P6: trycmd / assert_cmd for the non-TTY, `NO_COLOR`, `TERM=dumb` and `--json` modes, and the portable-pty outer PTY for the TTY-only behaviour (any SGR span beside its word).
- Supply CLI input through stdin / `--file` only, with no interactive prompt. This follows a11y-plan §3 Keyboard test harness → Tooling and §5 Keyboard Navigation (cli: N/A). Free-text `answer` responses (question text, permission / plan `message`) arrive this way and are asserted this way.

## Anti-patterns to avoid
- NEVER colour CLI `unable`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` (per a11y-plan §11 → Visual). Also NEVER show a refusal without its `hint:` line, or with a bare code and no `unable` (per a11y-plan §11 → Cognitive).
- NEVER add a spinner, redraw or progress glyph while `wait` / `answer` are pending (per a11y-plan §11 → Motion, the spinners ban, and §4 → P6).
- NEVER block, refuse or delay a human keystroke, and never let the hook's dialog path write terminal bytes of its own (per a11y-plan §11 → Keyboard). NEVER claim WCAG conformance for the cli or tui on the strength of these checks (per a11y-plan §11 → Strategy).

The hint text for `unverified-cli` / `unknown-dialog` is design-owned and pinned by trycmd (per a11y-plan §8 → Plain language).

A11y never renames these fields or writes a literal `null` for `corr` (per a11y-plan §1 → event stream binding, and §11 → Universal).

## Acceptance criteria contributions
- (a11y, cli) `viola answer <name> <id>` on an unverified CLI prints `unable  unverified-cli  <detail>` on stderr, with a `hint:` as the last stderr line, and exits 12. An unknown or stale `dialog_id` prints `unable … unknown-dialog …` with a final `hint:` and exits 13. With `--json`, each gives one document with no hint text. `unable` carries no SGR under the outer PTY. Pinned by trycmd and assert_cmd on all three OS legs (per a11y-plan §4 → P3 and §8 → Error recovery).
- (a11y, cli) Under non-TTY, `NO_COLOR`, `TERM=dumb` and `--json`, the human-mode `wait` dialog line `<kind>  <name>  dialog <id>  cursor <n>` and every `answer` output contain no SGR, cursor-control or raw C0 / C1 byte (other than `\n` / `\t`). Under the outer PTY, any SGR sits beside its word, and a parked `wait` prints `waiting: <name>` once with no `\r` redraw (per a11y-plan §4 → P6).
- (a11y, tui boundary) A dialog that viola does not answer reaches the human's `claude` TUI with the hook having exited 0 and written no stdout body and no stderr, so viola adds zero terminal bytes. These are the cases: deadline expiry, a second dialog while one is pending, and an unverified CLI's immediate `null` (per a11y-plan §1 → Entity: `viola run` TUI passthrough, and §11 → Keyboard).
- (a11y, cli) `viola wait` on a pending dialog never returns `timed_out` unless the caller passed a timeout, and the dialog deadline never times out the human (per a11y-plan §8 → Timeout extensions).
