## Constraints
- **Placement across the crate boundary.** Per architecture §Established Decisions [Agent Coverage] and §Infrastructure Patterns → Crate dependency direction, the dialog answer mapping (S3/S7/S8), hook payload parsing for PreToolUse/PermissionRequest, the `hookSpecificOutput` decision bodies and the new ledger rows belong only in `viola-agent-claude`, which must stay pure (no I/O, no `viola-state` dependency). The dialog registry, `dialog_id` counter, await/deadline and `pending_dialog` snapshot write belong to the root bin's `run` (it alone writes `snapshot.json`, §Standard Contracts → Instance snapshot). The CLI verb is a `src/cmd/` module (§Infrastructure Patterns → Project directory structure). Any new refusal `detail` or event kind is added only in `viola-core` (§Conventions → `RefusalReason`, → Normalised event kinds). Whether the `question`/`permission`/`plan` kinds and the `unknown-dialog` detail already exist in `viola-core` is research's question.
- **`hook.dialog` contract.** Per §Standard Contracts → Channel methods (`hook.dialog`) and the paragraph after Event `data` per kind: a dialog hook sends only `hook.dialog`, never a `hook.event` for the same dialog; the wrapper assigns `dialog_id` and appends the dialog event (`source: hook`) before it can wake `wait` or reply, including every immediate-`null` path (unverified CLI, wheel `human`, another dialog pending). `hook.event`'s re-validation admits only its five hook kinds (§Standard Contracts → `hook.event`), so a dialog kind must not enter through it. Event `data` per kind is fixed in §Standard Contracts → Event `data` per kind; `hook.dialog`'s `data` is that object minus `dialog_id`.
- **`dialog_id` and the one-pending rule.** Per §Established Decisions [Message Broker / IPC]: `dialog_id` is an integer, monotonic per instance, its counter restored from `events.ndjson` at start so an id never repeats across restarts; at most one dialog is pending; a second `hook.dialog` is answered `null` at once, still logged with its own id, and a later `answer` for it is `not-delivered`/`unknown-dialog`. `wait` without `after` (or with `after` at/before the pending dialog's line) returns the pending dialog at once — the as-landed note there says this return lands with `working-route.md:78`.
- **Deadline relation (closes part of scope §1's [inferred]).** Per §Established Decisions [Hook Contract]: the dialog deadline's VALUE is an open item, but arch requires it to be ONE built-in value compiled into both `hook` and the embedded `hooks.json`, with the `hooks.json` `timeout` exceeding it by a margin so viola, never Claude Code, ends the wait; on expiry the hook exits 0 with no body and the wrapper clears the pending id. Per [Deployment / Distribution] and §Occupied Resources → Claude Code integration names, the dialog tier (PreToolUse matcher `AskUserQuestion|ExitPlanMode`, PermissionRequest) is registered in `hooks.json` by this chunk and never earlier with a no-decision body.
- **`answer` contract and refusal order.** Per §Standard Contracts → Channel methods (`answer`): `{dialog_id, from?, response}` → `{}`, `response` normalised per kind (question / permission / plan shapes listed there). Per §Conventions → Error handling schema: the `answer` refusal order is `human-typing`, `unverified-cli`, `not-delivered`/`unknown-dialog`; exits `12`/`13` per §Conventions → CLI exit codes, plus `20`/`21` and the `--json` mirror per §Standard Contracts → CLI `--json` output. Per §Conventions → CLI: `viola answer <target> <dialog_id>` takes the `response` object as JSON from stdin or `--file` (closes scope §2's CLI-input [inferred]). `from` typing: §Standard Contracts → Channel methods names only `send`/`wait`/`last` as `from` readers (absent / `null` / valid `ViolaName`, else `-32602`, `data: null`); `answer` reads `from` too, so it must take the same typing — the sentence is an arch amendment at wrap. arch places `control-character` in `answer`'s order nowhere; that ordering is test-plan's (`:587`).
- **Transport-only withholding.** Per §Established Decisions [CLI Version Compatibility] and §Standard Contracts → `hook.dialog`: on an unverified CLI the wrapper replies `null` at once and drivers get `unverified-cli`; a version is verified only when its stamp holds every landed row `pass`. ## Patterns to follow
- **Append under the wait feed's lock.** Per §Standard Contracts → Channel methods (`wait`): each hook line's append runs inside `WaitFeed::appending`, then the generation bumps and parked calls wake; the dialog event's append must take the same path so `question`/`permission`/`plan` (members of `EventKind::WAIT_WAKE`) wake a parked `wait`.
- **Rebuild-at-start from the log.** The `dialog_id` counter restore mirrors `WaitFeed::rebuild` (§Standard Contracts → `last`: rebuilt once from the whole `events.ndjson` before `server.serve`), read through the one reader `viola_state::events::read_from` with its torn-line skip (§Established Decisions [Database / State Store]); `pending_dialog` itself is never rebuilt (§Standard Contracts → Instance snapshot).
- **Snapshot writes through the one helper.** `pending_dialog` add/remove rewrites `snapshot.json` only through `viola_state::fs::replace_private` (§Established Decisions [Snapshot writer]).
- **CLI client verb shape.** `answer` follows the landed `send`/`wait`/`last` client pattern: liveness pre-check then frame, `role_of` filing under `cli`, one `error: internal error` from the `main` catch site, codes-only `cli-<name>.ndjson` lines (§Conventions → CLI exit codes `1`; §Occupied Resources → Filesystem `diagnostics/`).
- **Hook fail-open + sync std path.** The dialog hook uses the sync `viola-channel` client on std threads (§Cross-cutting Patterns → Tokio containment), writes only its decision body to stdout and nothing to stderr (§Cross-cutting Patterns → Diagnostic output channels; §Established Decisions [Hook Contract]).

## Anti-patterns to avoid
- Claude-specific shapes (`hookSpecificOutput`, `updatedInput`, `permissionDecision`, tool names `AskUserQuestion`/`ExitPlanMode`) anywhere outside `viola-agent-claude`, or I/O / `viola-state` inside it (§Established Decisions [Agent Coverage]; §Cross-cutting Patterns → Capability ledger).
- Policy in the binary: viola picks no default answer and never interprets dialog text, plan text or tool `input` (§Design Philosophy "Mechanism, not policy"; §Cross-cutting Patterns → Untrusted upstream text) — a `null`/no-body reply is the only thing viola decides on its own.
- A hook exit other than 0, a stderr write, or Claude Code's `timeout` ending the dialog wait instead of viola's deadline (§Established Decisions [Hook Contract]; §Conventions → `viola hook` exit codes).

## Acceptance criteria contributions
- Every `hook.dialog` — including the immediate-`null` replies for an unverified CLI and for a second concurrent dialog — appends exactly one dialog event (`source: hook`, kind-specific `data` with a wrapper-assigned integer `dialog_id`) through `WaitFeed::appending` before the reply; ids stay strictly increasing across a `run` restart on the same instance; no `hook.event` line is written for a dialog (per architecture §Standard Contracts → Channel methods / Event `data` per kind; §Established Decisions [Message Broker / IPC])
- Decision bodies are produced only by `viola-agent-claude` in the §Standard Contracts → Hook contract shapes (PreToolUse `allow` + `updatedInput`; PermissionRequest `decision{behavior, message?}`); on `null`, deadline expiry or any internal failure `viola hook pre-tool-use|permission-request` exits 0 with empty stdout and stderr (per architecture §Established Decisions [Hook Contract] / [Agent Coverage])
- `viola answer` reads `response` JSON from stdin or `--file`, returns `{}` on success, refuses in the order `human-typing` → `unverified-cli` → `not-delivered`/`unknown-dialog` with exits 10/12/13, mirrors the channel result under `--json`, and a non-`ViolaName` `from` is `-32602` with `data: null` (per architecture §Conventions → Error handling schema / CLI exit codes / CLI; §Standard Contracts → Channel methods)
- The embedded `hooks.json` registers PreToolUse (matcher `AskUserQuestion|ExitPlanMode`) and PermissionRequest as exec-form entries on the pinned path, each with a `timeout` strictly greater than one compiled dialog-deadline constant that `hook` also uses (per architecture §Established Decisions [Hook Contract] / [Deployment / Distribution]; §Occupied Resources → Claude Code integration names)
