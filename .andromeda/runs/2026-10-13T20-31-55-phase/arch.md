## Relevance
relevant — the chunk adds capability-ledger rows and `viola verify` probes, which architecture names as the single gate for CLI-specific behaviour and places in `viola-agent-claude` + the root bin's `verify`.

## Constraints
- Every relied-on undocumented `claude` behaviour must be a ledger row in `viola-agent-claude` with a `viola verify` probe that checks a post-condition, never an unconditional assumption; the plan names the owed dependences this entry holds (the inner-LF paste shape, `claude --resume <id>` reopening the session, and the statusline's `rate_limits`, `--settings` override and `/bin/sh` shell) and their owners, with the Windows legs owed to "Windows-only live measurements"; the one ruled limit is "a shape no `send` relies on needs no probe" (per architecture §Cross-cutting Patterns, Capability ledger as the single gate).
- A CLI version is verified only when its stamp holds every landed row `pass`; the plan states the precedent that a stamp holding only the older row ids reads unverified, so a new row in the closed set makes every existing stamp (2.1.287 today) unverified until re-stamped, and an unverified version degrades to transport-only with dialog answers withheld (per architecture §Established Decisions [CLI Version Compatibility]; per architecture §Design Philosophy, Measured, never assumed).
- The verify child set is fixed by the plan: one print-mode probe plus Runs A–D; Run B gets exactly four compiled pastes (`PROBE_PROMPT`, `PROBE_LONG_PASTE`, `PROBE_TAG_PASTE`, `PROBE_LOCAL_COMMAND`), each added one only into a settled input box; no byte is typed into a CLI dialog; a modal start is killed with no key; a run stopped by Ctrl-C or TERM starts no later run and writes no stamp — a fifth paste, a resume child or a compaction turn changes this set (per architecture §Established Decisions [CLI Version Compatibility]).
- `viola-agent-claude` stays pure (no I/O, no `viola-state` dependency): rows, compiled paste texts, `check(row, &Probes)`, `LOCAL_COMMANDS`, `framing_variants`, `resume_args` and the statusline module live there; the stamps file I/O stays in `viola-state` and the root bin (per architecture §Established Decisions [Agent Coverage]; per architecture §Infrastructure Patterns → Crate dependency direction).
- `ledger/stamps.json` has one writer, `viola_state::stamps::update_stamps`, called only by `viola verify`; a merge replaces only its own version's entry, keeps unknown versions and fields, and a failing row still writes its stamp; new `measured` readings are additive with no `v` bump; `run` reads no `measured` field (per architecture §Standard Contracts, Ledger stamps envelope; per architecture §Occupied Resources, Filesystem `ledger/stamps.json`).
- A local command's delivery is decided by the compiled `LOCAL_COMMANDS` list with its measured post-condition (or "none" → `unconfirmable`), classified by exact equality on the typed text, never by a leading slash; `/compact` is not on the list (per architecture §Established Decisions [Delivery Confirmation]; per architecture §Established Decisions [CLI Version Compatibility], Local commands).
- The flag and program literals have one home each in the agent crate: `SETTINGS_FLAG` (used by `run` and by verify's Runs C and D), `PROGRAM`, and `resume_args` as the one product home of `--resume` / `--fork-session`; the `claude agents --json` join (child pid or session id) is an open ledger row whose readers spawn the CLI directly through the npm-shim resolution and degrade to `status: unknown` on any failure (per architecture §Occupied Resources, Claude Code integration names; per architecture §Standard Contracts, the `claude agents --json` bullet).

## Patterns to follow
- A row lands as a member of the closed `viola_agent_claude::ledger` set, read by `check(row, &Probes)`; a Run B that did not paste a text fails that text's row, and a run that raised no dialog fails its dialog rows (per architecture §Established Decisions [CLI Version Compatibility]).
- `/clear`'s row `local-command-clear` is the template for a local-command row: a compiled list entry, its post-condition read from Run B's captures (SessionEnd then SessionStart of source `clear` with a new id), and recorded framing variants `SessionEnd.clear-<n>.json` / `SessionStart.clear-<n>.json` (per architecture §Established Decisions [CLI Version Compatibility], Local commands; per architecture §Occupied Resources, Repository).
- `--record <DIR>` writes scrubbed variants `<Event>.<stem>-<n>.json` only when 0 rows fail, refuses an unclean recording whole with a closed code (`home-path` · `absolute-path` · `username` · `email`), and the fake agent replays them in CI (per architecture §Occupied Resources, Repository).
- External payloads (statusline, `claude agents --json`, hook JSON) are parsed tolerantly — no `deny_unknown_fields`, `Option`/`#[serde(default)]`, raw `Value` kept for the recorder; a malformed `resets_at` becomes `unknown` (per architecture §Established Decisions [Validation]; per architecture §Established Decisions [Timestamps]).
- Each verify probe dir is 0700 with its own drop guard, removed on pass, fail or Ctrl-C/TERM, only the dirs that run made (per architecture §Occupied Resources, Filesystem verify's interactive probe dirs).

## Anti-patterns to avoid
- Hard-coding a measured CLI shape as an unconditional assumption, or landing a relied-on dependence with no row and probe (per architecture §Cross-cutting Patterns, Capability ledger as the single gate).
- Spawning a verify child or a probe through `sh`/`bash`/`cmd`: children are spawned directly, and the only shell-out is `hook statusline` running the user's command — a `/bin/sh` probe observes the CLI's shell, it does not start one (per architecture §Cross-cutting Patterns, Cross-platform discipline).
- Putting a Claude-specific shape outside `viola-agent-claude`, or giving that crate file I/O or a `viola-state` edge (per architecture §Inherited Defaults, Agent isolation; per architecture §Infrastructure Patterns → Crate dependency direction).

## Contract bindings
- arch ledger ↔ security: the verify child set (Run B's four compiled pastes, no key into a dialog, no write under `~/.claude`) is the security rule set ratified by the founder; any added paste or child is a boundary widening owned there (per architecture §Established Decisions [CLI Version Compatibility]).
- arch ledger ↔ tests: CI runs `verify` only against the fake agent's print and interactive `--screens --turn-stop --trusted-root --dialogs --framing` modes, and the committed 2.1.287 set is stamped at the current row count by `contract_ledger_probes`; whether the fake agent already emits the shapes a new row's probe reads is research's question (per architecture §Established Decisions [CLI Version Compatibility]; per architecture §Occupied Resources, Repository).
- arch ledger ↔ obs: `run`'s version gate records `cli_verified` in the snapshot and the `claude-child` `process-start`, and a malformed or strict-refused stamps file logs one `parse-rejected{parser:"ledger-stamps"}` (per architecture §Standard Contracts, Ledger stamps envelope).
- arch ledger ↔ ui/list: `cli_verified` / `cli_version` reach `/api/sessions` items from the snapshot (per architecture §Standard Contracts, `/api/sessions` item).

## Acceptance criteria contributions
- Each new row is a member of the closed ledger set in `viola-agent-claude` and gates `cli_verified`: a stamp holding only the seventeen older ids, all `pass`, reads unverified (per architecture §Established Decisions [CLI Version Compatibility]).
- `viola-agent-claude`'s manifest gains no `viola-state` or I/O-bearing dependency, and `ledger/stamps.json` is written only through `update_stamps` from `viola verify` (per architecture §Infrastructure Patterns → Crate dependency direction).
- CI's `viola verify` against the fake agent passes at the new row count, and no CI job starts the real `claude` (per architecture §Established Decisions [CI/CD]).
- Every new recorded variant passes the scrub, the `unclean` refusal and the fixture hygiene walk, and `--record` writes nothing when any row fails (per architecture §Occupied Resources, Repository).
