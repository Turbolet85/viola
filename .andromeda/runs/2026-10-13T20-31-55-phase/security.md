# security extract

## Relevance
relevant: the chunk adds capability-ledger rows and `viola verify` probes that change the founder-ratified verify child set, the stamp that switches on dialog answering, recorded fixtures and the probe dirs, and it touches the one shell-out (the statusline rows).

## Constraints
- Every `viola verify` interactive child must be a direct spawn (never through a shell) under the R8 strip at a fixed 80×24, with its output capped at `MAX_FRAME` into a `Screen` fed under `catch_unwind`. Run B's pastes are the compiled literals the plan enumerates (four today), each added one only into rows that hold the input-box literal and no modal literal. No run writes a byte into any dialog, and a modal start is killed with no key. A fifth Run B paste (the LF row, `/compact`) or a new child that resumes a session (`--resume`) changes this ratified set. Each is a boundary widening that needs the founder's own live word, with its shape shown (per security-plan §Threat Model Summary, Attack surface: Child process spawning and PATH resolution).
- A stamp gates a non-`null` dialog decision only when every row of `LedgerRow::ALL` passes. The plan states the set as seventeen rows (counter `/17`, the rows named by family). A row added to `ALL` must gate `cli_verified` like the seventeen, so a stamp holding only the older ids records `cli_verified:false`. Only `viola verify` may write `ledger/stamps.json` (per security-plan §Security Anti-Patterns → Universal).
- `ledger/stamps.json` is written only by `viola verify`, under its `.lock`, at 0600. `update_stamps` reads it without strict-modes only under the dated interim gap until Epoch 6, and `viola run`'s version gate reads it only through `read_stamps_strict` (per security-plan §Authentication & Authorization, `~/.viola/` access control).
- Recorded fixtures (`fixtures/claude/<cli-version>/`) must come from synthetic probe prompts and pass verify's scrub before any write. Screen fixtures keep only rows that hold a compiled signature literal. A refusal names the file and a closed code (`home-path` · `absolute-path` · `username` · `email`), never the content (per security-plan §Data Protection, Repository fixtures).
- `statusline_command` through `/bin/sh -c` (`statusline::shell_argv`) must stay the only shell-out. The settings-override and Unix-shell rows are owed to this entry. Any probe of them must not add a second shell-out or run a user string. The override file keeps its plain-character pinned-path rule and `SETTINGS_FLAG` as its one home (per security-plan §Input Validation, Statusline shell-out row; per security-plan §Data Protection, Code-bearing artefacts).
- The `rate_limits` reading stays tolerant (an absent object means no reading and no write; out-of-range or malformed fields read `"unknown"`). The budget gate stays fail-open. A probe of the shape must not make `budget.json` a trusted file or give it a second writer besides `hook statusline` (per security-plan §Input Validation, Hook stdin row; per security-plan §Input Validation, Own state files on read row).
- Child output from `claude agents --json` is read through `Read::take(MAX_FRAME)` and parsed tolerantly, and a failure becomes `unknown`. A join field taken from it must never become a `ViolaName` or `target`. A session id placed on a child's argv goes only through `viola_agent_claude::resume_args` with the closed `is_session_id` shape (per security-plan §Input Validation, Child process output row; per security-plan §Input Validation, Session id as a child argv value row).

## Patterns to follow
- Probe dirs: each verify dir is 0700 and removed by a drop guard when verify passes, fails or is stopped by Ctrl-C or TERM (`cmd::verify::stop`). Each guard removes only what its own run created, never by a pattern (per security-plan §Data Protection, Interactive probe dirs). Any new child dir must follow the same rule.
- Probe captures go through the hidden `hook --capture [--answers]` arm. Each capture is an exclusive `create_private_new` claim at 0600 under `ledger/probes/<pid>/` (0700). Answers are closed `ProbeAnswer` ids read through `take(64)`, and the body is built only by `dialog::decision_body` (per security-plan §Input Validation, Hook stdin row; per security-plan §Data Protection, Probe captures).
- Screen signatures and local-command lists come only from compiled `viola-agent-claude` ledger rows. A `/compact` listing is a compiled literal, never built from runtime or upstream text (per security-plan §Security Anti-Patterns → Code Patterns).
- Each new trusted-run transcript under `~/.claude/projects/` belongs to the accepted residual class, and its count per verify is shown at plan review, as the +2 and +1 were. viola itself writes nothing under `~/.claude` (per security-plan §Data Protection, Accepted risk (verify's trusted runs, B, C and D)).

## Anti-patterns to avoid
- NEVER add a second shell-out, and NEVER interpret upstream text (a resumed session's content, `claude agents --json` output, statusline payload values) as a viola command or config (per security-plan §Security Anti-Patterns → Code Patterns).
- NEVER commit fixtures recorded from non-synthetic prompts, or fixtures not checked for home paths and usernames (per security-plan §Security Anti-Patterns → Data Protection).
- NEVER let any process other than `viola verify` write `ledger/stamps.json`, and NEVER let a non-`null` decision flow on a stamp that lacks a passing row (per security-plan §Security Anti-Patterns → Universal).

## Contract bindings
- security ↔ tests: re-recorded fixtures are replayed by the fake agent in CI, so the fixture scrub and the signature-only screen rule bind to the test-plan fixture contract. Every stamped test home must be re-stamped to the new row count, or the stamp gate reads `cli_verified:false`.
- security ↔ architecture: each new row is a capability-ledger row with a `viola verify` probe (architecture §Cross-cutting Patterns, Capability ledger names this entry for `rate_limits`). The plan's seventeen-row count and the founder-ratified verify child set are master text that the chunk amends at wrap.
- security ↔ CI: any new `cfg(windows)` product file owes its `windows-mutants.yml` matrix line. The plan states the matrix as ten items. The operator's direction excludes any dispatch (per security-plan §Dependency Security, CI integration).
- security ↔ secret management: the R8 identity-floor row and the harness-prefix row stay out of this entry. Each needs its own ruling (security-plan §Secret Management, Storage holds the floor).

## Acceptance criteria contributions
- (security) A stamp with any of the new rows missing or failing records `cli_verified:false`, the dialog hook prints nothing, and `answer` exits 12 `unverified-cli`. A stamp with every row passing records `cli_verified:true` (per security-plan §Security Anti-Patterns → Universal).
- (security) Each verify child the chunk adds or extends is a direct spawn under the R8 strip, and any added paste is a compiled literal written only into a settled input box. A test or code read shows no key typed into a dialog and no paste after a stop. Any widening is landed only with the founder's recorded live word (per security-plan §Threat Model Summary, Attack surface: Child process spawning and PATH resolution).
- (security) Every re-recorded fixture under `fixtures/claude/<cli-version>/` passes `--record`'s scrub, holds no home path, username or email, and its screens keep only signature rows (per security-plan §Data Protection, Repository fixtures).
- (security) A search of product source shows exactly one shell-out (`statusline::shell_argv`), and `cargo deny check` passes with no new ignore, skip or allow (per security-plan §Security Anti-Patterns → Code Patterns; per security-plan §Dependency Security).
