# tests extract

## Relevance
relevant — every part of the scope adds a ledger row with a `viola verify` probe, recorded fixtures and fake-agent replay. The test plan governs all three (row-count literals, fixture recording/hygiene, the fake-agent contract), and CARRY 2/3 fall under its mutation rules.

## Constraints
- Every ledger row needs a `viola verify` probe with a post-condition, read through the exit code and the `stamped … pass … fail` line. A row added for the LF-in-paste, `--resume`, `/compact`, settings-override, `/bin/sh`, `rate_limits` or `agents --json` shape therefore carries its own probe; a row with no probe does not meet this requirement (per test-plan §1 multi-version-compat trigger).
- `contract_ledger_probes.rs` must list each literal ledger row id exactly once, with ids written as test literals. The `<n>` in `stamped <ver>  <n> pass  0 fail` must equal the literal row count, and every fixture dir sits on exactly one list (stamped or drift-only). The plan records seventeen, so an added row moves the literal list, the count and possibly the stamped/drift-only lists. Whether the code holds exactly seventeen today is research's question (per test-plan §5 Integration Test Strategy).
- `tests/cli_verify.rs` pins the `[NN/17] <row id> <row words>  pass|fail` step lines and the last line `stamped <ver>  <n> pass  <m> fail` by literal asserts. It also pins which rows fail when a replay option is absent (without `--framing` only `local-command-clear` fails). A new row, and a fifth Run B paste, moves those literals and that per-option failure set (per test-plan §5 Integration Test Strategy).
- The harness `--local-live` suite checks a compiled `LEDGER_ROWS: [&str; 17]` literal with failure code `row-missing`. It refuses under `CI` (`live-in-ci`, exit 2) and stamps whichever `claude` is first on `PATH`. A new row moves this literal and its unit proof in `harness::run::tests`, and any live firing counts against the founder's live-start cap (per test-plan §3 `run`).
- Recorded hook payloads come only from live `viola verify` (`--record`). They are scrubbed (home → `~`, usernames → `<user>`) and `unclean`-checked, and a dirty payload refuses the whole recording. Each must pass the `claude_fixtures` walk in `tests/contract_fixture_hygiene.rs` against `schemas/claude-fixture.v1.json` (screens against `schemas/claude-screen.v1.json`). This covers a recorded SessionStart of source `resume` and any `paste-<n>` / `compact` variant (per test-plan §7 Fixture hygiene).
- The fake agent invents no shape before a recorded fixture: `agents --json` lands only with its consumer chunk. Its `--resume` SessionStart is today a rewritten `SessionStart.default` (5 key names against 10 live), and the plan owes the recorded payload to "Paste newline ledger row". Without a recorded fixture, neither the `agents --json` row nor the `resume` payload can be replayed in CI (per test-plan §7 Test Data & Fixtures, fake agent).
- The mutation gate is judged only at the epoch boundary or on demand (`run --mutants`). No chunk, pre-push or CI mutation gate exists. A mutant the 10 s kill alone grades `caught` is no assertion, so CARRY 2/3's assertion tests are shown through hand-applied mutants, red under the mutant and green restored, with no mutation run made (per test-plan §10 Mutation gate).

## Patterns to follow
- Each ledger probe arm reads its Run B capture in named unit cases: it passes on the recorded shape, fails without a matching capture, and fails on each broken post-condition (`check_framing_rows_pass_on_the_recorded_shape`, `check_paste_rows_fail_without_a_matching_capture`, `check_local_command_clear_fails_on_each_broken_post_condition`). New rows take the same three-case form (per test-plan §4 Unit Test Strategy, viola-agent-claude).
- Under `--framing` the fake agent replays a compiled Run B paste as its recorded `paste-<n>` UserPromptSubmit variant with its bytes unchanged. `contract_fake_agent_drift` compares each hook's `stdin_hex` byte for byte with the recorded variant. A fifth paste or a `/compact` probe follows the same replay-and-compare form (per test-plan §2 Contract row).
- Stamped homes come from `viola verify --home <home>` run against the fake agent (the rstest `stamped_home` fixture, or harness `boot`). After the row set grows, every stamped test home is re-stamped by running verify again, never by editing stamps (per test-plan §7 Seed strategies).
- The version gate keeps its unit case that a stamp holding only the older row ids, all `pass`, reads unverified. An added row extends that older-set oracle as a literal (per test-plan §4 Unit Test Strategy, viola-agent-claude).
- Survivor disposal follows chunks 2026-10-13-epoch-4-survivors / -ii: add a nextest case in the package that owns the mutated file, with a behaviour-preserving restatement where a site is unreachable. Each case is shown red under its hand-applied mutant (`src/bin/viola-fake-agent.rs` `replay_dialogs` / the `"--screens"` arm, `src/cmd/verify.rs` `ProbeDir::typed`, `crates/viola-state/src/fs.rs` `replace_private_retrying`) (per test-plan §10 Mutation gate).

## Anti-patterns to avoid
- NEVER import the product's ledger rows (`LedgerRow::ALL`) as the test oracle. Row ids and counts are literals in the test (per test-plan §11 Unit).
- NEVER run the real `claude` or `viola verify` against it in CI, and NEVER treat a green fake-agent run as proof of real-CLI behaviour. A new row's shape needs a local `viola verify` fixture refresh plus the contract suite (per test-plan §11 Test Strategy).
- NEVER hand-write `ledger/stamps.json`, and NEVER accept interactive snapshot review (`cargo insta review`, trycmd overwrite). Stamps come from `viola verify`, and snapshots change only through the local fixture refresh (per test-plan §11 Test Data; per test-plan §11 Universal).

## Contract bindings
- tests §3 `run` `--local-live` ↔ architecture §Cross-cutting Patterns, Capability ledger: the harness's `LEDGER_ROWS` literal and `row-missing` code mirror the ledger row set, so a row added to `LedgerRow::ALL` binds the harness literal and its unit proof.
- tests §7 fake agent `--framing` / `--resume` ↔ security-plan's ratified verify child set (Run B's four compiled pastes): any fifth paste or new verify child (a `--resume` probe) needs its fake-agent replay arm and recorded variant in step, and lands only on the founder's word.
- tests §5 `tests/cli_verify.rs` ↔ obs `schemas/diag-line.v1.json` / `process-exit.detail`: verify's role log lines are held valid against the diag-line schema. A new verify run or probe step must keep every line schema-valid with no `panic` line.
- tests §7 Fixture hygiene ↔ security NEVER-log floor: the scrub codes (`home-path` · `absolute-path` · `username` · `email`) refuse a dirty recording whole and name a class, never content.

## Acceptance criteria contributions
- `contract_ledger_probes.rs`, run against the fake agent with `--dialogs --framing` over each stamped set, lists every literal row id exactly once and ends `stamped <ver>  <N> pass  0 fail`, where `<N>` equals the new literal row count (per test-plan §5 Integration Test Strategy).
- Every newly recorded fixture passes `tests/contract_fixture_hygiene.rs` (scrub classes + jsonschema), and `contract_fake_agent_drift` replays each new variant byte for byte (per test-plan §7 Fixture hygiene).
- `tests/cli_verify.rs`'s step-line literals, and the harness `LEDGER_ROWS` unit proof, read the new row count and pass. A run without the relevant replay option fails only the rows that option feeds (per test-plan §5 Integration Test Strategy; per test-plan §3 `run`).
- Each OS job holds `cargo llvm-cov nextest … --fail-under-lines 85 --fail-under-functions 95 --fail-under-regions 80` over the chunk's new code (per test-plan §10 Quality Gates & Coverage Targets).
