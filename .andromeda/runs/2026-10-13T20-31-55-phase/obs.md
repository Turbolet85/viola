# obs extract

## Relevance
partial — the chunk is capability-ledger rows and `viola verify` probes; obs binds only where verify's child spawns, the ledger read/write and the diag-line schema meet them (a new verify child, a new probe subject, or a changed spawn-pair count).

## Constraints
- obs-plan §4 Edge flows → `verify` / `plugin install` requires `verify` (under a `VIOLA_NAME`) to log one `process-start{subject}` / `process-exit{subject, child_exit_status, duration_ms}` pair per child spawn into `cli-<name>.ndjson`, with no row text, prompt or path in any line; the plan names six pairs today (`version-probe`, `verify-probe`, four `verify-pty-probe` for Runs A–D). A new verify child (a `--resume` run, a `claude agents --json` probe) or a fifth Run B paste that changes this shape owes an amendment of that count; whether the code's pair count matches the plan is research's question.
- obs-plan §4 Edge flows → `verify` / `plugin install` requires a `verify` stopped by Ctrl-C or TERM to start no further spawn, close every pair it opened (a killed child closes with `duration_ms` and no `child_exit_status`) and end `process-exit{subject:"self", exit_code:1, detail:"interrupted"}`; any child added by this chunk must fall inside that rule.
- obs-plan §6 Log Coverage → Boundary-call wrappers (Child / shell spawns) requires `subject` to stay within the closed `$defs.subject.enum` of `schemas/diag-line.v1.json` (`self|claude-child|version-probe|verify-probe|verify-pty-probe|agents-probe|statusline-shell`), verify to log its spawns at the call site (`run_bounded` stays unlogged), and a `claude agents --json` parse failure to give `parse-rejected{parser:"claude-agents-json"}` and the value `"unknown"`; a new subject value is a schema amendment, not an open string.
- obs-plan §4 Edge flows → Capability ledger requires the stamps file to be read inside `run.version_gate` as `state.ledger_read`, its outcome carried only as `cli_verified` on `process-start{subject:"claude-child"}`, an unreadable/malformed/strict-modes-refused ledger to give `parse-rejected{parser:"ledger-stamps", detail}` and count as unverified, and the path and stamp contents never to appear — an eighteenth (or later) row changes no field of this.
- obs-plan §4 Edge flows → `verify` / `plugin install` requires the dispatch spans `cli.verify`, `cli.verify_step` per step and `state.ledger_write` for the stamp, and the hidden `hook <event> --capture <DIR> [--answers <DIR>]` arm to stay uninstrumented (no `VIOLA_*` read, no obs init, no role or detail file, no `hook-invoked` / `hook-decision`); a capture for a new probe (SessionStart `resume`, `compact`, statusline payload) goes through that arm unchanged.
- obs-plan §8 PII Scrubbing → Data classification rules requires recorded fixtures to stay scrub-required and not a telemetry source (obs adds no fixture content), `claude agents --json` rows and unwrapped session ids never to be logged verbatim (only `parse-rejected` counts), and `statusline_command` never to reach a home-level line; `rate_limits` percentages and `resets_at` are Low class, loggable only as typed fields.
- obs-plan §6 Log Coverage → `detail` code catalog requires `process-exit.detail` to stay within the 12 closed values of `schemas/diag-line.v1.json`; a new verify failure or refusal shape is a closed kebab-case code with no path or pid, never a free string.

## Patterns to follow
- The verify spawn-pair pattern (obs-plan §6 Log Coverage → Boundary-call wrappers): `process-start{subject}` before the spawn, `process-exit{subject, child_exit_status, duration_ms}` after, written at verify's call site, as the four Run A–D `verify-pty-probe` pairs are specified.
- Verify's agent-readable outcome (obs-plan §4 Edge flows → `verify` / `plugin install`): one `[NN/MM] <row id> <row words>  pass|fail` stdout step line per ledger row and the last line `stamped <version>  N pass  N fail`; `MM` follows `LedgerRow::ALL`'s length, so a new row moves the denominator.
- CI verify runs only against the fake agent at the recorded version 2.1.287 (obs-plan §4 Edge flows → `verify` / `plugin install`): `tests/cli_verify.rs`, harness `boot` step 4 and the rstest `stamped_home` fixture, `verify` the only writer of `ledger/stamps.json`; the real-`claude` verify runs only through `run --local-live`, refused under `CI` (`live-in-ci`).
- Spans as `#[instrument(skip_all, fields(...))]` and lines only via `obs_event!` with explicit typed fields (obs-plan §8 PII Scrubbing → Integration points, item 1).

## Anti-patterns to avoid
- NEVER log any field not named in the §6 catalog, and NEVER put paths or pids inside `detail` codes (obs-plan §11 Obs Anti-Patterns → PII Scrubbing) — a probe's row id, prompt, capture path or session id stays out of every line.
- NEVER use a bare `#[instrument]`, or `#[instrument(err)]` / `(ret)` where an error or return can carry a serde source or upstream content (obs-plan §11 Obs Anti-Patterns → Spans / Traces) — probe parsing of hook payloads and `claude agents --json` output is exactly such content.
- NEVER derive telemetry from screen content (obs-plan §11 Obs Anti-Patterns → Telemetry Strategy) — a probe's screen reading decides a row's pass/fail, never a log field.

## Contract bindings
- obs ↔ tests: `schemas/diag-line.v1.json` (obs-owned) closes `subject` and `process-exit.detail`; G4 (obs-plan §9 CI Integration → Gate commands) checks every home-level line of a `stamped_home` / `cli_verify.rs` run against it, so a new subject or detail value moves the schema and `tests/contract_diag_schema.rs` together.
- obs ↔ tests: the fake agent's recorded fixtures and the verify run in CI (obs-plan §4 Edge flows → `verify` / `plugin install`) — re-recorded fixtures and the `stamped_home` re-stamp are tests-owned; obs requires only that verify's lines stay within the schema and the G2 / G4 / secret-scan scope under `target/e2e-home/` (obs-plan §9 CI Integration → Pipeline integration, Integration tests).
- obs ↔ security: the verify child set and the `--capture --answers` arm are security-ratified; obs mirrors them (uninstrumented capture arm, no row text in lines) per obs-plan §4 Edge flows → `verify` / `plugin install` and obs-plan §8 PII Scrubbing → Data classification rules.

## Acceptance criteria contributions
- Under a `VIOLA_NAME`, a `viola verify` against the fake agent writes exactly one `process-start` / `process-exit` pair per child it spawns (the count the plan names, amended if this chunk adds a child), each `subject` a member of the closed enum, and no line holding row text, a prompt, a path or a session id (per obs-plan §4 Edge flows → `verify` / `plugin install`).
- Every home-level line of a verify run over the stamped home validates against `schemas/diag-line.v1.json` under G4, with no new `subject` or `process-exit.detail` value absent from the schema (per obs-plan §6 Log Coverage → Boundary-call wrappers).
- `verify`'s stdout prints one step line per `LedgerRow::ALL` row with `MM` equal to the row count, then `stamped <version>  N pass  N fail` with `N pass + N fail = MM` (per obs-plan §4 Edge flows → `verify` / `plugin install`).
- A `run` over a home stamped with the added rows reports `cli_verified:true` on `process-start{subject:"claude-child"}`, and with no stamp for the child's version `cli_verified:false`, with no stamp content or path in the line (whether a stamp written before the added rows still verifies is architecture's and research's question, not obs's) (per obs-plan §4 Edge flows → Capability ledger).
