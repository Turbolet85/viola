# a11y extract

## Relevance
partial — the chunk adds no web, ARIA, focus or keyboard surface; its a11y reach is `viola verify`'s terminal output (step lines for each added ledger row, any new fail or refusal pair), plus the CLI column's `unverified-cli` state word on the board when a new row gates `cli_verified`.

## Constraints
- a11y-plan §1 A11y Scope Summary (critical path 6, "CLI board, wait/last, verify and launch-line output") requires `verify` output to be linear and static, as step lines `[NN/NN] … pass|fail`. Each row this chunk adds to `LedgerRow::ALL`, and each new probe step, falls under that form. Whether the current step lines already take that form, and whether the `NN/NN` count comes from `ALL`, is for research to answer.
- a11y-plan §1 A11y Scope Summary (the cli surface's Notes) requires no SGR, glyph or cursor control under `--json`, non-TTY, `NO_COLOR` or `TERM=dumb`, and no spinner or redraw. That covers any progress shown while a new probe child runs (a fifth Run B paste, a `--resume` child, a `/compact` live turn).
- a11y-plan §8 Cognitive Accessibility → Error recovery requires every CLI refusal to be an `unable` line followed by a `hint:` line, which is the last stderr line, with a typed exit code. Any new failure or refusal text this chunk gives `verify` (for example, a new probe row that does not pass) takes that form. The interrupted pair (`unable: verify was stopped before it finished` / `hint: run viola verify again to stamp this CLI`) is pinned there by the stop table in `tests/cli_verify.rs`.
- a11y-plan §8 Cognitive Accessibility → Plain language requires every fixed CLI string to be pinned by trycmd or by literal, so a copy change fails CI until someone deliberately updates the pinned string. A new row's step-line label is new fixed copy under this rule.
- a11y-plan §6 Visual Design Verification → State color tokens (not-color-alone) requires the `cli_verified:false` state to be carried by its printed word `unverified-cli` on both the CLI board and the web CLI column, never by colour alone. If an eighteenth row turns an existing stamp into `cli_verified:false`, that is this state. Whether a home stamped under seventeen rows reads unverified once a row is added is for research to answer.
- a11y-plan §11 A11y Anti-Patterns → Strategy forbids claiming WCAG conformance for the cli or the `viola run` TUI. The assert_cmd, trycmd and portable-pty results this chunk adds are output-discipline stand-ins for SC 1.3.2, 1.4.1 and 3.3.1 only.

## Patterns to follow
- Output-discipline assertions on the tests' existing CLI drivers (assert_cmd with predicates, trycmd, SGR-only checks through the portable-pty outer PTY), run on all three OS legs, per a11y-plan §1 A11y Scope Summary (the cli surface's Automated tool reach).
- The fixed-message `unable:` / `hint:` pair (design-system cli pattern 2), pinned by a table of literal cases in `tests/cli_verify.rs`, as the interrupted pair is, per a11y-plan §8 Cognitive Accessibility → Error recovery.
- State shown by its printed word alone: `viola list` emits no SGR and prints `unverified-cli` as the word, per a11y-plan §6 Visual Design Verification → State color tokens (not-color-alone).

## Anti-patterns to avoid
- Never colour CLI `unable` or `fail`, and never emit SGR under non-TTY, `NO_COLOR`, `TERM=dumb`, `--json` or `viola run` (per a11y-plan §11 A11y Anti-Patterns → Visual).
- Never show an error without a recovery suggestion: every human-mode CLI refusal except `unknown` ends with a `hint:` line (per a11y-plan §11 A11y Anti-Patterns → Cognitive).
- Never parse the rendered `claude` TUI screen for content, or use screenshots, as a11y evidence (R7). A new verify probe's readings are ledger evidence, never a11y evidence (per a11y-plan §11 A11y Anti-Patterns → Universal (agent-driven specific)).

## Contract bindings
- a11y cli output discipline ↔ the tests harness: the checks run inside `nextest-integration` / `nextest-e2e` locally, and in CI inside the per-OS `test` job's instrumented `coverage` suite on all three legs. There is no separate a11y driver (per a11y-plan §1 A11y Scope Summary; §3 CI integration, `.andromeda/registries/contracts/a11y-plan/ci-integration.md`).
- a11y not-color-alone ↔ design-system §State color tokens: the `unverified-cli` word in the CLI column on both the board and the web, never a colour alone (per a11y-plan §6 Visual Design Verification → State color tokens (not-color-alone)).

## Acceptance criteria contributions
- (a11y) Every ledger row the chunk adds shows up in `viola verify`'s human output as a static, linear `[NN/NN] … pass|fail` step line, with no SGR, cursor control or redraw under non-TTY / `NO_COLOR` / `TERM=dumb`, asserted by assert_cmd or trycmd (per a11y-plan §1 A11y Scope Summary, critical path 6).
- (a11y) `fail` and `unable` in verify's output are never wrapped in SGR, asserted by an SGR-absence check on the line holding the word (per a11y-plan §11 A11y Anti-Patterns → Visual).
- (a11y) Any new verify failure or refusal prints one `unable` line and then a `hint:` line as the last stderr line, with a typed exit code, pinned by literal; the interrupted pair in `tests/cli_verify.rs` stays byte-identical (per a11y-plan §8 Cognitive Accessibility → Error recovery).
- (a11y) Every new fixed CLI string the chunk introduces (step-line labels, refusal texts) is pinned by a trycmd case or a literal in the same chunk (per a11y-plan §8 Cognitive Accessibility → Plain language).
