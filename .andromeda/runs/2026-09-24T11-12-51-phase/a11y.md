# a11y extract

## Relevance
Partial. This chunk adds no web-spa UI, ARIA, focus or contrast work. It does change two things a11y governs: the CLI error and fault text on stderr (the `main` catch site and the fixed `Display` messages), and the `viola run` terminal boundary (content-bearing records must reach the detail file, never the terminal).

## Constraints
- a11y-plan §1 (tui surface → Notes) requires that viola's diagnostics for `run` go to `diagnostics/` and never to the terminal. §3 Keyboard test harness → Tooling says viola's own message literals (diagnostics, refusal text, `hint:`) must never appear on the outer-PTY stream. Anyhow chains and serde drift reports rerouted by this chunk must respect that boundary.
- a11y-plan §8 Error recovery requires this CLI error layout:
  - a refusal prints `unable  <reason>  <detail>` on stderr, then `hint:` as the last line, with a typed exit code (`10`–`14`, `20`, `21`);
  - faults (`error: wrapper fault`, `error: internal error`) are not refusals and carry no hint;
  - `--json` gives one document with no hint.

  Fixed `Display` messages must fit this layout. Whether the catch site at HEAD prints a fault line at all is research's question; scope says it discards `Err(_)` and exits 1.
- a11y-plan §8 Plain language requires that page and CLI never show a stack trace, Problem URN or bare status number as the only error text. The chain goes to the detail file, and what reaches the human stays a fixed plain line.
- a11y-plan §1 (Structured violation JSON schema → Obs additions a11y inherits) carries the same never-log set a11y depends on: no line may contain the GUI token, `Cookie`, `?t=` or a stripped `CLAUDE*` value. §3 Structured violation JSON schema → Scrubbing adds absolute paths to the ban for a11y artifacts. Fixed displays with no paths fit that ban.
- a11y-plan §1 (cli surface → Notes) and §4 P6 require no SGR under `--json`, non-TTY, `NO_COLOR`, `TERM=dumb` or `viola run`. Any new or changed stderr fault or error line must be emitted unstyled in those modes.
- a11y-plan §1 (cli surface) says CLI output-discipline assertions are stand-ins for SC 1.3.2 / 1.4.1 / 3.3.1, not a WCAG conformance claim. See also §11 Strategy.

## Patterns to follow
- Refusal vs fault split per a11y-plan §8 Error recovery: a refusal is `unable <reason> <detail>` plus `hint:` (`unknown`, exit 14, has no hint), and a fault is a fixed `error: …` line with no hint. Fixed `<Crate>Error` messages should map onto one of the two.
- Kebab-case reason/detail codes always sit beside the plain word `unable` (a11y-plan §8 Plain language). A fixed error code surfaced to the human, such as `ConfigRejection::Unreadable`, keeps that pairing wherever it reaches stderr.
- Copy pinning: trycmd pins every fixed CLI string, so a change to a displayed message fails CI until the pinned string is updated on purpose (a11y-plan §8 Plain language → Verification). New fixed displays are pinned strings.
- Output is linear and static (a11y-plan §4 P6): one line per error, no redraw or cursor control, and no multi-line chain dump on stderr.

## Anti-patterns to avoid
- NEVER render a stack trace, Problem URN or bare status as the only error text in the CLI (a11y-plan §11 Cognitive).
- NEVER colour CLI `unable` / `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` (a11y-plan §11 Visual).
- NEVER write a11y violation rows into `<home>/diagnostics/` (a11y-plan §11 Universal; §3 Structured violation JSON schema → Emission location). The detail sink and `diag-detail.v1.json` must not become a carrier for harness rows.

## Contract bindings
- a11y ↔ obs: `event:"a11y-violation"` is a harness-only row, validated by the tests-owned `e2e-web/schemas/a11y-row.v1.json`. It is not an `ObsEvent` value, and neither `diag-line.v1.json` nor the detail schema should admit it (a11y-plan §3 Structured violation JSON schema → Binding fields; Decisions Log D-A11Y-09). The never-log set in §1 (Obs additions a11y inherits) is the obs/security floor this chunk enforces. a11y relies on it and adds its own scrub on top.
- a11y ↔ tests: the tui zero-viola-bytes nextest case (a11y-plan §3 Keyboard test harness → Tooling; §4 P4 tui clause 1) runs on all three OS legs. Routing chains to the detail file instead of the terminal must keep it green. The CLI trycmd/assert_cmd pins for refusal layout and typed exit codes (a11y-plan §8 Error recovery → Verification; §4 P6) sit in `nextest-integration` / `nextest-e2e` (a11y-plan §1 CI integration).

## Acceptance criteria contributions
- Under `viola run`, a forced anyhow error or serde drift writes its chain or drift report only to `instances/<name>/diagnostics/detail-<process>.ndjson`. The outer-PTY stream contains none of viola's own literals, chain text or SGR. (per a11y-plan §1 tui Notes; §3 Keyboard test harness → Tooling)
- A human-mode fault at the `main` catch site prints at most one fixed `error: …` line on stderr. That line has no path, upstream/serde text, payload, stack trace or `hint:`, and carries no SGR under non-TTY / `NO_COLOR` / `TERM=dumb`. (per a11y-plan §8 Error recovery; §11 Cognitive; §11 Visual)
- `--json` error output is one document with no hint text and no chain or drift content. (per a11y-plan §8 Error recovery)
- Existing trycmd/assert_cmd pins for the `unable <reason> <detail>` + `hint:` layout and the typed exit codes stay green, or are updated on purpose if a displayed message changes. Whether such pins exist at HEAD is research's question. (per a11y-plan §8 Plain language → Verification; §4 P6)
