# arch extract

## Relevance
relevant — the chunk is one live run of the product binary over nearly every landed arch contract (wheel, delivery confirmation, version gate, dialog channel, home resolution), and architecture.md names this entry as the owner of several live readings; the code it may change is small (the `input-not-ready` hint line, plus any fix a falsified reading or a switch gap brings).

## Constraints
- **Mechanism, not policy (W2).** architecture.md §Design Philosophy ("Mechanism, not policy") and §Established Decisions [Scope Boundary] require that driver-side policy stays outside the binary and that every feature is a general bridge verb. The overseer's procedure, its start line and the switch off the prototype are therefore outside the product; a gap P3 finds between the prototype's start line and the product may enter the binary only as a general verb or flag (§Project Intent "How new functionality is added"), never as an overseer-specific behaviour. The dialog wait is the compiled `viola_core::DIALOG_DEADLINE` per §Established Decisions [Hook Contract], and §Cross-cutting Patterns "Config management" lists the whole settings set and rules env vars out as a configuration channel — so the prototype's `--dialog-timeout` has no arch-sanctioned twin today; whether the switch needs one is a founder question, as the scope already says.
- **The wheel (W1 takeover).** architecture.md §Established Decisions [Human Takeover / Wheel] requires: any human editing byte on the wrapper's host stdin since the last turn boundary moves the wheel to `human`; a closed non-editing list (focus reports, mouse reports, terminal replies) never counts; a host resize is no stdin byte. So focusing the window through the compositor must not be what the proof rests on — only the typed key is an editing byte. The same entry requires that, once the wheel is `human`, a driver `send` is refused `human-typing`, `answer` is refused `human-typing`, and a pending `hook.dialog` is answered `null` at once — so the takeover step is ordered after every dialog step of the run, or it voids them. Whether the code already moves the wheel on a compositor-typed key is research's question (inputs#I3).
- **The wheel's return.** architecture.md §Established Decisions [Human Takeover / Wheel] requires that the wheel returns only through CLI `viola release`, and §Established Decisions [MCP] requires that a `release` whose `params` carry a string `from` is refused `-32602` `release-from-driver` — the CLI adds `from` whenever the calling process has `VIOLA_NAME` set (§Conventions "CLI"). A `release` issued from inside any wrapped session is therefore refused by design; how the wheel comes back with no human at the desk is P4's to state against that rule, and no driver-facing line may suggest the verb.
- **The verified-CLI gate (W1, W3, W4).** architecture.md §Established Decisions [CLI Version Compatibility] requires: `run` reads the version of the resolved child executable by one `--version` spawn; a version is verified only when its stamp holds all seventeen rows `pass`; on an unverified version dialog answers are withheld (`unverified-cli`) and the gate is partial. §Standard Contracts "Ledger stamps envelope" requires `viola verify` to be the one writer of `ledger/stamps.json`, per home. So W3's decided dialog and W1's `/clear` confirmation both need the chunk's own home stamped for exactly the binary the builder runs (2.1.287 by path); the same entry prices a verify at five `claude` starts, which is the arithmetic the cap of 8 rests on. Whether `run --local-live` can name a program is research's question (the scope's W4 premise).
- **Delivery confirmation (W1, W5).** architecture.md §Established Decisions [Delivery Confirmation] requires: every `send` is confirmed against the typed text (the sent text less its trailing LF characters, nothing else trimmed); a skill send is an ordinary send confirmed by its `prompt-submitted`; `/clear` is classified by exact equality with the compiled local-command list and, on a verified version, confirmed only by a `session-start` with `cause` `clear` and a new `agent_session_id`; a `send` returns within the gate's maximum wait plus the paste plus the window. That entry states the live proof of the `/clear` confirmation is owed to this entry and that a send ending in newlines, a text of only newlines and a trailing CR are unmeasured on a live CLI; §Established Decisions [CLI Version Compatibility] states a `send` under the real CLI's paste hint is unmeasured since the build. The run reads these, it does not presume them.
- **The driving surface (W1, W3).** architecture.md §Established Decisions [CLI Conventions] requires prompt text from stdin or `--file`, never a leading-slash argument — the pipeline skill and `/clear` are both leading-slash texts. §Conventions "CLI" and "CLI exit codes" fix the verb shapes and the typed exits (`10` `human-typing`, `12` `unverified-cli`, `13` `not-delivered`, `21` unreachable); §Established Decisions [Message Broker / IPC] requires `answer` to name its target by the wrapper-assigned `dialog_id`, at most one pending dialog per instance, and `wait` to return a pending dialog at once and otherwise the first wake event at or after `after`. §Established Decisions [Deployment / Distribution] states `.mcp.json` ships no server until the `mcp` verb exists, so the run drives through the CLI verbs only.
- **Home and identity of the driving process (W1, W2).** architecture.md §Cross-cutting Patterns "Config management" requires the home to resolve as `--home`, then the grandparent of `VIOLA_DIR`, then the default; §Cross-cutting Patterns "Identity by instance, never by location" and §Established Decisions [Links] require the CLI to pass its own `VIOLA_NAME` as `from`, which records a `driver → driven` link on the first `send` or `answer`. The driving session in this chunk is itself wrapped by another tree's wrapper: whether that wrapper sets `VIOLA_DIR` / `VIOLA_NAME` in the driver's environment — and so whether a product `viola send` without `--home` would resolve the wrong home and what `from` it carries — is research's question. Every verb of the run names the chunk's home explicitly.

## Patterns to follow
- **Read the run on the product's own records.** architecture.md §Standard Contracts "Event `data` per kind" and "Instance snapshot" give the evidence shapes: the `wheel` line (`holder`, `cause`), `send-issued` / `send-confirmed` / `send-refused`, the dialog lines with `dialog_id`, `session-start` with `cause`, and the snapshot's `cli_version`, `cli_verified`, `wheel`, `pending_dialog`. §Established Decisions [Delivery Confirmation] fixes the order to read (`prompt-submitted`, or the `clear` `session-start`, before `send-confirmed`).
- **Cursor-chained driving.** architecture.md §Established Decisions [Message Broker / IPC] and §Standard Contracts "Channel methods" (`send`, `wait`): each `send` `ok` carries `cursor`, passed as the next `wait --after`, so a turn that ends before the `wait` is never missed; a cursor-less `wait` returns only what is appended after the call.
- **One isolated home per run, stamped by the product's own verb.** architecture.md §Cross-cutting Patterns "Config management" (the `--home` isolation point) with §Established Decisions [CLI Version Compatibility] (`viola verify [--record <DIR>] [-- <program> [args…]]`): the home is stamped by `verify` naming the program after `--`, and `run` in that home is given the same program. §Occupied Resources "Repository" gives `run --local-live` its own home class (`target/e2e-home/viola-live-<pid>/home`) and §Occupied Resources "Environment variables" (`CI`) its `live-in-ci` refusal under a set `CI`; whether the builder session's environment carries `CI` is research's question.
- **The no-live-start key measurement over the fake agent.** architecture.md §Established Decisions [CI/CD] gives the substitution (the fake agent named after `--`); §Occupied Resources "Binary, subcommands and exit codes" marks `viola-fake-agent` a test-only binary behind feature `fake-agent`. A `viola` built with that feature is not the product (§Occupied Resources "Workspace crates"), so that measurement settles the keystroke question only; the claim's run uses the product build.
- **A reworded hint line stays in the one human writer.** architecture.md §Infrastructure Patterns → Build system requires `src/human.rs` to be the root bin's only human writer, with the `unable:` / `hint:` pair fixed and written as one write; §Conventions "Error handling schema" keeps the refusal reasons and details a closed set extended only in `viola-core`. W7 changes a fixed line's wording, not a detail, an exit code or a `--json` field.

## Anti-patterns to avoid
- **A new screen-content exit to prove "never renders" (W3).** architecture.md §Stack and Technologies (row "Screen model") and §Established Decisions [Screen Model] require that `run` never reads screen content and that `Screen::rows()` is the only row-text exit, read by `viola verify` alone. The reading is taken outside the product's `run` path; how is P3's.
- **Hard-coding a behaviour the live session shows.** architecture.md §Cross-cutting Patterns "Capability ledger as the single gate for CLI-specific behaviour" requires any new dependence on an undocumented `claude` behaviour to be a ledger row with a `viola verify` probe (one ruled limit: a shape no `send` relies on needs no probe). §Established Decisions [CLI Version Compatibility] prices a new row at a re-stamp of every stamped version, five starts each — a fix of that kind does not fit the cap of 8 and is carried, not folded.
- **Closing a prototype gap through the environment or a driver-reachable `release`.** architecture.md §Cross-cutting Patterns "Config management" (env vars are not a configuration channel; `VIOLA_*` is wrapper-to-child plumbing set by `run` only) and §Established Decisions [MCP] (`release`, `pause`, `link`, `unlink` are human controls, CLI-only, never offered to a driver).
