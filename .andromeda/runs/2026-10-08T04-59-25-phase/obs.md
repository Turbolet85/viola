# obs extract

## Relevance
partial — the chunk adds no instrumentation of its own; it reads the product's process logs and event stream as the evidence of one live run (W1, W3, W5, W6), and a product change from W5 or W7 would fall under the log allow-list (tier per obs-plan §1 Obs Scope Summary: Standard with Minimal exporter carve-outs).

## Constraints
- Every reading the live run rests on is a machine verdict: obs-plan §2 Telemetry Strategy → Agent-readable invariants requires a `jq` / harness assertion that sets an exit code, over the ndjson process logs and the event stream; a reading taken by eye from a log is not a verdict.
- The live session's input is not synthetic. Obs-plan §8 PII Scrubbing & Compliance → Data classification rules classes prompt text, assistant output, tool `input`, plan text and dialog questions/answers as High: they may stand only in contract payloads and the instance `detail-<process>.ndjson`. Obs-plan §8 → Integration points item 6 admits detail-file and `target/agent-run/` carriage only on synthetic input, so the chunk's evidence files quote home-level role-file lines and codes, never a detail line or an event payload's text.
- Home-level role files are required to be codes-only by construction, 0600 in 0700 directories, under `<home>/diagnostics/` of whichever home the chunk stamps (per obs-plan §3 Log file location). Whether the code already writes the live home so is research's question; a home behind the `target/e2e-home` link holds its diagnostics in memory and loses them at a reboot (same key), so evidence that must outlive the session is copied out as codes before then.
- A product change this chunk brings (a falsified W5 reading, the W7 hint wording) may log no field outside the catalog and no new `event` value without a Decisions Log entry (per obs-plan §6 Log Coverage → Additive field catalog; obs-plan §8 → Default-deny posture). The refusal detail `input-not-ready` is a closed code taken verbatim from the arch `RefusalReason` (per obs-plan §6 → `detail` code catalog): rewording the human hint line moves no code.
- Obs-plan §4 Span / Trace Coverage → Scenario: Human takes the wheel requires that a `release` carrying a string `from` is logged as its own `release-from-driver` line beside the `-32602` reply, and notes that CLI `viola release` forwards `VIOLA_NAME`. How the wheel returns with no human at the desk (W1) is therefore bounded on the obs side: a release issued from a session that has `VIOLA_NAME` set reads as a driver's. Whether the code already behaves so is research's question.
- The zero-unlogged-panics invariant covers every role of the live run after init step 4 (per obs-plan §10 SLO Invariants & Telemetry Budgets → Always-required SLO invariant). Gate G2's scope is the home-level role files under `target/e2e-home/` (per obs-plan §9 CI Integration → Gate commands); whether the live home sits inside that scope, and what G2, G4 and the secret scan then read from a non-synthetic home, is research's question.
- The real-`claude` verify runs only through the local `run --local-live`, which refuses under `CI`; no obs gate depends on verify's own log lines, and its agent-readable outcome is the exit code plus the stdout step lines and last line (per obs-plan §4 → Edge flows, `verify` / `plugin install`). With `VIOLA_NAME` set, that section requires six spawn pairs in `cli-<name>.ndjson`; from a plain terminal, no process-log file. Which case W4's firing is, is research's question.

## Patterns to follow
- Follow one send across every side with the canonical query: send lines selected by the target's `instance`, the `event` filter and the cursor in `corr`, joined to that call's `channel-*` lines by `(conn, rpc_id)`, the hook side by `hook_event` and timestamp (per obs-plan §3 Snapshot / paste-to-AI integration). Whether `agent-run logs` reads a home the harness did not boot is research's question.
- W5's readings map onto fields the plan already requires: `text_bytes` on `send-issued` as the typed-text length, `send-confirmed{confirmed, duration_ms}` with the readiness gate's wait inside `duration_ms`, a `/clear` confirmed by the `session-start` hook line, an unconfirmable send as one `send-issued` and one `send-confirmed{confirmed:false}` with no hook side (per obs-plan §4 → Scenario: Confirmed `send` (CL-1) from driver to readback; obs-plan §5 Metric Coverage → Per-surface / per-path metrics, `viola.send.confirm_ms`). W7's `viola wait` reading is `channel-response{method:"wait"}.outcome` (per obs-plan §4 → Scenario: `wait` / `last` event-driven readback).
- W3's decision half is read on one `dialog_id`: `dialog-raised`, `dialog-answered`, then the hook's `hook-invoked` and `hook-decision` with `decision_emitted` and `deadline_hit`; the deadline path is the one on which the dialog renders for the human (per obs-plan §4 → Scenario: Dialog → `answer`).
- W1's takeover is read on the product's records: the `wheel` product event in `events.ndjson` is the audit record, beside the wrapper's `send-refused` with `refusal:"human-typing"` and the client's `process-exit` (per obs-plan §4 → Scenario: Human takes the wheel). Whether a driver verb leaves a `cli-<name>.ndjson` line depends on an instance resolving for it (per obs-plan §4 → Instrumentation per surface, cli short-lived verbs); which name resolves for the session that plays the overseer is research's question.
- The live builder's identity and W6's Unix reading come from the start lines: `process-start{subject:"claude-child"}` with `cli_version`, `cli_verified`, `pty_backend` and the stripped and kept names, `endpoint_kind` on the wrapper's own start line, and the start order read from `events.ndjson`, not from process logs (per obs-plan §4 → Scenario: `viola run` start sequence to child spawn).

## Anti-patterns to avoid
- NEVER derive telemetry from screen content (per obs-plan §11 Obs Anti-Patterns → Telemetry Strategy). W3's "never renders" reading and the compositor keystroke are measurements of the run; no product event, field or span may be added that carries what the screen showed, and typed keys never appear in a span or line (per obs-plan §4 → Scenario: Human takes the wheel).
- NEVER use human-review-gated log analysis, and no log-based wait on a sleep (per obs-plan §11 → CI; obs-plan §10 → Standard+ invariants, Deterministic emission).
- NEVER log send text, tool `input` or `last_assistant_message` in a home-level file, and never a path or pid inside a `detail` code (per obs-plan §11 → PII Scrubbing); the chunk's evidence keeps the same floor.

## Contract bindings
- obs ↔ tests: the consumption path is the harness `logs` / `status` commands (obs-plan §3 Snapshot / paste-to-AI integration ↔ test-plan §3).
- obs ↔ tests: the line schema is tests' Log format, reproduced as binding; obs owns `schemas/diag-line.v1.json` and `schemas/diag-detail.v1.json`, tests own the check body (obs-plan §3 Log format JSON schema; obs-plan §9 → Gate commands, G4 ↔ test-plan §3 Log format).
- obs ↔ security: the NEVER-log floor and the secret scan over `diagnostics/` (obs-plan §8 → Integration points item 6 ↔ security-plan §Bootstrap phases, `logging-redaction-wire`); the `env_stripped_known` / `env_kept` fields are names only (obs-plan §4 → Edge flows, E2).
- obs ↔ architecture: `events.ndjson` is the arch-owned product audit stream, never rotated and never copied into process logs (obs-plan §2 → Telemetry signal pyramid, Audit Logs); a home the overseer keeps driving through after W2 has no rotation in v1 (obs-plan §10 → Operational retention).

## Acceptance criteria contributions
- (obs) The live home's home-level role files hold zero `event:"panic"` lines, counted by `jq` with `detail-*` files excluded, and zero schema-conformance failures against `schemas/diag-line.v1.json` (per obs-plan §10 → Error budget).
- (obs) The takeover reads as one wrapper `send-refused` carrying `refusal:"human-typing"`, `wheel:"human"` and `side:"wrapper"` after the `wheel` record in `events.ndjson`, with the driver's exit code 10, and no line carries the typed key (per obs-plan §4 → Scenario: Human takes the wheel).
- (obs) For the dialog the driver decided, `dialog-raised`, `dialog-answered` and `hook-decision` share one `dialog_id` in `corr`, and the `hook-decision` line reads `decision_emitted:true` with `deadline_hit:false` (per obs-plan §4 → Scenario: Dialog → `answer`).
- (obs) No evidence file the chunk commits holds a `detail-*.ndjson` line, an event payload's text, a `CLAUDE*` value or an absolute path; every quoted log line is a home-level, codes-only line (per obs-plan §8 → Data classification rules).
