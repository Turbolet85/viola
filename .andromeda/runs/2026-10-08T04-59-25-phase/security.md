# security extract

## Relevance
relevant — the chunk adds little code but runs the plan's highest-impact surface live (channel `send` / `answer` into a real `claude` child, a `viola verify` stamping round, a home it creates itself), so the stamp gate, the verify-children rulings, the home modes, the dated IPC gaps and the NEVER-log floor all bind its run and its evidence; the loopback GUI, MCP and dependency sections are untouched.

## Constraints
- The stamp is the only switch for a decided dialog (W3, W1's "answers a review" when it is a dialog): security-plan §Security Anti-Patterns → Universal requires that a non-`null` `hook.dialog` decision flows only when `ledger/stamps.json` holds a `viola verify` stamp for the child's CLI version with all seventeen rows passing, read by `run`'s version gate through the strict-modes read, and that no process other than `viola verify` writes that file. The chunk's home is therefore stamped by a verify run on 2.1.287 by path and by nothing else: no copied, hand-written or edited stamp, and nothing taken from the earlier by-path home. A red verify round leaves `cli_verified:false`, and the plan gives no way around it.
- Every stamping round (W4, and any `run --local-live` firing) runs verify's four interactive children under the standing rulings: security-plan §Threat Model Summary (Attack surface, child process spawning and PATH resolution) requires direct spawns under the R8 strip, output through `MAX_FRAME`, compiled-literal pastes only, no byte typed into any dialog (CLI-native or the probe's own) and a modal start killed with no key. Security-plan §Data Protection (Interactive probe dirs; Dev-host prerequisite) requires the probe dirs to be 0700 and removed on every exit path, and the verify to start from a folder already trusted in Claude Code with the external-import question already answered. Whether the folder the plan picks for the chunk's verify meets that prerequisite is research's question; verify never answers the dialog if it does not.
- The home this chunk creates must itself pass strict-modes: security-plan §Authentication & Authorization (`~/.viola/` access control) requires 0700 dirs and 0600 files set explicitly, and a read rule that refuses a home or `instances/<name>/` carrying any group or other bit. A home made by hand with the umask, or on a backing that does not keep modes, reads `cli_verified:false` at `run`'s gate, which would make W3 unreadable; how the chunk creates its home (by the binary, never by a pre-made directory with loose modes) is the plan's to state, and whether the binary already creates every level at those modes is research's question.
- The driving verbs run under the dated interim gaps and widen none: security-plan §Authentication & Authorization (IPC client-side server verification) records that CLI `send`, `wait`, `last`, `answer`, `pause` and `release` write their frame after a liveness-only pre-check until the Epoch 6 entries, each gap ruled for its own frames only. The chunk adds no channel method, no listener, no new client of those frames and no script that writes a frame itself (security-plan §Security Anti-Patterns → Authentication; §Security Anti-Patterns → Universal, the new-listener / new-method bullet). The residual the gaps name (a same-user process on a stale endpoint name could answer a dialog, a PermissionRequest `allow` included) stands during the live run; what `allow` the run's review answer may carry is a plan decision made knowing it.
- W5's four readings exercise the paste rule as written, and any fix a falsified reading brings keeps it: security-plan §Input Validation (Paste text row) requires validation over decoded chars on the text as received, refusal whole on a refused character, and the one removal (trailing LF only, after validation) feeding the local-command classification, the exact match, `text_bytes` and the paste alike. A trailing CR is not removed by that rule, and a text of only newlines is typed as the empty text; the readings record what the live CLI does with each, they do not re-decide the rule. Security-plan §Security Anti-Patterns → Input bans stripping a refused character; security-plan §Security Anti-Patterns → Code Patterns bans building the local-command list from runtime or upstream text.
- The wheel's return is not an automation step: security-plan §Authentication & Authorization (Driver-originated `release`) requires a `release` carrying a string `from` to be refused `-32602` `release-from-driver`, and states the guard is an affordance a same-user process can step around by leaving `from` out. With no human at the desk, a plan step in which an agent runs `release` without `VIOLA_NAME` to get the wheel back is exactly that step-around; it is a founder question for P4, never a default. Security-plan §Security Anti-Patterns → Universal also requires that no refusal ever blocks, delays or answers the typed key itself.
- Evidence stays names-only: security-plan §Bootstrap phases (`logging-redaction-wire`) requires that no GUI token, launch URL, `Cookie` value or R8-stripped `CLAUDE*` value reaches any log, diagnostic, event, snapshot or fixture, and that user content sits only in the content-bearing contract payloads and `instances/<name>/diagnostics/`. Security-plan §Secret Management (Storage) requires the strip, and its `process-start` record, to handle names only. Security-plan §Threat Model Summary (Data classification, credential) records that the two dev-host crossings of 2026-10-07 (one peer message, one names-only environment list) cover no second message and no other probe: this chunk's live session repeats neither, and reads no `CLAUDE*` value into any file.

## Patterns to follow
- The builder child is named by path and resolved by `run` itself: security-plan §Input Validation (Child executable resolution) requires `viola run` to resolve the child program and hand the PTY layer an absolute path, with the child's cwd set explicitly; `viola run <name> -- <path to 2.1.287>` is that pattern, and PATH `claude` is never what the run reaches.
- The product writes its own plugin and settings at every start, with absolute pinned exec paths: security-plan §Data Protection (At rest, Code-bearing artefacts) and security-plan §Security Anti-Patterns → Universal (the exec-form `command` bullet). For W2's gap list this is the reference: the prototype's external plugin directory has no counterpart to carry over, and a gap is never closed by a PATH-resolved hook command or a plugin tree outside the pinned folder.
- A refusal line is a fixed message with a validated name and nothing else: security-plan §Error Handling (External responses; Internal logging) requires fixed `Display` text with no path, no upstream text and no internal type name on stderr. Every candidate wording shown to the founder for the `input-not-ready` hint (W7) is of that shape.
- What the overseer reads back is content, escaped for a terminal: security-plan §Bootstrap phases (`logging-redaction-wire`) requires human-mode `wait` / `last` output to escape C0/C1 controls. Evidence quoting a live `last` goes through the product's own output, and security-plan §Authentication & Authorization (Accepted risk, driver prompt injection) leaves what to answer to the driver, outside viola.
- If any fixture is recorded, only through `viola verify --record` and its scrub: security-plan §Data Protection (Repository fixtures) requires synthetic probe prompts, the home-prefix and user-word scrub, signature-only screen rows and a whole-recording refusal by file name and closed code.

## Anti-patterns to avoid
- No control is switched off or stood in for to make the live run pass: security-plan §Security Anti-Patterns → Universal bans any `config.json` key, `VIOLA_*` variable or CLI flag that disables a control, and allows the two test seams only under the `fake-agent` feature. A build carrying `fake-agent` or `test-support` is not the product (security-plan §Dependency Security, CI integration, the `release` job's check), so the fake-agent window used to measure the compositor key proves nothing about the product run, and no seam is called the typed key.
- Nothing recorded from the W1 builder session becomes a fixture, and no home is committed: its prompts are a real pipeline skill, not synthetic. Security-plan §Security Anti-Patterns → Data Protection bans committing `fixtures/claude/*` recorded from sessions with real prompts; security-plan §Security Anti-Patterns → Secrets bans committing a local `--home` test directory.
- Builder output is never treated as a command or a config by viola or by anything this chunk adds to it: security-plan §Security Anti-Patterns → Code Patterns (the R1 bullet; `statusline_command` stays the only shell-out).

## Contract bindings
- obs: the NEVER-log floor binds to the artifact canary scan obs owns (security-plan §Bootstrap phases, `secret-scanning-ci-gate`); the live home's diagnostics and the chunk's evidence are local and reach no CI upload.
- tests: `viola verify` against the real CLI, and so `run --local-live`, run only locally and never in CI (security-plan §Threat Model Summary, Infrastructure, CI/CD). If the chunk's home sits under `target/e2e-home`, the test-side removal rule and the link keepers apply to it (security-plan §Security Anti-Patterns → Code Patterns, the `target/e2e-home` bullet): only a dir the test side itself created is removed, and viola never reads the backing by that name.
- architecture: the seventeen-row counter that gates `cli_verified` is the capability ledger's (security-plan §Security Anti-Patterns → Universal); W4's pass line and the stamp gate read the same row set.
- Accepted residual: security-plan §Data Protection (Accepted risk, verify's trusted runs B, C and D) names the transcripts verify's runs leave under `~/.claude/projects/` and requires that viola itself writes nothing under `~/.claude`. That paragraph names verify's runs only; the W1 builder session's own transcript is the CLI's ordinary record of a `viola run` child and is not named there.
- Not covered by the plan: a key synthesized by an agent through the compositor (`wtype`, `hyprctl`) into a terminal window on a shared desktop. The security plan has no row for it and nothing is extracted; its authority is the founder's ruling the scope records (inputs#I3), and the scope's own focus read-back rule is the only control named.

## Acceptance criteria contributions
- The chunk's home holds a 2.1.287 stamp written by `viola verify` alone, with all seventeen rows `pass`; the home and its `instances/<name>/` carry no group or other bit; the live `run` reads the stamp through the strict read and records the CLI as verified; and the driver's `answer` in W3 is accepted, never exit 12 `unverified-cli` (per security-plan §Security Anti-Patterns → Universal; security-plan §Authentication & Authorization, `~/.viola/` access control).
- After each verify round, passing or failing, no `.viola-verify-*` dir remains in the cwd or under the OS temp root from that round, no key was written into any dialog, and viola wrote nothing under `~/.claude` (per security-plan §Threat Model Summary, Attack surface, child process spawning and PATH resolution; security-plan §Data Protection, Interactive probe dirs).
- No file the chunk commits (evidence, report, any fixture) holds a GUI token, a launch URL, a `Cookie` value or the value of any `CLAUDE*` variable, and none is a copy of the chunk's home or of the builder session's content-bearing files; `CLAUDE*` variables appear by name only (per security-plan §Bootstrap phases, `logging-redaction-wire`; security-plan §Security Anti-Patterns → Secrets).
- After the typed key, a driver `send` is refused and no step of the run returns the wheel through a `release` issued by an agent with `from` left out unless the founder ruled that step; the `input-not-ready` hint, whatever wording he picks, prints as a fixed line carrying only the validated instance name (per security-plan §Authentication & Authorization, Driver-originated `release`; security-plan §Error Handling, External responses).
