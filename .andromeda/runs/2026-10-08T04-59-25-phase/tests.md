## Constraints
- The real `claude` CLI is local-only and never runs in CI; the only plan-sanctioned entry is `agent-run run --local-live`, which must refuse with `live-in-ci` (exit 2) before any build or spawn when `CI` is set (per test-plan §11 Test Strategy; per test-plan §3 `run`).
- test-plan §3 `run` requires `--local-live` to run AFTER the selected suites (the default selection is `--all`, so a bare firing runs the unit, integration and fake-agent E2E steps first), then build into `target/harness`, then ONE `viola verify` with the program default `claude` and no `--`, in `target/e2e-home/viola-live-<pid>/home`. As specified that reaches PATH `claude`, which pulls against R-L3 (2.1.287 by path, PATH `claude` unstamped). Whether the code at HEAD still passes no program is research's question; the plan holds no by-path form, so any by-path firing is a change to this contract and a P4 question, not a lean (per test-plan §3 `run`).
- The `local-live` suite passes only on verify exit 0, each of the seventeen literal row ids naming exactly one step line ending `  pass`, and a last line `stamped <version>  <n> pass  0 fail`; its failure codes are the closed four, and it claims no live product measurement beyond that. It is not a `gate --require` value. So W1, W3, W5 and W6 readings are not covered by a green `local-live`; their proof form is the chunk's evidence, stated at P4 (per test-plan §3 `run`; per test-plan §3 `gate`).
- `ledger/stamps.json` is written only by `viola verify`; the home W1 drives must be stamped by a real verify run, never hand-written or copied in (per test-plan §7 Seed strategies; per test-plan §11 Test Data). The plan's verify shape is one print probe plus four interactive runs (per test-plan §3 `boot` step 4), consistent with the scope's five-start price; whether that count still holds at HEAD on the real CLI is research's question.
- A green fake-agent run is never proof of real-CLI behaviour, and a Linux-only local run is never proof for Windows or macOS. This bounds what W6 and the re-worded `v1-33` may claim: the Linux dev host only; and a W5 reading that falsifies a compiled behaviour requires a local `viola verify` fixture refresh plus the contract suite with its fix, not a fake-agent green (per test-plan §11 Test Strategy).
- Verdicts come from hook events, `events.ndjson`, channel payloads and the product's own exit codes, never from parsed child-screen content; screen evidence is limited to the compiled signature literals, and content beyond them is never asserted. W3's "never renders" reading must be stated in that form (which record or signature shows a dialog did or did not draw is research's question); a reading that needs scraped screen text is a P4 question (per test-plan §11 E2E; per test-plan §4 viola-agent-claude).
- No human-in-the-loop step, no sleep-based synchronisation, no retry for green: every live step waits on a cursor, an event offset or the product's own exit code, and a red is fixed at its cause inside the chunk (per test-plan §2 Agent-runnable invariants; per test-plan §10 Zero-flakiness budget).

## Patterns to follow
- Live readback flow: `send` returns a cursor, `wait --after <cursor>` wakes only on `turn-ended` / `question` / `permission` / `plan` / `session-end`, `last` reads the newest `turn-ended`; `activity` and `wheel` records wake nothing. W7's question (what a driver can usefully do after `input-not-ready`) is read against this wake set (per test-plan §6 Path 3).
- Dialog answer flow: `wait` returns the dialog event with its `dialog_id`, `answer` goes by that id, and a decision body exists only with a verify stamp and wheel `driver`; an unstamped home refuses `answer` with exit 12 (per test-plan §6 Path 4; per test-plan §6 Path 7).
- Takeover signals: a `wheel{holder:"human",cause:"human-input"}` record, then driver `send` exit 10 with detail `null`, then `release` returning `{wheel:"driver"}` and the next `send` exit 0; on Unix focus, mouse and resize reports never take the wheel, so the wheel record must be attributable to the typed key and not to the focus change that precedes it (per test-plan §6 Path 5).
- The readings §6 Path 2 names as owed here are read on the same signals its fake-agent cases use: exit code, the `send-issued` → `prompt-submitted{origin:"driver"}` → `send-confirmed` records, absence of `send-refused` and `wheel`, and for `/clear` on a verified CLI the `session-start` with cause `clear` and a new session id (per test-plan §6 Path 2).
- A home under `target/e2e-home` on the Linux dev host lives on a tmpfs behind an operator-set link and does not survive a reboot; evidence the chunk needs is copied out of it by path. The plan ratifies removal through that link only for `viola-session-*` dirs the harness made; it names no removal for `viola-live-<pid>` (whether `--local-live` leaves it is research's question) (per test-plan §3 `logs`; per test-plan §3 `cleanup`).

## Anti-patterns to avoid
- Never turn the live session's content into fixtures or committed test data: fixtures come only from `viola verify` probe text, scrubbed and `unclean`-checked, and no `--home` test dir, token or cookie is committed (per test-plan §11 Test Data; per test-plan §7 Fixture hygiene).
- Never auto-approve a dialog or accept a decision emitted without a stamp and wheel `driver`, and never replace an event wait with a sleep or a re-run (per test-plan §11 Universal; per test-plan §11 E2E).
- Never change a pinned human-mode line by snapshot overwrite or interactive review: a re-worded `input-not-ready` hint moves its literal pins in the same change (per test-plan §11 Universal).

## Contract bindings
- tests ↔ architecture (capability ledger): the seventeen row ids of `LEDGER_ROWS` are test literals in the harness and in `contract_ledger_probes.rs`, and the `<n>` of the stamped line must equal the literal row count; the same check is the one `--local-live` applies to the real CLI (per test-plan §5 CLI; per test-plan §3 `run`).
- tests ↔ security: `viola verify` is the single writer of stamps, and its live children run under the standing verify rulings; the harness never types into a dialog (per test-plan §7 Seed strategies; security-plan owns the rulings).
- tests ↔ obs: the harness `schema-check` and `secret-scan` walk `target/e2e-home/**`; a live home left there with real session content is inside that walk on any local run of those subcommands (per test-plan §3 Internal harness subcommands; obs-plan §9 owns the gates).
- tests ↔ design/layout (CLI human mode): every refusal ends in a last stderr `hint:` line that names its cause, no two causes share a hint, and no driver-facing hint contains `release`; W7's candidate lines are bound by all three (per test-plan §6 Exit-cause matrix; per test-plan §6 Path 5).
