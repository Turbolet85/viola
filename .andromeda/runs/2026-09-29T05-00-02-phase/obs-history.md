## Relevant amendment history
- **2026-09-25-pty-wrapper-on-windows** — The proposal to make `viola-pty` tracing-free in §3 was rejected. obs §3/§4 require seam spans (`pty.spawn` and the other viola-pty seam operations), and "Wrapper channel" was given a CARRY for `pty.spawn` and for where the seam spans live. The same entry records in §7 that `PtyError` has a hand-written fixed `Display` (no thiserror in `viola-pty`). It also records that `run`'s pre-spawn refusal stderr is the `run` path's print exception. Why it matters: this chunk must check which seam spans actually shipped, including whether `resize` has one. A resize or write `Err` on the fix path must keep `PtyError`'s fixed-`Display` shape (no path, no payload).
- **2026-09-24-three-os-ci-headless-harness-skeleton** — Sets the precedent for exempting a test-only print-emitting binary from the §11 print-macro ban. `viola-e2e` alone has its own `[lints.clippy]`. The root-package bin `viola-fake-agent` inherits root `[lints]` and is exempted only by a crate-level `#![allow(clippy::print_stdout, clippy::print_stderr)]` listed in the §11 carve-out. Why it matters: if the recorder's `pty_child_entry` (which prints `byte NN` / `size=WxH`) ships in the product crate rather than under test cfg, any new report line needs a carve-out of this listed kind. It cannot be a silent allow.
- **2026-09-28-cli-output-tokens** — Amended the §11 print-macro rule: an output module may carry a local `#[allow]` only where it actually uses a print macro. `run`'s refusals go through `src/human.rs`, which uses none and has no allow. Why it matters: this is the current §11 rule that a child-report print path added or changed in `viola-pty` is judged against.
- **2026-09-24-observability-gates** — The raw-tracing ban is now enforced by clippy `disallowed-macros` (path-banned `tracing::{info,warn,error,debug,trace}`) plus a fail-closed raw-`event!` grep in `scripts/lint-probes.sh`, which is a build failure (D-33). Inner `#[allow]` placements were measured as ineffective. Why it matters: any resize or write observation added to the seam or the pump must go through `obs_event!`. A raw `tracing::warn!` on a resize failure fails lint, and no local allow can rescue it.
- **2026-09-24-diagnostics-plane** — `obs_event!` attaches `event` + `process` + `instance`, and `corr` is caller-supplied. `diag-line` default-deny is a top-level `unevaluatedProperties: false`. Why it matters: a new resize-outcome `event` value or field only validates if `schemas/diag-line.v1.json` is extended (G4). This goes with the extract's rule that a new event or detail needs a Decisions Log entry. `instance` / `corr` are passed as values, never recovered from span context.
- **2026-09-27-wrapper-channel** — `diag-line.v1.json` now carries conditional `corr`-required rules per event (for example `send-*` on the wrapper side, `channel-request`/`-response`). Why it matters: any new event added for a resize or write-ordering outcome on the pump or send path must state its `corr` rule in the schema, not default to "optional".
- **2026-09-27-instance-state-and-start-order** — A §4 status line ("spans not yet declared") was rejected as a sequencing deferral, and the spans were pinned as a CARRY on "Wrapper channel". Why it matters: this is a precedent against writing "seam span not yet built" into obs-plan at wrap. If `pty.resize` is found missing, this chunk adds it or routes it as a CARRY; it does not amend the spec to match the gap.
- **2026-09-24-log-redaction-and-never-log-floor** — anyhow is used only at the root-bin dispatch edge and its catch-site reporter (`viola::obs::report_internal_error`). §7 layer 3 keeps `chain:[...]` only in `detail-<process>.ndjson`, and only when an instance resolves. Why it matters: a resize or write `Err` surfaced by the `run` pump follows this reporter path (one WARN/ERROR line with a closed `detail`, chain in `detail-run.ndjson`). It does not add a new chain-rendering site.
- **2026-09-28-capability-ledger-and-viola-verify (panic backtrace)** — The §7 panic detail line's `backtrace` is now raw, never-symbolised frames (`src/panic_frames.rs`). This was measured at CI run 36436266196, the same windows-2025 run whose job 108974874287 holds the H2 red. Why it matters: a panic added by a fix in the pump or seam threads yields exactly one `event:"panic"` line with raw frames. The shared run ID is only coincidence: the backtrace measurement did not cause H2 and does not explain it.
- **2026-09-28-hook-perf-gate (perf uploads)** — Precedent for a dedicated per-OS CI job. The `perf` job moved out of `test` into its own job with its own G2, G4 and secret scan, and its artifacts upload only on `steps.secret-scan.outcome == 'success'` (a failed scan uploads `secret-scan-perf-<os>`). The operator accepted this with no new crossing: same channel, same scan gate, synthetic inputs. Why it matters: this is the model for P4 if the probe gets its own Windows job. It also shows what the extract's contract binding flags: G2 needs a viola home, so a probe job that creates none cannot run G2 unchanged.
- **2026-09-28-hook-perf-gate (G2 exemption)** — G2 runs as `scripts/g2-zero-panics.sh` (`--probe` first, in the `test` and `perf` jobs). Its only exemption is the exact-path `src/cmd/hook/seam.rs:<digits>` panic location, which the founder ratified, and a new exemption needs a Decisions Log entry. Why it matters: a probe job or fix must not widen G2. A deliberately forced child exit or panic in the recorder is not exempt.
- **2026-09-27-browser-verdict-reachability** — `junit-<os>` carries both nextest's and Playwright's JUnit. Step 3's secret scan covers `target/agent-run/*`, because a JUnit file can hold a failing test's output, and the G2 → G4 → capture → scan → uploads → gate order is unchanged. Why it matters: the recorder's child report is captured into nextest JUnit on a red, so a probe loop's JUnit rides this scan-gated order.
- **2026-09-28-mutation-testing-to-the-epoch-boundary** — The CI Mutation row and the `mutants-verdict-<os>.json` unscanned upload are gone, and step 3's `chunk.diff` is now only `run --mutants`' diff. §10 build failures no longer include a per-chunk mutation gate. Why it matters: this is the current CI job and step-order baseline a P4 probe job or loop is added to. The probe's fix gets no per-chunk mutation gate.
- **2026-09-26-ci-chunk-base-and-union-verdict** — The secret scan covers `target/agent-run/*` except exactly `target/agent-run/chunk.diff`, and the `harness-<os>` upload excludes the same file. It set the rule that the scan may narrow only for a file the upload also drops. Why it matters: a probe's report or loop output under `target/agent-run/` is scanned by default. Excluding it from the scan without also dropping it from the upload would widen the boundary.
- **2026-09-24-workspace-tree-and-code-graph-planes** — Classifies an unscanned CI upload as the never-routine "Boundary widening" class: escalated, and admitted only by content with a binding guard. The guard: a member that could carry a host path or log content is scanned before upload, or dropped. Why it matters: a probe artifact (a report or a reproduction-count file) uploaded outside the scan would need the same escalation. The default is the scan-gated upload.
- **2026-09-24-quality-gates** — Created §8 item 6's "unscanned uploads, admissible by content" inventory and added the nightly fuzz time-box to `nightly.yml`. Why it matters: this is the inventory any new unscanned probe upload would have to join. Together with the next entry, it sets `nightly.yml`'s declared scope if P4 considers a scheduled Windows probe venue.
- **2026-09-24-supply-chain-and-workflow-gates** — `ci.yml` stays the single push/PR workflow, and `nightly.yml` sits beside it for scheduled work only. Why it matters: a probe loop in the standing push/PR CI goes into `ci.yml`. A scheduled loop would widen `nightly.yml`'s stated scope in §9 Platform and needs an obs amendment.
- **2026-09-27-epoch-2-cleanup** — `target/run-archive/<n>/` (each harness run's JUnit and `outcomes.json`, including absolute argv paths) is never uploaded: it is gitignored and outside every upload path. Why it matters: a repeated-run reproduction loop through the harness archives each run there. Reading the fixed reproduction count from machine output must not pull those path-bearing archives into an upload.
