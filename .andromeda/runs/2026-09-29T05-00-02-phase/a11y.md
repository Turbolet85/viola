# a11y extract

## Relevance
partial — no web-spa or CLI output surface is touched. The chunk touches only the `viola run` TUI passthrough seam (ConPTY resize + key delivery), which a11y-plan §1 classes as a **boundary-only** entity with no WCAG conformance claim.

## Constraints
- a11y-plan §1 (CLI and terminal entities → `viola run` TUI passthrough) sets three boundary clauses for the wrapper: zero viola-originated terminal bytes; human keystrokes never blocked, refused or delayed past the current atomic paste; focus, mouse and resize sequences pass through and do not count as human editing. Any fix in `PortablePty::resize`, the writer or the `run` pump's resize-then-write ordering must keep all three. That includes any serialisation, wait or retry added to protect a resize (this matches the scope's "human always wins" invariant).
- a11y-plan §1 (Surface: tui) requires that diagnostics for `run` go to `diagnostics/`, never to the terminal. Any new resize/key observation the probe adds on the wrapper side must not print to the outer terminal stream. The child-side recorder in viola-pty's own test child is test content, not wrapper output. Whether the recorder's lines can ever reach a real `viola run` outer stream is research's question.
- a11y-plan §4 P4 (Human takes the wheel) requires SC 2.1.1 as a tui boundary stand-in: the human keyboard path through the wrapper is never blocked. It also requires that resize sequences are ignored for wheel purposes. A fix that makes a resize look like "human editing" and move the wheel would break P4.
- a11y-plan §3 (Keyboard test harness → Tooling) fixes the tui harness as the portable-pty `=0.8.1` outer-PTY driver, with three separate nextest cases on all three OS legs, one per boundary clause. The recorder change is cross-platform per the scope, so these cases must stay green on windows-2025, macos-latest and ubuntu-latest.
- a11y-plan §12 D-A11Y-13 records that a11y inherits the portable-pty `=0.8.1` pin and does not re-pin it. If a fix is proven to need a portable-pty bump (a P4 fork per the scope), the a11y tui boundary driver moves with it and D-A11Y-13's inherited-risk note needs a revisit.

## Patterns to follow
- The Windows ConPTY carve-out in a11y-plan §3 (Keyboard test harness → Tooling): on Windows the zero-viola-bytes check asserts only that viola's own literals are absent. This is because ConPTY itself emits spawn-time sequences and re-renders output. A resize also makes ConPTY re-render, so any byte-level observation the probe adds on Windows should follow the same rule: attribute bytes to viola only when they are viola's own literals, never to ConPTY's re-render.
- a11y-plan §1 (Surface: tui) and the R7 note: the tests never parse the rendered child screen for content. The recorder's localisation (a size-change line, key arrival) should come from the test child's own report lines, not from parsing a rendered screen.

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste, and never count focus / mouse / resize sequences as editing (per a11y-plan §11 Keyboard). This directly rules out a "hold keys until the resize settles" fix in the wrapper.
- NEVER claim WCAG conformance for the `viola run` TUI (per a11y-plan §11 Strategy). A "documented platform limit" record for H2 must not be phrased as an a11y conformance statement. It is a boundary measurement.

## Contract bindings
- a11y ↔ tests: the tui boundary cases (a11y-plan §3 Keyboard test harness, §4 P4) run on the tests' portable-pty outer-PTY driver in the per-OS `test` job, with results through the harness `run` JSON (a11y-plan §9 CI Integration, unit/integration row). Any Windows probe job or loop that P4 adds must not replace or skip these cases on the windows-2025 leg.
- a11y ↔ arch: the scope's "human always wins" invariant is the same clause as a11y-plan §1's keystroke boundary. A "document" outcome that lands as an architecture amendment should keep the two consistent.

## Acceptance criteria contributions
- The three tui boundary nextest cases (zero viola-originated bytes; human keystrokes delivered unblocked past the atomic paste; focus/mouse/resize sequences do not move the wheel) stay green on all three OS legs after the recorder change and any fix (per a11y-plan §4 P4).
- Any fix to the resize/write path adds no wait, queue or reorder that delays a human keystroke behind a resize. Its witness observes both the resize and the key, with the key delivered (per a11y-plan §11 Keyboard).
- No new wrapper-side resize/key observation writes to the outer terminal stream. It goes to `diagnostics/` or the test report only (per a11y-plan §1 Surface: tui).
