## Relevance
partial — the chunk builds no rendering surface (no web-spa token, type, spacing, depth, radius, motion or icon rule applies); the design plan binds it only through the cli surface's fixed human output, on three conditional paths: a landed ledger row (W1/W2/W3) moves `viola verify`'s step-counter lines and summary, a `--record` of a paste-shape fixture (W3) meets `verify`'s fixture refusal line, and W4's live reading tests the advice the `input-not-ready` hint prints.

## Constraints
- design-system §Surface: cli → Component Patterns (5. `viola verify` / `viola ui` / `viola run`) requires one static appended stdout line per ledger row in the `[nn/NN]` step-counter form, each row carrying its id and a fixed one-phrase description, then one summary line as the last stdout line; a row this chunk lands needs its own id + description phrase in that form and moves both the `NN` denominator and the summary's pass count. The plan's text names seventeen rows and says the count grows as owning chunks land their rows, so a landed row is also a spec-text move here (the wrap's to amend). Whether the code derives the denominator from the row list or holds it as a literal is research's question.
- design-system §Surface: cli → Component Patterns (2. `viola send`: the readback mirror) fixes the `not-delivered · input-not-ready` hint text, which advises a `viola wait` and then a second send. W4 measures that advice on the live CLI; the hint string stays as the plan fixes it in this chunk, and a remedy that changes what the hint says is a design-system amendment that follows the founder's card, never a builder's rewording. Whether `send_hint` in the code reads exactly as the plan fixes it is research's question.
- design-system §Surface: cli → Component Patterns (2. `viola send`: the readback mirror) requires that a hint never quotes the sent text or any upstream text and is printed in human mode only; this binds any hint-side remedy option on the W4 card, and any option that would print a paste-hint reading to the driver.
- design-system §Surface: cli → Exit-code phraseology requires exit 13 to print `unable  not-delivered` with a detail from its closed list, and gives a `verify` run with a failing ledger row no stderr word (the summary line is the whole answer); the W4 `send` inside the hint window is read against that phraseology, and a remedy option that needs a new detail word is a plan amendment (with architecture's), not a free string.
- design-system §Surface: cli → Exit-code phraseology requires the `viola verify` fixture refusal to name the fixture file and one closed code and never the content; a W3 shape recorded under `fixtures/claude/2.1.287/` goes through that refusal unchanged, and no new refusal wording is introduced for a paste-shape capture.
- design-system §Brand Identity (domain anchor "Verified aircraft type") requires a stamped CLI version to print `verified` and an unstamped build `unverified-cli`; the chunk's boundary that PATH `claude` 2.1.289 gets no stamp means that build keeps printing `unverified-cli`, and no intermediate word (for a measured-but-unstamped version) exists in the vocabulary.
- design-system §Brand Identity (domain anchor "Standard phraseology and "unable" plus a reason") requires short fixed words as the vocabulary of every CLI column and refusal, with no filler and no guessing; a new row id, row description or any word a W5 leftover-removal path would print follows it.

## Patterns to follow
- The `verify` step counter is the project's one progress pattern (design-system §Surface: cli → Component Patterns, 5): static appended lines, lower-case hyphenated row id, one-phrase description, `pass` / `fail` word, uncoloured. A new row's line copies that shape; the existing seven dialog and framing rows in that section are the model for the description's register.
- Streams (design-system §Surface: cli → Tokens (platform-specific), Streams): results and data on stdout; context lines, refusals, their `hint:` lines and errors on stderr; under `--json` one JSON document and no hint. Any new line this chunk makes `verify` or `send` print is placed by that rule.
- Colour decision order (design-system §Surface: cli → Tokens (platform-specific), Colour decision order): only the `DIALOG` word and a `stale` row are ever styled; a new `verify` row line and any leftover-census or removal line is plain at every depth.
- Refusal + hint pairing (design-system §Surface: cli → Component Patterns, 2): one `unable` line, then exactly one `hint:` line keyed by reason or reason · detail; a fault (not a refusal) and an opaque `unknown` get no hint. A W4 remedy that adds an outcome picks one of those existing shapes.
- Readback semantics (design-system §Brand Identity, domain anchor "Readback"; §Anti-Patterns → Rejected Defaults, the optimistic-send entry): a send counts only once read back or once its measured post-condition holds. The W3 newline-terminated-paste reading and the W4 options are judged against it: an option that reports a send as delivered without that confirmation contradicts the signature.

## Anti-patterns to avoid
- No spinner, progress bar or in-place redraw for a longer wait: design-system §Anti-Patterns → Per-Surface Bans (cli) bans them, which prices the W4 card's "longer bound" and "wait on a quiet screen" options — a longer `send` wait stays silent or prints static lines only.
- No upstream text, path or pid in an error or hint: design-system §Anti-Patterns → Per-Surface Bans (cli) bans it, so a paste-shape mismatch, a hint-window reading or a leftover probe-dir name never reaches a product line as content (a W5 removal line names no path).
- No bare "done" / "success" and no colour or glyph as the carrier of a verdict: design-system §Anti-Patterns → Per-Surface Bans (cli) requires the word plus its context; a new row's verdict is the word `pass` / `fail` on its counter line, nothing else.
