# a11y extract

## Relevance
partial — no web-spa surface is touched; the chunk reaches a11y only through the cli output-discipline surface (W4's `send` refusal and its `hint:`, the live `viola wait`, `viola verify` step lines if a row lands) and the tui boundary (W3/W4: pastes and a `send` inside the hint window of a wrapped live CLI).

## Constraints
- The chunk's two surfaces carry no WCAG conformance claim: cli is output-discipline only and the `viola run` passthrough is boundary-only, so nothing this chunk measures or records is conformance evidence (per a11y-plan §1 A11y Scope Summary → CLI and terminal entities).
- a11y-plan §1 A11y Scope Summary → `viola run` TUI passthrough requires the wrapper boundary to hold in every state W4 exercises: zero viola-originated bytes on the terminal, and no human keystroke blocked, refused or delayed past the current atomic paste. Whether the live `send` inside the hint window, as the code stands, holds that on the real CLI is research's and the live round's question; the plan only states the requirement.
- Each of the four options on the founder's hint card (wait on a quiet screen, a longer bound, type under the hint, stay as it is) is bounded by that same clause as restated for the wheel path: a remedy may refuse or delay automation, never the human (per a11y-plan §4 ARIA Patterns & Roles → P4).
- a11y-plan §8 Cognitive Accessibility → Error recovery requires a human-mode CLI refusal to read `unable <reason> <detail>` on stderr with `hint:` as the last stderr line, a typed exit code, and no hint under `--json`. W4's `not-delivered` / `input-not-ready` refusal and `send_hint` fall under it; the plan requires a recovery suggestion to be present, and W4's hypothesis (a `viola wait` with nothing to wake on) is a finding about whether the present hint is a working recovery — its disposition belongs on the founder's card, not before it.
- a11y-plan §8 Cognitive Accessibility → Plain language requires every fixed CLI string to be pinned, so a changed `hint:` or refusal text fails until the pin is moved on purpose, and requires any kebab-case reason or detail code to sit beside the plain word `unable`. This binds a remedy that introduces a new detail code or rewrites `send_hint`; whether this chunk builds one is P4's sizing.
- a11y-plan §4 ARIA Patterns & Roles → P6 requires linear static CLI output: `waiting: <name>` exactly once on stderr under a TTY and absent under non-TTY, no redraw or cursor sequence, and `viola verify` step lines in the `[NN/NN] … pass|fail` form. The live `viola wait` in W4 and any `verify` step line a landed row (W1/W2) adds fall under it.
- a11y-plan §6 Visual Design Verification → State color tokens (not-color-alone) → CLI equivalent requires `unable` / `fail` to carry no SGR and viola to emit zero SGR of its own under non-TTY, `NO_COLOR`, `TERM=dumb`, `--json` and `viola run`; a new verify step line or refusal variant inherits this.

## Patterns to follow
- The tui boundary is asserted by three portable-pty outer-PTY nextest cases against the fake agent, one per boundary clause, on all three OS legs; a product change on the send or paste path is covered by extending those cases, not by a new harness (per a11y-plan §3 A11y Assertion Harness Contract → Keyboard test harness → Tooling). Whether those cases exist in the tree as specified is research's question.
- Refusal layout is pinned by trycmd and the typed exit codes by assert_cmd, on all three OS legs (per a11y-plan §8 Cognitive Accessibility → Error recovery → Verification).
- cli and tui failures produce no a11y violation rows; they surface only as nextest failures in the harness `run` JSON `suites[].failures[]` (per a11y-plan §3 A11y Assertion Harness Contract → Structured violation JSON schema → cli / tui).
- The cli output-discipline cases run inside `nextest-integration` / `nextest-e2e` locally and inside the per-OS `coverage` suite in CI; no new `suite` value is added for them (per a11y-plan §9 CI Integration → Per-pipeline-stage a11y artifacts).

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste, in the hint window or under any card option (per a11y-plan §11 A11y Anti-Patterns → Keyboard).
- NEVER parse the rendered `claude` TUI screen for content, or take a screenshot of it, as a11y evidence; the chunk's hint timing and paste readings are product measurements and are not offered as a11y evidence. Whether the timing method reads screen signatures only is research's question (per a11y-plan §11 A11y Anti-Patterns → Universal).
- NEVER leave a human-mode CLI refusal without its `hint:` line (the one exception the plan names is `unknown`), and NEVER colour `unable` / `fail` (per a11y-plan §11 A11y Anti-Patterns → Cognitive; a11y-plan §11 A11y Anti-Patterns → Visual).

## Contract bindings
- a11y ↔ tests: the cli output-discipline and tui boundary assertions live in the tests' nextest suites and are judged by the tests' gate (`gate --require coverage,doctest,playwright`); a11y contributes the form, tests own the cases (a11y-plan §9 CI Integration ↔ test-plan §3). If a ledger row lands and `verify`'s step count moves, the pinned `[NN/NN]` lines are a tests-owned pin that a11y's P6 form constrains.
- a11y ↔ design (cli surface): the `unable … hint:` copy, the `waiting:` line and the SGR rules are design's cli contract; a11y pins them, so a hint-text change decided on the founder's card moves a design string and its trycmd pin together (a11y-plan §8 Cognitive Accessibility → Error recovery ↔ design-system cli).
- a11y ↔ security: the human-keystroke boundary is the same invariant as security's "a refusal never blocks the human", and the R7 no-screen-content ban is shared with the tests plan (a11y-plan §1 A11y Scope Summary → Critical paths → 4 ↔ security-plan / test-plan).
- a11y ↔ obs: none in this chunk (cli / tui emit no a11y rows).

## Acceptance criteria contributions
- (a11y) After any product change on the send or paste path, the three outer-PTY boundary nextest cases (zero viola bytes, keystrokes unblocked past the atomic paste, non-editing sequences leave the wheel) pass on all three OS legs; with no such change they are untouched and still pass (per a11y-plan §4 ARIA Patterns & Roles → P4).
- (a11y) If the `send` refusal in the hint window or `send_hint` changes, its trycmd case pins `unable <reason> <detail>` followed by a final `hint:` line on stderr, the typed exit code is asserted, and `--json` carries no hint text (per a11y-plan §8 Cognitive Accessibility → Error recovery).
- (a11y) If a ledger row lands, its `viola verify` human output is one static `[NN/NN] … pass|fail` line with no SGR on `fail` and none under non-TTY (per a11y-plan §4 ARIA Patterns & Roles → P6).
- (a11y) The founder's hint card states, per option, whether a human keystroke arriving in the hint window is delayed or refused by it; an option that would do either is marked as breaking the tui boundary (per a11y-plan §1 A11y Scope Summary → `viola run` TUI passthrough).
