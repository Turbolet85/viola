# security extract

## Relevance
relevant — the chunk drives real `claude` children, touches the R8 strip and the capture arm's ruled shape (both probe-path widenings), records fixtures and evidence from live sessions, meets the probe-dir removal rule, and may move the stamp's row count.

## Constraints
- **The verify child's isolation is a ruled shape, and widening 1 sits outside it.** security-plan §Threat Model Summary (Attack surface, Child process spawning and PATH resolution) requires each of `viola verify`'s interactive children to be a direct spawn under the R8 strip, and security-plan §Secret Management (Storage) requires the identity floor, both messaging variables among them, to be removed whatever the persistent set says. A path that lets a second session address a `verify` child has no standing in either section; security-plan §Security Anti-Patterns → Universal requires a Security Decisions Log entry for any new listener or channel method. Nothing on that path is built before the founder's answer.
- **Names only, never a value.** security-plan §Secret Management (Storage) requires the strip, the registry reader and the logs to handle `CLAUDE*` names only and never read a value; security-plan §Bootstrap phases (`logging-redaction-wire`) requires that no R8-stripped `CLAUDE*` value reaches a log, diagnostic, snapshot, `events.ndjson` or fixture. W2's reading is a list of names against `IDENTITY_FLOOR`. The floor's text names fixtures and logs; the chunk's `evidence/` files are held to it by the scope's own boundary, not by a plan sentence.
- **The capture arm's ruled shape reads no environment, and widening 2 sits outside it.** security-plan §Input Validation (Hook stdin row, Capture arm) requires the hidden `hook <event> --capture <DIR>` arm to read no `VIOLA_*`, do no obs init, open no channel, read stdin through `take(MAX_FRAME + 1)`, write it raw to an exclusively claimed 0600 file, and print nothing, with empty stderr and exit 0 on every failure. Recording environment names through that arm, or through another probe, is a change to a founder-ratified boundary; the plan gives it no path.
- **What verify types is a closed, founder-named set.** security-plan §Threat Model Summary (Attack surface, Child process spawning and PATH resolution) requires Run B's pastes to be compiled literals, each added only into rows holding the input-box literal and no modal literal, no byte written into any dialog, and a start showing a modal killed with no key; it records the three added pastes as a founder's live answer given after that widening was shown. If a W3 paste shape becomes a probed row, its paste is a further compiled literal of that same kind, so it needs the same showing. Whether the chunk's scratch shape probes (outside `viola verify`) fall under these rulings is not stated by the plan: P4's question.
- **Recorded fixtures are synthetic and scrubbed, or refused whole.** security-plan §Data Protection (At rest, Repository fixtures) requires probe prompts to be synthetic, every string and key scrubbed before any write, and the whole recording refused (exit 1, nothing written) when a home path, absolute path, username or email-shaped token survives, the refusal naming the fixture file and a closed code only. A cross-session `prompt` carries the sending session's text, so that text is a compiled or synthetic one. A fixture variant under `fixtures/claude/2.1.287/` goes through `--record`, never a hand copy of a capture.
- **Probe dirs are owner-only and removed on every exit path; the transcripts are a counted residual.** security-plan §Data Protection (At rest, Interactive probe dirs) requires Run A's OS-temp dir and `<cwd>/.viola-verify-<pid>/`, `-dialogs/`, `-plan/` to be 0700 and removed on every exit path by a drop guard each, and names the `.gitignore` line for a leftover; security-plan §Data Protection (At rest, Probe captures) requires the content-bearing 0600 captures under `ledger/probes/<pid>/` to be removed the same way. Whether a kill is reached by any of those guards is research's question. security-plan §Data Protection (Accepted risk, verify's trusted runs B, C and D) accepts the CLI's own transcripts per real-CLI verify by count; it names verify's runs only, so transcripts from a session started outside `viola verify` are covered by the scope's boundary line, not by that paragraph.
- **A stamp is the dialog switch, and its row count is in the plan's text.** security-plan §Security Anti-Patterns → Universal requires that only `viola verify` writes `ledger/stamps.json`, that a stamp holds the seventeen `LedgerRow::ALL` rows, and that a stamp holding only an older id set records `cli_verified:false` (the hook prints nothing, `answer` exits 12 `unverified-cli`). If a row lands, every stamped home reads unverified until a full re-verify, and PATH `claude` 2.1.289, unstamped by R-L3, gets no non-`null` decision.

## Patterns to follow
- **The names-only record that already exists in the spec.** security-plan §Secret Management (Storage) requires `process-start{subject:"claude-child"}` to name the stripped (`env_stripped_known`) and kept (`env_kept`) names. Whether a `viola run` started from inside a 2.1.287 session already yields W2's name list through that event, with no new probe, is research's question; it is the one path the plan already rules.
- **Bounded, closed reads on every probe input.** security-plan §Input Validation (Hook stdin row, Capture arm) gives the shape for anything a probe reads back: `take(MAX_FRAME + 1)` on stdin, `take(64)` into a closed id for an answer file, an exclusive `create_private_new` claim, one stdout write. security-plan §Input Validation (Child process output row) requires verify's PTY output capped at `MAX_FRAME` into a `Screen` fed under `catch_unwind` and read only against compiled signature literals.
- **`send` text is refused, never stripped.** security-plan §Input Validation (Paste text row) requires LF, CR and TAB to be allowed and the text to reach the PTY as sent, because stripping breaks the delivery-confirmation exact match; W3 shape 3 (a text ending in a newline) and any fix to the unwrap stay on the matching side and never alter what `send` types. security-plan §Input Validation (CLI arguments / stdin row) requires `send` text from stdin or `--file` only, through `take(MAX_FRAME + 1)` then `validate_paste_text`.
- **A removal takes only what its maker created, by an exact identity.** security-plan §Security Anti-Patterns → Code Patterns gives the two standing shapes (the mutation scratch guard keyed on an exact final component, the test-home removal keyed on an owner record), each refusing with a fixed message that names no path. A way for `viola verify` to remove what a killed run left (W5) follows that shape; the plan has no rule of its own for it yet.
- **The dev-host prerequisite for a real-CLI probe.** security-plan §Data Protection (Dev-host prerequisite, the real-CLI probe) requires the run to start from a folder trusted in Claude Code with its external-import answer already given, because verify never answers that dialog; the flags are read before the first live round, not set by the chunk.

## Anti-patterns to avoid
- NEVER build a harness prefix, screen signature or local-command list from runtime or upstream text: security-plan §Security Anti-Patterns → Code Patterns requires the four harness prefixes to be compiled literals matched on the prompt's raw start with no trim. A W1 reading that differs from a compiled literal changes the compiled row; it is never matched from the measured prompt at run time.
- NEVER write an R8-stripped `CLAUDE*` value into a log, stderr, `events.ndjson`, snapshot, `diagnostics/` or fixture (security-plan §Security Anti-Patterns → Secrets), and NEVER commit `fixtures/claude/*` recorded from a non-synthetic prompt or before the home-path and username check (security-plan §Security Anti-Patterns → Data Protection).
- NEVER reach a probe path through an environment variable, a `config.json` key or a CLI flag used as a switch: security-plan §Security Anti-Patterns → Universal holds that environment variables are not a configuration channel and that another seam needs its own Decisions Log entry.

## Contract bindings
- **security ↔ obs:** the `process-start{subject:"claude-child"}` name fields (security-plan §Secret Management, Storage) are obs-plan event-catalog fields; the artifact canary scan's stripped-`CLAUDE*` class (security-plan §Secret Management, Secret scanning in CI) is obs-plan §9's and reads any harness capture this chunk produces.
- **security ↔ tests:** the real `claude` runs only locally and CI replays fixtures through the fake agent (security-plan §Threat Model Summary, Infrastructure, CI/CD), so a new fixture variant is test-plan's replay input; the `--local-live` row list (W6) and `LEDGER_ROWS` bind to the "seventeen" count in security-plan §Security Anti-Patterns → Universal.
- **security ↔ architecture:** a landed row is an architecture [CLI Version Compatibility] ledger row; the founder's answer on either widening is a dated Security Decisions Log entry and a wrap amendment to security-plan §Threat Model Summary (Child process spawning), §Input Validation (Hook stdin row) and §Security Anti-Patterns → Universal (the row count), mirrored in `.claude/rules/security.md`.
