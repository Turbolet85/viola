# obs extract

## Relevance
partial — W1 turns on the process-log side of `send`'s terminal outcomes (obs-plan §4 Scenario 2, §6, §5, §8, §9 G4); W2 and W3 touch obs only through the closed readiness-gate outcome and the screen-content ban; W4 (two comments) has no obs content.

## Constraints
- The `unconfirmable` outcome has no event of its own: obs-plan §4 Scenario "Confirmed `send` (CL-1) from driver to readback" (Required log fields) requires the wrapper's `send-confirmed` line with `confirmed:false`, after the same call's `send-issued`, and §3 Log format JSON schema fixes `corr` on every `send-*` line as the send `cursor` (required by `schemas/diag-line.v1.json` when `side` is `wrapper`). The wrapper `send-*` lines also carry `conn` and `rpc_id` (same Scenario, D-30). Whether the wrapper already emits a `confirmed:false` line, and whether the schema already admits it, is research's question (the scope's `[inferred]` M5 reading is not attested here).
- Default-deny on fields: obs-plan §8 PII Scrubbing (Default-deny posture) with §6 Additive field catalog admit on `send-issued` / `send-confirmed` / `send-refused` only the catalogued fields. A field naming which local command was sent, which post-condition confirmed it, or `cli_verified` on a send line (the catalog lists `cli_verified` on `process-start` only) is outside the catalog: it needs a catalog entry, a schema change and a Decisions Log entry, or it is not written.
- `detail` is a closed catalog: obs-plan §6 `detail` code catalog takes the refusal details from architecture's `RefusalReason` verbatim and does not list `unconfirmable`. On the process log the outcome is expressed by `confirmed:false`, not by a `detail:"unconfirmable"` value on a home-level line; whether the schema's `detail` enum admits that word on any line is research's question. What a ledger-listed command returns when its post-condition does not arrive in the window (the scope leaves it to P2 / P3) must land on an existing closed `refusal` / `detail` pair or go through an amendment.
- Send text is High class: obs-plan §8 PII Scrubbing (Data classification rules, prompt-text row) and §4 Scenario 2 ("Never text") require that only `text_bytes` reaches a home-level line or a span field. `/clear` and `/remote-control` are send text like any other, compiled literals or not: no line, span attribute or `detail` code names the command.
- Levels: obs-plan §6 Log levels mapping puts refusals and every other normal product outcome at `info`. A `send-confirmed{confirmed:false}` line and the client's `process-exit` for it are not `warn` / `error` events.
- Spans: obs-plan §4 Scenario 2 requires the chain `send.client` › `channel.request` → `channel.dispatch` › `run.readiness_gate` › `pty.paste_write` › `run.confirm_window{window_ms}`, declared per §4 Span naming convention (`skip_all`, static names, explicit field list). Its Cleanup clause names two closes of `run.confirm_window` only (the matching `prompt-submitted{origin:"driver"}`, or window expiry). A close on the `/clear` post-condition, and a send that returns `unconfirmable` without a full window, are not written there: the chunk adds no span name or attribute for them, and the wording gap is an amendment candidate, not a licence.
- Deterministic emission: obs-plan §10 Standard+ invariants (Deterministic emission) and §11 Telemetry Strategy require that events key on hook events and `events.ndjson` offsets, never on screen content. The `/clear` confirmation therefore keys on the SessionStart hook event, and any W2 card option keeps `run.readiness_gate`'s `outcome` at the closed `ready|input-not-ready` (§4 Scenario 2, Required span attributes) with no per-chunk event from the pump or the vt100 feed.

## Patterns to follow
- Emit every new or changed line through `obs_event!` with explicit typed fields, under `#[instrument(skip_all, name = "...", fields(...))]`; `corr` is passed as a typed value, never `?corr` / `%corr` (obs-plan §8 Integration points, item 1; §11 Logs).
- Carry `corr`, `conn`, `rpc_id` and `instance` into the hook-event tap as explicit values; span context does not cross threads (obs-plan §11 Spans / Traces).
- The client side closes `send.client` with `process-exit{subject:"self", exit_code}` in `cli-<name>.ndjson` when an instance resolves; the `exit_code` on the line is the code the process exits with (obs-plan §4 Scenario 2, Cleanup; §4 Instrumentation per surface, cli row). Which code an `unconfirmable` send exits with is layout's and architecture's, not obs's.
- `channel-response` stays the `Drop`-guard line of `channel.dispatch`, with the closed `result_class` (`ok|refusal|error`) and no result body: the `ok` body's `confirmed` / `detail` / `cursor` are never copied onto it (obs-plan §4 Scenario 2, Cleanup; §6 Boundary-call wrappers, IPC invocation).
- Derived metrics need no code: `viola.send.outcome` counts `send-confirmed{confirmed}` beside `send-refused`, and `viola.send.confirm_ms` reads `send-confirmed.duration_ms` (obs-plan §5 Per-surface / per-path metrics). The plan defines the latter as the `open` → `read back` latency; what `duration_ms` measures on a `confirmed:false` line, and whether the schema requires it there, is research's question.

## Anti-patterns to avoid
- NEVER log send text, or any field not named in the §6 catalog, in a home-level file (obs-plan §11 PII Scrubbing).
- NEVER add an `event` value (a `send-unconfirmable`, a post-condition event) or rename a tests field without a Decisions Log entry (obs-plan §11 Logs).
- NEVER reach for `print!` / `println!` / `eprintln!` / `dbg!` outside the output modules that own human CLI output and `--json`: the `[  ] unconfirmable` mirror writer lives in such a module under its local `#[allow]`, the wrapper side writes nothing to the terminal, and no telemetry goes to stdout (obs-plan §11 Logs; §3 Observability Harness Contract).

## Contract bindings
- obs ↔ tests: the send-line `corr` rule and the required fields are test-plan §3 Log format reproduced as binding text (obs-plan §3 Log format JSON schema; obs aligns to tests). test-plan §6 Path 2's `local` case reads these lines through `agent-run logs`.
- obs ↔ tests (CI): every viola home a changed or new `tests/cli_send.rs` / `tests/cli_verify.rs` case creates must sit under `target/e2e-home/`, so G2, G4, the secret scan and the `diag-<os>` upload cover it (obs-plan §9 Pipeline integration, Integration tests row; §9 Step order).
- obs ↔ security: the home-level-content ban and the secret scan over `diagnostics/` (obs-plan §8 Integration points, item 6) bind to security-plan's NEVER-log floor and error-sanitization rules.
- obs ↔ architecture: the refusal `detail` values on `send-refused` are architecture's `RefusalReason` details verbatim (obs-plan §6 `detail` code catalog); a new outcome word is architecture's to mint first.
- obs ↔ design / layout: the readback word `unconfirmable` pairs with `send-confirmed{confirmed:false}`, joined by the send `cursor` in `corr` (obs-plan §4 Frontend observable boundary). The CLI mirror line's text is layout's; the DOM state is owed to Epoch 8 per the scope.

## Acceptance criteria contributions
- A send that returns `unconfirmable` under the fake agent leaves in `run-<name>.ndjson` one `send-issued` and one `send-confirmed` with `confirmed:false`, both with `corr` equal to the returned `cursor` and with `conn` / `rpc_id` matching that call's `channel-*` lines, and no `send-refused` for that `corr` (per obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback).
- Every send the changed tests issue, the post-condition-confirmed `/clear` included, ends in exactly one terminal wrapper line for its `corr` (`send-confirmed` or `send-refused`, never both, never neither), and the client's `process-exit{subject:"self"}` carries the exit code the test observes (per obs-plan §4 Scenario: Confirmed `send` (CL-1), Required log fields and Cleanup; §10 Standard+ invariants, Correlation propagation).
- G4 and G2 pass over the homes of the changed and new tests: every home-level line validates against `schemas/diag-line.v1.json`, with no field outside the §6 catalog and no `event:"panic"` line (per obs-plan §9 Gate commands, G2 and G4; §8 PII Scrubbing, Default-deny posture).
- No home-level `diagnostics/*.ndjson` line holds the sent command's text; the send lines carry `text_bytes` only (per obs-plan §8 PII Scrubbing, Data classification rules; §11 PII Scrubbing).
