## Constraints
- **The outcome is decided by the ledger, three ways, and nothing is presumed.** architecture §Established Decisions → [Delivery Confirmation] and §Design Philosophy ("Measured, never assumed") require: a ledger-listed local command whose measured post-condition is met returns `ok`, confirmed; a listed one whose post-condition is "none" or not yet measured on this CLI version returns the `unconfirmable` `ok` payload; nothing else is ever `unconfirmable`; every other unconfirmed send is `not-delivered`. The decision reads the ledger's list, never a leading slash. [Delivery Confirmation] also carries a dated "does not consume them yet" sentence naming this route entry: whether the code already consumes `ledger::LOCAL_COMMANDS` is research's question, and that sentence is a wrap-time amendment, not a mandate.
- **The wire shape is fixed.** §Standard Contracts → Wrapper channel frames and → Channel methods fix `send`'s two `ok` payloads (confirmed; `confirmed:false` + `detail` + `cursor`) and what `cursor` is. §Conventions → Error handling schema requires that `unconfirmable` is never a refusal detail and appears only inside an `ok` payload; §Standard Contracts → CLI `--json` output requires the `--json` view to mirror the channel `result`; §Conventions → CLI exit codes makes an `ok` exit 0; §Conventions → Error handling schema (MCP) makes it an `isError: false` tool result carrying the `ok` payload as `structuredContent`.
- **The refusal order has no local-command carve-out.** §Conventions → Error handling schema fixes `send`'s order (control-character, human-typing, budget-paused, turn-running, then the readiness gate, then confirmation); a listed local command passes every earlier rung like any text. For a listed command whose measured post-condition does not arrive in the window the plan requires `not-delivered`; the `not-delivered` detail set is closed and extended only in `viola-core`, and the only confirmation-rung detail the plan names is `no-prompt-submitted`. Which detail that case carries is P2/P3's to close against that closed set; a new detail would be a `viola-core` extension plus a plan amendment, not an implementation choice.
- **`/clear`'s post-condition is read as a normalised event.** §Conventions → Naming patterns (Hook → kind map) and §Standard Contracts → Event `data` per kind define `session-start` with its `cause` and `agent_session_id`; §Infrastructure Patterns → Crate dependency direction requires the root bin (the send slot and the hook-event tap included) to consume only normalised events, and §Inherited Defaults (Agent isolation) keeps Claude payload shapes in `viola-agent-claude`. "A new session" is therefore a comparison of normalised ids in the wrapper; what the wrapper holds as the previous id at send time is research's question.
- **"Not yet measured on this CLI version" comes from `run`'s version gate.** §Established Decisions → [CLI Version Compatibility] defines `cli_verified` (every landed row `pass`, the `local-command-clear` row among the seventeen) and where it is recorded; [Screen Model] names `Launched.cli_verified` as the value `run` already hands the gate. §Cross-cutting Patterns → Capability ledger as the single gate forbids an unconditional assumption in its place. Whether the send slot can reach that value today is research's question (the scope's `SendSlot` carry).
- **The plan names no `events.ndjson` record for an `unconfirmable` outcome.** §Standard Contracts → Event `data` per kind requires the wrapper to append `send-issued` and then `send-confirmed` or `send-refused` for each send, as the source the audit trail, the SSE feed and a replay learn each send's outcome from, and gives `send-confirmed` one field. An `unconfirmable` send is neither. §Conventions → Interfaces and versioning makes an added field additive (no `v` bump) and §Conventions → Naming patterns allows a new kind only in `viola-core`. Which record such a send appends is an open contract point for P2/P4, amended in §Standard Contracts at wrap.
- **The time bound and the gate constants are compiled and validated, not tunable.** [Delivery Confirmation] bounds how long `send` blocks (gate maximum + paste + window), requires the result no later than the window's close and the MCP total below the client's tool-call timeout, and keeps the window a compiled constant outside `config.json`. [Screen Model] makes `GATE_MAX_WAIT` and `QUIET_PERIOD` compiled built-ins validated per version by the stamped `quiet-period` row, and requires `input-not-ready` when a verified CLI's screen shows no input-box literal within the maximum; [CLI Version Compatibility] records the measured post-long-paste footer window and states that `run`'s gate is unchanged by verify's own wait. W2's hypothesis is what that text predicts; whether the code behaves so is research's question. Any change to the maximum, or to `send` under the hint, moves that bound and the `quiet-period` row's validated claim, so it is an amendment to [Screen Model] taken at the P4 card, never inside implementation.

## Patterns to follow
- **Claim, append, then settle.** [Delivery Confirmation] and §Standard Contracts → Channel methods (`hook.event`) describe the wrapper's one hook entry claiming the in-flight send's matching line, appending it, and only then settling the send, so the confirming line precedes the send's outcome record. The plan states this order, and `submitted_at`'s source, for the `prompt-submitted` path only; for `/clear`'s `session-start` it states the post-condition and nothing about order or which line's `ts` fills `submitted_at` — P2/P3 close it, keeping the one confirmed payload shape.
- **One in-flight slot, running-turn state keyed on line kind.** §Established Decisions → [Human Takeover / Wheel]: a send is "in flight" until its outcome is recorded, a second send in that span is refused and never queued, and `session-start` ends a running turn while only `prompt-submitted` starts one. Every new outcome path settles the same slot; a local command marks no turn.
- **Placement per §Infrastructure Patterns → Project directory structure.** The wrapper's `send` method, slot and relabel in `src/run/send.rs`; the client in `src/cmd/send.rs` over `cmd/client.rs`; every human-facing line, the readback mirror included, in `src/human.rs`; the fake agent in `src/bin/viola-fake-agent.rs` behind feature `fake-agent`. The key's `human.rs` line lists three mirror lines; a fourth is a wrap-time amendment. The plan requires no new crate, module or dependency for this chunk.
- **Both version cases are reachable under the fake agent.** §Cross-cutting Patterns → Config management (each test's own home, whose stamps can stamp the fake agent's reported version) and §Established Decisions → [CI/CD] (the fake agent named after `--`) give the verified and the unverified `/clear` case without a live CLI.
- **Fake-agent options are argv, test-only and registered.** §Occupied Resources → Binary, subcommands and exit codes lists the fake agent's options (the `--framing` replay of the probed local command, the `--paste-hint-ms` hold and its cap, stated there as serving verify's interactive runs). That line does not name `--local-command-mode`, which the scope reads at HEAD: whether the option exists, and whether the hold is reachable under `viola run` for a `send` test, are research's questions; any option or screen variant W1–W3 land is recorded on that line at wrap.

## Anti-patterns to avoid
- Deciding by a leading slash, presuming a local command delivered, or retrying an unconfirmed send — forbidden by [Delivery Confirmation] and §Cross-cutting Patterns → Fail open toward the human; equally, carrying `unconfirmable` as a refusal `detail` or on a non-zero exit (§Conventions → Error handling schema).
- Reading a raw Claude hook shape (SessionStart's own source or session-id fields) in the root bin, or matching the command text anywhere but against `viola-agent-claude`'s compiled list (§Infrastructure Patterns → Crate dependency direction; §Inherited Defaults, Agent isolation).
- Reaching the outcomes or the W3 variant through a new env seam, `config.json` key, ledger row or hand-authored file under `fixtures/claude/<cli-version>/`: §Cross-cutting Patterns → Config management closes env and config as channels, §Conventions → Naming patterns (Environment variables) admits two seams only, and §Occupied Resources → Repository makes `viola verify --record` the only writer of those sets with a closed screen-phase set.

## Acceptance criteria contributions
- (arch) A `send` of a listed local command with no post-condition returns the channel `ok` payload `{confirmed:false, detail:"unconfirmable", cursor}`, mirrored as `{"v":1,"ok":{…}}` under `--json`, exit 0, and never a `refusal` (per architecture §Standard Contracts → Channel methods / CLI `--json` output; §Conventions → Error handling schema / CLI exit codes)
- (arch) `/clear` returns `ok` confirmed only when a `session-start` with cause `clear` and a new `agent_session_id` lands in the window on a CLI version whose stamp passes; on a version without a passing stamp it returns `unconfirmable` (per architecture §Established Decisions → [Delivery Confirmation] / [CLI Version Compatibility]; §Design Philosophy, "Measured, never assumed")
- (arch) A slash-led text that is not on the compiled local-command list and is not confirmed still ends `not-delivered`, exit 13; `unconfirmable` is produced for nothing else, and the earlier refusal rungs still apply to a listed command (per architecture §Established Decisions → [Delivery Confirmation]; §Conventions → Error handling schema; §Cross-cutting Patterns → Fail open toward the human)
- (arch) Workspace discipline holds: the wrapper reads the post-condition through normalised events and `viola-agent-claude`'s compiled list, the `send` path stays std-thread, and the chunk adds no env var, `config.json` key, ledger row or crate dependency (per architecture §Infrastructure Patterns → Crate dependency direction; §Cross-cutting Patterns → Tokio containment / Capability ledger as the single gate / Config management)
