# security extract

## Relevance
partial — the chunk changes the outcomes of the existing `send` method on the IPC trust boundary and touches verify's Run B paste guard and the fake agent; it adds no listener, no channel method, no dependency, no secret and no GUI surface.

## Constraints
- Which text counts as a local command, and what its post-condition is, may come only from the compiled `viola-agent-claude` ledger rows; security-plan §Security Anti-Patterns → Code Patterns bans building a local-command list from runtime or upstream text. Whether `send` today reads any such list at all is research's question (scope W1 reads that it does not).
- The SessionStart fields the `/clear` confirmation compares (`source`, `session_id`) are upstream content: security-plan §Security Anti-Patterns → Code Patterns (R1) requires them to be compared as data only, never interpreted as a command or config; security-plan §Input Validation (Channel frames row, `hook.event` re-validation) requires the wrapper to re-validate a `hook.event` before it is used. Whether that re-validation already covers the session-start fields the confirmation would read is research's question.
- `validate_paste_text` must stay first in the wrapper's `send` refusal order and authoritative, with the client-side check before any frame, and the text is rejected, never stripped (security-plan §Input Validation, Paste text row). The local-command branch must sit behind it on both sides and must classify the same unmodified text that is typed.
- The `send` params closed-type check (`text` a string, `from` absent / `null` / a valid `ViolaName`, else `-32602` with `data: null`) precedes everything the chunk adds (security-plan §Input Validation, Channel frames row).
- The new outcomes are external responses: security-plan §Error Handling (External responses; Error format → Channel) requires codes and fixed messages only — no sent text, no hook payload text, no absolute path, no internal type name — in the channel result, CLI `--json`, the human mirror line and any stderr line.
- Any log line the chunk emits or changes (`send-confirmed{confirmed:false}` included) stays under the NEVER-log floor: user content only in `instances/<name>/diagnostics/` (0600), never in a role log, stderr or error output (security-plan §Bootstrap phases, `logging-redaction-wire`, scope bullet).
- "Measured on this CLI version" must be decided from the one `cli_verified` value `viola run`'s version gate produces through `read_stamps_strict` (security-plan §Input Validation, Own state files row; §Security Anti-Patterns → Universal, the two stamp bullets): threading it into the send slot may not add a second, non-strict read of `ledger/stamps.json`, and no process but `viola verify` may write that file. A new strict-modes exception would need its own Security Decisions Log entry; the seven dated gaps may not be borrowed or widened (security-plan §Authentication & Authorization, IPC client-side server verification row).

## Patterns to follow
- Two-sided validation with the wrapper authoritative: the client refuses before any frame, the wrapper re-runs the shared `viola-core` validator first (security-plan §Input Validation, Boundary paragraph and Paste text row).
- Compiled-literal classification: the same shape the plan requires for screen signatures and harness prefixes — matched against compiled ledger literals only (security-plan §Security Anti-Patterns → Code Patterns).
- Closed, fixed-string outcomes on the wire: `result.refusal` / detail codes with fixed `Display` messages (security-plan §Error Handling, External responses and Error format).
- Test-only behaviour stays in the test-only binary or behind `cfg(feature = "fake-agent")`, and the release build is judged by `scripts/release-check.sh`, which refuses any test-only binary or feature (security-plan §Dependency Security, CI integration; §Input Validation, the two test-seam rows).
- verify's Run B guard as the plan states it: each added compiled paste goes only into rows holding the input-box literal and no modal literal, and a modal, a poisoned screen or the deadline ends the added pastes with no key (security-plan §Threat Model Summary, Attack surface → Child process spawning and PATH resolution).

## Anti-patterns to avoid
- Deriving, extending or overriding the local-command list or its post-conditions from the sent text, a hook payload, `config.json`, an env var or a CLI flag (security-plan §Security Anti-Patterns → Code Patterns; → Universal, the no-switch-off bullet).
- Neutralising the `framing_turns` guard for W3's control through anything that survives the control — a `viola` flag, a `VIOLA_*` or other env seam, a cfg left in product source — or running the neutralised guard against a real `claude`; a third env seam or a typed byte into a dialog is a boundary widening that needs its own Decisions Log entry (security-plan §Security Anti-Patterns → Universal; §Threat Model Summary, Attack surface → Child process spawning and PATH resolution).
- Echoing the sent text, the SessionStart payload or an anyhow / serde chain into the `unconfirmable` or confirmed outcome, its `--json` form, stderr or a role log line (security-plan §Security Anti-Patterns → Logging; §Bootstrap phases, `logging-redaction-wire`).

## Acceptance criteria contributions
- A `send` whose text holds a refused control character is refused `not-delivered` / `control-character` on the client before any frame and first in the wrapper, on the local-command path as on every other; no such text reaches the PTY or returns `unconfirmable` (per security-plan §Input Validation, Paste text row).
- The local-command decision in the send path names only the compiled `ledger::LOCAL_COMMANDS` / `PostCondition`, and the verified-version input is the version gate's `cli_verified`; grep finds no second read of `ledger/stamps.json` and no config, env or flag source for either (per security-plan §Security Anti-Patterns → Code Patterns; §Input Validation, Own state files row).
- The `unconfirmable` and `/clear`-confirmed outcomes carry only closed codes and fixed strings in the channel result, `--json`, the human mirror and every log line — a test sends a marked text and finds the marker in no stderr, role log or `--json` error output — and CI's `secret-scan` step stays green (per security-plan §Error Handling, External responses; §Bootstrap phases, `logging-redaction-wire`).
- At the chunk's last commit: the `framing_turns` guard is restored (the neutralised form exists only in the evidence record), `viola` reads no new env var and gains no flag or `config.json` key, the new fake-agent variant lives only in the test-only binary or feature, and `scripts/release-check.sh` and `cargo deny check` pass with no dependency added (per security-plan §Security Anti-Patterns → Universal; §Dependency Security, CI integration).
