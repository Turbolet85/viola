# a11y extract

## Relevance
partial — no web-spa markup, token or ARIA surface is touched; the chunk meets the plan at the `viola run` tui boundary (the keystroke clause, scope item 8), at the cli refusal layout (the `input-not-ready` hint line, scope item 7) and at the cli output discipline of a longer-blocking `send` (scope item 9).

## Constraints
- a11y-plan §1 A11y Scope Summary (CLI and terminal entities → `viola run` TUI passthrough) requires that a human keystroke is never blocked, refused or delayed past the current atomic paste. The only delay the clause admits is the atomic paste itself; the gate's wait happens before any paste is written (scope item 4: nothing typed), so the clause admits no delay at all during the up-to-8.5 s wait. Whether the code already forwards a key to the child while the gate waits on a literal-less screen is research's question.
- a11y-plan §5 Keyboard Navigation (Focus order per layout → tui) requires that the terminal belongs to the child and repeats the keystroke clause; a longer automation-side wait may not turn the terminal into a surface viola holds.
- a11y-plan §1 A11y Scope Summary (Critical paths → Path 4) requires that when the human takes the wheel automation is the side that is refused (`send` → `human-typing`), with the refusal on stderr as `unable … hint:` and a typed exit code. What a `send` already waiting in the gate returns when a key arrives mid-wait is research's question; the plan requires only that the human side is never the one that waits.
- a11y-plan §3 Keyboard test harness (Tooling) requires the zero-viola-bytes clause across a driver `send` and a refused automation send: none of viola's own literals (diagnostics, refusal text, `hint:`) on the outer-PTY stream. The wait and the refusal at the bound (scope item 4) fall under it.
- a11y-plan §8 Cognitive Accessibility (Error recovery) requires every human-mode cli refusal to be `unable  <reason>  <detail>` on stderr, then `hint:` as the last stderr line, with a typed exit code, and `--json` to carry no hint. Scope item 7's fork is bound by this: the `input-not-ready` refusal keeps a hint line whatever its wording becomes.
- a11y-plan §8 Cognitive Accessibility (Plain language → Verification) requires every fixed cli string to be pinned by trycmd, so a copy change fails CI until the pin is updated on purpose. A changed `input-not-ready` hint string and its pin move together in this chunk. Where the pin lives is research's question.
- a11y-plan §1 A11y Scope Summary (A11y surfaces → cli → Notes) requires cli output to be static and linear, with no spinner or redraw, and no SGR under `--json`, non-TTY, `NO_COLOR` or `TERM=dumb`. `send`'s longer block (scope item 9, 18.5 s) may add no progress output to satisfy a waiting reader.

## Patterns to follow
- The keystroke case of scope item 8 follows a11y-plan §3 Keyboard test harness (Tooling): the portable-pty outer PTY injects human keystrokes during a driver `send` and asserts they are delivered unblocked, with the wheel probed by an `answer` to no pending dialog (exit 13 = driver, 10 = human). Here the injection lands while the gate waits under the fake agent's held hint.
- a11y-plan §4 ARIA Patterns & Roles (P4 → tui) requires one nextest case per boundary clause on all three OS legs; clause (2) is the keystroke one. Whether the existing clause-(2) case already injects during a gate wait, or a new case is needed beside it, and whether it can run on all three legs, is research's question.
- Refusal text checks follow a11y-plan §8 Cognitive Accessibility (Error recovery → Verification → cli): trycmd pins the `unable <reason> <detail>` + final `hint:` layout per refusal, assert_cmd checks the typed exit codes and that `--json` carries no hint text, on all three OS legs.
- These checks live where a11y-plan §9 CI Integration (Per-pipeline-stage a11y artifacts → Unit / integration row) puts them: `nextest-integration` / `nextest-e2e` locally, the per-OS `coverage` suite in CI, with no a11y violation rows and no conformance claim.
- a11y-plan §8 Cognitive Accessibility (Timeout extensions → CLI) gives the framing for a moved bound: a cli deadline bounds the driver, never the human. The 8.5 s bound is of that kind.

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste (a11y-plan §11 A11y Anti-Patterns → Keyboard). The gate's wait is not an atomic paste and earns no exemption.
- NEVER show a refusal without a recovery suggestion: every human-mode cli refusal except `unknown` ends with a `hint:` line (a11y-plan §11 A11y Anti-Patterns → Cognitive). Scope item 7 may reword the `input-not-ready` hint; it may not drop it.
- NEVER parse the rendered `claude` TUI screen for content or take screenshots as a11y evidence, and never claim WCAG conformance for cli or the `viola run` TUI (a11y-plan §11 A11y Anti-Patterns → Universal and → Strategy). The keystroke case proves delivery through the outer-PTY driver and the wheel probe, not by reading the child's screen.

## Contract bindings
- a11y ↔ tests: the tui boundary and cli output-discipline cases run on the tests' portable-pty outer-PTY driver, assert_cmd and trycmd, inside the `test` job's `gate --require coverage,doctest,playwright` (a11y-plan §9 CI Integration); where they live in crate tests the epoch-boundary mutation audit covers them (a11y-plan §10 SLO Invariants & A11y Budgets → Standard+ invariants). The scope expects test-plan §4 and §6 at the wrap.
- a11y ↔ design / layouts: the `hint:` line's text is design's (cli refusals) and the cli layout's; a11y binds only its presence, position and pin (a11y-plan §8 Cognitive Accessibility → Error recovery). Scope item 7 names both masters' lines.
- a11y ↔ architecture / security: the keystroke clause is the plan's reading of the architecture convention "Human input priority" and of security's rule that a refusal never blocks the human (a11y-plan §1 A11y Scope Summary → Critical paths → Path 4 → Source).
- a11y ↔ obs: none added. The chunk emits no a11y violation row; an `input-not-ready` refusal reaches the web page only through the existing `send-refused` path of a11y-plan §4 ARIA Patterns & Roles (P2), which this chunk does not touch.

## Acceptance criteria contributions
- (a11y) On the portable-pty outer PTY, with the fake agent holding the paste hint and a verified-CLI driver `send` waiting in the gate, an injected human keystroke reaches the child while the gate is still waiting (not at the bound), and the wheel probe then reads human (exit 10) (per a11y-plan §3 Keyboard test harness → Tooling).

- (a11y) While `send` blocks for the gate and the confirmation, its output holds no spinner, `\r` redraw, cursor-movement or erase sequence, and no SGR under non-TTY, `NO_COLOR`, `TERM=dumb` or `--json` (per a11y-plan §1 A11y Scope Summary → A11y surfaces → cli → Notes).
