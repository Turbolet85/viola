# obs extract

## Relevance
partial — the chunk changes when and how the readiness gate ends (scope items 1-4, 9) and runs one live `viola verify` (item 10); obs-plan asks for no new event, field, detail code, span or budget for it, but the gate's existing span, the `send-*` lines, the default-deny schema and the hot-path bans all bind the build.

## Constraints
- obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback requires `run.readiness_gate` on the send path between `channel.dispatch` and `pty.paste_write`, with exactly two span attributes: a closed two-value `outcome` (`ready|input-not-ready`) and `vt100_panicked`. A gate that waits out the hint must still end in one of those two values: the plan holds no third outcome for "waited" and no wait-length attribute. Whether the span in `src/run/gate.rs` already encloses the whole wait, the new waiting arm included, is research's question.
- obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback (Required log fields) requires the bound-expiry refusal of scope item 4 to be the same wrapper-side `send-refused` as today's first-quiet-instant refusal: `detail:"input-not-ready"`, `side:"wrapper"`, no `send-issued` before it, and the `conn` / `rpc_id` pair on the line. A send delivered after the wait is the ordinary `send-issued` then `send-confirmed` sequence, with nothing added between `channel-request` and `send-issued` for the wait.
- obs-plan §3 Log format JSON schema requires a send refused before `send-issued` (it names `input-not-ready`) to carry `corr` = the target's `events.ndjson` end offset at the moment of refusal (D-28). With the refusal now up to 8.5 s after the send's issue, "at the moment of refusal" is the binding reading; whether the code samples the offset at the refusal or at the gate's entry is research's question.
- obs-plan §6 `detail` code catalog requires refusal details to be the arch `RefusalReason` details verbatim, a closed list. The paste-hint cause and the bound running out get no detail of their own: both stay `input-not-ready`.
- obs-plan §8 Default-deny posture requires every logged field to be named in the §6 catalog, enforced by G4 against `schemas/diag-line.v1.json`. A new field for the gate's wait (a waited-ms, a cause, a "hint seen" flag) is outside the catalog and is a build failure; adding one is a catalog and schema amendment with a Decisions Log entry, which this chunk's scope does not plan (the masters are the wrap's).
- obs-plan §5 Per-surface / per-path metrics derives `viola.channel.duration_ms` from `channel-response.duration_ms` and `viola.send.confirm_ms` from `send-confirmed.duration_ms`, raw samples, report-only. A `send` channel sample can now reach the 18.5 s of scope item 9; no obs gate reads it. §5 ties the confirm sample to the readback's open → read back span, so whether the code starts `send-confirmed.duration_ms` before or after the gate's wait is research's question (if before, the metric's meaning moves with this chunk).
- obs-plan §7 Error classes captured requires a poisoned screen to yield exactly one `parse-rejected{parser:"vt100-feed"}` per episode and a refused send (`send-refused{detail:"input-not-ready"}`, exit 13), witnessed at run level by `tests/chaos_feed_panic.rs`. Scope item 1's "a poisoned screen still refuses at once" is what keeps that witness's shape and timing: the new waiting arm must add no line and no wait on the poisoned path.

## Patterns to follow
- A gate function split or added for the waiting arm is declared in the plan's one span form, `skip_all` first, a static `<area>.<operation>` name and an explicit field allow-list (per obs-plan §4 Span naming convention); G1 reads the whole workspace for a bare `#[instrument]`.
- Every line goes through `obs_event!` with explicit typed fields, `corr` as a typed value and never stringified (per obs-plan §8 Integration points, item 1).
- A refusal is a normal product outcome logged at `info`; the refusal at the bound gets no `warn` for having waited (per obs-plan §6 Log levels mapping).
- `corr`, `conn` and `rpc_id` reach the gate's emission site as explicit values, never through span context, since the wait may now straddle the feed thread and the dispatch thread for seconds (per obs-plan §10 Standard+ invariants, Correlation propagation).
- The new and turned end-to-end cases keep their viola homes under `target/e2e-home/` with synthetic inputs, so G2, G4 and the secret scan read their lines (per obs-plan §9 Pipeline integration, Integration tests row).

## Anti-patterns to avoid
- No span, event or `info` line per poll, per quiet check or per fed chunk while the gate waits up to 8.5 s: the gate logs its outcome once (per obs-plan §11 Obs Anti-Patterns § Telemetry Strategy).
- No telemetry derived from screen content: the hint's words, a row's text or a literal-less-screen marker never becomes a field or a value; vt100 feeds the gate's outcome only (per obs-plan §11 Obs Anti-Patterns § Telemetry Strategy).
- No log-based wait on a sleep and no retry-once around a telemetry assertion in the cases that hold the hint window open (per obs-plan §11 Obs Anti-Patterns § SLO).

## Contract bindings
- **obs ↔ tests (log format):** the `send-*` lines and their `corr` rule are the tests-bound format reproduced in obs-plan §3 Log format JSON schema; a case that reads `agent-run logs` for the turned `hint` case or the bound-expiry case reads that shape. Nextest and harness timeouts sized against 15 s (scope item 9) are tests-owned; obs-plan names no value for the gate's bound and none for `send`'s longest block. The 5 s and 15 s in obs-plan §10 Performance budgets are the heartbeat flip and the SSE keep-alive, unrelated to the gate.
- **obs ↔ tests (gates):** G2 and G4 run over `target/e2e-home/` home-level role files (obs-plan §9 Gate commands). The mutation gate holds `obs_event!` call sites like product code at the epoch boundary (obs-plan §9 Pipeline integration, Mutation row): a gate-outcome emission site the chunk moves needs a case that reads its line.
- **obs ↔ security (live round):** obs-plan §8 Integration points, item 6 holds the diagnostics upload admissible only because every input is synthetic. The one by-path re-verify of scope item 10 handles real CLI content, so its home and any lines it writes must stay off CI's upload and scan-exempt paths; which home the round stamps is P3's (scope item 10), and obs binds only that it is not a CI-uploaded one.
- **obs ↔ arch / `verify`:** obs-plan §4 Edge flows (`verify` / `plugin install`) requires `verify`'s six spawn pairs in `cli-<name>.ndjson` only when `VIOLA_NAME` is set and no process-log file from a plain terminal, and states that no obs gate depends on verify's own lines. Longer settles (scope item 11) change `duration_ms` values on those pairs and nothing else. The same passage says the real-`claude` verify runs only through the local `run --local-live`; how the scope's by-path `viola verify` round stands against that sentence is research's question, not answered from the plan.
- **obs ↔ design:** the readback word `unable · <reason> · <detail>` uses the §6 refusal codes (obs-plan §4 Frontend observable boundary); the `input-not-ready` hint line's wording (scope item 7) is design-owned and has no obs string behind it.

## Acceptance criteria contributions
- (obs) A send refused at the bound writes exactly one wrapper-side `send-refused` with `detail:"input-not-ready"`, no `send-issued` for that call, and a `(conn, rpc_id)` equal to its `channel-*` lines' `(conn, corr)` (per obs-plan §4 Scenario: Confirmed `send` (CL-1) from driver to readback).
- (obs) A send delivered after the gate waited writes `send-issued` then `send-confirmed` and no line of its own for the wait: the count of `run`-role lines between its `channel-request` and its `send-issued` is the same as for a send with no hint (per obs-plan §11 Obs Anti-Patterns § Telemetry Strategy).
- (obs) Every home-level line the new and turned cases write passes G4 with no field, `event` value or `detail` value outside the catalog, and G2 counts zero panics over the same homes (per obs-plan §9 Gate commands).
- (obs) No home-level line from those cases carries send text or screen text, the hint's words included; a send line carries `text_bytes` only (per obs-plan §8 Data classification rules).
