# design extract

## Relevance
partial — the chunk is a gate/bound change with no web-spa surface and no token work; design binds only on the cli surface: the `viola send` readback mirror and its `input-not-ready` hint line (scope item 7), what `send` may print while it blocks longer (items 3, 9), and the `viola verify` output form of the one re-verify round (item 10).

## Constraints
- design-system §Surface: cli → Component Patterns → 2. `viola send` requires a refusal to print `unable` plus `reason  detail` and then exactly ONE `hint:` line keyed by the reason (or reason · detail where listed); `not-delivered · input-not-ready` is one listed key with one hint string. Per-cause hints under one key exist there only for `instance-unreachable` and the exit-1 start refusals (T4, "because the code is shared"), so splitting the `input-not-ready` hint by cause (modal / never-quiet / poisoned / hint past the bound) would be a new pattern, not an existing one: item 7's fork is settled inside the one-key-one-line form unless P4 brings it as a master change for the wrap.
- design-system §Surface: cli → Component Patterns → 2. `viola send` requires that no hint ever names `viola release` (T3) — binding on any reworded `input-not-ready` line.
- design-system §Surface: cli → Component Patterns → 2. `viola send` requires that a hint never quotes the sent text or any upstream text — a reworded line may not carry the CLI's own paste-hint wording (screen text is upstream content) nor any part of the refused prompt.
- design-system §Surface: cli → Component Patterns → 2. `viola send` withholds a hint where it "would have to guess" (the `unknown` bullet): a hint is fixed advice that holds for its key. Scope records that the present advice was measured not to lead out of the paste-hint window; after this build the key covers a modal, a never-quiet screen, a poisoned screen and a hint that outlasts the bound, so whichever string ships must be true for every cause still under the key.
- design-system §Surface: cli → Tokens (platform-specific) → Streams requires the issue line of a send, the refusal (with the `[/ ]` mirror prefix and `unable` padded to the readback-word column) and its `hint:` line on stderr, the `[RB]` result on stdout, and under `--json` one JSON document with the typed exit and NO hint text. The longer gate wait changes none of these placements.
- design-system §Brand Identity (per-surface expression table: cli human TTY 0.2; `--json` / non-TTY / `viola run` passthrough 0.0) requires that nothing redraws in place, that there are no spinners, and that `viola run` prints nothing at all while the wrapped TUI runs — so a `send` blocking up to 18.5 s shows only its static issue line and then its one result, and the gate's wait on the `run` side writes no byte of its own to the child's terminal.
- design-system §Surface: cli → Exit-code phraseology fixes exit 13 as `unable  not-delivered  input-not-ready` (among the listed details): a hint that outlasts the bound (scope item 4) keeps this exact reason, detail and exit; the chunk mints no new detail word.

## Patterns to follow
- The readback mirror sample in design-system §Surface: cli → Component Patterns → 2. `viola send`: `[  ]` open issue line (stderr, TTY only), then `[RB]` on stdout exit 0 or `[/ ]` on stderr exit 13 followed by the hint. A send delivered after the paste hint clears is the ordinary `[RB]` line — "confirmed as any other" (scope item 3) means no distinct word, column or marker for a waited-out send.
- The readback rule in design-system §Brand Identity (Domain anchors → Readback; "Nothing announces success before it is confirmed"): the box stays open through the whole gate wait and closes only on the matching read-back or an `unable` plus typed reason; no intermediate "waiting" state is drawn or printed.
- The step-counter and summary form in design-system §Surface: cli → Component Patterns → 5. `viola verify` / `viola ui` / `viola run`: the re-verify round prints one static line per ledger row and the last-line summary; the row count stays seventeen (scope adds no row), and `fail` is uncoloured.
- The `RefusalDetail::input-not-ready` row in design-system §Color Palette → Domain status colors: the web prints the same word pair with the buff/anthracite refusal treatment; the chunk changes when the refusal occurs, not how it is drawn, so no web change follows.

## Anti-patterns to avoid
- A spinner, progress bar, elapsed-time counter or in-place redraw to cover the longer block — banned by design-system §Anti-Patterns (NEVER do these) → Per-Surface Bans → cli ("NEVER use a spinner, progress bar or live-redrawing dashboard"; a spinner is progress presumed before it is confirmed).
- Upstream text, paths or pids in the refusal or its hint — banned by design-system §Anti-Patterns (NEVER do these) → Per-Surface Bans → cli ("NEVER print upstream text, paths, pids or anyhow chains…").
- Hint or refusal text on stdout, or result text on stderr — banned by design-system §Anti-Patterns (NEVER do these) → Per-Surface Bans → cli ("NEVER mix data and messages").

## Contract bindings
- **layout-templates:** the `input-not-ready` hint string stands in two masters (design-system §Surface: cli → Component Patterns → 2. `viola send`, and layout-templates per scope item 7); a changed product string diverges from both until the wrap amends them together. The masters' text is the wrap's; the product string is this chunk's.
- **security-plan (NEVER-log floor / error sanitization):** design-system §Surface: cli → Component Patterns → 2. `viola send` ("A hint never quotes…") is the design face of the upstream-text ban; a reworded hint is a fixed compiled string.
- **architecture (refusals, exit codes):** design-system §Surface: cli → Exit-code phraseology mirrors architecture's typed codes; `input-not-ready` stays a member of the closed detail set under exit 13.
- **tests:** whether a test pins the present hint string, the `[/ ]` line or the stream placement byte-for-byte (so a reworded line turns a case) is research's question; design cannot attest it.
- **a11y:** no design token binds here; the keystroke clause (scope item 8) is a11y-plan's. The web status region's refusal announcement (design-system §Surface: web-spa → Navigation Pattern) is unchanged by this chunk.

## Acceptance criteria contributions
- A `send` refused at the bound on a verified CLI prints, on stderr with exit 13, the `[/ ]` mirror, `unable`, `not-delivered  input-not-ready`, then exactly one `hint:` line that names neither `viola release` nor any sent or upstream text; whether the code already prints exactly this is research's question (per design-system §Surface: cli → Component Patterns → 2. `viola send`).
- A `send` issued under the paste hint and delivered once the input box returns prints the ordinary `[RB] read back` line on stdout with exit 0 and no `hint:` line (per design-system §Surface: cli → Component Patterns → 2. `viola send`).
- Between a send's issue line and its result line nothing is written to stdout or stderr for the whole gate wait — no spinner, counter or redraw — and under `--json` the result is one JSON document with no hint text (per design-system §Surface: cli → Tokens (platform-specific) → Streams; design-system §Anti-Patterns (NEVER do these) → Per-Surface Bans → cli).
- The re-verify round's stdout is seventeen static step-counter lines and a last-line summary in the stamped form, uncoloured (per design-system §Surface: cli → Component Patterns → 5. `viola verify` / `viola ui` / `viola run`).
