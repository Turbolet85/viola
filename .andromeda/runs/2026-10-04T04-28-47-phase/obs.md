# obs extract

## Relevance
relevant: the readiness gate is a must-trace span on the send path, the vt100 parser-panic degrade has a named obs event, and the verify typed-input probe adds a child spawn to verify's logged spawn set. Part 5 (CARRY 4, the fixture-repo git maintenance) is outside the obs domain.

## Constraints
- **Gate span shape.** obs-plan §4 (Scenario: Confirmed `send`, Required span attributes) requires a `run.readiness_gate` span (INTERNAL kind, per §4 Span kinds). Its only fields are `outcome` (`ready|input-not-ready`, closed) and `vt100_panicked` (bool). It has a static snake_case name and is declared `#[instrument(skip_all, name = "...", fields(...))]` with no `err`/`ret`, per §4 naming convention and §11 Spans / Traces. §4 (instrumentation table, `cli (viola run)`) requires the span to be manual because vt100 has no tracing. Research must answer whether a span can open here with no `send` consumer, or whether only the verify probe and the pump open it (the scope §1 consumer question).
- **Parser-panic degrade event.** obs-plan §7 (Error classes captured) requires a vt100 panic under `catch_unwind` to yield `parse-rejected{parser:"vt100-feed"}` and the refusal detail `input-not-ready`, and requires that it is not a process panic. §6 (additive catalog D-05, `detail` catalog) fixes the detail as `panicked` with a `count` field. §6 (Log levels mapping) puts `parse-rejected` at `warn`. obs-contracts `Log format JSON schema` (the `parse-rejected` row) makes `corr` null by key absence. `diag-line.v1.json` constrains `parse-rejected.detail` to the catalog list (§6, D-31).
- **Panic-hook tension (open for P3/P4).** obs-plan §7 (Panic hooks) requires the custom hook to write one `event:"panic"` line for every panic, before any catch site decides the outcome. §10 (Zero unlogged panics, counting rule) and §9 G2 count every home-level `event:"panic"` line, and the only exemption is a `panic_location` of exactly `src/cmd/hook/seam.rs:<digits>`. A contained vt100 panic would therefore also write a panic line that G2 counts, unless the hook can tell it apart. Research must answer whether the code's panic hook already suppresses or distinguishes a gate-contained panic. Any new G2 exemption or panic-line carve-out needs a Decisions Log entry (§9 G2, the founder-ratified single exemption).
- **No hot-path telemetry.** obs-plan §11 (Telemetry Strategy, first bullet; Logs, "NEVER log at `info` inside hot loops") requires that the PTY pump read loop and the vt100 feed get no span or event per byte or per chunk. Only gate outcomes are logged, with counts carried on the boundary event.
- **No telemetry from screen content.** obs-plan §11 (Telemetry Strategy, "NEVER derive telemetry from screen content"), §10 (Deterministic emission) and §1 (no screen scraping: "vt100 is used for gate outcomes only") require that screen bytes, matched signature text and typed probe text never reach a span field, event field, detail file or derived metric. §11 PII Scrubbing (default-deny) permits only fields named in the §6 catalog.
- **New event values and verify spawn subjects.** obs-plan §1 (Alignment gaps for Phase 3, (b)) records that readiness-gate `input-not-ready` has no `event` value of its own. On the send path it surfaces as `send-refused{detail:"input-not-ready"}` (§4 Scenario: Confirmed `send`), which belongs to `:74`. §11 Logs forbids adding an `event` value without a Decisions Log entry. §4 (Edge flows, `verify` / `plugin install`) and §6 (Child / shell spawns, D-35) fix verify's logged spawns to exactly two pairs, `version-probe` and `verify-probe` (the print-mode probe). `diag-line.v1.json` closes the `subject` enum. A PTY-driven typed-input probe therefore either redefines `verify-probe` or adds a `subject` value; either path is an obs amendment plus a schema change. That probe's steps run under `cli.verify_step`, and its stamp under `state.ledger_write` (§4 Edge flows).
- **Timing constants and the injected clock.** obs-plan §10 (Liveness signal) and obs-contracts `Heartbeat ticks` fix the heartbeat as a 1 s touch with no line per tick, flipping at >5 s (4.9 s live, 5.1 s stale or gone). If the heartbeat moves onto `viola_core::Clock`, those values and the transition-only `liveness-changed` must stay as they are. §4 (Scenario: Confirmed `send`) gives `run.confirm_window` the field `window_ms`, so the named confirmation-window constant is the value that field will carry. §10 (Performance budgets) leaves the spine hook deadline value to tests (provisionally 1.0 s, with the hook's 750 ms connect deadline below it). Obs requires only that hyperfine `max` is gated against that deadline.

## Patterns to follow
- All emission goes through `obs_event!` under `#[instrument(skip_all, fields(..))]`, never raw `tracing::*!` macros. `corr` is set as a typed field or left absent, never `?corr`/`%corr` (obs-plan §11 Logs).
- The ledger-read failure pattern is the closest model: `parse-rejected{parser:"ledger-stamps", detail, count}` in `run-<name>.ndjson`, treated as unverified (obs-plan §4 Edge flows, Capability ledger). For an unverified CLI, the gate's fallback should report its outcome as a closed value in the same way, never as text.
- `verify` spawn logging is done at the call site, with each `process-exit` carrying `child_exit_status` and `duration_ms`, and `run_bounded` stays unlogged (obs-plan §4 Edge flows, §6 Child / shell spawns, D-35). The typed-input probe follows the same call-site convention.
- The new vt100 fuzz target joins the nightly `fuzz` job, which uploads `fuzz/artifacts/` on `failure()` only (obs-plan §9 Platform; §8 item 6).
- `run` worker-thread bodies run inside `catch_unwind`, with the outcome decided at the catch site (obs-plan §7, `run` worker threads). The vt100 feed's own `catch_unwind` must leave the pump thread running and passthrough intact. It must not route to `main`'s exit path.

## Anti-patterns to avoid
- Never use a bare `#[instrument]`, `#[instrument(err)]` or `#[instrument(ret)]` on the gate, the feed or a verify step. A bare one records the PTY bytes or probe text through `Debug` (obs-plan §11 Spans / Traces; G1 in §9).
- Never write telemetry to stdout or stderr from `run`: its terminal carries the child's screen. Never let the default panic hook run (obs-plan §11 Logs, §11 Error Reporting).
- Never add an env var, `config.json` key or flag that widens or disables gate telemetry or redaction. `diagnostics_level` changes volume only (obs-plan §11 PII Scrubbing).

## Contract bindings
- **obs ↔ tests (G2 / §10 zero panics):** the contained vt100 panic must not read as an unlogged or extra `event:"panic"` against test-plan §10 and obs-plan §9 G2. The fake agent's `--vt100-panic-bytes` (or another forcing seam) is the tests-side witness, and a new seam needs a security Decisions Log entry.
- **obs ↔ tests (G4 schema):** any new `subject`, `event` or field value lands in `schemas/diag-line.v1.json` (obs-owned schema) with tests-owned validation bodies (obs-plan §9 G4, §6).
- **obs ↔ security:** `parse-rejected{parser:"vt100-feed"}` is the same event the security-plan degrade cites (scope §4: security-plan :238 / :591). Signatures come only from compiled ledger rows and are never logged. The NEVER-log floor covers screen content (obs-plan §11 PII Scrubbing).
- **obs ↔ architecture:** `input-not-ready` is the arch `RefusalReason` detail, used verbatim (obs-plan §6 detail catalog).
- **obs ↔ tests §3 time mocking:** the injected `viola_core::Clock` is the seam test-plan :1106 names for the heartbeat 1 s / 5 s values and the confirmation window. The obs liveness flip thresholds (§10) are the asserted values.

## Acceptance criteria contributions
- A forced vt100 feed panic produces exactly one `parse-rejected{parser:"vt100-feed", detail:"panicked", count}` line at `WARN`, with no `corr` key, in the home-level role file. The process keeps running with no `process-exit`, and G2 reads that home clean without a new unratified exemption (per obs-plan §7 Error classes captured, §6 detail catalog, §10 Zero unlogged panics).
- G4 passes over every home the chunk's tests write, including `verify`'s typed-input probe spawn pair. Any new `subject` or `event` value is present in `schemas/diag-line.v1.json` and carried by an obs amendment (per obs-plan §6 Child / shell spawns, §9 G4).
- No diagnostics or detail file holds screen bytes, signature text or probe-typed text. The gate's verdict appears only as the closed `ready|input-not-ready` (with `vt100_panicked`) (per obs-plan §11 Telemetry Strategy, §4 Scenario: Confirmed `send`).
- G1 passes: every new `#[instrument]` on the gate, the feed or a verify step has `skip_all` first. There is no span or event per PTY read or per vt100 feed call (per obs-plan §9 G1, §11 Telemetry Strategy).
