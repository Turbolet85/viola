# tests extract

## Relevance
relevant: the chunk adds pure parser and gate logic, a time seam, ledger rows with `viola verify` probes, a property and fuzz surface, a fake-agent mode, and a fix to a harness fixture. Each of these is test-plan territory, and the plan's tier is Comprehensive (per test-plan §1).

## Constraints
- The readiness gate is asserted only by its verdict (`ready` / `input-not-ready`) over fed vt100 bytes, and screen content is never asserted. A forced panic in the vt100 feed under `catch_unwind` must give `input-not-ready` (per test-plan §4 viola-agent-claude, last two bullets). No test parses the vt100 grid or the PTY master output; verdicts come from hook events, `events.ndjson`, channel payloads, the fake-agent receipt and DOM attributes (per test-plan §11 E2E, R7; §1 discipline trigger).
- Time: sync crates inject `viola_core::Clock` (or use mock_instant 0.6.1 global mode) for the heartbeat (1 s / 5 s), the send confirmation window and `budget_override_until` (per test-plan §8 What to mock, Time; §7 Seed strategies, Time-sensitive data row). A test may mock `Clock` with mockall only because `Clock` is a seam trait the product itself defines (per test-plan §4 "mockall doubles only for traits the product already defines"; §8 Mocking libraries). Every deadline this chunk names (quiet period, maximum wait, confirmation window) needs a §4 unit case driven by that clock before any E2E may block on it (per test-plan §11 Universal, the real-time clause). Whether `viola_core::Clock` exists, and whether heartbeat timing moves onto it in this chunk, is research's question.
- Spine deadline: test-plan §10 Performance budgets, "Spine deadline", hands the naming of the product constant to this chunk ("Readiness gate and timing constants"). The gate is meant to read a named product constant that `viola-harness` imports, replacing the provisional `1.0 s` literal and the harness's `SPINE_DEADLINE_S` (per 5-command-implementation §3 `gate`; test-plan §10). The hook's crate-private `SPINE_DEADLINE` = 750 ms in `src/cmd/hook.rs` is the current provisional value. Whether that constant is in this chunk's "deadlines" is P3's question; if it is, the gate's literal and the harness const must both switch to the import.
- Property and fuzz: the vt100 feed under `catch_unwind` over arbitrary bytes is one of the seven parser surfaces. It needs a proptest property at `cases: 512` with `proptest-regressions/` committed (per test-plan §6 Property suite; §1 property-test trigger; §11 Test Data and Universal, deterministic replay). It also needs a `fuzz/fuzz_targets/<target>.rs` with a non-empty seeded `fuzz/corpus/<target>/`, because an empty corpus fails with `corpus-empty` and never passes vacuously (per 5-command-implementation §3 `run`, `--fuzz-replay`; test-plan §6 cargo-fuzz paragraph).
- Ledger rows: every ledger row needs a `viola verify` probe with a post-condition (per test-plan §1 multi-version-compat trigger). Stamps come only from `viola verify` and are never hand-written (per test-plan §7 `ledger/stamps.json` row; §11 Test Data). The `--local-live` pass condition names "each of the six literal row ids" (per 5-command-implementation §3 `run`, `--local-live`), so adding rows changes that literal set. Tests write the expected row ids as literals and never import ledger rows as the oracle (per test-plan §11 Unit).
- The real `claude` never runs in CI. A live `viola verify` is local-only, through `agent-run run --local-live`, which refuses under `CI` with `live-in-ci` (per test-plan §11 Test Strategy; 5-command-implementation §3 `run`). A green fake-agent run is not proof of real-CLI signatures (per test-plan §11 Test Strategy), and a Linux-only run is not proof for ConPTY screen behaviour (per test-plan §11 Test Strategy; §1 multi-os-compat).
- Zero flakiness: `retries = 0`, with no `#[ignore]` parking. Mutation is judged at the epoch boundary only, with no chunk, pre-push or CI mutation gate. CARRY 4's two-sided witness runs are operator evidence under `TMPDIR=<repo parent>/viola-mutants-scratch` (NOCOW) (per test-plan §10 Zero-flakiness budget; §10 Mutation gate). Coverage holds at ≥ 85 % lines / ≥ 95 % functions / ≥ 80 % regions per OS (per test-plan §10 Coverage thresholds).

## Patterns to follow
- Unit tests sit inline in `#[cfg(test)] mod tests`, named `<subject>_<condition>_<expected>`. Table cases use rstest `#[case::label]`, but `viola-e2e` uses a labelled case table because it has no dev-dependencies (relevant to the CARRY 4 `Pass` fixture fix). An rstest `#[fixture]` for a `Clock` is the named example (per test-plan §4 Conventions and Fixture pattern).
- The fake agent's `--vt100-panic-bytes` mode is the deferred consumer-first mode (per test-plan §7 Fake agent, Modes: "land with their consumer chunks; no shape is invented before a recorded fixture"). It feeds the chaos case: forced vt100 panic mode → exit 13 with `input-not-ready`, while human passthrough still reaches the receipt (per test-plan §6 Chaos suite; §1 Vector 8 trigger). `send` belongs to `:74`, so that E2E leg waits for its consumer (scope Boundaries).
- Fuzz targets and seeds follow the existing shape: `viola_name`, `channel_frame` and `hook_stdin` each carry N synthetic seeds, and every reproducer is committed alongside its fix (per test-plan §6 cargo-fuzz paragraph; 5-command-implementation §3 `run`, `--fuzz-replay`).
- Contract and fixture hygiene: any new recorded or synthetic screen/probe fixture passes the run-time hygiene walk (absolute-path / username / schema classes). Fixture prompts are synthetic probe text only (per test-plan §7 Fixture hygiene).
- On-disk state for any E2E comes from real `viola run` / `verify` against the fake agent in a fresh TempDir home. Env is set with `Command::env`, never `set_var` (per test-plan §7 Seed strategies, Test data lifecycle; §11 Integration).

## Anti-patterns to avoid
- Asserting screen content, or deriving a verdict from the rendered child screen. Only the gate's closed verdict may be asserted (per test-plan §11 E2E, R7).
- Any test-owned sleep, timer or elapsed-time verdict for the quiet period, maximum wait or confirmation window. In-process `MockClock` used to steer a spawned `viola run` (per test-plan §11 Universal).
- A new fault seam built from a failpoint crate, or from an env var outside the two existing `fake-agent` seams, without a Decisions Log entry. Faults go through mockall doubles of existing traits plus process and file operations (per test-plan §11 Mocking; security.md test-seam rule).

## Contract bindings
- tests ↔ obs: the `run.readiness_gate` span (`outcome`, `vt100_panicked`) and `parse-rejected{parser:"vt100-feed"}` are obs-owned shapes. Tests assert them through `events.ndjson` and diagnostics only, and the §3 log-format binding applies (per test-plan §3 Log format). If the `--vt100-panic-bytes` seam panics through a non-seam path, the G2 panic-line gate's exemption rules apply (security.md; obs-plan §9).
- tests ↔ arch: the spine-deadline constant (arch request (3)) becomes a product const that `viola-harness` imports for the perf `gate` (per test-plan §10 Spine deadline; 5-command-implementation §3 `gate`).
- tests ↔ security: the vt100 crate must pass `cargo deny` and the no-C-build invariant in the Supply-chain stage (per test-plan §9 Supply-chain row). Its fuzz target joins the separate `fuzz/Cargo.lock` audit (per test-plan §9 Fuzz replay / Supply-chain rows).

## Acceptance criteria contributions
- `scripts/agent-run.sh run` (unit + integration) passes on all three CI OSes. New §4 cases hold the gate verdict over fed bytes (`ready` / `input-not-ready`), the forced-panic → `input-not-ready` case, and each named deadline expiring exactly at its boundary under the injected `Clock`, never before it. Per-OS coverage stays at ≥ 85 / 95 / 80 (per test-plan §4 viola-agent-claude; §10 Coverage thresholds).
- A proptest property over arbitrary bytes into the vt100 feed under `catch_unwind` runs at `cases: 512`, with its `proptest-regressions/` file committed. A new `fuzz/fuzz_targets/` vt100 target with a non-empty committed corpus makes `run --fuzz-replay` report it in `passed` (per test-plan §6 Property suite; 5-command-implementation §3 `run`, `--fuzz-replay`).
- Each new ledger row has a `viola verify` step with a post-condition and is stamped only through `viola verify`. The `--local-live` row-id literal set and its count are amended to the new row set (per test-plan §1 multi-version-compat; 5-command-implementation §3 `run`, `--local-live`).
- CARRY 4 has a two-sided operator witness: a full `run --mutants --package viola-e2e` in a fresh short NOCOW `TMPDIR` leaves 0 half-removed `Pass` repos with the fix, and a control run without it leaves ≥ 1. The evidence stays report-only and adds no gate (per test-plan §10 Mutation gate).
