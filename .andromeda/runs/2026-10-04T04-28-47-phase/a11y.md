# a11y extract

## Relevance
partial — the chunk adds no web-spa surface, but it puts a vt100 feed and a pre-send gate on `run`'s pump thread, which is the `viola run` TUI passthrough. a11y-plan scopes that surface as boundary-only. It also adds a `viola verify` probe step, which falls under the cli output-discipline surface. Section 5 (CARRY 4, the fixture git repos) is out of a11y scope.

## Constraints
- The `viola run` TUI is boundary-only, with three clauses (per a11y-plan §1 A11y Scope Summary → CLI and terminal entities → `viola run` TUI passthrough):
  - viola writes zero bytes to the terminal other than the child's output;
  - human keystrokes are never blocked, refused or delayed past the current atomic paste;
  - focus, mouse and resize sequences pass through and do not count as human editing.

  The vt100 feed, the quiet-period wait and the parser-panic degrade must all hold these clauses. Whether the pump already tees bytes to a screen model without delaying them is research's question.
- `input-not-ready` (and the panic degrade's `not-delivered` / `input-not-ready`) is a refusal to automation only. The human keyboard path through the wrapper is never gated. This is the tui stand-in for SC 2.1.1 (per a11y-plan §4 P4 Human takes the wheel, Required focus order → tui; §5 Keyboard Navigation → tui).
- On a vt100 panic, passthrough continues and the `parse-rejected{parser:"vt100-feed"}` diagnostic goes to `diagnostics/`, never to the terminal (per a11y-plan §2 A11y Strategy → tui, Notes: run diagnostics never reach the terminal).
- The gate's quiet period, maximum wait, confirmation window and send deadlines bound automation only. They impose no time limit on a human, and SC 2.2.1 keeps "no surface". No new timer may add a human-facing timeout or an auto-dismissing notice (per a11y-plan §8 Cognitive Accessibility → Timeout extensions).
- The gate reads the screen only as a closed verdict. viola never parses the rendered `claude` TUI for content, and screen captures never count as a11y evidence (per a11y-plan §11 A11y Anti-Patterns → Universal, the R7 row). This makes no WCAG conformance claim for the TUI (per a11y-plan §11 → Strategy).
- The new `viola verify` typed-input probe step must keep cli output discipline (per a11y-plan §4 P6 CLI board, wait/last, verify, launch line):
  - the step prints a `[NN/NN] … pass|fail` line;
  - output stays linear and static, so waiting out the quiet period draws no spinner, `\r` redraw, cursor-movement or erase sequence;
  - `fail` carries no SGR;
  - no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`.

  Whether `verify`'s current step printer already enforces this is research's question.

## Patterns to follow
- Use the portable-pty `=0.8.1` outer-PTY boundary driver, with `viola-fake-agent` as the child, for the tui clauses. Each clause is its own nextest case on all three OS legs (per a11y-plan §3 Keyboard test harness → Tooling; §4 P4 → tui). Judge clause (1) two ways:
  - Linux/macOS: byte for byte against an unwrapped fake-agent run;
  - Windows: viola's own literals are absent, on both the sideload and inbox ConPTY backends.

  Whether these three cases already exist, and whether their scripts would exercise a gate wait, is research's question.
- Output-discipline failures surface only as nextest failures in the harness `run` JSON `suites[].failures[]`. The cli and tui surfaces emit no a11y rows (per a11y-plan §3 Structured violation JSON schema → cli / tui; §9 CI Integration → Unit / integration row).
- Crate-level tests of these invariants fall under the epoch-boundary mutation audit (per a11y-plan §10 SLO Invariants & A11y Budgets → Standard+ invariants, the CLI output-discipline row).

## Anti-patterns to avoid
- NEVER block, refuse or delay a human keystroke in `viola run` past the current atomic paste, and never count focus / mouse / resize sequences as editing. A gate verdict, a quiet-period wait and a vt100 panic are all covered (per a11y-plan §11 → Keyboard).
- NEVER emit SGR under `viola run`, and never write a viola diagnostic or refusal literal onto the passthrough stream (per a11y-plan §11 → Visual; §2 → tui Notes).
- NEVER parse the rendered `claude` TUI screen for content, and never take screen captures as evidence. Gate tests assert only the `ready | input-not-ready` verdict (per a11y-plan §11 → Universal).

## Contract bindings
- tui boundary ↔ tests: the three outer-PTY clauses run on the tests' portable-pty driver (test-plan E2E driver → tui). Results go through the harness `suites[]` JSON with no a11y rows (a11y-plan §3 Keyboard test harness, §3 Structured violation JSON schema → cli / tui, §9 Unit / integration row).
- tui boundary ↔ obs: the `parse-rejected{parser:"vt100-feed"}` degrade logs to `diagnostics/` only, never to the terminal stream that clause (1) measures (a11y-plan §2 → tui Notes; obs-plan §6 catalog).
- cli ↔ design: the `verify` probe step line's SGR placement follows design cli (a11y-plan §4 P6; §6 Visual Design Verification → State color tokens, CLI equivalent).

## Acceptance criteria contributions
- (a11y) With the vt100 feed and gate active, a fake-agent `run` under the outer PTY passes clause (1), zero viola-originated bytes:
  - Linux/macOS: the stream equals the unwrapped run byte for byte;
  - Windows: none of viola's literals appear, on both ConPTY backends.

  The check also runs with the feed forced into its parser-panic degrade (per a11y-plan §3 Keyboard test harness → Tooling; §4 P4 → tui case 1).
- (a11y) Human keystrokes injected through the outer PTY reach the child unblocked in each of these states:
  - while the gate waits out its quiet period;
  - while it returns `input-not-ready`;
  - after a vt100 panic.

  In none of them does viola delay the keystroke or emit any byte to the terminal (per a11y-plan §1 → `viola run` TUI passthrough; §4 P4 → tui case 2; §11 → Keyboard).
- (a11y) The new `viola verify` typed-input probe step meets P6 output discipline:
  - it prints a `[NN/NN] … pass|fail` line;
  - the TTY stream has no `\r` redraw, cursor or erase sequence during the wait;
  - `fail` carries no SGR;
  - there is no SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json`.

  These are checked by assert_cmd / outer PTY on all three OS legs (per a11y-plan §4 P6).
- (a11y) No gate, proptest, fuzz or fake-agent test asserts rendered screen content. Each asserts only the closed verdict and the degrade outcome (per a11y-plan §11 → Universal, R7 row).
