# arch extract

## Relevance
relevant: arch locks the gate's semantics, its crate placement (vt100 in `viola-agent-claude`, wiring in `src/run/`), the ledger and stamps shapes, the confirmation-window home and the spine-deadline hand-off to this chunk. CARRY 4 (the fixture git maintenance) touches arch only at the edge.

## Constraints
- The gate behaves as follows (per architecture §Established Decisions [Screen Model]). vt100 0.16.2 is a pre-send readiness gate only. After `turn-ended` it waits for the screen to go quiet, then requires the version-stamped input-box signature and the absence of every known modal signature. If the screen is not quiet within the maximum wait, or either check fails, it types nothing and yields `not-delivered` / `input-not-ready`. The quiet period and the maximum wait are ledger rows "beside the signatures", never `config.json` keys. On unverified builds "the gate falls back to delivery confirmation only". What that means for the gate's verdict (skipped, or always `ready`) is research/P4's to pin. The Stack row "Screen model" says the model is "never used to read content".
- Crate placement (per architecture §Infrastructure Patterns → Crate dependency direction and → Project directory structure). vt100 is a dependency of `viola-agent-claude` alone ("the screen model and signatures behind the readiness gate; `run`'s pump feeds it bytes"), and the gate wiring lives in the root bin's `src/run/`. `viola-agent-claude` stays pure: no I/O, and no `viola-state` dependency unless a consumer needs one (§Established Decisions [Agent Coverage]). `viola-core` depends on no viola crate. Whether vt100 is in any manifest yet is research's question; scope says it is not.
- The ledger is a closed set (per architecture §Established Decisions [CLI Version Compatibility] and §Cross-cutting Patterns "Capability ledger as the single gate"). The "Modal and input-box screen signatures" row lands with the readiness gate, each row with its own `viola verify` probe and a post-condition check. A version is verified only when its stamp holds every landed row `pass`, so adding rows to `viola_agent_claude::ledger` turns every existing stamp unverified until it is re-stamped. That includes the 2.1.283 fixture set and every fake-agent test home. Under [CI/CD], the real `claude` probe and `--record` run only locally, and CI runs `verify` against the fake agent.
- Stamps go through the one writer (per architecture §Standard Contracts "Ledger stamps envelope" and §Occupied Resources → Filesystem `ledger/stamps.json`). Measured values (quiet period, maximum wait, the confirmation window) are written as additive `measured` keys in the existing `v:1` envelope, through `viola_state::stamps::update_stamps` only, called only by `viola verify`. A merge keeps unknown versions and fields, and the rows' probes and expected post-conditions are compiled into `viola-agent-claude`.
- The confirmation window has one home (per architecture §Established Decisions [Delivery Confirmation]). It is a capability-ledger row per CLI version plus a built-in fallback compiled into `viola-agent-claude`, never `config.json`. `send`'s total is the gate's maximum wait + the atomic paste + the window, and it must stay below the MCP client's tool-call timeout. That total is the set of send-path deadlines this chunk names; the use of the window (matching) belongs to `:74`.
- The spine deadline belongs to this chunk (per architecture §Established Decisions [Hook Transport]). The hook-local, crate-private `SPINE_DEADLINE` = 750 ms (provisional) is open to be named "as the product constant the perf gate reads … with the 'Readiness gate and timing constants' chunk (test-plan §10)". Arch names this chunk, which closes scope §3's `[inferred]` on whether the spine deadline is among the deadlines. The dialog deadline (§[Hook Contract]) and MCP `wait`'s default `timeout_ms` (§[MCP]) stay open items owned by other entries.
- The human always wins, and the terminal stays clean (per architecture §Design Philosophy "The human always wins the wheel", §Cross-cutting Patterns "Diagnostic output channels" and "Tokio containment"). Feeding vt100 must never delay or alter byte passthrough. While the child runs, `run` writes nothing to the terminal except the child's output. The gate runs on std threads with blocking I/O; no Tokio enters `run`, `viola-agent-claude` or `viola-core`, and the tokio ban runs on `deny-sync.toml` per sync crate.

## Patterns to follow
- Split pure decisions from I/O, as the CLI version gate does (per architecture §Established Decisions [Agent Coverage]). There, the pure verdict lives in `viola-agent-claude` (`ledger::verified`), the bounded spawn and the stamps read are the root bin's `run::version_gate`, and the file I/O is `viola_state::stamps`. Mirror that split: signatures, matching and constants in `viola-agent-claude`; the clocked wait loop and `catch_unwind` feed in `src/run/`.
- Prefer a named attempt-count or deadline constant with one home over an inline literal (per architecture §Established Decisions [Snapshot writer] `viola_state::fs::REPLACE_ATTEMPTS`, and §[Hook Transport] `SPINE_DEADLINE`). Constants are SCREAMING_SNAKE_CASE (§Conventions → Naming patterns).
- Follow the `viola verify` step shape (per architecture §Established Decisions [CLI Version Compatibility] and §Conventions → CLI exit codes). Each row prints one stdout step line, followed by the `stamped <ver>  <n> pass  <m> fail` summary; a failing row still writes its stamp and verify exits 1. The probe dir is `ledger/probes/<pid>/`, removed by a drop guard. A typed-input probe is a second probe drive under the same discipline.
- Spawn the probe child directly through the `viola-pty` seam, never through a shell (per architecture §Established Decisions [PTY] and §Cross-cutting Patterns "Cross-platform discipline"). Spawners outside `viola run` stay on the inbox ConPTY. Per H2, a key written right after a `resize` can be lost, so a probe that types waits until the child has seen the new size. An interactive child with no terminal answering DA1 is the open "headless" stall finding under [PTY]. Whether the verify probe is that first headless runner is a P4 question.
- Changes to own formats are additive (per architecture §Conventions → Interfaces and versioning, and §Established Decisions [Validation]). New `measured` keys and any new detail values need no `v` bump. Readers never use `deny_unknown_fields`. `input-not-ready` is already in the closed `not-delivered` detail set in `viola-core`. Whether the code already carries it is research's question.

## Anti-patterns to avoid
- Never read screen content outside the readiness verdict, and never take signatures from runtime or upstream text (per architecture §Stack and Technologies "Screen model" and §Cross-cutting Patterns "Untrusted upstream text"). Signatures come only from compiled ledger rows.
- No new env var outside `VIOLA_*` (per architecture §Conventions → Environment variables and §Cross-cutting Patterns → Config management). Only the two ratified `fake-agent` seams exist. A new forcing seam for a vt100 panic, or any dependency or feature that reads the environment, breaks the rule unless a Decisions Log entry covers it. The fake agent's `--vt100-panic-bytes` CLI flag on the test-only `viola-fake-agent` is not an env seam. A CARRY 4 fix through `git -c maintenance.auto=false` adds no env var; a `GIT_*` env setting would need to be judged against the `AGENT_RUN_` harness-only rule.
- No C-building crate, and no licence outside the allow list (per architecture §Infrastructure Patterns → Build system: `deny.toml` allows exactly MIT, Apache-2.0, Zlib and Unicode-3.0, with C-build bans). Never widen an allow or add a skip to admit vt100's transitive graph or a `mock_instant` dependency. Their licences and build status are research's to confirm under `cargo deny check`.

## Contract bindings
- Arch ↔ tests (ledger growth vs stamped homes): new closed-set rows make the fake agent's stamped test homes (`stamped_home` at 2.1.283, harness `boot` step 4) and `fixtures/claude/2.1.283/` unverified until the fake agent's verify drive passes the new rows (per architecture §Occupied Resources → Repository `target/e2e-home/`). The fake agent therefore needs an interactive mode that a typed probe can drive in CI. Today it has only the print mode (§Occupied Resources → Binary, subcommands).
- Arch ↔ obs/tests (panic hook vs G2): the custom panic hook reports a `vt100` panic even when `catch_unwind` catches it. `scripts/g2-zero-panics.sh` admits zero `event:"panic"` role lines under `target/e2e-home`, exempting only `src/cmd/hook/seam.rs:<digits>` (per architecture §Infrastructure Patterns → Project directory structure). A forced-panic test needs either no role line on the caught path or a new G2 exemption, and an exemption needs a Decisions Log entry.
- Arch ↔ tests (fuzz workspace): the proptest and fuzz target for the vt100 feed reach vt100 through `viola-agent-claude`, which `fuzz/` already depends on by path. `fuzz/` stays outside the root `[workspace]` and has its own lockfile audit (per architecture §Occupied Resources → Workspace crates and → Repository `fuzz/`).
- Arch ↔ tests (the injected `Clock`): the test plan places a `viola_core::Clock` in `viola-core`. Arch lists `viola-core`'s third-party dependencies as nutype only (per architecture §Infrastructure Patterns → Crate dependency direction), so a `Clock` there must stay std-only, or any new dependency must be added to that list at wrap.
- Arch ↔ tests harness (CARRY 4): the `Pass` fixture in test-only `viola-e2e` is outside every product crate. Its git calls follow the spawn-directly, no-shell discipline (per architecture §Cross-cutting Patterns "Cross-platform discipline").

## Acceptance criteria contributions
- `vt100` appears only in `crates/viola-agent-claude/Cargo.toml` (and `[workspace.dependencies]`). The gate wiring sits in `src/run/`, `viola-agent-claude` gains no I/O, and `cargo deny check` plus the per-crate `deny-sync.toml` tokio ban stay green, with no new allow, skip or exception (per architecture §Infrastructure Patterns → Crate dependency direction and → Build system).
- The input-box signature, the modal signature set, the quiet period, the maximum wait and the confirmation window (plus its compiled fallback) each have exactly one named home in `viola-agent-claude`, with no `config.json` key. Each new ledger row has a `viola verify` step line, and its stamp goes through `update_stamps` only (per architecture §Established Decisions [Screen Model], [Delivery Confirmation] and [CLI Version Compatibility]).
- The hook spine deadline becomes one named product constant that both `viola hook` and the perf gate read, never an edited literal (per architecture §Established Decisions [Hook Transport]).
- When the gate fails (not quiet within the maximum wait, signature mismatch, a modal present, or a parser panic), `run` types zero bytes and the verdict is `not-delivered` / `input-not-ready`. Human passthrough bytes are unchanged and undelayed, and the terminal gets no viola-written byte (per architecture §Established Decisions [Screen Model], §Design Philosophy "The human always wins the wheel" and §Cross-cutting Patterns "Diagnostic output channels").
