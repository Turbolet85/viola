# arch extract

## Relevance
Partial. The chunk is test-side gate work: CI jobs, harness verbs and a `fuzz/` tree. Arch covers where the code lives (workspace placement), the CI/CD discipline, the toolchain pin and floor, the deny graph, and registering new repository paths. It does not cover gate thresholds or suite semantics; those belong to test-plan.

## Constraints
- **The toolchain pin stays; MSRV is a separate check.** architecture §Stack and Technologies (Language / runtime) and §Inherited Defaults require Rust 1.98.1 pinned exactly by `rust-toolchain.toml`, with `rust-version = "1.96"` as the declared floor. The MSRV job has to check 1.96 without changing the pin. Because `rust-toolchain.toml` takes precedence over a default toolchain, the job must select 1.96 explicitly (`+1.96` or an equivalent override). Whether all locked dependencies and all HEAD code build on 1.96 is research's question.
- **Toolchain install method conflicts with the scope.** architecture §Stack and Technologies (CI/CD row) and §Infrastructure Patterns → CI/CD approach (Setup steps) require `rustup toolchain install` and state "no toolchain action". The scope's item 2 names dtolnay/rust-toolchain `1.96`, and the nightly fuzz job would also need a non-pinned toolchain. Either install both with `rustup toolchain install <ver>`, or amend arch at wrap to name the exception. The plan must pick one.
- **`fuzz/` must stay out of the main workspace and the deny graph.** architecture §Established Decisions [Module Boundaries] requires workspace members to be `crates/*` plus the registered test-only `viola-e2e`. §Infrastructure Patterns → Build system (Dependency policy) requires `deny.toml` to ban C-building crates, including `cc`. libfuzzer-sys builds with `cc`, so `fuzz/` must be its own workspace or excluded, never a member. It must not affect `cargo check --workspace`, `cargo deny check` or the sole-root `deny-sync.toml` runs. If it has a manifest, §Build system (Publishing) requires `publish = false`.
- **CI least-privilege discipline applies to every new job and step.** architecture §Infrastructure Patterns → CI/CD approach requires `permissions: {}` at the top of the workflow and `contents: read` per job. Every `uses:` must be pinned by full SHA with a version comment. Event values reach a step only through `env:`. Every gate step is fail-closed `shell: bash`. Uploads that carry test output go out only behind the secret scan, following the `test` job's `steps.secret-scan.outcome` gating. This governs the new MSRV, fuzz-replay and coverage steps, the `mutants.out/` decision (scope item 8) and any `concurrency:` block (scope item 7).
- **Two workflows with distinct roles.** architecture §Infrastructure Patterns → CI/CD approach requires `ci.yml` (push/PR, 3-OS matrix) to be the only push/PR pipeline. `nightly.yml` runs weekly and on dispatch, and arch currently describes it as advisories-only. The time-boxed fuzz run in `nightly.yml` changes that description, so arch needs an amendment at wrap. §CI/CD approach "Target jobs" names Quality gates as the owner of its rows, and target job 5 (the workspace test suite) is the row this chunk's instrumented run takes over. Target job 6 (`cargo build --release`) belongs to the Workspace tree chunk.
- **Every OS-specific branch compiles and is tested on its own runner.** architecture §Cross-cutting Patterns → Cross-platform discipline requires it. This is why the coverage floors are per OS: `#[cfg(windows)]` / `#[cfg(unix)]` code is measured on the runner that compiles it.
- **Harness placement.** architecture §Occupied Resources (Binary; Workspace crates) and §Established Decisions [Module Boundaries] require the `gate` / `--coverage` / `--fuzz-replay` verbs to live in the test-only `viola-e2e` (`viola-harness`) behind `scripts/agent-run.{sh,ps1}`, with no product crate depending on it. §Occupied Resources (Binary) makes test-plan §3 the owner of its command contract. §Infrastructure Patterns → Build system (Lint) says `viola-e2e` denies only `dbg_macro`, because the harness prints its JSON document. Harness builds use `target/harness/` as `CARGO_TARGET_DIR` (§Occupied Resources → Repository).

## Patterns to follow
- **Proven-live probes.** A ban or gate is proven to fire by a negative probe plus a clean control, as `scripts/deny-probes.sh` and `scripts/lint-probes.sh` do (architecture §Infrastructure Patterns → Build system). This applies to the zero-retries check and to `gate`'s breach and missing-artifact paths.
- **Harness artifacts go under `target/agent-run/artifacts/`.** Per-suite JUnit and `run-summary.json` live there, written by `viola-harness` and gitignored (architecture §Occupied Resources → Repository). `llvm-cov-summary.json` and the other artifacts `gate` reads belong in the same place.
- **Tool installation.** Version-pinned cargo tools come from the single `taiki-e/install-action` v2.87.19 line; a tool without a manifest gets a sha256-verified script such as `scripts/install-ripgrep.sh` (architecture §Infrastructure Patterns → CI/CD approach, Setup steps). cargo-llvm-cov 0.9.1 joins the taiki-e line; cargo-fuzz follows whichever pattern applies.
- **Uploads follow the `test` job's scan gating.** Upload on `always() && steps.secret-scan.outcome == 'success'` with actions/upload-artifact v7.0.1 and 7 days retention (architecture §Infrastructure Patterns → CI/CD approach, Jobs wired today). Use this for `mutants.out/` if it keeps being uploaded.
- **Shims forward verbs.** Both `agent-run` shims forward to `viola-harness` identically, as `schema-check` / `secret-scan` already do (architecture §Infrastructure Patterns → Project directory structure, `scripts/agent-run.{sh,ps1}`).

## Anti-patterns to avoid
- **Registry over-reach.** Do not register the environment the harness sets for its children (`LLVM_PROFILE_FILE`, like the existing `PATH` / `CARGO_TARGET_DIR` / `NEXTEST_PROFILE`) as an Occupied Resource. The arch registry tracks only variables the product reads or sets, plus `AGENT_RUN_`-prefixed harness variables (architecture §Occupied Resources → Environment variables). Any new harness-read variable must use the `AGENT_RUN_` prefix and be registered.
- **Moving test tooling into arch's Stack.** Do not add cargo-llvm-cov, cargo-fuzz, proptest or arbitrary to arch's §Stack and Technologies. architecture §Established Decisions [Deferred] hands the test framework to test-plan, which pins those versions.
- **Changing `rust-toolchain.toml` for MSRV or nightly.** Do not replace the exact 1.98.1 pin, and do not add a nightly channel to it (architecture §Infrastructure Patterns → Project directory structure, `rust-toolchain.toml` comment).

## Contract bindings
- **arch ↔ tests:** `viola-harness`'s command contract (the `gate`, `run --coverage`, `run --fuzz-replay` verbs, the `tool-missing` exit and the artifact paths) is test-plan §3. Arch owns only where it lives and the registered paths (architecture §Occupied Resources → Binary / Repository).
- **arch ↔ security:** SHA-pinned actions, `permissions: {}`, no widened ignores, no silenced zizmor persona (the `concurrency-limits` decision), and the deny C-crate ban that keeps `fuzz/` out of the graph (architecture §Infrastructure Patterns → CI/CD approach and Build system).
- **arch ↔ obs:** scan-gated uploads (obs-plan §9 scan roots do not cover `mutants.out/`), per architecture §Infrastructure Patterns → CI/CD approach, Jobs wired today.
- **arch ↔ Workspace-tree chunk (next):** the `cargo modules dependencies --acyclic` / `orphans --deny` and `cargo tree -e features` rows in scope item 1. Arch lists cargo-modules 0.27.0 as boundary review "on demand", not as a CI gate (architecture §Infrastructure Patterns → Build system, Boundary review; §Stack and Technologies, Code quality row). The rmcp feature set (`server` + `transport-io`) is fixed by §Stack and Technologies (MCP server row) and already enforced by the `deny.toml` feature bans. Whether rmcp is in the graph at HEAD at all (`viola-mcp` is created by its first consumer) is research's question.
