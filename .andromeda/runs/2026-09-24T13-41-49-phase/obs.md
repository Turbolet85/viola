# obs extract

## Relevance
Partial. The chunk is test-plan-owned CI gating. Obs has a stake in five areas: the per-OS `test` job restructure (G2/G4, the secret scan and the scan-gated uploads have to survive it), the `mutants.out/` upload, the `nightly.yml` scope, G1/G3 reaching into `fuzz/`, and the §10 budget semantics that `gate` has to parse.

## Constraints
- The instrumented `cargo llvm-cov nextest` run that replaces the separate unit / integration / e2e runs must keep the §9 step order after it: G2 and G4 `if: always()`, then harness capture `if: failure()`, then `id: secret-scan` `if: always()`, then the uploads gated on `steps.secret-scan.outcome == 'success'`, then the hit-report upload (per obs-plan §9 Step order and conditions). Every viola home must stay under `target/e2e-home/`, and `AGENT_RUN_KEEP_HOMES=1` must hold (per obs-plan §9 Step order 1). If the instrumented run moves homes or output, G2's non-empty check fails. Whether that happens is research's question.
- The secret scan must keep covering the nextest JUnit file, which carries failing tests' captured output (per obs-plan §9 Step order 3, and the JUnit row of the Telemetry artifact handling table). cargo-llvm-cov may move the nextest output under its own target dir, which would change the JUnit path the scan and the `junit-<os>` upload expect. Whether HEAD's scan and upload paths still resolve under `--coverage` is research's question.
- Every upload that carries test output leaves CI only after the secret scan passes (per obs-plan §11 CI "NEVER upload `diagnostics/` artifacts before the secret-scan step passes", and §8 PII Scrubbing integration point 6). This is what item 8 (`mutants.out/`) is about: §8 point 6 does not list it among the scanned roots. Any new artifact (`llvm-cov-summary.json`, `lcov.info`, fuzz crash output) follows the same rule if it carries test output. Absolute paths are Medium class (per obs-plan §8 data classification table).
- G1 (bare `#[instrument]`) and G3 (`panic = "abort"`) scan the whole tree, and G1's comment names `fuzz/` explicitly (per obs-plan §9 Gate commands). G3 also scans `*.yml` workflows and `CARGO_PROFILE_*_PANIC` (per §7 Unwinding is required, and D-17). So `fuzz/Cargo.toml`, `nightly.yml` and every new CI job must carry no `panic = "abort"` spelling. Fuzz code must not use a bare `#[instrument]`.
- Every CI telemetry verdict is an assertion that sets an exit code (per obs-plan §11 CI, and §11 SLO "NEVER define a budget without an exit-code-setting assertion"). When `gate` reads `perf-<hook>.json`, it must use the §10 budget semantics: hyperfine `max` is the gated statistic, the equivalent of `jq -e '.results[0].max < <deadline_s>'`, and p50/p95 are report-only (per obs-plan §10 Performance budgets, and §11 Metrics "NEVER report latency without the gate statistic").
- The §10 error budget (0 panics, 0 secret-scan hits, 0 schema-conformance failures) is measured by the in-job exit codes of G2, G4 and the `secret-scan` step, not by an uploaded artifact (per obs-plan §10 Error budget, Measurement). `viola-harness gate` adds a per-job verdict alongside them. It does not replace them, and it must not make them conditional.
- Zero retries is the tests-side parallel of obs's zero-unlogged-panics invariant (per obs-plan §10 Cross-input parallel, and §11 SLO "NEVER add retry-once policies"). A re-run is not a substitute under `retries = 0` (per §11 CI).

## Patterns to follow
- Gate step shape: one `run:` step per gate, `shell: bash` on all three OSes, fail-closed on tool-missing and I/O errors. G1/G3 pass only on rg exit 1. G2 fails first on an empty scope so it cannot pass vacuously (per obs-plan §9 Gate commands). `gate --require <suites>` should also fail closed on a missing artifact, which is the same pattern.
- Evidence surfaces for an agent reader: gate output is machine-parseable and never echoes content. G4 prints file, line and schema keyword only, and the scan hit report prints file, line, offset and pattern class, never the matched bytes (per obs-plan §9 G4, and §8 Scan failure). `gate` breach messages should follow the same form.
- Artifact discipline: SHA-pinned `actions/upload-artifact` v7.0.1, `retention-days: 7`, one unique artifact name per OS per run (per obs-plan §9 Telemetry artifact handling, and Artifact retention).
- The build must not depend on CI env metadata, and nothing may inject it into product log lines (per obs-plan §9 CI-specific resource attributes). `LLVM_PROFILE_FILE` is consumed by the instrumentation runtime, never by product code as configuration (per obs-plan §11 Logs, env-as-config ban).
- Obs code (`obs_event!` call sites, `MillisUtc`, the panic hook, TraceLayer closures) is covered by mutation and coverage like product code (per obs-plan §9 Pipeline integration, Mutation row). The coverage ignore regex must not reach obs code.

## Anti-patterns to avoid
- Losing a failing job's diagnostics. This covers bare `always()` or `failure()` on uploads, and any restructure that skips G2, G4 or the scan after a failed test step (per obs-plan §11 CI). It bears on item 7: a `concurrency:` block with `cancel-in-progress` cancels in-flight jobs, so its effect on the `always()` gate and upload chain should be weighed and recorded.
- Setting an abort panic strategy anywhere G3 sees it, including a cargo-fuzz profile or a `nightly.yml` env (per obs-plan §11 Error Reporting "NEVER call the default panic hook", §7 Unwinding is required, and §9 G3).
- Weakening a gate to get green: widening a scan exemption, or making a telemetry verdict human-read (per obs-plan §11 CI "NEVER use human-review-gated log analysis", and §11 Universal).

## Contract bindings
- obs ↔ tests harness: G2 and G4 read home-level role files under `target/e2e-home/**/diagnostics/`, and G4 validates against the obs-owned `schemas/diag-line.v1.json` and `schemas/diag-detail.v1.json` (per obs-plan §9 G4, and §8 Detail-file scope). The instrumented test run has to keep producing that input.
- obs ↔ tests secret scan: obs requires the scan to check 0600 permissions (a non-0600 `diagnostics/` file is a build failure per obs-plan §10 Build / deploy failure conditions). The scan body is tests-owned (per §3 Bootstrap phases, Ownership). Item 9's `file_mode` mutants in `crates/viola-e2e/src/harness/secret_scan.rs` sit on exactly that 0600 check, so killing them keeps the obs permission floor tested.
- obs ↔ tests perf gate: `gate` parses `perf-<hook>.json` per the obs-plan §10 Performance budgets table. The deadline values are tests-owned (provisionally 1.0 s). No job requires `perf` at HEAD.
- obs ↔ workspace lint assertion: the CI member-list assertion says every product member has `[lints] workspace = true` and only `viola-e2e` lacks it (per obs-plan §3 obs-ci-gate-wire). If `fuzz/` joins the root workspace rather than being its own or excluded workspace, that assertion and the print-ban scope are affected.
- obs ↔ arch CI platform: `nightly.yml` is written as "runs only the weekly `cargo deny check advisories`" (per obs-plan §9 Platform). Adding the time-boxed fuzz run to `nightly.yml` makes that sentence untrue, so an obs §9 Platform amendment is expected.

## Acceptance criteria contributions
- In the restructured per-OS `test` job, G2, G4 and `secret-scan` still run `if: always()` after the instrumented run. G2's non-empty `target/e2e-home` check passes on a green run. Scan-gated uploads (`diag-<os>`, `harness-<os>`, `junit-<os>`) still point at paths that exist under `--coverage`, and the JUnit file they point at is covered by the scan (per obs-plan §9 Step order and conditions).
- The `mutants` job either stops uploading `mutants.out/`, or runs the secret scan over it first with the upload gated on `steps.secret-scan.outcome == 'success'`. No test-output artifact leaves CI unscanned (per obs-plan §11 CI).
- G1 and G3 stay green with the new `fuzz/` tree, `nightly.yml` and all new jobs present, so no `panic = "abort"` spelling and no bare `#[instrument]` anywhere (per obs-plan §9 Gate commands).
- `gate` exits non-zero on a `perf-<hook>.json` whose `.results[0].max` meets or exceeds the deadline, and on a missing required artifact. It never passes on report-only statistics (per obs-plan §10 Performance budgets).
