- Log lines (per obs-plan §4 Scenario: Confirmed `send` (CL-1) Required log fields + §6 Additive field catalog): `channel-request{corr:<rpc id>, conn, method, from, from_trust:"self-reported", sender}`; `send-issued{corr:<cursor>, from, text_bytes}`; `send-confirmed{corr:<cursor>, confirmed, duration_ms}`, where `confirmed:false` means `unconfirmable`; or `send-refused{corr, refusal, detail, side:"wrapper", wheel}`; and `channel-response{corr, conn, result_class, refusal, detail, duration_ms}` on both sides. Every wrapper-side `send-*` line also carries `conn`/`srv_conn` + `rpc_id` (D-30). The client-side `send-refused{side:"client"}` carries neither, and its `corr` is absent.
- `corr` semantics (per obs-plan §3 Log format JSON schema, keyed contract `log-format-json-schema`): `corr` on `send-*` = the send `cursor`. A send refused BEFORE `send-issued` (`input-not-ready`, `turn-running`) carries `corr` = the `events.ndjson` end offset at refusal time (D-28). That offset is a log join key only and is never returned to the caller. `corr` is copied as a typed JSON number, never `?corr`/`%corr`. Null is written as key absence, never a literal `null`. `schemas/diag-line.v1.json` requires `corr` on `send-*` when `side` is `wrapper`.
- Closed codes (per obs-plan §6 `detail` code catalog): wrapper `send-refused.detail` ∈ `input-not-ready|no-prompt-submitted|turn-running`; client validation is `refusal:"not-delivered", detail:"control-character", side:"client"`, with a wrapper mirror line if the frame reached it (§4 Scenario 2). Refusal details are the arch `RefusalReason` details verbatim. The one-in-flight detail must come from that closed set (`turn-running` is the catalog's candidate; P4 confirms it against arch §Conventions). A new `detail` or `event` value needs a Decisions Log entry (§11 Logs). `parse-rejected` also lists `parser:"paste-text", detail:"control-character"` (§6). Whether a paste-text rejection emits that line in addition to `send-refused` is P4's to pin.
- Process role and exit (per obs-plan §4 Instrumentation per surface, cli short-lived row + §7 Panic hooks): `viola send` is `process:"cli"`. It writes `process-start` / `process-exit{subject:"self", exit_code, detail}` to `cli-<name>.ndjson` only when an instance resolves (D-06). The full anyhow chain goes only to `detail-cli.ndjson`. `send.client` closes with `process-exit{exit_code}` ∈ 0/10/11/13/14/20/21 (§4 Scenario: Confirmed `send` Cleanup). A panic in the verb writes `process-exit{exit_code:1, detail:"internal-error"}`, then exactly `error: internal error\n` on stderr.
- Feed-panic containment (per obs-plan §7 Error classes captured + §7 Panic hooks `run` worker threads): a vt100 poisoning gives exactly one `parse-rejected{parser:"vt100-feed", detail:"panicked", count:1}` at WARN with no `corr`, and `run` continues. - Zero-panics SLO (per obs-plan §10 Always-required SLO invariant + §9 G2): G2 counts every home-level `event:"panic"` line, with exactly one exemption (`panic_location` == `src/cmd/hook/seam.rs:<digits>`). That answer is shown at P4 and held, never ratified here. A test design that keeps the forced panic outside a G2-gated home is the non-widening candidate (scope §7).

## Patterns to follow
- `obs_event!` with explicit typed fields only, under `#[instrument(skip_all, fields(..))]`; never raw `tracing::{info,…}!` / `event!` outside `viola_core::obs` (per obs-plan §8 Integration points 1 + §11 Logs).
- `channel-response` is emitted from a `Drop` guard in `channel.dispatch`, so an early return, refusal or contained connection-worker panic still logs it (`result_class:"error", error_code:-32603` on panic) (per obs-plan §4 Scenario: Confirmed `send` Cleanup + §7 Panic hooks). The new `send` method follows the same guard as `hook.event`. Whether the landed dispatcher already carries that guard is research's question.
- Content separation: the prompt reaches only `instances/<name>/diagnostics/detail-*.ndjson`, inside a chain. Home-level lines carry `text_bytes` only. `SendParams.text` carries veil `#[derive(Redact)]` + `#[redact]` (per obs-plan §8 Data classification rules, "Prompt text" row + Integration points 2).
- Human output goes through `src/human.rs` with one `write_all` per line and no print macro. A local `#[allow(clippy::print_stdout)]` is admissible only in an output module that actually uses a print macro (per obs-plan §11 Logs, `print!` ban + §3 harness pattern). The `[RB]` stdout line and the `--json` result are product output, not telemetry. No log line goes to stdout or stderr on any role.
- Log at boundary outcomes only: one gate verdict per send, and counts on the boundary event (per obs-plan §11 Telemetry Strategy, "NEVER over-instrument hot paths").

## Anti-patterns to avoid
- No per-byte or per-chunk span or event on the PTY pump or vt100 feed, and no `info` inside hot loops (per obs-plan §11 Telemetry Strategy + §11 Logs). This binds CARRY 5's bounded tee → feed queue: an overflow is recorded at most as a gate outcome or count on the boundary event, never as a line per dropped feed. tracing-appender `non_blocking` and any lossy writer stay banned.
- No send text, screen content or prompt in any span field, home-level line, `detail` code or fixture. No bare `#[instrument]`, and no `#[instrument(err|ret)]` on send paths (per obs-plan §11 Spans / Traces + §11 PII Scrubbing + §11 Telemetry Strategy "NEVER derive telemetry from screen content").
- No new G2 exemption, no retry-once policy for panics, and no new `event`/`detail` value or schema field without a Decisions Log entry (per obs-plan §11 SLO + §11 Logs + §8 Default-deny posture).
