## Patterns to follow
- **File and name placement.** Per test-plan §2 Test directory + naming conventions: root integration binaries take a `<surface>_<topic>.rs` prefix (`cli_`, `channel_` for this chunk), unit cases sit inline in `#[cfg(test)] mod tests`, crate-level cases in `crates/viola-<area>/tests/<topic>.rs`, functions are `<subject>_<condition>_<expected>`. Root cases read the log and start children only through `tests/support/{events.rs,cli.rs,ndjson.rs,home.rs}`; no root test file defines its own reader, wait, child guard or result struct.
- **Every event kind round-trips on disk.** Per test-plan §5 Cross-module patterns → On-disk: the plan records `crates/viola-state/tests/state_events.rs` as round-tripping the 13 kinds through the crate's writer and reader with zero on all three counts, and `state_replay.rs` as the replay suite. The two new kinds join that round-trip and the replay suite gains the link cases; the plan's "13" is a count the wrap amends with its rule beside it.
- **CLI output is asserted per exit code and by line match.** Per test-plan §5 Cross-module patterns → CLI: root `tests/cli_*.rs` covers the `--json` document per exit code; human lines are matched with snapbox `[..]` redactions over timestamps and cursors (the `since` clock time of the `link` line), with no `\x1b[` under non-TTY / `NO_COLOR` / `TERM=dumb`; trycmd holds human layouts and a `viola-help` case, which two new verbs change if it exists (research's question).
- **Same verdict with and without the control.** Per test-plan §5 Cross-module patterns → CLI (`tests/cli_controls_not_disableable.rs`): a control negative is asserted as "the same verdict as without the setting". For the folded case this reads: each of `answer`, `wait`, `last`, `pause` gives under the closed gate the exit code and `--json` document it gives under an open one, asserted as literals, not merely "not 11". test-plan §4 What unit tests cover → root bin gives the two handles that need no booted pair: `answer`'s refusal order holds no budget step (human-typing → unverified-cli → unknown-dialog), and the `wait` handler returns at once when a matching record is at or after `after`.
- **Ordering without sleeps, time without a test clock.** Per test-plan §2 Agent-runnable invariants: waits key on `events.ndjson` byte offsets or `viola wait --after <cursor>`; a pending dialog for the `answer` implicit-link case comes from a committed `fixtures/fake-scripts/<scenario>.json` released through `--control` (§7 Fake agent). `since` is asserted against the `link` record's own `ts`, never against a time the test read.

## Anti-patterns to avoid
- Never hand-write `snapshot.json`, `budget.json` or `ledger/stamps.json`, and never write `events.ndjson` lines by hand in a booted-wrapper case: the E5 `link` step's log and the folded case's closed gate come from the product (the wrapper, `viola hook statusline`, `viola verify`); a reader's own unit cases may alter only bytes the writer wrote (per test-plan §11 Test Anti-Patterns → Test Data).
- Never take the product's own tables as the oracle: the kind names `link` / `unlink`, the `data` keys `driver` / `driven`, the refusal strings and the exit codes are literals in the test, compared on the serde kebab-case value and the integer exit code, never a `Debug` string (per test-plan §11 Test Anti-Patterns → Unit).
- Never synchronise with `sleep(N)` or judge by a test-owned timer; a root case may block on the product's own `wait --timeout-ms` only when the verdict is the product's exit code or status field and the same deadline is clock-driven in a §4 unit case (per test-plan §11 Test Anti-Patterns → Universal).
