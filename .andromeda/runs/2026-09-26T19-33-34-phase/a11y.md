# a11y extract

## Relevance
Partial and peripheral. The chunk has no UI surface and triggers no WCAG SC. It does edit `ci.yml`, the harness `gate` and the secret-scan scope, and those sit next to a11y's CI-gate invariants, which must not regress.

## Constraints
- a11y §9 Pipeline integration (as amended 2026-09-24-supply-chain-and-workflow-gates) requires the a11y leg to stay in the one push/PR workflow `ci.yml`, on the ubuntu leg only. Any restructuring of the mutation leg or the `mutants-verdict` union job must leave the ubuntu leg's order intact: lint step, then `run --browser`, then `gate --require playwright`, then the `if: always()` aggregation step, then the `if: always()` upload step. Whether `ci.yml` already carries these a11y steps is research's question.
- a11y §3 CI integration and §11 CI require `gate --require playwright` to stay unchanged, with skips never allowed. The chunk's `gate --mutants-legs` union change must not add a `suite` value or change how `gate` treats the `playwright` suite.
- a11y §10 Standard+ invariants require the CLI output-discipline invariants (P4, P6) to pass on all three OS legs "under the tests' mutation gate where they live in crate tests". The per-leg union may reclassify a mutant as not-a-survivor only where it is unviable on the leg that compiles its code. A mutant missed on the compiling leg must stay a survivor, so these invariants keep their mutation coverage.
- a11y §10 Build/deploy failure conditions (the unscrubbed token, `Cookie`, `?t=`, absolute path or `CLAUDE*` bullet) and a11y §3 Structured violation JSON schema → Scrubbing require a11y artifacts to stay free of the token, `?t=` and similar values. The fixture's `scrub-leak` check enforces this, and it is separate from `secret-scan`. Narrowing `secret-scan` to exclude stale `target/agent-run` mutation residue must not be read as covering, or replacing, the a11y scrub. Whether `secret-scan`'s scope includes `e2e-web/test-results/` at all is research's question.
- a11y §10 always-required invariant and §11 SLO require no retry-once policy and no soft gate. Per a11y §11 CI ("a11y is FAIL-fast gate"), no change to CI job dependencies may downgrade the a11y gate to a warning.

## Patterns to follow
- a11y §9 Aggregation row and §3 Bootstrap phases → a11y-ci-gate-wire: post-gate reporting steps run with `if: always()`, so they still report after a failed gate. This is the model if the union `mutants-verdict` job gains reporting or upload steps.
- a11y §3 CI integration: every check goes through the 5-command harness discipline (`scripts/agent-run.* run` then `gate --require …`), with no second driver and no new `suite` enum value. The union verdict should stay inside `gate`, not become a side script.
- a11y §3 Structured violation JSON schema → Scrubbing: a detected leak writes a row naming the attachment and JSON path of the match, never the matched value. This is a useful precedent for how the kept planted-secret red test and the secret-scan findings should report hits.

## Anti-patterns to avoid
- a11y §11 CI: NEVER add a `suite` value, a `webServer` or a separate driver outside `scripts/agent-run.* run --browser`. NEVER run `--browser` on the Windows or macOS legs. NEVER treat `browser-missing` as a skip. This matters if the mutation-leg matrix or job wiring is refactored.
- a11y §11 SLO: NEVER define a soft gate or a retry-once policy. The union rule must not turn into "red only if every leg missed" for mutants on code that one leg compiles.

## Contract bindings
- a11y ↔ tests: a11y §10 Standard+ (CLI output-discipline under the tests' mutation gate) binds to test-plan's mutation-gate rule, which this chunk amends. The test-plan wrap amendment that states the chunk-base rule and the per-leg union must keep "missed on the compiling leg = survivor".
- a11y ↔ tests §9 (CI a11y gate in the same workflow): `ci.yml` edits to the mutation leg (the `AGENT_RUN_CHUNK_BASE` derivation) and to the secret-scan step share the workflow with the a11y ubuntu steps.
- a11y ↔ security (secret-scan): the a11y `scrub-leak` check (a11y §3 Scrubbing) and the chunk's secret-scan scope are two separate token-leak guards. The chunk sets only the latter's scope.
