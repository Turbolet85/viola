# layouts extract

## Relevance
partial — the chunk touches two cli-surface outputs (`viola verify`'s step lines and `viola send`'s `unconfirmable` mirror line) and, at most, the web readback box's `unconfirmable` state; it creates no new surface, screen, region, focusable element, modal or breakpoint.

## Constraints
- `viola verify` output is one appended stdout step line per ledger row, `[NN/MM] <row id> <row words>  pass|fail`, in ledger order, with `MM` growing as owning chunks land their rows, closed by the `stamped <ver>  <n> pass  <m> fail` summary as the last stdout line; plain ASCII, no colour, no progress bar, no redraw, and `--record` adds no human line (per layout-templates §Surface: cli › Output structure — `viola verify`). W1/W3/W4's new `LedgerRow::ALL` rows therefore each need a stable row id and row words, and the counter moves off `/06`; the six named rows in the plan's ledger-order list are the "today" set, so the new rows' ids and their order are this chunk's to fix (whether the code's step-line renderer derives `MM` from `LedgerRow::ALL` or hard-codes it is research's question).
- `viola verify` exit codes: 0 when every row passes, 1 on a failing row or a refusal, and the stamp is still written on a failing row (per layout-templates §Surface: cli › Output structure — `viola verify`). A screen row that fails on 2.1.288 is a `fail` step line plus a written stamp, not a refusal.
- `viola verify`'s refusals are fixed-message `unable: <text>` / `hint: <text>` pairs with no name, path or pid; the existing pair `a recorded payload still holds a path or a username` / `record with a viola home under your user home` is the plan's form for the `--record` scrub refusal (per layout-templates §Surface: cli › Component — Primary content block 2). The new screen-text fixture class (W1 `--record`, refused whole if a path or username survives) should reuse that pair or add a sibling fixed pair in the same form; any new verify refusal (e.g. the live leg refused under `CI`) needs its own fixed `unable:` / `hint:` pair, and a failed or panicked verify prints exactly `error: internal error` once with no hint.
- `viola send`'s unconfirmable outcome is `[  ] unconfirmable  <name>  local command, no measured post-condition` on stdout, exit 0, the box never filled, the word padded into the same column as `open` / `read back` / `unable` so NAME starts in the same column; the TTY-only issue line `[  ] open …` stays above it on stderr and is dropped when stdout is piped (per layout-templates §Surface: cli › Output structure — `viola send` and Component — Hero / signature output line).
- Under `--json` the unconfirmable outcome is only the typed document `ok` with `confirmed:false` + `unconfirmable` (with `cursor` per the chunk scope), no glyph, no hint, no issue line (per layout-templates §Surface: cli › Component — Hero / signature output line › Machine view).
- Colour stays reserved: the mirror is words and brackets only, `unconfirmable` takes no colour, `fail` in verify is never coloured (per layout-templates §Surface: cli › Component — Hero / signature output line › Colour, and Output structure — `viola verify`).
- The human output is a contract LLM drivers may read: new fields go into `--json` first, and the readback vocabulary (`open`, `read back`, `unable`, `unconfirmable`) is shared across surfaces (per layout-templates §Surface: cli › IA notes).

## Patterns to follow
- The existing six-row step-line pattern and summary line in `viola verify` (per layout-templates §Surface: cli › Output structure — `viola verify`) — extend it row by row; it is the project's only progress pattern (§Surface: cli › Primary screens).
- The `[/ ] unable` mirror line already shipped for `send` (per layout-templates §Surface: cli › Output structure — `viola send`) — the `[  ] unconfirmable` line is its sibling in the same padded word column, on stdout instead of stderr.
- The fixed `unable:` / `hint:` refusal pairs of verify (per layout-templates §Surface: cli › Component — Primary content block 2) — the template for any new verify refusal.
- Web readback box `unconfirmable` state: the open drawing, never filled, word `unconfirmable` (per layout-templates §Surface: web-spa › Component — Hero / signature section) — applies only if this chunk makes an unconfirmable send visible on the tape; whether an unconfirmable outcome emits an event the page renders is research's question.

## Anti-patterns to avoid
- No spinner, progress bar, elapsed counter, `✓`, `done` or redraw — neither while the live PTY probe waits for captures/quiet in `verify`, nor on `send` (per layout-templates §Surface: cli › Output structure — `viola verify` and Component — Hero / signature output line › What never happens).
- No path, username, pid, upstream text or screen content in any human line or hint — a recorded screen row's text never reaches a verify step line or refusal (per layout-templates §Surface: cli › Component — Primary content block 2 › Hint line).
- No `turn-ended` as a send outcome, and no colour on `unconfirmable` / `read back` / `unable` (per layout-templates §Surface: cli › Component — Hero / signature output line).

## Contract bindings
- layouts ↔ tests: the verify step-line format `[NN/MM] …  pass|fail` and the summary line are what a CLI test asserts once `MM` grows past 06; the `send` unconfirmable line and its exit 0 bind to the `send_window_local_command_is_not_presumed_delivered` test the scope says changes here (per layout-templates §Surface: cli › Output structure — `viola verify` / `viola send`).
- layouts ↔ security: the no-path/no-username rule on verify's human lines binds to the security plan's NEVER-log floor for recorded screen text (per layout-templates §Surface: cli › Component — Primary content block 2).
- layouts ↔ web-spa: the shared `unconfirmable` readback vocabulary binds the CLI mirror to the web box state, if the chunk surfaces the outcome on the tape (per layout-templates §Surface: cli › IA notes › Multi-surface coordination).

## Acceptance criteria contributions
- `viola verify` against a stamped CLI prints one `[NN/MM] <row id> <row words>  pass|fail` line per `LedgerRow::ALL` entry, with `MM` equal to the new row count (not 06), in ledger order, then `stamped <ver>  <n> pass  <m> fail` as the last stdout line, with no colour and no redraw (per layout-templates §Surface: cli › Output structure — `viola verify`).
- A failing new row exits 1 and still writes the stamp; a scrub failure on a recorded screen fixture prints a fixed `unable:` / `hint:` pair naming no path, username or pid (per layout-templates §Surface: cli › Component — Primary content block 2).
- `viola send` of a ledger-listed local command prints `[  ] unconfirmable  <name>  local command, no measured post-condition` on stdout with exit 0, its word aligned with `open` / `read back` / `unable`; with `--json` it prints only the `ok` document with `confirmed:false` and `unconfirmable` (per layout-templates §Surface: cli › Output structure — `viola send` and Component — Hero / signature output line).
