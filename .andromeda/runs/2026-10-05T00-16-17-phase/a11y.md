# a11y extract

## Relevance
partial — no web-spa surface; the chunk touches two cli surfaces a11y asserts for output discipline (the `viola verify` step lines, whose row count grows, and `send`'s new `unconfirmable` outcome and its mirror line) plus the tui/screen boundary (R7) that verify's new PTY child and screen fixtures come close to. No WCAG conformance claim applies (per a11y-plan §1 → CLI and terminal entities).

## Constraints
- `viola verify` is a P6 cli surface. Its output must stay linear and static: `[NN/NN] … pass|fail` step lines, with no `\r` redraw, cursor movement, erase sequence or spinner while the live PTY probe runs under its bounded deadline. The growing `LedgerRow::ALL` changes the `NN` total (today `/06`), and the line shape must hold at the new count (per a11y-plan §4 P6; §1 → A11y Scope Summary, cli surface notes "output is static and linear, with no spinner or redraw").
- verify's PTY child is internal to the probe. Its screen bytes (the `claude` TUI) are not viola output, and §1 requires verify's own stream to carry only viola's step lines. Whether the probe's child output can reach verify's stdout or stderr is research's question (per a11y-plan §1 → cli surface notes; §1 → tui entity, boundary "viola writes zero bytes to the terminal except the child's output", which covers `run` only).
- State is carried by the printed word, and colour is at most a second cue. `pass|fail` and the new `unconfirmable` outcome must be readable as words. `fail` and `unable` carry no SGR. viola emits no SGR, glyph or cursor control under `--json`, non-TTY, `NO_COLOR`, `TERM=dumb` or `viola run` (per a11y-plan §6 → State color tokens (not-color-alone), "CLI equivalent"; §11 Visual).
- `send`'s `ok {confirmed:false, detail:"unconfirmable"}` is the cli half of P2 (`[RB]` mirror). The mirror line must state `unconfirmable` in text. That word is one of the closed state words a11y asserts across surfaces, and it must match the web readback word for the same state (per a11y-plan §4 P2 "cli: `[RB]` mirror …"; §3 WCAG criteria mapping → SC 1.4.1 row and SC 3.2.4 row).
- C0/C1 escaping covers any upstream text the new paths print to a human (for example a local-command or dialog field echoed by `verify` or `send` in human mode): escaped except `\n` / `\t` (per a11y-plan §1 → cli surface notes; §4 P6 C0/C1 bullet).
- The screen recording, the input-box/modal signatures and the screen fixtures serve readiness only. They must never become a content read or a11y evidence (per a11y-plan §11 Universal, R7 ban; binds to architecture [Screen Model] "Never used to read content").

## Patterns to follow
- Output discipline on cli is asserted with the tests' existing drivers: trycmd / assert_cmd for non-TTY and `--json`, and the portable-pty outer PTY for TTY-only behaviour, on all three OS legs. There is no a11y tool and no a11y JSON for cli (per a11y-plan §1 → A11y testing tool pick, "cli / tui"; §3 Structured violation JSON schema → "cli / tui": failures surface only as nextest failures).
- The `verify` step-line pin is the P6 `[NN/NN] … pass|fail` assertion. Re-pin the counter at the new row total rather than loosening the shape (per a11y-plan §4 P6).
- A send outcome renders the same word on the cli mirror and wherever the web readback shows that `corr` (`open` / `read back` / `unable · …` / `unconfirmable`) (per a11y-plan §4 → Per-component pattern catalog, Transfer marker / Readback box rows; §11 Cognitive, SC 3.2.4 ban).

## Anti-patterns to avoid
- NEVER parse the rendered `claude` TUI screen for content, and never take screenshots or the recorded screen fixtures as a11y evidence (per a11y-plan §11 Universal, R7).
- NEVER colour CLI `unable` / `fail`, and never emit SGR under non-TTY / `NO_COLOR` / `TERM=dumb` / `--json` / `viola run` (per a11y-plan §11 Visual).
- NEVER let a kebab-case code (here `unconfirmable`, `not-delivered`, `no-prompt-submitted`) be the only text without its plain word. A human-mode refusal ends with a `hint:` line (per a11y-plan §11 Cognitive). `unconfirmable` is an `ok` outcome, not a refusal, so the `hint:` rule does not cover it. Whether design gives it a plain-language line is design's call.

## Contract bindings
- a11y ↔ tests: the P6 / P2 cli checks are nextest / trycmd cases in the tests harness (`nextest-integration` / `nextest-e2e`, CI per-OS `test` job), not an a11y suite (per a11y-plan §3 Structured violation JSON schema → "cli / tui"; §1 → Bootstrap, "CLI output discipline runs inside nextest-integration / nextest-e2e").
- a11y ↔ architecture / tests (R7): the screen model is a readiness gate only (architecture [Screen Model]), and tests ban parsing the child screen for content (test-plan §11). This chunk's screen recording and fixtures must stay on that side of R7 (per a11y-plan §11 Universal).
- a11y ↔ design: the `unconfirmable` word and the cli `[RB]` mirror form come from design's cli surface and state words. a11y asserts only that the word is present and that colour is secondary (per a11y-plan §6 → State color tokens).
- a11y ↔ web-spa P2: if the `unconfirmable` outcome reaches the GUI tape as an event, the `a11y-p2` readback-`unconfirmable` state (axe verdict plus the word in the accessible name) applies there. Research must answer whether the web readback surface exists at HEAD and whether this chunk's event reaches it. The scope names no web surface (per a11y-plan §4 P2 Tests).

## Acceptance criteria contributions
- (a11y) `viola verify` human output, under non-TTY and under the outer PTY, is one `[NN/NN] <row> pass|fail` line per row at the grown row total. It has no `\r` / cursor / erase sequence, no SGR on `fail`, and no SGR under `NO_COLOR` / `TERM=dumb` / non-TTY. None of the probe child's screen bytes appear on verify's stdout or stderr (per a11y-plan §4 P6).
- (a11y) A `viola send` of a ledger-listed local command prints the `unconfirmable` word on its readback mirror in human mode (no SGR off-TTY). Its `--json` result carries `detail:"unconfirmable"` with no SGR or control bytes (per a11y-plan §4 P2 "cli"; §6 → State color tokens, CLI equivalent).
- (a11y) No new test or verdict reads the rendered `claude` screen for content. The screen fixtures feed only the readiness signature rows and are never cited as a11y evidence (per a11y-plan §11 Universal, R7).
