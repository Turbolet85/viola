# obs extract

## Relevance
partial — the chunk adds a third `verify` child spawn (the PTY probe), recorded screen text, and the `send` `unconfirmable` outcome, each of which has an obs logging contract. The probe's measurements themselves are ledger/arch content, not telemetry.

## Constraints
- **Spawn subject is a closed enum.** obs-plan §6 (Boundary-call wrappers → Child / shell spawns) closes `subject` in `schemas/diag-line.v1.json` `$defs.subject.enum` as `self|claude-child|version-probe|verify-probe|agents-probe|statusline-shell`. §6 and §4 (Edge flows → `verify` / `plugin install`) define `verify-probe` as "the print-mode probe" and say verify logs exactly "two child spawns". A PTY-driven typed-input child therefore needs one of two things: a new `subject` value, or a redefinition of `verify-probe` covering both probes. Either way it is a `diag-line.v1.json` change plus an obs Decisions Log entry, using the D-35 / D-36 amendment as the template (§8 Default-deny posture; §11 Logs "NEVER … add `event` values without a Decisions Log entry"). This is the scope's open crossing (3), and it has to be ruled before the build.
- **Each verify spawn is a logged pair.** When `VIOLA_NAME` is set, each spawn writes `process-start{subject}` / `process-exit{subject, child_exit_status, duration_ms}` at the call site, between verify's own `self` pair, into `cli-<name>.ndjson`. `run_bounded` stays unlogged (§4 Edge flows `verify`; §6 Child / shell spawns, D-35). If verify ends the PTY child by kill, `exit_source` (`handle-wait|kill-fallback`) is the catalogued field that records it (§6 Additive field catalog, `process-exit`). Whether the schema admits `exit_source` on a verify subject is research's question.
- **R8 fields if the strip applies.** If the R8 strip is ruled to apply to verify's PTY child (the scope's open sub-question (1)), the strip is logged by names only: `env_stripped_count`, `env_stripped_known` and `env_kept`, never values, and no env map passed to a span or event (§4 Edge flows E2; §8 table, `CLAUDE*` row; D-34). The §6 catalog scopes these fields to `claude-child` today. Carrying them on another subject is the same schema-plus-Decisions-Log change as the first constraint.
- **Screen text never becomes telemetry.** Screen content is never a telemetry source (§11 Telemetry Strategy "NEVER derive telemetry from screen content"; §10 Deterministic emission). It must not reach a home-level line. It must not reach a `detail-*.ndjson` line either, because `diag-detail.v1.json` admits only `panic_payload`, `backtrace`, `chain` and `drift_report` (§8 Detail-file scope). Recorded screen fixtures are classed "scrub-required (security/tests-owned)", and obs adds no fixture content (§8 table, Recorded fixtures row).
- **Spans and gates for the new code.** The verify drive sits under the existing spans: `cli.verify`, `cli.verify_step` per step, and `state.ledger_write` for the stamp (§4 Edge flows `verify`). Any new span is static `<area>.<operation>` with `#[instrument(skip_all, fields(...))]`: no bare `#[instrument]` (G1), no `err` / `ret`, and no paste text, prompt or screen bytes in fields (§4 Span naming convention; §11 Spans / Traces). The PTY output reader and the quiet-period wait get no per-chunk span or event (§11 Telemetry Strategy, over-instrumenting hot paths; §11 Logs, no `info` in hot loops).
- **`unconfirmable` uses the existing line.** `send`'s `unconfirmable` outcome is logged as `send-confirmed{corr:<cursor>, confirmed:false, duration_ms}` plus the wrapper's `conn` / `srv_conn` and `rpc_id`. It is not a new event or detail value (§4 Scenario "Confirmed `send` (CL-1)"; §4 Frontend observable boundary `<viola-readback>`; §5 `viola.send.outcome`). The local-command text never appears, only `text_bytes` (§8 table, prompt-text row).
- **Live leg stays out of CI.** The real-`claude` verify never runs in CI. It runs only through the local `run --local-live`, which refuses under `CI` (`live-in-ci`). In CI, verify runs against the fake agent at a recorded version, and its home-level lines fall under G2, G4 and the secret scan like any other (§4 Edge flows `verify`; §9 Pipeline integration).

## Patterns to follow
- **D-35 / D-36 amendment shape.** One Decisions Log entry, the closed value added to `diag-line.v1.json` (`$defs.subject.enum` or the event's property list), the §4 / §6 bullets updated together, and `tests/contract_diag_schema.rs` kept green (§6 Child / shell spawns; §8 Default-deny posture; obs-plan-amendments.md `2026-09-29-verify-stamped-test-homes-and-harness`).
- **Instrument the spawn at the call site, as verify already does.** verify logs each spawn pair at the call site, with no logging inside the shared spawn helper (§4 Edge flows `verify`). The PTY seam itself logs paste as `text_bytes` only (§6 Boundary-call wrappers → PTY seam).
- **vt100 panics, if verify feeds the screen model.** Use the `run` feed-thread discipline: `catch_unwind` around each feed, with one `parse-rejected{parser:"vt100-feed", detail}` per poisoning episode at `WARN` (§7; §6 `detail` code catalog). Whether verify reuses `src/run/gate.rs`'s feed or adds a second one, and whether a `cli`-process emission of that line conforms to the schema, is research's question.
- **Use existing `send` events.** The new `send` outcome and the `/clear` new-session post-condition go on the existing `send-issued` / `send-confirmed` / `send-refused` lines, joined by the cursor in `corr` (§4 Scenario CL-1; §10 Correlation propagation).

## Anti-patterns to avoid
- **No screen text in logs.** Never log screen text, the typed `PROBE_PROMPT`, a captured hook payload, a fixture body or a probe-dir path, at any level or in any file (§11 PII Scrubbing; §11 Telemetry Strategy). The probe dir `ledger/probes/<pid>/` and the capture paths are paths, so they stay out of home-level lines and out of `detail` codes (§11 PII Scrubbing "NEVER put paths or pids inside `detail` codes").
- **No uncatalogued values.** Never emit a `subject`, field or `detail` value that is not in the §6 catalog without its Decisions Log entry and schema change. G4 fails on it as a build failure (§8 Default-deny posture; §10 Build / deploy failure conditions).
- **No stdout telemetry.** Never write telemetry to stdout. verify's stdout carries only the `[NN/MM] … pass|fail` step lines and the `stamped <version>` line (§11 Logs; §4 Edge flows `verify`).

## Contract bindings
- **obs ↔ tests.** `tests/cli_verify.rs` and the `stamped_home` fixture assert verify's spawn pairs and its only-writer role on `ledger/stamps.json`. G4 / `tests/contract_diag_schema.rs` validate any new `subject` value. Verify test homes under `target/e2e-home/` are covered by G2, G4 and the secret scan (§4 Edge flows `verify`; §9 Pipeline integration).
  - Drift to flag: §4 says CI verify runs "only against the fake agent's print mode". If the fake agent replays the recorded screen through an interactive leg, that wording needs an amendment.
- **obs ↔ security.**
  - The scrub of recorded screen fixtures (paths and username, refused whole if either survives) is security/tests-owned (§8 table, Recorded fixtures row).
  - The NEVER-log floor for R8-stripped values and for screen content in every sink (§8 table).
  - The open R8-on-verify ruling decides whether the E2 strip fields appear on the new spawn.
- **obs ↔ design-system / arch.**
  - verify's step-line counter `/MM` grows with `LedgerRow::ALL` (§4 Edge flows `verify`).
  - The `unconfirmable` readback word maps to `send-confirmed{confirmed:false}` (§4 Frontend observable boundary).

## Acceptance criteria contributions
- (obs) With `VIOLA_NAME` set, `viola verify` writes one `process-start` / `process-exit{child_exit_status, duration_ms}` pair per child spawn into `cli-<name>.ndjson`, including the PTY probe, and every line passes G4 against `schemas/diag-line.v1.json`. The PTY probe's `subject` value is either already in `$defs.subject.enum` or added there under an obs Decisions Log entry (per obs-plan §6 Boundary-call wrappers → Child / shell spawns, D-35).
- (obs) No screen text, `PROBE_PROMPT`, captured payload or probe path appears in any `diagnostics/*.ndjson` (home-level or detail) after a fake-agent verify run. The secret scan's canary check stays clean (per obs-plan §8 Integration points item 6; §11 Telemetry Strategy).
- (obs) A `send` of a ledger-listed local command logs `send-confirmed{confirmed:false}`, carrying the cursor in `corr` and the wrapper's `conn` / `rpc_id`. It logs no `send-refused{detail:"no-prompt-submitted"}` (per obs-plan §4 Scenario "Confirmed `send` (CL-1)").
- (obs) Every new `#[instrument]` in the chunk passes G1 (`skip_all` first). G2 reads zero panics over the verify test homes (per obs-plan §9 Gate commands G1 / G2).
