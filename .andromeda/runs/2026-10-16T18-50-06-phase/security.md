# security extract

## Relevance
relevant — the chunk lands the plan's owed `claude agents --json` child spawn (a named Threat Model vector and Input Validation boundary), prints its untrusted rows to a terminal and to `list --json`, adds a `viola revive` preflight refusal, a recorded fixture and possibly a capability-ledger row that gates dialog answering.

## Constraints
- The `claude agents --json` read is a child process spawn resolving `claude` from the calling process's own PATH; security-plan §Threat Model Summary (Vector: Child process spawning and PATH resolution) names `list` as this spawn's owner and marks it owed to this entry; the trust boundary is "whatever the calling process's PATH resolves to", with output parsed tolerantly and failure becoming `unknown`.
- security-plan §Input Validation (Child executable resolution row) requires `list` to join `run`'s resolution rule when this entry lands: a direct spawn of a resolved real `.exe` (on Windows a `claude.cmd`/`claude.bat` only through the fixed `node_modules/@anthropic-ai/claude-code/bin/claude.exe` sibling, the shim never read; any other batch script is `Refusal::BatchScriptChild`), never through a shell. Whether `list`'s refusal of a batch-script child should be a `list` exit change or degrade to `unknown` is not stated by the plan for `list` (the row's exit-1 shape is `run`'s) — a P4 question.
- security-plan §Input Validation (Child process output row) requires the agents output read through `Read::take(MAX_FRAME)` and a tolerant parse whose failure becomes `unknown`, and that an unwrapped row's `name` is never a `ViolaName` and never a valid `target`; the parser lives in `viola-agent-claude` on std `process::Command` (the row's "How" column). The plan's §Input Validation Constants paragraph bounds the `--version` child reads at 5 s with stdout and stderr drained through the cap, but states no time bound for the agents read — the bound the scope infers is not yet a plan mandate (P4 / plan amendment).
- security-plan §Bootstrap phases (`logging-redaction-wire`) requires human-mode `list` rows to escape every control character (`\n`, `\t`, DEL and C1 included) as `\xHH` through `escape_row`, so each row stays one line, and names the fields taken from `claude agents --json`, unwrapped session names included, as taking the same escape when these rows land.
- security-plan §Input Validation (Session id as a child argv value row) requires that no `viola revive` refusal line or hint hold the recorded directory, a pid or a logged id — the new `session-live` refusal's `unable:` / `hint:` pair included; revive's strict-modes check on the instance's files stays ahead of every snapshot or log value use (§Input Validation, CLI arguments row, `revive` arguments).
- security-plan §Data Protection (Repository fixtures) requires the recorded `claude agents --json` fixture under `fixtures/claude/<cli-version>/` to come from `viola verify --record` with synthetic prompts only, scrubbed (home prefix → `~`, the user word → `<user>`) and refused whole on a surviving `home-path` · `absolute-path` · `username` · `email`; the agents rows' `cwd` field is an absolute path the scrub must rewrite or refuse.
- security-plan §Security Anti-Patterns (Universal, the ledger bullet) ties dialog answering to a `viola verify` stamp over `LedgerRow::ALL` (twenty-two rows); a new join-field row that joins the relied set leaves every earlier-stamped home `cli_verified:false`, switching non-`null` dialog decisions off until re-verified, and `ledger/stamps.json` stays written only by `viola verify`.

## Patterns to follow
- `run`'s program resolver (`viola-agent-claude::resolve_program` + `src/run/mod.rs::resolve_program`) as the one resolution path for the agents spawn (per security-plan §Input Validation, Child executable resolution row).
- `MAX_FRAME` reads with tolerant-parse-to-`unknown`, as on the `--version` child reads (per security-plan §Input Validation, Constants).
- `escape_row` (`src/human/escape.rs`) for every printed field of an agents row (per security-plan §Bootstrap phases, `logging-redaction-wire`).
- Revive's fixed `unable:` / `hint:` refusal pair, exit 1, no child, with no path, pid or id in it (per security-plan §Input Validation, Session id as a child argv value row).
- A new parser surface gets fuzz coverage inside the separate `fuzz/` workspace, never linked into `viola` and never joining the root `[workspace]`, its `fuzz/Cargo.lock` audited for advisories and sources (per security-plan §Input Validation, Parser surfaces; §Dependency Security, the `fuzz/` exemption). The plan's exemption text names the fuzz crate's path dep as `viola-core`; whether `fuzz/Cargo.toml`'s current path deps already reach the crate the parser lands in is research's question.

## Anti-patterns to avoid
- NEVER use a `claude agents --json` row `name` as a `ViolaName` or `target`, nor join it into `instances/<name>` (per security-plan §Security Anti-Patterns, Input).
- NEVER print `list` rows taken from `claude agents --json` to a terminal without escaping C0/C1 controls (per security-plan §Security Anti-Patterns, Logging).
- NEVER spawn the agents child through sh/bash/cmd or as a `.cmd`/`.bat` — `statusline_command` stays the only shell-out (per security-plan §Security Anti-Patterns, Code Patterns; §Security Anti-Patterns, Data Protection).

## Contract bindings
- security ↔ capability ledger / `viola verify`: the join-field row and its probe extend verify's child set, which security-plan §Threat Model Summary (Child process spawning vector) enumerates run by run (five interactive children, seven spawn pairs per uninterrupted verify), each tied to a founder ruling; a probe that adds a child or a live start changes that enumeration (P4 ruling, per the scope §4).
- security ↔ R8 strip: security-plan §Secret Management requires the inherited `CLAUDE*` credentials stripped from the `viola run` wrapper's child and never serialised; the plan states no strip rule for `list`'s or revive-preflight's `claude agents --json` child, and whether that child runs under the R8 strip (and whether the strip changes what `claude agents` reports) is a P3/P4 question, not a plan mandate.
- security ↔ obs: pids and session ids from agents rows may go to `diagnostics/` only, never to CLI `--json` error output or channel `error.data` (per security-plan §Bootstrap phases, `logging-redaction-wire`); the `session-live` `process-exit` detail stays a closed code (per security-plan §Error Handling).
- security ↔ tests: the agents parser is a named parser surface for property and fuzz coverage (per security-plan §Input Validation, Parser surfaces); the fake agent's recorded agents fixture binds to the `--record` scrub (per security-plan §Data Protection, Repository fixtures).

## Acceptance criteria contributions
- An oversize (over `MAX_FRAME`), malformed, absent or failed `claude agents --json` read leaves every wrapped row `unknown`, lists no unwrapped row, and does not change `list`'s exit (per security-plan §Input Validation, Child process output row).
- An agents row whose `name`, `cwd` or other printed field holds ESC, `\n`, DEL or a C1 control prints as one `\xHH`-escaped line on the human board, and no unwrapped row's name is accepted as a `send` / `answer` / `revive` target (per security-plan §Bootstrap phases, `logging-redaction-wire`; §Security Anti-Patterns, Input).
- The `session-live` refusal's stderr pair holds no pid, no directory and no session id, and it runs only after revive's instance strict-modes check (per security-plan §Input Validation, Session id as a child argv value row).
- The committed agents fixture passes `viola verify --record`'s scrub with no `home-path` · `absolute-path` · `username` · `email` survivor, and `cargo deny --manifest-path fuzz/Cargo.toml check advisories sources` stays green with the new fuzz target (per security-plan §Data Protection, Repository fixtures; §Dependency Security).
