# viola-mcp

_Crate implementation notes. Primary source: `.andromeda/architecture.md` [MCP], §Conventions (MCP), §Standard Contracts (MCP refusal result); security §Input Validation (MCP row), §API Security (MCP transport); obs §3 (`mcp` sink, D-09). Generated by `/andromeda-setup-project`._

## Responsibility
The stdio MCP server `viola mcp` (rmcp 3.4.1, features exactly `server` + `transport-io`, spec 2026-07-28): a thin adapter that maps tools `send · wait · last · answer · list` onto the wrapper channel (Tokio client) and onto the caller-side `list` board (`list::board_document`, the provider `viola mcp` hands `viola_mcp::serve`, one `claude agents --json` read per call, the board's refusal returned as `instance-unreachable`). It adds `from` from its own `VIOLA_NAME` only when it has a name of its own. It is the only crate allowed to build a Tokio runtime.

## Key integrations

### Consumes from
`viola-core`, `viola-channel[tokio]`, `viola-state`, `viola-agent-claude`; rmcp (default features off; `server` + `transport-io`), schemars 1.2.2, tokio 1.53.3 (`rt`), serde_json, thiserror, tracing (no serde); `[lints] workspace = true`; `fake-agent = []`.

### Publishes to
Claude Code driver sessions (the MCP client) via the embedded `.mcp.json`, which registers the server `viola` as `{"mcpServers": {"viola": {"command": "@@VIOLA_BIN@@", "args": ["mcp"]}}}`, the pinned copy's absolute path substituted at every start, and, for an unwrapped driver, the `.mcp.json` of `viola plugin install`'s local marketplace (`viola@viola`, no hooks), which registers `viola` as `{"command": <the canonical current_exe, forward slashes>, "args": ["--home", <the canonical home, forward slashes>, "mcp"]}`; the tools reach a session as `mcp__plugin_viola_viola__<tool>` (as measured live on claude 2.1.287). A wrapped session that also has the installed plugin enabled starts one `viola` MCP server, the `--plugin-dir` plugin's, which answers its tools; the installed plugin's `viola mcp` never starts there (as measured on claude 2.1.287 on the Linux dev host; no capability-ledger row; its Windows leg owed to "Windows-only live measurements").

### Dependencies
Tokio allowed: `viola-mcp` is never a root of the `deny-sync.toml` tokio ban, which runs only for the crates in `scripts/sync-crates.txt`.

## Internal conventions
- Tool inputs: `send {target, text}`, `wait {target, after?, timeout_ms?}`, `last {target}`, `answer {target, dialog_id, response}`, `list {}`. `release`, `pause`, `link`, `unlink` are CLI-only (an affordance, not enforcement).
- schemars schemas are advisory: each handler re-validates its raw argument object (`target` through `ViolaName::try_new`, `text` a string, `after` / `timeout_ms` absent, `null` or a `u64`, `dialog_id` a `u64`, `response` an object through `Response::parse`), a failure being an `isError: true` result `{"error":"invalid-params","detail":"<field>"}` (closed field words `target` · `text` · `after` · `timeout_ms` · `dialog_id` · `response`) with no frame written, and run `validate_paste_text` on `text` and free-text answers.
- Success = `isError:false` + the channel `ok` payload as `structuredContent`; refusal = `isError:true` + `{refusal, detail}` + text `refused: <reason>`; unreachable / fault = `isError:true` + `{"error":"instance-unreachable"|"wrapper-fault","detail":…}`. Every `isError` text is `refused: <code>`. JSON-RPC errors are the MCP connection's own faults, an unknown tool name (`-32602`) and an internal handler fault (any other channel error, a reply of no known shape, a `wait` / `last` refusal, a panicked call), which is `-32603` `internal error` with `data: null`.
- stdout carries MCP frames only; logs go to `<home>/diagnostics/mcp.ndjson` (stderr JSON only if the file cannot be opened) once its home and `diagnostics/` (each that exists) pass `viola_state::strict::check_path`; a refusal exits 1 with nothing on stdout or stderr and no role file, and does not block the CLI's start: the session reaches `idle` and the CLI logs that server's connection as failed (as measured on claude 2.1.287 on the Linux dev host; its Windows leg owed to "Windows-only live measurements"). The `rmcp` log target is OFF.
- MCP `wait` sends `timeout_ms` = `min(given, 50 000)` (`viola_mcp::WAIT_CAP`, `wait_timeout`), 50 000 ms when none is given, and `after` as given: below claude 2.1.287's stdio tool-call default, which exceeds 50 s (as measured live; the exact default unmeasured).

## Crate-specific gotchas
- `tools/list` must be exactly the five tools — the MCP E2E asserts it — and its result carries `ttlMs` 0 and `cacheScope` `private`: claude 2.1.287 negotiates protocol `2026-07-28` and drops every tool of a list result without them (as measured live); claude 2.1.302 on that protocol opens with `server/discover` (its JSON-RPC id a string) and then `tools/list`, each carrying `_meta`, sends no `initialize` or `notifications/initialized`, and viola's two results each carry `ttlMs` 0 and `cacheScope` `private` (as measured live, `viola-0.1.0/chunks/2026-10-20-epoch-5-cleanup-ii/evidence/live-tap.md`).
- A main-thread panic → `process-exit{detail:"internal-error"}` then exit 1, nothing on stdout; Tokio task panics are contained.
