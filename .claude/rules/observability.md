# Observability Rules

Path-scoped rules for product code that logs, spans or handles errors. Authoritative source: `.andromeda/obs-plan.md` (tier Standard with Minimal exporter carve-outs); the log format itself is bound to `.andromeda/test-plan.md` §3.

## Pipeline
- **Library:** tracing in every instrumentable crate; tracing-subscriber 0.3.23 (`default-features = false`) as a product dependency in the root bin only (`viola-channel` and `viola-state` take it as a dev-dependency for their unit tests' line capture). No OTel SDK, no exporter, no reporter (sentry banned), no `tracing-appender`, no `metrics` instruments, no `/metrics` route.
- **Builder:** `fmt().json().flatten_event(true).with_current_span(false).with_span_list(false).with_ansi(false).log_internal_errors(false)`, `MillisUtc` timer (RFC 3339 UTC ms + `Z`), explicit writer — never the stdout default.
- **Levels:** `filter::Targets` from `config.json` `diagnostics_level` (`info` | `debug`); never `RUST_LOG` / `EnvFilter` / the `env-filter` feature. Third-party targets (`rmcp`, `portable_pty`, `sysinfo`, `interprocess`) are OFF; capture their failures from returned `Result`s at viola's seam.

## Sinks
- Codes-only role files: `<home>/diagnostics/{run-<name>,hook-<name>,mcp,cli-<name>}.ndjson`; `mcp` always writes `mcp.ndjson` (D-09), no stderr fallback (a file that cannot be opened exits 1 printing nothing), never stdout (it carries MCP frames). Content-bearing records (anyhow chain, drift report, panic payload + backtrace) only in `<home>/instances/<name>/diagnostics/detail-<process>.ndjson`, written by the root-bin detail writer, never through the subscriber.
- 0600 files in 0700 dirs; `OpenOptions::append`; one `write_all` per complete line (concurrent hook processes share a file). A failed log write is swallowed — `hook` still exits 0. `open_role_file` and `write_detail` (`src/obs.rs`) run `strict::check_diagnostics` on the existing `diagnostics/` folder and on the role or detail file before `ensure_private_dir` narrows anything (a symlink refused, a folder held to the read rule, a file to the read rule, an absent path passing): a refusal is a failed open — `viola_obs_init` returns the error and installs no subscriber (`hook` carries on writing no line, every other role, `mcp` included, returns the error) and the detail line is dropped.
- Init order: panic hook first → clap → home/instance/role → home strict-modes (create first if new) → diagnostics dir/file checks and open → `config.json` → subscriber → `process-start`. Every `viola hook` arm but the `hook <event> --capture` arm (the event and dialog paths) runs its instance check (`canonical`, then `trusted`: `check_instance`) BEFORE this init (the role-file open sets an existing home to 0700, so a check made after it passes a widened home) and a refused or absent instance (a `VIOLA_DIR` naming no existing instance directory included) writes no line and opens no role file (exit 0 at once; the event and dialog paths also read no stdin, send no frame and make no SessionEnd append); its stdout carries the decision body, never telemetry. Both `viola revive` arms (the start arm and `--list`) and `viola adopt`'s start run their instance check before the log init as well: a refused check is the stderr pair, or under `--json` the `{"v":1,"error":"strict-modes-failed","detail":null}` document, and exit 1 with no log opened. `viola link` / `viola unlink` (on `instances/<driven>`) and `send`, `wait`, `last`, `answer`, `pause`, `release`, `viola focus` and `viola switch` (on their named instance; `send` after its text read) run `check_instance` on the home and the instance through the one `client::refuse_untrusted` before the log init too: a refusal is exit 21, the fixed instance-state pair or under `--json` the `{"v":1,"error":"instance-unreachable","detail":"strict-modes-failed"}` document, with no role file opened and the directory's mode left as found. `viola run`, `viola revive`'s start arm and `viola adopt`'s start (after their instance check) run the home-tree check `strict::check_home_tree` (through `checked_exe`: the home, the `check_instance` set, `ledger/`, `bin/`, `plugin/`, `bin/<key>/`, the pinned copy, `plugin/<key>/` and its `hooks/` and `.claude-plugin/`, each that exists) before the wrapper log: a refusal is exit 1 with the home pair (the instance pair for an instance-level refusal; under `viola revive --json` or `viola adopt --json` the `strict-modes-failed` document), no log opened, no line and no child.

## Lines
- Every line goes through `obs_event!` (defined in `viola_core::obs`): it attaches `event`, `process`, `instance` (from `ProcessCtx`); the caller passes `corr` as a typed field on the events that carry one; `message` is a static literal equal to the event name. Raw `tracing::{event,info,warn,error,debug,trace}!` is banned in two halves. Clippy `disallowed-macros` (`clippy.toml`) bans the level macros by path. Raw `event!` is caught by the fail-closed grep in `scripts/lint-probes.sh`, because on clippy 1.98.1 no allow inside `obs_event!` can exempt its inner `::tracing::event!` (obs-plan §3 logger-stack-install, D-33).
- `event` is a closed kebab-case enum (`ObsEvent`): a new value needs an obs Decisions Log entry and a `schemas/diag-line.v1.json` update.
- `corr` per event (JSON-RPC `id` · `dialog_id` · send `cursor`), copied as a number or string — never `?corr` / `%corr`, never renamed. A null `corr` / `instance` is key absence, never a literal `null`.
- Channel lines carry `conn = "<process>-<pid>-<t0>-<n>"`; wrapper `send-*` lines carry `conn` + `rpc_id`; `from` is logged with `from_trust:"self-reported"`, both absent on a line whose call carried no `from` (a `dialog-answered` for an answer that carried none, as on the hold's expiry line). On Unix a peer the wrapper's `accept_loop` refuses by euid (`peer_admitted`) is dropped on the accept thread, before its worker thread and before any frame, and writes no line by rule (no frame to key a line on); the client reads end-of-file.
- Log only fields named in obs-plan §6 (default-deny, enforced by G4). `detail` codes are closed kebab-case lists — never a path or pid. The session id an operator types to `viola adopt` never appears in any line, field or detail. `schemas/diag-line.v1.json` closes `process-exit`'s; `viola focus` ends exit 1 with one `process-exit` detail: `window-not-found` (nothing dispatched), `unsupported` (no hyprctl reachable, nothing spawned), `unreachable` (hyprctl reachable, no compositor answering), or the hyprctl seam's `oversize`, `malformed` or `refused`; exit 21's closed causes are `instance-dead`, `unwrapped-name`, `endpoint-lost`, `strict-modes-failed`, `server-verify-failed`, `socket-dir-refused` (`during` `call` for `endpoint-lost` alone; `instance-dead`, `unwrapped-name`, `server-verify-failed` and `socket-dir-refused` are `during` `connect`), and `stale-heartbeat` is exit 1's cause alone (a frame verb against a stale instance reads `instance-dead`). `channel-response` carries `detail` on a `-32602` only (`unsupported-version` · `invalid-params` · `release-from-driver`, from `ProtocolError::cause`, on the server's and the client's line alike, closed by `schemas/diag-line.v1.json`) and none on any other `channel-response` line, a refusal's included, whose own `detail` stays on `send-refused`. A hyprctl reply that is oversize or malformed gives one codes-only `parse-rejected{parser:"hyprctl-json"}` line, written by the Hyprland seam (never `unknown`). A StopFailure error word outside the CLI's 13 writes one WARN `parse-rejected{parser:"hook-stdin", detail:"unknown-value", count:1}` (code and count only) and the event is still delivered as a turn end with cause `api-error`; a known word writes no line.

## Spans
- `#[instrument(skip_all, name = "<area>.<operation>", fields(..))]` or `info_span!` with an explicit field allow-list only — never bare `#[instrument]` (gate G1), never `err` / `ret` on anything that can carry a serde source or user content. Span names are static; no instance names, ids or paths.
- Spans are not serialized: pass `corr`, `conn`, `instance` as explicit values into threads/tasks.

## Panics and errors
- `panic = "unwind"` in every profile (gate G3). The panic hook writes one line to the role file (no stderr, never the default hook); `catch_unwind` at the main-thread catch site, around `hook` dispatch, the three `run` PTY threads (the two pump copy threads and the paste writer thread) (the child's exit is polled inline on run's main thread, under main's catch site), and the vt100 feed.
- `hook` → exit 0, empty stdout; `cli` → `process-exit{detail:"internal-error"}` when an instance resolves, then exit 1 with exactly `error: internal error` (no hint), or under `--json` (read from argv before any `--`) the `{"v":1,"error":"internal-error","detail":null}` document on stdout with stderr empty; `run` → `process-exit{detail:"internal-error"}` (the catch site prints nothing; under `viola revive --json` an anyhow error from `trusted`, `checked_exe`, `open_wrapper_log`, `preflight` or `start` prints the `internal-error` document before it returns, `pump_child`'s prints none); `mcp` main-thread → no `process-exit` line (`obs::internal_error_exit_line` covers `Run` and `Cli` only), then exit 1 with nothing on stdout. Exit 21's `--json` document carries one cause word of `viola_core::UnreachableCause` in `detail`, written by the one `unreachable_document` (`src/cmd/client.rs`; `refuse_untrusted` and `src/cmd/plugin.rs` through it), and the type writes no log line of its own.
- The detail-line `backtrace` is raw, never-symbolised frames (`src/panic_frames.rs`: `0x<ip> <module path> base=0x<base> +0x<offset>`, up to 62) — symbolising cost 351 of a 403 ms hook run on chunk 2026-09-28-capability-ledger-and-viola-verify's retired Windows runner; never call `Backtrace::force_capture().to_string()` in a panic path.
- The hidden capture arm, `hook <event> --capture`, does no obs init and writes no line (a bounded panic-line exemption, obs-plan §10). `viola verify` runs `strict::check_home_tree` on the home, `ledger/`, `bin/` and `plugin/` before its `cli` log opens: a refused tree is exit 1 with the home pair, no step line, no log and no line; a refused `update_stamps` (`StampsError::StrictModes`, nothing read or written) prints the same pair and exits 1 through its own `process-exit`, which under a parsed `VIOLA_NAME` carries `detail:"strict-modes-failed"`; every other refusal past the tree check writes its own code there (`program-not-found`, `pinned-hash-mismatch`, `version-unreadable`, `unclean-fixture`, `untrusted-folder`), a failing row is no refusal and carries no code, and the fixture's `<file>` enters no code. `viola verify`'s trust-record write and removal emit no log line and no span (a refused symlinked, non-regular or foreign file included); the outcome rides only the stamps. The reading of the CLI's browser-tools prompt as a modal adds no log line, span, event or detail code of its own; verify's reading of it (its `absent` step word included) reaches only the ledger stamp and verify's stdout, whose one fixed line on a met prompt is the only record that the prompt stood at start. The readiness gate's standing-modal reading adds no log line, span field, event or detail code of its own: a modal label quoted above a ready input box lets the send proceed with nothing written, and a standing modal refuses with the existing detail `input-not-ready`. Each wrapped start of `viola run`, `viola revive` and `viola adopt` on a verified CLI opens no span for its trust step and writes exactly one INFO `trust-record` line to the run role file, its required `detail` one of a closed set of 16 start words (`trust-record` in the event enum of both the diag-line and the detail-line schema), and the word never refuses the start; no path, key or value of the claude config reaches any line, stamp or summary. A `viola verify` stopped by Ctrl-C or TERM (`SIGINT` / `SIGTERM`) starts no further spawn, kills and reaps the child it is running, closes every spawn pair it opened (a child of an interactive PTY run killed at the stop closes with `duration_ms` and a `child_exit_status`, the PTY pump's exit code; every other spawn pair it started closes with `child_exit_status` and `duration_ms` as well, and a stopped run writes only the pairs it started) and ends `process-exit{subject:"self", exit_code:1, detail:"interrupted"}` (a member of the `process-exit` `detail` enum `schemas/diag-line.v1.json` closes); `run`'s version gate observes no stop, save during the start's automatic verify: a SIGINT or SIGTERM there TERMs the verify child, KILLs it after a 30 s grace, writes the `auto-verify` `process-exit`, then re-raises the signal, the start ending with no `process-exit` of its own, no stamp, no snapshot and no session.
- `viola list` (span `cli.list`) runs its strict-modes scan before its log; a refused scan (exit 21) opens no log and writes no line (obs-plan §10 exemption 7; the founder's own answer, 2026-10-13, superseding the operator's). Under a `VIOLA_NAME` it writes the self pair, one `parse-rejected{parser:"state-entry"}` per nonzero scan count, one `state-recovered` per replayed snapshot (its `instance` the caller, its `scanned` the scanned instance dir's own last component when it parses as a `ViolaName`, absent otherwise — never a path or a literal `null`), the `config-json` `parse-rejected` lines (a retired `five_hour` or `seven_day` key counted as skipped under `unknown-keys`, nothing refused) and one `agents-probe` spawn pair around its `claude agents --json` read (plus one `parse-rejected{parser:"claude-agents-json"}` on an oversize or malformed answer) into `cli-<name>.ndjson`; with no name it opens no log. `viola mcp`'s `list` tool makes the same board read (through `list::board_document`) and writes its `agents-probe` pair, `state-recovered`, `parse-rejected{parser:"state-entry"}` and `config-json` `parse-rejected` lines into `mcp.ndjson`. `viola plugin install` runs its strict-modes tree check before its log; once it passes, under a parsed `VIOLA_NAME` it writes the self pair (`process-exit` exit 0, no detail) into `cli-<name>.ndjson`, and its span `cli.plugin_install` is no dispatch span: it is on `write_tree`, opened after the `cli` log opens, so the tree check and its refusal run outside it; no path in any line. `viola link` / `viola unlink` log as `cli` into the driven instance's `cli-<driven>.ndjson` (never the caller's `VIOLA_NAME`), their request inside spans `cli.link` / `cli.unlink`, once their instance check of it has passed. `viola open` logs as `cli` into the opened instance's `cli-<name>.ndjson`, its work inside the `cli.open` dispatch span; its refusals `terminal-not-found` and `not-live` are each one `process-exit{exit_code:1, detail}`, and a strict-modes refusal is exit 1 (under `--json` the `strict-modes-failed` document). `viola focus` logs as `cli` into the named instance's `cli-<name>.ndjson`: a `process-start` and a closed-detail `process-exit` inside the `cli.focus` dispatch span, which carries no fields. `viola up` logs as `cli` into the caller's `cli-<VIOLA_NAME>.ndjson` only under a parsed `VIOLA_NAME`, after its strict board scan, inside the `cli.up` dispatch span: its own `process-start` and `process-exit`, one `process-start{subject:"terminal"}` per spawn and `state-recovered`; a refused scan writes no line, and a home tree refused after the scan ends that log with `process-exit{exit_code:1, detail:"strict-modes-failed"}`; any other exit 1 of `viola up` carries `process-exit` detail `not-live` when an instance reads not-live, else no detail (no-session, cwd-missing, session-live or not-taken alone), and each of its refusals writes its own detail word. `viola switch` logs as `cli` into the named instance's `cli-<name>.ndjson`: a `process-start` and a `process-exit` inside the `cli.switch` dispatch span; a refusal ends `process-exit` with no detail, as `send`'s does.
- `viola adopt`'s start is no `cli` verb: it logs as process `run` into `run-<name>.ndjson` through run's own lines and spans, adding no event, field, subject or span of its own and one detail word only, `not-resumed`, on its own self `process-exit` exit 1. `viola revive`'s start arm logs as process `run` once its instance check has passed (`run-<name>.ndjson`, each preflight refusal — `already-live` (a live holder or a fresh replayed beat), `stale-heartbeat` (a stale holder), `no-session`, `session-live`, `cwd-missing` — one `process-exit{exit_code:1, detail}`; `viola adopt`'s preflight likewise ends one `process-exit{exit_code:1, detail:"session-live"}` with no child started, and a resumed child ending before its session starts gives one `process-exit{exit_code:1, detail:"not-resumed"}` after the child's `process-exit`; its `session-live` reading (and `viola adopt`'s start's, alike), skipped under revive's `--fork` and passing on a failed read, writes one `process-start` / `process-exit{subject:"agents-probe"}` pair there, plus one `parse-rejected{parser:"claude-agents-json"}` on an oversize or malformed answer); `viola revive --list` is role `cli` (chunk 2026-10-17-cli-machine-contract; the sixth exemption retired): after its strict-modes check passes and only under a parsed `VIOLA_NAME` it writes `process-start` / `process-exit` (`exit_code` 0 with no detail; `exit_code` 1 `detail:"no-session"` on an empty chain) into the caller's `cli-<VIOLA_NAME>.ndjson`, with no name no log, and its dispatch `Err` or panic reaches the `cli` catch site. A refused instance check on either `viola revive` arm (start or `--list`) or on `viola adopt`'s start, or `viola mcp`'s refused `viola_state::strict::check_path` of its home or `diagnostics/` (run before its `mcp` role file opens; exit 1 with nothing on stdout or stderr), or `viola plugin install`'s refused `check_path` of its home or a `marketplace/` tree dir (run before its `cli` role file opens; exit 21, the stderr pair or under `--json` the `instance-unreachable` document), or `viola link` / `viola unlink`'s refused `check_instance` of the driven instance (run before their `cli` role file opens; exit 21, the fixed instance-state pair or under `--json` the `instance-unreachable` document), opens no role file and writes no line (the seventh exemption). So does a refused strict-modes check on the hook event and dialog paths (exit 0, nothing printed), on `send`, `wait`, `last`, `answer`, `pause`, `release`, `viola focus` or `viola switch` (exit 21, the instance pair or under `--json` the `instance-unreachable` document), on `viola verify`'s home tree (exit 1, the home pair) or on the home tree of `viola run`, `viola revive`'s start arm or `viola adopt`'s start (exit 1, the home or the instance pair) (the eighth exemption). A refused peer euid (Unix) or a failed server check (the peer pid and start-time comparison, run on Linux, the one target) sends no frame and opens no `channel.request`: the eight CLI frame verbs (`send`, `wait`, `last`, `answer`, `pause`, `release`, `link`, `unlink`; `link` / `unlink` into the driven instance's `cli-<driven>.ndjson`) end `process-exit{subject:"self", exit_code:21, detail:"server-verify-failed", during:"connect"}` at WARN inside their dispatch span with no `channel-request` line; `viola hook` writes `hook-decision{detail:"server-verify-failed"}` at WARN (on a dialog hook `hook-invoked{corr:null}` first, then `decision_emitted:false`); MCP's frame tools return `instance-unreachable` with `detail` `server-verify-failed` and no line, as their refused `check_endpoint_dir` (made after `live_endpoint`) does with `detail` `socket-dir-refused` and no frame, and as the liveness pre-check's does with `without_endpoint`'s reading (`instance-dead` or `unwrapped-name`) and as their own refused `check_instance` of the home and the instance directory does (made before `live_endpoint`, `detail` `strict-modes-failed`, no frame), and as `send`, `wait`, `last` and `answer` do at the MCP call deadline, `MCP_CALL_DEADLINE` (`detail` `call-deadline`, a cause the MCP frame tools alone write and the CLI never does; the frame dropped); no pid, start time, path or endpoint in any line. A refused socket directory (`check_socket_dir`, the strict-modes read verdict) is none of these exemptions and writes under its own closed word `socket-dir-refused`, with no path, pid or uid in any line: `viola run`, `viola revive`'s start and `viola adopt`'s start (`socket_dir_ready`, no span, before any snapshot, child or `Server::bind`; a failed create, a lost race and a refused check read one code, and a `Server::bind` failure is not this refusal) one `process-exit{subject:"self", exit_code:1, detail:"socket-dir-refused"}`, under `viola revive --json` the same-shaped `socket-dir-refused` document; the nine CLI frame verbs one `process-exit{exit_code:21, detail:"socket-dir-refused", during:"connect"}` at WARN inside their dispatch span, no `channel-request` line and no frame; `viola hook` one `hook-decision{detail:"socket-dir-refused"}` at WARN inside `hook.handle` (on a dialog hook after `hook-invoked{corr:null}`, with `decision_emitted:false`), exit 0, empty streams and no frame.
- Run start's span chain is `run.start` (INTERNAL, root) › `state.snapshot_recover` › `run.collision_check` › `run.pin_copy` › `run.version_gate` › `channel.bind` › `state.snapshot_write` › `state.heartbeat_start` › `pty.spawn` (CLIENT), with no budget span; under `--origin`, `run.window` (its one field `outcome`, never an address, pid or workspace) follows the trust step, before `state.snapshot_write`; the window step's reads of the active workspace before and after its move, and its restore of the earlier active workspace when the move changed it, add no placement word, span field or log line of their own (a failed read or restore leaves the placement word as the move set it). The wrapper's stdin typed mark and its held scheduled-wakes count are in-memory state that open no span and write no line of their own, and carry no key and no prompt text. - No per-byte or per-line logging in hot loops (PTY pump); no line per heartbeat tick — transitions only.
